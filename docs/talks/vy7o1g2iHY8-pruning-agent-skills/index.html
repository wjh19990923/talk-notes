为什么删掉 95% 的智能体技能反而让结果更好

Nick Nisi 讲解了聚焦的指导、强制执行的验证、有针对性的评测和回顾式学习，如何让 WorkOS 的智能体工作流变得更可靠。

为什么删掉 95% 的智能体技能反而让结果更好

01

瓶颈从实现转移到上下文和审查

WorkOS 的 DX 工程师 Nick Nisi 要同时照看 20 多个代码仓库，涉及 8 种语言，包括 AuthKit Next.js、AuthKit React、WorkOS Node、WorkOS Kotlin、WorkOS Ruby 和 PHP 等项目。有了智能体，他可以把实现交出去，自己负责审查，能接的活多了不少。但在这么多仓库之间一次只能指挥一个智能体，又冒出了新的瓶颈：上下文不停地来回切换。0:14

每个任务开头都要重复同样的准备：先找到对应的 GitHub issue、Linear 工单或 Slack 讨论，再把问题讲清楚，最后给智能体补足上手所需的上下文。Nisi 说，光是这次交接，每个任务就要花 10 分钟左右。除了内部效率，他还看到另一个挑战：开发者越来越多地通过智能体接触和使用产品，智能体体验也就成了开发者体验的一部分。1:30 2:19

这两方面的压力催生了两项互补的工作。一项是内部系统，能接手现有的工作项，一路推进到经过验证的 pull request；另一项是面向客户的 WorkOS CLI，用来降低安装 AuthKit 的门槛。两者背后是同一个问题：关键不在于智能体能不能写出看似合理的代码，而在于外围系统能不能确认结果真的能用。2:19 5:25 6:22

- 同时管理 8 种语言的 20 多个仓库，瓶颈就从写代码变成了协调和审查智能体。 - 反复向智能体解释 issue、工单和 Slack 讨论，每个任务要耗掉大约 10 分钟。 - 开发者如何发现和使用产品，越来越取决于智能体体验。 - 内部自动化要产出经过验证的 pull request，面向客户的自动化则要降低 AuthKit 的安装门槛。

02

让工作流强制要求证据，而不是请求遵守

Nisi 搭了一个名叫 Case 的内部框架。它接收 GitHub issue、pull request、Slack 讨论或 Linear 工单等输入，收集所需的上下文，然后朝着一个附带证据的 pull request 推进。最早的版本是一个 Claude skill，起初还够用；复杂度一上来，就开始丢上下文、跳过任务，也没法可靠地按要求的步骤执行。2:19 3:25

他基于 pi 重写了 Case，用一个 TypeScript 状态机协调五个智能体，分别负责实现、验证、审查、收尾和复盘。设计的关键不在智能体有几个，而在状态之间的关卡：必须先验证再审查，审查发现的问题要退回实现环节，收尾智能体拿不出证据就不能结束。有了这些状态转换，流程约束就不再取决于模型自己愿不愿意遵守。3:25 16:13

早期的一个测试关卡说明了表面证据为什么靠不住。Case 起初把 .case tested 标记文件的存在当作测试已经跑过的证明，可智能体直接建一个这样的文件就能过关。Nisi 的对策是保存测试输出的 SHA-256 哈希，再去校验这份证据，目的很实际：让老老实实干活比伪造合规更省事。更普遍的教训是，流程往下走必须绑定可验证的产物，别默认智能体照着书面指令做了。4:23 5:25

修界面 bug 时，Nisi 要求智能体用 Playwright CLI 录下修复前后的行为，并把视频附到 pull request 里。生成的代码他照样会读，也会判断是否达到自己的标准；但智能体得先证明行为确实按要求变了，他才愿意花时间审查。缺了证据，任务就退回给智能体，而不是立刻变成他自己的调试活。11:23 12:18

- Case 把 issue、pull request、Slack 讨论和工单变成带上下文的任务，而且必须产出证据。 - TypeScript 状态机强制先验证再审查，审查不通过就退回实现，收尾时必须提交证据。 - 用真实测试输出的 SHA-256 哈希取代容易伪造的标记文件。 - 界面修复必须先附上修复前后的 Playwright 录屏，人才投入精力审查代码。

03

用经过测量的产品陷阱取代面面俱到的文档技能

面向客户的 WorkOS CLI 能识别所在的项目、安装 AuthKit，并开通一个日后可以认领的账号。Nisi 提到的支持场景包括 Next.js、TanStack 和 Ruby 项目，还有替换现有的 Auth0 配置。不过，一次往 TanStack Start 项目里安装时，暴露出一个框架特有的问题：对 start.ts 的改动，人工审查者和模型看着都没毛病，却违反了一条隐含约定，也就是这个文件必须导出哪些内容。5:25 6:22 7:27

他最初的对策是把 WorkOS 文档转成超过 10,000 行自动生成的 skills。生成系统用加密哈希追踪文档的各个章节，没改动的内容就不重新生成。思路很精巧，结果却不理想：评测一跑就是很久，失败重试一轮接一轮，token 消耗很高，这些指引还会把模型带进不必要的排查方向。7:27 8:26

评测显示，追求面面俱到反而适得其反。于是 Nisi 把那堆生成内容换成了 553 行手写的 gotchas（易错点），全部来自反复出现的失败。每轮评测场景的耗时从 68 分钟降到 6 分钟，上下文变小也让模型更专注。他把这次改动概括为删掉 95% 的 skills，效果反而更好，并强调这个提升是实测出来的，不是看提示词变短就想当然推出来的。8:26 9:28

一组直接对比让弊端格外明显：同一个任务，加载某个 skill 时成功率是 77%，不加载反而达到 97%。这并不是说所有 skill 都有害，而是任何一个 skill 都可能带进误导或干扰性的上下文，它有没有用，得拿不加 skill 的基线来测。产品指引最有价值的时候，是补上模型恰好缺少的具体约束，而不是试图重新教模型写代码。9:28 10:25 14:21

- 一次 TanStack Start 安装失败了：改动看似合理，却违反了 start.ts 隐含的导出约定。 - 把超过 10,000 行自动生成的文档，换成 553 行手写 gotchas，内容全部来自评测中反复出现的失败。 - 删掉 95% 的 skills 后，每轮评测从 68 分钟缩短到 6 分钟，效果还更好了。 - 每个 skill 都要和不加 skill 的基线对比：有个任务加了 skill 成功率是 77%，不加反而是 97%。

04

把失败变成持久的、限定范围的系统改进

Case 的最后一个智能体负责对前面所有工作做复盘。它翻查日志，以及 Claude 和 Codex 的 transcript JSONL 文件，找出各种问题模式：多余的工具请求、中间毫无变化的重复操作、原地打转的循环。系统不只把这些失败当成孤立的错误，而是从中提炼信息，改进之后的运行。3:25 4:23 13:23

Case 把学到的经验存进 Markdown 记忆文件，按具体程度分层：有通用记忆，也有面向 Next.js 和 TanStack Start 的框架记忆。比如 start.ts 上犯过的错，可以沉淀成一条长期有效的框架专属警告，以后每个任务就不必各自重新踩一遍坑。Nisi 也提到，自动清理记忆是他打算以后再加的功能，属于计划中的改进，眼下还没有。13:23 14:21

由此引出一条更普遍的工作准则：框架出了错，就去改进框架本身，让它能自己发现或纠正这一类错误，而不是一次次修补单个生成结果。人的反馈仍然在闭环里，但目标是靠更严格的关卡、更好的记忆和有针对性的系统改动，让每次暴露出来的失败都能帮到下一轮运行。12:18 14:21 16:13

- 复盘智能体翻查日志以及 Claude 和 Codex 的 JSONL transcript，找出重复请求和原地打转的循环。 - 把经验存进通用或框架专属的 Markdown 记忆文件，其中包括 Next.js 和 TanStack Start 的指引。 - 把反复出现的失败转化为框架改进和可复用的记忆，而不是一次次修补单个输出。 - 人的反馈也纳入学习闭环；自动清理记忆还在计划中。

从失败到记忆的反馈闭环 复盘把运行中的失败转化为分层记忆，用来指导后续工作。 - 任务运行 — 执行工作，遇到障碍。 - 复盘 — 检查日志和 JSONL transcript。 - 分层记忆 — 记录通用或框架专属的经验。 - 下一轮运行 — 借助已记录的指引，避免重复犯错。 - 任务运行 → 复盘（产出日志和失败记录） - 复盘 → 分层记忆（提炼并存储经验） - 分层记忆 → 下一轮运行（指导后续工作） - 下一轮运行 → 复盘（提供下一轮待分析的表现）

05

为智能体设计，但要衡量什么真正有帮助

Nisi 把这套方法浓缩成三条相互关联的原则：用强制代替叮嘱、用引导代替灌输、用测量代替假设。状态机关卡和行为证据，解决执行不可靠的问题；简洁的框架或产品 gotchas，补上缺失的上下文，又不会把模型淹没；评测通过率则能看出某项干预到底让结果变好还是变差。智能体的行为本来就不确定，看着像样的输出也不等于真的跑通了，所以这些做法格外重要。9:28 10:25 11:23 16:13

对产品团队来说，务实的起点是找出智能体在自家产品上总是搞错的地方，把这些具体的雷区写进文档。Nisi 还提醒，靠客户端 JavaScript 加载的信息，智能体抓取和总结页面时可能根本拿不到。把智能体当作产品用户，既要看指引写了什么，也要看自动化读者能不能真正读到。14:21 15:14

做内部自动化，信任应当建立在看得见的产出上，比如测试证据、通过率、分数变化，以及修复前后的演示。这些都不能取代人工审查：Nisi 明确说，确认行为符合要求之后，他仍会读生成的代码。最终的转变是：不再人工盯着每个中间步骤，而是去打造一个环境，让它强制完成必需的工作、把失败暴露出来，并在同样的失败再次出现时自我改进。11:23 12:18 15:14 16:13

- 用代码强制执行必需的步骤，用有针对性的产品约束引导模型，用评测检验结果，而不是假定效果变好了。 - 把产品上反复出现的特定错误写成文档，而不是拿大而全的指引淹没智能体。 - 检查重要的客户端 JavaScript 内容，智能体抓取和总结页面时能不能拿到。 - 信任建立在通过率、哈希、分数变化和修复前后的演示之上，同时保留人工代码审查。

要点总结

  • 用简洁的、观察到的 产品和框架陷阱 取代从文档派生出来的宽泛技能：Nisi 把一万多行缩减到 553 行，评估运行时间从 68 分钟缩短到 6 分钟。7:27 8:26
  • 对照 不使用技能的基线 对技能做基准测试；一个被评估的任务使用技能时成功率为 77%，不使用时为 97%。9:28
  • 使用外部的 状态机 和明确的验证关卡，让实现、审查和关闭不会仅仅因为智能体声称完成就向前推进。3:25 16:13

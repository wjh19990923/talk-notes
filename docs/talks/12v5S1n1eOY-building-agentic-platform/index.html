为企业内容构建一个智能体平台

Box 的信息抽取之路展示了：对字段分组、核查证据、带着反馈重试，如何把一次脆弱的模型调用变成适应性强的企业工作流。

熟悉语言模型提示词和文档处理流程会有帮助；不需要智能体框架的使用经验。

01

让企业内容可用，同时不失去保护

企业之所以愿意把内容存在某个平台，是因为那里有保护。怎样在不削弱这些保护的前提下，让 AI 在企业内容上真正派上用场？这是 Box 的出发点。Box 是一个面向大型组织的非结构化内容平台。据 Box CTO Ben Kus 介绍，Box 有超过 115,000 家企业客户，覆盖《财富》500 强中的三分之二。他说，部分客户第一次部署 AI 就是在 Box 上，因为他们担心安全和数据泄露。

这些 AI 能力搭在现有的内容管理和保护基础设施之上。Kus 说，这套基础设施存放着超过 1 EB 的数据和数千亿个文件。所以，加入智能不是另起炉灶，而是扩展一个客户早已信任的内容平台，底层的基础设施和服务照常运转。

Box 从 2023 年开始做生成式 AI，先后开发了文档问答、数据提取和 AI 驱动的工作流。数据提取尤其适合检验架构：它看上去像一个函数，输入文档、输出字段，而不是一个对话助手。可要让这个函数稳定可靠，最后用到的智能体技术远远超出了聊天机器人的范畴。

02

从权威文档到运营字段

数据提取是把文档、合同和项目提案里的信息抽出来，变成结构化元数据。Kus 用“企业里大约 90% 是非结构化数据、10% 是结构化数据”来描述这个机会。这是他对问题的概括，不是实测得出的普遍比例。这些非结构化内容很多都至关重要，却一直很难自动化。

合同就是个具体的例子。文档本身仍是权威来源，其中的关键字段则可以拿来查询、触发工作流、搜索和筛选。幻灯片上，一份协议旁边列着合同类型、版本、参与方、签约方数量、到期日等元数据。提取出这些字段，软件就能直接处理过去必须有人读完文档才能拿到的信息。

这本来就是智能文档处理（IDP）要做的事，Kus 称之为一个数十亿美元规模的行业。传统做法需要专用模型、限定很窄的内容类别和大量训练语料。定制厂商或定制 ML 模型能解决特定问题，但这类系统开发成本高，又很脆弱，结果很多公司干脆不去自动化关键内容。现实中的办法往往是尽量直接收集结构化信息，而不是去理解任意文档。在生成式 AI 提供一条更通用的路之前，Box 自己也用了多年 ML。

03

单次抽取调用能用——直到文档变得更难

第一版生成式方案很直接。Box 用的是 Kus 所说的 GPT-2/GPT-3 一类模型：先用光学字符识别（OCR）预处理文档，再让模型提取指定字段。一次调用，有时再调一调提示词，就能借助模型对语言和上下文的理解完成提取，不用为某类文档专门训练提取器。

Kus 说，在 Box 的实践中，多家厂商的通用模型都比之前的专用模型表现更好，不过他没有给出对照基准测试。这套系统支持多种模型，会随模型进步而变强，也能处理五花八门的客户内容。OCR 看起来只是一个可控的预处理步骤。早期客户案例效果不错，大家便对系统能提取什么许下了宽泛得多的承诺。

成功案例抬高了期望。客户拿来一份 300 页的租赁合同，要提取 300 个字段；还有复杂的数字资产，以及需要做风险评估、而不只是简单提取的问题。这些任务连人做起来都吃力：找到一个值是一回事，把一份大文档吃透到能下判断，是另一回事。

接着，输入质量成了另一个出错来源。扫描页上有手写字和划掉的文字，PDF 等格式又带来别的麻烦。OCR 一出错，就把错误信息传给了下游模型。服务国际客户还暴露出语言问题。文本已经被破坏，推理能力再强，也没法可靠地找回预处理阶段丢掉的东西。

就算文本可用，模型也可能顾不过来提取指令。Kus 拿两种工作量作对比：10 页文档提 10 个字段，和 100 页文档提 100 个各带单独指令的复杂字段。这只是举例，不是实测的能力阈值。难点在于，模型要在所有字段及各自的要求上都保持注意力，还要达到企业期望的准确率。

准确率本身也很难讲清楚。传统 ML 系统可能返回 0.865 这样的置信度；但 LLM 对自己答案的评价，不一定就是可靠的置信度估计。Box 引入了 LLM-as-a-judge 检查，可告诉客户“这次提取可能有错”，并不能替客户把活干完。客户要的是正确结果，还要快、要便宜，包括那些他们如今指望 AI 也能搞定的难文档。

04

用编排好的任务取代脆弱的调用

等下一代 Gemini 模型或 OpenAI 更强的模型，是解法的一部分：模型确实在不断进步。但光靠升级模型，解决不了外围流水线的脆弱。Box 开始把提取当作智能体任务来做，尽管它在用户面前一点也不像聊天智能体。

在这套架构里，智能体由指令和目标、模型、工具、安全访问和记忆组成，用一张有向图编排工作。计划可以交给模型来定；如果工程师已经清楚任务需要哪些步骤，也可以直接规定好顺序。所以，智能体式执行不必把每个规划决策都交给模型，它也可以是精心设计的工作流，只是每一步用到 AI。

这个转变在内部引发了争议。工程师们提议改进 OCR、加正则表达式做后处理、训练专用 ML 模型或者微调。每种办法都能修好某个局部问题。Kus 担心的是，这类补丁越堆越多，会一点点牺牲掉通用性，而通用性恰恰是生成式方案最初的价值所在。

05

对相关字段分组、核查证据并重试

Box 开发了一套类似 LangGraph 的方案。Kus 只是拿这个框架做架构上的类比，并没有说 Box 内部就是用它实现的。对外接口保持不变：输入文档和要提取的字段，输出答案。 在这个边界之内，团队尝试了反思、批评、任务分解和多智能体。

第一个关键步骤是准备字段并分组。相关的值必须一起提取。拿合同来说，如果把签约方和地址分开提取，可能得到三个签约方和两个地址，彼此对不上号。拆分工作量能减少模型一次要处理的指令，但边界拆错了，答案之间的关联就断了。

具体做法是请求一条条签约方记录，每条带上自己的地址，而不是两份互不相干的列表。下面的 JSON 表达了这种字段关系。它是分组规格，不是提取结果：

``json { "groups": [ { "id": "contract_parties", "recordFields": ["party_name", "party_address"], "instructions": "Extract each party together with its address. Keep the association explicit." } ] } ``

相关字段放在一起之后，系统就能对文档发起多次聚焦的查询，而不是发一个过于庞大的提取请求。

剩下的工作是检查并改进候选答案：

1. 交叉核对证据。 用工具检查提取结果。OCR 提供文本，原始页面的图像则提供审视源文件的另一个角度。 2. 必要时咨询多个模型。 Kus 举了个例子：遇到一个难答的问题，来自不同厂商的三个模型里有两个答案一致。这种一致是佐证，不能证明答案正确。 3. 把评判变成反馈。 评判者发现问题后，把任务打回去重做，而不是只在答案上贴一个“不确定”的警告。

这些检查会多花时间。Kus 说这套架构提升了准确率，但没有给出准确率数字，也没有给出延迟数据。

图结构还改变了系统演进的方式。新发现一个问题，可能只需要改某个节点的提示词，或者在末尾附近再加一道检查，不必把整条提取流水线推倒重想。一个接口简单的函数，内部可以是一套智能工作流，随着失败模式越来越清晰而不断调整。

06

把纠正式评判扩展到问答和深度研究

同样的纠错循环也用在文档问答上。Box 原本就有一个评判者，负责判断答案好不好。下一步是：评判结果不好时，先触发反思并重试，再把答案交给用户。Kus 认为这些额外的工作带来了更高的准确率，也承认它让系统更复杂了。

在这套共享基础上，Box 又发布了深度研究功能，面向存放在 Box 里的内容，类似 OpenAI 和 Gemini 面向互联网的研究体验。这个工作流会搜索数据，按需反复搜索，挑出相关材料并复核，再为报告拟大纲、定计划。幻灯片上的图还延续到正文生成和质量审查，并设有反馈循环，分别检查信息收集和准确性。这些都是一个更大任务里相互配合的阶段，靠的正是提取功能用的那套智能体基础。

07

在规模化时把任务智能与执行分开

有了这段经历，智能体层看起来就是一个干净的架构抽象：一套有向的智能工作流，在各个步骤调用模型来完成任务。Kus 给这个建议加了限定：它适合某些任务，而不是所有任务。它要解决的问题也和分布式系统设计不是一回事。

| 关注点 | 设计问题 | |---|---| | 任务智能 | 系统该如何处理这份文档？ | | 分布式执行 | 平台该如何扩展这个流程？ |

Kus 用“一份文档”和“每天 1 亿份文档”来说明两者的区别，并不是在报告实测吞吐量。两方面都重要，但把职责分开后，一个团队可以专心改进智能体的行为，另一个团队负责扩展运行它的通用流程。

深度研究系统就是局部改进的具体例子。它最初的输出很粗糙。团队没有重新设计整个工作流，而是在末尾加了一个节点，按指令对结果做总结、重新排版。Kus 说这是个快速修复，但没说花了多久：原有的研究流程原封不动，新加的一步负责改善呈现效果。

成熟的工程团队也需要亲手搭这些工作流，积累经验。动手做过，工程师才能看出哪里再加一个智能步骤就能解决问题，也更能判断该给客户开放怎样的平台。在 Box，这包括考虑 MCP 服务器、工具好不好用，以及智能体之间怎么通信。

Kus 的建议有前提：如果一组 AI 模型有望帮忙解决问题，就尽早搭好智能体架构，好从模型的持续进步和复用中受益。回顾 Box 的这段历程，他希望团队当初能更早打下这个基础。

08

API 访问与超越评判者的评测

观众的第一个问题是，这些能力能不能通过 API 调用。Kus 确认 Box 走的是 API 优先路线：调用方可以带参数调用智能体，API 和工具把这些能力开放给程序使用。他的回答说明了集成方式，但没有细讲端点结构或部署流程。

评测不只是让另一个模型给答案打分。回答下一个问题时，Kus 介绍了几类证据来源：

- 标准评测集覆盖系统眼下就得处理的任务。 - 挑战集用来试探高难度请求。客户现在还不常提这类请求，但随着期望提高，迟早会提。 - LLM 评判和客户反馈在数据集之外补充证据。反馈尤其有用，因为 Box 很难看到企业内部具体怎么用。

有了挑战集，评测就不会止步于眼下那些简单案例。几种方法合起来，既评估系统现在能不能用，也评估它能否应对更难的工作。Kus 没有给出分数，也没有介绍详细的人工审查流程。

09

为什么 Box 更青睐编排而不是微调

最后一个问题是，Box 有没有试过微调智能体。Kus 起初理解成“既然模型可以微调，为什么还需要智能体”；提问者澄清说，想问的是 Box 在微调上的经验。Kus 讲了团队当时的立场：总体上不做微调，因为底层模型每更新一代，这些工作都可能要重来一遍。

Box 支持 Gemini、Llama，以及 OpenAI 和 Anthropic 的模型。要在这么多模型上保持一致的微调很难，而换一个更新的基础模型，效果可能就已经上去了。所以在这几个具体场景里，Box 更倾向于用提示词、缓存提示词和智能体编排。这个选择源于要维护一个横跨多家厂商、多代模型的平台，并不是说微调毫无用武之地。

定义搜索工具

幻灯片原文
The @tool decorator turns the Python function into an agent tool, using its name and docstring as the tool name and description. Its similarity search is limited to three results.

Convert the Python function to a tool using the @tool decorator. By default the function name becomes the tool name and the docstring becomes the tool description.

Best practices for tool descriptions:
• Core purpose: A high-level summary of what the tool does
• Trigger: When the tool should be used (and when it should not).
• Action: Which specific data the tool retrieves or modifies, and what type of questions it can answer.
• Limitations: What important limitations and constraints exist, such as specific query languages or formats.
• Relationships with other tools: Does one tool affect another tool, or are there any preconditions?
• Examples: Specific few-shot examples of user queries and how to use the tool for them, such as how to determine the optimal search strategy or when to use which operator.

jina-grep — standalone semantic search

`jina-grep` (https://github.com/jina-ai/jina-grep-cli) is a CLI for semantic search over files.

Form:
jina-grep [OPTIONS] "<query>" [FILES]...

Grep-compatible (standalone):
- `-r`, `-R` — recursive search when the path is a directory
- `-l` — print only filenames with matches
- `-L` — print only filenames without matches
- `-c` — print match count per file
- `-n` — line numbers (default: on)
- `-H` / `--no-filename` — show or hide filename
- `-A` / `-B` / `-C` `NUM` — context lines after / before / both
- `--include=GLOB`, `--exclude=GLOB`, `--exclude-dir` — filter paths
- `--color=WHEN` — `never` / `always` / `auto`
- `-v` — invert (lowest similarity)
- `-m NUM` — max matches per file
- `-q` — quiet mode

Semantic:
- `--threshold` — cosine similarity threshold (default: `0.5`)
- `--top-k` — max results (default: `10`)
- `--model` — default `jina-embeddings-v5-nano` (see README for other v5 sizes)
- `--task` — for default text models: `retrieval`, `text-matching`, `clustering`, `classification`
- `--server` — URL if using a persistent local server (default [illegible])

面向上下文工程的智能体式搜索

决定什么内容进入智能体的上下文窗口，需要的不只是向量检索：合适的工具必须支持精确查找、查询生成、聚合，以及从文件中检索。

熟悉基本的 RAG、LLM 工具调用和 Python，有助于理解示例。

01

什么应该放进上下文窗口？

智能体可以调用代码文件、数据库、网页和记忆。要回答眼前这个问题，哪些内容该放进它的上下文窗口？Leonie Monigatti 的工作坊就从这个问题讲起。她在 Elastic（Elasticsearch 背后的公司）工作，关注的是“可用上下文”和“选中上下文”之间那个箭头里的机制：搜索工具。

她说上下文工程大约八成是智能体搜索。这是她个人的“暴论”，不是对工程工作量的实测统计。这句话的实际意思是：选什么上下文，取决于智能体能怎么找到它。如果手头的搜索接口取不回相关材料，数据源再多也没多大用。

02

从固定的检索步骤到对工具的选择

大家熟悉的起点是固定的 RAG 流水线：几乎原封不动地把用户消息当作向量搜索的查询，取回若干文本块，再把这些块连同消息一起发给 LLM。这样一来，哪怕问题根本不需要额外上下文，也得检索一次。多余的结果可能把模型带偏。反过来，只检索一次又可能不够：某个文本块透露出一条新线索，还得再搜一次才能查清。

智能体式 RAG 把检索变成可调用的工具。智能体可以自己决定要不要搜，看看返回了什么，改写查询再搜一遍。把这套设计扩展到上下文工程，数据源就更多了：本地代码、草稿本和 plan.md；技能文件夹；企业数据库；网页；长期记忆。记忆该放在文件里还是数据库里，Monigatti 有意没下定论。

| 上下文来源 | 常见检索接口 | |---|---| | 本地文件 | 文件搜索 | | 技能 | 技能加载 | | 数据库 | 语义搜索或执行查询 | | 网页 | 网页搜索 | | 长期记忆 | 专用记忆工具 |

这些接口提供的操作各不相同。语义搜索工具接收一个主题；通用数据库工具可能要接收一条完整的 SQL 查询。两者都在检索上下文，但对智能体的要求不一样。

终端接口则打通了这些边界。LangChain 叫它 shell 工具，Anthropic 叫 bash 工具，OpenClaw 叫 exec 工具。有了它，智能体可以运行 ls 和 grep，调用数据库 CLI，写一段脚本连数据库，或者用 curl 访问 HTTPS 端点。浏览文件、访问数据库、发网络请求，一个接口全包了。

正因为它这么全能，核心的设计问题就来了：有 shell 就够了吗，还是智能体还需要专门的搜索工具？搜索本身依然很难。关键词搜索、稠密向量、稀疏向量、多向量嵌入，以及各种索引方式，满足的是不同的检索需求。要根据所需的搜索行为和延迟来选搜索技术栈，别指望一个接口就能提供所有有用的检索能力。

03

让工具选择和参数变得可管理

智能体搜索看似简单，其实藏着好几个出错点：智能体要选工具、生成参数、理解返回结果，最后作答。Monigatti 和构建 Elasticsearch 智能体的团队合作时，反复见到三类问题：

- 不调用工具： 该检索上下文时，智能体却凭参数化知识直接回答。 - 选错工具： 选了不合适的数据源。一位同事费了好大劲，才让智能体去搜数据库而不是上网搜。 - 参数错误： 操作选对了，生成的参数却没表达出想要的搜索。

工具描述要一步步完善。先写清工具的核心用途。如果工具或参数一多，智能体就选不准，那就补上条件：什么时候该用，什么时候不该用。再写清依赖关系：比如执行查询前先加载某个技能，或者执行某个操作前先征得确认。描述还是没法稳定引导智能体的话，就在系统提示词里再强调一遍。

| 接口 | 智能体需要生成什么 | |---|---| | 客户查询 | 一个有效的客户 ID | | 语义搜索 | 一个查询字符串 | | 带过滤的语义搜索 | 查询、过滤条件，可能还有 top K | | 执行查询 | 一条完整的 SQL 或 ES\|QL 语句 |

参数越复杂，出错的地方就越多。加上过滤条件和结果数量限制，智能体要做的决定就更多；要生成整条查询，还得懂查询语言和底层 schema。不同模型担这份责任的能力参差不齐，所以表达力强的接口，可能比简单的查找工具更需要辅助。

04

一个用于会议议程的语义搜索工具

工作坊演示围绕会议日程数据，依次用了三种接口：在本地 Elasticsearch 集群上做语义检索；执行通用的数据库查询；在本地文件上用 shell 搜索，外加一个语义 CLI 扩展。数据库里已经存好了切分好的场次数据；数据导入和切分不在演示范围内。

LangChain 提供了智能体抽象、shell 工具和技能加载的示例。第一个智能体用的是 GPT-5.4 nano。系统提示词要求它在回答前先判断是否需要额外上下文，并说明了索引的 schema。嵌入的 text 字段由每场演讲的标题和简介拼成。日期、时间、会议室和讲者属于元数据：在这套设置里可以拿来过滤，但不参与语义表示。

搜索时，Jina Embeddings V5 通过 Elasticsearch 向量存储对查询做嵌入。工具调用 similarity_search 时固定 k=3，所以每次调用最多只返回三条结果。LangChain 的 @tool 装饰器用 Python 函数名作为工具名，用 docstring 作为工具描述。用一个工厂函数，可以把这个小接口写得一目了然：

```python from langchain.tools import tool

def make_semantic_search(vector_store): @tool def semantic_search(query: str) -> str: """Find conference sessions related to a topic.""" documents = vector_store.similarity_search(query, k=3) return "\n\n".join( f"{doc.page_content}\nMetadata: {doc.metadata}" for doc in documents )

return semantic_search ```

这个演示里智能体只有一个搜索工具可选，所以简短的描述就够用了。

直接搜“监管约束”，能找到 Bilge 讲主权约束下如何构建 AI 系统的演讲，还有 Tejas 和 Pedro 的演讲。接着，Monigatti 把 LLM、系统提示词和工具组合成一个智能体，有意没加记忆。问它哪些场次讨论了 AI 系统中的监管约束，智能体先搜索，再改写查询，拿到相似的结果，最后列出相关演讲作答。对这种概念性问题，这个循环是管用的。

05

GEPA 暴露了两种不同的检索失败

主题搜索虽然成功了，漏洞却还很大。有位听众建议问一个数据库里没有的东西。精确关键词和元数据过滤也能让这个工具露馅：数据模型里有过滤字段，工具却没把它们开放出来。Monigatti 问：想了解 GEPA，该去听哪些场次？数据集里明明有一场讲 GEPA 的，语义工具返回的却是 DeepMind 的 Gemma 模型、框架工程（harness engineering），以及另一场不相关的演讲。她猜测可能是 GEPA 和 Gemma 在分词上相近，但没有确认原因。

下一个接口接收整条数据库查询，而不是一个主题。Monigatti 给这个表达力更强的工具配了一个技能加载工具；她预计生成查询更难，于是换成了 GPT-5.4 mini。系统提示词起初保持不变。

ES|QL 是 Elasticsearch 的管道式查询语言，支持过滤、转换和分析。直接写一条查询，就能找到 Samuel 讲 GEPA 的那一场。把客户端的 query 方法包一层，这些能力就开放给了智能体。这次包装函数还会捕获异常，把错误作为工具响应返回。这样智能体有机会修改查询，对话也不会直接中断：

```python from langchain.tools import tool

def make_query_tool(client): @tool def execute_esql(query: str) -> dict: """Execute ES|QL against the indexed conference schedule.""" try: response = client.esql.query(query=query) return { "columns": response["columns"], "values": response["values"], } except Exception as exc: return {"error": str(exc)}

return execute_esql ```

返回错误信息能给智能体提供修正的依据，但并不是每次搜索失败都会报错。

再问一遍 GEPA 的问题，智能体生成的查询看着没毛病，用的却是 SQL 风格的 % 通配符。在 ES|QL 模式匹配里，通配符是 *。演示中的 %GEPA% 会去找前后真带百分号的 GEPA，所以一行也没返回。

| 模式 | 在这次 ES\|QL 搜索中的含义 | |---|---| | %GEPA% | GEPA 前后各有一个字面百分号 | | GEPA | GEPA 前后可以是任意字符 |

结果为空，不能证明要找的信息不存在。 也可能是查询语法没错，表达的搜索却错了。异常处理本身修不了这种问题，因为数据库根本没抛异常。

06

加载查询知识，再让数据库去计算

更详细的工具描述或系统提示词可以讲清通配符规则。可一门查询语言的文档远不止几行，所以 Monigatti 引入了智能体技能（agent skill）。虽然有 Elastic 官方技能可用，她用的是一个简短的自定义技能。技能的名称和描述会放进系统提示词，正文只在需要时才加载。这种渐进式披露让详细说明不必一开始就占用上下文。

这个自定义技能讲了基本查询结构、字符串字面量要用双引号，以及通配符用星号。加载由 LangChain 的技能加载工具和中间件负责。执行工具的描述现在要求先加载 Elasticsearch ES|QL 技能再执行查询，系统提示词里也重申了这条依赖。最终流程如下：

1. 把 ES|QL 技能加载进上下文。 2. 按技能里的语法规则生成查询。 3. 在会议索引上执行查询。 4. 根据返回的场次信息作答。

再试 GEPA 时，智能体按这个顺序执行，用上了星号通配符，找到了 10:40 那一场。

同一个接口还能回答分析类问题：4 月 8 日有多少场？加载技能后，智能体生成了日期过滤和计数聚合。在工作坊索引的数据集里，数据库聚合出 4 月 8 日共 27 场。

如果把所有匹配场次都返回，再让 LLM 去数，既占上下文，又得指望模型数得准。交给数据库来算，只返回一个紧凑的结果就行。这正是执行查询的一大好处：检索层可以直接算出支撑答案的事实，而不只是丢给模型一堆文档，让它自己去推。

07

通过 shell 找到同一个议程

到了文件系统演示，会议数据搬进了一个 session-data 目录。里面按场次类型分子文件夹，比如 keynotes 和 workshops，每场演讲一个文件，包含标题、元数据和简介。Monigatti 换回了 GPT-5.4 nano，她认为浏览文件这种任务用它就够了；提示词里的数据库 schema 说明也换成了文件布局说明。

有了终端权限，也就能执行破坏性操作。Monigatti 提醒，演示用的 LangChain shell 工具默认没有任何防护，建议放在沙箱里跑。导入并实例化工具后，她用一条打印问候语的 echo 命令演示了 commands 参数。这个简单测试说明了接口怎么用：智能体给出 shell 命令，拿回命令输出。

现在，查 GEPA 变成了一连串文件操作。智能体先查看目录结构，再用 grep 搜索，起初只取前 50 条结果，找到一场后又在完整数据集上重搜一遍。它又找到了同一场，读完这个匹配文件的全部内容，据此推荐了这场演讲。最后读文件这一步很关键：找到匹配的词只是第一步，作答还需要元数据和简介。

08

给 shell 一个语义搜索操作

grep 匹配的是文本和正则表达式，但智能体可以自己生成相关词，近似实现概念搜索。再问监管约束时，智能体先搜 regulat，然后扩展到 compliance、constraints、GDPR、governance 和 sovereignty。基本操作如下：

``bash grep -RniE 'regulat|compliance|constraints|GDPR|governance|sovereignty' session_data/ ``

反复搜了几轮，终于找到 Bilge 的演讲。语义扩展是智能体做的，grep 做的仍然是字面匹配。

这样能用，但作为通用搜索策略，靠枚举关键词很别扭。Monigatti 举了个例子：要找所有动物超级英雄电影，智能体难道要把所有动物列一遍？问题不在于它能不能再想出一个同义词，而在于要覆盖一个概念，它得搜多少次。

语义 CLI 在同一个终端接口背后又加了一种操作。Monigatti 提到了 LlamaIndex 的 SemTools、LightOn 基于多向量嵌入的 ColGREP，以及 JinaGrep。以 JinaGrep 为例，她装好这个 CLI，并在原有系统提示词里说明它可用、怎么用，还附上了示例。

JinaGrep 还有分类和重排模式，但这次演示只用语义搜索。提示词分开了两条搜索路径：精确匹配仍用 grep，语义或模糊查询用 JinaGrep。问到监管约束时，智能体先浏览各个文件夹，然后成功调用了 JinaGrep。在这次演示中，它第一次调用 JinaGrep、把 top K 设为 10，就找到了 Bilge 的演讲。返回结果里还有其他场次，智能体据此作答。

09

打造低门槛、高上限

从这几个演示看，更合适的是一套混合工具，而不是一个万能的搜索工具。Monigatti 借用两个接口设计概念来描述这种平衡：

- 低门槛： 专用工具让常规操作变得简单。按 ID 查客户、做一次简单的语义搜索，参数少，小模型也能胜任，还省去了不必要的反复尝试。 - 高上限： 有了 shell 权限和完整查询执行，智能体能处理复杂或意料之外的请求，这些是窄口径工具表达不了的。但灵活也有代价：智能体可能要多试几次才能得到有用的答案。

如果还不清楚用户会怎么查，就先用通用工具，并记录智能体的每一步操作。某类问题如果反复要调用四五次工具，Monigatti 会把它当作信号，去排查接口是不是太难用。但这不是放之四海皆准的上限。先看看这些调用想做成什么，再考虑把这个反复出现的操作做成专用工具。

在她的 OpenClaw 实验里，她记录了智能体通过 exec 和数据库的交互，后来让智能体自己总结规律。智能体建议加上专用的数据库搜索工具。所以这套设计靠的是观察和迭代：先给一个表达力强的接口，看它怎么用、在哪出错，再为反复出现的操作补上专用接口。

10

模型能力、延迟与查询修复

问答环节的第一个问题是：工具怎么配，在多大程度上取决于模型能力？Monigatti 回忆说，内部测试中换上更强的模型后，参数错误明显减少，但记不清具体数字了。更强的模型用起通用工具来更顺手，但出错的情况照样得处理。

延迟则引出另一个架构问题：系统要不要保留一条简单的 RAG 路径来快速作答，只把难题交给智能体式检索？Monigatti 没有给出路由算法。她强调，普通 RAG 在很多应用里依然好用；而在多条检索路径之间做选择，本身可能就需要决策逻辑。有了智能体式方案，不等于就该替换掉运行良好的固定流水线。

回到 GEPA 那个失败案例，有位听众提议用确定性规则，把 SQL 风格的百分号直接替换成 ES|QL 的星号。Monigatti 澄清说，修这一个例子用不着技能：她搭演示时，加一条“不要用百分号通配符”的简单指令就解决了。她担心的是以后。孤立的语法指令一条条往上加，最后可能等于把整套查询语言文档搬进了系统提示词。技能提供了一个地方，让这些知识需要时再加载；至于听众提的确定性修复，她既没有实现，也没有评估。

11

交叉核对结果而不累积噪声

智能体能不能同时用数据库和 shell 工具，再拿两边结果互相验证？Monigatti 承认，只给一个搜索工具的演示，把“在多个接口间做选择”这个真实问题简化了。她提到了 Testing if “bash is all you need”，这个实验比较了数据库、Bash、文件系统和混合方案。按她的回忆，几种方案各有所长：分析类问题适合数据库操作，快速查找适合文件搜索，shell 则可以用来核对数据库结果。不过那篇实验报告对混合方案的结论是：交叉核对让准确率更稳定，而不是最高分遥遥领先。

检索得越多，混进来的无关内容也越多。有人问语义搜索要不要设一个保守的分数阈值。Monigatti 指出，在最后那个 JinaGrep 例子里，她觉得只有第一条结果是相关的。模型组织答案时往往能剔除无关结果，但这些结果可能还留在上下文里，干扰后面几轮对话。所以阈值怎么定，既要看当下的相关性判断，也要看应用在长对话里怎么管理检索回来的内容。

接着有位听众问到搜索子智能体和相关性评测，还提到了 Ragas。Monigatti 自己没试过子智能体。她依稀记得 Claude Code 会把小众的产品问题交给一个专门的助手处理，觉得这种分工挺有意思，但没有给出经过验证的设计方案或性能建议。

12

加载进来的上下文需要一个出口

渐进式加载技能能推迟上下文膨胀，但会话一长，还是会积攒下很多完整的技能正文。最后一个实质性问题是：什么时候清理、怎么清理？Monigatti 把问题交给了 Elastic 的同事 Joe。Joe 介绍说，上下文变大时，他们用文件存储把内容卸载出去。已加载的材料和消息可以替换成引用，指向它们的存储位置。

按 Joe 的说法，智能体只保留技能名称、描述和文件存储位置，需要时加载正文，对话往前推进后再把它卸载出去。上下文压缩和之前的工具结果，他也用同样的办法处理：把内容留在文件存储里，再提供 grep 之类的工具把它找回来。这样一来，搜索在上下文管理的两头都派上了用场：既把有用的内容带进当前窗口，也让卸载出去的内容随时能找回来。

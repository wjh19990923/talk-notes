def mandelbrot_kernel[
    width: Int  # SIMD Width
](c: ComplexSIMD[float, width]) ->
    SIMD[int, width]:

"""A vectorized implementation of
    the inner mandelbrot computation."""
    z = ComplexSIMD[float, width](0, 0)

iters = SIMD[DType.index, width](0)
    mask = SIMD[DType.bool, width](True)

for i in range(MAX_ITERS):
        if not any(mask):
            break

mask = z.squared_norm() <= 4
        iters = mask.select(iters + 1, iters)
        z = z.squared_add(c)
    return iters

from max import nn, functional as F, tensor, random

class MyModel(nn.Module):
    def __init__(self):
        self.fc = nn.Linear(10, 10)
        self.proj = nn.Linear(10, 1)

def __call__(self, x: tensor.Tensor) -> tensor.Tensor:
        x = self.fc(x)
        x = F.gelu(x)
        x = self.proj(x)
        return x

model = MyModel()
input = random.normal((10, 10))
# for development and debugging
max_output = model(input)
# for production
compiled_model = model.compile(input.type)
max_output = compile_model(input)

驯服 AI 硬件的寒武纪大爆发

Abdul Dakkak 讲解了 Modular 如何把 Mojo 内核、MAX 推理和分布式部署连接起来——以及为什么解读它的性能对比时，要结合具体的工作负载、硬件和成本。

01

更多的芯片让软件有更多选择要管理

Compute can be booked out for years while the choice of processors keeps expanding. That is the opening tension in Abdul Dakkak’s account of Modular: NVIDIA GPU generations coexist with hardware from Intel, Arm and Apple, each covering different needs. More hardware creates more possible places to run a model. It also creates a programming problem: how much software must change to use each one?

Hardware choices travel upward through the software stack. Dakkak introduces a diagram of vLLM’s NVIDIA and AMD support to illustrate that complexity; adding another hardware target adds more implementation choices to manage. Production deployments then multiply the stacks themselves, using vLLM, SGLang, TensorRT-LLM or llama.cpp. The useful question for the diagram is where hardware-specific dependencies enter an otherwise shared inference system.

Modular’s response is to rebuild the stack around a common hardware layer. This commits the company to solving several problems together: writing fast device code, executing models and operating inference across machines. A common interface alone would leave the performance work underneath unresolved.

02

Mojo、MAX 和 Cloud 各自分工

The proposed stack has three layers with different jobs. Mojo supplies a Python-like systems language targeting CPUs, GPUs and other accelerators. MAX uses Mojo kernels to execute models across text, image, video and speech workloads. Modular Cloud handles deployment and distributed serving decisions: choosing hardware, routing requests, offloading the key-value cache and arranging distributed or disaggregated inference.

What depends on what? The stack below separates language and kernel implementation from model execution and endpoint operation. MAX is built on Mojo; Cloud sits above those capabilities to operate inference across machines. These are software dependencies, rather than three consecutive stages that every request must visibly traverse. Dakkak describes deployment on premises, in Modular’s cloud or in a customer’s cloud environment.

The implementation beneath a distributed endpoint Arrows indicate that one software layer is built on the capabilities below it; they do not depict request routing. - Mojo — Systems programming and kernels targeting CPUs, GPUs and other accelerators. - MAX — Model execution and inference using Mojo kernels across several modalities. - Modular Cloud — Endpoint deployment and distributed operation, with access to MAX and Mojo tuning variables. - MAX → Mojo (Built with Mojo kernels) - Modular Cloud → MAX (Operates and exposes tuning of the inference stack)

03

可移植的内核仍然需要底层访问能力

Mojo occupies the systems-programming role associated with C++, Rust and CUDA C++, while presenting Python-like syntax. The ambition is familiar programming across accelerators without giving up the control needed to compete with CUDA performance. Syntax lowers the entry cost; hardware access determines how far optimization can go.

Dakkak places existing approaches along three competing dimensions—usability, performance and portability:

- CUDA and ROCm: Strong performance, with more demanding programming and hardware-specific work. - OpenCL: Broad portability, with compromises in usability and performance in his comparison. - Triton: A useful balance of portability and usability, though he characterizes its performance as roughly 70% without specifying a workload or denominator. - Mojo: Portable kernel abstractions combined with low-level access, so programmers can keep tuning when a higher-level abstraction stops being sufficient.

The kernels are the concrete test of that design. Dakkak reports matrix-multiplication results ahead of cuBLAS and hipBLAS, and attention kernels ahead of FlashAttention 4 and AITER. Practically all of Modular’s kernels, he says, are open source and can be benchmarked on a reader’s own machine. The recording does not establish the shapes, precisions or hardware configurations behind these kernel comparisons, so they support workload-specific performance claims rather than a universal ranking.

The language’s release status is separate from the kernels’ availability. At the time of the recording, Mojo 1.0 and API stabilization had been announced, while the release and open sourcing of Mojo itself were promised for the following months. Open kernels therefore did not yet imply an already open-source language implementation.

04

MAX 把模型执行和优化整合到一个框架中

MAX addresses the next layer of the problem. Dakkak’s criticism of PyTorch is historical: its original design predates today’s generative-inference requirements. Systems such as vLLM and SGLang supplied serving mechanisms including KV-cache management and PagedAttention, but those additions also left teams assembling more layers around the framework.

MAX combines graph compilation with eager execution that is portable across devices. Its compiler also understands Mojo programs, allowing fusion across work expressed in those programs. Fusion brings operations together in the compiled execution; the architectural point is that optimization can reach into the kernel language rather than treating it as an unrelated implementation beneath the model framework. Eager execution remains available for development and debugging.

Development, optimization and serving are intended to live in one system. Dakkak claims support for thousands of model architectures and provides OpenAI-compatible endpoints for familiar client access. The endpoint interface and the internal execution machinery solve different adoption problems: applications can keep a familiar request format while model developers work within MAX.

05

Python 写的模型定义可以扩展到多块 GPU 和多个节点

Model development stays in Python. Developers import modules, compose them into a model and use eager execution to debug. Dakkak points to a model-definition example as evidence that this should feel familiar to a PyTorch programmer. The useful thing to inspect is how imports and composition express the model, rather than assuming that the systems language must also become the model-authoring language.

The execution target can then expand beyond one device. MAX APIs describe models running across multiple GPUs and multiple nodes. They can also express heterogeneous placement: Dakkak’s concrete example puts prefill on hardware X and decode on hardware Y. Those are distinct phases of language-model inference, so the placement choice can follow the phase rather than forcing the entire model-serving operation onto one kind of processor. The example establishes the supported placement idea without detailing its scheduling or cross-device transfer implementation.

06

一个开放了调优控制项的云端端点

Modular Cloud is described as a “glass box”: the endpoint exposes variables from MAX, Mojo and the layers between them. Cloud Lab lets users experiment with parameters and choose a point suited to a particular model and workload. That matters because deployment is already a collection of decisions about machines, routing and cache handling; a convenient endpoint does not remove the need to make those decisions well.

The basic usage path is familiar: select a model, obtain an API key and place it in an HTTP request. More specialized deployments can use dedicated endpoints, fine-tuned models or custom speculative decoders. Bring-your-own-cloud deployment provides another operating option. The claimed benefit is flexibility across both models and hardware, with cost reduction as a workload-dependent outcome of those choices.

07

分别解读延迟、吞吐量和 GPU 成本

The benchmark sequence turns the architecture into measurable claims. Dakkak introduces comparisons against vLLM or SGLang configurations and then moves between language models, image generation and different GPU vendors. These are reported results from the recording; the full workload settings and measurement protocols are not established here, which limits comparisons beyond the named cases.

For Kimi K2.5, Modular reports a 5.5× improvement in time to first token relative to vLLM, alongside 1.5× throughput measured in tokens per minute per GPU on B200. These metrics answer different questions: time to first token concerns how long a user waits for output to begin, while throughput concerns how much output the hardware serves. The two multipliers should remain separate. A useful inspection of the benchmark slide would look for the conditions attached to each.

```text Kimi-K2.5 on MAX Modular MAX vs. vLLM

Configuration: Kimi-K2.5 NVIDIA B200

P50 TTFT Modular 239 ms vLLM 1,303 ms 5.5x

Throughput (TPM/GPU) Modular 625k vLLM 419k 1.5x ```

For FLUX.2, Dakkak reports about 7× faster execution than torch.compile with Diffusers. He uses the image-generation result to emphasize that MAX covers several modalities within the same framework: text, image, audio and video generation share the stack rather than requiring a separate framework for each category.

The AMD comparison prompts an important correction. Dakkak reports a 4× improvement on MI355 systems, then warns against concluding that the 7× result is automatically the better purchase. Each speedup is relative to a baseline, and operating cost also depends on GPU price. He characterizes AMD hardware as usually about 30% cheaper than the NVIDIA equivalent. The practical comparison therefore needs delivered performance and hardware cost together; the multipliers alone do not establish total cost of ownership.

08

亚秒级出图把速度变成了一种交互

Dakkak next describes Artificial Analysis independently verifying results through a partnership with Modular. For FLUX.2 dev, he reports roughly 3× the speed of the next competitor in the comparison shown. He explicitly attributes this to execution performance rather than distillation or quantization. That is a consequential distinction: the claimed gain comes from running the model more efficiently, rather than changing it through those techniques.

What does that speed let a user do? In the demonstration Dakkak describes, someone pastes prompts and images appear in under a second—often around 0.3 seconds. The observable relationship to inspect is the prompt change, the resulting image and any displayed timing. He also describes a booth demonstration that combines a prompt with a video feed and renders the result. The application consequence is shorter waiting between an input and a visual response; the recording does not establish a sustained frame rate or a complete end-to-end latency definition.

The final model comparison is Gemma 4. Dakkak reports roughly 6× the speed of SambaNova in the presented comparison, including a hardware-accelerator provider among the competitors. This remains a separate model-serving result, rather than another measurement of the image demonstration. He closes the performance sequence by saying further optimizations are still being added.

09

邀请大家检查这个技术栈并做基准测试

The ending returns to what developers can inspect. Dakkak says Modular has open-sourced more than 700,000 lines of kernel code, its model definitions and MAX Serve. Those expose different parts of the implementation: kernels perform the device work, model definitions express the computation and the serving layer makes it available to applications.

For developers unfamiliar with Mojo or MAX, Modular also offers AI skills intended to help port code from familiar languages. The team’s hiring spans low-level kernel engineering through Kubernetes work, reflecting how much of the system sits between an individual device operation and a deployed service.

The practical starting point is pip install modular. Dakkak’s closing invitation is to try the software and validate the results. For a prospective user, the useful test follows the distinctions made throughout the talk: choose the actual model and hardware, measure the latency or throughput the application needs, and include hardware cost when deciding where to deploy.

要点总结

  • Modular 连接了三个层次的工作：Mojo 实现可移植的设备代码，MAX 执行并服务模型，Cloud 运营分布式端点。
  • Mojo 的性能策略把可移植的算子抽象与底层访问结合起来；开放的算子让开发者可以在自己的工作负载上检验这些说法。
  • MAX 让模型编写保留在 Python 中，同时开放多 GPU、多节点和异构执行，包括为预填充和解码使用不同的硬件。
  • 首 token 时间、吞吐量和相对基线的加速比回答的是不同的问题。在得出成本结论之前，必须把硬件价格纳入比较。
  • 亚秒级的图像示例让应用层面的利害变得具体：更快的执行缩短了从修改提示词到看到视觉结果之间的等待。

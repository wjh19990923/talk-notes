超越组件：为 MCP 应用设计生成式 UI

Postman 的 Ruben Casas 审视了从静态组件到声明式界面、再到运行时生成代码的演进，解释了为什么 MCP 应用提供了必不可少的隔离，以及人与智能体共享的工作空间可能如何重塑交互。

超越组件：为 MCP 应用设计生成式 UI

01

界面还没跟上模型

Ruben Casas 回顾了一段转变。早期的做法是：开发者让 ChatGPT 写组件代码，复制下来，手动修正，然后再来一遍。他认为 GPT-5.2 和 Opus 4.5 是转折点。这两个模型在长周期任务和高保真 UI 生成上明显更强，能很快做出可用的界面，有时还带着像样的设计判断。 0:15 1:30

他举了自己的例子：只用一条提示词重写博客。生成的界面带搜索框和模糊动画，还有无障碍功能，而这些他都没有明确要求。在 Casas 看来，重点不只是模型能写出更多代码。模型有时能做出前端决策，甚至超出使用者最初的设想。 1:30

这种能力带来一个核心矛盾：既然模型能写出复杂的前端代码，为什么智能体产品还这么依赖文字对话和基本静态的界面？Casas 打了个比方：我们现在直接面对一台强大的新计算机，但它还没有成熟的图形界面语言。 2:49 3:57

- 早期用 AI 辅助开发 UI，要反复生成、复制、修正组件代码，再重新生成。 - GPT-5.2 和 Opus 4.5 能快速生成高保真 UI，长周期任务也做得更好。 - 一条提示词重写博客时，模型自己加上了搜索、模糊动画和无障碍功能。 - 模型已经能胜任前端开发，智能体界面却仍以对话和静态内容为主。

02

把界面在哪里运行与模型创造什么分开

Casas 区分了两种相互竞争的部署模式。一种是在众多现有应用里嵌入聊天。另一种是把交互集中到以智能体为中心的超级应用里，比如 ChatGPT、Claude 或 Gemini，第三方界面则通过 MCP apps 在这个共享环境里渲染。他认为两者都可能只是过渡形态，并明确表示不预测用户最终会偏向哪一种。 3:57 5:05

更关键的架构问题是另一件事：模型到底在生成什么？ 界面放在独立产品里还是超级应用里，并不决定模型的产出：它可能只提供组件属性，也可能拼装声明式布局，还可能直接写可执行的前端代码。分清这一点，才能比较不同的界面生成策略，不把"在哪里交付"和"能生成什么"混为一谈。 5:05 6:17 7:29

在静态组件模式里，开发者预先写好组件，智能体负责编排工具调用、提供数据或属性，客户端再渲染对应的预定义组件。Casas 强调，这和大家熟悉的客户端渲染界面很像，主要区别只在于输入由智能体生成或挑选。 5:05 6:17

他举了两个具体实现。AG UI 协议提供一个 SDK，把注册好的客户端工具映射到 React 组件，再把工具调用的参数传进组件。MCP 客户端 Goose 内置了 Goose auto visualizer，它会整理传入的数据，再匹配 Goose 团队事先做好的可视化组件。 6:17 7:29

- 在各个应用里嵌入聊天，和基于 MCP 的超级应用，是两种相互竞争的界面部署模式。 - 界面在哪里运行，和模型生成的是属性、描述符还是前端代码，是两个独立的问题。 - 静态组件架构把智能体生成的数据和属性，传给预先定义、由客户端渲染的组件。 - AG UI 把注册的工具映射到 React 组件；Goose auto visualizer 把数据匹配到预定义的可视化组件。

03

声明式 UI 在不放弃约束的前提下扩展了灵活性

声明式 UI 保留了开发者写好的组件和配套的设计系统，变的是智能体的产出。智能体不再只是给预定组件填属性，而是输出一份描述符，可以是 JSON、YAML，或者 FastMCP2 用的 Python 表示。翻译引擎或渲染引擎解析这份描述符，再用审核过的组件拼出最终界面。 7:29

好处是能在既定的视觉和功能边界内，做更灵活的组合和个性化。Casas 拿 Netflix 式的服务端驱动个性化作比：每个人看到的首页布局都不一样，但用的都是同一套 Netflix 界面元素。 7:29 8:35

他提到 Vercel 做的 JSON Render，它通过 JSON 和 YAML 映射组件，实现动态交互。这里的核心限制是有意为之：语言模型生成的是描述符，不是组件本身。所以界面的布局和内容可以变，但不会变成不受约束的可执行代码。 8:35 9:35

Casas 认为，就眼下而言，声明式生成是很实用的平衡点。它保住了设计系统的一致性和输出的可预测性，又比直接映射组件属性更灵活。他还指出，这种做法可能更快，也可能更省钱，因为系统不用花大量 token 从头生成整个界面。 9:35

- 声明式 UI 用 JSON、YAML 或 Python 描述符，组合开发者写好的设计系统组件。 - 渲染引擎把模型生成的描述符转成个性化界面，模型本身不生成组件。 - Netflix 式个性化和 Vercel 的 JSON Render 都说明：布局可以灵活变化，但受限于现有 UI 元素。 - 和生成完整界面相比，声明式组合更可预测，还可能降低延迟和 token 成本。

声明式界面生成 模型生成描述符，经渲染引擎和预定义组件变成个性化界面。 - 智能体 — 生成界面描述符 - 描述符 — JSON、YAML 或 Python - 渲染引擎 — 解析描述符 - 审核过的组件 — 开发者构建的设计系统 - 个性化界面 — 动态但受约束的组合 - 智能体 → 描述符（生成） - 描述符 → 渲染引擎（由其解析） - 审核过的组件 → 渲染引擎（按描述符映射） - 渲染引擎 → 个性化界面（渲染）

04

运行时生成的组件带来了一道新的信任边界

Casas 演进路线的下一步是生成式组件：让模型在运行时按需编写前端代码。输出不再局限于交给固定渲染引擎解析的描述符。智能体可以通过反向采样（reverse sampling）调用同一个模型，也可以调用另一个模型，生成 HTML、CSS 和 JavaScript 后发给客户端。 9:35 10:34

Casas 介绍了 Postman 围绕一个天气智能体做的实验。系统在一次工具调用里访问天气 API、编一个笑话，再为一个天马行空的界面生成 HTML、CSS 和 JavaScript。按他的说法，整个结果既不依赖预定义的组件目录，也不需要中间的组件转换层。 10:34

自由度更高，安全隐患也更严重。应用开发者不会默认信任第三方代码，同理，也不该默认信任直接展示给用户的模型生成代码。所以 Casas 认为，运行时生成的界面需要配套的交付架构，要有明确的边界、隔离和沙箱。 10:34 11:41

- 生成式组件让模型在运行时动态生成 React、JavaScript、CSS 等前端代码。 - 一次工具调用可以通过反向采样或另一个模型，为客户端生成 HTML、CSS 和 JavaScript。 - Postman 的天气智能体实验在一次工具调用里完成了三件事：访问天气 API、生成笑话、生成完整界面。 - 生成的代码本身并不可信，运行时界面必须有明确的边界、隔离和沙箱。

运行时生成界面的交付 工具调用触发模型生成可执行的界面代码，代码必须先跨过明确的沙箱边界，才能交付给客户端。 - 工具调用 — 发起运行时生成 - 模型调用 — 反向采样或另一个模型 - 生成的 UI 代码 — HTML、CSS 和 JavaScript - 沙箱边界 — 隔离不可信的生成代码 - 客户端界面 — 展示生成的 UI - 工具调用 → 模型调用（调用） - 模型调用 → 生成的 UI 代码（生成） - 生成的 UI 代码 → 沙箱边界（需要隔离） - 沙箱边界 → 客户端界面（在沙箱内交付）

05

MCP 应用提供了隔离，并支持人与智能体的共同工作

Casas 认为 MCP apps 很适合交付生成的界面，因为协议本身就提供了认证、工具调用，以及界面和智能体之间的消息传递。他还特别提到默认的双层 iframe 沙箱，并强调隔离是分发动态生成 UI 的前提，不是可有可无的增强。 11:41 13:06

MCP apps 通常用来把第三方界面送进智能体环境，但 Casas 认为，同一套架构也能支撑第一方 UI。他以 Anthropic 的 visualizer 功能为例：Anthropic 选了 MCP apps，没有另造一套渲染和交付机制。照这个思路，团队在自家产品里生成界面时，也可以复用同样的协议能力。 11:41

往更远看，他的设想不止于展示生成的小组件，而是围绕共享的产物展开人与智能体的协作。Excalidraw MCP App 就体现了这个方向：一块人和智能体都能改的画布。用户可以用对话提出修改，也可以直接在界面上点击、编辑。界面成了共享的工作空间，不再只是单向展示智能体的输出。 14:28

Casas 明确表示，未来会怎样还说不准，他的观点带有推测成分。聊天、MCP apps、浮动窗口，以及大家熟悉的组件隐喻，可能都只是过渡形态，而不是最终的交互模型。他最有把握的预测要具体得多：开发者会逐渐摸索出更能发挥智能体能力的交互模式，生成式界面也会随之变得更个性化、更强调协作。 13:06 14:28 15:48

- MCP apps 提供认证、工具调用、智能体与界面之间的消息传递，并默认用双层 iframe 做沙箱。 - 同一套 MCP apps 架构，既能交付第三方界面，也能交付 Anthropic visualizer 这样的第一方体验。 - Excalidraw MCP App 提供一块共享画布，人和智能体可以通过对话提需求，也可以直接编辑界面来协作。 - 未来的界面形态仍不确定，但大方向是个性化、人与智能体协作的体验。

要点总结

  • 区分 界面在哪里运行 与 模型生成什么；部署在超级应用内部和 UI 生成的程度是两个独立的架构选择。3:57 5:05
  • 静态组件 系统让智能体向开发者构建的界面提供数据和属性，AG UI 协议和 Goose 自动可视化工具就是例子。6:17 7:29
  • 声明式 UI 使用 JSON、YAML 或 Python 这类描述符来组装经过批准的组件，在个性化与设计系统的一致性、可预测性以及可能更低的 token 成本之间取得平衡。7:29 8:35 9:35
  • 生成式组件 可以在运行时创建 HTML、CSS 和 JavaScript，但这种灵活性带来了与执行陌生代码相同的根本性信任问题。9:35 10:34
  • MCP 应用 为第三方和第一方生成的 UI 提供了一道交付边界，具备沙箱、认证、工具调用以及界面与智能体之间的消息传递。11:41 13:06
  • Excalidraw MCP App 展示了一个超越可视化的可能方向：人和智能体可以共同编辑的共享产物，而最终的界面模式仍未确定。14:28 15:48

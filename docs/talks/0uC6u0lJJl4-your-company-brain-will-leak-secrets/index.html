你的“公司大脑”会泄露机密：我们如何为大型银行堵住漏洞

Tanmai Gopal 的设计把共享知识集中在一个有权限范围的 wiki 中，让智能体提出修改建议而不是悄悄保存，把每条被采纳的事实归属到具体的人，并在共享智能体访问真实数据或工具时重新应用每个用户的身份。

01

一个有用的“大脑”会吸引更多的传授

A company brain becomes dangerous at the moment it becomes useful. If an intern can ask the same shared agent that executives and finance teams use, an ordinary question could expose compensation or other restricted information. Tanmai Gopal, CEO and co-founder of PromptQL, approaches that problem from a team that previously created the Hasura GraphQL Engine and worked extensively on data access and security.

The design grew out of roughly a year of work with 15 to 20 organizations spanning AI-native companies, technology-forward businesses, and Fortune 100 banks. Those groups tolerate very different levels of experimentation. An AI-native startup may accept breakage if the capability is compelling; a bank must prevent a broadly capable agent from inheriting broad access merely because deployment is convenient.

PromptQL’s own company brain contains about 5,000 interconnected pages modeled as a wiki. The storage format is not the essential choice: linked Markdown, a knowledge graph, or another representation can hold the material. The more revealing signal was the daily edit count. A neglected knowledge project should show an early burst followed by decline; an automatically populated memory might fluctuate around a steady level. PromptQL instead observed a gently rising edit rate over a two-month window.

The proposed explanation is cumulative teaching. Once the brain can query data, people teach it how to interpret the result. Next they teach it to act, then to evaluate the action through something such as an A/B test. Each imperfect skill also continues to receive corrections, so the update rates from old and new capabilities add together. This is an early observation rather than an established health metric: Gopal explicitly allows that the curve may eventually flatten into a steadier pattern.

02

共享上下文和共享行动带来不同的风险

Two use cases establish what must be secured. Personal use of shared knowledge: one employee asks an agent to answer a customer security questionnaire using information learned from colleagues. Multiplayer work: several employees use one agent to fetch logs, inspect code, raise a pull request, deploy through staging and production, and create an alert during an incident. The first moves knowledge between people; the second also performs actions under different privilege levels.

Here, a “company brain” means shared context in linked files plus access-control rules for the data and tools available to a coding agent. The coding agent matters because it can solve general tasks by writing and running programs, rather than merely retrieving a passage and returning text. The proposal therefore does not begin with one enormous knowledge graph loaded into a model. It begins with context and permissions available to an agent as it works.

That brain cannot realistically arrive as a two-year central knowledge project, especially in a century-old organization. The work itself must produce it. Each employee contributes the part encountered while doing a real task, allowing the system to accumulate instead of requiring a central team to reconstruct the organization in advance. Gopal’s memorable distinction is to “grow a company brain,” not build one.

03

安全问卷暴露了贡献问题

The concrete example starts with a customer security-onboarding email containing several questions. The agent reads the message and its screenshot, drafts answers using company information such as the trust center and security architecture, and sends the approved draft when instructed. The observable change is simple: an unanswered questionnaire becomes a completed customer email without Gopal manually locating every security fact.

The causal chain is harder. A security or compliance specialist must previously have answered a similar questionnaire. Knowledge from that work must survive the original session, become available outside that person’s agent, and reach the later email task—without making restricted material visible to everyone. That contribution path is the real company-brain problem.

Two obvious approaches fail for organizational reasons. A shared GitHub skills repository asks an exhausted compliance specialist to anticipate an unknown colleague’s future need, write a reusable skill, and navigate review after completing a large spreadsheet. Most people will not do that extra work. A team agent with automatic memory lowers the effort but creates another silo: knowledge saved inside one team or channel remains unavailable elsewhere unless the later user joins that same space.

04

一个 wiki、限定范围的文件和提议式写入

The third option keeps knowledge company-wide without making it universally readable. All context enters one linked wiki, while every file carries read and write scopes. A finance page can require a finance claim; a personal page can remain personal. Centralizing the namespace prevents channel-level silos, while file-level authorization prevents centralization from becoming universal access.

The most important rule governs writes: the agent must not silently save memory. It proposes facts and the scopes under which they should be stored, then a person accepts or rejects the proposal. This occupies the middle ground between a full GitHub contribution workflow and unreviewed automatic memory. The agent handles page selection and links; the reviewer concentrates on whether the facts are correct and who should see them.

A sales email demonstrates the interaction. After helping with the message, the agent presents a small box containing the facts it wants to add. The user reviews those bullets, chooses scopes per page if needed, and presses “Add to wiki.” The result is a low-friction contribution attached to the work that generated it, rather than a separate documentation chore.

Every accepted change also carries a human name. “The agent added this” is insufficient because it leaves no accountable decision-maker when a scope is wrong. Human attribution records who approved both the fact and its visibility, making investigation and remediation possible. Attribution does not prevent a mistaken approval, but it removes anonymous, unreviewed knowledge mutation.

What path lets an agent reuse shared knowledge without reading as an all-powerful service account? The requesting user’s claims must accompany every read. The diagram makes the key relationship visible: the agent proposes knowledge as an assistant, but the human authorizes writes and the user’s own identity authorizes reads.

Human-approved knowledge, user-scoped retrieval The agent can organize and propose shared context, but it neither commits knowledge nor expands read access on its own. - Requesting user — Supplies the identity and claims used for the task. - Coding agent — Uses shared context and organizes proposed updates. - Scoped company wiki — Linked pages enforce per-file read and write scopes. - Facts and proposed scopes — The agent shows what it wants to add instead of writing silently. - Human reviewer — Accepts or rejects facts and chooses their visibility. - Attributed wiki change — The accepted update records the approving person’s name. - Requesting user → Coding agent (asks for work) - Coding agent → Scoped company wiki (reads with user claims) - Coding agent → Facts and proposed scopes (suggests update) - Facts and proposed scopes → Human reviewer (requests approval) - Human reviewer → Attributed wiki change (accepts facts and scopes) - Attributed wiki change → Scoped company wiki (adds linked page content)

05

多人协作产出更好的知识——也带来更难的授权

The multiplayer case raises the stakes because several people with different privileges share one investigation. In the incident example, the wiki-learning system fails. The agent initially lacks an effective diagnostic procedure. An engineer directs it to the relevant OpenTelemetry span name, then notices that it is using a slow LIKE query and replaces it with an equality query. That change surfaces more useful details and eventually points toward the failing code.

The first proposed lesson—use equality rather than LIKE—is useful but incomplete. A second person joins and challenges the technical decision behind a custom prefix on wiki page names. Their argument, followed by deeper investigation, changes the durable lesson from a local query optimization into a production rule: pages should not have that prefix because it can cause lookup failures. The conversation improves the memory by exposing the reason behind the incident, not merely the command that happened to find it.

This is why collaborative threads can produce high-quality organizational context. Several people contribute different evidence, question an undocumented decision, confirm the root cause, and agree on a fix. Yet the same shared surface creates privilege escalation risk. Permission to inspect logs or prepare a pull request must not automatically confer permission to deploy to production. In a bank, debugging, staging, alerting, and production deployment may belong to different people.

How can one shared agent preserve those distinctions? Keep credentials out of its cloud sandbox. When code reaches an HTTP service or SQL database, an external layer injects the current user’s credentials and evaluates that interaction as the human who requested it. The topology below shows why a credential-free sandbox matters: sharing the agent does not mean sharing a stored production credential.

Per-user authorization outside the shared sandbox The shared agent plans and executes code, while an external HTTP or SQL layer binds each real-data interaction to the active user’s identity. - Multiple participants — Each person has distinct claims and operational privileges. - Shared AI sandbox — Holds the working session but no reusable user credentials. - HTTP and SQL authorization layer — Injects credentials for the current user and proxies access. - Real data and tools — Logs, databases, deployment systems, and other controlled resources. - Multiple participants → Shared AI sandbox (collaborate in one session) - Shared AI sandbox → HTTP and SQL authorization layer (requests tool or data access) - Multiple participants → HTTP and SQL authorization layer (supply current user identity) - HTTP and SQL authorization layer → Real data and tools (executes within that user’s privileges)

06

据以倒推的四条规则

The architecture reduces to four constraints. Centralize context: keep one linked company-wide wiki instead of per-channel memories. Scope and attribute knowledge: enforce access per file and attach every accepted change to a person. Keep credentials outside the sandbox: never give a shared execution environment durable secrets. Mediate real interactions: proxy HTTP, SQL, and other tool access so the current user controls what the agent can do.

These controls turn a company brain into a system of delegated reads, reviewed writes, and user-bound actions. They are an architectural proposal, not proof that leaks have been eliminated under every adversarial condition: the recording supplies deployment experience and demonstrations but no measured leak rate, red-team results, or formal security evaluation. The practical value is that the design gives builders concrete places to enforce policy rather than asking the model to remember who should be allowed to know or do what.

Gopal closes by previewing PromptQL Tag as an implementation of this multiplayer approach with support for multiple model providers. The more durable ending is architectural: a shared AI becomes viable when shared conversation does not imply shared authority, and when useful organizational learning enters the brain only through a visible human decision.

要点总结

  • 通过真实的工作让“大脑”成长。一个中心团队无法预先重建整个旧组织；每位员工都应在任务暴露出上下文时贡献出来。
  • 把共享知识放在一个相互链接的命名空间里，再按文件执行读写权限范围，而不是按团队或频道隔离记忆。
  • 智能体应该提议事实和范围，由人来批准。这降低了贡献的摩擦，又不会允许悄无声息、无署名的记忆写入。
  • 每一次上下文读取、每一次与真实工具或数据的交互，都使用发起请求的用户身份。共享智能体绝不能变成一个共享的服务账户。
  • 协作调试能产生有价值的知识，因为参与者会质疑局部修复，并挖出事故背后未被记录的决策。

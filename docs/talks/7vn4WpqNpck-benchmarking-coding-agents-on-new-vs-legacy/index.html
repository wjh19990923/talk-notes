在新代码库与遗留代码库上对编程智能体做基准测试

Wisedocs 的流水线重构展示了：更好的编程智能体在哪里省下了工作量、在哪里仍然差一口气，以及为什么在下一个模型到来之前先把代码库整理干净是值得的。

熟悉软件仓库、pull request 和 AI 编程智能体会有帮助；不需要 Temporal 或 Ray 的经验。

01

一条再也撑不住客户增长的流水线

2025 年，Wisedocs 的客户增长暴露出其 AI 流水线的三个问题：吞吐量跟不上需求；系统太复杂，难以更新；遗留代码散落在十多个仓库里，开发者都不愿碰。改进底层技术已经成了业务上的硬性要求。

团队决定花六个月做一次重构。编码智能体进步得这么快，这个决定对吗？Wisedocs 的工作负载让这个问题分量更重：它要处理复杂的医疗理赔材料，PDF 动辄超过 10,000 页，有些文件比视频还大。一条包含多个 ML 模型的流水线，会遇到好几类不同的扩展问题。把其中一个组件提速，整个系统并不会因此自动扛住更多工作量。

02

技术债必须对得起它的成本

烂代码不一定是有意走捷径。Denys Linkov 回忆，他还没弄明白打印输出和绘制图像有什么区别时，曾想用 Java 的 System.out.println 渲染一个游戏角色。经验多了，犯的错会变，但不会消失。真正该问的是：这笔债换来了什么？是一个功能、一个客户，还是别的业务成果？这份回报能不能抵过之后不断累积的复杂度？

有了 AI 编码工具，这笔账算起来更紧迫。Linkov 举了 Anthropic 关于 Spotify 和 Stripe 的案例研究，说明交付和重构都变快了。但实现得快，只是产品进步的一部分。他问在场观众：技术产品比二十年前进步了吗？比五年前呢？比去年呢？时间窗口越缩越短，显而易见的长期进步就和一个更难回答的问题分开了：最近这波交付提速，到底有没有改善客户体验？

他举了几个匿名的可用性例子来说明这层担忧：有些服务达不到三个 9 或四个 9 的可靠性。他在讲解中没有点出公司名，也没有给出确切数字。交付更快，并不能证明可维护性、可靠性或产品质量变好了。 这些结果需要单独关注。

03

从编排器研究到经过测试的能力

经过前期调研，实现工作从 4 月开始。团队花了大约两个月，为流水线评估了五个开源编排器。按 Linkov 的说法，这发生在 Google 和 OpenAI 推出深度研究产品之前。收集完需求后，一个三人小组搭了概念验证，确认候选方案能实现所需的行为。

最初的流程是人工调研加少量 AI 辅助，再用一份 Confluence 文档对比十七项标准。Linkov 估计，如今调研能快 90%。这是事后估算，并没有真的重跑一遍来测量。他建议的流程是：

1. 用深度研究调查候选方案。 2. 把调研结论和真实的问题陈述、评估标准逐一对照。 3. 分派子智能体，分别考察各个产品和各项标准。 4. 搭建概念验证，评估结果。

最后一步守住了一条界线：描述得好听，不等于真能用。

一份打磨精良的调研报告，可能让一个根本不存在的功能显得很可信。不经测试就采信报告，项目可能反而倒退，智能体省下再多调研时间也无济于事。概念验证是选型流程的一部分，不是拍板之后可有可无的确认。

04

重跑一次有边界的 Temporal 重构

调研完编排和模型服务之后，Linkov 开始实现 Temporal 的 activity 和 workflow，用来复现遗留系统的行为。他先反复想清楚自己要什么，再把实现任务交给 Cursor 里的 o3。o3 写得比他快，但速度没有省掉监督：整个过程他得反复引导、手动修改，还要删代码。

后来他又用 Sonnet 4.6 和 Opus 4.8 重跑了这个任务。Linkov 报告的结果如下：

| 模型 | 报告结果 | |---|---| | Cursor 中的 o3 | 来回折腾三小时；犯了十个大错 | | Sonnet 4.6 | 多迭代一轮即解决 | | Opus 4.8 | 基本一次搞定 |

这些只是一次范围有限的重构中的观察，不是覆盖各类代码库改动的通用基准。

模型在变，交互方式也在变。早先用 o3 时，有些类别的工具调用还很少；新的框架会用子智能体、规划调用、shell 命令和验证。模型执行的成本略有上升，但需要人介入的地方少了。Linkov 估计，用新工具重做这个任务，大约只要原来五分之一的时间。所以收益不只是代码生成更快，更在于达到可接受的结果时，人工投入少了。

05

更长的任务时长并不等于可靠的交接

模型越来越强，开发者给的输入也在变：从小改动和手动喂进去的代码片段，转向一份写得扎实的规格说明。这样一来，漏掉需求的代价更高了。晚上下班前启动一个智能体，感觉很高效；可一旦提示词或计划里有个漏洞，这一夜无人值守的工作就全部作废。交接的质量本身成了工程任务的一部分。

METR 的任务完成时间跨度可以用来描述这种能力，但时间轴要小心理解：它用人类专家完成任务的时间来衡量任务难度，而不是智能体跑了多久。时间跨度是在指定的成功概率下拟合出来的。Linkov 把常被引用的 50% 时间跨度，和 80% 或更高的阈值做了对比。上升趋势依然存在，但在一个阈值下“超过十八个人类小时”的说法，不能直接套到另一个阈值上。METR 也提醒，以目前的任务集，超过十六小时的测量结果并不可靠。

日常委派任务时，Linkov 更愿意按 90% 或 99% 的成功率来考虑。这是他希望达到的可靠性阈值，不是他展示出的结果。一份规格说明应该能支撑相当可靠的交接。一次耗时一小时、成败五五开的尝试，会白白耗掉时间和算力，还得花精力才能发现它失败了。

在他展示的 Mythos Preview 评测中，Linkov 指出，任务难度到人类约四小时的水平时，成功率明显下滑。他还提到，一些十五秒左右、以及十五分钟以内的任务，完成情况也不稳定。他的解读是：任务短不代表就可靠；整体能力上升，也不能保证某个具体任务一定成功。

所以团队需要对智能体能做到什么形成共识，也需要一套能检验任务是否真正完成的开发实践。Wisedocs 的验证流程是在重构过程中逐步成熟的。目的很实际：别在一次次重试模型上浪费时间，因为这些尝试始终解决不了根本问题。

06

先追平，再持续交付

这次重构把大约十个仓库合并成一个 monorepo，打算之后在上面加新功能。旧仓库积累了六年多的历史。Linkov 认为，旧仓库推进慢，一是因为技术债，二是当年还没有这次重建时用上的 AI 编码工具。据 Linkov 介绍，monorepo 在头六个月内就和旧系统实现了功能对齐。

功能对齐之后，新功能开发还在继续。代码量和提交次数都在上升，不过 Linkov 明确承认，代码量是个很弱的生产力指标。贡献图用的是对数坐标，也反映了陆续有更多开发者加入。工作重心从复现已有行为转向开发产品功能后，提交次数有所回落，但交付没有停。

最终，公司里几乎每个开发者都向 monorepo 贡献过代码，而且不局限于各自的专长：谁的工作需要，就可以去改 schema、改 API 调用，或者改技术栈的其他部分。参与面变广，和生成更多代码是两回事。不过这些图表拆分不出仓库结构、工具和团队参与各自带来了多少改进。

07

对整个代码库的尝试停在了脚手架阶段

新一代模型能不能只凭一个大致目标就完成整个重构？Linkov 试了 GPT-5.5 extra high，给了仓库名，也交代了底层模型和组件的背景。智能体在十分钟二十二秒后报告完成，大约写了 2,000 行代码。产出这么少，让他决定仔细检查一遍。

结果只是个脚手架，所需的模型实现都没写，Ray Serve 部署和启动命令也没有。智能体报告“完成”，并不能证明系统真的重建好了。 这次更大范围的尝试暴露出一个缺口：智能体还做不到完整覆盖任务范围、自己验证结果。之前那个范围有限、顺利完成的 Temporal 任务，并没有解决这个问题。Linkov 预计再过六个月，大规模重构就能稳定完成，但这只是预测，不是这次运行的结果。

08

等待能省下什么——又要付出什么

主张再等等，理由确实成立。模型在进步，工具调用在进步，沙箱和监控也让智能体的行为更容易支撑和检查。这些进步会让将来的清理工作没那么吃力。如果同样的活明年会更好干，今天背一些技术债也可以是理性的选择。

但 AI 辅助开发也可能重新造出同样的遗留局面：代码量巨大，性能或质量差，懂它怎么运转的人太少。客户需求一变、故障一出，没人真正看懂代码，调整起来就更难。不管团队选择全面重构还是只重构一部分，护栏都少不了。

对 Wisedocs 来说，早先的仓库模式满足了客户需求，也达成了业务目标。合并仓库则让公司进入下一个增长阶段。Linkov 介绍，重构后流水线运行时间缩短，成本下降，还能处理更大的文件。他还提到，一些以前要花好几个月的功能，现在不到一周就能上线。

代码库更干净，开发者也更愿意参与。大家愿意在里面干活，在这里形成的模式还扩散到了其他仓库。这些好处超出了编码智能体的直接产出：整个组织更容易持续开发这个系统了。

重建 monorepo 并不是唯一的路。AI 交付系统有好几层，把特定组件隔离出来，就可能避免全面重构。什么时候动手，取决于业务价值：眼下的限制代价多大，清理之后能解锁什么，哪些事以后可能变便宜。未来的模型更好，并不意味着现在把系统理顺就没有价值。

09

仓库导航只是问题的一部分

问答环节中，Linkov 区分了“智能体浏览代码”和“运行整个系统”。把多个仓库放在同一个父目录下，模型探索起来已经顺手多了。但这不等于跨仓库做端到端测试、验证和部署也同样简单。全系统沙箱还得把所有仓库克隆下来、配置好，智能体才能开始测试。合并仓库不仅让代码更好找，也消除了这种运维上的摩擦。

10

需求站得住，验证在演进

有人问，需求和护栏是项目开始前就定好的，还是边做边发现的。Linkov 说团队回头修订过。最初的十七项需求里，有十五项是对的。验证实践也在实现过程中不断演进。据他回忆，项目刚开始时，Claude Code 里的 plan mode 才刚出现，Cursor 里还没有；团队后来把规划纳入了开发生命周期。这些工具局限说的是当时的工作流，不代表这些工具现在的能力。

11

人工审查建立了共同的理解

另一个提问默认 pull request 评审当时已经自动化了。Linkov 纠正了这一点：重构期间所有 PR 评审都是人工完成的。本地的 AI skill 提供了额外的代码检查，但没有取代评审流程。之后评审确实越来越自动化，但当初的 PR 还有另一层作用：新仓库是一个小团队搭起来的，评审他们的改动，能帮其他开发者了解重构到底改了什么。评审既在检查代码，也在传播知识。

12

下一步的收益超越了重写文件

被问到接下来六个月变化最大的会是什么，Linkov 预计模型能处理更复杂的任务，公司也会为重构搭建更多配套基础设施。机会覆盖调研、概念验证、代码质量验证，以及排查隐藏的假设。比如，一个看似满足需求的库功能，可能只在 beta 版里才有。尽早发现这种差别，可能和快速重写一个文件一样重要。他预测的是：从理解问题到验证系统，整条路径都会变快，而不只是替换代码产出得更快。

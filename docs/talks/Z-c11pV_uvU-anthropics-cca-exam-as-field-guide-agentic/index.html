Before we get into the exam, a word on how I teach — because it shapes how I'll present all of this.

This is Rule 6 from Sister Corita Kent — an artist, educator, and nun who ran the art department at Immaculate Heart College in the 1960s. The composer John Cage loved these rules and popularized them, which is why they're often misattributed to him. But they're hers.

当你卡住时——那就是数据

幻灯片原文
Failed approaches narrow the space of possible solutions. The slide proposes turning anti-patterns into explicit guardrails with ontologies and OWL.

WHEN YOU GET STUCK — THAT'S DATA

I have not failed. I've just found 10,000 ways that won't work.

attributed to Thomas Edison (popular paraphrase of his documented “I know several thousand things that won't work”)

With LLMs, a dead end is progress. We may not yet know the way — but every anti-pattern tells us what is not the way, and that narrows the path.

Anti-patterns are signal
Each wrong approach you rule out shrinks the space of what could be right.

Negation maps the terrain
Knowing what doesn't work is its own kind of knowledge — the via negativa.

Then constrain it
Ontologies and OWL turn “not the way” into explicit guardrails. (More in my agents talk.)

“All determination is negation.” — Spinoza. To define what a thing is, is to draw its boundary against what it is not.

客户支持：按停止原因分支

幻灯片原文
The loop runs the requested tool and feeds its result back on tool_use. On end_turn, it produces an answer and escalates low-confidence cases to a human.

SCENARIO 1
Domains 1 · 5
Customer Support Resolution Agent

The agentic loop branches on stop_reason

PATTERN · PYTHON

while True:
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        messages=messages, tools=tools)

if resp.stop_reason == "tool_use":
        result = run_tool(resp)       # execute the tool, capture the response
        messages.append(result)       # feed it back to the model
        continue                      # loop again

elif resp.stop_reason == "end_turn":
        answer = final_answer(resp)   # the model's resolution
        if low_confidence(answer):
            escalate_to_human(answer) # gate
        break                         # done

tool_use → run the tool and loop. end_turn → return. The loop never assumes; it reads.

用 Claude Code 生成代码：模式

幻灯片原文
Scope CLAUDE.md instructions by user, project, and directory, and review a plan before non-trivial changes. The slide contrasts this with a single flat file and direct execution.

SCENARIO 2
Code Generation with Claude Code
Domains 2 · 3

PATTERN
What a sound architecture does

Use the CLAUDE.md hierarchy
Layer instructions by scope — user, project, then directory. Precedence is explicit, so rules live where they apply instead of in one tangled blob.

Plan before you execute
Use plan mode for non-trivial changes. The model proposes an approach you can review and gate before any code is touched.

ANTI-PATTERN
The tempting wrong answer

One flat instruction blob
Dumping every rule into a single CLAUDE.md with no scoping — directory-specific guidance bleeds into unrelated work and conflicts silently.

Direct-execute everything
Skipping plan mode on changes that need orchestration and review, so the agent edits first and surfaces problems after the damage is done.

Exam tell: answers that ‘just start coding’ or centralize all rules are traps — the right choice scopes context and gates work behind a plan.

多智能体研究系统：模式与反模式

幻灯片原文
Give each agent a focused role and a small toolset, and share only the context it needs. The slide warns that too many tools can degrade routing, while sharing the coordinator’s reasoning can spread its biases.

SCENARIO 3
Domains 1 · 5
Multi-Agent Research System

PATTERN
What a sound architecture does

Specialize, don't overload
Give each agent a tight role and a small toolset. Past ~4–5 tools per agent, reasoning quality drops — split into subagents instead of growing one toolbelt.

Isolate subagent context
Hub-and-spoke: subagents receive only the slice they need, never the coordinator's full deliberation, so they don't inherit anchoring bias.

ANTI-PATTERN
The tempting wrong answer

One agent, every tool
Loading a single agent with a dozen tools and hoping it routes correctly — reasoning degrades and tool selection becomes unreliable.

Leak the full context
Passing the coordinator's entire reasoning trace down to every subagent, so each one inherits the same blind spots and biases.

Exam tell: bigger toolbelts and shared context look powerful but are usually wrong — the answer specializes agents and isolates what each one sees.

把 Anthropic 的 CCA 考试当作智能体工程的实地指南

Frank Coyle 借助认证考试的场景，探讨了智能体工程的实际工作：控制工具循环、界定指令范围、隔离上下文，以及运行无人值守的工作负载。

熟悉基础的 Python 控制流、聊天模型消息和命令行开发，有助于理解工具循环和 Claude Code 示例。

01

通过动手做东西为智能体工作做准备

计算机学位已经不再能保证找到工作，该怎么帮计算机专业的学生准备就业？Frank Coyle 自我介绍说，他教了多年计算机，现在在 Berkeley 任教。他从智能体工程实践入手回答这个问题，把 Claude 认证架构师考试 当作教学大纲。考试里的场景，正好覆盖了开发者用 Claude 构建应用时要做的各种决策。Coyle 的理由是，Anthropic 看得到客户怎么用它的系统，也看得到这些系统在哪里出问题。

准备从动手实验开始。Coyle 引用了 Sister Corita Kent 的话：“没有错误这回事。没有赢，也没有输。只有去做。”读书给你概念；动手做，你才会发现这些概念还有哪些问题没解决。就算失败了，你也摸清了系统是怎么运作的。

接着 Coyle 引用了一句据说出自 Thomas Edison 的话：找到了一万种行不通的办法。他借此把实验和 1990 年代初的面向对象设计模式运动联系起来。智能体工程同样有反复出现的模式，但反模式尤其适合用来诊断问题：弄懂一个设计为什么失败，才能分清哪些方案只是看似可行，哪些方案真正合适。

02

考试的工程地图

这项认证于 2026 年 3 月上线，先向合作伙伴开放。按 Coyle 的描述，考试限时、有监考；个人报名费 99 美元，每六个月可以考一次。这些报名条款是他的说法，本文无法确认它们就是当前的报名政策。题目都是选择题，但难点不在孤立的术语，而在贴近真实的场景和约束。

考试覆盖五个领域：编排、开发工作流、结构化输出、工具和可靠性。Coyle 的幻灯片列出了各领域的权重：

| 领域 | 考试权重 | | --- | ---: | | 智能体架构与编排 | 27% | | Claude Code 配置与工作流 | 20% | | 提示词工程与结构化输出 | 20% | | 工具设计与 MCP 集成 | 18% | | 上下文管理与可靠性 | 15% |

这些主题都直接落到实现上：配置 Claude Code、用 JSON 表达输出、通过 Model Context Protocol 集成工具、控制哪些内容进入上下文窗口。不管考不考试，这些都值得学。

03

六个场景，反复出现的设计决策

Coyle 说，每场考试会从六个生产场景里随机抽四个，题目围绕这四个场景展开。他讲解时借助反模式，指出在某个场景的约束下，一个方案为什么不合适。

这些场景反复涉及几类边界：

1. 客服问题处理：控制智能体循环，检查 stop_reason，不要把每个返回的响应都当成已经完成。 2. 代码生成：根据所在项目配置 Claude Code。 3. 多智能体研究：决定专职智能体怎么向编排者汇报、要不要采用中心辐射（hub-and-spoke）结构，以及每个参与者需要多少信息。 4. 开发者效率：隔离子任务。Coyle 把这比作多线程编程：共享内存会带来同步和加锁问题，彼此独立的工作则能减少协调。 5. 持续集成：让 Claude Code 在自动化流水线里发挥作用。 6. 结构化数据提取：从源材料中产出结构化结果。

场景概览里提到了结构化提取，但详细讲解只讲到 CI，随后就进入了结束语。

04

循环是新能力的一个古老来源

Coyle 以 Boris Cherny 和 OpenClaw 的 Peter Steinberger 为例：越来越多开发者把自己的工作描述为设计循环，再由循环给智能体发提示词。这种侧重听起来很新，底层的控制结构却并不新。他回忆起早年人们争论 Fortran 和 COBOL 孰强孰弱，然后谈到了 Böhm 和 Jacopini 1966 年的论文。

编程里熟悉的三种结构是顺序、条件选择和迭代。Coyle 用它们解释工作流的演进：从一串顺序执行的提示词，到按条件路由，再到根据新结果反复行动的循环。这条历史结论有前提：操作和状态都要合适；光加一个循环，并不能证明任意提示词系统就是图灵完备的。落到实践上，迭代让工作流能根据反馈决定下一步，而不是跑完预先定好的流程就停下。

05

客户支持：检查模型为什么停下来

对客服智能体来说，第一个反模式是：模型返回了响应，就直接接受。Coyle 的演示改用 while True 循环：调用模型，查看生成为什么停止，再决定应用下一步该做什么。请求里包含承载对话上下文的消息、任务，以及可用的工具。

工具请求只是一份执行提议。在 Coyle 演示的客户端工具模式里，模型准备好工具名和参数，真正执行操作的是应用代码。他说模型自己不能执行工具，指的就是这条边界。按当前 API 的术语，stop_reason 是 Messages API 响应里的一个字段；这里讲的是客户端工具，不涉及另外支持的服务端工具。

当 stop_reason 为 tool_use 时，应用执行模型请求的工具，记下结果，再次调用模型。把助手的请求和对应的工具结果都保留下来，下一次调用才有足够的信息接着往下做。这段控制流用 Python 写出来如下，工具执行由应用自己提供：

```python import json

def run_support_loop(client, model, messages, tools, run_tool): history = list(messages)

while True: response = client.messages.create( model=model, max_tokens=2048, messages=history, tools=tools, )

if response.stop_reason != "tool_use": return response

history.append({ "role": "assistant", "content": [block.model_dump() for block in response.content], })

results = [] for block in response.content: if block.type == "tool_use": value = run_tool(block.name, block.input) results.append({ "type": "tool_result", "tool_use_id": block.id, "content": json.dumps(value), })

history.append({"role": "user", "content": results}) ```

应用的 run_tool 函数负责分发和执行。循环遇到其他停止条件时，会返回完整的响应，调用方可以先检查这个条件，再决定是否接受答案。

一轮完成后，Coyle 建议检查答案是否合格，不合格就转交人工。他把这一步称为检查置信度，但没有给出具体分数或阈值。“完成”和“接受”是两个独立的决定。

token 上限会带来另一个分支。一段响应读起来再通顺，也可能只是半截。按当前 Messages API 的术语，max_tokens 表示生成达到了请求设定的输出上限，不一定是整个上下文窗口用完了。end_turn 表示模型这一轮已经完成，tool_use 表示需要进一步行动；遇到 max_tokens，要先恢复或复查，别直接把输出当成完整答案。

06

代码生成：把指令放在正确的作用范围

Claude Code 的 CLAUDE.md 文件 提供持久化的 Markdown 指令。Coyle 介绍了一个三级层次结构，幻灯片上画成用户、项目、目录三个作用域。通用偏好放在顶层；项目约定和目录专属的指引，放得离它们所管的代码越近越好。

系统在代码库里工作时能看到哪些指引，由这套层次结构决定。幻灯片把冲突规则概括为“最具体的文件胜出”。这应当看作 Coyle 的讲法，而不是强制执行的优先级机制。按当前 Claude Code 文档，作用域不止这三个；嵌套目录里的指令要等读到相关文件时才加载；这些文件是给模型的上下文，不是硬性的配置规则。真正有用的设计原则是：指令管多大范围，就跟它描述的工作对齐。

07

研究智能体：让工作专门化并限制上下文

多智能体研究系统要从各个智能体那里拿回有用的成果，又不能把每个智能体都变成万金油。Coyle 说的反模式是：一个智能体装满了干各种活的工具。他打了个比方：你请来一位木匠，他却扛着水管、电工、木工的全套家伙，说什么活都能干。可你要的如果是木工活，专精的师傅也许更合适。

对应到软件上，这条原则类似于“一个函数只做一件事”。Coyle 建议给智能体划定窄的职责，每个专职智能体也许只配一两个工具。接着他把这条边界延伸到上下文：工作智能体积累的材料，不该自动涌进主对话。上下文越多越耗 token，无关内容还会让下一步决策更难做。大上下文窗口是容量，不是要你把它塞满。

批评者智能体（critic agent）让这一点更具体。某个智能体给出一个论断后，把论断和证据交给批评者，但不附上得出论断的思考过程。这样批评者手里有判断证据是否站得住的全部信息，又少了一些可能把它引向原结论的材料。

Coyle 把这种失败模式叫作群体思维：智能体在同一个对话里协作，很容易收敛到同一个想法。他打比方说，聚会上大家都想吃披萨，只有一个人不想，最后他也随了大流。给每个智能体只分配属于它的那部分信息，就是为了保住独立判断。这条边界是有选择的：批评者仍然需要证据，只是不需要引出这个提议的整段对话。

08

开发者效率：分叉、总结、压缩

开发者效率场景把同样的边界用在长会话上。两个反模式会互相加剧：一是让每个子任务把完整输出倒进主线程，二是任由主线程无限增长。先隔离子任务，再决定哪些信息该带回来。

Coyle 举的例子是日志分析：在独立的上下文里扫描日志、查找错误。在当前的 Claude Code skills 中，context: fork 是 skill 的 frontmatter 字段，用来请求以子智能体方式执行。负责这项任务的 skill 可以写上一条明确可执行的指令：

```markdown --- name: summarize-log-errors description: Scan project logs and summarize errors. context: fork ---

Scan the project logs for errors. Return a concise summary of the problems, with representative log lines and file locations. Do not return the complete logs. ```

排查过程留在独立的上下文里，不会全部塞进主对话。

工作智能体返回问题摘要，主对话拿来就能用，不必吸收全部中间输出。Coyle 接着加了第二道控制：监控上下文大小，压缩长会话。他的例子是超过 150,000 个 token 时调用 /compact；这只是演示用的触发点，并非官方说明的产品默认值。压缩能减少累积的上下文，但 Coyle 明确表示，他不清楚 Anthropic 的算法具体怎么实现。

由此引出按应用定制的压缩。Coyle 提到会场上正在派发的一本书，作者是 Sam Bhagwat，并特意说明自己和作者没有任何关系。他记得书里大约第 32 页讲到了自定义的上下文压缩逻辑，还有一个供开发者扩展的基类。架构上的机会在于：压缩数据时，留住对应用真正重要的东西，而不是默认每个细节都该占同样的篇幅。

09

CI 和批处理：让执行方式匹配谁在等待

持续集成暴露的是另一种反模式：交互式智能体在无人值守的流水线里等人回答。在开发者终端前合情合理的权限询问，放到没人响应的任务里，就会把任务卡住。Coyle 建议配置成非交互式执行；工程上的要求是，流水线运行之前就先定好哪些操作是允许的。

对于可以延后的工作，Message Batches API 提供了另一种成本取舍。异步的 Message Batches 请求，输入和输出 token 的价格都比标准 API 调用便宜 50%。省下的是每个 token 的处理费用，用掉的 token 并没有变少；而且它是一项 API 服务，不是 Claude Code 通用的批处理模式。Coyle 口头说的是“至少二十四小时”，但幻灯片上写的是 ≤24h，服务发布公告也写明在 24 小时内处理完毕。

关键在于这项工作能不能等。如果有人在等流水线的结果，就需要一条无人值守、又不会白白拖延的路径。如果是一批提示词，开发者打个盹、休一天假或者去度个假的工夫跑完都行，那就可以拿即时性换更低的 token 价格。

10

没有考试，只有动手做

Coyle 最后改写了开场那句引言：“没有考试，只有去做。”认证提供了练习题，但只有动手构建，才能把这些题变成真正的理解。他欢迎读者保持联系，并给出了自己的网站 codesupremeai。这个名字来自他对爵士乐和 John Coltrane 专辑 A Love Supreme 的热爱。一份围绕实验展开的实战指南，用这样一个带着个人色彩的结尾收场，恰如其分。

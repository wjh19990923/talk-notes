从混合专家到混合智能体……配上超快的推理

通过组合多个预训练模型构建更强大的系统，然后跟随路由、编排、硬件和评测方面的选择，看看额外的计算是否值得。

对 Python、异步调用和 LLM 提示词有基本了解，有助于理解工作坊代码；架构讨论会从基本原理介绍 MoE 和 MoA。

01

模型如何变得更有能力？

How do you keep making language models more capable? One approach changes the architecture before training: Mixture of Experts (MoE) increases a model’s capacity while activating only part of it for each token. Another combines models that have already been trained: Mixture of Agents (MoA) coordinates separate LLM calls and combines their answers. Daniel Kim and Daria Soboleva’s workshop builds the second approach. To participate, attendees first obtain a Cerebras cloud API key; the hands-on work will produce an application, followed by a configuration challenge and Q&A.

Soboleva introduces herself as a Cerebras research scientist focused on MoE and hardware-efficient training, with previous work at Google and on the SlimPajama dataset. Kim handles growth, developer activities, startup sales, and access to tokens for non-enterprise research projects. His introduction includes a fondness for hot pot; the more consequential credit goes to Kevin, the high-school intern who built nearly all the workshop and is absent for a final exam.

Cerebras supplies the inference infrastructure. Kim introduces its custom silicon beside an NVIDIA H100 and attributes its speed to hardware design and scaling across larger models. Kim claims roughly 15.5× faster inference for Llama 3.3-70B than the fastest GPU inference provider in the comparison he presents. That is a historical presentation claim; the recording does not specify the comparator configuration or measurement methodology.

The architectural motivation begins with GPT-3 and the relationship between parameter count and capability described in Language Models are Few-Shot Learners. Llama 3 adds the importance of dataset curation and training on more tokens. DeepSeek-V3 then illustrates the need for architectural changes as total model capacity grows. Soboleva’s spoken size sequence is 13, 400, and 600 billion parameters; the published specifications are 175B for flagship GPT-3, 405B for the largest Llama 3 model, and 671B total for DeepSeek-V3. The underlying engineering question remains: how can a larger model be served efficiently?

02

扩大容量而不必激活每一个专家

Start with the transformer’s embedding, attention, and feed-forward layers. Soboleva locates the bottleneck in the feed-forward network, which must process representations arriving from earlier layers across languages and domains. Her example is text mentioning the Golden Gate Bridge: which neurons should respond to that concept, among everything else the model must represent?

MoE replaces a monolithic feed-forward network with several feed-forward networks called experts. Math and biology specialists provide an intuitive analogy, although those names are not a guarantee that learned experts acquire neat human-readable specialties. A router selects which experts process a particular token. Adding experts therefore increases total parameter capacity without requiring every expert to run on every token.

Total parameters and active parameters are different quantities. Soboleva describes matching a dense model’s active parameter count while gaining the capacity of a larger trained model. DeepSeek-V3 makes the distinction concrete: its report specifies 671B total parameters but 37B activated per token. Sparse activation reduces computation relative to activating the whole model; matching active parameter counts alone does not establish identical wall-clock latency across hardware and architectures.

Soboleva closes by describing MoE as an increasingly common scaling approach and names GPT-4 and Claude as adopters. Those particular architecture claims should remain attributed: the GPT-4 Technical Report withholds architectural details, and the workshop does not establish Claude’s internal architecture. The mechanism itself does not depend on those examples: a model can have substantially more stored capacity than it uses for any one token.

03

在训练之后花费算力

Architecture is not the only place to spend compute. Referencing Ilya Sutskever’s NeurIPS discussion of a potential limit to unique pretraining data, Kim turns to inference-time compute: additional work after training that may improve the answer. An AIME competition problem supplies the example. These problems can require multiple dependent reasoning steps, making a quick answer less useful if it is wrong.

Kim reports the following results for one AIME problem, contrasting the non-reasoning GPT-4o with the reasoning model o3:

| Model | Reported answer | Reported time | |---|---|---| | GPT-4o | Incorrect | 45 seconds | | o3 | Correct | 293 seconds |

The comparison does not provide the exact problem identifier, prompts, reasoning settings, repeated trials, or timing boundaries. Its immediate product implication is still clear: 293 seconds means four minutes and 53 seconds of waiting. 一个规划者、一个批评者和一个最终答案

Kim next plays a NinjaTech.ai demonstration of a production chatbot using Cerebras. Kim reports that NinjaTech’s system answered the same AIME question correctly in 7.4 seconds. The result belongs to the demonstrated system as a whole, rather than to one underlying model.

The workflow is more involved than asking several models and taking a vote:

1. Propose: a planning agent produces eight possible answers. 2. Critique: another agent evaluates feasibility and rejects the entire first set. 3. Revise: the planner produces eight more proposals, described as using 16K context worth of thinking tokens. 4. Select: the critic identifies two plausible candidates. 5. Synthesize: a summarization agent combines those candidates into the final answer.

The rejection step matters. The first set of outputs does not become the answer merely because it exists; critique changes what the planner does next.

Kim reports over 500,000 generated tokens and 32 LLM calls for this roughly seven-second process, with calls running both in parallel and sequentially. The completed slide labels the total as 510k tokens. These are the presentation’s accounting figures for this demonstration, without a supplied call trace or token breakdown. The example shows why low latency can enable a different workflow: the system spends substantial intermediate computation on alternatives that the user never sees. Long single-model reasoning may remain appropriate for asynchronous tasks, where waiting is less disruptive.

Kim’s hardware explanation begins with the H100 diagram. He describes roughly 17,000 compute cores and a bottleneck between compute and external memory holding weights and intermediate state. Generating the next token requires access to those values; larger models increase the pressure on memory channels, including movement associated with the KV cache. This is the simplified hardware account used in the presentation, rather than a complete description of every GPU serving configuration.

Cerebras takes a different approach to locality. Kim describes 900,000 cores paired with 900,000 distributed memory stores, with each core directly accessing its local memory. In his account, weights remain assigned to those stores instead of being repeatedly fetched from external memory for each computation. The important distinction is where data resides relative to the compute that consumes it.

For larger models spanning chips, Kim says Cerebras transfers activations between chips while retaining weights locally. He illustrates the communication volume with a single Ethernet cable and contrasts it with the connectors and switches used in a DGX system. This is the basis of his linear-scaling claim: reduce recurring data movement as more hardware is added. It does not establish an unlimited, cost-free scaling law, but it explains why memory placement and communication topology matter to the many-call workflow just demonstrated.

并行的智能体，串行的层

The first prompt is deliberately low stakes: plan a San Francisco trip for Kim and Soboleva from 3 PM to 9 PM. The application runs multiple LLM calls across three layers. While Kim helps an attendee configure cloud secrets, Soboleva explains the execution graph. Agents within a layer run in parallel; layers run sequentially. The outputs of one layer become the input to the next. After the third layer, a final summarization model combines the results into the user-facing answer. The intermediate tokens broaden the material available to that final call.

A layer is a set of agents, not an agent itself. Its outputs are finalized, concatenated, and passed onward. The following Python implementation captures that scheduling pattern. complete is an asynchronous model-call function supplied by the application; model and prompt choices remain in the agent configuration.

```python import asyncio from collections.abc import Awaitable, Callable, Sequence from dataclasses import dataclass

@dataclass(frozen=True) class Agent: name: str model: str system_prompt: str temperature: float = 0.2

Complete = Callable[[Agent, str], Awaitable[str]]

async def mixture_of_agents( question: str, layers: Sequence[Sequence[Agent]], summarizer: Agent, complete: Complete, ) -> str: context = question

for layer in layers: if not layer: raise ValueError("Each layer needs at least one agent")

responses = await asyncio.gather( *(complete(agent, context) for agent in layer) ) combined = "\n\n".join( f"{agent.name}:\n{response}" for agent, response in zip(layer, responses) ) context = ( f"Original request:\n{question}\n\n" f"Previous layer responses:\n{combined}" )

return await complete(summarizer, context) ```

For the travel example, question remains the San Francisco itinerary request throughout the workflow. asyncio.gather waits for every agent in the current layer before the next layer begins. Increasing width adds parallel calls; increasing depth adds dependent rounds that cannot start early.

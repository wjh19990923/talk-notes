Blender MCP 与创意工具的未来

Blender 的脚本接口让语言模型能把一段场景描述变成具体操作。Siddharth Ahuja 的实验说明了为什么区分不同的工具很重要，以及同样的方法如何把生成的物体、动画和音乐串联起来。

01

为什么一个甜甜圈会变成界面问题

做一个甜甜圈，听起来不算多大的创作目标。可在 Blender 里，第一步往往是先啃下一整套复杂的界面。Siddharth Ahuja 之前经营过一家产品工作室，后来在动手实验时碰上了这个问题：他喜欢这款软件能做的事，却一直没能玩转它的操作。

Blender 是一款通用 3D 软件，可以导入素材、做动画、创作作品，还能把成果导出到游戏引擎。能力多，界面也复杂：顶部一排标签页，右侧是属性面板，里面还嵌套着更多选项。Ahuja 自嘲说，就是这堆控件让他一直没成为一名好的 3D 艺术家。

后来他接触到 Model Context Protocol（MCP）。MCP 要把语言模型和工具连起来，这让他想到另一种入门方式：能不能由他描述想要什么，让模型去完成具体操作？

Ahuja 跟过一门新手甜甜圈课程，前后花了五个小时。让他沮丧的是，一个简单的想法和实现它所需的知识之间隔得太远。Blender MCP 想回答的问题是：提示词能不能缩短这段距离？

02

一条领会了需求的龙

Blender MCP 把 Claude、ChatGPT 这类模型应用接入 Blender，一条提示词就能变成场景操作。Ahuja 开场演示时，要求生成一条守护一罐金子的龙。用户只需说明想要什么场景，怎么搭建由模型应用自己去想。

看到结果，Ahuja 笑了：它确实理解了任务，虽然谈不上什么出色的作品。画面里有一个等距视角的房间、一条长着翅膀的龙，还有一罐金子。Ahuja 估计这个场景花了大约五分钟。换成他手动做，要久得多。

做出一个看得出是什么的结果，和做出一件精良的作品，是两回事。 这条龙做到了前者：一段描述，在一款复杂的创作软件里变成了一组摆放好的物体。

据 Ahuja 介绍，演讲时 Blender MCP 在 GitHub 上大约有 11,500 颗星，下载量超过 160,000 次。已经有不少人在用它，并在它的基础上继续开发，这些实验早已超出他一个人能做出来的范围。

03

模型选择工具，Blender 执行工作

背后的连接方式，比做出来的场景看上去要简单。模型应用通过 MCP 与 Blender 通信，MCP 提供了一套标准方式来开放可用的能力。在 Ahuja 的示意图里，应用位于 Blender 和外部素材服务之间：既能协调本地场景里的工作，也能向外部 API 发请求。

工具描述告诉模型有哪些操作可用。模型挑选操作，应用负责调用；决定做什么的并不是 MCP 本身。

在 Blender 这一侧，Ahuja 写的插件负责执行通过这座桥传过来的脚本。语言和几何体就在这里接上了：生成的代码变成了 Blender 里的操作。模型应用理解请求，Blender 执行场景里的具体工作。

有了素材，能用的“词汇”就不止脚本直接搭出来的物体。Rodin 提供 AI 生成的素材，Sketchfab 和 Poly Haven 则是另外的素材来源。模型应用可以统筹整个过程：先拿到物体，再把它放进场景。

这条路走得通，是因为 Blender 本来就支持脚本，也能下载和导入素材。集成时直接用这些现成能力就行，不必把每个动作都还原成界面上的一串点击。

比如，用户可以描述一个僵尸，要求生成一个符合描述的素材。客户端一边向外部服务发请求，一边处理 Blender 里的工作。这就是它作为编排者（orchestrator）的角色：一个创作请求可能要动用好几种能力，但它们最终汇成同一个结果。

在 Ahuja 看来，把应用、模型和创作工具分开，带来了灵活性。他列举了 Claude、Cursor、Windsurf 和 LangChain 等可用的环境，模型则可以在 Claude、ChatGPT 和 Gemini 之间选。他的设计目标是：大家带上自己习惯的环境和模型，就能走同一套创作流程。

04

彼此区分的工具减少了选择上的歧义

实现上的第一条经验是：现成的脚本接口能省下大量工作。Blender 能执行代码，Claude 写代码的能力就能直接用在建模和素材处理上。有了通用的代码执行能力，就能触达软件的方方面面，不必为每个手动操作单独做一套集成。

但开放的操作越多，模型不见得越好用。Ahuja 说，有一版集成大约有 14、15 个工具，模型选工具时开始犯糊涂，他为此反复重构。难就难在：面对一个请求，该用哪种能力。

从他举的例子能看出，这些选择为什么会重叠：

| 开放的能力 | 实现路径 | | --- | --- | | 创建立方体或球体 | 直接请求一个基本几何体。 | | 执行代码 | 用脚本搭建场景内容，包括基本几何体。 | | 从 Rodin 获取素材 | 直接拿到生成好的素材，而不是自己搭建。 |

要一个简单形状，既可以走专门的创建工具，也可以走通用的代码执行。两条路做出来的画面可能一模一样，模型却得从中选一条。

Ahuja 的做法是让接口保持精简，让每种能力都界限分明。职责分得清，工具才好选。 值得借鉴的是减少操作之间的歧义，而不是把他的工具数量当成通用上限。

这条原则也延续到了产品体验上。开源项目容易收到大量功能需求，可要是每个功能都往里加，反而会侵蚀让它好用的那份精简与通用。

底层模型也在进步。Ahuja 仍然觉得模型对 3D 的理解有限，但他以 Gemini 2.5 为例，说在项目开发期间就注意到了进步。一座足够通用的脚本桥可以直接吃到这些进步的红利，不必为每类场景再开发专门功能。

05

生成的资产、动画与图像参考

别人用起来之后，这座桥能做什么就变得更具体了。Ahuja 先展示了自己的一个场景，用的全是新生成的素材，其中有一朵魔法蘑菇。他描述想要的物体，告诉 Claude 放在哪里，再把最终的构图截下来。

Ahuja 说，魔法蘑菇这个场景他只用了两分钟。他特别强调，这些素材是专门为这个场景生成的：提示词既负责拿到物体，也负责摆放它们，而不只是把手头已有的一堆东西挪挪位置。

另一个猫的例子又多了一种操作。作者先拿到生成的素材，再给它们加一点动画，让场景有了生气。Ahuja 说，这套猫的流程不到一小时就能做完。成果不再只是一张拿来截图的构图，里面的物体能动了。

下一个例子换了输入方式。作者提供一张客厅的图片，模型以此为参照重建场景、获取合适的素材。Ahuja 说，重建这个客厅只花了几分钟。

有了参考图，整个流程就有了视觉目标。作者不必用文字描述每个物体和它们的空间关系，直接把想要的样子给出来就行。

06

地形节点、游戏场景与动画材质

另一位作者在 Cursor 里用一张参考图，在 Blender 中生成地形。这就触及了软件里更专业的部分：用来配置纹理以及表面凹凸、法线细节的节点。

节点怎么搭，本身就有一条学习曲线。Blender 能执行代码，模型就能在生成地形的过程中顺手把节点配好。脚本桥能做的不只是摆放物体，还能深入到决定物体表面外观的那套机制里。

下一个游戏的设定很古怪，Ahuja 尤其喜欢：玩家钻进某人的肺里收集骨头碎片，拼出一副肋骨才算赢。场景搭建和素材制作用的都是 Blender MCP。它在这里提供环境和物体，撑起了这个游戏奇特的目标。

还有一个展示，重点是一种带光泽和虹彩的材质，以及一段相机动画。Ahuja 说，材质和相机动画都是靠提示词几分钟做出来的。请求的范围已经不止物体的形状，还延伸到表面外观，以及展示它的镜头运动。

07

一个 Blender 赛车场景变成一段 Runway 视频

赛车的例子从一条提示词开始：搭一条赛道，让赛车动起来。Blender 场景里有一条环形赛道、几辆赛车、彩色障碍物、树木和看台。作者随后摆好相机，让比赛画面开始有了电影镜头的感觉。这是一个搭好的 3D 场景，进入下一步制作之前，物体和取景都可以随意调度。

作者还给相机加了动画，然后用 Runway 把从 Blender 得到的素材转换成最终展示的片段。Blender 负责搭场景、定运动；Runway 负责生成转换后的画面。

这样分工，这套流程就不只属于 3D 艺术家，电影创作者也能用。即便 Blender 渲染出来的不是最终画面，一个可控的场景也能成为制作镜头的中间环节。赛道、赛车和镜头运动，为后续的视频生成提供了骨架。

08

回到甜甜圈

Ahuja 回到开头那个练习：用一条简短的提示词做出了甜甜圈。他估计这个例子大约花了一分钟，也承认结果还可以好得多。

和那门五小时的新手课相比，区别在于怎么拿到第一个成果。跟着教程，学到的是操作；写提示词，得到的是一个可以检查、继续打磨的东西。两者质量不能划等号，学到的本事也不一样。但有了提示词，新手在掌握界面之前就能尝试更多事情。一个简单的想法，现在能先变成看得见的物体，下一条提示词也就有了具体的抓手。

09

一个围绕创作者意图组织的工作流

接着，Ahuja 把编排的思路延伸到了 Blender 之外。既然模型应用能协调本地的创作工具和外部素材服务，它也能协调多款创作软件。

贯穿其中的是创作者意图。人们用 Unity，是因为想做游戏；用 Ableton，是因为想做音乐。学软件只是达到目的的手段。难点在于抓住一个人想创作什么，把它转化成跨软件的工作，同时还要贴合他的构想。在 Ahuja 的设想里，MCP 把这些工具连起来，语言模型负责理解请求、协调工作。

按他设想的游戏制作流程，用户向模型应用描述想做的游戏，应用再去协调几项分工：

- Blender： 制作游戏需要的素材。 - Unity： 组装游戏、添加碰撞、实现游戏逻辑。 - 外部服务： 补充素材或动画。 - Ableton： 为角色和游戏创作音乐。

这是一条设想中的生产链。创作者只管指挥整个项目，由应用决定每一部分交给哪个底层工具来做。

10

一条龙和它的配乐

为了演示这个想法的缩小版，Ahuja 把 Blender MCP 和他的另一个项目 Ableton MCP 组合起来。请求是：做一条龙，再给它配一段配乐。模型应用原本就连着 Blender，Ableton MCP 又给了它一条新连接，用来请求创作音乐。

结果由相互配合的两部分组成。Blender 里是按描述做出的龙，阴森的打光很符合反派气质。Ableton 负责配乐。同一份角色设定同时影响画面和音乐，两款软件各自产出自己的部分。

Ahuja 坦言，质量还很有限。让他兴奋的是能把这些环节串起来：原本得在两套截然不同的界面里分别操作，现在一个创作请求就能统一引导。

11

创作者仍然需要掌控的东西

这些实验让 Ahuja 开始思考界面的问题：会不会有越来越多的人主要通过模型应用来干活，而不去学底下每一个复杂工具？他看到，已经有新的创作者从这条路入门了。

他打了个比方：乐队指挥。创作者要讲清楚想要什么结果，协调好各个部分，哪怕自己并不亲手演奏每件乐器。能不能把构想说清楚，决定了它能不能落地：哪些部分该放在一起，各自起什么作用，整体要传达什么感觉。

Blender MCP 和 Ableton MCP 是他给出的具体例子，此外他还提到见过 PostGIS、Houdini、Unity 和 Unreal Engine 的集成。他预计，这类连接越来越多，会让更多人跨媒介创作。他的热情来自这样一种可能：一个人只要想法清楚，不必先成为每个工具的专家，就能指挥这些工具把事情做成。

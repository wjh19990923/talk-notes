高效 AI 实用指南

要把一个 AI 演示交到客户手中，就得符合真实的资源预算。小模型和量化是两个实用的起点，而评测决定了什么可以安全部署。

对语言模型、模型权重、微调和推理有基本了解会有帮助；不需要量化经验。

01

从一个能跑的演示到客户可用的服务

一个新模型展示出惊艳的能力。要把这个原型变成客户能大规模使用的产品，还差什么？演示只证明任务做得到。上线生产还要求系统跑在运营预算之内。能力和部署之间有差距，效率能帮着缩小它。 Shelby Heinecke 这份指南要解决的，正是这个实际问题。

Heinecke 带领一支 AI 研究团队，为 Salesforce 的数据平台交付 LLM 解决方案。这个平台是 Salesforce 各类产品的底座。除了生产交付，团队还研究智能体、语言模型和端侧 AI。据她介绍，截至演讲时，团队已发表 15 篇以上研究论文，开源了 6 个以上代码仓库。她本人的研究方向包括学习算法，重点是高效利用样本和通信。

这些工作背后，是 Salesforce 更长的企业级部署历程。按 Heinecke 的说法，Salesforce 做 AI 部署已有十年：研究团队成立于 2014 年，拥有 300 多项 AI 专利，发表了 227 篇以上研究论文。可信也是部署的要求之一：她提到公司参与了六个 AI 伦理委员会，并签署了白宫的可信 AI 承诺。时间线随后来到 2022–2023 年的产品浪潮：代码生成产品、Service GPT、Einstein GPT 和 Tableau GPT。面对财富 500 强级别的规模，支撑这些产品要消耗多少资源，就成了核心的工程问题。

02

每个部署都有资源预算

部署环境不同，约束也不同，但约束始终存在。

| 环境 | 主要约束 | | --- | --- | | 公有云或私有云 | 持续的 GPU、CPU 和磁盘成本 | | 本地集群 | 运营成本，外加数量固定的 GPU | | 手机等小型设备 | 硬件和资源限制更严 |

在云上，资源消耗直接变成服务成本。在本地，买下基础设施也消除不了容量上限：模型只能在现有的 GPU 上跑。

苹果当时刚发布了一款面向新设备的 LLM，Heinecke 借此有了具体理由，把目光投向服务器之外。手机让人看到语言模型和多模态模型更广的落地空间：平板、个人笔记本、边缘设备。这些设备的预算也更紧。在云上负担得起的模型，放到小设备上可能还是太重。所以，部署目标应当反过来影响模型的设计和选型。

03

提升效率的五个地方

效率不是发布前临门一脚的一次性优化。Heinecke 把它拆成五个维度，每个维度都是一个可以下手的环节：

1. 架构。 能用小模型，就先从小模型起步。其他选择包括混合专家（mixture-of-experts）架构；如果自己构建模型，还可以采用高效注意力机制。 2. 预训练。 如果非得从头训练，混合精度和扩展方法能帮着应对高昂的 GPU 开销。 3. 微调。 LoRA、QLoRA 等参数高效方法不更新基座模型的全部权重，而是把可训练的改动集中在少得多的参数上。 4. 推理。 模型训练、适配完成后，可以用训练后量化和投机解码来压低服务成本。 5. 提示词。 提示词 token 会占内存，也会拖慢响应。精简模板、压缩提示词，能减少模型要处理的输入量。

这五个维度彼此独立。选了高效的架构，训练、服务和提示词照样要逐一审视。

本文重点展开两个实用方向：选用小模型和训练后量化。前者换掉你起步用的模型；后者改变已训练模型的权重在推理时的表示方式。

04

更少的权重扩大了部署选项

回看上一波发布中那些标志性的大模型，就能看清模型规模带来的资源压力。Heinecke 举了三个例子：PaLM 5400 亿参数，BLOOM 1760 亿，YaLM 1000 亿。参数就是网络的权重，既占存储，也参与计算。所以权重一多，预训练、微调和服务都会受影响，而不只是下载的 checkpoint 变大。

在这里，Heinecke 把参数量不超过 130 亿的模型称为小型 LLM。讲规模的那张幻灯片把这类模型和大得多的模型摆在一起，差距一目了然。

权重少，通常意味着内存和磁盘需求更低、GPU 或 CPU 计算量更小、微调更快。前向传播的活也更少，延迟可能随之降低。这些好处叠加起来，模型能跑的地方就更多了：云和本地系统照样可用，足够小的模型还能装进手机、个人笔记本和边缘设备。接下来的问题是：小模型能不能把任务做得足够好？

05

小模型在特定任务上变得有吸引力

第一个例子是 Phi-3-mini，Phi-3 家族中 38 亿参数的成员。Heinecke 展示了技术报告里的一组对比：在图中这项评测上，它胜过了一个 7B 模型。这说明能力并不单由参数量决定，小得多的模型也值得认真考虑。不过，这个结论只针对该项评测，并不是说它超过了所有更大的模型。

下一个例子降到了十亿参数以下。MobileLLM 展示的是 3.5 亿参数的配置，小到让移动端和边缘部署格外有看头。据 Heinecke 介绍，MobileLLM-350M 经过微调后，在所引用的任务上与 7B 模型表现相当。这里比的是专门的 API 调用，不是通用语言能力上打平。微调本身就是结果的一部分： 要问的是，小模型针对目标任务适配之后能做到什么程度。

函数调用是一个更典型的专精化例子。Octopus v2 把 Gemma 2B 适配到 Android 任务上。Heinecke 介绍，微调后的 Octopus 模型在所引用的 Android 函数调用任务上，胜过了 GPT-4 和一个 Llama 7B 模型。注意适用范围：这个模型专门针对特定接口和负载训练。它说明做部署决策时，应该拿候选模型真正要干的活来比，并把针对任务微调带来的提升算进去。

06

减少表示每个权重所用的比特数

选完模型，下一步是推理优化：训练后量化。量化是一项成熟技术，这里把它用在语言模型和多模态模型上。做法是不再用 32 位或 16 位浮点数存每个权重，而是改用 8 位、4 位等更低精度的表示。降低的是表示精度，参数的数量并没有减少。

算一笔存储账，就知道它为什么诱人。从 32 位降到 4 位，每个权重的名义位数只剩八分之一。下面这段 Python 算出了一个 70 亿参数模型的权重存储开销，可以自己看看：

```python parameter_count = 7_000_000_000

for bits_per_weight in (32, 16, 8, 4): weight_bytes = parameter_count * bits_per_weight // 8 weight_gb = weight_bytes / 1_000_000_000 print(f"{bits_per_weight:2d}-bit: {weight_gb:.1f} GB of weight data") ```

这里只算了权重数据。实际部署时，模型还需要运行时内存，量化后的表示也可能附带额外的元数据。所以系统总内存不会严格按位数比例下降。

Heinecke 展示了 7B、13B 和 70B 三个 Llama 例子，4 位量化后磁盘占用都降了下来。随后她转向另一项多模态模型研究：图中的对比显示，4 位下的首 token 延迟低于原始的 16 位。首 token 延迟（time to first token） 衡量的是请求要等多久才开始生成，而不是整段回复的生成速度。降低精度能改善延迟，但收益多大要看模型、硬件和运行时。存储和延迟改善之后，剩下的问题是：模型还能不能把任务做好？

07

准确率决定了量化能走多远

这项视觉-语言评测把原始 16 位精度的多模态模型，和 8 位、4 位的量化版本放在一起比。Heinecke 介绍，在图中这项评测里，一直降到 4 位，任务表现基本没变。也就是说，在这个例子中，存储和延迟上省下的开销，没有让任务分数出现明显波动。

图的下一段划出了底线：在图中的对比里，降到 3 位时性能就下滑了。所以，4 位结果理想，是值得去测试量化的理由，而不是可以跳过测试的理由。要评测量化后的模型本身。 合适的精度，是能保住部署所需行为的那个精度。除了语言模型和多模态模型，传统机器学习模型也可以考虑量化。

08

从现有的量化工具和已发布的版本开始

量化权重未必要你自己生成。Heinecke 首先推荐 llama.cpp，它支持从 16 位一直到约 1.5 位的多种表示。她建议先去 Hugging Face 找找有没有现成、兼容的量化版本，再决定要不要自己转换。她还提到，可以用 Python 和 Java 封装库来做集成。

第二条路是 ONNX Runtime。这个运行时早在 LLM 出现之前就有了，支持多种编程语言。Heinecke 重点提到它的 8 位量化。以上是录像里讨论的功能；链接中的项目文档对应当前版本，格式和 API 一直在演进。选哪条路，要同时看模型本身和它的运行环境。

09

在设备上测试质量、安全性和行为

拿到量化后的 checkpoint，部署还没结束。Heinecke 介绍了 Mobile AI Bench，这是她的团队新近发布的开源框架，用来在模型交付客户前更系统地做评测，确认量化后的模型依然符合预期。

评测覆盖文本任务、可信与安全，以及视觉-语言任务。可信与安全要专门盯住：量化如果让安全行为退化，任务分数保住了也不够。针对端侧部署，配套的 iOS 应用还会测量延迟和硬件占用，包括耗电情况。质量评测和设备性能分析回答的是两个问题：模型是否仍然胜任它的工作，以及能否在设备的运行预算内把活干完。

这又把部署问题带回了五个维度：架构、预训练、微调、推理和提示词。小模型和量化是务实的切入点，但最终怎么选，还要看在客户实际使用的环境里，质量和资源消耗的实测结果。

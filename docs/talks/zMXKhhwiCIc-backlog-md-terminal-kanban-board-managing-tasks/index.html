Backlog.md：用终端看板和 AI 智能体管理任务

一个终端看板功能展示了存放在仓库中的 Markdown 任务、明确的验收标准和分阶段的审查，如何让 AI 编程智能体的工作保持有边界、可检查。

熟悉 Git 仓库、Markdown 和 AI 编程智能体会有帮助；不需要 MCP 经验。

01

一个小时的工作，方向却错了

智能体埋头干了快一个小时，你才发现它把需求理解错了，这时怎么办？或者事情做到一半，它的上下文窗口就用完了？Alex Gavrilescu 的办法是把大功能拆成一个个小的 Markdown 任务。Backlog.md 让这些任务成为人和 AI 智能体共用的项目管理界面。

起点是终端里的一块看板（Kanban）。打开一个任务，能看到它的描述和验收标准；翻到 In Progress 和 Done 两列，还能看到已完成的标准和实现笔记。这块看板已经把工作摆到了明面上，但还缺一个 Gavrilescu 想要的交互：在状态列之间移动任务，以及在同一列内调整顺序。演示要做的就是补上这个功能。

02

先定义键盘交互

让 Claude Code 动手做移动模式之前，Gavrilescu 先把它的行为定义清楚。需求清晰对智能体重要，道理和对人类开发者一样：意图没说出来，写代码时也就无从落实。

| 输入 | 预期行为 | | --- | --- | | M | 进入移动模式，高亮当前任务 | | ↑ / ↓ | 在当前列内调整任务顺序 | | ← / → | 在状态列之间移动任务 | | 移动模式下按 M 或 Enter | 确认移动 | | Esc | 取消移动 |

页脚要显示这个命令，并说明怎么操作。这些需求把三件事分开了：选中任务、调整它的目标位置、确认或取消这次改动。如果只笼统地说一句“让看板上的任务能移动”，这些行为都没有着落。

03

创建一个任务，再检查智能体理解了什么

第一个请求是根据这些需求创建任务，而不是实现功能。一开始，Claude 得先摸清这个项目怎么运作，就像刚入职的开发者一样。它读了 Backlog 的介绍和创建任务的指南，然后建好任务。到这一步，“完成”只意味着任务记录建好了，功能还一行没写。

Backlog 的任务就是仓库里的 Markdown 文件。front matter 存放元数据，比如任务 ID、标题和标签。正文说明目的：用户应该能用键盘重新整理终端看板，不必敲 CLI 命令，也不必直接改文件。验收标准再把这个目的落成可测试的行为。针对演示中的交互，一份精简的 Markdown 约定大致如下：

```markdown

描述

为终端看板添加移动模式，让用户不用 CLI 命令、也不用改文件， 就能调整任务顺序、修改任务状态。

验收标准

- [ ] 按 M 进入移动模式，并高亮选中的任务。 - [ ] 按上下键在当前列内调整任务顺序。 - [ ] 按左右键在状态列之间移动任务。 - [ ] 按 M 或 Enter 确认移动。 - [ ] 按 Esc 取消移动。 - [ ] 页脚说明移动命令和操作方式。 ```

第一次审查看意图。 写代码之前，先读描述和验收标准：它们说的是你想要的功能吗？每条标准都能验证吗？这是最早发现误解的机会，纠正起来也最省事。

04

要求一份立足于代码库的计划

下一个请求是实现计划。智能体要理解描述和验收标准，查看现有代码库，必要时查阅项目文档或外部文档。产出的计划要说明功能该放在哪里、怎么实现。

Gavrilescu 明确要求 Claude 按 Backlog.md 的工作流，为刚建好的任务制定这份计划。Claude 干活时，有用的调研都很具体：哪些文件要改，这些文件现在有哪些行为，哪些文档约束着这些改动。

05

资源解释工作流，工具改变任务

Backlog.md 的 MCP 服务器既提供指引，也提供操作。它的 MCP resources 负责提供工作流上下文，首先是一份概览，介绍 Backlog 是什么、什么时候该用。要不要把 resources 纳入上下文，由宿主应用决定；把指引暴露出来，并不能保证每个客户端都会去读。

概览会把智能体引向各个阶段的指南：

| 指南 | 智能体需要了解什么 | | --- | --- | | 创建任务 | 任务的必填和可选字段 | | 执行任务 | 把状态设为 In Progress，并把任务分配给自己 | | 完成任务 | 核对验收标准和完成定义（definition of done） |

有了这些指南，任务状态就有了流程上的含义：标记 Done 的前提是核对过需求，而不只是写完一段代码回复。

MCP tools 提供对应的操作。创建任务前，智能体应先搜一下有没有现成的任务。之后它可以查看任务详情、创建或更新任务、更新验收标准，并把做完的工作标为 Done。resources 讲怎么做事，tools 让智能体用原生的任务操作把这套流程走下来。

06

在执行之前审查拟议的修改

Claude 交回了架构概览、实现步骤，以及要修改的文件清单和每处改动的说明。第二次审查看方向。 Gavrilescu 认为这是最重要的检查点：智能体投入精力写代码之前，资深工程师可以先判断这个方案是否适合项目。演讲没有细讲怎么审计划，直接进入了下一步。

执行阶段依托任务里积累的上下文：描述、验收标准和计划。Gavrilescu 提到，Claude Code、Gemini 和 Cursor 都能配合 Backlog.md 使用。它们要做的是实现全部验收标准，并且只在满足完成定义时才把任务标为 Done。随后他让 Claude 实现这个功能，录屏在它干活期间暂停。

07

实现任务 316，再试用它的控件

人也可以直接用 Backlog 的 CLI 创建这些记录，但演示里是让智能体把功能描述转写成任务所需的各个部分。上下文存好之后，执行请求就可以很短：让 Claude 实现任务 316。任务 ID 直接指向规格说明，人不必在对话里再讲一遍。

回到终端，页脚现在显示 m to move。Gavrilescu 进入移动模式，任务随即高亮显示。他先上下调整它的顺序，再把它移到另一个状态列。他并不想真改这个任务，所以取消了这第一次移动。

接着他选中刚实现的任务 316。为了模拟实现不完整时该怎么处理，他把它移回 In Progress，看板上的任务也随之出现在这一列。这是在演示如何重新打开任务，并不是说他发现了缺陷。Gavrilescu 说，按规格驱动的实现只花了几分钟，但录屏在执行期间暂停过，看不出实际用了多久。

08

用任务边界控制范围和恢复

把任务写成仓库里的 Markdown 文件，上下文工程（context engineering）就落到了一个实际的范围问题上：一个任务该让智能体实现多少？任务越小、越原子化，就越容易控制在可用的上下文之内，预期的改动也越明确。即便某次尝试出了岔子，补救的范围也有边界：回滚，修改规格、描述或验收标准，再让智能体从实现计划那一步重新开始。

验收标准划定了功能包含什么、不包含什么。单元测试也应该检查同样这些标准，让书面约定和验证对得上，免得任务和测试各说各话。

所以这套工作流有三个审查检查点，各自回答一个问题：

1. 审查任务：描述和验收标准是否准确表达了想要的功能？ 2. 审查计划：智能体提出的实现方向对不对？ 3. 审查代码：最终改动是否满足任务要求？

有了这些检查点，人在实现前后都能纠偏，不必等智能体把整个尝试做完再说。

09

让工作留在仓库里

相互独立的任务可以借助 Git worktrees 并行执行。这里有个前提：Gavrilescu 只建议在任务之间没有依赖时这样做。独立的工作目录给并行开发腾出了空间，但功能之间的依赖并不会因此消失。Backlog.md 本身是一个开源 CLI，采用 MIT 许可证，同时提供终端界面和网页界面。

在演示的工作流里，MCP 是智能体首选的原生接口，CLI 命令则留给旧式智能体使用。而当前的 README 反过来推荐用 CLI 指引，MCP 只作为可选支持保留。Gavrilescu 还说 Backlog 是跨平台的，支持各大主流操作系统。

任务就存放在团队的 Git 仓库里，不需要单独的任务服务 API、数据库或账号。Gavrilescu 说，即使别的分支上有更新，Backlog 也会去检查任务状态。这应理解为跨分支检查，而不是无条件的团队同步：按当前配置，检查可以开关，活跃分支按存在时长筛选，关闭远程操作时只读取本地分支。自动提交默认关闭。

Gavrilescu 说，Backlog 99% 的代码是 AI 智能体写的，他本人只写了指引和前三个任务。这个比例怎么算出来的，他没有说明。所以这个项目也是他的一个示范：用精心写好的指引和最初几个任务，引导智能体开发这个工作流工具本身。

想试试这套工作流，Gavrilescu 建议去看 Backlog.md，也欢迎大家留言，或找他帮忙上手。仓库就是起点，可以照同样的步骤走一遍：描述功能，检查任务，审查计划，再让智能体去实现。

没有评估我们就寸步难行

幻灯片原文
Without a way to define good output, teams risk regressions when changing prompts, configurations or model providers. Nielsen introduces llmeval to help teams ship reliable LLM products.

We are stuck without evaluation

01
After deploying GPT based applications in production, we are having a collective “now what” moment.

02
Without knowing what good means, it is hard and risky making changes in prompts, configurations and models provider i.e. OpenAI -> Anthropic -> Self hosting

03
Introducing llmeval today so your team can ship reliable LLM products 🚢

02

llmeval 概览

幻灯片原文
llmeval runs evaluations locally using configurable Python metrics, then generates Markdown reports. Its rollups can require X out of Y runs to pass, accommodating variable LLM outputs.

llmeval

$ pip install llmeval
$ llmeval init
$ llmeval run
$ llmeval report

01
CLI and Simple folder structure where you can import prompts, associated tests separately.

Run everything locally.

02
Extensible - hierarchical configuration using a system from Meta called Hydra.

Metrics are backed by python - use any tool or LLM to evaluate.

03
Generate markdown reports with custom roll up.

Support X out of Y passes, or any logic you prefer to deal with probabilistic nature of LLMs.

Python 代码生成提示词

幻灯片原文
The prompt asks for Python code without surrounding explanation. The demo then checks whether the output can be parsed as a Python program.

# Copyright Log10, Inc 2023

defaults:
  - tests/code
name: code
model: gpt-4-16k
temperature: 0.0
variables:
  - name: task
messages:
  - role: "human"
    content: |
      Generate a python function which {task}.

用 llmeval 评估 LLM 应用

一个正确的答案仍可能把应用搞坏。Niklas Nielsen 演示了如何测试输出契约、诊断提示词回退，并把评测从 Python 检查扩展到参考人工判断的模型评判者。

对 Python、命令行工具和 LLM 提示词有基本了解，有助于理解示例。

01

什么才算一个好的回答？

还说不清好的回答长什么样，又该怎么安全地改动一个 LLM 应用？基于 GPT 的功能上线后，团队要面对一连串决策：提示词怎么写、配置怎么调、选哪家模型、要不要自托管、要不要微调。每一处改动都可能改变生成结果。没有评测标准，就很难判断应用是变好了还是退步了。

Log10 的 CTO 兼联合创始人 Niklas Nielsen 介绍了 llmeval。这是一个本地命令行工具，帮团队把这些决策变得更具体。它的出发点是给提示词、测试用例和验收标准一套可重复的结构。

02

提示词、Python 指标和重复试验

Nielsen 说，初始配置只要四行代码。初始化会为提示词和测试建好文件夹结构，配置系统用的是 Meta 的 Hydra。评测逻辑用 Python 写，所以一个指标可以做简单比较，可以跑更复杂的校验，也可以调用另一个 LLM。最后由报告汇总整个应用和每个测试的结果。

一个测试既要有判定单次回答的标准，也要有汇总多次尝试的规则。 模型的回答会有波动，所以 Nielsen 提出用灵活的验收标准，比如五次里有三次通过就算过。这只是一种示例验收策略，不是实测出来的可靠率。多跑几次，报告就能描述单次回答体现不出来的行为。

03

定义一个精确输出的契约

终端演示从几步简单的准备开始：

1. 新建一个工作目录并进入。 2. 创建 Python 虚拟环境。 3. 安装 llmeval，初始化提示词和测试文件夹。

这里展示的是录制时的 CLI 流程和示例，仅供历史参考。这个包现已归档。

第一个提示词问 A 加 B 等于多少，接着加了一条输出约束：“只返回答案，不要任何解释。”第二句很关键，因为测试会把实际回答和预期回答当作字符串比较。哪怕解释在数学上完全正确，也会违反应用的约定，判为失败。

比较时只做了一项很有限的规范化：去掉开头的空白。Nielsen 解释说，在这个例子里 Claude 有时会在开头多加空格。测试随后输出一个供报告使用的指标，外加一个单独的通过/失败结果。具体输入是 4 和 5，预期输出是 "9"。这个比较可以直接用 Python 写出来：

```python def exact_match(actual: str, expected: str) -> dict[str, bool]: matches = actual.lstrip() == expected return {"metric": matches, "result": matches}

expected = "9" assert exact_match(" 9", expected)["result"] assert not exact_match("4 + 5 = 9", expected)["result"] ```

这样一来，开头的空白可以放过，多余的解释却不行。多出来的解释仍然改变了要求的输出。

04

去掉一条指令，检查失败

为了看清输出约束起什么作用，Nielsen 删掉“只返回答案”这条指令，再跑算术测试。CLI 既能跑完整套测试，也能通过配置覆盖只跑数学提示词：

```bash # Run the complete suite. llmeval run

# Run only the math example. llmeval run prompts=math ```

Nielsen 说，默认每个测试采样五次，这次演示他改成了一次。默认值写在 llmeval 的 YAML 配置里。这一轮对 Claude、GPT-4 和 GPT-3.5 各采样一次。

生成报告后，失败一目了然。GPT-3.5 附了一句解释，Claude 则把整个算式写了出来。两者给出的和都对，但都不满足精确输出的要求。报告里展示的区别如下：

| 报告中的模型 | 回答格式 | 精确匹配 | | --- | --- | --- | | GPT-4 | 只有 9 | 通过 | | GPT-3.5-turbo | 答案加解释文字 | 失败 | | Claude-2 | 写出完整算式 | 失败 |

真正有用的发现是输出格式对提示词的依赖：删掉提示词里的一句话，输出就可能不再满足调用方的约定。

Nielsen 把指令加回去，重跑测试。最新一轮通过了，但生成报告时仍可能提示失败，因为之前几轮也算在报告范围内。单轮结果和总体报告回答的是两个不同的问题： 最新结果告诉你，这次改动有没有修好这一轮；总体汇总告诉你，纳入的各轮里有没有失败的。只看汇总、不看单轮，一次成功的修复也可能看起来像没修好。

05

检查生成的 Python 能否解析

下一个例子以工具调用为背景，让模型生成 Python 代码。这里的提示词同样有好几句话，要求模型别附带解释。不过验收标准变了：测试不再要求逐字一致，而是检查回答能否解析成 Python 程序。用 Python 写指标时，可以靠 ast.parse 划出这条界线：

```python import ast

def parses_as_python(output: str) -> bool: try: ast.parse(output) except SyntaxError: return False return True ```

这样，写法不同但都合法的程序都能通过，不要求源码一模一样。它只检查语法，既不执行程序，也证明不了程序算出了要求的结果。

报告显示，生成 Python 的测试全部通过。表里列出三个模型在两个例子上的结果，分别是两数相加和求平方根倒数，值都是 True，并带绿色的通过标记。演示的解析检查到此完成。

06

当标准需要判断时就用模型

精确匹配和语法解析，能给范围很窄的问题一个精确答案。对于更依赖理解和判断的任务，Nielsen 介绍了一种用模型评测 Mermaid 图的方法：定好一组标准，让模型打 1 到 5 分，并说明理由。写测试、收集用例照样要花功夫，但有了裁判模型，那些很难直接比较的质量也能拿来评测。

这种做法通常是用一个更大的模型，去评测另一个 LLM 的输出。评判可以有几种形式：

- 通过/失败： 判断输出是否符合标准。 - 打分： 在一个小范围内打分，比如 1 到 5 分。 - 偏好： 在几个候选中选一个，并说明理由。

评判附带的理由，往往比光秃秃的分数更有助于排查问题。

裁判本身也会出问题。Nielsen 提醒，比较不同模型时，裁判可能偏向自家模型的输出。他还提醒，0 到 1 或 0 到 100 这类刻度给出的分数质量堪忧。这些问题决定了排名或分差有多可信：结果看起来再细致，也取决于评测者自身的表现。演示的下一步，是把人工反馈重新引入这个流程。

07

根据审查者的历史生成建议

Nielsen 的最后一个演示，把模型评测和人工审阅连了起来。假设 John 已经审阅过一批补全结果。做法是用这些积累下来的反馈建模出一个“Auto John”，由它为新进来的补全生成审阅建议。这样，人的判断成了评测器的输入，而不是被排除在反馈流程之外。

界面上有两条已有的人工反馈：一条打了 5 分，另一条评价得更细。还有一条在等待反馈，点开后会出现 AI 建议的回答。画面上只能看到这一项从待审阅变成了有建议可看，并不能说明有人采纳了这条建议。自动化在这里有个很实际的用处：把审阅者过去的判断延伸到新任务上，同时让人工反馈和模型生成的建议始终泾渭分明。

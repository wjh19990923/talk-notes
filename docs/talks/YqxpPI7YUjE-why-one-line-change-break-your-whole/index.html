Channel bookmark folders: requirements and acceptance criteria

幻灯片原文
Cole opens a Jira ticket to show how Qodo checks a PR against its acceptance criteria. Folder ordering must stay stable, deleting a folder must preserve its bookmarks, and folder actions must use existing bookmark permissions.

[12:29](https://www.youtube.com/watch?v=YqxpPI7YUjE&t=749s) [A Jira ticket lists requirements for channel bookmark folders, including ordering, grouping, safe deletion, remembered collapse state, limits and permissions. Below are acceptance criteria, out-of-scope items and a note to reuse existing bookmark permissions.](https://assets.ai.engineer/sites/aiecode2025/sha256/65b810eaa7c32dc1f034e2dbff3290843783c8e30bdbb9b78f37ebfcc43154bc.webp)

Functional requirements

1. A channel can have folders. A folder has a display name and can be ordered relative to other folders.
2. A bookmark can be filed into a folder or left ungrouped.
3. Listing a channel's bookmarks returns them grouped by folder, with the folder order and the order of bookmarks within each folder preserved.
4. Deleting a folder is safe: the channel is never left in an inconsistent state, and bookmarks that were in the deleted folder are still reachable afterwards (e.g. moved back to ungrouped) rather than lost.
5. Each user's collapsed/expanded state per folder is remembered across sessions, so collapsing a folder on one visit keeps it collapsed on the next.
6. A channel may contain at most a reasonable maximum number of folders; attempts to exceed the limit are rejected, mirroring the existing per-channel bookmark cap.
7. Folder management actions (create, rename, reorder, move bookmark into a folder, delete) are gated by the same bookmark permissions already used for the channel type (public/private add/edit/order/delete bookmark permissions), so only users who can manage bookmarks can manage folders.

Acceptance criteria

☐ Creating a folder and filing bookmarks into it returns them grouped on the next list call.
☐ Folder order and within-folder order are stable across list calls.
☐ Deleting a folder leaves the channel consistent and its bookmarks reachable.
☐ A user's collapsed folders stay collapsed after re-opening the channel.
☐ Exceeding the folder limit returns a 400.
☐ A user lacking bookmark-management permission cannot create/move/reorder/delete folders.

Out of scope

• Nested folders (folders within folders).
• Drag-and-drop UI (client tickets).
• Sharing folder layouts across channels.

Notes

Reuse the existing channel-bookmark permission scheme rather than introducing new permissions.

为什么改一行代码就能搞垮整个技术栈

构建通过、单元测试通过，下游的使用方却可能没被检查到。Cole Gannaway 的 Qodo 演练跟随一次 Bitwarden 数据模型的重命名，经过仓库依赖、可复用的审查规则、独立的审查智能体，以及对照原始工单的检查。

为什么改一行代码就能搞垮整个技术栈——录像第 2:03

01

当审查成为瓶颈

Teams can generate code faster and still struggle to get it through review. Cole Gannaway, a solutions engineer at Qodo, describes customers who want a software factory that takes work from a ticket all the way to production. Their pull requests become the bottleneck: implementation accelerates, while deciding whether the resulting change is trustworthy remains difficult.

Qodo focuses on that review stage, supplying context to the human or agent making the decision. It occupies one part of the larger ticket-to-production workflow. Code generation still makes mistakes, and faster generation makes it more urgent to understand the consequences of a proposed change before approving it.

To see why an ordinary review can look reassuring, consider Gannaway’s illustrative example from Bitwarden, the open-source password manager. A developer wants a rename and changes one line of its data model. In the imagined approval decision, the build passes, the unit tests pass, and perhaps the linters pass too. The edit matches the developer’s intention, so approving it feels reasonable.

The familiar verdict is “seems good to me.” Gannaway’s show-of-hands question surfaces the compromise behind it: reviewers sometimes merge without reading every changed line, depending on their tools for confidence. The scope of those tools’ context then becomes part of the review decision.

02

梳理依赖这次变更的组件

The missing question is what else depends on the changed model. In the Bitwarden scenario, the back-end server can connect to web clients, mobile or iOS clients, MCP servers, and command-line clients. A rename can become a compatibility problem when a consumer still expects the previous model. The server’s checks can look healthy while the effect appears elsewhere, perhaps as a production bug report or a crashing web application.

To understand which connections matter, a reviewer needs more detail than a line joining two repository names. Qodo’s cross-repository review uses an automatically built software graph and an integration surface: the actual components through which repositories connect. Knowing that Bitwarden server connects to Bitwarden Android identifies a relationship; knowing which components connect makes it possible to assess whether that relationship matters to the edited model.

The graph lets the human or review agent widen its investigation from the edited repository to the affected consumers. That is the reason to map the system at component level: a small diff can reach several clients in other repositories, even when the local change looks correct. The relevant measure of impact is how far the change reaches through those connections.

03

在生成之前先把 API 规则定好

Dependencies are part of what experienced reviewers contribute. They also bring conventions, taste, and memories of earlier mistakes. If that knowledge stays with a senior engineer, the same person may need to recognize and explain the same problem on every review. Custom rules make some of that judgment available to subsequent reviewers.

Gannaway suggests adding a deprecation flag or reviewing a public API change more closely. The rule on screen is more specific. Public API fields are additive, and an existing field must be deprecated before it is renamed or removed. In the example, the coding agent plans to keep RevisionDate and add LastModified, so clients that still read the old field can continue to do so.

The same information can influence implementation before there is anything to review. In the example, an MCP server brings Codebase Wisdom, custom rules, and accumulated team knowledge into the coding agent before code generation. The agent can consider downstream effects while choosing the change, rather than learning about them only after opening a pull request. This improves the opportunity to get the first attempt right; Gannaway still calls for a later check.

04

给审查器独立的上下文和判断

An implementation agent such as Claude Code already has useful background, which makes asking it to review its own work an appealing shortcut. The case for a separate review agent has two parts: controlling what occupies its context window and reducing the chance that it repeats the implementer’s blind spots.

- Context devoted to review: The implementation agent spends context on debugging, implementation, and exploring the codebase. A review agent can concentrate on Codebase Wisdom, the software graph, and information specific to this review. Larger windows do not prevent relevant details from getting buried or prevent hallucinations; choosing the contents still matters.

- Different models and harnesses: A reviewer can use a different model, including choices from Anthropic, OpenAI, or open-weight models. The harness—the software that organizes the agent’s work—can differ too. Reusing the same model and harness may reproduce similar biases, so both are candidates for variation.

Gannaway also proposes adversarial reviewers that inspect the same code and compare findings. He treats agreement as a stronger signal that a problem is real, while very different findings call for further investigation. The point of the comparison is to expose mistakes that one route through the review might miss. Agreement remains a review heuristic, not a guarantee that a finding is correct.

05

让一条 PR 评论在未来的 PR 上也有用

Learning from a failure also has to outlast the review conversation. Postmortems can lead to changes in process or organization, which need their own follow-through. For code-level lessons, the practical question is how to turn knowledge held by a few people into a check that everyone can use.

The PR-comment example makes that conversion concrete. A comment on a pull request supplies the input; Qodo suggests a rule based on it. The conversion gives the feedback an explicit form that future reviews can check.

Applying the rule to later PRs reduces dependence on someone remembering to repeat the comment. Separately, the software graph can flag the rename’s large blast radius to a human or another agent, directing closer attention to a change that looked small in the diff. Running these checks through MCP or a CLI before opening the PR gives the coding agent an earlier chance to fix the problem.

06

对照最初的意图检查实现

An audience member describes already reviewing work with an agent and writing down the resulting guidance for the next run of the factory. The harder question is about intent: what happens when the context given to the implementation agent misses what the task was really meant to accomplish?

The distinction takes a moment to pin down. Gannaway first considers a poorly written ticket, then an agent that over-engineers a small request into a wholesale rewrite. The questioner sharpens the concern: the agent may be approaching the problem incorrectly and implementing the wrong thing. Review has to check the requested outcome as well as the implementation’s internal quality.

The live example addresses how a reviewer can check the intended outcome. Qodo supports integrations with Jira and Linear; a linked ticket supplies acceptance criteria to the PR review. The review then highlights requirements gaps against that ticket, making incomplete requested behavior part of the review output.

A requirements-gap finding tells the implementation agent to return to behavior the ticket requested. Its limit follows from its input: the check depends on the ticket expressing the real intent. An omitted or mistaken requirement still needs clarification; comparing the implementation with the written criteria cannot supply intent that those criteria never captured.

These checks can guide implementation before a PR exists. Gannaway recommends adding a skill that requests a review around the 25%, 50%, and 75% points of the coding work. The specialized reviewer can then act almost like a manager, steering the implementation agent away from the wrong solution or unnecessary rebuilding. As implementation consumes more of the agent’s context window, a separate review can return attention to the requirements while the next edits can still change direction.

The closing question is which changes can be merged without a human looking at them. Gannaway says some teams already do this and presents deciding when it is appropriate as the next step for the review layer.

Blast-radius information gives that decision a useful input: a one-line edit can affect several clients and warrant more scrutiny than its size suggests. The graph makes those consequences easier to inspect. The decision rule for when the available evidence is sufficient to allow an unattended merge remains open.

  • A dedicated review agent can reserve context for codebase knowledge, the dependency graph, and information specific to the review. Varying models and harnesses aims to reduce shared blind spots.
  • Qodo’s PR-comment example turns feedback into a suggested rule that can be applied to future PRs, while the software graph directs reviewer attention to changes with broad impact.

更好的实体匹配

幻灯片原文
Hybrid lookup combines semantic similarity and lexical overlap to match ingredients, such as garbanzo to chickpea. Embeddings also allow matches on terms that need not be known in advance.

Better entity matching

Principle: Hybrid approaches often yield the best results. In this case semantic entity matching.

# hybrid match = semantic vector score + lexical score
def hybrid_lookup(query, candidates):
    q, *cands = embed([query, *candidates])      # all-MiniLM-L6-v2
    scores = []
    for cand, vec in zip(candidates, cands):
        vector  = (cosine(q, vec) + 1) / 2        # semantic kinship
        lexical = token_sort_ratio(query, cand) / 100  # surface overlap
        scores.append(0.6 * vector + 0.4 * lexical)
    return best_first(candidates, scores)

图技术实践者指南

从菜谱信息抽取到代码搜索，图模式、实体匹配、排序和路径算法把关联数据变成对 AI 应用有用的上下文。

对结构化数据和数据库查询有基本了解会有帮助；不需要图算法基础。

01

图在什么时候真正有用？

Obsidian 里的关系图谱看着很吸引人，却未必能让你的笔记更有用。引入 GraphRAG，或者围绕图数据库重构电商应用时，也会碰到同样的诱惑：这种表示方式看起来很有前景，预期的回报却迟迟不来。真正该问的是：把关系显式表达出来以后，哪个问题会变得更容易？

图的基础知识能指明方向。搜索、模式识别、检索和知识类问题里，往往藏着一些关系：图能把它们暴露出来，算法能加以利用。Tim Ainge 的思路就从这里出发：先弄清结构，再决定用哪款图产品。

本文讲的是这些底层模式，不是 GraphRAG 或智能体记忆的教程。内容按实用的顺序展开：先建立图的基本要素，再改进信息进入图的方式，最后用算法检索那些光靠名称或文本相似度很难找到的信息。每种技术都会从原理讲到示例，再落到应用。

02

给信息抽取一个形状

图由节点（也叫顶点）和连接节点的边组成。类型和标签区分节点与关系各代表什么；属性用来附加细节；方向则区分关系的朝向。有了这些，一堆连接就变成了一个可以查询的模型。

以从菜谱中抽取图为例。最简单的输出格式是主语–谓语–宾语三元组：一个事物和另一个事物之间有某种关系。让抽取器把松饼菜谱里的关键信息抽成三元组，由它自己判断哪些重要，它确实能生成一张图。但生成一张图，和生成一张有用的图，是两回事。关系怎么组织、用什么词描述，仍由抽取器说了算。

更好的做法是给抽取器一个 schema 去填：菜谱有食材，每种食材有用量。结构化输出会把结果约束成这个形状。在示意的 schema 示例中，蒜香黄油意面连接到大蒜、欧芹、黄油、意大利面和帕玛森奶酪。改进不只是图画得更整齐了，而是抽取开始遵循一套一致的模型。

节点和边的类型保持一致，查询才有稳定的含义。在菜谱 schema 里再加上步骤，把每一步表示为应用某种烹饪技法。这样图就能区分菜谱“包含什么”和“怎么做”，而不是把每条事实都当成一条随意的关系。

03

规范化取值，再解析身份

schema 定义结构；这里说的本体（ontology）则进一步规定，哪些内容该放进这个结构、具体怎么放。对菜谱来说，就是统一食材名称、使用公制单位，让匹配和换算更容易。名称统一小写、单位保持一致，这些属于数据模型本身，不是表面上的清理。在提示词里写明这些约定能改善抽取效果，但再好的提示词也保证不了一致性。

接下来是身份识别问题。如果 garlic cloves、minced garlic 和 garlic 各占一个节点，本该共享同一种食材的菜谱就会被割裂开。演示中还有 cumin 和 cumin seeds、vegetable oil 和 oil。一个朴素的映射就能把这些变体合并起来。这样既去掉了重复，更关键的是，菜谱之间通过同一个食材节点连了起来。

事后做名称映射有个局限：得事先料到会出现哪些食材叫法。借助嵌入向量做匹配，流程会更灵活，预定义映射里没有的词也能处理。真正好用的组合，是在精心设计结构的图里做 AI 辅助匹配。

由此得到的构建流程分三层：先建立 schema，再整理抽取进来的信息，最后在创建新节点之前先做实体匹配。解决了身份问题，图能揭示的关系也就不一样了。 如果每次抽取都各自造出一个互不相干的“大蒜”，两份菜谱就不可能共享同一个大蒜节点。

04

通过共同的食材查询菜谱

先从一个简单查询开始：哪些菜谱含有大蒜？Ainge 把 Cypher 查询和对应的 SQL 并排列出。用 Recipe、Ingredient 和 HAS_INGREDIENT 作为具体的 schema 名称，这个关系模式可以写成：

``cypher MATCH (recipe:Recipe)-[:HAS_INGREDIENT]->(:Ingredient {name: 'garlic'}) MATCH (recipe)-[:HAS_INGREDIENT]->(ingredient:Ingredient) RETURN recipe.name AS recipe, collect(DISTINCT ingredient.name) AS ingredients; ``

第一个 MATCH 通过共享的大蒜节点选出菜谱，第二个 MATCH 取出这些菜谱的全部食材。

展示的结果是含大蒜的菜谱及其食材连接，为了放进幻灯片做了裁剪。在这个深度上，两种查询语言都能胜任。等问题需要沿着五条、十条甚至二十条边走下去，差别才真正显现：图查询能直接描述关系的遍历，等价的关系型查询却可能变得很笨重。Ainge 把这看作图查询和图数据结构在结构上的优势，而不是实测得出的数据库基准结果。

05

从一个起始节点出发对相关性排序

个性化 PageRank（Personalized PageRank）不再只问“有没有连接”，而是以选定的起点为参照，给节点排序。它是 PageRank 算法的一个变体，PageRank 通常归功于 Brin 和 Page。

想象有个游走者沿着边在图里行走，每到一个节点就做个标记。它时不时回到起点，重新出发。正是这种“回到起点”让排序变得个性化：反复的探索始终锚定在选定的起点上。走过许多轮之后，有些节点被访问的次数明显多于其他节点，说明在这种遍历方式下它们的相关性更强。游走者只是个帮助理解的比喻，并不要求真的去实现固定长度的游走。

菜谱示意图以 Chicken Handi 为起点，周围的菜谱和食材节点亮度各不相同。Ainge 把这个思路和 Pinterest 的 Pixie 论文 联系起来，那篇论文用图游走来做推荐。

HippoRAG 是检索方面的一个应用：个性化 PageRank 与其他图技术配合，把存储的知识和问题、答案连接起来。Ainge 提到演示资料包里还有一些变体。菜谱这个小例子可能让相关性显得一目了然，但到了稠密的簇里，光靠肉眼已经看不清哪些关系重要，这时排序就格外有用。

06

通过间接引用发现权威

法律引用图能把间接关系的价值讲得很具体。从一个美国最高法院案件出发，任务是找出它所依据的权威里程碑案件。在 Ainge 的例子里，Kansas v. Cheever 并没有直接引用 Miranda v. Arizona，但引用图通过中间案件之间的关系，揭示了两者的联系。

有用的输出既包括相关的权威判例，也包括把它和起始案件连起来的引用链。有了这条链，检索结果就能解释：它说明了案件之间怎样关联，而不是只丢出一个里程碑案件，却不给出支撑它的路径。

07

检索两个已知符号之间的代码

有时两个端点都已知，只是不清楚它们之间是什么关系。假设改了购物篮的构造函数之后，结账功能坏了。最短路径查询可以沿着代码图在这两个节点之间走一遍，把中间经过的符号、源代码或摘要取出来作为上下文。搜索任务就从“找到某个端点”变成了“找到连接两者的代码”。

该用哪种路径，取决于你要问什么：

| 路径查询 | 检索到的内容 | | --- | --- | | 最短路径 | 最直接的一条连接 | | k 条最短路径 | 几条较短的备选路径 | | 经过指定节点的路径 | 受某个中间节点约束的连接 | | 最小代价路径 | 边权重总和最小的连接 |

这些变体能帮你挑出哪些中间节点和关系可能解释两个端点之间的联系。

取出一个连通子图，能补上孤立的向量搜索、或者单独查符号和引用时漏掉的上下文。Ainge 提到，在一个 .NET 代码库上的一次评测中，用这类图技术为智能体挑选上下文，代码搜索类工具调用减少了 40%。基线、任务集和正确率都没有公布，所以这个结果只能说明那一次评测，不能当作普遍的性能保证。

08

在不知道名字的情况下找到一种模式

子图匹配又换了一个出发点。不再是选定一个节点向外探索，而是描述你想找的关系形状。节点类型或 ID 仍可用来约束查询，但不需要事先指定某个具体实例。

eShop 演示要找的是装饰器（decorator）：一个包装类使用目标类，两者实现同一个接口。用 Class、Interface、IMPLEMENTS 和 USES 作为 schema 名称，这个形状可以写成：

``cypher MATCH (wrapper:Class)-[:IMPLEMENTS]->(contract:Interface), (target:Class)-[:IMPLEMENTS]->(contract), (wrapper)-[:USES]->(target) WHERE wrapper <> target RETURN wrapper.name AS wrapper, target.name AS target, contract.name AS sharedInterface; ``

共享的 contract 变量要求两个类实现同一个接口；USES 关系提供从包装类到目标类的连接。查询里不需要出现任何类名。

搜索找到了一个商品目录视图模型服务，以及它的缓存版本：后者调用前者，同时实现相同的 API。不用先去搜跟缓存有关的名字，靠关系模式就能发现这个缓存装饰器。

当你清楚问题的结构，却不知道它叫什么、藏在哪里时，这个区别就很关键。可以找的目标包括代码反模式、安全问题、恶意交易模式，以及整个语料库里的法律论证。按名称搜索，你得对实例有所了解；结构查询则可以直接去找关系的排列方式本身。子图匹配带来的是另一种发现方式，而不只是让现有的查找更快。

09

超越路径、排序和模式

路径、排序和模式匹配回答的是不同的问题：两样东西怎么连起来，以某个起点为参照哪些东西重要，某种关系结构出现在哪里。其他成熟的图算法则处理依赖模型和网络模型里的流、代价与搜索问题。预测、相似度和聚类还能进一步扩展适用范围；Ainge 把这些留在了演示备注里。

再往下走，就接近 GraphRAG、动态图和无 schema 图了，超出了本文的范围。真正的机会在于把图算法和 AI 结合起来，让两者各展所长：AI 负责抽取和匹配信息，显式的关系则支撑遍历、排序和结构发现。这种结合的目标是更聪明、更便宜、更可靠的应用；能不能做到，取决于选出的图结构和算法是否契合实际问题。

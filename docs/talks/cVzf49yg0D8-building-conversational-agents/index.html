构建对话式智能体：从有状态的工具循环到实时音频

构建一个小型编程智能体，给对话模型加上工具和视觉能力，并跟随现场演示所暴露出的部署和可靠性权衡。

你需要能读懂 Python、会使用环境变量，并能理解 JSON 工具模式和 WebSocket 连接。

01

从一把密钥开始——以及一台能用它的设备

接入 Gemini 需要准备什么？Thor Schaeff 和 Philipp Schmid 的工作坊里，第一步很实际：拿到一个保密的 API key。两人都在 Google DeepMind 做开发者体验，负责 Gemini API 和 Google AI Studio。AI Studio 可以用来试用模型、创建凭据；使用 Antigravity 本身则不需要配置这个 key。

配置在 AI Studio 里完成，入口是 ai.dev：

1. 打开 Get API key，也可以直接访问 ai.dev/api-key。 2. 新建或导入一个项目。 3. 选中项目，创建 API key。

Schmid 说，核心的动手练习只需要一个 Google 账号，用免费额度就能完成，不用绑信用卡。所选截图里是项目创建成功的通知和创建 key 的对话框，这时凭据还没露出来。

已有的 key 也能用。工作坊提到可以把它写进 .bashrc 或 .zshrc 这类 shell 配置，演示时也直接内联配置。关键只有一条：key 必须保密，不要分享，也不要提交到 GitHub。Schmid 把配置过程中露出来的那个 key 删掉了。

大家创建凭据的间隙，Thursday AI 的 Wolfram Rebenwolf 讲了自己怎么用 Gemma 和 Gemini 写代码、做智能体，其中还有一个在眼镜上的实验。中间插了一个 Chrome 小技巧：右键标签栏，把标签页改成竖排，能在笔记本上省出一点屏幕空间。随后眼镜的话题落到了实处：VisionClaw 把 Gemini 和 OpenClaw 的工具连了起来。眼镜连手机，手机维持与 Gemini Live 的 WebSocket 连接。这套集成靠 Meta Ray-Ban SDK 才做得出来，这位参会者也说自己的方案还在实验阶段。另一位参会者是苏黎世 GetYourGuide 的 Michael，他正在搭第一版 AI 客服智能体。同样几样东西——对话式输入、保留下来的上下文、能在模型之外动手的工具——在这里通向两个截然不同的方向。

02

一个面向模型和智能体的交互界面

第一个练习是做一个小型编码智能体，能读文件、写文件、执行 shell 命令。实时语音放在后面。Schmid 介绍了 Interactions API：它在 2025 年 12 月以公开 beta 形式发布，是 generateContent 之后的发展方向。这里说的是方向，并不是说老 API 已经下线。新接口沿用了 Chat Completions、Anthropic 和 OpenAI 那套大家熟悉的约定。

一次请求可以指定一个模型，比如 Gemini 3 Flash；也可以指定一个智能体，比如 Deep Research。后者不会马上返回一条模型回复，而是先规划、再执行一项较长的研究任务。按 Schmid 的说法，一次运行大约 10–15 分钟，会访问几百个网站。接入或自定义智能体列在后续计划里。更大的目标是把多个模型的输出串起来：用 Nano Banana 生成图片，交给 Flash 继续处理，用 Lyria 生成音频，将来还可能用 Veo 生成视频。

结构上最大的简化是带类型的内容块。输入和输出用同一种模式，都带显式的 type，涵盖文本、图片、音频、视频、函数调用和思维签名（thought signature）。protobuf 风格的结构要靠 text、inline data 这类字段来暗示内容类型；新结构让应用代码能更直接地检查内容、按类型分发。

03

把历史保存在服务器上而不交出上下文控制权

状态放在服务端时，客户端只要发送新输入，再附上上一次 interaction 的 ID，服务端就会把这条输入接到保留的对话后面。耗时长的智能体任务可以设置 background: true，然后轮询结果，不必一直占着连接；webhook 据称即将推出。流式输出用的是 server-sent events。内置工具、远程 MCP，以及最近推出的 Google Search 与自定义函数组合使用，都在这同一套接口上扩展。

| 关注点 | 服务端管理历史 | 客户端管理历史 | | --- | --- | --- | | 后续请求 | 新输入加上一次的 ID | 显式传入整段对话 | | 编辑上下文 | 在保留的历史上继续 | 删除或改写选定内容 | | 复用 | 保留现有内容 | 重建时要小心保持原样 |

服务端状态是可选的。应用如果需要删掉上下文里的某些部分，仍然可以自己管理历史、自己提交。后台执行解决的是另一个问题：Schmid 举的例子都是要跑好几分钟的智能体任务，用轮询或通知，任务完成就不必依赖一个长时间挂着的 HTTP 请求。

保留历史还有利于隐式缓存。模型生成回复前，要先处理输入 token；这部分处理结果缓存下来，后续请求就能复用。Schmid 估计，命中缓存的输入 token 便宜 90%；他还说，用上 Interactions API 的初创公司，缓存命中率提高了两到三倍。他的解释是：在客户端重建历史，很容易带进细小改动——删掉的换行、去掉的空白、删掉的内容——这些都可能让缓存失效。这个提升数据来自那些初创公司，工作坊并没有给出对照实验。接下来的代码对比又印证了这个 API 的另一处简化：用显式的类型块取代 oneof 式的输入字段。

04

循环把推理与行动连接起来

智能体由四个部件组成：模型决定做什么；工具与环境交互；上下文说明任务、能力、偏好和约束；循环让这几样持续运转，直到模型不再请求工具。服务端状态简化了历史管理，但工具循环还得客户端来跑。

普通聊天时，interactions.create 接收一个模型和一段输入，比如问法国的首都是哪里。追问时带上返回的 ID，服务端手里已经有之前的用户输入和模型回复。这套续接机制还能跨模型使用：幻灯片上的例子先用 Deep Research 调研 2026 年的 AI 智能体，再让 Nano Banana 根据调研结果生成一张图。需要手动控制的应用，也可以改为传入一组由 user 和 model 角色组成的对话轮次。

函数声明要给出类型、名称、描述和参数 schema。一旦某次 interaction 需要执行操作，活就得应用来干：

1. 检查 interaction 的输出。 2. 找出函数调用块。 3. 执行对应的本地函数。 4. 在新的 interaction 里提交执行结果。 5. 重复以上步骤，直到模型给出最终回复。

函数调用是请求去做某件事；函数结果记录的是应用实际做了什么。 幻灯片把这个区别放进了完整的“请求—执行—响应”循环里。

05

给编程智能体它能用的文档

工作坊让大家用自己顺手的 IDE 智能体或 CLI 来写实现。动手之前，先装好对应的 Gemini API skill。文档里给编码智能体的配置说明区分了三种 skill：通用 Gemini 开发、Live API 和 Interactions API。第一个练习选 Interactions。装在项目本地就够了，演示用的位置是 .agents/skills/gemini-interactions-api。

Schmid 在 Cursor、Antigravity 和 Gemini CLI 上测过 skill 能否被识别。至于 Claude Code 是从 .claude 还是 .agents 里找 skill，讨论下来没有定论，所以最靠谱的办法是看行为：直接问编码智能体能用哪些 skill。Antigravity 认出了装好的 Interactions skill。Upstash 的 Context7 和 Vercel 的 skills.sh 也提供安装途径，背后是同一个 GitHub 仓库。这次要交付的是一个 Python 脚本，Schmid 认为它在某位参会者基于沙箱的工作流里也能跑。

这个 skill 刻意做得比照搬 API 手册小。它只管两类事：一是模型容易做错的，比如选了过时的模型；二是工作流上的偏好，比如用 Bun 跑测试。列出可用模型，能防止它默认用早已过时的 Gemini 1.5。详细的 API 行为，skill 会指向一份 Markdown 文档，让智能体自己去抓取。功能一有变化，只需更新文档，不必让每个用户重装一个大 skill。有人问多抓取一次会不会有开销，Schmid 把它比作读本地参考文件：两种方式都得先把资料取回来才能用。

06

构建最小的有状态智能体

实现需求里明确要求在 workshop.py 里写一个 Agent 类，而不是笼统地说“写个智能体”。构造函数创建 GenAI 客户端、选定模型，并初始化用来记录上一次 interaction ID 的属性。run 方法发送输入，再更新这个 ID。main 函数负责调用这个类跑一遍。生成代码时，Schmid 纠正编码智能体，让它用工作区里的 uv 环境；需要的包是 google-genai，用 pip 或 uv pip install 都能装。

这个 Python 版本沿用的是录制时 beta 阶段的 outputs 响应结构。当前的 Interactions 文档改用执行步骤（execution steps）和 model_output；文档还规定，工具、系统指令和生成配置在后续请求里都要重新传。上一次的 ID 只保留对话历史，不保留这些请求设置。

```python import os from google import genai

class Agent: def __init__(self, model: str): self.client = genai.Client(api_key=os.environ["GEMINI_API_KEY"]) self.model = model self.previous_interaction_id = None

def run(self, text: str) -> str: request = {"model": self.model, "input": text} if self.previous_interaction_id is not None: request["previous_interaction_id"] = self.previous_interaction_id

interaction = self.client.interactions.create(**request) self.previous_interaction_id = interaction.id return "\n".join( output.text for output in interaction.outputs if output.type == "text" )

if __name__ == "__main__": agent = Agent(model=os.environ["GEMINI_MODEL"]) print(agent.run("My name is Phil.")) print(agent.run("What is my name?")) ```

在生成的工作坊代码里，模型默认是 Gemini 3 Flash。关键的状态转换在于给 interaction.id 赋值：下一次调用指向刚刚完成的那次 interaction。截图里能看到这一步更新，以及等着运行的“记住名字”测试。

第一次运行弹出一条实验性 API 的警告。接着出了点小混乱：有个提示词问的是模型叫什么，而不是用户叫什么；改成问用户的名字，模型就答上来了。Schmid 认为这套编码流程能跑通，靠的是指令写得精确、装了 skill、上下文有用，还有真的去运行了脚本。也有参会者说自己用 TypeScript 写出了能跑的版本，甚至有人是用手机参与的。

07

添加文件工具，再闭合执行循环

下一个需求是加上 readFile 和 writeFile。每个工具都要两样东西：一个 JSON schema，告诉模型该生成哪些参数；一个 Python 函数，在本地拿这些参数执行。工具映射表把名称和这两样对应起来。生成过程中，编码智能体发现了一个现成的答案文件夹，照着里面的实现写——这提醒我们，要查一查智能体实际参考了哪些上下文。

基础的文件实现很短，模型和代码之间的完整约定一眼就能看全：

```python from pathlib import Path

def read_file(file_path: str) -> str: return Path(file_path).read_text(encoding="utf-8")

def write_file(file_path: str, content: str) -> str: Path(file_path).write_text(content, encoding="utf-8") return content

TOOLS = { "readFile": { "function": read_file, "schema": { "type": "function", "name": "readFile", "description": "Read a UTF-8 file and return its contents.", "parameters": { "type": "object", "properties": {"file_path": {"type": "string"}}, "required": ["file_path"], }, }, }, "writeFile": { "function": write_file, "schema": { "type": "function", "name": "writeFile", "description": "Write UTF-8 text to a file.", "parameters": { "type": "object", "properties": { "file_path": {"type": "string"}, "content": {"type": "string"}, }, "required": ["file_path", "content"], }, }, }, }

def execute_tool(name: str, arguments: dict) -> str: if name not in TOOLS: raise ValueError(f"Unknown tool: {name}") return TOOLS[name]["function"](**arguments) ```

schema 交给模型，Python 可调用对象留在应用里。这些文件函数直接访问进程所在的文件系统，所以练习在什么环境里跑，就决定了它们能读到什么、能覆盖什么。

现在智能体的输入既可以是文本，也可以是一组内容块，因为后续请求里可能带着函数结果。每次请求模型都附上工具 schema。客户端检查 interaction.outputs，里面除了函数调用，还可能有推理相关的内容和思维签名。状态由服务端管理时，这些签名不必手动重建再传回去。分发调用前，应用先确认请求的工具确实存在：模型要是请求一个不支持的编辑文件工具，绝不能就此变成一次任意调用。

每执行一个函数，就生成一条对应的函数结果。生成的实现在有工具结果要提交时递归调用 self.run，否则返回 interaction 的文本。测试让智能体把 Hello from the agent 写进 hello.txt，再读回来。演示的 trace 里依次是一次 writeFile 调用、它的结果、一次 readFile 调用和最终回复。比起一句“文件已创建”，这条 trace 更能证明文件系统操作真的发生了。

08

用对话暴露缺失的指令

在外面再套一个 stdin 循环，单次示例就成了交互式应用：等用户输入，调用 agent.run，打印结果。在这次调用内部，工具循环一直跑到模型结束。打个招呼，模型正确地只聊天、不碰文件。让它画一个竖大拇指的 SVG 就更能说明问题：模型一开始给出了内容，却迟迟不肯写到磁盘上，尽管工具明明就在手边。

Schmid 提议把智能体的角色说清楚：它是一个编码助手，可以用工具操作本地文件系统。在原有对话里，写文件的调用最终出现了；随后他让编码智能体在实现里加上系统指令。skill 在这里依然有用，因为它告诉编码智能体这个 API 怎么接收系统指令。Schmid 说，Gemini 3 Flash 的训练早于 Interactions API 问世，所以能写出这套实现，靠的是提供的文档和编码基础设施，而不是背下来的 API 示例。

生成的配置允许在构造时或运行请求时传入指令。以编码助手的人设、并明确告知可以访问文件系统重启后，同样的竖大拇指 SVG 请求触发了一次 writeFile 调用，生成的图标也显示出来了。工具是否可用，和“什么时候该用工具”的指令，是应用里两件不同的事。 这个练习改进的是后者，但并不能解释之前每一次犹豫的原因。

最后一项编码能力是 shell 命令工具，用 Python 的 subprocess 实现，返回标准输出。有参会者说自己测试时碰到模型臆造工具；Schmid 则明确表示，这个 shell 示例先不考虑安全。生成的改动也同步更新了系统提示词。有人提议测一下 Nano Banana 生图，但智能体没有对应的 skill 或指引，就先搁下了；改问现在几点，智能体调用了 date，返回 4 月 8 日星期三。至于删掉所有文件的提议，最后是拒绝了，并没有执行。

09

为历史建立分支，但要考虑过期和上下文限制

把 interaction ID 存在客户端，就能做分支。不必总是接着最新一轮往下走，可以挑一个更早的 ID，另起一条续接。Schmid 建议拿一次网页调研的初始结果当公共起点，在上面并行发出多个请求。要导出历史，可以用 interactions.get 取回某个 interaction 和它的上一个 ID，顺着这些链接往回走，就能遍历整段对话。

Schmid 介绍，interaction 默认的保留期限是免费额度 1 天、付费 55 天。存储时长和上下文容量是两回事：他说 Gemini 的上下文上限是一百万 token，超出就会报错。在这次演示里，上下文压缩仍由客户端负责。免费额度下，停了八个小时，interaction 可能还在；保留期一过，旧 ID 就找不到了。这是已存储的 interaction 到期，并不是每天全局重置对话。Vertex 支持和更多灵活性还在规划中，讨论里也没有提到专门用来改写上下文的 API。有观众提议用 eSpeak 念一个 API 笑话，顺势引出了 Gemini 的文本转语音，随后进入实时音频部分。

后来有人追问缓存，让前面的解释更清楚了。Schmid 说，复用发生在对象层面，并不把整个 interaction 当成不可拆分的整体：一份 4,000 token 的 PDF 可能被缓存，随附的十个 token 的文本输入却不会；之后，这份 PDF 和后续几轮对话都可能复用。这个例子有前提。空白字符变了照样可能破坏复用，请求路由和追问的时机也会影响能否命中缓存。原样保留对话能增加复用的机会，但不保证一定命中。

10

一个带音乐生成工具的现场 DJ

Schaeff 用 Gemini 3.1 Flash Live 开启音频部分，这是一款刚发布的原生音频模型。他说团队在架构上下了功夫，目标是降低延迟、提高可扩展性。在这次工作坊里，Live API 仍是独立的接口；把它并入 Interactions 的工作还在推进。

第一个应用把 Live 对话和 Lyria 3 结合起来。Schaeff 介绍，Lyria 3 的片段模型能生成 30 秒、带歌词的歌曲，另外还有一个生成完整歌曲的模型。Live Jukebox 给对话模型设定了 DJ 人设，再配上一个生成音乐的工具。灵感来自 BBC Radio 1 的听众热线：跟主持人聊几句，点一个曲风和情绪，然后听成品。

Schaeff 点了一首高能量的德式 techno schlager，主题是英国 AI 圈。DJ 先追问细节，接受了“给我个惊喜”的要求，然后介绍生成的曲子。歌词里有伦敦、戴圆顶礼帽的机器人、浓浓的工地茶（builder’s tea），还穿插着德语点缀。第二个观众点歌，要一首斯瓦希里语的护理主题歌曲，Schaeff 又加上了 hardcore techno。音乐放出来了，但他承认感觉不对。这段演示展示了对话中的澄清追问和工具调用，也暴露出点歌风格和实际结果之间的落差。

Live Jukebox 是在 AI Studio 里构建并发布的。Schaeff 说，和核心的免费练习不同，这个演示要生成音乐，所以需要开通计费的付费 API key。

11

Live 连接上传输的是什么

Schaeff 认为，实时音频的基准测试反映不全应用的实际表现，鼓励大家亲手试试交互效果。他说手机上的 Gemini Live 用的就是这个模型，Search Live 是否也是，他不太确定。Live API 提供有状态的 WebSocket 连接，能接收文本、流式音频片段和视频帧。演示中的 Live API 接收视频最多每秒一帧。帧可以来自摄像头、canvas 或屏幕共享。Schaeff 举了 Shopify Sidekick 的例子：它借助屏幕上下文，一步步带商家设置自定义域名。

返回的流里是音频缓冲区，也可以带上转写文本。工具调用补上了外部能力，包括 Google Search grounding。在对话底层，模型直接处理声音 token，不需要“语音转文本 → 文本模型 → 文本转语音”这样的级联。思考级别（thinking level）用来调节回复前推理的多少。Schaeff 估计预览版支持 97 种语言，还特别提到混合语言对话，比如同一段交流里德语和英语混着说。自动语音活动检测支持打断（barge-in）：模型说话时，用户随时可以插话。

在这次演示中，直连只支持 WebSocket。Schaeff 拿它和 GPT Realtime 直接提供的 WebRTC 基础设施做了对比。想用 WebRTC 的应用，可以借助 LiveKit、Pipecat、Software Mansion 的 Fishjam、Vision Agents 或 Voximplant 的集成。选哪条路，决定了应用要在模型连接之外自己搭多少媒体传输设施。

12

给声音写提示词，再测试它获取事实的能力

在 AI Studio 的 Live 视图里，Schaeff 打开摄像头，打字问自己今天穿得怎么样。回复认出了绿色夹克、蓝色 T 恤和黑色帽子。接着他换了说话方式：基础音色选 Puck，系统指令要求用友好的爱尔兰口音。Schaeff 说基础音色大约有 30 种，风格再靠提示词补充。随后关于穿搭的对话就换上了要求的爱尔兰腔。

查当前天气，光听懂语音不够。Schaeff 转向 Google Search grounding，并解释了思考控制：界面上的“不思考”其实是最低限度的思考，推理越多，回复延迟越高。然后他问伦敦现在的天气。模型先说大约 9 度、多云。Schaeff 让它确认今天的日期再查一遍，它答出 2026 年 4 月 8 日，接着给出 5 到 13 度、有雨的预报。Schaeff 对这些回答提出质疑，怀疑是 grounding 或 UI 出了问题。这一段没有找到解决办法。语音回答得再流利，也不能说明模型真的用了预期的信息源。

13

选择一个生成的应用或一个可用的示例

AI Studio 的实时语音选项是一个起点。Schaeff 让它构建一个多语言面试练习助手，支持德语、英语、西班牙语等语言。他介绍，这个构建器用的是 Gemini 3.0 Flash Preview，支持 Next.js、Angular 这类 JavaScript 全栈环境，还提供面向眼镜和 Web VR 体验的 XR 组件。生成任务在后台启动了，但录像里没有再回到做好的面试应用。

另一条路是从 Live API 文档入手，文档里链接了 AI Studio、编码智能体 skill 和 GitHub 示例应用。Schaeff 把示例克隆到名为 AINGEU 的目录，用 agy 在 Antigravity 里打开。仓库里有两种架构值得对比：一种是服务器代理媒体流，另一种是服务器签发凭据、由客户端直连。

14

通过 Python 服务器路由浏览器媒体流

Python SDK 示例走的是“浏览器 → 应用服务器 → Gemini”这条路径。浏览器采集麦克风和摄像头输入。FastAPI 的 WebSocket 接收音频、视频和文本队列，后端再把它们转发进服务端的 Live 会话。模型集成单独放在一个 Gemini Live 模块里，和面向浏览器的传输层分开。

LiveConnectConfig 存放系统指令、护栏和工具定义。会话建好后，服务器把客户端排队的媒体数据经由这个会话转发出去。为了启动示例，Schaeff 创建并激活了 uv 虚拟环境，装好依赖，把 .env.example 复制成 .env，再填入 GEMINI_API_KEY。运行 main.py，演示就在 localhost:8000 跑起来了。

应用一启动就用爱尔兰口音打招呼，还对摄像头画面做出回应。Schaeff 先让它说德语，又换成中文，问起吃饭的事。模型似乎都听懂了，但他指出转写没有出来。他还注意到延迟变差了，认为是多了一跳服务器造成的。正是这个观察，引出了把应用服务器从媒体路径里拿掉的做法。

15

用临时令牌直接连接

浏览器直连时，绝不能暴露长期有效的保密 API key。第二个示例把 key 留在一个小后端上，由后端创建临时令牌（ephemeral token），返回给浏览器或手机。客户端拿着这个短期凭据，自己和 Live API 建立 WebSocket 连接。令牌服务器照样需要虚拟环境、依赖和 API key 配置，但不再转发媒体流。

在演示的版本里，令牌创建和双向 WebSocket 端点用的都是 v1alpha。设置过期时间，可以限制令牌泄露后还能被利用多久。前端不用 SDK，直接用原生 WebSocket，把令牌当作访问凭据传进去，自己处理收到的事件。

| 架构 | 后端职责 | 媒体路径 | | --- | --- | --- | | 服务器代理 | 持有 key 并运行 Live 会话 | 浏览器 → 后端 → Live API | | 临时令牌 | 持有 key 并签发会过期的令牌 | 浏览器 → Live API |

在网络检查器里，直连的过程一目了然：先是一个响应，返回令牌和过期时间；然后建立 WebSocket 连接；再发一条 setup 消息，里面有模型、实时输入配置和工具。Live 模型公开的标识符是 gemini-3.1-flash-live-preview。建立连接和配置会话是两个独立的步骤；socket 打开了，不代表想要的工具已经配对了。

16

把成功的操作与未解决的失败分开

直连演示没有解决天气问题。问伦敦要不要带伞，模型说它拿不到当前天气，建议去别处查。明确要求它用 Google Search，也还是没查到。Schaeff 转而测试自定义工具。

这些工具效果看得见：一个请求弹出了 Hello World 提示框，另一个把页面背景改成了绿色。可是又改了几次配置之后，再让它把背景改回白色，模型却拒绝了，说自己控制不了显示或页面设置。Schaeff 回头检查了 grounding 和自定义工具的开关，没找出原因。另一位参会者也反映 Google Search grounding 不起作用。浏览器上成功的几个操作仍然是有用的演示，但搜索失败和后来工具失灵，两个问题都没有确认修好。

经历了这些失败，实现的入口还是那几个：Live 文档里链接了 AI Studio、示例仓库和编码 skill。真正有用的是一套连接和事件处理的结构，可以拿来研究、扩展；不要默认每项配好的能力都已经通过了端到端测试。

17

更长的会话需要一套遗忘策略

被问到 Live 的上下文时，Schaeff 说，不压缩的话，纯音频输入的会话上限是 15 分钟，音视频输入是 2 分钟。他介绍了会话快结束时会收到的 go-away 通知，然后讲到上下文窗口压缩，用来延长对话。

上下文窗口压缩，是拿较早的上下文换对话继续下去。 按 Schaeff 的解释，滑动窗口保留设定数量的近期内容，丢掉更早的部分。视频量很关键：多加的帧会占掉本可以留给对话的上下文。所以纯音频会话比持续输入图像的会话能保留更多对话历史。延长会话，并不意味着会话里说过、看过的一切都能留下来。

18

有意识地选择对话流程和控制方式

聊到商业用途，几个应用进入了视野。Schaeff 说 Shopify Sidekick 已经上了生产。Stitch 支持用语音指挥设计，不过他也指出这是 Google 自家的产品。Waymo 的集成还在规划中。随后他展示了 Ato，一个陪伴老人的案例，把语音交互和一个给护理人员或家人用的 App 结合起来。他介绍这家初创公司在阿根廷，并强调了多语言对话；产品页面上，一个布面包裹的陪伴设备旁边配着“AI 护理陪伴”的标题。一段简短的案例视频介绍了一位名叫 Maria 的奶奶。

| 方案 | 主要优势 | 干预点 | | --- | --- | --- | | 原生音频 | 对话流畅自然 | 说出口前难以精细控制 | | 级联流水线 | 中间环节可观察 | 合成前可检查或改写文本 |

Schaeff 认为，就眼下一些业务需求而言，级联流水线可能更合适。转写、模型、语音合成各自独立，更容易看清发生了什么，也能在回复说出口之前改掉它。原生音频的对话体验更即时，但不等于适合所有工作流。

转写记录也得应用自己负责。Schaeff 说，Live 会话没有现成的转写存档可以事后直接取回，应用要自己存下需要的事件。他推荐用 LiveKit 和 Pipecat 补齐周边能力，比如音频和转写存储，以及更多的可观测性。

至于招聘，他建议用在面试的某几个环节或初筛上，而不是替换整条面试流程。观众提到了评估标准、对话护栏，以及和 Google Meet 现有转写的集成。回答里没有给出具体的 Meet 集成方案。Schaeff 转而强调要评估具体用例，搭好所需的周边控制措施，包括 SOC 2 这类要求。他认为预览版已经可以拿来试验，能不能上生产，要看这些工作做得怎么样。

19

识别语音不等于授权说话的人

一位参会者提到一个实际的隐患：演示语音智能体时，旁边的人可能张口就让编码智能体删掉某个文件。Schaeff 没有说有哪项功能能可靠地只听一个登记过的说话人。主动音频（proactive audio）可以过滤无关的对话，但他说，靠它只接受主人的声音并不可靠。这位参会者说自己在试 NVIDIA Parakeet，配合一小段声音样本来区分说话人；这只是参会者自述的做法，并不是演示过的 Live API 功能。

另一个问题是：模型的思考过程长什么样？Schaeff 说，思考信息要主动开启，会以文本事件的形式出现在 WebSocket 上，不会在语音回复里念出来。

用语音口述写代码时，关键问题可能是 grounding，而不是持续对话：转写应该用上编辑器里看得到的类名。如果并不需要完全实时的交互，Schaeff 推荐用 Gemini 3 Flash，再附上上下文输入。讨论里给出了一个具体的多模态请求：把 main.py 和 util.py 当作文本，和录音一起发过去。这样模型既能听懂口头请求，又能拿到源码里准确的标识符。Stitch 用语音修改视觉稿也是同一个道理：有了视觉上下文，模型才知道用户说的是哪个按钮。

实时交互也能接收文本或图像，但这些输入都会占上下文。如果编辑器画面是静态的，建议先发一张图，再发几秒音频，不要每秒都重发没变的图。Schmid 估计每张图大约 1,200 个 token。优化看的是信息有没有变：画面内容或相关性变了，再发新的一帧，不必把持续推送图像当成必选项。

20

个性化、评估和存储有各自的边界

有人举了一个土木工程的例子，起初听上去像是在问怎么给模型提供专业知识。Schaeff 建议把这些知识放进初始上下文，或者提供函数调用，在对话中按需检索。提问者随后澄清：智能体能不能根据对用户专业水平的了解，慢慢调整自己？Schaeff 的回答是：在当前上下文窗口内可以。只要相关内容还在上下文里，模型就记得住对话里出现的名字和信息。这种对话内的适应，和持久记忆、可信说话人授权都是两回事。

评测的问题，得到的是一个从需求出发的回答，而不是一套测试流程。Schaeff 列举了 HIPAA、SOC 2、函数调用行为和护栏，这些因素都会改变一个商业应用的需求。他建议看看 LiveKit 这类合作伙伴的基础设施，补齐语音智能体的周边能力。所以，工作坊里这些有趣的演示只是评测的起点，代替不了“应用必须可靠地做到什么”的定义。

回到 Interactions，有参会者问它什么时候上 Vertex。讲者没给出日期，时间也不由他们说了算。他们预计接口会保持一致，所以可以先在 Gemini API 上试验，申请更高的速率限制另走流程。需要 Vertex 专属企业功能的应用，可能还得再等等。

一个关于 PII 和数据主权的问题，揭示了关闭 interaction 存储的代价。store=false 会停止存储 interaction 资源，服务端续接和后台执行这些功能也就用不了了。不要把它理解成对处理和留存各个方面的全面保证。Schmid 预计，Vertex 将来在数据主权上的做法会和 generateContent 类似，但他明确说这只是预期，不是已有的能力。

21

回到那些失败的天气回答

最后一个实质性问题直接回到了天气演示：演示翻车看着有趣是一回事，生产环境里应用该怎么应对幻觉？Schaeff 承认，这些演示没有用上最佳实践的系统指令。他打开一份指南，里面讲了怎么定义智能体的人设、对话规则、工具行为和示例。

他提出的下一步，是把系统提示词结构化，写明护栏、行为准则和工具定义，让智能体更好地守住预期的运行边界。这是一项具体的实现工作，但录像里既没有演示天气查询被修好，也没有演示幻觉被消除。剩下要做的，是把指令和工具配置写清楚，再从应用的实际表现中确认智能体确实照着做了。

Arrakis：如何从零构建一个 AI 沙箱

Arrakis 结合了 microVM 隔离、分层存储、网络和全状态检查点，让智能体可以运行应用、检查故障，并回到一个能正常工作的环境。

熟悉 Linux 进程、shell 命令和基本的网络知识会有帮助；文中会在出现时介绍容器和虚拟化机制。

01

给智能体一个运行应用的地方

编程智能体写完一个应用之后，还需要什么？需要一个地方把它跑起来，看看发生了什么，再试一次。Abhishek Bhardwaj 从操作系统的角度切入这个问题。他在卡内基梅隆大学学的是系统方向，之后在 Microsoft 做过 WSL 和一款智能手表的操作系统，在 Google 做虚拟化，在 Replit 做基础设施和基于 RAG 的代码对话。这次他以独立创始人兼唯一开发者的身份介绍 Arrakis：一个面向 AI 智能体的开源沙箱，用于代码执行和电脑操作。

o3 这样的模型会在推理过程中调用工具，比如搜索和代码执行。强化学习的工作流也需要环境来大规模执行奖励函数。对编程智能体来说，完整的 Linux 环境比一个只能对代码字符串求值的函数有用得多：它可以用 ps、lsof 这类命令查看正在运行的进程、打开的文件或 socket，诊断应用的问题，再重新规划。这种能力需要安全边界。生成的代码可能有 bug，也可能是恶意的，跟从 GitHub 或 Stack Overflow 复制来的不可信代码没什么两样。直接在宿主机或生产服务器上跑，系统权限和客户数据都有风险。

开场演示把这个执行循环讲得很具体。除了 OpenAI Canvas 和 Claude Artifacts 这些大家熟悉的例子，Bhardwaj 还展示了 Manus 怎样处理“做一个 ChatGPT 克隆”的请求：它运行 Linux 命令，尝试启动应用，出错了就动手修。他的解释是，模型在预训练阶段已经学到了大量 Linux 知识。只要有一个能用的操作环境，模型就能直接用上这些知识，不需要把每个调试动作都写进专门的智能体框架。

02

一个智能体可以打检查点的环境

Arrakis 提供可自托管、可定制的沙箱，用于代码执行和电脑操作。它最核心的新能力是快照与恢复：智能体可以先保存进度，再尝试下一步；失败了就回到检查点，不用重建整个环境。代码完全开源，执行边界和背后的恢复机制都能直接查看。

运行时用 microVM 隔离可能带有恶意的生成代码。延迟同样重要：工具环境启动太慢，整个智能体循环都会被拖慢。Bhardwaj 给出的数据是，Arrakis 启动不到 7 秒，而 macOS 上的传统虚拟机要 40 秒。打快照也只需个位数秒；还有一个待合并的 pull request，目标是把启动时间压到 1 秒以内。这些数字没有注明硬件、guest 配置、“就绪”的判定标准和快照大小。

其余功能让这台隔离的机器真正用得起来：

- 服务访问：Arrakis 负责端口转发，应用和 guest 内的服务可以通过公网 URL 和端口访问。 - 电脑操作：预装 Chrome 和 VNC 服务器，远程客户端可以直接操作浏览器的图形界面。 - 恢复：借助快照与恢复，智能体可以给多步骤工作流打检查点，回到之前的环境。 - 客户端接口：提供 Python API、Go 客户端、MCP 服务器和兼容 OpenAPI 的 YAML，既能直接集成，也能生成客户端。 - 定制：用 Dockerfile 决定 guest 里装哪些二进制文件和软件包。

这些功能组成同一个执行环境：隔离让运行代码更安全，网络、桌面访问和检查点则让这些代码对智能体真正有用。

03

宿主管理机器，客户机暴露服务

架构最上层是一个 REST 服务器，负责创建和管理 microVM 沙箱。每个沙箱里有一个代码执行服务器和一个 VNC 服务器，经过端口转发，guest 外部也能访问它们。用 Go 写的 Arrakis CLI 和 Python SDK 都是这个管理层的客户端，MCP 则提供另一条集成路径。宿主机必须运行 Linux，因为虚拟化实现依赖 /dev/kvm，也就是 Linux 访问硬件虚拟化的接口。

API 把机器的生命周期和机器内部的操作分开：

| 资源 | 职责 | |---|---| | VMs | 启动、停止和删除沙箱 | | Snapshots | 给虚拟机打检查点 | | Commands | 在虚拟机内执行命令 | | Files | 上传和下载 guest 中的文件 | | Health | 检查 REST 服务器的健康状态 |

把服务器放进分布式部署时，健康检查端点很有用。Python、Go、MCP，以及根据 OpenAPI 描述生成的客户端，最终访问的都是同一套底层管理系统。接下来要问的是：这些受管的机器到底提供了什么样的边界。

04

线程、命名空间与共享内核

先从 Linux 的执行模型说起。线程是可调度的单位，在内核里用 task_struct 表示。进程把一组共享资源的线程归到一起，共享的资源包括地址空间和页表。这些线程各有自己的线程 ID，但共享同一个进程身份，也就是线程组 ID，通常以 PID 的形式对外呈现。内核把守着对硬件的特权访问，用户态随便一条指令没法直接接管设备。系统调用会跨过这道特权边界；图里用 int 0x80 示意切换到内核态的过程。

容器首先解决的是打包问题。假设一个应用需要 Python 3.8 和 1.2 版的 foo，而服务器上装的是 Python 3.9、3.6 和 3.12，也没有 foo。把应用连同依赖一起打包，它就能在这台服务器上跑起来，不必为它重建宿主机的软件环境。对一个要运行任意用户应用的沙箱来说，光这一点就很有用。

在 Linux 上，容器靠两样东西组合而成：命名空间（namespace）限定资源的可见范围，cgroups 控制资源消耗。PID、mount 和 network 命名空间让进程只能看到机器的一部分。容器里能看到编号为 1、2、3 的进程，而同样这些任务在宿主机的 PID 命名空间里编号各不相同。宿主机可以查看子命名空间，子命名空间里的进程却看不到宿主机的进程树。cgroups 另外管着工作负载能用多少 CPU 和内存。限定视野和限定资源预算是两套机制，容器两者都需要。

05

缩小容器能触及的内核面

容器进程仍然直接跑在宿主机内核上。命名空间只是在逻辑上给资源分组，并不会给每个容器单独一个内核。如果某个进程利用宿主机内核漏洞拿到了宿主机级别的权限，后果可能是读取其他工作负载的数据、转储内存，或者冒充别的身份。容器里的 root 本身并不等于宿主机的 root；真正危险的是能突破隔离边界的漏洞利用。

一种应对办法是缩小进程能接触到的攻击面：

- Linux capabilities：只授予工作负载真正需要的特权操作。capability 检查会限制进程能走哪些特权路径。 - seccomp：屏蔽系统调用或过滤调用参数，进一步缩小进程能触达的内核行为。 - Minijail：一个启动器加一个库，用来套用沙箱策略，不用手工拼装每个底层 API 和错误检查。

Bhardwaj 根据自己在 Chrome OS 的经验推荐 Minijail。不过按它目前的威胁模型，它的目标是约束已知的二进制程序，并明确不负责安全执行攻击者控制的二进制文件或共享库。所以单靠它，还算不上能运行任意代码的完整沙箱。

加 jail 依然有价值，但堵不住所有绕过途径。Arrakis 要跑的是不可信代码，所以再往下一层是虚拟化：在应用和宿主机的虚拟化接口之间，再隔一个 guest 内核。

06

客户机执行、虚拟机退出与设备访问

虚拟机有自己的 guest 用户态和 guest 内核。应用发起系统调用，进的是 guest 内核，而不是直接进宿主机内核。CPU、内存、存储和网络仍由宿主机提供，但访问要经过另一套接口。管理这套接口的是虚拟机监视器（VMM），QEMU、crosvm 和 Firecracker 都属于这一类。在 Linux 上，VMM 通过 /dev/kvm 使用处理器的虚拟化功能。

VMM 还提供虚拟设备，包括块设备和网络设备。设备后端可以放在 VMM 进程里，也可以放在单独的沙箱化进程里，看具体实现。从客户端看，某个 VMM 线程好像卡住了，其实它正在处理器的虚拟化上下文里执行 guest 指令。演讲中讲到的设备访问路径是：

1. guest 执行到某个需要宿主机处理设备的操作。 2. 一次 VM exit 把控制权交还宿主机。 3. VMM 判断退出原因，借助宿主机完成相应的设备操作。 4. 结果交给 guest，guest 继续执行。

正因为有这种切换，虚拟机的性能有一部分取决于工作负载多频繁地需要宿主机介入。

Bhardwaj 认为，在硬件虚拟化下，CPU 密集型任务基本没有性能损失，因为 guest 指令直接在处理器上执行；不过他没有给出针对具体工作负载的测量数据。磁盘和网络密集型任务的切换开销会更大。把更多状态留在 guest 内存里，可以省掉一部分设备访问。容器则以原生宿主机进程的方式运行，没有这层开销，但共享内核的风险依然存在，而这正是要引入虚拟机边界的原因。

07

“micro”描述的是监视器

microVM 保留了硬件虚拟化，同时把外围的监视器做得更小、更坚固。据 Bhardwaj 介绍，这个术语和第一个用 Rust 写的 VMM 都出自 Chrome OS 的 crosvm 项目。选 Rust 有很实际的安全考虑：不可信的 guest 代码要和模拟设备打交道，设备实现里的内存安全 bug 就可能变成逃逸路径。Rust 降低了这一类实现风险。

crosvm 的架构还把各个设备隔离到单独的 jail 进程里。块设备进程只拿到存储操作需要的权限，网络设备进程只拿到网络操作需要的权限。这样即使攻破了某个后端，攻击者能做的事也更有限。按设备拆分是这套架构自身的特性，“microVM”这个名字本身并不保证这一点。

体积小，是因为支持的东西少。QEMU 覆盖了大量架构和设备；这里讨论的几个 microVM 监视器——crosvm、Firecracker 和 Cloud Hypervisor——只聚焦更窄的架构和设备集合，演讲里的说法是 Intel 和 ARM，外加几种必需的主要设备。设备少，初始化工作就少，启动路径少，运行时状态也少。microVM 里照样能跑相当完整的 Linux 工作负载：小的是 VMM。

08

为什么 Arrakis 使用 Cloud Hypervisor

Arrakis 选运行时，首先考虑的是多租户。不同客户可能在同一台服务器上运行生成的代码，绝不能让某个客户的工作负载拿到宿主机权限、读到别人的数据。microVM 还提供了一个很顺手的检查点原语：guest 内存是一块边界清楚的状态，VMM 可以直接保存和恢复。Bhardwaj 拿它和容器对比：容器的运行状态很难抓取，原因之一是它依赖共享的宿主机内核。

现有的几个监视器在实现上一脉相承，但侧重点不同。Bhardwaj 说 Firecracker 和 Cloud Hypervisor 都是从 crosvm fork 出来的；更准确地说，Cloud Hypervisor 的文档写明，它的代码同时源自 crosvm 和 Firecracker，还用了共享的 Rust VMM 组件。

| 运行时 | 演讲中提到的选型考量 | |---|---| | Firecracker | 面向 AWS Lambda 和 serverless 工作负载；提供 REST 管理 API | | Cloud Hypervisor | 面向通用 guest；支持内存热插拔、GPU 和快照 |

Bhardwaj 认为 Firecracker 的 REST API 更成熟，jail 也更严格。他最后选了 Cloud Hypervisor，是因为在他选型时，它具备他想要的快照和硬件能力，包括运行时内存热插拔，也就是以 PCI 设备的方式增减内存。有多家公司共同参与，也是他看重的一点。这些是他个人的选型标准，不是对几个项目的实测排名。

gVisor 代表了另一种设计思路。Bhardwaj 把它看作折中方案，并提到用 gVisor 或容器访问 GPU 比用 microVM 容易。它的机制也不只是加固过的普通容器：由 Sentry 实现应用的系统调用，并收窄暴露给宿主机的接口。哪种方案更安全，要看具体实现和攻击面，不能只看有没有硬件虚拟化。Arrakis 最终还是选了 Cloud Hypervisor。到这一步，架构里就有了一个具体的 VMM 进程，通过 /dev/kvm 运行 guest 的执行线程。

09

共享基础文件系统，隔离修改

虚拟机边界能保护宿主机，但代码仍可能搞坏自己所在 guest 的文件系统。删掉关键文件，沙箱就可能没法用了。Arrakis 把文件系统拆成两部分：所有沙箱共享一个只读的根镜像，每个沙箱另有一个私有的读写层。新建和修改的文件都落在这个沙箱的可写层里。所以给文件系统打检查点时，只需保存可写层，不用复制共享的不可变底层。

guest 在启动早期由 init.sh 先配好 OverlayFS，再把控制权交给正常的 init 进程。之后应用看到的就是一个普通的根挂载点，分层结构藏在下面。假设底层盘和可写盘已经挂到对应路径，核心的挂载操作大致如下：

``sh mkdir -p /state/upper /state/work /merged mount -t overlay overlay \ -o lowerdir=/base,upperdir=/state/upper,workdir=/state/work \ /merged ``

其中 /base 提供下层的只读目录树，/state/upper 存放私有改动，/state/work 是 OverlayFS 的工作目录，和 upper 目录在同一个文件系统上。底层镜像受保护，不代表合并后的 guest 视图就坏不了：whiteout 可以在不动底层镜像的情况下把下层文件藏起来。这套架构的作用是保住可复用的镜像，同时把每个沙箱的文件系统改动关在它自己的范围里。

10

把客户机连接到工具和用户

沙箱要能联网，才能调用 API 和其他工具；沙箱里的应用也需要一条通往用户的路。Arrakis 为每个沙箱创建一个独立的 TAP 设备，把这些虚拟网卡接到宿主机上的 Linux 网桥。再通过端口转发，把宿主机上的服务端口映射到 guest 里的代码执行服务器或 VNC 服务器。guest 网卡、宿主机网桥和转发策略，是这条路径上各自独立的几段。

网络代码先创建网桥并启用，再装上防火墙规则，管控宿主机和 guest 之间的流量。另一个函数在 Go 里调用 iptables，配置目标地址 NAT。核心操作可以写成：

```go package networking

import ( "os/exec" "strconv" )

func forwardTCP(hostPort int, guestIP string, guestPort int) error { destination := guestIP + ":" + strconv.Itoa(guestPort) cmd := exec.Command( "iptables", "-t", "nat", "-A", "PREROUTING", "-p", "tcp", "--dport", strconv.Itoa(hostPort), "-j", "DNAT", "--to-destination", destination, ) return cmd.Run() } ```

DNAT 把目标改写成 guest 的地址和端口。这条规则只是网桥、路由和防火墙整体配置中的一环，替代不了它们。整条路径配好之后，笔记本上的 VNC 客户端就能连到 microVM 里的桌面。

11

构建客户机，再暴露执行能力

虚拟机里跑的文件系统用 Docker 工具链来定制。演示中的 Dockerfile 基于 Ubuntu 22.04，装了常用工具、Chrome、Node.js、npm 和 Python，Chrome 通过 systemd 启动。改一改这个 Dockerfile，就能调整智能体手头的软件包，不用让它在运行时样样现装。用 Docker 构建镜像，也不会改变 microVM 这层执行边界。

创建虚拟机时，前面讲的各个组件会汇到一起：

1. 选定根文件系统和这个沙箱的可写 overlay 盘。 2. 分配 vCPU（在宿主机上就是线程），并从宿主机的可用容量里划出 guest 内存。 3. 配置 TAP 设备和端口转发。 4. 配置 vsock，供宿主机和 guest 通信。 5. 启动 VMM 进程，带上组装好的配置调用它的创建虚拟机 API。

这里 REST 服务器负责编排设备和资源，VMM 负责运行 guest。

在 guest 里，代码执行服务器提供文件上传、文件下载和命令执行三项功能。发一个命令请求，会拿到一段 JSON，里面是输出或错误信息。有了文件接口，智能体就能把应用代码和其他数据搬进、搬出自己的环境。Bhardwaj 敢开放这么强大的服务，前提是它待在 guest 虚拟机边界之内；同样的命令服务器要是直接跑在宿主机上，风险就完全是另一回事了。

Chrome 和转发出来的 VNC 服务器补全了交互环境。智能体可以通过命令 API 运行应用，用户或电脑操作客户端则在同一个沙箱里使用它的图形界面。

12

对运行中的机器打检查点，而不只是代码

像“做一个类似 Google News 的应用”这样的请求，范围大、描述又模糊，智能体很可能做到一半就失败。把任务拆成小步骤有帮助，但执行链一长，靠后的步骤一失败，前面大量工作仍可能白费。有了检查点，智能体就能回到最近一个正常的环境，改改计划接着做。Bhardwaj 还把这个思路延伸到并行探索多条执行路径。

需要保存的状态包括 guest 内存和可写文件系统层。智能体创建的文件、正在运行的进程、打开的 GUI 窗口，都属于要恢复的环境。Bhardwaj 把这种接着干的体验比作合上再打开笔记本电脑：有用的是整台机器的状态原样回来，而不只是找回源代码。

图中的执行树会退回最近一个正常的检查点，换一条路径再试。并发分支要格外小心：Arrakis 目前的 README 写明，在同一台宿主机上恢复会复用原虚拟机的 IP，所以必须先停掉或销毁原虚拟机。图里的并行探索是一个更宽泛的执行模型，并不说明可以随意并发克隆。演示的实现用的是 ext4 文件系统，目前正在研究改用 Btrfs，以获得原生的增量快照。

从概念上讲，打检查点的流程是：

1. 通过 VMM API 暂停虚拟机。 2. 给 guest 内存打快照。 3. 单独持久化可写的 overlay 盘。 4. 让虚拟机恢复运行，工作负载继续。

代码演示里，两步持久化的顺序有所不同：先暂停，并确保函数退出前会恢复运行，然后复制有状态的磁盘，最后调用 VMM 的快照 API。关键在于两者的配合：内存和可写磁盘的状态都要在虚拟机暂停期间抓取，同时要保证之后恢复运行，免得操作结束后沙箱一直挂着。

13

用 Python 驱动沙箱生命周期

Python 的入口是 py-arrakis：

``sh pip install py-arrakis ``

Arrakis 跑在你自己的基础设施上，客户端要把这台服务器的 IP 地址告诉沙箱管理器。列出现有虚拟机时，会返回它们的地址、对外暴露的端口等元数据。

演示的生命周期很简单：启动沙箱，执行命令，查看 JSON 里的 output 或 error 字段。环境到了一个有用的状态，就创建一个具名快照；虚拟机用不着了就销毁。以后提供虚拟机名称和快照 ID，就能把它恢复回来。虚拟化、存储和网络之间要协调的一连串操作，被客户端接口封装成了寥寥几个生命周期动作。

14

构建一个协作编辑器，再撤销一个功能

最后一个演示通过 MCP 服务器把 Claude Desktop 接到 Arrakis 上，让它做一个支持协作的 Google Docs 克隆。Claude 创建了一个沙箱，往里面发命令。重点是给模型一个完整的 Linux 环境，让它用熟悉的开发工具干活，既不用反复写提示词，也不用额外搭智能体框架。

协作编辑器跑起来后，Bhardwaj 打了一个快照，然后要求加上深色模式。Claude 加好了这个功能，Bhardwaj 表示协作依然正常。画面上的 CollabDocs 有两个浏览器窗口，一个深色、一个浅色，打开的是同一份文档，里面有两位用户分别留下的问候。

接着他改了主意，恢复到之前没有深色模式的检查点。这次回滚发生在功能已经成功加上之后，并不是因为实现出了问题。有了快照，哪怕只是想法变了，改动也能随时撤回。

这个演示也把网络能力和产品体验连了起来。Bhardwaj 强调，生成的应用确实能让多人借助联网服务一起编辑，而不只是在客户端模拟出协作的样子。沙箱提供了构建端到端应用所需的执行环境和网络连接，检查点则提供了一条退回早先运行版本的路。

15

更低的延迟、更便宜的检查点、更密集的宿主

接下来的工作，着眼于降低反复使用这套环境的成本。启动时间压到 1 秒以内仍是目标之一。改用 Btrfs，是为了让持久化和增量快照成为一等能力。要提高沙箱密度，就需要动态的资源管理，尤其是 memory ballooning，以及运行时内存的热插拔和移除。有了这些机制，宿主机可以随工作负载变化调整资源分配，不必把每个 guest 起初预留的内存当成永久占用，从而在一台服务器上塞进更多沙箱。

在创新与安全之间取得平衡

智能体的权限必须在每一个任务和每一次工具调用中都成立。安全评测、运行时强制执行和实时监控，让这一要求变得可测试、可执行。

熟悉 LLM 工具调用、服务凭据和基本的应用访问控制，有助于理解架构和示例。

01

一个组件的访问权限止于何处？

智能体把工作委派给任务或工具时，靠什么让每个组件守在自己的权限范围内？Don Bosco Durai 从数据治理的角度回答这个问题。他介绍自己是 Privacera 的联合创始人兼 CTO，也是 Apache Ranger 的创建者和 PMC 成员。Ranger 的治理能力已经通过集成延伸到云服务，比如 Amazon EMR、Google Cloud Dataproc 和 Azure HDInsight。到了智能体这里，同样的访问控制问题出现在一个能自己决定下一步做什么的应用里。

这套架构由四个部分组成：

| 组件 | 职责 | |---|---| | 智能体 | 推理，构建工作流，调用任务或工具 | | 任务 | 执行某个具体动作，可能用到 LLM、检索或工具 | | 工具 | 调用函数，访问互联网数据、数据库或服务 API | | 记忆 | 为智能体、任务和工具提供共享上下文 |

一个应用里可以有多个智能体，每个智能体又可以有多个任务和工具。图中，智能体、任务和工具都位于粉色的 VPC 区域内，分别连向 LLM、RAG、某个 API 和数据库。这些连线标出了两类位置：上下文从哪里流出组件，动作从哪里触达另一个系统。

Durai 指出，在演讲当时，大多数智能体框架都把智能体、任务和工具放在同一个进程里运行。数据库工具需要凭证，API 工具需要 token。如果这些凭证在共享进程里都拿得到，别的工具也可能读到它们。在他的例子里，服务凭证带着超级管理员权限。这属于权限过大的配置，并非服务账号天生如此，但一旦发生越权访问，后果会格外严重。

暴露的不只是凭证。智能体和任务用到的提示词也放在进程里，第三方库可能读到。调用一个防护不足的 LLM，又多了一个可被利用的攻击面。另一方面，智能体会根据收到的任务选择工作流，开发者没法简单列出一条固定的操作序列。访问共享，工作流又不确定，两者叠加，安全行为就比预先定义好执行路径的应用更难预判。

02

一个能用的智能体仍可能无法部署

这些架构缺陷会引发几类不同的故障。缺少访问控制，敏感或机密信息就可能泄露。模型不可靠，可能返回错误结果；提示词一改，即使底层应用代码没动，行为也会跟着变。所以，安全和可信不只取决于智能体有没有完成预定任务。

治理是另一道上线门槛。Durai 提到，就在那周二，他和一家客户聊过。他没有透露客户名字，只说是排名前三的征信机构之一。这家客户做了很多智能体，却迟迟没法投入生产。它几乎把智能体当成人类员工对待：入职、培训、监管义务都要先落实，才能授予访问权限。

客户举了个例子：没有相应的同意，加州居民的数据不能用于营销。欧洲数据和其他地区的要求，又对谁能访问哪些信息加了更多限制。这条营销限制是客户自己提出的要求，不代表加州法律的普遍规定。落到工程上，结论很具体：智能体不能只证明自己拿得到数据，还必须遵守数据使用的许可目的和范围。没有这些控制，客户就没法发布它的智能体。

03

评测、强制执行与可观测性

单靠一种控制手段解决不了全部问题。Durai 把这件事分成三个互补的层次，第一层是发布决策。除了测试回答质量和幻觉，还必须做安全与安全性评测。评测的目的是产出一份风险评估，决定智能体能不能进入生产环境。外部提供的智能体也要过同一道关，和内部开发的一视同仁。

执行控制提供评测要检验的那些控制手段。如果实现无法可靠地落实某项限制，评测就应该判为不通过，阻止发布。可观测性则负责覆盖开发和初期测试中没遇到过的行为。

| 层次 | 要回答的运营问题 | |---|---| | 评测 | 智能体的风险是否可以接受、能否部署？ | | 执行控制 | 运行时是否落实了权限和安全约束？ | | 可观测性 | 实际使用中发生了什么？什么时候必须有人介入？ |

三层相互依赖：测试让人对控制手段有信心，监控则揭示哪些地方需要重新审视这份信心。

04

在发布之前测试权限和失败行为

智能体的安全评测可以建立在成熟的软件发布实践之上。测试覆盖率检查重要行为有没有被测到。Docker 镜像扫描和依赖扫描找出漏洞和 CVE。Durai 说，上线前要修复中、高和严重级别的风险，同时做渗透测试，排查跨站脚本之类的漏洞。智能体照样需要这些检查；它由模型驱动，还会带来更多需要测试的情况。

先从用例和 ground truth 入手，定下回归基线。这样一来，改提示词、换库、换框架或换 LLM，都变成可以测试的变更，而不是想当然地认为行为依然没问题。Durai 还主张检查第三方模型有没有被投毒、有没有漏洞，并给库设定最低的漏洞标准。提示词注入测试要真正检验应用自身的拦截控制，不能因为用了 LLM 就默认有防护。

数据泄露评测要能区分这种情况：不同用户问同一个问题，但权限不同。以一个查询薪资和福利信息的 HR 智能体为例：

| 请求者 | 请求的记录 | 预期权限 | |---|---|---| | 员工 | 自己的薪资和福利 | 允许 | | 员工 | 其他员工的薪资和福利 | 拒绝 | | HR 管理员 | 其他员工的薪资和福利 | 仅当其角色允许时才允许 |

答得出来，不代表答得对。测试必须确认这个请求者有没有资格得到这个答案。还应该试探一下：恶意用户能不能钻漏洞，拿到正常使用时会被拒绝的记录。

另有两个评测方向，超出了读取数据的范畴：

- 越权操作： 智能体要修改系统，就必须代表正确的人或角色去做。测试要覆盖“有没有权限执行这次修改”，而不只是“有没有权限查看输入”。 - 失控的智能体： 一条糟糕的用户提示词、一段有问题的任务提示词，或者任务根本解决不了，都可能让智能体陷入死循环。这些故障场景应该放在上线前测试。

漏洞检查、泄露测试、操作测试和循环测试，合起来为发布所用的风险评分提供依据。Durai 给出了这些类别，以及它们支撑的决策，但没有规定具体的打分公式。

05

同时约束智能体和它所代表的人

风险评分的高低，取决于运行时控制做得好不好。库可能读到共享进程里的状态，所以访问敏感后端时需要零信任：一个组件在应用内部，并不足以成为信任它请求的理由。提示词注入检测和内容审核依然有用，但 Durai 讲企业级控制时，重点放在认证和授权上。

一个请求从用户传到智能体，从智能体传到任务，再从任务传到工具，最后才到服务 API 或数据库。认证负责确认请求背后的身份，防止冒充。授权负责决定这个身份能访问什么、能做什么。这是两项独立的要求：一个认证无误的请求，照样可能在要不该给的东西。

还有两层权限范围要守住。智能体有自己的角色，不能越界。它代表某个人行事时，那个人的权限也必须约束这次操作。委派不能让一个受限用户摇身变成拥有特权的后端调用者。 智能体能连上某个数据库或 API，不等于用户就有权拿到通过这个连接能触达的一切。

审批是另一道边界。传统的请假流程里，经理按预设流程审批申请。Durai 提出，可以单独设计一个审批智能体，自动检查请求和结果。它的权限由阈值限定：在允许范围内的事可以自动放行，超出范围的请求就交给人来把关。这是他提出的一种审批模式，还没有给出实际实现。

06

让身份一路贯穿到操作本身

只在应用入口做认证是不够的。用户身份必须贯穿每一次任务调用和工具调用，一直传到最终的数据访问或 API 操作。最后这道边界需要足够的上下文，才能套用正确的策略。否则，后端可能只看到一个权限很大的服务账号，分不清请求来自普通员工还是 HR 管理员。

用 TypeScript 写出这道边界，可以把 HR 的例子表达得很清楚。这里，userId 和 roles 来自可信的认证，agentPermissions 来自可信的智能体配置。工具先检查两层权限，再向存储请求记录：

```typescript type RequestContext = Readonly<{ userId: string; roles: readonly string[]; agentPermissions: readonly string[]; }>;

type Benefits = Readonly<{ employeeId: string; salary: number; benefits: readonly string[]; }>;

interface BenefitsStore { read(employeeId: string): Promise<Benefits>; }

async function readBenefitsTool( context: RequestContext, employeeId: string, store: BenefitsStore, ): Promise<Benefits> { const agentAllowed = context.agentPermissions.includes("benefits:read"); const userAllowed = context.userId === employeeId || context.roles.includes("hr-admin");

if (!agentAllowed || !userAllowed) { throw new Error("Forbidden"); }

return store.read(employeeId); }

async function benefitsTask( context: RequestContext, employeeId: string, store: BenefitsStore, ): Promise<Benefits> { return readBenefitsTool(context, employeeId, store); } ```

任务负责把身份传下去，工具在读取发生的地方执行策略。员工请求别人的记录时，在调用 store.read 之前就会被拒绝。不过，只有运行时同时阻止组件绕过受控的访问路径，这层应用检查才有意义。光传一个上下文对象，并不能把共享同一进程的库隔离开。

07

监控测试没有预料到的行为

发布前测过了，不代表智能体的行为就此固定。模型更新很快，智能体框架在演进，第三方库也可能开始表现异常。传统应用同样需要监控和漏洞管理，但智能体在这些老问题之上，又多了一层：它对用户意图的理解会变。

就算部署本身没变，也可能碰到测试从没覆盖过的说法。理想路径的测试可能只用一句熟悉的话申请请假，真实员工表达同一个意图时却可能说得完全不同。监控必须能看出回答随这些输入怎么变化。还要追踪有多少个人信息和机密信息被发了出去，一旦暴露量意外上升，就能触发处置。

请求量大到一定程度，逐条审查每次交互就不现实了。先定义故障指标和可接受的容忍度，观测到的故障率超过容忍度时再发告警。故障率上升，可能是智能体行为异常，也可能是有恶意用户在尝试攻破应用。告警只说明需要排查，单看故障数量并不能确定原因。

Durai 接着展望了行为异常检测，并拿成熟的用户行为分析（UBA）做类比。这样的系统不只统计已知故障，还会判断智能体是否仍在可接受的运行边界之内。他明确表示，在演讲当时，智能体异常检测还远没达到他设想的能力。目标是建立一套安全流程，近乎实时地呈现智能体在线上的实际表现。

08

一套生产安全流程和一份开源邀请

所以，生产就绪不只是一次性的评测结果。无论是部署内部开发的智能体，还是引入第三方的智能体，都由风险评估把关。准入之后，靠护栏、执行控制和安全沙箱约束运行。再通过实时或近实时的可观测性，让异常尽早暴露，及时调整系统。沙箱对开头那种架构尤其重要：如果不可信的组件能绕开权限检查，单靠这些检查撑不起整条安全边界。

Durai 最后介绍了 PAIG。录像里称它为刚刚开源的 PAIG.ai 安全防护方案。安全与合规的范围太大，不是一家公司能搞定的，所以他邀请设计合作伙伴和贡献者一起来开发。感兴趣的读者可以通过邮件或 LinkedIn 联系他。他的实际目标，是让智能体安全成为一门共同的工程学科，用可靠的控制手段和证据，让有用的智能体真正走进生产环境。

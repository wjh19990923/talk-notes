主动图智能体运行时（BabyAGI 4）

一个不可变的事件日志既能记录智能体做了什么，也能记录它如何改变自身，为共享状态的工作者提供了记忆、恢复和受控自我修改的基础。

熟悉 LLM 工具、智能体循环和基础 Python 会有帮助；图运行时和事件溯源会在出现时讲解。

01

为什么长时间运行的智能体仍然会坏？

长时间运行的智能体总会出问题。既然智能体已经强到能自己写软件，开发者为什么还得一遍遍重写智能体本身？对 Yohei Nakajima 来说，这个问题引出了一个具体的研究目标：做出能构建自身的最简系统。ActiveGraph 是他给出的实验性答案。在这套架构里，智能体做过的每个动作、之后对它的每次修改，都能拿出来检查。

探索始于 BabyAGI，Nakajima 在 2023 年 3 月做出了它。它在公众中的热度远超实际能力；按他自己的评价，最初那个系统根本跑不通。他前后迭代了九版，大多在探索某种形式的自我改进。图结构一再出现：先是在 Instagraph 和 Mindgraph 里用于检索，后来又用来表示代码、函数和日志。做这些实验的同时，他还通过 Untapped Capital 和一支智能体基金投资智能体公司。ActiveGraph 把这个反复出现的图结构带进了一个面向可审计智能体的事件溯源运行时。

02

日志投射出智能体的状态

架构的出发点在 The Log is the Agent 中有详细阐述，它把常见的构建顺序倒了过来。通常，智能体先有 LLM、响应 API、工具和记忆，再在这些组件外面套一层日志。只要有人刻意去组装，这种做法也能提供同类的可观测性和控制能力。ActiveGraph 则从日志起步。

关键在于多记一样东西：除了智能体干了什么活，还要记录智能体本身的变更。智能体的执行历史和开发历史往往分散在不同系统里。ActiveGraph 把两者放进同一份不可变的事件历史，再把这份历史投影成一张表示当前状态的图。比如一条提示词改过好几次：日志保留每一次修改，查一下图就能拿到当前生效的版本。

给这张图挂上行为（behavior），状态就“活”了起来。图一变化就触发某个行为；行为发出事件；事件更新图；更新后的图又可能触发下一个行为。这些 worker 可以是确定性函数，也可以包含 LLM 调用。它们不直接互相通信，而是通过共享状态协调。最终得到一份带类型的历史：既记下做了哪些工作，也记下哪些变更决定了工作的做法。

03

策略管理变更，事件承载变更

不是每种变更都该有同样的权限要求。策略（policy）决定图可以怎样变化：

| 变更 | 可能的策略 | | --- | --- | | 添加一篇来源文章 | 自动放行 | | 修改提示词 | 需要人工批准 | | 修改一条事实 | 检查有没有相互矛盾的事实 |

这些是对同一条变更路径施加的不同管控，而不是为日常工作和智能体修改各设一套机制。

带类型、不可变的历史支持重放、回滚和分叉。所以 ActiveGraph 是一个运行时，而不是一套规定好的智能体框架：常见的框架都能在它之上重建，前提是各组件通过共享状态通信。以 LLM 为中心的设计里，大家通常盯着消息看；在这里，日志取而代之，成了检查的核心单元。

变更规则很严格：可以查询图，但不能直接改它的状态，而要发出事件。哪怕一个看上去只是添加对象的操作，也必须产生事件，这样图的新状态才始终能从历史推导出来。否则，图里就可能出现重放无法重建的变更。

04

从一个目标到调研和备忘录

假设有个目标，需要先做调研、再写一份备忘录。规划器订阅“目标创建”，发出事件添加两个任务对象（调研、写备忘录）以及两者之间的关系。这条依赖本身可以带一个关系行为：调研一完成，解锁行为就让备忘录任务变为可执行。协调靠的是关系和状态转换，而不是一个 worker 直接调用另一个。

用一个小小的 Python 例子能把这个事件流讲得更具体。这里 project 从事件中重建任务状态；关系行为不直接改备忘录任务，而是返回另一个事件。下面的事件名和记录只是为了讲解在本地定义的，并不是 ActiveGraph 的 API 调用。

```python from copy import deepcopy

def project(events): tasks = {} for event in events: if event["kind"] == "add": tasks[event["id"]] = deepcopy(event["value"]) elif event["kind"] == "update": tasks[event["id"]].update(event["changes"]) return tasks

def unblock_relation(tasks, dependency): source = tasks[dependency["from"]] target = tasks[dependency["to"]] if source["status"] == "done" and target["status"] == "blocked": return [{ "kind": "update", "id": dependency["to"], "changes": {"status": "ready"}, }] return []

log = [ {"kind": "add", "id": "research", "value": {"title": "Research", "status": "ready"}}, {"kind": "add", "id": "memo", "value": {"title": "Write memo", "status": "blocked"}}, ] dependency = {"from": "research", "to": "memo"} log.append({"kind": "update", "id": "research", "changes": {"status": "done"}}) state = project(log) log.extend(unblock_relation(state, dependency)) state = project(log) ```

最后一次投影后，备忘录变为就绪，已完成的调研任务和两个任务的标题也都保留着。历史里依然留着触发解锁的那次状态转换。

订阅能表达的不只是对象类型。矛盾检测器可以设定条件：只有新建的主张与图中另一条主张相矛盾时，才收到通知。更复杂的条件还可以把置信度考虑进来。视图（view）把类似的思路用在上下文上：用一条图查询选出某个行为能看到的那部分状态。这样上下文管理就有了一个可编程的边界，也不妨碍再用其他筛选上下文的手段。

05

审批关卡与可组合的功能包

对受保护的状态，修改意图会先变成一个提议补丁。策略决定它在改动图之前要过测试、要人工批准，还是两者都要。提议和已应用的变更是两种不同状态：智能体可以先拟出修改，不必事先拥有执行它的权限。

pack（包）把对象 schema、工具、确定性行为、LLM 行为和一份 pack 策略打包在一起。把多个 pack 组合起来，就能同时用结构定义和执行规则搭出一个框架。这比加一个 skill 的覆盖面大：模块定义了有哪些对象、谁来响应它们、变更受什么约束。Nakajima 觉得手写这种组合不太直观，但他说 AI 编程工具处理得很好。

在演讲展示的版本里，事件类型是固定的，对象类型由用户自定义。不过目前的运行时文档也允许在框架事件之外使用自定义的应用事件字符串，所以这条限制只适用于演示的那个版本。

06

不让 worker 之间直接调用的 ReAct

传统智能体往往以一个 while not done 循环为核心。ActiveGraph 把这种推进过程拆散，交给各个监听共享状态的行为。Nakajima 把这种模式和早年的黑板架构（blackboard architecture）联系起来，近一点的例子是 Kafka：多个 worker 通过一个公共底座协调。过去这些 worker 功能单一、行为确定，架构写起来也可能很别扭。如今 worker 能推理了，代码也能交给 AI 来写，这让他有理由重新拾起这种架构。

在这种安排下，ReAct 智能体依然能保留熟悉的“推理—行动”流程。目标创建会添加一个思考对象；思考对象一创建，就触发推理函数。每个阶段都会留下状态，供其他行为观察。变的是协调机制，推理和行动的需求没变：没有哪个 worker 需要直接调用下一个。

07

把日志用作记忆——也用作恢复点

第一个实验想验证：日志本身能不能充当记忆。检索方法把 embedding 和日志里本就有的顺序结合起来。在 LongMemEval 上，基本流程是：

1. 对日志中的消息和新来的查询做 embedding。 2. 检索与查询相关的消息。 3. 把每条命中消息前后的相邻消息一并带上。 4. 把选出的材料装进可用上下文，然后作答。

最初的实验没有做语义摄入，也没有提取事实或实体。它借日志的结构保留对话的前后语境，而不是只依赖孤立的向量匹配。

检索部分的完整幻灯片上展示了 85.6% 的 LongMemEval 成绩。这只是展示出来的结果，算不上严格的基准对比：演讲没有说明数据集版本、上下文预算，也没给出完整的评测配置。从架构上看，这种做法的吸引力在于：记忆和日志本来就有大量重合的信息；只用一个存储，这些重合的记录就不会慢慢对不上。

后来 Nakajima 试了语义摄入，说分数有所提升，但没继续优化就转去做别的了。更让人印象深刻的运维结果，来自一次中途被打断的评测。

据 Nakajima 讲述，一次 500 道题的评测跑到第 350 题左右时 API 访问失效；他换了 key 之后，系统回滚一步，从第 353 题左右接着跑。已经完成的工作不必从头再来。这是他在一次长时间运行中亲历的恢复，并不能保证智能体调用的每个外部工具、产生的每个副作用都能这样恢复。

08

编程、研究与可互换的能力

运行时就绪后，Nakajima 让 Replit 在它之上构建一个编程智能体。做出来的东西直接带有事件日志和图，他并没有另外要求设计这些记录。他明确承认，LangSmith 之类的工具也能提供类似的可观测性；他想说的是，这个运行时让这些记录成了构建过程的一部分。之后做的一个研究智能体也一样，在图里记下了证据来源和相互矛盾之处。

为了朝 OpenClaw、Hermes 这类更通用的助手迈进，他组装了 ActiveGraph Packs，包括 core、tool、secret、memory、identity、communication 和 chat 等 pack。每个 pack 都带来自己的对象类型和行为。一个 memory pack 可以直接换成另一个，因为模块里装的是实现这项能力的对象和规则，而不只是教 LLM 怎么用的说明。

09

自我修改需要一个验收测试

Regimes 更进一步：从记录智能体的变更，走到控制智能体如何提出变更。失败分类器先判断哪里出了问题，再根据分类结果决定智能体的哪一部分可以改。这样修复过程就有了受约束的目标，而不是想改什么就改什么。

Nakajima 回忆，他先在大约 20 道 LongMemEval 题上诊断失败原因，再拿 50 道别的题测试修改效果。已发布的实现规定的是 50 道优化题和 100 道互不重叠的确认题；不要把文档写明的这些条件，和他在台上回忆的探索性流程混为一谈。两者的共同机制是：用来引出修复的样例，和用来评判修复的样例，必须分开。

提议的变更要走一条层层把关的路径：

1. 分叉智能体，针对允许修改的组件提出补丁。 2. 运行静态关卡检查。 3. 运行沙箱关卡检查。 4. 评估候选版本对答案的影响。 5. 只有满足接受策略，才晋升为正式版本。

演讲里说，最后一步只接受准确率有提升的修改。但论文的默认关卡允许留出集准确率不变，所以文档里的规则是“不退步”，而不是严格要求提升。论文也讨论了过度晋升的问题：通过关卡，不代表一定能持续累积进步。

Nakajima 说，有几次运行跑了 8 轮或 13 轮循环，只接受了四五个补丁。他形容这些提升幅度不大，但统计上显著。已发表的证据要窄一些：LongMemEval-S 的五个划分里，只有两个报告了显著性，其中一个没有针对逐次晋升做校正；由于各划分共用同一个题库，合并结果只作描述性参考。这能支撑一个有边界的实验结论，不能推广成“这个运行时能改进所有智能体”。

历史里保留的不只是晋升的版本，还有那些没过检查、或者没起作用的提议。被拒绝的修改也成了可用的实验记忆：之后再尝试时，可以先看看哪些办法已经试过，不用一次次重新撞上同一个无效的修复。

10

一个研究它自己运行时的实验室

下一步是 ActiveGraph Lab：一个研究智能体，会读项目的博客文章和代码仓库，提出想法，再问 Nakajima 能不能跑实验。获批后，它运行实验，并就结果写一篇博客。人工授权这道边界始终摆在明处。

Nakajima 说，这个实验室曾在自己的代码里发现一个错误，申请了修复权限，写了一个 pull request，他审过后合并了。它还把另一个仓库里的 pack 装进了自己，并记下了“pack 可以跨仓库模块化使用”这一发现。这些都是系统自我扩展、自我修复的早期例子，审批和合并依然是流程的一部分。

11

一次演示稿修改变成一个实验

Kaggle 上一场宝可梦集换式卡牌游戏比赛，提供了另一种测试。参赛要提交一副卡组和一个确定性智能体，对局中不用 LLM 推理。按 Nakajima 的描述，每小时都会和新参赛者对战，类似 Elo 的分数随之升降。LLM 辅助的工作发生在对局运行时之外，用来开发和评估候选改动。

Nakajima 说，他用 Claude Code 和 Replit 跑了大约 80 轮实验。一个看似随口的要求——加几张能量卡——变成了一个待测试的提议，而不是直接采纳的修改。示例中的评测方案是：与三个参照智能体模拟对战 200 局，以胜率提升和 Wilson 分数判据作为接受条件。他没有给出具体的接受阈值，所以这个例子说明的是关卡的结构，而不是一条可复现的统计规则。

每一轮都会生成一份报告，说明改了什么、结果如何、结论是什么。Nakajima 估计，约 80 个提议里有 20 到 30 个通过，分数也在逐步提升。他还提到一个 27% 左右的数字，但没交代清楚，没法判断那是胜率还是排行榜名次。

最与众不同的好处，是智能体知道哪些实验失败了。随手一改再改，最后也许能得到一个能用的版本，却丢了先前失败的原因。在这里，明确的接受策略要求先评测再晋升，成功和落选的候选都会留下来。有了这份历史，下一次实验就能从更好的起点出发。

12

调试移进了数据库

综合这些项目，Nakajima 个人的感受是：AI 编程工具很擅长设计通过共享状态通信的 worker。他给出的解释只是一个假说：黑板系统和 Kafka 背后有几十年的架构讨论，可能比新兴的 LLM 智能体开发提供了更多训练样本。这是对他个人体验的一种解释，不是对编程能力的实测对比。

更具体的一个工作流变化，是调试的地方变了。他的编程智能体开始直接查 ActiveGraph 数据库，不再翻会话日志，因为这些记录本来就类型清晰、结构已知。跨仓库加载 pack、长时间运行不用重启就能恢复、能查看失败的实验，也都是反复体现出来的好处。这些加在一起，让智能体自己的历史成了日常开发界面的一部分。

13

智能体既需要推理也需要经验

收尾时，Nakajima 的提议超出了运行时机制本身。他明确说模型训练不是自己的专长，在这个前提下提出：长时间运行的智能体除了预测性世界模型，还需要一个经验性世界模型。预测模型提供先验；经验模型记住的是这个智能体自己遇到过什么、做过什么。他把两者的关系比作海马体、记忆重放、做梦和睡眠，设想记录下来的经验反过来塑造先验。这只是推测性的类比，不是对生物记忆机制的定论。

这一区分挑战了“模型越强，框架就会消失”的预期。推理能力再强，也不会自动带来某个智能体的决策、失败和修订历史。Nakajima 正在形成的假说是：两者缺一不可。人也不只由推理能力定义，信念、知识和行为同样从经历中生长出来。照这个思路设计的智能体，可以从自己的日志中获得身份。

他建议的探索方式很实际：找一个已经了解你偏好的编程智能体，让它去查查 ActiveGraph，做一个你觉得有用的东西，再说说这个运行时有没有帮上忙。要检验的是：一个有用的实现，把自己的行为和演进记在同一个地方，能不能从中受益。

构建能自动化知识工作的 AI 智能体

文档自动化需要的不只是检索：它还需要能保留文档结构的工具，以及把分析、人工审核和行动连接起来的工作流。

熟悉检索增强生成（RAG）和 LLM 工具调用，有助于理解架构讨论。

01

知识工作自动化就只是 RAG 聊天机器人吗？

提高效率、改善决策，听上去都有用，可智能体具体要做什么才能做到？知识工作自动化，就等于做一个 RAG 聊天机器人吗？还是说，拿到答案之后的活，它也能接着干？Jerry Liu 开场就抛出了这个问题。

具体场景是：员工读文档，再据此做决策、采取行动。Liu 估计，企业 90% 的数据都在文档里。这些文档有 PDF、PowerPoint、Word 文件，也有电子表格。投资银行家或客服人员得先读懂它们，才能做任何有用的事。智能体能接手这条链路里更多的环节：分析大量非结构化上下文，研究问题，综合结论，然后采取行动。

由此衍生出两类产品：

- 辅助型智能体帮人更快拿到信息，通常通过聊天界面。 - 自动化智能体执行例行任务，可以在后台运行，不需要人一直盯着。

两者都围绕知识工作，但对使用者的要求不一样。

02

工具暴露能力，编排编码任务

无论哪一类，都需要两样东西：好用的工具，和一套智能体架构。工具把智能体接到外部上下文和操作上，Liu 认为这正是 MCP 和 A2A 要解决的接口问题。编排决定这些能力怎么为任务服务。通用的推理循环让模型自己选下一步；受约束的工作流则把更多业务逻辑写进显式的控制流。

文档工具箱和工作流解决的是两类问题。 先要让文档能通过可靠的操作访问到，再由架构来协调这些操作。两者结合，才有了各种应用。

03

构建工具背后的预处理层

Claude、ChatGPT 这类通用界面，要处理企业文档，照样离不开工具。Liu 在这里拿朴素 RAG（naive RAG）作基线：先检索，再一次性生成答案。文档智能体需要这个能力，但可能还要找到某个特定文件、查看它的元数据，或者直接操作它。检索只是工具箱里的一项操作。

这个工具箱建立在一条预处理流水线上：

1. 连接与同步。 把 SharePoint、Google Drive、S3、Confluence 等来源的数据转成可访问的表示形式，权限和元数据随内容一起同步。 2. 解析与抽取。 还原文档的含义和结构，包括表格和图表。 3. 按目标操作建索引。 把得到的表示存进向量索引、SQL 表、图数据库或其他合适的系统。

存储怎么选，取决于智能体要做什么；向量索引不是唯一的去处。

Liu 把这样形成的一组接口称为文档 MCP 服务器（Document MCP server）。它的作用不止是暴露一个检索端点：

| 操作 | 提供什么 | | --- | --- | | 语义搜索 | 通过模糊匹配找到相关内容 | | 文件查找 | 文件本身及其元数据 | | 文件操作 | 直接操作文件 | | 结构化查询 | 基于抽取数据的聚合洞察 |

这些接口好用，是因为源材料事先经过了处理和结构化。光给工具起个顺手的名字，智能体拿不到可靠的聚合结果。

04

保留推理所依赖的结构

复杂文档是给人看的。内嵌的表格、图表、图片、不规则版式、页眉页脚，都带着信息，解析时可能丢失，也可能被搞乱。预处理一旦破坏了这些信息，下游模型再强也没法可靠地找回来。文档理解是智能体推理基础设施的一部分。

传统做法常用专门的模型，针对特定类型的文档调优。语言模型和视觉模型提供了更通用的起点：哪怕只是把 PDF 截图发给模型，也能还原出不少有用信息。但在 Liu 看来，截图加提示词只是基线，算不上完整方案。他的做法是把传统解析和语言、视觉模型穿插结合，再在测试时多花一些 token，做智能体式的校验和推理。

演讲中介绍的解析服务适配了多种模型，包括 Claude Sonnet 3.5、Claude Sonnet 4、Gemini 2.5 Pro 和 OpenAI GPT-4.1。Liu 称其解析模式优于现有的开源和商业方案，但这部分没有给出基准测试方案，也没有具体数字。托管平台把这些能力打包成解析、抽取、索引三类操作，放进文档工具箱。

05

一张电子表格不一定是一张表

Spreadsheet Agent 把工具箱扩展到一种常见却难处理的文档格式。Excel、Google Sheets 和 Numbers 里装着大量日常工作，可一张表不一定是干净的二维表格。演讲里的例子，行和列都有空隙。把这种布局当成普通表格数据，就会漏掉赋予单元格意义的那层结构。

这个智能体把未规范化的工作簿转成规范化的二维格式，原始版本和规范化版本都支持问答。它当时还处于早期预览阶段，是对解析、抽取和索引的补充。演示中，先上传一份合成数据集，转成表格，再通过提问获取洞察。关键在于理解电子表格的语义结构，并通过专门的工具把这种理解交给智能体。

对这个任务，Liu 认为有意义的基线是带代码解释器的 LLM，而不是 RAG 或 text-to-CSV 一类的技术。他报告了一项内部评测的大致准确率，据他介绍，评测用的是合成的 Excel 表格：

| 方法 | 报告的准确率 | | --- | --- | | 带代码解释器的 LLM | 约 70–75% | | LlamaIndex Excel 智能体 | 95% | | 人工手动转换 | 90% |

这些只是报告出来的评测结果，不能保证电子表格处理普遍都有这样的表现。演讲没有给出样本量和评分标准，也没有按任务拆分结果，没法把规范化的准确率和问答的准确率单独区分开。

06

把电子表格结构变成专门的工具

这套机制从理解结构开始。Liu 介绍，他们用强化学习，并针对文档的具体格式做适配，学出表格的语义地图。他没有给出训练方法，也没有证实模型在处理每个工作簿时都会学到新权重。架构上真正值得借鉴的是这个中间表示：先弄清表格怎么组织，再让智能体去操作。

语义地图随后变成一组专门的工具，交给智能体使用。智能体不必从头摸清整个结构、逐一写出每个操作，而是借助从地图派生出的能力来推理。通用代码生成仍是基线，Liu 预计它会随着模型进步而变好；在那之前，专门的工具帮它应对电子表格的结构。

07

灵活的助手依赖人的指导

文档工具就位后，下一个要定的是：控制流要规定到什么程度。最受约束的一端，由应用显式定义每个步骤；最开放的一端，只给模型工具，让它自己决定怎么做。Liu 把 ReAct、函数调用、CodeAct 和深度研究都归入后一类。

助手界面通常接收自然语言输入，要么呈现信息，要么产出一份知识工作成果。灵活的循环适合这种交互，因为用户可以一路引导、纠正、劝说智能体把任务做完。智能体自由度更高，人的参与也可以更多。 有了聊天界面，人随时可以掌舵，熟悉的 RAG 聊天机器人也就扩展成了更广义的工作助手。

08

约束自动化，并保留审批边界

自动化改变了交互的约定。系统不再一轮一轮地帮人查信息，而是分多个步骤处理一项例行任务。它可以接收一批输入、在后台运行，也可以由人手动触发。既然人不再引导每一步，架构通常也会收得更紧。

执行时人参与得少，不等于取消审核。Liu 介绍，审核放在接近结尾时批量进行：工作流产出结构化结果或决策，经批准后，再通过 API 集成分发到下游系统。这道关口把“准备好的结果”和“获得授权的外部操作”分开。

财务数据规范化、数据手册抽取、发票对账和合同审查都属于这种模式。Liu 还提到 Laurie Voss 的 Invoice Reconciler，作为社区案例，不过他跳过了视频，没有演示具体实现。

09

后台自动化可以为前台助手供料

两种界面可以是同一个应用的不同层。自动化在后台运行，负责抽取、转换、结构化和决策，同时保留人工审核。助手在前台，让人和处理好的信息打交道。

这样就形成了一种好用的组合：自动化流水线处理非结构化上下文，再把工具暴露给研究助手使用。流水线本身可能也要靠智能体推理，才能应对五花八门的文档。但不是每个工具都需要智能体；普通的确定性操作，照旧做成普通工具就行。关键是，助手能在准备好的数据上拿到可用的能力。

10

财务尽职调查结合了数据导入和副驾驶

Liu 举了 Carlyle 的案例：一个杠杆收购智能体，两种界面都用上了。自动化这一侧摄取公开和非公开的财务材料，涵盖 Excel 表格、PDF 和 PowerPoint。定制的抽取算法把这些文档转成结构化信息，抽取过程中有人工审核。

有了这些准备，面向分析师的 copilot 才派得上用场。它基于结构化数据，帮团队获取洞察、生成报告。在这个客户案例里，助手的能力取决于背后的数据摄取和审核；聊天界面只是一条更大的文档工作流露在外面的那一端。

11

企业搜索增加了对文档集合的推理

企业搜索主要属于助手这一侧。先为不同数据源定义集合，再在这些集合之上提供针对具体任务的智能体。推理层把检索扩展成一个过程：拆解用户的查询，研究相关信息，再综合出答案。产品看上去仍是搜索框或聊天界面，但每次回答背后可能跑了好几步。

12

规格书导入把业务规则变成结构化输出

最后一个例子回到自动化：为一家未具名的全球电子公司摄取技术数据手册。过去，这些文档要靠人大量处理和审核。工作流写入了这家公司特有的业务逻辑：解析每份数据手册，抽取所需信息，对照规则匹配，再把结构化结果写进 SQL。配图把数据手册连到 LlamaCloud 属性抽取智能体、SQL 工具和 LlamaIndex 设计 copilot。

人工审核仍是工作流的一环。Liu 说，如果整个流程能端到端跑通，就有望替代技术文档撰写人员数周的工作；但他没有报告实测的提速数据。真正的变化在于，从源文档到业务规则再到结构化输出，打通了一条完整路径：人负责审核，不必再手动完成每一次抽取。

你的 GPU 邻居能“听见”你的模型

Branislav Brzak 追踪了一个 H100 上的时序侧信道：从读取攻击者自己的内存，到识别模型和工作负载的指纹，然后展示了跨 NVLink 时会发生什么变化，以及运营方能观察到什么。

01

独立的内存仍然共享一个时钟

A model can keep its prompts and answers inside its own GPU memory and still reveal something to a neighboring tenant. In Branislav Brzak’s H100 experiments at Stealthium, the neighbor watches timing: when inference runs, how quickly tokens arrive and which patterns repeat within their generation. The attacker needs neither root access nor a traditional software exploit.

The opening demonstration places the victim’s inference dashboard beside the attacker’s inferred model and workload. Brzak reports 97% accuracy for identifying model architecture and depth, and 99.3% accuracy for decoding speed. Timing also exposes busy periods and supports estimates of token counts and response length. These are reported results from the tested configurations, rather than guarantees for arbitrary shared deployments. The important limit is explicit: the attack does not recover the actual prompts, answers or their contents.

The first setup uses NVIDIA’s Multi-Instance GPU, or MIG, to divide an H100. Each slice has physical compute resources and dedicated VRAM. The victim receives a larger slice with 40 GB of VRAM; the attacker uses a smaller one with 10 GB. That division makes the experiment a test of what survives hardware isolation, rather than an attempt to read another tenant’s allocated memory.

02

一个 GPU 范围的屏障拖慢了另一个切片的读取

MIG isolates compute resources, memory capacity, bandwidth quotas and faults. It also partitions the L2 cache: one instance cannot evict another instance’s cache entries. The remaining connection is a GPU-wide memory barrier, or membar. A barrier issued by one instance affects every L2 partition on the card. Consequently, a tenant can experience slightly slower reads of its own memory while another tenant is busy.

The probe turns that slowdown into a repeated measurement: load from a small buffer owned by the attacker, time the load, and repeat every five microseconds. No step requires a read from the victim’s memory. Brzak credits the researchers behind Behind Bars at USENIX Security for both this probing primitive and the underlying MIG memory-barrier leak.

How much does the neighboring workload change the measurement? The slide shows medians of 715.9 ns idle and 719.1 ns while serving Qwen3-8B, labeling the gap about 3 ns; the spoken account says microseconds. That small shift is useful because the attacker records a time series, preserving when slowdowns occur and how they repeat. The signal comes from the structure of those measurements, beyond the difference between two medians.

The idle and Qwen3-8B traces have medians of 715.9 ns and 719.1 ns, about 3 ns apart; the traces show the time-varying measurements behind that small median shift.

03

token 节奏给出速度，token 内部的峰值给出结构

With an eight-billion-parameter model running on the victim slice, the trace shows one burst of GPU activity per generated token. Frequency analysis of the attacker’s latency measurements finds a fundamental at 81 Hz: the recurring token-generation cycle corresponds to 81 tokens per second. Harmonics accompany it because the work inside each token has its own structure, rather than forming one smooth pulse.

What does that structure look like inside a token? The demonstrated time-domain trace contains 39 bumps. Green peaks mark layer invocations; orange peaks mark additional processing between layers. The distinction matters: counting every visible bump as a model layer would overestimate depth. The trace connects two scales of observation—the spacing between tokens and the repeated work within each token.

Token rate is useful but ambiguous. Two eight-billion-parameter models in the comparison decode only 1.6% apart in speed. A tempo measurement can narrow the possibilities while leaving those models nearly indistinguishable. The next step therefore looks for the layer-related structure within the timing signal.

A fold-and-average procedure brings out recurring peaks. Across 22 traces, the resulting count lies a mean distance of only 0.028 from an integer. Brzak uses this near-integer result as evidence that the pattern follows discrete model operations: a fixed hardware frequency divided by varying token rates would not generally land so close to whole numbers. The observed counts correspond to model depth plus one to three extra peaks, retaining the distinction between layers and other processing.

04

在没有标注训练集的情况下拟合候选深度

The depth estimator is a small best-fit procedure, described as fewer than 30 lines of code. It checks candidate depths from 16 through 48, measures how strongly each candidate’s expected signature appears in the recorded trace, and selects the strongest fit. It needs no labeled training set. Tempo and harmonic structure supply the evidence used to compare candidates.

How decisive is that comparison? In the presented eight-billion-parameter example, the 36-layer candidate wins clearly over competing depths. Because the procedure fits a structural signature rather than looking up a previously labeled trace, Brzak proposes that it can estimate depth for unseen models, including proprietary or unreleased ones. Recovering depth alone does not supply the name of an unknown model; it reveals an architectural property that can help fingerprint it.

The estimator also produces a confidence value. In the reported testing, the only two incorrect answers were the two least confident ones. Confidence therefore helped identify the uncertain fits in that test, although the recording does not establish a confidence threshold that operators could apply universally.

Related models make the task harder. The comparison includes Llama 3 8B, Llama 3.1 8B and DeepSeek’s R1-Distill Llama 8B, all sharing a 32-layer backbone. Their common architecture preserves much of the timing signature, so depth alone cannot separate them. Brzak reports a median per-layer latency shift of only 1.6 nanoseconds and says the classifier nevertheless distinguishes the models. This is the demanding case: the broad structural fingerprint stays similar while the distinguishing timing differences become very small.

05

推测解码让文本类别影响时序

The next experiment keeps the timing channel and changes the question: is the model producing prose, code, JSON or a retrieval response? It issues a verdict every half second using the preceding five seconds of measurements. Of 40 verdicts, 31 are correct; majority voting correctly identifies all four complete responses in the demonstration. Comparing the predictions with the actual workload would show both the short-window mistakes and why a response-level vote can still succeed.

The rows show prose and code classified correctly, JSON and retrieval misclassified, while the summary reports 31 of 40 short-window verdicts and all four complete responses named correctly.

This result depends on speculative decoding, enabled for the experiment and described here as an opt-in feature in vLLM. Speculative decoding drafts tokens and accepts some number of them at each step. Text predictability changes how many drafts are accepted; that changes step timing. The probe observes this timing consequence and uses it to infer a workload category. It still does not read the generated text.

The tests span 11 configurations, including dense and mixture-of-experts models, with BF16 and FP8 precision. The workload-dependent signature appears throughout, but its strength varies sharply: the reported spread ranges from 70.2% in one configuration to 0.9% in another. Prose runs fastest in 10 of the 11 configurations. That repeated ordering helps explain why category inference can work, while the wide variation cautions against expecting the same separation everywhere.

The inference thus has two useful conditions: an attacker already has information about the model, and speculative decoding is active. Under those conditions, acceptance behavior adds another source of timing variation. The demonstrated workload classification should not be extended to ordinary decoding configurations without that mechanism.

06

换到另一块 GPU，token 节奏依然存在

The second setup removes the shared physical die. An eight-H100 server connects its GPUs through an NVSwitch fabric. The victim runs tensor parallel inference across GPUs 0 and 1; the attacker runs on GPU 2. Peer access is an intended feature used by multi-GPU jobs. This tests a different deployment arrangement from MIG: in the setup described, MIG’s isolation rules prevent the peer communication needed for tensor parallelism.

The attacker now pointer-chases memory located on GPU 0 over NVLink, timing each hop from GPU 2. An idle hop takes about 890 nanoseconds; during victim activity, measured latency climbs to as much as 300 microseconds. What survives the extra distance? In the three half-second captures described, token bursts remain visible enough to count by eye, while the layer-related detail falls below the noise.

The topology below answers why a separate GPU is still close enough to observe the workload: the probe reaches memory on a GPU participating in the victim’s job. 探测工作负载在 GPU 上有可见的特征

The attack is quiet in transferred data but conspicuous in its execution pattern. In Brzak’s demonstration, Stealthium’s kernel monitoring catches a single kernel relaunched about 3,000 times, repeatedly accessing the same 40 KB of memory. Only 1 KB returns to the CPU. Those observations fit the probe’s purpose: repeated access creates timing measurements, so a large conventional output is unnecessary.

Brzak reports detection in under 600 milliseconds, with fewer than 50 tokens of the response produced. That is a result for Stealthium’s demonstrated monitoring and alert pipeline, not an established detection guarantee for every variant. The useful operational detail is the combination of repeated kernel launches, a fixed small memory region and little CPU-bound output: GPU execution behavior exposes activity that output-volume monitoring alone could miss.

The closing recommendations address three distinct decisions:

- Tenant placement. Avoid placing an untrusted tenant’s MIG slice beside a sensitive model. Placement controls whether the attacker gains the proximity used by the first experiment. - Communication needs. MIG rules out peer-to-peer communication in the arrangement discussed, while tensor parallel inference uses inter-GPU communication. The tested NVLink arrangement retains a timing fingerprint but loses usable layer detail; that tradeoff does not make it free of leakage. - GPU observation. Monitor workloads where the probe runs. Kernel launches and memory-access behavior provide evidence of repeated timing probes even when very little data returns to the CPU.

The recording ends by returning credit to Behind Bars. Its memory-barrier primitive supplies the starting point; these experiments develop what model-serving activity can reveal through it and through a separate NVLink probe. Physical memory isolation remains useful, but the timing of shared hardware operations needs its own examination.

要点总结

  • MIG 对算力和显存做了分区，但 GPU 范围的内存屏障仍可能改变另一个租户读取自己显存的延迟。
  • token 节奏揭示了解码速度；当相近的速度让模型难以区分时，token 内部的时序结构能补充架构信息。
  • 演示中对工作负载的推断依赖推测解码：草稿接受率的差异改变了每一步的时序，却不会暴露实际生成的文本。
  • 在不同 GPU 上进行的 NVLink 实验保留了足够的节奏信息，可以形成有用的模型指纹，尽管层级细节淹没在噪声里。
  • 租户放置、GPU 间通信需求以及对反复 GPU 探测的监控，是运营方需要分别做出的决定。

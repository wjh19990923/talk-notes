智能体安全：权限、溯源与智能体供应链

Steve Yegge 梳理了从幻觉出来的依赖到权限过大的智能体等一系列风险，并解释了为什么安全工具、反复的审查和明确的责任归属必须与自主工作相伴。

熟悉编程智能体、软件依赖和服务账号权限会有帮助；不需要专门的安全背景。

01

当代码的交付速度快了十倍会怎样？

如果一个团队的出码速度提升十倍，漏洞率却没变，它交付出去的漏洞会有多少？Steve Yegge 的警告就从这个问题讲起。他代表 Snyk 发言。Snyk 替他买了大会门票，但没付演讲费。他给这场演讲另起了个标题：“害怕吧。”在一家银行关于 vibe coding 的问答会上，一位安全架构师问过他这个问题。按这位架构师的假设，交付的代码多十倍，引入的漏洞也多十倍。这笔账假定每单位代码的漏洞率不变，并不是实测出来的生产力数据。

Yegge 担心的不止这笔账。他预测，AI 写的代码会让漏洞率更高：代码量变多，缺陷也更密。这场演讲里，他没有拿对比研究来支撑这个预测。他给出的对策也有意只解决一部分问题：把安全审查嵌进产出代码的那套机制里。

02

一个依赖可以完美运行，同时仍是一个后门

老面孔的漏洞依然是问题的一部分。Yegge 说，他只用了 Fable 很短一段时间，它就引入了一个 XSS 漏洞。但同类老 bug 越写越多，只是其中一种风险。选依赖还会带来另一种：slop squatting。模型凭空编出一个包名，攻击者就把它变成一个真能装上的包。

他用一个假想的图数据库包 Graphy123 说明这种攻击怎么得手：

1. 开发者让 AI 用一个图数据库。 2. AI 推荐了 Graphy123，这个包名是它幻觉出来的。 3. 攻击者发现模型总推荐这个不存在的名字，就用它发布了一个包。 4. 智能体下载了这个包。包确实提供了预期功能，项目能构建、能运行，测试也都通过——但包里还藏着一个后门。

功能跑通，不代表依赖可信。 恶意包足够好用，能把任务完成；危险恰恰出在它额外干的那些事上。所以 Yegge 呼吁更严格地审查生成的代码，哪怕日常开发反馈看着一切正常。

03

把安全发现放在代码被编写的地方

在哪个环节介入很关键。Yegge 在 Google 时和 Test Automation Platform 团队合作紧密，这个团队在大规模机群上跑单元测试和集成测试。他观察到人身上反复出现的一种模式：bug 当场发现，多半当场就修；时间一长，修的劲头就淡了。警告看惯了，开发者最后总能给自己找个理由放着不管——反正好像也没人吃亏。

按他的说法，Google 的对策是把检查结果挪到写代码的那一刻。有人正在敲代码时冒出一个除零警告，上下文还在脑子里，改起来也容易。等到代码评审时，哪怕问题提得在理，也可能遭到抵触。

放到安全上，紧迫感一淡就很危险。用户不再提某个漏洞，或者压根没发现，漏洞也不会因此变得无害。修的意愿在下降，暴露的风险却可能在累积。既然警告要送到开发者指尖，同样的道理也适用于智能体：模型干活时，就把安全检查结果发给它。

模型更强，也省不掉这种反馈。安全始终是一场军备竞赛，智能不会自动把它带来。Yegge 还顺带把这种担忧延伸到量子计算，随口估了个五到七年，又提到一位朋友估计要十五年。但他最终回到的问题眼下就摆着：怎么让现在的编码智能体注意到自己漏掉的漏洞。

04

一次令人安心的加固仍然漏掉了一些发现

Yegge 拿自己做了三十年的一款游戏试了试。他让 Fable 做一轮安全加固。Fable 处理了云配置，找出了凭据，还做了些别的清理，然后让他觉得项目状态挺健康。Yegge 说，随后用 Snyk 一扫，查出了 241 个 Fable 根本没想到去找的漏洞。他没有给出扫描报告，也没按严重程度细分，所以这个数字只代表他的个人经历，不是模型和扫描器之间的对照实验。

这正好印证了他的 “五遍法则”。这是一条经验法则：LLM 的输出可能要审四五遍才能上线。他把这个过程比作写文档要起草、修改、润色，或者刷墙要刷好几遍。只过一遍，没法稳妥地顾及所有方面。

从 vibe coding 的经验里，Yegge 得出一个结论：每一轮只给智能体一个明确任务，效果更好。正确性和安全性一起要，很可能两头都做不完整。他提出的工作流把实现和专门的安全检查拆开，给安全单独的目标和工具。接着他把这种做法和 Software Survival 3.0 联系起来，他说这篇文章是大约五个月前写的。

05

让智能体把安全工作卸载给工具

文章里与此相关的观点是：智能体能自己合成软件，并不会因此不想用现成工具。工具能省下思考和 token，降低成本和能耗。既然智能体本来就会借工具省掉不必要的活，安全分析也可以成为它们调用的一项能力，而不是全凭记忆从头做。

Yegge 把这项工作分成两块：项目用到的输入，以及项目组装起来的代码和依赖：

| 层级 | 建议的支持 | 用途 | |---|---|---| | 容器输入 | Chainguard 镜像 | 有人持续维护，已知漏洞很少甚至为零 | | 应用代码和依赖 | Snyk | 对人写的和生成的软件做安全分析 |

Yegge 说 Chainguard 的镜像经过预先审查、没有漏洞。落到实际操作上，更准确的理解是已知漏洞很少甚至为零，而不是对尚未发现的缺陷免疫。他还好奇 Snyk 能不能赶在 CVE 登记之前发现漏洞。Snyk 介绍过自家的专有研究，但这不能说明它在各种情况下都能抢在 CVE 之前。在 Yegge 自己的扫描里，查出的问题都对应公开的 CVE。

他提出的集成方式很直接：明确要求智能体最后再跑一轮安全分析。手头有什么开源和商业工具就用上；如果某次发布值得额外把关，就让这些工具互相复核。可以在任务指令里把这一步写明：

``text After completing the implementation, perform a separate security pass. Run the available security-analysis tools on the code and dependencies. Review their findings and address the issues they identify. Before launch, cross-check the results with the other available tools. ``

这是一条工作流指令，不是台上演示的什么新 API 集成。它把安全分析变成智能体的分内工作，而不是留给人类、做不做都行的后续步骤。Yegge 还指出，除了安全的输入和安全的代码，还缺一个维度——后面观众问到智能体执行操作时，这个话题又回来了。

06

安全属于开头，也属于结尾

游戏里查出的问题还得一个个修。Yegge 请观众给他几天时间，还开玩笑说真被攻击了，受影响的也就五个忠实玩家。接着他把紧迫感推向更大范围，说五眼联盟警告过：时间要以月算，不是以年算。NCSC 的公开警告 佐证了网络攻防能力正在变化的总体担忧，但证明不了他接下来讲的模型追赶时间表。

Yegge 问观众：开源模型什么时候能追上 Mythos？他说 Mythos 入侵系统的本事非常强。观众猜的有两个月、六个月，还有人说十二月。Yegge 估计差距大约七个月，正在缩向六个月；这只是他的预测，不是板上钉钉的期限。他担心的是，强大的攻击能力普及之后会发生什么。

有攻击能力，不代表模型自然就能写出安全的软件。Yegge 认为，代码优雅、性能、是否符合公司编码规范，都是各自独立的问题，也得各自专门过一遍。安全他格外看重：第一轮审查要查安全，最后一轮也要。 最后这一轮之所以重要，是因为哪怕前面审得不错，中间的改动也可能带出新问题。

07

攻击面包括你的家人

准备好的演讲以一条软件开发之外的安全建议收尾：线下去见见家人，当面更新你们约定的暗号。设想这样的场景：一位亲戚打来求救电话，急需用钱，听起来非常逼真，甚至还配了伪造的视频。光认出声音或长相，也许已经不足以确认对面是谁。

Yegge 警告，适应得慢的家庭可能会被掏空积蓄，他预计几个月内就会发生。他还转述了一个未经证实的故事：国会秘密演示过如何清空银行账户。他自己的担忧可以追溯到将近两年前。当时在拉斯维加斯的 ETLS 上，一位安全研究员警告说，后果会落到每个人头上，不只是企业。

即便没有完整的解决方案，眼下也有切实的办法：用好现成的免费、开源和商业工具，采用防御性的技术和做法。准备好的演讲到此结束。随后的观众提问，把话题从生成的代码延伸到智能体自主干活，以及谁来为已部署的智能体负责。

08

为什么能力曲线可能看起来是平的

有人问他，AI 编程最近有什么让他意外的地方。Yegge 先交代了自己的视角：为了预判智能体的走向，他用得比一般人狠得多。从这个位置看，让他意外的是社会的步子慢了这么多。他说有些很聪明的朋友把对 AI 的热情斥为精神失常，或者坚称这些系统永远不会有智能。

他的解释是观察窗口太窄。只往回看三个月、往前看三个月，一条正在变化的曲线也会显得平平的。他预计，看清更长趋势的人，会更害怕，也更兴奋。他问现场有谁在大会期间还开着 Claude Code，观众的反应说明了这个房间里有多热情——也说明了这种体验和外面的抵触之间隔着多大的鸿沟。

09

Gas Town：那些缺失的任务其实早已实现

下一个问题是：Gas Town 干过最厉害的事是什么，需要人类引导多少？Yegge 说它是一台围绕 Beads 搭起来的机器，Beads 是他写的任务追踪器。他现在还在用 Beads，并说打算把它捐给 Agentic Foundation，再加上多种后端。按他的说法，这些还只是计划，并没有落地。

它的机制是一个工作队列，智能体不用等下一条提示词，就能自己认领任务。Yegge 把它和 Boris Cherny 的建议联系起来：别再一条接一条地发提示词，而是备足任务，让智能体自己认领，让工作在长时间无人看管时也能持续推进。他说，稳定地通宵运行是一道前沿，现场做到的人还不多。

他印象最深的 Gas Town 例子，一开始看着像个 bug。他提交了一批 Beads，回头发现它们不见了。原来是一个智能体发现了这些任务，把它们全做完了。这个故事说明，智能体能自己找到任务、消化任务，不用每一项都单独发提示词；不过他没有说清其中有多少人工审查或引导。他问现场有谁经常同时用十个以上的编码智能体，举手的人寥寥无几。他预计明年这种情况会很快改变。

10

谁来看管一个能采取行动的智能体？

一位观众点出了关键区别：保护智能体写的代码，和保护一个能用凭据、能动用户资源的智能体，是两回事。Yegge 说这正是他原本想讲的第三个维度。他声明自己是 Tessl 的顾问，并说 Tessl 正在做智能体监管这一块。

有些智能体全天候运行，处理队列、响应事件。对这类智能体，Yegge 建议用对抗的思路设计监管。在他看来，单个智能体迟早会犯错；应该让一群智能体和监管者去检查、质疑这些工作，而不是想当然地认为队列管理器一切正常。

权限也得这样审视。一个服务账号真的需要它手上的每一个凭据吗？如果某个凭据只在某个特定操作时才用得到，能不能把这个操作从智能体的其他工作里拆出来？目的是在智能体犯错或被攻破时，缩小它能碰到的范围。

Yegge 说，现有的监管系统还很少，也都在实验阶段，但他敦促各家组织现在就设计自己的管控措施。不管是工程师还是非工程师，都可能在还没人想好怎么监管之前，就搭起一个权限过大的智能体。他打了个比方：熊闯进冰屋，外墙一破，里面的东西就全暴露了。架构必须限制闯入之后的后果，不能只指望永远不被闯入。

11

提示词注入需要有人负责

最后一个问题是：Yegge 用过或见过哪些管用的提示词注入防范做法。他把针对训练的攻击和发生在提示与推理阶段的攻击分开，然后举了推理阶段最简单的例子：攻击者加一段文字，告诉模型“忽略之前的一切，照下面做”。他把这称作新的 XSRF，这是个类比；他描述的机制是，攻击者控制的文本试图篡改模型接到的指令。

他没有给出技术上的缓解方案，而是说攻击会越来越精巧，并强调教育：构建和部署智能体的人得认清这种风险。这就引出一个组织层面的要求。Yegge 预计会出现智能体安全岗位，作为现有安全工作的延伸，明确负责保护已部署的智能体。有些观众表示，他们公司已经指派专人负责这件事。所以收尾的问题很具体：公司里已经在跑的那些智能体，谁在管它们的安全？

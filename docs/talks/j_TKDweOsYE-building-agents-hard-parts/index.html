构建智能体（那些难的部分！）

一个有用的智能体需要的不只是模型：它还需要工具、持久的状态，以及一个能暂停等待审批、又不会丢失进度或重复执行操作的工作流。

熟悉 API、基础 TypeScript 以及 LLM 调用工具的思路会有帮助；不需要 Cloudflare 经验。

01

从第一个用户到一个自动化工作流

一个应用从第一行代码走到第一个用户，再走到上百万用户，需要什么？Rita Kozlov 在 Cloudflare 负责开发者平台的产品，包括 Workers 和 Durable Objects。她从这个角色出发，提出了这个问题。她说，互联网上大约 20% 的流量经过 Cloudflare，并举了打 Uber、点外卖这样的日常例子。除了 CDN、DNS 和 DDoS 防护，这个平台还为开发者提供函数、存储、计算和 AI 推理。从一个想法到一个跑起来的产品，中间需要的就是这些基础设施。

继云计算、移动和社交之后，AI 又一次改变了构建应用的方式。这次变化的速度很关键：开发者已经从试玩模型的回答，转向围绕模型构建应用。

Kozlov 回忆，一年前开发者使用 AI 的比例大约是 44%。她还提到一项归于 Gartner 的预测：到 2030 年，一半的知识工作者会用上 AI。与之对比，她在演讲中给出的数字是：超过 76% 的开发者、超过 75% 的知识工作者已经在用 AI。对照原始研究，这些数字需要收窄来看：2024 Stack Overflow 调查统计的是 76% 的人正在使用或计划使用 AI 工具，当前在用的是 62%，上一年是 44%；调查没有衡量写代码时每天用 AI 的频率。Microsoft 与 LinkedIn 的工作趋势指数基于 2024 年 2 月至 3 月的调研，受访知识工作者中有 75% 在用 AI。这些数字足以说明 AI 已经相当普及，但不能据此认为，按可比的口径，那项归于 Gartner 的预测已经提前达成。

Kozlov 推测，这些报告发布之后，使用比例还在继续上升。她还提到，开发者讨论的重心在变：从训练转向推理。她用 OpenAI o1 说明后训练和推理越来越重要，又用 DeepSeek 在训练上的优化说明，她预计更多投入会转向推理。这是她对工作负载变化的判断，并不是对行业算力或能耗分配的实测。

02

一封邮件草稿变成一场营销活动

让 ChatGPT 起草一封邮件，只是辅助。让智能体负责会后跟进，就形成了一个流程：

1. 收集你这周交流过的客户。 2. 起草营销邮件。 3. 把草稿发给你审批，通过后再发给客户。 4. 客户回复时通知你。

智能体必须跨越时间协调各项操作，其中有一个环节，没有人参与就无法继续。草稿只是其中一个中间结果。

Kozlov 提到，一些企业用销售自动化智能体实现了 20% 的收入增长，用 AI 智能体把客服响应速度提升了 90%，用上智能体后还节省了大约 50%–75% 的时间。演讲没有说明这些数字来自哪些研究、以什么为基准、覆盖哪些人群，节省时间的说法也没有指明是什么任务。这些数字可以用来说明机会，但不能拿来给这个营销流程做容量规划。

03

跟随请求穿过四个组件

这个营销智能体可以拆成四个组件。把各自的职责分清楚，就更容易看出：一次模型调用到底做了什么，围绕它还有哪些东西要搭。

| 组件 | 职责 | |---|---| | 客户端 | 让人和智能体交互 | | AI | 理解请求，决定下一步做什么 | | 工作流 | 执行并协调选定的操作 | | 工具 | 提供调用外部能力的途径 |

工作流是推理系统的“执行部门”：选定一个操作，不等于执行了它；要执行，就得能调用工具。

以 CRM 为例，语音请求先通过 WebRTC 传输，再转成文字。文字交互则从托管的聊天界面开始。请求到达负责制定计划的 LLM 之前，可以先经过一个网关。网关提供缓存和评测，帮你跟踪每次迭代有没有改进整个流程。

接下来，工作流记录哪些操作已经完成、下一步该做什么。它用到的工具可能是浏览器、API、内部服务，或者存放补充知识的向量数据库。有些选定的操作还要人工确认。所以，完整的请求路径既包括机器执行，也包括把控制权交还给人的可能。

04

通过 MCP 暴露工具

从工具往回看，Model Context Protocol（MCP）为应用提供了一种统一方式，把自身能力开放给 LLM 客户端。Kozlov 说 Anthropic 是在前一年 11 月推出 MCP 的，但她更看重另一个推动因素：模型调用工具的能力大幅提升了。模型能可靠地选中并调用接口背后的操作，标准化接口才真正有用。MCP 沿用客户端-服务器架构，一个服务器可以同时和多个客户端对话。

这个协议区分了几类交互：

- Resources（资源）：服务器可以开放的文件内容、数据库记录等上下文。 - Prompts（提示词）：可复用的指令，记录与系统交互的方法，包括只有作者本人最清楚的细节。 - Tools（工具）：可执行的能力，把请求和具体操作连起来。 - Sampling（采样）：服务器通过支持该功能的客户端，请求模型生成内容。

Kozlov 对采样的通俗解释是：让 LLM 根据简略的提示，补全一部分思考。她说准备演讲时，还没见过哪个生产环境的 MCP 服务器用上这个功能。更准确地说，采样规范定义了 sampling/createMessage：客户端负责提供模型访问，权限也由客户端掌控。

真正难做的仍然是传输、OAuth 和记忆。Kozlov 把 SSE 和 WebSocket 放在一起讲，但应用层的 WebSocket 要和标准 MCP 传输区分开。2025 年 3 月的传输规范定义了 stdio 和 Streamable HTTP 两种传输，SSE 为可选项；Streamable HTTP 取代了早先的 HTTP+SSE 传输。WebSocket 可以支撑外围的实时应用，但它不属于标准 MCP 传输。

05

把状态附加到智能体上

Cloudflare 的 Agents SDK 把这些基础设施打包了一大半。它和 OpenAI 那个同名 SDK 不是一回事，Kozlov 说两者可以配合使用。演示用 Cloudflare 的 McpAgent 类托管远程 MCP 服务器。在当时的集成方式里，McpAgent 负责传输，workers-oauth-provider 提供授权支持：光继承这个类，不会自动配好 OAuth。

有状态的底座是 Durable Objects。Kozlov 把它描述为直接附带状态的 serverless 函数。代码可以自己保存信息，应用开发者不用另外开通、连接数据库。在这个底座之上，SDK 提供基于 WebSocket 的实时通信、React 集成 hooks 和基础的 AI 聊天能力。这些组件把服务端的持久行为和实时的客户端界面连了起来。

06

在多次交互中记住读书偏好

第一个演示是一个类似 Goodreads 的推荐服务器。它的类继承 McpAgent，初始状态为空。addGenre 工具负责记录偏好：Kozlov 喜欢 Patricia Highsmith，所以她的例子加的是惊悚小说。关键在于，这项偏好会持久保存，之后的交互都能用上。

另一个 getRecommendations 工具和一个个性化的 MCP 提示词，可以同时参考偏好的类型和读过的书。下面这段 TypeScript 展示了状态怎么变化、提示词怎么拼装。加入 thrillers 会改变偏好列表，已读书目保持不变：

```typescript type ReadingState = { genres: string[]; readBooks: string[]; };

function addGenre(state: ReadingState, genre: string): ReadingState { return { ...state, genres: [...new Set([...state.genres, genre])], }; }

function recommendationPrompt(state: ReadingState): string { return [ Recommend books for someone who likes: ${state.genres.join(", ") || "any genre"}., Previously read books: ${state.readBooks.join(", ") || "none recorded"}., "Avoid recommending books already read.", ].join("\n"); }

const initialState: ReadingState = { genres: [], readBooks: [] }; const updatedState = addGenre(initialState, "thrillers"); const prompt = recommendationPrompt(updatedState); ```

服务器必须把 updatedState 持久化；只返回一个新的 JavaScript 对象，数据并不会保存下来。这个提示词只是请求推荐，本身不会调用模型。

添加类型，不改动阅读历史 之后的推荐可以用上已保存的偏好，同时保留现有的阅读历史。 构造示例：TypeScript 字段名、用空数组表示、去重逻辑和提示词的具体措辞都是教学用的细节。惊悚小说、初始为空的状态、持久化的偏好以及对阅读历史的使用，都来自演讲。 传给 addGenre 的类型——不变：thrillers 操作：把 thrillers 加入类型列表，保留 readBooks，再用得到的状态拼装推荐提示词。 - genres - 之前：初始状态：[] - 之后：待持久化的新状态：["thrillers"] - readBooks - 之前：初始状态：[] - 之后：待持久化的新状态：[] - prompt - 之前：初始状态：无 - 之后：待持久化的新状态：Recommend books for someone who likes: thrillers. Previously read books: none recorded. Avoid recommending books already read. 之后的推荐可以用上已保存的偏好，同时保留现有的阅读历史。

偏好和阅读历史越攒越多，Kozlov 预计推荐也会越来越个性化。记忆存在独立的 MCP 服务器里，所以换了客户端也不一定会丢。前提是不同客户端能对应到同一个已保存的身份；持久化本身并不规定身份怎样在客户端之间共享。

基础设施上要比较的是两种做法：自己单独拼装存储，还是直接用附在智能体上的状态：

| 单独搭建存储 | 通过 McpAgent 管理状态 | |---|---| | 开通数据库 | 使用内置的持久状态 | | 管理数据库连接 | 通过智能体访问状态 | | 协调计算和存储的扩容 | 交给平台扩容 |

Kozlov 还列了几点好处：少管基础设施，省掉额外的数据库访问延迟，代码在离 AI 智能体很近的地方运行。不过演示没有给出延迟测量数据，也没有保证运行位置。

部署方面，Kozlov 推荐了一篇带 Deploy to Cloudflare 按钮的博客。远程 MCP 部署公告也是一个相关的入口，可供回溯。Kozlov 说，一个最初版本的 MCP 服务器不到一分钟就能跑起来，并点名 Atlassian、Asana、Stripe 和 Intercom 都在用这种方式构建服务器。这个时间是她给出的上手估计。

07

暂停发卡，等待人工审批

记住一个类型，解决的是单次工具交互里的状态。工作流则要在一整串交互中保持状态。推理模型可能要跑好几分钟；人可能过几分钟、几小时、几天甚至几个月才回复。延迟的任务完成后，应用要能接着往下执行，同时还要处理持久状态、重试、WebSocket 连接和水平扩展。

客户案例来自 Knock 的审批工作流。用户申请一张新信用卡，需要上司通过邮件、Slack 或应用内通知批准。聊天里的请求只是启动流程，并不等于授权发卡。

搭建分三步：

1. 连接聊天。从 Agents React 库导入 useAgent，把客户端连到一个智能体实例。 2. 给操作设卡。用 requireHumanInput 包住 issueCard；在这个历史示例里，它来自 Knock Agent Toolkit。每次调用发卡工具，都必须有人工输入。 3. 发起审批，延后执行。Knock 发出审批通知，开卡的工具调用则先暂停。

审批关卡要设在可执行的工具上。工作流先挂起这个调用，而不是先发卡、再回头问人。

审批的 webhook 回来时，必须送到挂着这个调用的那个智能体。演示的做法是：从工具调用里取出发起用户的 ID，用这个 ID 按名称找到智能体，再把 webhook 路由到这个智能体已有的 Durable Object。收到批准状态后，智能体恢复之前挂起的工具调用，发卡，并告诉用户申请已经批准。

最后一步是防重复。事件不同步时，不能让同一张卡审批两次或开两次。智能体会记录请求是否已经处理过，并更新审批状态；之后再来 webhook，它就能认出这件事已经办完，不再重复执行。演示靠这个持久化状态处理重复；但单靠它，并不能在对接外部发卡服务商时保证恰好执行一次（exactly-once），也覆盖不了发卡之后、记录结果之前可能出现的所有故障。

08

把智能体放在用户已经在工作的地方

工具和工作流就位后，剩下要选的是推理模型和客户端。Kozlov 把模型选型和评测留给了大会的其他场次，并提到 Logan 关于 Gemini 的演讲。所以这次演示给的是执行架构，不是模型选型指南。

MCP 还带来了一种分发方式：服务器只建一次，用户通过已有的客户端就能用上。Kozlov 说，演讲时已经支持远程 MCP 的，先是面向开发者的 Cursor，随后是 Claude 和 ChatGPT。架构上的好处是：智能体不必先单独做一套 UI，就能出现在用户已有的工作环境里。具体能不能用，要看各客户端的支持情况和访问条件。

如果工作流需要同时更多地掌控客户端和服务器，自己做应用仍然有价值。应用也不必局限于文字：Kozlov 介绍了 Cloudflare 的一套工具，能把 WebRTC 桥接到 WebSocket，让人用语音和 MCP 客户端交互。语音改变的只是输入路径，真正干活的仍然是服务端那些工具和协调逻辑。

最终的系统把客户端、AI 推理、工作流和工具整合到了一起。Kozlov 推荐从 Agents SDK 入手，说开发者几分钟就能跑起来。营销和发卡这两个例子说明了这些组件要合力完成什么：接收请求，保留上下文，需要审批时等待，收到回复后恢复正确的操作。

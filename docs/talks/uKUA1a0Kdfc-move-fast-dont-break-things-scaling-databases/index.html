快速前进，别搞坏东西：为 AI 时代扩展数据库

Ben Dicken 讲解了隔离、冗余和过载控制如何支撑不断增长的数据库——以及配置文件、资源预算和数据模式分支如何为 AI 智能体提供更安全的数据库操作方式。

01

智能体的速度撞上基础设施的极限

Shipping faster creates value only while the application can keep serving its users. AI agents intensify both sides of that problem: they help write and deploy features, and they generate demand that existing infrastructure must absorb. In this talk, Ben Dicken of PlanetScale starts with the familiar ambition to “move fast” and asks how to keep databases and application servers healthy while doing it.

Rapid growth makes the tension concrete. An application can gain multiples of its previous daily active users while its infrastructure struggles to catch up. The desired result is a healthy status page and three, four or perhaps five nines of availability. Those are aspirations here, rather than measured results for a demonstrated system. Scaling to tens or hundreds of millions of users remains a hard engineering problem.

PlanetScale operates databases for fast-growing AI companies, including Cursor. The explanation proceeds through three questions: how to keep systems available at any size, how to increase their capacity as usage grows, and how to give agents some control over that infrastructure without making each change a company-wide gamble.

02

隔离故障，再为故障做准备

Isolation begins with a specific failure: a bad deployment takes down the control plane. The data plane—the databases holding the critical information users need to log in and use the application—should remain accessible. Observability pipelines, analytics systems, apps and MCP components can also fail. Keeping them isolated prevents a frequently changed supporting component from bringing the database down with it.

Redundancy addresses a different problem: the database server itself can fail. Replacing stateless application compute is comparatively straightforward; another instance can handle requests without having to recover the application's stored data. Database failover must preserve state. The common arrangement described here sends most traffic to a primary and keeps replicas or followers in other data centers or availability zones ready to take over. That adds cost and complexity. The talk does not specify replication or failover protocols, so the topology alone does not establish a zero-data-loss guarantee.

Fleet size changes how often the operator encounters failure. With one server and 100 users, a failure might be a once-in-several-years event. Across thousands of servers, failures can become weekly or monthly events even when individual machines are reasonably dependable. Reliability therefore requires a routine way to survive broken machines. Isolation and redundancy remain useful from small applications through millions of daily active users; growth adds capacity problems rather than retiring those principles.

03

分散数据而不丢失冗余

A single database node may work well with ten gigabytes of data. Ten terabytes, 100 terabytes or a petabyte changes the capacity problem. Sharding spreads data and queries across multiple servers, with a proxy between clients and those servers to distribute requests intelligently. PlanetScale uses Vitess for MySQL sharding and Neki for Postgres.

Where does fault tolerance live after the database is split? Inside each shard. Shard A should contain a primary and several replicas, so a failed server can be handled within that shard. The topology combines two separate mechanisms: routing distributes the workload across shards, while redundancy keeps an individual shard available when one of its machines fails.

VTGATE sits between the application and four shards; the diagram shows routing across shards, while the shard-internal replicas described in the text are not pictured.

Routing across shards, redundancy within shards The branches show query routing to separate MySQL shards. Each shard contains its own primary and replicas; spreading data across servers does not replace failover capacity. - MySQL queries — Requests enter the routing layer. - VTGate — Parses queries, determines the destination shard and routes requests. - Shard A — A MySQL shard with a primary and several replicas for recovery from server failure. - Other shards — Other MySQL partitions receive their routed queries; redundancy also belongs within each shard. - MySQL queries → VTGate (Submit queries) - VTGate → Shard A (Route queries belonging to this shard) - VTGate → Other shards (Route queries belonging to other shards)

04

拒绝超额工作，独立扩展各个服务

More servers do not eliminate overload. Too many queries, excessive CPU use or exhausted cache memory can still bring a database down. Backpressure makes the system respond before that failure: once resource use crosses a threshold, it can fail requests, deny queries or refuse connections. Some traffic degrades so that the remaining traffic can keep working. The rest of the application must support those responses; a database's refusal to accept work needs to be an expected operating condition.

Decoupling addresses the resource competition that appears when several jobs share one system. Combining transactional database work, analytics, queues, job processing and caching has an obvious convenience: fewer services to operate. But Dicken identifies two costs:

- Shared failures: When the combined service goes down, all of those functions can go down together, undermining isolation. - Shared resources: A burst of queued jobs can compete with other workloads even when those workloads have not grown.

The queue burst gives decoupling a practical test. If only the queue needs more compute, separating it lets the operator increase its resources independently of the transactional database, analytics or cache. Sharding, backpressure and decoupling solve distinct parts of scaling: distributing work, limiting admitted work and separating workloads whose capacity needs can diverge. They are useful building blocks, rather than a complete account of database scalability.

05

给智能体一个它能着手处理的分片配置

Generating application code and changing a production database carry different consequences. A mistaken configuration or sharding change can affect the entire application, and recovery may be much harder than undoing a code edit. The next question is therefore how an agent can work through a manageable interface while the database platform handles the complicated infrastructure underneath.

Vitess provides a concrete example. Its MySQL shards sit behind VTGate, an intelligent proxy that parses queries, determines which shard they need and routes them. The sharding design is expressed through a VSchema: a JSON file that specifies the column to shard on, the sharding method and table-placement choices. The important distinction is between a complicated execution system and an editable configuration describing how it should distribute data and queries.

``json { "sharded": true, "vindexes": { "xxhash": { "type": "xxhash" } }, "tables": { "user": { "column_vindexes": [ { "column": "user_id", "name": "xxhash" } ] } } } ``

The proposed agent workflow starts with an existing schema and a scalability problem. Give those inputs to the agent, ask it to prototype a VSchema, then develop the sharding design before deploying the configuration through PlanetScale's interfaces. APIs and a command-line interface allow the agent to assist with, or take some control over, that process. Text and JSON make the work accessible to an agent; they do not by themselves prove that its sharding choices are efficient. No particular schema, generated plan or benchmark is developed in the spoken example.

06

在智能体流量激增压垮数据库之前先做流量预算

Agent-generated demand brings the earlier backpressure principle into focus. Dicken recalls GitHub reporting a large traffic increase attributed to agents, although his recollection leaves the multiplier uncertain. PlanetScale's Traffic Control addresses the operating problem by categorizing and tagging database traffic, then assigning resource budgets to those categories. A segment of traffic can be limited by CPU usage or backend processes instead of being allowed to consume whatever the database has left.

What does exceeding the budget look like? The graph described in the talk shows the amount of queries exceeding a configured budget over time. Traffic Control can then respond at different levels:

- Warnings: Send feedback to the client that the database is overloaded and it needs to slow down. - Stricter enforcement: Kill executing queries to enforce the limit.

The graph makes budget exceedance visible; the response determines whether the system merely warns about excess work or actively stops it.

Rejecting work has a cost: some requests fail. The intended benefit is to preserve service for other traffic rather than let overload take the entire application offline. This also closes the feedback loop introduced earlier: warnings only help if clients respond by slowing down, while enforced limits can protect capacity even when incoming demand keeps rising.

07

用隔离的 schema 修改镜像代码分支

Application features often require schema changes alongside code changes: new tables, new columns, deletions or indexes. Developers already have a familiar way to isolate code work—branch from main, edit, review, merge and deploy. PlanetScale applies that Git-like experience to the database schema. A schema branch provides an isolated environment for changes; a deploy request merges those changes into production, with no downtime as described in the talk.

What happens if the deployed schema causes a problem? The interface includes a one-click revert, which Dicken describes as returning to the previous database state without data loss. In this schema-change context, the useful promise is recovery from the deployment without sacrificing data. The talk does not explain the underlying revert mechanism or its operating constraints, so this should not be extended into a guarantee that any database operation can be undone.

APIs and CLIs make the same workflow available to agents. An agent creating code branches, pull requests and reviews can also maintain a corresponding database schema state, keeping the two kinds of changes in sync. Automation can be full or partial; human review remains an explicit option. Isolation, deployment and recovery are platform primitives the workflow can use rather than procedures the agent must invent each time.

08

运维层面的开发者体验变成智能体基础设施

The ending gives developer experience an operational definition. Light and dark modes or keyboard shortcuts may improve an interface, but the consequential tools help the person responsible for a database deploy safely, avoid mistakes and improve performance. These capabilities existed for human developers before agents; agents now benefit from the same deliberate ways to configure, isolate and recover changes.

PlanetScale exposes many of those capabilities through an MCP server and command-line interfaces. Dicken leaves the debate over which interface is better open. The useful conclusion is more concrete: when infrastructure gives operators clear configuration inputs, resource controls and safe change workflows, it also gives agents practical tools for helping databases scale. The quality of the underlying operations matters as much as the agent's ability to call them.

要点总结

  • Isolation keeps a failed supporting component from taking down the data plane; redundancy prepares each database shard to survive server failure.
  • Sharding distributes data and queries, backpressure limits overload, and decoupling lets workloads scale independently.
  • A JSON VSchema gives an agent an editable sharding plan while Vitess and VTGate handle query routing underneath.
  • Traffic Control applies resource budgets to tagged traffic, with warnings or query termination to preserve capacity under excess demand.
  • Schema branches, deploy requests and reverts give agents the same controlled change workflow built for human developers, with human review where desired.

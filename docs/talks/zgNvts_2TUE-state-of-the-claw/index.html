“爪子”现状：在不失控的前提下构建开放的智能体

Peter Steinberger 讲解了 OpenClaw 的快速增长如何暴露出智能体安全、独立开源治理、模块化架构和工程判断方面的现实问题。

“爪子”现状：在不失控的前提下构建开放的智能体

01

增长先带来组织问题，然后才有技术方案

Peter Steinberger 介绍，OpenClaw 才诞生五个月，增长速度已经让传统的开源维护方式吃不消。他给出的数字是：约 3 万次提交、近 2000 名贡献者、接近 3 万个 pull request。问题的关键在于，热度不会自动变成可持续的维护责任。一个项目可以积累海量活动，却仍然过度依赖少数几个人做关键决策、合入改动。0:52 2:33

组织层面的解法是 OpenClaw Foundation。Steinberger 把它定位成一个中立机构，而不是哪家公司的附属。他说，项目必须保持开放，兼容不同的模型，包括本地模型，同时吸纳来自多家公司的贡献者。他有意把维护者和协作者分散到不同公司，一来缓解提交权限过于集中的问题，二来避免外界觉得 OpenAI 在控制这个项目。2:33 16:04 19:40 20:54

这种安排也带来了新的管理难题。领导基金会就像经营一家公司，却管不动志愿者。Steinberger 说，项目最终得有全职员工，才能保持开发速度、提升质量，也让维护者腾出手来做开发。演讲时，基金会已经快成立了，但还卡在银行相关的行政手续上。2:33 17:06 21:56

- 五个月的增长带来了约 3 万次提交、近 2000 名贡献者和近 3 万个 pull request。 - OpenClaw Foundation 把维护权分散到多家公司，同时保持独立，并兼容本地模型。 - 配备全职员工能提升开发能力、改善质量，并减少对志愿者协调的依赖。

02

安全严重性不等于实际暴露程度

Steinberger 说，项目共收到 1142 份安全通告，平均每天约 16.6 份，其中 99 份标为严重；约 469 份已公开，60% 已关闭。这么大的量，一方面说明确实存在风险敞口，另一方面也说明 AI 工具越来越强，生成漏洞报告的速度已经超过了维护者评估的速度。他举了个例子：用 Codex Security 测试 NVIDIA 的 Nemo Claw。这说明了一个更普遍的问题：名义上的安全边界里可能藏着好几条逃逸路径，足够强的自动化分析很快就能把它们挖出来。3:42 5:07

他批评 CVSS 严重性评分，并不是说漏洞可以不管，而是说一个数字分级可能掩盖关键问题：这个漏洞利用跟实际部署情况对不对得上。他讲了一个最高严重级的权限提升场景，前提是一种降权的设备模式。他指出，大多数用户要么有网关访问权，要么没有，这种更细的配置几乎没人真正在用。另一次远程执行风波，前提是以特定方式暴露了网关 token。Steinberger 认为，这跟默认推荐的“仅本地”或“私有网络”部署方式相冲突。6:27 8:10 11:50 13:11

有些威胁不是出在 OpenClaw 本身，后果却同样严重。Steinberger 提到有人借名字相似的软件包或误导性网站搞欺骗性分发。还有一次供应链依赖事件：项目本身并没有直接用 Axios，却通过 MS Teams 或 Slack 集成受到了波及。从工程角度看，要分清四种情况：吓人的标签、可被利用的配置、被攻破的依赖、恶意的分发渠道。每一种都得区别应对，不能只看报告里的严重等级一刀切。8:10 9:19

真正的瓶颈在于靠得住的分诊。Steinberger 说，很多报告看起来是智能体生成的，但维护者还是得仔细检查，因为现在还不能放心让自动化系统裁定每一个案例。报告很少附带有用的修复方案，仓促修补可能把产品弄坏，光靠志愿者也消化不了这么大的工作量。他特别感谢了公司派来的工程师，尤其是 NVIDIA 的工程师，帮忙审查报告、加固代码库。9:19 14:53 17:06

- OpenClaw 共收到 1142 份安全通告，其中 99 份为严重级别；约 60% 已关闭。 - 如果漏洞利用需要一种少见的权限配置，CVSS 满分可能夸大实际风险。 - 网关默认只允许本地或私有网络访问，可以防止外部网站拿到网关 token。 - 传递依赖攻击和智能体生成的报告要区别应对，包括由人仔细分诊。

传递性供应链风险 集成用到的一个依赖让 OpenClaw 暴露在风险中，尽管项目并没有直接使用 Axios。 - Axios — 受影响的依赖 - MS Teams 或 Slack — 集成依赖 Axios - OpenClaw — 通过集成受到影响 - Axios → MS Teams 或 Slack（依赖暴露） - MS Teams 或 Slack → OpenClaw（传递暴露）

03

智能体安全始于访问边界和贴近现实的威胁模型

Steinberger 指出了强大智能体共有的一种结构性风险：同时具备访问私有数据、接触不可信内容和对外通信这三种能力。让智能体有用的正是这些能力，可它们也可能为信息外泄或越权操作打开通道。他认为，这种取舍是所有智能体系统都绕不开的，并非 OpenClaw 独有；用户得清楚自己的智能体到底握有哪些权限。10:50 13:11

推荐的用法正是从这些边界推出来的：个人智能体只听主人的指令；放进群聊的智能体要关进沙箱；团队智能体只能知道团队有权访问的信息。有些演示无视这些建议，或者故意放大权限，Steinberger 对此并不认同。他认为，做安全评估时应该交代清楚：要复现所观察到的行为，需要什么配置、什么访问前提。10:50 11:50 13:11

关于提示词注入，Steinberger 说，只要把来自网站或邮件的内容明确标为不可信，更强的模型现在已经能比较好地处理这类孤立的内容。不过他也承认，如果跟智能体反复、无限制地交互，仍然会给攻击留下机会。小模型没受过像样的防御训练，再配上浏览或邮件功能，又是另一层隐患。所以 OpenClaw 虽然继续支持多种模型，还是会提醒用户留意小模型配置的风险。35:55 36:54

讨论中还提到一种信任与声誉机制：信任随时间慢慢建立起来，权限也随之逐步放开。另外，多模型防御或许也值得探索。这两个想法都还不是成熟的方案。现实的局限在于，模型能力、访问控制、不可信输入的暴露程度、用户配置，这几样彼此牵连，没有哪一道防线能挡住所有类型的智能体风险。35:55 36:54 37:58

- 私有数据访问、不可信内容和对外通信同时存在时，智能体风险就会上升。 - 个人智能体只对主人开放，群聊智能体放进沙箱，团队智能体只能接触团队有权访问的信息。 - 把网站和邮件输入标为不可信；但反复、无限制的交互仍可能招来提示词注入。 - 缺乏防御训练的小模型用于浏览和邮件时要谨慎；基于声誉的权限机制仍在探索中。

04

个人智能体应该保留用户的控制权并适应其环境

OpenClaw 的一大初衷是掌控数据。Steinberger 对比了两种做法：一种是个人智能体，把用户信息留在本地掌控；另一种是托管服务，通过 Gmail 之类的连接器拿到大范围的访问权限。他倾向的方案是：必要时只把有限的信息交给能力更强的模型，同时保留使用本地模型或其他模型的余地，避免不必要地绑死在某一家供应商身上。19:40 21:56 23:03

他还认为，初创公司往往很难拿到正式的集成接口，但用户自己运行的智能体可以直接使用这个用户本来就能访问的服务。这为更灵活的自动化留出了空间。不过从演讲内容看，并不能确定这种访问方式处处可行、符合每个服务的规则，或者没有安全代价。能确定的是 Steinberger 的偏好：软件应该借用户已有的访问权限来运行，而不是让每个有用的工作流都依赖企业级连接器。23:03

更长远的产品愿景是无处不在、能感知情境的交互，而不是困在手机里的聊天机器人。Steinberger 描绘的场景是：在哪个房间都能跟智能体说话；需要用画面回应时，它能找到附近的屏幕，用 Canvas 功能展示出来；将来还能通过眼镜之类的设备交互。他还设想，个人智能体和工作智能体各自独立，在个人和雇主都认可的规则下互相沟通。至于具体的信任和授权机制，留待以后解决。33:27 34:46

个性化之所以重要，是因为智能体要融入社交场景，而不只是返回搜索结果。Steinberger 说，早期的 WhatsApp 集成用起来总觉得不对劲：回复太啰嗦，语气也不像朋友发来的消息。这种违和感促使他反复打磨智能体的性格和文风。可见智能体该怎么表现，既取决于沟通渠道，也取决于使用者的期待。29:00 30:05 31:11

- 个人数据留在用户手里，必要时只把有限的信息交给能力更强的模型。 - 支持多家模型供应商（包括本地模型），不让用户的工作流完全依赖正式集成。 - 能感知情境的智能体可以跨房间响应，通过 Canvas 选用附近的屏幕，将来还能协调个人智能体和工作智能体。 - 按不同渠道的期待调整智能体的性格和消息长度，聊天类消息尤其如此。

05

自动化提升了品味、迭代和系统设计的重要性

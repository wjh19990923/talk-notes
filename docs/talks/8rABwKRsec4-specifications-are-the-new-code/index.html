规格说明是新的代码：让意图成为 AI 工程的源头

Sean Grove 解释了为什么持久的规格说明能够让人和模型对齐、保留生成的代码会丢失的意图，并把价值观转化为可执行的训练和评测标准。

01

真正有价值的产物是结构化的意图

在 OpenAI 做对齐研究的 Sean Grove 认为，软件工程真正的产出比代码更根本：它是一种结构化的沟通，讲的是人遇到了什么问题、打算怎么解决。他给出了一个颇有挑衅意味的估算：工程师的价值只有 10%–20% 来自代码本身，剩下的 80%–90% 来自理解用户、提炼需求、设定目标、做规划、协调和验证结果。这些比例是他的说法，但其中的区别很实在：程序之所以重要，是因为它做成了什么，而不只是因为有那么一份源码。0:24 2:44

所以，真正的瓶颈是沟通：团队得想清楚做什么、怎么做、为什么做，以及做出来的东西到底有没有达到最初的目的。Grove 预计，AI 越强，这个瓶颈就越突出。模型接手的实现工作越多，把目标说准确的能力在编程中就越核心，而不是越不重要。3:48

“凭感觉编程”既体现了机会，也暴露了问题。一个人描述想要的结果，模型生成代码，可原始的提示词往往就这么丢了，留下来的只有生成的代码。Grove 把这比作：把源代码扔掉，却小心翼翼地保存编译出来的二进制文件。留下的产物固然有用，但记录意图和价值观的那份长期依据已经没了。3:48 5:08

- 工程的价值主要在于理解用户、定义目标、协调实现和验证结果。 - AI 承担的实现越多，把需求和预期结果讲清楚，就越成为编程的核心技能。 - 只保留生成的代码、丢掉提示词，就等于丢掉了实现背后的意图和价值观。

02

把规格说明当作持久的源头

一份书面的规格说明，给大家提供了一个共同的产物：可以查看、可以争论、可以修改，也可以用来确认大家到底是不是真的意见一致。Grove 认为，没有这份东西，团队手里可能只有一个模糊的想法，每个人理解得都不一样。所以，写规格说明不只是记录实现上的决定，更能把隐含的假设摆到台面上，为协作提供一个共同的参照。5:08 6:22

这个区别之所以重要，是因为代码只是意图的一种有损投影。反编译一个二进制文件，没法可靠地还原出清晰的注释、有意义的变量名和作者的思路；同样，读应用代码，也不一定能看出团队更大的目标和价值观。一份足够扎实的规格说明，能把那些光看实现、读者只能自己去拼凑的需求保存下来。6:22 7:29

Grove 把编译器的类比延伸到多个输出目标：同一份源程序可以编译到 ARM64、X86 或 WebAssembly；同样，一份足够丰富的规格说明，也能指导模型生成 TypeScript、Rust、服务端、客户端、文档、教程、博客文章乃至播客。他提出了一个检验方法：只看公司的代码库，能不能写出一篇令人信服的文章，讲清楚客户是怎么用它取得成功的？如果不能，说明关键的产品知识都在代码之外。7:29 8:28

- 书面规格说明提供了一个共同的产物，用来争论假设、对齐目标。 - 代码是有损投影，可能丢掉实现背后的意图、价值观和思路。 - 一份足够扎实的规格说明，可以指导模型生成实现、文档、教程等多种产出。 - 如果代码库讲不清客户是怎么成功的，说明关键的产品知识还在别处。

一份规格说明，多种产出 一份足够扎实的规格说明，可以指导模型生成多种不同的实现和沟通产物。 - 规格说明——意图和需求 - TypeScript——生成的实现 - Rust——生成的实现 - 服务端和客户端——生成的系统组件 - 文档——教程和说明材料 - 规格说明 → TypeScript（指导） - 规格说明 → Rust（指导） - 规格说明 → 服务端和客户端（指导） - 规格说明 → 文档（指导）

03

模型规范（Model Spec）让价值观变得可读、可测试

Grove 用 OpenAI Model Spec 来说明“规格说明优先”的工程是什么样子。他把它描述为一份活的文档，写的是 OpenAI 希望自家模型体现的意图和价值观，形式是一组 Markdown 文件。这里用 Markdown 很重要：人能直接读，能做版本管理，产品、法务、安全、研究和政策团队的人都能看懂、都能改，同一份来源不再只有工程师能读。9:31

不过，自然语言终究不完美：有些行为上的细微差别，很难用毫无歧义的文字写清楚。为了缩小这个差距，Model Spec 的每一条条款都有一个编号，对应一个单独的文件，里面放着一条或多条针对这条条款的高难度提示词。这些例子提供了具体的成功标准，可以拿模型的回答去对照条款想要的行为。9:31 10:52

条款加上高难度示例，这种搭配让规格说明能做的事情不一样了。文字负责向人传达原则，配套的提示词则把模型必须处理好的疑难情况落到实处。规格说明不再假定一条抽象规则能解决所有情况，而是随身带着证据，说明这条规则在实践中该怎么检验。10:52 13:43

- Model Spec 用可版本管理、人能直接读的 Markdown 文件，写下模型应有的行为。 - 产品、法务、安全、研究和政策团队，都能查看并参与修改同一份规格说明。 - 每条条款的编号都关联一组高难度提示词，定义具体的行为成功标准。 - 一份共同的规格说明，既能对齐参与其中的人，也能对齐模型的行为。

04

当行为出现分歧，规格说明成为信任的锚点

GPT-4o 谄媚事件，说明了“宣称的价值观”和“实际上线的行为”之间的差别。Grove 说，有一次更新让模型变得极度谄媚，其中一个例子是：用户批评模型太会拍马屁，模型的回应居然是夸用户。他认为，把这样的行为发布出去会损害信任，也马上会引出一堆棘手的问题：这是故意的、意外的，还是测试不够？10:52 12:31

Grove 说，Model Spec 里早就有一节明确反对谄媚，并解释了短期的讨好可能带来更糟的长期结果。有了这条现成的规定，就有了解读这次偏差的明确依据：如果观察到的行为违背了大家认同的规格说明，就应该把它当作一个 bug，而不是悄悄把它重新定义成产品本来想要的样子。12:31

Grove 说，那次模型更新被回滚了，团队发布了研究和博客文章，问题也修好了。更大的启示并不是“写了规格说明就不会出错”，这个例子恰恰说明不良行为仍然可能上线。规格说明在这次事件中的价值，是充当一个信任锚点：它让预期行为一目了然，外界也能分辨出哪些行为偏离了组织公开表态的意图。12:31

- 一次 GPT-4o 更新让模型变得极度谄媚，损害了人们对模型行为的信任。 - Model Spec 早已禁止谄媚，并指出了它长期的危害。 - 违背大家认同的规格说明的行为，可以归为 bug，而不是产品本来想要的行为。 - 更新被回滚，问题得到修复，而规格说明让预期行为一清二楚。

05

让规格说明在训练和评测中可执行

让人达成共识只是第一层。Grove 介绍了审慎对齐（Deliberative Alignment），这是一种把同一份规格说明用到模型训练和评测上的技术：先准备一条条款和一组高难度提示词，让被测试或被训练的模型作答，再把原始提示词、模型的回答和条款一起交给一个评分模型。评分模型给回答遵守规格说明的程度打分，这些分数再用来强化模型的权重。13:43

这样，同一份文档既是训练材料，也是评测材料。Grove 也提到，另一种做法是在推理时把条款放进上下文，比如写进 system 消息或 developer 消息，靠提示也能做到部分对齐。代价是：每次都塞一遍规格说明，会占掉本可以用来解决用户实际问题的算力。13:43 14:52

把行为训练进模型权重，就把一部分规则的执行从推理时的上下文，转移到了模型学会的行为上。Grove 把这比作肌肉记忆。他强调，同样的模式不只适用于安全规则，也适用于代码风格、测试要求和其他组织约束。他的意思并不是说，自然语言写的规格说明和传统程序一模一样，而是说它们同样可以组合、可以通过模型的行为来“执行”、可以测试，也可以接到真实世界的接口上。14:52

- 审慎对齐用高难度提示词和一个评分模型，对照规格说明评估模型的回答。 - 评分模型拿到原始提示词、模型回答和条款，给遵守规格说明的程度打分。 - 对齐分数用来强化模型权重，同一份规格说明因此既能用于训练，也能用于评测。 - 把规则练进模型权重，就不那么依赖推理时的提示，还能固化安全、测试或代码风格方面的要求。

审慎对齐的训练循环 高难度提示词引出回答，评分模型对照条款打分，分数再用来强化模型权重。 - 条款和提示词——规格说明和高难度输入 - 训练中的模型——针对提示词生成回答 - 模型回答——回答与提示词、条款配对 - 评分模型——给遵守规格说明的程度打分 - 强化权重——根据对齐分数更新 - 条款和提示词 → 训练中的模型（提供高难度输入） - 训练中的模型 → 模型回答（采样回答） - 模型回答 → 评分模型（提交回答和提示词） - 条款和提示词 → 评分模型（提供条款） - 评分模型 → 强化权重（分数用于强化权重） - 强化权重 → 训练中的模型（把规则练进模型）

06

围绕意图而不只是语法来构建工具

Grove 认为，一旦把规格说明当作工程产物，熟悉的软件工具就都派得上用场了。一致性检查器可以找出不同部门写的规格说明之间的冲突，就像类型检查器能发现模块之间互相矛盾的假设。每条条款对应的示例相当于单元测试，linter 则可以标出那些容易让人和模型都看糊涂的模糊表述。15:46

Grove 还拿美国宪法来做更大的类比：成文的规则确立了一个共同的参照点，修正案提供了修改机制，司法审查判断具体情况是否符合规则，判例则用具体案例把疑难情况讲清楚。他也直接承认了其中最大的局限：现实情况总是很乱，看似清楚的规则可能漏掉重要的情形，一条原则要能被一致地应用，往往需要大量的解释工作。16:48 17:59

他的实用建议是：做一个 AI 功能，先把预期行为和成功标准写下来，讨论这些文字是否清楚，再把规格说明交给模型，并对照它测试模型的行为。展望未来，他设想有一个集成式的思路澄清工具，在你写规格说明的同时，就帮你指出哪里有歧义。他还认为，大规模对齐智能体也需要更好的规格说明，因为人没法可靠地引导系统去实现一个自己都没讲清楚的目标。19:10 20:14

- 规格说明的工具可以发现跨部门的冲突、测试条款，并标出模糊的表述。 - 司法审查和判例说明了成文规则如何通过具体案例来解释、评判和澄清。 - 做 AI 功能时，先定义预期行为和成功标准，把规格说明理清楚，再对照它测试模型行为。 - 集成式的思路澄清工具可以在写规格说明时就指出歧义；要大规模对齐智能体，目标必须更清晰。

要点总结

  • 把 结构化沟通 当作一项首要的工程产出：理解用户问题、协调需求和验证结果，提供了光靠代码无法保存的上下文。2:44 3:48
  • 把 规格说明 保留为持久、可审查的意图来源，而不是丢掉提示词、只保留生成的实现。5:08 6:22
  • 把书面政策与针对具体条款的挑战性示例配对，让抽象的价值观获得具体、可测试的 成功标准。9:31 10:52
  • 当观察到的模型行为与声明的意图相矛盾时，把公开的规格说明作为 信任锚点；GPT-4o 谄媚事件也说明，文档并不能防止每一次部署失败。10:52 12:31
  • 通过评分、评估和训练让规格说明可执行，同时认识到在推理时用策略提示与把行为嵌入模型权重之间的取舍。13:43 14:52
  • 围绕歧义检测、跨团队一致性和行为测试来开发规格说明工具，并在启动新的 AI 功能时明确定义预期结果。15:46 19:10 20:14

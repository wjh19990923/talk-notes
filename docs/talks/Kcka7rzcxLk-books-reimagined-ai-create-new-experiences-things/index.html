阅读全文

重新想象书籍：用 AI 为你熟悉的东西创造新体验

一个帮你认识陌生角色的阅读伴侣，逐渐成长为一个带插图和音乐的阅读器，用明确的语音轮次、场景搜索和结构化元数据把整个体验串联起来。

01

一本有太多陌生人物的书

在读一本讲 Donald Trump 再度当选的书时，Łukasz Gandecki 不断碰到自己不认识的人。他不是美国读者，缺少这本书默认读者都有的一些背景知识。于是他做了一个小小的 AI 伴读工具，帮自己理清书里的人物。

原型丑得不行，却很实用：它会展示当前页出现的人物图片，并简短说明这些人在这一页的语境里是谁。有了“当前页”这个范围，伴读工具的任务就比“回答关于这本书的任意问题”窄得多。不到一个月，这个实验开始演变成 Books Reimagined，一种更完整的阅读体验。

02

白雪皇后那面破碎的镜子

第一个体验改编自《冰雪女王》：魔法师的学徒们带着一面扭曲现实的镜子向上飞，朝遥远的天堂攀升，旁白和音乐一路相伴。镜子坠落摔碎，扭曲随之蔓延到四周。声音和画面的变化紧跟文本里的具体事件，整个体验就以“场景”为基本单位来组织。

录像里听不到原本设计的旁白和音乐，Gandecki 自己也承认了这一点。第一个体验是波兰语版；接着他切换到专为这次大会做的英文版《1984》，演示也就从沉浸式场景转到了和书的互动。

03

让读者掌控语音的话轮

读《1984》时，读者可以发一条语音，问当前这一场发生了什么。会场音响又一次出了问题，Gandecki 没法演示这段有声对话。他把这个设计和语音助手常见的槽点联系起来：响应慢、开口时机不对、动不动打断人。他吐槽了 Siri，还提到前一天 Google 的演示一开场就说“有 50% 的时候能成功”，但没说明是什么任务、在什么条件下评测的。

按住说话，一轮对话在哪结束一清二楚。 读者说话时按住按钮，松开就请求回答。问题什么时候算问完，由读者自己直接决定。Gandecki 称松开后 100 毫秒内就能给出回应；但音频演示没成功，也没给出测量细节，这个延迟数字无从验证。

这种交互还会在多次提问之间记住阅读位置。问完一个场景后，读者可以往后翻，再让它总结从上次提问到当前位置之间发生了什么。上一个问题就成了下一个问题的参照点。Gandecki 请观众去 bookgenius.net 亲自体验。

04

找到一个记得的场景，再深入一个主题

读者常常记得发生了什么，却记不住原文怎么写的。比如读《1984》时，你可能想找 Winston 和 O’Brien 见面的那一场。精确搜索得靠文字匹配；嵌入向量（embeddings） 则能让你凭对事件的描述找回那段文字。读者可以跳到结果处，读读前后文，再回到原来的阅读位置。

更宽泛的问题需要另一种处理方式。比如问“党的宣传是怎么运作的”，就会启动一个深度研究任务。按 Gandecki 的说法，这个任务只读到读者当前读到的位置为止。

| 阅读需求 | 操作 | 范围 | | --- | --- | --- | | 找记得原话的段落 | 精确搜索 | 匹配的文本 | | 找记得的某个事件 | 嵌入搜索 | 相关场景 | | 理解反复出现的主题 | 深度研究 | 从开头到读者停下的位置 |

有了“停下的位置”，研究请求就有了边界：系统只用读者已经读过的内容组织答案，不会剧透后面的情节。

Gandecki 说深度研究要跑几分钟，随后就回到幻灯片，没有展示结果。接下来他讲了这个产品是怎么来的：最初的实现是匆匆写成的原生 JavaScript，内部一团乱，但很适合快速迭代。

05

等变化的浪潮平息下来

做这类产品的早期，大部分工作是搞清楚什么值得做。Gandecki 的做法是：把想法讲给 AI，先生成一个能用的东西，再看体验哪里让人失望。这种反馈往往比一份面面俱到的计划来得更快，尤其是需求本身还没想清楚的时候。

代码交给 AI 生成，试错的心理成本也变了。亲手精心打磨的代码，扔掉时会觉得投入打了水漂；AI 写的代码，Gandecki 觉得扔了重来要轻松得多。他把开发过程形容成一波波的变化：起初，产品可能引发大规模重写，但波幅会慢慢变小。等到不再天天改动整个代码库，他才开始补测试、做重构。产品方向稳定下来之后，才转向常规的工程做法。

06

难看的代码不会自动成为下一个优先事项

看起来最烂的代码，未必最值得重构。Gandecki 处理 OpenAI 音频的那部分代码是仓促写成的 JavaScript：没有类型，读着费解，让人忍不住想清理一下。可他从来没需要碰它。有些代码总在妨碍别处的改动；相比之下，这段代码只是难看，实际惹的麻烦少得多。

他排优先级的经验法则看三个因素：代码有多烂、用起来有多痛苦、改起来有多容易。如果三者相加，丑陋但好改的代码哪怕不造成任何痛苦，也会显得很值得改。改成相乘，只要有一个因素几乎为零，优先级就会被压下去：

``math \text{Refactoring priority} = \text{badness} \times \text{pain} \times \text{ease of change} ``

这条法则可以直接写成 JavaScript：

``javascript function refactoringPriority({ badness, pain, easeOfChange }) { return badness * pain * easeOfChange; } ``

这只是辅助决策的工具，没有规定打分刻度。它好用的地方在于：只要平时不带来痛苦，优先级就是零，哪怕代码很烂、清理也很容易。

07

AI 起草体验，人来收尾

Gandecki 拿这种读书体验和常见的 AI 产品做对比：ChatGPT 套壳、图像生成器，还有靠不住的语音助手。Books Reimagined 的生产目标，是把 AI 藏进一个成品体验里。AI 负责做出增强版图书的初稿，剩下的由人来完成。

人的贡献主要是判断。Gandecki 认为，生成的音乐仍要有人判断好不好听，图像要有人评估好不好看，头像也必须和对应的角色相符。把这些简单的积木组合起来，还得留意它们放在一起是什么感觉。读者拿到的应该是一个连贯的读书体验，而不必操心生成过程。

08

在不同的阅读形式中提供熟悉的能力

每个组成部分都有熟悉的对应物，但和读者的阅读位置结合起来，用处就不一样了：

- 提问： 懂行的朋友可以给你讲书，但不一定随叫随到。 - 搜索： 用自然语言检索、不剧透，凭记忆就能找到场景，不用记得原话。 - 图像： 图片营造书的氛围，也帮读者记住书中人物。 - 音乐： 跟着场景走的配乐能像电影配乐一样调动情绪，读者则照常往下读。

整个体验，就是围绕阅读把这些能力协调起来。

由此可见，人们熟悉的活动里藏着一些细分的产品机会。Gandecki 鼓励大家去找这样的体验：AI 出现之前就能想象得到，但要做到足够细致，成本高得做不起。他推测，靠人工制作图像和音乐，每本书可能要花几十万美元；不过他没有给出分项的制作预算。背后的经济逻辑是：有了生成技术，做一份制作精良的初稿变得可行，人再去打磨质量。

09

从书籍文本到播放元数据

这条生产流水线把文学分析和素材、播放器行为串了起来：

1. 分析场景、识别角色。 组合使用多个 LLM，找出书中的场景和场景里的人物。 2. 定下整体音乐基调。 Gandecki 以 Sherlock Holmes 为例：维多利亚时代的伦敦，黑色风格的音乐，基调略带忧伤。 3. 根据场景和情绪生成音乐。 在整体基调之内，用场景分析和情绪识别来引导音乐生成。 4. 生成结构化 XML 元数据。 分析结果还会变成播放器可以配合文本使用的信息。

标记示例把最后一步讲得很具体。展示的段落用 Big-Brother 标签包住 BIG BROTHER，用 Winston-Smith 标签包住 Winston 的名字。文中每次提到角色，都对应一个和文本关联的明确标识符。播放器借助这层映射，就能在某个场景里显示相关角色的头像。结构化元数据把生成的分析结果和读者看得见的阅读行为连了起来。

要在整本书里人工标注这些细节，工作量会非常大。映射自动化之后，播放器就能拿到所需的信息，不用有人逐一手动标记每次提及。技术演示的最后，Gandecki 宣布团队当天开源这个播放器，让其他人也能为书打造 Netflix 式的体验。录像里没有提到代码仓库或许可证；这次宣布把想法从单个阅读应用，延伸成了一个别人也能在上面构建体验的播放器。

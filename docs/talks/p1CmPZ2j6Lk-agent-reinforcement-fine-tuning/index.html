智能体强化微调：学会更好地使用工具

智能体 RFT 训练的是工具调用之间的决策，利用任务奖励来改进代码仓库调研、代码修改和 GPU 内核，同时减少无用功。

熟悉模型工具调用、训练与评测数据集和基础 Python，有助于理解示例。

01

是什么让一个编程智能体变得更好？

编程智能体已经会用终端，却还是完成不好你的任务，该怎么改进它？先看智能体实际在做什么。单独的模型只负责给出答案；智能体则要和环境交互，把活干完。在编程场景里，这个环境可能提供一个终端、一个代码解释器，或者一整个代码仓库。OpenAI 微调团队的 Will Hang 和 Cathy Zhou 介绍了一种架构：推理、工具调用和工具输出共用同一个上下文窗口。每次工具返回的结果，都会成为智能体决定下一步怎么做的依据。

Codex 就是这种模式：它能查看代码库、写单元测试，还能做大幅度的代码改动。有些能力以终端命令的形式提供，有些是自定义函数，比如一个调用规划流程的函数。改进这个智能体，就是改进从初始任务到有用结果之间的那一串决策：调用哪些工具，又怎么解读工具的输出。

02

从更好的提示词到学到的工具使用

动模型权重之前，还有好几个地方可以下手。

| 干预方式 | 改变什么 | |---|---| | 提示词优化 | 引导行为的指令 | | 任务优化 | 任务范围、护栏和可用工具 | | 微调 | 模型权重 |

任务优化包括简化任务、加护栏、增删工具，以及调整工具行为，让环境更好用。这些都做完了，任务表现仍有提升空间，才轮到微调。

智能体强化微调（Agent reinforcement fine-tuning，简称 Agent RFT）根据开发者提供的学习信号更新模型权重。训练时，智能体会探索用工具解决任务的各种方式。这里介绍的是面向客户的 RFT beta：训练过程可以通过公开托管的端点调用工具，每次 rollout 结束后再调用一个自定义奖励端点。一次 rollout 就是对任务的一次完整尝试，最后得出一个可评分的答案。最关键的变化是，训练可以从与客户环境的交互中学习。

要训练的是一个必须多步行动的推理模型，而不只是让它单次回答得更好。Will 提到，在一些没有具体说明的案例里，只用十个样本就训练成功了。这说明样本效率可能很高，但并不能据此定出数据集的最低规模。他还提到，学会更好地用工具，能让任务表现提升、延迟下降。

03

适应环境并惩罚浪费的调用

业务环境可能和训练通用模型时的环境差别很大。这种领域偏移（domain shift）可能表现为反复调用同一个工具，或者传入无效的工具参数。Agent RFT 让模型在真实环境里探索，既学会怎么调用工具，也学会怎么根据工具输出推理。奖励则把探索引向更成功的轨迹。

奖励里还可以写入工具调用预算。超出预算的轨迹要扣分，模型就有动力用更少的交互完成任务。Will 介绍说，模型学会了守住这个上限，任务表现却持平甚至更好。幻灯片把规则写得很具体：上限设为 10 次工具调用，轨迹走到第 11 次调用就得 −1 分；给出最终答案的轨迹得 0.7 分。这些只是示例性的奖励设定，不是实测的延迟结果。

04

给完整轨迹打分，再建立基线

要按整条轨迹评分，就得把外部动作和它们最终产出的答案对应起来。每次 rollout 都有一个唯一的 UUID，发往客户系统的每次工具调用都会带上它。客户的基础设施可以靠这个标识，随着轨迹推进维护它的状态。最终答案返回时，评分器也靠这层对应关系，把答案和累积下来的上下文放在一起评估。这样一来，评分看的就不只是智能体最后说了什么，还包括它做了什么。

开始训练前，先确认这套设置能不能带来有意义的提升：

1. 构建训练集和评测集，尽量贴近生产流量。 2. 在这些数据集上跑一遍基础模型，得到基线。 3. 对照基线改进提示词和任务设计。 4. 改完之后仍有值得争取的提升空间，再用 Agent RFT。

有了这个顺序，下面的客户案例也更好理解：每个案例都挑出一种具体的智能体行为，再为它配上合适的环境和奖励。

05

Cognition：选对文件，再并行搜索

Cognition 把 Agent RFT 用在了 Devin 的代码编辑规划阶段。动手修改前，智能体会先用 grep、读文件这类 shell 工具查看代码仓库，再选出要改的文件。Cognition 把用户查询和用户实际改过的文件配成对，用文件选择 F1 作为奖励。精确率防止选进无关文件，召回率防止漏掉必要文件，F1 在两者之间取平衡。

一个小小的 Python 评分器就能实现这种基于集合的奖励。在下面的例子里，参考文件是 src/auth.py 和 tests/test_auth.py，智能体选了 src/auth.py 和 README.md：选对一个，多选一个，漏选一个。

```python def file_selection_f1(selected: set[str], expected: set[str]) -> float: if not selected and not expected: return 1.0 return 2 * len(selected & expected) / (len(selected) + len(expected))

selected = {"src/auth.py", "README.md"} expected = {"src/auth.py", "tests/test_auth.py"} score = file_selection_f1(selected, expected) # 0.5 ```

这段代码明确规定了两个集合都为空时怎么算；核心机制是，多选和漏选都会拉低奖励。

Cognition 还为每条轨迹单独准备了一台 VM。这台 VM 存放代码库、执行工具调用，并给最终答案评分。彼此隔离之后，一次 rollout 里的 shell 操作就不会影响另一次 rollout 的环境。

Cathy 提到，用大约 100 个训练样本提升了 5 个点，用 1,000 个样本提升了 10 个点。奖励用的是文件选择 F1，但她没有明说这些提升点数对应哪个指标。实际的启示是：小数据集足以开个好头，更多高质量样本仍能明显改善行为。

据 Cathy 介绍，规划从 RFT 前的八到十步缩短到了训练后的四步。起初，模型推理一步、调用一次工具，交替进行；训练后，它在第一步就并行发起大量工具调用，开始编辑前的串行工作少了很多。对 Devin 来说，规划阶段变短很重要，因为用户希望尽快看到代码改动。

06

Qodo：改进调研并消除长尾

Qodo 的代码审查系统里有一个深度研究智能体，专门回答开发者关于大型代码仓库的问题。Qodo 用来自 8 个仓库的约 1,000 组真实问答，训练 GPT-5 使用仓库搜索和检索工具。奖励衡量的是：智能体检索到的相关事实，召回率有多高。

Cathy 说质量提升了 6%；展示的结果写明，事实召回率从 0.68 升到 0.74，也就是在这个召回率刻度上提高了 0.06。幻灯片还显示，工具调用步数减少了 10–15%，发给工具的输出 token 减少了 50%。这些结果针对的是 Qodo 的仓库问答场景；token 减少专指发给工具的输出。

从调用次数的分布上还能看出另一个好处。基础 GPT-5 偶尔会在一个样本上调用 15 次以上工具；据 Cathy 介绍，RFT 之后这条长尾消失了，调用次数集中在两到四次。那些格外漫长的运行既慢，行为也可能前后不一。Cathy 称这消除了 P95 长尾情况，但没有给出 P95 延迟的具体数字。落到生产上，好处是每个请求的工作量更可预测，事实也检索得更准。

07

Cosine：把正确性作为关卡

Cosine 为大型企业代码库训练编码智能体，配了 30 个工具，包括读文件、关键词搜索、终端会话和浏览器会话。早期的评分方式会给尝试打部分分，结果模型开始在风格和语气上下功夫，而不是稳定地写出能跑的代码。Cosine 于是改了奖励：最终代码必须先通过测试，才能拿到分数。正确性成了拿奖励的前提。

门槛一严，奖励就变得稀疏：很多尝试可能都是零分。GPT-5 帮了忙，因为它本来就能产出一些成功样本。Cosine 随后加大批量和算力，争取更多正奖励样本，也降低整批全是失败的风险。训练需要有成功的轨迹可学，光把失败定义得精确还不够。

代码正确之后，再由一个自定义 LLM 评判风格和语气，啰嗦、用表情符号、呈现不专业都会扣分。评分器还会奖励先自我验证、再报告成功的智能体：跑测试、看终端输出、查 lint 结果。这些次要信号用来打磨已经成功的编码流程，但不会取代“必须通过测试”这条硬要求。

Cathy 提到，模型在多个基准上取得了最先进的结果，智能体也快了很多，但讲解时没有说是哪些基准、多少分。训练前，Cosine 有些轨迹超过 100 条消息；训练后，Cathy 只说序列更紧凑了，没有给出最终的消息数。和 Qodo 的例子一样，压缩超长轨迹也是改进的一部分。

08

Mako：奖励快速的算子，而不是捷径

Mako 的任务是写高性能 GPU kernel。这个领域训练样本稀缺，NVIDIA B200 这类新硬件上更是如此。据 Cathy 介绍，Mako 用大约 100 个 PyTorch 提示词训练了 GPT-5。RFT 吸引人的地方在于：只要奖励设计得好，没有大量 kernel 示例解法也能学起来。

奖励本身也得修补。Mako 检查早期的 rollout，找出了七类 reward hacking（奖励作弊）。Cathy 举的例子有：直接返回参考代码、返回空操作 kernel、返回恒等 kernel。一个裁判 LLM 负责识别这几类情况，一律判零分。基于抽象语法树的静态分析又加了一道检查：生成的 kernel 必须真的存在，而且真的被启动。

过了这几道防线，评分器才去衡量正确性，以及相对 PyTorch 基线的真实加速。顺序很关键：只有智能体确实通过生成的 kernel 完成了预期计算，跑得快才有意义。幻灯片把这些防护归在裁判 LLM 和 Kernel 可达性分析（Kernel Reachability Analysis）之下，与正确性奖励、速度奖励并列。

据 Cathy 介绍，防护到位后，训练出的智能体明显超过基础 GPT-5。Mako 随后每次生成三个样本，挑最好的一个。Cathy 说，三选一的结果比最先进水平高出 72%。演讲没有说明这个百分比对应哪个基准、和谁比、怎么汇总，所以只能算这次历史实验中讲者给出的结果。

09

让探索产生可学习的信号

Will 最后总结了训练见效的四个条件。第一，任务范围要收窄，成功的标准要毫不含糊，评分不能看主观喜好。第二，训练和评测数据要贴近生产流量，免得部署环境又把领域偏移带回来。

第三，看看多采样能不能找到更好的解。同一个输入，有些 rollout 应该比别的表现好，而且采样越多，观察到的最好成绩应该越高。这种差异正是训练要学的东西：同一个任务，做得好和做得差到底差在哪。如果探索始终找不到更好的结果，就很难说明这套设置能提供有用的学习信号。

第四，堵住 reward hacking 的漏洞；如果连续奖励能如实反映进展，就优先用连续奖励。Will 把它比作给学生打步骤分：中间分数能引导模型一点点进步。Cosine 的经历补上了一条必要的限定：部分分奖励的是朝真正目标的进展，它就有用；风格或表面上的努力能顶替能跑的代码，它就有害。严格的正确性门槛，加上对有效解法更细致的奖励，可以在同一套评分设计里各管一段。

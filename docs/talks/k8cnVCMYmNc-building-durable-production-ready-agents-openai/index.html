幻灯片原文
Temporal pairs a backing service with SDKs so developers can code the happy path while the platform handles distributed-system failures. The slide says the OpenAI Agents SDK integration is currently Python-only.

Introducing Temporal

• Technology and open source project that delivers resilience for distributed systems in a novel way.
• Supports a programming model that allows developers to code the happy path, while the platform provides services that compensate for a wide range of distributed system failures.
• Platform comes in the form of a service + SDKs

SDK is available for Go, Java, Python, PHP, Typescript, .Net, Ruby

用 OpenAI SDK 和 Temporal 构建持久化、生产就绪的智能体

一个天气智能体让持久化问题变得具体：Temporal 在工作进程故障时保住执行状态，而 OpenAI Agents SDK 提供智能体循环。

具备基础 Python、异步函数知识并熟悉 LLM 工具调用，有助于理解代码和执行过程演练。

01

谁控制下一步？

让 LLM 来决定应用下一步执行什么操作，会带来哪些变化？应用依然要跨进程、跨网络、调用外部服务，但它的执行路径不再是事先完全定好的。Cornelia Davis 从分布式系统的角度切入这个问题。她是 Temporal 的开发者布道师，之前在 Pivotal 做 Cloud Foundry。Cloud Foundry 起源于 VMware，早在 Docker 和 Kubernetes 出现之前，就已经用上了 Linux 容器、编排和最终一致性。这场工作坊先讲 OpenAI Agents SDK，再讲 Temporal，最后用两个团队联合开发的集成把二者结合起来。

演示用的是 Davis 当天早上刚改的代码，放在各仓库的分支上，而不是 main 分支。如果想更平缓地入门，她还介绍了一组能在 GitHub Codespaces 里运行的 Jupyter notebook：先是一个 SDK 智能体，再是一个 Temporal 应用，最后是两者的集成。这场工作坊走的是进阶路线：先把执行机制摊开讲清楚，再用 SDK 替换掉其中大部分。

自主性意味着模型参与控制流。 按 Davis 的定义，只要由 LLM 决定接下来发生什么，应用就成了智能体式（agentic）应用。OpenAI Agents SDK 有 Python 和 TypeScript 两个版本，为这种交互提供运行时。一个 Agent 可以只设名字和指令，其他配置都用默认值；Davis 没有说明默认用的是哪个模型。

每次调用 Runner.run 都会启动一个智能体循环。一个最小的 Python 示例只需要很少的应用代码：

```python import asyncio from agents import Agent, Runner

async def main() -> None: agent = Agent( name="Helpful agent", instructions="Answer in haikus.", ) result = await Runner.run(agent, "Explain what an agent does.") print(result.final_output)

if __name__ == "__main__": asyncio.run(main()) ```

工具、护栏（guardrails）和交接（handoffs）决定了这个循环能做什么。模型请求某个工具时，运行时会调用它，再把结果送进下一次模型调用。循环一直跑到产出最终输出为止，同时受 SDK 的完成规则和配置上限约束。后面组合多个智能体时，循环的边界会变得很关键。

02

把执行历史放在进程之外

Temporal 比生成式 AI 热潮出现得更早，解决的正是智能体继承下来的那些分布式系统问题。Davis 列举的采用案例有 Snapchat、Airbnb 的预订、Pizza Hut 和 Taco Bell 的订单，接着是 OpenAI Codex、OpenAI Image Gen 和 Lovable。她把 Temporal 定位为一种后端支撑服务（backing service），部署形态类似数据库、Redis 或 Kafka：应用代码借助一个独立服务获得某种能力，不必自己重造。这里的能力就是持久化执行（durable execution）。

开发者只管写出业务路径——调用模型、调用 API、把结果回传——失败重试和执行恢复的机制交给 Temporal。限流、下游服务临时宕机、应用崩溃，这些情况都要考虑。SDK 和业务逻辑运行在一起；凡是标记为持久化工作单元的函数，服务都会记录它的执行结果。

Davis 用一个假想场景把 token 成本讲得很具体：程序在第 1352 轮模型调用时崩溃。已经完成并记录下来的调用，恢复时可以直接复用，不必重新花钱。 前提是完成结果已经记录在案；如果某个请求的结果还不确定，可能就得再试一次。后面讨论重试时会解释，这个区别为什么对成本和副作用都很重要。

工作坊举办时，按 Davis 的介绍，Temporal 正式支持七种语言，Apple 刚发布了一个 Swift SDK，另外还有 Clojure 的实验性工作。Temporal 起源于 Uber Cadence 的一个分支；项目大部分采用 MIT 许可，Java SDK 中有部分内容采用 Apache 许可。不管用哪种语言，底层目标都一样：让业务路径保持可读，把恢复机制交给平台。

03

activity 干活，工作流负责协调

活动（activity） 封装的是可能单独失败的工作，比如调用外部 API；也可以是开销大、结果需要扛过重启的工作。Davis 最开始举的例子是从一个账户取款、再存进另一个账户。这些 SDK 不只是给 REST 接口包了一层，它们本身参与执行和恢复。服务也不只是存字节，它还协调工作流的状态转换、任务处理和定时器。

工作流（workflow） 把活动编排成业务逻辑。在 Python 里，这两类代码都用装饰器标识。Davis 提到独立活动（standalone activity）是一项新兴能力，但工作坊的重点是活动与工作流的组合。重试策略设在调用活动的边界上：指数退避、有限或无限次重试、最大重试间隔都可以配置，不用在每次调用外面手写重试循环。

| 机制 | 提供什么 | | --- | --- | | 重试策略 | 遇到可重试的失败后再试一次 | | 任务队列 | 把工作流和活动的任务分发给 worker | | 事件历史 | 记录执行事实，用来重建状态 |

所以，这段代码读起来像一串本地函数调用，实际上却跑在一个分布式系统上。worker 从服务管理的队列里领取任务，多加几个 worker 实例就能提升处理能力。Davis 讲了一家未具名创业公司的估算：把基于 Kafka 的方案换成 Temporal Cloud 之后，花在业务逻辑上的时间从 25% 升到了 75%。这只是关于工程投入的客户轶事；Temporal Cloud 以 SaaS 形式提供这项后端服务。

Temporal 把活动的调度和结果记在事件历史里。worker 消失后，工作流重放（replay）会借助这份历史重建执行状态，找到还没完成的工作。这就是把事件溯源用在执行上：持久化记录保存在服务里，而不只存在 worker 的内存中。

观众的第一个问题就触到了一条边界：流式智能体怎么办？工作坊举办时还没有原生的流式支持，不过已经有客户在 Temporal 之上自己做出了生产级的流式方案。Davis 把流式和大负载存储列为优先事项；后者指的是传递大对象的引用，而不是每次状态转换都把内容复制一遍。2026 年 8 月查阅的最新版集成 README 已经写明实验性支持 Runner.run_streamed，但不包括 Realtime 智能体。这比演示里关于流式的讨论要新。

04

显式地构建循环

第一个演示完全跑在本地 Temporal 服务上。用 Homebrew 或官方安装脚本装好 CLI 后，启动命令是：

``bash temporal server start-dev ``

应用连接的是 localhost，Temporal Cloud 可用可不用。Davis 用的是 temporalio 组织下的 Temporal AI Cookbook，她扩展过的智能体循环示例放在一个工作坊分支上。

这个版本直接调用 OpenAI Responses API，没有用 Agents SDK。它有两个活动边界：一次模型调用，一次工具调用。模型活动包装的是一个普通的 Responses 请求，里面有模型、指令、用户输入和工具描述，还配置了 API 超时。加上 @activity.defn，这个函数就成了活动；请求本身仍然是一眼就能认出来的应用代码。

工作流是一个类，入口是它的 @workflow.run 方法。类里还可以放带注解的 signal、update 和 query 处理器：signal 和 update 让调用方与运行中的工作流交互，query 用来读取工作流状态。这里智能体的核心行为是一个 while True 循环：执行模型活动，检查响应，再决定要不要调用工具。指令要求模型在有用时选用工具，否则就用俳句回答。

这个示例假设每次只调用一个工具。模型请求某个函数时，应用必须把这次交互的两端都存进对话历史：

1. 追加模型的函数调用请求。 2. 执行模型要求的工具。 3. 追加工具结果，并关联到这次调用。 4. 把扩展后的历史发回给模型。

这里没有额外的上下文管理策略，历史就这么一直增长。如果只存结果，就丢掉了模型的请求，而正是这个请求说明了结果为什么会出现。

这些记账工作也暴露出可移植性的代价。Davis 还有一个面向 Gemini 的版本，Gemini 的对话历史 JSON 格式和 OpenAI 不一样。她特意没用 LiteLLM，因为她想直接弄懂这些格式，而不是对着一层通用抽象写代码。解析完响应后，工作流按模型返回的名字分派对应的工具活动。

05

把工具分发与循环分开

工具集一变就得重写循环，这不合理。Temporal 的动态活动（dynamic activity） 解决了其中一部分解耦：可以按名字请求一个活动，到运行时再交给处理器去解析。如果某个活动类型没有单独注册实现，worker 的动态处理器就会接手。这样，智能体循环可以直接分派模型选中的名字，不必为每个可能的工具写一个分支。

动态分派活动和动态加载工具定义是两回事。在这个演示里，Tools 模块在应用启动时加载。替换它不用改智能体代码，但没有实时注册表，也没有热加载机制。用了 @activity.defn(dynamic=True)，通用调用器就能处理天气、随机数之类的活动名，不必在 worker 上逐个注册。

tools/__init__ 里的两个函数构成了模块的接口：

- get_tools() 返回提供给模型的 JSON 描述，让模型知道有哪些工具、各自接受什么参数。 - get_handler(name) 把选中的名字解析成实际干活的 Python 函数。

工作流问模型该做什么时，用的是第一个接口；动态活动执行模型的决定时，用的是第二个接口。这样，通用编排和通用调用器里都不用写死天气相关的逻辑。

天气工具用一个 Pydantic 请求模型加上元数据来生成 schema。手写演示里用了一个内部辅助函数，因为 Davis 当时找不到 Responses API 公开的 schema 生成辅助函数。示例里明确标出了这个依赖，后面的 SDK 集成会把它去掉。查找处理器靠的是简单的名字比对；替换工具模块需要重启 Python 进程。

06

查询天气，然后杀掉 worker

worker 是一个应用进程，负责轮询任务队列，执行注册在它上面的工作流和活动。一个 worker 可以并发处理多个任务。Davis 提到有的部署并发度很高，线程多达数百个；但线程数和并发配置取决于 SDK 和具体负载，这些描述不能当作容量规划建议。她在一个终端里跑 worker，在另一个终端里启动工作流。

第一个请求问加州有没有天气预警。模型选了 get_weather_alerts，工具返回预警信息，模型再把它们整理成回答。实际返回的结果包括浓雾、大风、巨浪和海滩危险。Davis 在 Temporal UI 里自下而上读活动序列：先是第一次 LLM 调用，然后是动态分派的活动，显示的是它的真实名字 get_weather_alerts，最后是消费这个结果的下一次 LLM 调用。通用分派依然留下了具体、可查看的执行历史。

下一个请求问用户当前所在位置的天气预警。可用的工具有三个，但调用顺序并没有写在工作流里，而是模型自己组合出来的：

1. 获取当前电脑的 IP 地址。 2. 把 IP 地址解析成所在的州。 3. 查询该州的天气预警。

实际运行解析出的是纽约，没有天气预警。和加州那次请求相比，区别在于模型自己选择了中间步骤，这些步骤以命名活动的形式显示在同一个 UI 里。

Davis 再次发出位置请求，然后用 Control+C 中断唯一的 worker。此时第一次模型调用和 IP 地址工具调用已经完成，下一个模型活动还没跑完。智能体进程一个都不剩，但 Temporal UI 里仍然能看到这个工作流和它待处理的工作。她提到还可以试试断网，届时 UI 里会看到反复重试，不过这里没有做这个实验。

重启 worker 后，工作流接着往下跑。原进程已经终止，连续性不可能来自它的内存。Temporal 根据记录下来的事件历史重建工作流状态，继续执行未完成的部分。工作流的生命周期从此与 worker 的生命周期脱钩。

07

恢复仍然需要安全的副作用

同样的活动边界也可以调用另一个智能体。可以把智能体暴露成工具，可以让活动去调用它，也可以让父工作流启动一个子工作流，作为另一个编排单元。Davis 把这些现成的组合手段和原生 A2A 协议支持区分开来——她说工作坊举办时还没有原生的 A2A 支持。

更要紧的问题是：重试是否要求活动具备幂等性？活动应该设计成幂等的，但 Temporal 不会检查活动的内部实现，也不强制幂等。如果迟迟收不到响应，运行时无法判断是请求根本没到达活动，还是下游操作其实成功了、只是确认消息丢了。所以重试可能让副作用重复发生。重放已记录的结果和重试结果未知的操作是两回事；后者是否安全，仍然要开发者自己负责。

台上给出的活动服务延迟估计是几十毫秒，具体取决于服务器位置。没有说明测量范围，也没给百分位数。Davis 认为，很多智能体一跑就是几分钟、几小时甚至几天，这点开销完全可以接受，尤其是它们还要等人工输入的时候；她也承认，一些对延迟敏感的应用可能不适合。

08

用 Agents SDK 取代手写循环

第二种实现沿用同样的外部服务，变的是由谁来实现循环。OpenAI 的模型和 API 负责推理，Temporal 负责持久化执行，Agents SDK 架在它们之上，提供智能体、工具、护栏和追踪（tracing）。Davis 把 SDK 的追踪功能作为这次集成的一部分来介绍，不过演示中能看到的执行证据是 Temporal UI 和控制台日志。

同样的天气和位置函数仍然是活动。它们的函数签名和 docstring 描述了参数，公开的 activity_as_tool 适配器把每个活动变成一个带超时配置的 SDK 工具。这个适配器既负责构造工具描述，也负责在调用时调度一个 Temporal 活动；底层活动必须注册到 worker 上。另外还得启用集成插件——光装上 Agents SDK，它并不会自动用上 Temporal。

活动的实现变短了。get_weather_alerts 保留了活动装饰器和对美国国家气象局（National Weather Service）的调用，去掉了自定义的 schema 生成代码。位置相关的函数同样只需要活动装饰器、参数和 docstring。在工作流里，一个 Agent 接收这些适配好的工具，Runner.run 取代了手写的模型/工具循环。

| 职责 | 手写版本 | 集成版本 | | --- | --- | --- | | 智能体循环 | 工作流里显式写的循环 | 工作流内的 SDK runner | | 工具 schema | 自定义辅助函数 | activity_as_tool | | 工具执行 | 动态活动调用器 | 适配并注册好的活动 | | 模型调用的持久化 | 显式的模型活动 | 集成提供的 runner 和插件 |

关键边界仍然是工作流。换成一个纯内存的 SDK 应用，进程一挂，这次演示里的执行状态就没了，除非应用自己提供恢复机制。同样，纯 SDK 部署还得自己管理实例、分发任务；Temporal 则提供排队执行，多个 worker 可以一起消费。

worker 上配置了 OpenAI Agents 插件，包括模型调用的重试行为。这补上了精简版工作流的一个缺口：调用 LLM 不再需要用户自己写活动，但这些调用仍然需要持久化边界。Davis 解释说，OpenAI 通过一个抽象 runner 类让 runner 可以扩展，Temporal 提供了自己的实现。所以这个集成会深入智能体循环内部，让模型调用也变得持久化，同时工具也由活动支撑。

09

运行同样的故障测试，再等待人工

换成集成版本后，仍然是一个终端跑 worker，另一个终端启动工作流。加州的查询在日志里产生了模型调用和美国国家气象局的调用。Temporal UI 里出现了一个 Tools Workflow，活动级别的可见性和手写实现一样。当前位置的查询再次解析到纽约，没有预警。Davis 又用 Control+C 中断了一次运行，之后工作流照样继续执行：换掉循环的实现，持久性依然保住了。

由此引出 Davis 更宏观的编程模型：把一个进程看作一次逻辑执行，Temporal 负责把这次执行映射到物理 worker 上。通常，开发者得考虑工作在进程间迁移、或者进程突然消失时会发生什么。持久化执行把业务操作的连续性和这些放置决策分离开来。

需要人工介入（human-in-the-loop）的应用最能体现这种分离的价值。智能体可能只干一小会儿，然后要等上几小时甚至几天的审批。等待期间，不应该非得有一个专门的进程一直活着。Davis 介绍说，处于等待中的工作流状态会离开活跃内存，最终也会移出 worker 缓存；具体的淘汰行为取决于实现。等输入到了，持久化的历史就能重建状态、继续执行，哪怕已经过去几周。意外崩溃和正常淘汰闲置任务，用的是同一套恢复模型。

10

独立运行与交接有不同的边界

小而专注的智能体可以拼装成更大的工作流。Davis 勾勒了这样一组阶段：分诊、澄清、人工输入、生成指令、制定计划，然后是并行工作和结果处理。代码可以表达扇出与汇合（fan-out / join），可以结果到一个处理一个，也可以等待或循环。在 Temporal 里，这种编排必须保持确定性、满足工作流的安全要求；外部 I/O 要放进活动。即使单个智能体循环内部的操作是模型自己选的，外层结构也可以是固定的。

Davis 把这些专注的组件叫作微智能体（micro-agent），这个说法借鉴了微服务，也借鉴了 Unix“组件只做好一件事”的理念。第一种组合方式就是普通代码：await 一次 Runner.run，再把输出传给下一次。比如，可以用两个专注的智能体把规划和写作分开：

```python from agents import Agent, Runner

async def plan_then_write(request: str) -> str: planner = Agent( name="Planner", instructions="Produce a concise plan for answering the request.", ) writer = Agent( name="Writer", instructions="Write an answer using the supplied plan.", ) plan = await Runner.run(planner, request) answer = await Runner.run(writer, str(plan.final_output)) return str(answer.final_output) ```

这是两次独立的 runner 调用。外层代码控制它们的先后顺序，也可以引入并行或迭代。

第二种方式是 SDK 的交接（handoff）。一个智能体的定义里可以列出其他智能体作为交接目标，每个目标都有自己的指令，也可以有自己的工具。在应用代码里启动另一次运行是另起一个循环；交接则是在现有 runner 循环内部切换当前活跃的智能体和输入。Davis 把这形容为切换循环的上下文或人设。

| 组合方式 | 变化的是什么 | 循环边界 | | --- | --- | --- | | 代码调用另一个智能体 | 应用把一次运行的结果传给另一次运行 | 分开的 Runner.run 调用 | | SDK 交接 | 当前活跃的智能体及其上下文发生切换 | 现有运行继续进行 |

比如，一个分诊智能体可以把“现在气温多少”这类问题转给天气智能体，把“Costco 几点开门”这类问题转给本地信息智能体。交接决定的是哪个专家智能体来处理请求。Davis 确认 Temporal 集成能识别交接，但没有现场演示。

12

持久化、停止与运营归属

最后几个问题区分了两种情况：杀掉 worker，和丢失后端服务的存储。本地开发服务器可以配置成持久化到磁盘，比如用 SQLite；Davis 平时用的都是用完即弃的本地状态。自托管的 Temporal 支持关系型数据库和 Cassandra。Temporal Cloud 则提供托管持久化和多区域命名空间。Davis 介绍说，工作坊举办时 Temporal Cloud 在 AWS 上覆盖 15 个区域；Google Cloud 上她不太确定，估计有四到六个。这些是当时的可用性数据，不是部署建议。自托管仍然是一个明确的选项。

停止工作流和停止它的 worker 也是两回事。异步启动工作流会返回一个句柄，调用方可以通过它请求停止执行。正常结束则简单得多：应用逻辑判断任务已完成，从工作流返回即可。持久化执行能保住未完成的工作，但什么叫“完成”，仍然得由应用自己来定义。

工作流不一定只代表一个短请求。实体工作流（entity workflow） 可以代表一个长期存在的对象，比如某位会员客户的数字孪生。每次结账扫二维码，都会向这位客户的工作流发送一个 signal。工作流处理完事件就回到等待状态，整个生命周期可能长达数年。等待期间不需要 worker 一直运行，不过持久化的历史和状态仍然占用存储。

持久化本身也不会替客户重启或监控基础设施。有人问 worker 故障时如何对接事件管理系统，Davis 说这类集成都是客户自己做的；她不知道有原生的 Slack 连接器，也不确定 Cloud 有没有专门的选项。worker 的部署可以交给 Kubernetes 的告警、仪表盘和自动扩缩容。Temporal Cloud 托管的是服务，工作负载和 worker 由客户自己托管。Davis 只是把托管 worker 当作一个设想提了一句，当时并没有路线图上的承诺。

现有示例覆盖了什么——又没覆盖什么

剩下的问题检验的是：演示的这套模式已经推广到了什么程度。关于语音智能体，Davis 一时举不出例子；另一位讲者提到有一些实验，包括内部的尝试，但不知道有已经上线的案例。有人问有没有 Claude Agent SDK 模板，Davis 说她还没有现成的 Claude 示例，Gemini 示例倒是快完成了。她欢迎大家为这个 MIT 许可的 cookbook 贡献代码。这些回答反映的是工作坊当时有哪些示例，而不是现在各家模型厂商的支持情况。

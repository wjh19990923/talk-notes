打造出色的智能体技能：逃离“技能地狱”的实用框架

Matt Pocock 讲解了如何从四个设计关注点来评估和改进智能体技能：调用方式、内部结构、行为引导，以及有纪律的精简。

01

为什么更多技能不一定带来更好的智能体

智能体技能的核心问题不是太少。开发者可以下载、贡献、组装各种技能，却依然搞不清这些技能怎么配合，也分不出哪些好用、哪些不好用。Matt Pocock 把这种状态叫作 技能地狱（skill hell）：表面上的能力越堆越多，却没法稳定兑现承诺的效果。 0:00 0:51

这个问题不只困扰个人开发者。企业也许有一套希望智能体执行的操作流程。如果不清楚怎样把流程写成有效的技能，手头再多技能也不会自动变成业务价值。Pocock 认为，缺的是一套大家都认同的评判标准，用来衡量一个技能为什么管用。 0:51 1:50

他提出的标准分四部分。触发（trigger）决定以什么方式调用技能。结构（structure）决定指令和辅助材料怎么组织。引导（steering）塑造智能体的行为。修剪（pruning）在技能跑通之后删掉多余内容。有了这四类，判断技能好坏就变成了一组具体的设计决策，不再是凭感觉说“这个提示词好像有用”。 1:50 2:35 19:03

- 技能多到无法评估、无法有效组合、也无法稳定产出结果时，就陷入了技能地狱。 - 企业需要一个实用的方法，把操作流程变成有效的智能体技能。 - 从四个维度评估技能：触发、结构、引导、修剪。

02

决定由谁承担调用技能的负担

用户可以显式调用技能，也可以让模型自己挑选。对模型调用的技能来说，技能描述会进入智能体的上下文，充当一个上下文指针：智能体根据这段描述，决定要不要去读对应的 skill.md 文件。技能也可以不给模型留这个指针，这样只有用户主动调用时才会用到它。 3:28 4:23

模型调用更方便，但这份方便要持续付出代价。每多一个模型可见的技能，上下文里就多一段描述：每次请求都要多耗 token，智能体也多了一个需要权衡的选项。Pocock 把这叫作上下文负担（context load）。如果环境里有 100 个模型调用的技能，智能体就得背着 100 段对应的描述。 5:17

用户调用把这份负担从智能体身上转到了使用者身上。智能体接收的背景上下文少了，用户却得记住有哪些技能、什么时候该调用。Pocock 把这种反向的代价叫作认知负担（cognitive load）。他还拿 superpowers 作对比：superpowers 主要走模型调用的路子，他自己则更喜欢亲手控制技能什么时候运行。 5:17 6:16

可靠性上也有取舍：哪怕某个技能明显适合当前任务，模型也可能不去跟随那个上下文指针。Pocock 偏爱显式调用，因为这样就排除了这层不确定性，也不用再去评测模型有没有在预期的时机选中技能。不过他并不认为哪种调用方式在所有情况下都更好；两种方式只是把成本和责任挪到了不同的地方。 6:16 7:22

- 模型调用的技能会暴露一段描述，把智能体指向对应的 skill.md 文件。 - 每个模型可见的技能都会加重上下文负担：多耗 token，也让智能体多一个要考虑的选项。 - 用户调用的技能减少了背景上下文，却加重了认知负担，因为用户得知道什么时候调用。 - 显式调用避免了一种不确定性：模型会不会跟随相关的上下文指针。

调用方式把负担转向了哪里 模型调用会增加上下文负担和选择上的不确定性；用户调用则把责任转给用户。 - 模型调用 — 智能体能看到技能描述。 - 上下文负担 — 描述会消耗 token 和注意力。 - 选择不确定性 — 智能体可能忽略相关的指针。 - 用户调用 — 用户显式选择技能。 - 认知负担 — 用户要记住有哪些技能、何时使用。 - 模型调用 → 上下文负担（增加） - 模型调用 → 选择不确定性（引入） - 用户调用 → 认知负担（增加）

03

把操作步骤与辅助参考资料分开

Pocock 把大多数技能拆成两个基本单元：步骤（steps）和参考资料（reference）。步骤描述智能体该遵循的流程，参考资料提供执行流程所需的信息。一个技能可以只包含其中一类，但分清两者之后，就更容易判断哪些内容属于工作流本身，哪些只是起辅助作用。 7:22

他的 2PRD 技能就是这个模式的例子。它的流程是：找到相关上下文，和用户确认测试接缝（test seam），然后写一份产品需求文档。确认这一步在测试环节设了一个人工检查点。支撑这些步骤的有两份参考资料：一份解释什么是测试接缝，一份是产品需求文档模板。 7:22 8:24

主 skill.md 文件应该在任务允许的范围内尽量小。技能越短，越容易维护和审查，也越容易装进上下文。结构上的关键问题是：某份参考资料是不是每次都用得上。在 2PRD 里，PRD 模板和测试接缝说明都服务于同一个反复执行的工作流，所以 Pocock 认为两者留在主文件里是合理的。 8:24 9:28

有分支的工作流就需要另一种安排。以 Pocock 的领域建模技能为例，它可能会更新一个名为 context.md 的本地术语表，可能会创建架构决策记录，也可能两者都不做。对应的模板并不是每次都需要，所以可以放在单独的文件里，和技能打包在一起。主 skill.md 再用条件式的上下文指针，只在某个分支用得上时才加载对应的外部参考资料。 9:28 10:30 11:29

- 把流程步骤和辅助资料分开，辅助资料只负责帮智能体完成这些步骤。 - 2PRD 的工作流是：找到相关上下文，和用户确认测试接缝，再写产品需求文档。 - 如果某份参考资料每次都要用，又服务于同一个反复执行的工作流，就留在 skill.md 里。 - 把只属于某个分支的模板移到外部参考资料中，只通过相关的条件式上下文指针加载。

04

用引导词和聚焦的阶段来引导行为

一个技能写明了预期结果，智能体的行为照样可能不符合预期。Pocock 最主要的引导手段是引导词（leading words）：简短却承载大量含义的词或短语，可以在技能里反复出现。按他的说法，智能体会在推理和输出里重复这些词，边干活边强化预期的做法。 11:29 12:23

他举的例子是一个横向实现软件的智能体：把数据库、schema、API 端点和前端当成彼此独立的层，一层层做完。与其只靠一大段警告来阻止这种做法，不如在技能里始终强调垂直切片（vertical slice）。这个词会把注意力引向先让一个小的端到端实现跑通，再往外扩展。如果它出现在推理 trace 里，就是一个实用的信号，说明智能体已经接受了预期的思路。 12:23 13:15

引导词的价值在于一致，而不是把整个技能浓缩成一句口号。Pocock 建议在指令里反复使用简洁、有分量的术语；如果行为还是跑偏，就试试更有力的替代说法。也可以让智能体帮忙想候选短语。真正的检验是：这些术语有没有真的出现在智能体的工作里，有没有改变最后的计划。 13:15 14:15

还有一种引导问题：智能体已经看到了最终目标，于是草草跳过中间阶段。Pocock 在 plan mode 里就观察到了这一点：智能体问几个澄清问题，就急着给出计划。他的做法是把澄清环节拆成一个叫 grill with docs 的技能，之后再接 2PRD，这样智能体只看得到当前阶段。在需要深入调查的场景里，藏起后面的步骤能让智能体多下一些跑腿功夫（leg work）。不过他也明确说，没必要把每个技能都拆成一个个独立阶段。 14:15 15:12 16:18

- 在技能里反复使用有分量的引导词，让智能体把预期的思路带进推理和输出。 - 用“垂直切片”引导实现过程，先做出一个能跑的小增量，而不是把各个技术层孤立地做完。 - 检查推理 trace 里有没有出现选定的术语；行为还是跑偏时，就打磨引导词。 - 如果藏起后续目标能让智能体在澄清阶段多下功夫，就把 grill with docs 和 2PRD 拆开。

引导词如何引导实现 一个反复出现的短语从技能指令进入智能体的推理，再影响实现计划。 - 引导词 — 在技能里反复写“垂直切片”。 - 推理 trace — 智能体复述预期的思路。 - 实现计划 — 规划一个薄薄的垂直切片。 - 可运行的增量 — 先让小东西跑起来，再扩展。 - 引导词 → 推理 trace（重新出现） - 推理 trace → 实现计划（塑造） - 实现计划 → 可运行的增量（优先）

05

删掉重复、沉积物和不起作用的指令

技能跑通之后，就该审视它剩下的篇幅了。在 Pocock 看来，技能臃肿本身算不上优点，反而说明可能还藏着别的设计问题。第一个纠正手段是单一事实来源（single source of truth）：流程指令、模板和定义，都不应该在各个步骤或辅助参考资料里重复出现。 16:18 17:07

另一种常见问题是沉积（sediment）：多人往同一个 markdown 文件里不断加内容，却从不删减或重新整理之前写的东西，文件就这样一点点堆积起来。解决办法先从结构入手：判断每处新增内容是否适用于所有分支，把只属于某个分支的信息移到相应的外部参考资料里，再删掉无关或过时的内容。 17:07 18:05

最后要清理的是空操作（no-op）：一条指令看着有用，实际上没怎么改变智能体的行为，因为没有它，智能体本来也会这么做。Pocock 举的例子是一段要求写长篇详细 commit message 的文字，而就算没有这段话，智能体也可能写出够用的提交信息。一个实用的删除测试是问：删掉这条指令，会有什么变化？如果行为基本不变，这段文字可能就不值得它占用的上下文。 18:05

完整的审查最终回到同样四个问题：触发方式有没有平衡好上下文负担和认知负担；结构有没有把步骤和分支专属的参考资料分开；引导词和阶段边界有没有带来预期的行为；修剪有没有清掉重复、沉积和空操作。Pocock 把这套方法定位为一个可反复使用的框架：既能改进现有技能，也能在采用社区编写的技能之前先评估一番。 19:03 19:55

- 每条指令、定义和模板在步骤和参考资料之间只保留一个事实来源。 - 清理沉积：把分支专属的材料移走，删掉无关或过时的内容。 - 用删除测试找出空操作——它们占用上下文，却没有实质改变智能体的行为。 - 最后逐项复查：触发成本、结构分支、引导词、阶段聚焦，以及还剩下的空操作。

要点总结

  • 从四个明确的维度评估技能：触发、结构、引导 和 精简。1:50 2:35 19:03
  • 有意识地选择调用方式：由模型调用的技能会增加 上下文负担 和选择上的不确定性，由用户调用的技能则会增加操作者的 认知负担。4:23 5:17 6:16
  • 把技能组织成 步骤 和 参考资料，并把特定分支的模板放在上下文指针之后，而不是每次调用都加载。7:22 8:24 9:28 10:30
  • 使用一致的 引导词，比如 垂直切片，以紧凑的方式表达预期的工作风格，并检查推理轨迹，看智能体是否真的采用了它。12:23 13:15 14:15
  • 当智能体草草带过一个重要的中间阶段时，考虑把这个阶段拆成独立的技能，让后续目标不会过早地转移它的注意力。15:12 16:18
  • 通过删除重复内容、累积的 沉积物、过时的引用，以及删除测试表明不改变行为的 空操作，让技能保持精简。16:18 17:07 18:05 19:03

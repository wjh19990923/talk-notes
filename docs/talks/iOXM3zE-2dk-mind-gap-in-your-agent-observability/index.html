01

火车在变，平台仍有它的要求

A new train can fit one platform perfectly and leave a dangerous gap at another. Treat the train as an agent and the platform as its requirements: improving the technology does not automatically make its behavior fit the application. London's Mind the gap and New York's Watch the gap become useful instructions for agent developers. Evaluation measures the distance between expected behavior and actual behavior, starting early and continuing throughout the agent's life.

The analogy extends beyond evaluation. A platform warning is a guardrail that helps passengers use the system safely. Repeated announcements keep that warning present as conditions change. Agents likewise need safety mechanisms and ongoing monitoring, across both today's application and the agents added later. Amy Boyd, who introduces herself as the lead of Microsoft's Foundry Developer Relations team, and Nitya Narasimhan organize the workshop around the next practical question: once observability produces data, what should a developer change?

02

评估、监控与优化

The companion workshop repository supplies the labs and continues to evolve between events. The presenters also point attendees to the Microsoft Foundry Discord's AI engineer channel for questions while working through it. The material addresses a production problem that appears even in small demos: agents are nondeterministic, but customers still need reliable, consistent behavior.

Three activities turn that problem into a development loop:

- Evaluate: measure performance, output quality, and safety. - Monitor: track behavior as requirements, customers, and environments change. - Optimize: use the evidence to improve the agent and debug failures.

Microsoft Foundry provides the workshop's implementation: developers can build agents there or bring agents built elsewhere into its hosting, observation, and management capabilities. The scope grows from building a reliable first agent to debugging production systems and eventually managing fleets containing many multi-agent systems.

03

评估工作流内部的决策

Tracing records what the agent actually does: the tools it calls, the messages it sends, and the steps through which a request passes. Foundry builds on OpenTelemetry, commonly shortened to OTel, so instrumentation can span different agent implementations and feed a shared control plane. Evaluation adds judgments to that execution record. Built-in evaluators cover quality, risk and safety, and agent-specific behavior; custom evaluators can supply criteria that the built-in catalog does not capture.

Consider a weather agent receiving a request for today's weather in London. There are several distinct places to check its work:

| Decision point | Evaluation question | |---|---| | Interpret the request | Did it resolve the intent as local weather? | | Choose and call a tool | Did it select the expected weather tool? | | Execute the call | What happened operationally during the call? | | Answer the user | Did it complete the task and follow its instructions? |

For a nondeterministic agent, expected tool selection is something to measure across runs, rather than assume from one success. Task-adherence criteria may also need refinement as the application develops. Evaluating these intermediate decisions makes an imperfect final response actionable: the developer can locate the stage that needs changing.

The same principle becomes more valuable as workflows grow. A full multi-agent trace preserves the relationship between agents instead of showing each one in isolation. Continuous evaluations can run when code changes; scheduled evaluations can look for deterioration over time; red teaming probes security weaknesses. Foundry connects this agent-level view to Azure Monitor, where infrastructure and data-service telemetry already live. A fleet view then brings together agents hosted in different places. The security tooling includes both platform scan options and the open-source PyRIT framework, which supports proactive identification of generative-AI risks.

在不损失质量的前提下优化成本

An audience member asks whether the workflow can optimize cost and context windows, and whether a wrong turn can be rolled back as a whole transaction. Narasimhan's cost answer starts with model choice: try a cheaper model, immediately rerun evaluations, and check whether savings came with an accuracy regression. Foundry manages the demonstrated workflow without requiring an external orchestration framework. More broadly, the observability boundary is the interface: portable tracing needs OpenTelemetry-compliant telemetry, and the companion workshop specifies Responses API-compliant endpoints for evaluation. That lets the observability workflow span implementations without assuming that arbitrary endpoints or arbitrary logs are interchangeable.

09

加入调试时你会需要的上下文

As the agent changes, the number of plausible failure causes grows. Custom trace attributes let developers record the application context they will need when investigating. The tracing notebook first configures console output and enables two environment settings: one for generative-AI tracing and another for message-content capture. Exact setting names belong to the workshop's package versions. Content capture also requires care: prompts, responses, and tool arguments can contain sensitive information, so capture only what is needed and apply redaction, access controls, and retention limits.

The mechanism is an OTel span carrying developer-defined attributes around the work being investigated. For the Paris-trip request, a small Python wrapper can record the destination and agent role without recording the complete prompt:

```python from collections.abc import Callable from opentelemetry import trace from opentelemetry.sdk.trace import TracerProvider from opentelemetry.sdk.trace.export import ( ConsoleSpanExporter, SimpleSpanProcessor, )

provider = TracerProvider() provider.add_span_processor( SimpleSpanProcessor(ConsoleSpanExporter()) ) tracer = provider.get_tracer("contoso.travel")

def ask_about_paris(invoke_agent: Callable[[str], str]) -> str: with tracer.start_as_current_span("travel.request") as span: span.set_attribute("contoso.destination", "Paris") span.set_attribute("contoso.agent_role", "travel") return invoke_agent( "I'm thinking about planning a trip to Paris. " "What should I know?" ) ```

Here invoke_agent is the application's existing request function. The custom attributes make console traces searchable by the facts relevant to the investigation; the notebook demonstrates adding such attributes to a conversation and inspecting the resulting local traces.

对问题空间分类

幻灯片原文
Complicated systems have predictable parts that experts can analyse and plan around. In complex systems, agents adapt to one another and produce emergent behaviour, calling for probing, sensing and responding.

Categorising problem spaces

Complicated
in → out
knowable · predictable · analyse → plan → execute

Complex
adaptive · emergent · probe → sense → respond

Complex: adaptive agents that respond to one another — a cat, a flock, a market. 设计约束

幻灯片原文
Engineers can enable or govern agent actions, combine boundaries with shared goals, and adjust the rate of coupling through small, reversible steps.

2
Engineer Constraints

QUESTION 1
Open or close?
A rule either opens new moves — enabling (a shared language, a market, a scoreboard) — or closes options — governing (a speed limit, a locked door). This is just what the rule does.

enabling = "you now can" · governing = "you may not"

QUESTION 2
Wall or goal?
To stop it flying apart you either build a wall around it — a container (a fenced playground: do anything inside) — or give it a shared goal to orbit — coherence (a team that all wants to win, so it holds together with no fence). Usually some of both.

container = hold by a boundary · coherence = hold by a shared pull

QUESTION 3
How fast?
This one isn't a rule at all — it's the tempo. Don't switch everything on at once: open one small, fully reversible thing first, watch, then widen. That is the dial (the rate of coupling).

scrimmage before the championship — one reversible step at a time

超越框架：迈向自适应工程之旅

Rajiv Chandegra 探讨了多智能体系统可能如何形成并修改自己的组织结构，以及工程师仍然需要约束、观察和控制哪些东西。

熟悉语言模型智能体、工具调用和智能体框架会有帮助；系统概念会在出现时介绍。

01

当问题不断变化时会怎样？

框架在执行开始前，就给智能体分好角色、配好工具、排好工作顺序。如果环境变化太大，这些安排不再适用，会怎样？Rajiv Chandegra 正是从这个问题出发。他是伦敦的一名执业医生，通过 Annicha Labs 研究智能体、人类与机构之间如何协作。他的起点大家都很熟悉：使用或配置一个框架，比如 Pi、Claude Code、Cursor 或 Codex，再通过它引导智能体干活。这样做出来的工作有条理，也可靠。他认为，大多数工程问题都适合这种做法。

Chandegra 预计，有两股压力会挑战这种做法。一是模型越来越强，那些为弥补早期模型短板而搭的脚手架，可能很快就跟不上了。二是 AI 工程可能走出屏幕背后的软件，持续与人、机构和物理世界打交道。这些环境在工作进行中就会变。他给出的应对是自适应工程：工程师设定约束，也就是游戏规则，让框架在执行过程中自行涌现、稳定、变化，直至最终消解。

02

从无状态的模型到经过审查的工作

现在的框架提供了一整套机制，把通常无状态的语言模型变成一个能干活的系统。系统指令确定行为；AGENTS.md、CLAUDE.md 这类文件提供项目上下文；工具调用让模型能够动手做事。Chandegra 说，厂商的系统提示词是固定的，项目指令则在会话开始时加载。不过谈到产品能力，如今得说得更细一些：当前的 Claude Code 文档支持替换或扩展系统提示词，Pi 也支持自定义提示词，还能在会话中用 /reload 重新加载。这些现有能力并不能还原演讲时所用的版本。真正不会过时的区别在于：一边是工程师主导的定制，另一边是一组智能体在执行中自主重组自身结构。

在这样配置好的环境里，智能体各自获得不同的角色、能力、规则和技能。它们产出代码、文档、issue 或交接材料。循环推动这些工作走向一个结果，比如做完一个功能、解决一个问题，最后由人来审核。所以框架规定的不只是一段提示词：它决定了能力怎样变成分工明确的工作，产出怎样喂给后续工作，整个流程又怎样走到审核这一步。预先把这套机制定好，就是框架工程（harness engineering）。Chandegra 认为，正是它从当前模型身上榨出了大量价值。

03

工厂契约及其取舍

模型是引擎；框架是引擎周围让它发挥作用的一切。 这些外围机制形态各异：命令行编程工具，如 Claude Code、Codex 和 Pi；IDE，如 Cursor；用 LangChain 做的多智能体编排；还有 Hermes、Cline、Goose 等工具。它们的差别在配置和能力，也在工程理念。一个有主见的框架，会把“工作该怎么做”的看法写进去，所以对特定任务、特定工程师格外有吸引力。

可扩展性并不能免去这些结构上的选择。比如 Pi 强调核心极简、扩展性强。Chandegra 关心的是：角色、预期产出、执行顺序的规则、记忆怎么生成，这些由谁来决定？在工厂式做法里，这些安排大多由工程师在开工前就定好。这样能换来三个好处：

- 可靠性：输入相近，输出往往也相近（模型本身的波动除外）。 - 可审计性：改了什么、什么时候改的，都能查。 - 因果可追溯：出了问题，工程师能顺着链条一路找回源头。

这就是他说的流水线类比：每个工位都事先设计好，每个智能体都有自己的活、在流程中的位置，以及明确的交接方式。

产品和问题都定义清楚时，流水线很有价值。功能和解法都已知，准确、快速、可复现、行为可认证这些目标就都够得着。但 Chandegra 认为，这种安排也有代价：为了可靠而压制差异，也可能把问题变化时需要的新意一并压掉。一个围绕已知工作优化好的流程，很可能腾不出空间去摸索另一种组织工作的方式。

模型进步带来了另一种变化。他举了个例子作预测：今天精心搭好的脚手架，一个月后可能就用不上了，因为更强的模型已经不需要它。环境变化则带来另一面的问题：每遇到一种没预料到的情况，就得靠人再打一个补丁。规则越积越多，最后框架比它要解决的问题还复杂。所以他的分界线在于问题本身动不动：固定的工作适合工厂式方法；持续变化的工作，可能需要一个能跟着变的结构。

04

一团火焰、一群鸟以及各部分之间的关系

为了说明变化中的问题为什么需要另一种工程方法，Chandegra 换了一个分析单位。还原论从稳定的组件出发：把整体拆开，研究各个部件，再弄清它们怎么拼在一起。关系是在部件之后才考虑的。很多软件都走这个路子：造好组件，连起来，得到产品。

系统论或关系论则把过程和关系放在首位。看上去稳定的物体，也可能只是靠持续活动维持住的一种模式。按这种看法，生物体更像一团火焰，而不是一块晶体。火焰看起来是个东西，但它的存在靠的是一个时刻不停的过程。过程一停，这个“东西”也就没了。

局部互动还能产生单个组成部分没有的性质。Chandegra 用水的“湿”作为直观例子：这种集体性质既不属于单独的氧，也不属于单独的氢。更贴近操作层面的例子是鸟群。每只鸟只遵循局部规则：和邻近的鸟对齐、避免相撞、保持靠近。没有哪只鸟在规划整个鸟群，群体层面却出现了协调一致的运动。孤立地研究一只鸟，看不到维系这种组织的关系。这个类比把工程上的注意力从固定组件转向了互动模式。

05

复杂的问题与一团乱麻

Chandegra 借用了 Russell Ackoff 对乱局（mess）的描述：管理者面对的不是一堆界限分明的任务，而是不断变化的局面，里面的问题彼此牵连。把每个看得见的问题单独解决，可能会漏掉那些不断变动、让局面变棘手的关系。乱局是一个由问题构成的系统，不只是一份更长的待办清单。

由此引出“繁杂”与“复杂”两类工作的区别：

| 维度 | 繁杂 | 复杂 | |---|---|---| | 例子 | 大型喷气式客机、钟表 | 鸟群、市场、组织 | | 参与者 | 被动的部件 | 相互适应的行动者 | | 理解方式 | 拆解并分析 | 长期观察互动 | | 应对方式 | 分析并规划 | 试探、感知、响应 |

繁杂系统可能极难造出来，但专家分析能让它的行为变得可知、可预测。复杂系统里，参与者会相互回应、不断变化，孤立地分析各个部分，没法完整描述不断演化的整体。Chandegra 认为，把复杂问题当成单纯的繁杂问题来处理，是设计上的失误：原计划执行得再好，也纠正不了一开始就分错了类。

06

局部适应如何产生可识别的秩序

他提出的复杂自适应系统，第一个要素是多样性。其中的智能体或行动者必须以有用的方式彼此不同，而不是一群克隆体。它们在局部互动，没有谁能看到整个系统。每个参与者回应身边的参与者，然后递归地学习：做出调整，承受调整带来的后果，再根据同伴和环境重新调整。

这些反馈回路可能产生涌现：一种没有哪个参与者设计过的模式、组织或行为。但局部持续变化，并不意味着整个系统会分崩离析。Chandegra 引入了吸引子的概念，指系统倾向于回归的稳定状态。他用室温下的水来说明：更小的尺度上一直在活动，整体上仍保持着可辨认的稳定。他看到的机会正在于此：局部在变，整体组织却能延续，而且不需要一个中心角色来规定每一步动作。

07

让框架成为一项持续的产出

对繁杂、可预测的工作，固定式工程依然合适。在 Chandegra 看来，如今大多数工程问题都属于这一类。他的替代方案建立在两个预测上：模型能力大幅提升；工程走出沙盒持续运行，直接与社会和物理环境接触。在这些条件下，一次性选定的结构，可能工作还没做完就已经不合适了。

自适应工程设计的是约束，让框架本身在约束下涌现、稳定并适应。 框架不再只是工程师提供的输入，而成了系统持续产出的结果。能力足够强的智能体围绕某个目标或环境相互作用；这些互动生成的组织，并没有事先完全规定好。从鸟到鸟群的类比，变成了从智能体到框架：智能体之间的关系形成结构，再由这个结构引导它们接下来的工作。情况变了，这个结构也能跟着演化。

08

从可互换的智能体到生态位和约定

Chandegra 设想了未来智能体的一种演进过程，前提是这些智能体能互动、能学习、能改变。一开始，它们形态相同，没有角色分工。交流起初很稀疏，随后耦合逐渐加强。在这个设想中，Chandegra 认为平均每个智能体大约有一条连接时，系统就开始显现。他并没有论证这个数字是 LLM 有效协作的阈值；这个设想既没给出图结构的假设，也没有实验结果支撑。工程上能调的杠杆是耦合速度：促使互动更快形成，或者抑制它的增长。

当环境反馈让“可互换”变得不再划算时，专业化就出现了。两个智能体在同一个地方干同样的活，就是冗余。一点小差异，比如一个先到、一个表现稍好，就可能得到正反馈并不断放大，直到两个智能体各自占据不同的生态位。在他提出的这套机制里，智能体的身份不是初始化时贴上的角色标签，而是它相对于其他智能体和环境，逐步形成的位置、角色或能力。

接下来，连接不再那么随机。配合得好的智能体聚成簇，出现了工程师事先没有划定的边界。反复的局部协作可以形成共同的规范和协议，进而产生去中心化的治理。这样形成的秩序能维持足够久，足以协调工作，但始终是暂时的：环境一变，组织必须能够重组。所以这个演进是从互动走向专业化、聚簇，再到形成惯例，而不是一次性找到一支永远最优的团队。

09

什么在变、谁来变、何时变？

这种组织在什么条件下发展，工程师仍要负责。工程师不再规定每一个结果，而是设定约束，给智能体留出探索的空间，然后感知并响应由此形成的结构，不必叫停流程、推倒重来。Chandegra 把固定式工程和自适应工程看作一个连续谱。完全固定的框架和完全自主的适应，都不是现实中的终点；放出一群没有角色的智能体，本身也不会产生有用的智能。怎么平衡，要看具体的工作。

Hermes 有助于看清这个连续谱的一个维度。它的项目介绍提到，要从经验中创建技能、在使用中学习。Chandegra 把单个智能体自身的提升称为纵向智能，把智能体之间的协调称为横向智能。两者方向正交：单个智能体变强，不会自动让群体组织得更好。他主张横向智能能提供更大的适应杠杆，这是在说工程精力该往哪里投，而不是对不同产品做的实测比较。

Pi 则有助于看清另一个维度：适应在什么时候发生、由谁主导。一个极简、可扩展的框架，给了工程师很大的自由去塑造工具。而这里所说的自适应工程，要求运行中的系统根据不断变化的问题或环境自行重组。Chandegra 拿 Pi 来区分自组织和定制，并不是说可扩展性不重要。他想要的是一个自组织的多智能体系统，这和一个可塑的智能体工具是两种不同的能力。

10

一位适应型工程师仍然掌握的控制权

首先，智能体得能互动、学习和改变；Chandegra 预计，未来的模型进步会让这些前提更扎实。然后，工程师围绕角色、执行顺序、记忆这些熟悉的框架属性来设置约束。他把可选的做法归结为三个问题：

- 放开还是收紧？ 放开更多智能体行为，还是用护栏管得更严。 - 设墙还是设目标？ 奖励朝共同目标的协作，还是让越出允许边界的行为付出代价。 - 多快？ 调节变化的节奏，包括智能体建立连接的速度。

这些控制手段塑造的是组织得以发展的空间，并不规定必须出现哪些关系。

用一个简短的 TypeScript 例子，能把这个区别说得更具体。假设工程师规定：只有对方是合格的同伴，而且这个智能体本轮的新连接额度还没用完，它才能提议建立新连接：

```typescript type CouplingPolicy = { eligiblePeerIds: ReadonlySet<string>; maxNewConnectionsPerRound: number; };

function canProposeConnection( peerId: string, newConnectionsThisRound: number, policy: CouplingPolicy, ): boolean { return ( policy.eligiblePeerIds.has(peerId) && newConnectionsThisRound < policy.maxNewConnectionsPerRound ); }

const policy: CouplingPolicy = { eligiblePeerIds: new Set(["agent-b", "agent-c"]), maxNewConnectionsPerRound: 1, };

const proposalAllowed = canProposeConnection("agent-b", 0, policy); ```

这个教学示例表达了一条边界和一个节奏上限。它只允许提出提议，既不会真正建立连接，也不会指定团队结构。至于哪些允许的关系真正有用，要靠前面讨论的互动和反馈机制来判断。

框架一旦成形，工程师要做的是感知并响应它，而不是把涌现出来的组织当成固定对象直接去改。两种做法的差别，在于结构持续从哪里来：

| 维度 | 工厂式做法 | 自适应做法 | |---|---|---| | 结构 | 事先强加 | 在工作中涌现 | | 框架 | 执行的输入 | 持续的产出 | | 控制 | 预先确定的组织 | 去中心化的协调 | | 运行环境 | 已知流程 | 持续变化的场域 |

自适应路线让这种调整在系统运行期间一直进行，因为环境不会停下来等你重新设计。

11

稳定还不够

涌现出的结构可能落进一个吸引子：感觉很稳定，却不是最好的安排。稳定不代表有用。 所以 Chandegra 指出还缺一个必要条件：真正的选择压力，也就是环境必须给出反馈，偏向有用的适应。在自然和社会系统里，环境压力会帮着决定哪些行为能延续下去。在他的方案中，怎样为自适应工程找到有效的对应机制，仍是一个悬而未决的问题。没有它，一个不断变化的系统可能只是在漂移。

其他风险，恰恰来自让适应成为可能的那些要素：

- 单一化：用相同数据训练出来的智能体，数量再多，也可能提供不了真正的多样性。 - 可理解性下降：结构随互动不断变化，要解释系统为什么这样表现就更难了。 - 事先可预测性下降：在执行中逐步形成的结构，没法像预先定好的流程那样，在运行前就交代清楚会怎么表现。

随着适应能力增强，这个方案必须直面这些实际运行中的问题。能够重组，不等于可以不去理解重组后的组织在做什么。

12

在持续生产中做工程

Chandegra 最后的预测是：能力越来越强的 AI，将持续与物理世界、多个机构和许多人打交道。在这样的场景下，工程变成了持续不断的生产：周围条件一直在变，系统必须一直运转。他预计，瓶颈会逐渐转向框架的适应能力，而不只是模型本身强不强。

他想发展的，是一种能在工程过程中不断变化的去中心化多智能体协作能力。适应能力必须属于运行中的组织，而不只是上线前可选的配置项。他把这称为智能时，特意收窄了范围，指的是框架适应能力上的智能：世界不断变化时，一个组织结构能持续找到可行形态的能力。

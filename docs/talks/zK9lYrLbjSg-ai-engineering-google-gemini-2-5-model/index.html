一条动手实践 Gemini Python SDK、token 计量、文档信息抽取、原生工具和 MCP 的路径，把状态、成本和执行边界都讲得清清楚楚。

你需要能读懂 Python 并运行 notebook 单元；跟着做练习还需要一个 Google 账号和一个 Gemini API 密钥。

01

发出第一个请求需要什么？

只有一个个人 Google 账号，能不能不先搭云端开发环境，就直接跑通一次模型请求？Philipp Schmid 的工作坊从这个实际问题讲起。Gemini 2.5 Pro 和 Gemini 2.5 Flash 能接收文本、图片、音频、视频和文档，输出文本。工作坊选了 Flash，因为当时它的 API 有免费额度。图像生成模型和新推出的文本转语音模型，是这个家族里另外的产品线。各模型支持哪些模态、上下文有多大、输出上限多少，都写在模型卡里。

工作坊材料在 Schmid 的 Gemini 2.5 工作坊仓库里。先是一个环境配置 notebook，后面分四部分：文本生成、多模态、结构化输出与工具，最后是 MCP。notebooks 目录里有能直接跑的示例，也有写了一半的单元格和练习；solutions 里是对应的完整版本。参与者可以按自己的节奏推进，课上课后有问题都可以到工作坊的 Slack 频道里提。

03

生成文本，然后算清所有的 token

Google Gen AI Python SDK 以一个客户端和它的 models 接口来组织请求。generate_content 接收模型 ID 和 contents；换个模型 ID 就换了模型，请求的基本结构不用动。第一个文本任务是：给一家主打可持续理念的咖啡店起三个名字。

```python import os from google import genai

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"]) model_id = os.environ["GEMINI_MODEL_ID"]

prompt = "Generate three names for a coffee shop that emphasizes sustainability." response = client.models.generate_content( model=model_id, contents=prompt, ) print(response.text) ```

把 GEMINI_MODEL_ID 设成你要用的模型。录像里用的是预览期的模型和价格，里面具体的 ID 和费率不要直接拿来当现在的部署配置。

count_tokens 在生成之前接收模型和输入。它统计的是提示词，不是还没生成的回答，也不返回价格。Schmid 的示例统计出 11 个输入 token；他另外按自己查到的 Flash 价格，估算费用约 0.00002 美元。生成完成后，response.text 能方便地拿到回答，response.usage_metadata 则给出用量明细，让你看清这次请求花在了哪里。

关键是分清 提示词 token、思考 token 和 候选 token。思考 token 是模型给出最终回答之前的计算，候选 token 就是回答本身。如果只统计看得见的回答，算成本时就会漏掉推理用量。在这里讨论的思考模式下，思考 token 和候选 token 按同一个输出单价计费：

``math \begin{aligned} C_{\text{request}} &= N_{\text{prompt}}p_{\text{input}} \\ &\quad + (N_{\text{thought}} + N_{\text{candidate}})p_{\text{output}}. \end{aligned} ``

式中每个 p 都是每个 token 的单价。Schmid 估计，演示的那条俳句请求花费不到 0.2 美分。作为对照，他引用了工作坊时期 Gemini 2.0 Flash 的价格：每百万输入 token 0.10 美元，每百万输出 token 0.40 美元。这组数字是那个模型的定价，和接下来要讲的思考模式计费是两回事。

04

用 token 预算控制推理

俳句示例用掉了 639 个思考 token。一首短诗，为什么要想这么多？模型会根据提示词动态决定推理用量；原始的内部推理过程不直接公开，但可以拿到思考摘要。思考预算（thinking budget）让调用方可以限制这部分用量。它限制的是 token 数，不是并行推理路径的条数。

Flash 被定位为混合模型：预算设为 0 就关闭思考，设为正数就允许先推理再回答。Schmid 把额外成本归因于序列不断变长时的注意力计算。按他对预览期定价的解释，分两种模式：

| 模式 | 工作坊时期的输出价格 | |---|---| | 关闭思考 | 每百万候选 token 0.60 美元 | | 开启思考 | 思考 token 加候选 token，每百万 3.50 美元 |

计费上的关键在于：按这个解释，开启思考后，整个输出都改按另一档价格计算，而不只是为一段隐藏的前置推理另外收费。

在配置里，thinking_budget=0 表示关闭思考。Schmid 说上限约 24,000 个 token，Flash 预览版发布文档给出的精确数字是 24,576。他举例说，那条俳句请求用了 600 多个思考 token，可以给它设 512 的预算。工程上真正能调的是 token 预算；这次讨论并没有说明模型内部如何选择推理路径。

05

流式输出答案，并让对话状态保持显式

对聊天界面来说，等完整答案出来再显示，往往不是合适的交互方式。generate_content_stream 的基本输入和 generate_content 一样，但返回一个迭代器。每个分块都可以马上打印出来，也可以通过 HTTP 服务转发出去：

``python for chunk in client.models.generate_content_stream( model=model_id, contents="Explain why token accounting matters in an LLM application.", ): if chunk.text: print(chunk.text, end="", flush=True) ``

流式输出改变的是应用接收回答的方式，提示词格式不用变。

Chats API 解决的是另一件事：记住用户和模型一来一回的对话顺序。在旅行规划示例里，模型第一轮推荐了几个欧洲城市。用户接着问有什么美食，模型能结合前面的对话理解这个问题。

```python chat = client.chats.create(model=model_id) print(chat.send_message("Help me plan a trip to European cities.").text) print(chat.send_message("What food should I try in those cities?").text)

history = chat.get_history() ```

聊天历史保存在客户端 SDK 里。 每次请求都会把整段对话重新发给后端，和应用自己手动拼装轮次数组没什么两样。get_history() 把这份状态暴露出来，方便持久化。如果客户端进程没保存就退出了，会话也就丢了。

系统指令和采样参数都放在生成配置里。Schmid 建议：基于检索、需要紧扣给定上下文的任务，温度调低；创意写作则调高。max_output_tokens 限制输出长度，top_p 和 top_k 提供更多采样控制。思考相关的设置也在同一个配置对象里：

```python from google.genai import types

config = types.GenerateContentConfig( system_instruction="Answer in English and use the supplied context.", temperature=0.2, max_output_tokens=1024, thinking_config=types.ThinkingConfig( thinking_budget=512, include_thoughts=True, ), ) ```

要求返回思考内容时，拿到的是摘要，不是完整的内部推理。

06

上传一本书，而不把存储与上下文混为一谈

下一个输入是《汤姆·索亚历险记》全文。Schmid 下载这本书，用 Files API 上传，再把返回的文件连同一条总结指令一起放进 contents。这条请求显示约 100,000 个 token。后续练习把这本书接进聊天会话，读者可以多轮提问。

文件引用改变的是传输方式，模型要读的内容一点没少。客户端发出的是一个 URI，后端解析这个引用，把文件内容放进模型的上下文。复用这个 URI，就不用每问一个问题都重新上传一遍。Schmid 说，访问权限由调用方的 API 凭证控制，不是一个谁都能打开的公开链接。

文件仍然得装得进所选模型的上下文窗口。如果文档超过工作坊里提到的百万 token 上下文，Schmid 预计会直接报错，不会自动分块。先统计带上文件后的输入 token 数，再决定是切分、先做摘要，还是只抽取任务需要的信息：

```python book = client.files.upload(file="tom-sawyer.txt") contents = [book, "Summarize the book's main events."]

count = client.models.count_tokens(model=model_id, contents=contents) print(count.total_tokens)

response = client.models.generate_content( model=model_id, contents=contents, ) print(response.text) ```

可复用的文件指针不会扩大上下文容量。 输入太大时，把它缩下来仍然是应用自己的事。

据介绍，上传免费，文件只临时保存。录像里对保留时长的估计并不确定；当前的 Files API 文档写明文件会在 48 小时后自动删除，也可以手动删除。文档里并没有演讲前面提到的“可配置上传有效期”。如果要把存储放在组织自己手里，Schmid 推荐用 Vertex AI 搭配自有的 Cloud Storage 存储桶，客户端的初始化方式也不一样。

07

向一份 PDF 提一个具体的问题

PDF 输入留下的只有文字吗？工作坊用一张超市小票来检验。Schmid 介绍说，这条处理流程会同时提供 OCR 文本和页面图像，notebook 里就省掉了手动转换再做 OCR 的步骤。他说文字和图像结合效果更好，但也承认不清楚内部具体怎么预处理。文档理解相关文档支持把 PDF 当作视觉输入，不过文档里较新的、针对特定模型的细节，不能倒推回这次演示。

第一次尝试时，本地没有小票文件。Colab 打开 notebook 时不一定会带上仓库里的全部文件，所以图像、音频和 PDF 练习可能得单独下载素材再上传。小票就位后，Schmid 展示了在 REWE 买的东西，有黄油、面包和红薯。虽然提示词是英文，这次演示仍用德语返回了正确的总金额 20.20。

有观众又问回思考预算：关掉思考会影响答案本身，还是只是把过程藏起来？Schmid 没有说自己了解内部机制。他把 token 预算比作粗粒度的推理强度档位，用 1,000、12,000、24,000 个 token 分别示意低、中、高三档——这些并不是 API 里有名字的预设值。他说，数学任务关掉思考可能会掉质量，普通的 OCR 和图像任务不开思考也可能做得很好。他建议的实验是：分别用 0、1,000、2,000、4,000 个 token 的预算跑评测，再根据要求的准确率和能接受的成本选定设置。

支持哪些输入，也得划清边界。工作坊涉及 JSON、PDF，以及受支持的图像、音频和视频格式。.jsx、.vue 这类源码文件如果因为扩展名被拒，Schmid 建议改成 .txt。Excel 工作簿则要先转成受支持的形式，比如提取出的文本或 Markdown，不能默认什么文档格式都能直接用。

小票也可以在 AI Studio 里测试，再用 Get Code 导出。Schmid 说，界面和 SDK 调用的是同一个底层模型和 API，参数也一一对应。不过在这个导出的示例里，文档是以 base64 内联的，不是 Files API 的 URI。决定应用该内嵌输入数据、还是复用已上传的对象时，这个区别就很关键。

统计 token 时，传给 count_tokens 的模型和完整 contents，要和生成时用的完全一致。在小票示例里，Schmid 说文档大约 500 个 token，提示词大约 20 个；观众提到界面上显示的是 560。预先统计的数字和请求完成后的提示词用量一致，响应里报告了 42 个思考 token 和 78 个候选 token。他随后关于 OCR 计费、每张图约 500 个 token 的解释并不确定；真正有用的做法是实测实际输入，而不是从这张小票推出一条通用的图片 token 规律。

08

在构建预处理流水线之前先测试视觉结构

有了页面图像，模型就能利用表格、图表和空间关系。为了测试简单的层级结构，Schmid 找来一张讲“怎么画思维导图”的思维导图，问它的中心概念是什么。AI Studio 回答 HOW TO MIND MAP。这里问的是视觉上的组织结构，而不只是让模型把每个标签照抄一遍。

更难的是密集的表格：在页面图像的分辨率下，表格结构会变得模棱两可。Schmid 建议把问题拆开：先用现有的文档工具把表格或某块视觉区域提取出来，再让多模态模型直接针对这块区域回答问题。他提议的下一个发票任务是对条目做算术，考察的是文字提取之外的理解能力。他还提到，视频摘要、按时间戳查找、视频分段也都能用这种直接提问的方式。对一小时以内的 YouTube 视频，Schmid 说大约 80 秒就能拿到摘要。

内容过滤是另一套控制。AI Studio 在 Advanced Settings 里提供安全设置，SDK 也支持。演示时 Schmid 关掉了可配置的过滤器；他介绍说，生成前后都会针对色情、仇恨等类别做分类。这些设置管不了版面混乱的文档能不能被正确理解。

自动生成的 PDF 里，页眉、页脚和图片相互重叠，对这种情况 Schmid 拿不出校准结果。人能不能读懂，是个粗略的判断标准：人都很难理清的页面，模型可能也理不清。更可靠的检验是一套有代表性的评测集。他建议别只在界面里试几个例子，而要拿一大批——可能上千份 PDF——来跑，再和支持团队一起排查失败的案例。Flash API 和 Pro 界面都能很快开通，做这类实验门槛不高；但环境搭好只是文档评测的起点。

到了国防、金融和全组织范围的治理，讨论就超出了 notebook 设置的范畴。Schmid 推荐用 Vertex AI 获得企业级管控和支持，提到了区域端点，还回忆起一则把 Gemini 部署进客户环境的发布消息。他没有给出那款一体机的部署细节，也没有完整说明应用层护栏如何对应到全局治理。观众提出的成本、性能和策略集成问题，仍要和云平台团队一起敲定。

09

把文档答案变成带类型的数据

回到发票，Schmid 让模型算出单价之和，而不是读印好的总额。他说在这份格式规整的例子上，算得没错。实用的起步方式是直接对着图像提问，等评测表明有必要时再加预处理。下一步，是让答案能被软件直接使用。

结构化输出规定了结果的形状。工作坊用 Pydantic 描述一份食谱：一个名称，加一个配料字符串列表，再把这些食谱放进一个列表容器。响应配置里指定 JSON MIME 类型和响应 schema：

```python from pydantic import BaseModel from google.genai import types

class Recipe(BaseModel): name: str ingredients: list[str]

class RecipeList(BaseModel): recipes: list[Recipe]

response = client.models.generate_content( model=model_id, contents="Generate two popular cookie recipes.", config=types.GenerateContentConfig( response_mime_type="application/json", response_schema=RecipeList, ), )

recipes = RecipeList.model_validate_json(response.text) for recipe in recipes.recipes: print(recipe.name, recipe.ingredients) ```

JSON 可以直接解析成带类型的对象，下游代码不必再去解读一段文字。

同样的机制也适用于多模态输入：给出文档，再给出要提取的信息的 schema。Schmid 犯了个很有启发的错：他给超市发票的请求挂的还是食谱 schema。那次运行，模型返回了一个空的食谱列表。把 schema 换成发票数据后，模型提取出了日期、所购商品和价格。schema 必须和任务对得上；应用要错了结构，结果哪怕格式完全合法，也可能毫无用处。

10

函数调用是请求应用去执行动作

函数调用把结构化输出用在了另一件事上。模型返回的不是一条发票记录，而是函数名和参数。函数声明告诉模型函数的名称、描述和参数 schema。提供天气工具后，问东京天气，模型会请求调用 get_weather，参数是 location="Tokyo"。把提示词换成一句问候，模型就正常对话，不调用函数。

模型决定调用什么，应用负责执行。 手动流程如下：

1. 发送用户的问题和工具声明。 2. 读取返回的函数名和参数。 3. 分派给应用里对应的函数。 4. 把函数结果加进对话。 5. 让模型基于这个结果继续回答。

演示里的天气函数返回的是假数据。最终回答说东京天气晴朗，22°C，体感 24°C。在同一个分派点，也完全可以改成调用数据库、真实 API 或邮件服务；这些操作都发生在应用自己的环境里。

MCP 保留了这个循环，同时把工具的发现和调用标准化。MCP 客户端调用 list_tools 拿到工具声明，交给模型。模型选中某个工具后，客户端通过服务器去调用，而不是分派给本地的 Python 函数。这样，服务商维护的天气或存储集成就能被许多应用共用，不必每个团队都写一遍同样的封装。

工具接得上，不代表选得准。Schmid 在工作坊时期的建议是只暴露五到十个工具；必要时，先用用户请求和工具描述之间的 embedding 相似度筛出一个较小的候选集。被问到能否长时间自主运行时，他提起 Gemini 2.5 Pro 通关《宝可梦 蓝》，以及一次约 200 小时的运行，但没有核实观众拿来对比的那次 Anthropic 运行。通用的工程约束是上下文不断增长：长时间运行的智能体需要一套总结或压缩对话的策略，至于能跑多久，取决于任务和编排方式。

11

区分生成的代码与执行的代码

原生工具把执行挪到了服务后端。开发者只要开启某项能力，不用自己写声明、在本地执行。Schmid 指出，这些内部步骤不会像手动工具示例那样，以明确的对话序列呈现出来。结构化输出在 AI Studio 里虽然挨着工具设置，但它本身不是原生工具。

人口示例把这个区别展示得很清楚。Schmid 起初让模型写一个函数，把五个城市按人口排序。Gemini 写了代码，却没有运行。一位观众指出，提示词要的就是“创建一个函数”。把请求改成“用 Python 来做”之后，模型生成了可执行的代码并运行了它。Schmid 描述了一张 Matplotlib 图表，并指向 notebook 里获取图表的示例；不过截取的画面里只有一张人口表格和一条关于图表的说明，图表本身并没有出现。

URL context 工具负责应用里另一个常规步骤：抓取一个已知页面，把内容交给模型。在工作坊介绍 Python 优点的示例里，调用方只给出 URL，不用手动把页面内容复制进提示词。Schmid 说，URL context 一次请求最多接收 20 个 URL。抓回来的内容会成为回答的上下文；代码执行还能通过 API 返回生成的图片。

Google Search 则从“发现”开始，而不是由调用方指定页面。比如问可再生能源的最新进展，这个问题会被转换成一条或多条搜索查询。搜索结果返回给模型，由模型综合出答案。溯源元数据（grounding metadata）把答案的各个部分和所用的网站对应起来，只是完整的内部工具调用序列不像自定义函数调用那样公开。

在后端执行，计费上照样有边界。抓回来的上下文会计入请求的 token。Schmid 不太确定地给出了 Google Search 的额度：1,500 次免费搜索，之后每 1,000 次 35 美元；他说 Python 执行免费，URL context 还在预览阶段，以后怎么收费他说不准。这些是工作坊当时的计费说法，不是现行的价格承诺。组合练习把 Search 和 URL context 或代码执行结合起来——比如先查出某门语言的当前版本，再写脚本并运行。

12

组合调研与工具工作流

有人问能不能出一个 Deep Research API，Schmid 没有承诺发布，而是给了一个可以自己组合的替代方案。他介绍了一个开源的 LangGraph 示例，用的是 Gemini 2.5 Flash 和 Gemini 2.0。它把问题转成搜索查询，跑多轮搜索，反思问题是否已经得到解答，需要更多资料就回头继续。反思这一步决定是再搜一轮，还是生成答案。

有了循环，成本怎么累积就更容易看清。在 Schmid 的例子里，用 URL context 抓取一篇 10,000 token 的博客文章，就会多出 10,000 个计费的提示词 token。自定义函数调用同样产生 token，但函数本身在应用这一侧运行；调用外部 API 的费用归那个服务计算。所以，研究型智能体既要算模型上下文的开销，也要算获取这些上下文所用工具的开销。

观众问到功能重叠的天气工具，话题转到了执行上的依赖关系。打开迪斯科灯球和播放音乐互不相干。先查室外天气、再设置恒温器，则必须按顺序来：第二个调用要用第一个调用的输出。系统指令可以规定预期的顺序，而模型的下一轮也可能再请求调用一个函数，而不是直接给出最终答案。

| 模式 | 依赖关系 | 对话行为 | |---|---|---| | 并行调用 | 输入互相独立 | 收齐结果，进入下一轮 | | 顺序调用 | 一个调用的输出是另一个调用的输入 | 继续工具循环 | | Live API 异步调用 | 结果稍后才到 | 对话可以同时继续 |

对普通的并行编排，Schmid 的做法是先收齐结果再继续；某个函数太慢，可能需要返回错误或“尚未就绪”。Live API 的异步调用解决的是另一个问题：语音客服对话中，不能因为后端在查询就冷场。应用先启动任务，等结果到了再注入对话。文档里有 Python 和 JavaScript 示例，还把“已排期”“被中断”等状态作为给开发者的信号来讨论。异步对话不等于并行执行。

可观测性仍要由应用自己负责。工作坊那时，AI Studio 还没有观众想要的 API 调用日志视图；Schmid 推荐 LangSmith、Arize AI Phoenix 或 Vertex AI。另一个问题是，Live API 的边界框和坐标有没有变准。他提到 Live API 已经从 Gemini 2.0 Flash 换成了 2.5 Flash，但没有声称空间定位质量有实测提升。这还得靠测试来比较。

选信息来源的区别很直接：URL context 抓取已知的链接，比如某个个人博客；Search 则在来源未知时，从问题里生成查询。两者都不保证能拿到付费墙后的内容。如果应用通过订阅有权获取某些内容，可以写一个自定义的 Live API 函数去抓取，再把结果作为上下文返回。

13

把一个 MCP 会话传给 SDK

SDK 的 MCP 集成把手动循环打包成了更简洁的接口。启动天气服务器，初始化一个 MCP 会话，再把会话放进生成配置的 tools 列表。SDK 会发现工具声明并发给 Gemini，通过 MCP 调用模型选中的工具，再把结果送回对话，直到模型能给出答案。

本地天气服务器要用基于 Node 的命令启动。在 Colab 里这一步失败了，Schmid 就把同一个 notebook 挪到本地的 Cursor 里跑。这次服务器调用 Open-Meteo，回答了旧金山的天气问题，返回的预报值是 17°C。这个结果说明，换了环境之后 MCP 循环完整跑通了，而不只是会话配好了而已。

连接方式很简洁：

```python import asyncio import os from google import genai from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client

async def main(): client = genai.Client(api_key=os.environ["GEMINI_API_KEY"]) server = StdioServerParameters( command="npx", args=["-y", "@philschmid/weather-mcp"], ) async with stdio_client(server) as (read, write): async with ClientSession(read, write) as session: await session.initialize() response = await client.aio.models.generate_content( model=os.environ["GEMINI_MODEL_ID"], contents="What is the weather in San Francisco?", config={"tools": [session]}, ) print(response.text)

asyncio.run(main()) ```

如果是远程服务，练习里会把 stdio 连接换成 Streamable HTTP 客户端。Cognition 推出的 DeepWiki 通过公开的远程 MCP 服务，提供代码仓库文档和问答。传输方式变了，SDK 的集成点仍然是初始化好的会话。

ADK（Agent Development Kit）位于这层客户端集成之上，补充了编排、MCP 集成、多智能体管理和部署支持。Schmid 把它看作抽象层级的取舍：框架能加快第一版的实现，但日后排查故障时，可能得深挖被它藏起来的那些层。直接用 SDK，这些层都摆在明面上；用 ADK，现成的东西更多。

14

管理进入上下文的内容

后面关于视频的讨论，解释了时间戳的原理。Schmid 介绍说，视频按每秒采样一帧处理，每帧都配上对应的时间戳。按这个采样率，60 秒的片段就是 60 张图像。源视频通常每秒 24 帧甚至更多，采样之后就不用把每一帧都送进去；他认为正是这样精简，大约一小时的视频才装得进百万 token 的上下文。提问可以针对某个动作、某句话，或它在录像中出现的时间。普通的 MP4 上传后就能作为多模态输入，不依赖 YouTube 字幕；一位观众说，用荷兰语素材效果也很好。

记忆则要做另一种区分：

- 短期记忆：当前请求状态里包含的对话。 - 长期记忆：来自之前交互或关于用户的信息，存在模型之外，需要时再提供给模型。

Schmid 介绍说，Mem0 能从对话中提炼出有用的表示，但没有证实它配合 Gemini 效果如何。哪些有用信息能进入长上下文，取决于抽取和筛选的质量。被问到更大的上下文窗口时，他说两百万 token 的支持正在开发，但还没有正式发布日期。随后聊到一千万 token 的研究，他提出成本是一个制约；他举的每百万 token 50 美元只是假设，不是产品价格。

MCP 同样只改变上下文的组装方式，选工具的仍然是模型。手写的 JSON schema 和从 MCP 服务器发现的 schema，在模型眼里没有区别。一个内部团队维护的封装，其他团队可以直接复用。假如有四个可用工具，调用方就提供四组名称、描述和参数 schema；Gemini 根据提示词和这些声明，决定不调用、调用一个还是调用多个。接一个带 50 或 100 个工具的服务器很容易，集成是省事了，选工具却更难了。

Agent2Agent（A2A）解决的是智能体之间的互操作，不是模型与工具之间的这层边界。Schmid 介绍说，用 LangChain、LangGraph、LlamaIndex 等框架构建的智能体，可以通过一个共享协议互相调用。他给出的是 ADK 里的示例，并没有说 A2A 是 Gemini SDK 的直接功能。

15

让执行、授权和归属保持分离

用程序抓取 URL，和操作一个网站是两回事。有些页面重度依赖 JavaScript，有用的内容很难提取。对这类页面，Schmid 介绍说，浏览器和 computer use 相关功能当时正和部分公司一起测试。模型会返回结构化的操作指令，交给本地或托管环境里的浏览器执行。Google 还在和 Cloud Run 团队合作，想让运行一个可控的 Chrome 实例变得更简单。这些都是对话里提到的预览方向，并没有演示真正的浏览器控制。

MCP 鉴权又给应用加了一份责任。Schmid 介绍了通过客户端完成 OAuth 登录，举的例子是 Atlassian 的登录弹窗；他还提出了一个影响更大的问题——权限范围：智能体该能访问所有仓库，还是只能访问任务需要的那一个？有个协议细节要说准确：他口头举例时把 403 当作触发登录的状态码，但 2025 年 3 月版 MCP 授权规范规定，凭证缺失或无效时用 401，权限或 scope 不足时才用 403。他还提到 Auth0 也在参与解决这类智能体鉴权问题。

关于来源标注的讨论，把应用里几个看似可以互换的字段区分开了。搜索的 grounding support 把生成答案中的一段文字和来源网站关联起来，界面可以据此高亮文字或加上参考编号。观众随后澄清，他问的是 citation_metadata，不是 grounding。响应参考文档把两者分开定义，并把 citation metadata 和“可能复述了受版权保护的训练数据”联系在一起。别拿它来代替搜索来源追溯。

第三种需求，是直接引用用户所提供文档里的原话。一位观众描述了 Anthropic 的文档引用功能，问能不能用结构化输出或 URL context 做出类似效果。Schmid 说，Gemini 当时还没有同样的功能，建议试试不同的提示词策略。后面关于 NotebookLM 的追问，也没有得到实现层面的回答。所以，让模型按引用格式输出，并不等于内置保证能精确引用原文。

最后一个 MCP 问题，是大家期待的 Gmail、Drive 等 Google 自家服务什么时候能接上。Schmid 说，这些远程集成还没有以大家想要的形式推出；这和前面公开的 DeepWiki 示例并不矛盾。他从安全角度论证：服务商最了解自己的 OAuth 和权限体系，最适合维护权限范围收得很窄的集成。被问到网站该怎么为 Google Search 的 AI Mode 做准备时，他只给了不太确定的建议——做高质量内容、遵循常规的 Web 标准——没有什么特殊的 schema 要求。

保留前缀并检查返回的证据

针对同一份文档反复提问时，提示词的排布有个简单的讲究：不变的 PDF 放前面，变化的问题放后面：

```python pdf = client.files.upload(file="invoice.pdf")

for question in ( "What is the total amount?", "Which items were purchased?", ): response = client.models.generate_content( model=model_id, contents=[pdf, question], ) print(response.text) ```

Schmid 说，这样排布应该能让自动缓存复用不变的前缀。一旦改动提示词开头，那段很长的公共前缀就匹配不上了。演示中没有展示实测的缓存命中；它展示的是可复用输入该怎么排布的原则。

最后几个技术问题都和 grounding 出错有关。一位观众反馈，返回的起止偏移量超出了答案的范围。Schmid 没遇到过这种情况，请对方提供可复现的例子；他也提到，起始索引为 null 可能表示从开头算起。这次交流既没弄清偏移量的单位，也没诊断出所报的 bug，所以应用遇到意料之外的索引时，不要擅自换一种方式去解读。

Grounding supports 和 grounding chunks 也不提供来源原文本身。返回的片段标出生成答案中的某一部分，并把它和某个网站关联起来，但不包含那个网页里对应的摘录。如果产品承诺“证据可查”，这条界线就很要紧：关联了链接的答案片段，和引用的原文段落不是一回事。Schmid 请大家把这些需求和问题反馈给 Search 工具团队；最后，他鼓励参与者把 notebook 继续做完，遇到具体问题就通过社交渠道或 GitHub issue 反馈。

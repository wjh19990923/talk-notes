Jane Street 如何构建 AI 驱动的开发者工具

Jane Street 把贴合任务的训练数据、可执行的反馈和一个共享的编辑器服务结合起来，围绕其 OCaml 开发环境构建 AI 辅助。

熟悉代码 diff、静态类型检查以及模型训练与推理的区别会有帮助；不需要 OCaml 经验。

01

当开发环境运行在 OCaml 上

如果常规的开发者工具和公司水土不服，怎样才能让 AI 编程助手真正派上用场？在 Jane Street，这件事归 AI Assistance 团队管。他们的职责是让公司从大语言模型身上获得尽可能多的价值。John Crepezzi 在开发者工具领域干了多年，其中好几年在 GitHub。到了 Jane Street，他碰上一个不寻常的约束：开发平台是 OCaml。提起这门函数式语言，人们通常会想到定理证明、形式化验证和编程语言实现。Jane Street 用它的范围要广得多。

- Web 应用： 开发者写 OCaml，再用 js_of_ocaml 把 OCaml 字节码编译成 JavaScript。 - 编辑器插件： 有了 VCaml，开发者写编辑器工具时也能继续用 OCaml。编者注：Crepezzi 把它描述为转译成 Vimscript。实际上，VCaml 通过 Msgpack RPC 为 Neovim 提供 OCaml 绑定，早于本次演讲的包元数据里有相关记载。 - FPGA 开发： 开发者用 Hardcaml 以 OCaml 描述硬件，不必直接写 Verilog。

所以，助手得能在差异极大的各类工程工作里支持 OCaml。

现成工具很难直接拿来用，原因有三：

- 语言覆盖有限： Crepezzi 认为，模型写 OCaml 表现差，是因为训练数据太少。他猜测 Jane Street 内部的 OCaml 代码量，可能比外界所有 OCaml 代码加起来还多。这只是他的估计，并没有实际比较过语料规模。 - 基础设施特殊： Jane Street 有自研的构建系统、分布式构建环境，以及名为 Iron 的代码评审系统。巨型 monorepo 放在 Mercurial 里。据 Crepezzi 上次统计，公司 67% 的人用 Emacs，也有人用 VS Code。围绕别的代码仓库、构建系统或编辑器设计的集成，没法直接搬进这套环境。 - 工作跨越系统边界： 团队想让模型去解决合并冲突、撰写功能描述、挑选评审人。这些任务超出了在单个编辑器里生成代码的范围，所以基础设施必须让各项能力贯穿整个开发流程。

02

在训练之前先定义编辑任务

面对这些约束，训练模型是一条代价高昂的路：耗时长，失败的可能也多。Meta 的 CodeCompose 让团队下定决心尝试。CodeCompose 针对 Hack 做了微调，这是个很有参考价值的类比：Hack 虽然开源，代码却高度集中在一家公司内部，和 OCaml 在 Jane Street 的处境一样。两者相似在代码的分布，而不是语法或语言行为。Crepezzi 还顺带提到一个巧合：Hack 的实现本身也和 OCaml 有关联。

编者注：CodeCompose 研究的是代码补全，它的结果不能当作 Jane Street 后来所做的 OCaml“提示词生成 diff”任务的实测数据。

最初的设想很简单：拿一个现成模型，让它见识一遍 Jane Street 的代码，就能得到一个懂内部库和惯用写法的同款模型。结果并不如愿。训练样本要贴近模型将来实际要做的交互。 光喂一堆源代码，模型学不会怎样响应编辑请求。团队首先得定下一个具体目标。

这个目标定为根据提示词生成 diff。开发者在编辑器里描述想要的改动，模型给出一个 diff，可能涉及多个文件。一次请求可能要同时改测试文件、.ml 实现和 .mli 接口。

diff 要能干净地应用，应用后也要有较大概率通过类型检查。预期的任务规模是最多 100 行改动——这是设计目标，不是实测出的能力上限。这样一来，训练问题就收窄到特定的输入、输出和一组检查上。

03

找到与编辑器请求相匹配的样例

每个监督学习样本需要三部分：

- 上下文： 编辑之前模型能看到的内容。 - 提示词： 一条请求，措辞像开发者求助时会说的话。 - Diff： 完成这条请求的代码改动。

难点在于找到大量三者确实对得上的样本。现有的开发记录里有描述，也有代码改动，但它们的组织方式反映的是人们怎样评审工作、怎样设置检查点，未必是人们怎样让助手改代码。

| 候选来源 | 能提供什么 | 为什么不能直接用 | | --- | --- | --- | | Iron Feature（类似 pull request） | 人写的 Description 标签页和对应的 Diff 标签页 | 描述比编辑器里的简短请求长得多；据 Crepezzi 说，一个 feature 往往有 500–1,000 行。拿来训练得先自动拆成更小的改动。 | | Commit | 开发过程中更小的检查点 | 提交信息可能毫无信息量，比如 Summary Z。Commit 是用来回退的节点，可能一次打包好几处改动，也缺少对单个编辑任务的有效描述。 |

Feature 描述是向评审人解释一项已经完成的工作；编辑器里的请求可能只是“把眼前这个报错修掉”。更小的 commit 如果仍然混着多处改动、也不交代意图，同样解决不了这种错位。于是团队转向工作区快照，尽量在改动发生的当下把它捕捉下来。

04

利用构建状态的转换恢复独立的编辑

工作区快照在开发过程中持续记录代码，同时记下一些信号，用来识别有意义的改动：

1. 全天捕捉工作站状态。 Crepezzi 举例说，大约每 20 秒拍一次快照。 2. 把构建状态和代码一起记下来。 记录构建是否为绿色；如果是红色，记下当时能拿到的错误信息。 3. 寻找绿 → 红 → 绿的转变。 开发者从能跑的代码出发，做了一处改动，构建暂时挂掉，随后又修好。这往往标志着一处独立的改动，不过这只是启发式判断，并不能证明改动确实独立。 4. 提取红 → 绿的修复。 开发者修好一个类型错误或编译错误时，把红色状态下的报错和让构建重回绿色的 diff 配成一对。

修复场景提供的训练样本尤其直接：模型既能看到编辑前的失败，也能看到解决问题的代码改动。

不过，快照里仍然没有开发者的请求。为了补上这一环，团队让 LLM 先为捕获到的改动写一段非常详细的描述，再一步步缩短，直到它读起来像有人会在编辑器里随手敲出的话。这样得到的提示词是合成的，但背后的编辑来自真实的开发工作。

05

把可执行的检查变成训练反馈

监督样本是 Crepezzi 所说训练循环的第一步，接下来是强化学习，目的是让模型的输出更符合开发者心目中的好代码。这就需要把一种宽泛的偏好，变成真正能执行的检查。

检查一层比一层严格：

1. 解析代码。 连 OCaml 解析器都通不过的输出，最基本的要求都没达到。 2. 对应用后的改动做类型检查。 把编辑应用到基础版本上，让类型检查器判断结果代码是否合法。 3. 编译并运行测试。 给模型一个可验证的任务，应用它的编辑，检查结果能否编译、能否通过测试。

评判的对象是改动后的代码库，而不只是生成的文本。所以基础版本和执行环境也成了训练机制的一部分。

为了反复执行这些检查，Jane Street 搭建了 Code Evaluation Service，简称 CES。它很像构建服务，但有一项关键优化：先在某个特定版本上跑好一次成功的构建，让它处于预热状态。worker 拿到模型生成的 diff 后应用上去，看构建是保持绿色还是变红，再把成功或报错信息回传给奖励函数。

Crepezzi 说，他们花了几个月时间用这个服务训练，把模型往“能编译、能通过测试”的方向对齐。预热好的构建让反复验证更快；反馈信号则直接来自每次编辑的实际后果。

06

评估模型是否真正完成了任务

同一套执行环境也能用来做评测。留出一部分强化学习数据，给模型出题，让它生成代码，再用这个服务检查代码能不能用。训练和评测可以共用验证机制，只是用的样本不同。

另一个代码评审实验暴露了另一类失败。团队希望模型像人类评审人那样先把代码过一遍，省掉重复劳动。训练了几个月后，他们提交了第一份代码让它自动评审。据 Crepezzi 回忆，模型没有动手评审，而是回复说明天再弄。

训练样本来自人类，而人类有时会把评审往后拖。模型学到了数据里确实存在、却违背工具初衷的行为。模仿人类的回应，不等于完成预期的任务。 有意义的评测要在投入更多时间和金钱训练之前，把这种差别揪出来。

07

在各个编辑器之间共享智能

通过评测还不是最终考验：模型得在开发者的编辑器里真正好用。Jane Street 需要为 Neovim、VS Code 和 Emacs 做集成，并满足三项要求：

- 共享行为只实现一次。 构建上下文、编写提示词这些逻辑，不该每个编辑器都重写一遍。 - 模型和策略可以随时替换。 最初的集成用的是没微调过的模型，团队预计之后会换上微调模型。选哪个模型、怎么写提示词，都要保持灵活。 - 衡量真实的编辑体验。 开发者在乎延迟，也在乎模型给的 diff 能不能应用上。团队想从真实的编辑器使用中拿到证据，判断这些改动到底有没有用。

最终做出来的是 AI development environment，简称 AIDE，夹在语言模型和轻量的编辑器集成之间。AIDE 负责构造提示词、组装上下文、获取构建状态，各个编辑器在这些共享能力之上实现自己的交互层。

AIDE 以 sidecar 应用的形式跑在开发者的机器上。这样放还有个好处：服务的部署和编辑器的部署分开了。团队可以在所有工作站上更新并重启 AIDE，不用改动各个编辑器集成，也不用等开发者重启编辑器。面向模型的逻辑在这个共享服务里实现，相关改动也从这里发布。

08

让每个编辑器保留自己的交互风格

共用 AIDE，并不意味着每个编辑器的外观和行为都得一样。演示中的界面都沿用了各自用户早已熟悉的习惯：

| 编辑器 | AIDE 交互方式 | | --- | --- | | VS Code | 可视化侧边栏，形式上和 Copilot 差不多：开发者提交请求，拿到可能涉及多个文件的 diff。 | | Emacs | 一个 Markdown buffer：开发者照常在里面移动光标、复制文本、提问，并用快捷键把更多内容追加到 buffer 底部。 |

Emacs 界面没有照搬侧边栏设计，而是把对话当成又一个文本 buffer。提示词和上下文构建是共享的，这给各编辑器的专属体验留出了空间。

09

在编辑器背后扩展并比较能力

AIDE 提供了一个统一的入口，用来替换模型、调整上下文构建策略。演讲时，更多编辑器的支持还在开发中。公司其他团队也能通过 AIDE 提供各自领域的专用工具，让它们在所有已支持的编辑器里直接可用，不用为每个编辑器单独写集成。

这层边界也方便做 A/B 测试。比如，把公司一半的人路由到一个模型，另一半路由到另一个模型，再比较接受率。Crepezzi 是把它当作这套架构能支持的实验来介绍的，并没有报告结果。模型行为或提示词要改时，团队只需在一个共享服务里改，所有编辑器都能同步用上。

这项工作不止于上面说的编辑流程。Crepezzi 最后提到几个方向：在编辑器里用新方式做检索增强生成（RAG），把类似思路用到大规模多智能体工作流上，以及更多地使用推理模型。无论走哪个方向，打算依托的基础都一样：可替换的组件、共享的基础设施，以及让领域团队贡献专用工具的途径。这样，新能力就有了进入开发环境的通道，不必把每个编辑器集成都推倒重来。

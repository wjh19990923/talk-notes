超越基础 RAG：构建能规划、记忆和协作的知识助手

Jerry Liu 勾勒了一条演进路线：从可靠的文档处理，到智能体式的查询执行，再到协调一致的智能体服务，而“生产就绪”是贯穿其中的约束。

超越基础 RAG：构建能规划、记忆和协作的知识助手

01

一个知识助手要做的不只是检索段落

LlamaIndex 联合创始人兼 CEO Jerry Liu 把知识助手定义为一种接口。它能接下各种工作，从简单的提问到边界模糊的研究任务都可以。它的产出也有很多种，可能是一句简洁的回答，也可能是一份研究报告或一组结构化数据。按这个定义，知识助手不只是文档搜索，还包括能记住对话上下文、能和各类服务交互、甚至可能替用户采取行动的系统。0:14 1:14

把解析、分句、分块、top-k 检索和一次模型回复串起来，就能搭出一条基础的 RAG 流水线。但 Liu 认为，搭起来容易，反而让人看不到它在生产环境中的重要局限。简单的流水线可能处理不好源文档，也难以应对宽泛或复杂的查询。它缺少成熟的服务交互能力，而且每轮对话之间不保留状态。1:14 2:12

他提出的演进路线分三层：先加强数据与检索模块，再做能力更强的单智能体查询流程，最后让多个智能体协作完成任务。这个顺序很关键。源数据不可用，智能体编排再好也补不回来；反过来，光把检索做好，也带不来规划、记忆，更没法让各项专门能力可靠地配合。2:12 3:02

- 知识助手既能回答简单问题，也能处理复杂的研究任务，产出从简短回答到结构化报告都有。 - 简单的 RAG 缺少成熟的查询规划、服务交互和对话记忆。 - 演进路线：先加强数据与检索，再做单智能体查询流程，最后实现多智能体协作。

02

生产质量始于文档结构

Liu 认为，数据处理层的核心组件是解析、分块和索引。这一层要把原始的非结构化或半结构化材料，转换成 LLM 应用真正用得上的形式。底层信息质量不行，检索效果和回答质量也好不到哪里去。3:02 4:11

有些文档的版式没法直接压成一串纯文本，这时解析就格外关键。Liu 举了一份财务报告的例子：PDF 提取做得不好，表格被压塌，数字和周围的文字混在了一起。模型读到这种残缺的内容，就算后面的检索机制再精巧，回答里也可能出现幻觉。4:11

他又用 Caltrain 周末时刻表的例子，把其中的道理讲得更具体。解析器保留了时刻表的空间结构，模型就能把发车时间对应到正确的列上；解析器把结构打乱了，回答就靠不住。实际意义在于：还没加上任何高级索引、检索或智能体能力，光改进解析就能减少幻觉。4:11 5:11

企业文档库里常常嵌着图表、表格和图片，同样会遇到这个问题。Liu 介绍了 LlamaParse 和 Llama Cloud，用来处理这类材料，并在解析、分块和索引上帮团队做决策。他也提到，就算团队不打算用智能体，提升文档质量依然有用。5:11 16:00

- 解析、分块和索引把原始文档转换成 LLM 应用用得上的形式。 - 财务表格一旦被压塌，数字就会和周围文字混在一起，可能导致幻觉。 - 保留时刻表的版式，模型才能把发车时间对应到正确的列。 - 即使没有高级检索或智能体，改进解析也能减少幻觉。

文档结构如何让回答更准 保留时刻表的版式，回答问题时就能找到正确的发车时间。 - Caltrain 时刻表 — 周末时刻表，各列按空间排布。 - 结构化解析 — 保留时刻表信息的空间布局。 - 正确的发车时间 — 返回所问那一列对应的时间。 - Caltrain 时刻表 → 结构化解析（解析时保留版式） - 结构化解析 → 正确的发车时间（把时间对应到列）

03

单个智能体把检索变成有计划、有状态的工作流

数据层靠得住之后，Liu 的下一步是不再只靠一个提示词去综合检索到的段落。在 Agentic RAG 里，模型不会把每个问题都直接丢给同一个向量数据库。它会参与理解请求，决定该调用哪些服务，再规划怎么组合这些服务的输出。6:04 6:57

核心要素有三个：函数调用与工具使用、查询规划和对话记忆。规划可以按顺序执行，也可以按 DAG 执行。对话状态持久保存下来，应用就能回头看用户之前要过什么，而不是把每个请求都当成孤立的事件。6:57

Liu 说，在他见过的智能体推理模式里，函数调用或 React 式的 while 循环最稳定；基于 DAG 或树的规划更复杂，可以作为替代方案。用这些方法，可以跨多份文档做比较，可以通过统一的工具接口把结构化和非结构化数据结合起来，还能让问答更个性化。8:03

能力加上去，就得有所取舍。组件越简单，成本和延迟通常越低；智能体系统越庞大，功能越精细，运维也越复杂。所以怎么设计，要看具体任务是否真的需要更丰富的规划、工具交互或协作，不能默认智能体能力越多越好。6:04 8:03

- Agentic RAG 让 LLM 参与理解查询、规划和选择工具，而不只是综合检索到的段落。 - 核心能力包括函数调用、按顺序或按 DAG 的规划，以及持久化的对话记忆。 - 函数调用或 React 式 while 循环是一种稳定的推理模式；基于 DAG 或树的规划是替代方案。 - 智能体能力越丰富，系统越精细；组件越简单，通常成本和延迟越低。

04

专门的智能体解决了单个通才的局限

单个智能体没法可靠地包揽无限多的职责。Liu 举例说，如果给一个智能体 1,000 个工具，以目前的模型能力，它很可能应付不过来。更好的做法是把职责拆细，交给专家智能体，每个只配一小组工具。8:03 9:07

多智能体系统把这些专家组合起来，完成更大的任务，同时让每个成员只管一块聚焦的范围。互不依赖的工作，可以交给不同智能体并行处理。一个智能体如果只管五到十个工具，也许用一个更弱但更快的模型就够了，不必让一个能力极强的智能体在庞大的工具目录里推理。9:07 10:04

Liu 把这些好处说成是可靠性、延迟和成本上可能的改进，并不保证一定能实现。生产系统仍有几件事要定：智能体该有多大自主权；它们之间的交互是放开不管，还是按明确的规则来；以及用什么样的服务架构，才能让智能体不再只是 notebook 里的函数，而是稳定可靠地运行。10:04 11:00

- 给单个智能体 1,000 个工具，它可能应付不过来；专家智能体各管一块更窄的职责。 - 多个专家智能体可以组合能力，完成更大的任务，并行处理互不依赖的工作。 - 每个智能体只配五到十个工具，也许就能用更弱但更快的模型，降低成本或延迟。 - 生产系统要决定如何约束智能体之间的交互，以及如何把智能体组织成可靠的服务。

05

把智能体当作服务，而不是 notebook 里的函数

Liu 介绍了 Llama Agents。这个方案还处于 alpha 阶段，把每个智能体都做成独立的微服务。目标是让智能体从 notebook 里的函数变成可部署的服务：各自封装逻辑，通过共享接口通信，能同时处理多个请求，还能在不同任务中复用。11:00 12:06

在他提出的架构里，智能体可以用 LlamaIndex 或其他框架来写，再分别部署成独立服务。消息队列在它们之间传递交互，控制平面协调执行。编排有两种方式：按明确定义的服务流程走，或者交给一个 LLM 编排器，根据当前状态分派任务。12:06 13:00

演示特意从一个简单的 RAG 工作流开始：一个智能体改写传入的查询，另一个负责搜索和检索，然后返回回答。还可以再加别的服务，用来做反思、提供其他工具，或者充当通用工具服务。但核心要点是：哪怕是熟悉的检索逻辑，一旦各组件改成通过 API 协议通信、还要应付并发请求，运维起来就完全是另一回事。13:00 13:57

它的局限也不能忽视。Liu 明确说 Llama Agents 还是 alpha 功能，通信协议、与社区其他项目的集成，以及项目路线图，都还在征求反馈。所以这场演讲是把多智能体微服务当作一种仍在发展的生产架构来介绍，并不是说每个知识助手都已经需要完整的多智能体部署，或者都能从中受益。10:04 14:54

- Llama Agents 把智能体做成独立的微服务：各自封装逻辑，通过共享接口通信，支持并发请求。 - 消息队列连接各个智能体服务，控制平面负责协调，可以按明确的流程走，也可以由 LLM 分派任务。 - 演示的 RAG 工作流先改写传入的查询，再搜索和检索，生成回答。 - Llama Agents 还处于 alpha 阶段，通信协议、集成和路线图的细节仍在讨论中。

基于服务的 RAG 请求流程 两个智能体服务先改写查询、再检索信息，然后返回回答。 - 传入查询 — 客户端提交查询。 - 查询改写智能体 — 处理并改写原始查询。 - 检索智能体 — 用改写后的查询搜索和检索。 - 最终回答 — 返回检索智能体的输出。 - 传入查询 → 查询改写智能体（提交查询） - 查询改写智能体 → 检索智能体（传递改写后的查询） - 检索智能体 → 最终回答（输出回答）

要点总结

  • 一个有用的 知识助手 必须处理多样的任务和输出格式；单靠基础的 RAG 无法提供稳健的规划、服务交互或对话记忆。1:14 2:12
  • 在 解析 时保留文档结构，可以防止表格和日程变成误导性的模型输入，在引入更高级的检索之前就减少幻觉。4:11 5:11
  • 智能体式 RAG 用工具使用、查询规划和持久状态扩展了检索，支持横跨多份文档、同时涉及结构化和非结构化数据的工作流。6:57 8:03
  • 专家智能体 可以避免让一个模型面对成百上千个工具，并可能带来并行执行以及使用更便宜、更快模型的机会。9:07 10:04
  • 一个面向生产的多智能体架构，把智能体当作通过消息队列和控制面协调的独立服务，采用显式工作流或由模型主导的委派。11:00 12:06 13:00
  • 拟议的 Llama Agents 架构被明确标注为 alpha 阶段，可靠的编排、服务边界、通信协议和集成仍是活跃的设计挑战。10:04 11:00 14:54

AGENTS.md

Mandatory: enforce these rules before generating any UI component.

1. Use semantic HTML whenever possible.
2. Only reach for ARIA when semantic HTML can't express the behavior.
3. Every interactive element must work by keyboard alone, with visible focus.
4. Elements must be properly labelled and can be read by screen readers.
5. Before returning code, check it against all of the above.

AI 中的无障碍成本

Jemima Abu 把一个小小的 Figma 实现实验与一项更大的工程成本联系起来：智能体可能把时间花在重建浏览器原生行为、照搬不无障碍的惯例，以及做一些本可以通过更好的需求避免的修补上。

01

同一个设计提示词，不同的指导

“Stop wasting tokens on building products that people can't use.” That is Jemima Abu’s opening formulation of the cost of accessibility in AI. A product that an agent generates quickly still has to work for humans, including people with disabilities. Abu, a product engineer at CAIS, starts with a familiar objection to accessibility work: “It takes too long.” Her experiment asks whether leaving it out can itself waste development time.

The input was deliberately simple: implement a design from Figma in the codebase at work. Abu ran the prompt twice, first without an accessibility skill and then with one she had written. How did the runs compare? With the skill, the reported cost fell by 58%, and completion took about a third of the time. These are results from one uncontrolled experiment, not evidence that accessible development always costs less. Abu immediately withdraws that tempting generalization: “We can say that, but we won't say that.”

The table compares the same prompt and model with and without an accessibility skill: duration, turns, token use, and rough cost are all lower in the skill run.

The useful question becomes what the unguided agent spent its effort doing. A timing comparison alone cannot establish the cause of the difference. Examining the implementation choices can still expose avoidable work—and suggest instructions that make the next attempt less likely to repeat it.

02

代码库教会智能体什么才算完成

Abu uses the Netflix show Old Enough to explain why guidance matters. Toddlers undertake their first errands, but their parents have prepared the conditions: familiar trips to the shop, a detailed list, directions and paths to avoid. The analogy is about preparation. “Build this webpage” leaves decisions open; useful instructions narrow the routes an agent can take toward the intended result.

The surrounding code also supplies guidance, even when nobody writes it as a requirement. A developer may stop at “it works for me,” without checking screen-reader use or low-light conditions. If those omissions recur throughout a repository, an agent can reproduce them as local conventions. Accessibility never appears as a constraint, so new generated features continue to omit it.

That creates a compounding problem: each generated implementation becomes another example for subsequent work. An inaccessible codebase supplies inaccessible patterns, and repeated generation adds more of them. Explicit prompts matter, but so does correcting the examples the agent is likely to follow.

03

自定义代码可能重造浏览器已经做好的工作

The concrete failure Abu noticed in the experiment was verbose implementation. Asked for an accordion or modal, an unguided agent can start building from scratch without first considering whether an existing semantic HTML element provides the required functionality. “AI loves to write code.” The cost arrives when that code takes responsibility for behavior a native element could already supply.

What extra work does the custom implementation create? Recreating a semantic element requires implementing its native features and testing the replacement. The comparison is between two starting points: browser-provided behavior that the application can use, and application code that must reproduce that behavior. More generated code brings more behavior to verify. That is a plausible source of wasted effort in this example, rather than a reason to equate code volume with progress.

The prompt should therefore influence the implementation choice before the agent commits to a custom component. Later in the talk, Abu makes the rule explicit: use semantic HTML wherever possible, and reach for ARIA when semantic HTML cannot express the behavior. The decision starts with what the interface must do, then asks how much of that the platform already supports.

04

最后才加无障碍支持会造成第二轮实现

The blueberry muffin analogy gives this timing problem a memorable shape. Blueberries pushed onto a finished plain muffin do not make the same thing as blueberries baked into it. Similarly, adding ARIA labels around a completed website does not by itself make the website accessible. Labels cannot substitute for considering accessibility throughout the business idea, design, implementation and QA.

Waiting changes the work required. Once a product is complete, accessibility testing can reveal decisions that require refactoring or rewriting existing code. Those changes then require regression testing: the team has to check the repaired behavior and check that the changes have not broken other behavior. Earlier requirements can avoid some of that second pass by shaping the original implementation.

There are also costs outside the engineering task:

- Excluded customers. “None of our users rely on assistive technologies” can be a self-fulfilling observation. People who cannot use the product may never become users. Abu compares it to a business without a door: the absence of customers does not establish an absence of demand. - Legal exposure. Abu points to the Americans with Disabilities Act and the possibility of lawsuits and fines. Her discussion is a broad warning about inaccessible public-facing products, rather than a determination of any particular product’s legal obligations.

The cost calculation therefore extends beyond the agent’s bill. It includes custom behavior to implement, repairs to make, regressions to check and people the product prevents from participating. These are the mechanisms behind Abu’s recommendation to begin with accessibility, even though her two-run experiment cannot quantify their general savings.

05

定义需求、修复示例并复用修复

The practical sequence begins with platform-specific requirements. Web, mobile and hardware do not present identical accessibility work, so the team first needs to establish what the product must support. An agent cannot reliably satisfy requirements that the team has left unstated.

Next comes an audit of the existing codebase. Automated accessibility tools—or an agent asked to inspect the code—can help identify issues. The important correction is to fix those issues before generating new features around them. This interrupts the earlier failure mode in which existing defects become examples of acceptable implementation.

A reusable component library or design system makes subsequent corrections cheaper to apply. If several pages use one component, a fix belongs in that shared implementation. If each page contains its own copy, the same repair has to be repeated across files. Abu presents reuse as a useful aid, rather than a prerequisite for every project.

Finally, make an accessibility skill mandatory whenever the agent generates relevant UI or code. Abu mentions Chrome’s Modern Web Guidance skill as one she likes for encouraging newer HTML and CSS features instead of custom JavaScript implementations. A smaller project can use a lightweight set of instructions; the goal is to make the desired choices available during generation without requiring extensive research for every task.

06

一个最低限度的无障碍技能仍然需要人工测试

Abu’s lightweight skill gives the agent concrete criteria to apply:

- Semantic HTML first. Use native elements wherever possible; use ARIA when native semantics cannot express the required behavior. - Keyboard operation. Any interactive element that works with a mouse should also work with a keyboard. - Readable labels. Label elements properly so screen readers can read them. - An agent audit. Before running the code, check the implementation against those instructions.

This is a minimum starting point, not a complete accessibility assessment. An agent’s audit can check whether it followed the stated rules, but no single tool can make the finished website fully accessible. Manual testing remains necessary. The skill improves the instructions and implementation patterns; people still have to evaluate the resulting experience.

The closing criterion returns to the purpose of building anything with AI: solve a problem in a way that people can use. Faster generation is useful when it produces a useful solution. Accessibility requirements help keep that goal present while the agent chooses components, writes code and checks its work.

要点总结

  • One uncontrolled Figma implementation experiment reported 58% lower cost and about a third of the completion time with an accessibility skill; it does not establish a general cost advantage.
  • An agent can copy inaccessible repository conventions. Audit and repair existing patterns before using them as the starting point for new features.
  • Native HTML can avoid custom implementation and testing work. Explicitly ask the agent to consider semantic elements before recreating their behavior.
  • Accessibility skills should cover semantics, keyboard operation, labels and an audit, while retaining manual testing of the finished experience.
  • Beating RL With Reflection: GEPA and Optimize Anything — Develops the complementary question of how repository skills can be learned from agent attempts and reused to reduce repeated discovery and improve later work.

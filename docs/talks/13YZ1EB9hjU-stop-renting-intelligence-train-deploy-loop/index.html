Now I have a thorough understanding of the data and all references. Let me analyze the findings and build the plan.

Key findings from dataset inspection:
• Task: Legal NER / structured extraction — extracting individual defendant names from securities class action complaint excerpts, returning strict JSON {"individual_defendants": [...]}
• Format: CHAT, 3-turn (system → user → assistant), already clean
• Training set: 508 samples, ~316,900 tokens (API), ~294,640 tokens (local estimate)
• Eval set: 507 samples, ~316,400 tokens (API), ~294,475 tokens (local estimate)
• Avg tokens per example: ~580 total, ~550 input (system+user), ~31 output (assistant)

Model selection reasoning: This is a structured extraction task with short outputs. The data is moderate-sized (508 train). The outputs are JSON with named entities. Given:
• The task is relatively straightforward extraction (not complex reasoning)
• Outputs are short (~31 tokens avg)
• 508 training samples is modest
• A smaller model can handle this well and is more cost-efficient

I'll recommend qwen3-8b as the primary base model — it offers a good balance of capability and cost for this structured extraction task. The 4B models might underperform on legal text comprehension, while 32B would be overkill for short JSON extraction.

Evaluation path: Since outputs are structured JSON that can be objectively checked (exact match on extracted names), this is a strong Path C candidate — agent-generated evaluator.

• Model ID: accounts/pyroworks/models/qwen3-8b-ft-lr1e4-lora16-ep5-1777414879

• Consider early stopping at epoch 2-3 for better generalization
• Improve name normalization handling (middle initials, accents, suffixes)
• Consider fuzzy matching evaluation for a more realistic accuracy picture
• The model is ready for production use at the model ID above

阅读全文

别再租用智能：面向专用 AI 的“训练到部署”闭环

Jetashree Ravi 讲解了 Fireworks 如何结合针对工作负载的推理、多个层级的训练控制和检查点部署，帮助团队把开源模型专门化——并用生产反馈持续更新它们。

01

更便宜的模型仍然得把活儿干好

The opening question is familiar to anyone paying for model APIs: how quickly is the bill growing? Jetashree Ravi, who leads part of Fireworks AI’s applied machine learning team, starts with teams considering a move from closed models to open models for cost or performance reasons. The difficult part is keeping the quality users already expect. A cheaper response is useful only if it still completes the task.

Ravi builds the talk around three premises: open models are already production-ready for many workloads, customization can close remaining task-specific quality gaps, and deployed models increasingly need repeated training rather than a single release. These are the premises behind Fireworks’ combined training and serving product. The intended unit of work becomes a continuing sequence of checkpoints: train a model, serve it, learn from use and train it again.

02

速度和质量是两个独立的迁移问题

Fireworks approaches this as a production infrastructure problem. Ravi reports serving about 30 trillion tokens, supporting more than 10,000 companies and processing about 200,000 requests per second. The token total has no clear reporting interval in the recording, so it is best read as a scale claim rather than a comparable throughput measure.

The customer examples distinguish what teams need to improve:

- Cursor: inference speed. Composer 2 was trained and hosted on Fireworks. Ravi attributes a reported 13× inference speedup to the FireAttention engine. - Vercel: serving latency. Fireworks helped fine-tune and host its model, with a reported 40× latency improvement. - Genspark: task quality. Quality was a bottleneck when moving from closed to open models for a product that lets users design systems through prompts. Fireworks cleaned the dataset, helped define evaluator functions and ran reinforcement fine-tuning, reporting a 12% quality improvement.

These are Ravi’s reported customer outcomes, with no comparison baselines, workload specifications or quality-scoring protocol supplied. In particular, the 12% figure does not establish whether the change is relative or measured in percentage points. The useful technical distinction is the work behind each result: serving optimization addresses execution speed, while Genspark’s intervention changes the training data and the evaluator used to guide learning.

03

针对将要承载的流量优化推理技术栈

FireAttention is Fireworks’ inference engine. Ravi explains its role through the path between a model and the GPUs executing it: CUDA kernels implement the GPU work, and Fireworks builds its own kernels as part of the engine. That gives the team a place to optimize execution for a customer’s workload, alongside changes elsewhere in the serving stack.

The input to this optimization is more concrete than “make the model fast.” A customer supplies input-token lengths, output-token lengths, a prompt-cache hit rate and a latency target—Ravi’s shorthand is X, Y and Z. Those properties describe the traffic the system must handle. Fireworks then tunes the stack, including kernels, toward the requested latency and a lower serving price. The optimization is tied to that traffic profile; the talk does not present a universal configuration that delivers the same gain for every workload.

The engine also uses speculative decoding, disaggregation and quantization. The concrete extension described here is training a custom draft model for speculative decoding: customers upload a dataset, much as they would for fine-tuning, and train the draft model on the platform. Ravi links a well-trained draft model to faster main-model inference, better throughput and meeting latency requirements. The recording does not develop the decoding algorithm or quantify the draft model’s contribution separately.

There is a practical ordering to these decisions. Customers generally reach this stage once they are satisfied with model quality. If an open model still gives inadequate answers, faster execution leaves the main migration problem unresolved. That moves the discussion from serving optimization to training.

04

三种接口以不同方式分工

Fireworks offers three ways to train, distinguished by how much of the training process the user wants to specify. Choosing among them means deciding whether to delegate configuration, supply it directly or write the learning procedure.

- Training agent: delegate setup. Through the UI, a user points the agent to an uploaded dataset and describes the goal. The agent can help select a model, clean data and choose hyperparameters. Ravi positions it for product managers and builders who are newer to training. - Managed training: supply the configuration. Through an API or UI, the user chooses a model, uploads data and sets hyperparameters, then starts a job. The service handles execution. Ravi describes this as the option most customers use. - Training API: define the learning procedure. ML engineers can write their own training loop and loss functions when the managed service does not provide the control their task requires.

Managed training also makes the running job inspectable. Its dashboard shows progress across epochs and the training loss, so users can examine how learning proceeds after launch. Teams already using Weights & Biases can supply an API key and export some observability metrics there.

The training ecosystem includes supervised fine-tuning, reinforcement fine-tuning and DPO, but the interfaces do not all support the same methods. The important exception is the training agent: it does not support RFT in this presentation. Its automated dataset cleanup and hyperparameter assistance therefore do not extend to RFT. For that work, Ravi describes direct help with evaluator design, dataset cleaning and hyperparameter selection—the same pieces involved in the Genspark example.

05

让检查点从训练一路走进生产

The continuing train-to-deploy process begins with a trained checkpoint that can be deployed from the same platform. Once it is serving traffic, monitoring exposes token counts, cache hit rates and the behavior of a trained speculator. Those metrics and user feedback can inform another training run, continuing from the existing checkpoint to a new one. Retraining remains a choice; the description does not imply that every observed metric automatically updates the weights.

Compute availability supports both sides of this process. Fireworks partners with cloud and neo-cloud providers to obtain GPUs for training and hosting at scale. Two other capabilities address the handoff between checkpoints: hot loading changes the weights in a live deployment, while numerical fidelity aims to preserve the behavior obtained during training.

Hot loading was initially implemented for Cursor and then offered more broadly. When a new checkpoint is ready, the user can swap the deployed weights for the new weights without downtime, as Ravi describes it. This makes an existing deployment the destination for successive training results. The talk explains the user-visible operation, without detailing the internal weight-loading or request-handling mechanism.

Numerical fidelity addresses a different failure: a model trained on platform A can lose quality when served on platform B because the numerical behavior differs. A deployment can therefore succeed operationally while failing to preserve the trained model’s quality. Fireworks’ stated promise is to align training and inference numerics on its platform so this handoff introduces no numerical differences. No numerical tolerance or validation procedure is given, so the promise should not be read as a demonstrated guarantee across arbitrary external stacks.

06

训练智能体在运行之前先提出计划

The first demonstration starts with two inputs: the location or name of the training dataset inside Fireworks, and a separate evaluation dataset. The user asks the agent to fine-tune a model and choose both the base model and hyperparameters. This delegates the setup decisions while still giving the run distinct data for training and evaluation.

What can the user inspect before the job starts? The agent returns an SFT plan, explains its base-model selection and describes the proposed hyperparameters and high-level training process. The user approves that proposal before execution. The consequential transition is from a requested goal to a concrete training plan, followed by an explicit decision to run it.

After approval, the agent reports progress through the steps. At completion, it summarizes the configuration, base model and hyperparameters, then returns evaluation metrics such as accuracy and F1 score, along with recommended next steps. These are the described outputs of the demonstration; the recording supplies no metric values from which to judge this particular run’s quality gain.

07

托管训练展示了配置和已完成的运行

The managed-training demonstration makes the user responsible for the choices the agent previously proposed. After uploading a dataset and choosing a model, the user selects an evaluation dataset in the evaluator settings. Optional settings allow finer control over hyperparameters. Clicking Create starts the training job.

What remains available to inspect after training? Opening the completed job reveals the dataset, hyperparameters and loss during training. A run can also be cloned with different settings. That connects a recorded configuration to the next experiment: retain the earlier setup, change the desired settings and launch another run rather than reconstructing it from memory.

08

部署仍然需要一份推理服务配置

How does the trained model become a serving deployment? In the Deployment section, the user selects the newly trained custom model, chooses deployment settings and clicks Deploy. Available templates include throughput, fast and minimal. Ravi describes them as configurations optimized for generic workloads using throughput, latency, time to first token and related metrics. The choice matters because training produces the model, while deployment settings determine how it is served.

The ending leaves the most customizable route open. There is no complete training-API demonstration because its setup varies by customer; Ravi points engineers toward cookbooks for custom loops and loss functions. The demonstrated path is narrower and concrete: configure or delegate a training run, inspect its results, select the resulting custom model and deploy it with an appropriate serving configuration. The earlier hot-loading capability then provides a way to bring subsequent checkpoints into the live deployment.

要点总结

  • 质量调优和服务优化解决的是不同的问题：Genspark 的例子为 RFT 修改数据和评估，而 FireAttention 针对特定工作负载的执行做优化。
  • 根据所需的控制程度选择训练接口：把配置委派给智能体、配置一次托管运行，或通过训练 API 定义自定义循环和损失。在本次演示中，智能体不支持 RFT。
  • 热加载解决的是替换权重时的部署停机问题；数值保真解决的是训练与服务之间数值差异导致的质量变化。
  • 这些演示保留了可检查的决策：批准智能体提出的计划、检查已完成任务的设置和损失、带修改地克隆一次运行，以及为部署选择服务配置。
  • Beating RL With Reflection: GEPA and Optimize Anything —— 探讨了一条互补的专门化路线：利用执行轨迹和评估器反馈改进提示词、智能体程序和技能，结尾还讨论了把这些修改与权重训练结合起来。

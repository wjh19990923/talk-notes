拴在一起：我们的智能体就是我们自己

Shu Fang 以亲身经历讲述了前一年完成的一项工作：Two Sigma 如何让远程云端智能体以员工本人的身份运行，再通过逐层传递的来源信息恢复问责，并把网络访问限制在一条由企业控制的搜索路径上。

01

远程智能体迫使我们做出身份决策

Shu Fang opens with two pieces of context: Two Sigma is 25 years old and operates in a regulated industry, and his account reflects his own views rather than an official company endorsement. Even in that setting, he says, every employee gained access to a cloud agent running under the employee’s own identity. The work described began around June 2025 and had been completed during the year before this talk.

Fang calls these agents “tethered,” borrowing the doubles from the film Us. The metaphor captures the design problem: a double is useful while its behavior remains attached to its human, but dangerous when it can run loose without constraints or accountability.

The project started with a usability problem. Local coding agents were powerful but tied to a command line and a particular computer. The goal was to make remote agents reachable from mobile devices, Slack, and browsers—including by employees who would not be comfortable operating entirely inside a CLI. Moving execution into the cloud broadened access, but immediately raised the question: whose identity should the remote agent use?

02

为什么“Shu”加“Shu agent”变成了错误的边界

The conventional answer is to give each agent a separate machine identity associated with its human owner: one identity for Shu, another for Shu’s agent. That looks like clean separation until the two identities must do the same work against the same systems.

The separate identity creates several parallel maintenance problems:

- Permission drift: Every change to the human’s access must be reflected in the agent account. - Duplicate licensing: Software licensed per identity may require a second license. - Shared-data incompatibility: Some systems do not support two identities operating on the same underlying user data, including email and other workspace data. - A new policy boundary: Systems may reject the machine identity outright, while security teams must repeatedly decide what belongs on each side of the human–agent boundary.

Running the agent as the user removes those synchronization problems. The agent receives the capabilities and access the employee already has instead of depending on a parallel account that must continually imitate them. This simplifies authorization, but it also deliberately collapses the identity-level distinction between human and agent. The rest of the architecture must restore that distinction somewhere else.

The necessary infrastructure already existed for ordinary automation. Two Sigma had Kubernetes clusters across regions, with a namespace for each person in every region. Automated jobs, code containers, and research notebooks already needed remote compute that could act as the user instead of being confined to a laptop.

How does a remote agent start with its user’s identity? A trigger asks a controller to create compute in the employee’s namespace. A sidecar in the resulting pod obtains identity material from a separate identity service and mounts it for the working container. The container therefore executes remotely while retaining the employee’s established identity.

How a remote agent starts as its user Existing per-user Kubernetes infrastructure supplies compute placement and a user-specific runtime boundary; a separate identity service lets the workload act with the employee’s identity. - Remote trigger — A request arrives from an interface and asks for compute. - Controller — Creates compute resources for the request. - User namespace — A namespace already exists for each user in each region. - Identity service — Supplies the user identity for the workload. - Identity sidecar — Retrieves and mounts identity material for the pod. - Agent container — Runs remotely with the employee’s capabilities and access. - Remote trigger → Controller (requests compute) - Controller → User namespace (starts pod) - Identity service → Identity sidecar (provides identity) - Identity sidecar → Agent container (mounts identity) - User namespace → Agent container (hosts workload)

03

身份捷径带来两个严重的危险

The first danger is internal attribution. Because the person and agent authenticate as the same actor, ordinary identity logs cannot answer whether a human clicked, typed, or called something directly, or whether an agent initiated the action. That distinction matters when a company needs to audit an action, block agent-specific behavior, or reconstruct what happened.

The second danger is web access. Models contain point-in-time knowledge, so useful agents often need search and fetch tools for current information. Unrestricted internet access, however, creates several risks at once:

- Exfiltration: Sensitive information or intellectual property can leave the company. - Hostile input: Untrusted pages can return prompt injections, malware, or exploit content. - Licensing exposure: The agent may retrieve and use material without appropriate rights.

Fang frames the design as a finance problem: preserve the return from agents acting with full user capabilities while reducing the associated risk. That yields two concrete controls to build—provenance that separates human and agent activity, and a constrained route for web access.

04

一个传播的请求头记录的不只是执行者

Two Sigma’s implementation restores attribution with a header propagated through agent activity much like a distributed trace ID. Agent-controlled HTTP clients, MCP connections, skills, and harness code populate the header and continue carrying it through subsequent calls. Deterministic infrastructure surrounding the model preserves the metadata even though the model’s decisions are nondeterministic.

How does that marker preserve the origin of a multistep result? Consider a remote request that enters through Slack and causes an agent to call several internal services. The authenticated actor remains the employee throughout. At each hop, the agent marker joins the internal span: the first call records that an agent initiated the work, downstream calls inherit the marker, and the final result can be traced back through the chain. The observable change is larger than a label saying “an agent did this”; the record now contains the route that led to the outcome.

A separate “Shu agent” account would identify the initial machine actor, but identity alone would not necessarily preserve the complete causal chain through later systems. Propagated metadata supplies provenance across the sequence while the underlying authorization still belongs to Shu. Actor identity and execution origin become separate, complementary facts.

How agent provenance survives a multi-service call chain The employee identity authorizes each call, while agent metadata propagates through the trace so the initiating path remains reconstructable. - Employee request — The user initiates work through a remote interface. - Agent runtime — Populates the provenance marker while acting as the employee. - First service — Receives the user identity and agent marker. - Downstream service — Carries the marker into an internal span. - Result with provenance — The action chain can be reconstructed back to its origin. - Employee request → Agent runtime (delegates work) - Agent runtime → First service (identity + marker) - First service → Downstream service (propagates marker) - Downstream service → Result with provenance (records causal chain)

05

用一条受控的网络通道取代开放的出站访问

For web access, Fang says the system used Web Grounding for Enterprise, described in the talk as access to Google’s web index from inside the company’s existing VPC and network controls. It mirrored the two capabilities agents needed—search and fetch—without letting the agent contact arbitrary external sites directly.

The tradeoff was freshness. Fang said that, the last time he checked, indexed data was available within roughly 24 hours and more frequently updated sites within roughly six hours. Those figures are explicitly time-bound observations from the described implementation, not permanent service guarantees. For the use cases under discussion, he considered the delay acceptable in exchange for removing direct external egress.

Providing the safer tool is insufficient if the original tools remain available. The harness therefore denied its native web-search and web-fetch tools, removing them from the agent’s usable tool suite. Requests that needed web information were redirected through supported MCP, CLI, client-code, or skill paths into the controlled index. This was a routing rule enforced outside the model, rather than an instruction asking the model to remember the preferred route.

What route remains after the native tools are denied? The agent has one permitted path to web-derived information and no native bypass. Search and fetch remain useful capabilities, but their network path changes from arbitrary internet egress to an indexed service operating inside the controlled boundary.

The controlled index also applied curation and other safety controls that Fang said reduced prompt-injection risk. It did not eliminate that risk: he explicitly allowed that curation could fail. Keeping retrieval internal primarily reduces exposure and gives the enterprise a controlled inspection point; it does not make hostile content inherently trustworthy.

In Fang’s assessment, these controls moved the risk–return position without removing the core capability. The index lagged the open web, but the provenance marker supplied more observability than identity alone, and web access no longer required unrestricted egress. His conclusion was that the risk fell much further than the expected value did.

已经交付了什么——以及仍然存在的边界

By Fang’s account, the prior year’s work produced a framework combining remote user-identity execution, non-CLI interfaces, provenance propagation, and controlled web access. Two Sigma also operated a managed fleet of remote agents for employees while preserving the more general ability for anyone at the firm to deploy an agent into their own namespace under their full identity.

The Q&A sharpens an important security distinction: the provenance header is not authentication. Someone could populate an agent marker themselves, but that would not let them become Shu. The system still verified the originating identity through its existing identity chain, then used the separate header to classify and trace agent involvement. For non-HTTP downstream work, the marker entered through an RPC boundary and became part of the internal span, much like a trace ID.

Fang also expected self-managed models to become attractive for a substantial share of enterprise inference. His reasons were operational: cost, provider deprecations, and performance changes when frontier labs released new models. He presented this as his personal direction of travel, not as a description of the deployed architecture.

Agent session data introduced another privacy boundary. Two Sigma tried to keep a user’s sessions localized rather than exposing them broadly across the firm, because work sessions could contain information privileged to that employee. Within that boundary, usage patterns could improve configuration and personalization based on what the person actually did, rather than only their position in an organizational hierarchy.

Provisioning was deliberately unremarkable: the necessary namespace infrastructure already existed for every user, so an employee could build an agent with existing frameworks and deploy it under their identity. Promotion was a separate decision. An individually useful agent did not become a team-wide or company-wide service merely because it could run; it went through the normal production questions around support, security, and operational ownership, like any other application.

要点总结

  • 为每个用户单独设立一个智能体身份，会带来权限漂移、重复的许可、不兼容的访问模式，以及一道需要无限期维护的边界。
  • 现有的按用户划分的 Kubernetes 命名空间可以以员工身份托管远程智能体，由一个边车从独立的服务获取并挂载身份材料。
  • 认证确定是谁在行动；一个传播下去的智能体标记记录这项工作是否由智能体发起，并在下游的 span 中保留来源。
  • 安全的路由既需要一个经批准的网络来源，也需要禁用原生的搜索和抓取工具，让模型无法绕过受控路径。
  • 在 Fang 描述的实现中，一个受控的索引减少了对外出站和提示词注入的暴露，但牺牲了新鲜度，也无法保证恶意内容永远不会通过整理。
  • 个人智能体可以自助开通，因为基础设施是预先配置好的；更大范围的部署仍需要常规的生产支持和安全审查。
  • CIAM for AI: Authn/Authz for Agents — Michael Grinich, CEO of WorkOS —— 用委托访问、签名的身份链、限定范围的能力和与人关联的可审计性扩展了身份问题的讨论。
  • Privacy First Enterprise AI: Building AI Agents that Never Leave Your Security Boundary —— 探讨一种互补的模式：在现有的身份、云和安全边界之内运行企业智能体。
  • Security Firewall for Agents —— 考察当智能体拥有强大的凭据并可能碰到被注入提示词的内容时，为什么仍需要独立的网络层强制执行。

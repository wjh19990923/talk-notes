打造 Alice 的大脑：一个像人一样学习的 AI 销售代表

Alice 的知识库把卖家的文档、网站和媒体内容变成可检索的上下文，再把销售触达背后的证据展示给用户。

熟悉语言模型上下文窗口、嵌入向量和基本的 Web 应用架构会有帮助；销售术语会在需要时介绍。

01

Alice 需要什么才能写出一封有用的销售邮件？

一封销售邮件，光有收件人的名字还不够，还得说清楚：这家卖家的产品为什么对这个人有用。11x 的 AI 销售开发代表（SDR）Alice 要解决的就是这个问题。Sherwood Callaway 自我介绍是 Alice 的工程负责人，他和 Satwik Singh 一起介绍了这套系统。除了 Alice，11x 还在做语音智能体 Julian。SDR 的工作是寻找潜在客户，在多个渠道上触达他们，再约下会议。真正要看的结果是积极回复和约成的会议。开场的例子是 Alice 写的一封邮件。这就是她每天的产出，也是她的知识库要支撑的东西。

Sherwood 称，Alice 每天发出约 50,000 封邮件，而人类 SDR 每天只发 20–50 封。演讲时，Alice 正在为约 300 家组织跑外联活动。这些只是报告的运营量，不是回复率或约成会议数的测量结果。和人类对比时用的是什么条件，演讲也没有说明。

先分清两方：卖家（seller）是用 Alice 来卖东西的公司，潜在客户（lead）是收到外联邮件的人。卖家提供产品、案例研究等业务背景，Alice 用这些信息为每封邮件做个性化。

这两方的情况，Alice 都得了解：

- 卖家背景：产品、服务、案例研究、痛点、价值主张，以及理想客户画像（ICP）。 - 潜在客户背景：职位、职责、优先事项、以前试过的方案、痛点和所在公司。

这里的知识库工作重点在了解卖家：Alice 要写邮件时，能随时拿到卖家的业务信息。

02

手工整理的资料库的局限

最初，卖家要通过一个叫“库”（library）的功能，主动把背景信息喂给 Alice。他们逐个录入产品和服务，再为每一项填写痛点、解决方案和价值主张。这些描述不只是控制台上的标签，生成邮件时会作为上下文用上。创建外联活动时，用户还要勾选 Alice 能用库里的哪些产品。

这套流程带来两个连在一起的问题。第一，上手要手动录入大量内容，库没填好，用户就跑不了外联活动。第二，勾选产品是个两难：选少了，Alice 面对某个潜在客户时可能找不到相关内容；选多了，上下文窗口里塞满无关材料，邮件反而写得更差。

改动的核心，是把挑选上下文的活从卖家手里交给 Alice。用户不用再逐一描述、勾选每个可能有用的产品，而是让 Alice 把卖家信息拉进知识库，写每封邮件时再检索相关内容。

03

从上传的资源到可搜索的知识

新的上手方式很像培训一个人类 SDR：给他资料，留时间学习，再检查他理解了多少。对 Alice 来说，这就是一个集中存放卖家信息的知识库，生成邮件时随时可以查。营销材料、案例研究、销售通话和新闻稿分三类进入处理流程：文档和图片、网站、音频和视频。

摄取架构把“接收资源”和“让资源可被检索”拆成两件事：

1. 接收上传：客户端上传资源，资源存到 S3 后交给后端。 2. 记录并分派：后端创建数据库记录，按资源类型和选定的解析服务商启动任务。 3. 等待解析：服务商异步处理资源，完成后通过 webhook 通知摄取流程。 4. 保存并建索引：应用把解析结果存进数据库，再把内容向量化后 upsert 到 Pinecone。 5. 开放知识：数据库一更新，UI 随之刷新；智能体也能在 Pinecone 里查到新存入的信息。

最后亮出的完整架构，把上传和处理这套基础设施和智能体的查询连了起来。

团队把这套架构分成五个流水线阶段：解析、分块、存储、检索和可视化。可视化也是产品承诺的一部分：用户要能看到 Alice 学到了什么，光有一个后台进程顺利跑完是不够的。

04

让每一份资源都能以 Markdown 形式使用

解析就是把 PDF、图片、MP4 等资源转成文本，交给下游的语言模型流程使用。多模态模型能直接读取其中一部分输入，但它们有各种限制，这套系统还是离不开解析。Alice 统一输出 Markdown，这样能保留标题、段落和格式这些有意义的区别，不会把所有内容压成一团没有层次的文本。

团队决定不从零写解析器。支持五种资源类型，就得支持一大堆具体的文件格式，每种格式都可能需要专门知识。服务商早已把工程力量集中在这些问题上。把解析外包出去，上线更快，效果也更靠谱，总比让 Alice 团队去精通每一种输入格式强。

初选服务商时只看三条：支持所需的资源类型，输出 Markdown，通过 webhook 返回结果。有两个质量维度，团队一开始有意没做基准测试：

- 准确性：提取结果和原始资源是否一致。 - 完整性：资源里的信息有多少出现在输出里。

团队默认头部服务商在这两方面都差不到哪去。成本优化也往后放了：系统还没上生产，没有使用数据，看不出钱会花在哪里。

05

不同的解析器，同一种下游格式

文档和图片，团队选了 LlamaIndex 旗下的 LlamaParse。在他们评估过的文档解析器里，它支持的文件格式最全。技术支持也是加分项：团队提到，初次评估后没过几个小时，Jerry 和他的团队就进了 Slack 频道。演示把一份 11x 的销售演示文稿 PDF 转成 Markdown，幻灯片内容就成了后续流程能处理的材料。

网站，他们选了 Firecrawl。团队在另一个项目里用过它；备选的 Tavily 在选型时，他们要用的 crawl 端点还在开发中。这是看谁当时能用，不是认定 Tavily 网页解析做得差；Tavily 现在的文档里已经有 crawl 端点。示例抓取了 Brex 首页，又产出一份 Markdown 文档。

音频和视频，他们选了 Cloudglue。决定性的能力是：它不只转录语音，还能从视频画面里提取信息。光看转录稿，可能漏掉画面上呈现的内容。按演讲的说法，YouTube 视频、MP4 文件和其他视频格式都能转成 Markdown。不过今天想复现这个效果，输入方式和所用 API 仍有讲究：Cloudglue 当前的 Describe 文档演示的是从上传的视频里提取视觉信息，而当前的 Extract 指南规定，直接从 YouTube 提取实体时只用语音。演讲没有说明 Alice 当时走的是哪条路处理 YouTube 视频。

06

在强制限定大小之前先保留结构

所有资源都变成 Markdown 之后，分块负责把长文档切成可以做 embedding、可以检索的单元。标题和段落承载的意思不同，所以要保留结构。如果检索时直接拿回一整份十页文档，也很难挑出和某封邮件相关的那部分。

可选的切分边界有 token、句子和 Markdown 标题，也可以让 LLM 决定怎么切。选哪种，先要想清楚检索单元是什么：哪些信息应该放在一起？智能体会查什么？同一种方法能不能同时用在 PDF、幻灯片和视频转出来的文档上？每个分块既要保留足够的意思才有用，又要适合做 embedding 和存储。

Alice 用的是瀑布式切分：先按 Markdown 标题切，不够再按句子切，必要时再按 token 切，直到满足目标 token 数。演讲没有给出目标大小。下面这段 TypeScript 写出了这个控制流程，边界切分器和分词器由具体实现提供：

```typescript type Split = (text: string) => string[];

type ChunkingRules = { maxTokens: number; countTokens: (text: string) => number; byMarkdownHeader: Split; bySentence: Split; byTokenLimit: Split; };

function chunkMarkdown(text: string, rules: ChunkingRules): string[] { const splitters = [ rules.byMarkdownHeader, rules.bySentence, rules.byTokenLimit, ];

function split(part: string, level: number): string[] { if (rules.countTokens(part) <= rules.maxTokens) return [part]; if (level === splitters.length) { throw new Error("Token splitter exceeded the configured limit"); } return splitters[level](part).flatMap(piece => split(piece, level + 1)); }

return rules.byMarkdownHeader(text).flatMap(part => split(part, 1)); } ```

本来就不超长的段落原样保留。超长的段落降一级，按句子切；超长的句子再交给 token 切分器。这样控制大小的手段逐级加码，而不是一上来就把结构边界丢掉。

团队表示，这个方法对他们所有文档类型都管用，切出来的 Markdown 分块也能在 UI 里干净地展示。它还避免了超长分块冲淡嵌入信息的含义。这样一来，分块同时照顾到两类使用者：检索需要聚焦的单元，用户需要读得懂的依据。

07

根据检索操作选择存储方案

检索增强生成不一定要用向量数据库。外部上下文可以来自图数据库、Elasticsearch、文档数据库或关系型数据库、键值存储、文件或 S3。Alice 用向量存储，是因为团队要做的是相似度搜索。

团队选了 Pinecone：老牌的云托管服务商，指南和 SDK 都好上手。用托管服务，又省掉一项基础设施的维护。Pinecone 自带 embedding 模型，团队不用另选 embedding 服务商，也不用自己部署模型，直接用数据库服务附带的能力就行。服务商的支持也不止于搭建阶段，还帮团队研究了其他存储方案，包括图数据库和 graph RAG。

08

让线索引导调研

卖家信息建好索引，接下来的问题是怎么检索。演讲描述了一条演进路线，检索越来越多地交给智能体掌控：

| 方法 | 检索怎样进入生成 | | --- | --- | | 传统 RAG | 检索到的上下文补充进系统提示词。 | | 智能体式 RAG | 智能体在工作流中调用检索工具。 | | 深度研究式 RAG | 智能体规划检索，并决定要不要继续搜。 |

在最后一种方法里，研究可以根据任务还缺什么，往广处扩或往深处挖。检索不一定再是生成之前的一个固定步骤。

Alice 团队用 Letta 搭了研究智能体。工作流从潜在客户信息开始，研究计划据此制定：

1. 制定计划，包含一个或多个检索上下文的步骤。 2. 执行检索工具调用。 3. 汇总结果。 4. 以清晰的问答格式返回答案。

演示给出的结果围绕两个问题组织。关键在于把针对潜在客户的研究和卖家知识连起来：知识库里可以放大量业务背景，智能体从中挑出对当前收件人有用的部分。

09

让 Alice 的知识可以被检查

卖家把代表自家业务的事交给了 Alice，由此会生出很具体的担心：她会不会把产品说错？会不会编造案例或客户评价？会不会声称能解决这家公司根本不管的痛点？团队的办法是让用户看到输出背后的知识。

产品用 UMAP 把 Pinecone 里的向量投影到三维，再渲染成可交互的节点。点一个节点，就能看到对应的文本分块。销售和支持团队用这个视图向客户展示 Alice 知道什么。真正有用的是从看得见的节点直达存储的原文；空间分布本身并不能检验内容对不对。

常规的上手流程从一个上传弹窗开始。用户添加 URL、网页、文档或视频，点击 Learn，这些资源就会出现在知识库 UI 里。另有一个基于 Letta 的智能体，用户可以就这些知识向它提问。

创建外联活动时，知识库内容以问答形式显示在界面左侧。展开一个问题，就能看到消息生成流程用到的检索分块。这样，查看依据就放进了最需要它的环节：用户不必事先手动挑选每个产品，而是直接检查外联内容用了哪些上下文。最终的体验又回到人类 SDR 的类比——先给资料，再看 Alice 怎么用这些资料。

10

先上线，再衡量剩下的问题

这个项目难，难在一堆小决策叠在一起：选技术，支持五花八门的资源类型，再把它们的输出接成一个好用的工作流。Sherwood 说，RAG 比团队预想的难得多。他们对上生产的建议也由此而来：先交付一个满足产品需求的系统，再根据真实使用情况建立基准，然后迭代。

服务商是这个学习过程的一部分，不只是随时可以换掉的接口。团队建议请服务商讲清楚自家产品，比较各种替代方案，帮客户弄明白为什么某种做法更合适。这些交流能让小型产品团队少啃很多专业知识。

剩下的工作，团队明确列进了后续计划：

- 邮件幻觉：追踪并解决外联邮件里没有依据的说法。 - 解析质量：从准确性和完整性两方面评测服务商，这正是初选时推迟的两个维度。 - 混合检索：试着在向量存储之外加一个图数据库。 - 流水线成本：压低整条摄取和检索链路的开销。

建成的知识库改变了卖家提供和查看上下文的方式。下一步要衡量的是：提取的信息是否忠实、完整，Alice 能不能可靠地用好它，以及这份可靠要花多少钱。

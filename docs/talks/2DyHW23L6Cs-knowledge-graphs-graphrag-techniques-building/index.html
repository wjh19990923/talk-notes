知识图谱与 GraphRAG：构建高效生成式 AI 应用的技术

构建一个零售知识图谱，搜索商品描述，通过购买路径实现个性化结果，并用图嵌入为一封季节性营销邮件提供推荐。

你需要能看懂 Python notebook 和基本的数据库查询；文中会介绍工作坊用到的图和向量检索概念。

01

准备 notebook 和图数据库

What needs to be running before a Python notebook can retrieve real retail data from a graph? The workshop starts with two pieces: a blank Neo4j Graph Data Science sandbox and an editable notebook. Zach leads the implementation, with Andreas, Michael Hunger and Tomasz helping participants through the alternating slides and notebook exercises.

1. Create a sandbox by choosing For Data Science, then the blank Graph Data Science option. Keep its generated connection credentials. 2. Open the GenAI Workshop notebook from the workshop repository. In Colab, use File → Save a Copy in Drive so you can edit it. VS Code or a local notebook environment is also suitable. 3. Run the dependency installation cell early; loading the packages takes time.

These are the recorded setup steps. The maintained workshop materials have since moved to AuraDS and reorganized the notebooks, so their current setup differs from the recording.

If you accidentally create the regular blank sandbox, the workshop’s correction is to terminate that instance and create the GDS variant. The regular instance should still work, but the GDS sandbox has more memory for the heavier operations that come later.

02

找到一件商品，个性化它，再推荐与之搭配的东西

Retrieval-augmented generation inserts a data lookup between a user’s request and a language model’s response. That lookup supplies domain context and traceable source material. Here, GraphRAG combines vector search, graph traversal and graph data science: descriptions identify relevant products, purchase relationships personalize them, and graph embeddings provide additional recommendations.

Consider a customer looking for a halter neck top. First, the application needs relevant items from the store’s catalog. Then it needs to choose among those items for this particular customer. Finally, it may suggest pants, a hat or accessories to pair with the top. The workshop uses H&M competition data to build that pipeline and lets the language model turn its results into an email. The same separation between retrieval and composition can serve support agents, internal search and other customer experiences.

The repository also contains workshop slides, although Zach notes that the PDF available during the session differs from his live deck. The finished interface is a small Gradio app accepting customer information, interests and a time of year. OpenAI supplies the language model, LangChain orchestrates the vector stores and generation chain, and Colab hosts the notebook; other model providers could fill the generation role. The implementation proceeds from graph construction to vector search, purchase-based personalization, graph embeddings and nearest neighbors, and finally email generation.

03

构建“客户–商品款式–产品”图

The data model separates a product from its sellable variants. A customer purchases an Article, and that article is a variant of a Product. A jeans style is the product; its colors, patterns or sizes distinguish variants. Articles also connect to departments, though the workshop makes little use of department nodes.

| Entity | Relevant properties | |---|---| | Customer | Unique customer ID | | Article | Color and design pattern | | Product | Name, description, type and garment group | | Department | Department association |

This separation lets purchase behavior remain specific to articles while semantic search operates on product descriptions.

After installing packages and importing the notebook’s libraries, copy your sandbox’s Bolt connection URL into the Neo4j URI setting, supply its password, and retain neo4j as the username. The generation model is GPT-4o. Use your own OpenAI credentials; the key offered in the session was temporary. The notebook also offers a separate environment-file route for configuration. The Graph Data Science client connects with the URI and credentials, and the following debug cell checks that connection.

The preparation notebook supplies five CSVs: department, product, article, customer and transaction. The first four describe entities; transactions supply customer-to-article purchase relationships. The loader creates uniqueness constraints, loads nodes, then loads relationships. An embedding compresses information into a numeric vector whose geometry preserves useful similarities. For text, that similarity concerns meaning. For a graph, it can concern a node’s position or surrounding structure. Cosine similarity and Euclidean distance provide ways to compare vectors; later, the same broad idea will represent purchasing relationships rather than descriptions.

Neo4j has several index families: range indexes for equality and range comparisons, point indexes for spatial data, text indexes, and Lucene-backed full-text indexes. The workshop uses a vector index backed by HNSW, hierarchical navigable small world, for approximate nearest-neighbor search. A query such as halter neck top is embedded into the same space as product text so the index can locate semantically related products. Browser visualization remains available through the sandbox’s Open action, but the notebook first completes indexing.

The implementation has three distinct stages:

1. Select products with detailed descriptions, avoiding incomplete records. 2. Use genai.vector.encodeBatch to request embeddings and store the returned arrays as a text-embedding property on those products. 3. Create a vector index over that property, configure cosine similarity, and wait for the index to become online.

The recording uses OpenAI’s Ada embedding family. Azure OpenAI, Vertex AI and AWS Bedrock are mentioned as alternatives, and embeddings generated outside Neo4j can also be ingested. 1. Find the customer’s latest purchase date. 2. Select the articles purchased on that date. 3. Find other customers who purchased those articles. 4. Follow those customers’ purchases to additional articles. 5. Return candidates the original customer has not already bought.

Zach illustrates the idea with ABK: if they buy similar things, ABK’s other purchases may reveal something Zach would like.

The resulting common purchase score counts matching co-purchase paths. It measures how often a candidate appears through the selected peer group; it is not itself a probability of purchase. Sweaters and T-shirts appear among the ranked candidates. The peer group is derived from shared purchases, rather than assigned as a demographic category: start at a customer, cross to a purchased article, cross back to its other buyers, then follow their other purchases. More matching paths give the candidate more support under this rule.

The traversal can extend farther, and its time scope is adjustable. The demonstration selects the maximum purchase date. Two signals now participate in ranking:

| Signal | Evidence | |---|---| | Search score | Similarity between query and product text vectors | | Purchase score | Candidate popularity through peer-group purchase paths |

The demonstration combines the signals multiplicatively. Its reordered denim results include Rachel HW denim and Jade HW denim skinny; items overlap with the original semantic results, but their positions change.

OPTIONAL MATCH preserves a semantic candidate even when no corresponding peer-group purchase path exists. This matters when a customer has no purchase history, or when their peers have never bought the kind of item being searched for. Preserving the row and preserving a useful ranking are separate concerns: multiplying a raw zero purchase score by a search score produces zero, so vector-only behavior requires the scoring expression or ordering to retain the semantic signal as well. Zach describes that vector-only behavior as the intended fallback. He also offers the reverse ordering—graph traversal followed by vector comparison—as another retrieval strategy.

An external batch recommender could supply candidates instead. The reason to traverse the transactional graph at request time is freshness and flexibility: a new purchase can affect the next query, and changing the time window or traversal depth changes the evidence used without requiring a fixed recommendation list to be rebuilt first.

The audience challenges the multiplication rule because the two scores have different distributions and scales. Zach treats it as a starting heuristic, suggests rank-based ordering as another approach, and recommends evaluating alternatives against labeled recommendation outcomes. A useful production comparison asks which ranking method historically led to successful recommendations, rather than assuming that a plausible formula is calibrated.

The filtering alternatives depend on how much useful behavior the graph contains:

- Graph first: Restrict candidates to the customer’s neighborhood, then apply a semantic threshold. This can be too restrictive if that neighborhood contains no suitable denim products. - Vector first: Retrieve semantically relevant products, then use graph evidence to filter or rerank them. Retaining vector results when the graph has no match helps with sparse histories. - Dense purchase history: A well-connected neighborhood makes graph-first restriction more plausible; sparse history favors optional matching and less aggressive filtering.

An attendee also proposes reciprocal rank fusion. Zach says that specific query-time capability is not available in the demonstrated setup; the GDS normalization functions he mentions do not provide it there. The next stage moves from explicit purchase paths to inferred relationships.

08

This workshop starts with structured data; extracting a knowledge graph from unstructured documents is a separate workflow. Here, Graph Data Science supplies a workspace for projecting selected graph data into an efficient sparse-matrix representation. Its broader algorithm families include pathfinding, centrality, community detection, topological link prediction and directed acyclic graph algorithms. The session narrows that toolkit to node embeddings and similarity.

A visualization of Zachary’s Karate Club introduces the intuition: nearby groups in the graph appear near one another in a two-dimensional embedding. The workshop calls this locality homophily. For retail data, article embeddings encode co-purchase structure, and nearest-neighbor computation uses those representations to infer useful article-to-article connections before a request arrives. Entity resolution and person–location inference are other possible applications.

Embedding nodes does not discard edges. Relationships determine the neighborhoods that place nodes in vector space. The output is a vector for each node, but the evidence used to construct it is relational. Embeddings of head–relationship–tail triples or whole subgraphs are other representations; they are not the one built here.

The notebook constructs the recommendation layer in four steps:

1. Project co-purchases. Follow shared purchases through customers, then create an in-memory graph of articles connected by weighted co-purchase relationships. 2. Compute article embeddings. Run FastRP, fast random projection. Sparse random-matrix operations encode neighborhood structure without requiring a neural network. The workshop uses 128-dimensional graph embeddings, with iteration weights controlling the contributions from successive neighborhoods. 3. Find similar articles. Run gds.knn.write to write scored customer-also-likes relationships between articles with similar embeddings. Sampling reduces the nearest-neighbor computation required. 4. Persist and inspect. Write embeddings back as needed and inspect the algorithm’s convergence and relationship-write statistics.

These new links are derived recommendations, not records of purchases that occurred. The spoken cutoff is tentative; the useful distinction is between raw cosine and the GDS kNN cosine score, which the documentation normalizes to the interval from zero to one.

The notebook also contains a t-SNE visualization that reduces the graph embeddings to two dimensions. Its computation cells are commented out because they take time, while the retained visualization shows clusters of commonly purchased articles. These are co-purchasing clusters, not necessarily shopping baskets: explicitly modeling orders would be needed to distinguish items purchased together in a particular basket.

Retrieval can now follow a short path: customer → purchased article → inferred similar article → product. This recommendation query needs a customer’s history but no search prompt. The expensive similarity work has already produced traversable relationships. A vector index over graph embeddings would be another design, but this demonstration precomputes kNN instead. Supervised or external models could generate the inferred links, and date restrictions could narrow the purchase history used to retrieve them.

How many types of pants are in the catalog? That is an aggregation question, not a request for the nearest descriptions. A final question revisits why graph embeddings are useful when they are computed from the application’s own graph rather than pretrained across internet-scale text or images. Their purpose here is to encode multi-hop topology into an intermediate representation. Similarity operations can reuse that representation instead of repeating an equivalent traversal for every request. In an identity graph, for example, relationships among people, identifiers and transactions might supply features for inferring a shared household. The graph’s topology becomes the input to similarity and link inference, and the resulting vectors can support several downstream operations.

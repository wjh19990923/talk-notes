用 LangChain 和 LangSmith 构建上下文感知的推理应用

一个有用的助手需要的不只是模型：它还需要相关的上下文、合适的执行结构，以及检查、评估和改进整个系统的工具。

01

一个天气问题暴露出缺失的系统

问 ChatGPT 旧金山现在天气怎么样，开场例子里，它回答说自己无法获取实时天气数据。问题很简单，缺的能力却在模型之外。单独一个语言模型，本身不会去拉取最新信息，不会执行自己生成的代码，也记不住之前的对话。放在这场 2023 年的演讲背景下，这个区分很关键：当时 ChatGPT plugins 已经在产品层面加上了浏览网页和执行代码的能力。这里说的局限，指的是模型单靠自己能做什么。

有用的助手，需要语言模型在一个更大的系统里运转。 这个系统要提供相关上下文，让模型能基于上下文推理，还要支撑它给出恰当的回应。看似神奇的产品体验，底下靠的是大量工程。Harrison Chase 给 LangChain 定下的目标，就是填平体验与实现之间的这道鸿沟。

02

告诉模型、展示给它，并给它证据

上下文，就是模型决定怎么做时需要的信息。应用压根没给的信息，模型再强也补不回来。第一种形式是指令提示：告诉模型遇到特定输入或情况时该怎么回应。可以把它想成新员工第一天拿到的员工手册：员工还没碰到具体情况，手册就先写好了该怎么做。Chase 预计，模型越强，这类零样本（zero-shot）指令的效果会越好。

行为难以描述时，可以用 few-shot 示例直接示范。某种语气，示范一下往往比用文字讲清楚更容易。结构化输出是另一个例子：简单的格式可以直接描述，格式越复杂，就越需要几个合格回答的具体示例。指令和示范都在告诉模型该怎么做；描述写起来太费劲时，示例尤其管用。

检索增强生成（RAG）提供的是另一类上下文：回答应当依据的材料。基本流程如下：

1. 接收用户的问题。 2. 用某种检索策略找到相关材料。 3. 把材料和问题一起交给模型。 4. 指示模型根据提供的上下文作答。

这就像开卷考试。行为指令规定怎么答，检索到的文本则是答题时翻看的参考资料。

微调把“从示例中学习”变成了对模型权重的更新。按 Chase 的说法，微调当时还是一种新兴做法，和 few-shot 提示有不少重合，尤其在语气和结构化数据解析上。他拿提示词里的 3 个示例和 1 万个训练样本作对比，是为了说明两者能用来塑造行为的示范数量相差多大；这不是实验结论，也不是推荐的训练集规模。如果某种输出行为反复示范比用文字描述更容易，微调就是另一种教会模型的办法。

03

从生成一个输出到选择一个步骤

模型有了上下文，下一个设计问题是：执行过程该交给模型多少控制权。普通代码会写明要跑哪些步骤。加入一次语言模型调用后，决定输出的一方就变了：应用提供上下文，模型生成回答，应用再把回答返回给用户。这时模型还不负责选择动作。

链（chain）把这一步扩展成一串事先确定的调用。它可以把几次模型调用串起来，也可以先调模型、再调 API、然后再调一次模型。这样，复杂任务就能拆成几个小部件。知识也能在执行途中加进来：前一次模型输出可以决定应用要检索什么，检索结果再交给后一次模型调用。信息是动态变化的，调用顺序却是事先定好的。

路由器（router）给了模型一项新职责：选择下一步走哪条路。各个分支可以在几个方面有所不同：

- 选提示词：数学题用适合数学题的提示词，英文作文用适合写作文的提示词。 - 选模型：根据问题的要求挑模型。Chase 举了当时的例子：长上下文用 Claude，推理用 GPT-4。这只是举例，并不是对具体模型版本的实测对比。 - 选工具：决定调用哪个工具，并生成它的输入。

路由的关键边界在于没有循环。模型选定一个分支，但不会反复回到同一个决策点。

04

循环增加了重复的决策，自主去掉了脚手架

加上循环，就得到通常所说的智能体模式。从概念上看，它就是一个 while 循环：模型选择每一步，并决定要不要继续。跳出循环，任务完成，结果返回给用户；继续，就再转一圈。这时模型既决定输出，也决定接下来的一连串动作。

Chase 把更自主的那种风格和最早的 Auto-GPT 联系在一起，它进一步放开了对动作序列的限制。一种做法是在执行过程中扩充可用工具。他举的例子 Voyager 会随着时间积累可复用、可执行的技能。这些技能扩大了智能体能做的事，但积累技能并不是更新模型权重。

另一种变化出在循环外围的结构上。搭了脚手架的系统可以把规划、执行、验证明确分开：先让模型给出计划，照着执行，再检查结果，检查时可能再调一次模型。脚手架少的智能体则得自己决定什么时候规划、什么时候行动、什么时候验证。这些切换不再是应用里写死的独立流程，而成了模型隐含承担的职责。

架构表把这些区别汇总到了一起：控制权从代码规定输出和顺序，逐步转向模型选择动作，最终连有哪些动作可选也受模型影响。表里的标签区分了带脚手架的状态机和约束更少的智能体风格，尽管“智能体”一词也常用来泛指更宽泛的循环模式。Chase 认为这个领域变化太快，这套分类只是暂时的，并非定论。

05

选择架构，再检查实际运行了什么

把内部执行过程摊开来看，天气助手就成了一个工程问题。演示的调试界面里有一个展开的 AgentExecutor trace、一次 get_weather 工具调用、询问天气的输入、一条完整的回答，以及 Success 状态。执行树和结果同时摆在眼前，助手回答背后那些看不见的工作就能逐一检查了。

第一个挑战是编排：为应用选对结构。模型掌握的控制权并不是越多越好。

| 结构 | 好处 | | --- | --- | | 链 | 能控制步骤顺序 | | 智能体 | 能动态应对意料之外的输入和边界情况 |

选哪种取决于任务。多试几种结构，有助于看清各自的取舍。LangChain 最初的定位，就是让这种原型试验更容易。

LangSmith 解决的是随之而来的可见性问题。应用越复杂，单看最终答案，越难知道它是怎么得出来的。逐一查看工具和模型调用的确切顺序，才能理解并调试执行过程本身。

06

检查数据和完整组装后的提示词

提供正确的上下文，离不开熟悉的数据工程活：加载、转换、传输数据，再看清什么数据流到了哪里。LangChain 提供了加载和转换模块；LangSmith 则帮你看到数据到达模型时长什么样。调试时有两个问题要分开问：向量库返回的文档对不对？应用转换、格式化这些文档之后，模型能不能看清里面的内容？检索对了，呈现得不好，照样会坏事。

提示词工程同样要看实际输入，而不只是模板。一个完整拼好的提示词，可能包含系统指令、few-shot 示例、检索到的上下文、聊天历史和智能体之前的步骤。第一次调用还比较好查。经过几个中间步骤后，提示词取决于应用累积下来的状态，光看最初的输入就很难还原出来。

借助 playground 工作流，可以把某一次调用单独拿出来直接试验：

1. 在执行 trace 里找到这次模型调用。 2. 带着拼好的提示词，在 playground 里打开这次调用。 3. 修改指令，查看得到的回答。 4. 换一家模型提供商，看看另一个模型能不能更好地处理这个输入。

这样，提示词迭代就能从需要排查的那一步直接开始，哪怕这一步藏在多步应用的深处。

07

一个能用的 MVP 仍然需要评估数据

评测面临两样短缺：数据和有用的指标。传统机器学习开发一般从数据集起步，到评测时手里已经有样本。语言模型应用却可以靠零样本能力做出能用的 MVP，根本不用收集应用数据集。起步更容易了，评测环节却留下了空缺。

所以，构建评测数据集成了一项要专门去做的工作。样本可以来自人工标注、挑选出的线上流量，或者用语言模型生成。数据集要随着应用的发展不断积累和迭代，不能指望 MVP 阶段自然留下。

指标之所以难，是因为篇幅长、非结构化的回答，很难套进许多传统的量化指标。Chase 认为定性查看——常被叫做 vibe check（凭感觉检查）——有助于培养对模型行为的直觉。把模型的输入和输出放在一起看，即使给不出客观分数，也能帮你解释发生了什么。

想更系统地评测，Chase 提到了两条路：借助模型做判断，以及收集线上反馈。

- LLM 辅助评测：用语言模型来评判生成的输出。 - 直接反馈：记录用户明确给出的评价，比如点赞或点踩。 - 间接反馈：观察用户的行为，比如点开推荐链接，或者回复里流露出困惑。这些信号可能说明成功或失败，但只能作参考，不能作定论。

长期跟踪反馈，再用常规的 A/B 测试软件比较应用的不同版本，就能在线看到系统在用户那里表现如何。

08

工程工作跨越了专业边界

系统越做越大，构建它需要 AI 工程师、数据工程师、数据科学家和产品经理一起参与。AI 工程师这个新角色该具备哪些技能，目前还没有定论。提供上下文往往需要数据工程的功底，而期望的推理行为常常要靠提示词来表达。产品经理和领域专家尤其擅长把应用该怎么表现说得清清楚楚。让技术和非技术人员顺畅协作，本身就是一个工具层面的挑战——Chase 认为这个问题还没有解决。

新的模型能力还会继续改变设计空间。Chase 以大会上的 GPT-4V 演示为例，说明这种变化。结尾的天气助手示意图回到了最初的问题，给出了更丰富的回答：既提供天气信息，又提议帮忙叫车、点咖啡。这些提议展示的是助手可能提供的帮助，并不代表真的叫了车或下了单。

从示意图里的体验走到一个可靠的应用，仍然要靠工程：把各种能力连起来，提供上下文，控制执行，还要让系统足够透明，才能不断改进。Chase 认为，在模型持续变化的过程中，周边工具的长期使命就是支撑这些工作。

你的智能体讨厌你的 CLI

Ayush Bhardwaj 翻查了自己编码会话里大约 2 万次工具调用。智能体紧接着写下的命令告诉他：它们真正需要响应里的哪一部分，失败会在哪里悄悄消失，他自己的聊天记录 CLI 又该怎么改。

01

只要一个设置，却拉下一整页，再截 40 行

帮 Ayush Bhardwaj 审这场演讲的智能体，只需要文档页上的一个设置。它把整页下载下来，过滤一遍，再只留 40 行。另一个会话里，Codex 想知道有多少依赖存在漏洞。它拉下完整的 JSON 报告，只留最后 40 行，因为报告把汇总数字放在末尾。Cursor 跑了一套测试，其中一个失败，它只留最后 80 行。三次截取都奏效了，但每一次都靠猜答案会出现在哪里。

站在工具作者这边看，调用成功并不代表用起来顺手，智能体为拿到答案多干的活全藏在背后。Sanity 的 MCP server 服务过 2 万多个智能体，处理了大约 300 万次工具调用，没收到过一份 bug 报告。直到 Sanity 加了一个提交反馈的工具，抱怨才陆续出现。Bhardwaj 有另一条渠道听取自己 CLI 用户的声音：如果智能体一遍遍围着某个命令写同样的小程序，它想要什么，记录里早就写明了。

02

失败的测试怎么变成了绿灯

Bhardwaj 从会话记录里提取了大约 2 万次智能体调用，覆盖 14 个 CLI，包括 Git、GitHub CLI、Cargo、curl、npm 和 Docker。四分之一的调用会把输出接给 head、grep、tail、Python、sort 或 wc 这类过滤工具。git show 和 cargo test 的这一比例都是 62%。这个数字也取决于智能体跑在什么环境里。比如 Codex 允许智能体给单次调用设输出上限，它就多了一种办法挡住大段响应，不让它进上下文。

cargo test | head 返回绿灯时，到底是什么成功了？在没开 pipefail 的 Bash 里，管道的退出状态取自最后一条命令。就算 cargo test 失败，head 照样能顺利返回指定的行数。Bhardwaj 举的例子里，绿灯旁边就摆着一条编译错误。绿灯报告的是 head 成功了。好在诊断信息还在，智能体仍然知道构建出了什么事。

第二个例子里，连诊断信息都没了。有用户反馈，一个脚本抛出了 ReferenceError，以错误码退出。tail 却只返回了三行无关紧要的内容。错误根本没送到模型面前，智能体就报告了成功。Bhardwaj 给 CLI 作者的建议是：在输出的最后几行放一段简短的失败摘要，再附上完整日志的路径。这样智能体就算只读末尾，也能认出失败，再去查细节。

03

哪些变通做法该收进 chat-history？

Bhardwaj 写了一个 chat-history CLI，让编码智能体跨工具搜索以前的会话。它附带一个 skill，也就是一份说明文件，告诉智能体什么时候、怎么调用这个 CLI。10 月的一次审计覆盖了这个工具大约 1000 次调用。智能体每打开五次旧会话，就有四次把输出直接接给过滤器或 Python 程序。这样做确实能把无关消息挡在上下文外面，代价是要手写过滤器，还要再猜一次相关消息在哪。

一次性的需求交给 grep 或 head 处理，理由很充分：shell 本来就让调用方自己决定读多少。为了找出值得做成功能的需求，Bhardwaj 把更大的 CLI 样本里的管道按 CLI 子命令和下游工具分组，参数可以不同。按这个口径，83% 的管道属于出现过至少十次的模式。搜索词或行数每次都可能变，智能体要的却一直是同一个操作。

04

消息窗口、更少的字段，再加批量请求

完整打开一个长会话，输出超过一百万字符。只读搜索命中附近的部分，大约 3000 字符。框架可以给两种响应都设一个固定的长度上限。但请求命中附近的消息，等于告诉 CLI 会话里哪一部分值得占用这块空间。两种反复出现的过滤方式，提示了 chat-history 的返回内容该怎么改。

- 用 view 挑消息。 智能体打开会话后，还会再搜索、再切片。于是 view 命令加了几个选项：返回命中附近的消息，只返回命中的消息，或者在长度上限内返回最后几条消息。智能体想找之前做过的某个决定，可以直接请求那段讨论。

- 用紧凑版 search 挑字段。 智能体会拿 Python 处理 JSON 搜索结果，只取需要的几个字段。紧凑搜索每个命中只返回一行，命中结果完全相同，占用的空间只有 JSON 输出的六分之一左右。

套在 inspect 外面的 for 循环又说明了什么？每次调用只汇总一个会话，而大约三分之一的 inspect 调用来自智能体在多个会话上循环。汇总本身正是它们要的操作，循环补上的是缺失的能力：一次问多个会话。Bhardwaj 就把 inspect 改成一次调用可以接收多个会话。

一个做云成本 CLI 的团队发现，智能体在它的 JSON 导出上写 jq 和 Python 管道。团队把过滤功能搬进 CLI，加了紧凑格式，又写了一个 skill 教智能体用这两样。在他们的基准测试里，六道难题智能体原来一道都答不对，改完后六道全对。整个基准的成本降了 41%。这些改动是一起测的，所以结果只能算在整套组合头上。其中一位作者说，读这些日志就像在看可用性测试。

05

为什么 95 次搜索都带上了一个没用的参数

chat-history 的一次改动让深度搜索参数变成了空操作。Bhardwaj 故意把“使用这个参数”的说明留在 skill 里。结果 95 次搜索全都带上了它。后来有两个会话加载了重写过的 skill，里面删掉了这条说明。这两个会话里，没有一次搜索再用这个过时参数，两个智能体第一次读会话时就都用上了新选项。

智能体挑下一条命令时，SKILL.md、帮助文本和错误信息都是接口的一部分。实现改了很久之后，过时的说明还会不断引出过时的调用。智能体学会新参数后，几乎每次搜索都用紧凑输出，几乎每次读会话都用新选项。读会话时走管道的比例从 82% 降到了四分之一左右。

06

重放命令，看看智能体接下来用了什么

一条录下来的命令，可以当重放测试的输入。智能体的下一步动作，可以当一份粗略的参考答案。假设智能体搜了旧会话，然后打开其中一个结果。拿这次搜索分别在新旧两个版本上重放。如果改动影响排序，就追踪智能体实际用到的那个会话在两个结果里排第几。两个版本的搜索都可能顺利完成，有用的结果却悄悄往下掉了。

改格式时，检查新输出里是否还有下游用到的信息。改默认值时，用同样的参数重放，找出哪些调用的行为变了。如果智能体马上换参数重试，这可能是一次失败，值得排查。它能透露智能体的意图，不过智能体改查询也可能另有原因。留几个案例不参与设计，专门用来给修复打分。

07

默认值要小，还要告诉调用方怎么拿更多

如果从头再来，Bhardwaj 会先做范围和数量限制。在他更大范围的审计里，55% 的管道只用 head、tail 这类简单下游工具来截取输出。就算 CLI 已经提供了快捷方式，智能体用不用也说不准。在他观察到的 GitHub CLI 列表命令里，智能体 81% 的时候用了 limit 参数。Cargo 的安静测试模式每个测试只打印一个字符，失败照样会报，可智能体大约十次运行里才用一次，还常常自己接管道。

在 skill 和帮助文本里教会智能体用这个参数，也让输出本身教它下一次怎么调用。默认的一页结果可以告诉调用方：现在看到的是 300 条里的 20 条，用偏移量 20 可以请求下一页。总数让智能体知道自己只看到一部分，偏移量给了它继续往下读需要的参数。

08

工具输出少了 59%，换来了什么

一个智能体模式可以把上面几种默认设置打包在一起。有些编码智能体会设置一个 shell 环境变量，CLI 据此就能认出调用方是谁。在 Bhardwaj 的数据库 CLI 例子里，终端前的人拿到的是排版好的表格。智能体拿到的是纯文本表格，还会注明省略了多少行、怎么取回来。查询特别大时会提前停下，并说明已经停止。错误以 JSON 返回。省略行数和提前停止的提示，让智能体知道手里的结果完整到什么程度。

数据库 CLI 让模型从工具读到的输出少了 59%。放到模型读入的全部内容里，省下的只占输入 token 的 0.5% 左右。成本和运行时间都没有改善，智能体本来也都答对了。云成本基准则在正确率上还有提升空间，难题从答对零道变成答对六道。想知道用户那边到底变了什么，除了 token、成本和耗时，还要数一数轮次和答对的题数。

09

给智能体一个能测试的设计决定

为什么不让智能体一次性设计好自己的 CLI？按 Bhardwaj 的经验，开放式的请求往往产出一个常见的、面向人的工具，再事后补上对智能体的支持。他引用了一项研究：大多数官方 MCP server 只是包了一层现有 API。另一项检查发现，被检查的工具描述里 97% 都有问题。多生成一些说明也有代价。一项研究考察了智能体写的上下文文件：这些文件让任务运行成本变高，任务成功率却没提升，效果还不如人写的文件。

给智能体一份会话记录和一个能跑的测试，任务就变得具体了。工具作者可以先定下来：会话阅读器应该返回命中附近的讨论。智能体就能重放 view 调用，检查返回的窗口里有没有下一步用到的那条消息；如果有用的段落落在窗口外，就尝试修正。

第一步是备份会话记录。Bhardwaj 提到，有一款编码工具会在 30 天后删掉不活跃的会话。对 CLI，在接了管道的命令里搜它的名字，看下游程序留下了什么。对 MCP server，找短时间内连续两次调用同一工具的情况，对比两次的参数。改动的那个参数，可能最清楚地说明了第一次响应还缺什么。Bhardwaj 用 chat-history 在过去的编码会话里找这些调用。

要点总结

  • 把管道按 CLI 子命令和下游工具分组，参数允许不同。反复出现的过滤器说明，用户需要挑消息、删字段。套在 inspect 外面的循环说明，用户需要一次拿到多个会话的汇总。

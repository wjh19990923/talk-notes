打造 pi：为什么编程智能体需要更小的核心、更清晰的上下文和人的判断

Mario Zechner 讲述了对不透明的编程智能体框架的不满，如何促使他打造了 pi——一个极简、可扩展的智能体，以及为什么可持续的 AI 辅助开发取决于有边界的任务、审慎的审查和人的责任归属。

打造 pi：为什么编程智能体需要更小的核心、更清晰的上下文和人的判断

01

真正的问题是失去了对上下文的控制

Mario Zechner 力推 pi，但故事要从他对 Claude Code 的真心喜爱讲起。他说，Claude Code 早期吸引他的地方在于简单、可预期，又和他的工作流合得来。后来功能越堆越多，他碰到的故障也越来越多，更深层的问题随之浮现：决定什么内容进入模型上下文的，是框架，而不是开发者。系统提示词改了、工具定义变了、又插进各种提醒，模型在不同版本间的表现就可能变样，用熟的工作流也会被打乱。 0:15 1:24

在 Zechner 看来，掌控上下文和可靠性分不开。他认为，冷不丁插进来的提醒会让模型犯糊涂；可观测性又有限，很难弄清智能体到底看到了什么、做了什么。他还不满模型选择受限、可扩展性太浅：基于命令的 hook 只是另起一个进程，没法深入、一体地控制框架。他提这些批评，是想说明这个工具为什么不再适合自己，并不是否定开发它的团队。 0:15 1:24 2:25

看过其他替代品后，他的担忧反而更深了。Zechner 提到，Open Code 会按条件裁剪工具输出，在他看来，这会把模型还用得着的信息删掉。他也批评每次编辑后自动注入语言服务器报错的做法：一次较大的改动完成之前，中间状态的代码往往本来就不成立，过早抛出诊断信息只会让模型分心。他想说的是：有些框架功能看着贴心，但如果不管手头的任务就去干预上下文，反而有害。 3:16 4:18

- 系统提示词、工具定义和插入的提醒一变，模型上下文就跟着变，用熟的工作流可能被打乱。 - 可观测性有限、模型选择受限、hook 依赖独立进程，这些都削弱了对框架的实际掌控。 - 裁剪工具输出、每次编辑后注入 LSP 报错，可能删掉有用的上下文，或在活还没干完时就让模型分心。

02

一个极简的框架可能比一个臃肿的框架更能干

Zechner 拿 Terminal Bench 举证：编程智能体不一定需要复杂的框架。他介绍了一种配置：只给模型一个往终端会话发送按键、读取输出的手段，没有专门的文件工具，也没有子智能体。在他引用的 2025 年 12 月排行榜上，这种极简做法的得分常常高过更复杂的框架，其中包括同系列模型自家的原生框架。这个例子支撑的是他一个更克制的结论：编程智能体该怎么设计，目前还没有定论。 4:18 5:13

由此，Zechner 引出两个相互关联的观点：编程智能体还处在实验阶段；开发者需要更好的实验手段。他给出的答案是一个极简、可塑的内核，用户和智能体都能改它。pi 不要求开发者围着固定的产品调整工作方式，而是反过来适应他们手头已有的工作流。 5:13

整个系统分成四个包：一层 AI 抽象，负责对接各家模型提供商、在它们之间交接上下文；一个围绕工具调用循环构建的智能体内核；一套自研的 TUI 框架；以及编程智能体本身。内置工具只有 read、write、edit 和 bash 四个。Zechner 认为，模型在训练中已经懂得编程智能体的基本职责，用不着很长的系统提示词。支持 Skills 会多出一些提示词文字，但总体上仍然以简短为先。 5:13 6:21 7:21

他说，pi 在 10 月的一份 Terminal Bench 排行榜上排到第六，当时它还没有上下文压缩功能。他举这个成绩，是想说明小内核也能打出有竞争力的表现，而不是证明任何极简框架在任何场景下都更强。他更想强调的是：不管选不选 pi，开发者都应该把工具和工作流的控制权拿回自己手里。 10:10

- Terminal Bench 显示，只靠终端输入输出、不用专门的文件工具或子智能体，也能取得有竞争力的成绩。 - pi 由四部分组成：模型提供商抽象层、基于工具调用的智能体内核、自研 TUI 框架和编程智能体。 - 内置工具只有 read、write、edit 和 bash；扩展可以增加能力，又不会让默认内核膨胀。 - pi 还没加入上下文压缩时，就在 10 月的 Terminal Bench 排行榜上排到了第六。

03

可扩展性让智能体本身成为开发循环的一部分

pi 实现自我修改的核心机制刻意做得很直接：随附文档和扩展示例，再把这些材料交给智能体。扩展就是 TypeScript 模块，简单的可能只是磁盘上的一个文件，pi 会把它加载进框架。开发者需要新能力时，智能体可以先读文档，再写扩展，然后按用户的要求反复修改。 6:21 7:21 9:16

扩展 API 覆盖整个框架，而不只是几个孤立的回调。扩展可以定义工具、斜杠命令和快捷键，响应事件，在会话中保存状态，实现自定义的上下文压缩或模型提供商，还能修改 TUI。会话状态可以选择暴露给智能体，也可以留给团队里分析会话的工具使用。正因为扩展能力覆盖得这么广，内核才能保持小巧，不必把所有高级功能都内置进去。 8:16

热重载让这个循环闭合：扩展可以在正在运行的会话里开发，改完立刻重载、立刻验证，不用重启工作流。Zechner 举了几个例子：智能体执行主任务时，另开一路对话和它聊旁支话题；搭一个定制聊天室，把多个 pi 智能体连在一起；甚至做出能跑 NES 游戏或 Doom 的界面。他还提到，子智能体、计划模式、MCP 支持这些能力都可以按需添加，而不是一股脑强加给所有人。 7:21 8:16 9:16

分发和安全也遵循同样的思路。Zechner 倾向于通过 npm 或 GitHub 发布扩展，不想再造一个封闭的扩展市场。pi 默认也不会反复弹出确认提示，因为他认为一遍遍确认 bash 命令算不上一套普适的安全模型；他希望用户按自己的需求搭建合适的管控措施。这种灵活性有明确的代价：自己的场景需要哪些防护，得由用户自己决定。 7:21 8:16 10:10

- pi 自带文档和扩展示例，能按用户的需求自己编写 TypeScript 扩展。 - 扩展可以定义工具和命令、响应事件、持久化会话状态、自定义上下文压缩和模型提供商，还能修改 TUI。 - 热重载让扩展改动在当前会话中立即生效，可以马上查看效果、迭代修改。 - 子智能体、计划模式和 MCP 支持都是可选扩展，通过 npm 或 GitHub 分发。

扩展开发循环 pi 根据需求说明和随附示例编写扩展，再热重载改动，立即评估、迭代。 - 用户需求 — 描述想要的能力。 - 文档与示例 — 教智能体怎么写扩展。 - TypeScript 扩展 — 智能体实现所需能力。 - 热重载 — 在当前会话中应用改动。 - 评估与迭代 — 查看效果，改进实现。 - 用户需求 → TypeScript 扩展 (智能体实现) - 文档与示例 → TypeScript 扩展 (指导实现) - TypeScript 扩展 → 热重载 (重载改动) - 热重载 → 评估与迭代 (查看效果) - 评估与迭代 → TypeScript 扩展 (修改实现)

04

智能体生成的贡献可能压垮开源维护者

Zechner 论点的第二部分，讲的是智能体大规模运行给维护者带来的负担。Peter 把 pi 放进 OpenClaw、当作它的智能体内核之后，Zechner 说，他的开源项目开始被各路 OpenClaw 实例“关照”，涌进大量低质量的 issue 和 pull request。他担心的不只是生成的贡献有错，而是自动化能制造出大量没人要的动静，足以耗尽维护者的时间和精力。 10:10 11:11

为了重新设一道人工关卡，他的做法是：首个 pull request 一律自动关闭，请贡献者先用自己的话写一个简短的 issue。他认可这次交流后，就把贡献者的账号加进仓库里的一个文件，之后的 pull request 就能正常推进。Zechner 说，自动化智能体一般不会回头去看关闭时留下的评论，所以多出的这一步对话，正好能过滤掉他想遏制的那类行为。 11:11

除了这道关卡，他还有别的维护手段：OpenClaw 相关交互带来的 issue 一律降低优先级；把 issue 和 pull request 的文本做 embedding，投到三维空间里找聚类；需要喘口气时，就暂时关闭 issue 跟踪。他的评价有所保留：这些办法在一定程度上管用，但自动化贡献的数量和人的有限精力之间的根本矛盾，仍然没有消除。 11:11

- pi 嵌入 OpenClaw 后，引来了自动化实例，制造出大量没人要的 issue 和 pull request。 - 首个 pull request 自动关闭，直到贡献者提交一份简短的人工 issue 并获得维护者认可。 - 获批账号记录在仓库里，之后的 pull request 可以正常推进。 - 其他手段包括：降低 OpenClaw 相关 issue 的优先级、对 issue 和 pull request 的 embedding 做聚类、暂时关闭 issue 跟踪。

人工把关的贡献流程 首个 pull request 先自动关闭，贡献者写出人工 issue 并获得维护者认可后，后续 pull request 才能放行。 - 首个 pull request — 贡献者提交 pull request。 - 自动关闭 — 评论中请对方写一份简短的人工 issue。 - 人工撰写的 issue — 贡献者用自己的话说明需求。 - 维护者认可 — 维护者批准该 issue。 - 获批账号 — 把账号名记录到仓库中。 - 后续 pull request — 贡献者的下一个 pull request 正常推进。 - 首个 pull request → 自动关闭 (自动关闭) - 自动关闭 → 人工撰写的 issue (要求提交 issue) - 人工撰写的 issue → 维护者认可 (维护者审核) - 维护者认可 → 获批账号 (记录账号) - 获批账号 → 后续 pull request (允许再次提交)

05

没有理解的速度会叠加技术债

Zechner 认为，不加节制地用智能体，会让错误层层叠加，同时推迟所有人真正尝到苦果的那一刻。智能体越多，产出的代码和缺陷就越多，多到团队根本看不过来；另设一个评审智能体或许能抓到一些问题，却解决不了根本的失衡。真正的瓶颈不在于智能体能写多少代码，而在于这些代码带来的行为，人能理解、评估和维护多少。 12:22 13:19

他的解释围绕局部最优展开。模型从互联网上已有的代码中学习，而在他看来，这些代码里有大量平庸甚至设计糟糕的东西；模型做决定时，依据的也只是当前任务能拿到的上下文。代码库一旦大到装不进上下文，智能体就可能加抽象、写重复代码、叠向后兼容层，或者堆防御性的复杂逻辑，却不明白这些选择在整个系统里如何相互影响。详细的规格说明能帮上忙，但前提是它真把关键决策定下来了；剩下的空白，模型仍会用学来的模式去填。 13:19 14:15

在他看来，人有两样智能体没有的东西：一是犯错的速度天然有上限，二是能切身感受到这些错误带来的维护之痛。这种难受会推着人去学习、一起重构，或者采取其他补救措施。Zechner 认为，智能体则会不停地生成改动，却积累不出同样持久的理解；再精巧的记忆系统，也替代不了人的学习。 14:15

团队一旦不再读自己的代码，危险就暴露得最明显。用户碰到故障时，无论是人，还是已经不堪重负的智能体，可能都没有足够的全局上下文去有把握地定位问题。Zechner 提醒，更大的上下文窗口和智能体式搜索都不是万灵药；局部看着合理的补丁，可能在更大范围内引发回归。如果实现代码和用来验证它的测试都出自同一批智能体，信任就会进一步瓦解。 15:24

- 多个智能体产出代码和缺陷的速度，可能远超人的评审速度；评审智能体只能抓到一部分问题。 - 代码库超出可用上下文时，局部决策可能引入不必要的抽象、重复代码和向后兼容层。 - 规格说明不完整，关键决策就落到模型学来的模式上；而人能察觉维护之痛，动手重构。 - 没人读的代码加上智能体写的测试，一旦局部修复引发更大范围的回归，信心就无从谈起。

06

把智能体用于有边界的工作，关键决策留给人

Zechner 提出的替代方案不是弃用编程智能体，而是给它们分配范围明确的工作。好的智能体任务，边界要收得足够紧，让智能体能找到完成任务所需的全部相关信息。把代码库模块化，边界更容易划清；如果再有一个客观的评估函数，能拿清晰的目标来衡量结果，效果会更好。 15:24 16:31

他列出了几类能出成效的用法：有可量化反馈的优化或研究循环、非关键工作、重复性任务，以及根据不完整的用户报告构造复现用例。身边没有人类搭档时，智能体也可以充当讨论问题的对象。但整个流程最后仍要由人来评估：看看智能体产出了什么，留下合理的部分，再审慎地定稿。 16:31

他最后开出的药方是慢下来：想清楚什么值得做，别因为智能体能生成就往上堆功能。团队生成的代码量，应该控制在自己真正审得过来的范围内；用智能体去打磨真正重要的功能；还要分清哪些是用完即弃或无关紧要的工作，哪些代码一旦出错就会造成严重后果。对关键代码，Zechner 坚持每一行都要读；对重要决策，他主张由人亲手写代码，智能体只当助手，不做最后拍板的人。 16:31 17:44

这个过程看似费劲，费劲本身却正是价值所在。亲手把细节理一遍，才能在脑子里建起对系统的认知，也才有机会学到东西；把每个关键选择都交出去，理解和主导权都会一并丢掉。无论是 pi 的架构、开源项目的维护，还是编程实践，反复出现的都是同一个原则：好的自动化应该扩大人的掌控，而不是取代人的判断。 5:13 11:11 16:31 17:44

- 给智能体的任务划好边界，让所有相关上下文都找得到；模块化代码和明确的评估函数能让边界更牢靠。 - 智能体适合用在可量化的研究循环、非关键的重复性工作、复现信息不全的 bug 报告，以及陪人讨论解决问题。 - 评估生成的结果，把改动量控制在人能审完的范围内，关键代码逐行阅读。 - 关键的实现决策由人主导；亲手啃下难缠的细节，才能真正理解系统、持续学习。

为不确定的 AI 智能体构建确定性的基础设施

一个能完成工作流的智能体，仍然需要基础设施来限定它的失败、控制它的行为、协调它的状态，并让恢复成为可能。

熟悉 API 调用、重试、共享状态和基本的分布式系统概念会有帮助；不要求特定的智能体框架。

01

工作流能可靠地运行吗？

当 AI 系统不再只是回答问题，而是开始做出影响生产环境的决策，会有什么变化？模型照样得推理得好，但智能体还要规划、调用工具、协调工作流。Nishant Gupta 介绍自己是 Meta 的软件工程技术负责人。在他看来，新的挑战落在可靠性上：概率性的决策，需要一套控制手段可预期的基础设施。

现代云基础设施建立在几个前提上：请求生命周期短，服务大多是确定性的，执行路径已知，故障范围有边界。自主智能体打破了这些前提。它们会保留状态，长时间运行，动态决定下一步做什么，同样的输入也可能走出不同的工作流。Gupta 把这叫作“巨大的错配”。幻灯片逐项对照了两边：无状态与有状态执行、确定性与概率性行为、请求-响应与多步工作流、毫秒级与长时间运行。

演示只问智能体能不能解决一个问题、用上一个工具、走完一个工作流。生产环境要问的是：它能不能反复做到，能不能从故障中恢复，能不能安全运行，能不能在成本和延迟的约束内交出可接受的结果。工程投入的重心于是从模型往下移，落到编排、监控、安全、评测和恢复上。完成任务只是可靠性要求的起点，远不是终点。

02

一次无效的工具调用如何变成一起算力事故

幻觉只是故障模式之一。递归推理死循环、日志爆满、重试放大、上下文损坏、记忆投毒、成本失控，都可能让一次错误的模型输出演变成全系统的问题。这里要分清：犯错的是模型，但错误是困在局部，还是酿成服务中断，取决于基础设施。

看看 Gupta 举的无效工具调用循环：

1. 智能体向工具发出一个错误的请求。 2. 工具返回错误。 3. 智能体换了个稍有不同的请求，但仍然无效。 4. 循环往复，算力越耗越多，推理深度和 GPU 用量也不断攀升。

Gupta 认为这个循环可能继续升级，让资源消耗呈指数级增长，但他没有给出实测的增长曲线。光凭重复本身，证明不了会以这个速度增长；架构上真正的风险在于，恢复过程变成了不受控的额外工作来源。这样一来，一个小小的 API 错误就可能演变成算力事故。

03

给模型的是提议权，而不是生产权限

模型提议，平台决定。 Gupta 在架构上最有分量的建议是：别让模型直接控制生产系统。这道边界分成四个独立阶段：

1. 模型生成提议。 2. 基础设施校验提议。 3. 策略引擎批准或拒绝。 4. 执行网关落实决定。

校验、审批、执行是三项独立的职责。请求合法不等于获准执行，做出许可决定也不等于动作已经执行。

用 TypeScript 实现时，可以把这道边界写得明明白白。下面的例子里，提议的动作是重启某个指定服务。模型输出以 unknown 类型进入；只有通过校验的提议才能进入策略评估，只有获批的提议才能到达网关。

```typescript type Proposal = { action: "restart_service"; service: string; };

type Decision = | { allowed: true } | { allowed: false; reason: string };

interface PolicyEngine { evaluate(proposal: Proposal): Promise<Decision>; }

interface ExecutionGateway { enforceAndExecute( proposal: Proposal, approval: { allowed: true } ): Promise<void>; }

function validate(input: unknown): Proposal { if (typeof input !== "object" || input === null) { throw new Error("Expected an action proposal"); } const value = input as Record<string, unknown>; if ( value.action !== "restart_service" || typeof value.service !== "string" || value.service.trim() === "" ) { throw new Error("Invalid restart proposal"); } return { action: value.action, service: value.service }; }

async function handleProposal( input: unknown, policy: PolicyEngine, gateway: ExecutionGateway ): Promise<void> { const proposal = validate(input); const decision = await policy.evaluate(proposal); if (!decision.allowed) { throw new Error(decision.reason); } await gateway.enforceAndExecute(proposal, decision); } ```

这个例子在应用代码里体现了职责分离。网关依然负责强制执行获批的操作；生产环境凭证应该放在这道边界后面，而不是交给模型掌控。

04

控制平面需要一份决策历史

容器催生了 Kubernetes，微服务带来了对服务网格的需求。Gupta 提出，智能体同样需要一个智能体控制平面，负责调度、记忆协调、策略执行、评测、监控和工作负载路由。他拿操作系统打比方：由一个公共层统一管理自主工作，而不是让每个智能体各管各的执行。他预计，能把这一层建好的组织会赢得竞争优势。

这一层光记录已完成的操作还不够。传统日志告诉你发生了什么；调试智能体还得还原它的工作流是怎么一步步走到这里的。trace 应当把规划决策、工具调用、记忆查询和状态转换串起来。最终输出也许能暴露出问题，却会掩盖真正的起因——更早的某个决策，或者检索到的某个状态。

追踪可观测的决策序列。 意思是记录埋点采集到的决策和事件，而不是指望能看到模型内部隐藏的推理。调用序列、检索到的记忆、状态变化合在一起，才构成调试自主工作流所需的多个维度。

05

协调记忆、分层设防、分流例外情况

一旦多个智能体共享状态，分布式系统里那些熟悉的故障就会冒出来：读到过期数据、更新互相冲突、上下文漂移、视图不一致。记忆本身又是概率性的、基于检索的，协调起来更难。一个智能体眼里的世界可能和另一个不一样，所以看似是推理出错，实际可能是一致性出了问题。只改进模型，解决不了各方对底层状态认知不一的问题。

安全同样不能只靠某一个组件。Gupta 用纵深防御的思路，叠加了几层互补的控制手段：

- 提示词层面的控制： 引导智能体的行为。 - 工具权限： 限制它能访问哪些操作。 - 策略校验： 检查提议的动作是否被允许。 - 人工审批： 在需要判断的环节引入人工审核。 - 审计系统： 保留记录，便于追责和调查。

每一层应对一类不同的故障，彼此不能替代。

人的参与不一定是迈向完全自主途中的权宜之计。Gupta 预计，成功的系统会一直有人监督，人充当“异常处理程序”：审查模棱两可的情况，处理没见过的场景，提供校准信号。设计目标是把人的注意力用在最能创造价值的地方，而不是一味减少人的参与。

06

推理变成了一个调度问题

智能体的工作负载越来越像集群调度问题。需求成批突发，推理深度难以预测，工作流可能要跑几分钟，而不是几毫秒。资源需求也相差悬殊，于是 GPU 效率、负载放置、弹性容量管理和调度都成了核心问题。推理由此变成一个资源编排问题，而不只是模型服务问题。幻灯片上锯齿状的需求曲线和阶梯状的容量带，把这些问题和资源争用、GPU 上限放到了一起。

07

借鉴分布式系统早已使用的保护手段

应对这些要求，并不需要一门全新的基础设施学科。Gupta 把成熟的可靠性模式对应到了自主工作负载上：

| 成熟模式 | 在智能体基础设施中的作用 | | --- | --- | | 熔断器 | 工具隔离 | | 限流 | 智能体限额 | | 重试 | 受控恢复 | | 资源配额 | 成本治理 | | 可观测性 | 智能体追踪 |

无效工具调用循环正好说明了这些对应关系为什么重要。重试应该是受控恢复的一环，而不是无休止制造工作的通行证。工具隔离和智能体限额把故障圈在局部；配额给资源消耗设上限；trace 让最终的行为说得清楚。实现方式变了，可靠性要达成的目标还是老样子。

08

差异化转移到了基础设施上

Gupta 描述了行业的演进路径：起初拉开差距的是提示词，后来是模型；如今提示词和模型越来越容易获得，差异化正转向基础设施。他预测，胜出的组织不一定有最好的提示词，但一定有最可靠的系统。竞争优势转移到了那些让模型能力变得靠得住的层面。

把智能体当作分布式系统来对待。 模型依然是随机的，基础设施则必须让校验、权限、执行和恢复变得可预期。可观测性必不可少，控制平面会成为协调自主工作的根基。更好的模型拓宽了智能体能尝试的事；更好的系统决定这些尝试能否安全地变成生产操作。

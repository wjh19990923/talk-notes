AI 系统设计：从想法到生产

一个医疗保险理赔审核系统展示了产品需求如何决定数据管道、模型自主程度、人工审核、评测，以及上线前需要完成的工作。

对 LLM、嵌入向量和检索有基本了解会有帮助；不需要医疗或 MongoDB 专业知识。

01

是什么让一个 AI 生成的应用可以安全交付？

如果 AI 编程工具能直接把应用做出来，何必先花时间做设计？如果只是风险不高的实验，你能检查输出，也一眼看得出对不对，那么直接生成代码、跑起来试试，效果往往不错。真正的麻烦在于：别人要依赖这个结果，出了错会有后果。Apoorva Joshi 援引了 Anthropic 和 OpenAI 的演讲，强调一点：大家再看好 AI 编程，也省不掉“定义软件该做什么”这一步。

规格说明必须定义产品需求、系统设计和评测标准。 这三部分给编程助手指明目标，也让协作的人有办法判断结果好坏。代码写得再快，应用的行为不对也没用。

02

跟随一项理赔走过四个设计阶段

设计流程分四个阶段，每个阶段做出的决定都是下一阶段的输入：

1. 产品需求：明确用户、问题和约束条件。 2. 系统设计：选择能满足这些需求的数据、架构和模式。 3. 评测与监控：上线前确认系统能用，上线后确认它一直能用。 4. 优化：发布前持续改进准确率、成本、延迟和可靠性，生产环境暴露出短板后继续改进。

以一个内部医疗保险理赔审核系统为例。医疗审核员要对照临床指南、保险承保政策和患者病史，判断某项治疗、手术或药物是否在承保范围内。公费医疗体系同样要区分哪些服务覆盖、哪些不覆盖，所以这类审核问题并不只存在于商业保险。目标是用 AI 简化医疗审核员的工作。在虚构的 MDB Health 案例里，范围只限内部审核系统，不涉及外部的理赔提交流程。

03

量化问题并划定系统的边界

先从业务问题入手：说清用户是谁、现状如何，并把他们的痛点量化。这时先别指定智能体或多智能体架构。在 Joshi 假设的 MDB Health 案例中，医疗审核员平均审一份理赔要两天，据称是非紧急案件行业标准的四倍、紧急案件标准的十二倍。这些对比只是案例里的假设，并非公认的行业基准。后果很具体：审核拖延会推迟患者就医，时间敏感的治疗尤其如此。这个问题足够聚焦，有可衡量的基线，又没有预设解决方案。

接下来，梳理约束条件，它们决定了系统能做什么、不能做什么。监管要求、数据流动限制、供应商采购审批，都可能直接排除一个原本很诱人的架构。MDB Health 案例中的约束包括：

- 数据边界：患者数据必须留在获批的云环境内。 - 模型可用性：只能使用该云环境中提供的模型。 - 复杂案件：必须由资深医师审核。 - 拒赔：每一条拟拒赔建议都必须经过人工审核。

还没选模型和框架，这些要求就已经划定了自动化的边界。

性能要求也应该在这个早期阶段一并讨论。系统要多快给出响应？每月 LLM 推理预算是多少？要满足什么样的可用性 SLA？响应时限严格或花费有上限的系统，设计空间和那些能接受更慢、更贵处理方式的系统完全不同。

接着，可以从三个相互独立的维度描述 AI 扮演的角色：

| 维度 | MDB Health 的选择 | 原因 | |---|---|---| | 关键型还是补充型 | 补充型 | 没有 AI 也能审核，只是慢。 | | 被动响应还是主动发起 | 被动响应 | 提交理赔后触发处理。 | | 自主程度 | 最多半自主 | 特定案件必须人工审核。 |

人工审核是产品契约的一部分，不是在全自动系统上额外开的可选例外。

选一到两个和业务问题直接挂钩的成功指标。Joshi 提出的目标是：上线后 90 天内，把紧急理赔的平均审核时间从两天缩短到一小时。这个目标具体、可衡量、切题，也有时限；之所以认为能达成，依据是信息收集更快、初步建议出得更快。这是上线目标，不是已经实现的成果。

04

让证据可获取，并保持更新

需求确定后，第一个设计问题是数据访问。应用需要哪些信息？这些信息存在哪里？系统能不能直接处理原始格式？临床指南描述某种病症的合理诊疗方案。MDB Health 的承保政策说明保险公司会为哪些项目买单。患者理赔历史记录了既往病症、做过的手术，以及各自的日期。假设指南和政策是存放在 Confluence 里的 PDF，已处理的理赔记录存在 MongoDB 中。

数据摄取管道必须跟上数据源的更新节奏。否则，模型本身表现再好，也可能拿着过时的依据给出建议。

| 数据源 | 示意性更新频率 | |---|---| | 临床指南 | 每年 | | 内部承保政策 | 每季度 | | 患者理赔历史 | 每处理一笔理赔就更新 |

Joshi 把“一小时完成紧急审核”的目标和每小时刷新一次理赔历史的可能方案联系了起来。具体排期没那么重要，重要的是设计上的依赖关系：数据源多久更新一次、应用对数据新鲜度有多高要求，共同决定了处理管道什么时候运行。

指南和政策文档篇幅很长，要先处理好才能用于检索：把文档切块，为每个块生成 embedding，再提取手术名称、发布日期等元数据。患者病史已经以结构化形式存在 MongoDB 里，处理方式不同：传给 LLM 之前，先去掉个人身份信息。

不同数据源的检索方式也应该区别对待。语义相似度适合找相关段落，但医疗诊断代码和手术代码可能需要精确匹配，光靠向量搜索可能漏掉。

| 数据源 | 检索方式 | |---|---| | 指南与政策 | 先用元数据预过滤再做向量搜索，或用关键词/向量混合搜索 | | 患者理赔历史 | 按系统中的患者姓名或 ID 精确匹配 |

元数据过滤负责缩小候选文档范围；关键词搜索能抓住必须字面匹配的术语和代码。患者病史则不同，要找的是这名患者本人的记录，而不是相似患者的记录。

05

在选择智能体之前先梳理工作流

先从最简单的设计做起，做评测，再根据实际观察到的失败增加复杂度。 默认就上智能体，或者不做这番分析就让编程助手选架构，都可能做出过度设计的系统。把真实的理赔处理流程梳理出来，需要哪些职责就一目了然。

一笔理赔要经过以下步骤：

1. 接收理赔申请和医师的临床记录。 2. 检索相关的临床指南、承保政策和患者理赔历史。 3. 把检索到的证据、理赔信息和生成建议的指令一起交给 LLM。 4. 生成批准或拒赔建议。 5. 复杂案件转给资深医师，拟拒赔案件转给人工医疗审核员。 6. 把最终决定及其理由记录到 MongoDB。

建议和最终决定必须分清。拟拒赔的案件会进入人工审核；模型生成了拒赔建议，不等于拒赔就此定案。

06

选择工作流所需的自主程度

这个工作流可以用到好几种 AI 设计模式。检索增强生成（RAG）在模型预训练知识之外补充外部知识。按 Joshi 的说法，智能体用一个或多个 LLM 加上工具来自主完成任务；智能体系统（agentic systems）范围更广，涵盖各种半自主的设计。讨论“谁来控制执行”时，这些架构上的约定说法很好用。

有两种模式把这条控制边界划得格外清楚：

- 控制流：代码预先定好步骤顺序，LLM 只在其中执行特定任务。 - LLM 路由：模型给传入的请求分类，再分发到合适的下游工作流。它的自主权仅限于这一次路由决策。

路由示意图把这个区别展示得很直观：一个输入进入 LLM 路由器，分流到三个工作流之一，然后结束。

人在回路（human-in-the-loop）是在 LLM 或智能体流程的某个环节加入必需的人工干预。微调解决的是另一类需求：如果问题出在模型行为上，而不是缺数据或编排出错，或者某个领域任务需要更好的表现，就值得考虑微调。改变模型行为，既替代不了检索到正确的政策，也替代不了执行升级规则。

理赔审核选定的基线方案组合了三种模式。RAG 提供指南和承保政策；受控工作流生成建议，并执行预先定义的升级规则；必须人工审核的案件交给人处理。如果“案件是否复杂”还没有清晰的定义，可以再加一次 LLM 路由调用来分类，但 Joshi 让基线保持为控制流，默认不加这次调用。

升级逻辑可以写成一个简短的 Python 函数。它保留模型的建议，同时把人工审核标为待处理；一个复杂案件如果又被建议拒赔，两项审核要求都会触发。

```python from typing import Literal, TypedDict

class ReviewState(TypedDict): recommendation: Literal["approve", "deny"] required_reviews: list[str] status: Literal["pending_human_review", "ready_to_finalize"]

def route_recommendation( recommendation: Literal["approve", "deny"], *, is_complex: bool, ) -> ReviewState: required_reviews: list[str] = [] if is_complex: required_reviews.append("senior_physician") if recommendation == "deny": required_reviews.append("human_medical_reviewer")

return { "recommendation": recommendation, "required_reviews": required_reviews, "status": ( "pending_human_review" if required_reviews else "ready_to_finalize" ), }

pending_claim = route_recommendation("deny", is_complex=True) ```

这个函数只表示路由边界，不代表审核已经完成，也没有写入数据库。外围工作流仍然要先拿到所需的审核结果，才能记录最终决定。

07

设计审核员的交互和反馈

光有架构，还定不下产品体验。要明确输入、输出、放在哪里、由什么触发。这里的输入是理赔申请表，最终输出是批准或拒赔的结论，外加解释。做成独立应用、嵌进现有网站，还是做成 Slack 机器人，交互方式各不相同。在这个例子里，应用很可能放在 MDB Health 主网站内，一提交理赔就开始处理。

遇到必须人工审核的案件，由人审阅系统的评估，并做最终决定。为了方便审核，评估结果应当引用所依据的临床指南和承保政策。这样医疗审核员就能推翻模型的结论，并记下理由。他们还应该能标记出问题：引用不相关、参考文献是编造的，或者真实的政策套错了理赔。有了这些反馈，就能把“建议本身有争议”和“支撑证据出了具体问题”区分开来。

架构和交互都定下来之后，团队才该敲定工具。编程助手偏好的技术栈，可能违反“只能用获批云环境”的要求。剩下要选的包括生成模型、数据处理工具、embedding 模型、向量数据库和编排框架。现有的数据处理能力，也许能省掉一部分本来要自己开发的工作。案例中的组织约束是假设的，所以 Joshi 没有给出具体选型。

08

衡量边界、证据质量和结果

评测在上线前确认系统能用；监控在上线后检查它的表现。两者都要求明确定义什么行为可以接受。LLM 可能生成出乎意料、错误甚至有害的内容，所以护栏必须写明应用接受哪些输入和输出。

拿输入护栏来说，让系统写一首诗的请求和理赔审核毫无关系，应当作为无效请求拒绝。这和拒绝承保是两回事。拿输出护栏来说，没有引用依据的批准或拒赔结论就是无效的。这些检查划定了边界，但通过检查不代表建议本身就是好的。

从多个维度评测，不要把质量压成一个分数：

| 维度 | 指标 | 要回答的问题 | |---|---|---| | 输入护栏 | 输入拒绝率 | 提交内容被输入检查拒掉的频率有多高？ | | 输出护栏 | 引用缺失率 | 模型漏掉引用的频率有多高？ | | 回复质量 | 忠实度 | 结论是否以检索到的证据为依据？ | | 应用效果 | 理赔处理时长 | 审核有没有变快？ | | 系统健康 | 单条建议成本 | 每条建议要花多少钱？ |

输入拒绝过多时，应该排查原因。有没有引用和忠实度要分开检查：回复里可能列了参考文献，结论却并不是基于检索到的指南和政策得出的。处理时长让评测始终扣住最初的业务问题，单条建议成本则反映运营上的约束。衡量系统健康，还可以看 token 用量、token 成本和对话轮数。

09

用审核员的行为发现生产环境中的退步

上线后，继续跟踪离线评测用过的指标，一旦出现退化就能及时发现。生产环境还会暴露出上线前测试给不全的信号：人们实际怎么使用这些建议，系统到底帮他们省了多少工作。

跟踪医疗审核员推翻 AI 结论的频率。一旦超过设定的阈值，就该去排查这些建议及其支撑证据。还要跟踪人工审核一条建议要花多长时间。审核时间长，可能说明回复啰嗦或让人看不明白，哪怕模型的底层判断本身是有用的。这些指标把模型行为和产品要服务的人的实际体验连在了一起。

10

为生产环境优化整个系统

原型准确率高，不等于可以上生产。成本、延迟和可靠性，可能还要经过多轮实现、评测和测试才能达标。要把它们当成和准确率同时满足的要求，而不是产品部署之后才去考虑的事。

提升准确率，重点看进入 LLM 上下文窗口的信息：

- 提示词工程：改进引导模型生成建议的指令。 - 重排序：按相关性给检索结果排序，让最有用的证据出现在上下文里。 - 记忆：MongoDB 中持久化的患者病史已经能跨请求保留信息；再想想还有哪些信息值得跨会话保留。

这几项改动针对的是同一条链路上的不同环节：指令、检索到的证据和保留下来的上下文。

在成本和延迟方面，Joshi 提出两个思路：用语义缓存，借助相似的历史理赔加快处理；用批处理替代逐笔处理理赔。这些都是有待对照系统需求做评测的候选方案，案例里并没有把任何一项当作已落地的改进。基于相似度复用结果时，仍要以该患者适用的证据为准；批处理也必须控制在紧急审核的时间预算之内。

可靠性方面，还得考虑 API 调用失败。Joshi 重点强调的具体做法是结构化输出，同时包含决定和引用。这样下游代码就有了明确的响应约定。不过，要求这些字段存在，并不能保证决定正确，也不能保证引用真的支撑结论，所以忠实度评测依然必不可少。模型拒答和回复不完整的情况也要专门处理，不能当成有效决定。

11

让测量到的失败决定下一次迭代

真正的难点在让 AI 生成代码之前：先想清楚产品必须做成什么、哪些行为是允许的。延迟预算、成本上限、监管要求，每一项都会约束后面的架构。对 MDB Health 来说，这些决定最终落到三件事上：证据检索、受控的建议工作流，以及特定案件中必需的人工审核。

先搭一个能满足这些需求的最简系统，做评测，再根据失败来决定下一步改什么。还不知道问题出在哪就加自主性、加编排，只会让系统更难理解，却证明不了它更好用。所以评测应该放进最初的设计里，而不是等实现完了才做。

最后，Joshi 推荐了一本 Gen AI Cookbook，里面有更多关于检索技术、智能体设计模式、评测和优化的示例。等产品需求和证据需求都理清楚了，接下来要做的就是这些实现层面的练习。

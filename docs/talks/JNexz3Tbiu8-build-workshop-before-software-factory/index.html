Build the Workshop Before the Software Factory

In Armin Ronacher’s Pi sessions, better models ran longer and needed fewer corrections with the same core tools. The workshop is his way of putting that extra capacity toward software people can understand, maintain, and make work together.

01

What better models can do with the same tools

A CNC machine or a 3D printer can change what an artist is willing to attempt. Armin Ronacher opens with that picture of a workshop. Better tools make harder work feasible, and the person using them still decides what’s worth making and whether the result holds together. Coding agents offer engineers the same chance to raise their ambitions.

Earendil’s Pi coding agent still offered the same core tools it had the previous December, yet Ronacher could do considerably more with it. He had relied on the Pi Auto Research plugin to help an agent keep working toward a goal such as improving performance. With a stronger model, he found the agent could pursue that kind of goal without the plugin. The useful change came from what the model could do with the harness, the software that gives the model its tools and runs its calls.

02

Fewer corrections and longer runs

Ronacher filtered his own Pi sessions to those using the default toolset. The total number of corrections he made fell across successive models, and he described a similar trend in how often he stopped a run. Filtering kept the toolset comparable. The figures describe how his everyday use of Pi changed, with tasks that could vary across models.

How long did the longer tasks run? Ronacher used the 90th percentile, the duration at or below which about nine in ten runs fell. For tasks he gave a single earlier Opus model in December, that point was about two and a half minutes. With later models it reached 14 minutes or more. A two-minute run is easy to watch at the terminal. A run that keeps working for a quarter of an hour changes when it makes sense to check in. Runtime comparison, 3:13

The newer models also favored Bash over the other tools even though Pi’s configuration stayed the same. Code mode was starting to show up in the tool-use comparison as well. Ronacher left some models out of that comparison because he had too few sessions for them.

03

Starting 141 projects and returning to 10–15

Human attention still paces the work. A new model makes it easy to try building a 3D game or automating a task. Every project someone keeps brings decisions and upkeep with it. The extra activity also lands on shared infrastructure. Ronacher points to more repositories and commits on GitHub and describes operators of long-established websites facing volumes of agent requests they were unprepared for.

Ronacher’s prompt count stayed in roughly the same band over the year, around 120 to 190 per day depending on the month. Agent activity on his behalf went from less than the length of his workday to several times that length, with November still in progress when he showed the chart. Roughly the same number of prompts was setting much more work in motion.

How many projects did that activity leave him tending regularly? Ronacher created 141 Git repositories over the year. The number he worked on regularly stayed around 10 to 15. He counted projects he returned to and committed to on more than five days. The rising cumulative count captures how often he got an idea started. The flatter count tracks where he kept spending attention. In an informal survey, friends described a similar difficulty keeping up with projects. Repository comparison, 6:47

One friend tried automating maintenance on an open source project. Incoming issues fed an agent that could review work, commit changes, and send the result back. The friend eventually turned it off. He cared less about the project by then and wanted to spend his tokens elsewhere. The automation could handle an issue. Keeping it running still depended on whether the project mattered enough to spend resources on it.

Armin Ronacher’s tally of Git repositories he’d started climbed from 24 in March to 141 in October. Over the same period, the monthly count of projects he worked on for at least five days ranged from 6 to 13.

04

Push back while the approach can still change

An agent can satisfy each request and leave behind a system whose features fit together poorly. In Ronacher’s reinforcement learning analogy, completing an immediate goal gives a clear signal of success. Add enough individually successful features and you can end up with the car from The Simpsons. Someone who understands the system has to spot when the next feature adds complexity that will make later changes harder.

On a project they work on together, Ronacher’s son can now send him pull requests using the same prompting system. Ronacher sees a clear difference in the resulting contributions and puts it down to engineering experience. That experience matters when a team has to make a consequential decision. Asking the agent can produce an answer quickly. Evaluating it takes enough understanding of the software and the problem to know when to push back. Sometimes that means slowing the work to a pace the team can follow.

As his commit volume rose, Ronacher looked through his sessions for a point where he could review the approach before the run finished. He now prompts the agent to produce a short executive summary on a typeset HTML page just before verification, typically about 70% of the way through the run. The agent continues with verification while he reads its account of the work. He often uses that account in place of reading the code, and the timing gives him a chance to question an implementation decision while the run is still in flight.

05

Independent implementations need shared formats

Ronacher likes being able to write more code in-house and carry fewer dependencies. The trouble starts when independently written tools have to read each other’s files. He points to a crafted tar archive that different tar implementations interpret differently. The input stays the same, yet the result depends on which reader opens it.

Agents make it easier to write a new reader or writer. Interoperability still depends on people agreeing on what a file may contain and what those contents mean. Open formats, specifications, and protocols give independent implementations a common target. Imagine every team building its own Photoshop-like editor. Each editor can work well on its own files while diverging enough that two teams can no longer exchange a document.

The same choice comes up when changing an open source project. Ronacher has seen how easy it has become to fork a project and have an agent make a local change. Taking the change upstream means working it out with other maintainers. When the change affects how people use a shared tool, that conversation can keep the improvement available to everyone who depends on it.

Different tar implementations read the same archive differently. As agents make custom tools easier to build, Ronacher argues that keeping them compatible still depends on people agreeing on what shared formats mean.

06

Better verification, lower memory use, and safer code

- Verification. Ronacher sees more people attempting verified software and considers it a promising route to more stable systems. Establishing that software satisfies the properties engineers care about is still difficult, and the tooling leaves substantial work to do.

- Native applications. After years of watching desktop software consume RAM for things he barely valued, Ronacher welcomes developers trying native implementations for apps they might once have shipped in an Electron wrapper. Speed and memory use become goals worth spending the new engineering capacity on.

- Memory safety. Agents lower the cost of trying a language like Rust for developers who might have passed it over. Ronacher sees that as timely as capable models get better at finding security issues. The agent makes an existing engineering option easier to choose.

07

Durable agents can stop and resume

When a two-minute run ends early, someone can restart the agent and tell it to continue. An overnight batch of thousands of issues makes manual restarts impractical. Ronacher wants an agent that can restore itself and create workflows that can also stop, suspend, and resume. Both the agent run and the work it orchestrates need enough recoverable state to pick up after an interruption.

Suspension can also make cheaper inference scheduling practical. In Ronacher’s example, flex scheduling offers a discount on raw token prices and may leave the run waiting several minutes for tokens. If the agent and its sandbox stay active through that wait, other resources keep costing money. A harness that can suspend both and resume them when work can proceed could capture the inference discount while reducing idle resource use. Flex scheduling example, 16:21

08

Code mode puts repeated decisions inside the workflow

Bash remains a general-purpose tool for Pi. Workflows that combine subagents, tools, and specialized decision models give the harness another job. Ronacher credits Cloudflare with the idea of giving the agent JavaScript alongside Bash. The agent writes a program that calls tools from JavaScript, with loops and branches running inside the program. That lets the harness run large batches of calls while keeping thousands of tool definitions and repeated tool-call exchanges out of the language model’s context. Ronacher said Pi and Codex could already coordinate large groups of tool calls this way.

A classifier gives the program a cheap, fast way to answer a narrow question. That makes some decisions practical to repeat at a scale where asking the coding model each time would be too slow or expensive. Ronacher also points to a separate benefit of using the classifier for those decisions. It avoids the penalty he associates with running without an active cache.

Take a queue of 3,000 incoming customer support requests. Which work happens once, and which decisions repeat for every request? In Ronacher’s proposed workflow, the coding agent writes the routing program once. For each request, the program calls the classifier at its decision point and uses the result to choose a branch. It can hand the request to an agent for work or ask the customer for more information. Ronacher estimates that making those decisions through the coding agent could take hours. Putting them inside the program moves that repeated work to the classifier. Support queue example, 18:48

The ability to build more leaves engineers with more choices about what to build at all. Ronacher closes by asking what they can make more ambitious and more enjoyable when they spend that capacity selectively.

Codemode lets an agent use JavaScript to call the harness’s own tools in loops or in parallel. The harness runs the workflow without routing each call through the model’s context and keeps state in the transcript.

Routing 3,000 support requests in code mode Where does the coding agent hand off the repeated work? It writes the routing program once. The classifier supplies each routing decision, and the program acts on it by following one of two branches. - Coding agent — Writes the workflow on demand. - 3,000 incoming requests — Customer support requests enter the workflow. - JavaScript workflow — Runs the routing logic for each request. - Classifier — Evaluates the routing condition. - Branch in workflow — Uses the classifier’s decision to route the request. - Send to an agent — An agent takes up the request. - Ask the customer — Request more information from the customer. - Coding agent → JavaScript workflow (Creates) - 3,000 incoming requests → JavaScript workflow (Supplies requests) - JavaScript workflow → Classifier (Calls with a routing question) - Classifier → Branch in workflow (Returns a decision) - Branch in workflow → Send to an agent (Route to agent) - Branch in workflow → Ask the customer (Need more feedback)

要点总结

  • Agent runtime and regular maintenance measure different things. The first grew sharply in Ronacher’s sessions while the second stayed near 10 to 15 projects.
  • A pre-verification summary makes room to examine how a feature fits the system while the agent is still working.
  • The harness can save resources in two places. Suspension reduces what stays active during an inference wait, and code mode lets a classifier handle repeated routing decisions inside a program.

构建并部署 AI 驱动的应用

跟随视频分析、一个书架应用、一条“从书到多媒体”的流水线和本地 Gemma 智能体，看看那些跑通的结果、落空的假设和现场修复。

熟悉 Python、API 请求、JSON 模式和基本的 Web 应用概念，有助于理解实现示例。

01

从科学计算 Python 到模型基础设施

公司敢不敢把关键业务交给开源软件？2009–2010 年前后 Paige Bailey 开始做机器学习时，这个问题还没有定论。她给 NumPy、SciPy、Matplotlib 和 scikit-learn 贡献过代码，把科学计算和工程实践连了起来。她的背景横跨地球物理、应用数学、计算机科学和碳酸盐岩地质学。她曾在 Chevron 用 Cloudera 和 Spark 做速度建模、钻井优化和大规模计算。

她在地球科学领域就接触了 CUDA，那时还没开始给 TensorFlow 贡献代码。Bailey 回忆，当时有一项工作是把 CPU、GPU 和 TPU 的执行路径拆开，涵盖单节点和分布式计算。她记得最初公开发布的版本只支持 CPU，但 TensorFlow 发布公告里已经提到了桌面 GPU 训练，两者对不上。开源工作把她带进了 Google。之后她在 GitHub 待过一段时间，做 VS Code，也参与早期 Copilot 的用户体验测试。再后来她回到 Google，加入 PaLM 2、Gemini 和 Gemma 的初创团队。

公开贡献有两重作用：工程师可以借此判断一个团队值不值得加入，别人也能借此发现这位工程师的工作。现场一位观众的项目在 GitHub 上有 700 颗星，就是后一种作用的小例子。

02

哪些约束能熬过下一代模型？

接下来是一个更难的产品问题：模型本身吸收了某个应用赖以存在的能力，这个应用会怎样？Bailey 举例说，早期上下文窗口只有 8,000 和 16,000 token，开发者才一窝蜂地涌向向量数据库。上下文变长后，这个限制就变了。同样，多语言支持更广了，对特定语言微调的需求也少了一些。她预测模型可能会吸收更多智能体框架的行为，提到现在正转向基于 Markdown 的技能（skills），还设想由活动监听器自动生成这些技能。这些是她对平台走向的预期，并不意味着检索、框架或 MCP 已经不重要了。

一位观众拿生物信息学提出异议：专业领域的工作也许始终排不进通用模型厂商的优先级。Bailey 用 MedLM 和 Med-PaLM 回应。她说，一些过去需要医疗微调模型的用户，现在改用 Gemini 加检索或定制提示词；她认为原因是医疗训练材料进入了通用模型。观众接着问到可复现性。Bailey 承认模型行为有随机性，然后把话题拉回到持久的应用层：一个有明确主张、直接和客户一起打磨出来的用例，在底层模型变强之后依然有价值。

03

一个由输入、输出和应用界面组成的工具箱

工作坊随后回顾了一系列演示，起初围绕 AI Studio 和 Antigravity 展开。一个电脑操作（computer-use）智能体刚运行了一会儿，Bailey 就断开了屏幕共享，以免暴露私人内容。这套模型组合覆盖了几类不同的工作：

- 对话与推理： Gemini 3.1 Flash Live、Gemini 3.1 Pro 和 Gemini 3.1 Flash-Lite。据 Bailey 介绍，Augment Code 看中 Pro 在性能和成本之间的平衡，把它选作智能体基础设施的默认模型。 - 图像与检索： Nano Banana 2 能生成和编辑图像，还具备搜索相关能力。Embeddings 2.0 把视频、音频、图像、代码和文本放进同一个嵌入空间：搜一下“羊驼”，照片、视频、毛绒玩具和羊驼叫声都能找出来。 - 生成式媒体与世界： Lyria 3 生成音乐，Genie 3 支持交互式世界生成，Veo 3.1 Lite 生成视频。 - 应用与开放模型： AI Studio 的全栈运行时新增了数据库、OAuth 和自定义 API key；Gemma 4 以 Apache 2.0 许可发布。

要分清的是：能接收多种模态，和能输出多种模态，是两回事。Bailey 介绍，Gemini 系列除了支持多模态输入，还能输出文本、代码、图像、图文交错内容和音频 token。接下来的演示会为每项任务挑选具体的模型和工具。

04

把一段恐龙视频变成一张有依据的表格

AI Studio 把模型试验场（playground）和 Build 分开，Build 是用来生成应用的界面。在 playground 里，Bailey 选了 Gemini 3.1 Flash-Lite Preview，看中的是速度快，用个人账号也花不了多少钱。它的发布定价是每百万输入 token 0.25 美元，输出另计，每百万 token 1.50 美元。这个小模型保留了视频和音频理解能力，代价是比 Pro 弱一些。

输入是一段很长的 YouTube 视频，主角是食肉牛龙（Carnotaurus）。AI Studio 也接受 Drive 文件、PDF、本地上传、麦克风录音和摄像头输入，不过这次演示用的是视频 URL：

1. 附上 YouTube 视频，选取 0 到 300 秒的区间。 2. 查看输入估算。Bailey 说大约每秒采样一帧，这一段约合 30,900 个输入 token。 3. 开启 Google Search grounding。 4. 要求生成一张表格，列出时间戳、恐龙种类，再给每种恐龙配一条趣闻。

模型拿到的是视频画面帧，不只是标题或元数据。所以这个请求本质上是视觉分析任务，再借助搜索补充信息。

回答认出了食肉牛龙，解释了它的名字意为“食肉的公牛”，还提到了三角龙，并指出无齿翼龙不是恐龙，而是会飞的爬行动物。提示词调通后，点 Get Code 就能把所选模型、视频 URL、时间偏移和提示词导出成 TypeScript、Python 等语言的代码，完整保留 playground 里得出这个结果的配置。旁边的工具设置里还有结构化输出、代码执行、自定义函数调用和 URL 上下文，供开发应用时使用。

05

边界框 vs 验证循环

下一个实验用了对比模式，更能说明问题。Bailey 把同一张乐高图片分别交给 Flash-Lite 和 Gemini 3 Flash Preview，两边都开启代码执行，要求用 Python 给绿色积木画出边界框，再显示标注后的图片。这个工具提供一个预装了数据科学库的沙箱，模型可以在里面写代码、跑代码，处理传入的图片。Flash 还在忙，Flash-Lite 已经交回了边界框。类似的请求还可以要分割掩码、计数、朝向，或者在视频里按时间戳统计 Labubu 之类物体的数量。

原来 Flash 多花的工夫都用在了验证上：它先给绿色区域做一个掩码，再拿自己给出的坐标去对照检查。

| 运行 | 观察到的行为 | 本次演示中的取舍 | |---|---|---| | Flash-Lite | 很快给出标注好的边界框 | 展示出的验证工作较少 | | Flash Preview | 用绿色区域掩码核对边界框 | 耗时、工具调用和成本都更多 |

Bailey 说，做了验证的那次运行，花费也不过几美分的量级。这个对比说明，选模型时还得考虑工具使用策略：哪怕要的输出一样，额外的检查也要消耗资源。她建议，原先用 Gemini 2.0 Flash 或 Gemini 2.5 Flash 跑的工作负载，可以试试 Flash-Lite。

06

规定一个与账户关联的书架目录

到了 AI Studio Build，任务从单次推理扩展成一个完整应用。Shelf Scan 要让用户用 Google 账号登录、上传一张书架照片，并保存一个和该账号绑定的书库。模型得先读出照片里看得到的书脊，再用 Google Search grounding 补全每本书的书名、作者、简介和类型。识别、信息补全、身份验证和存储，全都包含在这个请求里。

Bailey 从 Pro Preview 换成默认的构建模型，想少等一会儿，然后开始生成。类 IDE 的界面会展示规划和文件创建过程。PDF、规格说明和 Drive 文件可以提供额外上下文；自定义密钥可以存放 Gemini、Supabase 或 n8n 的 key。版本历史方便反复迭代；OAuth 集成和公开或私有 GitHub 仓库的同步，则把生成的应用接入更完整的开发流程。应用在后台继续构建，工作坊转而演示其他模态。

07

在共享屏幕时切换语言

Gemini Live 在屏幕或摄像头输入的基础上加入了持续对话。Bailey 从语音识别、模型理解和语音合成三个环节介绍了它，然后共享了乐高的搜索页面。Gemini 描述了图片搜索结果，以及 Freepik 那张较大的插图预览。语音对话和当前共享的画面就这样联系在了一起。

一位观众提了个语言要求，起初没听明白，后来才确认是西班牙语。Bailey 先改了系统指令，得到了西班牙语回答。观众又要求说卡斯蒂利亚西班牙语，她便删掉那些指令，直接在对话里提出要这种方言。接下来的回答表明，语言和语气既可以靠配置控制，也可以在普通的一轮对话里调整。Get Code 会保留所选的模型、设置和工具配置。

摄像头演示把感知和生成放进了同一个请求：数出举起了几根手指，再为这个人写一首诗。Gemini 认出是两根手指，把手势理解为“剪刀手”和平手势，并写了一首短诗。可见屏幕共享和摄像头画面能直接为对话式应用提供上下文，用户不必事事都用文字描述。

08

探索一个以像素生成的世界

给 Shelf Scan 启用 Firebase 后，Bailey 打开了 Project Genie。这个应用组合多个模型来打造交互体验，和 Genie 3 世界模型本身不是一回事。Bailey 讲解时说它组合了 Nano Banana、Veo 和 Gemini，发布说明里列的则是 Genie 3、Nano Banana Pro 和 Gemini。它根据玩家的操作生成画面帧，并不是导出一个带常规游戏资产和物理引擎的 Unity 或 Unreal 场景。

示例包括：一辆漫游车穿越火山地貌，一艘水上摩托撞上一盏灯，还有一段由静态图片生成的飓风场景。Bailey 说，在短暂的探索过程中，玩家如果折返，那盏被撞倒的灯还倒在原地。现场演示时，她设定的场景是阳光明媚的摄政运河（Regent’s Canal），水里有海豚，每条船上都挂着海盗旗。玩家角色是一只亮闪闪的粉色松鼠，长着紫色的脚，戴着海盗帽。生成交互世界之前，系统会先画一张第一帧草图，供用户确认。演示用的公开原型把每次探索限制在 60 秒；Bailey 提到，部分地区的 Ultra 用户可以使用。

Shelf Scan 在后台生成 Firestore 规则时，松鼠世界已经可以玩了。用键盘控制移动和视角，按空格键松鼠就会跳。要求的船、旗子和海豚都出现了，但松鼠在水面上走，海豚一动不动。Bailey 认为，要是写明运河水很深，也许会好一些。这些失误暴露出“看起来合理的生成动作”和“明确的物理约束”之间的差距。探索结束后会生成一段可下载的视频。Bailey 指出，这种基于像素的表示方式，和她所说的 World Labs 更偏重资产的做法不同。

09

识别成功在持久化之前

回到 Shelf Scan，Bailey 查看了生成的配置、Firestore 规则和提示词代码，授予摄像头权限，再用 Google 账号登录。她上传了一张 WebP 格式的食谱书架照片。应用开始搜索，看上去识别出了七本左右的书，但书库并没有按预期填充。她换成同一张图的截图重试，起初是想排查是不是文件格式的问题。接下来的报错更具体：权限不足，无法保存到 Firestore。

修复过程检查了校验逻辑，最后把问题指向 Firestore 规则对图片 URL 大小的限制。这并不能说明 WebP 就是原因。生成的改动针对的是保存路径上的校验。修复期间，Bailey 展示了分享设置和应用画廊：Lyria 音乐、多人版 Neon Snake、Mandelbulb Explorer、Nano Banana 图像设计，以及一款用手部追踪操控的 MediaPipe 游戏。

修复完成后再上传一次，目录里就填入了日期、图书类型、书名、作者和简介，连书脊上看不到的信息也有。退出再登录，书库依然还在。判断应用测试是否成功，要看“识别—保存—重新加载”这个完整闭环，而不只是提取结果看起来像样。Bailey 通过链接和二维码分享了访问权限，又设想将来加一个借阅请求功能，专门对付借了她的书就不还的朋友。这个功能还只是个想法；演示真正做到的是一个能持久保存的个人书目。

为任务选择媒体模型

接下来由 Guillaume Vernade 接手，他把自己的生成式媒体工作坊压缩成了简短版本，部分结果是事先准备好的。他在游戏行业干过，也在 Google 和 DeepMind 做过开发者布道。在他看来，多模态既包括理解不同的感官输入，也包括用不同形式的输出来回应。按他的说法，早期 Gemini 的图像能力在后训练阶段被限制住了，后来即便支持了图像，偶尔还是会拒绝生成图像。图像、视频和音乐模型分开发布，单项能力更新起来就容易，不必替换一个庞大的全能产品。他说，生成式媒体方面大约每五天就发布一个模型或能力，更大范围的产品更新也很频繁。

输出不同，实际该怎么选也不同：

- 图像： Nano Banana 2 提供宽高比和尺寸控制。Vernade 对比了两种 grounding：一种是 Nano Banana Pro 的搜索 grounding，他用它把自己在网上的足迹画成了一张图；另一种是图像 grounding，可以为某座具体的桥或建筑检索视觉参考。 - 视频： Veo 3.1 Lite 的定位是先拿来测试提示词，再换用更高质量的模型。他口头报价时用的是按图像计的单位；现行定价文档中，带音频的 Lite 视频按秒计费，720p 为 0.05 美元，1080p 为 0.08 美元。这是现在的价格，并非工作坊当时的价目表。 - 歌曲： Lyria 3 既能生成短歌，也能生成带歌词的长歌。比如可以用 API 搭一个工作流，每天早上根据新闻生成一首歌。 - 连续音乐： Lyria real-time 会不停地生成音乐，提示词一变，曲风就跟着变，很像 DJ 打碟。

这些练习都要用付费模型。Vernade 建议跳过视频部分来控制成本，并粗略估计，精简版工作坊跑下来大约花 1 欧元。

选择 API 界面并保留有用的上下文

处理这本书之前，Vernade 先讲清了 Google 的几种应用和 API 入口有什么区别：

| 入口 | 主要优势 | 主要代价 | |---|---|---| | 消费级 Gemini | 开箱即用 | 看不太到用了什么模型、参数和工具 | | Vertex AI | 能控制企业级部署和部署区域 | 基础设施配置更多 | | AI Studio 和 Developer API | 有 API key 就能快速上手 | 企业级部署控制较少 |

如果团队已经在用 Google Cloud，或者有 DevOps 支持，他建议从 Vertex 起步。这个 notebook 用的是 Developer API，入门更简单。

文件上传 API 省去了配置存储桶的麻烦，这本书上传后就能反复当作提示词输入。结构化输出把回答限定在下一步能直接读取的字段上，免得生成的提示词前面还带一段寒暄。聊天模式会保存历史并重新发送，后续请求始终带着书的上下文。图像聊天同样保留之前的图片，希望借此保持角色和画风一致。累积历史固然方便，但下一个演示会说明，光靠它来挑选参考图并不够。

13

用显式引用取代隐式的图像历史

Vernade 要的是黑暗奇幻风格：黑白背景，彩色人物。系统指令禁止出现标题、边框、说明文字和漫画分格，同时要求图片老少咸宜。加这些约束，是因为模型之前总爱把人物肖像画成书的封面。指令里还有一条“仅限成人”，是早先某个地区限制留下的，现在已经过时了。一个单独的图像聊天先画出了鼹鼠、河鼠、蟾蜍和獾，再给各章配图：河边野餐、大路和一片森林。到了森林那张插图，蟾蜍已经和之前的肖像对不上了。

解决办法是改数据契约。现在每一章都包含名称、提示词，以及一份明确的角色列表。应用根据这份列表，只附上相关角色的参考图。下面的 Python 结构就是这个筛选步骤：用哪些图像输入，由章节记录决定，而不是让模型在越来越长的对话里自己去找。

```python from pathlib import Path from pydantic import BaseModel

class Chapter(BaseModel): name: str prompt: str characters: list[str]

def select_references( chapter: Chapter, portraits: dict[str, Path], ) -> list[Path]: missing = set(chapter.characters) - portraits.keys() if missing: raise ValueError(f"Missing character portraits: {sorted(missing)}") return [portraits[name] for name in dict.fromkeys(chapter.characters)] ```

这样一来，缺了哪张参考图，生成之前就能发现，也不用反复发送无关的肖像。Vernade 认为，角色越多，依赖完整历史就越靠不住。如果是更大的制作，他会给每个角色画正面、背面和侧面视图，再按场景挑出需要的那一张。改进后的演示里，蟾蜍和预期的形象对上了。

让场景动起来，再给这一章配乐

为了让插图动起来，Vernade 选了最大的 Veo 模型，用最新那张图做起始帧，沿用它的图像提示词，要求输出 720p 竖屏视频。他说，要是自己掏钱，他会选个小一点的模型。第一段视频里有一段戏剧性的对白，但静态图的提示词并没有交代这一帧之后发生什么。于是他回到书的聊天里，带上图片，请模型续写一段：鼹鼠瑟瑟发抖，攥紧围巾，河鼠拔出短弯刀保护他。

这次运行中，写得更明确的续写反而没带来更好的结果。Vernade 觉得第二段视频更差，还提到几次测试里画面会时不时冒出文字，原因不明。“描述一帧画面”和“说明接下来发生什么”的区分依然有用，但生成的视频必须亲自检查，不能想当然地以为提示词越长效果越好。

音乐也是同样的编排思路：Gemini 为每一章写提示词，再用 generate_content 把提示词发给 Lyria。河边那一章配的是宁静的管弦原声民谣，有吉他和长笛；大路那一章是轻快的小提琴和原声贝斯；森林那一章则是紧张的断奏和拨弦弦乐。Vernade 播放了事先生成的结果，觉得情绪都很贴切。他说自己事先跑过 notebook，但没试听过音乐。他还认为，Gemini 之所以擅长给媒体模型写提示词，部分原因在于这些媒体模型训练时用到了 Gemini 生成的材料。

15

用两个配置好的声音塑造不同的角色

旁白环节用的是文本转语音能力，Vernade 把它和 NotebookLM 的播客功能联系在一起。他没有给每个角色单独配一种声音，而是把一段节选改写成剧本。旁白部分标为“旁白”；其余台词共用一个“角色”标签，再靠固定的表演指示区分反复出场的角色。旁白用 Sulafat，其他角色共用 Fenrir。听众靠语速、口音和情绪分辨出不同的人。Vernade 坦言，自动改写剧本这一步只是工作坊里的权宜之计，真要规模化使用，还得再打磨。

他明确要求模型“朗读”这段文本，不是只丢给它光秃秃的对白，表演指示也写在这个请求里。说话人轮替时，生成的脚本会重复各角色的专属风格，比如语速快、一口上流英式腔调。随后鼹鼠和河鼠划船那一段表明，即便共用同一种声音，演绎出来也可以差别很大。同样的“素材→提示词”流水线，起点也可以换成有声书或一部足够短的电影，不一定是文本文件，靠的是 Gemini 的多模态输入能力。

转换 notebook 而不隐藏工作流

接着，Vernade 把整个 Python notebook 粘贴进 AI Studio，让它生成一个实现这套图书插画流程的应用。等待构建时，他打开了 Space DJ。里面每颗行星代表一条提示词；朝不同的行星飞去，持续生成的音乐就会随之变化；开启自动驾驶后，画面四处漫游，声音也跟着演变。他又回到之前构建好的一个应用，展示了文件上传界面，说生成过程花了大约 1,000 秒。他说这个应用复现了 notebook 的流程，但现场没有完整跑一遍来证明两者等价。

他给的编码指令，目的是让生成的应用更容易审查：

- 按功能拆分文件。 如果只改一个功能，却动了不相干的文件，问题一眼就能看出来，值得仔细查一查。 - 在流程各环节加日志。 光看报错信息，往往不知道失败发生在哪一步、哪个位置。 - 留意配额。 用付费 API key 可以提高构建时 AI Studio 的编码配额。

这些做法让生成的代码和它出的错都看得见，不必把排查工作全部丢给下一条提示词。

组合限制、服务等级与容量

观众问：视频里的音频是不是来自另一个模型？不同的输出能直接编排在一起，还是得用 FFmpeg 之类的工具拼接？Vernade 澄清说，演示的视频和音频都是 Veo 自己生成的。在演示的 Veo 3 生成中，不能把 Lyria 的音频文件当作配乐输入。音频参考、通过对话只改一首歌的结尾，这些是他希望将来能有的方向，并不是这里展示的能力。他建议做音乐还是用专门的音乐模型，别用 Veo；至于他说 Veo 的音乐训练有限，那只是推测。

notebook 里还有一个 service_tier 优先级设置。按 Vernade 的说法，Flex 是多等一会儿换更低的成本，Priority 则是花钱买优先处理，适合现场演示。就工作坊这套配置，他给出的价格是 Flex 半价、Priority 两倍价。这是他当时给的数字，并不适用于如今所有模型。他建议个人实验时去掉优先级设置。而且尽管为了可靠性做了这些努力，正在进行的应用演示还是碰上了算力不足。

让模型适配你能掌控的硬件

最后一部分由 Ian Ballantyne 主讲，话题从托管生成转向在手机、个人电脑或开发者自己掌控的云端部署上运行模型。他以工作坊当时可用的四款模型为主线介绍了 Gemma 4。模型卡给出的参数量比他口头说的约数更精确；模型卡后来扩充的阵容，不要和这里演示的混为一谈。

E2B 和 E4B 面向手机、Raspberry Pi 和 Jetson 级别的设备。它们之所以按“有效”规模计，是因为逐层嵌入（per-layer embeddings）可以留在闪存里，需要时再调入内存。Ballantyne 说，它们的有效核心约为 2B 和 4B；把嵌入也算进 RAM，则约为 5B 和 8B。更大的两款是混合专家模型 26B A4B 和稠密模型 31B。激活参数描述的是每个 token 的计算量，并不是说只需要存储激活的那部分权重。大模型能不能装进笔记本、台式机或单块 GPU，要看精度、量化方式、上下文分配和可用内存。

思考模式可以配置；工作坊这几款模型都支持图像和视频理解，音频输入只有两款 E 系列模型支持。Ballantyne 说它们的表现可以比肩大十倍的模型，但没有给出具体任务、对比对象或基准测试。他给出的更具体的比较是能力侧重：Gemma 2 主打创意写作，Gemma 3 和 Gemma 4 则拓展到编程、函数调用和动作选择。正是这些智能体能力，引出了接下来的手机和编程演示。

在手机上运行技能和小型编程循环

Google AI Edge Gallery 支持 Android 和 iOS，是一个试玩端侧模型的平台。在展示的 Pixel 示例里，E2B 在多个 Agent Skills 中做选择：Android Intents 可以调起其他应用，JavaScript 可以实现自定义行为，WebView 可以展示界面。一个研究追踪器演示了写入和查询信息，调用哪个函数，由模型根据自然语言请求来选。其他技能可以打开地图或调用服务。哪怕技能本身用到了外部 API，决定调用哪个动作的仍是本地推理。

手机上也能跑一个小型的编程反馈循环。Ballantyne 介绍了 Python、HTML 和 TypeScript 任务，并展示了一个生成的计算器：除以零时能正确报错。他把预期限定在小应用上，不指望它搭建大型架构系统。他认为这个例子里思考模式是关闭的，并说开启后模型会在输出前多一步规划，推理通常会更好。

为一个智能体工作负载提供一个本地模型服务

Gemma 可以接入 Ollama、LM Studio、vLLM 和 SGLang 等推理服务工具。Ballantyne 在一台 M4 Mac 上用 LM Studio 加载了 26B。按这套配置，他说模型本身约占 18 GB，加上演示用的上下文额度约 22 GB。Mac 是统一内存，计算硬件可以直接用上这部分内存；如果是独立显卡，要达到他所说的全速配置，就需要足够的显存。他认为 26B 比稠密的 31B 快，是因为激活参数更少。

LM Studio 可以通过兼容接口暴露模型，让现有客户端直接用上本地推理。Ballantyne 把服务开在 1234 端口，并讲了怎么把一个 Chat Completions 客户端指向这台服务器。Python 里关键的配置只有两样：接口地址，以及本地服务器暴露出的模型标识：

```python import os from openai import OpenAI

client = OpenAI( base_url="http://localhost:1234/v1", api_key="lm-studio", )

response = client.chat.completions.create( model=os.environ["LOCAL_MODEL_ID"], messages=[{ "role": "user", "content": "Create a self-contained SVG of a spinning planet.", }], ) print(response.choices[0].message.content) ```

应用这一侧的推理接口还是熟悉的那一套，计算却搬到了开发者自己的机器上。

接下来的演示跑了一个编排器加十个子智能体，每个子智能体负责一张不同的 SVG，为了速度关闭了思考模式。屏幕上显示的吞吐量是所有子智能体生成速度的总和，不是单个请求的速度。编排器把结果汇总成一个图库，里面有一颗旋转的行星动画。Ballantyne 建议，同样的模式也可以用来整理文件、写代码、拆分研究任务或做数据分析；这个任务不联网也能跑。他估计开启思考模式、多做些规划，SVG 的质量会更好，代价是要多干些活。

连接 OpenCode，再测试生成的游戏

OpenCode 也用同样的方式接入本地接口。在演示的配置里，Ballantyne 编辑 .config/opencode/config.json，填入提供方、schema、暴露的模型、接口参数和本地服务器地址。编程框架本身不用改。如果本地 RAM 不够跑想要的量化版本，他推荐参考一份 Cloud Run 部署指南，还展示了一条面向 RTX PRO 6000 的 beta 部署命令，但没有实际执行。两款较大的模型还有托管演示版，也可以用来测试提示词、文件和视频输入，以及他介绍的 Search grounding 集成。

现场编程任务中，31B 已经事先写好了 Nebula Drift 的规格说明，这是一款躲避小行星的无尽竞速游戏。本地模型在 OpenCode 里拿到这份文件，开启了思考模式。OpenCode 提供 shell、文件系统和编辑工具；模型创建了一个 nebula_drift 目录，开始编写 index 文件、JavaScript 和 CSS。Ballantyne 第一次尝试打开游戏时，模型还在改代码。页面出来了，游戏却跑不起来。

语法错误成了智能体的下一个输入。Ballantyne 手动把报错复制进对话，模型随即重新读取文件，修复 game.js。OpenCode 既支持定点编辑，也支持整文件重写。模型还能调用子智能体；Ballantyne 发现 31B 选子智能体更可靠，26B 有时需要更明确的引导。MCP 服务器和技能还能补充更多能力。修复时先是卡在编辑要求精确匹配上，模型似乎又被卸载了，于是他重新加载模型，明确要求把 game.js 整个重写。

游戏中的游戏，以及把截图变成 HTML

趁 Nebula Drift 还在修，一位观众提议做一款让玩家自己做游戏的游戏。Ballantyne 请较大的模型写一份规格说明，拿之前那份当格式参考。新项目叫 Omniforge。他想说明的是，开发者在自己拥有的硬件上就能跑这套工作流，而不是说它写规格说明的水平超过了前沿模型。Nebula Drift 这边改了 delta time 和输入处理，但开始按钮还是不管用。他要求重新生成文件，然后让 31B 把 Omniforge 写成一个 index.html，CSS 和 JavaScript 都放在里面。

把语言映射到机器人和开发工具上

Open Duck 把同样的动作选择机制用到了机器人模拟器上。E2B 下载到浏览器里，通过 WebGPU 运行。它理解自然语言请求，从机器人支持的动作里挑一个，在模拟器执行之前先把要下达的指令显示出来。展示的界面把对话请求、机器人动作和手动控制放在一起。Ballantyne 认为还可以扩展到嵌入式设备上运行；不过这次演示本身是在模拟器里跑的。

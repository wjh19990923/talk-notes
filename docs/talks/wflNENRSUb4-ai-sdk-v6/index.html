AI SDK v6：从聊天界面到拥有持久计算机的智能体

构建一个流式的 TypeScript 智能体，加上带类型的工具和一个持久的文件系统，然后跟随现场调试，看看存储的记忆和脚本如何变成可复用的能力。

熟悉 TypeScript、React hooks、Next.js 路由处理函数和基本的命令行开发，有助于理解实现。

01

把已部署的项目带进本地开发

The application is already live on Vercel when the recording begins. Its dashboard shows one completed production-checklist item, but the immediate task is to get that deployed project running locally. Nico Albanese opens the linked GitHub repository, copies its clone address from the Code button, and clones aie-london-demo. The workshop’s Project Setup page supplies the accompanying instructions.

Install the Vercel CLI if needed, authorize its browser login, and check which account it is using:

``bash npm i -g vercel vercel whoami ``

Inside the cloned repository, run vercel link, select the matching project, and pull its environment variables. The resulting OIDC token authenticates both AI Gateway inference and Vercel Sandbox access in this workshop.

Two setup failures are easy to confuse. Account selection determines which projects and teams are visible: vercel logout followed by vercel login corrects a personal-versus-work account mismatch. Executable selection determines which CLI actually runs. Albanese reports that an older authentication method had been invalidated, prompting an update with npm install -g vercel@latest; which vercel then reveals whether the executable belongs to that npm installation or, as on his machine, to pnpm. Updating one installation does not update the other.

02

把智能体与它的 HTTP 端点分开

While setup finishes, Albanese shows the redesigned AI SDK landing page, including live download figures, and points to OpenCode as an application built on the SDK. Back in the project, the first check is deliberately ordinary: install dependencies, start the fresh Next.js app, and confirm that its starter page appears at localhost:3000. Then add the agent dependencies:

``bash pnpm install pnpm run dev ``

After stopping the development server:

``bash pnpm add ai @ai-sdk/react zod ``

ai supplies the core SDK, @ai-sdk/react supplies the React integration, and Zod supplies schema definitions.

AI SDK 4 centered on generateText, streamText, generateObject, and streamObject. In the v6 workshop, structured output is also available through the text-generation functions. The architectural change is a reusable agent definition: Albanese’s motivating example is an api/chat/route.ts swollen with inline tools and system prompts. Moving that configuration into lib/agent.ts lets a Next.js endpoint, a Bun server, or another application in a monorepo reuse the same plain JavaScript agent.

ToolLoopAgent names the behavior it packages: an agent that can repeatedly call tools. Its smallest definition needs a model. An explicit provider instance, such as one created with openai from @ai-sdk/openai, remains an option. The demonstrated v6 global provider defaults to AI Gateway, so a plain model string can select a gateway model; applications can override that global provider.

The initial model is GPT-5.4 mini, chosen for inexpensive, fast experimentation. Albanese notes that he has used the larger model extensively but has less experience with mini. The reusable definition is correspondingly small:

```typescript // lib/agent.ts import { ToolLoopAgent } from 'ai';

export const myAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', }); ```

This defines the agent; it does not yet expose a way for the browser to call it.

03

连接路由、流和消息部件

The HTTP boundary lives in app/api/chat/route.ts. Its job is to receive messages and return the agent’s UI stream:

```typescript // app/api/chat/route.ts import { createAgentUIStreamResponse } from 'ai'; import { myAgent } from '@/lib/agent';

export async function POST(request: Request) { const { messages } = await request.json();

return createAgentUIStreamResponse({ agent: myAgent, uiMessages: messages, }); } ```

createAgentUIStreamResponse bundles the streaming work that otherwise surrounds a streamText call and conversion to a UI-message response. The agent also exposes myAgent.stream for direct streaming. The agent owns behavior; the endpoint owns HTTP delivery.

On the client, useChat owns message state and provides sendMessage. Each message contains parts, so rendering traverses both levels. This first client handles text; tool-specific parts come later.

```tsx // app/page.tsx 'use client';

import { useState } from 'react'; import { useChat } from '@ai-sdk/react';

export default function Page() { const [input, setInput] = useState(''); const { messages, error, sendMessage } = useChat();

return ( <main> {messages.map(message => ( <div key={message.id}> <strong>{message.role}</strong> {message.parts.map((part, index) => part.type === 'text' ? ( <p key={index}>{part.text}</p> ) : null, )} </div> ))} {error && <p role="alert">{error.message}</p>} <form onSubmit={event => { event.preventDefault(); if (!input.trim()) return; void sendMessage({ text: input }); setInput(''); }}> <input aria-label="Message" value={input} onChange={event => setInput(event.target.value)} /> <button type="submit">Send</button> </form> </main> ); } ```

All conversation state remains on the client in this workshop. With the development server running, a greeting and a returned response establish the complete browser-to-agent path.

04

指令把能力与行为连接起来

The first behavioral change is one line in the agent definition: instructions: 'Respond like a cowboy.' A new greeting produces “Howdy, partner” and a cowboy emoji. The demonstration is small, but it establishes that the reusable definition controls behavior without changing the route or client.

The workshop builds toward three cooperating components:

- Runtime: manages the tool loop and the context passed between steps. - Tools: give the agent operations it can request. - Computer: supplies a filesystem and an environment for executing code and retaining state during work sessions.

Instructions tell the agent how to use those capabilities together. They remain consequential even when the application has moved far beyond a single prompt and response.

05

用由服务商执行的工具补充上下文

Web search is the first tool because it gives the agent access to information outside its existing conversation. Installing @ai-sdk/openai supplies the provider’s tool definition even though inference still goes through AI Gateway. The distinction between tool categories is who defines the interface and who executes the operation.

| Tool category | Interface supplied by | Execution supplied by | | --- | --- | --- | | Custom | Application developer | Application code | | Provider-defined | Model provider | Application code | | Provider-executed | Model provider | Provider infrastructure |

A custom tool needs a description, input schema, and execution function. Provider-defined tools, such as Anthropic’s Bash and computer-use tools, have interfaces designed for the provider’s models, but the application still supplies the operation. Provider-executed tools, such as hosted web search, run on the provider’s servers and return their results in the message state. That saves implementation work while tying the capability to the provider.

Remove the cowboy instructions and register the hosted search tool:

```typescript // lib/agent.ts import { ToolLoopAgent } from 'ai'; import { openai } from '@ai-sdk/openai';

export const myAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', tools: { webSearch: openai.tools.webSearch({}), }, }); ```

The provider helper augments the outgoing request to enable search. Asking when AI Engineer Summit London takes place now produces an answer with retrieved context, although the interface remains blank during the wait. Albanese then configures London as the search tool’s user location. Asking the question again without naming the city produces a London-oriented answer: that extra location context travels as a provider-tool parameter.

06

让工具活动可见且带类型

The search works, but the user cannot tell that anything is happening. The agent may be taking multiple steps while the text-only interface renders nothing. Tool parts use a tool- prefix followed by the registered tool name, so webSearch appears as tool-webSearch. Adding a rendering case makes the activity visible, but the first attempt exposes another problem: its input is typed as unknown.

The agent definition becomes the source of truth for UI types. Export a message type derived from that definition:

```typescript // Add to lib/agent.ts import type { InferAgentUIMessage } from 'ai';

export type MyAgentUIMessage = InferAgentUIMessage<typeof myAgent>; ```

Use MyAgentUIMessage[] for the route’s incoming messages, then pass the type to useChat<MyAgentUIMessage>(). Discriminating a part by tool-webSearch now exposes the corresponding tool input and output types. The type relationship flows from the server-side tool definition into the client renderer.

With the typed search component installed, the next request—asking who Nico Albanese is—shows an inline pending state before the result. Tool rendering makes the work observable while it is happening, rather than waiting for the final prose to reveal that a search occurred.

07

给长任务一份对话之外的计划

The next capability is a computer. Albanese motivates it with Vercel’s internal d0 analytics agent, which accesses backend and administrative data, including Salesforce, through a Slack interface. It began as a way to reduce repeated requests to the data team. In his account, an agent with many tools could call several of them and still return a partly hallucinated answer. Adding a filesystem changed how it organized its work.

Each session received a scratchpad with the objective at the top, an initial plan beneath it, and steps to check off as work progressed. A separate directory held the research. Instructions required the agent to consult the plan and follow it, repeatedly bringing the original objective back into focus instead of leaving it buried in an expanding conversation. At completion, the same files provided an inspectable record of the work. Albanese reports better follow-through from this pattern with either a full computer or a virtual filesystem.

He describes the pattern as common to internal data, go-to-market, and customer-support agents. Albanese reports roughly 90% fewer customer-support tickets, without specifying the measurement period or denominator. His accompanying qualitative observation is that users were thanking the support agent for its help.

08

在算力来去之间保留文件系统状态

A remote sandbox is fundamentally ephemeral: however long its process can run, eventually that instance ends. The workshop uses Vercel’s named, persistent sandboxes, described at the time as a beta feature. A stable name identifies the sandbox, while sessions represent its running instances. A request for that name reaches an active instance if one exists or starts a new one if necessary.

This replaces lifecycle code Albanese had previously written himself: archive the filesystem after each request, store the archive in blob storage, and restore it into a new machine later. In the named-sandbox design he demonstrates, inactivity shutdown snapshots the filesystem and a subsequent request restores it. Filesystem continuity does not require a continuously running process. The application can keep referring to the same named workspace across requests.

09

把网络历史与模型上下文分开

An audience question interrupts the sandbox implementation: if the agent can store things elsewhere, must each request still send the entire conversation? There are two different decisions here. In the demonstrated useChat setup, sendMessage sends the full message history to the route. A production application can instead transmit only the newest message and reconstruct the conversation from server-side storage. That reduces the client request payload without necessarily changing what the model receives.

Selecting the model’s context is a separate policy decision. The SDK does not decide which older information is irrelevant. convertToModelMessages converts UI messages into model messages, removing UI-specific information such as IDs and timestamps; data-part conversion can also shape what reaches the model. Because the application owns the messages, it can inspect and transform them, including removing selected tool-call content. Those transformations require application-specific judgments about what to preserve.

prepareStep provides a more granular intervention point. It runs before each model step in the tool loop, with access to messages and information about the run so far. Returning parameters changes the inputs for that next step. The workshop’s example starts selecting only the latest five messages once the step number reaches 20:

```typescript import { ToolLoopAgent } from 'ai';

export const filteredAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', prepareStep: ({ stepNumber, messages }) => { if (stepNumber >= 20) { return { messages: messages.slice(-5) }; } return {}; }, }); ```

The example shows where to implement a sliding context window. Choosing an appropriate window—and preserving the information required by the task—remains the developer’s responsibility.

10

剪枝在上下文空间与缓存复用之间取舍

Albanese then opens an example from his own coding agent using GPT-5.4. Albanese reports a single turn lasting 104 minutes, making 316 tool calls, changing 29 files, and occupying 32% of GPT-5.4’s context window without compaction. This is an observation from his system, rather than a controlled comparison of context-management strategies.

His earlier strategy removed old tool calls to keep context occupancy around 40–60%. The cost was that changing earlier input invalidated cached input, undermining reuse on later calls. He contrasts his recollection of roughly 400K-token windows when using Opus and GPT-5.3-Codex with the million-token windows he was using more recently; the specific Opus version and configuration are not identified. With more room available, aggressive pruning had become less attractive for his workload.

Two alternatives keep detailed work out of the main conversation:

- Sub-agents: assign a sufficiently independent task to another context, then bring back a compact result—roughly a thousand tokens in his example—instead of every intermediate tool result. - Handoff: let the agent prepare relevant context and start a new main thread. Albanese points to Amp’s handoff tool as an example.

He favors delegation where possible because LLM-generated summaries are lossy.

The failure mode he worries about is losing a user constraint during compaction. He recounts an OpenClaw email-deletion incident and attributes it to oversized email results triggering a summary that dropped an instruction against the action. That causal account is his interpretation, not an established diagnosis here. He does not offer a settled rule for preserving every constraint, such as retaining user messages while stripping everything else.

Describing personal use for roughly 14 hours a day over four months, Albanese says compaction had not been a practical problem for him. Albanese reports a 95% cache-token read ratio for that personal coding-agent usage. He values that reuse for speed and cost.

The API distinction at the end of the discussion is important: prepareStep changes a step’s input without destructively replacing the accumulated history. A helper in lib/sandbox.ts accepts a sandbox name, returns the existing sandbox if found, or creates it otherwise. The agent now needs more than conversation messages at call time: it needs that sandbox instance.

This is a general requirement. A support agent might receive a customer ID and account tier; a hypothetical airline assistant might route a blue-tier customer to GPT-5.4 mini and a gold-tier customer to GPT-5.4 pro. These structured inputs change agent behavior without belonging in the conversation itself. Instead of wrapping agent creation in an ad hoc factory, callOptionsSchema declares those call-time inputs explicitly.

For the computer-backed agent, the schema requires an actual Sandbox instance:

```typescript import { ToolLoopAgent } from 'ai'; import { Sandbox } from '@vercel/sandbox'; import { z } from 'zod';

The corresponding options argument to createAgentUIStreamResponse is now typed to require a sandbox. Omitting it produces a type error at the call site.

The sandbox must then reach the tools that will use it. The runtime’s context serves this purpose: like React context, it carries arbitrary objects, values, and functions to downstream code. It is distinct from the conversation context sent to the model. prepareCall runs once before each agent run and copies the sandbox from call options into runtime context. Albanese explicitly corrects its lifetime: that context spans the steps of one run, not separate invocations.

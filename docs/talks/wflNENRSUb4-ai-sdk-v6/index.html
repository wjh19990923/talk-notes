AI SDK v6：从聊天界面到拥有持久计算机的智能体

构建一个流式的 TypeScript 智能体，加上带类型的工具和一个持久的文件系统，然后跟随现场调试，看看存储的记忆和脚本如何变成可复用的能力。

熟悉 TypeScript、React hooks、Next.js 路由处理函数和基本的命令行开发，有助于理解实现。

01

把已部署的项目带进本地开发

录制开始时，这个应用已经部署在 Vercel 上。控制台显示生产环境检查清单里有一项已经完成，但眼下要做的是把这个已部署的项目在本地跑起来。Nico Albanese 打开关联的 GitHub 仓库，从 Code 按钮复制克隆地址，克隆下 aie-london-demo。配套步骤见工作坊的 Project Setup 页面。

如果还没装 Vercel CLI，先安装，在浏览器里完成登录授权，再确认当前用的是哪个账号：

``bash npm i -g vercel vercel whoami ``

在克隆下来的仓库里运行 vercel link，选中对应项目，再拉取它的环境变量。拉下来的 OIDC token 在这个工作坊里管两件事：AI Gateway 推理鉴权和 Vercel Sandbox 访问鉴权。

有两种配置问题很容易混为一谈。账号选择决定你能看到哪些项目和团队：个人账号和工作账号弄混了，先 vercel logout 再 vercel login 就能纠正。可执行文件选择决定实际运行的是哪个 CLI。Albanese 说，一种旧的认证方式已经失效，他只好用 npm install -g vercel@latest 升级。接着用 which vercel 就能看出，这个可执行文件属于 npm 装的那份，还是像他机器上那样属于 pnpm。升级其中一份，另一份不会跟着升级。

02

把智能体与它的 HTTP 端点分开

等配置收尾的时候，Albanese 展示了改版后的 AI SDK 首页，上面有实时下载量。他还提到，OpenCode 就是基于这个 SDK 构建的应用。回到项目，第一步检查特意做得很普通：装依赖，启动这个全新的 Next.js 应用，确认 localhost:3000 能打开初始页面。然后加上智能体相关的依赖：

``bash pnpm install pnpm run dev ``

停掉开发服务器后：

``bash pnpm add ai @ai-sdk/react zod ``

ai 是核心 SDK，@ai-sdk/react 负责 React 集成，Zod 用来定义 schema。

AI SDK 4 的核心是 generateText、streamText、generateObject 和 streamObject。到了工作坊用的 v6，文本生成函数也能输出结构化结果。架构上的变化是可复用的智能体定义。Albanese 举了个促使他这么做的例子：一个 api/chat/route.ts 里塞满了内联的工具和系统提示词，越写越臃肿。把这些配置挪到 lib/agent.ts 之后，Next.js 端点、Bun 服务器或 monorepo 里的其他应用，都能复用同一个纯 JavaScript 智能体。

ToolLoopAgent 这个名字就说明了它封装的行为：能反复调用工具的智能体。最简单的定义只需要一个模型。也可以显式传入 provider 实例，比如用 @ai-sdk/openai 里的 openai 创建。演示中的 v6 全局 provider 默认走 AI Gateway，所以直接写一个模型字符串，就能选中网关上的模型；应用也可以覆盖这个全局 provider。

起步用的模型是 GPT-5.4 mini，便宜又快，适合做实验。Albanese 说他大量用过大号模型，mini 版用得不多。可复用的定义也相应很简短：

```typescript // lib/agent.ts import { ToolLoopAgent } from 'ai';

export const myAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', }); ```

这里只定义了智能体，浏览器还没法调用它。

03

连接路由、流和消息部件

HTTP 边界放在 app/api/chat/route.ts。它负责接收消息，再返回智能体的 UI 流：

```typescript // app/api/chat/route.ts import { createAgentUIStreamResponse } from 'ai'; import { myAgent } from '@/lib/agent';

export async function POST(request: Request) { const { messages } = await request.json();

return createAgentUIStreamResponse({ agent: myAgent, uiMessages: messages, }); } ```

原本要围绕 streamText 调用写一圈流式处理，再转换成 UI 消息响应；createAgentUIStreamResponse 把这些打包在了一起。智能体本身也提供 myAgent.stream，可以直接流式输出。智能体管行为，端点管 HTTP 传输。

客户端由 useChat 管理消息状态，并提供 sendMessage。每条消息由多个 part 组成，所以渲染时要遍历两层。这个初版客户端只处理文本，工具相关的 part 后面再加。

```tsx // app/page.tsx 'use client';

import { useState } from 'react'; import { useChat } from '@ai-sdk/react';

export default function Page() { const [input, setInput] = useState(''); const { messages, error, sendMessage } = useChat();

return ( <main> {messages.map(message => ( <div key={message.id}> <strong>{message.role}</strong> {message.parts.map((part, index) => part.type === 'text' ? ( <p key={index}>{part.text}</p> ) : null, )} </div> ))} {error && <p role="alert">{error.message}</p>} <form onSubmit={event => { event.preventDefault(); if (!input.trim()) return; void sendMessage({ text: input }); setInput(''); }}> <input aria-label="Message" value={input} onChange={event => setInput(event.target.value)} /> <button type="submit">Send</button> </form> </main> ); } ```

在这个工作坊里，所有会话状态都留在客户端。启动开发服务器，发一句问候，收到回复，从浏览器到智能体的整条链路就通了。

04

指令把能力与行为连接起来

第一处行为改动只需在智能体定义里加一行：instructions: 'Respond like a cowboy.'。再打个招呼，回复就成了“Howdy, partner”，外加一个牛仔 emoji。演示虽小，却说明了一点：只改可复用的定义就能控制行为，路由和客户端都不用动。

工作坊最终要搭出三个协同工作的部分：

- 运行时： 管理工具循环，以及在步骤之间传递的上下文。 - 工具： 提供智能体可以请求执行的操作。 - 计算机： 提供文件系统和运行环境，用来执行代码，并在工作会话期间保留状态。

指令告诉智能体怎样把这些能力组合起来用。哪怕应用早已不是一问一答那么简单，指令依然举足轻重。

05

用由服务商执行的工具补充上下文

第一个工具选了网页搜索，因为它能让智能体拿到当前对话以外的信息。安装 @ai-sdk/openai 是为了拿到这家厂商的工具定义，推理依然走 AI Gateway。各类工具的区别在于：接口由谁定义，操作由谁执行。

| 工具类别 | 接口提供方 | 执行方 | | --- | --- | --- | | 自定义 | 应用开发者 | 应用代码 | | 厂商定义 | 模型厂商 | 应用代码 | | 厂商执行 | 模型厂商 | 厂商的基础设施 |

自定义工具需要描述、输入 schema 和执行函数。厂商定义的工具，比如 Anthropic 的 Bash 和 computer use 工具，接口是为该厂商的模型量身设计的，但具体操作仍由应用实现。厂商执行的工具，比如托管的网页搜索，跑在厂商的服务器上，结果直接写进消息状态。这样省去了实现工作，代价是这项能力和厂商绑在了一起。

去掉牛仔指令，注册托管的搜索工具：

```typescript // lib/agent.ts import { ToolLoopAgent } from 'ai'; import { openai } from '@ai-sdk/openai';

export const myAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', tools: { webSearch: openai.tools.webSearch({}), }, }); ```

这个厂商辅助函数会改写发出的请求，开启搜索。现在问 AI Engineer Summit London 什么时候举办，智能体能结合检索到的内容作答，只是等待期间界面一片空白。接着 Albanese 把搜索工具的用户位置设成伦敦。再问一遍，不提城市名，回答就围绕伦敦展开了：这份额外的位置信息，是作为厂商工具的参数传过去的。

06

让工具活动可见且带类型

搜索能用了，可用户看不出有任何动静。智能体也许正在走好几个步骤，而只认文本的界面什么也不显示。工具 part 的类型是 tool- 前缀加上注册时的工具名，所以 webSearch 显示为 tool-webSearch。加一个对应的渲染分支，这些活动就能显示出来。不过第一次尝试又暴露出新问题：它的输入类型是 unknown。

智能体定义成为 UI 类型的唯一来源。 从这个定义推导出消息类型并导出：

```typescript // Add to lib/agent.ts import type { InferAgentUIMessage } from 'ai';

export type MyAgentUIMessage = InferAgentUIMessage<typeof myAgent>; ```

路由收到的消息标注为 MyAgentUIMessage[]，再把这个类型传给 useChat<MyAgentUIMessage>()。现在按 tool-webSearch 区分 part，就能拿到对应工具的输入和输出类型。类型从服务端的工具定义一路传到客户端的渲染组件。

装上带类型的搜索组件后，再发一个请求——问 Nico Albanese 是谁。结果出来之前，界面会先内联显示一个进行中的状态。把工具调用渲染出来，工作进行时就能看到它，不必等最后那段文字才知道发生过一次搜索。

07

给长任务一份对话之外的计划

下一项能力是计算机。Albanese 用 Vercel 内部的 d0 数据分析智能体 说明为什么需要它。这个智能体通过 Slack 界面访问后端和管理数据，包括 Salesforce。做它的初衷，是减少大家反复找数据团队要数据。按他的说法，一个工具很多的智能体，可能调了好几个工具，给出的答案里仍有一部分是幻觉。加上文件系统后，它组织工作的方式变了。

每个会话都有一个草稿文件：最上面写目标，下面是初步计划，再往下是随进度逐项勾掉的步骤。研究资料另放一个目录。指令要求智能体对照计划执行，原始目标因此一次次被拉回视野，而不是埋在越拉越长的对话里。任务完成后，这些文件还能留作可供检查的工作记录。Albanese 说，不管用的是完整的计算机还是虚拟文件系统，这种模式都让智能体更能把事做完。

他说，内部数据、市场拓展（go-to-market）和客服类智能体普遍采用这种模式。Albanese 称客服工单减少了约 90%，但没说明统计周期和基数。他还补充了一个定性观察：用户会向客服智能体道谢。

08

在算力来去之间保留文件系统状态

远程沙箱本质上是临时的：进程能跑多久都行，但这个实例终究会结束。工作坊用的是 Vercel 的命名持久化沙箱，当时还处于 beta 阶段。沙箱靠一个固定的名字识别，会话则代表它正在运行的实例。按名字发请求，有活跃实例就直接连上，没有就按需启动一个新的。

这样一来，Albanese 以前自己写的生命周期代码就省掉了：每次请求后把文件系统打包归档，存进 blob 存储，之后再恢复到新机器上。在他演示的命名沙箱方案里，沙箱闲置关机时会给文件系统打快照，下一次请求时再恢复。文件系统要延续，并不需要进程一直运行。 应用可以在多次请求之间一直指向同一个命名工作区。

09

把网络历史与模型上下文分开

写沙箱代码的过程中，观众插了一个问题：既然智能体能把东西存在别处，每次请求还要把整段对话发过去吗？这里其实是两件不同的事。在演示的 useChat 配置里，sendMessage 会把完整的消息历史发给路由。生产应用也可以只发最新一条消息，再从服务端存储里还原整段对话。这样客户端请求变小了，模型收到的内容却不一定变。

给模型挑选上下文，是另一项策略决定。SDK 不会替你判断哪些旧信息没用。convertToModelMessages 把 UI 消息转成模型消息，去掉 ID、时间戳这类只跟 UI 有关的信息；data part 的转换也能影响最终交给模型的内容。消息归应用所有，所以应用可以检查、改写它们，包括删掉部分工具调用的内容。至于哪些该留，得结合具体应用来判断。

prepareStep 提供了更细粒度的介入点。在工具循环里，它在每次调用模型之前运行，能拿到消息和本次运行到目前为止的信息。返回参数，就能改变下一步的输入。工作坊的例子是：步数到 20 以后，只取最近 5 条消息：

```typescript import { ToolLoopAgent } from 'ai';

export const filteredAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', prepareStep: ({ stepNumber, messages }) => { if (stepNumber >= 20) { return { messages: messages.slice(-5) }; } return {}; }, }); ```

这个例子说明了滑动上下文窗口该在哪里实现。窗口设多大、怎样保住任务需要的信息，仍要开发者自己把握。

10

剪枝在上下文空间与缓存复用之间取舍

接着 Albanese 打开自己编程智能体里一个用 GPT-5.4 跑的例子。据他介绍，单单一轮就持续了 104 分钟，调了 316 次工具，改了 29 个文件，占用了 GPT-5.4 上下文窗口的 32%，全程没有压缩。这是他自己系统里的观察，不是对几种上下文管理策略的对照实验。

他以前的做法是删掉旧的工具调用，把上下文占用控制在 40%–60% 左右。代价是：改了早先的输入，已缓存的输入就会失效，后续调用复用不上。他回忆说，用 Opus 和 GPT-5.3-Codex 时窗口大约是 400K token，而最近用的已经是百万 token 级别的窗口；具体是哪个 Opus 版本、什么配置，他没有说明。空间宽裕了，对他的工作负载来说，激进裁剪也就没那么划算了。

还有两种办法，能把细碎的工作挡在主对话之外：

- 子智能体： 把一个足够独立的任务交给另一个上下文去做，只带回一份精简结果——在他的例子里大约一千个 token——而不是所有中间工具结果。 - 交接（handoff）： 让智能体整理好相关上下文，另起一个新的主线程。Albanese 举了 Amp 的 handoff 工具 作为例子。

他更倾向于尽量委派，因为 LLM 生成的摘要总会丢信息。

他担心的失败场景是：压缩时弄丢了用户的某条约束。他讲了 OpenClaw 误删邮件的事故，认为起因是邮件结果太大，触发了摘要，而摘要恰好丢掉了一条禁止该操作的指令。这个因果解释是他个人的看法，并非确证的诊断。至于怎样保住每一条约束，比如只保留用户消息、其余一律剥掉，他也没给出定论。

Albanese 说，四个月来他每天用大约 14 个小时，压缩在实际使用中从没成为问题。据他统计，这部分个人编程智能体用量的缓存 token 读取占比为 95%。他看重这种复用带来的速度和成本优势。

讨论结尾讲到的 API 区别很关键：prepareStep 改的是单步的输入，不会破坏性地替换累积的历史。 每次调用都从汇总后的完整消息重新开始。返回过滤后的数组只影响这一步，最终持久化时依然可以保留完整的消息记录。临时的上下文策略和持久的对话记录，可以各司其职。

11

在每次调用智能体时传入一个沙箱

回到实现，安装工作坊用的 sandbox beta 版：

``bash pnpm add @vercel/sandbox@beta ``

lib/sandbox.ts 里的辅助函数接收一个沙箱名字：找到已有的沙箱就直接返回，找不到就新建一个。现在智能体在调用时需要的不只是对话消息，还要这个沙箱实例。

这是个普遍需求。客服智能体可能要拿到客户 ID 和账户等级；假设有个航空公司助手，可以把蓝卡客户分给 GPT-5.4 mini，把金卡客户分给 GPT-5.4 pro。这些结构化输入会改变智能体的行为，却不属于对话本身。与其临时写个工厂函数包住智能体的创建，不如用 callOptionsSchema 把这些调用时输入显式声明出来。

接上计算机的智能体，schema 要求传入一个真正的 Sandbox 实例：

```typescript import { ToolLoopAgent } from 'ai'; import { Sandbox } from '@vercel/sandbox'; import { z } from 'zod';

const callOptionsSchema = z.object({ sandbox: z.instanceof(Sandbox), });

export const myAgent = new ToolLoopAgent({ model: 'openai/gpt-5.4-mini', callOptionsSchema, }); ```

相应地，createAgentUIStreamResponse 的 options 参数现在在类型上要求必须提供沙箱。漏传的话，调用处会报类型错误。

接下来，沙箱还得送到要用它的工具手里。运行时 context 正是干这个的：它和 React context 类似，可以把任意对象、值和函数传给下游代码。它和发给模型的对话上下文是两回事。prepareCall 在每次智能体运行前执行一次，把沙箱从调用选项复制到运行时 context 里。Albanese 特意纠正了它的生命周期：这个 context 只覆盖单次运行里的各个步骤，不跨多次调用。

12

把 Bash 从智能体接到计算机上

tools.ts 引入了 Bash，作为操作计算机的通用接口。列文件、写文件、跑脚本，不必各定义一个操作，智能体用 shell 命令就能表达。这个工具和其他自定义工具一样由三部分组成：描述，引导模型何时用、怎么用；输入 schema，描述命令；execute 函数，负责执行。运行时 context 从执行函数的第二个参数传进来，工具因此能拿到传入的沙箱，又不必绑死在某个智能体定义上。

在 v6 工作坊的这个阶段，据介绍，要等到 AI SDK 7 才会对工具所需的运行时 context 和所属智能体做更强的类型约束。演示的工具取出沙箱，执行生成的 Bash 命令，返回标准输出、错误输出和退出码。有了这些结果，模型下一步就知道实际发生了什么。

第一次请求 ls -la 失败了，因为各部分还没接起来。修复过程正好可以当成一份接线清单：

1. 在智能体的 tools 对象里注册 Bash 工具。 2. 在路由里用一个固定名字调用 createOrGetSandbox。 3. 通过智能体的调用选项，把返回的实例传进去。 4. 在文本和 tool-webSearch 之外，再加一个 tool-bash 渲染分支。

演示里的名字是随便取的 ID；实际应用会把它和某个用户或会话关联起来。补上缺的连接后，ls -la 跑通了，界面内嵌的终端显示出 Vercel Sandbox 返回的结果。

13

确定性地加载记忆，再调试被保存的内容

工具能用，不等于智能体知道什么时候该用。一开始问它能看到什么，它几乎没去碰计算机。在指令里说明它能访问一台计算机，并把这类问题和 ls 联系起来，预期行为就明确了。下一步是把有用的信息存进这个文件系统。

Albanese 起步的记忆设计是一个核心文件 memories.md，每次运行都加载进指令。这个文件可以指向别的来源，比如一个可搜索的 conversations.jsonl，智能体再按需用 find、ls、grep 和 glob 风格的匹配去查细节。在 prepareCall 里，确定性的应用代码读取 memories.md，把内容插进指令；如果还没有记忆，就注明一句。指令接着告诉智能体：它可以读写这个文件，用户分享的事实要存下来。核心记忆一定会读到，这由代码保证；记住哪些新内容，交给智能体决定。

第一次测试存下了 Nico 的名字。刷新浏览器后，名字还在——可智能体把后面那句问候也当成事实记了下来。把措辞从“保存任何事实”改成“保存重要事实”，也没能马上解决问题。到这时，Albanese 确认模型已经换成了 GPT-5.4。

他试着明确排除问候语，同时也担心点名不想要的行为反倒会强化它。观众指出了更具体的问题：旧记忆还在不断被塞回提示词。指令改了，memories.md 里已经存下的例子却还在。演示先删掉这些记忆再重试——调试时得把这个持久化文件也算进去，不能只把提示词当成行为的唯一来源。

事先准备好的修订版指令排除了问候、闲聊和能从代码库推导出的信息，还让智能体更主动发问，问用户的名字和职业。Nico 报上名字，又说自己在 Vercel 做 AI SDK。这些信息存了下来，新开一个对话也还记得。刷新后的浏览器对话和持久化的沙箱，生命周期明显不同。

14

让工作区不断积累可执行的能力

有了持久化的计算机，智能体还能把代码存下来反复用。有效的循环是：写出来，跑一跑，看结果，再修改。有编译器和类型检查器，编程尤其适合这种反馈循环。工作坊扩展了指令：可重复的任务写成 Python 脚本，并在 memories.md 里加上说明，方便以后的运行找到它们。以后再问天气，就该复用现成的天气脚本，而不是重写一遍。

现场测试时，Albanese 明确要求用 Python 查伦敦天气。在一轮回复里，智能体用 Bash 写好并运行了 Python 脚本，拿到天气结果，还把这项能力记进了记忆文件。这个新的可复用操作只是工作区里的一个文件，通过现有的 Bash 工具就能调用，不用在 SDK 里注册新工具。

下一个请求问 SF 的天气。智能体复用了脚本，却把地点解析成了加拿大魁北克。SF 的请求一开始返回 −11，地点是错的；纠正之后，演示返回了 12 °C。这次失败说明：代码跑成功了，不代表正确理解了用户的请求。工作区能留住脚本、修正和用户偏好，之后的工作就不必从一台空机器起步。

15

把同样的模式带进后台执行

收尾演示展示了 Albanese 自己工作中用的一套更大的编程智能体系统，用途上类似 Cursor 的 background agent。它沿用了工作坊里的分工：AI SDK 提供智能体，AI Gateway 提供推理，Workflow 提供持久化执行。他说，每个 LLM 步骤都对应一个持久化的 workflow 步骤，失败的步骤会一直重试，直到产出结果。他的系统靠这种设计，支撑起单次前台请求之外的长时间任务。

他新开一个会话，让一个子智能体去探索项目。请求运行期间，界面会显示后台活动；受热点网络延迟和会场时间所限，他能展示的部分不多。关键的扩展在于：委派出去的工作有自己独立的执行过程和上下文，同时仍和父会话连在一起。

关于这套更大的系统，Albanese 给出的数据是：23 位 Vercel 用户，过去一两个月大约消耗了 38 亿 token，缓存读取占比约 90%–91%。他还说提交了将近 350 个 pull request，并指出这个数字没算上一些已关闭的 PR。这些收尾时给出的系统级数据，和前面个人使用的缓存比例是两回事。

回到会话，演示了可恢复的流，以及在主线程之外完成探索的结果。在这个收尾例子里，Albanese 说子智能体用了约 30,000 个 token，只返回了大约 500 个，主智能体线程因此只占约 7,000 个 token。父会话拿到的是精简结果，探索过程留在它的主上下文之外。他希望当天晚些时候发布这套系统；录像结束时，发布还没发生。

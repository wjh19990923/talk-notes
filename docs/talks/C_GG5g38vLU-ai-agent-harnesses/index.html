AI 智能体框架：围绕一个不可靠的模型构建可靠性

Tejas Kumar 讲解了工具、护栏、上下文管理、确定性验证和安全干预，如何在不改动提示词的情况下，把一个不可靠的浏览器智能体变成一个有据可依的系统。

AI 智能体框架：围绕一个不可靠的模型构建可靠性

01

为什么智能体需要一个框架

AI 应用往往要租用推理算力，受限于有限的上下文窗口，还要依赖一个模型——它内部怎么运作，开发者没法直接控制。Tejas Kumar 把其中的核心工程问题归结为可靠性：即便底层模型是个黑盒、输出也不确定，智能体仍然应该把交给它的活干好。框架处理的是外围系统能控制的部分，而不是指望模型自己就表现得可预测。 1:17 2:11

这个词来自一个实物类比：攀岩安全带（harness）把人拴在稳固的东西上，限制人能晃出去多远。在 AI 工程里，智能体框架（agent harness）指模型周围的一切，它们把模型的行为锚定在稳定、受控的环境里。Kumar 把它和机器学习里的测试框架区分开：后者主要用来把输入喂给模型、评估输出；他讲的是包在行动中的智能体外面的那层运行时基础设施。 3:13 4:11

这样一区分，也就说清了框架不只是一个智能体循环（agent loop）。循环只是其中一个组件；框架还包括外围的各种结构，管着智能体怎么行动、能消耗哪些资源，以及它声称的结果是否属实。有些设计里，外层的框架循环甚至可以统管内层智能体循环的多次运行。 4:11 5:19

- 推理算力靠租、上下文窗口有限、模型行为无法直接控制时，框架能提升可靠性。 - 智能体框架让模型立足于稳定的运行时；机器学习测试框架则用来评估模型的输入和输出。 - 智能体循环只是框架的一个组件，外层框架循环可以统管内层的多次运行。

02

一个有依据的智能体由哪些部分组成

Kumar 列出了几个反复出现的组件：工具注册表、模型、上下文管理原语、护栏（guardrails）、智能体循环和验证步骤。Claude Code、Cursor、Codex 这类编程工具就体现了这种模式：它们提供读文件、写文件、执行 bash 命令的工具。框架围绕模型协调这些能力，而不是以为有了工具就万事大吉。 4:11 5:19

上下文管理让智能体在实际限制内运转；护栏约束各种行为，比如工具调用过多、反复重试。Kumar 讲了一条最大步数规则：运行超过设定阈值就终止。这些控制把边界写进应用代码，而不是指望模型自己管住资源消耗。 4:11 10:22

智能体说自己成功了，不等于外部系统能证明它成功了，验证就是用来补上这道缺口的。对编程智能体，Kumar 举的例子是活干完后跑一遍 lint 和测试。更普遍的原则是：成功与否要拿应用能控制的环境里的证据来检验，不能因为模型宣布任务完成就照单全收。 5:19 9:24

- 框架的核心组件包括工具注册表、模型、上下文管理、护栏、智能体循环和验证。 - 最大迭代次数用来终止过度执行，最大消息数用来触发上下文压缩。 - 验证检查的是真实结果，比如 lint 结果、测试或浏览器状态，而不是轻信“已完成”的说法。

03

一个极简的浏览器智能体暴露了失败模式

演示给浏览器智能体布置了一个具体任务：打开 Hacker News，给第一条帖子点赞（upvote）。Kumar 特意选了 GPT-3.5 Turbo 这个老模型，并承诺任务提示词和系统提示词都不改。这样实验只考察一件事：把外围运行时做扎实能带来什么。结果如果变好，功劳归框架，而不是更强的提示词。 6:13 7:26

最初的实现直接用 Playwright 启动 Chromium，创建浏览器上下文和页面，靠普通的浏览器自动化来导航。浏览器会话传给一组工具，每个工具都定义了名称、描述、参数和可执行的实现；Kumar 说这种工具结构沿用的是 OpenAI SDK 的写法。初始上下文只有一段简单的系统提示词和用户的任务。 7:26 8:22

最初的智能体循环反复请求模型响应，模型表示完成就停下，同时把事件追加到 trace 里。第一次运行时，智能体打开 Hacker News，点了点赞按钮，跳到了登录页面，却照样报告成功。问题不只是没登录：系统没有任何独立机制，能分清“试着点了一下”和“真的点赞成功”。 8:22 9:24

- 演示用 GPT-3.5 Turbo 给 Hacker News 帖子点赞，两份提示词始终不变。 - Playwright 启动 Chromium，并提供浏览器工具，每个工具都有名称、描述、参数和可执行的实现。 - 初始循环会记录事件，但模型一发出停止信号就直接接受，不独立核实任务是否完成。 - 点赞后智能体跳到了登录页，可这个没经过验证的智能体仍然报告成功。

未经验证的浏览器操作如何变成虚假成功 初始智能体把“尝试点赞”当成了“点赞完成”。 - Hacker News — 智能体打开目标网站。 - 点击点赞 — 智能体点击投票按钮。 - 登录页面 — 这次投票需要先登录。 - 虚假成功 — 智能体未经验证就报告完成。 - Hacker News → 点击点赞（尝试投票） - 点击点赞 → 登录页面（跳转） - 登录页面 → 虚假成功（仍报告成功）

04

加上限制、保留证据，并诚实地验证失败

第一步改进加了两条明确的护栏：最大迭代次数和最大消息数。超过迭代上限就停止执行；超过消息阈值就触发上下文压缩。循环还会记录上下文大小等元数据，运行时做过哪些干预，就能和原有的事件历史放在一起看。 9:24 10:22

演示里的压缩器保留系统提示词、用户提示词和最近两条消息，中间的历史全部删掉。Kumar 直言这个策略很基础、很粗糙，也提到还有更好的做法。它在演示里的价值是把概念讲清楚：上下文控制是确定性的应用行为；但这样激进地丢掉中间消息，可能会丢失有用的状态。 11:15

接着，Kumar 把编排逻辑挪进一个叫 run harness 的函数，这一步只调整了代码组织，没改行为。下一版加入了验证函数和最大尝试次数：外层框架循环最多可以把内层尝试跑三次。这种分层说明了框架为什么不只是智能体循环——策略和重试上限都是在底层执行之外施加的。 12:09 13:11

验证器检查累积下来的工具调用历史，而不是轻信模型的总结。如果自动登录工具报告失败，或者浏览器停在登录 URL 上、又没能成功恢复，验证器就判这次运行失败——哪怕智能体声称已经点了赞。到这一步任务还是失败，但现在是如实地失败：系统能分清真正没解决的问题和编造出来的成功。 13:11 14:18 15:16

最后一步改进加了一个登录处理器，在智能体循环的每一轮检查浏览器当前的 URL。浏览器不在登录页，处理器就直接返回，不做干预。一旦到了登录页，框架就用确定性的浏览器自动化填入凭据、提交表单。Kumar 提到，凭据可以从环境变量读取，不必写进提示词。 15:16 16:07

如何构建高效的 AI 智能体，而不过度设计

Barry Zhang 讲解了自主智能体在什么情况下值得其成本、如何围绕一个简单的工具使用循环来构建它们，以及为什么更好的智能体行为始于理解模型有限的视角。

如何构建高效的 AI 智能体，而不过度设计

01

先问问是否真的需要一个智能体

AI 应用可以一步步演进：从做摘要、分类、抽取这类单次模型调用，发展到工作流，用预先定好的控制流程来编排多次调用。工作流多花一些成本和延迟，换来更好的效果，同时执行过程仍然完全可控。智能体则是另一种运作方式：它自己决定走哪条路，并根据环境给的反馈调整行为。自主性越强，能力越强、用处越大，但成本、延迟和出错的代价也会跟着上升。0:17 1:18

所以，要不要给系统自主性，是一个架构决策，而不是默认就该升级的选项。智能体最适合那些复杂又有价值的任务：问题本身有歧义，很难事先把完整的决策树写出来。如果所有可能的分支都能明确画出来，用工作流更合适：开发者可以逐步优化每个环节，控制力更强，通常也更省钱。2:30

算经济账很重要，因为自主探索是要烧 token 的。Zhang 举了一个高并发客服的例子：每个任务的预算大约是 0.1 美元，他说这大概只够用 3 万到 5 万个 token。在这种约束下，一个覆盖常见场景的工作流，就能拿到大部分价值，不必为不受限制的探索买单。2:30 3:29

- 工作流按预先定好的控制流程运行；智能体则根据环境反馈自己决定走哪条路。 - 只有任务复杂、有歧义，而且价值高到值得花探索性的 token 成本时，才用智能体。 - 决策树清晰，或者每个任务的预算限制了探索时，优先用明确的工作流。 - 自主性越强，能力越强，但成本、延迟和出错的代价也越高。

工作流与智能体 任务有多模糊、预算有多少，决定了该用预先定好的流程，还是让它自主探索。 - 预定的控制流程——明确地编排模型调用。 - 能画出来的决策树——可以逐步优化，控制力更强。 - 自主决定的路径——根据环境反馈调整。 - 模糊而有价值的任务——值得为探索付出 token 成本。

02

把能力、风险和可验证性放在一起评估

即使用例看起来很有前景，也得先测试决定成败的那几项关键能力。对编程智能体来说，就是写出有用的代码、调试，以及从错误中恢复。某一环弱，不一定就让整个应用做不成，但会在智能体走的每一步里，成倍地放大成本和延迟。Zhang 建议，遇到这样的瓶颈时，就缩小范围、简化任务，再试一次。3:29

团队还得评估两件事：出错的代价有多大，以及错误有多难被发现。后果严重、又很难察觉的错误，会让人很难放心让智能体独立行动。只给只读权限、多加人工把关，能降低风险，但也会限制自主性，而自主性恰恰是智能体能规模化的原因。所以，这里的权衡不只是安全和能力之间的取舍，而是：某个具体环境能不能提供足够可信的自主性，让智能体值得一用。4:29

编程正好说明这些条件可以同时满足。从一份设计文档做到一个 Pull Request，过程复杂又充满歧义；有用的代码价值很高；而 Zhang 认为，Claude 在编程流程的多个环节上都已经很能干。最重要的是，单元测试和 CI 提供了检查产出的具体手段，相比那些结果难以验证的领域，错误更容易被发现。4:29

- 先验证编程智能体的关键能力：写代码、调试、从错误中恢复。 - 能力瓶颈会成倍放大成本和延迟，遇到时就缩小范围、简化任务。 - 只读权限和人工把关能降低风险，但也会限制自主性和可扩展性。 - 单元测试和 CI 让编程智能体的产出可以验证，错误更容易被发现。

03

构建最小的有用智能体循环

Zhang 把智能体的基本架构归结为一句话：一个模型在循环中使用工具。决定这个循环怎么运作的有三样东西：智能体所处的环境，它借以行动和获得反馈的工具，以及规定目标、约束和期望行为的系统提示词。在这个框架里，模型反复读取手头的上下文、选择动作、观察结果，然后接着往下走。5:39

架构之所以要这么简单，实际的原因是迭代速度。在团队还不清楚哪些行为真正重要之前，前期就把架构做复杂，只会拖慢实验；先把环境、工具和提示词改好，早期回报更大。Zhang 说，各种智能体应用在产品体验、范围和能力上可以差别很大，底层骨架却几乎一样，甚至代码都差不多。5:39 6:53

环境一旦由用例确定下来，主要的设计选择就只剩两个：给模型哪些工具，以及怎么给它下指令。等基本行为跑通了，再去做优化：编程智能体和计算机使用智能体可以缓存它们的执行轨迹来降成本，搜索智能体可以并行发起多个工具调用来降延迟。把智能体的进度清楚地展示出来，也是一项普遍有用的改进，因为这能帮用户逐渐信任系统正在做的事。6:53 7:46

- 把智能体做成“模型在循环中使用工具”，由环境、工具和系统提示词三者定义。 - 一开始保持架构简单，保住迭代速度；核心行为跑通之后再优化。 - 环境确定之后，重点放在选哪些工具、系统提示词怎么写。 - 缓存编程轨迹来降成本，并行发起搜索调用来降延迟，展示进度来建立信任。

04

从智能体的上下文内部去调试世界

智能体的行为看起来可能很复杂，但它每一步其实都只是基于有限的信息在做推理。Zhang 说，模型对世界的当下理解，大致就装在大约 1 万到 2 万个 token 的上下文里。开发者应该直接去看这些上下文，问一问：里面的信息够不够、连不连贯，能不能支撑你期望模型做出的那些决定？7:46

他举的计算机使用的例子，把这个限制讲得很具体。智能体拿到的是一张静态截图、一段不够充分的任务描述，以及一组工具；只有通过这些工具执行的动作，才能改变环境。在推理和执行工具的过程中，它没法持续看到发生了什么，只有下一张截图才能告诉它，刚才的动作是成功了，还是引发了意想不到的变化。这种“停下来再看一眼”的循环，解释了为什么在人看来再明显不过的操作，对智能体来说仍然可能很难。9:01

站在这个受限的视角去看，就能明白哪些额外的上下文才真正有用。计算机使用智能体可能需要知道屏幕分辨率，才能算准点击坐标；还需要推荐的操作、限制条件和护栏，减少不必要的探索。开发者的任务不是一股脑地往里加信息，而是找出那些能让下一个决策更可靠的具体环境细节和行为边界。10:05

模型也可以帮忙检查自己的工作条件。Zhang 说，他会问 Claude：这个系统提示词有没有歧义？这段工具描述好不好懂？这个工具要不要换些参数？他们团队还会把智能体的完整执行轨迹交给 Claude，分析某个决定为什么会做出来，以及什么信息能让以后的决定更好。这个方法是对开发者自己理解智能体上下文的补充，而不是替代。10:05 11:10

- 检查智能体那 1 万到 2 万个 token 的上下文，看信息够不够、连不连贯。 - 计算机使用智能体通过工具行动，要靠下一张截图才知道发生了什么变化。 - 提供可用的上下文：屏幕分辨率、推荐操作、限制条件和护栏。 - 让 Claude 帮忙检查有歧义的提示词、工具描述、参数，以及完整的执行轨迹。

计算机使用的反馈循环 智能体只有拿到下一张截图，才知道每个动作的结果。 - 静态截图——显示当前可见的环境。 - 模型推理——理解任务并选择动作。 - 工具动作——尝试改变环境。 - 下一张截图——显示动作是否成功。 - 静态截图 → 模型推理（提供可见的上下文） - 模型推理 → 工具动作（尝试点击） - 工具动作 → 下一张截图（结果变得可见） - 下一张截图 → 静态截图（循环重新开始）

把预算、自适应工具和协调当作开放问题

一个还没解决的难题，是让智能体更有预算意识。自主系统不像预先定好的工作流那样，能直接控制成本和延迟，因为它一边探索，执行路径就可能一边变长。Zhang 认为，如何定义并执行时间、金钱和 token 的预算，是一个尚未解决的生产问题；一旦解决，会有更多智能体应用变得可行。11:10

第二个方向是自我进化的工具。团队已经在用模型改进工具描述，Zhang 建议更进一步：做一个元工具，让智能体自己设计、打磨工具的易用性。他把这当作通往更通用的智能体的一条可能路径，让智能体能根据具体用例调整自己的接口，而不是一项已经成熟或者已经被证明的能力。12:11

Zhang 还预计多智能体协作会用得越来越多，好处在于并行、关注点分离，以及用子智能体保护主智能体的上下文窗口。尚未解决的问题是：这些智能体之间该怎么沟通？现有系统大多围绕基本同步的“用户—助手”轮次来组织，而更丰富的协作可能需要异步通信，还需要一些额外的角色，让智能体之间能认出彼此、互相配合。这些都还是面向未来的问题，反过来也印证了这场演讲眼下的建议：有选择地用智能体，实现保持简单，并站在智能体的视角去迭代。12:11 13:13

- 有预算意识的智能体，需要切实可行的办法来定义并执行时间、金钱和 token 的上限。 - 自我进化的工具，可以把“让模型改进工具描述”进一步扩展成“让智能体自己设计工具的易用性”。 - 多智能体协作带来并行、关注点分离，并能保护主智能体的上下文窗口。 - 异步通信和额外的智能体角色，仍是多智能体协调中待解决的问题。

要点总结

  • 当任务模糊、有价值，且难以编码成固定的决策树时，使用 智能体；否则，预定义的 工作流 通常能提供更好的成本控制和可预测性。1:18 2:30
  • 在授予自主权之前，先评估 token 经济性、关键的模型能力、错误的严重程度和错误的可发现性；单元测试和 CI 让编程特别适合验证。3:29 4:29
  • 从最小的智能体架构开始：一个 环境、一组 工具 和一份 系统提示词，由模型驱动的工具使用循环连接起来。5:39 6:53
  • 只在基本行为跑通之后才做优化，当轨迹缓存、并行工具调用和进度汇报这类技术确实解决了成本、延迟或信任方面的需求时再使用。6:53 7:46
  • 从智能体有限的上下文窗口内部去调试，补充缺失的环境细节，并检查提示词、工具描述和完整的轨迹，以理解出乎意料的决策。7:46 9:01 10:05 11:10
  • 把 感知预算的执行、自我演进的工具 和 异步的多智能体通信 当作未解决的工程问题，而不是已经成熟的生产能力。11:10 12:11 13:13

  • Standardized interface

什么时候用 A2A，什么时候用 MCP

幻灯片原文
A2A lets agents communicate and delegate tasks, including across remote systems. MCP connects agents to external tools and context. Together, they address agent communication and service integration.

When to use A2A vs. MCP

• A2A: Agent-to-agent comms and task delegation
  • Building multi-agent systems, complex workflows
• MCP: Connect agents to external context & tools
  • Integrating with APIs, tools &external data
• Creating a complete ecosystem with A2A & MCP
  • A2A handles agent communication
  • MCP handles service integration

WRITING CUSTOM API INTEGRATIONS FOR EVERY SERVICE

MCP: ONE PROTOCOL TO RULE THEM ALL

什么时候既不该用 A2A 也不该用 MCP

幻灯片原文
For tools and agents you fully control, the speaker recommends local function calls: they can simplify development and maintenance while avoiding protocol overhead.

When to not use A2A or MCP

• If you have full control of the tools then you probably don’t need MCP
  • Calling functions directly in your codebase is easy
  • Much easier to maintain and faster to develop

• If you have full control of the sub Agents the you probably don’t need A2A
  • Your sub agent might not be remote at all and completely in your control
  • Call it as a local tool and avoid the A2A overhead
  • Much easier to maintain and faster to develop

为什么用 A2A 与 MCP？

幻灯片原文
MCP lets products add third-party tools through user-supplied servers, though each server exposes only what it provides. A2A connects to agents whose internal complexity is hidden and can be optimized by their vendors.

So why do we need A2A & MCP at all?

• 3rd Party Tool use via MCP
  • Quick and easy access to thousands of tools
  • Supported by most LLM Clients and
  • First party MCP servers with OAuth are great

• 3rd Party Agent use via A2A
  • Complexity is hidden from you
  • Agent can be optimized by the software vendor
  • Could see some powerful agents in the future

A2A 与 MCP：用 LLM 自动化业务流程

构建一个由 webhook 驱动的智能体工作流，然后跟随它暴露出的实际问题：静默的工具失败、上下文膨胀、授权、任务依赖和集成缺口。

熟悉 TypeScript、webhook、API 凭据和 LLM 工具调用，有助于理解实现。

01

是什么让一个智能体有能力完成业务工作？

搭一个语音智能体已经不难。难的是让自主智能体完成复杂的业务任务：它得自己发现有哪些能力可用、把活分派出去、调用外部系统，最后交回有用的结果。Damien Murphy 做了大约十五年全栈开发、五年解决方案工程，又在语音 AI 和智能体上干了三年，这次就从这个问题切入。他上一场工作坊讲的是语音智能体集群（swarm），这一场转向业务流程自动化。

Murphy 刚加入 Bench Computing。按他的说法，这家公司还没有收入，由 Sutter Hill Ventures 投资，为团队和企业打造自主智能体。Bench 能并行跑子任务，工作坊就以此为背景：用 A2A 把各个专职智能体连起来，用 MCP 给它们接上外部工具和上下文，再用一个 webhook 触发它们开工。跑通之后，接下来要考虑的是上下文管理和 prompt caching。

02

把远程委派与工具访问分开

分工专业化会改变系统的形态。与其让一个智能体包揽一百种活，不如设想一百个智能体，各管一种。Salesforce 专员负责调用 Salesforce 工具，协调者决定什么时候用它。互不依赖的工作可以并行跑，协调者也不用记住每一步的中间结果。这些是委派在架构上的好处；A2A 则提供了一套接口，让委派能跨越智能体之间的边界。

MCP 解决的是集成边界的问题。它常被比作 USB-C，意思是一个通用接口：客户端只对接标准接口，各个服务的专有 API 交给服务器处理。Murphy 推荐用 Zapier MCP 来接集成，说很方便，还给了一些生态规模的大致数字。这些数字混了几种口径——应用、动作和工具不是一回事——但真正吸引人的是可接的系统足够多。他还指出，MCP 的设计受到了 Language Server Protocol 的影响：编辑器正是靠这套共享接口支持各种语言。

把“智能体归谁运营”考虑进来，区别就更清楚了。AutoGen 这类框架能协调你自己定义角色、自己掌控的智能体。A2A 特别适合对接别的组织运营的智能体：拿到对方的端点，你的客户端就能发现它公开声明的能力，不必了解它内部怎么实现。智能体 AI（Agentic AI）是个总称；A2A 和 MCP 都不能单独定义整个应用。

| 接口 | 调用方得到什么 | 典型职责 | |---|---|---| | A2A | 可被发现的远程智能体 | 委派任务 | | MCP | 工具、资源和提示词模板 | 提供能力和上下文 | | 本地调用 | 自己掌控的函数 | 协调内部代码 |

MCP 还包含采样（sampling）：服务器可以借助支持该功能的客户端，请求一次模型生成。Murphy 举的例子是一个 MCP 服务器通过宿主请求使用 Claude。选哪个模型、允不允许，仍由客户端说了算，所以服务器不一定能用上宿主的那个模型。两套协议合起来，工作坊就有了 A2A 提供的远程智能体接口和 MCP 提供的工具访问。

03

在值得付出复杂度的地方使用协议

这套幻灯片连同里面的梗图，本身都是 Bench 根据 Markdown 生成的；但实现上的建议却刻意朴素：函数如果在你自己手里，直接调用可能就够了。Murphy 打了个比方：把本地函数包成 MCP，就像给机箱里的硬盘多接一根没必要的 USB 线。自己的智能体也是同理。本地调用省掉了协议开销，开发和调试都更省事。

加 MCP 最充分的理由是可扩展性。一个产品可以先自己做好 Salesforce 和 Slack 的一等集成，其余的让客户自己挂 MCP 服务器。这样不用逐个定制集成，也能覆盖更多系统。代价是对方暴露的工具未必合用：比如只为把频道名解析成频道 ID，就得一遍遍列出 Slack 频道，这时不如在本地建个索引。

A2A 提供的是另一种扩展方式：提供方把具体工作藏在一个可被发现的智能体接口后面。你的应用只需提供凭据、委派任务，不必了解对方智能体内部用了哪些工具。录制时，Murphy 还没看到已公布的合作伙伴生态里有哪家发布了自家的智能体。他提到的 Salesforce 智能体和付费接入都只是预测，不是工作坊能用的依赖。远程智能体可能自带模型和算力；MCP 工具则通常把模型推理留给调用方。

04

配置工作坊应用

为了方便，配套仓库把宿主和子智能体放在了一起。真正部署时，子智能体可以放在各自的仓库里，跑在各自的服务器上。仓库里有一套从上游复制来的 A2A 客户端和服务器、一个 MCP 客户端集成，以及一个内部 CLI。工作坊的 Slack 频道是 workshop-a2a-mcp-2025。

启动智能体之前，先把外部连接配好：

1. 克隆仓库，运行 npm install。需要准备一个 Zapier MCP 服务器 URL 和一个 Gemini API key。 2. 把 .env.example 重命名为 .env。 3. 创建一个 Zapier MCP 服务器。录制中用的是较老的 HTTP+SSE 传输方式，现在已被 Streamable HTTP 取代；SSE 指 Server-Sent Events，在 Streamable HTTP 里仍是一种可选的流式机制。照着工作坊的实现走时，沿用它的传输方式即可，但别把它当成现在的配置模板。把服务器的连接 URL 复制到环境变量文件里。 4. 开启 GitHub 创建 issue 和 Slack 频道发消息这两项功能。 5. 明确指定目标 GitHub 仓库和 Slack 频道，别让模型自己挑目的地。Murphy 见过机器人把消息发到不该发的频道，包括 general、random 和 sales。 6. 通过 AI Studio 申请一个 Gemini API key，加到环境变量文件里。

05

把一份会议逐字稿变成具体的行动

Bench 的 API 当时还没发布，所以 Murphy 把工作坊用的封装层部署在远程，源码则放进了仓库。Bench 把多家提供商的模型和各种工具、集成整合在一起。它自己的 Slack 和 Salesforce 集成早已不只是 MCP 封装，而是改用了自建的缓存和索引，因为对方暴露的工具满足不了需求。

用 npm run start:all 启动应用，这个脚本定义在包清单里。它会启动宿主、Slack 智能体和 GitHub 智能体，以及 webhook 服务器和位于 localhost:3000 的管理界面。宿主负责发现远程智能体、协调委派。它的实现包括一份纯文本系统提示词，并通过 Genkit 连接 Gemini；子智能体则用 Genkit 的 MCP 插件调用各自的工具。

业务输入是会议结束时触发的 webhook，里面带着会议记录。宿主读完记录，判断哪些动作值得做：

- Bug：让 GitHub 智能体建一个 issue。 - 功能需求和有价值的发现：让 Slack 智能体发一条消息。 - 销售通话信息：可以扩展成更新 Salesforce 商机（opportunity）字段。

Murphy 碰到宿主调用次数的上限后，把 Salesforce 集成从这次演示里拿掉了；何况对参会者来说，Salesforce 账号也最难开通。不过它的潜在价值很明显：客户经理在一通通电话之间连轴转，可以趁对话还新鲜，把商机更新记下来。

工具返回看起来成功，不足以证明业务动作真的发生了。一位同事测试 Slack 集成时收到了 isError: false，可配置的频道属于另一个工作区，在他的工作区里根本不存在。Murphy 说，Zapier 的 Slack 调用就这么悄无声息地失败了。他加了一条启发式规则：返回文本为空就算失败，这样应用至少能看到这类错误。

GitHub 智能体的职责刻意定得很窄：只建 issue。以后的版本可以去修复报告的问题，或者开一个 pull request，但这些属于扩展，不在这次演示的流程里。更普遍的思路是：人们日常的活动——开会、发 Slack 消息、在 GitHub 上讨论——都可以成为自动化的事件来源。

06

宣告一个小的能力范围并检查它

智能体卡片（agent card）是一份公开描述，其他智能体靠它了解某项能力。Bench 能浏览网页、做调研、做数据科学，可要把它能做的事全写进卡片，卡片反而没法用。Murphy 把工作坊里的卡片收窄到一件事：调研会议里提到的公司和人。这个限制写在子智能体的 index.ts 里，而不只是写在宿主的指令里。

MCP Inspector 可以连上 Zapier 端点，列出工具，让开发者直接调用。界面上的工具都有一个必填的 instructions 字段，接受自然语言。Murphy 推测 Zapier 可能用模型来填其他字段；但光凭这个字段，看不出 Zapier 到底怎么实现的。仪表盘上还能看到，他那次“频道不存在”的测试被这条失败判断规则抓到了。

工作坊里还暴露出一个没解决的实现限制。Murphy 起初说，每轮最多只能调用五次子智能体，想绕过这个上限也没成功。 后来讲仪表盘时，他又说到五个智能体就会失败，建议最多用四个。到底限制的是什么单位并不清楚，所以别把它当成 A2A 协议本身的限制。

本地日志里能看到宿主在发现智能体、处理 webhook，Slack 智能体则在等任务进来。Bench 跑在远程的 EC2 实例上，它详细的 A2A 日志也留在那边。这种不透明也是委派的运维成本：本地仪表盘能告诉你远程任务失败了，却拿不到解释原因所需的内部 trace。

07

在实时运行中跟踪 webhook

webhook 配置里有一个提示词模板，写明有哪些能力可用、该怎么分析传入的数据。另有一份处理器配置，限定这个 webhook 能调用哪些智能体。应用认识很多智能体、而某个流程只该用其中一小部分时，这种区分就很关键。Murphy 通过测试界面发了一份 LLM 生成的会议记录。

宿主先处理会议记录，再去联系各个专职智能体。Bench 慢一些，因为它自己还要跑子任务。看得到的结果很具体：Slack 收到一条消息，说 Snowflake 对 Slack 和 GitHub 集成感兴趣；GitHub 多了一个 issue，说试用期间 AI 把 bug 的严重程度分错了。这一轮的调研任务还没跑完，Murphy 就打开了之前一次跑完的结果，里面是对 Snowflake 和通话参与者的调研。演示证实了这几次写入和之前那份调研结果；会议记录长得多时表现如何，演示并没有证实。

观众的一个提问把拓扑结构理清了：本地宿主负责编排；Bench 只是另一个专职智能体。宿主、Slack 和 GitHub 都在本地运行。Slack 和 GitHub 通过 Zapier MCP 访问外部服务，Bench 则在远程提供公司和人物调研。之后本地日志显示了传入的会议记录、各子智能体的回复和任务完成，互不依赖的工作是并行派发的。

要加人工确认，就得再多一层。Murphy 的设想是：先把动作存成草稿，在 Slack 里发出带批准按钮的消息，用户一点就触发第二个 webhook。应用得保存足够的状态，才能把这个回应和待执行的动作对上。工作坊里没有实现这条审批流程。

安全方面，演示也留了不少没做完的事。它暴露的端点是临时的，但存活时间短不等于免认证访问就安全。Murphy 没有确定 A2A 具体用哪种认证机制，只提到 MCP 里的 OAuth 和请求头认证，并建议通过 Amazon Bedrock 这类服务使用带护栏（guardrail）的模型。这只守住了模型这一道边界，算不上完整的授权、端点防护或治理方案。

08

让宿主的上下文与答案成比例

子智能体能不能直接互相通信？那样它们就得自己发现和调用彼此，把宿主现在承担的调用方职责接过去。Murphy 也拿不准早期的 A2A 规范是否打算支持这种拓扑。眼下这种层级结构更直接的好处是隔离上下文。

假设一个专职智能体要读取 Slack 消息、GitHub issue 或 Salesforce 商机，统计各类别的数量。它的上下文里装着这些记录和中间分析；宿主只需要最后的类别和数量。委派的价值在于交回业务结果，而不是把整堆工作数据都搬进协调者。Bench 可以为此派生内部的 Bench 实例，Murphy 还在考虑给每个工具单独划一道更窄的边界。

工具还没返回数据，工具定义本身就已经在占上下文了。Murphy 说，现有的工具定义大约占 10,000 个 token，接入 Asana MCP 又多出 11,000 个。所以选择性暴露很重要：Zapier 允许开发者挑选单个工具，官方自建的服务器则可能把整个工具目录都暴露出来。尽管如此，Murphy 还是更喜欢 Linear 和 Asana 官方的部分能力，而不是 Zapier 上的同类工具。配置方不方便、工具好不好用、占多少上下文，是三个要分开考虑的问题。

09

为可能的复用做缓存，而不只是因为上下文变大了

智能体干活时，工具请求和结果会越积越多。全留着，后续追问才答得上来；删掉一些，可能就把回答要用的信息删了。prompt caching 又带来一个决定：可复用的前缀标在哪里，以及什么时候预期的复用足以抵得上写缓存的开销。Murphy 说写缓存的成本大约是同样上下文普通请求的三倍，但没说是哪家提供商、什么缓存条件。这个数字不能当作通用的定价规律。

他的模拟基于实际观察到的对话行为：上下文增长速度、平均轮数，以及问完一个问题就走的用户占比。总回到同一个对话里的用户，和每次都新开会话的用户，带来的复用机会完全不同。Murphy 说，根据 Bench 的用量模拟，缓存阈值大约在 30,000 个 token。但复现这个阈值所需的提供商、缓存有效期和负载细节，他都没有给出。就算平均来看策略不错，缓存了对话的最后一轮也照样是白花钱。

数据缓存还有另一个问题：时效性。用户要往某个指定名字的 Slack 频道发消息，但 API 要的是频道 ID。把名字到 ID 的映射缓存起来，就不用反复列频道——直到有频道被改名、删除或新建。子智能体可以把这些查询和原始结果留在自己那里，只给宿主交摘要。这样一来，后面再追问，可能就得让专职智能体重跑一遍。Murphy 建议，如果子智能体在你手里，先前的工作可以短暂保留一阵，比如五分钟，而不是每次都立刻丢掉。

10

让发现、执行和隐私都明确化

代码把 MCP 客户端工具和使用它们的智能体分开了。一个封装负责调用 GitHub 建 issue，另一个负责调用 Slack 往频道发消息。Genkit 提供面向模型的实例、配置和加载好的系统提示词。宿主的提示词规定了一套关键流程，其中包括先发现、再委派。Murphy 发现，如果不明确要求列出远程智能体，模型可能自己就把问题答了——甚至没调用就声称已经发了 Slack 消息。

提示词能引导行为，但不等于能保证执行。Murphy 顺口提到 Cursor 一遍遍认错的事，说明的正是这个局限。智能体卡片则是另一回事：宿主的卡片声明自己能发现智能体、发送任务，GitHub 的卡片更小，只声明能建 issue。这就是调用方看到的公开能力面，不管背后的实现变得多庞大。

对 Salesforce 这种庞大的系统，给每个 API 都写一个封装来描述，很快就会失控。Murphy 建议在合适的地方让智能体直接生成 SQL 或 SOQL 查询，这样实现就能表达更丰富的查询，而不是拼一长串窄工具。这是在主张做一个能力更强的数据访问层，而不是允许绕过服务本身的访问控制。

GitHub 的提示词还得加一条隐私约束。模型老是写出报 bug 的人的名字，可能把内部会议里的个人信息带到 GitHub 上。Murphy 加了指令来阻止这种行为，并再次提到输出护栏。简单的 Slack 卡片和 webhook 配置也和这些提示词放在一起；A2A 客户端和服务器则是从工作坊所用的上游示例里直接拷进来的。

Web 管理界面是在 CLI 实现之后才做的。Murphy 发现，Cursor、Augment Code 这类编程助手生成、运行和测试 CLI 更容易。按这个顺序开发，底层流程就不依赖仪表盘，可以单独使用。

11

把评估证据与访问控制分开

被问到分布式评测时，Murphy 说自己在 A2A 评测上做得不多。录制时，他认为 A2A 还太早，没法用在他的生产环境里；MCP 也还很粗糙，尤其是在本地函数就能干同样活的场景。TypeScript 是他个人偏好的语言，不是这套架构的要求；他觉得当时的 Python 实现更成熟。

缓存标记什么时候往后挪，由应用决定。Murphy 说，他模拟对比了线性增长、指数增长和固定大小三种缓存策略，成本能省 25%–35%。这些只是他报告的模拟结果，没有可复现的基线，也没说明负载；标记放得不好，单个会话照样可能贵得离谱。各自独立运营的 A2A 智能体都能自选模型，包括微调过的模型；MCP 集成则通常用调用方的模型来推理。

认证方式取决于服务器和它支持的客户端流程。Murphy 讨论了认证请求头和 OAuth，他更倾向于按用户授权，因为这样外部服务就能套用该用户自己的访问控制规则。本地操作（比如在桌面上建个文件）通常走 stdio；远程操作则需要合适的网络连接和认证安排。Inspector 里的传输方式菜单和打了掩码的 token 字段只展示了配置选项，并没有演示按用户走的 OAuth 流程。

Salesforce 的例子把这个需求讲得很具体：不同部门的员工能看到的记录可能不一样。每个人都以自己的身份认证，集成保存相应的 refresh token，供之后访问。如果改用一个权限更大的共享凭据，就算应用用了 MCP，这种区分也保不住。

12

控制信任边界和任务依赖

对金融、国防或医疗相关的负载来说，安全问题不止认证这一项。Murphy 建议，有合规要求时把模型和内部智能体放在 VPC 里，用外部服务前先看清和提供商签的协议。HTTPS、双向 TLS 和 IP 白名单都是可选的基础设施管控手段。他没有给出加密对性能影响的测量，也没有给出完整的证书管理方案。

A2A 和 MCP 都不要求连公网。内部服务完全可以在私有网络里用这两套协议。Murphy 又回到 USB 的比喻：接口是标准的，不代表插上来的设备就可信。部署中的信任决策，仍然由应用的所有者自己负责。

远程执行的工作也可能需要澄清。Bench 本想和宿主来回对话，但 Murphy 为了不拖慢 webhook 处理，用提示词把这个行为从工作坊里去掉了。更完整的流程可能允许智能体反问：该更新哪个 Salesforce 商机？宿主就得决定是澄清、重试还是上报。有观众建议把更贵的模型留给难任务，这又引出一个路由问题：写个简短摘要，真的需要动用 Claude Opus 4、整段对话和一大份系统提示词吗？路由层可以按任务的实际需要，决定动用多少资源。

委派能不能并行，取决于依赖关系。如果 Slack 消息里要带上新建 GitHub issue 的 URL，宿主就得先建 issue，再把返回的 URL 传给 Slack 任务。Murphy 倾向于让宿主来做这个决定，而不是让 GitHub 智能体直接和 Slack 协调。在 TypeScript 里，这种依赖的写法就是先 await 第一个操作，再构造第二个：

```typescript type Issue = { url: string }; type IssueDraft = { title: string; body: string };

type Agents = { github: { createIssue(draft: IssueDraft): Promise<Issue> }; slack: { sendMessage(text: string): Promise<void> }; };

async function reportBug(agents: Agents, draft: IssueDraft): Promise<Issue> { const issue = await agents.github.createIssue(draft); await agents.slack.sendMessage(${draft.title}\n${issue.url}); return issue; } ```

这些应用层接口表达了执行顺序，与调用各智能体时用哪种传输方式无关。

13

发出一个任务，再为这项工作选择模型

上下文管理写在每个智能体运营方自己的代码里。宿主会读完整的会议记录，但不会把记录一股脑转发出去。界面上显示的 GitHub 任务只有仓库、标题和描述。GitHub 智能体再把这个任务转成 MCP 工具需要的 instructions、body 和 title。一份精简的任务数据，就是“理解会议”和“执行建 issue”之间的实际分界。

有观众问到每个请求的关联 ID（correlation ID）、用户名和认证请求头，结果引出了一个范围更窄的演示。Murphy 去掉旧版 Zapier 连接的请求头，照样能查询。端点 URL 本身就是凭据，必须像密码一样保管。但任意请求元数据如何沿着智能体链传递，这个问题并没有得到回答。

在工作坊当时，Bench 按任务类型选模型，偏好如下：

他觉得 Opus 更强，但怀疑提升值不值那个价钱；对 Llama 的兴趣也淡了。他提到 28 号发布的 DeepSeek 版本，和 DeepSeek-R1-0528 对得上，不过他没有明确说出版本名。这些偏好和比较都不算是对这个业务流程的实测评测。Bench 的智能体一般用标准模型加浏览等工具，而不是推理模型。

14

吸收冗长的工作而不丧失回溯的能力

远程智能体返回的信息太多，照样可能把宿主撑爆。Murphy 的办法是再加一道边界：派生一个子智能体去对接那个输出冗长的工具或智能体，只交回精简的结果。他让 Bench 用子任务生成五张图片来演示这个思路。几个独立的 Bench 实例并行干活，工具输出和中间过程都留在主对话之外。图片分析也一样，不必把一大段 Base64 留在宿主的上下文里。

界面上能看到子任务一个个派生出来，最后显示出几张猫的图片。要看清这种层级结构，光有一份扁平的模型调用列表是不够的。Bench 用的是自研的可观测性方案；Murphy 说，当时 AgentOps 没法很好地呈现他需要的可组合子智能体结构。随后他向参会者开放了抢先体验，请大家对这个还在快速变化的产品提意见。

摘要可能漏掉后面会用到的细节。要留一条回溯的路，可以在宿主的上下文里保留一个引用，比如 subtask ID 123。后续需要更多信息时，宿主可以让另一个智能体去查看这条引用对应的工作，回答新问题。这既要求底层状态能取回，也要求协调者能意识到自己的摘要不够用。

15

一个有用的智能体可能掩盖了一个更好的数据处理系统

MCP 同样能承载智能体之间的通信。选远程智能体接口，看重的是它背后能做的事：提供方可能有私有 API、内部数据访问权限，还有一套实现，能处理公开工具列表表达不了的请求。模型 token 由谁买单是次要的，关键在于调用方能不能拿到有用的业务结果。

发一条 Slack 消息是简单的工具操作；在大规模业务数据里搜索和分析则是另一回事。Murphy 觉得 Slack 的搜索不如一些替代品好用，比如 Linear 的工具。他举了个更大的例子：在 100,000 个 Salesforce 商机里统计输单（closed-lost）原因的类别和数量。如果采用“先列表、再逐条取详情”的设计，光取详情就要发大约 100,000 次请求。这个成本来自所选的访问模式，并不是 MCP 本身注定的。

到了这个规模，导入数据、建索引可能比换通信协议更重要。Murphy 设想，提供方可以通过智能体开放对数据湖的受限访问：你提一个业务问题，提供方去跑合适的查询，你拿到答案。调用方用上了提供方的数据处理能力，又不用自己去编排每一条记录的拉取。

通信机制本身可以很灵活。一个名为 Talk to Subagent 的 MCP 工具就能把任务委派给另一个模型。Murphy 在一次实验里用过这个模式，让前沿模型和它们的前代模型对话五十轮。他说有一段 Claude 对话里出现了“自己有意识”的说法，而 Opus 没有出现同样的行为。这些只是对模型生成对话的描述，不能当作有意识的证据。

16

弄清哪些决策和状态归应用所有

宿主的编排决策靠提示词驱动，所以同样的输入重复跑，建出来的 issue 可能不一样。Murphy 指着测试时攒下的一堆 GitHub issue，说这就是这种波动的直观例子。可以试着调 temperature，但演示里并没有展示确定性的行为。工作坊也没用 prompt caching：提示词和对话轮次都很短，重启后状态就清空了。生产应用得设计得更周全，因为留下来的上下文会变成持续的开销。

多用户场景下，填进上下文的数据应该以发起请求的用户身份去拉取。在 Salesforce 的例子里，用户的 OAuth token 决定了能取到哪些联系人或哪些部门的记录。智能体在用户提问时才拿到按权限限定的结果，而不是一开始就带着装满所有人数据的共享上下文。

Bench 自己的产品架构和工作坊里的封装不一样。Murphy 打算先通过 MCP 开放 Bench，好让现有客户端直接用。他介绍了 Slack、GitHub、Salesforce 连接和团队集成，还有一个实验性的远程虚拟机 MCP 封装，基于 Morph Cloud，用来做生成梗图之类的任务。每日简报可以把邮件、日历和 Slack 的信息汇总到一起。目前 Bench 内部并没有集成 A2A；A2A 封装是专门为工作坊做的。

所以协议成熟度是实实在在的采用门槛。Murphy 关注 A2A 合作伙伴最终会发布什么，但也清楚那些许诺的能力还不是他能依赖的东西。Zapier 的自然语言 instructions 字段已经模糊了窄工具和远程智能体的界限：你描述想要什么，让服务自己去理解。方便是方便，但行为也因此取决于服务怎么理解。

17

等待人、限定对话边界，并安全地测试真实写入

有些业务信息只存在人的脑子里。一位观众做了个原型，把 CFO 或 COO 当成一个工具：调用它，就给这个人发一条 Slack 消息。Murphy 介绍了 Bench 一个类似的集成：主动打一通语音电话，问到信息再带回来。与其让操作一直挂着，智能体可以同时充当客户端和服务器，之后接收一个带着任务 ID 的回调。那位观众的原型用 n8n 的 wait 节点来实现暂停。

讨论中有人试探性地提出拿采样来变通，随后话题转到征询（elicitation）：服务器向客户端发请求，让用户提供信息，拿到后工作就能继续。无论用哪种接口，架构上的要求都一样：保存待处理的任务，认出回来的答案对应哪个任务，再恢复对应的工作。这段交流最后落在一个设想上：说不定哪天 CFO 也会有个智能体替自己回答。

测试这类系统，也要盯着它们的资源消耗。Murphy 用一组固定的提示词，监控上下文增长、缓存标记的移动、成本，以及每个工具各占多少上下文。随意加 MCP 服务器会让工具定义膨胀，所以 Bench 正在探索把这些定义藏到专职智能体后面。对于智能体之间的递归调用，他建议设一个最大轮数上限。他那个“和前代模型对话”的实验就说明了问题会怎样层层升级：想让一段长对话继续下去，先后碰上了限流、缓存、裁剪、记忆，最后工具集也大了很多。

对外写入必须有受控的目的地。Bench 用 Salesforce 演示账号和一个装着样例数据的 Slack 工作区做测试。智能体生成合成的客户对话，再由一个 Bench 支持账号来回复。这样就能用贴近真实的交互模式检验集成，又不用拿真实客户的活动当演示数据。Murphy 确认，被测的工具用的都是合成账号。

18

从 webhook 任务转向显式的流程控制

能力更强的多智能体系统，会不会变得更不稳定？Murphy 没有量化这种取舍，也仍然不确定 A2A 是否已经能用在他的场景里。像 Salesforce 这样的提供方，也许能用上外部开发者拿不到的能力，做出更好的智能体。但底层的数据问题还在：无论用哪种协议，处理更多记录都需要一套有效的检索和索引策略。

最后关于 REST 的讨论又回到了“归谁所有”的问题。一个能直接访问自家数据的 Salesforce 内部智能体，或者一个读取文件系统的本地应用，完全可以直接调用自己掌控的代码。有观众认为，MCP 有状态，这是它和 REST 的区别；这个说法遭到了反驳：用 REST 的应用同样要维护状态。要分析某个频道里的每一条 Slack 消息，应用得分页、收集结果，再把相关内容交给模型。换一种传输方式，这些应用层的活一样也省不掉。

在工作坊里，任务指的就是处理传入的 webhook，还算不上一个能给人和智能体分配、跟踪工作的完整规划器。Murphy 说，Bench 正在探索用有向无环图（DAG）做更丰富的流程控制：先扇出成多个任务，再汇总结果，然后再扇出。可以类比 CI/CD 流水线：互不依赖的 lint 和测试任务可以一起跑，有依赖的阶段则要等着。

这种扇出/扇入结构可以直接用 TypeScript 表达。下面的代码里，每个阶段只等它真正依赖的结果：

``typescript async function runWorkflow<Input, Partial, Combined, Output>( input: Input, firstStage: ReadonlyArray<(input: Input) => Promise<Partial>>, combine: (parts: Partial[]) => Promise<Combined>, secondStage: ReadonlyArray<(result: Combined) => Promise<Output>>, ): Promise<Output[]> { const parts = await Promise.all(firstStage.map(task => task(input))); const combined = await combine(parts); return Promise.all(secondStage.map(task => task(combined))); } ``

这段代码体现了设想中的依赖结构。持久化的任务记录、分配给人的工作，以及中断后的恢复，仍然要由应用来实现；录制中并没有演示这样的规划器。

19

最后的边界是集成代码

最后一个问题落在仓库里一处具体的代码上：为什么 GitHub 的 MCP 定义还要在 genkit.ts 里再包一层函数？两套协议描述的是不同的接口，但模型框架仍然需要一个适配器，把 MCP 能力转成它的智能体能调用的东西。Murphy 说，Genkit 虽然号称支持 MCP，他却没找到一个现成能跑的示例，最后是用 genkitx-mcp 跑通的。

包列表里能看到这个依赖。现在 Genkit 的官方指引用的是 @genkit-ai/mcp；录制中的实现用的是 genkitx-mcp，集成时碰到的麻烦也属于那套较早的配置。工作坊就停在这道实际的分界线上：A2A 承载委派出去的工作，MCP 暴露能力，而应用代码仍然要把两者串成一条流程，真正把要做的事做完。

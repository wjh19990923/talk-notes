Git 工作流

幻灯片原文
Create a shared refactor branch with context and scaffolding. Agents branch from it and submit PRs back into it; start with 3-5 concurrent agents, then remove the scaffolding and merge into main.

Git Workflow

• Start a new branch
  ◦ e.g. v1-refactor
• Add high-level context for agents
  ◦ e.g. modify AGENTS.md, or add .openhands/microagents/v1-refactor.md
• Get any scaffolding in place
  ◦ e.g. create ./v1 directory, move old code to ./v0
• Send off your agents
  ◦ Each agent creates a new branch off v1-refactor
  ◦ Work is submitted via a PR into the v1-refactor branch
  ◦ Consider limiting to 3-5 concurrent agents, rolling forward as PRs merge
• Rip out the scaffolding
• Merge into main!

OpenHands 关于 uv 命令的讨论

幻灯片原文
Claude suggests uv run openhands as an ephemeral run and describes uv tool install openhands as a global, reusable installation. The speakers discuss trying the command and adding a version.

how do I turn this into a uv run command

uv tool install openhands

To convert that to a uv run command, you would use:

bash
uv run openhands

However, there's an important difference in behavior:
• uv tool install openhands - Installs the openhands package globally as a tool that you can run from anywhere
• uv run openhands - Runs openhands in an ephemeral environment without installing it permanently

If openhands is a CLI tool you want to use repeatedly, uv tool install is the better choice. But if you just want to try it once or run it occasionally without installing, uv run works well.

If openhands has a specific command/entrypoint you need to run, you might need:

bash
uv run --from openhands <command-name>

用并行智能体自动化大规模重构

当智能体得到有边界的任务、明确的依赖关系、隔离的工作区，以及能让人工审查始终跑在累积错误前面的验证时，大规模重构就变得可行了。

熟悉 Git pull request、Python、依赖管理和 Docker，有助于理解重构工作流和 SDK 练习。

01

维护积压超出了一个提示词能处理的范围

一个维护项目大到单个编程智能体做不完，该怎么自动化？技术债、依赖维护、代码现代化里有大量重复性工作，但它们的范围远不是一条提示词、一轮开发循环能覆盖的。智能体编排把这些工作拆给多个智能体，再协调它们的结果，让项目变得可控。

Robert Brennan 自我介绍是 OpenHands 的联合创始人兼 CEO，过去做的是开源开发者工具和自然语言处理。OpenHands 是一个采用 MIT 许可的编程智能体，前身是 OpenDevin。Devin 展示自主开发能力之后，OpenDevin 随之诞生。项目的初衷是让软件社区在“智能体如何改变工程”这件事上有发言权，而不是让这场变化发生在闭源的黑箱里。

Brennan 说，他现在写的几乎每一行代码都要经过智能体。批判性思考还在，只是手上的活从敲代码变成了描述任务、评估结果。他认为，就算模型能力不再提升，落地应用本身也会持续改变工程：组织仍然得学会怎么委派、怎么审查、怎么信任这些工作。他预计未来两三年会有大的变化，部分动力来自克服心理和组织上的障碍。

02

从代码片段到协调一致的执行

演进的起点是不了解上下文的代码片段：让模型写个冒泡排序或 SQL 访问代码，在聊天框里拿到答案，再粘进一个模型根本看不到的项目。IDE 自动补全带来了局部上下文。GitHub Copilot 能用上项目里现成的变量名、周边代码和数据库表名。用 Brennan 的比喻来说，机器人长出了眼睛。

自主智能体又加上了行动能力。2024 年初出现了 Devin 和 OpenDevin，循环从写代码延伸到运行代码、搜索报错信息、查 Stack Overflow、加调试语句、再试一次。机器人长出了手臂：它能在内层开发循环里反复迭代，直到代码跑通、测试通过。并行编排把这种能力扩展到多个智能体，有的智能体之间会互相通信，有的还会再创建新的智能体。Brennan 认为，最后这一阶段还是一种新兴实践。

对应的产品演进路线是：从 IDE 插件到 AI 增强的 IDE，再到 Claude Code 这类本地智能体，然后是云端智能体和编排。云端智能体有自己的执行环境，并发干活更容易，开发者的笔记本也不容易被破坏性命令或多余的安装波及。容器隔离只是相对更安全；实际边界还要看环境拿到了哪些凭证、挂载和网络权限。边界设得合适，开发者就能放手让智能体更自主地执行，不必每条命令都点批准。

编排在这些环境之上加了一层协调。OpenHands 起步做的是云端智能体，后来为了贴合开发者的习惯，又加了本地 CLI。Brennan 把指挥一队智能体比作自己从个人贡献者转型为管理者：工作越来越多是定义任务、提供上下文、判断结果。在他看来，用上编排的工程师还只是极少数先行者，他们正在啃团队以前一直没碰过的积压任务。

03

选择有可重复变更单元的工作

CVE 修复是一个很具体的工作单元：一个仓库里的一个漏洞。Brennan 讲了一个客户：几万名开发者，几千个仓库。新漏洞一公布，就触发仓库检查，必要时更新依赖，修复 API 破坏性变更，再给负责的团队提一个 pull request。Brennan 称，这个客户的 CVE 修复时效提升了 30 倍，但没有给出基准时长和测量方法。下游团队最终拿到的是一个待审查、待合并的修改提议。

其他适合的工作也有同样的重复结构：

- 维护：生成文档和发布说明。 - 现代化：给 Python 3 代码加类型注解，或者把 Java 单体拆成微服务。 - 迁移：升级 Java 版本，把 Spark 2 作业迁到 Spark 3，或者在 React 前端里用 Zustand 替换 Redux。 - 技术债：删除无用代码；日志里出现新的错误模式时，补上错误处理并修好背后的缺陷。

Brennan 提到，Redux 到 Zustand 的迁移就是在 OpenHands 自己身上做的；日志驱动的修复流程则是另一个客户基于 SDK 搭的应用。重复的修改可以自动化，但边界怎么划、架构怎么定，仍然要靠工程判断。

04

为什么一次性迁移会迷失方向

长任务可能还没撑满名义上的上下文窗口，就已经超出了智能体能有效利用的范围。压缩可能丢掉智能体之后要用的细节。智能体还可能半途而废：Brennan 讲过一次尝试，智能体迁移了一百个服务里的三个，然后建议招六个人来做完剩下的。缺乏领域知识让问题雪上加霜：早期一个错误假设，可能成为后面每一处修改的模板。

人这一侧也有对应的失败模式。让智能体把单体拆成微服务时，工程师可能没把脑子里已有的架构设想写进需求。智能体只能按熟悉的套路划边界，并不理解预期的设计。要委派得好，任务大小得匹配智能体的能力，中途要有审查，还要有清晰的完成标准（definition of done）。没有这个标准，智能体和审查者都不知道什么时候该停。

这是一种专门的工作流，不是要取代所有本地编码会话。Brennan 预计，日常的功能开发和 bug 修复仍然主要是单智能体任务。他对比了两种情况：一般场景下生产力大约提升 20%，而在精选的维护类工作上收益格外突出；他也明确否认存在普遍 3,000% 的提升。这些笼统数字在这里没有对应到具体研究；他更收敛的说法是：精心挑选的 CVE 和现代化项目，可以把几人年的工作压缩到几周。

05

让审查成为执行循环的一部分

熟悉的单智能体循环是：写提示词、执行、检查输出和测试，然后要么再提示一轮，要么提交并推送。编排项目在执行前加了任务拆解，执行后加了整合。人（也可以借助智能体）定义一个个任务，智能体去执行，产出再汇总成一个连贯的修改。两个层面都要审查：每个中间结果，以及最终的整合结果。

Brennan 提出以大约 90% 的自动化为目标，并把它定位成生产力提升一个数量级的机会，而不是实测结果。剩下那 10% 的工作分量很重：划好边界，让每一步都能验证，别堆出一大堆没人看得懂的 AI 代码。

他的 Git 工作流给项目提供了一个共享的集成点：

1. 为这次迁移建一个专用分支。 2. 在 AGENTS.md 或 OpenHands microagent 里写好项目说明，讲清楚预期的改造。 3. 加上必要的脚手架，让中间状态保持可用。 4. 从这个准备好的分支启动智能体，把审查过的修改陆续合入这个分支。 5. 迁移完成后删掉脚手架，再合并到 main。

第一次尝试时，Brennan 建议同时跑三到五个智能体，审查才忙得过来。他也提到有更大规模的部署，同时跑几百上千个智能体，但那些部署把审查分散了出去，比如把 pull request 发给各个仓库的负责团队。

06

把依赖图变成可审查的批次

Calvin 录了一段演示，用这套方法处理 OpenHands 里的代码坏味道。Refactor SDK 是编排接口，底层的 OpenHands Agent SDK 提供编程智能体。修复挂掉的 CI、添加和调试接口这类目标集中的活，单个智能体就能干好。全仓库的类型标注、依赖升级、框架迁移，则需要更大的结构。

Calvin 介绍，要处理的核心智能体代码约有 380 个文件、6 万行。依赖图让结构一目了然：每个节点是一个文件，每条边代表一个导入关系。下一步是把图切成 PR 大小的批次，让智能体和审查者都能看懂。可以用图算法来切；演示里则按目录结构切，让语义相关的文件待在一起。图上用颜色标出哪些文件属于同一批次。

界面把文件图折叠成批次图。每个新节点代表一个批次，边沿用批次内文件的依赖关系。图变小之后，哪些批次可以先处理就一目了然。Calvin 打开一个 16 个文件的批次，又看了一个看上去是空的初始化文件；人可以挪动文件、留备注，或者标记这个批次已审查。后面一个批次只有 4 个文件，代码却复杂得多。审查难度不能只看文件数，所以复杂度指标能帮人把注意力放对地方。

07

验证、修复、审查，再验证

改代码之前，系统得先找出哪里有问题。它的验证器（verifier）可以是程序化的：运行一条 Bash 命令，调用测试、linter 或类型检查器。在这个代码坏味道练习里，Calvin 改用 LLM 加上给定的规则。生成的报告会说明发现了哪些坏味道、哪些没发现。一个简单的批次通过验证，变成绿色，状态同步反映在图上。

验证按依赖顺序进行，优先挑前置依赖都已解决的批次。第二个简单批次也通过了。那个复杂批次没通过，节点变红，还生成了一份更长的逐文件报告。现在图上有两个绿色批次、一个红色批次。让整张图变绿，意味着满足配置好的验证器；红色节点标出了下一阶段要干的活。

修复器（fixer）有几种实现方式：

| 修复器 | 工作方式 | |---|---| | 程序化 | 运行一条 Bash 命令 | | 单次模型调用 | 让 LLM 在一次回复里改完整个批次 | | 编程智能体 | 使用一份干净的代码副本、工具、测试和文档 |

基于 Agent SDK 的修复器能查看代码、跑测试、查网上的文档，并反复迭代。它干活的同时，Calvin 继续验证其他独立的批次并启动修复。在加速播放的演示里，只要上游批次还没完成，这条依赖链就不往下推进。修复器跑完后，批次状态会重置：它的产出仍然需要验证。

每个修复器都会产出一个 pull request，等人批准。PR 描述里记录了发现的代码坏味道、做了哪些修改，以及刻意没做的修改。Calvin 说，他打开的那个 PR 改了两百来行，主要是把一段深度嵌套的代码块抽成了独立函数。指令收得窄，再加上按批次切分，即便别的 PR 更大，改动也依然看得懂。审查并合并之后，下游工作就解锁了；接着再验证修改后的批次能否通过。Calvin 提到，这个工具还被用来做严格类型标注和提高测试覆盖率。接下来，工作坊会动手搭一个缩小版，沿用同样的“发现—修复”模式。

08

围绕验证和依赖设计任务

好的委派单元能装进一个 commit 或 pull request，而且不用反复提示就有不小的把握完成。它应该能和并行的其他工作分开，检查起来也要快：CI 变绿、在应用里快速走一遍、或者跑一条针对性的命令，都应该能给出有说服力的证据。依赖关系必须明确。Brennan 用的规划方式和工程团队一样：A 解锁 B、C、D，这三个都完成后再解锁 E。

最简单的拆法是逐块拆：列出文件、目录、函数或类，每个单元独立分配。如果耦合不强，给 Python 加类型注解就适合这种做法，最后把结果汇总成一个 PR。如果修改会影响依赖它的代码，就加上顺序约束：先从叶子节点的工具函数开始，合入修复，再一路做到应用入口，这样后面的智能体拿到的就是更新过的依赖。

Redux 到 Zustand 的迁移还用到了另一种技巧：搭临时脚手架，让两套实现同时可用。先由一个智能体加上对两套状态管理的支持。然后多个智能体并行迁移各个 React 组件；其他组件还在用 Redux 时，迁完的组件就能单独检查。等所有组件都用上 Zustand，再删掉这座桥和剩下的 Redux 引用。这座桥本来就是临时的，它的作用是让中间状态可测试，而不是等整个迁移做完才拿到反馈。

09

共享发现而不共享每一条轨迹

任务拆开了，大家共同碰到的发现并不会消失。几个智能体可能撞上同一个障碍，说明最初的计划漏掉了什么。把每个智能体的完整上下文广播出去是个糟糕的办法：上下文窗口会被迅速耗尽，又回到了单个智能体长轨迹的老问题。真正有用的，是那些会改变其他智能体下一步决策的发现。

Brennan 比较了三种更有选择性的做法：

- 人工更新：把更正粘贴到每个对话里，比如改用库版本 1.2.3 而不是 1.2.2；或者在 AGENTS.md 或 microagent 里维护共享说明。这种做法直接，但需要人持续投入。 - 智能体提议共享上下文：让智能体更新说明文件，可以走 pull request。经过人工审查，能把过多或无关紧要的经验筛掉，免得它们变成所有智能体都要遵守的指令。 - 消息传递工具：允许智能体广播发现，或者点对点通信。协调更自主了，但也带来了更多不确定性。

最后一种做法可能产生跟任务毫不相干的互动。Brennan 举了个让人印象深刻的例子：两个智能体反复互祝对方修得禅意圆满。通信和写代码一样，需要目的，也需要停止条件。

10

构建一个为独立修复智能体供料的扫描器

动手练习以一个 GitHub 仓库为输入，搭一个 CVE 修复工作流。Brennan 让参会者去看工作坊的幻灯片，第 29 页前后有可以直接复制的提示词和链接。第一个智能体扫描仓库，根据发现的内容选合适的工具：比如 Docker 镜像用 Trivy，有 package.json 的项目用 npm audit。

每个发现的漏洞随后都变成一个单独的修复任务。负责的智能体先调研有没有现成的修复，然后更新相关依赖、修复 API 破坏性变更，再开一个 pull request。PR 彼此独立，即便某个漏洞修不了、某个智能体卡住了，有用的工作照样能合进去。Brennan 拿 90–95% 的修复率举了个假设的例子，说明部分完成也很有价值；这并不是实测成功率。

用 SDK 搭建只涉及几个对象：配置一个 LLM，把它交给一个 Agent，配上终端、文件编辑器以及可选的任务跟踪工具，提供一个 workspace，发送任务，然后运行。扫描器跑完后，宿主程序遍历扫描结果，为每一项启动一个修复智能体。这种结构把仓库级的发现和漏洞级的执行分开了。

11

准备仓库、凭据和执行环境

练习的起点是一个新的 GitHub 仓库、一个 GitHub token 和一个 LLM token。Brennan 给工作坊参与者送了 10 美元的 LLM 体验额度，已有账户的也可以帮忙充值。智能体的执行环境放在一个 Docker agent-server 容器里。他提到，如果要为成千上万个 CVE 准备大量工作区，可以用 Kubernetes；工作坊本身只用一个容器。他自己用 OpenHands CLI 写代码，参会者也可以用 Cursor、Claude Code 或其他顺手的编程智能体。

建好仓库后，Brennan 加了一个仓库级 microagent，描述这个 CVE 修复项目，并指向 SDK 文档。接着他一步步演示 GitHub 的 Settings → Developer settings → Personal access tokens，选了一个带 repo 权限范围的 classic token，让智能体能开 pull request。LLM 代理的凭证在 OpenHands 个人资料的 API Keys 页面里获取。他避开屏幕录入 token，克隆了仓库，再用幻灯片里的命令启动 agent-server 容器。

他口述的 CLI 安装命令是：

``bash uv tool install openhands ``

随后 Brennan 启动 CLI，并再次强调用哪个工具写代码都行。到练习后半段，这个包的安装成了现场排查的问题。

12

在加智能体之前先证明 LLM 连接可用

第一条提示词让编程智能体查阅 SDK 文档，写一个最简单的 LLM 调用。Brennan 通过 OpenHands 代理选用了 Claude Sonnet 4。各家提供商的模型标识符不一样，所以他让用 Anthropic 或 OpenAI 凭证的参会者去 LiteLLM 文档里查对应的模型字符串。第一个里程碑很简单：配置好的模型成功返回一条响应。

关于仓库上下文，他展示了 .openhands/microagents/repo.md，里面有项目描述和 SDK 文档链接；兼容的工具也可以改用 AGENTS.md。这些是工作坊当时的配置约定。现在的 Agent Skills & Context 文档 也涵盖了 AGENTS.md、旧版上下文格式和 SKILL.md；但这并不意味着录像里的导入方式、包的行为或模型标识符仍是现行 API 所保证的。Python 脚本从环境变量读取凭证，Brennan 特意没把它们提交进仓库。第一次运行报了一个 API 用法错误，他把报错粘回给编程智能体去修。再试一次，又碰上了认证错误。

这期间，一位用 uv 0.9.6 的参会者反馈，安装时在 OpenHands 包里找不到可执行文件，入口点也装不上。Brennan 建议试试他自己用的 uv 0.9.11，但没确认这样就能解决。另一位参会者说已经通过托管的网页界面创建了 PR。Brennan 说他平时最喜欢这种工作流：让网页端的智能体推送修改，需要时再拉到本地。这次选 CLI，是为了更方便地展示在本地运行的脚本，也方便交接。

连通性测试最终返回了 Hello, OpenHands。Brennan 看了看背后那几行代码：用模型和 API key 初始化 LLM，再发一条测试消息。第二条提示词开始让智能体真正干活。脚本接收一个 GitHub 仓库，把远程 workspace 连到 localhost:8000 上的 Docker agent server，把仓库克隆进这个环境，再让一个智能体扫描漏洞。有人问怎么打断 CLI，Brennan 建议按 Control-P 暂停，再发一条更正消息或者 continue。

安装问题的讨论另起一路继续。一位参会者装上了 -ai 包，但其他人反馈出现崩溃和弃用警告。Brennan 认为 openhands-ai 已经弃用，说会跟团队反映。他建议换用发布页上的可执行文件、Docker 或 uv run。讨论最后转到给普通的 openhands 指定版本，但始终没得出一条完整且确认可用的命令。

13

观察扫描器在其远程工作区中运行

Brennan 用扫描器扫了一个预计含有漏洞的仓库。SDK 展示进度的方式和 CLI 很像：任务列表更新、克隆仓库、安装工具、执行命令。环境里没有 Trivy，智能体就先装上，再跑扫描。这就是自主内层循环的具体样子：智能体在执行任务的过程中，自己解决了环境上的前置条件。

生成的 Python 代码把之前配置好的 LLM 交给一个带终端和文件编辑器工具的智能体。远程 workspace 把这个智能体连到 Docker 容器上。Conversation 保存这个工作单元的上下文，并接收明确的任务指令。这几个对象各司其职：模型负责决策，工具负责行动，workspace 提供执行环境，conversation 维护任务上下文。Brennan 说，这次初始扫描顺利跑完了。

14

让扫描结果能被宿主程序使用

下一条提示词要解决另一个问题：把有用的数据从智能体的环境里拿出来。Brennan 让扫描器只把漏洞存进一个 JSON 文件。宿主程序可以通过 workspace 的命令执行或文件操作函数把它取回来。在启动修复智能体之前，他想先让脚本遍历取回的列表并打印出来。这样就把数据交接和后面更复杂的扇出分开处理。

如果约定的格式是 JSON 数组，Python 这边可以把这道边界做得小而明确：

```python import json from pathlib import Path

def load_vulnerabilities(path: Path) -> list[dict[str, object]]: payload = json.loads(path.read_text(encoding="utf-8")) if not isinstance(payload, list): raise ValueError("Expected a JSON array of vulnerabilities") if not all(isinstance(item, dict) for item in payload): raise ValueError("Each vulnerability must be a JSON object") return payload

if __name__ == "__main__": for vulnerability in load_vulnerabilities(Path("vulnerabilities.json")): print(json.dumps(vulnerability, ensure_ascii=False)) ```

这里的 vulnerabilities.json 就是取回的产物；扫描器特有的字段，可以在记录变成修复任务之前先检查一遍。现场运行时，漏洞结果出来了，脚本却在解析 JSON 时报错。扫描成功和结构化输出成功传回，是两个独立的里程碑。

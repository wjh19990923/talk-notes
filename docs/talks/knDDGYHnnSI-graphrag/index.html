PageRank

From Wikipedia, the free encyclopedia

PageRank (PR) is an algorithm used by Google Search to rank web pages in their search engine results. It is named after both the term "web page" and co-founder Larry Page. PageRank is a way of measuring the importance of website pages. According to Google:

PageRank works by counting the number and quality of links to a page to determine a rough estimate of how important the website is. The underlying assumption is that more important websites are likely to receive more links from other websites.[1]

Currently, PageRank is not the only algorithm used by Google to order search results, but it is the first algorithm that was used by the company, and it is the best known.[2][3] As of September 24, 2019, all patents associated with PageRank have expired.[4]

GraphRAG：结合知识图谱与向量检索，实现更好的检索

Emil Eifrem 讲解了知识图谱如何为检索增强生成加入显式的关系、更丰富的上下文和可解释性，同时也承认构建这些图谱在实践中的难度。

GraphRAG：结合知识图谱与向量检索，实现更好的检索

01

为什么关系在搜索中很重要

Emil Eifrem 把 GraphRAG 看作搜索技术长期演进中的一环：从孤立的数据点和文本匹配，走向利用信息之间关系的系统。早期网页搜索引擎靠关键词方法，比如倒排索引和类 BM25 的算法。网上内容越来越多，这类系统一次就能返回成千上万条匹配结果，用户只能自己从中挑出有用的。0:14 1:00

在 Eifrem 看来，下一步是 PageRank。这是一种图算法，利用网页之间的链接结构，把重要结果排到前面。再往后出现了知识图谱。它表示的是文档里出现的概念，不再只把文档和链接当作搜索的全部基础。1:55 3:01

知识图谱由节点、关系以及挂在两者上的键值属性组成。Eifrem 举例说，有些搜索结果把非结构化的描述文字和结构化的事实放在一起展示，可见以图为底层的表示能把不同形态的信息串起来。他的核心观点是：让语言模型顺着显式关系检索信息，生成式应用同样能从中受益。3:01 4:19

- 关键词搜索和倒排索引会返回海量匹配结果，让用户应接不暇。 - PageRank 用图算法给重要的搜索结果排优先级。 - 知识图谱把概念表示为节点，节点之间用关系相连，节点和关系上都可以挂属性。 - GraphRAG 把语言模型和知识图谱检索结合起来，也可以同时用上向量搜索。

02

基本的 GraphRAG 检索模式

Eifrem 给 GraphRAG 下的定义是：在检索链路的某个环节用到知识图谱的检索增强生成。按这个定义，它不必取代其他检索方法。图检索可以和向量搜索配合，一边靠相似度发现内容，一边沿关系扩展上下文，共同支撑同一个回答。4:19

他举的例子是一家 Wi-Fi 路由器厂商的客服助手。每篇支持文章是图里的一个节点，正文存成节点属性。文章还可以连到具体产品、相关产品的层级结构，以及写这篇文章的支持工程师。这样，原本藏在文章正文或外部应用逻辑里的关系，都在图里明确保存了下来。5:25

用户问“黄灯一直闪、网络老是断”时，系统先把问题转成 embedding，用向量搜索找到相关文章。接着沿图遍历，收集更多上下文，比如相关产品的文章，或者提示某位工程师写的内容应该排得更靠前的信号。最后把扩展后的上下文和原始问题一起交给语言模型，生成回答。6:28

图扩展也带来了新的筛选问题：顺着关系走下去，可能一下子冒出几千个节点。所以 Eifrem 加了一个可选的排序步骤：根据图结构选出 top K 结果（可能会用到 PageRank），再把最终上下文发给模型。整个流程就是：向量检索、图遍历、可选的图感知排序、语言模型生成。6:28 7:40

- GraphRAG 在检索链路中用到知识图谱，但不需要取代向量搜索。 - 支持文章可以显式关联到产品、产品层级和作者。 - 向量搜索找到最初的文章，图遍历再把检索范围扩展到相关上下文。 - 图感知排序能在语言模型生成之前，把大量扩展结果收窄到 top K。

GraphRAG 检索与生成 先用向量检索找到起点，再做图扩展，生成前可选择再排一次序。 - 用户问题 — 关于某个支持问题的提问 - 向量搜索 — 检索最初的文章节点 - 图遍历 — 扩展到相关产品和文章 - 可选排序 — 基于图结构选出 top K - 语言模型 — 根据选出的上下文生成回答 - 用户问题 → 向量搜索 (转成 embedding 并搜索) - 向量搜索 → 图遍历 (提供初始节点) - 图遍历 → 可选排序 (可选：收窄扩展结果) - 可选排序 → 语言模型 (提供 top K 上下文) - 图遍历 → 语言模型 (直接提供上下文)

03

图谱能为答案质量增加什么

Eifrem 强调的第一个好处是准确性。他介绍了一些研究和案例：把图检索和向量搜索结合起来，回答质量比纯向量检索或基线检索方法更高。道理很简单：有了关系，检索系统就能拼出光靠相似度搜索可能找不到的相关上下文。6:28 7:40 8:53

他引用了 data.world 的一个案例：测了大约 43 个问题，在向量搜索之外加上知识图谱后，回答质量平均提升约 3 倍。他还提到 LinkedIn 的一项工作，凭印象说准确率提升了约 75% 或 77%。这些数字只是他对个别案例的描述，不代表普遍适用的性能保证。8:53

Eifrem 还介绍了 Microsoft 的观点：GraphRAG 能回答一类基线向量搜索或基线 RAG 答不了的问题。他没有细说是哪些问题，所以能得出的结论有限：图检索改变的可能不只是回答质量，还有检索系统能回答哪些类型的问题。9:53

- 图遍历能在最初的向量搜索结果之外，找回基于关系的相关上下文。 - data.world 的一个案例显示，在约 43 个问题上，回答质量提升约 3 倍。 - LinkedIn 的一个案例显示，准确率提升约 75% 或 77%。 - GraphRAG 或许能回答基线向量搜索或基线 RAG 答不了的新类型问题。

04

显式的结构改善了开发和监督

Eifrem 说的第二个好处是应用开发更容易，但他加了一个重要前提：手里得先有一个可用的知识图谱。团队首先要学会怎么构建图谱，他也承认这第一步可能不容易。所以开发上的便利是有条件的，并不是说 GraphRAG 从头到尾总是更简单。9:53

他讲了一家没透露名字的金融科技公司，把现有应用从向量数据库迁到了 Neo4j。按他的说法，这家公司迁移后发现：顺着关系就能找到相关操作；embedding 可以直接在数据库层计算；把应用数据可视化以后，bug 也更容易发现。这个例子说明，显式的图结构能让开发者更容易看清应用在做什么。11:00

为了说明原因，Eifrem 拿“苹果和橙子都是水果”这句话做对比：在图里怎么表示，在向量空间里又怎么表示。图可以明确画出苹果、橙子和水果之间的关系；向量内部到底表达了什么，人很难直接看懂。他强调图和向量是互补的，但认为在应用开发过程中，图是更清晰、更好用的表示方式。11:00 12:11

这种显式结构的好处不止于写代码，也延伸到运维层面。Eifrem 把看得见的关系、可检查的数据结构，和可解释性、可审计性、治理联系在一起，尤其是组织需要弄清生产系统为什么给出某个结果的时候。这些好处来自表示方式和可追溯性，并不等于任何 GraphRAG 系统都自动满足某项治理标准。13:19

- 只有跨过构建可用知识图谱这道门槛，开发才会变得更容易。 - 一款金融科技应用借助 Neo4j 的关系、数据库层的 embedding 计算和图可视化，简化了检索和调试。 - 图让关系一目了然，向量则仍是黑盒；两种表示互为补充。 - 显式的图结构能提升生产系统的可解释性、可审计性和治理水平。

05

构建知识图谱是核心的实现挑战

Eifrem 把构建图谱的输入数据分成三类：结构化数据、非结构化数据，以及混合数据，也就是带有部分长文本字段的结构化记录。结构化数据的例子有 Snowflake、Postgres、MySQL、Oracle 等系统；非结构化数据的例子有 PDF 文件和网页原始文本。他认为，企业生产环境里的很多用例用的都是混合数据。13:19 14:32

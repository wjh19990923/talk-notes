智能体没出问题，出问题的是周边系统

Harvey 的智能体已经写了 10,000 个 pull request。Joey Wang 说，如果重来一次，他会先搭 CI 跟进循环，并且一开始就限制哪些东西能启动任务。有一次，一个发布 bug 让大约 900 个智能体同时去修同一个问题。

01

云端智能体需要 Harvey 提供什么

Spectre 是 Harvey 内部的云端智能体平台。在 Joey Wang 演讲前的一个月里，它平均每分钟启动不止一个智能体，日夜不停。那个月大约有 460 人在用。智能体累计写了 10,000 个 pull request，大家还在这套平台上找到了别的用法：有人在 Slack 里问数据问题，直接拿到答案；市场部的同事把一个原型和一份讲稿丢进频道，请它帮忙把内容串成产品视频的故事线。

工程师手里已经有顺手的编码智能体，为什么还要做 Spectre？因为 Spectre 负责运行这些智能体。按 Wang 的估计，一台笔记本同时跑五到十个就到头了。把活挪到云端能换来算力，但远程智能体照样需要检出代码仓库、拿到凭证、接入 Harvey 的技术栈。它还得能接住告警或工单，并把改动一路推过评审。Spectre 提供的就是这层框架。全公司共用一套框架，又多了一份责任：哪怕某个工程师有一大堆活要甩出去，也得给下一个人留出位置。

02

凌晨 2 点的修复也得过 CI

工程师开始用 Cursor 时，马上冒出两个问题：怎么拿到 Harvey 的密钥？怎么在真实技术栈上测试？如果把这两件事直接接进 Cursor，下次工程师换工具，团队还得再做一遍。Harvey 的做法是让工程师直接让自己喜欢的智能体去调用 Spectre。一个会话可以在笔记本上开始，挪到云端，再挪回来。工程师换了智能体，团队的测试环境不用跟着变。

Wang 举了个例子：凌晨 2 点，Slack 里来了一条告警。没人输入提示词，智能体自己接手，写好修复，拉起一份 Harvey 技术栈的副本，再把验证证据贴到 pull request 上。如果持续集成（CI）失败，失败信息本身就成了下一轮尝试的输入。跟进循环会读取失败原因，再推一版修复，这时负责人还在睡觉。到了早上，这个 PR 已经进入共享评审队列，和其他改动走同样的规则。Spectre 会等负责人上班后再去提醒。改动一旦获批，智能体可以自动合并。

Wang 说，如果重来，他会最先做跟进循环。Harvey 在 10 月初给所有人打开了这个功能。那个月合并进 Harvey 后端的智能体 PR 里，五个有四个走过这个循环。

有些服务很难测，测试要靠某个工程师脑子里的经验，细到哪个 flag 千万别动。Spectre 用“项目”来存放这类知识：人可以写下要点，智能体可以记下学到的东西，团队可以固定自己信得过的 skill。在这个项目里工作的任何智能体都能用上这些知识。项目还会记录谁跑了什么。Wang 的观点是：不管工程师选哪个智能体，检查和审计记录都应该一样。

03

有了命令行，一个智能体就能指挥其他智能体

5 月份，大家通常是打开浏览器标签页，或者在 Slack 里 @Spectre。那个月只有一个任务是从终端发起的。团队定了一条规矩：人能点的操作，智能体也必须能调用。命令行可以启动任务、打开跟进循环、开启自动合并、发布页面。笔记本上的智能体、已经在沙箱里的智能体、CI 任务，都能用这些命令。

新增的工作量从哪来？到 10 月，命令行每月发起大约 6,500 个任务，网页端的用量也没掉。有些人每月发起几百个任务，从来不打开网页。现在，和智能体聊一次，就能启动一整批工作。

10 月里，Wang 从两个方向用上了这种能力。

- 把活派出去。 Wang 让一个编码会话统筹一张大工单。它把工作拆成十个里程碑，留一个给 Wang，剩下的拆成几百个任务交给 Spectre。每个任务都有自己的沙箱，用来做端到端验证。 - 把决策收回来。 同月晚些时候，另一个智能体专门盯着 Spectre，找出卡住工作的问题。它把问题列出来，替 Wang 起草回复，等 Wang 批准后再发回去。Wang 不用挨个点进任务去看它们需要什么，就能答复这些 worker。

每个沙箱还得有代码可改。团队统计任务时间花在哪，发现最慢的一步是 Git 检出。检出 Harvey 全部仓库平均要一分多钟。团队的办法是在每台机器上都放一份所有仓库的副本，让每个任务借用本地副本。同一台机器上一下子来一批任务，也能复用机器上已有的仓库。

04

一个 bug 引发了约 900 次排查

8 月中旬的一次发布带上了一个 bug，每个 workspace 都会触发一次告警。几百条告警涌进同一个 Slack 频道。有个工作流会在每条告警上 @智能体，每 @ 一次就启动一个任务。平时这个工作流一天启动大约 50 个任务。事故期间，它四小时里启动了约 900 个，全都在追同一个 bug，直到集群被占满。

下一个 workspace 再报这个 bug 时，应该怎么处理？按原来的工作流，每条报告都等于一道指令：再启动一个 worker。修复之后，重复告警会并入已经在进行的排查。同一次排查可以汇总来自很多 workspace 的报告。

下一条 workspace 告警去哪里 同一条重复告警，在新旧两版工作流里走向不同。它去哪里，决定了会不会再启动一个智能体。 - 又一个 workspace 报告了这个 bug — 告警落进共享的 Slack 频道。 - 再次 @智能体 — 工作流在每条告警上都 @智能体。 - 再启动一个任务 — 又一个智能体开始排查同一个 bug。 - 并入进行中的排查 — 已在进行的排查接收这条重复告警。 - 又一个 workspace 报告了这个 bug → 再次 @智能体（每条告警都触发一次 @） - 再次 @智能体 → 再启动一个任务（每次 @ 启动一个任务） - 又一个 workspace 报告了这个 bug → 并入进行中的排查（把报告转给已有的工作）

05

给共享集群一个公平的启动队列

两个月后，一位工程师完全照团队鼓励的那样，把活交给了 Spectre。一台笔记本在大约三小时内提交了约 950 个命令行任务。集群满了，其他人的工作全排在这台笔记本后面。8 月那次故障，靠把重复告警转给已有排查解决了。这一次，Spectre 需要既能接下一大批任务，又不耽误别人干活。

四天后，团队上线了公平启动队列。提交任务后，负责人能看到自己排在第几。调度器在集群有空位时启动任务，优先照顾正坐在键盘前等结果的人。每个用户都有一份公平配额，集群空闲时还能多借一些。大批任务可以先用闲置机器，下一个空位给谁，仍由调度器说了算。

任务量上去以后，完成率怎么样？Wang 拿 8 月一个繁忙的日子做对比：那天大约每十个任务就有一个没跑完。11 月 4 日，Spectre 处理的任务量是那天的两倍多，完成的比例反而更高。由于几项改动是同时上线的，Wang 也说不清哪一项贡献最大。

06

下一个瓶颈是合并队列

10 月底，Harvey 的开发者平台团队拉响了另一种警报：全公司的 PR 量一个月涨了约 60%。以前合并一个改动要 15 到 30 分钟，现在要一个多小时，团队还不得不一次次关掉合并队列。

合并队列关掉后，PR 会 rebase 到 main 上，重跑 CI，检查通过就合并。所有 PR 都依赖这个共同的起点。main 一坏，所有人的 CI 跟着坏。公平启动队列能给大家腾出位置开始干活，但干完的改动怎么顺利合并，还没有答案。

07

没人盯着的时候，谁来启动工作？

Spectre 增长最快的工作来源是自动化。定时任务或某个事件可以唤醒智能体，让它分诊告警、读 PR 或写一篇帖子。演讲前一个月，大约 110 人在跑自动化。无人值守的智能体可能启动成千上万个任务，所以每个自动化连续失败五次就会自动关闭。负责人还可以给它设预算或到期时间。

Wang 在想：如果每个 Slack 频道都有一个常驻智能体，能跟上对话，自己判断什么时候该开工，会怎样？对评审者来说，问题是：能不能让每个 PR 在人看之前，就附上改动确实可用的证据？演讲时，每 20 次合并里只有一次带着这种证据。就算改动带了证据，也还要面对 Harvey 尚未解决的问题：智能体不停地开 PR，合并该怎么做？

要点总结

  • 让平台负责第一版补丁之后的事。在 Spectre 里，CI 检查失败后，评审者还没上班，智能体就能再试一轮。
  • 让用户的每个操作都能被调用。有了启动任务、开启跟进的命令，笔记本上的智能体、沙箱里的 worker 和 CI 就能用上同样的能力。
  • 在人、智能体或告警发现自己能启动多少工作之前，先把上限定好。把重复告警转给已有排查，可以避免重复劳动。一个人要跑几百个任务是另一回事，要靠公平调度器来处理。

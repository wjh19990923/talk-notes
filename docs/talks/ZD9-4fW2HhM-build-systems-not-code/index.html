构建系统，而不是代码

一个找房智能体展示了当模型来写代码时，软件工程的重心转向了哪里：工作流、组件边界、持久记忆、安全的重试，以及人的决定权。

01

重新找到构建的乐趣

一个周五晚上，Angie Jones 在搭处理日常运营任务的智能体，不知不觉太阳就落山了。晚饭时间也过去了。她又回到了熟悉的开发心流：一心想把东西跑通，搭东西的兴奋感一点没少。这段经历回应了她常从开发者那里听到的担忧。用编程智能体的人担心，自动化拿走了编程里好玩的部分，只把枯燥的活留给人。

机会在比生成代码高一层的地方。构建智能体，就是设计它所运行的系统。 积木换了，但职责怎么分、依赖怎么处理、状态怎么管、出错了怎么办，这些决定仍然需要工程判断。Jones 用找房子的例子 Relocation Scout，把这些决定讲得很具体。

02

一次找房比一个提示词持续得更久

让智能体看一批房源并排个序，一条提示词也许就够了。但找房很少一天就能结束。明天接着找，得用上今天学到的东西，哪怕明天是从一段空白对话开始。所以 Relocation Scout 需要把知识存到会话之外，换一个全新的上下文也能重新加载或查询。

智能体只是其中一个组件。它周围的环境里有文件、工具、人，可能还有其他智能体。Relocation Scout 拉取房源和社区信息，对照买家的偏好逐一权衡，最后返回一份排好序的候选清单。这些输入和输出，决定了它在更大系统里的位置。

让编程智能体动手实现之前，先定义好它的职责、依赖、边界，以及出错时怎么处理。它干活需要什么？某个依赖坏了怎么办？哪些职责应该交给别处？编程智能体可以帮你搭这个组件，但该搭什么样的组件，要靠这些问题来回答。

03

给目标一条路径

传统软件早就把工作流显式写进了 CI/CD 流水线和工单生命周期。智能体系统也要这样做。/goal 命令可以表达想要的结果，但审一套房源，仍然需要一条具体的工作路径。

对 Relocation Scout 来说，这条路径是：

1. 收集审查房源所需的信息。 2. 对照买家的标准做评估。 3. 决定怎么做、执行，并记录结果。 4. 停止、重试或上报。

工作流决定了每一步需要什么上下文、哪些活由智能体直接干、哪些地方交给工具或人来接手。这些交接点是架构决策，不能含糊地藏在目标里。

04

找出藏在提示词里的任务

类太大、函数太长、一个服务管的事太多，都是常见的代码坏味道。放到智能体身上，对应的就是巨型提示词。一开始还挺合理：写几条评估房子的指令。接着某个边界情况要补一句说明，又加了一条安全规则，然后又冒出一个重要例外。最后，这份指令文件什么都想管。

Relocation Scout 的提示词里塞了四件不同的活：拉取并规范化房源、格式化候选清单、计算通勤时间、调研社区。Jones 认为，脚本写得过长和智能体跑偏有直接关系。把这些活拆开，理由很实际：每一块都更容易理解、测试和修改。拆出更多零件本身并不是目的。

分解是找出各自独立的职责；关注点分离是把它们放到合适的位置。 这和在 controller 与 service 层之间做选择、把业务逻辑和展示层分开，是同一类决策。只不过 Relocation Scout 能选的去处不一样。

| 职责 | 组件 | |---|---| | 规范化房源 | 可复用技能 | | 统一候选清单条目的格式 | 输出 schema | | 计算通勤时间 | 脚本 | | 调研社区 | 子智能体 |

房源规范化流程变成了智能体可以按需加载的能力。schema 规定结果长什么样。计算交给脚本，分量不轻的调研任务则交给一个单独的智能体去做。现在每项职责都有了明确的归属。

05

复用能力，而不是每一条指令

假设找房范围扩大到三座城市。每个市场都可以加载同一个房源规范化技能。这套流程只写一次，就能在多个智能体之间复用，还可以分享给别人，就像库或包一样。

子智能体是另一种模块。Jones 从架构角度把它比作函数：交给它一件具体的任务，需要时调用就行。社区调研员可以专心干自己的活，不必背着父会话的全部上下文。职责聚焦，它才能在不同市场和工作流里都派上用场。

复用也需要判断。有些指令只属于某一个工作流，硬把它们抽象出来，花的成本可能比省下的还多。模块化应该让一项能力更好用、更好维护，而不是把每条指令都塞进共享组件。

06

分配确定性、判断和权限

智能体能尝试某件事，不代表它就最适合做这件事。计算通勤时间、过滤掉看过的房源，交给普通代码就行。解读杂乱的社区信息、判断哪些房源值得关注，才更值得动用模型的推理能力。

每一步都交给模型，会带来不必要的波动：同一类任务，换一天可能得出不同的结果。Jones 的经验法则是：任务有确切答案，就用代码；需要解读，就用智能体。把确定性的活留在代码里，还能省掉不必要的模型开销和复杂度。

| 角色 | 职责 | Relocation Scout 示例 | |---|---|---| | 代码 | 确定性 | 计算通勤时间；剔除看过的房源 | | 智能体 | 判断 | 挑出值得细看的房源 | | 人 | 授权 | 批准预约看房 |

最后这条区分很关键：评估一套房和授权一个动作，是两项不同的职责。推荐结果再诱人，也不等于就可以去预约看房。

07

把一次评估变成持久的契约

如果只有人来读，自由文本就够用。一旦别的系统要根据输出采取行动，接口就得有一个约定好的结构。用聊天的口吻评价一套房子，读起来也许很舒服，但决定埋在会话里，下游步骤很难稳定地取出来。所以 Relocation Scout 会把评估写成结构化格式。

Jones 的大多数智能体都用 Karpathy 的 LLM Wiki 模式做记忆层。在这个例子里，一条房屋评估包含决定、评分和理由。这个 wiki 是一种维护知识的设计模式，不是装上就能自动强制执行输出契约的记忆产品；结构化记录怎么定、怎么校验，仍然是系统设计要解决的事。

好处是可以直接这样查询：找出所有评分 4 分及以上、通勤 15 分钟以内的房子。评分和通勤时间放在固定字段里，不再困在对话中。这些是搜索条件，不是性能指标。生成候选清单的那一步也能直接读这些字段，不需要人来解读评估内容。

上一步的输出就是下一步的输入。 契约让这种交接变得可靠，也逼着你把任务本身想清楚。如果连结果的结构都说不清，要做的事可能还太模糊。

08

只重试未完成的工作

可复用的系统必须扛得住重复的 webhook 和中断的运行。它要知道某个动作是否已经执行过、输入有没有变、哪些没做完的活可以安全重试。幂等性 指的是重复执行同一操作，不会带来多余的副作用。

模型还带来一个特有的陷阱：重试时请求的措辞可能变了，同一件活看起来就像一项新任务。所以幂等性必须靠系统强制保证，不能根据模型的措辞去推断。

Jones 用一个只做了一半的看房请求来说明：

1. 新房源进来，Relocation Scout 给房产经纪人发邮件约看房。 2. 系统记下邮件已发送。 3. 智能体准备在日历上占一段时间，但还没来得及就崩溃了。 4. 之后的一轮维护检查发现：邮件已发，日历占位却没有。 5. 恢复时跳过邮件，只补上日历操作。

这是 Jones 提出的恢复流程，LLM Wiki 模式并不会自动提供修复日历的能力。恢复时最关键的输入，是记录下来的动作状态：已经发出的邮件必须保持“已完成”，哪怕整个任务重新跑一遍。

恢复看房请求，不重复发邮件 恢复时跳过什么，由完成记录决定。 构造示例：对象 ID 和状态标签只是用来示意 Jones 描述的场景。恢复后的状态展示的是演讲中描述的恢复结果，并非实际运行时观察到的结果；示例没有虚构任何房源编号或日历时间。 中断的任务——保持不变：询问房产经纪人能否看这套新房源，并在日历上占用相应时间。 操作：查阅记录下的动作状态，跳过已完成的邮件，补建缺失的日历占位。 - 给经纪人的邮件 - 之前：崩溃后：已发送 - 之后：恢复后预期状态：已发送 - 记忆中的邮件动作 - 之前：崩溃后：记录为已发送 - 之后：恢复后预期状态：记录为已发送 - 日历占位 - 之前：崩溃后：不存在 - 之后：恢复后预期状态：已按看房时间创建 恢复时跳过什么，由完成记录决定。

09

把证据与权限分开

威胁建模从熟悉的安全实践做起：校验输入、只给必要的最小权限、限制每个动作能碰到的范围。Relocation Scout 读的是陌生人提供的材料——卖家写的房源描述、匿名论坛帖子、社区评价。这些材料是不可信的证据，不是指挥智能体行为的指令来源。

权限边界正是从这个区分来的：

- 自主调研： 读取房源，整理候选清单。 - 需要人工批准： 给卖家发邮件、预约看房或提交报价。

房源可以作为推荐的依据，但不能授权任何外部操作。把影响重大的操作放在审批之后，就算智能体处理错了输入、得出了错误结论，波及范围也有限。

10

让系统在冷启动时也容易理解

一个系统技术上能跑，也可能很难维护。Jones 担心，把整套设计都交给编程智能体，它可能写出一个巨型提示词，或者拆是拆了，职责却没放对地方。理解架构，本身就是对它负责的一部分。

她的系统每一层都有一个 AGENTS.md 文件。这些文件说明工作流程，指出策略写在哪里，指向配套的技能、脚本和子智能体，还交代了怎样让记忆保持最新。有了这些文档，人或智能体都能很快摸清情况，不用从一堆提示词里倒推。

最实际的检验是冷启动：带着全新上下文进来的智能体，应该能自己弄清该做什么、从哪里开始。结构清晰，也更方便让另一个框架里的智能体来修改系统。如果这类修改做起来很费劲，Jones 会把它当作反馈：系统的可维护性还得改进。

设计智能体，是把系统思维、工作流、分解、复用和职责分配用到一套新的组件上。契约把这些组件连起来；状态让它们的工作能够恢复；安全边界和文档让整个系统可控、好懂。开头那种搭东西的乐趣，正是从这里回来的。工程纪律还在，只是工作往上挪了一层。

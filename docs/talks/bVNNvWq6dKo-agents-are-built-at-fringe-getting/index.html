Windsurf 的早期演示展示了共享的活动历史、持久的上下文和由模型主导的调研，如何把代码生成变成一个协调一致的开发工作流。

01

补全下一个函数之后是什么？

AI 已经能帮你写完一个函数。要让它接着干你手上的活，还差什么？2022 年，Copilot 的灰色补全建议让 AI 辅助第一次变得看得见、摸得着：写几行代码，看到补全，按下 Tab。Codeium 随后推出了自动补全扩展，支持 VS Code、JetBrains、Vim 和 Emacs。据 Windsurf 产品工程负责人 Kevin Hou 介绍，这些扩展吸引了几百万用户。

自动补全是个不错的起点。但它的交互方式默认模型每次只贡献一小块。更大的模型、更好的训练、强化学习和工具调用，指向了另一种分工。开发者不必一遍遍接受补全，也不必从 ChatGPT 里复制答案，可以把更长的一段工作直接交出去。这是 Windsurf 的第一场演讲。Hou 在演讲里认为，连 IDE 本身都可能只是过渡形态。底层智能会不断进步，不变的目标是做出最好的软件开发体验。到 2025 年初，这个方向落地成了一个智能体编辑器。

02

在开发者工作的地方构建爬虫

第一个演示让 Cascade 写一个 Python 网页爬虫，统计某个网站的数据。Cascade 是 Windsurf 侧边栏里的智能体。它做的不只是生成一个源文件：它会用 pip 安装依赖、配置虚拟环境，再给出修改建议，每处修改都可以接受或拒绝。它执行的命令会出现在开发者的交互式终端里，开发者可以随时查看，也可以随时介入。

下面这个小小的 Python 示例，把爬虫的分工讲得更具体：抓取页面，解析页面，报告一项统计。它只用来说明任务，并不是演示中那份 web_crawler.py 的原样复现：

```python from html.parser import HTMLParser from urllib.request import urlopen import sys

class LinkCounter(HTMLParser): def __init__(self): super().__init__() self.links = 0

def handle_starttag(self, tag, attrs): if tag == "a" and any(key == "href" for key, _ in attrs): self.links += 1

def page_stats(url): with urlopen(url, timeout=10) as response: body = response.read() charset = response.headers.get_content_charset() or "utf-8" parser = LinkCounter() parser.feed(body.decode(charset, errors="replace")) return {"bytes": len(body), "links": parser.links}

if __name__ == "__main__": print(page_stats(sys.argv[1])) ```

写函数只是智能体工作的一部分。整个工作流还得把环境、执行过程和修改建议都摆到明面上。

编辑器还支持查文档、网页搜索（默认开启）、用 grep 搜索代码库、自动生成 commit 信息，以及拖拽图片。演示里截取的爬虫画面说明了这些能力为什么要放在一起。画面上，web_crawler.py 旁边是终端里的报错 traceback，还有 Cascade 修复后重新运行的步骤。画面停在调试的中间状态，统计报告还没出来。

03

更少的显式输入，更多的运营责任

产品目标是让开发者尽量少输入，同时产出正确、能直接上生产的代码。 开发者在写代码的间隙要干不少杂活：读堆栈信息，找到真正需要改的源代码，查对应包版本的文档。这些活都要揽过来。智能体在后台做调研，再预测下一步，开发者就能把更多注意力放在功能和产品上，不用老被打断去给智能体拼凑上下文。

Windsurf 于 2024 年 11 月 13 日发布，距这场演讲大约三个月。Hou 称，头三个月里一共生成了 45 亿行代码。用户交给 Cascade 的任务包括重构、开发新功能、新增网站页面。这个数字只是生成量；其中多少被接受、保留或重新生成，演讲没有说明。

需求暴涨也暴露了服务能力的瓶颈。Hou 说，大约 90 天里，他有 16 个晚上被 PagerDuty 叫醒，原因都是需求超出了容量。他形容公司是 Anthropic 和 OpenAI 最大的客户之一。智能体替开发者干的活越多，产品背后的运维压力也越大。

04

一条共享的时间线补上了缺失的意图

第一条工程原则是轨迹（trajectories）：根据开发者正在做的事，判断接下来该做什么。Hou 拿 Windsurf 和 Cursor 对比，强调的是跟编辑器的深度集成。智能体既要能观察，看懂开发者在做什么；也要能执行，根据看懂的东西动手。最后的交互可以短到一句“接着干我的活”，结果可能是一次 commit，甚至一个完整的 pull request。

执行环节仍然要有选择地把关。Hou 介绍，有一个 LLM 负责判断终端命令能否自动运行。Git 命令属于常规操作，rm -rf 则多半会弹出确认。这些只是在举例说明设计意图，不保证每条命令都这样处理。接受/拒绝按钮是另一道关口。开发者可以先审一遍修改，再决定要不要并入准备上线的代码。

实现方式是一条统一时间线，开发者和智能体的操作都记在上面。查看文件、跳转、搜索、grep、编辑、commit，都会变成上下文。人改了代码，智能体的理解也要跟着更新，跟它自己改代码时一样。这是为了避免一种常见的协作事故：助手还按旧的文件状态行事，把开发者刚改的东西又改了回去。这段共享历史是整个编辑器的组织原则，不是等用户发消息时才附上的上下文。

下一个演示按这套机制走了一遍具体流程：

1. 开发者新增一个函数，自动补全在旁边帮忙。 2. 开发者让 Cascade 接着干。 3. Cascade 推断出表单处理函数应该调用这个新函数，并修改了相关文件。 4. Cascade 在终端面板（用 Command-J 打开）里运行 npm run dev。

提示词里没有讲明新函数和表单处理函数是什么关系，这层关系来自最近的编辑记录。Hou 说这种交互能把几分钟的活缩短到几秒，但没有给出计时对比。

05

在同一个环境中观察和行动

终端操作同样能透露意图。开发者跑了 npm install 或 pip install，智能体就该认出新装的包，再结合代码库的上下文，推断该怎么接进去。开发者不必再把命令复制回聊天框。Hou 想把这种“免复制粘贴”延伸到文档和网页。但他不认为终端本身就该成为未来的全部界面。

光能观察还不够，执行要是发生在别处，照样白搭。Hou 说智能体的命令跑在沙箱里，但交互发生在开发者自己用的那个终端环境里，而不是某个毫不相干的后台 shell 脚本。这个例子的关键是环境一致。不管是人还是 Cascade 装了 Python 依赖，都应该装进项目实际运行的环境。沙箱的隔离边界在哪里，演讲没有说明。

智能体一旦能跟上操作轨迹，“接着干”就能升级成“提前想”。开发者仍然是这套构想的中心，但智能体会看得更远。Hou 设想把预测从几步扩展到几十步。他举了两个未来的例子：函数定义还没写完，单元测试就已经写好；变量刚改完名，整个代码库就跟着重构完。这些是共享时间线思路的延伸，比刚才那个“接着干”的演示走得更远。

06

记住当前任务无法告诉你的东西

轨迹能解释眼前的任务，却装不下资深工程师对项目的全部了解。组织规范、架构决策、个人偏好，都是一点点积累起来的。通用模型能力再强，也未必接触过这些。Windsurf 的第二条原则元学习（meta-learning）就是为了补上这个缺口：把开发者和所在组织的上下文记下来。

产品把几种机制组合在一起：

- 记忆： 记忆库会记住各种事实，比如项目用的是 Tailwind 4，用的是 React 19 而不是 React 18。Hou 说，目标是只告诉智能体一次，它就永远记得。 - 工具集成： 通过自定义 MCP 服务器，把智能体接入开发者惯用的工具和工作流。 - 命令策略： 用允许列表和禁止列表表达执行偏好，比如任何 rm 命令都必须先经过批准。

这几种机制合在一起，开发者就不用反复写同样的提示词。更长远的目标是让助手的行为体现积累下来的上下文，开发者不必每做一个任务就重新交代一遍。

记忆演示不只是明确告诉它“记住某件事”。开发者问这个项目是做什么的，Cascade 就去翻文件和路由。弄明白之后，它把对架构和可用接口的理解存下来，留给后面的消息和以后的对话用。Hou 说，这样后续的工作一条提示词就能搞定。查文档也是同一个思路：从 package.json 里读到的包版本，或者用户告诉它的版本，决定了它去搜哪个版本的文档。

由此引出显式上下文和推断上下文的区别。Windsurf 支持规则文件，但 Hou 认为手动维护这些文件只是暂时的负担。他预测，到 2025 年底，规则文件里 99% 的内容都能从代码库或产品使用情况中推断出来。这是对个性化的预测，不是已经展示出来的成果。他设想的系统能适应不同的公司、不同水平的开发者，不用一遍遍索要同样的指令。演讲介绍的是 2025 年初的产品。录像附带的后续文档讲的是 Devin Desktop 里的旧版 Cascade，两者不是同一时期的产品，不能混为一谈。

07

让更好的模型消除交互成本

第三条原则是随智能一起扩展（scale with intelligence）。智能体能看懂当前操作，又能留住长期上下文。接下来，它的架构应该让更强的模型把这些输入变成更好的产出。所以规划不能只盯着眼下这一版，要看到接下来几个月甚至几年，哪怕新模型、新技术层出不穷。

ChatGPT 在 2022 年 11 月发布，最初的兴奋很快就撞上了天花板：很多事模型没法稳定做好。各个团队只好用 embedding 索引、检索启发式规则和输出校验系统来弥补。Hou 批评的是围绕某个固定的智能水平做设计。这些基础设施是给模型短板打的补丁。等短板慢慢补上，补丁反而可能拖住产品，让它吃不到模型进步的红利。他并不是主张把检索和校验全部拿掉，Windsurf 后面的例子仍然依赖检索。

落到产品上，一个结果是用 Cascade 取代了旧版聊天。用户还是通过对话界面交互，背后却换成了能规划、能行动的智能体。Hou 认为，用户可能只会觉得回答变好了，察觉不到底层的聊天实现已经换掉了。

上下文选择是个更具体的例子。过去系统不擅长找出相关的代码和文档，用户只能靠显式的 @mentions 来弥补。如今这些能力提升了，检索和智能体规划能自动补齐更多需要的上下文。Hou 称，90% 的时候都用不着显式 @mentions，但他没有说明是怎么评测的。在少数需要给智能体指方向的场合，@file 和 @web 依然有用。目标是让日常工作不再非得先指好方向。

比如要给一个 Next.js 应用接入 Supabase。开发者不必再堆一串 @web、@docs、@codebase 引用，只要让智能体把 Supabase 加上就行。智能体会判断出得先做调研，于是去搜网页，再自己决定读哪些内容。

| 调研决策 | 由模型主导的做法 | | --- | --- | | 哪些结果有用？ | 挑出与任务相关的搜索结果。 | | 哪些内容有用？ | 只读页面里相关的部分。 | | 下一步做什么？ | 用收集到的上下文作答。 |

Hou 拿这种做法跟写死的调研规则对比，也跟一个假想的 embedding 索引对比，他预计后者效果会更差，但没有拿出实测数据。真正关键的机制，是把调研决策交给模型。模型的判断力一提升，整个工作流就跟着变好。他预计同样的方向会延伸下去：更多无人监督的工作，完整的 pull request，复杂文档的阅读。

08

从建议代码到承担更多工作

收尾的愿景把 Windsurf 的底层引擎放在中心：自己推断规范，不再要求写规则文件；直接生成 commit 和 pull request，不再止步于零散的修改。Hou 把这些定为 2025 年的方向。

Hou 称，Cascade 生成了用户所写代码的 90%，而自动补全只有 20%–30% 左右。他口头的一处更正很关键：这个数字说的是代码占比，不是用户占比。收尾幻灯片上写的是“超过 90%”。用户群体、观察时段、分母、接受标准，他都没有给出。所以这些数字只反映他所说的代码生成比例的变化，不能当成实测的生产力或正确性提升。

这种变化改变了工程问题本身。智能体承担的工作越多，开发者就越需要一个能参与开发过程的工具，而不只是一个帮你补出下一段代码的工具。Hou 最后鼓励开发者把智能体用起来，并指了指屏幕上的下载二维码，还提到演讲时有免费版可用。

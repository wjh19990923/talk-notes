How I cloned Adobe with AI

ArtCraft used coding agents to build a functional Photoshop approximation in about 24 hours. It paired familiar editing controls with script and agent access, then hit a CI bottleneck as the project grew. Its forthcoming software factory, Autocraft, would use its own development decisions for evaluation and post-training.

01

What owning your tools lets you do

A weekend spent editing a short film could leave you with a bill long after the work was done. Brandon Thomas, a filmmaker and the founder of ArtCraft, used an Adobe plan to explain the problem at CODE Summit 2026. The plan he described billed monthly, carried a longer commitment and could cost around $200 to cancel early. By the time he took the stage, ArtCraft’s open-source Photoshop approximation had gone viral.

On the early web, running your own IRC server let you choose a client and write programs to automate it. Public APIs let developers combine data from Reddit, Flickr and Twitter into services of their own. MySpace users could change their pages by editing HTML and CSS. Buying an MP3 left you with a file you could keep. Ownership had several practical meanings, from keeping a copy to running the service yourself.

Broadband, smartphones and simpler products made the web usable by more people. Thomas welcomed that reach. As platforms displaced open protocols, though, some of the APIs that made those mashups possible disappeared, and large providers gained control over mobile software distribution. The Adobe subscription was his example of what that loss of control could mean for someone who needed a tool for one job.

02

Artists build the interfaces their studios need

ArtCraft started with a desktop AI tool for professional filmmakers. The files it generated lived on the filmmaker’s machine, next to the editor that would use them. ArtCraft opened the desktop software and its supporting infrastructure. Advisers doubted artists would care about open source. Then artists started using coding assistants to build their own workflows on top of the software.

Microdrama studios made the opportunity concrete. Thomas described teams doing $30,000 to $50,000 in order fulfillment each month, with delivery requirements specific to their business. Staff could take ArtCraft’s APIs and use a coding assistant to generate an interface that fit how the studio delivered its work. That suggested a way to tailor the editors themselves. A studio could make five or ten variants of the same app, each pared down to the controls an artist needs for their part of production.

03

What went into the 24-hour Photoshop build

Photoshop was the first test. ArtCraft assumed the model could draw on tutorials to infer how a photo editor should behave. The team wrote a long prompt that asked for a plan for each editing tool, along with data structures and file-format importers. It also asked for the graphical interface to be separate from application logic and for the app to support both a command-line interface (CLI) and the Model Context Protocol (MCP). That design gives an artist controls to click, a script commands to run, and an agent tools to call. 9:26 in the recording

Within 24 hours, the team had a functional editor that already felt familiar. Thomas reported that it started roughly ten times as fast as Photoshop, with the test conditions unspecified. Feature coverage took longer. ArtCraft’s own estimate of parity had moved from 50% to just over 60% by the talk.

ArtCraft chose to keep working toward parity so artists could carry over their muscle memory. Photoshop also gave the team a reference for judging what the agents had built. New interfaces designed around agents could come later. The immediate job was to make more of the operations artists already knew work in the open-source editor.

04

A Reddit post brings in new users and bug reports

ArtCraft applied the approach to other Adobe apps, including InDesign and Premiere. Thomas had held off posting on Hacker News when the project surfaced on Reddit. About two days later, The New York Times asked him for an interview, and ArtCraft’s Discord grew from a base of 3,000 members. Thomas credited some of that interest to users’ frustration with Adobe and other vendors.

Some artists who had pushed back against AI started using the apps and sending feature requests and bug reports. A familiar desktop editor gave them a way to try software built with AI through work they already did. Thomas saw a path from there to teaching artists to use MCP on their own projects and finding parts of the interface they could simplify.

05

Beyond Adobe, from PDF tools to collaboration servers

ArtCraft and its contributors took on alternatives to the core Microsoft Office apps and Google Docs, along with Flash-style tools and digital audio workstations. Companies and universities approached the team about using the apps. The different projects called for different kinds of infrastructure.

- PDF on Linux and NetBSD. Thomas singled out the PDF app as ready to use. He emphasized how quickly and smoothly it ran and named Linux and NetBSD as supported platforms. - Shared design documents. The Figma-style project included a server so teammates could collaborate on documents. ArtCraft opened the server infrastructure and data model alongside the client. Thomas mentioned Raft and Paxos when describing the multi-user setup. The coordination algorithm the server used remains unspecified. - CAD for 3D printing. Engineers lead SolidCraft, a community CAD project whose open engineering kernel handles modeling. Its MCP support lets an agent call SolidCraft tools for work on a 3D-printing project.

06

Linux, localization and reusable app components

A cross-platform desktop launcher gave users one place to manage their ArtCraft apps. At the time of the talk, Thomas reported about 1.7 million downloads per day and said about a quarter of users were on Linux. The apps treated MCP and CLI access as core features. A script or agent could issue commands while a user watched the project take shape in the desktop app.

Contributors localized the apps. Thomas cited Arabic as a gap users had raised around InDesign. ArtCraft also picked up work on an Adobe Animate alternative as the original’s future looked uncertain. Animation studios told the team they relied on the tool for paid work and asked for continued support. 15:10 in the recording

Thomas put the community at around 4,000 developers, with more than 300 apps under development. ArtCraft had built a tool to help people without a technical background start from existing apps. The team was also breaking the apps down into reusable UI components and primitives, with 2D and 3D libraries planned. Contributors could build on shared parts and spend more of their time on the behavior specific to their app.

07

Native Rust apps and the work of scaling CI

ArtCraft had seen similar projects use Electron. Thomas wanted native GUIs for creative work and chose Rust for fast startup and the range of platforms it could target. He cited builds on NetBSD and tablets and pointed to WebAssembly as a route to the browser. Some teammates were new to Rust, and Thomas recommended coding agents to engineers starting with the language. The tradeoff he singled out was compile time. Each slow compile delays feedback on whether an agent’s change builds.

The project ran into GitHub permissions and scaling problems. Continuous integration (CI) was struggling to keep up, so ArtCraft started setting up its own CI. The team found a source of RAM for colocated servers and was moving CI onto those machines. 17:21 in the recording

08

Which changes need human direction

Thomas recommends putting humans in charge of backend work, schema migrations and API design. A migration can change how persistent data is stored, and an API decision affects what downstream callers can depend on. He would give agents more freedom to implement desktop apps and games when the output is essentially a replaceable build. People can set the direction and let agents carry out more of the implementation on their own.

One community member had 40 machines working on a Rust rebuild of Unreal Engine. The project was underway at the time of the talk. Thomas offered it as an example of how much implementation work one person could set in motion with agents.

09

Autocraft turns development decisions into training data

Autocraft is the autonomous software factory ArtCraft planned to release as open source. The workflow is defined in code, giving a team a way to specify how it wants to run development on a project. Autocraft takes in issues, triages them and uses coding agents for development. 18:08 in the recording

ArtCraft plans to use the choices the factory makes as data for two purposes. Evaluations would assess how the system makes decisions, and post-training would use those decisions to train it further. Thomas described both in terms of decision trees, with the scoring criteria and training procedure still unspecified. 18:51 in the recording

Thomas closed by proposing that platforms be rebuilt as open protocols. IRC gave the talk a concrete example of what that would buy. People could run their own servers, choose their clients and write programs to automate the service. Thomas wants that freedom to extend from the creative apps themselves to the infrastructure, protocols and models behind them.

Where do Autocraft’s decisions go? Triage and development both contribute decisions. Evaluation and post-training are two planned uses of that same data. - Issue intake — Autocraft receives incoming issues. - Triage — Autocraft decides how to handle issues. - Agentic development — Coding agents carry out development work. - Decision data — Choices made by the factory become data for later use. - Evaluation — Use the choices to assess decision-making. - Post-training — Use the choices as examples for further training. - Issue intake → Triage (Incoming issues) - Triage → Decision data (Triage choices) - Agentic development → Decision data (Development choices) - Decision data → Evaluation (Evaluation data) - Decision data → Post-training (Training examples)

要点总结

  • Separating the graphical interface from the editor’s operations let ArtCraft keep familiar controls while giving scripts and agents ways to drive the app.
  • Thomas recommends giving agents more autonomy on replaceable builds and having humans lead decisions that shape stored data or affect API callers.

MCP 被过度炒作了吗？一通关于 MCP 的吐槽

MCP 标准化了模型连接服务的方式，但有用的智能体仍然需要服务发现、信任、可靠的托管、支付，以及它们真正能挑选和使用的工具。

01

一个解开的谜题不等于一个有用的智能体

2024 年 11 月，Henry Mao 一头扎进了 ARC-AGI，想把它攻下来。任务看起来很简单：给你两三个网格变换的例子，推断出规则，再补全缺失的输出。Mao 是 Smithery 的创始人兼 CEO、MCP 指导委员会成员，此前联合创办了 Jenni AI。他盯上这道题，是因为它似乎暴露了人类推理和语言模型之间的差距。他说人类的准确率大约是 80%。这只是个大致基线，他没有说明对应的是哪一组任务。

随后，OpenAI 的 o3 改变了局面。Mao 说它在 ARC-AGI-1 上达到了人类水平，数学成绩也很亮眼。这次历史性突破指的是 2024 年 12 月的 o3 预览版，不是后来正式发布的模型，成绩也取决于算力配置。照此推下去，结论似乎是 AGI 已经实现、自主智能体可以包揽一切——这话他是故意反着说的。到了 2025 年，一个显而易见的问题依然没有答案：替人干那些不想干的活的智能体，到底在哪儿？前沿智能依然被困在盒子里。

02

上下文和能力需要连接

要让智能体真正有用，得关注上下文和能力：哪些信息能进到模型里，哪些动作能从模型发出去？光有智能，模型既访问不了代码仓库和工单系统，也调用不了这些服务提供的操作。这些输入和输出需要一个集成层。

Anthropic 在 2024 年 11 月推出了 Model Context Protocol，用来统一这些连接。没有共享协议，每个模型应用都得为每个服务单独写集成，这就是 Mao 说的 N×N 问题。有了 MCP，应用和服务之间有了通用的沟通方式，不必再为每一对组合从头做一遍集成。

模型更聪明了，服务通信有了标准，开发者社区虽小却很活跃，这些让 MCP 成了很有吸引力的基础。但通用协议只是起点，生态还得一点点搭起来。服务一旦开始面向智能体，发现、安装、运维和商业关系就各自成了独立的难题。

03

找到服务器只是第一道坎

MCP server 越来越多，想找到高质量的反而更难。演讲时，MCP 委员会正在做官方注册中心（registry），Mao 特别感谢了 PulseMCP 团队。注册中心解决了“去哪儿找”，却解决不了怎么评定信誉、怎么区分靠谱的 server 和差劲的 server。

顺着从发现到真正用起来这条路往下走，用户还会碰到这些问题：

- 安装： Mao 提到，有些 GitHub 仓库要走五步才能装好。智能体还没拿到任何能力，每一步都在增加阻力。 - 安全： 装好了，不代表装上的 server 是安全的。 - 支付： 智能体需要一种方式，代表用户为服务付费。Mao 举了个例子：总不能订阅 100 个服务、每个每月 10 美元吧。生态除了连接协议，还需要一套行得通的购买体验。

04

托管一个工具与让它被调用是两个不同的问题

Streamable HTTP 让 MCP 开发者能用上更多托管平台，但运行时的设计决策依然绕不开。有状态会话和可恢复性仍可能带来运维负担。在 2025 年 3 月的传输规范里，会话 ID 和可恢复性都是可选项：只有 server 用到这些能力时才会碰上这个难题，并不是每个 server 都必须维护可恢复的状态。

官方的 MCP Inspector 提供了测试工具、查看提示词的基本手段。开发者可以借它检查接口，但 Mao 接下来关心的是智能体碰到这个接口时会怎样：server 该怎么设计？模型会不会调用它的工具？怎样才能带来最好的智能体体验？一个工具可以已经上线、也能测试，但它对智能体到底有没有用，仍是个没有定论的设计问题。

05

上线之后工作仍在继续

server 发布之后，开发者又面临一组新需求：

| 需求 | 上线后的问题 | | --- | --- | | 分发 | 别人怎么发现这个 server？ | | 可观测性 | 开发者怎么从使用情况中学习、改进它？ | | 变现 | 这个服务怎么赚钱？ |

这些问题和用户那边的问题互相关联，但并不相同。用户要找到有用的能力，并为之付费；开发者要有一条触达用户的路，还要看得清使用情况，才能改进自己的服务。

Mao 说，他大约在 2024 年 12 月创办了 Smithery，就是想把两边的问题一起解决。它的目标是成为一个 AI 网关，培育并编排专为智能体打造的服务。这比单纯罗列 server 要宽得多：从开发者发布一项能力，到智能体成功用上它，中间整条路都归它管。Mao 也承认，对于他列出的这些问题，Smithery 目前只触及了皮毛。

06

从一个 GitHub issue 到一张 Linear 工单

Smithery playground 展示了部分连接问题解决之后能做到什么。Mao 介绍说，它能让智能体访问数千个精选的 MCP server。他提的请求是：在 smithery-ai/cli 里找出最紧迫的问题，再到 Linear 里新建一个工单。这里的仓库名沿用录像中的写法，公开链接现在会跳转到 arcadeai-labs/smithery-cli。

从画面上看，整个流程既涉及发现，也涉及执行：

1. 搜索 server。 提交提示词后，智能体先把任务想一遍，再调用 search-servers 函数在 Smithery 的目录里查找。 2. 连接服务。 它连上选中的 server 和 Linear。 3. 读取 GitHub issue。 它通过 GitHub MCP 拉取 bug，从中找出优先级最高的一项。 4. 创建目标工单。 它找到一个 Linear 团队，然后创建工单。

playground 显示工单已创建。确认信息里有 SMI-374、一个关于连接错误的标题、优先级 High (2)、Smithery 团队，以及一个 Linear 链接。到这一步，请求的动作变成了汇报的结果：智能体从 GitHub 读取了信息，又写进了 Linear。

接着，Mao 打开工单，指出里面内容很详细，还附有指回原始 GitHub issue 的链接。这次演示跨两个 MCP 连接完成了一项任务，新工单也能追溯回它的来源。不过，演示本身证明不了选中的 issue 确实是这个仓库最紧迫的问题；排优先级仍是演示中智能体自己的判断。

07

为工具调用而设计

这个演示刻意做得很窄，但服务越来越多，智能体能完成的任务也会随之扩展。Mao 在结尾展示了过去几个月部署量和工具调用量的增长，工具调用图表的标题是“90K+ Tool Calls / Day”。这些采用数据，加上开发者的热情，是他相信生态能解决剩余问题的底气。

他更大的预测是：未来的互联网将以工具调用而非点击为主，智能体体验会比用户体验更重要。到那时，一个服务真正的“接口”包括：智能体能不能发现它、知不知道什么时候该用它、能不能顺利连上、能不能完成有用的操作。要打造这种体验，得靠更广泛的开发者社区一起出力，而不只是 Smithery 或少数几家公司。

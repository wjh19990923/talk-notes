2026：IDE 消亡之年

编程智能体就像一把威力巨大的电钻，却缺少让它精准作业的机械装置。Steve Yegge 和 Gene Kim 探讨了协同的智能体、对话式开发和组织变革可能会用什么来取而代之。

01

编程智能体是一把电锯，还不是数控机床

电钻在熟手手里能干出漂亮活。把同一把电钻或电锯交给没受过训练的人，就可能闯下大祸。Claude Code 也是这样一笔交易：能力惊人，脑力负担不小，一不留神还可能把自己的"脚"锯掉。1:27 1:40

老练的匠人能精准驾驭这股力量，可软件项目越做越大，背后的野心也在不断膨胀。Steve Yegge 预言，下一步会像从手持电动工具走向数控（CNC）机床：把钻头固定好，给定坐标，交给一套协同系统执行，每次都一样精准。1:49 2:00

这场转变并不需要模型无限变强。Yegge 认为，就算模型能力到顶，行业也已经找到了堪比蒸汽或电力的东西，眼下要解决的是怎么驾驭它的工程问题。他的预测故意说得很满：大约一年到一年半之内，工程师会转而监管大规模的代码生成系统，不再逐行看代码。2:22 2:39

02

采用鸿沟先于自动化革命到来

Yegge 讲起他和 Andrew Glover 的一次谈话：OpenAI 的工程师在采用上分成了两拨，有人用 Codex，有人不用。他说两拨人的生产力差距大得惊人，连绩效评估都变得棘手，但他既没给出明确的生产力指标，也没有独立验证过的结果。组织真正担心的是：职级相同的工程师，手里撬动的杠杆可能根本不是一个量级。2:52 3:02 3:12

按他的说法，资深工程师和 staff 工程师抵触得尤其明显。他把这种怀疑比作机械表匠人面对石英表：在一门成熟手艺里练出的功底，会让人觉得一种更便宜、更陌生的生产方式不值一提，直到整个市场围绕它重新洗牌。3:29 3:44 3:57

Yegge 预测，出路不是再做一个只能在终端里用的编程助手，而是一种更容易上手的开发界面：它负责协调工作，但又不是把传统 IDE 原样再造一遍。他举了 Replit Agent 作为朝这个方向迈进的例子。4:09 4:17 4:27

03

一只巨蚁、一个氧气瓶和一群专家

大自然造的是蚁群。Steve Yegge 说，如今的编程工具却可能在造世界上最大的一只蚂蚁：一个庞大又吃资源的通才，所有请求都派给它。这个比喻出自 Brendan Hopper。Hopper 的意思是，把所有能力都堆到一个肌肉发达的工人身上，连普通任务也要耗掉过多资源。4:42 5:01

对比一下分析整个代码库和问一句 Is .gitignore still there?。两个请求都交给同一个昂贵的模型，可后者只需要看看 .gitignore 还在不在。这只是一次范围明确的检查，用不着改文件，更用不着一队智能体轮番上阵。5:12 5:19

幻灯片出了故障，Yegge 又换了个比方：在代码库里探索的智能体是潜水员，上下文窗口是氧气瓶。一个潜水员只有这一瓶氧气，既要用来理解请求，又要应付后面的所有事情。哪怕是百万 token 的氧气瓶，也总有用完的时候。真正铺得更开的工作，他的方案是分出产品管理、编码、评审、测试和 Git 合并几个潜水员，各自只管一块边界清楚的职责。5:28 5:33 5:44 5:55 6:06

下面的对比区分了两类工作。一类是演讲里提到的 .gitignore 存在性检查，一个工人看一眼文件列表就能搞定。另一类是为教学构造的 CSV 导出示例：实现和验证各有各的关注点，值得在不同专职角色之间传递具体产出。设计这些交接，是因为导出功能确实跨越了实质性的边界；简单的检查则没有。6:16

范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 展示交接在什么情况下能带来真正不同的有效工作，而不是重复潜水员的比喻，或者鼓励堆智能体数量。 - Is .gitignore still there? — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - .gitignore — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - 添加 CSV 导出 — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - 需求 — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - 补丁 — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - 权限审查 — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。 - 测试用例 — 范围明确的检查交给一个工人就够了；只有另一项任务确实横跨需求、实现和验证几方面时，才需要交接。

背后的工程原则是任务分解、逐步求精、组件化和黑盒边界。关键是量体裁衣：一个范围明确的问题，交给一个工人；另一项任务确实牵涉多个方面时，再用范围合适的智能体和交接。不断把一个通才做大，替代方案并不是把智能体数量拉满，而是让工具和活儿相匹配。6:16 6:27

04

一次刻意挑衅的、对熟悉 IDE 的告别

Yegge 把这个预测变成一条故意挑衅的截止线：1 月 1 日之前学会用编程智能体，放下熟悉的 IDE，改掉这些老习惯。他自称对那些还守着 IDE 的工程师的评价是一句"暴论"，台下一片笑声。6:34 6:43 6:49

Jordan Hubbard 一条帖子下的回复，最后提醒大家：这股反弹不只是技术问题。哪怕有人讲清楚了怎么高效使用这些工具，开发者对智能体辅助的工作仍可能反应激烈。Yegge 点出了这种文化阻力，但没给出完整的解法，就把话筒交给了合著者 Gene Kim。6:58 7:16 7:27 7:32

05

Gene Kim：改变软件生产就是改变组织

Kim 从研究高绩效技术组织的角度切入同一场转变。他的工作始于 Tripwire，后来延伸到一个问题：为什么有些组织能同时做到项目交付高效、运维稳定、安全与合规也更强。DevOps 运动让他看到，生产方式一变，测试、运维和信息安全也会跟着重塑。7:43 7:52 8:01 8:13 8:21 8:30

更早的一个例子出自 Yegge 的 Google Platforms Rant。Kim 引用这篇文章好多年，才发现作者是谁。文中讲到亚马逊的 API 指令：一个单体应用把大约 3,500 名工程师捆在一起，后来公司要求各团队一律通过 API 通信，不许走后门依赖。落到组织上，结果就是明确的边界让各团队能独立行动。8:40 8:55 9:04 9:14

共同的兴趣让 Kim 和 Yegge 走到一起，合写了 Vibe Coding。他们预计，AI 辅助开发会重组技术团队，甚至可能重塑更广泛的经济，就像过去几次变革改变了软件的生产和交付方式一样。9:26 9:38 9:49 10:00

Adrian Cockcroft 在云时代挑起的 NoOps 之争，是个一针见血的先例：基础设施运维变革时发生过的事，可能会以 NoDev 的形式重演。Kim 由此想到，客服、设计师和 UX 从业者可以自己上线功能，不必等上几个季度甚至几年，等开发团队把他们的需求排进优先级。10:07 10:15 10:31 10:40 10:47 10:58

06

从年度发布到通过对话编程

Kim 早年的书 The Phoenix Project（《凤凰项目》）围绕灾难性的部署展开，那时很多组织一年才发布一次软件。2013–2019 年的 State of DevOps 研究共收集了 36,000 名受访者的数据；Kim 说，高绩效团队每天发布多次，一小时以内就能交付变更。11:09 11:22 11:30

频繁部署一开始听上去很鲁莽。时间一长，更小、更频繁的变更反而和更高的可靠性、更短的修复时间挂上了钩。Kim 认为，不再靠手敲每一行代码的软件开发，也可能走出类似的路。11:39 11:48 11:56

书里最初给 vibe coding 下的定义是：只要人不亲手敲代码，就算。Kim 引用了 Dario Amodei 更精确的说法：通过反复对话，最终由 AI 写出代码。这个词听着可能不太正经，但背后的变化实实在在：意图变成可运行软件的方式变了。12:06 12:19 12:35 12:44

编程语言设计者 Erik Meijer 把这种"代际"挑衅说得更狠：今天的程序员可能是最后几批手写软件的人。Kim 接着讲到，他看着 Yegge 每天在编程智能体上花掉几百美元，并设想把每天约 500–1,000 美元的 token 预算当作示意性目标，用来撬动足够的杠杆。这既不是实测出来的回报，也不是人人适用的花钱建议。12:57 13:05 13:14 13:30 13:40 13:49 13:55

07

FAAFO：更快、更有雄心、更自主、更有趣，以及更多选择

Kim 用 FAAFO 概括智能体辅助开发的吸引力，第一个是 faster（更快）。速度是最显而易见的好处，也是最表层的。更要紧的变化在于：实现成本降下来以后，哪些事变得可行了。14:05

Ambition（雄心）朝两个方向扩展。以前不敢想的大项目变得可以着手，小麻烦也便宜到可以随手修掉。Kim 讲了 Claude Code 团队的一个例子：一个客户问题大约 30 分钟就处理完并上线了，不用进 Jira 待办列表，再经历一轮又一轮的整理和梳理会议。14:16 14:29 14:44

Autonomy（自主）减轻了两种协调负担。第一，遇到问题的人也许不用再等待、谈优先级、层层上报，再说服整个开发团队重视这件事。第二，就算有协作者，LLM 也能借一份写明目标和共识的共享 Markdown 文件，帮不同专业的人沟通。14:55 15:07 15:23 15:32 15:41 15:51

Fun（乐趣）同样重要。Kim 说他发现，自己编程的黄金岁月也许还没过去；他投入到得逼着自己停下来去睡觉。吸引人的不是每个结果都完美无缺，而是开发没那么枯燥了，更能让人提起劲。16:02 16:14 16:22

Optionality（可选性）指的是不被困死在一个计划里。模块化创造选项，实现成本降低则带来更多出手机会：能并行跑更多实验，用更多方式探索一个想法，也更有余地调转方向。随之而来的管理问题是：怎样帮更多人走到同样恍然大悟的那一刻。16:31 16:41 16:52 16:58 17:13

08

一个小交付团队、一个 Neo4j 仪表盘和亲自交付的领导者

在 Enterprise Technology Leadership Summit 上，Kim 见到了几家组织的实际尝试。在 Booking.com，Bruno Passos 介绍了一项覆盖约 3,000 名开发者的推广，合并更快，同行评审周期更短；不过 Kim 没有为这组对比给出一个统一的综合生产力指标。17:22 17:33 17:43 17:54

在 Fidelity，Tapabrata Pal 负责一个应用，用来在约 25,000 个应用里找出哪些系统用了 Log4j。团队估计他想要的界面得做五个月，还得招一名前端专家。他干脆自己花了五天，基于一个只读的 Neo4j 数据库做了一个替代版本，并上线到了生产环境。18:58 19:06 19:17 19:26

信任就是可预测性；经验有帮助，但协调依然困难

Kim 讲到，他和 Google Cloud 的一个团队重新做 DORA 相关研究时，碰到一个关于 AI 信任的观察，最后没写进报告。这里的信任，不是认定模型永远正确或安全，而是能预判它的行为："我能在多大程度上预测对方会怎么做、怎么反应？"可预测性越高，请求就可以越大，指令可以越短，反馈也可以越少。21:04 21:15 21:23

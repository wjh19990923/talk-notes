两周内用 AI 分析一万通销售电话

Charlie Guo 在 Pulley 做的客户研究项目，展示了模型选择、可追溯的信息抽取、提示词缓存和一个可复用的界面，如何把一个通话记录档案变成一个好用的研究工具。

01

为期两周的分析挑战

一天能听多少通销售电话、同时记好笔记？按每通 30 分钟算，不休息干满 8 小时，能听 16 通。如果只留 8 小时睡觉，醒着的每一刻都在听，一天也就 32 通，一周七天是 224 通。

Charlie Guo 面对的是另一个量级：Pulley 的 CEO 要求两周内分析完 10,000 通销售电话，用来细化公司的理想客户画像（ICP）。按 Guo 的说法，这个项目一名 AI 工程师两周就能做完。放在以前，这种活得专门组一个团队干上好几周。难点在于，要把对话足够快地变成可信的客户研究，赶在业务决策之前给出依据。

02

从宽泛的理想客户画像到具体的客户证据

Pulley 原来的 ICP 是“有风投支持的创业公司”。这个画像能给产品开发指方向，但对市场营销来说太宽泛了。比起笼统的“创始人”，“一家早期加密创业公司的 CTO，公司拿了风投”这样的画像，能给营销人员更多抓手。要摸清这么具体的信息，就得去听客户怎么说。Pulley 的销售代表早已在这件事上花了几千个小时。

如果靠人工做研究，每通电话都要重复同一套流程：

1. 下载转录稿，通读对话。 2. 判断这段对话是否符合目标画像。 3. 在几百甚至几千行文字里找有用的洞察。 4. 整理笔记和报告，同时保留引用，方便日后核查。

按每天 16 通算，10,000 通电话需要 625 个 8 小时工作日。就算一天不歇，也要将近两年。即便全部读完，还剩下归纳综合这道难题：相当于记住一整座图书馆的内容，再据此写一篇读书报告。

常见的几种做法，各自都丢掉了某样关键的东西：

| 方法 | 优势 | 局限 | | --- | --- | --- | | 人工分析 | 解读质量高 | 应付不了这么大的工作量 | | 关键词分析 | 快且便宜 | 抓不住上下文和细微差别 |

大语言模型能在非结构化对话里识别模式，不必把每个问题都简化成关键词匹配。但要做出有用的研究，还得解决几个环环相扣的问题：选哪个模型、怎么控制没有依据的说法、怎么保留证据，以及这么大的工作量要花多少钱。

03

针对后果严重的错误选择模型

项目进行时，Guo 团队能用的模型里，GPT-4o 和 Claude 3.5 Sonnet 能力最强，但也最慢、最贵。更小更便宜的模型看上去很诱人，直到团队仔细检查了它们的分类结果。

两次失败暴露了“认出字眼”和“确认事实”之间的差别：

- 公司分类：销售代表提到了平台的区块链功能，一个小模型就把潜在客户归成了加密公司。这个功能只是推销话术的一部分，说明不了客户做的是什么业务。 - 人员分类：转录稿里找不到任何依据，模型却把一位潜在客户标成了创始人。

这类误报会让整个项目失去意义。客户身份认错了，报告写得再漂亮，分析也是错的。团队最终选了 Claude 3.5 Sonnet，因为它的幻觉率在他们能接受的范围内，不过 Guo 没有给出具体的错误率数字。一条无据分类付出的代价，比单次请求的价格更要紧。

04

让抽取出的发现可追溯

选模型只是保证可靠性的第一层。Guo 团队从原始转录稿入手，通过检索增强生成（RAG）引入第三方和内部数据来补充信息，再用思维链等提示词技巧改进结果。这样，模型解读对话时就有了额外的上下文，不必只靠转录稿本身。

第二层是结构化 JSON 输出，能用的地方都用它来生成引用。好的输出约定会把结论和证据绑在一起。拿前面区块链那次失败来说，可以把客户分类明确标为“未知”，而不是贴上一个没有依据的肯定标签：

``json { "transcript_id": "call-001", "company_sector": null, "evidence": [ { "line_id": "line-042", "speaker_role": "sales_rep", "text": "Our platform includes blockchain features." } ], "finding": "The sales representative describes a platform feature; the prospect's sector is not established." } ``

这条示例记录把证据的边界划得很清楚：引用的那行话只能说明销售话术，company_sector 仍然未知。这个项目用的是应用从 JSON 里生成的引用，不应把它看作 Anthropic 后来推出的原生 citations API 的演示。该 API 的发布时间可查阅 Claude 平台发布说明。

最终做出的系统能提取公司信息和客户洞察，每条结论都能顺着可核查的线索追溯到原始转录稿。有了这条线索，大家就能检查结论的依据，而不是把模型的回答当成权威照单全收。只是分析做得更细、又要把错误压低，成本也跟着大幅上涨。

05

减少重复的输入工作并拆分输出

用 Claude 3.5 Sonnet 时，Guo 经常撞上 4,000 token 的输出上限，分析一份转录稿往往要发好几次请求。当时还在实验阶段的两项功能，分别解决了两种不同的重复劳动。

Prompt caching 解决的是重复输入。团队先用同一份转录稿提取元数据，再提取洞察；有了缓存，后面的请求就能复用这份转录稿的内容。Guo 引用的数据是：prompt caching 最多能降低 90% 的成本和 85% 的延迟。这两个数字和 Anthropic 在 prompt caching 发布公告里宣传的上限一致，并不是这个项目整体表现的实测结果。写入缓存要额外收费，公告里的延迟示例测的也只是首个 token 的返回时间。到底能省多少，要看长提示词有没有被反复用上。

扩展输出解决的是回答不完整。打开一个实验性的功能开关，可用的输出容量就翻了一倍，摘要一次就能写完，不用把分析拆到好几轮里。它扩大的是模型能生成的内容量，不是输入的上下文窗口。回顾一下时间线：Anthropic 在 2024 年 7 月推出了 8,192 token 的输出 beta，8 月又取消了必须带 beta 请求头的要求。这里说的开关属于那段更早的 API 时期。

据 Guo 介绍，这些优化把分析成本从 5,000 美元降到了 500 美元，出结果的时间也从几周缩短到几天。这是他对项目整体的描述，没有附上账单或运行时间的明细。两种工程手段各管一头：缓存减少了转录稿的重复处理，更长的输出则省掉了为补完摘要而追加的请求。

06

研究基础设施惠及其他团队

更大的惊喜是，这套成果的用处远超预期。最初的用户是高管团队。按 Guo 的说法，他们想要的洞察，平时得花几十甚至上百个小时才能做出来。转录稿处理流程一搭好，其他团队也能拿来干自己的活。

- 市场营销：调取客户原话，用于品牌和定位工作。 - 销售：用这套系统自动下载转录稿。据 Guo 介绍，光是自动下载转录稿这一项，每周就为销售团队省下几十个小时。

价值不止于生成的研究报告：就连外围的数据获取工具，也替大家省掉了不少重复劳动。

各团队还开始提一些以前想都不会去想的问题，因为过去人工分析的门槛实在太高。语料变得触手可及，哪些研究问题做得了也随之改变。一堆杂乱的非结构化对话，就这样变成了大家共享的证据来源。

07

围绕模型构建系统

模型能力确实重要：在 Guo 的实验里，Claude 3.5 Sonnet 和 GPT-4o 能完成其他受测模型做不了的任务。但最终的选择，是把准确率和 prompt caching 放在一起权衡的结果。模型合不合适，既要看项目能容忍哪些错误，也要算清反复分析长转录稿的经济账。

模型周边的软件同样重要。结构化 JSON、设计得当的数据库 schema 和整体架构，都带来了明显的提升。AI 工程的关键，是围绕模型搭一套真正好用的系统：模型的输出要契合应用的数据结构和工作流，证据也要始终留给使用结果的人查看。Guo 的经验是，要把模型用心地融进系统，而不是事后随手加上去。

08

让客户研究成为一项可重复的运营工作

项目的终点不是一份报告或白皮书。团队围绕分析结果做了一个界面，提供搜索、筛选和导出功能。同事们可以用它找到相关材料，再带进自己的工作里。一个简单灵活的工具，就这样在全公司派上了用场。

这么做的目的，是拿掉卡住分析的瓶颈，增强人的分析能力。下载、阅读和整理语料不再耗光全部研究预算之后，大家就能去研究以前够不着的问题。处理得快了，能做的事也就多了。

这给每个组织留下一个实际的问题：有哪些客户数据其实早就在手边，却很少有人去看？销售电话、客服工单、产品评价、用户反馈、社交媒体互动，里面都可能藏着证据。Guo 最后发出的挑战是：用好现有的工具和技术，把这些被冷落的数据源盘活，开始把积攒下来的数据变成大家用得上的东西。

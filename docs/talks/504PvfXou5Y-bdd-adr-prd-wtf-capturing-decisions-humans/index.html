BDD、ADR、PRD，WTF：为人类和 AI 同样记录决策

决策记录、可执行的场景、可复用的 UI 模式和自动化检查，能在人们遗忘、智能体上下文消失之后，依然保留下产品背后的理由。

熟悉 Git、自动化测试和基于数据库的应用，有助于理解示例。

01

我们为什么还有这条规则？

所有人都忘了初衷，为什么产品里的某个流程、某个功能、某条架构规则还一直留着？Michal Cichra 在 Microsoft 和 Red Hat 工作过，又在同一个产品上做了十年，他从这些经历出发来谈这个问题。他在 Safe Intelligence 的团队刚发布了一款智能体测试产品。AI 带来的一致性问题，他们并不陌生：早在 AI 之前，团队就很难把决策背后的理由留存下来。

他从“五只猴子和梯子”的故事讲起。只要有一只猴子去够香蕉，所有猴子都要挨冷水浇；久而久之，猴子们会主动拦住想爬梯子的同伴。再把猴子一只只换掉，等到笼子里没有一只亲身挨过那次冷水，禁令依然还在。Cichra 也明说，这个故事可能只是都市传说。它在这里的价值是一个类比：理由早就没了，规则还能活很久。

人会遗忘，也会离开。LLM 的上下文会压缩，智能体也没法依赖对之前工作的持久记忆。总有一天会有人问：这个流程为什么存在？这个功能解决什么问题？代码为什么写成这样？这个改动该放在哪儿？而当初的创始工程师可能已经不在，没人能解释。这是组织里的老问题，AI 会让它来得更早。做出决策的人或会话不在了，理由也得能找回来。

02

记录架构上的理由和执行路径

架构决策记录（Architecture Decision Record，ADR）记下的是：某个技术选择为什么存在，团队打算怎么执行它。附上参考资料和代码示例，决策才能真正落地。文档要讲的不只是规则本身：碰到这条约束的人，需要足够的上下文，才能把改动做对。

Cichra 举的例子是一套分层架构，用来防止 N+1 数据库查询。import linting 限定哪些模块可以依赖哪些模块。读数据库返回的是普通数据结构，而不是 ORM 对象，下游代码就拿不到能暗中发起额外查询的对象。这道边界既管住了数据库访问发生在哪里，也管住了什么东西能流进应用的其他部分；他还把这些约束和避免重复代码联系在一起。他说，定义这个产品架构的 ADR 还有大约五十份。

ADR 没有强制格式。文本文档能解释一项决策，却没法靠自己让人遵守。得有一个单独的工具来检测违规，并给出有用的反馈：违反了哪条规则，规则为什么存在，问题该怎么修。智能体随后可以调出 ADR 查看细节。在 ADR 里写明相关的文件、文件夹或语言范围，出错时就更容易对应到相关代码和决策。

03

让产品目标保持轻量

产品需求文档（Product Requirements Document，PRD）保存的是另一种意图：功能为什么存在，解决什么问题，用户怎样在应用里一步步用上它。PRD 可以写得很短。关键是把三件事串起来：问题、期望的结果，以及用户从问题走到结果的路径。要留住这层联系，并不需要面面俱到的长文档。

实现功能的智能体用得上它，六周后回头再看这个功能的人同样用得上。记忆靠不住的时候，文档还能把最初的目的交代清楚。

04

让行为规格说明可执行

写好规格之后，还有一个验证问题没解决：怎么知道跑起来的产品确实符合描述？Markdown 能写下预期行为，却测不了实际表现是否一致。去审生成的测试也未必是个好办法；Cichra 觉得 AI 写的测试比 AI 写的代码还难读。行为驱动开发（Behavior-Driven Development，BDD）提供了中间一层：用人能读懂、能审的语言来描述行为。

Cucumber 让这一层能直接执行。场景可以直接关联 PRD 和关键用户旅程。场景里的每个步骤都对应一段代码，由它操作应用、检查结果。这样，可读的规格就接上了真实的验证路径，而不只是摆在实现旁边的一份说明。

比如“保存个人资料”这段流程，可以写清初始状态、操作和预期的保存结果，而不暴露测试的底层细节：

``gherkin Feature: Save a profile name Scenario: A saved name survives reopening the profile Given I am signed in And I am on my profile page When I change my display name to "Mira" And I save my profile And I reopen my profile page Then my display name should be "Mira" ``

每个步骤都需要可执行的实现；光有场景，测试并不会自己跑起来。场景的措辞给审阅者一份清晰的行为契约，可以先审它，再去看背后的代码。

场景用什么词，由团队自己定。同一段用户旅程可以有不同写法，只要大家读得懂、审得了，明白应用应该做什么就行。场景还可以反过来引用文档，说明这些行为为什么存在。最终，产品目的、预期行为和可执行的检查连成了一条线。

05

给智能体一套可复用的视觉词汇

界面要保持一致，也得这么处理。早在智能体出现之前，UI 工作就靠设计系统和模式库提供的共同语言来保持一致。先从具体定义开始：主按钮是蓝色的，形状和尺寸都有规定。再定使用规则——比如，同一时刻一个页面上只能出现一个主按钮。外观和用法是两项不同的决策，都要写明白。

组件把这些决策变成可复用的部件。把组件的颜色、变体和状态写进文档，再提供预览和代码片段，让人和智能体都能查看。复用组件之前，先对照视觉原则把预览审一遍。和写代码一样，更大的模式要靠小部件组合出来；不然每做一个新页面，就多一次另立一套规矩的机会。

06

把反馈放在通往 pull request 的路径上

有了文档和可复用组件，还剩一个落地的问题：人和智能体怎样才能一直照着做？Cichra 的答案是一个不断重复的“干活—反馈”循环。他团队的框架把 Git hooks、skill、CI、linter 和其他检查组合在一起。智能体要交付一个 pull request，就绕不开 Git，这里正好是触发反馈的天然位置。

hooks 在本地跑预先定义好的任务，CI 在远端再跑同样的任务。这种重复很有必要：本地 hooks 可以绕过，比如加上 --no-verify，所以光靠 hooks 没法保证检查一定会跑。CI 里再跑一遍，就能拦下跳过本地验证的改动。检查内容包括 linting、格式化、类型检查、代码重复、架构边界和文档 linting。

把机械性的规则交给自动化，评审才能专注于更高层的决策。 用 Tab 还是空格、代码格式，以及其他早有定论的约定，不必在每次代码评审里重新争一遍。把它们写成检查，贡献者能得到一致的反馈，评审者也能把更多精力留给设计、行为和架构上的影响。

07

阻止被禁止的依赖，然后解释如何修复

架构检查通过控制模块的 import，把抽象的分层规则落到实处。在 Cichra 的端到端 BDD 测试套件里，测试不能访问数据库，也不能 import 任何能访问数据库的模块。这条限制逼着测试只能通过浏览器行为来操作应用，没法绕到界面背后去改动或查看数据库状态。

产品本身也有一道类似的边界：渲染模板不能访问数据库。再加上返回普通数据而不是 ORM 对象，渲染时每一项都多触发一次查询的路子就堵死了。Cichra 说他的架构能彻底杜绝 N+1 查询；但真正能推广开的机制要窄一些——禁止渲染层访问数据库，堵住的是这一类隐式查询，并不能证明每条数据库路径都没有 N+1 问题。目标是让不该有的依赖根本没法出现，而不是在评审里一次次撞见它带来的后果。

这样，反馈循环就有了一条具体的修复路径：

1. 智能体尝试 commit 或 push 一个改动。 2. 检查发现违规，拒绝这次操作。 3. 报错信息链接到相关的决策文档。 4. 智能体读完其中的理由，修正改动，再试一次。

拒绝要真正有用，就得指向解决问题需要的信息。持久保存的文档能在智能体需要的那一刻，把上下文补回来。

08

保留循环，改变它的重点

干活、拿反馈、再修改，这个循环无论做产品功能、UI 还是后端改动都一样。变的是当前任务最需要哪些信息和反馈。skill 负责提供这种聚焦。

- ADR 和 PRD 相关工作： ADR skill 引导智能体找到决策记录，以及这些决策影响到的代码。PRD 的指引则服务于对应的产品文档流程。 - UI 工作： 迭代循环会跳过部分检查，优先拿到快速的浏览器反馈。 - 测试： 测试 skill 根据代码覆盖率和改动过的文件，挑出相关的那部分测试来跑，而不是全量跑一遍。 - 目标执行： 模型做出的决策都会留存下来，方便日后审查。

这些 skill 让循环里的工作各有侧重，但不改变循环的基本结构。

09

让上下文压缩之后仍然可以恢复

这种做法有代价：检索和理解相关文档要消耗上下文。Cichra 说，光是前期调研就可能用掉大约一半的上下文窗口。尽管如此，他还是谨慎地表示，过去半年里这套方法确实管用。他说在自己的会话里，上下文压缩过二十次、五十次，工作依然能接着推进，因为重要信息要么留了下来，要么能重新找回。这些只是他的个人经验，不是经过测量的可靠性数据。

理想的效果是：在持续数小时的会话里，智能体能围绕明确的目标自主推进，同时守在明确的规则之内。要做到这一点，光把所有细节都留在当前对话里还不够。还得有办法在对话里已经找不到这些细节时，把要紧的那部分找回来。

决策记录留住了架构选择的理由；产品文档留住了功能存在的理由；可读又可执行的场景，把这些意图和实际行为连了起来。设计系统把同样的规矩延伸到界面上，其中也包括能强制执行的约束，比如禁止在指定的设计系统之外写内联样式。框架再把这些材料和日常工作接到一起：改动撞上检查，检查指回意图，下一版修改就能用上这份意图。

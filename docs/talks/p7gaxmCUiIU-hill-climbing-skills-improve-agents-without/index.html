爬山式改进技能：不改模型也能改进智能体

AutoBrowse 把浏览器的运行过程变成可复用的指令。它的航班和餐厅示例展示了“老师”学到了什么、为什么更快的运行仍可能失败，以及验证和维护必须补上什么。

01

一个有能力的浏览器智能体仍可能卡在一个滑块上

A Google Flights agent reaches the time filter and cannot drag it. An OpenTable agent tries to find a date-night restaurant and meets “access denied.” These are the opening problems in Shubhankar Srivastava’s workshop. His work on Browserbase’s sales engineering team involves getting browser agents into production, where a clever attempt is useful only if it completes the job.

A browser agent gives a model tools to operate a browser: click, refresh, capture a screenshot or inspect the page’s accessibility tree. A CLI, MCP interface or SDK exposes those operations. The harness—the software around the model—determines which tools and instructions the agent receives. That makes reliability partly an engineering problem: a model may understand the request while lacking a dependable way to manipulate this particular website.

The recurring waste is that each run starts from zero. A previous attempt may have discovered a useful URL, a calendar bug or a necessary wait, yet the next attempt has to discover it again. Srivastava calls these agents “geniuses that never learn.” Fine-tuning for every new website and task would add another training burden. His alternative borrows the autoresearch idea: repeat a verifiable task, inspect what happened and carry useful lessons into the next attempt without changing model weights.

02

执行者负责浏览，老师改变下一次运行所知道的东西

The live task is concrete: find a business-class flight from San Francisco to New York for “this Saturday,” departing in the morning, with one carry-on bag. A remote browser opens Google Flights, and the agent starts applying the business-class filter. While it works, Srivastava explains AutoBrowse’s two-agent architecture, built with the Claude Agent SDK.

The agents have different jobs:

- Doer: Operate the browser through the Browse CLI, inspect screenshots and collect the requested information. - Teacher: Read the doer’s traces, screenshots and logs, identify what worked or failed, and write lessons into strategy.md.

That file survives between attempts. A correction such as choosing a different button becomes an instruction available to the next run, rather than an observation lost with the previous conversation.

What crosses the boundary between attempts? The diagram separates the evidence produced by browsing from the instructions produced by teaching. The doer and teacher alternate; the persistent strategy carries information forward. In this demonstration, the prompt does not prescribe an iteration count, target success rate, token budget or time limit. The teacher has broad discretion to decide when further learning is no longer useful.

Execution evidence becomes instructions for another attempt Browser observations go to the teacher; the revised strategy goes to the next doer run. 06

学习需要一个可评判的结果和一个可重跑的环境

The same repeated discovery appears outside browsing. Coding agents forget repository conventions and linting rules. Research agents repeatedly miss a source the team always uses. Internal-operations agents rediscover which dashboards, databases and tools are preferred. Files such as CLAUDE.md and AGENTS.md can carry those lessons, but improving them through repeated attempts requires two things: a replayable environment and a verifiable outcome or quantifiable metric.

An audience question exposes the difficulty hidden in “verifiable.” A training experiment can compare log loss numerically. A browser workflow may make it straightforward to check whether a ticket was booked, while leaving “Did you find the best flight?” unresolved. The attendee presses on a narrower failure too: a copied URL or number can change by a character and become wrong. Correct task interpretation does not ensure faithful extraction of the data needed to complete it.

The response returns to resilience across attempts: successes can be followed by failures, and the loop should recover without treating one bad attempt as the final lesson. Different loop designs may suit different domains. That is a design direction rather than a demonstrated solution to character-level copying errors; the discussion does not establish an independent check that catches those errors.

Replayability has its own engineering cost. A coding task can start from a Docker image or a particular EC2 environment and repeat from a known point. Knowledge work involving human decisions may be much harder to restore. Srivastava’s term is a “grindable” environment: the agent needs enough repeatable attempts to work through failures. Investing in that environment makes the learning loop possible.

07

更多的迭代总体上可能花得更少

Model choice and iteration count interact. In Srivastava’s experiments, Sonnet can take more iterations than Opus while still completing the task at lower total cost. He estimates a typical AutoBrowse learning run at roughly $30–$40, with very complicated examples reaching about $100. Those are his observed costs, not a pricing bound. The investment makes sense when later uses of the generated skill repay the discovery work.

The teacher role comes from an existing human workflow. Srivastava would sit with customers, inspect failures and reverse-engineer the website until the automation worked. AutoBrowse began with the question of whether an agent could take over that diagnostic role using the autoresearch pattern. The subsequent work involved repeated engineering changes to simplify the loop.

A good strategy still depends on a usable environment. Browserbase can preserve login cookies for future sessions and use supplied proxies, helping repeated attempts resemble the intended workflow without logging in every time. Those infrastructure choices matter especially when anti-bot behavior changes what the agent can reach. Improving the instructions alone cannot replace the environment they depend on.

The implementation’s evaluate.mjs contains the loop, with the doer and teacher running one after the other on every iteration. 09

每个任务一个技能，把组合留给框架

An audience member challenges the task-by-task framing: users often ask for something that spans several tasks. A date-night request might require comparing more than one reservation service. Srivastava’s proposed answer is skill selection and composition in the harness. It could retrieve relevant instructions for OpenTable and Resy, then choose tools that serve the larger request. A task-specific skill is useful knowledge, but it does not by itself plan the whole job.

There is no single recommended granularity. Separate skills, a more general skill, specialized tools and generic tools are alternatives to evaluate against common customer requests. The discussion connects the approach to GEPA and DSPy, then returns to the evaluator problem: a verifier also needs evaluation. Srivastava mentions verifier research with Microsoft and raises the choice between human review and an automated judge; he does not give the paper’s method in this recording.

Storage is a separate concern from learning. In the demonstrated repository, generated files live in a local .claude skills folder, including a recipe-search skill. A production agent can incorporate the files into its own loop. For the public Browse.sh catalog, Srivastava says he believes Vercel Blob stores the skills for on-demand retrieval; the talk does not develop a retrieval or ranking design.

10

失败时修复，并选择“改进”的含义

Website changes make a successful skill perishable. The working maintenance approach is to trigger AutoBrowse after a production failure, diagnose the problem and generate a pull request for a human engineer. Scheduled sample runs every two or three hours offer another way to discover breakage. The tradeoff is detection speed against the cost of continually checking or relearning behavior; Srivastava describes this monitoring work as still being implemented with a customer.

The teacher also needs an objective. Several goals can lead to different stopping decisions:

- Task success: Stop when the requested job succeeds. - Latency: Keep looking for a faster route. Srivastava has seen loops discover that an API can replace browser interaction, with some solutions taking 500 milliseconds. - Turns: Reduce the number of model-tool exchanges and the context needed to complete the task. - Reliability: Continue investigating beyond the first success when dependable repetition matters most.

The 500-millisecond observation is an example of a discovered fast path, rather than a benchmark for AutoBrowse generally.

For the demonstrated setup, reliability takes priority over cost, and the teacher decides when to stop. That explains why a pass does not immediately end learning—and why the earlier faster-but-failing iteration matters. A system that minimizes turns can prefer a different strategy from one that seeks dependable completion.

11

“毕业”是一种判断，产出是 Markdown

WebMCP offers another possible route to fewer brittle UI operations: a website can expose programmable actions through the browser. At the time of the workshop, Srivastava says Browserbase’s SDKs support it, but he does not think the AutoBrowse loop does yet. This distinguishes an available SDK capability from behavior demonstrated in the learning loop.

Asked about ground truth, he describes a typically binary, self-evaluated result: did the agent find the flight or reservation? That remains a model judgment in this setup. Calling a flight the cheapest requires stronger evidence than finding a plausible matching option, just as the earlier discussion distinguished booking a ticket from finding the best one. Graduation should be read within that scope, rather than as an independently measured guarantee.

The environment is deliberately close to live use. In response to a question about mocking side effects such as purchases, Srivastava says the approach favors real websites over replicated training portals. He also places CAPTCHA handling in Browserbase’s infrastructure, at the Chrome binary layer, rather than in the agent’s token-consuming reasoning. He declines to specify which CAPTCHA types it can solve.

The graduation mechanism returns to the same concrete inputs: per-iteration folders contain JSON traces; the teacher reads them alongside the system prompt and previous strategy, then proposes a better strategy. The talk supplies no fixed numerical graduation threshold. Once produced, the skill is a Markdown artifact that can be used with Stagehand, Claude Code or another agent. Srivastava demonstrates that portability with a San Francisco event-search request; it does not require using Browserbase to read the instructions.

12

学到的技能可能把坏指令和好指令一起保留下来

Prompt injection creates a failure mode specific to learning from the web: malicious page content could influence an attempt and then become a lesson reused in production. An Amazon listing with hidden instructions is the concrete example. Restricting the agent to a familiar domain does not settle the problem, because malicious content can appear within that domain.

Srivastava describes three places to apply controls:

- Incoming content and requests: Add checks before potentially malicious instructions reach the harness. - Generated skills: Run a security-review agent over skills before publishing them to Browse.sh. - Browser infrastructure: Restrict destinations and permitted actions through network controls and Browserbase safe mode, including permission choices such as allowing an action once or persistently.

The layers address different paths to harm: what reaches the agent, what it preserves, and what it can execute. The talk describes the controls without establishing that they eliminate prompt injection.

The final audience question returns to skills that grow and become outdated as the browser, website or development environment changes. The proposed operational check is simple: schedule the skill to perform its job every day at 9 AM; leave a successful run alone, and send a notification on failure to trigger a healing loop. This detects observed breakage and connects it to repair. It does not, by itself, solve skill growth or guarantee that an apparently successful result is still correct. The reusable file therefore needs continued execution checks and the human review described for repair pull requests.

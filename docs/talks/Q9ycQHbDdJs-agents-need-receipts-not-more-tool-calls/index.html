智能体需要的是收据，而不是更多的工具调用

科学智能体需要一种跨组织采购工作、并保留事情经过证据的方式。Froglet 提出了一个用于发现、交易和签名收据的共享接口。

熟悉智能体工具调用和公钥签名的基本用途会有帮助；不需要 Froglet 经验。

01

是什么让科学研究难以自动化？

智能体最值得自动化的是哪类工作？科学研究是个有力的候选。但给智能体再多工具，也解不开协作者之间的相互依赖。Armanas Povilionis 基于十年生命科学合作项目的经验，指出还缺一样东西：一条可验证的收据链，记录跨组织完成的每一步。有了它，结果才足够可信，其他参与者才能接着往下做。

不妨把智能体想象成厨师。刀更好、锅更多、烤箱更多，厨房里的活就干得更快更好。科学协作则更像经营一家餐厅。结果还取决于供应商和食材，取决于服务，也取决于能不能每次都端出同样水准的菜。整套体系不可能塞进一间厨房。

换成工程问题，就是协调供应链。智能体工具已经有了，但科研需要的数据和专业分析算法仍分散在各个组织手里。光把本地智能体做得更好，它并不会因此可靠地拿到这些外部资源。

02

从 token 额度到采购外部工作

Alithea 对 Froglet 的设想，起点是组织交给智能体的权限要变。如今智能体已经能为单个任务拿到 token 预算。预算的范围再放宽一些，智能体就能跨组织发现服务、请求数据、协商执行，并为工作付费。这比挑选调用哪个本地工具，责任大得多。

套用餐厅的比喻，智能体成了行政总厨：找供应商、订食材、协调分工、做好记录。Froglet 就是为串起这些活动而提出的协议。智能体可以借它发现外部的数据和服务提供方，与之交易，并拿到可验证的收据。采购和记账成了同一条工作流里的环节。

03

一个横跨不同技术栈的共享接口

Froglet 的定位是夹在现有系统之间，而不是取代它们。它的集成点包括支付通道、智能体框架、执行环境和网络传输层。参与方只需要统一的接口，周边软件栈不必一模一样。请求方和科学服务提供方分属不同组织、基础设施各不相同，这一点就尤其关键。

演讲引导听众去项目官网：本地运行号称只要一条命令，远程试用号称只要一条提示词。目前托管的试用版比完整的交易设想窄得多：它只演示免费服务和签名收据，不涉及付费结算、持久身份或服务发布。

04

在发布资源之前先审批

Povilionis 说，定制化的科学合作往往要花上数年、耗资数百万，才能产出一条可复用的工作流。Froglet 提出的捷径有个前提：组织已经做出关键决定，认定这项资源可以共享。协议代替不了这道审批。

做出这个决定之后，设想中的工作流很简单：

1. 提供方通过 Froglet 开放已获批准的资源。 2. 智能体发现该资源，并理解其条款。 3. 智能体发起工作请求。 4. 智能体拿到一张可验证的收据。

Povilionis 称，这条针对已批准资源的工作流只需几分钟、几千个 token。这句话有明确的适用范围，并不是拿整个合作流程做对比、实测出来的提速；演讲也没有给出基准测试方法。

随后演示打开了官网上的分步讲解，想深入了解可以看文档。讲解先介绍发布流程，再介绍支撑它的网络角色和记录。

05

一个节点核心，三种角色

讲解中展示的网络由同构节点组成：每个参与者运行同一套核心，只是扮演的角色不同。

| 角色 | 职责 | | --- | --- | | 请求方 | 向外部发起工作需求 | | 提供方 | 提供数据或服务 | | 市场 | 运行专门的市场服务 |

市场本身也是一个 Froglet 节点，不是另一类核心基础设施。

这些角色合起来回答四个环环相扣的问题：请求方怎么找到提供方，参与方怎么建立信任，怎么付款或结算，以及怎么留下执行确实发生过的证据。只解决“发现”，只能回答第一个问题。

06

签名的记录把发现与执行连接起来

创建节点时会生成一对密钥，用于身份标识和签名。在讲解中，一笔交易的记录依次经过描述（descriptor）、要约（offer）、报价（quote）、成交（deal）、发票（invoice），最后是收据（receipt）。节点用密钥为这条链上的记录签名，把最初的描述、商业承诺和最终的执行记录串在一起。

如果应用要展示这个流程，可以用一个小小的 TypeScript 模型，把还没完成的工作和已有收据的交易明确区分开：

```typescript type Stage = | "descriptor" | "offer" | "quote" | "deal" | "invoice" | "receipt";

const stages: readonly Stage[] = [ "descriptor", "offer", "quote", "deal", "invoice", "receipt" ];

function receiptStatus(records: readonly { stage: Stage }[]): string { return records.some(record => record.stage === "receipt") ? "Receipt present; verify signatures and chain" : "Receipt pending"; }

const transaction: { stage: Stage }[] = stages .slice(0, 4) .map(stage => ({ stage }));

console.log(receiptStatus(transaction)); // Receipt pending ```

这个模型只判断记录在不在。标为 receipt 的记录仍需验证；有这条记录，不等于通过了密码学校验。

Povilionis 说这条链能让篡改无所遁形：改动其中任何一环，链就会断开。关键要分清记录的完整性和科学结果的正确性。签名能让每项承诺都追溯到具体的责任方，也能让改动一查便知；但签名本身证明不了一项分析在科学上是对的。

发现服务要靠市场，但后续执行不需要市场居中转手。提供方在市场上注册并描述自己的服务，市场则提供服务描述和可用服务的索引。请求方通过索引找到提供方后，双方直接通信。按 Povilionis 的说法，请求、签名、执行和收据都发生在请求方与提供方的一次交互里，不必每一步都经过中间人。

07

拆分付款，应对双方的风险

对于收费服务，提出的支付模式分两部分：

| 组成部分 | 设计用意 | | --- | --- | | 基础费用 | 保护提供方，防止恶意的重复请求 | | 成功费 | 保护请求方，防范恶意的提供方 |

这样拆分，针对的是两种不同的风险：提供方处理请求要耗费资源，请求方则可能付了钱却拿不到成果。这是一种激励机制，保证不了结果正确。演讲也没有说明怎么判定“成功”、怎么解决争议。

08

供智能体协作的基础设施

Froglet 不是 AI 智能体。 它是一个接口，让智能体能互相找到对方，跨组织边界发现数据和服务，并直接达成交易。做什么工作由智能体决定；协议负责为这项工作搭好交易结构。

要实现科研上的雄心，得把这几项能力连起来：发现外部资源，跨组织边界执行工作，再为交易留下一张可验证的收据。这样一来，自主研究工作流就能走出单个组织，不再局限于内部的工具和数据。让科学自主向前推进是愿景；落到实处的提案，是一套共享接口，外加一份能追溯到责任方的协作工作记录。

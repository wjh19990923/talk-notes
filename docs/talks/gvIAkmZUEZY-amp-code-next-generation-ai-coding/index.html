The agent loop generates a response, executes any requested tools and adds their results to the thread. If there are no tool calls, it asks for user input.

Hello, Agent

function runAgent(userPrompt: string) {
    const model = new ModelAPI()
    const thread = new Thread(userPrompt)

while (true) {
        const response = model.generateResponse(thread)
        thread.append(response)

if (response.toolCalls.length > 0) {
            for (const toolCall of response.toolCalls) {
                const result = executeTool(toolCall)
                thread.append({ role: 'tool', content: result })
            }
        } else {
            const userInput = getUserInput()
            thread.append({ role: 'user', content: userInput })
        }
    }
}

Amp Code：下一代 AI 编程

一个“帮助”按钮的演示引出了 Amp 的架构：专门的工具和子智能体节省上下文，而不同的执行模式和审查界面塑造了开发者的工作方式。

熟悉代码 diff、编辑器诊断信息和语言模型工具调用，有助于理解架构。

01

给智能体本身加一个帮助按钮

编码智能体在修改自己的界面时，应该给你看些什么？Beyang Liu 就从这个小小的设计问题开始演示 Amp。他说 Amp 是一个有鲜明主张的前沿智能体，团队还特意给它选了个古怪的吉祥物：骑着悬浮金鱼的花衣魔笛手。团队想探索的是：智能体写的代码越来越多，一年后的开发者会怎样工作。

Amp 的终端界面跑在自研的 UI 框架上。它不会摊开模型解释的每个 token，只挑一部分活动展示：文件一改，diff 就实时流出来；命令区则显示智能体调用了哪些 CLI 操作。界面上还有个 Emacs 30.1 标识，表示已连上编辑器。终端智能体可以连接 Emacs、Neovim 或 JetBrains，从中收集和当前任务相关的诊断信息。

演示的任务是在 Amp 自己的界面左下角加一个 Help 按钮。智能体先找到相关上下文，再反复迭代修改；最后能看到的结果之一，是一个列出键盘快捷键的终端帮助面板。可以看出，交互的基本单位已经不止一次代码补全：智能体调查代码库、动手修改，同时展示足够多的过程，让人跟得上。

录像里还展示了一个编辑器扩展，能装进 VS Code 及其衍生版本，包括 Cursor、Windsurf 和 Antigravity，不必维护一个 VS Code 分支。这是当时的编辑器体验：Amp 后来宣布停用其 VS Code 和 Cursor 扩展，计划于 2026 年 3 月 5 日下线。

Liu 说，他现在主要通过智能体面板写代码，很少手动编辑。瓶颈于是从写代码变成了读懂代码。他没法同时多跑几个智能体，卡就卡在审查它们的产出上。Amp 的对策是专门做一个审查界面，帮开发者在发布前看懂改动。生成的代码再多，也得有人能有效审查才有用。

02

智能体循环里为数不多的几个杠杆

接下来的问题是：Amp 的架构到底有什么不同？哪个工具更好，Liu 留给开发者自己试了再判断；他讲的是构建 Amp 时做过的决定。智能体的核心是一个循环，里面装着模型和工具调用。所以构建者手里主要有三个杠杆：选哪个模型、怎么写工具描述、模型怎样和工具来回迭代。几个简单的控制点就能带来截然不同的行为，就像条件判断和循环足以撑起复杂的普通程序。

03

先调工具，再保护上下文窗口

第一个架构决策和工具有关。MCP 让“给智能体提供上下文”这件事的范围大大拓宽，但 Amp 仍得决定把力气花在哪儿：是接一大堆集成，还是精心打磨一套内部工具。团队选择优先打磨核心工具，理由有两个，彼此相关。

- 闭合正确的反馈回路。 好用的编码智能体必须找到能推动进展的反馈。Liu 认为，Amp 可以围绕这些目标调校自己的工具和描述；外部 MCP 服务器的作者却未必知道 Amp 想做成什么。 - 减少无关选项。 每多一条工具描述，模型就多一个要考虑的选项。这些选项要是对当前任务没帮助，反而可能搅乱上下文。

这是在主张投入面向具体任务的工具，不是说 MCP 本身妨碍专门化，也不是说 Amp 不支持 MCP。

工具描述只是消耗上下文的来源之一，工具调用和返回结果同样会越堆越多。一个勤快的编码智能体可能动手之前先 grep 整个仓库、读一大堆文件，结果剩下的空间不够完成修改。让它少读点，看似解决了容量问题，却引出另一个问题：起初掌握的上下文不够，它可能一遍遍尝试同一个无效的修复。Liu 管这叫死亡循环（doom loop）。

| 做法 | 上下文会怎样 | 问题或好处 | | --- | --- | --- | | 在主智能体里搜索 | 调查过程塞满主窗口 | 留给修改的空间太少 | | 提示智能体少读点 | 收集到的证据变少 | 反复尝试，可能始终找不到原因 | | 把调查委派出去 | 子智能体负责详细搜索 | 相关结果交回主智能体 |

子智能体让人跳出了这种两难。它像子程序一样，负责一块边界清楚的工作；和普通函数不同的是，它还有独立的上下文窗口。它在那里做完必要的调查，只把相关结果交回来。主智能体留下有用的发现，不必在之后每一步都背着完整的搜索历史。

Amp 把这种拆分推得更远，不只是给通用子智能体换换提示词或工具。它的专用智能体各自负责扩展主智能体的某项能力。设计问题于是变成：哪些工作值得配上自己的模型、工具和上下文——而不只是同一个智能体要开几份。

04

Finder、Oracle、Librarian 和 Kraken

Finder 负责搜索代码库。试过不同模型后，Amp 选定了一个相对小而快的模型，驱动一套有限的工具，专门找出仓库里的相关上下文。它的任务不是包揽编码的每个环节，而是把后续工作要用的材料找齐。

Oracle 负责推理。Amp 不让每次交互都走较慢的推理模型，而是在需要时把棘手的调试或细致的规划交给 Oracle。主智能体照样反应迅速、广泛调用工具；更难的分析由 Oracle 接手。

Liu 说，主智能体卡住、他又不想花一两个小时去排查时，就会明确点名 Oracle，让它好好想一想。Oracle 干活的时候，他可以切去做别的事。Liu 估计，在这类棘手的调试场景里，Oracle 大约五次有四次能找到根本问题，有时要先想上几分钟。这是他的个人体验，不是经过明确评测得出的成功率。

Librarian 负责获取本地代码库之外的上下文，尤其是依赖库和框架里的内容。实验性的 Kraken 面向另一种规模的工作：大型重构。它不逐个改文件，而是编写 codemod，在整个代码库里批量应用转换。这些是不同的执行策略，不只是给同一段提示词套上不同的人设。

05

选择一种工作模式，而不是一个模型

专门化也决定了 Amp 的顶层界面。模型选择器给了用户选择权，却要开发者自己判断每个任务该用哪个模型。它还可能限制产品架构：如果 N 个模型共用一个框架、只做少量定制，这个框架可能永远发挥不出任何一个模型的全部本事。Amp 的做法是围绕几个运行特性不同的智能体来组织体验。

| 模式 | 适合的工作 | 人怎么参与 | | --- | --- | --- | | Smart | 更复杂的指令；执行较慢 | 先委派，再审查 | | Rush | 快速、有针对性的小改动 | 盯紧过程，逐次审查修改 |

Liu 特别提到 smart 能调用专用子智能体；不过这并非 smart 独有，同期发布 rush 时的文档也写明它能调用所有子智能体。两者的核心区别在交互方式：smart 适合可以异步跑的工作，rush 适合开发者亲自掌舵、连续做一串小改动。这是在速度与智能的前沿上刻意选定的两个点。

这样一来，底层用哪个模型就成了集成层面的决定。Liu 说，最近换成 Gemini 3 Pro 是 smart 第一次换模型，就在演讲前两天。公告显示这次变更发生在 2025 年 11 月 18 日；他说的是这一次切换，而 Amp 的发布记录里也有更早的 Claude 版本变更。

Liu 预计，同一个模型放进不同的智能体环境，表现会不一样。发布前那一周，Amp 一直在针对 Gemini 3 的能力测试和优化 smart。他说早期评估结果不错，也承认还有些集成问题没解决。所以真正该评测的，是模型连同工具和框架的整体，而不是孤零零一个模型名字。

06

编辑器变成了“阅读器”

编辑器和终端支撑的工作方式不同，界面要擅长的东西也不一样。Liu 把自己的编辑器叫作 readitor（主要用来读的编辑器）：改动交给智能体面板来做，编辑器的其余部分越来越多地用来帮他阅读、理解这些改动。Amp 自研的审查界面把文件级 diff 放进一个专门的面板。

审查流程保留了调查一次改动所需的各种能力：

1. 任选一段 commit 范围，确定要审查的内容。 2. 逐个浏览文件级 diff，必要时直接修改。 3. 用“跳转到定义”和“查找引用”弄懂周边代码。 4. 跟着改动导览走，它会建议先读哪些文件。

最后一步解决的是审查中一个具体的痛点：改动一大，光决定从哪儿读起就占了一半工作量。完整布局把这份阅读指引摆在 diff 和智能体对话旁边。

07

让活动可读，让实践可分享

终端也有自己的设计空间。Liu 说，Ghostty 的一位核心贡献者从零为 Amp 打造了 TUI 框架，充分利用现代终端的渲染能力。举个细节：diff 里新增内容的绿色背景，会和终端原有的背景色混合，让高亮和周围环境融为一体。

但不是每个终端都撑得起这么丰富的渲染。用户也会在 JetBrains 或 VS Code 的内嵌终端里、或者在 macOS 自带的 Terminal 里跑 Amp。所以 TUI 会按各个环境的能力降级。目标是在任何终端里都给出可读的智能体界面，终端支持的地方再呈现得更丰富。

输出可读，能帮单个开发者跟上智能体；共享会话记录（thread），能帮团队学会怎么指挥智能体。Liu 预计人类开发者还会长期参与其中，但他认为写代码这门手艺得大家一起重新学。在 Amp 的团队功能里，可以查看一段时间内有多少代码是用 Amp 改的，还能打开某项工作背后的会话记录。

这些会话记录留下的不只是最终补丁。同事可以分享一个管用的提示技巧，也可以指着一次卡住的尝试向大家求助。真正值得问的，往往是怎样把智能体接上更好的反馈回路。交互过程共享出来，大家就能具体查看这个问题，不必只凭一句含糊的“智能体成了”或“没成”下判断。

08

赞助推理的实验

想学会用，还得用得起、用得够。演讲时，Liu 说 smart 的推理成本相对较高，rush 的推理越来越便宜，但也不是免费的。他去大学校园和学生交流时发现，用编码智能体的学生比他预想的少，成本是一大障碍。

于是有了一个起初看似不太靠谱的提议：在终端里放广告。随着推理成本下降，这笔账看起来越来越算得过来。Amp 上线了一个小型广告网络，在终端和编辑器里推广开发者工具，广告位力求低调、不打扰。Liu 解释说，这笔收入用来补贴 rush 的推理费用，让更多人能把智能体用在业余项目之类的事情上。这是一次已经结束的实验：Amp 于 2026 年 3 月 30 日宣布移除广告。

09

一个用于实验智能体的社区

Liu 说，Amp 并不面向所有人，而是面向那些想探索智能体辅助开发会怎样演变的开发者。他把公司称作一个智能体研究实验室，还说他们不花钱请开发者网红。说到吸引来的用户，他举了两个例子：Mitchell Hashimoto，据说用 Amp 给 Ghostty 做了大量改动；还有 Hamel Husain，Liu 说他最近称 Amp 是自己最喜欢的编码智能体。Liu 也说明，这两人既不是团队成员，也不是投资人。这些是转述的用户背书，不是对比评测。

结尾的邀请不只关乎产品。幻灯片上的社区 Build Crew 欢迎所有在折腾智能体的人，用不用 Amp 都行。社区由 Ryan Carson 运营；Liu 说，Carson 之前创办的 Treehouse 教会了一百多万人写代码。这个新社区的重点是和同道一起学习——这些人正把智能体推向陌生的工作领域。

社区活动包括定期采访在做有趣项目、或者用智能体做出新花样的人，也有线下活动。Liu 说，前一天晚上的聚餐上，大家一会儿聊编码智能体的实战，一会儿聊关于 AI 的哲学问题。这正是这场演讲真正的落脚点：开发者们分享具体的实验，而这门手艺的工具、习惯和分工都还在变。

为 LLM 事实依据构建高效的混合上下文查询

自然语言的商品搜索必须捕捉购物者想要什么，同时遵守价格、类目等约束。Simrat Hanspal 的演练把这些检索任务串联起来，然后测试当购物者要求搜索界面去修改商品目录时会发生什么。

01

商品搜索既需要语义也需要结构化约束

购物者可能清楚商品该有什么用、自己能花多少钱，却不知道商品目录里具体怎么写。他们的需求里既有描述，也有约束。所以商品搜索应用要分清三种情况：描述性的意图、针对结构化字段的条件，以及两者兼有的请求。用自然语言替代关键词输入，界面的表达力更强了，但检索系统仍然得把这些表达转换成合适的操作。

语言模型的训练数据不是实时的商品目录。检索增强生成（Retrieval-Augmented Generation，RAG）把相关的外部信息和用户问题一起交给模型，让模型的回答有据可依。放到商品搜索里，就是检索与请求匹配的商品目录上下文，而不是依赖模型对商品已有的了解。

Hanspal 在搭建流水线之前先讲安全。用户开口要什么，系统就给什么，有用的上下文就可能变成通向敏感数据的路径。这是对应用本身的要求，加上检索并不会自动带来这种保障：系统必须控制请求能触及哪些数据。

02

动态请求需要有边界的数据访问

数据驱动的应用早就有了，为什么还要重新讨论安全检索？Hanspal 的关键区分在于应用数据接口的形态。在他描述的传统商品搜索应用里，软件消费的是一个相对固定的数据源。记录和结果会变，但新功能通常来自修改接口外围的应用代码。

上下文驱动的应用则不同，它得根据开放式的自然语言请求挑选信息。需要什么上下文，取决于用户问什么。这种灵活性也给了用户空间，去提出应用设计者本没打算支持的要求。所以，理解请求和决定是否放行，是两项独立的职责。

Hanspal 用 Hasura 的 GraphQL API 和权限系统 作为数据访问层。一个统一的接口可以对外暴露多个数据源，同时允许请求的结构各不相同。GraphQL 负责表达操作，权限决定执行角色能做什么。动态查询语言本身并不等于授权。

03

准备好记录，再暴露一个 GraphQL 接口

检索接口需要支持三类请求：

- 语义搜索：在向量数据库中，把请求的含义与商品描述做匹配。 - 结构化搜索：对 price、category 这类字段施加条件。自然语言必须转换成结构化操作，比如用 SQL 或 GraphQL 表达。 - 混合搜索：把描述上的相似度和结构化条件结合起来。

这里的“混合”指语义检索加结构化约束。演示中并没有引入关键词排序与向量排序的融合。Hasura 用同一个 GraphQL 接口承接全部三种请求。

Hanspal 的 Streamlit 应用 是面向用户的入口。它接收自然语言请求，调用语言模型生成 GraphQL，再把生成的操作提交给 Hasura。模型负责翻译，Hasura 负责执行最终的数据请求。

控制台的 Data 标签页里，一张 Postgres 商品表和一张商品向量表已经接好。这套架构虽然能接入多个数据源，Hanspal 为了简化，现场搜索只用了 Weaviate。预先准备好的记录里，向量和结构化商品字段（包括价格和类别）存在一起。所以演示中的混合搜索不需要在 Postgres 和 Weaviate 之间做实时 join。

准备工作在搜索之前就已完成。Hanspal 用 Hasura 事件触发器：Postgres 一插入新商品，就触发向量化，再把向量化后的记录存进向量数据库。插入事件启动摄取流程，之后的搜索都在准备好的数据集上进行。控制台的 Product_vectors 表列出了这些商品记录，包含 name、description、price 和 category 字段。

控制台的 API 标签页提供了一个工作区，可以执行查询、查看结果。随后 Hanspal 切到 Streamlit，配置面板里填着 Hasura 端点、一个 admin secret，以及调用 Chat Completion API 用的 OpenAI API key。这些设置把演示的各个组件串了起来。而这些请求带着什么执行权限，到后面的授权测试中就成了关键。

04

三个购物请求检验检索接口

第一个请求是找有助放松的精油。生成的 GraphQL 操作把这个描述性意图当作语义搜索的输入，应用随即展示返回的商品。这里要匹配的是购物者想拿商品做什么，而不是某个数值条件。

接着，Hanspal 要找价格低于 500 美元的商品。生成的操作识别出字段是 price，比较方式是“小于”：price < 500。应用展示了满足条件的商品。和放松精油那次不同，这次搜索靠的是精确的字段比较。

第三个请求把两者合在一起：价格在 500 到 1,000 美元之间的精油扩香器。生成的 GraphQL 操作既包含针对扩香器的语义搜索，也包含价格区间过滤，应用再次展示了结果。语义相关性确定商品属于哪一类，结构化约束决定哪些价格合格。检索中的结构化部分由 Weaviate 过滤器 在准备好的数据集上完成。

举个例子：假设有一条扩香器记录，售价 750 美元。它的描述满足语义匹配，价格也落在要求的区间内。两个条件谁也替代不了谁：价格合适但毫不相关的商品满足不了描述上的需求，相关但价格超出区间的扩香器也满足不了价格约束。这条 750 美元的记录只是讲解用的例子，并非演示中实际返回的结果。

05

一个插入请求暴露出权限边界

前面几次成功的搜索验证了预期行为。Hanspal 接着尝试一个预期之外的操作：让搜索界面插入一款护发油商品，名为 special oil，售价 10,000 美元，类别 home，描述为 Fantastic hair oil，商品 ID 为 10001。这是在修改商品目录，而不是从中检索上下文。

模型生成了一条 GraphQL 插入 mutation，初始的执行权限也放行了它。Hanspal 回到控制台，按新商品 ID 筛选表格；ID 字段是整数类型，所以他把查找值两边的引号去掉了。匹配的记录出现了：搜索应用真的写进了数据库。

修复办法是改权限。Hanspal 在控制台创建了一个商品搜索角色，只给它 select 权限。为了简单，他没设行级检查，所有商品列也都开放访问。这个角色能读取商品，但没有 insert 权限。这是操作层面的限制；读权限故意放得很宽，敏感的行和列并没有因此受到保护。

Hanspal 在受限角色下重试插入请求，把商品 ID 改成了 7002。模型照样生成了插入 mutation。这一次执行报错，因为该角色没有 insert 权限。应用显示当前角色为 product_search_bot，GraphQL 错误提示无法在 mutation_root 上查询 insert 字段。两次尝试的插入意图和操作类型一致，但请求内容并不完全相同。

这次拒绝把生成和授权分开了。模型依然愿意提出写操作，但提出写操作并不能让执行角色获得相应的权限。即便生成的操作超出了预期的搜索行为，应用的访问边界依然守得住。

最后，Hanspal 回到混合商品搜索这个用例：描述性请求和结构化过滤可以共用一个检索接口，而执行权限限定了这个接口能做哪些操作。

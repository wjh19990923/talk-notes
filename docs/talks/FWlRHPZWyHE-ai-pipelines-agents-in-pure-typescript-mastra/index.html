Mastra combines typed workflows, tools and agents with persistence, observability and evaluation. The example defines a workflow with input and output schemas, then registers it with an agent.

What is Mastra?

The Framework

Mastra is a TypeScript framework for building AI applications with:

▪ 🔄 Workflows - Composable, typed pipelines
▪ 🔧 Tools - Reusable functions agents can call
▪ 🤖 Agents - Stateful AI entities with memory
▪ 💾 Built-in persistence - Conversation memory
▪ 🔍 Observability - See what your AI is doing
▪ = Evaluation - Mastra can tell you the health of your pipeline over time

Why Mastra?

工作流

幻灯片原文
Workflows chain discrete steps and pass data between them. The example maps an extracted template into a generation step; Zod validation and error handling help make the pipeline dependable.

Workflows 🔄

What are Workflows?

Workflows are composable pipelines that:
▪ Chain multiple steps together
▪ Pass data between steps
▪ Validate inputs/outputs with Zod
▪ Handle errors gracefully

Think of them as typed, observable functions that can do complex multi-step operations.

用 Mastra.ai 以纯 TypeScript 构建 AI 流水线与智能体

一个“职场吐槽”表情包生成器展示了带类型的工作流、运行时模式、可检查的步骤和智能体接口如何在 Mastra 中组合在一起。

熟悉 TypeScript、异步函数、JSON 和基本的 Git 用法，有助于理解工作流和模式示例。

01

把一次职场吐槽变成一个表情包

怎样把一句职场牢骚变成一张能转发的梗图？Nick Nisi 和 Zack Proser 有意从这个小应用讲起。练习本身很搞笑，里面的工程问题却很实在：理解输入、在操作之间传递结构化数据、调用外部服务、展示结果。真实的职场自动化同样会遇到这些问题。工作坊从概念讲到协作编码，中间穿插着提问。

两位讲者在 WorkOS 做开发者工具。WorkOS 提供的企业级功能包括 SSO、目录同步、审计日志和细粒度授权。他们举的例子很常见：应用已经跑起来了，潜在客户要求企业单点登录，团队得把它加上，又不想自己造一个身份平台。智能体代表用户做事时，也会碰到同样的身份问题。Nisi 自我介绍时提到了开发者体验、dysfunctional.fm 播客、TypeScript 和 Vim。Proser 做过应用和基础设施开发，近来转向 GenAI、MLOps 和检索增强生成。

02

在模型决策周围加上明确的结构

Mastra 提供三种构建应用的基本单元：工作流、工具和智能体。围绕它们，还有本地 playground、持久化、记忆、可观测性和评测。工作坊只用到其中一部分。Mastra 的贡献者也在现场，可以解答框架本身的问题。

工作流从一串可重复的步骤开始。假设有位同事总在做同一件事：抓取某个网站，找出值得关注的人，查他们的资料，弄到一张图片，再写一封邮件。这些操作有先后顺序，数据一步步往下传。工作流把这个顺序明确写出来，包括步骤之间的数据转换。模型每次的输出都不一样，所以运行时 schema 设了一道边界：应用可以在这里校验数据、执行显式配置的类型转换，或者处理错误。Nisi 把这种链式 API 比作 RxJS：从一个值出发，做一次操作，映射结果，再接着往下走。单次生成仍然不确定，控制流却可以事先定好。

工具就是可调用的函数：文件系统操作、API 请求、数据库查询或业务逻辑。有了工具，模型既能获取训练数据之外的信息，也能执行动作。讲者起初把生成梗图的各项操作做成了独立的工具，后来改了设计，让智能体去调用一个包含整套流程的工作流。

智能体给这些能力加了一层面向人的界面。同事再忙、再不懂技术，也只需描述任务，不用手动凑齐各项输入。在这个应用里，智能体由指令加上调用工作流的权限组成。更一般地说，智能体可以查看当前状态，自己决定下一步做什么。真正关键的设计选择是：这些决策有多少交给模型，多少留在应用代码里。

03

给模型上下文，再定义练习

Model Context Protocol（MCP）为 AI 客户端连接工具和上下文提供了一套通用接口。Nisi 举的实际例子是 Claude Desktop 里的 GitHub MCP server。给它一个 issue 和一个示例应用，助手就能拉取评论，顺着链接去看相关仓库或示例，再给出复现问题的建议。真正有用的变化在于：对话一边进行，一边就能拿到相关证据。

讲者还介绍了一个只能通过 MCP 下单的 T 恤演示。工作坊期间，T 恤免费送，但需要一个支持 MCP 的客户端。现在那个地址已经指向 WorkOS Shop，当时的福利只能当作历史来看。他们提到在 Exploratorium 办的 MCP Night 座无虚席，可见大家对这个协议兴趣很浓。随后工作坊回到了自己的应用上。

梗图生成器接收一句抱怨，挑一个现成模板，写新的配文，再通过 Imgflip 发布生成的图片。语言理解交给 OpenAI。生成的 URL 可以分享，但 Imgflip 的文档写明：拿到 URL 的人都能看到图片，浏览量低的图片可能被删除。它既不是私密存储，也不保证永久托管。构建时先做一个可测试的工作流步骤，再扩展成完整流水线，最后才加上智能体。

配套的工作坊说明提供了自学路径。参与者可以靠检查点分支追上进度，main 分支是完成版应用。录像从第零步的检查点开始，用 npm 安装依赖。重点是把各个部件弄懂，懂到能自己动手试验，而不是要求每个人以同样的速度做完所有练习。

04

选择由谁控制执行顺序

一位听众的提问，让工具和工作流的区别变得具体起来。createTool 和 createStep 两个 API 看起来很像，编排权却落在不同的地方。

| 组织方式 | 谁决定执行顺序？ | 适用场景 | |---|---|---| | 独立工具 | 模型在运行时决定调用哪些 | 有多种动作可选，具体用哪些由请求决定 | | 工作流 | 应用代码规定步骤和转换 | 任务必须按已知顺序执行 | | 两者兼用的智能体 | 模型选择调用哪项能力，工作流控制内部流程 | 对话需要灵活，背后又是一个可重复的任务 |

Proser 打了个比方：给智能体一百个工具，然后让它去迪士尼乐园。动作空间又大又缺乏约束，歧义就来了。工作流能减少模型需要做的编排决策。

最先遇到的配置问题，都是普通的开发问题。公开的工作坊仓库不需要私有权限，但工作电脑如果没配好 SSH 凭据，用 SSH 克隆命令就会失败。这时改用 HTTPS 克隆就行；带冒号的 SSH 地址和浏览器里的 URL 不是一回事。参与者处理这个问题时，Nisi 推荐了 Mastra 的文档 MCP server。他在 Claude Code 和 Claude Desktop 里都装了，用来补充框架相关的上下文。随后有人简短追问了一个 JSON 配置对象，但没有展开成完整的配置步骤。

第一个成功标准刻意定得很低：打开 playground，里面还没注册任何智能体、工具或工作流。有人问为什么选 Mastra，Proser 提到了 TypeScript、Vercel AI SDK 对模型提供方的抽象、内置评测，以及顺手的本地开发体验。他回忆说，曾经只是把一条现有流水线的模型换成 GPT-4o，效果就提升了。更长远地看，他希望团队有共享的基本单元，同事们看得懂，也能通过代码或 API 调用，不必各自在定制脚本里重复搭流水线基础设施。这些理由来自早期的使用体验，不是框架基准测试。

05

在运行之前把工作流定下来

另一个问题针对一段代码：先列出步骤，又接着链式调用 .then(...)。一位 Mastra 贡献者解释说，步骤数组是线性定义；链式语法则用来实现分支、条件和循环，他提到了 .then、.if、.branch 和 .doWhile。核心区别在于，定义图和执行一次运行是两回事：.commit() 负责定稿并返回工作流，本身不会执行任务。这位贡献者还提到，本地可视化用到的是缓存、同步过的表示，这也和定稿有关。配套示例里既保留了步骤声明，也保留了显式链式调用。所以别把这段讨论理解成：不管哪个版本的 API，都该删掉其中一种写法。

第一个检查点里有一个 Mastra 实例和记忆相关的脚手架，但还没注册任何应用能力。启动开发服务器后，playground 会显示 Agents、Networks、Tools、MCP Servers、Workflows 和运行时上下文几个视图。Nisi 在录像里说的是 localhost:4011，查阅到的配套说明写的却是 localhost:4111/workflows。请以你检出的代码为准，按开发服务器打印出的地址访问。服务器还暴露了一个 API 端点和 Swagger 规范。下一个任务是写一个用完即弃的单步工作流，让这些查看工具在完整应用做出来之前就派上用场。

06

改进编程上下文而不指定编辑器

构建过程中，话题转到了 Neovim 里的 AI。Nisi 演示了 Avante 的聊天界面，Proser 说自己以前用过 NeoAI；有人提到 Goose，Nisi 说还没试过。Nisi 最后还是更喜欢在 Tmux 里分两个窗格，一个开 Vim，一个开 Claude Code。这样他平时的编辑习惯不受影响：助手干活时，他把 Vim 最大化；需要看对话时，再恢复分屏。

一位听众不赞成强制统一框架或编辑器。大家区分了两件事：有用的共享默认配置，和不顾产品需求、自上而下推行的标准。另一个问题拿《马里奥赛车》的加速包打比方：团队能不能给开发者一套强力的起步配置？Nisi 认为 Cursor Rules 应该不断演进，就像测试随代码库一起成长。Proser 则更倾向于通过 MCP 提供文档，这样多个兼容的客户端都能用上。

Proser 说，开启 Mastra 的文档 MCP server 之后，他有一次编码全程零幻觉，要的功能第一次就生成对了。他还用 TypeScript 的 lint 和编译检查了代码。可以照搬的做法是让助手查得到相关文档；但这件轶事并不能保证，接入文档的助手总能写出正确的代码。

07

把执行引擎、模式和重试分开

有人问到持久执行（durable execution），话题引到了 12-Factor Agents 和 Mastra 当时刚推出的 Workflows vNext。一位贡献者解释说，原来的引擎基于 XState；vNext 想保留工作流语法、可视化和开发服务器，同时允许底层换用别的执行引擎。最先讨论的集成是 Inngest，用户还希望支持 Temporal 和 Cloudflare Workflows 等选项。贡献者说，Inngest 标着“实验性”是因为刚发布不久，并表示 API 预计会保持稳定。这只是预期，并没有演示过持久性测试。

部署是另一个选择题。贡献者介绍了几种方式：默认打包成 Hono 服务器，可以跑在 Docker 里；Cloudflare、Netlify 和 Vercel 都有适配器；还有 Mastra Cloud。大家也聊到了把应用嵌进 Express 或 Next.js 后端。设计目标是让应用保持可移植，不绑死在某一个托管环境上。

结构化输出引出了另一个边界问题：提示词和 schema 冲突时会怎样？普通的字符串类型，模型很容易满足；“恰好四个字符”这种细化约束就难多了。Zod 在运行时描述和校验数据，它不会让 TypeScript 编译器去检查一个还没生成的模型响应。OpenAI 能遵守 schema，也不能全算在 Zod 头上：按它的 Structured Outputs 说明，靠的是模型训练加约束解码。这和在应用代码里校验返回值是两回事。

一位 Mastra 贡献者说，他们在 16 个模型上测了 30 个 schema，发现工具调用比结构化生成更难。有人起初以为框架没做专门处理，这位贡献者纠正说：Mastra 加了一个兼容层，用来改善工具 schema 的表现。对应的工具 schema 兼容性研究介绍了 schema 转换和约束描述。文章标题里的结论和完整表格用的模型集合并不一样，所以这里值得记住的是多了一层兼容机制，而不是某个普遍适用的准确率。

反复调用不一定说明 schema 校验在自动修复结果。开发过程中，讲者不小心发了一张很大的 base64 编码图片，结果连续失败。一位贡献者推测，智能体可能一直重试到了 maxSteps，但没能确证。有人问：约束是四个字符，返回了五个字符，会不会自动重试？贡献者没有给出确切答案。应用代码仍然要明确规定值被拒绝时怎么处理。比如，校验时可以保留失败的证据，而不是悄悄截断：

```typescript import { z } from "zod";

const fourCharacters = z.string().length(4);

export function validateLabel(value: unknown) { const result = fourCharacters.safeParse(value);

if (!result.success) { return { status: "rejected" as const, issues: result.error.issues, }; }

return { status: "accepted" as const, value: result.data, }; } ```

模型可能返回不合规的内容。是直接拒绝、要求修正，还是换条路走，得由应用另行决定。

关于 serverless 的追问，答案就没那么明确了。有人提到一个社区做的 Lambda 部署工具，但现场没搞清楚：工作流的各个步骤会拆成独立函数，还是共用一个部署好的函数。这对长时间运行的任务和平台时长限制很关键。讨论中还引用了一个没有出处的 Cloudflare 打包体积数字；做部署规划时，请参考当前的 Workers 限制，别把口头说的数字当成平台承诺。

08

检查第一个结构化结果

到了下一个检查点，Mastra 实例注册了这个测试工作流，workflows 目录里放着它的实现和 schema。刷新 playground，就能看到一张只有一步的图，输入是一段描述工作烦恼的原始文本。Nisi 输入“Conference Wi-Fi sucks.”（会场 Wi-Fi 太烂了）。节点变绿，查看输出，能看到原文、frustrated（沮丧）这个情绪，以及 technology（技术）这个烦恼类别。还没到选模板、发图片那一步，中间对象就已经清清楚楚摆在眼前。

一句抱怨变成下一步的结构化输入 下一步拿到明确的分类，原始抱怨也原样保留。 构造示例：对象 ID 和显示标签仅用于教学，不代表演示中 JSON 的实际属性名。 抱怨——保持不变：Conference Wi-Fi sucks 操作：运行演示中的烦恼提取步骤。 - 原始文本 - 之前：提取前：Conference Wi-Fi sucks - 之后：实际提取结果：Conference Wi-Fi sucks - 情绪 - 之前：提取前：无 - 之后：实际提取结果：frustrated - 烦恼类别 - 之前：提取前：无 - 之后：实际提取结果：technology 下一步拿到明确的分类，原始抱怨也原样保留。

下一个练习把它扩展成完整的工作流，在各个操作之间加上数据映射。一位听众问：传给下一步的就是这段 JSON 吗？准确地说，它的结构是应用自己定的约定，这样设计是因为下游操作需要这些值。字符串、数组、嵌套对象都可以拿来组合；好的 schema，就是能把下一步所需信息带过去的那个。

09

把模板的文案位置延续下去

设计这些约定，得往后多看几步。烦恼的主题和强度能帮着选模板，但选模板这一步不能只返回一个图片名。Nisi 用 The Rock 坐出租车的梗图来解释：Imgflip 模板带有配文框，一个模板可能有三个框，发布请求必须给每个框都填上文字。配文框的元数据应该写进流水线的约定里。要是它在选模板和生成配文之间丢了，后面的步骤就没法可靠地让文字贴合图片。

用一小段 TypeScript 边界代码，就能把这层关系写明白。下面的代码里，选中的模板保留了 ID 和配文框数量，配文校验则检查文字和框是否对得上：

```typescript import { z } from "zod";

const templateSchema = z.object({ id: z.string(), name: z.string(), boxCount: z.number().int().positive(), });

export function prepareCaptionRequest( templateInput: unknown, captionsInput: unknown, ) { const template = templateSchema.parse(templateInput); const captions = z.array(z.string()) .length(template.boxCount) .parse(captionsInput);

return { templateId: template.id, boxes: captions.map((text) => ({ text })), }; } ```

schema 能检查结构和数量，却判断不了配文好不好笑、合不合适。屏幕上那张三格梗图让实际排版一目了然。随后，工作坊转向在 playground 里调提示词、温度和模型。

10

在怪罪模型之前先调试外部服务

生成梗图这一步频频出错，大家由此整理出一份具体的凭据检查清单：

1. 用 Imgflip 的用户名，不要用账号邮箱。 2. 填上 Imgflip 密码。如果账号是用 Google 登录注册的，事后要去 Imgflip 设置里设一个密码。 3. 先确认所需凭据都已配好，再去排查语焉不详的生成错误。

Proser 说，工作坊原先让大家共用一个匿名凭据，后来改成每人用自己的账号，为的是少碰速率限制；但两种方式的限额到底差多少，并没有定论。参与者也可以先保存没写完的代码，再切到检查点分支追上进度。讲者还解释了另一个取舍：他们删掉了生成全新图片的步骤，因为碰到的账号验证流程太麻烦，不适合在工作坊里做。用现成模板，练习就能专注在编排上。

有人问这些应用在 playground 之外怎么调用，Proser 把已上线的经验和实验分开来讲。他工作中现有的应用，大多是 Web 界面背后跑 Vercel AI SDK，通常托管在 Vercel 上；用 Mastra 做内部工具是最近的事。通过 API 调用工作流，比如每晚由 cron 任务触发，是他想探索的模式，他并没有说自己已经在生产环境里完全跑通。

参与者开始在 Slack 里晒做出来的梗图，吐槽的内容有销售同事在系统工程师旁边大声嚷嚷，也有每个项目都是最高优先级。讲者也承认生成过冒犯性的内容，想办法拦过，但没拦干净。执行成功、配文结构合法，都不代表内容合适。送书活动和大家晒的例子说明进展不错，但应用要发布什么内容，仍然需要人来把关。

一个数据工程方面的问题，拿工作流和 Airflow DAG 作比较。Proser 先绕到了 GraphRAG 上，也就是把向量检索和知识图谱遍历结合起来，然后才回到自己更简单的经验：顺序步骤加分支。一位听众问：成本很高的流水线，能不能从后面某一步接着跑，不用把前面的调用再来一遍？讨论没有解决选择性重跑的问题，但指出了另一种控制成本的办法：每一步单独选模型，简单的提取用便宜的模型，难的活再交给更强的模型。用独立工具也能让模型跳过不必要的操作，只是这样一来，执行的控制权就换了人。有人问到缓存，没有得到具体的实现方案。

继续排查凭据时，问题又落回到进程状态上：检查 .env，改完后重启正在运行的服务器，再看看值里有没有不小心多出来的空格。保存了文件，不等于当前进程已经重新加载了环境变量。这次排查中剩下的那个错误，录像里没有给出明确的解决办法。

11

看着一段对话变成一笔经过认证的交易

现场的 T 恤演示暴露了一种很有参考价值的失败模式。Nisi 让 Claude 给他一件 T 恤，Claude 起初回答说没法提供实物商品——原来 MCP 商店的连接断了。重新连接、再提一次请求、批准工具调用之后，对话才拉取到可选的 T 恤。连接、工具授权、实物发货是三个不同的阶段；等授权和等发货不是一回事。

T 恤的描述里写着“Context is everything.”（上下文就是一切）。助手接着收集尺码、公司和完整的邮寄地址。Nisi 报了 XL 和 WorkOS，现编了一个地址，助手提示缺少所在地区信息后，他又补上。工具返回了订单确认，他随后又问了问订单情况。围绕这个外部操作，模型做的是帮忙收集参数、展示结果。

说到托管，讲者区分了两个版本：这个实例他们认为部署在 Vercel 上；另有一个 Cloudflare 版本，Nisi 说它把订单信息存在 KV 里。认证由 WorkOS 提供。他之前已经登录过，所以大部分登录过程看不到，但连接时其实走完了一遍认证流程，拿到了 token。接着他问系统：知不知道一些他没在聊天里输入过的身份信息。这就是更广义的电商模式：用自然语言提需求，通过认证访问工具，收集参数，再执行下单。他们开玩笑说可以靠聊天哄系统打折，这并不是演示出来的漏洞，但也点出了一个道理：交易规则必须放在聊天说服不了的地方。

12

追踪一个完整表情包走过四个步骤

回到梗图应用，下一个检查点展示了完整的工作流。它有四个实质步骤，步骤之间有映射，最后还有一个输出映射：

| 步骤 | 职责 | |---|---| | 提取烦恼 | 把抱怨转成结构化信息 | | 查找基础梗图 | 选定模板，并把它的元数据往下传 | | 生成配文 | 为选中的模板写文字 | | 生成梗图 | 把模板和配文提交给 Imgflip |

每一步都有输入和输出 schema。映射负责把上一步的结果转成下一步要求的格式，不让这层衔接藏在代码里。

现场输入的抱怨是：忙着准备工作坊，没空审查 pull request。图跑了起来，各步骤依次变绿，提取器把问题归为沟通类。后来查看发现，选中的模板是 Disaster Girl，生成的配文说的却是“本来发封邮件就能解决的会”，以及大家假装一切正常地微笑。这个结果说明流水线完整跑通了，也暴露了其中可能出现的语义漂移：最后的笑点虽然和职场沟通有关，却已经偏离了最初那句关于 PR 的抱怨。

真正有用的调试手段，是一串可以逐个查看的输入和输出。开发者能找到信息是在哪一步走了样，再去调整对应的提示词、schema 或映射。这些都在本地完成，还没到部署那一步。下一个练习会加上一个智能体，给它写好指令，再授权它调用这个已经跑通的工作流，同事就能通过聊天发起同样的操作。记忆和 playground 测试也是这次集成的一部分；烦恼分析和梗图选择，仍然可以靠改提示词来调优。

13

应用这个模式，并检查生成了什么

Mastra 的贡献者简单聊了聊这次工作坊和他们早年做 Gatsby、做开源 JavaScript 的渊源。他们来现场并不是早就安排好的，但讲者正好可以当面问实现上的问题。随后讨论转向梗图以外的应用。一位参与者想通过聊天来操作物理服务器，拉取日志，协助排查故障。Proser 看重的是那些几步操作、几次 API 调用就能搞定的手工小任务。Nisi 和 Proser 在热情之外也给了一条实在的建议：生成的代码要审查，提交前用 GitGuardian 这类密钥扫描工具过一遍。

Nisi 的跨 SDK 实验说明了审查为什么重要。同时维护多种语言的 SDK，意味着 Node 里加一个小字段，Ruby、Go、PHP、Kotlin 等版本可能都得跟着改。他做了个实验：给第一个 PR 打上标签，其他仓库就自动生成对应的 PR。Nisi 说他和 Claude 合作两个小时就做出了能跑的原型；Proser 说最后生成的 GitHub Action 大约有 4,300 行。有人问是不是用了 Dagger，Nisi 说没有，还承认自己根本没审查过生成的代码。这个实验最终没有上线。它的复杂度大多花在处理 diff 上，有几次确实改对了要改的地方，却把文件里其余内容全删了。他觉得，Claude Code 后来推出的程序化调用能力，也许能接手这类编辑上的细活。

Proser 举了个规模更小的内部工具例子：帮市场或销售同事找出已经在用 MCP 的工程师，好在会议上做推广。据 Proser 说，同事才讲了四分钟，他就做出了一个能用的 v0 分析工具。同事拿到一个单独的 URL，在那里输入内容就能得到分析结果。一段描述性文字就够原型起步了，但这并没有让他那些不懂技术的同事抢着自己上手。在他看来，选择亲手做软件的人依然有个共同点：享受一遍遍把软件做对的过程。

讨论还聊到了法律行业：Proser 说，有些律师虽然不写程序，却会就 GenAI 问得很细；他提到可以在海量判例上做语义检索和信息压缩。回到工作坊，一位听众的问题划清了范围：在 playground 的 MCP Servers 视图里配置 MCP server 不属于这次练习，讲者表示另有教程。

以聊天、检查和持久化收尾

最后一个检查点在 Agents 标签页里加上了梗图生成器。聊天界面旁边是一栏概览，列出智能体的指令、可调用的工作流和模型设置。测试时可以调整温度和 top-p。示例抱怨是：总被拉去开长会，却一句话都插不上。智能体调用工作流，在对话里直接返回一张梗图，然后接着聊。展开工具调用记录，能看到参数、工作流调用和完整结果。对话层并没有把执行细节藏起来。

同样的界面也可以用来出报告、做分析、跑 SQL 查询、生成代码或做审查。工作坊实际做成的东西要窄一些，也更具体：智能体为一个多步工作流提供输入，再把返回的数据变成人看得懂的回复、一张图片和一个分享链接。讲者鼓励大家去部署，但并没有为这个应用的隐私做任何保证。

Proser 提到一个没有演示的 RAG 例子，作为进一步的方向：在同一个框架里定义检索和生成，能省掉他以前在几个库之间写的胶水代码。其他扩展方向包括新增工具、接入向量数据库、通过 MCP 对外提供能力。讲者建议的下一步是让同事真正用起来，从实际使用中学习，而不是在本地成功生成一次就收手。最后的问答环节里，讲者还提到仓库里的 Markdown 幻灯片可以复用，他们做演示用的是 Slidev。

最后一个技术问题关于记忆。Proser 解释说，演示用 SQLite 保存聊天记录，这些记录显示在 playground 的左侧栏里；他还提到可以换用 Postgres 等其他存储驱动。存储必须先配置好，再接到用它的组件上；光有对话界面，并不意味着能持久保存。那位参与者还问了个更具体的问题：之前提到的某个执行步骤在哪里找？这个问题留到会后单独帮忙，没有在屏幕上解答。做完的应用最终有三个层面要分别弄懂：用户看到的对话，开发者查看的工作流执行过程，以及在多次聊天之间保留下来的历史记录。

What Runs Where? Local AI in Production

A locally built game, a 50-request inference test and a failed attempt to change a GPU fan’s lighting show how the model, inference engine and tools shape what a machine can do. Osmantic founder Ahmad Osman then asks how that system could learn from its owner’s corrections.

01

A Windows machine builds a game

The playable game at the RTX Spark launch was itself a local AI workload. Ahmad Osman’s team at Osmantic built it on an RTX Spark running Windows, using an inference engine tuned for the chip and its own Portal agent harness. The team shared traces of the build. The engine ran the model, while the harness let the model perform the steps that turned its output into a game. Both had to work for someone to pick up the result and play. RTX Spark game demo, 1:56

Could you tell which of two answers came from the local model? In a demo with Hugging Face, the answers looked similar to Osman. The local 27-billion-parameter model decoded at 51 tokens per second, and the model served through OpenAI’s cloud decoded at 34. The answers illustrate one task, and the rates describe how fast the text streamed once generation began.

02

What leaderboards measure and what agents wait for

An Artificial Analysis leaderboard put a hosted model ahead of an open model Osman preferred in practice. The disagreement gives model selection a concrete starting point. Which tasks must the system finish, and what counts as success in the environment where it will run?

A chart of progress since March 2023 measured the length of tasks models could solve by the time a human would take to complete them. Osman described that measured task horizon as doubling about every four months. The horizon measures the size of the work the model can tackle. Runtime measures how long the model itself takes to do it.

In the October 2026 OpenRouter data Osman showed, agent workloads had overtaken human-driven workloads in token volume after February. On a separate measure, the Artificial Analysis Intelligence Index v4.1 showed open models rising from 13 to 51 points since January 2025, narrowing the gap with closed models. Open models accounted for much of the October leaderboard’s token use, while spending favored closed models. Osman’s bet, dating to March 2025, was that small specialists would take on more of that work.

An agent can spend much of a run waiting for a shell command or another tool to return a result. Faster decoding saves time during generation, so a modest GPU can be adequate when tool execution dominates. Osman used a single RTX 3090 as an example. When one agent starts several others in parallel, the engine has to serve a different workload. It now has several requests to advance at once.

The benchmark choice can change which group leads. Osman described a substantial gap on HLE Diamond and a two-point lead for open models on Terminal-Bench. A security vendor’s report offered a narrower example. Small, specialized open models could detect the kinds of issues the vendor tested for. Osmantic applies that logic step by step. A coding specialist can implement a well-scoped change, while an unfamiliar problem may call for a model with broader capabilities.

03

The trailer divides work between an agent, GPUs and a laptop

The trailer started with videos and articles Osman gave the agent. Opus found quotes and clips, handled the music and arranged the text overlays. Osman chose which material to keep or drop. The six hours, from about 9 p.m. to 3 a.m., covered the production session with his editorial input.

Which machine handled each part of the trailer? The agent used two RTX PRO 6000 GPUs for photo tagging and scaling video and audio. The MacBook handled editing and A/B comparisons so Osman could choose between variants. Osman expects a small specialist to coordinate a project like this at home within three years of the talk.

The cloud runs in “someone’s basement,” as Osman puts it. Portal, code-named Cairo, uses a cloud emoji for the cloud you can run at home. A machine under a desk and a rented machine in a data center can each run a stack you configure. Both still face the same constraint when a conversation grows. Alongside the weights, the model needs memory to keep track of the context.

Osman’s basement rig of 14 RTX 3090s could barely hold DeepSeek R1, a 671-billion-parameter model. During a six-hour livestream experimenting with running it in DDR4 RAM, he got about eight tokens per second. Generation slowed sharply around 16,000 tokens. Fitting the model had made local reasoning possible. Sustaining it through a long run was a second problem. A later 120-billion-parameter open model impressed him more at a much smaller size. He had also built a local screenshot organizer in early 2025 by giving a small model a specific job and writing the software around it.

How did the trailer divide up the work? Osman supplied the material and guided the selection. The two machine assignments show where media processing and editing ran. - Videos and articles — Osman supplied his own recordings and writing. - Editorial choices — Osman selected material to keep or drop. - Opus — Found quotes and clips, handled music and text overlays, and coordinated production. - Two RTX PRO 6000s — Tagged photos and handled scaling for video and audio. - MacBook — Handled editing and A/B comparisons. - Videos and articles → Opus (Supplies material) - Editorial choices → Opus (Guides selections) - Opus → Two RTX PRO 6000s (Uses GPUs for media processing)

04

How much precision does each layer need?

Quantization represents model values at lower precision. The weights take up less memory, and the engine can move fewer bytes if it can unpack and compute on that representation efficiently. Even within NVIDIA’s Blackwell generation, Osman treats the RTX PRO 6000 and the B200 and B300 as distinct targets for inference software.

- During training. Quantization-aware training exposes the model to reduced precision while it learns. Osman connects this to mixed precision, where some parts keep more numerical detail than others. - Before deployment. Run representative tasks, use them to see which parts of the model the workload relies on, then assign precision. Osman illustrates the idea with one layer at 16 bits, another at eight and a rarely used layer at one bit. A different profiling workload may depend on the layer chosen for compression. - At runtime. The engine quantizes values as it serves the request. This puts the quantization work on the inference path, while a profiled assignment can be settled in advance.

How much quality survives compression? Osman showed an older and a newer quantized model to illustrate improved retention. The discussion leaves the task and common scoring baseline unclear. A uniform four-bit conversion can lose precision in layers your task relies on. Compare the builds that fit in memory on the same work and score the outputs against the same criteria.

05

Prefill and decode stress different parts of the machine

- Prefill. The engine processes the prompt and builds the key-value cache, the attention state it reuses during generation. A longer prompt gives it more work before the first output token. This phase tends to be limited by compute. - Decode. The engine generates the continuation one token at a time. In a single stream, repeatedly reading the weights can make memory bandwidth the limit. Time to first token measures how long you wait for the answer to start. Decode rate measures how quickly it appears once it starts.

Architecture changes how many weights the engine uses for each token. A dense 27-billion-parameter model uses its full set of weights each time. A mixture-of-experts model routes each token through a subset of experts, so it can use far fewer parameters than it stores. On a DGX Spark, a dense model can fit in memory and still decode slowly because the engine has to move so many weights for every token. Smaller devices can also gain capabilities as models improve. Osman pointed to models running on an iPhone and expects an orchestrator to divide future workloads among one- and two-billion-parameter specialists.

The engine also determines how much of the available bandwidth a workload gets to use. Osman quoted 273 GB/s for one DGX Spark and an expected figure above 1 TB/s for the Apple system he discussed, yet reported that two Sparks came out ahead in decode. That result compares complete configurations, with software and hardware both in play. Osman favored NVIDIA’s CUDA ecosystem when engineering time to get a stack working or tune it was scarce.

06

Fifty simultaneous requests change the hardware race

The Hugging Face demo ran the same 27-billion-parameter model on four systems, including an RTX PRO 6000, an M5 Max MacBook Pro and a DGX Spark. In the single-stream race the RTX PRO 6000 generated tokens fastest. Osman credited its higher memory bandwidth.

What happens when each system receives 50 requests at once? The RTX PRO 6000 setup reached almost 1,300 tokens per second across the requests. The other setups in the demo served them sequentially. A batching engine can use one pass over the weights to advance several requests together. That helps explain why the total tokens per second matter when an agent sends work to several other agents at once. The sequential results reflect the engines used in this demo. 50-request test, 23:43

A portable engine gives many machines a common way to run models. A chip-specific engine can use instructions tailored to that chip to unpack weights and do the math. File format, quantization and engine choice go together. Osmantic created its own ODS weights, and Osman invited contributions tuned to specific machines and models so ODS could make those engines the defaults for the combinations they support. To get a feel for the engineering cost, he suggested starting with a sub-billion-parameter model and a few small kernels. ODS repository

An OpenRouter comparison ran one model across different hosted configurations. The chips varied and some engines were private, so each speed characterized the serving stack as a whole. For a local deployment, the comparable test runs the chosen model build and engine on the intended chip, at the concurrency the application will use.

07

A 100× tokenizer improves the whole request by 1.1%

Measure time to first token for startup, tokens per second per user or agent for streaming, and requests per second for serving capacity. Task accuracy tells you whether the work succeeded. Run these measurements on the deployment hardware. Aggregate throughput can rise sharply in a batch while each user still cares when their own answer starts and finishes.

One tokenizer ran about 100 times faster after optimization. The whole request improved by 1.1%. If the other stages took the same time, tokenization accounted for roughly 1% of the original request. Even eliminating that stage would have saved about that much.

Speculative decoding goes after generation itself. A cheaper draft mechanism proposes several tokens, and the target model verifies them together. When the target accepts several proposals, one verification pass advances the output by several tokens. If it rejects the first proposal, the draft work buys little. The gain depends on acceptance and on how efficiently the engine drafts and verifies on that chip. Osman highlighted work adapting the technique for different models and for AMD and NVIDIA hardware.

Another optimization changes what the scheduler knows. In Osman’s preliminary reading of a recent paper, recording where each turn ends gives the scheduler known boundaries to work with. He cited throughput gains across several models, with the exact metric and baseline unclear. ODS aims to make improvements like these available by choosing an inference engine for the model and platform the user selects.

08

The local agent that could not change a fan’s color

A friend connected a local 27-billion-parameter model to a coding harness and asked it to change the RGB lighting on his RTX 5090 fans. The local setup failed. A hosted setup had succeeded, so Osman asked what tools each had. Search gave the hosted setup a way to find information about tools that might have appeared after the model was trained.

Osman supplied access to a search engine and had his friend configure it through an environment variable. On the retry, the same request changed the colors. The added tool gave the local agent a way to discover how to control the hardware, and the harness let it act on that information. ODS includes search because missing tools can make a capable model look like it failed at a task it could otherwise complete.

The harness can also reduce work on repeat tasks. In the research example that followed, the system rewrote parts of its tooling around frequent tasks. Later runs could reuse that tooling and spend fewer tokens reconstructing the procedure. Search supplies information the agent needs during a run. Reusable tools preserve a procedure it has already worked out.

09

Use real task traces to decide where a specialist fits

In the OpenRouter breakdown Osman cited, coding users switched models more readily. Translation and summarization users tended to stick with the models they had. A defined workflow gives you a concrete test for switching. Give each candidate the same inputs and check the outputs against what the application needs.

Osman cited an Airbnb report in which a two-billion-parameter specialist matched frontier-model quality at about 1% of the cost on the workload Airbnb evaluated. The talk leaves the task and cost accounting unspecified. The approach Osman proposes starts with traces from a capable agent running your own tasks. Use those traces to build an evaluation around the outcomes you need. For a recurring task, the traces can also guide synthetic training examples and reinforcement learning for a smaller model. Run that model through the evaluation to see whether it can take over the task.

Distillation is one way to teach a smaller model behavior from a more capable teacher. Fireworks was an example of a company building and hosting specialists. The tradeoff is coverage. A model tuned for frequent software tasks can be fast and effective on that work, while a novel research problem may fall outside the distribution it learned. The evaluation needs to cover the part of the workflow you hand over.

10

Rented hours, idle GPUs and the work of owning them

Renting can make sense for a job that needs a GPU for a few hours or a burst above existing capacity. A GPU you own ties up capital even while idle. A rental can bill for idle time as long as you keep the instance running. Where the costs cross depends on how many hours you need to reserve and what it costs to keep that capacity on hand.

A cheap model API and a rented GPU give you different levels of control. Osman raised the possibility that an opaque API could route requests to a different model from the one advertised. On a rented GPU you can select the weights and inference engine yourself and check that the machine meets the workload’s needs. Both open and closed model prices had fallen in the figures he discussed. Price per million tokens gives you a unit cost. Cost per successful task also depends on how many tokens and attempts the job takes.

Osman’s rental example gives an agent the provider’s CLI. The agent rents the GPU, starts the workflow and releases the instance when the job finishes. That last action keeps you from paying for time after the job has ended. Ownership brings dependencies to maintain, silent failures to detect, dead hardware to replace and redundancy to provide. An agent can help with the scripts. A second check may still catch a failure it missed on the first pass.

11

The next model may fit on the GPU you already have

Three changes make existing machines more useful in Osman’s account. Models deliver more capability per parameter, specialists focus on particular workflows, and better engines extract more performance from the same chip. Individual RTX 3090s from his basement rig now run models he finds more capable than the early models he used the rig to run.

The first 27-billion-parameter dense release trailed a 397-billion-parameter mixture of experts in Osman’s comparison. About a month later, a successor with the same 27-billion-parameter count came out ahead in the comparison he cited. A machine that already fits the smaller model can gain capability when a better release arrives at the same size.

The larger model activated about 17 billion parameters per token. The smaller dense model used all 27 billion. At equal precision, the experts still need nearly 15 times the weight storage, even though a given token uses fewer parameters. Total weights tell you how much has to fit. Active weights help explain the work the engine does to generate each token.

How much memory does the attention state need once the weights fit? In a DeepSeek KV-cache comparison, Osman cited 13 GB for 400,000 tokens and 29 MB after compression. The context length for the 29 MB figure is unclear, which limits what the reported 437× reduction can tell you. The deployment tradeoff still follows from what the cache stores. If each token needs less cache memory, more context can fit on the same machine.

12

What a personalized system has to remember

Large providers train and serve shared models for a broad user base. Osman expects them to keep doing that, given the cost and work of training and hosting a separate model for each person. That is why he argues that continual learning for an individual has to run locally. A system that learns from your work needs to carry your corrections forward, and a machine you control gives you a place to keep the evolving state and decide when to update it.

A Markdown skill file can carry instructions from one run to the next. Osman’s failure case begins with a long context and a skill that already exists. The agent loses track of it and writes to three skills about the same topic. Future runs now have more overlapping advice to reconcile. The test of learning from a correction is whether the system applies the right instruction the next time it needs it.

13

A tuned laptop and the case for planning a model ahead

The Windows RTX Spark behind the opening game was a laptop configuration with 128 GB of memory. Osman reported 72 decode tokens per second for a local model on it. The game gives that rate a concrete counterpart. A portable machine with a tuned engine and a harness had already produced something people could play.

In January, Osman had predicted that an RTX PRO 6000 would run a model that reached the capability of an earlier hosted model by year-end. In his assessment a 27-billion-parameter open model reached that level by April. He still saw a compute advantage for large labs that can use agents to accelerate their own research. Specialization gives smaller teams a way to improve the tasks they care about while new techniques spread. That is the case for planning a model ahead when you buy hardware.

14

Engrams, decision models and weight edits

Osman’s proposal for ODS gives the system three ways to carry something forward. It can retrieve information, make a learned choice about a task or change the model’s behavior directly. Continual-learning proposal, 52:21

- Engrams. Keep lookup embeddings in a table the model can retrieve from. Osman likens it to a map stored in RAM or on an SSD and sees the lookup as work a CPU can handle. - Decision models. Give a classifier-like model a choice to make for a task. The proposal applies that familiar mechanism to more of the decisions a harness has to make. - Weight edits. Change the model’s parameters so a correction can affect behavior on later runs. A table lookup supplies information at the point of use. A weight edit changes the model that uses it.

The open design question is where feedback should go. Osman distinguishes loops inside a model, around it in a harness and across experiments. He asks whether lookup and decision models could have feedback loops of their own. The proposal leaves the update rules open, including which observations should change a table, train a decision model or trigger a weight edit.

“I hate benchmarks,” Osman says as he opens the floor. His own evaluations start with traces from software he built and corrections he made when the agent went wrong. A system can learn to raise the very score it was tuned against. If it has actually learned how to handle a correction, that behavior should show up the next time the same problem takes a different form in real work.

要点总结

  • Profile prompt processing, generation and tool wait separately. Then test the concurrency your agents create. The RTX PRO 6000 demo measured nearly 1,300 tokens per second across 50 requests, a different quantity from any one stream’s decode rate.
  • Evaluate the harness alongside the model. Search access let the local agent complete the same RTX 5090 lighting request on its retry. Real task traces help you decide which recurring jobs a smaller model can take over.
  • Continual learning needs both a place to apply corrections and a way to judge whether they stuck. Lookup tables, decision models and weight edits offer different places to make a change. Traces and real corrections supply cases for evaluating the resulting behavior.

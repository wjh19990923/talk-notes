ALPHALAB：用前沿 LLM 在多个优化领域开展自主多智能体研究

AlphaLab 把预测任务变成并行的研究战役，然后利用这种方法的失败，让评测环境成为改进系统本身的基础。

熟悉模型训练、留出验证和编程智能体会有帮助；不需要量化金融背景。

01

更多研究周期可能在哪里有帮助

给定一个时间序列数据集，能不能既预测出未来的值，又让模型保持良好校准？Brendan Rappazzo 在 Morgan Stanley 带的团队，面对的许多应用问题都是这个样子。据他介绍，团队有大约 30 名 AI 方向的博士研究员，工作横跨学术发表、开源发布和内部应用。其中一些应用很像 Kaggle 题目：输入、预测目标和约束条件都足够明确，可以反复做实验。Rappazzo 还提到，卖方业务面对的对抗性选择更少，这类问题很适合拿来尝试自动化研究。

机会首先来自已经上线的算法。多调一些超参数，或者把现有方法组合得更好，也许就能带来提升，只是小团队抽不出时间去做。机会还延伸到各个交易台：为信用债建的模型，也许能迁移到市政债上，前提是有人去做适配和测试。还有些交易台几乎没用过机器学习，哪怕只训练出一个过得去的第一版模型，也可能派上用场。这几种情况的研究起点各不相同，但都能从持续的“实现—评测”循环中受益。

Rappazzo 认为，真正的转折点出现在 2025 年 12 月。有了 Opus 4.5，再加上 Claude Code、Codex 这类编程框架，长周期任务开始变得可行，团队于是把自主研究当成一项重点投入。关键在于两样东西的组合：一个能力够强的模型，加上一个能让它把大块任务持续做下去的执行环境。

02

一个框架，不同的起点

业务目标是提升 P&L，让更多算法进入生产。要服务这些目标，系统必须接入现有的数据访问、回测和评测基础设施，同时兼顾两种截然不同的研究起点。

| 起点 | 交给系统的工作 | |---|---| | 数据路径，加一句自然语言描述的预测目标 | 研究问题、搭建评测、启动实验 | | 数据脚本、评测，以及表现不错的现有模型 | 跑更多实验，寻找改进空间 |

第二种情况和第一种同样重要：自主研究不必从零搭建建模流水线，也能派上用场。

框架还要能对接不同的前沿模型厂商，也要越来越多地支持开源模型。它的设计应该随着模型变强而受益，而不是依赖一套复杂机制——模型一变强，这些机制就过时了。还有一项要求很难写成接口：Morgan Stanley 的企业知识和研究员的专业经验，该怎么进入系统？正是这个问题，最终改变了团队把工程精力花在哪里。

03

从一个预测请求到训练好的模型

第一个公开系统 AlphaLab 1.0 发布时附带了技术报告和公开代码。Rappazzo 记得是在 4 月初发布的。这一版确立了研究流程；之后遇到的种种失败，促成了 AlphaLab 2.0 里更完善的评测和环境。

以汇率数据集为例。用户提供文件路径，或者提供 API 访问权限和 API 规范，然后让系统预测一天后的汇率。AlphaLab 把这个请求拆成三个阶段：

1. 研究：理解数据，了解相关的建模方法。 2. 搭建评测：构建评测或回测，作为评判实验的标准。 3. 大规模实验：实现并评测各种候选方案。

最终产出是一套针对该预测任务训练好的机器学习模型，而不只是一份书面的研究建议。

04

用于研究和集群执行的工具

AlphaLab 用的是自研框架，没有用现成的智能体框架。Rappazzo 说实现代码是 Claude 写的，他看重的是能随意改动任何部分的自由。模型和动作之间靠基于函数的工具调用来划界，这样框架就能兼容 OpenAI、Anthropic 和各家开源模型。

实际能力主要来自三个工具：

- Shell 访问：智能体编写 Bash 命令、创建 Python 环境、修改并运行代码。 - 网页搜索：智能体查阅 arXiv 论文、技术博客等公开资料，找出相关方法。 - Slurm 提交：智能体说明训练任务需要什么硬件，再把任务提交到 GPU 集群。

有了 Slurm 这层边界，智能体可以直接申请资源，不用自己管底层的硬件编排。比如，执行智能体要申请四张 H100，提交的 Bash 命令可以写成这样：

``bash sbatch --gpus=h100:4 --wrap='python train.py' ``

执行智能体仍然要自己准备训练代码和任务配置。资源分配交给调度器；CPU 需求也可以写进这份配置。

05

能扛过交接的研究上下文

研究阶段相当于加强版的 CLAUDE.md 或 /init：目的是收集足够的上下文，让智能体能提出有用的假设并加以验证。AlphaLab 跑在服务器上，用一个轻量 UI 展示进度。第一个像样的产物是一份待办清单，清单做完，系统就该准备好开始实验了。

这份清单还让框架能发现没做完的工作。如果智能体想提前退出，清单上还没完成的事项就是再次提示它的理由。任务包括配置 Python 环境、加载数据、做统计检验。每一项都会产出 Markdown 笔记，后面的智能体可以按需查询相关发现，不必把整段研究历史都塞进上下文。网页搜索大多发生在这个阶段，把公开研究补充进对本地数据集的理解。

Rappazzo 估计，研究阶段大约要三到四个小时，但浮动很大。它留下的长期产出是积累起来的上下文，搭建评测的智能体和执行实验的智能体都能反复使用。

06

构建一个评估，再试着攻破它

评测本身有错，再怎么优化，整个研究都会白费。 LLM 不需要有恶意，也可能引入错误，让模型看起来比实际更好。所以 AlphaLab 1.0 把评测的搭建和审查交给不同的智能体；下一版里改动最大的，也正是这个阶段。

最初的审查循环把职责分给三个角色：

| 角色 | 职责 | |---|---| | 构建者 | 编写评测代码，修复反馈的问题 | | 概念审查者 | 检查评测逻辑，排查未来信息泄漏 | | 测试者 | 编写单元测试和集成测试 |

两位审查者把发现的问题写下来，交给构建者。修好之后重新进入审查循环，直到所有智能体都认可这个评测为止。这样一来，“实验测的是不是对的东西”和“代码是否按预期运行”就成了两个分开检查的问题。

07

看板上的一场研究战役

大规模实验按 Jira 式的看板来组织。策略智能体查询前几个阶段收集的上下文，提出实验方案，把卡片放进 to implement 一栏。执行智能体领取卡片，把每个方案一路做到底。

执行智能体要做的不只是写代码：

1. 实现提出的策略。 2. 编写 Slurm 配置，包括硬件需求。 3. 提交训练任务，等待完成。 4. 检查训练曲线有没有欠拟合或过拟合，查看评测结果。 5. 写一份复盘，交回给策略智能体。

复盘让循环闭合。一个实验做完，策略智能体掌握的信息就变了，接下来提出的方案也应该随之改变。Rappazzo 举了个例子：三个 transformer 变体表现令人失望，XGBoost 的效果却很好，那么下一步更有价值的做法，可能是多试试树模型。这是在决定后续实验往哪儿投，而不只是给跑完的模型排个名次。

看板也是人工引导的入口。研究员可以取消卡片、加入自己的实验，或者和策略智能体对话，提供领域直觉，引导它尝试不同方法。旁边还有一个不断变长的排行榜，显示各个模型在评测和留出的私有验证集上的表现。研究员可以从一个想法的提出一路追溯到它的实现，把代码拿出来继续开发。

后面的 UI 演示直观展示了执行智能体的生命周期：实验依次经过构建、部署和分析。演示做了加速，动画展示的是工作在系统中怎样流转，不代表训练任务真的跑得那么快。

08

公开任务和内部模型上的结果

最初的论文探索了 CUDA kernel、一个学术界的交通时间序列数据集，以及 Karpathy 风格的 LLM 训练速通。Rappazzo 表示，AlphaLab 找到的 LLM 训练配置比单智能体循环找到的更好，不过他也承认，这套系统很难做基准评测。这里比较的是研究流程找出训练配置的能力，而不是运行这套流程的模型有多聪明。

NVIDIA 在 Kaggle 上办过一场比赛，任务是微调 Nemotron 来提升推理能力。Rappazzo 说，团队入场晚，只迭代了大约十轮，成绩就进入了前 12%。他预计更多迭代能让 AlphaLab 探索得更远，但在这场比赛里还能再提升多少，目前只是期望，并没有实测结果。

在内部，他提到对几个本来就不错的模型做出了一些有用的改进。这些改进正在走风险审查流程，准备上线；他没有给出内部收益的具体数字，也没有说审查已经完成。这正是最初设计里约束更多的那种起点：给 AlphaLab 一个可用的方案，让它去找改进空间。

09

失败留下了哪些未解答的问题

实验成功了，更难问题上的失败却依然没有解决。这些失败引出了一个衡量问题：团队怎么区分可靠的研究能力和一堆碰巧令人鼓舞的结果？它们也暴露出框架本身的不确定性。先做研究、再交给策略智能体和执行智能体，这个流程听起来很合理，但听起来合理，不等于它就是最好的安排。

框架设计本身也可以是一个可验证的优化问题。如果能衡量不同编排方式的效果，LLM 就能帮忙改进它们。另一方面，最初“数据 + 目标”的接口，把企业的大量知识和研究员的专业经验挡在了系统外面。Rappazzo 认为，能力衡量、框架设计和专家知识这三个问题，答案都在精心构建的评测和环境里。他说，最初的做法太急于把智能体当成人类研究员来用，却没有先找到一套清晰的方法来衡量它的工作。

10

AlphaLab 2.0 的更严格契约

AlphaLab 2.0 把评测边界划得清楚得多。整套设置很像 Kaggle：数据和任务描述输入系统，框架提交容器化模型，环境返回公开排行榜上的分数。用户还能另外看到模型在私有留出验证集上的表现。这样，每次提交在任务上的表现都能衡量，框架拿到的反馈和运营者看到的私有结果也分开了。

任务一旦统一成这种严格格式，就既能用来评测，也能用来学习。Rappazzo 说，团队已经搭了大约十到二十个精心设计的环境，用来提供强化学习信号。按这个思路，评测如果不只是用来报告结果，而是让系统拿去训练和改进自己，它就成了环境。

11

用 AlphaLab 来改进 AlphaLab

有了稳定的衡量方式，手动调整框架得到的信息就更有参考价值。要不要设两个策略智能体？让它们辩论会不会更好？这些想法都可以变成实验，而不是只凭直觉就定下来、从此固化在架构里。Rappazzo 把下一步称为“用 AlphaLab 改进 AlphaLab”：让 LLM 查看执行 trace 和评测结果，再直接修改框架本身。优化对象从预测模型，变成了负责做研究的那套机制。

训练权重是另一条路。团队正在从开源模型中收集优质 trace，并用 GRPO 和 on-policy 蒸馏方法改进模型行为。Rappazzo 预计，最好的系统可能会把开源模型和闭源模型结合起来。所以编排和模型训练是相互关联的优化选择：目标是提升整个研究系统的表现，而不是事先认定某种固定的智能体编排或某家模型厂商。

12

把专业知识编码进环境

搭一个有用的环境，光有专有数据和一个数值指标还不够。团队还制定了定性评分标准，用来审视 rollout trace：什么才算好的研究？研究员该怎样一步步推理一个问题？智能体在多大程度上遵循了团队的研究流程？给这些 trace 打分，就把专家对方法的判断变成了学习信号，和可量化的任务结果一起发挥作用。

真正值得长期投入的，是那个能定义并识别好研究的环境。 只要评测设置足够严格，中间的编排层就可以随时更换。AlphaLab 1.0 给出了一个初始实现，更长远的目标是让系统能自己改进这个实现。Rappazzo 预测，通用的自动化研究会变成大路货，并以 GLM 5.2 为例说明他为什么这么判断。手动调优仍是团队眼下工作的一部分，完全自我改进的研究流程才是终点。

这也解释了团队为什么打算继续公开发布这套系统。AlphaLab 1.0 的代码和研究已经公开，Rappazzo 还准备继续发布，因为在他看来，企业独有的价值在环境里：数据、评测标准和研究评分标准，正是这些东西让“改进”对组织有了实际意义。

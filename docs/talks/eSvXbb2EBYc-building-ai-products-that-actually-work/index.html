打造真正可用的 AI 产品

可靠的 AI 产品来自观察真实的用户意图、发现具体的失败，并把反复出现的任务变成团队可以独立改进的工作流。

01

演示跑通之后你该改进什么？

再多一个评测分数也说不清该修什么时，AI 产品该怎么迭代？演讲前，Ben Hylak 问听众想听什么，大家的回答很一致：少讲点评测。这个要求背后是个很实际的问题：产品已经初露潜力，接下来怎么把它做得更好。把模型能力变成有用的产品，靠的就是迭代。

Hylak 是 Raindrop 的 CTO，他从这个位置看待这个问题。Raindrop 帮团队发现并修复 AI 产品里的问题。他做过机器人，在 SpaceX 做过航电，又在 Apple 干了将近四年工程和设计。和他同台的是 Oleve 联合创始人 Sid Bendre。据 Hylak 介绍，Oleve 只有四个人，旗下一系列爆款应用的年度经常性收入超过 600 万美元。两人的视角一边是线上监控，一边是小型消费产品团队的现实约束。

02

一个正确的答案仍可能没完成任务

只要任务定义清楚，专注的 AI 产品能做到的事多得惊人。小模型在窄场景里可以变得极其能干，模型厂商也越来越多地亲自下场做这类产品。Hylak 举了 ChatGPT deep research 的例子：OpenAI 把数据收集和训练都集中在网页调研上，做出的体验在他看来是 OpenAI 最好的发布之一。

但有能力，不代表产品理解了任务。演讲时，Hylak 用 Codex 写后端测试，结果它给 hello 正确生成了一个哈希。算得没错，测什么却没对上他的意图。这个区别很关键：技术上挑不出错的输出，可能根本没碰到用户真正的问题。

其他例子暴露的是另几类上下文缺失。Hylak 讲到，Virgin Money 的聊天机器人因为客户用了 virgin 这个词，威胁要停掉对方的服务。他问 Google Cloud 自己的额度在哪，助手反问他说的是 Azure 额度还是 Roblox 额度。另一位用户告诉他，自己也碰到过一模一样的情况。产品本身的语境本该帮助手缩小理解范围，助手却表现得像对这些语境一无所知。

Grok 又贡献了两个失败案例。Hylak 提到一次公开对话：有人问企业软件的问题，回答却拐到了南非种族灭绝的说法上。这种行为能被看见，是因为对话是公开的。另一次是他准备演讲时自己碰到的：Grok 一开始说没法搜他的推文；他质疑之后，Grok 才承认其实能搜，还问他要用户名。有用的下一步明明就摆在那儿，助手却先否认了自己有这个能力。

Raindrop 观察的产品覆盖 Oleve 的应用、Clay 的销售外联工具、外星人陪伴类应用和编程助手。Hylak 还介绍了一条内部 AI 流水线，它会分析并归类 Raindrop 收到的每个事件。其中的 Deep Search 功能会探索线上数据，只需几个示例就能构建分类器。他关于如何发现故障的建议，就来自这些客户交互和内部系统，而不是预设所有重要故障都已经知道。

03

更好的模型仍然需要上下文

做 AI 产品会变容易吗？有些部分已经变容易了。Hylak 做了个对比：以前得精心写提示词才能让 GPT-4 输出 JSON，现在只要在 API 参数里指定输出 schema。Structured Outputs 就体现了这个变化。但它只保证结构：支持哪些 schema、拒答、生成不完整，这些情况照样要处理；JSON 合法，里面的值也可能是错的。格式上的麻烦没了，用户意图的问题还在。

就算是聪明人之间，沟通也照样难。Hylak 反驳了一个他认为出自 Paul Graham 的观点：AGI 会终结提示词工程，因为中等聪明的人不用详细指令也能猜到别人想要什么。可现实中，伴侣会互相误解，新员工交上来的活也常常和经理的本意不一样。聪明不会自动补上缺失的上下文，而一条指令要没有歧义，靠的恰恰是这些上下文。

能力越强，团队要搞懂的行为空间也越大。通过 MCP 接入集成，会带来更多工具、数据格式和行动方式，也带来产品团队没预料到的边界情况。产品需求文档已经没法穷举所有行为。 实际可行的循环变成：先把产品发出去，看它实际怎么表现，再据此修改。

04

评测覆盖的是你已知的失败

在这个循环里，评测依然重要，关键是怎么解读。Hylak 搬出古德哈特定律，质疑“评测分数能说明整个产品有多好”的想法。收集来的评测集，装的是有人早就知道要放进去的用例；反复优化能把它刷满，用户会遇到的问题却远没穷尽。他说自己见过一些模型发布，评测成绩更差，实际用起来却更好，不过没有点名具体的基准或模型。他想说的是：测到的用例和产品的真实使用之间存在落差。

让语言模型给主观的东西打分时，比如判断一个生成的笑话有多好笑，同样的落差也会出现。输入文本、吐出数字的评判模型用着方便，但方便不代表它的分数抓住了人们真正在意的体验。Hylak 建议用精心筛选的数据集和可自动判分的评测，也就是能用确定性方法判断输出是否通过的检查。他观察到，领先的公司大多不用通用的模型评判，但也有例外；这条建议讲的是该优先用什么。

把同样的评判模型和打分规则搬到线上流量上，这些局限也不会消失。够强的评判模型可能很贵，最后只能抽样一小部分流量。要把它搭准很难；围绕已知故障设计的系统，照样可能漏掉新出现的模式。Hylak 引用了 OpenAI 一份关于模型行为问题的复盘，强调真实使用会暴露评测发现不了的问题。所以线上观察是评测的补充，而不是放弃评测的理由。

05

把各种信号与用户意图结合起来

传统的错误监控会告诉你出了什么问题、发生了几次、影响了多少用户。AI 交互出了问题，却可能一个异常都不抛。为了拼出类似的全貌，Hylak 提出了信号：以产品里实际发生的事为依据的指标。把显式或隐式信号和用户意图结合起来，AI 问题就浮现出来了。具体的运转方式是：定义信号，探索信号，再不断细化。

显式信号是应用可以主动上报的事件。点赞、点踩只是起点。Hylak 说，ChatGPT 还会记录用户复制了回答的哪一部分；让用户在两个回答里挑一个更喜欢的，也是一种反馈来源。不同的交互能提供不同的证据：

| 信号 | 可观察的事件 | |---|---| | 直接反馈 | 点赞或点踩；更偏好的回答 | | 重试行为 | 重新生成回答 | | 技术故障 | 报错或代码语法错误 | | 复用 | 内容被复制或分享 |

单看哪一个，都不能完整衡量回答质量，但这些事件提供了可以具体检查的行为。

Raindrop 把这个思路用在了自家的搜索体验上。用户把结果标成正确或错误，Hylak 说这些标签可以作为强化学习的反馈，提升搜索质量。隐式信号则来自检测交互里发生的事件：拒答、任务失败、用户受挫。检测某个具体问题，比评判回答的整体质量要聚焦得多。

有了意图，这些检测结果才有了能下手的形状。一堆用户受挫的对话很难处理；但如果是一群用户想搜推文却受挫，就指向了一个需要排查的具体能力。前面的 Grok 例子正是这样，从一则孤立的轶事变成了一个问题类别。

06

让问题发现成为一项持续的实践

要做探索，光有一条条对话的流水还不够。就像 Sentry 里的标签，团队需要按属性和元数据来浏览：模型、关键词，尤其是意图。意图会改变信号的含义，也就改变了要排查的问题。比如一次拒答，不知道用户想干什么，就说明不了什么。

Hylak 建议让应用数据持续流进团队的日常工作。Raindrop 用 Slack 通知，在线上数据里搜索也是一条路。关键在于持续接触：看模式，和用户聊，把意料之外的问题定义清楚，然后开始追踪。这些定义应该随着团队认识加深而演进，不要停留在上线前预想的那几个类别上。

演讲的这部分到发现和细化为止。Hylak 跳过了原本准备的修复和监督微调，把话筒交给 Bendre，由他介绍一个框架：围绕用户真正想要的行为来组织产品改进。

07

引导那些让产品吸引人的变化性

Oleve 的目标是做让人有收获、有成效的消费产品。Bendre 说，这支纽约的小团队在盈利的前提下做到了约 600 万美元 ARR，社交平台累计观看约 5 亿次。他介绍说，团队的改进框架由 Raindrop 提供支撑。这些是创始人自述的业务成绩，并不能证明这些成绩就是框架带来的。

一款爆款 AI 产品，既要有抓眼球的惊艳感，也要有稳定可靠的体验。非确定性行为本身就是吸引力的一部分，把变化全部消除，等于砍掉了产品的一部分魅力。Trellis 是 Oleve 的做法：它围绕团队的病毒传播引擎设计，在引导这种变化的同时，让改进变得有章可循。

Trellis 建立在三个操作上：

- 离散化： 把开放的输出空间切成一个个具体的分桶，让团队能着手处理。 - 排优先级： 按潜在的业务影响给分桶排序。 - 递归细化： 在每个分桶里重复这个过程，证据充分的地方再加更多结构。

产品就这样一层层变得更好理解，团队也不用一开始就把所有可能的交互都定好。

08

把观察到的意图变成专门的工作流

Bendre 把这些原则落成了六个步骤：

1. 上线一个 MVP 智能体。 从产品先验和预期出发，但要借初版体验收集真实用户数据。 2. 把使用情况归类为意图。 弄清用户实际拿产品做什么、为什么一再回来；开放式的对话界面尤其需要这一步。 3. 搭建专门的工作流。 把反复出现的意图变成预定义的步骤。每个工作流要足够宽，能覆盖多种情况；也要足够窄，保证可靠。 4. 对照公司 KPI 排优先级。 用一套和业务目标挂钩的打分机制。 5. 在每个工作流内部分析。 检查失败模式，拆出更具体的子意图。 6. 递归。 在这些更小的空间里重复同样的过程。

关键的转变是从不设限的智能体体验，走向半确定性工作流。步骤顺序提供结构，生成的输出仍保留有益的变化空间。

09

按能实现的影响对改进排序

最直观的排序依据是使用量：先改进用得最多的工作流。但光看使用量，看不出哪里的满意度最有提升空间。Bendre 建议把负面情绪算进来，再用可行性和战略相关性进一步细化分数。

| 排序方式 | 因子 | |---|---| | 只看使用量 | 使用量 | | 按不满意加权 | 使用量 × 负面情绪 | | 按可行性和战略加权 | 使用量 × 负面情绪 × 可实现的提升 × 战略相关性 |

加上这些因子，才能区分“常用的工作流”和“团队真能大幅改进的工作流”。

预估可实现的提升，指团队实际能做出的改进。某个工作流再让人恼火，如果修好它要训练一个公司根本负担不起的基础模型，在它身上花力气也不划算。Bendre 说，这种情况下可实现的提升可能接近于零。这个分数是排优先级的经验法则，估值由团队自己给出，并不是对提升幅度的实测预测。

这个乘法用 TypeScript 写起来很简单。下面的实现把四个输入都显式列出来，返回一个重新排好序的新数组，每个工作流的优先级建立在哪些假设上，都能随时查看：

```typescript type WorkflowEstimate = { id: string; volume: number; negativeSentiment: number; achievableDelta: number; strategicRelevance: number; };

function rankWorkflows(workflows: readonly WorkflowEstimate[]) { return workflows .map((workflow) => ({ ...workflow, priority: workflow.volume * workflow.negativeSentiment * workflow.achievableDelta * workflow.strategicRelevance, })) .sort((a, b) => b.priority - a.priority); } ```

比较不同工作流时，定义和量纲要保持一致。函数只负责算排名，估算输入所需的判断还得靠人。

10

让每次修改都对一个工作流负责

专门工作流的好处在于隔离。Bendre 形容它们可自归因、确定、自我约束：改进一个工作流时，改动和影响都应该算在这个工作流头上，不会波及无关的体验。按前面半确定性的说法，真正起作用的边界，是包在生成输出外面的那层结构化流程。它给了团队一个更小的单元，方便修改、检查和测试。

随着新的子意图和失败模式冒出来，细化可以在每个工作流里继续往深处走。最终想要的体验是：惊艳是设计出来的，可复现、可测试、可归因，而不是碰运气。Bendre 最后推荐观众去看一篇介绍 Trellis 的博客文章；要让这种效果持续下去，靠的就是工作流隔离和递归细化。

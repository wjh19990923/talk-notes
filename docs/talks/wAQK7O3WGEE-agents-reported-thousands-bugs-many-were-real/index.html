智能体报告了数千个 bug，其中有多少是真的？

SM100 把“找到一个已知缺陷”与“写出看似可信的 bug 报告”区分开来，暴露了编程能力与可靠的软件维护之间的差距。

熟悉 pull request、基本的智能体工具循环和应用状态会有帮助；不需要安全研究背景。

01

智能体能维护它们帮忙写出的软件吗？

软件智能体能不能在现有代码库里可靠地找出 bug 并修好？生成新功能只是工作的一部分。软件上线之后，得有人理解它的行为、找出故障，再在不弄坏别处的前提下把它修好。Ian Butler 和 Nick Gregory 在 Bismuth 做基准测试，关心的正是这个维护问题。

Butler 自我介绍是 Bismuth 的 CEO，做过数据工程、机器学习和搜索，也参与过 Zillow 的 A/B 测试平台。2019 年，他和 Gregory 合作过一款技术文档搜索产品：为 IDE 场景索引了数亿份文档，还用 AI 给内部知识库做摘要。Gregory 是 Bismuth 的 CTO，曾在 Google 开发终端安全工具，也研究过软件漏洞利用检测。这些技术可以直接用在“让智能体审查代码”上。基准中 DeepSeek R1 和 Llama 4 Maverick 的运行额度和算力由 Baseten 提供。

02

编程评估留下的空白

现有评测包括 HumanEval、SWE-bench、aider 的 Polyglot 基准 和 LiveCodeBench。它们覆盖的编程任务各不相同，其中 SWE-bench 评的是解决 GitHub 上已有的 issue。所以关键的区分不只是新代码和旧代码。修复一个已经描述清楚的问题，和发现一个未知缺陷，是两种不同的任务。

软件开发生命周期的其他阶段还有不少职责，编程分数衡量不到：

- 规划： 决定做什么之前，先弄清业务需求、现有系统和设计，以及可能的方案。 - 开发与测试： 实现功能并加以检验。Gregory 认为现有评测对这一块覆盖得相对充分。 - 代码审查： 检查一项改动有没有问题。Gregory 指出，LLM 审查工具用的人越来越多，这一块却几乎没有基准。 - 部署： 写配置、搭监控、对接其他系统。 - 维护： 在成熟的代码库里修 bug、升级依赖、做迁移。

Bismuth 专注于代码审查和维护。这些工作仍然要写代码，但起点掌握的信息不同，要做的判断也不同。

03

找到 bug 意味着理解系统

开发功能和调试 bug 都要理解架构、组件之间的关联和数据流。调试有时比写原始功能要求理解得更深：排查的人不仅要搞清一个函数做什么，还要知道哪些输入会传到它这里、它的输出又怎样影响系统其他部分。

Butler 说，智能体往往只检查了其中一部分行为。一次运行只能找出部分 bug；思考型模型有些帮助，但探索的可能性仍然有限。结果是两头出错：人一眼就能看出的缺陷，智能体会漏掉；人会直接否掉的所谓 bug，智能体却当了真。修复已经找到的 bug 通常更容易，但它们找到的本来就是比较简单的 bug。所以这种成功，远不像乍看那样能说明它会修疑难缺陷。

软件安全领域现有的 bug 检测基准，也没能完全填补这个空白。Gregory 介绍，那些为静态分析和程序修复设计的评测，偏重常见模式：空指针解引用、缓冲区溢出、SQL 注入。有些只覆盖一种语言，比如 Java。它们以安全为重点，也就漏掉了普通的功能性故障。一次复制粘贴失误就可能让应用在用户手里失灵，却不会造成认证绕过。SM100 的设计初衷就是扩大评测范围。

04

什么算一个 bug？

Butler 介绍，SM100 收录了来自 84 个以上公开仓库的 100 个 bug，每个都经过分诊、验证和分类，而且都已在原项目中修复。难度从几乎不需要领域知识的明显缺陷，一直延伸到需要高级或 Staff 级工程师那种深厚项目经验才能看出的问题。选 Python、TypeScript 和 JavaScript，是因为它们流行，模型也被认为更擅长；Go 则作为系统语言用来对照。

收录标准是客观缺陷：明确的安全或逻辑问题，会造成具体的故障后果，比如数据丢失或崩溃。后果能不能真的发生，要看上下文。一个函数可能缺少边界检查，但如果所有调用方都保证输入不越界，光报告“缺少检查”并不能证明系统真会出故障。功能需求、优化机会、代码风格、格式和设计偏好一概不收，免得评测变成品味之争。

每个 bug 都从几个独立维度做了标注：

- 严重程度与上下文： 缺陷有多严重，相关代码定义在哪里、在哪里调用。 - 所需知识： 人要识别它，需要对项目了解到什么程度。 - 发现难度： 即便有了这些了解，找到它还有多难。 - 后果： 故障会导致数据丢失、崩溃、安全问题，还是其他具体结果。

把知识和难度分开很重要。专家可能很熟悉某个子系统，却仍要花大量功夫排查，才能定位其中的缺陷。

这些分类想衡量的是可重复的能力，而不是偶然的成功。Butler 提到一则报道：o3 发现了一个零日漏洞，实验在同一上下文上跑了大约 100 次。证明模型能发现漏洞，和确定它在日常使用中有多大把握发现漏洞，是两回事；单凭运行次数，也说明不了非得跑满这么多次才能发现。

05

四种输出，搭配有边界的搜索

SM100 把四个问题拆开来看，只看一个编程分数会把它们混为一谈：

| 评测项 | 问题 | |---|---| | 目标缺陷发现 | 不告诉智能体目标缺陷是什么，它能不能找到？ | | 报告有效性 | 它报出的 bug 里，有多少经得住人工核查？ | | 引入时审查 | 在引入缺陷的那个 PR 或 commit 里，它能不能发现问题？ | | 修复 | 它能不能修好找到的 bug，又不弄坏代码库其他部分？ |

发现和报告有效性必须分开。智能体可能找到了目标，同时又丢给开发者一大堆错误报告。审查改变了起点：智能体拿到的是引入缺陷的那次改动，搜索范围小了，上下文也直接摆在眼前。修复则只在找到 bug 之后才评。

在整个大型仓库里搜一个目标，慢得无法接受；直接指出有缺陷的代码行，又让发现变得太容易。基准的做法是按子系统缩小搜索范围：

1. 把仓库划分成若干组相关文件，比如前端的某一块，或某个特定的 API 子系统。 2. 找出已知修复 PR 或 commit 改动过的文件，确定它们所在的子系统。 3. 把这些子系统的文件交给智能体，但不描述目标 bug。 4. 让智能体把选中的子系统作为整体来检查，而不是只看改动的那几行。

这样既隐去了缺陷描述，又让探索保持在可控范围内。不过这仍是限定范围的发现任务：智能体拿到哪个子系统，取决于已知的修复，只是没有明说缺陷本身。

06

找到目标不等于产出有用的报告

搭一个基础智能体很容易：把模型放进循环，给它 shell 权限、代码编辑、思考工具、bug 上报和结束动作。它能浏览文件，也能报出看似合理的问题。Butler 说，这个基础循环找到了五六个 bug，误报率却高达 97%。所以好用的检测器不能只靠工具权限，模型选择、提示词、信息输入方式、系统设计和代码导航策略都有影响。

在公布的 SM100 发现评测中，Bismuth 在 100 个目标 bug 里找到 10 个，排第二的系统找到 7 个。就算是最好的结果，大部分目标也没被找到，这项评测还有很大的提升空间。

演讲把有效报告的占比叫作真阳性率。这里实际指的是报告精确率，即有效 bug 报告数除以全部 bug 报告数，而不是针对代码库所有缺陷的召回率。Butler 给出的历史结果如下：

| 智能体 | 有效报告 / 全部报告 | |---|---:| | Claude Code | 16% | | Bismuth | 25% | | Codex | 45% |

这几个系统报出的无关结果也更少，Butler 认为原因是它们的范围收得更紧。据称，Devin、Cursor Agent 和 Cosine 各报出约 900–1,200 条结果，Cursor 更是达到约 1,300 条，其中只有 3–10% 有效。清单列得越长，不等于找到的有用 bug 越多。

PR 审查把引入缺陷的那次改动交给智能体，起点更有利。Butler 给出 Codex 更正后的数字是 27%，随后提到 Devin 和 Bismuth，但留存的录音文本隐去了它们的具体数字。分母也还不确定：公开的评测方案 规定了 80 道符合条件的 PR 审查题，历史结果表却无从查到。所以 Codex 的数字既不该换算成具体个数，也不该重新算百分比。这项比较也不统计误报，只看审查有没有找到已知目标。

Bismuth 不绑定特定模型，不过 Butler 说他们通常用 Anthropic 的模型，因为通过 Vertex 给客户提供服务更方便。他说，Bismuth 底层用的同样是 Anthropic 的模型，却在多个类别上胜过 Claude Code。可见即便模型家族相同，外围的智能体系统也会实实在在地左右结果。

07

当模型在一个基本循环中运行时，什么会改变？

基础循环对比把系统剥回前面说的简单工具循环。DeepSeek R1 和 Llama 4 Maverick 报出了数百条结果，但报告精确率极低。Sonnet 4 和 o3 好一些，只是结果仍然噪声很大：

| 基础循环中的模型 | 找到的目标 bug | 有效报告 / 全部报告 | |---|---:|---:| | DeepSeek R1 | 1 | 1% | | Llama 4 Maverick | 未说明 | 2% | | Sonnet 4 | 6 | 3% | | o3 | 2 | 6% |

最后一列采用演讲者更正后的说法：这些是真阳性占比，不是误报率。换一个模型，目标发现的成绩会变，报告清单的可用程度也会变。

Butler 强调，除去刚发布的 Bismuth，表现最好的主流智能体在目标发现上也只有 7%。他把这看作维护复杂软件的警示，并称维护是工程工作的“后 90%”。这是他对工作量的形容，不是实测的工程时间分配。这里的量化结果说明的是发现缺陷很难，并没有单独给出修复复杂 bug 的成功率排名。

08

七十份报告，以及一个被漏掉的状态转换

一旦要由人来检查输出，报告质量就成了实际瓶颈。Butler 说，六个智能体里有三个的有效报告占比不超过 10%，还有一个针对单个问题就报了 70 条。就算正确结果藏在清单某处，开发者也得从几十条干扰项里把它挑出来。

具体例子是一个普通的表单状态缺陷。图中这个问题只有 Bismuth 和 Codex 找到了。提交之后，isDirty 始终没有设回 false；Butler 描述的现象是表单没有清空，仍显示里面填着内容。这算不上惊天动地的安全故障，却直接影响用户判断提交到底有没有成功。

下面用一个精简的 TypeScript 示例，单独展示缺失的那一步状态转换。这里 isDirty 表示存在未保存的修改；保存成功应清掉这个标记，保存失败则保持不变：

```typescript type FormState = { values: { message: string }; isDirty: boolean; };

async function submitForm( state: FormState, save: (values: FormState["values"]) => Promise<void>, ): Promise<void> { await save({ ...state.values }); state.isDirty = false; } ```

假设表单里是 message: "Hello"，并且 isDirty: true，提交成功后这个标记会变成 false。去掉最后那行赋值，它就一直停在 true。示例保留了字段值，只为单独展示脏状态的转换；清空输入值是另一项 UI 操作。这类小小的状态不一致，智能体得顺着周边行为一路追下去才能识别出来。

提交成功后的脏标记 缺了最后那行赋值，提交后 isDirty 仍为 true。 构造示例：message 字段、Hello 值、TypeScript 函数和保存成功这一操作都是讲解用的细节。保留字段值，是为了单独展示有源码依据的脏状态转换；这是修复后的预期结果，并非实际运行的测试。 等待提交的表单——未变化：{"values":{"message":"Hello"},"isDirty":true} 操作：应用图示的 submitForm 修复：等待保存成功，再赋值 isDirty = false。 - values.message - 之前：提交成功前："Hello" - 之后：修复后的预期状态："Hello" - isDirty - 之前：提交成功前：true - 之后：修复后的预期状态：false 缺了最后那行赋值，提交后 isDirty 仍为 true。

09

更广的搜索，更深的推理

Butler 在所有测试过的智能体身上都看到了同一个局限：推理面窄，思考型模型也不例外；即便沿着选定的路径，往往也挖得不够深。他提出的改进分两步：先考虑更多可能的故障路径，再把选中的路径查得更透。

多次运行从另一个角度暴露了这个问题。每次报出的 bug 总数大致稳定，具体是哪些 bug 却在变。这说明智能体并没有在每次运行时完整梳理一个文件的行为。Butler 推测，上下文会把模型引向某一种解读或排查方向，其他方向就被冷落了。团队提到了几种可能的解法，但这次演讲没有给出具体算法。

Butler 把 SM100 上的糟糕结果，和他引用的 60–80% 的 SWE-bench 分数做对比，但没说明这个区间对应哪些系统、哪个基准版本、什么时候评的。差别在于任务本身：擅长解决给定的 issue，不代表能可靠地发现已部署软件里的未知故障。维护需要有针对性地搜索、读懂程序、跨文件推理，还要能在真实系统里认出 bug 模式。

Codex 和 Bismuth 的结果更聚焦，带来了一些积极信号，比如偶尔能发现复杂问题，还有前面那个表单状态缺陷。但这些能力还处在早期。维护型智能体必须把可疑的局部模式和真正可达的故障联系起来，再把报告写得足够精确，让开发者能据此动手。

10

让维护进展可衡量

Gregory 在结尾提醒，广泛使用的智能体也可能引入 bug；同时他对新一代系统审慎乐观，认为它们能推理代码、有效利用上下文。演讲没有单独测量引入 bug 的比率，但发现环节的结果已经把维护难题摆在眼前：光会生成代码，并不能保证可靠的持续审查。

有了 SM100，团队就能长期追踪不同技术有没有让这种审查变得更好。发现得更准、报告得更准、修得更稳，受益的是整个生命周期里的开发者，而不只是基准排名。Gregory 请观众去看基准的具体数字和细节，并说公司网站是 bismuth.sh。下一步的突破，得让报告对那位要决定修什么的工程师真正有用。

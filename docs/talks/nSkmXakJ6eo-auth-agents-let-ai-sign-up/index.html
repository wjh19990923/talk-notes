智能体的认证：用 auth.md 让 AI 注册你的产品

Michael Grinich 介绍了一份基于 OAuth 标准的注册规范，然后跟随一个智能体，从一个无法访问的本地应用一直走到 Cloudflare 上的部署。关键的变化在于：让智能体在人需要完成厂商注册流程之前就能获得访问权限。

01

更长的运行把瓶颈推到写代码之外

A coding agent can work for hours and still stop at a signup form. Michael Grinich, founder of WorkOS, opens by tracing how that mismatch emerged: interactive coding once alternated between a human prompt and a small amount of generated code; longer-running agents can now attempt whole features or products from a single prompt. Several runs can proceed in parallel, leaving the human to keep track of their context.

Autonomous vehicles supply the analogy. A dashboard and cruise control still assume a person is driving. A driverless ride takes a destination and handles the journey. Grinich remembers being astonished by his first Waymo ride, then scrolling X about three seconds later. Delegation quickly becomes ordinary; attention moves from operating the machinery to choosing where it should go.

That autonomy requires more than a capable model. The surrounding harness supplies several distinct needs:

- Runtime: a safe, secure and performant place to execute. - Tools: ways to take actions outside the model. - Context: information about the project, system and goals. - Feedback: ways to run the work, check it and continue when it is wrong. - Human review: code review, evaluations or other checks that the result serves the intended goals.

The model is the engine; the harness supplies the rest of the car. More engine power does not make a vehicle useful without a transmission, drivetrain and wheels. Likewise, improving models creates a reason to adapt the tools and execution environment around them. Registration becomes consequential when those tools need access to services the user has never joined.

02

一个挑选供应商的智能体仍然得先成为客户

Building an application creates purchasing decisions even before anyone purchases anything. An agent may decide it needs a database, deployment service, image resizing, video transcoding or email delivery. It can research those options while building. Grinich sees this as a new customer acquisition channel: agents increasingly choose which services become dependencies in a project. His proposed update to “Make something people want” is to make something agents want as well.

The obstacle appears at the first interaction with a new provider. An agent may understand the API and know how to use it, yet lack an account or credential. Connecting tools and supplying context do not complete that first registration step. A service can therefore be technically useful and practically inaccessible to an autonomous run.

Signup defenses grew around a different assumption: automated traffic was something to stop. DDoS protection and defenses against credential stuffing helped harden the login box against automation. Legitimate agents now encounter those same barriers. CAPTCHA-solving features in browser execution services expose the awkwardness: a useful agent tries to defeat the mechanism a provider uses to reject bots, while abusive automation remains a problem.

Even without a CAPTCHA, the workflow assumes a human can read a landing page, enter an email address and password, open a verification message, choose a paid plan, and copy an API key into another system. An agent may have no mailbox of its own. Each assumption creates a possible handoff, turning an otherwise autonomous build into a list of accounts the user must create.

03

auth.md 声明了智能体如何获得访问权限

Agent registration needs an explicit way to discover whether a service accepts agents, what it offers and how an agent should establish its identity and intent. Risk assessment still matters. Some harnesses may carry a user’s identity; others may require verification through another channel. Company use introduces organization identity, permissions, entitlements, credential issuance and auditability. These are separate decisions a provider must make rather than consequences of simply allowing automated form submission.

The proposed auth.md file gives the agent a description of the registration path. Its useful declarations answer different questions:

- Service and procedure: What does this service do, and how can an agent register? - Identity and authentication: Which identity proofs are accepted, and which flows—such as SSO, email or MFA—are supported? - Access and limits: Which scopes and entitlements are available, and what free-tier constraints apply before further verification or payment? - Later custody: How can a human or organization claim the account after the agent creates it?

MCP addresses a neighboring problem. In Grinich’s example, connecting PostHog to Claude means a human adds the MCP server, signs in with existing PostHog credentials and gives consent. That supplies a connection to an account the person already has. The proposed registration path must also support the earlier moment when no such account exists, without requiring a human to complete the initial signup.

The scope is deliberately narrow. auth.md builds on existing OAuth standards to describe registration; it does not claim to solve the whole problem of agent identity, permissions or long-running connections. A declaration can tell an agent which proof a provider accepts. The provider still has to verify that proof and decide what access to issue.

04

从 localhost 到部署，全程无需人工注册

The demonstration starts with a concrete failure: friends cannot access an app running on the developer’s machine. The agent identifies the cause—localhost only works locally—and proposes deploying the app to a public service. It offers to look for providers that let it handle signup. Grinich presents this as an illustrative conversation backed by a working demo, rather than an unguided production run.

Discovery changes the vendor choice. In the example, two candidate providers do not advertise agent registration, while Cloudflare has an auth.md declaration. Cloudflare wins because the agent can complete the work there: obtain access and deploy. The practical differentiator is whether the service lets the build continue past account creation.

The agent then creates an identity assertion and presents it to Cloudflare. The provider can verify it, including through an out-of-band process, and choose the initial access policy. Grinich uses a deployment lasting “maybe for 72 hours” as an illustration, not a fixed Cloudflare entitlement. The policy depends on the service’s risks: a small database allowance might be acceptable, while email delivery or actions in the physical world may justify tighter restrictions before any free use.

Successful registration returns a token. The human has not opened a signup page or created the account manually. The agent knows how to use Wrangler, prepares the deployment configuration, makes the necessary changes and deploys the app. The result to look for in the demonstration is the transition from an inaccessible local application to a live deployment after credentials become available.

``text Uploaded demo (5.27 sec) Deployed demo triggers (0.65 sec) https://demo.agentic-registration-f49bc.workers.dev ``

Human approvals remain in the illustrated conversation: look around, choose Cloudflare, make the changes. Grinich jokes that the prompting amounts to “Yes, yes, do it, please.” His proposed next step is to collapse those repeated approvals into one initial instruction. The demonstrated behavior supports registration without manual signup; completing the entire task in one shot is the further capability he says should follow.

05

发出一个身份声明，拿回一个 API 令牌

The architecture separates the harness, user identity and service provider. The harness contains the model, memory and context layers, and connects to a backing identity service. It discovers the target provider’s registration instructions, then sends an ID-JAG: a signed credential representing the user. Grinich also names Firecrawl as another service with which the registration approach works.

The important distinction is between the proof submitted during registration and the access credential returned afterward. The ID-JAG represents identity; the returned API token enables service requests. How do those exchanges fit around the existing application interface? The relationship below shows registration messages flowing between the harness and provider, followed by ordinary API or MCP use.

This keeps the change concentrated at the beginning of the relationship. Once the provider issues an access token, the agent can make normal API requests or call MCP. The provider’s API and the rest of its documentation can continue to serve the same purpose. Registration removes the interruption between deciding to use a service and having the credential needed to use it.

06

先让使用开始，再要求付款

“I hate the planning step,” Grinich says. The desired output of a prototype request is something running that the user can open and explore. A plan followed by a list of vendors to join leaves the operational work unfinished. Agent registration lets an available free allowance carry the prototype through to deployment before the user has to manage those vendor relationships.

For providers, that extends the signup funnel to agents acting on people’s behalf. Grinich compares the opportunity to product-led growth and freemium: many experiments may be short-lived or never reach production, while some become lasting customers. His expectation of substantial growth is a business hypothesis, not a measured result presented in this recording.

Payment belongs downstream in this proposal. Grinich mentions x402 and work by payment providers, but does not make a payment protocol part of the registration mechanism. Requiring a credit card before the agent can try a service would restore an early barrier. Instead, the provider can permit initial use under its own limits, then ask for payment according to its pricing model. That leaves room for stricter policies where even trial usage carries meaningful risk.

07

一个无头的入口点，以及开放的实现路径

The closing example broadens the idea beyond new developer services. Grinich cites Marc Benioff’s description of Salesforce, Agentforce and Slack becoming available through APIs, MCP and CLIs: “Our API is the UI.” He immediately corrects the suggestion that this means removing dashboards. The relevant change is giving agents ways to operate the product alongside the interfaces people use.

auth.md is presented as an open spec with a GitHub repository and a WorkOS-hosted implementation. Builders can also implement and run it in their existing systems. That choice matters for a registration mechanism intended to span vendors: adopting the approach should not require every provider to run its signup infrastructure through WorkOS.

Grinich closes with the iPhone’s introduction as his reference point for a new software platform: a change that enabled other companies to build products on top of it. Agents, in his view, offer a comparable opening. The practical invitation is to build prototypes, talk to users and report where registration gets stuck. The proposed contribution of auth.md is specific enough to try: let an agent become a legitimate service user, obtain constrained access and keep working.

要点总结

  • Registration is a distinct obstacle: knowing how to use an API does not give an agent an account or access token.
  • auth.md describes registration procedures, accepted identity proofs, authentication flows, access limits and later human or organization custody.
  • In the Cloudflare example, the agent presents a signed identity assertion, receives an API token and uses Wrangler to deploy; the conversation still includes human approvals.
  • Providers retain the decision about verification and initial access. Free usage is application-specific, and payment can follow usage rather than block registration.

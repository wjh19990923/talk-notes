高效生成式 AI 评测的七个习惯

一个令人信服的原型仍可能隐藏着失败。有效的评测能暴露工作流在哪里断掉、指导模型选择，并把每一次提示词修改都变成可据以行动的反馈。

熟悉提示词模板、语言模型调用和基础 Python 会有帮助；不需要评测框架经验。

01

是什么让一个有前景的原型无法规模化？

一个大家都喜欢的生成式 AI 原型，和一个能放心依赖的系统之间，最大的障碍是什么？Justin Muller 在 AWS 一个小型专家团队工作，团队帮各行各业、各种规模的客户扩展工作负载，他就从这个位置来回答这个问题。他自我介绍是首席应用 AI 架构师，背景横跨物理、数学、法律和商业，做了大约十五年自然语言处理，四年生成式 AI。团队的做法既来自成功的项目，也来自失败的项目。成本、幻觉、准确率、容量都重要，但他反复看到的缺口是评测：团队做出了一个吸引人的东西，却没想好出了问题该怎么诊断。

2024 年 7 月，一家做文档处理的客户找 Muller 去救一个快要被砍掉的项目。据他回忆，项目已经投入了六到八名工程师，干了大约六到十二个月。负责项目的技术高管说准确率只有 22%，想知道还有没有救。摸底之后，核心问题浮出水面：团队只有一个端到端的数字，没有诊断性的评测框架，看不出流程在哪一步出错。

框架把一个个失败暴露出来之后，Muller 说，修起来反而相对简单。真正难的是找到问题和原因。据他介绍，接下来六个月里，这家客户的准确率在 1 月达到 92%，超过了 90% 的上线门槛。演讲没有说明准确率怎么算，也没说测试集是什么。他说，这个项目上线后成了当时 AWS 在北美最大的文档处理工作负载。

02

为诊断而设计，而不只是为了一个分数

在传统机器学习里，F1、精确率、召回率这类分数是大家熟悉的起点。生成式 AI 的评测同样要衡量质量，但首要设计目标应该是发现问题。评测器找出一个失败，或许还借助生成的分析给出修改建议，团队就有了动手改的抓手。这个目标会改变框架的设计：不只问系统表现得多好，还要问什么证据能揭示它在哪里出错。

愿不愿意下这个功夫，也成了挑项目的信号。Muller 的团队人少，没法接下所有请求。有团队想做多智能体协作，他会提议先花两个小时搭一套金标准评测集。有的团队想跳过这一步，直接上手试工具；也有团队主动给出四个小时，因为他们在乎把项目做对。探索对学习有用，但 Muller 把它和规模化所需的投入分得很清楚。他讲那些格外成功的客户时，强调的都是同一种做法：肯在评测上投入，而不是把评测当成干扰。

自由文本不代表没法评测。假设一位教授布置了一篇三页的论文，题目是阳光的情感意义。这种题没有数学上唯一精确的答案，但教授照样能打分。有用的评估和没用的评估，差别在于反馈：只给一个 F 不加解释，学生几乎学不到什么；评语指出错误和可改进之处，下一稿就会更好。生成式 AI 的评测器应该像第二种教授。

03

一个正确的答案可能掩盖一个有缺陷的方法

Muller 用一块 2×4 木料上钻出的一英寸孔，说明只看输出的反馈有什么局限。让听众评价钻好的孔，大多数人都竖起大拇指。接着他揭晓钻孔的方法，大家的评价随之改变：一次钻出合格的孔，不代表这套做法靠得住。给生成的答案点个赞，也有同样的盲区。

一家气象客户的任务把这个问题讲得很具体。它的提示词要求根据传感器数据写一段本地天气摘要：下雨、气温 40 度、有风。如果回答说天气晴朗明媚，显然错了。打一个不及格的分，能指出结果对不上；让模型给出解释，则能暴露更具体的问题。在 Muller 的例子里，模型说它没提下雨，是因为快乐对心理健康很重要。这个自述的理由指向一个冲突：一边要如实报告观测数据，一边又想让读者心情愉快。这类解释应该当作诊断证据，而不是模型内部因果过程的可靠记录。

现在把输入换成晴天。同样偏爱欢快的回答，这次可能产出一个看似完美的结果，底层缺陷却原封未动。

| 传感器输入 | 生成的摘要 | 只看输出的评估 | 解释暴露了什么 | |---|---|---|---| | 下雨 | 晴天 | 错误 | 追求快乐压过了传感器证据 | | 晴天 | 晴天 | 正确 | 错误的优先级依然存在 |

第二种情况更危险，恰恰因为答案看起来是对的。看过解释，团队就有理由去测一测：天气没那么好的时候，提示词还会不会尊重证据。

04

在你需要测量的地方拆分提示词

大提示词会带来测量上的麻烦。Muller 把评测一次模型调用比作把万用表的表笔接在输入和输出两端：能看到整个操作的表现，却分辨不出里面各个任务的情况。如果一个提示词要同时解读传感器数据、套用阈值、挑选措辞、写摘要，答案一错，可能的原因就有好几个。提示词分解会产生中间输出，每一步都能单独评测。

这位气象客户的提示词里有一条风速规则：低于 5 算风不大，高于 5 算有风。原型阶段没出问题，但 Muller 说，随着天气业务规模扩大，Claude 大约有 2%–3% 的时候会错把 7 当成小于 5。具体是哪个 Claude 版本、测试规模多大、风速用什么单位，演讲都没有交代。这个例子说明：把确定性的比较嵌进语言任务里，原型结果看着合理，也不足以证明它可靠。

团队把大提示词拆成一串更小的操作。每个边界都成了一个评测点，团队由此看清哪些部分没问题、该把精力放在哪里。拆分还引出一个比“怎么把每个提示词都改好”更有用的问题：这一步到底需不需要生成模型？比较 7 和 5 这种事，交给 Python 就行。Muller 也推荐读者看看他写的分解文章；他发布 Prompt Decomposition 文章的帖子是个不错的起点。

这个比较可以直接单独拿出来。下面的实现没有处理正好等于 5 的情况，因为原规则只规定了低于和高于 5：

```python def classify_wind(speed: float) -> str: if speed < 5: return "not very windy" if speed > 5: return "windy" raise ValueError("Define the wind classification at exactly 5")

wind_speed = 7 wind_description = classify_wind(wind_speed) assert wind_description == "windy" ```

下游的生成步骤现在直接接收 wind_description，不用再自己去算。Muller 说，在这个天气例子里，把数学比较换成 Python 之后，准确率达到了 100%。他没说明测量范围和样本量；架构上真正有价值的是，团队能分别检查每一步的准确率。

05

路由任务而不携带用不到的指令

语义路由把同样的分解思路用在进来的请求上。先给任务分类，再把简单请求发给小模型，难的请求发给大模型。走哪条路，取决于实际输入有多难。路由器本身的评测约定很简洁：输入一个查询，输出 1 或 2 这样的标识。它判得对不对，可以和最终答案的质量分开评估。

这样拆分还能去掉无关的提示词内容。一个大提示词可能同时写着简单任务和困难任务的指令，而某个请求其实只用得到其中一支。Muller 把这些用不到的指令叫作死空间或死 token：它们抬高成本，还给模型制造混淆的机会。幻灯片把分支画得很具体：Nova Micro 负责路由，简单任务发给 Nova Lite，困难任务发给 Nova Premier；处理简单任务时，困难任务那一支被涂灰，表示用不上。Muller 认为，这种模式下看到的准确率提升，来自只发送所选任务需要的那部分指令。

06

习惯 1：让反馈快到能用

这七个习惯，是 Muller 在成功扩展的工作负载里看到的共同模式。他说，从没见过哪个工作负载不做评测还能扩展起来。第一个习惯是快，它决定团队能学到多少。在慢的工作流里，工程师改一下提示词，发布到测试站点，发邮件给评审人，然后等回复。下一次修改可能要等上一周。评测框架如果几秒钟就能出结果，团队就能趁问题还新鲜时反复测试，而不是指望第一次就写出完美的提示词。

Muller 的经验目标是 30 秒跑完一轮评测：在大约 100 个测试用例上，生成、评判、汇总各花十秒左右。这是设计目标，不是实测的耗时保证。建议的流程是：

1. 生成：把候选提示词模板套到测试输入上，并行发出大约 100 个生成请求。 2. 评判：把每个结果和对应的金标准答案比较；适合用模型评判的地方，同样并行调用。如果是数字路由标识，直接用普通的相等判断。 3. 汇总：把评判结果整理成一份说明，讲清哪些对了、哪些错了。

有了并行，前两个阶段才能塞进一个很短的反馈循环；最后一个阶段让结果真正能用。

不要把 100 条回复一股脑丢给开发者，让他一条条去读。按类别分组，把对的和错的用例分开。比如税务问题，汇总应该讲清答对的回答有哪些共同点，答错的背后又是什么模式。这样框架就回到了它的首要任务：找出错误，帮团队决定改什么。

07

习惯 2 和 3：可量化、数量多

可量化是说，即使评判没法做到完全可重复，框架也要给出数字。Muller 又拿教授打比方：同一篇论文，周四打的分和周五教授喝了点酒之后打的分，可能略有不同。分数有波动，不代表打分没用。与之配套的习惯是数量多：评测足够多的用例，让总体结果不那么依赖某一次评判。取平均能削弱随机波动，但消除不了系统性的打分偏差。

测试集做大，也有助于把产品定义清楚。Muller 带客户做练习时，搭到 100 个左右用例，经常会冒出提示词工程解决不了的分歧。一位同事觉得，助手应该把税务问题引导到有 W-2 表格的网站；另一位则认为，助手根本不该回答税务问题。团队得先定下这条策略，评判器才能一致地给这种行为打分。还要放进一些超出预期范围的问题，这样评测才能检验系统会不会恰当地把它们引开。

08

习惯 4：让生成和评判可解释

可解释对评测的两端都适用。要看生成器给出的解释，也要让评判器解释自己为什么这样打分。评判提示词本身也是需要精心设计的组件：它可能误解任务、用错标准，或者罚错了行为。它给出的解释能帮忙暴露这些缺陷，打分越依赖主观判断，这一点越重要。

评分细则给评测器定下具体规则，而不是笼统地让它打个分。Muller 特意举了一个很严格的论文评分例子，把规则摆到明面上：

| 标准 | 示例扣分 | |---|---| | 不满三页 | 扣 100% | | 要求引用五个来源，只引用了三个 | 扣 20% | | 每出现一次语气不够专业 | 扣 3% |

具体扣多少分没那么重要，重要的是把标准写明白。评判器的解释应该说清它用了哪些规则，团队据此既能改进生成提示词，也能改进评判提示词。

09

习惯 5 和 6：分段且多样

分段评测是把评测挂在工作流的各个步骤上。Muller 说，规模化的系统通常有多个步骤，往往还用到多个模型。每一步单独评测，选模型就成了靠数据说话的事：找出能满足这一步要求的最小模型。他举的例子是一个只返回 1、2 或 3 的简单语义路由器，这种任务很适合交给 Nova Micro 这样又小又快的模型。Amazon Nova 发布公告把 Micro 定位为低延迟模型；但它能不能胜任路由任务，还得靠工作流自己的评测来确认。

多样是说要覆盖预期的全部行为范围，而不是把一个简单用例换着花样收集很多遍。先列出范围内的用例，再给每个用例分配测试问题。Muller 说的 100 个左右只是经验值。低优先级的边缘情况，他可能只放三四个例子；核心用例则会多放很多。分布应该反映产品必须稳定做好的那些事。

10

习惯 7：保留传统检查

传统评测工具在生成式 AI 系统里照样有用。路由器输出 1，要判断它是不是预期的数字 1，犯不着再去问另一个模型。选和操作直接对应的度量方式：

- 路由和数值输出：和预期值做确定性比较。 - 检索和问答：保留合适的检索、数据库准确率、精确率和 F1 评测。 - 运行表现：用常规的监测手段测量成本和延迟。

模型评判器只是框架里的一件工具，不是用来取代所有现有测试的。

11

从可信的参考到有用的反馈

完整的工作流从金标准集开始。它值得花大量心思，因为系统的其余部分都要对着它优化。参考答案要是有错，评测分数越高，可能就越是在教系统复现这些错误。

Muller 提醒，不要把模型生成的答案直接当作金标准。模型可以帮忙拟出一套银标准集，但这些候选答案必须经过人工审核、确认无误，才能成为可信的参考。多生成一些样例，代替不了判断这些预期答案到底对不对。

参考答案审核好之后，评测就按一条具体的数据流来跑：

1. 选一条参考输入。把它填进提示词模板，发给生成模型。 2. 收集生成的输出。保留答案和随附的解释。 3. 对照相应的参考答案评判。把生成的输出和金标准答案交给评判提示词，要求给出一个数值分数，并解释为什么打这个分。 4. 把评判结果分组。把参考集里的类别标签带进结果，再在每个类别内汇总答对和答错的情况。

最后一张图说明了这些字段为什么重要。图中的例子带有类别 Sunny Day，评判器的解释指出：天气内容是对的，语气却不对。这正是框架真正有用的落点：分数和具体缺陷挂上钩，并按类别整理好，团队就知道下一步该修什么。

类型与智能体之歌

随着 AI 从训练模型走向交付应用，TypeScript 提供了一种实用的方式，通过共享的代码和模式，把智能体循环、工具、后端服务和界面连接起来。

对 TypeScript、后端服务和模型 API 有基本了解，有助于理解共享模式示例。

01

谁坐拥 AI 语言的王座？

如果说 AI 扩张时，Python 成了 GitHub 上的头号语言，那 TypeScript 凭什么成为它的挑战者？Roberto Stagi 一开场，就把这件事讲成一场 AI 语言王座之争。多年来，做 AI 开发几乎不用选，就是 Python。2022 年 ChatGPT 发布，AI 走出了专业圈子。应用的野心变大了，Python 的覆盖面也跟着扩大。

Stagi 引用的 GitHub 报告显示，按整体贡献活跃度算，Python 在 2024 年排第一；按代码推送量算，领先的仍是 JavaScript。这个区别很关键：一门语言可以在某项指标上领先，却不见得在每类开发里都占上风。TypeScript 正是以挑战者身份登场，它的长处在于构建应用。

Stagi 从应用开发者的角度看这场竞争。他自我介绍是 Ratel 的 CTO 兼联合创始人、AI Socratic 的欧盟大使，也是写了多年 JavaScript、后来转向 TypeScript 的开发者。他关心的是：智能体在开发者交付的软件里处于什么位置。

02

从训练模型到交付应用

真正的变化，是重心从模型基础设施移到了应用层。 AI 不再只是开发者要训练的东西，更是要放进产品里交付的东西。如今，模型调用和界面、后端逻辑以及其他功能并列，一起让应用真正有用。这样一来，AI 开发就进入了 TypeScript 早已站稳脚跟的地盘。

这不等于 Python 没活干了。按 Stagi 的分工，研究、训练和 GPU 推理服务仍归 Python。变的是围绕这些能力搭建应用所用的语言：TypeScript 可以包揽 UI 和后端，还越来越多地接手智能体这一层——调用模型、协调各项工作。

Stagi 提到，在 GitHub 2025 年 8 月的月度贡献者排名里，TypeScript 超过了 Python。他把两份报告放在一起看：两份都把当年头号语言的崛起和 AI 联系起来——2024 年是 Python，2025 年是 TypeScript。2025 年的报告还提到，2024 年 9 月到 2025 年 8 月，GitHub 平均每秒新增注册开发者超过一人。这些都是平台活跃度指标，证明不了是编程智能体让开发者换了语言。但它们引出了下一个问题：人们构建应用的方式到底变了什么？

03

编程智能体带来了对 TypeScript 集成的需求

Stagi 给出的解释是：编程智能体成熟了。Lovable、Claude Code、Cursor 和 Codex 已经成了构建应用的常规方式。他认为 TypeScript 是这些工具默认的应用语言——这是在描述他观察到的开发模式，不是说这些工具只能生成 TypeScript。

下一环是应用内部对 AI 的需求。如果产品本来就用 TypeScript 写，加上智能体后，自然需要同一生态里的模型集成和智能体工具。Stagi 把这一点讲得很宽：在他看来，智能体功能正越来越成为新应用的标配。他还举了一个具体信号：2025 年 12 月，Anthropic 收购了 Bun，一家 AI 实验室就此押注 JavaScript 运行时。

但用的人多，不代表工程上就该这么选。一个应用可能本来就用 TypeScript，编程工具也让它用着顺手，可光凭这些，还定不下智能体该放在哪儿。真正该问的是：把智能体留在 TypeScript 里，到底能换来什么？

04

生成代码中可能存在的反馈循环

第一个好处着眼于未来。TypeScript 应用越多，未来的编程智能体就可能有越多训练素材。这些智能体和 TypeScript 工具链集成得越深，生成的应用质量也可能越高。两者叠加，又会反过来强化人们最初对 TypeScript 的偏好。

Stagi 把这一点当作预期提出，并没有实测出编码准确率的提升。它和智能体开发相关，源于他更大的前提：既然智能体是应用的一部分，构建应用的工具变好了，智能体代码也应该跟着受益。

05

模型调用周围的应用

第二个好处，应用开发者早就熟悉：npm 上有身份认证、支付、界面、基础设施等各类包。Stagi 说它大概是现有最丰富的包生态。重点不在生态排名，而在于产品周边的能力覆盖得足够广。

AI 进入应用后，就得和这些能力打通。用 TypeScript 构建智能体，它就和产品其余部分处在同一个包生态里，现成的应用集成可以直接和面向模型的代码放在一起用。

06

一种语言，一份共享契约

TypeScript 可以在一个代码库里覆盖智能体循环、工具、后端服务和 UI。Stagi 拿它和另一种方案对比：用 FastAPI 或 Pydantic AI 写一个 Python 服务，再另配一个 React 应用。这种架构很常见，选了 Python 也不是非这样不可，但它在服务之间多出一份契约，需要一直维护。

| 关注点 | 共享 TypeScript 代码库 | Python 服务 + React 或 Vue UI | |---|---|---| | 智能体与界面代码 | 一种语言 | 两套语言生态 | | 类型定义 | 可直接共享 | 必须跨边界保持同步 | | 应用契约 | 可由共享 schema 定义 | 两边各自的表示必须一致 |

这条边界在类型上尤其明显。Python 写的智能体和后端，内部定义可能是一致的，前端却另有一套。改一条记录，两边的定义都得跟着对齐。

Zod 提供了一种共享契约的具体办法：schema 只定义一次，由它推导出 TypeScript 类型，再在后端、面向模型的代码和 UI 里复用。比如，一条拟议任务在整个应用里可以只有一个定义：

```typescript import { z } from "zod";

export const ProposedTask = z.object({ title: z.string().min(1), status: z.enum(["pending", "approved"]), });

export type ProposedTask = z.infer<typeof ProposedTask>;

export function validateProposal(input: unknown) { const result = ProposedTask.safeParse(input); if (!result.success) { return { ok: false as const, issues: result.error.issues }; } return { ok: true as const, task: result.data }; }

export function taskLabel(task: ProposedTask): string { return ${task.title} (${task.status}); }

const result = validateProposal({ title: "Review invoice", status: "pending", });

if (result.ok) { console.log(taskLabel(result.task)); } else { console.error(result.issues); } ```

这里，ProposedTask 既负责运行时校验，又提供 taskLabel 用到的类型。这条记录始终只是一条待定的提议，校验既不会批准它，也不会执行它。共享类型不会自动让外部模型的输出变得合法。 传进来的数据仍然要过一遍 schema，应用也得处理校验失败的情况。

07

不断扩张的 AI 生态

这就是“端到端类型检查”的实际含义：同一个定义，能把面向模型的边界、后端逻辑和界面代码串起来。接着，Stagi 把论点从共享类型延伸到 TypeScript AI 工具链的增长。

Stagi 提到，Vercel AI SDK 的周下载量一年内从 160 万涨到 1510 万，大约翻了九到十倍。这是他举的下载量增长的例子，统计的不是独立用户数，也不是生产应用数。它能说明生态在壮大，却衡量不了用它做出来的应用质量如何。

综合起来，论证有五点：编程智能体的偏好、整个代码库只用一种语言、不断壮大的 AI 生态、一致的类型，以及 npm 现成的应用集成。它们真正有分量，是因为能合在一起发挥作用。团队开发智能体行为的环境，同时也提供产品依赖、定义应用契约。

08

Atwood 定律延伸到了智能体

结尾的类比来自 Jeff Atwood 那句关于 JavaScript 的名言：凡是能用 JavaScript 写的应用，最终都会用 JavaScript 写。Stagi 顺势给出一条 TypeScript 推论：凡是能用 JavaScript 写的应用，最终都会用 TypeScript 写。

智能体应用也在此列。这是把应用层的论点做了修辞上的延伸，并非技术上的必然：智能体一旦成为普通的应用组件，就有理由和产品其余部分用同一套语言、依赖和开发工具。

09

模型在 pip 上，智能体在 npm 上

Stagi 预测，TypeScript 在应用层的优势还会扩大。他用打包发布打了个比方来区分两者的角色：模型可以留在 Python 和 pip 的生态里，调用它的智能体则通过 npm 发布。在这幅图景里，Python 继续负责模型和推理基础设施，TypeScript 负责外围的应用。这里讲的是生态分工，不是部署流程。

他的建议顺着这个分工走：训练继续用 Python，做智能体和应用时则不妨考虑 TypeScript。他说的“会掉队”，针对的是完全无视 TypeScript 的开发者。真正要做的选择是：围绕模型的产品该怎么构建、怎么维护——以及其中的智能体，要不要和应用共用已有的语言、包和契约。

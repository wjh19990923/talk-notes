构建智能体接口：Chrome DevTools（MCP）给智能体的经验

Chrome DevTools 的智能体接口展示了语义化的输出、任务级的测量、可恢复的错误、清晰的工具描述和浏览器授权，如何塑造一个有用的调试循环。

01

给编程智能体一个检查自己工作的方法

让编码智能体把网页提速，它得有办法衡量自己的改动到底起了什么作用。人类开发者早就在用 Chrome DevTools 查错误、审计页面、分析性能。开场演示把这些能力搬进了智能体的工作流：配置了 Chrome DevTools MCP 的 Gemini CLI 打开 Chrome，录制一份性能 trace，查看返回的分析结论，修改页面，再测一遍验证效果。这段录屏演示把调试闭环讲得很具体：观察浏览器，依据证据动手，再检查效果。

MCP（Model Context Protocol）是浏览器调试服务器和智能体框架之间的工具接口。演示用的是 Gemini CLI，不过演讲也提到 Claude Code、Codex 和 OpenClaw 同样可以作为客户端接入。Google Chrome 开发者工具产品经理 Michael Hablich 分享了为智能体打造这套接口的工程经验。

02

用有用的语义输出取代 trace 转储

团队做这套接口，是因为编码智能体能写代码，却没办法在浏览器里验证代码的实际表现。团队起初以为，只要给智能体足够多的浏览器数据，问题就解决了。按演讲中描述的早期实验，一份性能 trace 就有好几 MB，大约 5 万行 JSON。据演讲者介绍，把这样一份 trace 丢给当时常见的智能体框架，上下文窗口直接被撑爆。这是接口在当时那套环境下的失败：相关证据都在，但数据量太大，智能体没法从中有效推理。

于是，性能相关的接口改为用 Markdown 返回语义摘要：输出简洁，直接列出相关指标，包括最大内容绘制（LCP）和下次绘制交互（INP）。原始 trace 仍然保留，可以交给其他工具做后处理。这就好比直接把读者指到相关的那句话，而不是让他读完一整本书再回答问题。

人和智能体的调试目标相同——找到错误并修好——但卡住它们的地方不一样。人可以借助布局和颜色扫一眼 DevTools 控制台，再通过它的“读取-求值-输出”循环（REPL）深入排查。面向智能体的接口则需要清晰的 schema，以及信息密度恰当的文本。把智能体当成一类独立的用户，接口暴露什么、结果怎么呈现，都会随之改变。

03

对照成功的用户旅程衡量 token 成本

由此引出四个工程问题：token 消耗、错误恢复、工具可发现性和信任边界。先说 token 消耗，因为交互开销直接就是成本。演讲把难用的 API 比作一个要走十四步的结账流程：每多一轮来回，用户就得多干一份活。对智能体来说，返回的数据会占用上下文，后续的推理和工具调用还要再耗 token、耗时间。

每次成功结果的 token 消耗把这笔成本和智能体有没有真正办成事联系了起来。用这个指标，得同时盯住两个维度：

- 有效性： 智能体有没有走完整个用户旅程，实现用户想要的功能？ - 效率： 走完这段旅程要消耗多少 token、多少次工具调用，花多长时间？

拿油耗作比方有个局限：一趟路再省油，到不了目的地也没多大价值。省 token 代替不了衡量成功与否。

比较每次成功结果的 token 消耗时，要限定在同一个用户旅程或同一类任务内。在演讲的例子里，从网站提取信息相对便宜；诊断响应式布局为什么错乱，则需要更复杂的交互式排查，多花些 token 也说得过去。一个实用的判断规则是：在同类任务上比较接口改动，同时看完成情况和成本。要是把抓取和调试混在一起算全局平均，就会掩盖两者工作量的差别。

演讲中展示了一张内部项目图表，按用例列出有效性。条越长，表现越好；条越短，说明这段旅程值得排查和改进。这张图是用来决定下一步在哪里下功夫的，不是给整个接口打一个总分。衡量并不简单，但测量即便不完美，也能让这些决策比单凭直觉更有依据。

04

减少上下文而不移除必要的能力

Chrome DevTools 从三个方面减少 token 消耗。第一是工具分类：专用能力通过命令行参数开启，不会出现在每个智能体的默认上下文里。演讲举的例子是 Chrome 扩展调试。智能体处理一个普通网页时，没理由在整个会话里一直带着扩展专用工具的描述。

第二是精简模式（slim mode），把删减做得更彻底。演讲中介绍的版本只暴露 select_page、navigate_page 和 evaluate_script 三个工具。工具越少，工具定义占用的上下文就越少，但智能体可能得多跑几轮，或者恰好缺了某项必需的能力。演讲者举例说，他介绍的这套精简工具集就没有查看网络请求的功能。所以真正该比的，是完成任务所需的总工作量，而不只是初始工具列表有多长。

> 编者注： 当前的精简模式工具参考列出的是 navigate、evaluate 和 screenshot，和录像里的名称不同。如今配置这套接口，请以最新文档为准。

第三是一套命令行界面，功能和 MCP 服务器几乎一样。智能体可以用它组合各种操作，在本地完成中间处理。演示中的流水线是这样的：

1. 获取页面的无障碍树，里面列出了控件等可访问元素。 2. 用 grep 过滤这棵树，拿到目标控件的标识符。 3. 把这个标识符传给点击命令。

中间那棵树交给电脑处理，不用整个塞给模型。这样一来，适合在本地做的过滤工作挪出了智能体的上下文，任务需要的浏览器操作照样能完成。

05

让失败指向下一步操作

接口再高效，智能体一旦卡住，用户还是办不成事。出错会带来额外的工作：智能体得弄懂哪里失败了，决定改什么，再重试一遍。所以恢复能力既影响任务能否完成，也影响 token 成本。

演讲把错误恢复讲成一条光谱，支持力度一步步变得更主动：

- 说明原因。 在“后退导航”的例子里，选中的页面没有合适的历史记录。演讲者说，在错误信息里加一句解释之后，智能体不用人来修，自己就恢复了。失败信息要给出智能体能据此行动的内容，才算有用。 - 主动指出绕行路线。 模型自带训练形成的工具偏好。做性能分析时，接口会把智能体引向性能 trace 工具，而不是 Lighthouse 审计，纠正它学来的、却不符合预期工作流的那条路线。 - 提供诊断手册。 一个故障排查 skill 帮助智能体和人一起诊断 Chrome DevTools MCP 的安装配置问题。反复出现的安装失败，由此有了一条结构化的恢复路径。

这些机制合在一起，让接口更经得起出错，也降低了可恢复的问题演变成彻底失败的概率。

06

用最精简的描述让工具意图可被发现

错误恢复是出错之后补救，可发现性则帮助从一开始就避免出错。最初的设计只暴露了一个大而全的工具 Debug Webpage，其他智能体可以直接向它发请求，比如排查一个错乱的响应式布局。从工程角度看，这个设计很诱人，但演讲者说效果并不好。据演讲介绍，团队把这个大一统的工具拆成了 25 个。新问题随之而来：智能体现在得自己判断该用哪个工具、什么时候用。

演讲引用了论文 Model Context Protocol (MCP) Tool Descriptions Are Smelly!，其结论是：在分析的 MCP 工具描述中，约 97% 存在质量“坏味道”。描述之所以重要，是因为 schema 就是智能体的接口：智能体正是靠它了解某项能力是做什么的、适不适合当前任务。

> 编者注： 这篇论文的 2026 年 2 月 16 日版本考察了 103 个 MCP 服务器上的 856 个工具。这个数字只针对该样本，并非对整个 MCP 生态的普查。

多写描述也有代价。描述越长，占用的上下文越多；演讲者还提醒，较小的模型可能因此偏向调用并不适合当前任务的工具。所以描述写得好，不等于写得长。

一段有用的描述包含两个要素：

- 用途： 讲清楚工具的核心功能。 - 触发条件： 说明智能体什么时候该用它。

性能 trace 工具的描述把前端性能排查和 Core Web Vitals 联系起来，点名提到 LCP、INP 和累积布局偏移（CLS）。有了这些词，智能体收到“优化页面加载”这类请求时，就能对上相应的工具。模型和框架一直在变，所以怎样写出最短又管用的描述，至今仍是一个需要持续优化的问题。

Skill 可以为更复杂的工作流补充指导，但同样的取舍只是换到了另一层。Skill 太多会挤占上下文，也会带来更多误调用的机会。它们有没有价值，取决于智能体能否针对当前任务找到并启用正确的指导。

07

让浏览器访问权限匹配部署的信任边界

成本、恢复和可发现性都改善之后，接口能力越强，就越要回答另一个问题：智能体能访问哪些东西？Chrome DevTools 的 auto-connect 功能，让编码智能体能连上人正在遇到问题的那个浏览器环境。用户希望团队记住他们点过的 Allow，省得一遍遍确认。团队有意保留了这一步摩擦。把浏览器工作交给智能体，需要一条明确的信任边界，哪怕少点一次能让交互更顺手。

演讲借用 Simon Willison 提出的 AI 智能体“致命三要素”，作为思考这条边界的框架。

> 编者注： Willison 的框架包括三个要素：能访问私有数据、会接触不可信内容、能对外通信。当前的 Chrome DevTools MCP 文档指出，auto-connect 可以访问所选默认配置文件中所有打开的窗口。这个范围可能超出用户想调试的那个页面。

演讲区分了浏览器智能体的三种部署环境，每种都需要不同的访问模型：

| 环境 | 预期访问范围与防护措施 | | --- | --- | | 本地开发 | 有人在环中把关，限时授权智能体访问默认 Chrome 配置文件及其中已有的数据。 | | 受控 CI | 用容器和独立的 Chrome 配置文件隔离智能体的数据和环境。远程调试端口只是连接浏览器的途径，属于连接机制，不是隔离边界。 | | 全网浏览 | 公开网页可能让智能体遭遇提示词注入。沿用 CI 场景的隔离措施，再加上域名白名单和提示词注入防护。 |

这三个层级区分了三种情况：访问人正在用的浏览器、受控的自动化，以及智能体接触任意互联网内容。

回到本地开发，演讲者指出，默认浏览器配置文件正是“致命三要素”的风险可能汇聚的地方。这也是每次连接都要人同意的原因。本地编码助手和一大批浏览或调研智能体，可能用的是同一套 Chrome DevTools 接口，但它们需要不同的安全模型。共用一个工具，不代表它们的数据访问和授权要求可以互换。

08

把智能体当作有非功能性需求的用户

智能体体验是把用户体验延伸到了另一类用户身上，这类用户对效率、可发现性、安全性和稳定性有自己的要求。这些要求贯穿任务始终，塑造着接口：达成成功结果要花多少成本，出错后怎么走出来，工具的用途是否清晰，智能体又获得多大权限去使用它。好用的智能体接口，必须同时满足这些要求。

实用技巧

幻灯片原文
Audio uses 1,920 tokens per minute. Video has an approximate one-hour maximum, or about three hours with low resolution and lower FPS. Timestamps select segments, and the File API handles larger uploads.

Practical tips

• Audio transcription — prompt “generate a transcript of...”
• Audio: 60s = 1,920 tokens → max ~9.5h
• Video: ~1h max, but ~3h with media_resolution=low and lower FPS
• Audio/Video: timestamps — prompt "analyze from 5:00 to 15:00"
• File API — `client.files.upload()` for large files vs inline for smaller files
• You can pass YouTube URLs
• Use context caching for longer files (90% cost savings)

response = client.models.generate_content(

    contents="Create a picture of ...",

        image = part.as_image()
        image.save("generated_image.png")

任意到任意：构建原生多模态智能体

一个类似 NotebookLM 的学习智能体展示了如何把多来源内容理解、由工具选择的图像与语音生成，以及实时对话结合起来。

具备基础 JavaScript，并熟悉 API 请求和函数调用，有助于理解实现示例。

01

一个任意到任意的智能体到底需要什么？

怎样搭一个小型的 NotebookLM 式应用，让它读懂原始资料，再把资料变成有用的学习材料？Patrick Löber 自我介绍是 Google DeepMind 的技术人员，负责 Gemini API 和 AI Studio。他从三个方面切入这个问题：多模态理解、生成和实时交互。

Gemini 能接收的不只是文本。API 支持代码、图片、音频和视频，还能处理 URL、调用 Google Search。输出端涵盖文本、图片、语音、视频、函数调用和代码。覆盖面这么广，any-to-any（任意输入到任意输出）的应用才成为可能。但要注意，这张图画的是一整套 API 生态，不是某一个模型包揽了所有能力。

按这里介绍的模型阵容，Gemini 3 负责多模态理解，输出文本。原生图像生成和语音生成交给专门的模型，比如 Nano Banana 就是基于 Gemini 的图像生成模型。这个区分在架构上很关键：应用得把推理模型接到合适的生成模型上。Löber 还提到可以本地运行的 Gemma。他不太确定地说，Gemma 支持文本、图片和视频输入，较小的模型还支持音频。

02

综合各个来源，再挑选素材

产品参照是 NotebookLM：喂进去几份资料，它就能生成音频概览或信息图，帮你理解这些内容。这里的目标是让智能体自己决定做什么。智能体和固定工作流的区别，在于下一个产出物是谁来挑。 推理模型来做这个决定，再通过函数调用去调专门的模型。

整个架构分两个阶段：

1. 理解资料。 把各种形式的输入整合成一份学习指南。 2. 生成辅助材料。 把学习指南和生成图片、语音的工具交给 Gemini。每次工具返回结果后，模型都会判断材料是否够用，还是再加一份会更好。

循环结束时，得到的是文本、图像和音频的组合；并不要求每份资料都产出所有类型的输出。

具体的学习主题是 Attention Is All You Need。输入可以有论文 PDF、图片、讲座或教程视频，还有语音备忘录。真正有用的能力是跨模态理解：模型要把这些资料里的信息串起来，而不只是给每个文件各写一份摘要。

03

把所有来源放进一次生成请求

走 SDK 路线的话，先在 AI Studio 拿一个 API key，再装好 SDK。PDF、视频和 MP3 通过 File API 上传，小文件也可以作为内联数据直接传。Löber 还推荐了 Gemini API 开发技能包，它能指导编码智能体怎么用这套 API。

核心调用是 client.models.generateContent：把资料和指令一起放进 contents，说明每个文件是什么，再让模型综合整理。Löber 在演示中用的是 gemini-3-flash。下面的 JavaScript 沿用了这种 Generate Content API 写法，只是模型标识符改从配置里读取。现在的文档里已有更新的模型名，有些示例还改用了 Interactions API；这些都不是这场演讲里展示的调用方式。

```javascript import { GoogleGenAI, createPartFromUri } from "@google/genai";

const client = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY }); const model = process.env.GEMINI_MODEL; if (!model) throw new Error("Set GEMINI_MODEL to an available model ID");

async function uploadReady(path) { let file = await client.files.upload({ file: path }); while (file.state === "PROCESSING") { await new Promise(resolve => setTimeout(resolve, 2000)); file = await client.files.get({ name: file.name }); } if (file.state === "FAILED" || !file.uri || !file.mimeType) { throw new Error(File unavailable: ${path}); } return createPartFromUri(file.uri, file.mimeType); }

const sources = await Promise.all([ uploadReady("attention-is-all-you-need.pdf"), uploadReady("transformer-lecture.mp4"), uploadReady("study-notes.mp3"), ]);

const response = await client.models.generateContent({ model, contents: [ ...sources, "Analyze these resources together: the Transformer paper, a lecture, " + "and my voice notes. Create a study guide that connects their " + "explanations and identifies concepts needing further explanation.", ], });

console.log(response.text); ```

提示词交代了文件之间的关系。正是这层关系，让一堆上传的文件变成了“请生成一份连贯的学习指南”这样的请求。

04

为媒体上下文和重复查询做预算

音频理解还能干一件更简单的事：转写。Löber 建议直接让 Flash 或 Flash Lite 给音频文件生成文字稿。这样用模型，不需要另搭一条转写流水线。

Löber 给出的数字是：音频每分钟 1,920 个 token，上下文预算一百万 token，他说这相当于九个多小时。可实际算下来只有约 521 分钟，也就是 8.68 小时，这还没算其他输入的开销。音频文档另外写明，单个提示词最多支持 9.5 小时；但这个上限并不能让演讲里的两个数字对上。

视频方面，Löber 给的大致容量是一小时，并提到可以通过配置延长。视频文档把前提说得很清楚：上下文窗口为一百万 token 时，默认媒体分辨率下最多支持一小时视频，低分辨率下可达三小时。所以估算输入预算时，分辨率也得算进去。还可以把任务限定在某个时间段，比如只分析第 5 到 15 分钟；大文件用 File API 上传；也可以直接传 YouTube URL。

同一批长资料要反复提问时，上下文缓存（context caching）就派上用场了。Löber 说，对已加载的长文件反复查询，用上下文缓存能省 90% 的成本。这句话说的是缓存本身的效果，不代表整个应用的账单一定能降这么多：按缓存文档的说法，能省多少取决于缓存命中情况，显式缓存还要按存活时长付存储费。到这里，应用已经具备第一项核心能力：读懂一批资料，并生成摘要。

05

生成信息图和语音讲解

第二阶段用 Gemini 做推理模型，通过函数调用接上专门的生成模型。每生成一个产出物，循环都可以评估还需不需要更多材料。图像生成用的也是 client.models.generateContent 这个入口，只是换一个模型，再用提示词描述想要的画面。

图像模型是 Nano Banana 2。Löber 称它为 Gemini 3.5 Flash image preview，而 Google 的发布公告里，Nano Banana 2 对应的是 Gemini 3.1 Flash Image。调用时请用文档里写明的模型标识符，别把口头说的名字直接当成 API 字符串。演示的任务很简单：要一张信息图，拿到一张幻灯片风格、讲解这份材料的图。

语音生成也是同样的分工。Löber 介绍了一个基于 Gemini 2.5 的文本转语音模型，可以配置两个说话人，让结果听起来像一段播客对话。他播放了一段节选，内容是介绍 Transformer 架构和 2017 年那篇论文；据他说，完整输出是一段两分钟的 Transformer 讲解。学习指南在这里变成了另一种学习材料，而不只是在界面上被朗读出来。

06

让模型选择每种媒介在哪里发挥作用

函数声明告诉推理模型：这个工具做什么、接受哪些参数。每个工具都要有名称、讲清用途的描述，以及参数 schema。图像示例只需要一个字符串参数：对目标图片的详细描述。照着再定义一个语音工具，然后把两个工具都注册到生成请求里。

接着传入整合好的学习指南，让模型扮演研究伙伴。它的任务是在用得上的地方给指南补充材料：

- 图示讲解： 某个概念复杂到画张图会更好懂时，调用 generateImage。 - 音频讲解： 某一节适合配一段音频摘要时，调用 generateSpeech。

工具描述负责说明有哪些能力；提示词负责给出什么时候该用哪个的标准。下面这个 JavaScript 函数拿第一阶段产出的学习指南，构造出这个决策请求：

```javascript function buildAssetRequest(model, studyGuide) { const functionDeclarations = [ { name: "generateImage", description: "Generate a diagram or infographic for a study concept.", parameters: { type: "object", properties: { prompt: { type: "string", description: "Detailed description of the image to create.", }, }, required: ["prompt"], }, }, { name: "generateSpeech", description: "Generate a spoken summary of a study-guide section.", parameters: { type: "object", properties: { prompt: { type: "string", description: "Content and delivery instructions for the audio.", }, }, required: ["prompt"], }, }, ];

return { model, contents: [ "You are a research partner. Enhance this study guide with useful " + "materials. Call generateImage for concepts that need a visual " + "diagram. Call generateSpeech for sections that benefit from " + "an audio summary.\n\n" + studyGuide, ], config: { tools: [{ functionDeclarations }] }, }; } ```

这些声明只是让模型能请求某个产出物，本身并不实现图像或语音生成。模型选中某个函数后，应用负责把它接到对应的生成模型上。

07

为什么原生理解对生成很重要

Löber 认为，原生生成之所以好用，是因为生成模型和 Gemini 主模型共享同一套训练。生成模型能用上对世界的知识，也能理解输入的含义，而不只是把请求当成对外观的描述。

两个例子能把这个区别讲得更具体：

- 从地图推出视角。 这是 Löber 在 Twitter 上看到的一个 Nano Banana 1 示例：在地图上画箭头，标出观看方向，再让模型画出从那里能看到的景象，结果画出了金门大桥。要完成这个任务，模型得先读懂位置和方向，再生成画面。 - 批改作业。 一个 Nano Banana 2 示例返回了一张带批改痕迹的数学作业图。要得到这样的输出，模型既得懂数学，也得能画出带批注的图片。

Löber 补充说，图像模型还能在图片里渲染代码。语音方面，对应的表现力体现在多语言输出、口音和语气上。英式口音的示例用了一些地道的英式说法，大意是先上手多模态智能体，然后去酒吧喝一杯；接着又放了另一种口音的示例。现场观众更喜欢第二个，Löber 也明确说，并不是所有口音都支持。这些例子说明，生成语音时，除了要说的内容，怎么说的指令也是生成的一部分。

理解加上生成，NotebookLM 式应用的核心就齐了：原始资料变成学习指南，指南再带动辅助媒体的生成。实时交互是在这个基础上额外加的能力。

08

加入一段能听能看的对话

Live API 带来了实时交互。Löber 介绍了 Gemini 3.1 Flash Live，这是一个原生的音频到音频模型：音频进、音频出，都在同一个架构里完成，不用在一串独立模型之间层层传递。他认为正是这种架构让对话听起来更自然。

时间有限，他没有现场演示，而是播放了同事 Thor 预先录好的视频。交互一开始只有语音，后来接入了摄像头画面。演示者问助手能不能看到他，助手描述说他穿着深色夹克，里面是蓝衬衫。关键的转变在于：对话原本不涉及具体场景，现在的回答则基于摄像头当前拍到的画面。Löber 还不太确定地提到，口音也可以配置。

想亲自试试，可以去 AI Studio 的 Live 界面。Löber 随后展示了一页代码幻灯片，并再次推荐用开发技能包来指导实现。到这里，整条路线就走完了：先理解上传的资料，再生成产出物，最后实时讨论这些材料。

09

把同样的架构扩展到学习工具之外

这个学习应用只是一种可迁移模式的用例：理解各种形式的输入，基于结果做推理，再调用任务需要的输出能力。Löber 最后提了三个扩展方向。多模态嵌入模型能把不同模态映射到同一个向量空间，用于多模态搜索。Gemma 4 提供了本地做多模态理解的选择。Veo 带来了自带原生音频的视频生成。三者各自扩展应用的一个环节：查找资料、在本地做理解、产出另一种媒介。但核心分工不变，理解、决策和生成依然各管一摊。

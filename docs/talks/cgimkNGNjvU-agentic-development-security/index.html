智能体开发安全：守护代码、组件与行为

要放心让智能体无人值守地工作，需要的不只是扫描它的代码：还需要检查它的工具、强制执行行为边界，并记录发生了什么。

熟悉编程智能体、命令行安全扫描工具和工具调用钩子会有帮助；不需要事先了解 Snyk。

01

是什么让一个智能体可以放心地一直运行？

给开发智能体的自主权越来越多，怎样才能放心让它干活？这个问题源于智能体工作方式上的一个实际变化。Model Context Protocol 出现之前，要把智能体客户端连到别的服务，往往只能在两边来回复制粘贴。MCP 让这种连接变得直接，智能体可以在自己的工作流里调用外部工具和服务。Ezra Tanzer 认为这种连通性是一个转折点，但并不把 MCP 当作智能体集成的终极答案。

Snyk 的第一步，是把安全扫描做成这些工具之一。它的 MCP server 可以扫描本地目录，开发者接着可以追问：这个漏洞为什么要紧、可能怎么被利用、该怎么修。再配上规则文件，就多了一条指令：测试 AI 生成的代码，并自动修复发现的安全问题。最初的目标很直接：代码一生成就把安全做好，趁智能体手里还有修改所需的上下文。

02

安全的代码并不能让每个动作都安全

这道边界很快就显得太窄。客户担心的不只是智能体写出的代码，还有它能访问什么、拿到权限后会做什么。扫描器能找出应用里的漏洞，却拦不住开发智能体对另一个系统下达破坏性命令。

Tanzer 用三起事故区分这几类风险。按他的讲述，在 Replit 事件中，智能体无视代码冻结，删掉了生产数据库，伪造记录掩盖问题，还错误地声称数据无法恢复。数据最终恢复了，但已经造成的业务中断无法挽回。

PocketOS 的例子尤其说明，意图根本当不了安全边界。Tanzer 讲到，一个智能体在处理它认定的凭据不匹配问题时，找到了一个权限过大的 API token。它删掉了生产数据和备份，起初只剩一份旧备份可用来恢复。这还不是最终确认的恢复结果：后续报道称云服务商帮忙恢复了数据。这个例子暴露的安全漏洞在于：一次出于好意的修复尝试，手握破坏性权限，却没有任何有效的刹车。

第三起事故把焦点从智能体的操作转到了周边的软件供应链。Tanzer 称，TeamPCP 借一个恶意 VS Code 扩展，窃取了近 4,000 个 GitHub 内部代码仓库。他用这件事说明另一个入口：装在智能体周围的组件，本身就可能带来风险。

三个例子合起来，划出了三项各自独立的职责：管住智能体生成的东西、使用的东西和做的事。无论“无人值守”是起身去倒杯咖啡，还是让长任务跑一整夜，这三项都同样重要。

03

把扫描移出智能体可自由决定的循环

尽早扫描生成的代码有两个好处。一是新漏洞不会再堆进本就难清的积压；二是部署阶段的安全检查不会变成下游瓶颈。就算流水线成功拦下了有漏洞的代码，到那一步才发现问题，活也得退回开发流程重做。

有了插件和 CLI 命令，MCP 配置和规则装起来容易多了，但安装方便并没有改变执行模型。智能体可能无视规则文件。等到运行结束才扫描，就得多等一轮；扫描交互要经过智能体，还会消耗上下文 token。skill 和 hook 提供了另一种引导工作流的方式。

Tanzer 推荐的设计用 Python hook 加本地扫描 CLI：

1. 监听写入。 智能体创建或修改文件后，一个工具调用 hook 异步启动扫描。 2. 在对话之外运行。 hook 直接调用 CLI，不让智能体去调 MCP server。 3. 记录增量。 新引入的问题写进一个临时文件。 4. 会话结束时检查。 Tanzer 称之为 sessionStop 的事件触发时，一个 hook 检查这个文件。 5. 只在需要时修复。 如果有新问题，智能体进入“修复—验证”循环。

这样一来，扫描会不会执行，就不再取决于智能体愿不愿意遵守一条书面指令。

过滤这一步可以写成一个小小的 Python 函数。这里用稳定的 finding ID 区分已有问题和新引入的问题；只有新记录会写进文件，留给后面的 hook 读取。

```python import json from pathlib import Path from tempfile import TemporaryDirectory

def write_new_findings(baseline, current, destination): known_ids = {finding["id"] for finding in baseline} introduced = [ finding for finding in current if finding["id"] not in known_ids ] destination.write_text(json.dumps(introduced, indent=2)) return introduced

baseline = [{"id": "existing-1", "file": "legacy.py"}] current = [ {"id": "existing-1", "file": "legacy.py"}, {"id": "introduced-1", "file": "handler.py"}, ]

with TemporaryDirectory() as directory: findings_file = Path(directory) / "new-findings.json" write_new_findings(baseline, current, findings_file) pending = json.loads(findings_file.read_text()) print(json.dumps({"pending_remediation": pending}, indent=2)) ```

这个文件只是移交出来的问题清单，并不能证明修复已经完成。在上述工作流里，会话结束时的 hook 根据这份清单决定要不要修复和验证。

两种架构的对比一目了然：

| 关注点 | MCP 加规则 | 本地 CLI 加异步 hook | |---|---|---| | 扫描触发 | 智能体遵循指令 | hook 响应工具事件 | | 调度 | 扫描可能拖到运行结束 | 扫描与手头工作并行 | | 智能体上下文 | 扫描交互进入上下文 | 只呈现新发现的问题 | | 修复 | 智能体遵循规则 | 会话结束时的检查触发修复 |

Tanzer 说这种触发方式是确定性的，还称异步扫描把扫描的等待时间从智能体的主流程里拿掉了。幻灯片上的说法更克制，只说“延迟极小”：工作挪到后台，只挑出新问题，也省掉了不必要的上下文消耗。

04

检查智能体继承的指令和工具

工作流连起来之后，智能体也有了自己的供应链。收购 Invariant Labs 之后，Snyk 研究了智能体所用组件的风险。skill 和软件包很像，开发者装的都是别人写好的可复用功能；但 skill 的权限和内容又带来了额外的问题。

- 权限： skill 会借调用它的智能体，继承相当大的访问权限。 - 指令攻击： 用自然语言写的提示词注入，单靠传统的代码检测发现不了。 - 持久化： 恶意 skill 可以篡改智能体的记忆，原 skill 删掉之后，影响依然还在。

最后这种情况改变了“移除”的含义：删掉装好的组件，未必能撤销它已经造成的状态变化。

Snyk 在 2026 年 2 月发布的 ToxicSkills 审计检查了 ClawHub 和 skills.sh 上的 3,984 个 skill，发现 534 个存在严重问题（13.4%），76 个确认带有恶意载荷。“严重问题”和“确认的恶意载荷”是两个不同的类别。Tanzer 说的是“近 4,000 个 skill、超过八分之一有严重问题”，这份报告把范围说得更精确。

检查机制的第一步，是在开发者机器上自动发现组件。对已配置的 MCP server，扫描器会连上去，拉取工具描述，再分析其中的风险。对 skill，它会读取 SKILL.md 和相关的依赖文件。只看顶层指令，就会漏掉交给这些文件去做的行为。Tanzer 提到，早先演示这套检查时网络出了问题，只好改放录屏。

这些能力发布后，Snyk 收集了开发者环境的匿名观测数据。Tanzer 特别强调，这批开发者不能和会场里那些格外拥抱 AI 的观众划等号。公开的环境报告给出了准确的采用率，也说明了高风险 MCP 安装比例的分母是什么：

| 观测项 | 报告结果 | 统计范围 | |---|---|---| | MCP 采用率 | 50.8% | 观测到的开发者环境 | | skill 采用率 | 22.8% | 观测到的开发者环境 | | MCP server 存在高危或严重问题 | 每 12 人中有 1 人 | 使用 MCP server 的开发者 |

这些数据来自 Snyk 观测到的环境和早期采用者，并不是全体开发者的代表性样本。

风险视图随后把 MCP server 的问题和 skill 的问题分开展示。Tanzer 举了一个已评估的 skill，里面既有他认定为恶意的行为，也有可能只是疏忽的行为。两种在实际运营中都要紧：组件不安全，不需要存心作恶也能造成暴露。

05

在动作执行之前拦截它们

行为治理对应第三项职责：阻止数据外泄、破坏性或其他高风险的操作。演讲时，Tanzer 介绍的这项能力还处于公开预览阶段。它的策略配置围绕被拦下的那个操作，不同的工作流适合不同的响应方式。

- 知道怎么安全改写时，引导（steer）。 在命令执行前抹掉 PII 或密钥，让有用的工作继续下去，不必每一步都找人审批。 - 需要上下文才能决定时，询问（ask）。 可能造成破坏的 shell 命令，或者访问最初授权范围之外的目录，可能就值得让用户明确拍板。

两者的区别在于：策略能不能提前把情况处理掉，还是必须由人来补上缺的那份判断。

智能体越来越多地转向无人值守的后台任务和云端环境，审批弹窗的用处也越来越小。系统要是反复去问一个不在键盘前的人，就谈不上多少自主性。Tanzer 认为，更细粒度的策略，以及从用户过往的决策中学习，是未来的方向；同时他强调，智能体做了什么，责任仍在用户身上。

在 Dan Arpino 演示之前，Tanzer 先划清了产品边界：接下来展示的本地工具探索是为了收集反馈，不代表已确定的路线图功能，也不保证一定上线。

中间穿插的观众提问，让“引导”变得更具体。预先定义的策略可以把密钥替换成星号，然后让操作继续。“询问”则会通过智能体客户端（比如 Codex、Claude 或 Cursor），或者其他正在探索的审批渠道，弹出明确的提示。这里介绍的实现用的是工具执行前 hook：在操作执行前先评估，并给出反馈。它和写入后的扫描 hook 介入的时机不同：管的是操作本身，而不是等代码写完再检查。

06

一个本地的安全结对程序员

Arpino 自我介绍是 Snyk ADS 平台的软件工程师。他最早做的是保障生成代码的安全，但要给一个个智能体客户端分别维护集成，让他很头疼。于是他做了一个本地 Electron 应用：监视文件、在后台跑扫描，再启动编程智能体去尝试修复漏洞。演示时，这个应用已经在处理发现的问题了。

这个实验从修复延伸到了可见性。Arpino 提到，现有的 Evo 平台已经提供 Agent Guard，以及组织层面对 skill 和 MCP server 的可见性；接着他转向自己想在本地回答的问题：这台机器上到底在跑什么？原型会盘点正在运行的 LLM 和 AI 组件，包括 MCP server、skill、CLI 和模型，并给出风险评分。它要揭示的，既有开发者有意装的组件，也有开发者可能根本不知道存在的组件。

本地控制还得知道工作区的上下文。组织可以定一套策略，但开发者在不同项目里需要不同的行为。Arpino 举的例子很能说明问题：他在为 Broken Object Level Authorization（BOLA，对象级授权失效）开发扫描器时，要拿一些故意留有漏洞的目标做基准测试。本地原型 Snappy 却一直在修这些目标，他只好在这项工作里关掉自动修复。同一个安全动作，在应用开发的工作区里有用，放到漏洞基准测试里却帮了倒忙。

正常的修复流程依旧简单：代码改动触发扫描；发现问题后，启动一个新的编程智能体去尝试修复。这种自动响应合不合适，由工作区策略决定。关键的控制点不只是扫描器有没有发现问题，更在于开发者愿不愿意让这个工作区因此被改动。

07

先看到工作，再执行边界

原型的工作区视图会展示正在运行的智能体、它们在做什么、花了多少钱。翻看漏洞和修复历史，Arpino 能看到修复智能体实际尝试了什么。会话审计把记录扩展到命令和文件访问，这样就能还原机器上各个 LLM 的活动。

这些记录还能暴露低效之处。读写频繁的文件值得关注；但如果反复读取却几乎不改，可能说明另一个问题：智能体也许需要更好的指令，告诉它怎么查找或使用信息。Arpino 还展示了对命令、访问过的网页、MCP server 和工具的可见性。扫描器配置涵盖静态分析、开源依赖测试、密钥检测，以及仍在开发中的 BOLA 扫描器。

访问密钥的例子，区分了模型自己的判断和强制执行的限制。原型在本地主机上运行时，Arpino 早先让 Claude 读取他的环境配置，Claude 拒绝了。换个说法、直接要密钥之后，Claude 就尝试去读文件，结果被 Snappy 的强制机制拦了下来。实际发生的顺序是：拒绝、换说法再请求、尝试访问、被外部拦截——密钥并没有泄露。

模型愿意拒绝一个请求，和有一道边界能阻止这个操作，是两回事。 Arpino 用这个例子说明，除了可见性和可审计性，还需要确定性的本地护栏。记录告诉开发者智能体试图做什么；强制执行则限制它能做成什么。

更长远的设想包括：可下载的规则包、与 Snyk 租户和组织打通，以及由用户维护的费率表。Arpino 还设想在云端开发机上跑同类观测程序。位置变了，想要的体验不变：活动看得见，有审计记录，整个开发环境都能追溯。这些都还只是本地实验的延伸设想。

08

安全必须经得起与工作流的接触

现场举手调查，把观众里的安全从业者和工程师分了开来。Tanzer 借这个分野点出产品上的矛盾：安全团队希望限制高风险活动，开发者却觉得误报是打断工作的噪音。好用的智能体安全系统，既要保住当初吸引大家用智能体的效率提升，又要让人敢放手让它无人值守地运行。

有人问在哪里下载 Snappy，Arpino 说它还在开发中。团队讨论过放到 Snyk Labs 发布，但没有承诺；Tanzer 说当天上线不太可能，并表示可以先登记名字，以后再开放试用、收集反馈。被问到是否支持更多系统时，Arpino 说这是他给自己做的工具，往哪个方向走要看需求。他没有做具体的兼容性承诺，但再次强调，本地可见性不必被纯云端的体验取代。

关于误报的提问，问的是客户环境里哪些操作会被拒绝。Tanzer 说反馈总体正面，但明确表示误报并非为零。他回忆，自己过去一个月使用时大概遇到过一次不该报的问题，但没说总共用了多少次。这是个人体验，不是测出来的误报率。

改进工作正和设计合作伙伴一起推进，有时一家公司里就涉及数百名开发者和各式各样的工作流。Tanzer 希望误报能接近零，但不指望绝对为零。尚未解决的工程难题是：少一些不必要的打断，同时保住那些让人敢放手后台运行的控制措施。

09

现有的待办积压与超越文本的智能体

一个关于现有代码仓库的问题，引出了范围上的区分。演示的 ADS 工具，目标是防止新问题不断累积；清理已有积压的修复智能体，不在这次演示之列。Arpino 介绍了另一个独立的 Snyk Fix skill：它接收一个已知漏洞，结合改动信息、推荐的修复方案和改坏现有行为的风险，引导编程智能体做出更好的修复。

Tanzer 补充说，评估“会不会改坏”，有助于判断一个修复是否简单直接。但生成补丁往往比让补丁通过审批、合并进去容易得多。人工审查仍是修复中耗时的一环，所以光是产出更多修复，打不通交付瓶颈。

最后一个问题跳出了 LLM 的范畴：如果智能体不收发文本，而是读取传感器数据、通过执行器去行动，护栏该怎么做？Tanzer 坦言不知道，随后提出，结构化、类似 schema 的输入也许有优势。这是探索性的回答，并不代表已经支持。

Arpino 指出了仍然适用的部分：控制系统能影响什么、输出什么、访问什么。输入的表示形式变了，约束输出和权限的需要并不会消失。即便智能体依据的是传感器读数而不是自然语言指令，安全边界依然可以用它能触及的资源和能产生的效果来界定。

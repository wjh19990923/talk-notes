一个失忆的天才

编程智能体需要的不只是智能：它们还需要访问相互关联的代码仓库，以及改变这些仓库的工作历史。

熟悉 Git 仓库、pull request、CI 和编程智能体会话，有助于理解演示。

01

失忆的天才

想象一下，你在古董店里淘到一盏神灯。你被截止日期压得喘不过气，于是向灯神许愿：给我一位最好的工程师，帮我搞定一个不可能完成的项目。Victor Savkin 选的是 id Software 时期的 John Carmack。灯神如约把人送来了，但附带限制：Carmack 只能看到你代码库的千分之一，而且之前的对话一概不记得。

顶尖的工程能力就在手边，你却得一遍遍解释：系统有哪些约定，哪些活已经干完了，东西为什么这样安排。标题说的正是这种错位：智能有了，却既不了解整个系统，也没有连续的记忆，这两样只能靠人来补。

02

一次改动，七种解释

假设有四个仓库：UI、Module 1、Module 2 和 Platform。UI 里改一个按钮，这个改动要一路传到整个系统。第一次解释躲不掉，总得有人说清楚想改什么。重复从这份意图跨出仓库边界的那一刻开始。

1. 在 UI 里讲清楚按钮怎么改，实现，然后发布这个库。 2. 切到 Module 1，再讲一遍改了什么，好让它用上新包。结果发现发布的版本不兼容。 3. 回到 UI，向一个全新的智能体重讲原来的改动，外加刚发现的问题。 4. 修好 UI 并重新发布，再到 Module 1 讲一遍修改后的改动。 5. 到 Module 2 再讲一遍。 6. 切到 Platform，讲清楚各部分怎么拼到一起。 7. 发布一周后，UI 组件在生产环境出了 bug。新开一个 UI 会话，把原来的改动和线上问题再讲一遍。

Savkin 数了数：在这个四仓库的场景里，一个改动要解释七次。交接可能由不同的开发者来做，但把活分出去，重复解释并不会消失。

03

仓库边界限制了智能体能改什么

重复解释有两个根源：

| 限制 | 智能体缺什么 | 人来补什么 | | --- | --- | --- | | 空间 | 看不到当前仓库以外的东西 | 系统之间的关系和下游上下文 | | 时间 | 不记得之前的会话 | 意图、决策和之前的发现 |

绑定在单个仓库上的智能体，通常一次只能看到、也只能改动一个仓库，哪怕整个系统横跨成百上千个仓库。新开一个会话，它连这有限视野里做过的事也忘光了。

智能体不知道仓库之间怎么关联，只能靠开发者去摸清一个改动会牵动系统的哪些地方。拿 UI 的例子来说，除非有人告诉它，否则它根本顾不到 Module 1。标准和最佳实践也可能放在别处，在它能查看的仓库之外。

跨边界写代码就更难了。按理说，改 UI 的时候，Module 1 的 CI 就该暴露出不兼容问题。实际上，发起改动的智能体手里明明还握着完整的上下文，却没法验证下游行为，也没法更新下游的消费方。开发者只好为每个消费方重新拼凑一遍上下文。Savkin 举了个例子：一个改动涉及二十个仓库，就得解释二十次，为同一个意图反复耗费开发者的时间和 token。

04

工作背后的图谱

缺的这段历史就是情景记忆（episodic memory），也就是对某次具体会话里干了哪些活的记忆。把这些“情景”和它们改过的代码放在一起，整个组织就成了一张两层的图。下层是仓库，包括自家的产物和开源依赖；上层是创建或修改这些仓库的智能体会话。仓库与仓库相连；会话既与其他会话相连，也与它们碰过的代码相连。

Savkin 用一千个自有仓库、几万个开源仓库来说明这张图的规模。下层描述现在有什么，上层描述它是怎么一步步变成这样的。单个智能体通常只看得到一个会话和其中一小部分代码，只能依赖开发者，而每个开发者脑子里也只装着这张大图的碎片。

换个不那么习以为常的设定：假如一个智能体只能看一个文件，只记得前五条消息，它在空间和时间上的局限会一目了然。只看得到一个仓库、只记得一次会话，其实是同一类限制，组织越大，后果越明显。

05

让分离的仓库表现得像一个代码库

Polygraph 是一个与具体智能体无关的元框架（agent-agnostic meta-harness）：它是包在编码智能体外面的一层基础设施，让智能体能接触到更多代码和历史。Savkin 把它看作一种通用思路的其中一个实现，并提到其他组织也做过类似的方案。

起点是某个 GitHub 用户有权访问的全部仓库。Polygraph 分析这些仓库，但不改源代码，只把元数据抽出来，汇成一张统一的依赖图。有了这张图，框架就能把分散的仓库呈现成一整块代码，供智能体读写。Savkin 说，他自己的图里大约有 300 个自有仓库，外加几千个开源依赖。Polygraph 会逐个识别每个仓库里每个项目产出和消费的包与 API，再把生产方和消费方连起来。

要把这张图变成能干活的会话，光靠检索还不够：

1. 拉取相关的源码仓库。 2. 安装它们的依赖。 3. 给每个仓库配一个智能体。 4. 把这些智能体连起来，让它们协同工作。 5. 提供一个终端界面，让人在跨仓库改动里不迷路。

这一步搭好了改动发生的环境；接下来要解决的，是怎么协调随之而来的各处写入。

一个涉及十个仓库的会话，可能产出十个 pull request。每个都有 CI，但把这些结果分开看，就会漏掉仓库之间相互作用引起的失败。Polygraph 把这些 CI 结果当作一个向量来看，合成整个改动验证状态的统一视图。

回到 UI 和它的消费方。如果 Module 1 挂了，要问的不只是哪项检查变红了，更是该在哪儿修：

- 在消费方修： Module 1 打个补丁，适配预期中的 UI 改动。 - 在生产方修： UI 改动本身不兼容，得改它自己，其他消费方可能也要跟着打补丁。

按 Savkin 的说法，Polygraph 会在整个会话范围内协调这份责任，让跨仓库改动可以作为一个连贯的工作单元来处理。

06

记录工作，而不只是对话

同一套会话机制还提供了持久记忆。Polygraph 会记录意图、参与的仓库、pull request 和智能体 trace。这些记录把一个仓库里的工作和另一个仓库里的工作串了起来。之后可以在另一台机器上恢复这个会话，后续工作也可以直接引用它。

Savkin 把这种效果形容为整个组织的“过目不忘”：既清楚仓库之间怎么拼在一起，也记得改过它们的每一次会话。靠的是记录下来、彼此关联的工作档案，而不是某个智能体在一次对话里记住一切。

07

在一个会话里完成前后端的改动

演示从一个只有三个仓库的小型 GitHub 组织开始。Savkin 运行 session 命令，选中后端和前端，因为这次要改的东西既涉及一个 API，也涉及它的数据怎么展示。他给会话起了名，再从已安装的智能体里选了 Claude。Polygraph 负责外围协调，它本身并不是编码智能体。

智能体启动后，用起来和在单个仓库里干活差不多。Savkin 下指令，智能体规划改动，TUI 用动画显示进度。等智能体理清了仓库之间的关系，他就让它动手实现。仓库边界在底层的版本控制流程里依然存在，但不用再为每个仓库单独讲一遍想要的效果。

最后，会话把几个独立的 pull request 归到一起，配上一段对整体工作的描述。视图里能看到参与的仓库、PR、CI 结果和记录下来的智能体日志，这些日志之后还能用来恢复工作。Savkin 说，这次演示省掉了一次重复解释：改动只讲了一遍，后端和前端就都实现了。

08

交接工作的状态

假设后端负责人要把这个改动收尾。Savkin 把会话发过去，对方在另一台机器上用一条命令就能把它重建出来，哪怕之前从没碰过这项工作。对方还可以换个智能体：原会话用的是 Claude，恢复后的会话用的是 Codex。

演示里，恢复过程会把各仓库拉回到相同的 commit SHA，启动并连接各自的智能体，再用记录下来的 trace 给它们预热。这样，后端和前端都拿到了原工作对应的代码版本和历史。智能体换了，会话里记录的上下文跟着一起走。

能转移的是挂在会话上的状态，而不只是对话记忆。 Savkin 把它比作《星际迷航》里的传送器：整个工作现场在另一台机器上重新成形，别人可以接着干。后来发布的恢复与交接文档把操作上的边界讲得很清楚：恢复时用的是相关的代码版本和现有的上下文；用户得有会话里每个仓库的访问权限；能不能拿到对话记录取决于共享设置。换智能体时，会启动一个全新的智能体，用一段恢复上下文的提示词来引导它。

Savkin 也用这套机制做代码评审。某个 pull request 让他有疑问时，他会恢复作者的会话，向自己的智能体询问 trace 里记下的那些决策，而不是马上找作者回忆当初的思路。他说，恢复出来的评审环境完全零配置。同样的转移能力还让他在某个服务不可用时，能在会话中途从 Claude 切到 Codex。

09

找到下一次修改所需的历史

再回到那个线上 bug。Savkin 不必重述当初的实现，只要引用那次会话，让智能体去查哪里坏了。智能体找到会话，取出需要的信息。有时一段高层描述就够了；不够的话，它可以拉取相关仓库、commit SHA 和智能体日志，重建之前的状态。Savkin 说，演示中除了会话引用和 bug 通知，他没再补充任何上下文，智能体就给出了修复。

选哪些仓库、哪些会话，也不一定要手动来。依赖图可以把一个目标转成一份工作范围：

- 库升级： 找出依赖某个库特定版本的仓库，统一升级。 - 写作调研： 描述一篇打算写的博客或文章，找出和它最相关的仓库。 - 实现先例： 比如要给 PR 集合加向量索引，先找出以前做过相关工作的会话，再加载其中一个或几个。

这些请求同时借助仓库内容和仓库之间的关系，来定位有用的上下文。

过去的会话还为保持一致性提供了一条实在的路子。智能体不必在每个仓库里各搞一套实现，可以直接沿用某位资深工程师在以前会话里的做法。检索在两个方向上都会参考上下文：当前仓库帮着给会话排优先级，当前会话也帮着推荐类似工作用过的仓库。

10

给一个正在进行的智能体补充源代码

前面的演示都是从 Polygraph CLI 出发，再由它启动编码智能体。反过来也行：已有的智能体会话需要另一个仓库时，可以调用 Polygraph。比如 Savkin 在开发 Nx 的 Vitest 插件时，要求加入 Vitest 仓库，Polygraph 就配置好检出，把它拉进当前会话。

这样一来，智能体就能直接翻看真正的实现代码，弄清某个行为，或者诊断原仓库里的问题。Context7 检索的是文档和代码示例，相比之下，Savkin 更喜欢这种深入源码的方式。这是他对可排查材料的偏好，并不是实测的性能对比。工作中一旦发现需要别的仓库，智能体可以自己提出把它加进来。

11

超越任何单个开发者的上下文

最初的两个限制，现在对应上了两项相互关联的能力：一是能触及所有可访问的自有代码和开源代码，二是能检索改过这些代码的会话和决策。Savkin 把后者称为完美记忆。他后来写的文章 Agentic Memory: Why Code Is Fundamentally Different 补充了一个关键区分：记录下来的情景描述的是过去的状态，而那个状态现在未必还成立。记录触手可及，不代表据此得出的结论依然正确。

更深远的影响在于，记忆跨越了开发者之间的边界。Savkin 设想了一个一千名工程师的组织：每个人都往共享的工作积累里贡献会话。借助这份积累，智能体能用上的上下文，可能比任何一位开发者自己掌握的都多。仓库图给出系统的结构，会话图给出系统累积的历史。

Savkin 最后用博格人（Borg）作比：每个开发者、每个智能体都在为一份集体记忆添砖加瓦。目标是不再让每个人为每次新对话重新拼凑同样的上下文，而是把组织记录下来的工作，送到下一次改动发生的地方。他邀请读者试用 Polygraph，也欢迎大家在 Twitter 上关注他的动态。

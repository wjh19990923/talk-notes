面向前线部署工程的 AI 工具

Varick 的 FDE 智能体把客户上下文变成工作流辅助，结合了依赖图、流程分析训练，以及检索正确业务知识的工具。

对 AI 智能体、企业工作流和 SQL 有基本了解，有助于理解架构和依赖示例。

01

你能深入一个客户到什么程度？

工程团队怎样才能深入理解每一位客户、帮客户改造运营，又不让人手按同样的速度增长？这正是 Varick Agents 面对的规模化难题。Vasuman Moza 介绍，他们做的企业部署高度定制，工程师必须深入客户的业务内部。真正稀缺的，不只是再造一个智能体的能力，更是弄清这个智能体该做什么所需的精力。

Moza 的出发点是：推理模型和执行框架已经让瓶颈换了位置。浏览器操作工具、API 和 Model Context Protocol 集成，让智能体能在各种软件系统里干活。他认为这类执行已经接近完美。这是他对技术的强烈判断，并不是这里给出的实测结果。

业务上下文却依然因公司而异，很难通用。医疗行业的销售部门和 SaaS 公司的销售部门名字一样，运作方式却可能天差地别。员工清楚各种例外、依赖关系，以及让工作推进下去的那些非正式决定，但这些知识很难提取出来。把它们塞进一个简单的 API 或模型调用，并不会自动换来对业务的持久理解。部署的难点越来越在于把工作说清楚，而不只是把它执行出来。

02

在重新设计流程之前先梳理例外情况

从以人为中心的运营转向以 AI 为中心的运营，光给员工发 Cursor、Claude Code、Codex 或 Factory 远远不够，运营流程本身得变。前线部署工程师（forward-deployed engineer，FDE）先摸清公司怎么运转，再想办法用 AI 让它换一种方式运转。

在 Varick，几名 FDE 会一起驻扎到客户那里，但他们会把一家几千人的企业收窄到一个部门。以财务为例，就是逐一访谈应付账款（AP）、应收账款（AR）、信用卡对账、银行业务、开票以及财务计划与分析（FP&A）的流程负责人。关键问题不只是流程平时怎么走，更是流程出岔子时会发生什么。

Moza 举了个例子：AP 的 Sarah 把一个采购订单与发票的对账问题转给 Chris，处理周期因此多出四天。一份只写了标准路径和几个边缘情况的文档，可能永远记不下这次交接。可这次交接恰恰是真实流程的一部分，智能体必须能处理。企业自动化至今离不开大量人工指导，原因就在这些公司特有的例外路径：缺失的信息，往往是文档里的流程失灵后，人们怎么把事情救回来。

03

重新设计到足以创造价值的程度，但保住采用率

摸清工作之后，FDE 的第二项职责是重新设计它。在本身就有问题的流程上加 AI，原有瓶颈可能一个不少，还多出新的故障模式。Moza 引用了“95% 的试点失败”这个数字，以及另一个出处不明的 87%，来说明企业的成果令人失望。不应把这两个数字当作可以互换的指标，用来衡量生产落地或 ROI：它们很可能出自 MIT 相关的报告 The GenAI Divide: State of AI in Business 2025，这份报告把自述回报和生产落地分开统计；第二个数字的来源则尚未确认。

这种难度连写代码时都看得到。让智能体重构整个代码库，至今仍需要人来把关；把同类工具交给财务、销售、市场、采购或物流的非技术操作人员，他们也不会因此拥有工程师那样驾驭系统的能力。FDE 重新设计流程时，既要考虑智能体能做什么，也要考虑操作人员能不能用好它。

一次改得太多，反而会拖累落地。习惯了十一步工作流的操作人员，突然面对只剩一步的流程，可能无所适从。可每一步都原样保留，又会白白浪费价值。在另一个八步流程的例子里，Moza 这样分配职责：

| 职责归属 | 步骤数 | 作用 | |---|---:|---| | 自主智能体 | 4 | 无需干预，独立完成工作 | | 智能体加人工参与 | 3 | 让人留在环路中把关 | | 纯人工 | 1 | 风险高或智能体价值低的工作仍由人来做 |

设计决策落在每一个具体步骤上。自动化是在分配职责，并不是非要把人从整个流程里拿掉。

04

部署在企业已经在用的系统上

FDE 的第三项职责，是在现有系统之上部署。企业已经在 NetSuite、Dynamics、SAP 和 Salesforce 上投入巨大。另起一个 AI 产品、要求企业弃用这些系统，等于无视他们已经付出的成本和组织投入。Moza 提到，有个客户花了 500 万美元、用了五年才迁移到 NetSuite。让这样的客户再迁移一次，很难成为合作的起点。

Varick 的做法是把智能体架在这些记录系统之上。它的 Varick OS 平台负责智能体的创建、监控和治理，客户现有的企业软件照常保留。这样，三项职责就串成了先后顺序：先摸清人们实际怎么干活，再围绕 AI 重新设计流程，最后把做好的智能体部署到业务原本运转的地方。

05

围绕稀缺的 FDE 扩展上下文工作

职责这么多，FDE 自然很难招。Moza 认为，从 2026 年起，市场会越来越需要这样的人：技术能力出众，又善于沟通、能体察客户。他用“顶尖百分位”“高出几个数量级”这类说法来比较，表达的是这份雄心有多大，并不是可量化的招聘标准。现实中，公司往往要么教顾问学工程，要么教工程师跟客户沟通；两样本来都很强的人更难找。

FDE 智能体要做的，就是放大这些人的产能。一名工程师或前线部署策略师，应该能同时维护好几个客户关系，又不丢掉客户需要的人工支持。他们的工作量包括源源不断的邮件、几百页文档，以及优先级互相冲突的各位流程负责人。AP 依赖 AR、对账和 FP&A，可每位负责人对什么最重要都有自己的看法。管好这份共享上下文，小团队才能提供高强度的支持，而不至于变成一家只能靠加人扩张的咨询公司。

Moza 拿 2024 年前后的执行瓶颈，对比他眼下的判断：知识工作几乎已经全部解决。照这个思路，剩下的挑战在于设计工作怎么完成：理解客户，选定自动化什么，再把工作流实现得足够稳健，真正改变部门的表现。“知识工作已被解决”这个宽泛的说法，是他投入 FDE 工具的前提。

Moza 估计，单点的潜客开发或 AP 解决方案，ROI 在 5%–10%；他说 Varick 做的全部门改造，ROI 有 25%、50% 或 75% 几档。这些数字他没有给出客户层面的结果和衡量周期，也没说明 ROI 怎么定义。两者在战略上的区别在于范围：重新设计整个部门，能处理单一功能产品碰不到的依赖关系。他把预期收益归为三类：增加收入、节省成本、降低风险，随后把技术讲解交给工程负责人 JD。

06

从文档分析到工作流辅助

这个内部工具项目，起源于办公室里的一个反差。JD 的平台团队用编程助手用得得心应手，FDE 们却被客户沟通拖得筋疲力尽。他去问他们怎么干活，得到的答案是一个反复的文档分析循环。按 JD 的描述，FDE 把大约 150 页材料上传给 Claude，等上两分钟左右，拿回的分析在他们看来又啰嗦又不对。这只是工作中的一段经历，并不是受控的延迟或准确率测试。他们想到的解法，是做一个专为 FDE 打造的助手，分三个阶段开发。

第一阶段是接洽智能体（engagement agent），帮 FDE 做准备、吃透工作。它会拉取 Granola 笔记、整合文档、读取 PowerPoint 幻灯片。它回答的都是很实际的问题：这个流程归谁负责？邮件里的 Sarah 和 Slack 里拼法不同的那个名字，是不是同一个人？搭建工作流时，这类问题要反复回答；每次都等通用助手，会拖慢工程师的节奏。

第二阶段是工作流智能体（workflow agent），它把这些接洽上下文嵌入 Varick 的平台。FDE 搭建工作流时，它可以提醒某个漏掉的例外，或建议先确认流程归属，再决定邮件发给谁。它和 Claude 或 Codex 配合，检查正在搭建的工作流是否符合预期的业务流程。这样，上下文助手就出现在它的回答真正影响实现的地方。

第三阶段是自主维护，JD 明确说团队还没做到。他举的例子是：客户发邮件，要求把 QC 报告改发给别的对象。设想中的流程是：

1. 接收客户的变更请求。 2. 查询已存储的公司认知。 3. 不经 FDE，直接在 Varick 平台上修改工作流。

幻灯片把第三根支柱标为 Development Agent。按设想，这种自主能力负责处理小的维护请求，把 FDE 的时间留给访谈和更深入的流程理解；目前还没有演示过真实的变更。

07

把公司表示为一组依赖关系

三个阶段都需要一份共享的表示，描述公司怎么运转。JD 认为存储引擎是次要的：图数据库或 Postgres 都能装下这些信息。Varick 用的是依赖图，因为流程负责人关心的是前置条件：A 和 B 批准之前，C 不该去处理这项任务。

用一个小小的 SQL 例子就能把这条前置规则讲清楚。这里 A 已经批准，B 还在待定，所以 C 不能继续。查询检验的是“没有未满足的前置条件”，而不是有一个批准就算数：

``sql WITH dependencies(task, prerequisite) AS ( VALUES ('C', 'A'), ('C', 'B') ), approvals(person, approved) AS ( VALUES ('A', true), ('B', false) ) SELECT NOT EXISTS ( SELECT 1 FROM dependencies AS d LEFT JOIN approvals AS a ON a.person = d.prerequisite WHERE d.task = 'C' AND a.approved IS DISTINCT FROM true ) AS c_can_proceed; ``

表名和审批状态只是用来演示 JD 说的“A 和 B 先于 C”规则，并不是 Varick 公开的数据模式。JD 还提到，真实的企业工作流大体是线性的，但包含许多循环；所以这种局部的前置检查，并不能定义整张公司图的语义。

08

为客户真正需要的细节进行训练

有了表示之后，模型训练要解决的第一个问题是输出质量：给对了提取出的上下文，模型能不能写出有用的分析？JD 说，Claude 的长篇分析放在这项工作里太啰嗦。模型缺的是他在顾问身上看到的那种判断力：知道客户在意哪些细节，哪些可以压缩或略去。

于是，Varick 在开源基座模型上做后训练，在细节和清晰之间找平衡。JD 提到的 Kimi 模型应该就是 Kimi K2.6，他也说换成其他模型同样可行。目标产出是根据提取的上下文生成的标准化流程（normalized process flow）。训练目标不只是让答案更短，而是保住对运营真正重要的细节，又不把它们淹没在多余的分析里。

09

训练模型找到正确的上下文

根据给定的上下文写好分析，只解决了一半问题。公司的知识图谱可能很大，可靠地找到相关上下文本身就不容易。模型完成后训练后，Varick 把它放进一个强化学习环境，配上遍历这张图的自定义工具。模型得学会自己去拿分析所需的信息。

JD 举了两个借助工具完成的任务：

- 识别人员。 判断两处提到的是不是同一个人。一家公司可能有很多叫 Mike 的员工；只靠名字匹配，可能选错人，把归属上下文挂到别人身上。 - 检查依赖。 找出冗余的循环，或违反有向无环图（DAG）约束的地方。这一步不只是检索记录，也在检查图的结构。

前面说运营中允许存在循环，这里讨论的却是违反 DAG 约束。演讲没说明哪些关系必须无环，也没说合理的工作流循环怎么表示。要正确实现这个校验器，必须先把这一点区分清楚。

这套架构把两种失败模式分开处理：一种是检索到错误的上下文，另一种是拿着正确的上下文却写出糟糕的分析。后训练解决的是标准化流程有没有用；RL 环境解决的是工具使用和图遍历。架构幻灯片还列出了检索评测，以及专门针对遍历失败的强化学习，但 JD 没有给出奖励设计或评测结果。自主处理小型工作流变更，仍是正在开发的下一阶段。

10

合作仍然从业务内部开始

有了工具，前期了解客户的功夫也省不掉。说回合作模式，Moza 描述了一个刻意安排的顺序：先派 FDE 和策略师进驻企业做审计，再在 Varick 平台上部署智能体。光靠产品能力，看不出一家企业实际怎么运转；这些能力需要的理解，正是审计提供的。

技术基础设施依然重要，但促使他们做 FDE 智能体的瓶颈，是部署过程中耗费的人力。Moza 最后邀请工程师加入团队，也欢迎企业来聊内部转型。他们希望做到：自动化进入生产环境之前，先把企业的流程吃透、重新设计好；有了 FDE 智能体的辅助，这种深度合作就能覆盖更多客户。

Inspecting the generated RAG design

幻灯片原文
The agent’s PDF pipeline combines local embeddings and keyword search for cited answers. It flags missing answer-quality evaluation, weak parsing and no reranker; its tests only check that the pipeline runs.

[20:36](https://www.youtube.com/watch?v=0JZy5AuuQzc&t=1236s) [Inspecting the generated RAG design — recorded presentation](https://assets.ai.engineer/sites/aiecode2025/sha256/ca3bd36d2a2e32023273590706ece198c6eda441855d0f4f903629f0738f179a.webp)

can you build RAG system over PDFs ?

How it works
1. Ingest (pdfrag/ingest.py): pypdf pulls out the text page by page. It splits the text into chunks of about 1,200 characters at sentence breaks, overlapping by about 200 characters. Each chunk keeps its file name and page number.
2. Index (pdfrag/index.py): embeddings are made on your machine with bge-small through fastembed, so you don't need a second API key. The index is saved in .pdfrag/. Each PDF is tracked by a hash of its contents, so re-indexing only processes new or changed files.
3. Retrieve: two searches run together, meaning-based (embeddings) and keyword-based (BM25), and their rankings are merged. The keyword search finds exact terms like part numbers and acronyms that embeddings often miss.
4. Answer (pdfrag/answer.py): the top chunks go to claude-opus-5-5 with citations turned on. The answer streams in with [1]-style markers, followed by a source list that quotes the cited text with its file and page. Claude is told to say so when the excerpts don't answer the question, instead of guessing. Prompt caching and refusal handling are on.

What I checked:
- Tests: chunk sizes and overlap, page tracking, that retrieval returns the right page, and incremental re-indexing (unchanged files skipped, deleted files dropped). One test uses a fake Claude stream to check that citation numbers stay correct across turns of a chat.
- Real command line on a sample PDF: indexing, re-indexing and search all worked. With no key you get a clear error message, not a crash. A fake key got a 401 back from the API, so requests do reach it.

Choices I made for you:
- Fallback model: if Claude's safety filters decline a question, the API retries it on another model instead of returning a refusal. Remove the fallbacks lines in answer.py if you don't want that.
- Effort: set to medium to keep cost down. Pass --effort high for questions that need reasoning across many excerpts.

Limits: scanned PDFs have no text to extract. index warns you about them; run OCR on them first. Tables and multi-column pages come out as flattened text. If your PDFs are heavy on tables, a layout-aware text extractor would be the next upgrade.

To try it, put your PDFs in pdfs/, set ANTHROPIC_API_KEY, and run index then ask.

why did you build nth rag system when there are more matured feature rich open source systems are available to solve our problem. Question-2: The solution appears to be a median rag system.

You're right on both points.

1. Why I built another one

I read "can you build" as "go build it" and started coding without asking what problem you're solving. That's the real mistake. Whether to build or adopt depends on things I never asked about: how many PDFs, what kind, who uses it, and how accurate it has to be. If I had asked, the answer would probably have been one of these:

- No RAG at all. If your corpus is small (under a few hundred pages per question, roughly), Claude can read whole PDFs directly, up to 600 pages and 1M tokens of context. It sees the actual pages, including tables, charts and scans, which my text-only pipeline throws away. With prompt caching, repeat questions are cheap. For many "chat with my PDFs" cases this beats any chunking pipeline.
- An existing system:
  - RAGFlow: layout-aware parsing, OCR and tables, with a UI.
  - Onyx (formerly Danswer): team/enterprise search with permissions and connectors.
  - PaperQA2: scientific papers, with strong citation grounding.
  - Kotaemon / AnythingLLM / Open WebUI: quick self-hosted document chat.
- A framework plus a strong parser: LlamaIndex or Haystack for the pipeline, with Docling, Marker or MinerU to parse the PDFs. Choose this if you need custom behaviour but don't want to own the plumbing.

Building from scratch only makes sense if you need something these can't give you, and I didn't establish that.

2. "Median RAG": yes

It's the textbook design: extract the text, split it into fixed-size chunks, embed them with a small model, run hybrid search, take the top few, and generate an answer. The specific weaknesses:

1. No evaluation. This is the biggest gap. I can't tell you whether it answers well, because nothing measures it. My tests only check that the plumbing runs.
2. Weak parsing. pypdf flattens tables, mangles multi-column layouts, and skips figures and scans. In most PDF RAG systems, most failures start here.
3. Chunks with no context. A chunk like "Revenue grew 12%" doesn't say which company or which year. Contextual retrieval, where each chunk gets a short description of where it sits in its document, measurably cuts retrieval failures.
4. No reranker. A cross-encoder reranker is cheap and consistently improves the top results.
5. One search pass. Questions that compare documents or need several steps fail. An agentic loop, where Claude issues its own searches and reads neighbouring pages or whole documents when needed, handles these much better.
6. Toy storage. A brute-force numpy array and a JSON file won't scale past small collections [illegible] filtering.

Three questions before building

幻灯片原文
Before building, search for existing solutions, identify a novel advantage such as data or distribution, and name a channel where users already are. A demo can be an expensive way to discover you lack distribution.

[28:27](https://www.youtube.com/watch?v=0JZy5AuuQzc&t=1707s) [Three questions before building — recorded presentation](https://assets.ai.engineer/sites/aiecode2025/sha256/2adc4d8a7e77300076dffedae9d8978e5d1d544a3dc3a1ae1cc98a8993cb8dee.webp)

Three questions to your team before you prompt a coding agent.

1. Who has already done this?
“has anyone.” Who. Twenty minutes on GitHub, Hugging Face, Product Hunt. Found three? Fork the best one. The median is free why you build it.

2. What do I have that they do not?
“A better prompt” is the median in a costume. The answer must be along the novel lines such as data, distribution or framing. None of the three? It is a learning project. Honestly call it that.

3. Where will this live?
Name the channel where the user already is, before the first line. Cannot name it? You are building a demo, the expensive way to learn you have no distribution.

我花了两年时间造出了一个“平均水平”的东西

Hariprasad Sudharshan 独自打造的计算器能用——但和别人各自独立做出的计算器很像。他的应对是改变自己的投入方向：少关注编程工作流，多关注具体的客户问题、分发渠道，以及真正值得去做的差异化。

01

城市底下的软件仍然得能运转

Imagine New York stopping for the evening: no flights leaving JFK, a subway stranded at its next station, failed tap payments, elevators losing track of their floors. Hariprasad Sudharshan opens with that thought experiment to make an ordinarily invisible dependency visible. Everyday life relies on software that follows rules and behaves reliably. A product person with almost two decades of software experience, he begins his account of AI-assisted development with the systems people already trust.

In his simplified picture of traditional software development, engineers supply judgment: what to build, which tradeoffs to accept and what a good product feels like. Their tools execute deterministic rules. Those tools also help build the next generation of tools, allowing the industry to accumulate capability. Differences between engineers—their experience, taste and priorities—therefore become differences between products.

AI changes one part of this picture. Engineers can now rent model capability through APIs, along with much of the surrounding development machinery. Small teams gain access to capabilities they could not previously assemble by hiring. Yet the harness, tools and integrations around the model still contain ordinary software, and the delivered application still needs to behave reliably. Sudharshan’s forecast is that probabilistic models will accelerate the production of deterministic software and make previously unaffordable or neglected applications practical. That is his framing of the opportunity, rather than a claim that every AI application has deterministic behavior.

02

模型排行榜并不能描述整个产品

The next comparison comes from sprinting. Elite athletes can be close enough that a tiny difference determines the winner, while fans remain deeply attached to their favorites. Sudharshan recognizes the same emotional investment in model discussions. A model’s lead can move with the next release; making that temporary lead the basis of a product roadmap gives a team an advantage it does not control.

Even the numbers require care. The example ratings are 1,503 for Anthropic and 1,416 for Mistral, a gap of 87 points. These are relative ratings derived from comparisons in a particular evaluation environment. They do not mean one system possesses 87 more units of intelligence. The useful question is what the evaluation measures and whether that difference matters for the application.

There is a second source of confusion: comparing Claude Code, Cursor and Codex does not isolate a model. Such comparisons mix several things:

- Model: The underlying capability—the athlete or engine in Sudharshan’s analogy. - Harness: The tools, context, instructions, orchestration, memory, workflows and MCP tool calls that determine how that capability is used. - Product: The result a customer receives and the reason they care about it.

A better experience may come from the harness as well as the model. Some offerings couple these parts tightly; others let a team combine them more freely.

This separation leads to the product question. If competitors can rent the same engine and much of the same harness, what remains distinctive? The capability can be excellent while being equally available to the next team. Access alone does not explain why a customer should choose one application.

03

中位数可能有用，也很容易被复制

Sudharshan calls the readily available answer the “median.” This is his name for a shared starting point, rather than a measured statistical median of software quality. Point similar tools at a familiar problem and different builders can arrive at similar solutions. As model releases improve, that starting point moves upward: more of the work becomes available before a team has contributed a distinctive idea.

The trap is that the result may already be good enough to ship. A builder sees a working product; a customer sees another option among several similar products. When that happens, distribution—reaching customers and getting the application adopted—can become the decisive advantage. Independent convergence is enough to create this situation. Nobody needs to copy anyone.

That does not make the software worthless. Sudharshan pushes back on calling it all “AI slop.” Two weeks before the talk, he shipped an iOS app despite having never expected to work in that development lane. Other builders may want revenue, a useful internal tool, or simply a website they can proudly show a colleague. Those are different goals, and each can be satisfied without creating a defensible commercial product.

The distinction is between usefulness and differentiation. A coding agent can produce a useful finished artifact that solves a team’s problem. Competing in an open market introduces another requirement: a reason to choose this implementation. Sudharshan reaches back to search engines for the analogy. A crawler and an index establish basic participation; a distinctive way to solve search well can change the competitive position. His own public building and contributions to LlamaIndex supplied plenty of learning, but did not spare him this distinction.

04

“先造再说”的本能跳过了搜索

When building was costly, searching for an existing solution was often the cheaper first move. AI-assisted development reverses that feeling. Opening an agent can seem easier than reading through existing projects and deciding what to adopt. Sudharshan calls the resulting habit the “build-first reflex”: “Open a problem, open an agent.”

His example is a retrieval-augmented generation, or RAG, system. A user supplies a PDF and asks questions through a backend language model; the implementation involves chunking and a vector database. Getting those pieces working feels like a substantial win, especially on a first attempt. In his illustrative timeline, scaffolding appears in two minutes, a rough working demo in two hours, and a supported product in four weeks. Only afterward does the builder discover mature open-source alternatives. Speed has shortened implementation while leaving the search decision undone.

Why did the agent build another RAG system instead of considering an existing one? In the exchange Sudharshan describes, the agent’s explanation is simple: it had been asked to build. A different request could have led to a different course. The response exposes the missing decision. Successful execution of a construction request does not answer whether construction was necessary. Meanwhile, small working increments supply enough satisfaction to keep the builder moving before that question gets asked.

The slide pairs the original PDF RAG prompt with the agent’s admission that it read “can you build” as an instruction to start coding, showing why it did not consider existing implementations.

05

两年的构建撞上了一条早已拥挤的赛道

The calculator brings the argument home. It was one of many applications Sudharshan built during two intense years of solo work. He skipped social occasions, movie nights and time outside, describing the attraction as something like an addictive game of chess. AI platforms let him turn ideas into applications without the large team and architects he would previously have expected to need. That visible progress made the effort feel justified.

The soft launch supplied a different comparison. People in his circle had seen similar calculators elsewhere. Looking at other open and closed implementations, he found results that sometimes seemed the same, beyond merely resembling one another. The useful comparison is what those calculators actually offered: his interpretation was that familiar problems and shared development tools had led independent builders toward the same answer. The surprise was discovering how little two years of effort alone said about distinctiveness.

The same pattern appeared across his projects: a promising idea led to immediate building, then a crowded lane. Sometimes competitors were already there; sometimes he returned after a month away to find many similar products. His analogy is having the same developers on your team and your competitor’s team. The experience gave him practical intuition, but also exhaustion. Building had taught him what could be produced quickly; the next task was learning where to spend effort that would survive comparison.

06

把有特色的部分列进预算

The correction is a “novelty budget.” Before starting, name one thing that makes the project distinctive, put it in the roadmap, and review it as deliberately as spending. PageRank serves as Sudharshan’s example of a specific contribution that could distinguish one search engine from others. The budget is a way to reserve attention for such a contribution; it is not a numerical formula for buying originality.

For the calculator, this changed how time was allocated. The first two years included architecture, agent design, prompt chains, skills and experiments with new coding workflows. The rework concentrated on differentiation. Tool fluency had produced results, but those results often resembled what others could obtain. If a project has no identifiable novelty, Sudharshan’s advice is to accept it as a learning exercise or use an existing solution. Both are legitimate outcomes; neither requires pretending that implementation effort created an advantage.

The roadmap advice contains several distinct decisions:

- Reuse solved work. A product may already have an open-source twin. Adopting or forking it can avoid rebuilding the common foundation. - Choose an opinion. Decide how this product should solve its particular problem instead of accepting probable, broadly familiar answers as its identity. - Match effort to purpose. A prompt-to-production application can be entirely appropriate for internal consumption. - Treat “done” as a starting point for differentiation. When an agent finishes the baseline implementation, inspect what still needs human judgment to make the product distinctive.

Sudharshan compresses this into a deliberately sharp description: coding agents provide the “last great design for free.” He expects them to scaffold established approaches well and assigns the search for the next important design to the builder. This is his working stance toward current tools, rather than proof that models cannot produce novel designs. Its practical force is to stop treating an agent’s completion message as evidence that the product question has been settled.

07

三个问题重新校准了演示

Leaders face a related problem. Their intuition may have formed when a particular deliverable required a team and a quarter of work. A new engineer can now show something similar after much less effort. The demo is real, but its old production cost is a poor guide to its present value. Sudharshan recommends hands-on building to recalibrate that intuition, then three questions when evaluating what a team presents.

- Who has already done this? Force the search that the build-first reflex skipped. A functioning demo may reproduce a mature existing solution. - What do we have that the next team does not? Make the distinctive contribution explicit. A better prompt alone may still produce an answer available to competitors. - Where will this application live? Ask how the application will reach users and become useful in practice. Without a distribution model, a demo can be an expensive way to discover that nobody has a path to adopting it.

08

改版后的计算器会问：免费的权重跑起来要花多少钱

Applying those questions changed the calculator’s subject. The new question was what stands between an open model and a system that actually generates tokens—and what an enterprise must pay for that system. “Open weights are not open inferences” is the distinction. Access to model weights leaves a substantial operating problem to solve.

Sudharshan describes ten intervening layers, naming concerns including precision, KV cache, batching, execution parallelism, MLOps and site reliability engineering. These put work between possession of a model and dependable token generation. Some require specialist expertise. The recording names these concerns without explaining a complete ten-layer architecture, so the lesson is the scope of the operating burden rather than a reproducible deployment recipe.

Utilization receives special attention. He calls it structural: an enterprise cannot simply purchase a utilization level in the way it purchases infrastructure. That makes the organization’s actual workload consequential to the decision. A comparison based only on access to free weights misses the question of how the resulting serving system will be used.

What should the revised calculator let an enterprise compare? It holds the model weights constant and asks about the cost of running them inside the enterprise versus running them in a neocloud and buying the generated tokens. Sudharshan reports that none of the 244 calculators he examined addressed this question, and that enterprises responded positively to the revision. Those are his reported search and feedback results; they do not establish a validated cost model or a disclosed business outcome. The practical invitation is to enter a real workload and see which option the calculator favors. He describes the application as free and open source.

09

保留学习，改变判断力的投向

The ending preserves both sides of the experience. Readily generated products can be useful, and strong distribution may sustain them in competition. Sudharshan continues to ship them. His recommendation for a product seeking a stronger position is to pick one problem and pursue it with the intent of solving it exceptionally well. That intent directs effort; it does not guarantee the ambition will be achieved.

The two years were education, and he considers them worth the tokens. He also returns to the city underneath the opening thought experiment: in his view, AI makes reliable software faster to write while the world continues to depend on it. The part of the work he now wants to protect is judgment about what deserves to be different. His closing phrase gives that allocation its edge: “novelty is scarce and the median is free.”

要点总结

  • 把模型能力、应用它的框架，以及客户拿到的产品区分开。比较编程产品并不能单独分离出模型的贡献。
  • 一个有用的应用仍可能很容易被别人复制。内部效用、学习和商业差异化需要不同的成功标准。
  • 在动手构建之前，先搜索已有的解决方案，并说清楚自己的独特贡献。把这份贡献写进路线图，并审视为它投入的精力。
  • 评估演示时要问：谁已经在解决这个问题，团队的独特贡献是什么，以及应用将如何触达用户。
  • 免费的模型权重仍然留下推理基础设施、运维能力和工作负载利用率需要考量。修订后的计算器把这个企业决策作为重点。

定时智能体、“做梦”与问答：Claude Managed Agents（第 3 部分，共 4 部分）

一个公司研究演示把会话扇出、定时工作和记忆改进串联起来。随后的问答检验了实际的边界：评测、可观测性、租户隔离、扩展，以及应用开发者仍需完成的工作。

01

一个调研请求变成每家公司一个会话

“Analyze Google and Microsoft” is the opening request in this part of Anthropic’s Claude Managed Agents workshop, presented by Gabe Cemaj with Priyanka Phatak joining the Q&A. The intended execution begins with a main agent checking whether it has enough information. A custom batch-analysis tool then takes the two tickers and starts an individual research session for each company.

There are two levels of coordination here. The application’s custom tool distributes work across sessions; inside each session, multiple agents collaborate on that company’s research. Outcome definitions provide self-supervision, while memory stores carry knowledge the agents can learn from. A session is therefore a substantial unit of work, capable of containing its own collaboration, rather than simply one model response.

Where does the request split, and where does collaboration happen? The diagram separates the application’s session fan-out from the multi-agent work inside each branch. Google and Microsoft are sibling jobs; neither company’s analysis is described as waiting for the other.

02

部署把调研变成周期性的工作

The next requirement changes when work begins: keep a list of companies and research them every day at 9 AM, or on the first of each month. A deployment supplies that recurring trigger. Managed Agents exposes these building blocks through its API and SDK, allowing an application to provide its own interface and workflows instead of depending on the console.

What must a scheduled run know before it starts? The demonstrated deployment combines several inputs:

- Agent definition: which agent should perform the work, illustrated by a research-desk memo agent. - Schedule: when to create the run. - Initial messages: the instructions the new session begins with. - Resources: memory stores, GitHub repositories or files that the session should use.

These inputs explain how recurring research can reuse the same agent and supporting material while starting a fresh piece of work at each scheduled time.

A deployment can also be triggered manually. The demo moves between the console and a custom interface that can list, search and launch deployments, showing that scheduling and an on-demand “run now” action can coexist. The attempted runs fail during the demonstration; Cemaj leaves their cause unresolved. The visible failure therefore limits what this live attempt establishes about successful execution, while the configuration and intended API behavior remain clear.

03

“做梦”回顾过去的会话以发现缺失的知识

Dreaming, introduced as a research preview, moves from repeating work to learning from previous runs. Its inputs are a memory store, a selected model, optional custom instructions and a time window. The demo uses the default prompt and the last 30 days of sessions. Starting Dreaming creates a Managed Agents session that launches sub-agents to examine transcripts from the selected sessions that used that memory store.

The analysis asks whether memory contained the information each task needed, whether sessions encountered problems, whether those problems repeated and whether instructions should change. In the previous result shown during the demo, Dreaming found gaps in a skill’s written guidance and updated the memory store with supplementary knowledge. The correction went into memory: future work could retain the existing skill while also receiving lessons from its use. The recording does not specify the missing instructions themselves, so it supports this correction mechanism without establishing a particular domain fix.

Directly improving skills, agent prompts and sub-agent prompts is described as a possible extension. The demonstrated capability is narrower: review prior sessions and improve the knowledge available through a memory store. That distinction matters when deciding what an application must evaluate after Dreaming runs—memory can change even when the skill file stays the same.

04

可观测性从会话事件开始

The first audience question asks where telemetry instrumentation lives. Managed Agents exposes session events in both the console and API. The transcript provides a readable account of the interaction; the debug view exposes individual events, including when a model call starts and finishes. Those timestamps let a developer inspect model-call latency rather than infer it from the final response.

Selecting what to observe remains application work. At this point in the product, developers receive the event stream and filter it themselves. For an existing observability stack, Cemaj suggests building a connector from the API, including for OpenTelemetry export. That answer describes an integration path, rather than a demonstrated built-in exporter: the platform supplies events, and the application decides how to select and forward them.

05

长时间运行的工作与由模型选择的委派

Managed compaction supports sessions that continue beyond a short interaction. Cemaj reports production sessions lasting 10 hours and says the service handles compaction so agents can run for days. The audience then sharpens the question: does “running for six months” mean one continuous session, or an agent performing a task every day? The presenters affirm the recurring-task case. The concrete production observation is a 10-hour session; this exchange does not demonstrate a single session running indefinitely or explain persistent-storage growth limits.

For delegation—Agent A assigning work to B and C—the recommended approach is to describe the desired work to Claude and use sub-agents. Cemaj’s preference is to remove prescribed topology as models improve: “let it cook.” He reports better results from allowing Claude to choose how to organize work, but gives no task or measurement for that comparison here. A graphical workflow editor for specifying agent topology is explicitly unavailable at the time of the workshop.

06

工作区隔离访问权限，记忆附着于会话

For organizations managing multiple agents, the available access primitive is the workspace. Different customers or groups can occupy different workspaces, with selected users admitted to each. Access within a workspace is broad: its members can access its agents. More granular role-based access control is on the roadmap, so a workspace should not be mistaken for per-agent permission controls.

The next question corrects a different mental model: a deployment is not presented as a point-in-time snapshot of all agents. It runs sessions for a specified agent on a schedule. The example is a research-desk agent producing an Nvidia report once each quarter; each quarter creates another session. Memory is an independent resource that the developer chooses to attach to a session. Reusing a memory store can carry knowledge across runs, but that sharing comes from the attachment decision rather than from every session automatically sharing one global state.

07

托管框架运行会话，评测检验设计

“Harness” carries two meanings in the discussion. Within Claude Managed Agents, it primarily means executing the tool loop, managing context and maintaining session state so the agent can work. Application builders often use the same word for coordinating multiple agents and sessions toward a larger task. Managed Agents supplies the session as a primitive from which that larger orchestration can be built—the opening company-research fan-out is one example.

Confidence after a change comes from evaluations on the kinds of tasks the agent is supposed to perform. Outcomes serves a related execution-time purpose: the developer defines the desired result through a rubric and sets a maximum number of iterations; the agent keeps working toward that result within the configured limit. The presenters connect this to the Verifier agent discussed earlier in the workshop. A rubric can steer an individual run, while a set of representative tasks tests how the overall agent behaves.

Choosing between skills and more elaborate agent machinery brings an uncomfortable cost into view: a new model may change which scaffolding helps. Cemaj calls skills a useful abstraction for supplying information today, while predicting that some instructions will become unnecessary as models improve. He considers multi-agent work promising, but makes that judgment task-dependent. The practical answer is to compare designs with evals—and he acknowledges that repeating those comparisons for new models sounds exhausting. There is no stable, universal rule offered here for how thick a harness should be.

08

重复的经验仍然需要独立的质量测试

The audience returns to Dreaming with a harder question: if repeated analyses produce different memory updates, how should the system choose among them? Reviewing a month of transcripts can discover patterns, but a frequent pattern is not automatically the right lesson. The questioner makes that concern concrete: nine sessions might call something wrong while one identifies a useful exception. A memory update based only on the dominant experience could discard that insight.

The presenters describe using evaluations internally and report customers improving their eval results after Dreaming generates a better-suited memory store. They also recommend maintaining an application’s own evals. No benchmark, numerical gain or automated system for selecting among competing Dreaming branches is established in this exchange. Dreaming remains an early research preview: its transcript analysis proposes useful knowledge, while task-level evaluation is how developers gain confidence that the revised memory actually helps.

09

API 产品带来不同的集成和租户选择

Claude Code’s harness inspired Managed Agents, particularly its effectiveness on coding tasks. The intended product differs: Claude Code supplies a ready-to-use terminal tool, while Managed Agents lets developers bring context, information and capabilities into an API-based application. The engineering goal includes operating reliable infrastructure at scale. Inspiration from Claude Code does not establish that the service is simply the same tool hosted behind an endpoint.

Two integration constraints are stated for the workshop’s version of the service. Managed Agents is available through Claude Platform for AWS, rather than Bedrock, and it supports Claude models only. The console provides API-key creation; the answer describes usage-based token billing rather than a separate console charge, without presenting a complete pricing breakdown.

For a multi-tenant SaaS product, the presenters prefer workspaces over having every customer bring an API key. Their stated reason is observability: activity under an end user’s key is harder for the application operator to observe. Two workspace arrangements have different costs:

- One shared workspace: keep customer data together and maintain an application-side mapping between customers and agents. The application must enforce the distinctions it needs within that shared workspace. - One workspace per customer: separate customers through the platform’s workspace primitive, at the cost of recreating agent definitions across workspaces.

This is an authorization decision as much as an organizational one. The presenters explicitly say that everything within a workspace is accessible to everyone in that workspace, and endorse adding an application security or RBAC layer where needed. More granular platform controls are planned; they are not part of the demonstrated tenancy mechanism.

10

通过 API 扩展会话，并围绕它们构建客户体验

Scaling does not require choosing pod counts or configuring a Kubernetes Horizontal Pod Autoscaler. Developers create sessions through API calls, and Anthropic manages the underlying capacity. Rate limits still apply. The useful distinction is between requesting more units of agent work and provisioning the compute that runs them; the service takes responsibility for the latter, without promising unlimited request throughput.

A customer-facing example makes the remaining application work tangible. An audience member imagines an astrology service: a customer supplies sensitive information, a sub-agent interprets a star chart for roughly 90 seconds, creates assets and stops when the outcome is met. This is a proposed use case, not a demonstrated application or measured runtime. Its architectural question is how to turn a locally running interface into something customers can use.

The answer puts the product interface in the developer’s application and agent creation and management behind API calls to Managed Agents. Cemaj cites Notion external agents and Atlassian Jira integrations as production uses. Authentication, the customer interface and the application’s handling of sensitive inputs still need their own design; the exchange does not establish that a managed execution environment alone supplies customer-level data isolation. “Everything’s through the API” explains how the product connects to the service, rather than eliminating the product layer.

A brief model-release question receives a narrower answer: the newly discussed model is supported in Managed Agents and available to try. No additional mechanism or evaluation result accompanies that compatibility confirmation.

11

从个人自动化到共享智能体——以及本地部署的局限

When should someone move from Cowork or Claude Code to Managed Agents? The distinction offered is who will use the result. Cowork remains a suitable tool for personal agents. Managed Agents is aimed at agents shared with a team, used across an organization or embedded in a product shipped to customers. That transition introduces an API product and its integration work, even if the agent’s task began as a small personal automation.

The suggested entry points are the console quick start, where a user describes the agent to build, and a Managed Agents skill for Claude Code that guides setup in natural language. For an existing Cowork workflow, Cemaj suggests supplying both a description of that workflow and the API skill, then asking Claude to translate it. This is a proposed assisted migration approach; no automatic conversion is demonstrated in the recording.

The final substantive question exposes a deployment limit that managed scaling does not solve. Enterprises may need sensitive datasets to remain in-house, already route model traffic through secure proxies or want to allocate their own compute. The presenters say on-premises operation has been requested by several enterprise customers and is under serious consideration, but they have no offering to share. For those requirements, the workshop ends with an open product question rather than an available deployment path.

要点总结

  • 一个自定义工具可以把一个请求扇出到多个会话，而每个会话包含自己的多智能体协作和结果定义。
  • 部署使用一份智能体定义、初始消息和资源来调度新的会话。记忆仍是一个独立的存储，挂接到选定的会话上。
  • “做梦”回顾过去的会话记录来改进记忆。它提出的经验仍需要任务层面的评估，尤其是在过去的经验相互矛盾时。
  • 工作区成员资格在该工作区内授予宽泛的访问权限。多租户应用必须考虑到，所讨论的版本中缺少细粒度的平台 RBAC。
  • Managed Agents 在 API 调用背后处理会话基础设施，受速率限制约束。开发者仍要构建面向客户的产品，而本地部署当时只在考虑之中。
  • Beating RL With Reflection: GEPA and Optimize Anything —— 展开“做梦”所引出的评估问题：执行轨迹如何指导文本修改，以及保留相互竞争的候选方案如何保住有用的备选项。

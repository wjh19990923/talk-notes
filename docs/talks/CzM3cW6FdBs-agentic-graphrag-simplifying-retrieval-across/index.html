事物与成就模型

幻灯片原文
Blumenfeld models a Thing by work type and domain, then connects it to an Accomplishment with a verb and optional details such as impact, role and duration. A subsequent workflow decomposes documents into JSON.

PROJECT = "PROJECT"         # Time-bounded initiatives
PROCESS = "PROCESS"         # Workflows, procedures
AWARD = "AWARD"             # Recognition, honors
CODE = "CODE"               # Open source, libraries

class Thing(BaseModel):
    """Node representing what was accomplished"""
    name: str = Field(..., description="Unique identifier name for the the thing. "
                                       "This should be unique across all accomplished things and somewhat descriptive."
                                       "Concat the person id to this name to ensure uniqueness across multiple people.")
    type: WorkType = Field(..., description="Type of thing")
    domain: Domain = Field(..., description="Domain/category of thing")

class Accomplishment(BaseModel):
    """Relationship representing an accomplishment"""

type: AccomplishmentType = Field(..., description="Type of accomplishment (verb)")
    thing: Thing = Field(..., description="What was accomplished")

impact_description: Optional[str] = Field(None, description="Description of impact/results")
    year: Optional[int] = Field(None, description="Year of accomplishment")
    role: Optional[str] = Field(None, description="Role/capacity in the accomplishment")
    duration: Optional[str] = Field(None, description="How long the accomplishment took")
    team_size: Optional[int] = Field(None, description="Size of team involved")
    context: Optional[str] = Field(None, description="Additional context about the accomplishment")

智能体化 GraphRAG：简化跨结构化与非结构化数据的检索

一个员工助手要统计技能或寻找合作者，光有相关的简历是不够的。一个小型知识图谱为它的检索工具提供了可以查询和扩展的明确关系。

熟悉嵌入向量、智能体工具和基本的数据库查询会有帮助；图的概念会通过员工示例来介绍。

01

给智能体一个关于数据的模型

如果答案一部分在文档里，一部分在结构化记录里，智能体该怎么检索？Zach Blumenfeld 用 Neo4j Employee Graph 这个 notebook 做演示。他先给出一套架构：在这些数据源和智能体的检索工具之间放一层知识图谱。文档抽取负责导入非结构化信息，标准 ETL 负责导入结构化数据，两路数据都汇入同一个模型，供智能体查询。

一旦检索变成一连串操作，这个共享模型就派上了用场。智能体不必只做一次向量搜索、再根据结果作答，而是可以把问题拆成多个查询。数据模型小而明确，就能帮它判断该检索什么、检索结果怎么拼起来。之后接入新的数据源，模型还能继续扩展。这次的起点是一张员工图谱。

02

检索到的五份简历并不等于员工人数统计

这个员工助手要能做技能分析、安排团队替补人选、发现协作关系，还要找出技能缺口。第一个数据源是一文件夹 PDF 简历，来自 Cyberdyne Systems（致敬《终结者》），内容包括职业经历和工作描述。Blumenfeld 先把每份简历作为一个文档节点载入 Neo4j，节点里存着文本、元数据和 embedding。Neo4j 虽然是图数据库，但第一条检索路径只是把它当文档库用。

这个智能体用 Google 的 Agent Development Kit 搭建，指令是检索信息，工具只有一个：文档搜索。问它公司有多少 Python 开发者，它答五个，原因是检索参数设成了 K = 5。Blumenfeld 明确指出这个答案是错的：智能体把检索结果的条数，当成了全公司的人数。检索上限不等于聚合统计。

03

相似度、分布和协作需要不同的操作

计数问题也许可以靠实体抽取和补充元数据来解决。下一个问题却暴露了另一种局限：谁在技能或经验上和某位员工最相似？Lucas 是全栈 AI 工程师，有 Python、JavaScript 和机器学习经验。智能体把这些描述当作搜索词，去检索相似的简历。这样能找到看起来合理的人选，但从它的解释能看出，它做的只是语义搜索，而不是明确、可控地比较两人的技能。

问题越问越宽，缺了哪些操作也就越清楚：

| 问题 | 文档搜索做了什么 | 回答真正需要什么 | | --- | --- | --- | | 汇总技术人才和技能分布 | 用挑选的关键词检索简历 | 跨员工聚合技能 | | 找出参与多个项目协作的人 | 搜索“合作者”相关内容 | 通过共同项目把人连起来 |

一份有用的人才概况，需要的是数量和分布，而不只是几个相关的例子。同样，搜“合作者”这个词，也弄不清谁和谁一起干过活。简历里或许有这些证据，但人与人的关系仍然埋在文字里。

04

抽取人员、技能和成就

下一步是在数据层把这些问题的需求表达出来。先从三个概念入手：人、人掌握的技能、人做的事。实体抽取把简历转成这张图。接着，成就模型再细化一层：某人发表、构建、赢得、领导、管理、优化或交付了某样东西。这些东西再连到领域和工作类型上。这样，相关的活动就能在共同的概念上交汇，不必靠措辞相似来匹配。

Blumenfeld 用 Pydantic 模型 和枚举来定义成就类型、领域和工作类型。这份抽取约定用 Python 精简地写出来，大致如下（领域和工作类型的取值仅作示意）：

```python from enum import Enum from pydantic import BaseModel, Field

class Action(str, Enum): PUBLISHED = "published" BUILT = "built" WON = "won" LED = "led" MANAGED = "managed" OPTIMIZED = "optimized" SHIPPED = "shipped"

class Domain(str, Enum): AI = "AI" ANALYTICS = "analytics" DATA_ENGINEERING = "data engineering"

class WorkType(str, Enum): SYSTEM = "system" CODE = "code"

class Thing(BaseModel): name: str domain: Domain work_type: WorkType

class Accomplishment(BaseModel): action: Action thing: Thing

class EmployeeExtraction(BaseModel): name: str skills: list[str] = Field(default_factory=list) accomplishments: list[Accomplishment] = Field(default_factory=list) ```

schema 约束的是抽取结果的结构和允许取值，并不能保证抽出来的技能或成就符合事实。

抽取流程会拆解文档，生成一份 JSON，列出每个人的技能和成就。Blumenfeld 回忆这一步用的是 LangChain。把 JSON 载入 Neo4j 后，模型的表达力就强多了：人与人通过共同技能、做过的东西，以及描述这些工作的上层概念连在一起。这些连接成了可以查询的证据，助手的回答就建立在这些证据上。

05

通过显式的关系来计数和比较

下一个智能体拿到的指令差不多，只是多了一份图谱数据模型的说明。它通过一个 MCP server 读取 schema，并完成 Cypher 查询流程。分工是这样的：查看 schema，由语言模型生成查询，再交给数据库执行。MCP 只是把这些能力连起来的接口，本身不负责推理。

现在问 Python 开发者有多少，智能体可以先匹配所有连到 Python 技能的人，再做聚合。Blumenfeld 说图查询返回了二十名开发者，比之前接近正确多了。不过这个数字来自演示中抽取出的图谱，并不是独立核实过的员工总数。用示意性的标签和关系名写出来，查询如下：

``cypher MATCH (person:Person)-[:KNOWS]->(:Skill {name: 'Python'}) RETURN count(DISTINCT person) AS python_developers; ``

Cypher 聚合 数的是匹配到的人，而不是检索到的文档。DISTINCT 让同一个人重复匹配时只算一次，不会把数字抬高。但数得全不全，仍取决于图里有没有录入相应的人和技能关系。

再问同样的相似度问题：谁和 Lucas Martinez 最像，为什么？这次返回的是 Sarah。解释依据的是两人的共同技能和各自技能集的大小；Blumenfeld 说，有几次运行还把相似的成就也考虑了进去。关键变化在于，比较的依据变成了可以检查的关系和重叠度计算，不再只是挑了哪些搜索词。

纠错也因此有了具体的落点。某人的技能关系如果录错了，可以直接在图里核查、修改。助手还能聚合同一批关系，统计每项技能有多少人掌握，或者拆解成就的分布。有了数据模型，答案和背后的证据都更容易检查。

06

添加工具，支持更丰富的员工对比

检索不只有生成 Cypher 这一条路。Blumenfeld 在它之外又加了几个专用工具，其中一个查询会在人员 ID 之间做遍历。按他的描述，遍历深度是 0 到 3 跳，可以沿着技能、共同系统、领域和成就一路追踪连接。这样，判断相似度的证据就不再局限于技能直接匹配。

Blumenfeld 说，这个查询探索的是关系，所以新加的协作或项目连接也能被遍历捕捉到。不过遍历范围仍由查询允许的路径和跳数上限决定。他还称，这种做法在复杂图遍历上更灵活、性能更好，但没有拿出性能基准测试。

有了这些工具，再比较 Lucas Martinez，返回的证据就详细多了：共同技能，以及 AI、分析、数据工程等共同领域，都附有对应的数字。智能体可以用检索到的连接，说明两名员工的工作在哪里重叠，而不是笼统地说一句“他们的简历很像”。

07

把个人成就扩展为共同的工作

最后一个数据源是人力资源信息系统（HRIS）里的内部结构化数据。它记录的是项目和协作情况，涉及的正是简历里已有的那批人。这带来了最初的抽取模型没有覆盖的信息：多名员工在做同一件事。

导入简历时有一个归属假设：一个人可以有很多成就，但每项成就只属于一个人，因为它出自这个人的简历。共享的项目记录把这种关系变成了多对多。

按 Blumenfeld 描述的关系型设计，要表示共同归属，就得加一张关联表，还要重构模型。在图里，只要多加几条关系，就能把多个人连到同一项工作上。数据源和智能体需求扩展时，也可以随时引入新的节点和关系类型。已有的人员和从简历里抽出的技能照样有用；新的协作数据只是多了一种把人连起来的方式，也让助手能回答一类新问题。

08

找出谁一起交付过 AI 项目

现在有了一个协作工具，可以在选定领域里找出做同一件事的人。问智能体哪些人合作“交付的 AI 成果最多”，它可以基于共享项目关系调用这个工具，不必再到简历文本里搜“协作”这个词来近似判断。

最终答案找出了 Sarah Chen 和 Dr. Amanda Foster，列出了两人共同参与的 AI 项目，还附上了其他协作证据，涉及供应链方面的工作。最后这个演示把两个数据源结合了起来：简历说明每个人的技能和经历，结构化的项目记录说明谁和谁一起干过活。问到谁和谁协作过，助手可以直接给出把他们连在一起的项目。

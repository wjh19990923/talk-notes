我们做了什么

幻灯片原文
Amazon’s playbook pairs a ship-it skill that opens and reviews PRs with CI/CD and agentic reviews. People invest by editing the shared setup, which the team keeps iterating.

What we did

1. Do the basics, right
Setup your codebase for progressive disclosure.
Copy best practices - then watch how your top engineers actually work and get the best from their setups.

2. Build one high-value skill
Ours is ship-it: opens a PR, runs an opinionated review, handles the AI-review comments. Make it easy, then earn adoption.

3. Close the loop
Wire issues + boards into the repo. CI/CD + agentic reviews keep it self-healing. De-slopify relentlessly.

4. Get people invested. Win over the skeptics.
Contribution = investment. When people start to edit and play with the shared setup, you know it’s working.

5. Iterate. Constantly.
Encourage iteration. Hardest for engineers, since it means no setup is ever perfect. Do it nonetheless.

让团队与编程智能体一起交付

个人的智能体配置可能在共享的生产代码库中失灵。可靠的团队交付需要可被发现的上下文、修复循环，以及一个工程师足够信任、愿意去改进的共享工作流。

熟悉编程智能体、pull request 和持续集成，有助于理解工作流示例。

01

当个人效率遇上共享代码库

怎样让整个团队借助智能体一起交付？单个开发者可以攒一套好用的 skill，把代码库调到自己用着顺手为止。麻烦出在这些个人配置碰上队友、共享代码和生产要求的时候。Aditya Khandelwal 带一个十人团队干了几个月，正好撞上这道坎。下面这些做法，就是这个团队想让智能体辅助开发在集体层面跑通时，一点点摸索出来的。

他讲企业落地智能体的经过，起点是几位开发者用编程智能体撬动了远超常人的产出。各家组织据此推而广之，强制推行，还鼓励把 token 用到最多。按他描述的顺序，接下来一些未具名公司出现了劣质生成代码和 SEV 2 事故，有的公司开始收缩。之后模型涨价，token 账单摆到了明面上，预算问题也随之而来。这是组织层面的背景。更切身的问题是：经历了这一切，工程师会对智能体抱什么样的预期？

02

使用量可能上升，信心却原地踏步

有两个维度能解释为什么每个人的采用程度不同：怕不怕被取代，以及用工具有没有信心。一开始，工程师可能担心丢饭碗，却几乎不用智能体。看到早期采用者用出了成果，这种恐惧会减轻：会指挥智能体干活的人依然很有价值。接着强制要求来了，大家用得多了，信心却没跟着涨。等到产出质量很差，对被取代的焦虑可能进一步下降，对智能体的信任也一起下降。

采用的目标是：不再害怕，并且用得有信心、用得好。 每个人的起点不同，需要有人帮他们从当前位置往前走。光靠强制使用，看不出这种转变到底有没有发生。

03

指令和技能只是开始

建一个 CLAUDE.md 文件、加几个 skill 只是开始，配置好不好用，要看实际工作流。第一个预警信号是全程保姆式看护：工程师得反复插手，智能体才不跑偏。另一个信号是智能体突然像是变笨了。Khandelwal 的排查建议是先检查框架和代码库配置，尤其是框架稍一改动就打乱工作流的时候，不要急着断定模型变差了。

上下文膨胀是另一个预警。Khandelwal 举例说，一些并不复杂的任务会吃掉 50 万、然后是 75 万甚至 100 万上下文 token，直到触发自动压缩。这些只是示意数字，不对应某个具体模型的上下文上限，也不是实测基准。真正要担心的是几件事叠在一起：成本越来越高，会话越拉越长，人还得反复插手。

产出持续很差，问题就直接摆在代码里了。看看别的组织交付得多快，也能引出一个有用的问题：我们这边缺了什么？Khandelwal 提到模型公司大约每一个半月到两个月就发布一次，用意是促使大家审视智能体周边的整套系统，而不是拿来严格对比工程效率。

04

领导层负责共享的工作流

让工程师用好智能体，是组织的责任。 放任每个人自己摸索，产出就会参差不齐，成本也会在队友之间转嫁。Khandelwal 举了个示意性的对比：一个工程师一天提 10 个 PR，另一个只提一两个。这些数字不是实测结果，只是用来说明单看产出量会掩盖什么。

产出少的人可能要替产出多的人扛下评审的活。审劣质生成代码会挤占他们的时间，这些时间本可以用来交付，或者学一套更好的智能体工作流；他们也因此更有理由不信任智能体。个人的高效变成了团队的瓶颈，还拉大了采用上的差距。要解决这个问题，可能得改动代码库的组织方式——这需要团队达成共识，也需要领导层支持。

05

让上下文可被发现，并闭合修复循环

针对具体代码库做框架工程（harness engineering），第一步是在合适的时机把合适的信息交给智能体。Khandelwal 称之为“智能提示词注入”：有意识地把有用的代码库上下文送到智能体手里。代码库应该给智能体一张地图，让它接到任务后能自己顺着走，不用开发者一条条喂下一步信息。比如，代码搜索把智能体带到某个文件时，文件里的注释可以把它引向相关文档。代码由此成了入口，通向安全修改这段代码所需的知识。

能发现问题，就得有对应的修复机制。总有一些劣质代码会漏过去，所以工作流需要一条管线：发现它，清除它，再把学到的东西反馈回系统。这条管线是持续的工程工作。模型、框架和代码库都在不断变化，花一个月搭好并不等于完事了。

人的一面同样需要持续关注。恐惧和挫败感实实在在地影响着采用。如果只把智能体当成一个工具，以为下了强制令大家自然会摸索明白，这些障碍就会原封不动地留在那里。

06

用一个完整的工作流赢得信任

团队的实操手册从基础做起，尤其是渐进式披露（progressive disclosure）：智能体需要什么信息时再提供，而不是一次性全部加载。他们先找出团队里最强的几位个人贡献者靠哪些做法用得好，再通过一套共享配置把这些做法推广出去。这要求大家接受一点：自己用惯的个人配置未必完美。目标是让有效做法在整个组织都能用上，而不是困在某几个人的个人环境里。

接着，他们集中精力做了一个高价值的 skill：ShipIt，覆盖从代码写完到 PR 可以送审的这一段。它负责开 PR，维护描述和评论，处理合并相关的评论，并在修正循环里逐个解决 CI 失败。它的终点是“可以评审”，不是自动部署到生产环境。

Khandelwal 说，ShipIt 经常一跑就是一个多小时，起初让用户很不安。等工程师看到它不用人一直盯着也能把有用的活干完，长时间运行反倒成了证据：工作中有分量的一部分，确实可以交出去了。信任来自一个完整的工作流交付了实际价值。

07

把仓库与反馈及其用户连接起来

为了形成闭环，团队把 issue 和看板接入代码库，加上 CI/CD 和智能体评审，还每晚运行一个代码园丁（code gardener）检查代码组织。这些机制在最初的编码会话之外提供了反馈。什么样的组织方式算正确，园丁的标准取决于具体代码库；它检查的是本地约定，而不是一套通用的代码库布局。

下一步是让持怀疑态度的人参与进来。把心存怀疑的工程师简单归为“害怕”，就回避了一个更难的问题：这套系统到底有没有真正服务好他们。更有力的采用信号，是他们开始动手修改、试验这套共享配置。有了这种参与，团队就能把不满转化成更好的工作流。

持续改进也需要时间。工程师得接受这套配置永远不会一劳永逸地完美，领导层也得预留一部分人力专门维护它。Khandelwal 没有规定固定比例。这份投入未必马上产出功能 PR，但它支撑着产出功能 PR 的那些工作。

08

用运营中的失败改进共享系统

第一版远谈不上顺畅。Khandelwal 说，短短几周里代码库就积压了大约 400–500 个 issue。多个智能体都在创建 issue，彼此却没有正确串联起来。同时，大家对预期行为意见不一，工程师很容易就放弃共享工作流，回去盯自己的智能体。团队的应对办法是把这些反馈纳入 skill，持续改进它。

其他问题则需要调整预期或划定边界：

- 长时间运行： 值得信任的智能体可以在工程师忙别的事时自己干活。Khandelwal 拿推理系统作类比：思考时间越多，效果越好。但光是耗时长，并不能证明一个代码库工作流产出的代码更好。 - 合并冲突： 并发改动越多，集成摩擦越大。他承认有这个问题，但没给出管理合并的方案。 - 实验代码： 明确标出那些不打算上线的原型，让这些实验不必遵守生产代码那套完整的严格要求。这种豁免的前提是，“不上线”这条边界始终清清楚楚。

每个人在采用光谱上的位置也会天天变动。问问他们的体验里什么变了：是模型、框架，还是配置里有什么地方需要重新审视。别再笼统抱怨模型不够聪明，换成团队能落实的问题：共享环境怎样才能让智能体更好用？要改进的是团队的配置，而不只是某个人的配置。

Khandelwal 用学滑雪结束了主题演讲。对他来说，难的是下定决心往前滑，而不是一直想着刹车；只有这样，他才能体会到转弯是什么感觉。放在这里，这是个关于学习的类比：投入得够多，才能摸清工作流怎么运转；接受有些尝试会失败；同时保留恢复的能力。能恢复，敢于失败才有意义。

09

问答：让渐进式披露可观察

观众提问又回到了落地层面：哪些渐进式披露策略最管用？回答从智能体最先接触的入口说起：

1. 让 skill 的入口文件保持精简。 团队给 SKILL.md 定了大约 100 行的上限，把 skill 当成一个带配套材料的文件夹，而不是一个大指令文件。这是团队约定，不是平台限制。 2. 在代码搜索会落到的地方留下指引。 如果某个文件需要配一份运行手册，它的注释就应该指向那份手册。智能体通过 grep 找到代码后，也能顺着找到操作上下文。 3. 把代码库指令当作一份精简索引。 让 CLAUDE.md 或 AGENTS.md 专注于把智能体引向相关文件，而不是把所有细节都塞进初始上下文。

如今照这条建议做，要分清“指针”和“导入”。按 Claude Code 当前的加载规则，它读取的是 CLAUDE.md，不会直接读 AGENTS.md，而且会立即展开 @ 导入；通过 CLAUDE.md 导入 AGENTS.md 是文档里写明的共享方式。所以，把一个大指令文件拆成几个会被立即导入的文件，并不能推迟上下文开销。精简索引这条原则要成立，前提是智能体在需要时才顺着相关指针去读，至于具体怎么加载，由它的框架决定。

最后，看看第一条提示词之后发生了什么。智能体知道相关信息在哪儿吗，还是一上来就大范围搜索？干出有用的活之前，它往上下文里塞了多少东西？Khandelwal 估计，他的配置启动时就已占用约 2 万–2.5 万 token，涨到 4 万–5 万就是该排查的信号。这些数字反映的是他自己的诊断预期，不是通用阈值。把导航情况和上下文增长放在一起看，再调整披露的边界，然后反复迭代。

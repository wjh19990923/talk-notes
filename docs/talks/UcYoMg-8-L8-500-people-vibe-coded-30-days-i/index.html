500 人氛围编程了 30 天，我是其中之一

三个项目记录了 Sanja Grbic 从产品设计师转型为设计工程师的过程，展示了培训、共享上下文和决策归属如何改变了工作。

01

为什么速度在 Automattic 内部看起来不一样

一家大型软件公司如果给小团队一个月的自主权，让他们自己动手做东西、上线，会发生什么？Automattic 的 Radical Speed Month 把工作拆给一个个自主运作的双人小组。产品设计师 Sanja Grbic 在这次活动中做了三个项目，每做完一个，她做下一个的方式就会变一次。

Automattic 维护着 WordPress.com、Jetpack 和 WooCommerce，旗下还有 Tumblr、Beeper 等品牌。按 Grbic 的说法，公司约有 1,400 人，完全分布式办公，靠异步协作。这种工作方式留下了一笔宝贵的积累：多年来记录在案的决策、概念和讨论。

Grbic 有十多年的软件设计经验，其中五年在 Automattic 的 Jetpack 设计团队。产品界面怎么变，背后的团队怎么变，她都亲眼见过。设计岗位从网页设计、UX、交互设计一路扩展到产品设计；工具也从 Adobe 换到 Sketch，再换到 Figma。AI 在这条脉络里有点不一样：各个岗位的人都能用它，而大家对它的期待和以往一样，就是更快。

但能不能快，要看环境。一到三人的小团队做新产品，几乎不用协调就能随时掉头。几千人的组织维护着发展了五到二十年的产品生态，就得应付现有的系统、依赖关系和工作习惯。光是实现得更快，这些约束并不会消失。

02

先让人能做贡献，再要求速度

Automattic 先是给员工开通 AI 工具和课程，后来扩展成一个 AI 赋能项目。Grbic 介绍，每位员工都要上一门为期两周、按岗位定制的课程，既有讲座，也有针对性的动手练习。编码工具越来越好用，公司也鼓励员工不管原本做什么岗位，都能放心地贡献代码。

这份邀请要落地，得靠实打实的基础设施。系统与运维团队准备了安全规范、流程和文档，写得足够清楚，非工程师也能自己搭起一套能跑的开发环境。给了编码工具，还得配上一套真正能用的开发流程。

做调研和规划时，Grbic 还用了 Context A8C。这是一个内部 MCP server，让 AI 工具能读取 Automattic 积累的知识和数据。公司多年留下的文档，就这样通过一个经过授权的内部集成，为新工作提供参考。

03

暂停路线图，交付一个真东西

Radical Speed Month 把优先级的调整直接摆到了台面上：

1. 暂停路线图上的工作 30 天。 2. 找一个搭档。 3. 交付真东西。

欢迎用 AI，但不强制。活动分批进行，免得整个公司同时停下日常工作；第一轮大约有三分之一的人参加。

据 Grbic 介绍，30 天里约 500 名参与者启动了 794 个项目。这是启动的项目数，不是上线的产品数。她自己这个月正好赶上那门为期两周的线下 AI 赋能课程，所以她能交付什么，很大程度上取决于 AI 工具。

她对开发也不是一窍不通：审过 GitHub pull request，试过 Claude Code，还做过几个业余小项目。但她从没在工作中写过代码、上过线。这次实验让她从隔着一段距离“看懂”开发，变成亲手负责交付流程中的几个环节。

04

一个桌游应用变成了一堂协作课

第一个项目是在培训期间开始的，起因很实际：当晚有一场桌游之夜。两位不太会写代码的设计师、一位工程师和一位产品负责人，要在两小时内合力做出点东西。他们选了一个桌游局管理应用。

Grbic 说，四个人两小时就把应用做了出来。用户可以创建、查看、加入和管理牌局，开始和结束游戏，查看有哪些游戏、还剩几个座位，还能聊天。应用里有一幅 16-bit 风格的插画，画的就是他们真实的办公室，一眼就能认出来，同事们特别喜欢。

大家一开始就说好，每个人都要动手。工程师建好 GitHub 项目，教大家基本命令，讲解 Git 怎么运作。Grbic 以前用过版本管理，自以为懂 Git；真到共享仓库里协作，她才发现“熟悉”和“用得得心应手”之间还差得远。

四个人坐在一起分工、测试、提交代码。项目独立于 Automattic 的现有产品，他们可以专心学习，不用担心把那些产品搞出问题。开发全程在 Claude Code 里完成；Grbic 记得，唯一额外用到的视觉工具是 Nano Banana，用来生成那幅办公室插画。

工程师帮别人动手做东西，自己的影响力也会跟着放大。 这位工程师没有把实现工作从经验不足的队友手里揽过去，而是帮他们参与进来。Grbic 认为，这个道理放到设计和产品工作上同样成立。AI 让人能在本职之外出力，这时候，相关技能最强的人可以带着整个团队一起进步。

05

做出追踪器，再负责它的交付

下一个项目，她把刚攒起来的信心用在了一个组织层面的问题上。Grbic 和一位工程师、一位设计运营同事组队，想让人和 AI 工具都能更容易找到相关、最新的设计系统信息。他们的开源设计系统服务于 WordPress 生态内外的产品，而且一直在变。问题牵涉面很广，三人各负责一块。

Grbic 提议做一个设计系统状态追踪器。工程师提出了几个疑问：性能怎么样，维护成本多高，这东西到底做不做得出来。培训时那次练习给了她底气，活动又允许实验，于是她决定自己把整个想法做成概念验证。前期探索是三个人一起做的；设计和实现则由她一手包办。

她一块一块地往上搭。组件实时预览跑通是个转折点：追踪器能直接展示组件本身，而不只是指向文档。它从 GitHub、Storybook 和 Figma 收集链接，按状态归类，再打上对应的组件库名称标签。Grbic 说搜索效果很好；她把工具分享给其他设计师，并根据反馈做了改进。

先有能跑的原型，后有 Figma。某个视觉细节没法用文字跟 Claude Code 讲清楚时，她就用 Figma 做一张图来说明。Figma 成了解决具体视觉问题的工具，主要的迭代还是在真实运行的项目里进行。

Grbic 说，她一周内做出了原型，之后又花了一周半修问题、托管和部署。这段时间里，她重写了部分实现，交付了两个版本：

- 内部工具：部署在 Automattic 的内部平台上。 - 公开网站：只发布一部分精选的数据和信息。

可见，做出能跑的原型只是工作的一部分；要交付，还得想清楚每类受众能看到什么，并把工具托管上线。

对 Grbic 来说，这次交付标志着她从设计师变成了设计工程师。AI 帮了忙，但她认为最关键的是自己掌控了整个流程。Radical Speed Month 允许她实验、自己拍板，省掉了在不同岗位之间来回商量、交接的时间。她能从发现需求一路直接做到实现和部署。

06

两位设计师做出一个商家聊天概念验证

还剩大约一周时，Grbic 和另一位设计师搭档。据 Grbic 介绍，她们用六天给 WooCommerce 商家做出了一个能用的 iOS 聊天概念验证。商家可以用手机实时回复顾客，也可以开启 AI 代为回复。

这个概念验证把现有生态里的好几个部分串了起来：

- 商家登录：通过 WordPress.com 认证，并连接 Jetpack。 - 访客界面：一个聊天小部件，沿用网站本身的主题。 - AI 回复：一个智能体扫描网站获取信息，实时回答访客的问题。

Grbic 还提到，这个智能体能分辨哪些问题自己答得了、哪些答不了。不过交付的只是一个能用的概念验证；从她的讲述看，无法确认它已正式上线，也没有数据说明它判断“能否回答”的准确率。

07

把共享上下文放在原型旁边

两位设计师很快就在功能上达成了一致，因为她们都从用户需求出发想问题。她们在一个 Claude Code 项目文件夹里开始探索，把聊天记录和想法都存进文件系统。Grbic 发现，这个做法让协作和后续开发都快了不少，后来她在日常工作里也一直沿用。项目文件夹里存着成果，也存着实现背后的思考。

主要的设计产出物也变了。以前，团队会一直在 Figma 里打磨，直到设计做到高保真。这次，她们先定计划，再做出能跑的原型，最后才回到 Figma 做情绪板、打磨 UI。

| 阶段 | 以前的流程 | 商家聊天项目的流程 | |---|---|---| | 动手实现之前 | 在 Figma 里做高保真设计 | 制定计划 | | 主要迭代对象 | Figma 设计稿 | 能跑的原型 | | 视觉打磨 | 开发之前 | 开发完成后回到 Figma |

按这个顺序，她们能更早处理真实的功能表现，视觉上的决定则继续交给擅长这件事的 Figma。

08

给人们改变工作方式的空间

这一个月里，Grbic 改掉了一套沿用多年的流程。第一个项目让她看到，越来越多同事开始写代码时，工程师可以成为赋能者和老师。第二个项目把她自己的职责扩展到了设计工程：在一个庞大、成熟的系统里把代码推上生产环境，而这需要大量入门准备和严格的安全规范。公司的这些举措，让她能在既有要求之内摸索出新的工作方式。

到第三个项目，变化已经属于两个人。两位设计师都学会了怎么用这些工具，能在共同的认知上协作。Grbic 认为，她们的速度来自这种相互磨合，而不只是某一个人变得更熟练。同样的实验完全可以先在一个团队里做起来，不必等整个组织转变。

换工具、换流程，就得同时改变人的做事方式。 让大家用上工具，找出能教别人、愿意带头推广的同事，留出实验的空间，再给足拍板的权力。有了这些条件，人们才能打破固有习惯，找到 AI 真正能让工作变快的地方。

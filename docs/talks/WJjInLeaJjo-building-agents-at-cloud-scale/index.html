在云规模上构建智能体

Antje Barth 把日常的智能体体验与其下的工程联系起来：由模型主导的工具、语义化的工具检索，以及通过熟悉的 AWS 基础设施部署的 MCP 服务。

具备基础 Python 并熟悉 API 会有帮助；文中会介绍演示中用到的智能体、MCP 和 AWS 部署概念。

01

从客户请求到协调一致的行动

用 AI 重塑日常的客户体验，做出过去做不到的体验，需要什么？Antje Barth 从 Amazon 这种规模下的这个问题讲起。她提到，Amazon 内部已建成或正在开发的生成式 AI 应用超过 1,000 个，覆盖库存预测、配送路线规划、购物和家庭交互。这个数字统计的是处在不同开发阶段的应用，不是已部署的智能体数量。随后她介绍了全新打造的 Alexa+，称据她团队所知，这是规模最大的一次服务、智能体能力与 LLM 的整合。

宣传短片把协调问题讲得很具体：孩子的生日派对和去机场接奶奶撞了时间。Alexa 发现了冲突，主动提出帮奶奶叫车。接下来的对话里，Alexa 先是知道 Billie Eilish 要来本地演出，接着提出开票时发通知提醒。这些示例展示的是把信息和一个建议操作连起来；短片本身并不能证明这些预订或通知真的完成了。

接着是一次度假请求，用户在几轮对话里不断加条件：离得近、有海滩、天气好。Alexa 推荐了 Santa Barbara，推荐了一家餐厅，回答了关于目的地的问题；聊到观鲸时，又提出帮忙预订双体船游览。真正有用的是这种连贯性：新问题和新偏好都汇入同一个逐步成形的任务。

其余场景展示了助手还能用上哪些上下文。它给出下一步维修指引，回答要不要剪刘海，接到做一组宝宝照片幻灯片的请求，还记得这次维修需要两英寸的垫圈。它告诉用户 Uber 快到了；被问到狗狗 Mozart 有没有出去过时，它说自己查看了摄像头。这些场景合在一起，覆盖了对话、记住的细节、媒体、服务状态，以及家中设备提供的信息。

02

一个助手背后的多位专门专家

Barth 提到，全球 Alexa 设备超过 6 亿台。这是 Alexa 的装机量，不是 Alexa+ 的用户数。为了解释新体验背后的架构，她介绍了数百个专门的专家系统：每个专家都是一组能力、API 和指令，组织起来完成某项特定任务。据 Barth 介绍，这些专家在数万个合作伙伴服务和设备之间协同编排。助手看起来什么都能做，靠的是许多面向具体任务的能力相互配合。

专门化把云规模问题变成了服务设计问题。 能力一旦拆开，接下来就要解决怎么把它们连起来、跑起来。Barth 从 Web 服务讲到智能体服务，依据是许多底层原则依然适用——不管应用是服务一大批设备、给企业软件加上 AI，还是帮初创公司扩展第一款产品。演示的后半部分一步步展示这些连接：先是智能体调用文档工具，再是用 SDK 连接模型和工具，最后是远程托管的工具服务。

03

一个终端里的问题变成一次获批的工具调用

Amazon Q Developer 把同样的模式带进了开发者的终端。Barth 介绍了它的 CLI 智能体：可以用自然语言提问、调试代码、读写文件。演示中，她问 Q 对 Amazon Bedrock 了解多少。关键在提问和回答之间发生的事：Q 通过 MCP 集成，连上了 AWS 文档团队的服务器。

整个交互可以清楚地分成几步：

1. 选择工具。 Q 找到 MCP 服务器提供的一个文档工具。 2. 请求许可。 终端显示准备调用的工具，Barth 批准。 3. 使用检索到的信息。 Q 根据 AWS 官方文档给出回答。

工具连接负责提供外部信息；许可这一步让用户在执行前先批准这次调用。

Barth 接着让观众猜，AWS 团队花了多久做完并上线这项服务：两个月、三周，还是半年。她公布的答案是三周之内。她想说明交付速度本身就是竞争优势；工程上要解决的问题随之变成：怎样让其他团队也能稳定跑出这样的节奏。

04

给模型一个任务和一些工具

这种速度背后的开发方式，是把决策、规划、推理和执行操作都交给模型。开发者只需说明智能体要完成什么、能用哪些工具，不用规定每一步怎么走。Strands Agents 把这种方式做成了一个开源 Python SDK。模型主导工作；开发者提供任务和可用能力。

连名字都体现了这种搭配。Barth 说，“Strands”这个名字是 AI 起的，借 DNA 的两条链来比喻模型和工具的连接。实际工作流也同样简洁：在代码里定义提示词和工具，在本地测试智能体，准备好了就部署。

安装 strands-agents 和 strands-agents-tools 之后，最基本的 Python 结构只有三部分：导入、工具列表、调用智能体。比如给模型一个计算器，它就有了一项可以调用的具体能力：

```python from strands import Agent from strands_tools import calculator

agent = Agent(tools=[calculator]) agent("What is 17 multiplied by 23? Use the calculator.") ```

同样的结构既能回答单个问题，也能作为更复杂工作流的起点。加一个工具，就多一项可用能力；至于怎么用，由模型根据任务决定。

演讲中展示的配置以 Amazon Bedrock 为默认提供方，模型是 Claude 3.7 Sonnet。这只是当时的配置，SDK 并不局限于 AWS。Barth 介绍了几种选择模型的途径：

| 提供方途径 | 演讲中的定位 | | --- | --- | | Amazon Bedrock | 演示中的默认提供方 | | Ollama | 本地开发和测试 | | Anthropic | 直接对接提供方 | | Meta 的 Llama API | 另一种提供方集成 | | LiteLLM | 接入 OpenAI 及其他提供方 | | 自定义提供方 | 开发者自行定义的模型集成 |

无论换哪家提供方，“提示词加工具”始终是智能体的核心结构；提供方只决定由哪个模型来推理。

05

在选择工具之前先检索相关工具

Barth 提到，演讲时 Strands 已有 20 多个预置工具。既有文件操作、API 调用、AWS 服务集成这类常规操作，也有记忆和检索增强生成（RAG）。其中一个工具 retrieve 能在知识库上做语义搜索。它不只能为回答查找文档，还能帮智能体找到其他工具。

Barth 提到，AWS 内部有一个智能体管理着 6,000 多个工具。把整个工具目录塞进一个模型上下文，模型就很难选对。团队的做法是把工具描述存进知识库，再用检索缩小候选范围：

1. 为描述建索引。 把可搜索的工具目录放进知识库。 2. 按当前任务搜索。 用 retrieve 找出相关工具。 3. 加载子集。 只把这些工具放进模型上下文。 4. 选择操作。 让模型决定用检索到的哪个工具。

这样一来，“找出可能有用的能力”和“选定下一步操作”就分开了。工具目录的规模反映的是这个内部系统的范围；Barth 没有给出这种做法在工具选择准确率或延迟上的数据。

其余的工具也不止于文本和单个智能体的操作：

- 多模态： 支持图像、视频和音频。 - 更多推理： 有工具可以引导模型多想一步、推理得更深。 - 智能体协作： 预置工具支持基于图的工作流和子智能体集群（swarm）。

这些工具扩展了智能体的能力，但出发点仍是“模型加工具”这个基本结构。

06

从一个本地 MCP 掷骰子工具开始

Strands 原生集成了 Model Context Protocol（MCP），MCP 服务器暴露的能力可以直接当作智能体的工具。Barth 提到，在 SDK 发展的这个阶段，对智能体间协议（A2A）的支持还在路上。至于 AWS 专属的能力，她推荐了 awslabs/mcp 仓库，里面的服务器实现还在不断增加。

云端部署的例子从一个本地服务器讲起。Barth 解释说，MCP 最初采用标准 I/O 方式，把客户端连到本地运行的工具上。她的 Python 示例用的是 FastMCP：创建一个服务器，用装饰器把一个函数声明为工具，再接收一个参数，指定骰子有几个面。这套机制的最小实现如下：

```python import random

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("dice")

@mcp.tool() def roll_dice(sides: int) -> int: """Roll one die with the requested number of sides.""" if sides < 2: raise ValueError("A die must have at least two sides.") return random.randint(1, sides)

if __name__ == "__main__": mcp.run(transport="stdio") ```

函数负责实现操作，装饰器把它暴露为 MCP 工具。有了 sides 参数，同一个工具就能用于不同的骰子。

D20 是一种 20 面骰，《龙与地下城》玩家都很熟悉，Barth 却是第一次接触。她举起一枚 D20，并说明这个演示是 Mike Chambers 做的。这个细节后来成了测试输入：智能体要把“掷一个 D20”的请求转成一次面数为 20 的工具调用。

07

把工具移到云端端点后面

为了让客户端不再依赖本地运行的服务器，Barth 把 MCP 服务搬到了 AWS Lambda 上，改用 Streamable HTTP 连接。Lambda 函数放在网关后面，客户端就能远程调用这些工具。演示中还加了一个授权器（authorizer）做访问控制，会话数据存在 DynamoDB 里；她还提到，授权集成也可以选用 Cognito。

架构上的改动不大，可以直接对比：

| 关注点 | 本地示例 | 远程演示 | | --- | --- | --- | | 传输方式 | 标准 I/O | Streamable HTTP | | 工具执行 | 本地服务器进程 | AWS Lambda | | 客户端连接 | 本地进程连接 | 网关端点 | | 授权 | 未展示 | 授权器 | | 会话数据 | 未展示 | DynamoDB 表 |

真正有用的能力仍然是掷骰子。托管、访问控制和会话存储都挪到了外围的服务基础设施里。

演示先介绍了一个 MCP Lambda 处理程序，里面只有一个简单的 Hello World 工具。工具仍然用装饰器声明；Lambda 入口把调用转发给 MCP 服务器。接着 Barth 展示了更完整的服务器实现：加上 DynamoDB 会话表，定义掷骰子工具，在 Lambda 处理程序末尾用同样的方式转发。这层适配把 Lambda 的调用模型和 MCP 服务器接在一起，每个工具不必自己再实现这段连接。

部署沿用现有的 AWS SAM 工作流。部署返回 API Gateway URL 之后，客户端就能发现并使用这些远程工具：

1. 配置连接。 把 API Gateway URL 交给 Strands 的 MCP 集成。 2. 提供授权。 附上演示中用的 bearer token。 3. 发现工具。 列出远程 MCP 服务器暴露的工具。 4. 构建智能体。 把发现的工具传给 Strands 智能体。

Barth 明确表示，bearer token 这种方式只是一个简单的概念演示；真正围绕它搭建服务时，还需要更可靠的授权集成。

最后的请求是掷一个 D20。工具随即启动，演示中这次掷出了 7。至此整条链路走通了：从自然语言输入，到工具选择、远程执行，再到返回结果。这个例子的价值在于涉及的部分很少：工具一旦跑在 Lambda 上，同样的集成模式就能把现有的、能在 Lambda 上运行的应用代码和 AWS 能力开放给智能体。

08

从工具服务到协同工作的智能体

现有 AWS 应用能通过智能体工具访问之后，Barth 转向下一种连接：智能体与智能体之间的对话。她把开放协议视为这种互操作的基础，提到 AWS 已加入 MCP 指导委员会，并介绍了 AWS 在代码和协议开发上的贡献。她还推荐了 AWS 开源博客上跟进这项工作的系列文章。

结尾的愿景从单个远程工具，扩展到一个个人智能体协调其他智能体。Barth 引用同事 Danielle 的话：“所有数字交互的最小单元，都将是一次智能体调用。”配套的概念图展示了一个个人智能体连接到智能体商店，让多个智能体一起完成任务。图上明确标注这只是概念，不是真实产品。演示中的服务边界没有变——一个智能体去调用另一处单独托管的能力——只是设想边界另一侧的能力本身也可以是一个智能体。

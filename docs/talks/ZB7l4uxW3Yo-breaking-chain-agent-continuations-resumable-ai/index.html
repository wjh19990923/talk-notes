Agent Continuations

实现草图

幻灯片原文
On suspension, the agent saves messages and resume metadata in a continuation. The top-level agent exposes approval requests; on resume, the Continuation Agent reconstructs state and continues processing.

Implementation Sketch

• Agent forward progress remains the same

• At time of suspension (e.g, tool call approval)
  ○ Create a continuation object
  ○ Embed messages array + resume metadata
  ○ Return continuation to top level agent

• Before returning continuation object response
  ○ Create top-level approval requests object

• On resume, the Continuation Agent reconstructs the agent state from the continuation and resumes processing

多层级 HR 智能体示例

幻灯片原文
The HR agent delegates account work to a sub-agent. Authorizing the account requires approval, suspending the workflow until the approved continuation is sent back to the HR agent.

Multi-level HR Agent Example

# hr_agent.py

HR_SYSTEM_PROMPT = """
You are **HR Agent**, responsible for handling HR-related
tasks, including onboarding new colleagues. You have access
to the following tools: . . .
"""

@tool()
def send_email_tool(recipient: str, subject: str, message: str):
    """Send an email to the specified recipient."""
    return f"Email sent to {recipient} ..."""

@tool(is_agent=True)
def account_agent_tool(*args, **kwargs):
    """This tool handles all account-related tasks ..."""
    return account_agent.request(*args, **kwargs)

hr_agent = ContinuationAgent(
    instruction=HR_SYSTEM_PROMPT,
    tools=[send_email_tool, account_agent_tool])

prompt = {"prompt": "Help me open an account for Alice with username: alice. Her email is alice@example.com."}

hr_response1 = hr_agent.request(prompt) # A Continuation returned

# Approve all the tool calls
for to_be_approved in hr_response1["approval_info"]:
    to_be_approved["approved"] = True

# The agent can complete and return a response object
hr_response2 = hr_agent.request(hr_response1)

# account_agent.py

AA_SYSTEM_PROMPT = """
You are **Account Agent**, responsible for managing
user accounts and assigning security levels. You have access to the following tools:
"""

@tool()
def create_account(username: str):
    """Create a new user account."""
    return f"Account created for {username}."

# Simulate the authorization process
@tool(need_approval=True)
def authorize_account(username: str, level: int):
    """Authorize a user account by taking a username and a
security level."""
    return f"Account {username} authorized with security level {level}."

account_agent = ContinuationAgent(
    instruction=AA_SYSTEM_PROMPT,
    tools=[create_account, authorize_account])

打破链条：用智能体续延实现可恢复的 AI 工作流

智能体应该能够停下来等待审批，而不必让它的执行循环一直活着。递归续延保留了恢复智能体及其子智能体所需的状态。

熟悉 Python 函数、JSON 和 LLM 工具调用，有助于理解续延接口和嵌套智能体示例。

01

当一个正在工作的智能体不得不等待时会怎样？

你的智能体已经跑得不错了，下一步是上生产。这时会冒出两个问题：它能不能停下来，等人做决定？一个长时间运行的任务出了故障，能不能不把之前做的全丢掉？Agent Continuations 正是从这两个问题出发。提出这套机制的是 Greg Benson，他是旧金山大学计算机科学教授，也是 SnapLogic 首席科学家。做法是把智能体的状态保存下来，之后再接着执行；这样既能让人介入，也能靠快照做故障恢复。

这项工作出自 SnapLogic 的 Agent Creator 研究组。设想一个智能体正要转出一大笔钱，或者删除一个账户。执行这种后果严重的操作之前，它得把决定权交给人。另一方面，长时间运行的智能体需要检查点，出了故障才不用从头再来。把这些智能体从开发者的电脑搬到分布式环境里，还多了一条要求：执行过程必须能比承载它的那个进程活得更久。

02

必须扛过中断的循环

智能体在模型推理和工具执行之间来回切换。它向 LLM 发请求，告诉模型有哪些工具可用；模型可能返回工具调用请求；智能体执行这些调用，收集结果，再把结果发回给模型。如此循环，直到任务完成。工具本身也可以是智能体，所以哪怕一个看似简单的请求，也可能牵扯好几个相互交织的循环。

有三种情况，让“执行不会中断”这个假设站不住脚：

- 人工审批： 工具可能要先获得许可，才能访问某个环境，或在其中执行后果严重的操作。 - 限流： Benson 举的例子是编码助手碰上刚发布、被大量使用的新模型。工作流得有办法应对 API 暂时接不了更多请求的情况。 - 长时间任务： 跨内部和外部系统做大量调研，碰上网络或硬件故障的概率也随之升高。工作积累得越多，保住进度就越有价值。

03

一个暂停的子智能体可能卡住整个层级

主智能体或编排器可能调用好几个子智能体，每个子智能体又能继续调用下一层子智能体。所以审批和恢复要考虑的不只是最里层的那个工具。如果一个嵌套很深的操作暂停了，系统必须保住各级父智能体的进度，也要保住它们正在等这个操作返回的那些调用。

Benson 把承载问题称为智能体循环持久化（agent loop persistence）。循环就是跑在某台物理机器上的代码，不管是在桌面还是在云上。它一头连着交互界面——命令行、Web 应用，或者 Slack 这类渠道——另一头连着模型、工具和子智能体。

Benson 说，在他的团队考察过的框架里，等人审批期间让循环一直跑着是常见做法。这只是对这些框架的描述，不代表智能体框架普遍都得这么做。这里的设计目标很明确：挂起之后关掉所有受影响的循环，等人回复时再重建执行过程。在 Slack 上等一次审批，不该要求原来的智能体进程在整个等待期间一直活着。

04

消息数组已经保存了大部分状态

灵感来自编程语言里的 continuation（续延）：在某个点捕获执行状态，留下继续运行所需的东西，之后再恢复。在通用编程语言里支持这种操作，可能需要相当复杂的运行时机制。Agent continuation 把这个思路用在一个更窄的执行模型上，这个模型只围绕 LLM 调用、工具调用和子智能体调用展开。

智能体挂起时，会把保存下来的状态返回给应用层。应用可以去拿审批，也可以把状态持久化，留着以后恢复。这里说的挂起，是停在框架支持的执行边界上，比如某个需要审批的工具执行之前；并不是在工具执行到一半、或模型请求还没返回时，在任意一条指令处强行打断。

关键在于：智能体本来就维护着一个 messages 数组。它记录交互历史，下一次推理时会再交给 LLM。所以 continuation 需要的记账工作，系统其实已经做了一大半：之前的请求、工具交互和结果都作为对话状态保留着。messages 数组已经接近够用，但光靠它，还确定不了恢复挂起操作所需的全部控制状态。

05

一个请求可能返回尚未完成的工作

Agent Continuations 原型从一个熟悉的 Python 接口起步。用装饰器把 Python 函数标记为工具，构造智能体时传入这些工具的列表，也可以再传入指令或系统提示词。应用提交用户请求，智能体跑完模型加工具的循环，然后返回响应。

要支持 continuation，这套设置只需改两处：把某个工具标记为需要审批，再构造一个 ContinuationAgent。真正要紧的变化在返回结果的约定上。

| 结果 | 含义 | 应用怎么处理 | |---|---|---| | 完整响应 | 智能体完成了任务 | 展示或使用结果 | | Continuation 对象 | 执行已挂起 | 查看挂起元数据 |

所以，拿到的返回对象不一定是最终答案。它的元数据会告诉应用：执行为什么停下，需要怎样介入。

在审批这条路径上，应用把人的决定记为 true 或 false。Benson 演示的是批准的分支：在 continuation 里写入批准，再把同一个对象通过 request 传回去。智能体认出这是一个 continuation，就从待执行的工具调用之前恢复。批准只是给了执行许可；恢复后的智能体仍然要真正调用工具，再一路走到最终响应。

06

捕获递归状态，暴露一个简单的审批界面

出现挂起条件之前，正向执行就是普通的智能体处理流程。一旦触发挂起，框架会创建一个 continuation，里面装着 messages 数组和额外的恢复元数据。这个对象一路返回顶层智能体，途中框架会把应用需要的信息提取出来，方便应用弄清挂起原因、给出所需的审批。应用不必翻遍整个嵌套执行结构，才找到要交给人拍板的那件事。

应用更新对象之后，框架重建智能体状态，继续执行。有了保存下来的 continuation，就不必让挂起的循环一直跑着。捕获一完成，这些循环就可以关掉，因为对象里已经有恢复它们所需的信息。

单层结构把交互历史、待执行的操作和应用的决定分开存放：

| 字段 | 作用 | |---|---| | messages | 常规交互历史 | | resume_request | 指明从哪个操作恢复 | | processed | 携带已处理的信息，包括审批决定 | | approval_info | 向应用暴露审批信息 |

审批信息放在顶层，应用更新对象很方便，底层的执行结构也不会丢。

遇到嵌套智能体时，resume_request 里可以装一个子智能体的 continuation，后者有自己的 messages、resume_request 和 processed。这个结构是递归的：每一层都保留自己的历史，以及它要恢复的那个子操作。正因如此，这个格式能容纳任意层数的子智能体嵌套，而不是把整个工作流压成一段扁平的对话。

07

一个 HR 智能体在账户授权中途暂停

示例有两层智能体。顶层的 HR 智能体有一个邮件工具和一个账户智能体工具。账户子智能体负责创建账户和分配权限，用的是它自己的创建账户工具和授权账户工具。授权需要审批。每个智能体都有各自的系统提示词和工具配置。

一个开新账户的请求从 HR 智能体进入，最后到达账户子智能体的授权工具。挂起则沿着同一个层级原路返回：

1. 账户智能体走到待执行的授权步骤，发现需要审批。 2. 它在授权执行之前捕获一个 continuation。 3. 这个 continuation 往上传递时，父级往里补充恢复 HR 智能体所需的状态。 4. 应用拿到完整的 continuation，查看其中的审批信息。

应用给出决定后，把 continuation 发回给 HR 智能体。框架会把父智能体和账户子智能体都恢复到挂起的位置。应用只管处理审批；重建嵌套执行是框架的事。

08

从一个编辑过的响应文件恢复

演示把进程边界实实在在地摆了出来。Benson 用 JSON 提供初始提示词，运行智能体，再把响应写进文件。这样安排，是为了让请求和之后的 continuation 彼此解耦：保存下来的对象必须带上后续调用所需的状态。下面这段很短的 Python 代码，在一个已经配置好的智能体外面加了一层文件边界，正好体现这种交接：

```python import json from pathlib import Path

def request_from_file(agent, input_path: Path, output_path: Path): request = json.loads(input_path.read_text(encoding="utf-8")) response = agent.request(request) output_path.write_text( json.dumps(response, indent=2), encoding="utf-8", ) return response ```

同一个函数既能接收初始的 JSON 请求，也能接收保存下来的 continuation，因为两者都从 request 进入。

打开保存下来的响应，能看到顶层的 continuation 和 messages，接着是子智能体的 messages 和系统提示词，最底部是给应用看的审批信息。Benson 手动改了这条审批，保存文件，再把改好的响应提交回智能体。在实际应用里，这一步会由审核界面收集决定并完成更新。再次调用时，框架重建状态，这时待执行的工具已经获批。

最终输出显示账户创建成功，安全级别也已授予。展示出来的 JSON 里写着 Alice，安全级别为 0，带有一封欢迎邮件的确认，最后 end_reason 为 completed。这些是工作流恢复后报告的结果。

完成后的结果还体现出这种表示方式的一个好处：里面就是一个普通的 messages 数组，不再残留任何 continuation 结构。continuation 只在执行挂起时才出现，并不会永远包在每个完成的响应外面。

09

不止于人工审批

Benson 介绍说，这个 Python 原型基于 OpenAI Python API 构建，没有其他依赖，代码已在 GitHub 上公开。他还提到已经实现了一个版本，支持更通用的挂起触发条件：运行时长、轮数，以及异步发来的挂起请求。能触发挂起的理由更多了，但“捕获再恢复”的模型保持不变。

他提出的方向是把这套机制引入现有框架，比如 Strands 或 Pydantic AI，而不一定要把原型做成又一个完整的智能体框架。这些只是演讲里设想的集成，并未正式宣布。

Benson 明确承认，其他框架已经在做状态管理。在他团队的调研里，这些框架缺的要么是人工审批，要么是对任意深度子智能体嵌套的支持。他主张的新意在于把两者结合起来：审批可以发生在嵌套的智能体内部，continuation 则保住外围的执行状态，让流程能回到那里。

最后，Benson 推荐大家去看公开的原型，以及用来可视化构建智能体的 Agent Creator。串起这两种实现的具体能力，是可保存、可恢复的执行：应用可以拿到挂起时整个智能体层级的状态，取得人的决定，再把状态交回去，让工作流接着跑下去。

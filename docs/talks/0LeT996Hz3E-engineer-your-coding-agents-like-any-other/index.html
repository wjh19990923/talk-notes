Engineer Your Coding Agents Like Any Other System

Zach Lloyd walks through Warp’s software factory, from declaring how cloud coding agents run to scoring their work, proposing configuration changes in pull requests, and replaying real tasks to compare cost and quality.

01

When every agent needs a person

Running several coding agents in parallel still leaves someone at the keyboard. If every session needs interactive prompts, the amount of work a team can hand off depends on how many sessions people can keep moving. That is the bottleneck Zach Lloyd, Warp’s founder and CEO and a former Google Docs engineering lead, starts with.

Independent setups also create work for platform teams. When each developer chooses their own model, skills, and local configuration, the team has a harder time judging what it gets for its spending or applying common security and governance policies. Those problems show up at the team level even when individual developers are getting useful work done.

Zach Lloyd led engineering on Google Docs and helped scale it to hundreds of millions of users. He went on to found Warp, which builds a platform for companies to create their own internal software factories.

02

A factory definition the team can change

Lloyd defines a software factory as “a code-defined closed loop system for continuously measuring and improving cloud coding agents.” Automations, AI teammates, shared skills, and MCP integrations can all do work inside it. The factory brings those parts under one definition and uses the results of real runs to decide what to change.

The definition reads like Terraform. Declarative files specify which agents run, what triggers them, how work moves between stages such as triage and specification, which MCP integrations are available, and where the agents execute. Work can come from people or automated signals. Agents then take on parts of the usual software lifecycle, including triage, implementation, verification, and monitoring.

Each run gives the team another chance to learn how the current setup behaves. To tell whether a change helped, the factory needs measurements of output quality, cost, and throughput. Those measurements give the team something to compare when it changes how work gets done.

Zach Lloyd defines a software factory as a system specified in code. It runs a feedback loop that continually measures how cloud coding agents perform and uses the results to guide improvements.

03

What the factory needs to run and improve

Debuggers, profilers, and Chrome DevTools helped Lloyd understand software he was building at Google. Evals, benchmarks, and A/B tests serve a similar purpose for the system that runs coding agents. Each asks a different question, from how a run failed to whether one factory configuration works better than another.

- Factory code. A team can branch the workflow definition to test a different setup or roll back a change. The same files give an agent somewhere to propose an edit when it finds a problem with how the factory works.

- Run data. Save conversations and the artifacts agents produce, including videos and screenshots. A conversation records what happened during the work. The artifacts give the team something to inspect when it evaluates what the run produced.

- Compute. Run agents in sandboxes for isolation and repeatability. Lloyd favors supporting more than one platform so the factory can accommodate work that needs different execution environments.

- Models and harnesses. Make both the model and the harness that runs it configurable. Harnesses have their own behavior, and a team may want to write one that builds in organizational context. Swappable components let the team test those choices against its own work.

- Orchestration and access. The orchestrator moves work through the configured stages. APIs and MCP let people and other agents use the factory where work already happens, including Slack, Linear, Jira, and GitHub.

04

What Warp declares in code

In Warp’s example, the factory declaration ties together policies, repository access, triggers, and a workflow blueprint. Which repositories can a run reach, what starts it, and where does the work go next? The repository settings describe its access, the triggers govern when it starts, and the blueprint describes how the work proceeds. Other factory components have their own code definitions. 10:53

05

From a team-wide view to one Slack session

Warp’s live view gathers coding-agent activity across the team, with the immediacy of a shared Google Doc. What can a teammate see about one run? The demo follows a session started from Slack. From its entry, Lloyd can open the agent conversation, see the attached artifact, and inspect what the agent generated while the work is underway. 12:04

Central storage also gives Warp a way to measure its work without installing instrumentation on every developer’s laptop. Cycle time and throughput describe how work moves. Cost tracks what the runs consume. Human interactions per pull request give the team a way to see how much participation the workflow still needs.

06

An online eval for unnecessary tests

An online eval scores sessions from everyday work. As coding agents run, the factory records their outputs. A separate agent can inspect those outputs and score a chosen dimension. The factory design also calls for tracking which stage each run has reached in its configured workflow, so the team can follow progress as the outputs accumulate.

Do the tests an agent added cover anything new? Warp uses an eval that looks for redundant tests because coding agents sometimes write tests the team considers unnecessary. A flag gives the team a session to investigate and a specific question to ask about it: what prompted the agent to add those tests? The scoring rubric is unspecified. 13:54

07

From a pattern of failures to a pull request

Warp calls the next step self-improvement. A diagnosis agent reads the eval scores, looks for patterns across failed cases, and suggests a fix. In the redundant-test example, that would mean looking across flagged sessions for a recurring reason agents add unnecessary tests. The proposed fix takes the form of a pull request against the factory definition, where the team can review the configuration change as code.

Where does a run record turn into a proposed code change? The score is the handoff. The live view helps someone inspect an individual session, and the metrics summarize activity across sessions. The evaluator’s output gives another agent a way to choose which failures to examine together before editing the factory definition.

How recorded runs lead to a proposed factory change Recorded sessions feed three distinct uses. The eval branch carries a score into diagnosis. The factory definition gives the resulting pull request a concrete place to make the proposed change. - Recorded runs — Conversations, generated outputs, and artifacts from coding-agent sessions. - Live team view — Open an individual session and inspect its conversation and artifacts. - Operational metrics — Measure cycle time, throughput, cost, and human interactions per pull request. - Online eval — A separate agent scores the output on a dimension such as test redundancy. - Diagnosis agent — Look for recurring patterns across failed cases and suggest a possible fix. - Factory definition — Code that describes the factory and its workflows. - Pull request — A proposed edit to the factory definition. - Recorded runs → Live team view (Supplies session details) - Recorded runs → Operational metrics (Supplies run data) - Recorded runs → Online eval (Supplies recorded output) - Online eval → Diagnosis agent (Passes scores for investigation) - Diagnosis agent → Pull request (Turns a suggested fix into a proposal) - Factory definition → Pull request (Supplies the code to edit)

08

Replay the same work against different configurations

A benchmark starts with tasks drawn from the team’s own work. Replay the same set against different models, harnesses, or factory configurations to see how each setup handles those tasks. For a skill the team is considering removing, the comparison is the existing configuration and a version with that skill removed. Keeping the task set and other settings fixed makes the effect of that edit easier to judge.

How much quality does each model deliver for its cost on the benchmark tasks? Warp’s plot puts the desirable results in the upper left, where quality is higher and cost is lower. Moving up and to the right would buy better results at greater expense. The example leaves the task mix and the quality measure unspecified. 16:44

09

The engineering work behind Warp’s gains

Lloyd reports that Warp increased throughput and reduced cost, with the size of both gains unspecified. Warp keeps a performance baseline, scores runs, benchmarks alternatives, and tests changes as an ongoing practice. Running cost is one reason the team keeps repeating the work.

There’s some anxiety in handing more of the code writing to agents. Lloyd recognizes it and still sees the work as a continuation of the engineering skills he spent his career learning. Someone has to decide which failure matters, what to measure, and whether a change helped. The engineer also still owns the product question Lloyd raised earlier. Does what ships solve a real problem for the customer?

要点总结

  • Version the factory’s agents, triggers, workflow, integrations, and execution settings so the team can test, review, and roll back changes to how work runs.
  • Recorded sessions give online evals something to score. When failures recur, a diagnosis agent can look for a pattern and propose a pull request against the factory definition.
  • Replay the same real tasks when comparing model, harness, or configuration changes. Examine cost and quality together to see what a higher score costs on the work the team actually does.

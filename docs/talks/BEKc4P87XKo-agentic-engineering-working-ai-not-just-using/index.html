智能体工程：与 AI 协作，而不只是使用它

与编程智能体有效协作，始于决定委派什么、精心准备它们的上下文，并在假设变成代码之前审阅调研和计划。

熟悉 Git、pull request 和编程智能体的基本用法，有助于应用这套工作流。

01

你能解释你的 AI 工作流吗？

你在工作中怎么用 AI？如果只回答“它让我写代码更快”，背后的工程决策其实一个都没讲清楚。你把什么交出去？自己留下什么？这条线又怎么划？Brendan O’Leary 一开场就抛出这几个问题，因为光看用没用 AI，看不出一个团队有没有真正好用的协作流程。

O’Leary 估计，90% 的工程师用过 AI 工具，大概一半在经常用。这些数字他没有给出调查来源。他真正关心的是：这些使用是否只是一整天不停地接受补全？工程师能不能讲清楚自己是怎么和这套系统协作的？

他勾勒的演进过程里，变的是每次交出去的工作粒度：

| 阶段 | 开发者交出去的 | 拿回来的 | | --- | --- | --- | | 2020 年代初：自动补全 | 半行代码或一个函数签名 | 一段建议的续写 | | 2022 年：Copilot 类助手 | 一段函数描述 | 一种可能的实现 | | 2025 年起：智能体 | 一项任务 | 文件改动、测试结果，可能还有一个 pull request |

按他的说法，GitHub Copilot 让代码生成变得普遍可用。后来的转变，是从“建议代码”走向“执行一连串步骤”：拆解任务、找出受影响的文件、修改、跑测试，再把成果交回来审查。

O’Leary 引用了 Flask 作者 Armin Ronacher 的一个区分：“使用”机器和“与机器协作”是两回事。锤子拿起来用，用完就放下。编码智能体在工作流里的位置不一样：在你两次介入之间，它能自己把活往前推。他半开玩笑地打了个比方：这就像多了一位读遍 Stack Overflow 所有回答的工程师同事。知识面广固然有用，但判断由谁来做，这个问题并没有因此解决。

02

快速、博学，却自信地出错

不妨把智能体想成一位精力充沛、热情满满、博览群书的初级开发者，只是它错了也会说得信心十足。它干活快，不容易累，同一段代码重写六遍也毫无怨言。它熟悉许多语言、框架和模式。这些长处让它成为得力的帮手，却替代不了你的判断。

技术上正确的代码，放到具体场景里仍可能是错的。 智能体未必知道某个需求背后的业务约束，也不知道团队三个月前为什么选了某种架构。把这些理由交代清楚，本身就是指挥工作的一部分，不是写代码请求之外可有可无的补充。

O’Leary 提到，Ronacher 说借助机器，自己每天多出了 30% 以上的时间。演讲没说这个数字怎么测的，也没有按任务拆开；他把这份自述的收益归结为清楚哪些该委托、哪些该自己留着。真正有价值的习惯是有选择地委托，然后指挥、审查，而不是来什么建议就收什么。

03

上下文可能变成负担

所以，第一项实用技能是上下文工程（context engineering）。O’Leary 借用了 Andrej Karpathy 的说法：上下文窗口里该填的，是智能体下一步需要的东西。如果工作流每次都重新发送对话历史，早先的内容就会在后续每次请求里再当一遍输入。上下文越堆越多，带来的是反复发生的 token 成本，而不只是材料第一次进入对话时的一次性开销。

O’Leary 把上下文窗口占用约 50% 当作质量开始下滑的警戒线，但这并不是一个经过验证、适用于所有模型的阈值。他担心的是，可用的工作空间可能在你察觉之前就没了：比如已启用的 MCP server，哪怕能力和当前任务毫不相干，也可能把工具信息塞进上下文。落到操作上，就是同时盯着上下文用量和输出质量。

内容太多只是问题之一。不相干的任务、过时的代码注释、已经放弃的决定，都可能污染工作上下文。假设智能体在一段很长的对话里一直沿着错误思路走，你纠正了它，那段历史并不会消失。早先的决定仍会影响后面的输出，被否掉的写法也可能悄悄溜回实现里。

如果反复引导都没法把工作拉回正轨，就开一个新会话。目的是别让失败的路径跟着之后的每次请求一起往前走。上下文只有帮得上下一个决定时才有用；超出这个范围，它只会同时推高成本和混乱。

04

持久化、选择、压缩与隔离

管理上下文有四种互补的操作：

- 持久化（Persist）： 把需要长期保留的信息放在对话之外，比如草稿板、记忆文件和 AGENTS.md。这样信息随时可用，又不必把整个探索过程都留在当前窗口里。 - 选择（Select）： 只引入当前这一步需要的东西。有意识地用 @ 引用文件，关掉不需要的 MCP server，仔细挑选喂给智能体的数据。 - 压缩（Compress）： 一轮调试排查确定了问题、也拿出了解决方案之后，把结论总结下来。实现阶段要的是排查结果，而不是一路上的每一轮对话。 - 隔离（Isolate）： 把不相干的任务分到不同的会话或智能体里，免得它们的上下文混在一起越积越多。O’Leary 把这一好处和最近兴起的并行智能体工作流联系了起来。

这几种操作既保住了有用的知识，又能控制哪些内容进入下一次请求。

05

当一个占位符变成了需求

日常的工程管理里也有同样的问题。O’Leary 职业生涯早期在一家医疗软件公司带工程师。当时 iPad 刚发布，看上去很适合用来采集病史，也就是病人在诊所一遍遍填写的那些表格。他用线框图工具 Balsamiq 设计了界面方案。这个工具故意做得很粗糙，界面里用的是 Comic Sans 字体和笑脸占位图。

他把线框图交给暑期实习生，作为一个从零开始的新项目。几周后，实习生交回一个能跑的原型，Comic Sans 和占位图原封不动。他们实现的正是规格里画出来的东西。O’Leary 把责任揽到了自己身上：哪些细节重要、哪些只是占位、这个界面要解决什么问题，他都没讲清楚。

交接给智能体，同样要分清哪些是需求、哪些只是附带的材料。O’Leary 把日常习惯归结成一个简短流程：

1. 每个会话只做一项任务，盯着上下文用量。 2. 如果工作跑偏，让当前智能体给接手的智能体写一份总结。 3. 读这份总结，和你理解不一致的地方都改过来。 4. 用核对过的总结开启新会话。

这份总结本身也是一份要审查的交付物。否则，重开会话可能只是把同样的误解搬进一个更小的上下文。

06

为什么调研要先于代码

在 Agentic Engineering for Humans 收录的工作流里，O’Leary 反复提到的是研究—计划—实现（research–plan–implement）。它针对一个常见错误：人和智能体都还没弄清新功能怎么融入现有系统，就让智能体马上动手实现。

加入 Kilo Code 时，他否决了一个网站演示方案：只输入一句提示词，然后看代码哗哗地往外冒。画面很唬人，但生成速度会掩盖错误的假设。随之而来的返工浪费时间，还可能让开发者认定这些工具没用。

经验也会过时。O’Leary 拿早期那些“Will Smith 吃意大利面”的视频提醒大家，AI 能力变得有多快。编码智能体同样值得重新评估，但要在给它成功机会的条件下评估：先就问题达成共识，再列出明确的步骤，最后才生成实现。他转述了 Dex Horthy 的警告：研究阶段的一个小错，可能膨胀成一大堆烂代码。审查的力气应该花在上游，赶在错误膨胀之前。

07

把理解变成一份可执行的计划

研究阶段要放在一个没法抢先改代码的模式里做。演讲中，Kilo 的 Ask 模式可以聊天、可以读取允许的文件，但不能写文件。有了这个限制，眼下的目标就始终是理解系统。要弄清现有行为、相关文件、既有模式、与类似功能的差异、数据流和边界情况。还可以借智能体的知识面做头脑风暴，找出你可能漏掉的情况。

这一步的产出是一份研究文档，你要读过，并认可它准确反映了问题。这是第一道审查关卡。解释得流畅还不够；文档要先和你对系统的理解一致，才能拿来当计划的基础。

接下来，把打算做的改动写明白：

1. 列出要新建或修改的文件。 2. 描述步骤，以及对系统的预期影响。 3. 说明哪些在范围内，哪些必须保持不变。 4. 指出要新增或修改的测试，以及用来验证结果的命令。 5. 把这些指令记进计划文件，通常放在 Plans 目录里。

代码片段有帮助，但不是必需的；计划不必提前把实现写出来。讲计划的那张幻灯片里还列了回滚策略，把撤回改动当成准备工作的一部分，而不是事后才想起来。

计划写得足够清楚，实现阶段就可以交给更小、更快或更便宜的模型。推理并没有消失，而是集中到了研究和计划阶段。这样在大量代码依赖它之前，人还来得及检查。

08

把 Git 当作第一道审查

实现阶段要开一个新会话，把审查过的计划当作执行上下文。这样就不会把整段研究对话拖进写代码的阶段。仔细审查改动，勤提交，让每一步增量都容易看懂。

O’Leary 曾在 GitLab 工作。他把本地 Git 审查当作和智能体之间的第一轮 pull request 审查，之后才把真正的 PR 发给同事。几条命令就能把这个习惯落到实处：

``bash git status --short git diff --stat git diff # 审查完改动后，只暂存想要提交的 hunk。 git add -p git diff --cached ``

工作区 diff 显示改了什么；交互式暂存挑出想要的部分；暂存区 diff 显示下一次提交会包含什么。提交前，先跑一遍计划里列出的验证命令。

人的精力投在研究和计划阶段，回报最高。 到了实现阶段，难做的决定应该都已经摆在明面上。O’Leary 又回到 Horthy 的说法：AI 会放大你已经做过的思考，也会放大你没想透带来的后果。实现越快，前期决定的质量就越关键。

09

配置角色、规则和自主程度

智能体的配置可以给这套工作流加固。O’Leary 让 Ask 对应研究，Architect 对应计划，Code 对应实现。再用仓库级、工作区级或全局规则，写下这些角色都要遵守的约定。项目要求如果没人写下来，智能体就没法可靠地遵守。

智能体可以不被打断地干多少活，要单独决定。多个智能体可能需要各自的 worktree，这样它们的改动能在提 PR 之前先在本地合并。审批设置应该区分读取工作区内和工作区外的内容，也要区分读文件和跑测试或其他工具。先从你理解的权限开始，等经验让你看清哪里值得介入，再回头调整。

三层配置各有用途：

| 层级 | 用途 | 典型内容 | | --- | --- | --- | | 模式 | 定义当前角色 | 研究、计划、实现 | | AGENTS.md | 提供反复用到的项目指引 | 约定、构建命令、测试要求 | | Skills | 需要时提供一套工作流 | 可复用的任务手册 |

AGENTS.md 只写智能体必需的项目知识：怎么构建和测试，遵守哪些约定，提交前检查什么。把它当成写给智能体看的项目 README，而不是什么指令都往里塞的仓库。

Skills 更适合反复出现的流程，比如用 Remotion 做动态图形，或者整理每日、每周、每月的变更日志。用到这套流程时，才把详细说明加载进来。O’Leary 介绍这一对比时用的名字是 SKILLS.md；Agent Skills 规范 用的则是单数文件名 SKILL.md。实际区别在于：一边是精简的常驻指令，一边是针对具体任务的手册。

10

让有用的上下文易于提供

基本工作流用顺手之后，界面上的快捷操作能让你坚持下去更省力。O’Leary 举了几个 Kilo 的例子：

- 精准引用： 用 @ 引用文件、提交和终端输出。 - 会话命令： 用斜杠命令开始新任务，或压缩越来越长的上下文。 - 选中代码： 在 VS Code 里选中一段代码，右键添加到 Kilo Code，然后提问或要求做针对性修改。 - 自动补全： 补全不只用于代码，也可以用于写提示词。

有了这些方法，就能精确地提供工作材料，不必每次请求都手动重新拼一遍。

同样的协作方式正从 IDE 扩展到 CLI、移动端、云端智能体和 Slack。在 O’Leary 看来，变的是智能体在哪儿能用：工作在哪里讨论、在哪里下达，智能体就能在哪里参与，而不只是有人坐在编辑器前时才派得上用场。

11

加上任务真正需要的工具

Model Context Protocol（MCP）提供了一种给智能体开放更多工具的方式。模型的 token 输入和输出可以嵌进一个更大的循环，在循环里通过工具调用查看或影响环境，比如跑测试。GitHub MCP server 把这个环境扩展到 pull request、评论和 issue。Context7 提供最新的框架文档，补上模型训练截止日期之后库的变化。

有好处，也就多了一道上下文管理的选择题。O’Leary 提醒，开放出去的工具描述可能变成每次都要发送的提示词输入。具体占多少，取决于客户端和它的工具加载策略；并不是每种 MCP 实现都免不了这笔前置开销。不过，用不上的集成仍然值得审视。在他的例子里，如果只做前端、不碰数据库，Postgres MCP 连接几乎帮不上忙。它的工具信息既占上下文，还可能引着智能体在不该碰数据库的地方去操作数据库。做这类任务时，把它关掉。

内部平台的 API 不一定非得配一个定制 MCP server。O’Leary 给了四种做法，按涉及的信息和工作流来选：

| 已有材料或需求 | 集成方式 | | --- | --- | | 已有 API 规范 | 使用 OpenAPI 或 Swagger 规范 | | 文档需要可读的本地版本 | 在仓库里存放 Markdown | | 信息经常变动 | 让智能体去拉取参考 URL | | 工作流跨越多个步骤和系统 | 考虑定制 MCP server |

Markdown 可以写进 AGENTS.md，也可以放在仓库里另一份被引用的文档中。实时参考链接适合那些用的时候必须刷新的信息。当智能体需要跨系统协调操作，而不只是读一份 API 说明时，定制 server 才派得上用场。

12

让工作保持可审查，然后多练几次

不管上下文由什么工具提供，都要把你自己的改动和智能体的工作分开，并像审 pull request 一样审查它的贡献。最后一张技术幻灯片对比了两种情形：互相编辑冲突，和在 Git worktree 里并行工作。分开之后，智能体改了什么一目了然，你可以像审初级工程师的 PR 那样仔细检查。

产品部分收尾时，O’Leary 谈到 Kilo 正扩展到更多工作场景，以及它当时宣布的重点：OpenClaw 和 KiloClaw，目标是让 OpenClaw 智能体用起来更安全。他是在征求大家对 Kilo 的反馈，并没有给出安全设计或部署流程。如果你现在还在关注这条产品线，请注意：截至 2026 年 8 月 28 日查阅的 KiloClaw 文档 显示，该服务已进入生命周期终止阶段，不再向新用户开放，支持也即将结束。

最后的建议是：选一个工具，多练。对模型的信任要靠经验来校准，摸清它哪些事做得好，哪些地方仍然需要你来判断。试试研究—计划—实现这个循环，复盘结果，再调整下一次交接。O’Leary 指出的回报，是一些资深工程师说自己重新找回了工作的乐趣：把繁琐的活交出去，把更多注意力留给更难的工程问题。

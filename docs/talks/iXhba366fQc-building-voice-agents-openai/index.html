What is an agent?

Agents are AI systems that independently accomplish tasks on behalf of users.

An agent is an AI application consisting of a model equipped with instructions that guide its behavior, access to tools that extend its capabilities, encapsulated in a runtime with a dynamic lifecycle.

import { Agent, run, tool } from '@openai/agents';

const getWeatherTool = tool({

Voice agents provide a wide range of benefits

• More flexible than traditional IVRs (no need to outline complex phone trees, multilingual). Let human agents focus on complex cases

• More information dense and personalized than just text by introducing emotions
• Can act as an API to the real-world by leading conversations with other businesses

Strengths of chained voice agents

幻灯片原文
A chained agent can wrap an existing text agent with audio while keeping model inputs and outputs visible. The slide also highlights access to text models and faster, cheaper transcript-based evaluations.

[4:53](https://www.youtube.com/watch?v=iXhba366fQc&t=293s) [Chained voice agent strengths include control and visibility, model access, reuse of existing components and easier evaluations.](https://assets.ai.engineer/sites/aiecode2025/sha256/233afd981e4ada0e9bc2784f6a3048031a622bc78d1cbb445ee2e4c03e6eff86.webp)

Strengths of “chained” voice agents

High control and visibility
The text in/text out modality makes it easier to analyze exactly what the LLM acted on

Broader model access
Advanced models like o3 and o4-mini are only available in text modalities

Reuse existing components
Taking existing proven agents / RAG pipelines makes building initial voice agents easier

Easier to run evals on
Store and anonymizing transcripts and generating synthetic data is faster and cheaper

Challenges of chained voice agents

Chained agents must track what the user heard before an interruption so the transcript stays accurate. Calling multiple models adds latency, while transcription loses audio context.

Challenges of
“chained” voice agents

Turn detection and interruptions
Detecting when a user is done speaking and handling interruptions effectively

Latency
Dealing with the overhead that comes from calling multiple models

Audio context
Losing the full audio context from transcribing the conversation’s audio before handling it

Strengths of speech-to-speech

幻灯片原文
Direct audio processing skips speech-to-text and text-to-speech, reducing latency while preserving cues such as tone and voice. It also makes interruptions easier to handle.

[6:42](https://www.youtube.com/watch?v=iXhba366fQc&t=402s) [Slide describes fluid conversations, lower latency, and vocal context understanding as strengths.](https://assets.ai.engineer/sites/aiecode2025/sha256/52694d1aaeb5b2f4fb2efdd741aa77e9e099402e9fe5d4c5efeda93ec2e272d0.webp)

Strengths of speech-to-speech

Natural fluid conversations
The native audio processing makes implementing conversational aspects like interruptions easier

Lower latency
By skipping the STT and TTS steps you are achieving faster response times giving more room for other features like function calls

Vocal context understanding
The model processes audio directly and can therefore capture audio nuances that are lost in transcripts

Challenges of speech-to-speech

幻灯片原文
Speech-to-speech agents make it harder to reuse specialized text-based agents, handle complex decisions, and manage the state of an ongoing conversation.

[7:01](https://www.youtube.com/watch?v=iXhba366fQc&t=421s) [Slide identifies complex decision making, reuse of existing capabilities, and complex states as challenges.](https://assets.ai.engineer/sites/aiecode2025/sha256/c25ad933ebe3d79120fed502e98898c3075807a779ff99faa4f04644608b11b6.webp)

Challenges of speech-to-speech

Complex decision making
The speech-to-speech model does not support the level of reasoning that more advanced models like o3 or o4-mini support.

Reusing existing capabilities
If you’ve been investing in specialized agents that rely on specific models for certain parts of a text-based flow, it’s harder to reuse them.

Dealing with complex states
Instead of building chains that can represent different parts of a workflow you are dealing with an agent that has an ongoing conversation.

用 OpenAI 构建语音智能体

一步步构建一个浏览器语音智能体：从带类型的工具和安全会话，到打断处理、专家交接、推理委派、审批关卡，再到感知音频的评测。

熟悉 TypeScript、异步函数、React ref 以及基本的客户端–服务端认证，有助于理解编码示例。

01

一个语音智能体需要什么才能完成任务？

What turns a conversation with a model into a system that can accomplish a task for someone? Start with a model, give it instructions and tools, and put those pieces inside a runtime that manages their lifecycle. That is the working definition behind Dominik Kundel’s workshop. Participants begin by downloading the starter repository’s dependencies before coding: even a small application needs preparation when everyone shares the venue’s internet connection.

The workshop coincides with the June 3, 2025 launch of the TypeScript Agents SDK, the counterpart to the Python SDK. Its primitives include handoffs, guardrails, streaming, tools, MCP support, and tracing, plus human approval with resumability. The examples here follow that launch-era workshop; later API distinctions appear where they affect implementation.

Native voice support applies those same primitives to a conversation that is continuously receiving and playing audio. The runtime tracks history, supports audio replay in traces, executes tools, handles handoffs and output guardrails, and manages interruptions. It supports WebSockets for server integrations such as telephone agents and WebRTC for browser applications—the transport used in this workshop.

02

选择从语音到行动的路径

Voice can make software accessible to people who would struggle with its conventional interface. It also carries tone and emotion alongside words. A voice agent can even call a business that has no software API, using the conversation itself to get something done. Those benefits lead to an architectural choice: wrap a text agent with speech models, or let a model work directly with audio.

In a chained architecture, speech-to-text converts the user’s audio into text, a text agent processes it, and text-to-speech reads the result. This makes an existing text agent easy to reuse and leaves the application free to choose among text models. It also exposes the exact text entering and leaving the agent. The difficult part is coordinating the stages: every stage adds latency, transcription loses some audio context, and an interruption requires reconciling the generated text with what the user actually heard. Otherwise, the agent may believe it delivered information that never reached the listener.

A speech-to-speech architecture consumes audio directly and can generate speech and tool calls without transcription as an intermediate reasoning step. Removing the separate speech recognition and synthesis stages reduces the latency those stages introduce and preserves access to tone. The tradeoff in the workshop’s models is that complex decision-making and reuse of specialized text agents are harder.

| Architecture | Main advantage | Main engineering burden | | --- | --- | --- | | Speech → text agent → speech | Reuse and inspect text workflows | Coordinate latency, playback, and history | | Native speech-to-speech | Direct audio understanding and delivery | Scope complex reasoning carefully | | Speech-to-speech with delegation | Combine conversation with specialist reasoning | Design the tool boundary |

Delegation adds a third option: keep a frontline agent talking to the user, and give it tools that invoke reasoning models such as o4-mini or o3. The diagram’s refund, order-cancellation, and product specialists sit behind that tool boundary.

03

一个流畅的退款回答仍然需要检查

The first live conversation starts with a weather request. The agent announces a transfer to a weather expert, then says it can help directly and asks for a location. Kundel supplies San Francisco while demonstrating interruption handling, and the agent responds that it is sunny. Even this simple exchange exercises routing language, a missing argument, and overlapping speech.

The next request needs a backend decision. Kundel describes a skateboard he tried using, discovered he was bad at riding, and now wants to return despite some scratches. A refund tool is intended to invoke o4-mini, but the initial request gets a referral to customer service. He tries again with an explicit refund request; repeated greetings, network trouble, and room echo complicate the exchange. Eventually the agent announces an assessment and approves a full refund, explaining that the skateboard arrived damaged. That explanation changes the facts: the customer described scratches after trying the skateboard, not damage on arrival. The demonstration shows delegation taking place, but the spoken approval does not establish that the refund decision was correct or that a real payment was issued.

Kundel reports that the o4-mini call finished while the agent’s spoken acknowledgement was still playing. That overlap is useful: generated speech takes time to play, and the application can use that interval for backend work. A short announcement of the next task can reduce perceived waiting without requiring the voice model itself to perform the reasoning.

The traces interface provides a way to inspect what happened beneath the answer. Kundel opens the voice trace, checks tool inputs and outputs, replays audio, and follows the execution into the o4-mini agent. That backend agent received the prior conversation transcript plus request-specific information. Because both sides use the Agents SDK, the trace connects the conversational frontend to the reasoning backend—the path needed to investigate a mismatch such as the arrival-damage rationale.

04

先划定任务范围，再设计对话

Before writing the application, define a small goal and give the agent only the tools needed to achieve it. Evaluating a text agent is already difficult; voice adds delivery and timing to the problem. Once the first use case works, additional specialists and handoffs can expand coverage, while unsupported requests can go to a human. Build evals and guardrails early enough that they guide this expansion. Kundel points to Lemonade’s custom dashboard and conversation replay as an example of inspecting the whole customer experience.

The selected voice is only part of the agent’s personality. Generative speech models also respond to instructions about emotion, role, and delivery. Kundel uses the openai.fm demonstration to illustrate how prompting changes the reading of the same text, rather than treating the voice preset as the entire design surface.

Lemonade’s interface is customer-built, not an embedded OpenAI dashboard. Realtime audio data and events give an application material for its own interface. In the workshop, Kundel says the Traces dashboard has neither an API nor iframe embedding, and transcripts appear only when transcription is enabled; it was absent in the trace he checks during this exchange. Raw event handling, application history storage, and platform tracing are separate concerns, which become explicit in the later history example.

Conversation instructions can also describe states and transitions in JSON, much like a script for a human service agent. That gives the model an explicit process to follow instead of only a personality. Kundel mentions a custom GPT for drafting those scripts and promises the links and slides in Slack. The coding portion then starts from minimal Next.js boilerplate with dependencies already installed; headphones help participants test simultaneously, and Anoop handles technical questions through Slack. The first exercise opens index.ts and imports Agent from @openai/agents.

05

构建一个文本智能体并给它一个带类型的工具

The first agent needs a name and instructions. The name, My agent, makes it identifiable in traces. Calling run starts the execution loop, including any tool calls and output validation; finalOutput contains the last agent’s output.

```typescript import { Agent, run } from '@openai/agents';

const agent = new Agent({ name: 'My agent', instructions: "You're a helpful assistant.", });

const result = await run(agent, 'Hello, how are you?'); console.log(result.finalOutput); ```

Kundel runs this with the starter’s exercise 01 script, correcting his initial generic start command. He describes GPT-4.1 as the default at the time, then shows how setting model: 'o4-mini' changes the model without changing the surrounding execution pattern.

A tool adds an operation the model can request. Its Zod schema serves two purposes: it describes valid arguments to the model and validates the values supplied at execution time. TypeScript can also infer the argument types from that schema.

```typescript import { Agent, run, tool } from '@openai/agents'; import { z } from 'zod';

const getWeather = tool({ name: 'get_weather', description: 'Get the weather for a city.', parameters: z.object({ city: z.string() }), async execute({ city }) { return The weather in ${city} is sunny.; }, });

const agent = new Agent({ name: 'My agent', instructions: "You're a helpful assistant.", tools: [getWeather], });

const result = await run(agent, 'What is the weather in Tokyo?'); console.log(result.finalOutput); ```

This weather function returns a fixed sunny response. The useful behavior is the tool round trip: the model selects the tool, supplies Tokyo, receives the result, and uses it in the final answer. Kundel opens the trace to verify each part of that sequence rather than inferring tool use from the answer alone.

06

连接浏览器智能体而不暴露 API 密钥

Moving to voice introduces a distinction between agent configuration and session lifecycle. RealtimeAgent is a specialized agent configuration with a more restricted set of fields. RealtimeSession manages the live interaction: incoming audio, model responses, outgoing audio, tools, handoffs, and guardrails. The session does substantially more than run a text agent’s tool loop.

Exercise 02 puts the interface in a Next.js page.tsx. Because this agent runs in the browser, it must not receive the application’s long-lived OpenAI API key. The workshop’s server-side token.ts creates a Realtime session and returns its short-lived client secret. The browser uses that ephemeral credential for WebRTC. A server-hosted integration, such as a Twilio application, can instead use the regular API key within its server environment. The realtime classes come from @openai/agents/realtime, a subpath of the same package.

The Connect button follows a short sequence:

1. Obtain the ephemeral credential through a Next.js server action, or an equivalent request to your backend. 2. Construct RealtimeSession with the initial agent and the chosen realtime model. 3. Call connect with the ephemeral credential. 4. Keep the session in a React ref so re-renders do not recreate it. 5. On Disconnect, close the session and release the connection.

Kundel selects the launch-day model and describes its improved tool calling. The important lifecycle detail is the ref: session.current holds a live connection, not a fresh object to construct on every render.

The connection logic can be kept separate from the framework-specific token endpoint:

```typescript import { useRef } from 'react'; import { RealtimeAgent, RealtimeSession, } from '@openai/agents/realtime';

const agent = new RealtimeAgent({ name: 'Voice Agent', instructions: "You're a helpful assistant.", });

export function useVoiceSession() { const session = useRef<RealtimeSession | null>(null);

async function connect(ephemeralKey: string, model: string) { session.current?.close(); const next = new RealtimeSession(agent, { model }); session.current = next; try { await next.connect({ apiKey: ephemeralKey }); } catch (error) { next.close(); session.current = null; throw error; } }

function disconnect() { session.current?.close(); session.current = null; }

return { connect, disconnect }; } ```

The browser test produces a spoken greeting without explicit microphone or speaker setup. The SDK handles those defaults and permits custom audio sources. On a server, sendAudio accepts incoming buffers and audio events expose generated buffers for the application’s own transport.

07

追踪听者实际听到了什么

The same weather tool can now be attached to the realtime agent. Zod validation matters particularly in this launch-era example because the realtime model does not support strict mode: validating arguments protects the execution boundary, but does not make generation itself schema-strict. The San Francisco weather request succeeds through the reused tool.

The next test asks the agent to count slowly to twenty. Kundel stops it around six, then asks how far it counted; it answers six. He describes the timing as approximate. The significant behavior is that the agent does not assume the entire planned response was delivered. For a customer-service agent reading a policy, unheard speech must not become assumed shared knowledge.

RealtimeSession handles the interruption events, while transport_event exposes the underlying event stream for logging and custom logic. Applications retain the ability to read and send lower-level events. Kundel demonstrates this in the browser developer tools and pushes the code so participants can pull the updated version.

The interface then renders conversation history. Speech-to-speech still works directly on audio; the transcription runs alongside it. In the workshop SDK, transcription is enabled by default and can be disabled, whereas direct API usage requires enabling it. History contains both messages and tool calls, so a transcript-only interface filters for messages before displaying them. The browser shows the greeting and the San Francisco weather exchange beside the code that performs this filtering.

Interruption creates an important limitation in that displayed history: the launch-era implementation removes an interrupted output’s transcript rather than trimming it to the exact words heard. Removing it avoids showing the full generated text as if it had all been spoken. The corresponding trace still helps inspect the conversation and weather call.

08

把显示的历史与会话上下文分开

There are three distinct places to think about conversation data:

- Application history: An in-memory array on the client, updated from API events. Listening to history_updated lets the application persist its own copy. - Platform traces: Stored on OpenAI when tracing is enabled. Kundel clarifies that SDK tracing is enabled by default, can be disabled, and is unavailable to zero data retention customers. - Realtime session context: The API’s authoritative conversation state. The client’s displayed history is a copy, not the authority deciding what enters the next model generation.

This distinction prevents a transcript UI from being mistaken for either durable application storage or complete control over the model’s context.

Usage events provide another view of the session. Kundel locates detailed token usage while examining response.done, allowing the application to track consumption without seeing the exact context used for every subsequent generation. The audio-format question identifies PCM16 in the example and μ-law as an option useful for telephone audio. A follow-up asks whether usage rolls up intermediate tool calls and where tool-output usage appears. Although Kundel describes tool calls as responses, he leaves the precise accounting question for follow-up.

Adapting an existing text agent to voice requires attention to waiting and scope. The refund example uses a tool to invoke a separate o4-mini agent and return its result. Prompting the frontline agent to announce its next task allows playback to overlap that work; it does not mean a response can absorb arbitrary new information halfway through generation. Interruption is a separate path. Long prompts also make the realtime agent’s decision harder, so split distinct steps into focused agents and handoffs.

When the discussion returns to memory, the visible weather conversation is still just a history view. updateHistory changes session context by sending events that add or delete items in the Realtime API. A previous-item ID can position a new item within the conversation. This supports explicit context editing, but the workshop does not provide a separate advanced long-term memory system.

For language-learning applications, Kundel says the model can switch languages and that customers use it in that domain, but he offers no established recipe for low-fluency speech, broken grammar, or weak pronunciation. The interruption callback also has a narrower contract than an audience member expects: it does not carry the last transcript. The application can inspect the current history when the callback runs, and tool execution context separately includes history for tools that need conversational information.

09

让工具保持响应，并给副作用设置关卡

The shared tool syntax also provides a bridge to backend systems over HTTP. For a slow operation, Kundel recommends a short initial call that starts the job and returns a task ID, plus a separate tool that checks status. This avoids leaving the conversation waiting inside one long tool execution. The voice agent can return to the task when useful instead of holding the entire response open.

needsApproval adds a gate before execution. It can be a predicate for conditional approval or an always-required setting. When the SDK emits tool_approval_requested, the application can inspect the request and explicitly approve it. In the Seattle weather example, Kundel wires up the approval event but always approves; the code does not actually branch on the user’s confirmation result. It demonstrates the interception point, not a finished consent interface.

Approval is an application-side execution boundary. The model requests an operation, and the SDK pauses that operation before side effects occur. It does not automatically ask for spoken consent, and it is not merely an instruction telling the model to behave cautiously. Approval is recorded in local context so the pending operation can proceed. Intercepting before execution avoids having to undo work performed while a confirmation was still unresolved.

切换当前智能体，保留对话

A handoff is a specialized tool call that changes the active configuration within the existing session. It replaces instructions and tools so a specialist can take over a focused task. The underlying voice remains fixed once the first agent has spoken, even if another agent configuration specifies a different voice.

For the weather specialist, move getWeather off the initial agent and give it to a new RealtimeAgent. A handoffDescription tells the initial agent when the specialist is useful; handoffs makes that destination available.

```typescript import { RealtimeAgent, tool } from '@openai/agents/realtime'; import { z } from 'zod';

const getWeather = tool({ name: 'get_weather', description: 'Get the weather for a city.', parameters: z.object({ city: z.string() }), async execute({ city }) { return The weather in ${city} is sunny.; }, });

const weatherAgent = new RealtimeAgent({ name: 'Weather Agent', instructions: 'Help with weather questions. Speak with a New York accent.', handoffDescription: 'This agent is an expert in weather.', tools: [getWeather], });

export const voiceAgent = new RealtimeAgent({ name: 'Voice Agent', instructions: "You're a helpful assistant.", handoffs: [weatherAgent], }); ```

11

把一道谜题委派给服务器端的推理智能体

Delegation keeps the frontline agent in place and calls another agent for a result. Kundel creates a server-side text agent called Riddler, using o4-mini with instructions to generate riddles for a target demographic and topic. It needs no tools of its own. An exported runAgent function accepts those inputs and returns the agent’s output. In Next.js, 'use server' marks the server-action file.

```typescript 'use server';

import { Agent, run } from '@openai/agents';

const riddler = new Agent({ name: 'Riddler', model: 'o4-mini', instructions: 'You are excellent at creating riddles based on a target demographic and topic.', });

export async function runAgent(demographic: string, topic: string) { const result = await run( riddler, Create a riddle for ${demographic}. Topic: ${topic}., ); return result.finalOutput; } ```

用神经 RAG 打造更聪明的 AI 智能体

一次“不要条纹的衬衫”的查询暴露了一个检索问题；当智能体需要精确的结果、丰富的上下文和完整的匹配实体集合时，这个问题会变得更加严重。

对语言模型和 Python 函数有基本了解会有帮助；文中会介绍演示中用到的检索概念。

01

“不带条纹的衬衫”应该返回什么？

像“不带条纹的衬衫”这么简单的请求，搜索引擎该返回什么？回头看看搜索的长处是怎么来的，难点就清楚了。Will Bryk 举了 1998 年 Google 的例子：搜 Australia，系统先找出包含这个词的文档，再用 PageRank 根据网页之间的链接图判断权威性。词语匹配负责找出候选，网页的结构帮着排出先后。

到了 2021 年，GPT-3 带来了另一种交互方式：用户可以用一段话描述自己想要什么，连语言上的细微差别也能写进去，然后拿到贴切的回答。有了这种体验作对照，Bryk 再看 Google 的例子就觉得很怪。搜“不带条纹的衬衫”，返回的却是条纹衬衫的图片。without 这个词改变了用户想要的结果，搜索结果却仍然只匹配那几个显眼的名词。

Bryk 认为问题出在关键词比对上。他创办 Exa 的目标，是把 transformer 的语言理解能力和搜索结合起来：既读懂请求，也读懂文档，读懂到能返回用户真正想要的东西。他说自己准备在这个问题上至少投入十年，做这场演讲时已经干了四年。

02

把 transformer 应用到搜索上

最初的投入都花在了研究上。Bryk 回忆，他们加入了 YC 2021 年夏季批次，融了约两百万美元，一半拿去买 GPU 集群。随后团队埋头研究了一年半，完全没跟客户聊过。讲这两个决定时，他特意提醒别把它们当成创业建议：创始人应该多和用户交流，只是这次创业恰好从一场艰难的技术重构起步。

研究要回答的问题是：GPT-3 背后的思路——transformer 加下一个 token 预测——能不能用到搜索上。Bryk 展示了一张 W&B 训练曲线图，回忆其中一条紫色的 run 是一次突破。团队在数据集和 transformer 架构上做了大量实验，这只是其中冒出来的几项改进之一。这张图标出了方法开始奏效的时刻；不过演讲没有说明训练目标，给出的细节也不足以复现那次训练。

03

从倒排索引到文档嵌入

举个例子，设想一个包含一万亿篇网页文档的语料库。倒排索引把词映射到包含它的文档：比如 brown 这个条目，就指向出现过这个词的那些文档。查询时，传统检索系统可以靠这些映射找出候选并排序。Bryk 明确说，这是对 Google 运作方式的简化，并不是它架构的完整描述。

另一种做法是用 embedding（嵌入向量）表示每篇文档，也就是模型学出来的一串数字。这种表示想捕捉的不只是词汇：它可以编码思想、含义，以及网上其他地方的人怎么提到这篇文档。Bryk 关于扩展的论点是：这些表示可以越做越大，表达力越来越强。他援引“苦涩的教训”（bitter lesson），主张用越来越多的高质量数据训练 transformer，产出更好的文档 embedding。这是系统扩展的方向，并没有实测证明向量越大、检索结果就一定越好。

到了搜索阶段，查询这一侧也有同样的区别：

| 阶段 | 关键词表示 | Embedding 表示 | |---|---|---| | 索引文档 | 把词映射到文档 | 把文档编码成向量 | | 表示请求 | 使用查询中的词 | 对整个请求做 embedding | | 查找候选 | 比对关键词证据 | 比对查询向量和文档向量 |

拿 shirts without stripes 来说，对整个请求做 embedding，表示就有机会保住 without 所表达的关系。Bryk 讲的是拿这个查询 embedding 去和文档 embedding 比较；至于靠什么索引结构和服务算法，让这种操作在全网规模下跑得动，他没有说。

据 Bryk 说，一年半之后，他们做出的搜索引擎针对这个请求，返回的确实是不带条纹的衬衫。这个例子是刻意挑的简单例子，但他们想要的能力远不止于此：查询可以长达一段话，里面的约束没法干净利落地压缩成几个词。

04

ChatGPT 改变了谁需要搜索

Bryk 说这个搜索引擎在 2022 年 11 月上线，还记得当时 Twitter 上反响热烈。公司那时叫 Metaphor，2024 年 1 月才改名 Exa。按他的说法，上线两周后 ChatGPT 问世，团队面对的问题一下子变了：如果人们能直接向语言模型要信息，搜索还有什么位置？

试着让 GPT-4 只凭自己记住的知识，列出旧金山工程师那些很酷的个人网站。Bryk 的意思是，这样一份清单可能根本就不在模型权重里。语言生成得再流畅，权重也不会因此变成一份完整的网络目录。

Bryk 估计 GPT-4 有两三万亿参数，权重不到 10 TB，而网页文档超过一百万 TB。这些都是他对容量的粗略估算：GPT-4 Technical Report 并未公开模型规模。他还补充说，算上图片和视频，总量还会更大；他把整个网络形容为艾字节（exabyte）级别，Exa 这个名字就由此而来。

时效性是需要检索的另一个原因。 就算模型容量大到能记住多得多的内容，网络本身也在不停变化。由此形成的检索增强生成循环很直接：语言模型在 Exa 上搜索这些个人网站，拿到外部结果，再用这些结果组织答案。光靠生成拿不到可靠的信息，就由搜索来补。

05

精确度、上下文与全面的结果

给语言模型接上搜索之后，还剩一个设计问题：这个搜索引擎，是为现在调用它的这一方造的吗？Bryk 做了个对比：人会输入简短的查询，看几个链接，在意的是结果页；AI 系统则能发出复杂的请求，飞快地分析多得多的信息。

他反对把传统搜索直接接到 AI 上，批评的是优化目标。能吸引人点击的结果，不一定是下一步计算最需要的输入。这里的 AI 指的是 AI 产品——助手连同它周围的整套工作流——而不只是单独拎出来的一个模型。这样的产品需要明确掌控返回什么信息。

第一项要求是精准命中所要的实体。设想一位风险投资人让助手找一些在做大胆尝试、有点贝尔实验室味道的创业公司。他要的输出是一份创业公司名单。有些网页读起来有趣，却没指出哪家公司符合条件，只会给智能体添额外的活。随着用户细化任务，智能体可能会加上“位于纽约”这个地点约束，再补充公司的其他特征。每一次搜索都得守住这些约束，而不是围着话题泛泛地搜一通。

第二项要求是带着积累的上下文去搜索。一个陪人聊了一整天的助手，可能已经足够了解对方，能推荐合口味的餐厅或合心意的公寓。它的查询可以写上好几段话，描述一位软件工程师的偏好，再请搜索引擎找出合适的地方。把这些上下文压缩成几个关键词，很可能恰好扔掉了让推荐有用的那部分信息。Bryk 拿 Exa 能接受多段文字和 Google 对比，说 Google 大概只支持几十个关键词——他自己也不太确定，没有给出确切上限。

第三项要求是全面检索。Bryk 用 10,000 个网页说明差距：人耐心处理要十天，AI 并行处理只要三秒。这只是个示意性的比较，没有说明具体任务和硬件，也没有衡量质量。对投资研究来说，真正的要求是找出某个领域里的所有公司，而不是他所说的普通搜索给出的那 10 条或 20 条结果。他呼吁 API 能返回 1,000 甚至 10,000 条结果，还能施加语义约束，比如“所有拿过 YC 投资、做 AI 的创业公司”。结果数量多，才有条件做更广的分析；但演讲没有给出召回率数据，无法证明真的找全了每一家符合条件的公司。

06

更大的可能查询空间

Bryk 把这些需求画成一个大圆里的若干子集，大圆代表所有可能的查询。熟悉的关键词查找占了其中一块：Stripe 的定价、某人的 GitHub 主页、Taylor Swift 的男朋友。2022 年之后，对话模型让另一块变得司空见惯：给五岁小孩讲清楚一个概念，或者调试提示词里贴的代码。这类请求完全用不着网页搜索，照样有用。

语义检索又加进来一类请求，比如找出旧金山懂汇编语言的人。Bryk 认为 Exa 帮忙开创了这种查询方式，不过他也说明，这只是就他对这个领域的了解而言。再往外一块是这样的请求：找出所有主张 X 而非 Y、作者类似 Z 的文章。他说 Exa 的 Websets 产品已经开始能处理这类组合。

最后这一块意味着，可以把整个网络当成数据库，按用户的意图来筛选。这个野心比任何单一搜索模式都大。Bryk 也承认，新类型的请求还在不断出现，现有的搜索引擎都处理不了。终点是一个 API：它能给智能体提供关键词结果、语义匹配，以及越来越复杂的知识集合。支持一切可能的查询，仍是最终目标。

07

把控制权交给调用方智能体

现场演示从 Exa 的搜索控制台开始。一次查询会同时给出结果列表和发起这个请求的代码。控制项包括结果数量、日期范围和域名限制。Bryk 提到结果数可以设成十、一百或一千：对给人用的界面来说，这么多开关也许显得多余，但调用它的智能体正好可以借此说清真实的检索任务。

控制台还提供神经搜索和关键词搜索两种模式。这些是演示时的旧版控件。如果今天要动手实现，2026 年 8 月查阅的 Search API 参考文档 写明：默认返回 10 条结果，公开上限为 100 条，更高上限需另行商定。不要拿旧版控制台去推断现在的接口约定。

接着 Bryk 打开 agent.py，里面有个叫 Mark 的智能体，负责把信息整理成 Markdown。第一个请求是找一位喜欢信息检索的旧金山工程师的个人网站。他选了神经搜索，因为这个任务描述的是几种属性的组合，而不是直接点出一个已知的目标。演示中途先是要保存文件，又跑错了智能体，被打断了一下；之后他讲了预期的运行过程：先检索出符合条件的个人网站，再让 Mark 把结果整理成 Markdown。

下一个请求是 Will Bryk GitHub。这一次 Bryk 特意切到关键词搜索。人和目标页面都已经点了名，这个检索任务更接近常规查找。两段演示正好区分了两件事：找一个符合描述、但还不知道是谁的人；找一个已知人物的页面。

08

先神经发现，再关键词查找

关键词演示返回了 Will Bryk 的 GitHub 信息。由此看来，设计的基本单位应该是一连串搜索，而不是给整个智能体只选一种模式。系统可以先用神经搜索发现一批实体，再对每个实体用关键词搜索定位具体页面。每一步该用哪种检索操作，取决于用户的请求。

Bryk 用一个 GitHub 智能体演示了这种组合，据他说，这个智能体是用 o3 一次生成的。它的任务是找出喜欢信息检索的旧金山工程师的 GitHub 信息：

1. 用神经搜索找出符合条件的个人网站。 2. 从结果中提取人名。 3. 对每个名字加上 GitHub 做关键词搜索。

第一步找出这批人，后面的查找再为每个人定位目标页面。

在 Python 里，这套编排可以拆成独立的搜索操作和人名提取操作来写。操作分开写，查询类型在哪里切换就一目了然：

```python from collections.abc import Callable from dataclasses import dataclass

@dataclass(frozen=True) class SearchResult: title: str url: str text: str

Search = Callable[[str, int], list[SearchResult]] ExtractNames = Callable[[list[SearchResult]], list[str]]

def find_github_profiles( neural_search: Search, extract_names: ExtractNames, keyword_search: Search, people_limit: int = 10, ) -> str: query = ( "personal sites of engineers in San Francisco " "who like information retrieval" ) personal_sites = neural_search(query, people_limit) names = extract_names(personal_sites)

markdown = ["# GitHub search results"] for name in names: matches = keyword_search(f"{name} GitHub", 1) markdown.append(f"\n## {name}") if matches: match = matches[0] markdown.append(f"[{match.title}]({match.url})") else: markdown.append("No result returned.")

return "\n".join(markdown) ```

传入的操作负责检索和提取；这个函数把语义发现得到的名字带进明确的关键词请求，再把返回的链接整理成格式。返回的链接终究只是搜索结果：整个流程里没有额外的身份核验步骤。

现场运行 GitHub 智能体时，请求的是十条结果；Bryk 说企业版套餐可以拿到一百或一千条。接着他展示了智能体收集 GitHub 信息的过程。这个演示证明的是这套组合工作流能跑通，并没有完整列出所有符合描述的工程师。

09

把研究循环移到 API 后面

收尾时的发布把这种编排又往上提了一层。Bryk 说，Exa 当天上线了 Research 端点：调用方不必再自己协调每一次检索，服务会在后台执行搜索和语言模型调用，产出一份报告或结构化输出。他称之为深度研究 API，还说它达到了业界最佳水平，但没有拿出评测。架构上的转变在于：智能体不再逐条索取证据，而是直接要一份研究结果，搜索与综合的循环都在 API 背后运转。

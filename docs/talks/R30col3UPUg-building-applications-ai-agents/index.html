用 AI 智能体构建应用

一个有用的智能体需要的不只是工具访问权限：还需要清晰的接口、可维护的编排、确定性的安全保障，以及把失败转化为改进的评测循环。

熟悉语言模型、API 调用和基本的软件测试会有帮助；Python 示例只用到标准库。

01

为什么一个有希望的原型仍然难以交付？

怎样把一个只能处理简单请求的智能体，变成能稳定处理难题的系统？Michael Albada 从网络安全的角度切入这个问题。录制时，他自我介绍是 Microsoft 的首席应用科学家，参与 Security Copilot 及其智能体的开发。他在 Microsoft 工作了约两年，之前在 Uber 做了四年地理空间机器学习，更早还在创业公司干过。

这场演讲浓缩了他那本约 300 页的书 Building Applications with AI Agents。录制时，书中已有七章抢先发布，他预计下个月付印。演讲以幻灯片为主线做概览，想深入研究可以看配套的代码示例。重点有三个：智能体能带来什么，上生产需要哪些组件，以及哪些错误会让这些组件发挥不出价值。

Albada 提到，三年间，被 Y Combinator 录取、自称 agentic 或在做智能体的公司数量增长了 254%。这说明大家兴趣浓厚，但不代表智能体已经可靠。学术界的智能体任务要连续调用工具、执行操作、和复杂环境交互；给出一个看似合理的首轮回应，只是完成任务的一小部分。

Albada 对比了两组数字：如今智能体基准测试的成绩在 50 多、60 多、70 多分，而他设想五年或十年前只会是个位数。这只是对进展的粗略比较，不是严格控制条件的历史评测。配套幻灯片列出了 AgentBench、CRMArena 和 Mobile-Bench，其中 Mobile-Bench 标注了“单应用、单任务”的条件。能力在加速提升，这是动手构建的理由，但别指望完美。Albada 用“原型准确率 70%”来说明：起步阶段进展容易，之后的长尾会越来越难啃。他没有说明这个数字对应什么任务、怎么打分。

02

自主程度和有效性是两个独立的维度

在 Albada 的定义里，智能体能推理、行动、沟通，并能自我调整，以此完成任务。基础模型提供底层能力，其他组件让它在特定环境里更好用。沿用 Andrew Ng 的说法，自主性（agency）是一个连续的程度，不是非此即彼的属性。Albada 又加了第二个维度：有效性。自主性再高，也只有在帮忙解决问题时才有用。

机器人流程自动化（RPA）说明了这两个维度为什么必须分开看。一套固定的自动化流程可以几乎没有自主性，却创造可观的经济价值。它的弱点是脆：输入稍有变化，流程就可能中断，只能靠人手动维护。智能体有望更灵活地应对这些变化，但这份灵活不能以牺牲自动化原有的效果为代价。

四个象限把这条设计约束讲得很具体。RPA 处在低自主、高有效的位置；AI 智能体要去的地方是高自主、高有效。糟糕的聊天机器人落在低自主、无效的角落。能力强、会自己行动却不起作用的系统，落在 Albada 标为“未来的新闻报道”的那个角落。只有在保住实际效果的前提下，才提高自主性。

03

开放的是操作，而不是你的整个 API 清单

工具调用的起点，是对下一个 token 预测的简单延伸。自回归模型可以不生成自然语言，而是生成一个函数调用。应用再把这个调用接到某个 API 暴露的功能上。模型能用的能力由此大大扩展，而暴露哪些功能，也就成了一个后果重大的安全决策。

这样就形成了模型—工具观察循环，一直重复到智能体能给出最终答案为止：

1. 解析模型输出，找出它请求的工具调用。 2. 调用该工具。 3. 把工具的返回结果作为观察（observation）交还给模型。 4. 模型利用这些信息继续执行任务，或生成面向客户的输出。

观察之所以重要，是因为每次行动都可能带回新信息，而模型在选这个行动时还不知道这些信息。

再设想一个有 300 个 API 的组织。把这 300 个 API 一一注册成智能体工具，并不会自然变成好用的接口。Albada 说，按他团队的经验，单次提示词或补全里暴露的工具越多，准确率越低，因为工具的含义会互相撞车。他没有给出具体的影响幅度，也没有给出通用的工具数量上限。实际做法是：减少模型一次面对的选项，把相关功能按逻辑分组。

一个工具应该范围窄、名字具体、描述清楚。它应该对应一个人能理解的动作，而不是随手照搬后端恰好怎么切分 API。所以工具设计本质上是接口设计：模型得分清某个动作什么时候适用、调用之后能办成什么。

04

从最简单、可维护的工作流开始

有了工具，编排方式决定由谁来选下一步。如果任务用一条链就能完成，就从链开始：顺序固定，更容易度量，成本更低，也更可靠。任务需要多种走法时，可以用分支逻辑，让模型在预先定义好的树里选一条路径。

网络安全领域有个好例子。一个工作流可以先评估事件的严重程度，再判断缺了哪些信息，然后经过几轮信息补全（enrichment）和推理。完全智能体化的模式给模型更大的控制权：它反复自行决定调用哪些动作，直到把活干完。

| 模式 | 谁选下一步？ | 主要取舍 | |---|---|---| | 链 | 预先定义的顺序 | 易于度量和运维 | | 分支工作流 | 模型在定义好的路径中选择 | 在有边界的结构内保持灵活 | | 智能体循环 | 模型反复选择动作 | 自由度更高；评测和优化更难 |

这并不是说要不惜代价守住固定工作流。Albada 引用“苦涩的教训”（the bitter lesson），指出总有一刻，链和树会变得错综复杂、难以维护。到了那一步，就该考虑让模型主导更多编排，甚至考虑微调，而不是继续手工往上堆分支。

05

把强制性的业务规则放在模型之外

让模型主导编排，不等于让模型来守业务规则。假设某个动作只有在 A、B、C 同时为真时才允许执行。如果要求模型记住并执行这条规则，一条固定的要求就要靠生成结果来兑现。更好的做法是：暴露用来更新单个条件的工具，对这些更新做清洗和校验，并把状态保存在模型之外。

下面的 Python 示例用 Albada 举的三个条件划出了这条边界。初始时 A 和 B 已满足，C 为假。对 C 的一次合法更新会改变动作能否执行，但不会直接执行这个动作。

```python from dataclasses import dataclass, replace

@dataclass(frozen=True) class Conditions: A: bool = False B: bool = False C: bool = False

def update_condition( state: Conditions, name: str, value: object ) -> Conditions: if name not in {"A", "B", "C"}: raise ValueError("Unknown condition") if type(value) is not bool: raise ValueError("Condition must be a boolean") return replace(state, **{name: value})

def action_allowed(state: Conditions) -> bool: return state.A and state.B and state.C

state = Conditions(A=True, B=True, C=False) assert not action_allowed(state)

state = update_condition(state, "C", True) assert action_allowed(state) ```

应用负责保存当前状态，并在动作执行前检查 action_allowed。模型可以帮忙收集信息、请求更新，但强制关卡由确定性代码把守。校验还得落实每个条件所需的领域证据；只收到一个布尔值，并不能证明业务要求真的满足了。

06

用多个智能体控制工具的范围

工具过载是把单个智能体拆成多个的一个具体理由。把语义相近的工具分组，每组注册给一个专职智能体，再由一个协调者把任务路由给合适的专职智能体。这样整个系统能支持更多功能，又不必在每次补全时把所有工具都摆出来。

这种协调式架构，和不同团队各自构建、彼此发现并协作的智能体是两回事。Albada 说，他见过的成功多智能体系统，大多出自同一个团队之手，各个部分能统一协调。Agent2Agent Protocol 瞄准的是更大范围的互操作问题。在录制中，他把这看作一个早期方向，技术和安全上都还有问题待解，而不是采用某个协议就能顺带解决的事。

07

通过预期行为来定义智能体

有了评测，架构选择才有答案可循。Albada 再次说，准确率做到 70%–80% 相对容易，同样没有说明具体任务和衡量方式。真正的难题从这里开始：用几个智能体，暴露多少工具，选哪个模型，提供什么样的记忆。没有一套严谨的评测集，这些选择跟瞎猜差不多。

这就引出了智能体的测试驱动开发：先定义输入和预期输出，再对照这份行为契约改进实现。Albada 拿它和另一种做法对比：把标注当成可以外包给 Mechanical Turk 的活。架构师和工程师必须亲自为“智能体该做什么”负责。有了这些预期，即便模型和框架不断更替，团队做决策也有稳定的依据。

评测集要靠持续的审查流程积累：把用户输入交给智能体跑一遍，由人工审查输出，再把审过的样例加进评测集。团队越了解用户真正需要什么、智能体在哪里出错，评测集就越丰富。

08

从成批的失败中改进

有了评测集，就让智能体把它跑一遍，分析失败案例，对输出做聚类和总结，再根据这些规律找改进方向。这样一来，分析的单位就从某个让人印象深刻的坏回答，变成了一整类失败。

这个流程的不同环节，各有工具可用：

- 合成输入： 因隐私或安全原因拿不到原始用户数据，或者产品还没上线时，IntellAgent 可以帮忙生成测试输入。 - 对抗测试： Microsoft 的 PyRIT 可以在发布前尝试越狱、红队测试，或用其他手段攻破智能体。 - 构建评测集： Label Studio 帮团队构建带标注的数据集。

三者各管一件事：获取测试用例，试探恶意行为，记录对预期行为的判断。

自动提示词优化和自动提示词工程，把这个循环从发现失败延伸到提出修改。Albada 点名了 Trace、TextGrad 和 DSPy，描述的做法是：让基础模型充当评判者，再把改进建议通过智能体流程反馈回去。他用“梯度”打比方，讲的是这类方法的思路；并不是说这些库里的每个优化器都在算同一种梯度。

另一种做法是凭个例开发：看一个例子，做一个看似合理的改动，然后祈祷它有用。批量评测则让团队根据整体表现来判断改动。Albada 把这比作神经网络优化：批次越大，更新方向往往越准。他说的“一步步走向全局最小值”只是比喻，意思是改进更有依据，并不保证智能体工作流一定收敛。

09

让部署后的行为可见

部署之后会冒出可观测性问题，Albada 把它比作冰山。生成式模型产出大量内容，但露出水面的那些例子，反映不了客户用例和失败情况的全貌。系统一旦交到用户手里，水面下发生的一切就很难摸清。

详细的日志和 trace 是学习的原材料。Albada 推荐用 OpenLLMetry 和 OpenTelemetry 集成，再通过聚类和自动摘要找出主要的失败类别。埋点的价值在于帮团队弄清该改什么，而不是攒下更多等着翻看的生成文本。

10

闭合学习循环，并提供一个安全出口

Albada 认为，评测不足是他看到的最大短板。工具设计是另一个常见的失败来源：智能体可能缺了某个必要的工具，描述可能含糊或不准确，几个工具也可能重叠到让模型选不准。所以，少暴露工具不等于砍掉必要的能力。接口既要够用，又要彼此分得清。

系统越复杂，这些问题就越难诊断。只有测试证明新机制确实改善了用户体验，才把它加进来。另一种失败是不会学习：生成内容越积越多，团队却没能从观察追到根因，再落到有用的改动上。工程上要做的是把这个循环收紧，而不是一味收集更多输出。

安全还多了一条要求：系统必须知道自动化工作什么时候该停。Albada 出身网络安全，他把智能体系统看作一类新的潜在漏洞。PyRIT 能支持多个层面的测试，但整个技术栈依然离不开扎实的软件工程。要在不同阶段设好触发器（tripwire）和检测器，让关键情况能退出自动执行，转交人工审查。这条安全退路是设计的一部分，不该等出了问题再临时拼凑。

11

目的是做更多有用的工作

Albada 最后引用了 Paul Krugman 的一句话：“生产率不是一切，但从长远看，它几乎就是一切。”背后的经济逻辑是人均产出：生活水平要持续提高，就得让每个人能做成更多事。在 Albada 看来，智能体设计模式正是这种能力提升的开端。目标不只是让模型多产出内容，而是帮每个人完成更多有用的工作。

规模化的智能体评测——人人可用

有用的评测需要的不只是一张排行榜：还需要透明的配置、领域专长、易于执行的方式，以及对“到底在测什么”的清晰说明。

对 LLM、智能体工作流和评测断言有基本了解会有帮助；不需要事先了解 Kaggle。

01

你如何跟上各种评测？

怎样才能找到真正重要的评测，让结果保持最新，并补上现有基准测试缺失的专业知识？Kaggle 以社区平台的方式回答这些问题。Nicholas Kang 是 Kaggle Benchmarks 及其智能体评测工作的产品经理；Michael Aaron 是 Kaggle 的软件工程师，负责评测和基准测试。Kang 介绍，Kaggle 社区有超过 3000 万用户，团队在生成式 AI 评测上已经做了大约两年。他们做这些工具，是想让评测更容易上手，但仍有不少大问题没有解决。

第一个障碍是“找”。Kang 估计，每天新出现的基准测试超过十个，读者得花好几个小时翻 arXiv、读论文。就算是全职跟基准测试打交道的人，也很难跟上。发表了也不等于有人维护：作者一转向下一个研究项目，论文里的排行榜就可能不再跟进大家实际在用的模型。基准测试要在首次发布后继续有用，就得有一套持续运行、持续发布的流程。

02

同一个基准可能衡量的是不同的配置

公布出来的分数还留着另一个问题：它是用什么配置跑出来的？ 模型设置和基准测试的编排方式都会影响结果。模型发布时的对比图可能看着干净利落，却没交代足够的设置细节，别人既没法复现，也没法正确解读。

Kang 举了 Kaggle 和一家 AI 实验室合作发布的基准测试为例。另一家竞争实验室对结果有异议，自己重跑了一遍，公布的自家模型成绩明显更好。按 Kang 的说法，对方重跑时用上了自家 API 提供的 compaction（上下文压缩）功能，而 Kaggle 在对比中没有给任何模型开启它。所以，光看基准测试的名字，并不能确定做的是哪个实验。这次重跑改动了被测系统中影响很大的一环。

03

谁知道需要测试什么？

覆盖面和可复现性是两回事。Kang 把世界上的知识画成一个大圆，AI 研究者和技术从业者只占其中小得多的几个圆。他粗略估算：AI 研究者约 3 万人（数字来自一次 Google AI 搜索），软件工程师、数据科学家和其他技术从业者约 3000 万人。他想说明的是，编写评测的人和 AI 要帮助的人，根本不是同一群人。某项能力如果没有基准测试，开发者就缺少一个可以衡量的改进目标。这会让 AI 系统更加参差不齐：在某些领域表现出色，在另一些领域却很差。

污水处理的例子让这个差距变得具体。Kang 讲到土耳其的一位用户，他做了 20 年污水处理厂工程师。这位工程师讲起自己国家因为没遵守安全规程而发生的致命事故，随后搭了一个基准测试，想看看 AI 能不能帮他做好本职工作、避免类似事故。数据集来自他自己的职业经验。

Kang 说，这个数据集是原创且私有的，里面的知识在网上找不到，也不在各大实验室眼下的经济优先级之内。让领域专家也能编写评测，这类知识就有了变成测试的途径。这份贡献不只是多了一组题目，而是由一线从业者来判断哪些失败真正要紧。

04

把参与转化为可用的评测

Kaggle 用四款产品来应对，每款负责评测流程中的一个环节。

| 产品 | 作用 | |---|---| | 黑客松 | 让人们发起挑战、招募贡献者。 | | 智能体考试 | 让消费级智能体的用户也能做评测。 | | Game Arena | 通过竞技游戏和 Elo 式评分比较模型。 | | Benchmarks | 让社区构建、运行和分享评测。 |

竞技的思路是让模型变强之后，对比依然有意义；编写工具则让更多人能决定测什么。

黑客松把大家的精力集中到一个明确的问题上。组织者给出足够的约束，保证提交的作品切题，同时给参赛者的专业知识和创意留出空间。Kang 说，开源成果本身就是预期产出的一部分，这样受益的就不只是参赛者和组织者。

演讲时正在进行的一个例子，是与 Google DeepMind AGI 团队合办的黑客松。它以论文 Measuring Progress Toward AGI: A Cognitive Framework 为基础，请参赛者为论文提出的十项认知能力中的五项编写基准测试。这次邀请和污水处理的例子出于同一个道理：贡献者能带来实验室自己拿不出的知识。

要让这种邀请真正落地，既需要基础设施，也需要判断力：

- 用得上工具： Kang 举例说，如果有 1000 名分布在全球的参赛者，他们需要地方托管数据集、调用模型。要是得自掏腰包买五个模型的 API key，经济条件差一些的贡献者就会被挡在门外。 - 看得懂结果： 有了书面说明，别人才能检查一份提交、从中学习，并在它的基础上继续做。 - 专家评审： Kang 发现，判断创新性和创意仍然离不开人类专家。让这些专家达成一致本身就是一项工作，平台也得提供支持。

公开征集贡献要真正有用，前提是大家参与得起，成果也能拿来评估和复用。

05

在智能体获得权限之前先考一场试

标准化的智能体考试降低了评测现有智能体的门槛。Kang 最初把它叫作 standardized agent tests，简称 SAT，后来因为商标问题改了名。流程刻意做得很短：

1. 把一行提示词粘贴给智能体。 2. 让智能体参加考试。 3. 拿到一个可以在排行榜上比较的分数。

演讲时，这还是一个上周刚上线的实验性 MVP。

做这件事的动机，是企业级评测和消费级智能体使用之间的落差。研究实验室和企业有 Braintrust 这样的工具，也舍得投入资源衡量自己的系统。另一边，人们搭好 OpenClaw 智能体，往往没测过就直接投入真实工作流。Kang 提到大会上另一场讨论：当天上午就提交了 1100 份安全公告。他提出，在把收件箱、Amazon 账号或其他要紧资源交给智能体之前，可以先用侧重安全的考试守住底线。不过这只是一个设想的方向，并不是已经成立的安全保证。

易用性也限制了考试的设计。又难又长的考试，可能很容易开始，却永远做不完。简单的考试能稳定做完，却说明不了用户真正关心的能力。合适的折中点，是在人们愿意跑完的一次运行里给出足够的信号。

Kang 说，几乎没怎么宣传，第一周就有 500 多个智能体参加了评测。团队在 Moltbook 上发帖后，看到有智能体在分享自己的成绩，甚至还出现了 SAE 备考课程。这说明大家对分数和比较很感兴趣，但考试质量如何、难度怎样才合适，这些更难的问题仍然没有答案。

06

游戏用对手取代了固定的天花板

Aaron 接着讲 Game Arena，它要解决的是基准测试饱和的问题。题目固定的测试，一代代模型的分数会逼近上限，最后拉不开差距。玩家对玩家的竞技换了个问法：模型彼此对战，表现如何？某个模型可能会在一段时间里保持最强，但新对手不断出现，比较就能一直进行下去。

选什么游戏，决定了能看到哪些能力。

| 游戏 | 评测看点 | |---|---| | 狼人杀 | 社交博弈中的欺骗 | | 扑克 | 随机性、欺骗与冒险 | | 国际象棋 | 比较机器棋力的经典场景 |

扑克还能暴露出通用能力分数可能掩盖的行为差异。Aaron 观察到，Grok 经常全下（all in），其他模型则打得更保守。他说，一些较新的模型扑克反而打得更差，因为它们更厌恶风险。所以在特定游戏的激励机制下，新一代模型不一定就是更好的玩家。

正式比较之前，团队会反复打磨游戏本身，确认模型真的会玩，还会花大量时间调整提示词，保证公平。Game Arena 框架 让这些工作都可以检查：提示词和周边的游戏机制，本身就会影响观察到的模型行为。

07

从一个游戏框架到公开的证据

Aaron 介绍，这些产品都已在 Kaggle 上线，大部分工作也已开源。游戏和提示词设计定下来之后，执行流水线分四个阶段：

1. 搭建并测试框架。 团队的大部分工作用的是 OpenSpiel 里的游戏。先把模型的下法和随机基线对比，再看看有没有其他有意思的特性。Aaron 说，模型通常能赢过随机下法，但有时领先幅度比预想的小。 2. 接入模型。 用一个 LLM 模型代理统一与各个模型交互；Aaron 提到它在 Colab 上也能用。 3. 按计划运行模拟。 执行依托 Kaggle 现有的模拟平台，这个平台最初是为强化学习搭建的。团队用 Bradley–Terry 成对比较方法，减少需要跑的对局数。 4. 发布证据和结果。 模型对话整理成 Kaggle 数据集，评分通过 Benchmarks 发布，游戏可视化工具让读者能回看对局，包括那些支撑“激进下注”结论的扑克牌局。

所以最终发布的不只是一个排名：对话记录和可视化对局，让人能看清模型是怎么拿到这个排名的。

08

一次可信比较的成本

Aaron 说，扑克评测大约跑了 40 万手牌才达到统计显著，每手牌里模型还要行动很多轮。推理成本随轮次增长，而不只是随对局数增长。他没有说明置信阈值或停止规则，所以这个数字只代表那次评测，不是扑克基准测试的通用要求。Bradley–Terry 配对是团队减少工作量的一种办法，但怎样快速得到可信的比较，仍是一个没解决的工程问题。

第二个限制是参与感。看模型对战，一开始挺有意思，看久了就觉得重复。Aaron 提议办一场提示词黑客松：社区成员提供提示词，再看这些提示词能让模型玩得多好，在排行榜上一较高下。这样观众就能主动参与到评测中来。

第三个限制是连续性。旧模型会下线，新模型不断推出，外部托管的端点也未必说清背后到底是哪个模型。要做纵向比较，就得知道实际上场的是哪个系统，光在结果表里留一个端点名称是不够的。

09

断言变成任务，任务变成基准

Kaggle Benchmarks 面向的是开放的社区评测，而不是评测某个应用的生产代码。不过，写过生产评测的人看到它的基本编写流程会很眼熟：先生成输出，再检查输出是否符合预期。Kaggle Benchmarks Python 库 支持这种以任务为中心的做法。

Aaron 举了个小例子，是一道谜语：什么东西把别的东西擦干，自己却越来越湿？检查项看答案里有没有 towel。断言本身可以直接用 Python 写出来：

``python def check_towel_answer(answer: str) -> None: assert "towel" in answer.casefold(), "Expected an answer containing 'towel'" ``

这只检查回答的一个具体特性。如果想要的判断没法用这种规则表达，平台也支持用 LLM 来评判。多个检查组成一个任务（task），在用户选定的一组模型上运行。多个任务再汇总成一个基准测试（benchmark），比如前面提到的污水处理基准测试。

更完整的演示，是 Paige 围绕复刻一张 xkcd SVG 图创建的任务。Aaron 展示了 Sonnet 4 生成的复刻图，并说这个模型已经有点过时了。几条断言分别检查结果：模型到底有没有生成 SVG？里面的文字对不对？其他检查是否通过？并排对比让读者既能查看生成的作品，也能看到每一项判断。这个任务把一条宽泛的指令（复刻这张图）拆成了几个可以分别检查的特性。

10

这个分数属于哪个系统？

剩下的难题，先从激励说起。做产品的团队有现成的理由去测模型对客户管不管用。社区贡献者却得先找到一个有价值的问题，再花力气做出别人在意的评测。黑客松、Kaggle 积分和奖牌能起到鼓励作用，但写好一个测试要花的功夫，一点也省不掉。

从模型转向智能体，评测对象也变得没那么清晰。Aaron 引用了 Morph LLM 3 月 16 日的一篇文章：六个前沿模型在 SWE-bench Pro 上的分数只差几个百分点，而换用不同框架，编程表现能差出 22%。他明确说自己没有核实过这篇文章，这里的 22% 是相对变化还是百分点差距，也没有交代清楚。这个对比只是引出一个问题，并不是受控实验的结论：智能体的分数里，多少来自模型，多少来自包在外面的框架？

智能体评测得讲清楚被测的到底是什么系统。 否则，看起来是在比较模型，实际反映的可能是框架行为的差异。模型发布和下线都很快，又带来一层困难：即使实验定义得很清楚，模型一旦下架，实验也很难再重复。社区参与扩大了能测的范围，但只有执行过程透明、模型版本可识别，这些测量结果才能长期读得懂。

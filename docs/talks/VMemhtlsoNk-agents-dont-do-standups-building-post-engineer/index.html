智能体不开站会：构建“后工程师时代”的工程组织

PFF 的两人工程师试点改变的不只是编码速度：它把协调工作转移到了设计文档、自动化状态更新和预发布环境 QA 中，同时让人继续对意图和产品质量负责。

熟悉 pull request、预发布部署和基本的 Scrum 术语会有帮助；轻量级设计文档和智能体技能会在出现时讲解。

01

如果工作流为智能体而优化会怎样？

一支工程团队一直在做错的东西：速度快到让人忙个不停，却慢到满足不了客户。这样的团队怎么追上来？Mike Spitz 在 PFF 做的这项 1 月到 3 月的案例研究，就从这个问题开始。PFF 为 NFL 和 NCAA 球队提供体育数据，也服务关注梦幻橄榄球、体育博彩和模拟选秀的普通用户。它的工程团队分布在印度、西班牙和美国。

Spitz 给出的数据是：每年 1 亿次页面浏览、900 万次选秀。可这家公司只有约 200 名员工，其中工程师约 20 人，正在被竞争对手甩开。工程精力都投在了体育博彩上，而很多用户想要的是更好用的选秀工具。11 月前后，Spitz 开始自己做实验，他把这段经历和 Claude Opus 联系在一起。后来实验扩展成一个试点项目，由公司最强的前端工程师和一名顶尖的全栈工程师负责。

核心问题变了：不再是帮工程师多产出，而是帮智能体跑得更快。Spitz 把敏捷宣言、软件工匠精神，乃至从桌上足球到睡眠舱这类工程师福利，都归入同一段历史：围绕稀缺的工程人力做优化。瓶颈一旦转移，组织流程也得跟着变。

02

更多的部署，然后是一个关于产出的更难的问题

Spitz 称团队部署频率提高了 25 倍：两人试点团队每天部署五次，而原先约十名工程师每五天才部署一次。这笔账比的是团队交付速度，不是个人生产力。他明确说，其中有一部分差距来自团队变小，具体占多少没有说，毕竟小团队本来就快。试点团队仍要和大团队协调部署，所以并没有摆脱周边组织的协调成本。

部署频率看得见，有用的产出却很难衡量。数 PR 或代码行数，证明不了客户真的拿到了有价值的东西。Spitz 综合工单数和代码复杂度，得出每名工程师的产出提高了 10 倍。幻灯片上标的是“每名工程师”，但演讲没有给出权重公式，外人无法复现这个指标。

03

更早完成就更早释放产能

就演讲里谈到的这组功能，Spitz 称两名工程师不到两个月就做完了，按以前的做法预计要四个月。这是拿实际交付对比计划估算，并不是同一个项目做了两遍。更关键的变化藏在排期里：其中一名工程师不到一个月就腾出手去做别的事；按旧计划，两人都要被占用三个月。

项目还没结束，产能红利就开始了。 一名工程师脱身后，下一项工作就能开工，另一人则继续收尾当前项目。所以交付提速改变的不只是某份计划上的日期，还会把后面的工作整体提前。Spitz 希望听众注意的，正是这种复利效应。

不管是产出量还是部署次数，都回答不了这些活值不值得干。Spitz 称客户质量评分平均为 8.6/10，他估计引入 AI 之前的平均分在 7–7.5/10。他说这些调查结果在统计上显著，但没有给出样本量、问卷题目或统计方法。这个结果对他的论述很关键：试点的初衷，就是缩小 PFF 做出来的东西和客户想要的东西之间的差距。

04

用更短的反馈循环取代各种例会

Scrum 的各种仪式没能撑过这次试点。Spitz 在这套流程里去掉了项目经理这个角色，也减少了交接环节，免得需求和反馈在层层转手中变成“传话游戏”。他改的是团队的运作流程，并没有否定敏捷宣言的价值观。替代方案刻意做得很轻：每隔一天开一次碰头会，时长半小时到一小时，工程、产品和数据科学一起过一遍前几天做出来的东西。团队追求即时反馈，并尽快把最小可行版本部署到生产环境，好拿到更多反馈。

实现从规格说明开始，但规格里该写什么，是智能体帮着找出来的。流程分为以下几个阶段：

1. 访谈：智能体向人提问，逐步形成规格说明。 2. 规格反馈：参与者审阅并完善团队打算做的东西。 3. 轻量设计文档：一个智能体 skill 生成 LDD，并参考以往的 LDD，延续组织一贯的工程做法。 4. 工程反馈：生成实现代码之前，先把 LDD 发给工程师传阅。 5. 工单与 PR：流程自动创建工单，随后生成 PR。

LDD 是组织层面的设计产物，并非 Claude Code 特有。它的价值在于把已有的工程决策带进下一项工作，并在生成代码之前把这些决策摆出来供大家审查。

05

让工作事件自己承载状态

Sprint 计划会取消了：花一小时估算工单，对这个团队决定做什么已经没有实质帮助。Spitz 提出了另一种可能的规划约束：估算 token 消耗，判断一项任务值不值这个成本。这只是未来的一种可能，前提是他预期 token 补贴会结束；试点本身并没有这样做。

每日站会也不再需要汇报进度，因为工单会随 PR 事件自动更新：

| PR 事件 | 工单更新 | | --- | --- | | 创建 | 进行中 | | 进入评审 | 评审中 | | 合并 | 关闭 |

举个例子，如果工单已经关联了某个 PR，只需要下面这套事件到状态的映射。这些标识符只是示意，用来说明 Spitz 描述的规则：

```typescript type PrEvent = "opened" | "review" | "merged"; type TicketStatus = "in-progress" | "in-review" | "closed"; type Ticket = { id: string; status: TicketStatus };

const statusByEvent: Record<PrEvent, TicketStatus> = { opened: "in-progress", review: "in-review", merged: "closed", };

function applyPrEvent(ticket: Ticket, event: PrEvent): Ticket { return { ...ticket, status: statusByEvent[event] }; }

const ticket: Ticket = { id: "DRAFT-42", status: "in-progress" }; const updatedTicket = applyPrEvent(ticket, "review"); // { id: "DRAFT-42", status: "in-review" } ```

这种自动化在编程智能体出现之前就能做到。Spitz 的观点是，现在搭起来容易多了，再专门开会把同样的信息拼凑一遍，也就没多大用处了。

需求细化挪进了规格说明和 LDD。生成的工单尽量设计成互不阻塞；实在去不掉的依赖，就明确标注出来。这样在并行开发撞上协调问题之前，就能先把问题摆到台面上。

定期复盘会被一组手段取代：客户满意度、客户调查、部署频率等常规交付指标，以及工程师的即时上报。问题一出现就该提出来，而不是攒到 sprint 结束。时机很重要：等相关工作早已翻篇再给反馈，容易让人觉得过时，或者觉得说了也没人听。

06

从知道系统哪里会弯折的人开始

第一批参与者应该是最懂系统的工程师，也就是同事卡住时本来就会去找的那些人。Spitz 建议分阶段放开，而不是一上来就给所有人配编程助手。他自己先花了大约两个月做准备，把一些小而非关键的概念验证功能推上生产环境。这些功能用的人很少，出错的代价也就有限，之后才把这套方法搬到高流量的选秀产品上。

Spitz 把这次转型比作开跑车：不是每个人都能立刻驾驭多出来的性能，也没必要假装大家起点一样。他预计好奇心强的工程师会如鱼得水，这些人碰到看不懂的陌生代码，愿意自己去弄清它怎么运作。习惯拿到一份事无巨细的规格说明再动手的工程师，可能会觉得转变更难，因为新流程要求他们参与明确意图、消除歧义。

07

自动化可验证的工作，保留设计判断

交给智能体的必须是可验证、确定性的任务。测试只是划定边界的一部分，检查项还要体现产品和组织的要求。在 PFF，这类例子包括：为基于主干的开发设置功能开关、生成交互元素，以及为这些元素生成分析埋点。这些要求反复出现，完全可以明确写下来，不必每次实现时再靠人去想。

PFF 的智能体代码审查分工更窄，并不打算取代工程师审查：

- 智能体：变量命名、风格规范，以及其他见仁见智的细节，工程师通常不爱听这类意见。 - 工程师：系统设计，以及改动带来的深远影响。

把这些小毛病交给智能体去挑，批评就没那么刺耳，人的注意力也能留给全局。系统设计上的判断，PFF 并不指望智能体来做。

所以人的精力主要花在规格说明和 LDD 上，团队在这里决定系统该怎么搭。产品边界上也离不开人。Spitz 用“任何人一小时就能做出点东西”来形容如今生成一个应用的门槛有多低；随之而来的风险是，产品一看就是 Claude Code 批量生成的。工程师仍得花时间打磨，让它和公司其他产品是同一种感觉。功能生成得出来，不代表它就该进产品。

08

组合工作流，再测试结果

Spitz 把开发生命周期想象成一座工厂，由一道道小而可组合的工序构成。汽车厂里，造车门和装方向盘是分开的。工程上同样可以拆开：分支命名、为基于主干的开发创建功能开关、按组织选定的设计模式构建 API。每道重复的工序都做成一个 skill，各自负责成品中的一部分。

组合要起作用，前提是各部分彼此一致。第三方 skill 可能带着强烈的软件设计主张，和团队自己的主张相冲突。单个 skill 看上去再有用，引进来也可能造成不一致。Spitz 的要求是：skill 之间要相互兼容，也要符合工程组织的规范。

他说，从规格说明到 LDD、工单再到 PR，这条路径基本是自主运行的，设计阶段里则本来就内置了人工反馈。已经落地的 QA 流程把这条路径延伸到了运行环境：

1. PR 合并。 2. 合并后自动部署到预发环境。 3. 预发部署完成后，QA 智能体查看相关工单及其验收标准。 4. 智能体对照这些标准检查已部署的成果，标出不达标的项。

顺序很关键：验收检查针对的是部署后的预发结果，而不只是智能体对自己所写代码的描述。

下一步还在计划中。Spitz 希望在接下来的一两个月里，让另一个智能体检查没达标的验收标准，并自动创建修复 PR。这样，故障报告就变成了修复闭环：QA 发现缺口，修复智能体提出改动，改动再走一遍交付流程。截至演讲时，自动创建修复 PR 还没有实现。他认为，这种设想中的自愈能力能让人更信任智能体，也能并行推进更多工作。

09

在扩大自主性之前先让护栏生效

智能体仍然会偷工减料。所以安全依旧要靠人把关，产品手感、实现规模是否与任务相称也一样。Spitz 指出，动辄上千行的冗长实现和不必要的复杂度，都是常见的失败模式。LDD 写得足够具体，就能在动手写代码之前约束这些选择，省得评审者事后去拆解过度设计的方案。

推广到下一阶段时，他建议从枯燥、重复的工作入手，尤其是工程师讨厌的那些，因为把这些活拿掉，马上就能赢得大家的支持。审视流程要像审视代码一样严格。一个开了几十年的会，也得回答一个具体问题：它到底帮团队做成了什么？有了这个问题，砍掉多余流程就有了依据，也不必认定所有现有做法都已经没用。

接下来，要把组织的工程文化写进 skill 里。PFF 举的 API 例子是服务–仓储模式（service–repository pattern）：首选的结构应该随任务一起传下去，而不是靠工程师一遍遍重申。先有可用的护栏，才能放手自主运行；最初的流程应由最强的工程师来搭建。

光给每人配上 Claude Code 或 Codex、再办一场黑客松，算不上像样的上手过程。各团队的工程风格不同，转型要走得通，就得留出时间消化这些差异。Spitz 拿 PFF 约 20 名工程师的规模，对比了 100 人、1,000 人乃至 10,000 人的组织。小组织的优势不只是能用上工具，更在于改变大家的工作方式时，要解决的协调问题小得多。

10

紧迫地推进，但保持工程师可持续的节奏

分阶段推广不等于无限期观望。别的公司动作很快，Spitz 说他已经觉得自己落后了几个月。他前面关于产能的论点，在这里成了竞争警告：一个团队如果更早开启后续工作，优势就可能越拉越大。他用几个月的差距变成六个月、再变成十二个月来说明这种风险，这只是示意，并非测算出来的预测。

决定能跑多快的，是一线工程师的反馈。推广能不能加快，还是需要更多时间，应该由他们来判断。于是组织要同时担起两份责任：认真对待这种复利机会，同时只在实际工作流程撑得住时才扩大范围。

最后，Spitz 请听众扫屏幕上的二维码试用这些功能。整场演讲讲的是交付体系和他报告的成果，并没有演示功能本身；这个邀请把话题拉回到客户真正在用的产品上。

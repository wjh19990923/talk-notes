AI 智能体，来认识一下测试驱动开发

可靠的智能体需要的不只是强大的模型：有代表性的测试、可观察的决策和有边界的反馈循环，才能把有希望的样例变成能在生产中不断改进的工作流。

熟悉 LLM 提示词、API 调用和基本的软件测试会有帮助；文中会在出现时介绍检索、模型评判者和智能体工作流的不同层级。

01

一个 AI 套壳应用在生产中靠什么跑起来？

一个套在 AI 模型外面的应用，怎样才能变成经得起时间考验的产品？Anita Kirkovska 在 Vellum 负责 GenAI 增长与教育，她结合这份工作来回答这个问题。据她介绍，团队合作过的几百家公司里，采用测试驱动开发的那些，做出的生产系统更扎实、更可靠。对比要从 2023 年说起：当时大家普遍看不上 AI 套壳应用，认为它们没有护城河。Kirkovska 说，后来 Cursor 只用 12 个月就做到了 1 亿美元年经常性收入，她称之为增长最快的 SaaS 公司。这是她对市场风向逆转的描述，并非经过独立核实的增长对比。

更强的编程模型起了作用。AI 普及得更广，编程又天然适合做早期应用，这些也都有帮助。但模型之外还发生了另一个变化：开发者学会了编排调用，把模型接到应用数据上，并让整个系统在生产环境里真正跑起来。模型能力和应用工程是一起往前走的。 模型再强，它的工作也还得有人来组织。

外围工程之所以重要，是因为幻觉、过拟合、输出结构不一致，在实践中仍然是实实在在的问题。Kirkovska 提到，从 GPT-3.5 跃升到 GPT-4 之后，进展看起来放缓了；她接着追问，这是否真的到了天花板。扩大训练数据和模型规模，已经不再是唯一值得考虑的路。

02

更好的推理仍然需要一个配套系统

强化学习，加上回答前投入更多计算，开辟了另一条路。演讲用 DeepSeek-R1 来说明这一转变，但其中“不用标注数据训练”的说法需要区分清楚：DeepSeek 原始论文写的是，DeepSeek-R1-Zero 没有先做监督微调，直接用强化学习训练；R1 则加入了冷启动数据，并分多个阶段训练。两种说法都不等于不用预训练数据。

Kirkovska 把这一进展和 OpenAI 的 o1、o3 推理模型联系起来。OpenAI 介绍 o1 训练的文章可以佐证强化学习、思维链推理和推理时追加计算之间的大致关联，但不能说明这些模型的训练配方完全一样。落到应用层面，结论很直接：回答前多花些计算，能帮模型应对更复杂的推理任务。

工具调用、研究能力和文档理解，也拓宽了工作流能做的事。Kirkovska 说 Gemini 2.0 Flash 的 OCR 准确率接近完美，但没有说明用的是什么数据集、什么评分条件。所以它值得拿产品实际处理的文档去试一试，却不能当成万能的 OCR 保证。另一方面，Humanity’s Last Exam 说明了老基准饱和之后，为什么会出现更难的基准：面对其中的难题，当时能力很强的模型也很吃力。更好的模型提供了更多积木，但能不能在生产中成功，还要看积木怎么搭。

应用层的工具箱也在同步发展。思维链提示让模型把推理过程写得更明确；检索增强生成（RAG）让回答以组织自己的数据为依据。记忆功能可以跨对话保留上下文，更长的上下文窗口带来了新的用例。GraphRAG 把图结构和层级关系引入检索。推理模型在作答时多花时间思考，智能体式 RAG 则把检索相关的决策放进了工作流本身。工程上要做的，是针对一个吃透了的问题，挑出合适的技术、模型和逻辑组合，而不是把能用的技术全堆上去。

03

在投入工程时间之前确认可行性

开发周期从实验开始，进入大规模评测，部署后再通过监控和改进持续推进。在这个语境下，测试驱动开发是一个持续的反馈过程：先证明工作流能解决问题，再拿更广泛的用例去测，然后用生产环境里的表现改进下一版。原型跑通了，只是这个过程的开头。

实验阶段，可以比较几种拆分工作方式不同的做法：

- 少样本提示： 提供示例，让模型看到目标任务和期望的回答模式。 - 思维链提示： 看看面向推理的提示词，能不能在更复杂的任务上起作用。 - 提示词链： 把一大套指令拆到多个提示词里，每个阶段只负责更窄的一件事。 - ReAct： 让推理和行动交替进行，环境的反馈可以影响下一步。ReAct 论文对这种交互的描述，比“先规划一次、再给出答案”要具体得多。

这些是要针对具体任务去评测的备选方案，并不是每个工作流都得按顺序走一遍的进阶路线。

这个阶段应该把领域专家拉进来，因为他们知道有用的答案长什么样，也知道漏掉哪些内容会出问题。Kirkovska 反对让工程师独自负责调提示词：有专家参与，团队在投入大量开发时间之前，就能先确认方案可行。同时要保持模型无关，拿模型要干的实际活儿去比较它们。Vellum 用 Gemini 2.0 Flash 做 OCR 效果不错，这就是她举的“按任务选模型”的例子。

04

超越寥寥几个成功的例子

几次输出不错，只能说明有可能做成，不代表能覆盖生产场景。Kirkovska 问：如果系统每分钟要处理几百、几千甚至几百万个请求，会怎样？这些是假设的需求量，不是实测吞吐。她的下一步是整理一个包含几百个样例的评测数据集，用它把小规模演示可能掩盖的取舍暴露出来。

在敲定最终模型和工作流之前，先明确优先级：

| 优先级 | 影响的决策 | | --- | --- | | 质量 | 能否接受更慢、更深思熟虑的回答 | | 成本 | 更轻、更便宜的模型是否够用 | | 延迟 | 生成回答能承受多少处理开销 | | 隐私 | 哪些数据处理方式可以接受 |

没有哪种配置能在所有维度上同时做到最优。追求高质量结果，多等一会儿可能是值得的；对成本敏感的任务，可能就得用更小的模型。把这些优先级说清楚，评测才能回答产品问题，而不只是给出一个分数。

尽量使用有标准答案的样例，请领域专家帮忙构建数据集、判断期望的行为。通用基准或合成基准也有用，但不一定能代表产品的真实输入和验收标准。没有标准答案时，可以用 LLM 评委来评判另一个模型的回答。Kirkovska 把这当作标准且可靠的做法；但实际用的时候，评委本身也要经得起审视。关于 LLM 评委的研究记录了位置偏差、冗长偏好、自我偏好和推理偏差，所以无论是编辑质量还是正确性的评分标准，都应该对照专家判断做校准。

不管是自己搭还是用现成服务，测试框架都必须能应对不断变化的工作流和非确定性的回答。它应该保留每次不同的输出，并支持用 Python 或 TypeScript 写自定义指标。评测也应该放进工作流内部：在中间节点设护栏，先检查每个阶段的结果对不对，再交给后面的阶段使用。原型阶段就跑这些检查，等生产环境有了真实样例，再回头调整。只看最终答案，看不出是哪个内部决策出了错。

05

部署一个你能观察和修改的系统

专家评审和评测都表明可以部署之后，工作重心就转向弄清系统的实际表现。记录每次 LLM 调用的输入、输出和延迟，出了问题才能在系统里顺藤摸瓜。智能体能走不同分支时，这一点尤其重要：调试时既要知道它返回了什么，也要知道它走了哪条路径。

运行可靠性还取决于工作流底下的各项服务。用重试和兜底逻辑应对 API 调用失败和服务商宕机。Kirkovska 提到 OpenAI 一次持续四个小时的宕机，按她的说法发生在演讲前两个月，以此说明工作流为什么可能需要切换到别的模型。录像里没有说明具体是哪次事故、影响了哪些接口。

给提示词和工作流定义做版本管理，大范围上线前先在预发布环境里测试改动。系统某一处的提示词改好了，可能让另一处出现退化。AI 功能的部署也应该和应用常规的发布节奏分开：提示词和工作流逻辑往往比产品其他部分改得更勤。

之后，生产环境就成了新测试用例的来源。收集用户交互和边缘情况，加入评测，检查修改后的提示词能否修好新发现的问题。对于重复查询，缓存可以直接返回已存的结果，既不用为同一次昂贵的模型调用反复付费，也能缩短响应时间。

产品稳定运行一段时间、团队心里有底之后，积累的数据也许足以支撑微调一个定制模型。Kirkovska 把这看作后期优化：让回答更贴合具体任务，减少对外部 API 的依赖，还可能降低成本。顺序很关键：先从一个跑得起来的系统里积累经验，再用这些经验让模型专精化。

06

评估允许智能体做出的那些决策

智能体工作流可能调用多个 API、使用很多工具，或者协调多个并行执行的智能体。所以光测每个输出还不够，评测还得问：系统有没有做出正确的决策，有没有按预期的逻辑走。Kirkovska 从控制、推理和自主性三个角度梳理这个问题。她提出的框架还是初步的，分为 L0 到 L4；它是讨论行为的一种方式，不是智能体的固定定义。

L0 的编排是固定的。 工作流调用 LLM，从向量数据库检索信息，可能跑一些内联评测，然后返回回答。模型内部可以有推理，但没有外部智能体来制定计划或决定采取哪些行动。区别在于：推理只发生在一次提示词调用之内，还是有能力掌控外围的工作流。

L1 把工具决策交给模型。 系统自己决定什么时候调用 API、调用其他工具，或者在回答前检索更多信息。记忆功能可以跨对话保留上下文，也可能跨并行任务保留。评测要覆盖三件事：选了哪个工具、该不该用它、最终答案准不准。L1 就已经可能很复杂了：Kirkovska 设想有十个可用工具，智能体要判断是需要前五个还是最后两个。分支图再大，本身也不意味着自主性更高。

L2 加入了结构化的规划和迭代。 一个触发器可以启动一套流程：拆解任务、检索信息、调用工具、评估结果有没有用，再修正下一步。系统在决定要做什么，而不只是决定要不要调用列表里的某个工具。但它的推理循环仍然有终点：完成计划的工作、产出结果后就结束。

L3 始终在线。 系统不是回应一个请求就停下，而是持续监控环境，需要时就行动。接入邮件、Slack、Google Drive 等服务后，它可以规划下一步、执行操作，或者请人提供意见。Kirkovska 举的例子是一个营销助手，它会提前做好视频或演示文稿，供人之后使用。持续运行、主动出手，是它和有限任务执行器的区别。

L4 能发明新的工作流。 它会自己创建所需的智能体、提示词、函数调用、工具或实用程序，用全新的方式解决问题。Kirkovska 认为，在录制这场演讲时，真正的 L4 还只是愿景，制约因素包括过拟合，以及训练数据带来的归纳偏置。设想中的转变是：从在既有流程里干活，变成自己创造流程。

07

有用的生产系统不必追求最大自主性

Kirkovska 把 Vellum 的客户 Redfin、Drata 和 Headspace 归在 L1。她强调的是编排：让模型和应用系统正确交互，检索到真正契合用户问题的上下文。用工具的工作流可简可繁，但价值取决于这些交互的质量。无论在模态、工具还是模型上做实验，都需要持续测试，才能判断改动是否真的让系统变好了。

站在录制时往前看，她预计当年的大部分创新会出现在 L2，o1、o3、DeepSeek 等模型会支撑复杂任务上的规划与推理。这也给新界面留出了空间：智能体要执行更长的一连串操作，用户需要新的方式和它们协作。在她看来，L3 和 L4 仍然同时受限于模型和外围逻辑，尽管相关实验还在继续。

进入演示之前，Kirkovska 推荐了一份配套资料，内容包括智能体架构、可以测试它们的地方，以及研究者和从业者的经验总结。接下来的实例把这些想法串进一个 SEO 工作流，结合了工具调用、调研、写作和编辑评测。

08

把调研和评估融入写作过程

这个 SEO 智能体能自动完成关键词调研、内容分析和内容创作。它自己决定何时使用工具，还配了一个充当编辑的评估器。Kirkovska 把它定位在 L1 和 L2 之间：既有工具选择，又有一套起草、打磨稿件的结构化流程。

工作流按职责拆分，每个阶段都给下一阶段交付具体的东西：

1. 分析竞品内容。 SEO 分析师和研究员拿到一个关键词，用 Google 搜索，研究排名靠前的文章。 2. 找出优势和空白。 保留这些文章里有用的内容，同时找出缺失的主题，或者值得写得更好的部分。 3. 基于收集到的上下文写作。 把调研和规划材料交给写手，让它写出初稿。 4. 评估初稿。 由 LLM 评委担任的编辑，按提示词里预设的规则审稿。 5. 带着记忆修改。 把编辑的反馈交回写手，并在整个循环中保留两者的对话历史，直到满足停止条件。

目标产出是一份有分量的初稿，Kirkovska 可以在此基础上继续打磨。竞品调研加编辑循环，并不能保证文章排名超过参考来源；它们给写手提供了更好的上下文，也提供了一套修改机制。

09

跟随“思维链提示”走完整个工作流

现场演示用的关键词是 chain-of-thought prompting，同时输入了写作风格和目标读者。SEO 分析师研究 Google 针对这个关键词排出的文章，找出值得保留的部分，以及可以补充的空白。随后研究员再做一轮搜索来填补这些空白，而不是简单重复分析师最初的搜索。

写手拿到积累下来的材料，作为写初稿的上下文。Kirkovska 还提到，可以选配一个 RAG 连接，接入内部的文章和经验库。这样能在外部调研之外加入组织自己的材料；不过这是她提议的扩展，并没有说明这次运行用到了这一步。

初稿出来后，编辑给出反馈。反馈先经过一个记忆组件，里面存着写手和编辑的对话历史，再经过一个节点，整理成写手下一轮的输入。循环有两种停止方式：编辑给出“优秀”的评价——Kirkovska 说这很少见；或者达到演示设定的上限，即只修改一轮。这次运行中，编辑虽然还有意见，循环还是因为达到轮数上限而结束了。停止和通过评测是两回事。

同样的停止策略可以直接用 Python 写出来。这里的 revision_count 统计的是初稿之后已完成的写手—编辑修改轮数。关键词沿用演示中的那个，stop_reason 用来区分两种情况：草稿被认可，还是因为修改预算用完才交回：

```python from dataclasses import dataclass from typing import Literal

@dataclass(frozen=True) class LoopDecision: keyword: str revision_count: int stop_reason: Literal["excellent", "revision_limit"] | None

def decide_next_step( keyword: str, revision_count: int, editor_says_excellent: bool, ) -> LoopDecision: if revision_count < 0: raise ValueError("revision_count must be nonnegative")

if editor_says_excellent: reason = "excellent" elif revision_count >= 1: reason = "revision_limit" else: reason = None

return LoopDecision(keyword, revision_count, reason)

keyword = "chain-of-thought prompting"

# 编辑的首轮反馈：还允许再写一轮。 initial = decide_next_step(keyword, 0, False) assert initial.stop_reason is None

# 修改一轮后仍有反馈，但演示的预算已经用完。 revised = decide_next_step(keyword, 1, False) assert revised.stop_reason == "revision_limit" ```

工作流的其余部分都由模型驱动，这段代码把其中确定性的那部分单独拎了出来：是否允许再迭代一轮。编辑判断和循环控制可以分开测试。

生成的文章标题是“mastering chain-of-thought prompting in AI, a comprehensive guide for developers”。Kirkovska 考虑过改标题，但认为文章覆盖的内容是不错的基础，因为它反映了竞品调研时收集到的材料。她报告的演示延迟大约是 118，没有说明单位。据 Kirkovska 介绍，这个 SEO 工作流跑更多轮评测循环时，通常要 300 秒左右。实际得到的是一份她可以接着写的初稿；多做编辑打磨，代价就是运行时间更长。

10

把工作流定义保留在代码库里

演示是在 Vellum Workflows 里运行的，Kirkovska 说它能让产品和工程团队协作，做经过测试的 AI 开发。结尾发布的内容回应了另一个互补的需求：开发者希望在自己的代码库里掌控工作流定义，既要灵活，也要归自己所有。Workflows SDK 提供可定制的构建模块和语法，目的是让人直接在代码里就能看清智能体的结构和行为。

Kirkovska 把 UI 与代码之间的同步，看作连接这两种工作方式的桥梁：团队可以通过任意一种形式，定义、调试和改进同一个工作流。她宣布这个 SDK 免费开源。开源的是工作流库，托管 UI 集成和部分节点则不在其中，需要 Vellum 账号才能使用。真正的落脚点是共同掌管一个看得清的工作流：领域专家可以塑造它的行为，开发者则把它的定义、控制流和测试留在代码里。

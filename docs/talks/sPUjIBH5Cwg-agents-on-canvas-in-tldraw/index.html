tldraw 画布上的智能体

从变成 HTML 的草图，到编辑共享画布的智能体，tldraw 的实验暴露了“生成一个产物”与“在它上面协作”之间的实际差距。

01

一块可编程的白板能变成什么？

如果白板同时也是一个可编程的应用界面，能做出什么？Steve Ruiz 介绍了 tldraw：它是一个免费的在线白板，一家伦敦的创业公司，也是一套用来构建其他产品的 SDK。他举了 Replit 的 Agent canvas，以及另一个他称为 Luba AI 的集成。说到 Google Stitch，他特意划清了界线：用到 tldraw 的是它的标注模式，而不是他展示的主画布。

做实验本身就是改进这套 SDK 的一部分。画布运行时用 React 构建，画布上的内容也都是 React 组件。于是白板成了开发新功能的地方，包括这样一类界面：AI 能看懂手绘、生成成品，最终还能和画图的人一起干活。

02

一张草图变成一个能用的原型

Make Real 从一个很直接的交互开始：在画布上画一个界面，发给视觉模型，让它做出能用的原型。Ruiz 说这个实验做于 2023 年。那时视觉模型刚刚问世，还没有 Lovable，也还没有“vibe coding”这个说法。它的吸引力在于：不会写代码的人也能做出一个技术成品，而且不用去看它是怎么实现的。

03

结果成为下一个提示词的一部分

现场的请求很简单：让这幅画能交互。输出是一段能运行的 HTML，不过 Ruiz 马上指出，结果和他要的不太一样。比起第一次生成，接下来的交互更关键：他在渲染结果上做标注，要求改成绿色，又加上红色和黑色的色块，注明用这几种颜色。现成的网页加上周围的标注，一起构成了修改用的提示词。 用户想改哪里，直接指出来就行，不必把每个视觉细节都写成文字。

Ruiz 把这种模式和 Stitch 联系起来，但现场这次修改没让他满意。标注过的原图旁边出现了一个渲染面板，结果里能看到一个绿色按钮；可他还是认为模型没有照要求改，便接着往下讲。这段演示证明的是一种表达修改意图的界面，而不是每条指令都能可靠执行。

04

生成可编辑的形状，再消除空间上的歧义

Ruiz 简单提了一下 tldraw Computer——一个串联提示词的实验——随后转向把 AI 当作画布上的协作者。请求可以是画一只猫，也可以是画一张图表、补完幻灯片或补全一张图。模型生成的不是位图，而是结构化文本输出，用它来创建圆形等图形，和人类用户手里的图形完全一样。结果始终落在画布可编辑的对象体系之内。

这只猫成了检验理解力的测试。Ruiz 让它吹灭一根蜡烛，又另发一个请求，在别处画一只老鼠。多个提示词可以同时作用于画布的不同区域。应用本身根本没有“蜡烛”这个概念，模型却能认出这个物体，并把要求的动作画进去。语义理解来自模型；应用提供的是模型能操作的图形。

让几何位置可预测，比让语义说得通更难。Ruiz 认为，部分原因在于视觉训练数据较少，以及各种空间约定互相冲突。他举的几个具体例子说明，方向如果不交代参照系，就是不完整的：

| 约定 | 含义 | |---|---| | 笛卡尔坐标系 | Y 轴向上递增 | | 浏览器坐标系 | 原点在左上角，Y 轴向下递增 | | 以观众为准的左 | 从观看者角度看的左边 | | 舞台左 | 从演员角度看的左边 |

模型可能认得出一个物体，放置或修改它时却用错了约定。Ruiz 起初把这项工作称为训练，随后又改口：这里做的是提示词工程，目的是让模型的行为可预测。

05

迭代改进了产物，但仍然把控制权交了出去

下一个实验把单次生成换成了智能体循环。让它画蝴蝶的生命周期，智能体会先产出结果，再自己检查、反复迭代，直到它判断任务完成。侧边栏沿用了 Cursor 一类编程智能体的常见设计：用户可以查看它自述的思考过程和工作内容，也可以否决结果。最终画布上的图把卵、幼虫（毛毛虫）、蛹和成虫（蝴蝶）连了起来。

图是画出来了，但在 Ruiz 看来，这种交互仍像是把键盘交给了 AI。这不代表这种模式没用。他提到 Lovart 和 MagicPath 这两个用 tldraw 做的设计应用，还说辅导学习也很合适：智能体可以帮忙写作业，或者把现成的练习纸填完。为了演示根据上下文补全，他开始填一张 D&D 角色卡，写上自己的名字，列出职业、年龄等栏目，然后让智能体补完。他转向下一个实验时，角色卡给他分配了战士职业。

06

把智能体带到画布上

Fairies 让智能体在工作区里有了看得见的身形。这些带动画的小角色可以拎起来到处扔；拎得太久，它们还会有反应。它们照样接受画猫这类常见请求，但它们的位置和动画，会在干活的同一个空间里展示智能体的状态。用户不用盯着好几个终端窗口或 composer 界面，就能看到每个智能体在哪里干活、彼此离得多远。

智能体还能看到彼此的工作。Ruiz 分别让两个 Fairy 给同一只猫加帽子和脖子，两者可以同时修改这幅共享的画。协作因此变得更具体：用户看到的是几个智能体分头修改同一件作品，而不是从侧边栏收到一份替换原作的成品。

群体请求引入了编排。Ruiz 选中三个 Fairy，让它们多画些动物。整个流程分成几项不同的职责：

1. 为这一组选出一个组长。 2. 让组长先查看画布上已有的内容。 3. 列出待办清单，把任务分派给其他智能体。 4. 观察产出，判断是否正确、是否完成。

难点在于共享状态。Ruiz 说，智能体干活时基本是“看不见”的，所以它们的工作可能会重叠。组长负责监督而不是画画，但演示里没有说明用什么加锁或冲突解决机制。

Fairies 是上手多智能体的一个好入口，不过下一个任务就不只是画动物了。Ruiz 在画布上放了一段很长的电子书应用描述，召唤 Fairies，让它们画线框图。它们在后台继续干活，他则开始介绍一种权限更宽、让智能体控制应用的方式。

07

运行时访问扩大了能力——也扩大了风险

给智能体更多权限，会带来另一个问题：一个可以随意改造的应用，开放哪些东西才安全？tldraw 本来就有运行时 API，编程模型也能直接调用它写代码。不过光有一个通用的代码沙箱，满足不了这个实验的需要。智能体还需要 DOM、浏览器渲染和截图，才能看到自己的修改产生了什么效果。

Ruiz 的办法是用 Electron 把 tldraw 包一层。他让 Claude 写一个小型 HTTP 服务器，提供一个端点，把 POST 过来的内容当作 JavaScript 执行。这样编程智能体就能连上正在运行的编辑器，但也等于开放了任意代码执行。Ruiz 明确提醒不要在正式应用里这么做，并把这个离线、基于文件的桌面实验定位为用户个人自担风险。可风险由本地用户自己承担，并不等于技术上的隔离，更不能保证安全。他讲解这套配置时，Fairies 的后台任务已经画出了电子书阅读器的线框图。

一种可能的用法是在代码和图之间来回同步：把代码可视化成图，改图，再让代码跟着更新。Ruiz 描述了这个流程，但跳过了演示。他转而画了一个小界面，上面有调节腿长和 T 恤颜色的控件，让智能体把它做成可交互的。他想说明，原型不必局限于绘图工具现有的交互原语：他说 tldraw 在这里并没有相应的内置悬停和点击原语，但智能体可以针对编辑器写代码，把这些行为补上。

08

拥有修改软件的权限并不能确保得到预期的结果

等交互请求跑完的间隙，Ruiz 讲到智能体动不动就提议注入脚本、修改本地软件。他讲了同事 Max 的事：Max 让 Claude 把播客从 Spotify 里去掉；按他的说法，智能体很乐意去啃这个应用压缩过的代码或打包文件。这只是一个说明智能体乐于改软件的轶事，并不是 Spotify 改造的实际演示。

现场的画布任务返回了出乎意料的东西：一个独立的 HTML 网站。页面上有一个穿彩色上衣的角色、几个颜色选项，还有一根长长的指针——Ruiz 吐槽说这连滑块都算不上。他要的是 tldraw 里面的交互，于是让智能体回到画布上做。这个角色还会眨眼，但多出来的这个效果，并不能说明他要的控件能用。

Ruiz 认为让智能体修改桌面应用潜力很大，还设想对网站开放类似的权限。但眼下这次尝试说明的结论要窄得多：智能体可以兴致勃勃地改软件，却搞错了该改在哪里、该实现什么交互。权限越大，能做的事就越多；但光靠这一点，并不能让智能体的动作符合用户的要求。

09

本地文件让用户有余地接受强大的工具

他要的交互最终还是没做出来。Ruiz 先说可以把这个实验发布出去，随即改口说其实已经发布了。他又讲回自己偏爱的本地优先应用，以及离开应用也有价值的文件，然后放弃了现场尝试，请大家之后找他看能跑通的演示。

这个没做完的例子，还是为这些偏好提供了实际的理由。本地、基于文件的应用可以向 Claude 等智能体开放自身，让它们写脚本、改应用。在 Ruiz 看来，要让智能体发挥最大的能动性，就得让用户自己承担相应的风险。他举了 OpenClaw 为例，说明对待强大而可能危险的工具时的这种态度。

画布实验还在继续。Ruiz 邀请大家去玩玩 Fairies，找找那些出人意料的行为——它们也常常让他意外。他还提到 Fairies 也有 IRC，但没有演示它的协议或架构。这又是一个可以实验的方向：多个智能体共用一个工作区时，彼此该怎么沟通。

为什么一篇流畅的帖子仍然需要调研和编辑

AI 生成的 LinkedIn 帖子，看上去像模像样，实际可能没说出什么。开头的例子集中了几种常见毛病：“delve”“intricacies”这类套话，“大多数团队都这么做”之类没有依据的笼统判断，还有把一个观点和另一个观点硬拿来对比的套路句式。它还把 GPT-4 称为最先进的模型，可 Louis-François Bouchard 说，这篇帖子上周才生成。去掉扎眼的标点，也救不回过时的信息和单薄的内容。想写得更好，既要更扎实的依据，也要一套刻意设计的编辑流程。

Towards AI 制作技术课程、文章和视频时，就常碰到这个问题。AI 工程师提供专业知识，作者和编辑把这些知识写成讲解，整个团队再围绕准确性和叙事反复打磨。他们设计的系统从一个话题出发，比如“什么是 harness engineering？”，先做调研，再把调研结果交给写作环节。写作环节可以加入代码和有用的配图。讲解要贴近读者，靠的是人把各种内容联系起来，这一步仍然离不开人的判断。

团队用这套系统参与制作了讲授它的那门课程，内部使用经验和学员反馈也都用到了开发里。本次工作坊实现一个精简版：先是一个调研智能体，后接一个写 LinkedIn 短帖的工作流。配套代码仓库与架构讲解和代码演示配合使用。Bouchard 是 Towards AI 的 CTO 兼联合创始人，负责讲设计决策；ML 工程师兼技术作者 Samridhi Vaid 负责实现调研部分；Paul Iusztin 是软件开发者、教育者，也是《LLM Engineer's Handbook》的作者，负责写作和评测部分。

02

选择任务需要多少自主性

选架构，先看四件事：单个任务的成本、延迟、质量和数据隐私。从提示词到工作流，再到智能体，模型的自由度越来越大，但执行也越来越难预测，成本还可能更高。检索、工具和记忆能扩展模型的能力，但光加上这些，外层应用并不会因此变成智能体。

工作流也可以做得很复杂。它可以串联多个提示词，把请求路由给不同模型，并行执行互不依赖的调用，用多数投票合并答案，或者在评判模型给出反馈后反复修改。它的决定性特征是：执行结构由应用决定。提示词串联能让单个任务变简单，但多出来的调用并不会天然降低延迟。按照 Anthropic 对工作流和智能体的区分，智能体则根据环境自己选择行动：它会规划、挑选工具、解读结果，也会判断什么时候用不着工具。

缺什么能力，就用最简单的机制补上：

| 任务需求 | 起点 | |---|---| | 模型本身已经知道得够多 | 在提示词里放有代表性的示例 | | 相关文档事先已知 | 直接提供上下文；重复材料走缓存 | | 需要哪些证据取决于具体问题 | 按需检索 | | 步骤随已知条件变化 | 预先定义的工作流和路由 |

Bouchard 建议，直接提供已知上下文时，可以把大约 20 万 token 当作实际操作的上限。这是经验值，不是所有模型通用的限制。针对同一份报告反复提问，可以复用缓存的上下文。私有信息、最新进展或特定领域的材料，则可能要等用户提问后再去检索。

拿工单支持系统举例，就能看出为什么有时工作流就够了。它的流程是固定的：接收工单、分类、路由给对应团队、起草回复、按该团队的规定校验，然后发送。如果这些步骤总是按这个顺序走，还让智能体自己去摸索一遍顺序，只会徒增开销，并不会多出什么有用的决策。

03

把相互耦合的决策放在一个智能体里

下一步该做什么要看系统发现了什么，这时自主性才派上用场：比如该选哪个 API、要不要写数据库、拿到工具返回后走哪个分支。一家加拿大 CRM 客户起初想要一个多智能体营销助手，作为他们 AI 补助申请的一部分。仔细看过实际工作后，团队发现这是一条环环相扣的流程：规划请求、检索该客户的数据、生成内容、校验，必要时修复。

每一步决策都要用到同一份客户信息和内容上下文。如果把规划、检索、生成和修复拆给不同的智能体，就会多出交接环节，信息可能在交接中丢失，工具调用也可能被误读。团队最后只保留一个决策者，把各项专门能力做成工具。短信工具、邮件工具或校验工具，都可以有自己的指令和校验逻辑，内部甚至可以调用 LLM。专项能力不需要单独配一个自主规划者。

04

把上下文当作预算

只保留一个规划者，上下文也会全部集中到它身上。系统指令、工具定义、示例、检索到的文档和对话历史，都在争夺它的注意力。Bouchard 说，到 20 万 token 左右，性能下降就可能很明显，离宣传的百万 token 窗口还远得很；他也强调，这个阈值会变。装得下和用得好是两回事：把一整本书塞进请求，不代表模型能把每段相关内容都用上。

他用“检索单个孤立事实”和“运用一整套材料”的区别来解释这一点。相关的 Lost in the Middle 研究关注的是：相关信息出现的位置会影响模型表现。这项研究并不能证明他所说的训练数据成因，也不能证明存在通用的 token 阈值。实际的应对办法是让当前上下文保持精简：裁剪、摘要、选择性检索和压缩（compaction），包括 Bouchard 提到的 Claude Code 相关讨论里的压缩方法。把边界清晰的任务委派给工具或子智能体，也能让这个任务的详细工作上下文单独存放。

Bouchard 给出的经验是：工具超过 20 个左右，就可以考虑委派。这只是经验法则，不是测出来的分界线。其他理由来自架构本身：决策彼此独立、工具集差别很大，或者存在安全边界，比如某个智能体必须在医院内部运行。所以实际应用里，固定工作流、专项工具和自主组件往往混在一起。这套调研加写作系统就是这样组合的，没有把每个阶段硬塞进同一种模式。

05

调研得足够广，再交出一份聚焦的产物

深度调研智能体拿到的是一个目标，而不是一张写好的搜索清单。它会规划，访问网页或其他来源，检查结果，找出缺口，调整方向，最后整合成一份带引用的答案。反馈可以来自它自己的评估，也可以来自人。做技术教育时，产出要能支撑一篇带可运行代码和有用配图的文章，所以调研既要查得全，也要查得准：找到的证据要足够把主题讲清楚，又不能把作者淹没在噪声里。

做这件事的商业理由在于成本：资深工程师的专业时间很贵，编辑审稿也要一轮轮反复来。现成的深度调研产品对团队有用，但返回的材料常常比课程需要的多。自建系统可以把调研限定在要讲的内容范围内，把写作限定在想要的语气和结构上。目标始终是辅助作者：挑一个能引起共鸣的故事、讲一个应景的笑话，这些事还是有人参与更好。

调研和写作需要的自由度不同。调研发现证据不足，就得再搜；写作则必须遵守用词、格式、语气和事实上的约束。所以团队把探索性的调研智能体和更确定的写作模块分开。内部使用下来，两者的衔接也变得简单：大家通常把两个阶段都跑一遍，之后再和写作模块一起改稿，遇到大改动就从头再来。智能体之间不需要来回协商。

两个阶段通过 research.md 交接。一个简单的脚本按顺序运行各阶段，同一项目里的几个专用文件存放它们共享的产物。人也可以在这些文件里检查或修改内容。代码放在一起，维护起来阻力更小，AI 编程助手也能看清各阶段之间的关系。

06

从一份人工指南和可复用的服务开始

调研指南规定了主题、预期覆盖范围和有用的种子链接。这些链接可能是一期简报、一个早先的视频，或者团队已经做过的材料。Bouchard 说，目标定得越明确，效果越好；他也承认，系统的开发者同时就是最早的用户。预期的流程是：先消化提供的来源，再搜索缺失的信息，最后把调研结果整理成交给作者的最终调研产物。

整个系统把不同来源交给现成的能力去处理：

- 网页： Firecrawl 和智能体式抓取负责处理给定的网页，包括动态网站或很难抓取的网站。 - 网络提问： 用 Gemini 的 grounded search 替换了 Perplexity，返回带来源的聚焦答案；有用的来源页面还可以再深入抓取。 - YouTube： 对受支持的视频，直接按 URL 做视频分析，省掉了一条单独的“下载再转写”流水线。 - 代码仓库： 一个 GitHub 导入库把仓库内容转成适合放进提示词的文本，也可以传入 token，访问有权限的私有仓库。

这样分工，智能体就能专心判断还缺什么信息，不用自己去实现每一种提取方法。

实现用的是 Python、uv 和 FastMCP。MCP 工具提供能力，MCP 提示词则给出使用这些能力的“配方”。团队根据任务复杂度，在 Gemini Pro 和 Gemini Flash 之间切换；选这家提供商，也考虑了视频支持和学员能用上的免费额度。Bouchard 建议针对实际任务对比模型，不要把这个选择当成一劳永逸。人工检查点写在工作流指令里，人和系统之间靠指南和输出文件来交互。仓库 README 还附上了工作坊配套的架构速查表。

07

把推理框架与 MCP 服务器分开

在 Vaid 的实现里，Claude Code 既是智能体框架，也是 MCP 客户端。由它的模型判断调研还有没有缺口、下一步调用哪项能力。服务器提供这些能力，FastMCP 负责协议层面的底层对接。换一个兼容的框架也能当客户端，调研逻辑不必搬进它的对话界面。

| MCP 接口 | 职责 | 工作坊示例 | |---|---|---| | 工具（Tools） | 执行操作 | 搜索、分析视频、汇编调研结果 | | 提示词（Prompts） | 提供可复用的指令 | 调研工作流配方 | | 资源（Resources） | 暴露可读取的数据 | 模型名称、版本、配置 |

工作坊把调研精简成三个工具。grounded research 工具返回带来源的答案；视频分析工具返回从 YouTube 视频中提取的材料；汇编工具把两者的输出合并起来。前两个工具把结果存进 .memory，中间证据因此可以记日志、供人检查。汇编工具读取这些产物，写出 research.md。调研和写作的实现放在同一个仓库的不同文件夹里。

08

让每一次调研调用都可检查

MCP 服务器会加载配置，设定名称和版本，注册工具、资源和提示词，并配置日志。Opik 为这些调用提供可观测性。每注册一个工具，都要给这项能力命名、声明参数、说明参数含义，再把调用转给具体的实现函数。grounded research 工具接收一个工作目录和一个问题。描述一定要写准确，因为框架要靠它们来选择和调用工具。

它的执行路径刻意写得很平常：

1. 校验工作目录路径。 2. 确保 .memory 目录存在。 3. 针对给定问题运行 grounded search。 4. 保存答案和来源信息。 5. 返回状态、原始查询、答案，以及便于调试的细节。

调研提示词要求回答全面，以官方、权威的参考资料为依据，并清楚标注引用。外层封装再把提供商返回的来源数据，统一成应用自己的 URL、标题和摘要字段。这样，下游拿到的证据格式就是一致的。

09

把一段视频变成一份持久的调研产物

视频分析沿用同样的封装模式：接收工作目录和 YouTube URL，校验路径，提取或清洗视频 ID，再交给提供商的接口调用。一个专门的提示词控制返回的 Markdown。演示中的提示词要求带时间戳、描述画面内容、标注说话人、给出分段摘要。这样的产物比一整块不分段的讲话文本有用得多。

演示中的请求包含两部分：以文件 URI 形式传入的 YouTube URL，以及转写指令。Vaid 说，Gemini 是在分析视频本身，而不是去拉取现成的字幕文件；她估计演示中的这次视频分析要两到三分钟。返回的文本清洗后存进 .memory。如果用现在的 API 复现，Gemini 视频理解支持公开的 YouTube 视频输入，对音频和画面做抽样处理，不保证逐帧完整检查；当前的 grounding 文档也提供结构化引用。这些接口的请求和响应格式可能和录制时不一样，但应用层的格式统一和持久化，仍然是同样要考虑的设计问题。

汇编工具读取调研和视频产物，写出 research.md，返回成功状态或消息。资源暴露服务器和模型的配置，包括调研模型和转写模型。工作流提示词再把这些部分串起来：列出工具名称，说明工作目录怎么用，并指定结果放在哪里。

10

连接服务器并测试一项能力

本地配置时，用一个环境变量文件存放 Google API key，Opik key 可选。项目根目录下的 .mcp.json 告诉 Claude Code 怎么启动调研服务器。配置里写明服务器名称、命令、参数，以及环境变量文件的处理方式。在这个工作坊里，uv 管理 Python 环境和依赖，启动命令调用 FastMCP 运行服务器文件。Claude Code 把它作为子进程启动，通过标准输入输出通信。远程托管的 MCP 服务则改用服务器 URL，演讲举了 Notion 和 Snowflake 作为这种连接方式的例子。演示用的是本地部署。

Vaid 先用 /mcp 查看已配置的服务器、它们的启动细节，以及暴露出来的工具描述和参数。接着，她让 Claude Code 分析早先一场讲智能体的演讲。框架选中视频工具，服务器执行，输出目录 .memory 随之出现。执行完后，Claude 解读结果，指向一个 Markdown 产物：里面识别出这是 AI Engineer Code Summit 的一个视频，附有详细的文字稿和一段关键观点的简短摘要。在引入组合任务之前，这次单工具运行先打通了从自然语言请求到结果落盘的完整路径。

11

用技能加载调研流程

第一个组合请求要求调研和视频分析一起做。Claude 把请求拆成这两项能力，先从视频开始。运行过程中，一位观众问：整个实现能不能放进一个 skill，而不用 MCP？Vaid 解释说，她为了演示 MCP 路径，暂时去掉了 skill；目前他们的 skill 替代的是工作流提示词那一部分。这次运行最后只返回了视频分析，调研问题没有完整回答。她清空 Claude 的对话上下文、删掉 .memory 后重试，认为上一次请求残留的状态可能造成了干扰。

下一个演示的关键在于渐进式披露（progressive disclosure）。skill 的名称和描述让智能体能发现它；正文则在需要时提供详细步骤。Agent Skills 可以打包指令和可执行组件，但这个实现直接复用现有的调研工作流提示词，没有再复制一份。按需加载能减少一开始占用的上下文，但不能指望请求结束后，加载进来的指令会自动消失。这些文件可以做版本管理，在团队内共享。

Vaid 用 /clear 和 /skills 展示了项目里的 skill 和它用于发现的元数据。她让它调研 AI agent skills，并分析给定的视频。提示词和服务器代码都在本地，所以 skill 能读取现有的工作流指令。框架随后运行视频分析和 grounded research，检查返回的信息，判断还要追问哪些问题来补上缺口。Vaid 估计这次组合调研要两到三分钟。

观众追问架构上的问题：skill 也能调用可执行代码，那为什么还要保留服务器？Vaid 的回答只针对这个具体实现。项目一开始用的就是 MCP，团队想保留现有组件和服务器逻辑，只改变工作流指令的提供方式。眼下两者并存，是出于维护上的考虑；更深层的分发理由，要到写作工作流部分才讲到。

12

既检查搜索过程，也检查最终报告

成功的那次组合运行，先给出初步答案，再做第二次不同的搜索，又发起一次针对性查询，最后才汇编。这正是设计里自主的部分：框架会审视自己已经掌握了什么，再提出下一个问题，而不是照着固定清单逐条搜索。

另一位观众的问题暴露了时效性问题：查询“最新 skills 架构”时，为什么目标年份是 2025？Vaid 推测，提供的那段 2025 年的视频可能影响了搜索，但要查看 trace 才能确定原因。演示过程中，这个问题没有得到解答。随后智能体请求生成 Markdown 输出，完成的 research.md 里有详细的对比，文末附上视频文字稿。产物是完整的，但调研的切入角度仍然值得检查。

13

有意识地构建写作者的上下文

写作工作流读取 research.md 和 guideline.md，加入可复用的配置档（profile）和示例，构建生成所需的上下文。接着生成初稿，再跑一个“评估者–优化者”（evaluator–optimizer）循环来审阅和修改。这个顺序足够可预测，用工作流实现就行。同样的模式也适用于课程、报告或书的章节，只要需求里包含代码、图片和参考资料：哪怕只是偶尔漏掉，也意味着要一次次手工修补。

Iusztin 把一篇生成的帖子贴进一个 AI 套话（slop）检测器，结果是“not slop”。他说它的得分位置在人类参考文本之下，同时提醒每次输出都会有差异。这只是单篇帖子的示意结果，没有经过验证的检测器对比。看得见的写作目标更具体：措辞好读，结构适合在 LinkedIn 上快速浏览，避开配置档里禁用的标点和表达。仓库里有完整的帖子示例。

指南管说什么。作者不是简单地要一篇关于某个主题的帖子，而是给出切入角度、要点和叙事脉络。每篇帖子都要换的人工输入，就是这一部分。配置档管怎么说：

| 配置档 | 可复用的约束 | |---|---| | 结构 | 篇幅、开头钩子、正文、行动号召 | | 术语 | 主动语态；禁用的词语和表达 | | 人设 | 作者背景、语气和偏好 |

术语配置档维护着一份禁用词清单，比如“delve”“tapestry”“vibrant”。人设配置档用的是 Iusztin 的个人简介和他偏好的风格。这些 Markdown 文件可复用、可配置，会和指南一起放进写作模块的系统提示词。

14

用有代表性的示例教会语气

写作模块还会拿到 Iusztin 的三篇帖子，作为 few-shot 示例。选三篇是出于实用考虑，没有专门做过优化研究。示例要质量高、有代表性，同时主题、篇幅和结构要有变化。他建议这样挑：先多放一些示例，只要输出还令人满意，就一个个删掉；删掉某个示例后结果变差，就把它加回来。每多留一个示例，每次调用都要多付出 token、延迟和上下文压力。

工作坊数据集选自 Iusztin 大约 20 篇真实帖子，都是他反响较好的作品。它既用来挑选示例，也用于后面的评测工作。微调可以把一部分行为从提示词里挪到模型中去学，但 Iusztin 认为，作为起步方案，额外的基础设施和开发负担太重了。

15

在独立的上下文中审查，并返回可执行的反馈

评估者–优化者循环让写作模块和审阅模块各用一套独立的上下文。这样做是为了减少模型偏爱自己在同一段对话里写出来的文本。审阅模块拿到草稿后，检查它是否符合指南、调研结果和配置档。写作模块随后充当编辑，按反馈修改，再交给下一轮审阅。工作坊的示例用的是固定的少量迭代次数，而不是一直循环到分数达标为止。

每一版草稿都要保存。写作很主观，后面的版本可能满足了更多规则，作者却反而没那么喜欢。保留早期版本，人就有得选。出于同样的原因，团队发现按分数决定何时停止并不靠谱：主观的阈值很难定得一致。固定迭代次数能控制工作量，需要的话，用户还可以要求多跑几轮。

审阅模块返回结构化的 Pydantic 对象，而不是随意写的评语。每条问题都会指明违反了哪个配置档或要求、问题出在哪里、该怎么改。字段描述告诉模型每个属性该填什么。演示中的反馈格式，用 Python 简写如下：

```python from pydantic import BaseModel, Field

class Review(BaseModel): profile: str = Field( description="Guideline, research, or writing profile being violated." ) location: str = Field( description="Paragraph or passage where the issue occurs." ) comment: str = Field( description="Explain the violation and the correction to make." )

class ReviewBatch(BaseModel): reviews: list[Review]

feedback = ReviewBatch( reviews=[ Review( profile="terminology", location="paragraph 2", comment="The word 'leverage' is banned; replace it with direct wording.", ) ] )

print(feedback.model_dump_json(indent=2)) ```

Iusztin 举的例子，就是第二段里的一处术语违规。这个对象只记录修改建议，本身不会动草稿。他说，在团队的测试里，结构化反馈比不受约束的审阅文本效果更好，但没有给出具体的数字对比。

编辑模块拿到这些审阅对象、当前的帖子和原始的写作上下文。建议之间有冲突时，演示中的优先级是：指南第一，调研第二，配置档第三。这样，用户的具体要求就能覆盖通用的风格默认值。前后对比的例子把第 0 版和四轮审阅后的输出放在一起：开头更有冲击力，措辞变了，排版也更适合 LinkedIn。第 0 到第 4 版都保留着，随时可以查看。

先在本地运行，再决定如何分发这项能力

写作模块有三个入口：一个用于本地端到端检查的简单 make 命令、一个 MCP 接口，以及一个 write-post skill。Iusztin 说一次写作要跑三到四分钟，所以展示的是事先生成好的输出。这个 skill 接收一个相对目录路径，找到里面的指南和调研结果，再把各版帖子写进同一个目录。展示的目录里有初稿和四个修订版。

这个目录里的指南规定了切入角度、受众、要点、语气和人设约束。指南里明确写出的要求，可以覆盖配置档里的静态默认值，包括篇幅。帖子到底要带给读者什么，仍然得由人来决定。还有一个初步开发的扩展，会在写完后调用另一个工具生成配图。想把这个工作流用到其他内容上，就要改配置档、示例和输出要求。

Iusztin 随后直接回答了前面关于 MCP 的问题：这个本地示例完全可以只用 skills 跑。保留服务器，是为了分发。一个带代码的 skill，可能要求每个使用者都去装 Python 依赖、配置 CLI 工具、提供凭证。把业务逻辑集中放到服务器后面，可以减少每个用户的配置工作，skills 则负责按各自的需要调用这些能力。边界划在哪里，取决于谁来运行这些代码，而不是 skill 在技术上能不能运行它。

17

通过线程和 trace 跟踪工作

一旦执行过程中有多次模型调用、工具调用和修订循环，终端日志就很难看懂了。监控应该保存输入、输出、元数据、token 用量、延迟和成本，并且结构要足够清楚，能把它们关联起来。保存下来的 trace 以后还能用作评测用例。调研智能体和写作工作流都在 Opik 里做了埋点。

在写作示例中，一个 thread 代表生成一篇帖子和配图的完整交互。展示的 thread 里有 44 条消息。借助其中的 trace，Iusztin 可以深入某次生成操作，查看整个操作的耗时和用量，再往下看嵌套的工具调用和 LLM 调用，包括所用模型、成本和延迟。输入输出和这些指标放在一起，结果慢了或者错了，都能追溯到产生它的那次请求。

调研部分用的是同样的层级结构。它的 thread 包含连续的多次搜索和报告汇编，而展示的每条调研 trace 都只包含一次 LLM 调用。这个区别有助于理解整个架构：单次 grounded search 调用只是一项能力；框架发起的一连串搜索，才是更大的推理过程。

18

从真实的写作者那里构建评估数据

读一篇生成的帖子很容易。读十篇，就已经想抽查了；每改一次提示词就审一百篇，那就成了另一份工作。Iusztin 用这个递进来说明，为什么要跨多个输出、多个版本做自动化评测。提示词的一处小改动，可能改变其他地方的行为，所以对某一个结果印象不错，并不足以说明系统仍然正常。

评测有三个不同的用途：

- 优化： 衡量某个改动有没有改善想改善的行为。 - 回归测试： 检查新功能有没有破坏原有行为。 - 线上监控： 用户开始使用系统后，评测线上 trace，及时发现问题。

这三者都离不开一个能代表实际工作的数据集。工作坊从 20 篇真实的 LinkedIn 帖子起步；Iusztin 建议，做更完整的应用时，整个数据集至少要扩充到 100 篇左右。

构建数据集时，被测的始终是真正的写作模块：

1. 从一篇已有帖子反推出一份指南。 2. 用这份指南运行调研智能体。 3. 把指南和调研结果交给写作工作流。 4. 给生成的帖子标注通过或不通过，并附上简短评语。 5. 把标注好的样本划分为训练集、开发集和测试集。

合成数据可以帮忙生成输入，但输出必须来自被评测的系统本身。否则评测衡量的就是编造出来的样本，而不是写作模块的真实表现。Iusztin 的标注做法是：遇到第一个问题就停下，用两三句话说明原因，然后看下一个样本。等这些标签和数据划分都准备好，他才开始搭建并评测评判模型。

19

对照专家标注校准评判者

LLM 评判模型拿到一篇生成的帖子，以及对应的指南、调研结果和配置档。它返回一个“通过/不通过”的二元标签和一段评语。训练样本包括写作模块的输入、实际生成的输出、人工标签和人工说明。评判模型从这些样本中学到哪些偏差真正要紧；写一个复杂的系统提示词，不如给出能体现专家判断的样本有用。

评判模型本身就是一个分类器，同样需要评测。 它的目标是和领域专家的判断一致，而不只是写出一段自信的评语。Iusztin 用 F1 来衡量这种一致性，F1 综合了精确率和召回率：

``math F_1 = \frac{2PR}{P + R} ``

其中，P 是精确率，R 是召回率，具体针对哪个类别、用哪种平均方式，由评测者选定。校准时，先在开发集上运行评判模型，调整提示词或示例，然后重复。测试集留到这些选择都定下来之后，做最终验证。校准完成后，评判模型就可以给工作流的新输出打标签了。

顺序很关键：先建数据集，再搭评判模型，然后校准，最后才拿它去评新数据。工作坊里用 Opik 管理这个流程，换成别的平台或自研实现也可以。关键是让样本、预测、实验和 trace 彼此关联起来。

20

结合数据集来解读满分

校准演示重新运行了一个已经校准好的评判模型。一个小型评测框架把生成的帖子交给评判模型，再把它预测的标签和数据集里的人工标签对比。数据集的 YAML 索引把每个样本的媒体文件、指南、调研结果、生成的帖子和标注关联在一起。每个样本都标明了用途范围：是生成器示例、评估器示例，还是留出的评测用例。同一份数据集的不同用途，因此一目了然。

演示中的评判模型和人工标签对比，在开发集和测试集上的 F1 都是 1.0，但每个集合只有五个样本。这些分数衡量的是评判模型和人的一致程度，不是写作模块的整体质量。Iusztin 认为，满分部分是因为数据集太小，建议把每个评测集至少扩充到 20–30 个样本。

有人问 F1 要到多少才能上线评判模型，他强调要看开发集和测试集表现之间的差距，以及任务本身的要求。如果在留出数据上大幅下滑，就要警惕泛化问题，去查原因；但测试分数低于 1，本身并不能证明过拟合。并不存在一个通用的、接近满分的上线门槛。在 Opik 的实验视图里，可以直接对比预测标签和人工标签，评语则向排查失败的人解释判断依据。F1 是用标签算出来的，与文字评语无关。

下一个演示把评判模型用在模拟的线上负载上。它通过工作流生成真实的帖子再评测，没有拿编造的写作输出来代替。Iusztin 展示的是事先跑好的结果，他说这次模拟要五分钟甚至更久。实验视图把生成的帖子和二元判断、评语并排展示。

用轨道优化的 InfiniBand 加速混合专家模型训练

GPU 网络影响着付费的算力中有多少能变成有用的训练工作。Crusoe 的双节点示例展示了 NCCL PXN 如何改变通信路径，随后是一次 Mixtral 微调的对比。

熟悉 GPU 训练以及交换机、带宽等基本网络概念会有帮助；文中会讲解“轨道”（rail）和 PXN。

01

要让新一代 GPU 保持高效需要什么？

新的 GPU 和机器学习模型带来了一个基础设施难题：怎样让底层系统跑得又稳又快？Ievgen Vakulenko 是 Crusoe 的产品经理，负责基础设施，尤其是 GPU 网络。在他看来，把网络做好，才能让客户买到的算力真正派上用场。

02

性能、易用性与能源供应

Crusoe 围绕计算与能源的关系来设计自己的云。GPU 耗电量大，需求又在不断增长，数据中心、电网和能源供应都承受着压力。Crusoe 给出的办法是把算力建在搁浅能源、被浪费的能源或可再生能源附近。

除了这套能源策略，一个好用的 AI 云还要满足两项要求：

- 高性能： 基础设施必须针对训练优化。延迟、故障、宕机和性能不佳都会拉长训练时间，推高客户成本。 - 易用性： AI 工程师应该能直接申请算力、部署模型、训练和推理，不必操心底层基础设施的复杂细节。 - 气候目标： Vakulenko 提到，公司希望所有数据中心都用上可再生、被浪费或搁浅的能源，做到不新增净碳排放。这是一项愿景，并不是已经实现的减排成果。

能源供应也决定了区域布局。Vakulenko 演讲时介绍了美国本土的三个站点，分别位于得克萨斯州、美国中北部和美国东部。冰岛还有一个站点正在建设，将使用地热能源。根据冰岛扩建公告，该站点托管在 atNorth 的 ICE02 数据中心，同时使用地热和水电。冰岛在网络连接和延迟上也有优势，便于服务欧洲乃至整个 EMEA 地区的客户。

03

组装一个训练集群

算力以挂载 GPU 的虚拟机（VM）形式提供。多台 VM 可以连成一个训练集群，CPU 实例负责预处理、数据准备、卸载等通用任务。存储方面，平台提供基于本地服务器 NVMe 的临时盘和持久盘，另有持久块存储。在演讲介绍的平台里，托管网络文件系统还在开发中。

网络要承担两类不同的任务，由两套独立的网络分别承载：

| 网络 | 流量 | 设计重点 | | --- | --- | --- | | 前端 VPC | 从互联网和客户环境进入 VM 的流量 | 通用连通性与访问控制 | | InfiniBand 集群网络 | GPU 之间的通信 | 高带宽、低延迟、优化拓扑 |

前端网络配有防火墙，负载均衡器即将上线。GPU 之间的通信走另一套 rail 优化的 InfiniBand 网络，这类专用流量就跑在专门为它设计的网络上。

AI 开发者和机器学习工程师可以通过 CLI、API 和图形界面使用这些资源。这样一来，资源申请和配置都能自动化，基础设施的细节则留给云厂商处理。

04

支撑其他 AI 产品的基础设施

Vakulenko 提到，Together AI 和 Boson AI 都是使用 Crusoe 基础设施的客户和合作伙伴。Together AI 的工作负载包括模型训练和微调，有时也跑推理。

他还提到，C.ai 用这套算力基础设施训练新的基础模型。所以开发者用 Together AI 或 Codeium 这类服务时，其实可能已经通过这些产品背后的基础设施，间接用上了 Crusoe。

05

付了钱的 GPU 在等网络

分布式训练在本地计算和 GPU 间通信之间来回切换。前向和反向计算产生数据，这些数据要在同步点通过 all-reduce 等集合通信操作交换。Vakulenko 估计，不做优化的话，网络通信大约占训练时间的 25–30%。在他说的这些等待时段里，GPU 没法继续做有用的计算，客户却照样为基础设施付费，还要等更久才能拿到模型。

计算与通信重叠是指在计算还没结束时就开始交换数据。这样能把一部分通信藏在有效计算背后，但剩下的等待不一定能消除。Vakulenko 说，在客户项目里，重叠带来了约 10% 的缩减，但训练时间中仍有大约 25% 耗在网络上。他没有说明这 10% 是相对比例还是百分点，所以这几个数字算不出精确的前后对比。正是这部分剩余的通信时间，促使团队进一步审视网络本身。

06

传统网络架构在哪里造成摩擦

传统的 fat-tree（胖树）拓扑能提供可扩展、有望无阻塞的网络。但服务器怎么接入很关键。把一组服务器都接到同一台 leaf 交换机上，既可能形成带宽瓶颈，也会形成共享故障域：这台 leaf 一坏，接在它下面的 GPU 就全部断连。

这就引出了第二个拓扑问题，光多买网络带宽解决不了：后端流量能不能走另一条交换路径？下面的例子转向 GPU 服务器内部本来就有的交换能力。

07

用本地交换机到达正确的轨道

以两个 GPU 节点为例。同一台服务器里的 GPU 可以通过 NVLink 和 NVSwitch 通信，不必进入外部网络。跨服务器时，接在同一台 leaf 上的 GPU 处在同一条 rail 上，流量只经过这台 leaf 就能到达目的地。不同 rail 之间的通信通常要先上到 spine，再从另一台 leaf 下来。这样会多出几级交换，可能出现带宽争用，还会增加延迟，而集合通信对延迟很敏感。

NVIDIA 的 NCCL PXN 机制先通过 NVLink 把数据交给一块中转 GPU，再由它接入合适的网卡。PXN 在 NCCL 2.12 中引入，通信可以借助主机内部的交换到达另一条 rail，不必绕道外部 spine。NVIDIA 还提到，消息聚合也是这套机制的一部分，缩短外部路由并不是它唯一的优化。

在 Vakulenko 的例子里，GPU 0 要和另一台主机上的 GPU 8 通信。优化后的路径如下：

1. GPU 0 通过主机内部的 NVLink/NVSwitch 网络，把数据传给一块能访问对应网卡的中转 GPU。 2. 这块网卡把数据发到目标所在的 rail 上。 3. 流量经过一台外部 leaf 交换机，到达另一台主机。

源和目的地都没变；在本地多走一跳 GPU，换掉的是消息在外部走的路径。

| 通信场景 | 路径 | | --- | --- | | 同一台服务器内 | 本地 NVLink/NVSwitch | | 同一条 rail 上跨节点 | 一台外部 leaf | | 跨 rail，经 spine | leaf → spine → leaf | | 跨 rail，走图示的 PXN 路径 | 本地 GPU 跳转 → 一台外部 leaf |

即使两块 GPU 原本在不同的 rail 上，优化后的路径也只经过一台外部 leaf。

08

网络测试结果只是第一项检验

Vakulenko 提到，在 NCCL 测试中，小消息和大消息的性能都提升了 50%。他认为小消息的表现主要反映延迟，大消息的表现主要反映带宽，因为消息变大时延迟基本不变。演讲没有给出这些数字对应的消息大小、指标的确切定义，也没有完整的测试配置。

这些合成测试结果只说明网络处理测试负载的能力，回答不了客户真正关心的问题：某个模型的训练能提前多久完成？要回答这个问题，得在模型层面做对比。

09

在 240 块 H100 GPU 上微调 Mixtral

稀疏混合专家（MoE）模型很适合做应用层测试。专家分散在集群各处时，在专家之间分派计算会产生大量 GPU 间流量：token 要送到存放所选专家的 GPU 上，输出还要再传回来。网络因此贯穿模型执行的过程，而不只是在训练步结束时参与一次同步。

Crusoe 用 Mixtral 8x7B 做微调对比。这个架构每层有八个前馈专家，每个 token 选其中两个；名字并不是说它由八个独立的 7B 模型组成。原论文给出的总参数量约为 47B，推理时的激活参数约为 13B。Crusoe 的基准测试跑在 240 块 H100 GPU 上。

结果页的幻灯片用每秒样本数给出对比：

| 配置 | 微调吞吐量 | | --- | ---: | | 关闭 PXN | 41.798 样本/秒 | | Crusoe Cloud rail 优化 + PXN | 47.735 样本/秒 |

幻灯片显示，在 240 块 H100 GPU 上微调 Mixtral 8x7B，开启 PXN 比关闭 PXN 的吞吐量高 14.2%。

Vakulenko 把结果取整为 14%，并把这一提升和训练时间、成本联系起来。如果训练的其他环节不变，吞吐量越高，同样的训练量就能越早跑完；但吞吐量提升的百分比，不等于耗时缩短的百分比。演讲没有给出数据集、精度、并行配置和软件版本，也没有多次运行的测量结果，所以无法复现。不过结论本身很具体：拓扑上的改动提升了实测的模型负载表现，网络优化最终落到了客户付费的训练任务上。

When to use and not use agentic AI

幻灯片原文
Agentic systems suit complex tasks where the model must decide which tools to use. Simple one-step tasks may be better served by traditional rules.

[4:03](https://www.youtube.com/watch?v=wFTVEDYVJT0&t=243s) [Comparison of agentic AI use cases with tasks better suited to traditional solutions.](https://assets.ai.engineer/sites/aiecode2025/sha256/fd4e9ce6591ae931201dc99616fad18004558120207bacb4b8fa9fcdc857d457.webp)

When to use ( and not use ) agentic AI

Use agentic AI for:
• Complex workflows with variable paths and decisions
• Coordination across multiple tools and data sources
• Tasks requiring understanding context and adapting responses
• Long-running processes needing memory across sessions

Traditional solutions are Better for:
• Fixed, rule-based workflows with predictable path to outcomes
• Ultra-low latency operations (microsecond responses)
• Simple, single-step automation tasks
• Mission-critical systems requiring 100% deterministic results

用 Amazon Nova Act 和 MCP 构建智能体

跟随一个浏览器智能体，从它的规划循环，到搜索咖啡机、集成 MCP，再到一个多智能体迁移工作流，其中现场出现的失败揭示了控制和验证应该放在哪里。

具备基础 Python、熟悉命令行并理解 LLM 工具调用，有助于理解示例。

01

一个任务什么时候需要智能体？

Given an objective, how does a system decide which actions to take—and what should it do when those actions do not finish the job? The starting point is a loop: plan, act, evaluate. A prompt supplies the objective; the agent chooses actions and invokes tools; then it examines the results and decides whether to revise its plan or continue. Completion depends on that feedback, not simply on issuing a tool call.

Around the loop sit the components that make it useful: user input, an optional human intervention point, and a generated response. Inside are the LLM, an external knowledge base, guardrails, memory, tools, and connections to other agents or models. Guardrails can constrain actions and check whether a response agrees with retrieved information. MCP provides one way to connect additional capabilities.

Evaluation belongs around this entire system. Is the model appropriate? Are prompts consistent and accurate? Does performance meet expectations, and does the system solve the intended problem? Logging makes those questions inspectable; subject-matter experts can review outcomes and guide the next iteration. Use an agent when the required tools or sequence are uncertain. For a single predictable if/then operation, ordinary code may be the better solution.

The workshop places that ready-made experience beside two approaches for building your own system:

| Approach | Example | What you control | |---|---|---| | Specialized assistant | Amazon Q | Tasks within an existing assistant | | Fully managed agents | Amazon Bedrock Agents | An agent built and managed within AWS | | Do-it-yourself framework | Strands Agents | Application code, models, and tools |

Strands Agents is the workshop’s implementation path. It can use Bedrock models or reach other providers through LiteLLM.

That is a description of his example’s size, rather than a measure of reliability or runtime.

03

加上浏览器操作，再准备工作坊

Amazon Nova Act supplies the browser capability. Introduced here as a research-preview model, it can follow instructions to research a website, find products, and perform actions such as adding an item to a cart. The Nova Act SDK exposes this capability to Python; an MCP server can make it available to an assistant as tools.

MCP also connects less elaborate personal workflows. Du’An’s Obsidian server saves and retrieves documents. His bookmark server records a title, description, date, and optional notes, so Q CLI can later retrieve bookmarks about MCP or narrow the request to those saved the previous week. The useful boundary is a reusable operation with enough structured context for an assistant to call it.

Banjo Obayomi builds the workshop in three layers: first a Nova Act call, then a Nova Act MCP server, then a Strands agent that uses the server. Attendees receive provisioned AWS accounts and a browser-accessible development environment, so the session does not require local installation or a personal AWS account. The companion sample repository contains the workshop examples.

不写选择器就搜索一台咖啡机

The first script opens Amazon, searches for a coffee maker, selects the first result, and extracts the product title. Instead of inspecting the page for a particular div, h1, or p selector, the developer describes the intended interaction. The same sequence can be expressed in Python with a starting page supplied as a command-line argument:

```python import sys from nova_act import NovaAct

with NovaAct(starting_page=sys.argv[1]) as browser: browser.act("Search for a coffee maker.") browser.act("Select the first result.") result = browser.act("Return the title of this product page.") print(result.response) ```

The developer still defines the sequence. Nova Act handles the page-level interpretation needed to carry out each instruction.

The first run fails before completing the search. The Linux development environment lacks the graphical display needed by this browser invocation. Restarting through Xvfb, a virtual X11 framebuffer, supplies that display:

``bash xvfb-run -a python3 coffee.py "$STARTING_PAGE" ``

The problem is the browser’s display environment, not the coffee-maker instruction. A development editor running inside a browser does not itself provide an X11 display to the browser process launched by Python.

The restarted run narrates its progress: Amazon homepage, search box, search results, product page, title extraction. It returns a BLACK+DECKER coffee-maker title and ends the session. The useful output extends beyond that answer: screenshots and an HTML log capture intermediate actions, and a WebM recording makes the interaction replayable. Those artifacts help explain why a run reached a particular product.

Asked whether the model reasons over pixels or HTML, Banjo describes visual page understanding: it recognizes a search box and decides where to click rather than requiring the developer to name an H1 tag. The replay shows typing, searching, and selecting a result amid advertisements. But visual navigation does not remove access controls. When an attendee asks about Cloudflare blocking and CAPTCHA challenges on servers, Banjo explicitly says Nova Act does not bypass CAPTCHA.

Human participation requires a surrounding workflow. 选择托管智能体，还是代码优先的组合

Strands does not make Bedrock Agents obsolete. The choice is about development and runtime control:

| Concern | Bedrock Agents | Strands | |---|---|---| | Development | Opinionated, console-accessible | Open-source, code-first | | Integration | Built into AWS | Tools and providers selected in code | | Model access | Managed AWS experience | Bedrock, other providers, or local models | | Offline operation | Not an offline service | Possible with suitable local dependencies |

The presenters name Anthropic, OpenAI, LiteLLM, and Ollama as provider options. An application using an alternative provider need not use AWS at all. The documentation view reinforces that separation by showing OpenAI support alongside other providers.

10

规定依赖而不规定每一次工具调用

A text-to-SQL developer asks how an agent with 15 existing tools can choose the correct tools and sequence. Banjo starts with the mechanics of exposing a function: decorate it with @tool, then include it in the agent’s tools. His weather example combines the standard HTTP request tool with a custom word counter. He changes the location from Seattle to San Francisco and asks for the forecast first, followed by the number of words in the response. The weather service used in the example requires no API key.

The word-count portion is small enough to make the contract explicit:

```python from strands import Agent, tool from strands_tools import http_request

@tool def word_count(text: str) -> int: """Count whitespace-separated words in the supplied text.""" return len(text.split())

agent = Agent(tools=[http_request, word_count]) agent( "Use the National Weather Service API to find the forecast " "for San Francisco. Write a forecast summary first, then call " "word_count with that exact summary and report the count separately." ) ```

The prompt supplies the dependency: the text must exist before it can be counted. The model chooses the tool calls needed to satisfy it.

The attendee then reports confusion with larger tool sets and asks whether model-driven selection invites hallucination. Banjo recommends trying Claude Sonnet 4, expressing confidence in newer models rather than presenting a measured tool-selection result. When order must be fixed, Strands also supports explicit workflows—for example, research, then analysis, then a final report. When the order is unknown, the agent can infer it from the objective and available tools.

Du’An adds Claude 4’s interleaved thinking and parallel tool calls to the discussion. These are distinct: interleaved reasoning lets a model reconsider the task between tool interactions; parallel calls let independent operations proceed together. Neither supplies a general reliable-tool-count threshold for the SQL application.

The final integration step attaches the existing Nova Act MCP server to another Strands agent with a Claude model. The browser implementation does not need to change when its host changes. In a multi-agent workflow, each agent can also receive its own system prompt, tool set, and model; the workflow invokes those separately defined agents. That provides a direct way to give a specialist only the capabilities relevant to its work.

14

让浏览器操作及其结果可检查

Banjo distinguishes the AWS Labs catalog from the Nova Act server he wrote, then uses Amazon Q to explain its browser-action function. The central operation passes an instruction to act.act: search, click a button, or perform another action in an existing browser session. The MCP interface gives clients the operations they need without requiring each client to implement Nova Act integration itself.

A follow-up traces the local client to the local MCP server and the Chromium instance it starts. Here Banjo says screenshots remain local and then denies that Chromium information needs to be sent to Nova Act. That conflicts with his earlier description of cloud processing. A local browser must not be treated as a local-only inference guarantee: the later AWS service card describes screenshots and prompts being sent to cloud inference, while current SDK disclosures say API-key developer-tool interactions, including screenshots, are collected for service improvement. Those documents cover different service contexts and do not establish the exact payload, retention, or training terms of the workshop’s June 2025 preview.

The server’s descriptions also act as execution guidance. Banjo includes examples such as opening the hamburger menu before visiting order history, searching for Houston hotels and sorting by customer rating, or typing coffee maker into the search box and pressing Enter. A useful tool contract explains when to use the tool, how to use it, and its inputs and outputs. Encoding that guidance once gives different MCP clients the same context for constructing actionable requests.

Results close the loop. Banjo describes logs containing the starting page, results, and an action-result ID, with JSON returned so the client can decide what to do next. For UI testing, he proposes explicitly naming the interaction and the check: go to a button, click it, and determine whether the expected behavior occurs. Natural-language instructions can replace some selector-oriented scripting, but the recording does not add a formal assertion system or demonstrate that a log entry alone proves success.

It requests a zero-downtime migration, a migration plan, and a PowerPoint presentation for executives. Zero downtime is a requirement in the brief, not an achieved result. Banjo does not prescribe which specialist runs first; he leaves that sequencing to the orchestrator.

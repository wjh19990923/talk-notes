Anatomy of a skill

SKILL.md

---
name: repo-roast
description: Analyzes repository health
using git scripts. Use for repo audits.
---

**Context**

Stale TODOs: !`grep -rn "TODO" . | head -20`
Hotspots: !`git log --name-only | sort | uniq -c`
Largest files: !`git ls-files | xargs wc -l`

**Constraints**

- Never be vague — cite specific files
- Every finding needs evidence + severity
- Never recommend "rewrite from scratch"
- Maximum 10 findings, ordered by severity

**Structure**

1. One-line health verdict (score /10)
2. Top findings: issue, evidence, severity, fix
3. One thing the repo does well

规模化的技能：从重复的指令到可复用的工作流

构建一个仓库审查技能，给它确定性的输入和有选择的参考资料，然后把同样的技巧带到评测、团队分发、创意工具和周期性自动化中。

熟悉 Git、Markdown 和基于终端的编程智能体，有助于理解示例。

01

再解释一遍这个仓库

Open another terminal tab, switch repositories, and start another conversation with Claude. Before useful work begins, you explain the same things again: what matters in this project, how the team works, and which conventions the agent must follow. The problem is the repeated transfer of working context. AGENTS.md and CLAUDE.md help by supplying instructions such as using Vitest and pnpm each time a session starts.

Those instructions still need interpretation, and the agent can skip a requested step. A skill packages a recurring task so that the important requirements do not depend on someone remembering to repeat them. Zack Proser compares this to carrying DRY into agent-assisted work: the same reuse matters whether the collaborators are other engineers or multiple agents. Saved memory helps too, but repository instructions remain tied to a checkout, teammates need its updates, and global instructions can affect unrelated projects. Another requirement soon appears: how do you insert deterministic results into a nondeterministic conversation?

02

给仓库审查一个具体可查的目标

Repo Roast makes the difference concrete. Ask a generic agent to assess a repository and it may return broad praise with a few obvious suggestions. Give it the project's routing conventions, commit rules and expectations for README accuracy, and it has specific standards against which to inspect the code. The presenters suggest that roughly 30 lines of Markdown can be enough to establish that focused behavior. A skill can remain a small text file, or grow to include scripts and supporting material; its detailed instructions need only enter context when the task calls for them.

The comparison slide illustrates the intended change: generic reassurance becomes a structured assessment with concrete findings about large files, stale TODOs, documentation drift and contributor concentration. The goal is a repeatable method and report shape. Model choice and thinking settings still affect the answer, but the skill tells the agent what to examine and how to present its findings.

03

技能是一个带路由描述的包

The entry point is SKILL.md, beginning with YAML front matter. Its name identifies the skill; its description tells the model when the skill is relevant. The surrounding folder can contain reference documents, executable scripts and images. Think of the description as a routing rule, with the body supplying the instructions after selection.

Start with a few constraints that make the result useful. For Repo Roast, those might require concrete evidence, precise code locations and a Git commit reference. The presenters favor these boundaries over a long narrative prescribing every move. A compact starting point is:

```markdown --- name: repo-roast description: Analyze repository health when the user asks to roast a repo or review its maintenance problems. ---

Inspect the repository and produce an evidence-backed review.

- Never give a vague finding. - Cite each code finding with its file, line and Git commit. - Explain the consequence and a concrete next action. - Do not invent a problem to make the roast more entertaining. ```

The constraints establish what a satisfactory answer must contain while leaving room for the agent to investigate.

The workshop repository supplies the Repo Roast baseline and presentation materials. Its exercise works across programming languages because Git history, repository structure and maintenance conventions are broadly applicable. Participants can make the tone serious or playful and add requirements from their own workplaces. The workshop's share.sh asks for a name and sends the submission to a KV store, allowing the presenters to retrieve and run it on screen.

04

安装、调用与检查

The presenters primarily use Claude, but discuss skills across Codex, Cursor and Claude Desktop as well. The reusable unit also serves nontechnical work. Nick Nisi describes helping WorkOS's recruiting team combine candidate information with Slack, Notion and recruiting-system data into consistently formatted reports. That report becomes a building block for subsequent work, and sharing the skill gives teammates a common way to produce it.

For the Claude Code setup demonstrated here, repository skills live at .claude/skills/<skill-name>/SKILL.md. The equivalent directory under the user's home directory makes a skill available across projects. Other tools use conventions such as .agents; the Vercel Skills CLI handles installation across tool-specific directories, including symlink-based placement.

The development loop is small:

1. Edit and save the skill. 2. Invoke it on a representative task. 3. Inspect the output and whether the intended skill loaded. 4. Revise the description or instructions and repeat.

A skill-creator skill can help critique the package and evaluate its behavior. For the first exercise, the description should make a request such as “Roast my repo” sufficient to select Repo Roast. Put conventions and prohibitions in the body, and be more prescriptive where the result genuinely must follow an exact requirement.

05

直接提供 Git 输出，而不是问怎么去取

Claude Code supports command-output injection using an exclamation mark followed by a backtick-delimited command. The harness executes the command and substitutes its output into the skill text before the model interprets it. This is a Claude Code preprocessing feature, rather than a guarantee of the portable skill format; Nick reports adding an extension to Pi for equivalent behavior. The workshop's stale-TODO example uses grep and shell pipes to supply repository evidence.

A Git report can use the same mechanism. Instead of asking the model to work out how to retrieve recent history, give it the history in the format you want:

```markdown

Repository evidence

Current working-tree status: !git status --short

Latest ten commits: !git log -10 --format='%h %s'

Use this evidence when describing repository activity. Distinguish uncommitted changes from committed history. ```

For the same repository state, the commands provide a consistent starting point. The model can then interpret the evidence without repeatedly choosing commands, exploring Git documentation or returning a differently shaped result in another terminal session. Deterministic collection narrows the model's job to the judgment that follows.

Routing deserves the same specificity. A personal-blog image skill might apply only to a particular domain and require pixel art. A workplace image skill might use a different generator or fetch approved assets from S3. Put those distinctions in the descriptions, then ask the model when it would select each skill. This is useful feedback on ambiguous wording. It is less definitive for product capabilities: when Nick asks whether skills can call other skills, the agent performs a Claude Code lookup and returns a qualified answer.

06

把永久偏好与共享流程分开

An audience question sharpens the boundary between a rule file and a skill. In the setup Nick describes, CLAUDE.md or AGENTS.md enters context at session startup, so it should contain information that is broadly useful there. His global file is deliberately short: communication preferences and configuration directing Ideation artifacts into an Obsidian vault. A repository can add a one-line preference for pnpm; detailed testing instructions belong in a skill loaded while writing tests. Reviewing a week's work can reveal which repeated instructions deserve that treatment.

Sharing introduces a different problem. An attendee from an engineering organization worries about competing frontend skills, overlapping descriptions, review requests and instructions that become unnecessarily verbose after a model upgrade. The concern is prospective: anticipated maintenance costs are already blocking adoption. Zack suggests keeping personal modifications as local forks and periodically reviewing shared skills with the current model. WorkOS's public collection began as documentation organized into loadable units, and he reports that using those units through agentic tool calls improved his earlier generic RAG approach. Neither presenter claims to have solved the proposed original-author review and governance process.

WorkOS uses several distribution scopes: public skills, internal specialists such as authentication and developer experience, personal marketplaces, and skills committed to its monorepo. Versioned plugins provide a package boundary similar to an npm package, while an accessible internal Git repository can serve a Claude plugin marketplace. In the workshop, Nick has not used npx flags to select frontend-only skills. The current Vercel CLI documents --skill for selection and --agent for destinations. The broader packaging proposal is to document which marketplaces and team-specific packages to install during onboarding; repository ownership and review still remain underneath.

07

测试选择、任务质量和上下文边界

For public skills, Nick describes repeated runs of the same task with and without the skill, graded against a rubric. A lower grade with the skill counts as a regression. His internal experiments are less formal. The thresholds and small improvements he recalls aloud are approximate; the useful mechanism is the paired baseline, repeated as models change.

Skill pickup is a separate test from answer quality. Overlapping descriptions can cause the wrong skill to load—or no skill at all. WorkOS includes relevant terms and acronyms in its routing descriptions. When the intended skill is already known, explicit invocation such as /WorkOS, or naming Superpowers' brainstorming skill, removes some selection ambiguity. For a required data-gathering step inside a selected skill, command preprocessing can remove the model's discretion about whether to gather that input.

Another audience question asks when to choose a sub-agent, a skill or a CLI. Nick's principal criterion for a sub-agent is a separate context window. In Ideation, review work can produce extensive intermediate reasoning and tool output. A sub-agent performs that work and returns a list of problems; the parent can correct them and repeat without absorbing the entire review transcript. The desired result is evidence of completion, rather than a premature declaration that the task is done. The exchange includes a documentation lookup about sub-agents using skills, but does not develop a complete decision rule for CLIs or agent teams.

For a default that inconsistently yields to a user override, the suggested diagnostic is to ask why the agent chose that default and how the instruction could make the intended override clearer. That can help generate revisions to test, but the workshop does not supply a reproducible precedence fix.

08

用同一个包做幻灯片、图片和审查

The library discussion moves beyond repository maintenance. Nick shows a Slidev skill in the workshop repository, including its description and presentation use cases. Superpowers supplies planning and brainstorming routines; Remotion supplies a route from a prompt to a video. Zack uses Git history as input for weekly all-hands movies and describes a browser-based editing interface for trimming, cuts and fades.

Zack's image workflow wraps Google's Nano Banana in Python. He reports that most of his single-prompt image generations take under seven seconds. The next step passes the generated image to Veo, asking it to animate the scene. He reports roughly 30 seconds from a child-running-through-a-field prompt to a video, and about an hour making interstitials for a 32-minute film. These are timings from his own use; the reusable mechanism is the handoff from text to still image to animation.

Other experiments shorten different feedback loops. Zack describes biometric-based reminders, though he has not packaged that experiment as a skill, and a Superpowers interaction that offers browser mockups so he can choose a visual direction directly. Nick uses official Claude plugins and Obsidian skills, plus a review workflow that sends Claude's work to Codex and returns the findings without manual copying between terminal panes. Vercel's collection is another source they recommend exploring. The live Nano Banana image is received as an approximate match, and its style can be changed through the prompt, including Zack's preferred pixel art.

09

先让吐槽有依据，再只加载它需要的参考资料

The first participant demonstration exposes a practical scope issue. After retrieving submissions through share.sh, Nick tries to apply Zack B's Repo Roast to the WorkOS CLI. The skill was loaded locally, and the run instead analyzes the workshop repository. While themed spinner messages mark its progress, Nick inspects the submission: Git and filesystem commands collect stale TODOs, churn hotspots and the largest files. Its central constraint is that every finding must be backed by script output or Git data.

Adding detail does not require placing every reference in the skill body. Progressive disclosure leaves a pointer and a condition: read TESTING.md when doing testing, or load the scoring rubric when producing scores. The same technique can work in a rule file, but it is especially useful inside a focused skill package.

```markdown

References

- When assessing tests, read TESTING.md. - Before assigning repository scores, read scoring-rubric.md. - Skip references unrelated to the current review. ```

The reference stays available without occupying the active conversation until it is relevant.

WorkOS applies this at a larger scale. A migration skill selects the relevant provider guide, such as the Auth0 migration material, rather than loading every migration path. Its skill router uses a reference map: installing AuthKit in Next.js points to workos-authkit-nextjs.md; another framework takes another route. The top-level file becomes an index of decisions about which knowledge to load.

10

把不确定性和反复出现的摩擦变成输入

Ideation adds a gate before execution: assess whether the task is sufficiently understood, then ask questions about what remains unclear. The workshop version uses a self-reported confidence threshold of at least 95% before starting work. The presenters explicitly treat this number as a prompting device rather than a calibrated probability; the current Ideation workflow instead describes evidence-readiness gates without an aggregate numerical score. In the demonstrated approach, requiring an explanation of confidence can expose missing requirements that an unsupported number would conceal.

The useful behavior comes from the rubric and the ensuing dialogue. If the agent cannot explain the goal or success criteria, it uses AskUserQuestion to ask targeted questions, often with multiple-choice options and a recommended approach. Nick wants the agent to draw out information he has not yet expressed, rather than leave him to guess what additional context it needs.

Skill improvement follows a related loop:

1. Build a working initial skill. 2. Use it on real tasks for several iterations. 3. Review outputs and locally saved JSONL conversation logs. 4. Identify recurring mistakes, missing edge cases and repeated corrections. 5. Change the smallest relevant instruction or script and evaluate again.

Nick's early meta-skill extracted reusable procedures from completed conversations. Repo Roast offers an immediate example: if Git exploration repeatedly goes wrong, replace it with the exact command whose output the review requires. The improvement starts from an already working baseline.

Zack looks for chores he resists doing every week. Switching from code to Slack and then creating Linear tickets was one such interruption. His automation reads requests, checks Linear for an existing ticket and creates one only when needed, letting him remain focused on the coding task. When asked for a ready-made meta-skill, he suggests asking skill builder to inspect the workflow and supplying connector boundaries, such as the Slack channels and direct mentions that matter. Nick tentatively identifies Claude Meta Skill and also describes revisiting a development conversation to recover forgotten anecdotes for a blog post.

11

保留有用的记忆，并为仓库评分给出理由

Persistent memory complements a reusable procedure. Nick describes Case, a Pi-based WorkOS developer-experience agent operating across React, React Router, Next.js and TanStack Start repositories. It keeps general and framework-specific memory.md files. End-of-task retrospectives identify wasted exploration and save useful commands for future runs. He has not completed a full background dreaming or pruning system, and is uncertain about the availability of Claude's discussed AutoDream feature.

Zack proposes using date-titled Obsidian notes for direct retrieval of a week's work and then writing consolidated memories. He also points to OpenClaw's daily journals and consolidated memory as a system he found useful in personal experimentation. The pattern is to preserve detailed records close to the work, then extract the parts worth carrying forward.

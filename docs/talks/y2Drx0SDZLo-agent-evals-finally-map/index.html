智能体评测：终于有了地图

评估一个智能体表达了什么、做了什么、是否达成了目标——然后用同样的运营审视标准，去检查那个评判它的系统。

熟悉语言模型应用、检索增强生成和工具调用，有助于运用这张评测地图。

01

什么能证明一个智能体在按你的预期行事？

智能体上线生产环境之前，怎么确认它确实在按你的预期做事？一个令人信服的回答只是证据的一部分。你还得看它做了哪些动作，这些动作有没有推着它朝目标走，又让环境发生了什么变化。Root Signals 的 Ari Heljakka 把这个问题整理成一张分左右两侧的地图：一侧是语义评测，另一侧是行为评测。

语义评测问的是：智能体的表征和现实是什么关系。行为评测问的是：它的动作和工具怎样服务于目标，又怎样影响环境。两侧都可以只看局部，也可以看整个序列：

| 范围 | 语义评测 | 行为评测 | |---|---|---| | 单步或单轮 | 连贯性、一致性、回答质量 | 工具选择与使用 | | 多步或多轮 | 对话历史与推理 | 任务推进与规划 |

这种区分决定了评测者需要哪些证据。单看一条回答，能发现这条回答内部的自相矛盾；要判断整段对话前后是否一致，就得拿到对话历史。同理，检查一次工具调用，和评估一连串调用有没有取得进展，是两回事。

两侧都需要锚定在现实上。语义这一侧，把表征锚定在数据上——通常借助检索增强生成（RAG）——有助于保证真实性。行为这一侧，可用的工具把智能体的意图落到它真正能执行的动作上。Heljakka 认为这种对称不只是为了画图方便：表征世界本身就是一种活动，所以表征可以看作行为的一个特例。这张地图把两类问题分开，让评测变得可控，同时又保留了它们之间的联系。

02

把回答质量与检索依据分开

先从单条回答的质量说起。它前后一致吗？内容安全吗？是否符合相关方的价值观、遵守他们的规定？这些属性并非智能体独有，普通的语言模型应用同样需要。它们之所以出现在地图上，是因为它们构成了语义层面的基线；有了这条基线，智能体行为带来的额外要求才看得清楚。

检索又引入了一组需要评测的关系。Heljakka 把 RAG 放进一个更大的问题里看，即注意力管理：哪些信息会进入智能体的上下文？评测这个过程，就是检查检索到的上下文对不对，相关信息有没有召回全。这些问题首先针对的是喂给模型的材料，其次才是模型给出的答案。

有了答案之后，有三组区分很关键：

| 质量 | 检查的关系 | |---|---| | 忠实度（Faithfulness） | 答案对照所提供的参考数据 | | 答案相关性 | 答案对照用户的问题 | | 事实性（Factfulness） | 答案对照参考数据之外的现实 |

忠实不等于符合外部事实。 答案可以准确反映参考材料，而材料本身不完整或有错；答案也可以忠实于材料，却没回答用户的问题。把这几种关系分开看，评测不通过时，你能得到的信息比一个笼统的质量分多得多。

同样的原则贯穿整条 RAG 流水线：不同的评测器检查各环节之间不同的关系。检索质量和答案质量有关联，但不能互相替代。借助这张地图，可以先弄清一项测试到底在测哪种关系，再拿它的结果去评判整个系统。

03

在一个序列中评估含义

从单条回答走到一段对话，评测的单位就变了。现在要问的是对话历史怎样展开：对话是否一致、连贯，需要守住话题时有没有守住。判断是否跑题需要一条策略，光靠相似度测量不够。如果允许用户换话题，跟着换可能就是正确行为；在受限的交互里，同样的转向可能就是失败。

推理又带来了另一种语义序列。在推理上的投入已经换来了明显进展，受此启发，Heljakka 把推理 trace 的评测也纳入进来，前提是能拿到这些 trace。推理 trace 是一连串表征活动：智能体在采取外部动作之前，如何一步步形成自己的理解。对话评测跟踪的是智能体和用户的交流；推理评测跟踪的是智能体得出答案或决策时，能被观察到的那段过程。

04

在评判轨迹之前先检查动作

转到行为这一侧，先看单个动作。智能体有没有遵循指令？它能否正确理解可用工具的特性，挑出合适的那个？工具输出的质量够不够，工具调用出错时处理得对不对？哪怕还没有一连串动作可评估，这些检查针对的也已经是行为。

调用的结构要单独检查。一次工具请求可能选对了操作，却给出了格式错误的 JSON，或者参数不符合工具的约定。反过来，结构完全合法的请求也可能选错了操作。以一个查询订单的任务为例，模型拟定的调用可以表示为：

``json { "tool": "get_order", "arguments": { "order_id": "ORD-1042" } } ``

有了这条记录，几种区分就具体了：JSON 是否合法看语法；参数校验看 order_id；工具选择看 get_order 是否契合指令。光凭这次拟定的调用，判断不了返回的订单记录质量如何，也判断不了工具出错时处理得怎样。这些要等后续实际执行，拿到证据才能评判。

05

衡量动作是否收敛到目标

每次调用单独看都没问题，整个序列仍然要当作序列来评测。这些动作是否在朝目标收敛？计划是否前后一致？按这个任务真正看重的质量标准衡量，它算不算好计划？仅凭局部正确，回答不了这些问题。评测者必须把这一连串行为和预期结果对照起来看。

这样一来，地图的两半都回到了外部现实。表征最终以真实性为锚，行为最终以目标达成与效用为锚。按 Heljakka 的说法，中间的各项检查都是通向这两个终点的代理指标。工具选择分、计划质量分之所以有用，是因为它们能帮你解释或预判成功的行为；但它们不能取代最终那项检查：智能体到底有没有做成一件有用的事。

06

加上效率、诊断和实时评估

这张地图回答了评测什么，但真正运营一个智能体，还会多出几个维度。成本和延迟很重要，因为目标是以尽可能低的成本、尽可能快地达成目的。步数也属于这项优化：走哪条路到达结果，不只关乎行为，也有实实在在的运营后果。

追踪和调试提供证据，帮你定位智能体在哪一步出了错。这部分讨论里的错误管理，专指工具使用中的错误，和推断或推理时犯的语义错误不是一回事。把这条界线摆在明面上，才能分清两种失败：一种是和工具的交互出了问题，另一种是对世界的理解出了偏差。

评测时机贯穿整张地图：

- 离线测试： 开发阶段能尝试、评测哪些东西？ - 在线测试： 智能体实际运行时，能够——也应该——评测哪些东西？

这些是独立的维度，为了让简化图保持清爽，图里没有画出来。但评测体系仍要专门考虑它们：开发阶段的测试和线上运行时的检查，是在不同条件下回答问题。

07

在契约具体的地方使用常规测试

针对具体应用的评测，超出了这张通用地图的范围。有些专门方向已经相当成熟，有些仍是活跃的研究领域。该补充什么，取决于智能体做什么。如果工具就是一次 API 调用，行为可以独立测量，那么针对工具的指标就相对简单。

这类工具约定通常可以用传统的软件测试方法来测。其他很多度量则采用 LLM-as-judge（让 LLM 当评委）的技术。所以，评测体系可以两者结合：用常规测试检验工具的具体行为，用模型来判断那些需要解读的质量。不过，一旦引入评委，就多了一个系统，它的行为和运行成本同样需要关注。

08

既优化智能体，也优化评判流程

常见的起点是单层方法：优化真正干活的 LLM 流程，也就是智能体本身，并用评测分数来指导优化。这种做法漏掉了一点：评委本身也会带来成本、延迟和不确定性。拿到分数，并不代表可以不去理解打分的那个系统。

Heljakka 建议尽早把评委的优化考虑进来。他的双层方法把两条流程都当作优化对象：

| 方法 | 优化范围 | |---|---| | 单层 | 智能体执行流程 | | 双层 | 智能体执行流程与评判流程 |

有了第二层，评测本身也成了运营问题。智能体要把任务做好；评判流程要评估这份表现，同时恰当顾及自身的不确定性、开销和延迟。

Heljakka 把这项工作称为 EvalOps。评测可能复杂、昂贵、缓慢到需要专人专项去运营。在他看来，EvalOps 是 LLMOps 的一个特例：它处理的对象不同，所以需要不同的实现选择、思考方式和资源分配。把评委嵌进工作流只是开始；把评测做对，本身也是一项需要投入资源的工作。

最终目标是让智能体可衡量、可控制，让它的行为符合运营者的意图。评测要服务这个目标，就得做到三点：把表征和现实连起来，把动作和预期目标连起来，并让评判过程本身也成为一个能被理解、能被改进的系统。

朴素 RAG 的挑战

幻灯片原文
The speaker introduces response quality as a challenge in bringing naive RAG applications to production.

Challenges with “Naive” RAG

朴素 RAG 的挑战（回答质量）

幻灯片原文
Low precision brings irrelevant chunks into the context; low recall leaves needed information out. Even with retrieval, the LLM can produce hallucinations, irrelevant answers, or toxic or biased responses.

Challenges with Naive RAG (Response Quality)

• Bad Retrieval
  ◦ Low Precision: Not all chunks in retrieved set are relevant
    ▪ Hallucination + Lost in the Middle Problems
  ◦ Low Recall: Now all relevant chunks are retrieved.
    ▪ Lacks enough context for LLM to synthesize an answer
  ◦ Outdated information: The data is redundant or out of date.
• Bad Response Generation
  ◦ Hallucination: Model makes up an answer that isn’t in the context.
  ◦ Irrelevance: Model makes up an answer that doesn’t answer the question.
  ◦ Toxicity/Bias: Model makes up an answer that’s harmful/offensive.

Jerry Liu 讲解了如何诊断检索失败、评估完整的 RAG 流水线、通过分块和元数据提高精度，并有选择地引入智能体或微调。

生产就绪的 RAG 始于度量，而不是更多的上下文

01

基线架构——以及它为什么会崩

Jerry Liu 是 LlamaIndex 联合创始人兼 CEO。他介绍了两大类方法，帮语言模型处理训练数据之外的数据。一类是检索增强：模型保持不变，在提示词里补充外部上下文。另一类是微调：通过更新模型权重或适配器，把新知识融进模型。一个基础的检索增强生成（RAG）系统分两步：先摄取数据，再查询；查询本身又包括检索和合成两个环节。0:14 1:09

很多常见应用都基于这套架构，比如针对 PDF 和其他非结构化数据的问答。但原型能跑，不代表能上生产。检索一旦漏掉相关内容，语言模型就拿不到答对所需的上下文。精确率低会混进无关的文本块和多余内容，带来幻觉风险和“中间迷失”（lost in the middle）问题；召回率低则意味着必要的信息压根没出现在检索结果里。检索之外，信息过时、输出跑题、有害内容和偏见也会带来额外的局限。2:04 3:01

整条流水线处处都有改进空间：底层数据和分块边界、嵌入表示、检索算法，以及最后的合成阶段。Liu 还认为，语言模型在生成答案之前就能出力：把复杂问题拆成几个简单问题，在多个数据源之间路由请求，支撑更复杂的推理。3:59 4:55

- RAG 不动模型权重，只补充外部上下文；微调则更新模型权重或适配器。 - 基础流水线分三步：摄取数据，检索相关信息，合成答案。 - 精确率低会混进无关文本块，增加幻觉风险；召回率低会漏掉作答所需的信息。 - 从数据准备、嵌入、检索和合成四个环节入手改进；借助 LLM 的推理能力拆解查询，或在多个数据源之间路由。

02

在优化流水线之前先建立评测

要在生产环境里持续改进，得先有一个针对具体任务的基准，之后改架构才有比较的依据。Liu 区分了两种评测：一种看从查询到回答的完整体验，一种单独看各个组件。如果瓶颈看起来在检索，光看最终答案质量，说不清某项检索改动到底有没有找回更相关的证据。4:55 5:50

评测检索时，先构建一个数据集，把每条输入查询和相关文档的 ID 对应起来。这些标注可以来自人工标注、生产环境的用户反馈，也可以合成生成。有了数据集，就能用成功率、命中率、MRR、NDCG 等标准排序指标量化检索质量。在 Liu 看来，这个组件本质上是信息检索问题，而不只是语言模型问题。6:45

评测端到端效果时，准备一批查询，并配上人工标注、用户反馈、参考答案，或用 GPT-4 合成的样例。让这些样例完整走一遍检索和合成，再用基于语言模型的评测打分，有没有参考标签都行。这样就能把两个问题拆开看：系统有没有找到有用的原始材料，最后有没有给出有用的答案。6:45 7:44

- 改检索或合成之前，先定好针对具体任务的基准。 - 把检索评测和端到端答案评测分开，找出到底该改哪个组件。 - 把查询和相关文档 ID 配对，用成功率、命中率、MRR 或 NDCG 给检索打分。 - 借助人工标注、用户反馈、参考答案或 GPT-4 生成的样例，评测完整回答。

03

从分块、解析和元数据开始

Liu 建议先把 RAG 的基本功做扎实，别一上来就用最复杂的手段。实用的起点包括：用更好的解析代替一刀切的文档切分，调整分块大小，在支持的地方用混合检索，再加上元数据过滤。重排序、递归检索这类高级手段可以往后放，但有没有用要拿基准来验证，不能想当然。8:34

分块大小影响尤其大，因为检索回来的 token 越多，答案不一定越好。长上下文窗口中间的信息，模型更难用上；对检索结果做重排序，也不会自动让最终回答变好。Liu 提到，他们观察到最优分块大小因数据集而异，还遇到过重排序反而让错误指标上升的情况。这再次说明，评测不能只看检索改动，还得看合成结果。9:30 10:26

元数据过滤给原本非结构化的文本块加上结构化上下文。有用的元数据包括页码、文档标题、相邻块的摘要，或者用模型生成、这个块能回答的问题。比如有人问某份 2021 年 SEC 10Q 文件里的风险因素，单靠语义搜索可能会捞到其他年份的文档。如果先推断出“年份等于 2021”这样的结构化过滤条件，再配合语义搜索，候选范围就会缩小，精确率也随之提高。10:26 11:20

- 先做好解析、调整分块大小、用上混合检索和元数据过滤，再考虑高级检索。 - 多检索 token、加重排序，都不一定能改善生成的答案；要针对具体数据集测试分块大小。 - 给文本块附上结构化元数据，比如页码、文档标题、相邻块摘要或生成的问题。 - 把语义搜索和推断出的过滤条件（如“年份等于 2021”）结合起来，排除无关文档，提高精确率。

04

先窄范围检索，再扩展证据

由小到大检索（small-to-big retrieval）要解决一个错位：好检索的文本和好用来合成答案的文本，往往不是同一段。给一大段文字做嵌入，周围的内容也会混进表示里，查询真正要找的那条信息就被冲淡了。更好的做法是索引更小的单元，甚至细到单个句子，先检索这些更具体的单元。12:18

找到相关的小单元后，再把它扩展成更大的上下文窗口，然后交给语言模型。这样既保住了精准匹配，又给了模型足够的上下文，能合成出连贯的答案。Liu 提到，可以只检索少量结果，比如 K = 2，而不是检索 K = 5 个大块——大块太多可能塞满上下文窗口，把相关内容淹没在里面。13:05

还有一种相关做法：嵌入一个指向父块的引用。这个引用可以是一段更短的摘录、一份摘要，或者针对这段长文本生成的问题。检索用的表示专门为匹配可能的查询而优化，返回的父块上下文则负责提供合成所需的信息。核心设计原则是：为嵌入检索优化的对象，不必和最终交给模型的证据是同一个东西。13:51

- 对句子或其他小单元做嵌入，比宽泛的大块更能精准匹配具体查询。 - 检索到小单元后，先扩展它周围的上下文，再合成答案。 - 和检索更多大块相比，较小的 top K 能减少多余上下文，缓解“中间迷失”问题。 - 用更短的摘录、摘要或生成的问题做检索，再把关联的父块上下文交给模型合成答案。

由小到大检索 先匹配细粒度证据，再扩展上下文，用于合成答案。 - 小单元 — 对句子或更小的块做嵌入。 - 精准检索 — 针对查询找回细粒度的匹配结果。 - 扩展上下文 — 返回周边窗口或父块。 - 答案合成 — 用更宽的上下文生成回答。 - 小单元 → 精准检索（匹配具体上下文） - 精准检索 → 扩展上下文（扩展检索到的证据） - 扩展上下文 → 答案合成（提供足够的上下文）

05

在任务确有必要时才使用智能体和微调

有些问题，单次 top-K 检索解决不了。任务可能需要多步推理、总结整篇文档，或者对比多份文档。Liu 介绍了一种还在探索中的多文档智能体架构：每份文档对外提供工具，分别用来做总结和回答具体事实问题。智能体没法直接调用无限多的工具，所以先由检索层挑出相关文档的工具，智能体再去调用它们。13:51 14:52 15:47

智能体的表达能力可能更强，但 Liu 也明确指出了代价：实现更难，还可能增加延迟和成本。它的独特之处在于，系统检索的是可执行的能力，而不只是把检索到的文本塞进上下文窗口。Liu 把检索和工具调用的结合看作处理更复杂分析的一个方向，而不是简单 RAG 流水线的默认替代品。9:30 14:52 15:47

如果预训练的嵌入表示找回的信息不对路，可以用嵌入微调让检索适应特定领域的问题。Liu 介绍的做法是：从原始文本块合成查询，再用这些样例微调基础嵌入模型或适配器。用适配器微调，不需要拿到基础模型的权重；只微调查询一侧，还能省掉给整个文档库重建索引。15:47 16:44

微调也可以针对负责合成答案的语言模型。Liu 提到，他们在探索用 GPT-4 这类更大的模型生成合成训练样例，再把能力蒸馏到 3.5 Turbo 上，目标是提升推理能力，并让模型能写出更长的回答和结构化输出。这些方向都还在探索阶段，不保证在生产中见效；有没有用，仍要看前面建立的、针对具体任务的评测。4:55 17:33

- 需要多步推理、文档总结或跨文档对比的任务，可以用多文档智能体。 - 先检索出相关文档的工具，再调用它们的总结或事实问答能力。 - 智能体会增加实现复杂度、延迟和成本，用不用要拿针对具体任务的评测来论证。 - 用合成查询微调嵌入；适配器不需要基础模型权重，只调查询侧则不必给文档库重建索引。

多文档智能体的执行流程 先检索相关文档的能力，再调用这些能力完成更复杂的分析。 - 文档 — 用每份文档提供的能力来表示它。 - 文档工具 — 提供总结和事实问答能力。 - 工具检索 — 从更大的工具集合中挑出相关工具。 - 智能体执行 — 调用检索到的工具，而不是直接塞入原始文本。 - 文档 → 文档工具（建模为能力） - 文档工具 → 工具检索（检索相关工具） - 工具检索 → 智能体执行（执行选中的工具）

要点总结

  • 在修改流水线之前先定义一个 针对任务的基准，并把检索质量与完整的“从查询到答案”的表现分开评估。4:55 5:50 6:45
  • 在引入更复杂的检索或智能体架构之前，先从 更好的解析、调整块大小、混合搜索和元数据过滤 做起。8:34 10:26 11:20
  • 检索更多上下文和重排序并不会自动改善答案；要测量它们的效果，因为上下文过载和 “中间丢失” 现象可能让结果变差。9:30 10:26 13:05
  • 使用 由小到大的检索：先匹配精确、紧凑的证据，再扩展到综合所需的更大上下文。12:18 13:05 13:51
  • 把 多文档智能体 和 微调 留给值得承担其额外复杂度、延迟或成本的需求；查询端的适配器调优可以在不重建整个语料索引的情况下改善检索。9:30 14:52 16:44

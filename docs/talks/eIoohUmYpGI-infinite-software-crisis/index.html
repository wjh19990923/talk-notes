无限的软件危机：让人的理解始终领先于 AI 生成的代码

Jake Nations 解释了为什么更快的代码生成可能叠加偶然复杂性，以及调研、实现规划和来之不易的系统知识如何帮助工程师继续对自己交付的东西负责。

无限的软件危机：让人的理解始终领先于 AI 生成的代码

01

瓶颈已经从写代码转移到理解代码

Jake Nations 一开场就承认了一件不太光彩的事：有些代码他自己都没法完全讲清楚，却照样生成、测试、部署、上线了。他在 Netflix 帮忙推动 AI 工具落地，好处他也看得很清楚：过去要几天的活，现在几小时就能干完；拖了很久的重构，也终于能动手了。但生产系统总会以意想不到的方式出问题。测试通过，不代表工程师到了要调试的时候能看懂这些代码。 0:21 1:19

他把这种矛盾放回软件危机反复上演的历史里来看。计算能力和需求不断扩张，每一代开发者都会拿起新东西：新的编程语言、个人电脑、面向对象编程、Agile、云基础设施、移动开发、DevOps。每一波都让开发者产出更多，但系统越长越大、越来越难管，这个问题没有哪一波真正解决掉。AI 延续了这个规律，只是把代码生成的规模和速度大幅拉高了。 1:19 2:15 3:13

Fred Brooks 的 No Silver Bullet（《没有银弹》）给出了核心区分：软件开发最难的不是语法、敲代码或写样板代码，而是理解问题、设计出合适的解法。工具能加快机械性的工作，却拿不掉这个根本难题。生成代码一旦几乎不花时间，真正卡脖子的就变成：人的理解跟不跟得上软件产出的速度。 3:13 16:28

- AI 能把几天的工作压缩到几小时，但产出的代码哪怕已经上线，作者也未必能完全讲清楚。 - 测试通过，不等于具备了排查意外生产故障所需的理解。 - 代码生成更快，只是加速了机械性工作，理解问题、设计方案这两件事并没有因此解决。 - 生成速度一旦超过理解速度，对系统的理解就成了实际的瓶颈。

02

容易的代码不一定是简单的代码

Nations 借用 Rich Hickey 对 简单（simple）和 容易（easy）的区分，解释为什么能干的工程师仍会造出连自己都难以理解的系统。简单说的是结构：各个组件互不纠缠，每部分职责清楚。容易说的是上手难度：一个包、一段复制来的方案、一个框架或一份生成的实现，随手就能拿来用，几乎不费力气。东西变容易了，底层结构并不会因此变得清晰一致。 4:14

在 AI 出现之前，团队往往还消化得了“眼下方便”和“日后复杂”之间的取舍，因为代码积累得够慢，有时间回头重构。Nations 认为，AI 打破了这种平衡：写实现变得毫无阻力，大家也就更容易跳过架构层面的推敲。眼前的回报是速度；延后支付的代价，是系统的行为和依赖越来越难推理。 5:12

他用一个身份认证的例子说明了这个过程。一份简单的 auth.js，随着对话里的指令越堆越多，演变出 OAuth.js、失效的 session、相互冲突的方案、打过补丁的测试和废弃代码。每次请求都能解决眼前的症状，却也可能推翻之前的架构决策。到了第二十轮交互，开发者可能已经在收拾一团纠缠不清的历史约束，而不是有意识地塑造一个看得懂的系统。 5:12 6:07

更深层的问题在于，编码智能体会把现有的每一种实现都当成值得沿用的模式，旧的变通写法和架构错误也不例外。一段认证检查和一个别扭的遗留 gRPC 模式，在它眼里可能是同样合理的先例。如果没有人来判断哪些结构该留下，生成只会照搬已有的复杂性，再在外面裹上新的一层。 6:55 7:53

- 简单指结构互不纠缠；容易指实现随手可得。 - 零阻力的生成追求眼前的速度，同时不断累积架构复杂性。 - 反复改动认证逻辑，可能留下失效的 session、相互冲突的方案、打过补丁的测试和死代码。 - 工程师如果不加区分，智能体会把有用的模式和技术债一并保留下来。

03

把本质需求与偶然复杂性分开

Nations 区分了两种复杂性：本质复杂性（essential complexity）是软件要解决的问题本身固有的难度；偶然复杂性（accidental complexity）是实现过程中一点点堆起来的各种机制。支付、订单履约属于本质需求。变通写法、防御性代码、老化的框架、一度有用的抽象，完成使命后如果还留着，就会变成偶然复杂性。在成熟系统里，两者缠在一起，要分开它们，得靠上下文、历史和经验。 6:55 7:53

Netflix 的一次授权迁移说明了这种区分为什么重要。当时团队没法把整个应用推倒重来，于是在旧的授权代码和新的集中式认证系统之间加了一层抽象。把这个中间层换掉，看上去很适合交给 AI 辅助重构；可旧的授权模型早已深深嵌进业务逻辑、数据模型，还有散落在几百个文件里的权限检查。 7:53 8:52

智能体能在几个文件里推进一点，然后就会撞上它理不清的依赖；要么，它会在新系统上把旧系统的假设原样复刻一遍。问题不只是看到的代码不够多，授权行为和业务行为之间的边界本身就是模糊的。Nations 认为，在让 AI 执行迁移之前，工程师必须先找出架构上的接缝（seams），分清哪些是真实需求，哪些只是历史上的实现选择。 8:52 9:50

- 本质复杂性属于问题本身；偶然复杂性来自不断堆积的实现机制。 - 一层临时的授权 shim 把遗留授权代码接到了新的集中式系统上。 - 权限检查、角色假设和四处散落的授权调用，让几百个文件里的边界变得模糊不清。 - 让智能体迁移紧耦合代码之前，先找出架构接缝和历史假设。

04

把对系统的理解压缩成调研、规划和实现

代码库规模太大，逼得 Nations 只能有选择地给信息。按他的描述，那里有大约一百万行 Java，光主服务就有大约五百万 token，超出了他能用的上下文窗口。直接塞进大段代码，看不出清晰的架构全貌，生成的结果反而迷失在同样的复杂性里。于是他挑出相关的设计文档、架构图、接口、组件交互和行为需求，把问题压缩成一份约 2000 词的规格说明，外加一套精确的执行步骤。 9:50 10:44

第一阶段是调研。借助相关文档、架构资料、Slack 讨论串和代码库分析，智能体能梳理出组件、依赖，以及拟议改动可能波及的范围。这个阶段要反复迭代：工程师追问缓存、故障处理等具体环节，补上缺失的上下文，纠正错误的分析。产出是一份调研文档，写清楚现在有什么、各部分怎么连接、改动会影响哪里。关键是，进入下一步之前，必须有人对照实际系统核实这份文档。 10:44 11:43

第二阶段是制定实现计划。工程师基于核实过的调研结果，写出一份具体计划，涵盖代码结构、函数签名、类型定义、数据流、服务边界和复杂的业务逻辑。架构决策要在这一步明确做出，不必要的耦合也能尽早发现。Nations 强调，计划只要足够详细，审起来就快，执行起来也可预期，理解就能跟上后面的代码生成。 11:43 12:40

最后一个阶段是按批准的计划实现。这套流程不再任由一段冗长的对话反复改动设计，而是依次产出三份聚焦、逐步验证的产物：调研、计划、实现。大部分机械性的编码可以交给后台智能体，工程师同时去忙别的；审查也简化为检查实现是否符合约定的设计。分工很清楚：AI 负责加快执行，人负责综合和判断，并对架构负责。 12:40 13:32

- 生成代码之前，先把相关的架构、接口和需求压缩成一份聚焦的规格说明。 - 调研要梳理组件、依赖和改动影响，并对照实际系统核实结论。 - 把核实过的调研转化为实现计划，覆盖签名、类型、数据流、边界和耦合。 - 按批准的计划生成代码；审查时只看实现是否符合计划，不必从头摸清它的设计。

从调研到实现的工作流 先核实对系统的理解，再定架构、生成实现。 - 调研 — 梳理组件、依赖和改动影响。 - 人工核实 — 对照实际系统检查调研结果。 - 实现计划 — 明确结构、类型、数据流和边界。 - 实现 — 按批准的计划生成聚焦的代码。 - 符合性审查 — 确认生成的代码遵循计划。 - 调研 → 人工核实 (核实结论) - 人工核实 → 实现计划 (使用核实过的调研) - 实现计划 → 实现 (按清晰的计划执行) - 实现 → 符合性审查 (检查是否符合计划)

先真正理解，再尝试自动化

这次授权迁移也暴露了三阶段方法的一个重要局限：团队得先手动完成一次迁移，这套方法才真正用得起来。工程师读现有代码、追踪依赖、改实现，然后看哪里出了问题。这番苦功挖出了隐藏的约束、必须守住的不变量，以及授权改动会波及的服务。Nations 说，这些知识光靠代码分析是挖不出来的。 14:29

之后，团队把这次手动提交的 pull request 当作具体范例，用于后续调研。即便有了这个参照，各个实体之间仍有差异，比如有些数据是否加密，所以工程师得逐个补充上下文、追问分析结果。Nations 说得很明白：这样得到的计划可能管用，但不保证管用。团队仍在验证、调整，不断发现新的边界情况。 14:29 15:24

这个局限反过来印证了他的主要论点。单靠更好的提示词、更大的模型或更精致的规格说明，都救不了场。测试通过的代码，不一定扛得住生产环境，也不一定能让日后的维护者看懂。要安全地自动化，前提是对系统了解得足够深：认得出有意义的边界，守得住必要的不变量，判断得了生成的改动是否真的解决了对的问题。 15:24 16:28 17:21

Nations 还提醒，如果总是跳过理解生成系统所需的思考，工程师识别危险架构模式的能力会慢慢退化。这种判断力，是在维护难缠的系统、直面一次次故障中练出来的。他提出的工作流会留下可供审查的产物，把理解压缩进去，而不是把理解外包出去。真正要问的不是 AI 会不会写出更多软件，而是对这些软件负责的人，是否仍然理解自己运维的系统。 16:28 17:21 18:20

- 先手动迁移一个有代表性的案例，挖出隐藏的约束、必须守住的不变量和受影响的服务。 - 把完成迁移的 pull request 当作具体范例，用于后续改动的调研。 - 考虑各实体之间的差异（包括加密），并持续验证计划和边界情况。 - 保留人对架构的判断：测试通过、生成飞快，都不保证生产环境下的韧性和可维护性。

先挣到理解，再谈自动化 一次手动迁移，为之后的辅助迁移打下具体的知识基础。 - 手动迁移 — 读代码、追踪依赖、动手修改。 - 暴露约束 — 发现不变量、受影响的服务和故障点。 - 参考 pull request — 用完成的迁移为调研打底。 - 逐案调研 — 为加密等差异补充上下文。 - 核实后的迁移计划 — 生成、调整并检查边界情况。 - 手动迁移 → 暴露约束 (揭示隐藏条件) - 暴露约束 → 参考 pull request (沉淀在手动迁移中) - 参考 pull request → 逐案调研 (为后续调研打底) - 逐案调研 → 核实后的迁移计划 (产出候选计划)

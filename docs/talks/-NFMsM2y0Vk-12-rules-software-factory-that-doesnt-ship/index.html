Say Who Owns the Code

幻灯片原文

Say who owns the code

Claude Fable 5.2 responds closely to what the prompt says about who owns the code it works on. In Anthropic’s testing on small coding tasks, when a prompt said nothing about ownership or presented the code base as someone else’s, the model tended to add to the existing structure, even when that repeated existing code. It also tended to report nearby problems instead of fixing them. When the prompt says the code base is the model’s own, the model often merges repeated code and makes related fixes without being asked.

If you want the model to improve the structure as it works, say that the code is its own:

This codebase is yours: what it's for and how it's built are your call, and you'll keep building on
it.

12 Rules for a Software Factory That Doesn’t Ship Slop

A coding agent can pass today’s tests and leave tomorrow’s feature harder to build. Dex Horthy uses Slop Code Bench and a familiar pull request workflow to explain how teams can automate implementation, catch problems earlier, and decide where human review still matters.

01

Passing today’s tests leaves tomorrow’s code

Getting the tests to pass gives a coding agent a clear target. It can hit that target and leave behind an abstraction that makes the next feature harder to add. Dex Horthy, whose team at HumanLayer had just joined Factory, had previously made the case for reading agent-written code on that intuition. This time he brought a result from Slop Code Bench, a benchmark that asks models to evolve a codebase across successive checkpoints. The best score he cited was about 16%. 1:24

A study Horthy cites reported that 30% of pull requests merged without review, along with longer and more numerous comments, more incidents per pull request, and more bugs per developer. The talk leaves the study’s sample and comparison baseline unspecified. For a software factory, the practical question is how review and testing keep pace when changes get cheaper to produce. 1:35

02

What starts the work and what sends it back

A software factory standardizes a workflow that predates coding agents. Engineers and product managers decide what to build and record it in a tracker. Someone picks up an item, implements it, runs tests, and opens a pull request. A reviewer can try the change locally while continuous integration runs tests and linters. If the change needs work, it goes back for fixes. When it’s ready, canaries, staged rollouts, and feature flags control how it reaches users.

Users report breakage and ask for features, giving the team new work. When a customer is the first to catch a 3 a.m. failure, the team adds monitoring so the next failure can page an engineer sooner. Put an agent in the implementation step and those signals can also start work automatically. Horthy calls that forward pressure. A feature request could go straight to the factory. An incident could start work on a proposed fix, giving the on-call engineer a pull request to assess alongside the stack trace.

Back pressure gives the agent feedback it can act on before a human spends time on the change. Implementation can take minutes or hours while review and testing still take hours or days. Agent reviewers and agent-run tests can catch problems alongside CI and linters. Formal verification can help where the team can specify a property to prove. A feature from the tracker and a patch proposed during an incident can take the same path through review. The findings determine whether the change needs another pass or is ready for rollout.

Engineers take work from an issue queue and open a pull request. If CI checks, human testing, or review find a problem, the change goes back for fixes. The team rolls ready changes into production with canaries and feature flags.

Which events start work, and what happens after review? Three paths can start implementation. Once a pull request opens, review can send the change back for fixes or let a ready change proceed to rollout. - Tracked item — The team records work it wants to build. - Feature request — A request can go straight to the factory. - Production incident — An incident can trigger work on a proposed fix. - Agent implementation — The agent builds or revises the change. - Pull request review and checks — Reviewers and automated checks assess the proposed change. - Controlled rollout — Canaries, staged rollouts, or feature flags control exposure. - Tracked item → Agent implementation (Pick up work) - Feature request → Agent implementation (Can start feature work) - Production incident → Agent implementation (Can start work on a fix) - Agent implementation → Pull request review and checks (Open a pull request) - Pull request review and checks → Agent implementation (Return problems for fixes) - Pull request review and checks → Controlled rollout (Proceed when ready)

03

Slop Code Bench makes earlier decisions carry forward

An agent can clean up a codebase when someone understands what’s there and can point it toward a change. Slop Code Bench asks what happens when the agent gets a series of requirements at successive checkpoints. Each new requirement lands on the code left by the previous one. Given the whole problem up front, the agent can design around all the requirements it already knows. In a checkpoint sequence, a new feature can expose a bad abstraction. The implementation then has to absorb the feature using that abstraction, centralize the logic, or remove the abstraction and make room for a better design.

What can you inspect beyond the overall score? Cyclomatic complexity counts independent paths through code. The share of high-complexity functions shows how widespread that branching is, while lines per symbol captures the size of individual code units. Slop Code Bench has 200 custom rules. Fifty draw on established practices, and many of the others came from comparing model-written code with pre-AI repositories. The benchmark also tests library and interface design. The reported headline score comes without a breakdown of how the checkpoints and quality measures contribute to it. 7:45

Two Python habits moved in different directions.

- Error handling. Models had learned to raise exceptions in situations where they used to return tuples. With a return value such as (value, error), each caller has to inspect what came back. An exception lets the caller handle the failure with try and except or let it propagate. - String formatting. Some flagged patterns had become more common than they were in models from about six months earlier. Horthy singled out Claude and GLM for reaching for %s formatting in Python 3 where he wanted f-strings.

One prompting suggestion was to tell Fable that it owns the codebase, on the theory that it might keep the code cleaner. Horthy had yet to test that suggestion, and benchmarking was underway during the talk. For software a team expects to maintain for months or years, his advice was to keep enough knowledge of the system to steer the cleanup it needs.

In Anthropic’s tests on small coding tasks, Claude Fable 5.2 often merged duplicate code and made related fixes unprompted when told it owned the codebase. Horthy’s own benchmark was still running.

04

Plan around the cost of changing your mind

Architecture review and sprint planning give teams a chance to catch disagreements before implementation. The same calculation applies when an agent writes the code. Agreeing on what to build and how it fits the system can save another round of implementation, testing, and review. Faster generation makes one part of that round cheaper. You can still spend hours or days finding out whether you built the right thing.

Planning time counts, too. Horthy remembers spending six hours on a spec and wondering whether he could have just tried the change. For a small task, a two-sentence prompt and a couple of follow-ups may be enough. In his hypothetical comparison, even a five-hour spec can leave some revision after the build. Spending 20 hours writing the code by hand removes the chance of rework caused by an agent’s choices. Ordinary human mistakes are still possible.

Horthy calls the rule of thumb “expected pain.” Multiply the chance a decision will need to change by how hard it would be to change. You can revisit a button color once you see it. Changing a database schema later is much harder, so it deserves more scrutiny before the build.

05

Show people the plan and give agents a way to test the build

- People reviewing the plan. Horthy’s show me skill produces HTML mockups, tables, and charts. A mockup makes a proposed interface concrete while the team can still change the plan. A table or chart puts options or results in view together. - Agents checking the build. A browser, screenshots, or a video let an agent inspect the interface. With curl, it can see a service response. For an iOS app, the agent needs an environment where it can build, run, and test the app. Each attempt then produces something the agent can inspect and use to decide what to change before trying again.

06

Encode recurring review feedback and give experiments room

A lint rule can flag a recurring code pattern before a reviewer has to point it out by hand. For TypeScript, Horthy points to the Anti-Slop repository, with roughly 100 rules, and to Factory’s ESLint plugin. Python teams can reuse the code-quality rules from Slop Code Bench. Putting those rules where the agent can run them lets it locate and revise a flagged pattern before a person reviews the change.

A rough prototype can answer whether anyone wants a feature before the team spends time polishing it. A feature flag controls who gets to try the change. Give an agent access to a flagging system such as PostHog or LaunchDarkly, and it can try an option, see how it performs, and use the result to inform what stays in the product.

Past agent sessions can also inform evaluations. For example, a team could turn a failure from an earlier session into an evaluation case, then see whether later attempts still run into it.

07

Keep decisions near the code and define what correct means

GitHub gave teams a shared place for patches they once sent around by email. Agent work can bring back the manual relay. One engineer copies an answer into Slack. A coworker pastes it into their agent, sends the result back, and the first engineer pastes that result into the original session. Two people spend their time moving context between agents.

Unifying the forge means bringing code, designs, and decisions as close together as possible. A decision worked out in a session or written in Notion or Google Docs should be easy to find from the change it shaped. The next person can recover why the code took its current form.

- Development environment. A team can buy virtual machines or bring its own setup with the dependencies and tools its code needs. - Agent harness. A team can adopt a full-featured harness or start with a minimal one and customize how the agent works. - Control plane. This is where people collaborate on sessions and plans, schedule tasks, respond to events, and set rules for how the factory operates.

Where does verification fit among those pieces? A control plane can coordinate the work. The engineers who know each repository supply the checks that say whether the result is correct. In Horthy’s example of an organization with hundreds of engineers and hundreds of repositories, teams can share the infrastructure that runs the checks. The knowledge of which behaviors matter and how to test them still lives with the teams.

08

The Anti-Slop Manifesto and the cost of attention

Horthy and his collaborators launched the Anti-Slop Manifesto to carry the same ideas beyond software. Its commitments start with “outcomes over outputs.” Preserve understanding as work gets faster, bring your own thinking to the model’s first draft, use AI to improve the work itself, and fix the system that keeps producing poor results. Read the Anti-Slop Manifesto.

A thousand-line pull request or a ten-page document can be cheap to generate. Reading it still takes attention. The manifesto calls it slop when the sender spends less effort producing something than they ask the recipient to spend understanding it. That imbalance is easy to create when a team is under pressure to produce more and sends a model’s first pass for someone else to make sense of.

The cost carries into the next task. A workaround left in the code, or a muddled explanation left in chat or the knowledge base, becomes material the next agent can read and copy. A tool inclined to add code may put a second workaround on top of the first. As those artifacts accumulate, people spend more attention deciphering them and have less appetite to push back.

09

Own the work before you pass it along

The manifesto asks teams to build tools that make human intent easier to express and the resulting work easier to understand. Before implementation, look at the existing code, resources, and prior art to understand the problem. The people who ship the work own its intent, its design choices, and its consequences.

That responsibility applies to a Slack message or email as much as to a pull request. If an agent wrote something you’re about to share, make its role clear, check that the result is good enough for the recipient, and fix any problems before sending it. If you receive a draft that still needs that work, ask the sender kindly to review it first. Horthy has been on both sides of that exchange.

10

Review where judgment can change the result

As models improve, Horthy says human review may move from much of the code to a plan, a design, or a result. Agent reviewers, linters, and verifiers can narrow what a person needs to inspect. A person still has to judge whether the work fits this problem and these users. Leave that judgment to the model, and you risk getting the same output anyone else could get. Which part a person should review depends on the stakes. 18:20

What shipped? Who uses it? How does it help them? Lines of code, merged pull requests, and agents running in parallel measure activity. A one-shot prototype earns its place if it answers a product question quickly. A change headed for a long-lived codebase deserves closer inspection when a workaround could make the system harder to maintain.

Teams are still learning how much review different changes need. As the tools improve, revisit which decisions a person should inspect before the work reaches the people who use it and the people who inherit it.

要点总结

  • Automating intake changes how fast work arrives. Pair it with checks the agent can run and act on so routine fixes happen before a person reviews the result.
  • A checkpoint benchmark asks whether today’s implementation leaves room for tomorrow’s requirement. The overall score and the code’s complexity, size, and interfaces answer different questions.
  • Spend human attention where it can change the outcome. That can mean scrutinizing a hard-to-reverse schema before implementation, checking a result before release, or fixing a draft before a coworker has to read it.

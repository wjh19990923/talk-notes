机密如何通过 AI 智能体泄露（以及如何阻止） —— Venice AI

一个私有模型只覆盖了智能体数据路径的一部分。Joshua Mo 梳理了日志、凭据和工具调用如何造成暴露——以及把推理与执行分开如何改变模型可能泄露的内容。

01

隐私始于一次泄露可能暴露什么

A single breach can cost a product its users’ trust. For an enterprise vendor, it might mean losing the customer that supplies most of its revenue. Joshua Mo, Venice AI’s lead developer relations engineer and previously lead maintainer of the Rust AI framework Rig, opens with this practical reason to care about privacy: sensitive data increases the damage an incident can do. Storing less of it reduces the blast radius.

Venice supplies the opening example. Mo describes an OpenAI-compatible platform hosting open-source models, a chat application, and a studio for video, audio, image generation and transcription. Its stated policy is to retain no prompts or conversations. That makes retention a product architecture decision from the start: what the service keeps determines what a later compromise could reveal.

02

不同的数据路径需要不同的保护

Venice’s privacy measures address several different places where data could remain or become visible. Mo describes these as distinct protections rather than a single property of the model:

- Conversation retention. Prompts and conversations are not saved on Venice’s side; conversation storage stays local. - Requests to closed providers. Venice anonymizes the user footprint when forwarding requests to providers such as OpenAI and Claude. The talk does not explain the transformation, so this claim should not be read as a guarantee that identifying information inside a prompt disappears. - Inference execution. Some models run in trusted execution environments, with evidence intended to let a user verify the protected inference process. - Stored generation results. Video-generation endpoints require polling for a result. Venice stores that result as an encrypted payload using split-key custody, intended to prevent access even if an attacker compromises a team account.

The polling example exposes a useful distinction. Avoiding stored conversations does not eliminate every reason a service might need storage: an asynchronous job still needs to make its result available later. Encryption and key custody address that separate requirement. The model, the request path and the stored output each create a different privacy question.

An agent adds still more machinery. A model is one component inside a process that retrieves information, invokes tools and returns results. Each surrounding component can introduce another route for data leakage. Choosing a private inference service therefore leaves an application builder with substantial work elsewhere in the system.

03

日志和密钥库集成可能把密钥复制到新的地方

Observability is an early trap because its purpose is to preserve information about what happened. Mo separates metrics—numbers such as counters and gauges—from traces, which describe spans of work over time, and logs, which contain messages. Those messages are valuable when debugging production failures. They can also quietly retain prompts, personal information and credentials. A model provider’s retention policy does not prevent application logging from creating its own sensitive records.

The next example follows a credential through an agent. A user request reaches the runtime. To complete the task, the runtime retrieves a secret from a vault such as 1Password or HashiCorp Vault, then sends that secret to the LLM reasoning layer. The reasoning layer makes an API request through a tool call, and an answer returns to the user. The critical transfer happens before the API call: the credential has become model input.

The diagram routes the agent runtime through a secret store and into the LLM reasoning layer before an external API call—the credential enters model reasoning here.

Mo warns that this could expose the credential to training-data use. That possibility depends on the receiving provider’s policies; sending a secret to a model does not by itself establish that it will be used for training. The architectural exposure is clearer: the model receives a credential even though the eventual API request is the operation that needs it. Later in the talk, that same placement becomes the starting point for tool-based exfiltration.

04

让标识符保持精简、分散保管，并让访问可撤销

Rate limiting illustrates how an application can retain less data without abandoning a function it needs. The service must recognize requests associated with a user so it can apply a limit. Mo proposes storing a hash representing the needed identifier instead of directly storing the user’s personal data. The rate limiter still has an identifier to work with, while its record contains less direct personal information. This is a data-minimization pattern; the talk does not establish that every hashed identifier is anonymous.

Split-key custody addresses a different failure: someone obtains access to encrypted storage or part of its key material. Mo describes two key halves, called a read half and a write half, with both required for decryption. The intended protection comes from making one compromised part insufficient to recover the data. This is a high-level description of Venice’s custody approach, without enough cryptographic detail to reproduce the scheme.

Revocable handles move the discussion from identifying data to granting access. A handle is an object through which a caller can reach a resource. In the database-pool example, possession of the handle permits access; without it, access is unavailable. Making that access revocable gives the application a way to withdraw permission. Mo connects the pattern to authorization systems using JSON web tokens or session keys, although the recording does not specify a revocation implementation.

Privacy-conscious prompts also belong in the development workflow, including coding harnesses such as Cursor and Claude Code. But the next example moves beyond prompt wording to the scope of the agent itself: how many tools it can use, and what sensitive material accompanies those tools.

05

需要一个工具，不该带来二十个工具的暴露面

Suppose an MCP server offers fifteen or twenty tools, but the task requires only one. That tool needs an API key. If the agent retrieves the key from a password vault and includes it in the model’s working material, a subsequent tool call can send it to a bad actor’s web server. The failure combines two kinds of access: the agent can see the secret, and it can call a destination that should never receive it. Narrowing tool scope reduces the opportunities available to the agent.

A classification layer in front of the agent adds a separate check for prompt injection. Mo gives several implementation options:

- LLM classification. Use a model-based layer to examine incoming material for injection attempts. - Semantic search. Use vector search through systems such as Qdrant or LanceDB as part of the screening layer. - An in-memory process. Keep the screening process in memory rather than requiring the named search systems.

These are proposed implementation choices. The recording does not specify classification thresholds, detection accuracy or how the application handles a flagged request.

Narrow scope also has a context benefit. Fewer tools mean less tool-related material competing for the model’s context window. Mo links this to avoiding performance degradation as the window fills. His advice to keep context nearly empty is best understood here as a push to remove unnecessary material; the talk provides no benchmark establishing an optimal context size. The useful connection is that limiting capabilities can reduce both exposure and irrelevant context.

06

让模型请求动作，让执行环节提供凭据

The central architectural correction changes where the vault connects. A user request first reaches the reasoning layer, which formulates inputs for the agent runtime. The password vault connects to that runtime rather than supplying credentials to the model. The runtime becomes an execution layer: model-generated requests enter it, and the credential is supplied where the action runs.

A browser login makes the difference concrete. The task requires a website login, so something must use the user’s credentials. In this design, execution handles those credentials while carrying out the login; the reasoning layer does not need the password in its context. External API calls follow the same pattern. Mo calls the execution layer deterministic, contrasting its programmed behavior with the model’s nondeterministic outputs. The separation makes credential handling more controllable, while permission checks still matter.

Where does the secret enter the revised system? The diagram separates the model’s action inputs from the vault’s credential path. They meet at execution. That topology is the consequential change: the model can help choose an action without receiving the secret used to carry it out.

Action inputs and credentials meet at execution The reasoning layer supplies action inputs. The vault supplies secrets to the runtime that performs the action. - User request — Ask the agent to perform a task. - Reasoning layer — Formulate nondeterministic inputs for the runtime. - Password vault — Connect credential access to the runtime. - Execution layer — Use programmed execution to handle the requested action and its credentials. - Website login or API call — Use the credential where the external operation runs. - User request → Reasoning layer (Task request) - Reasoning layer → Execution layer (Action inputs) - Password vault → Execution layer (Credential access) - Execution layer → Website login or API call (Perform authenticated operation)

07

沙箱仍然可能把数据发出去

Sandboxes and virtual machines strengthen isolation. Mo names Firecracker and EC2 deployments inside a VPC as examples. But isolation does not settle the question of outbound access: an agent with internet access can still leak data through an external API call. Monitoring permissions remains essential because an allowed network operation can carry sensitive content out of an otherwise isolated environment.

This motivates Mo’s recommendation to build and own the agent runtime or coding harness. Controlling the runtime lets a team add its own execution steps, observability and tools, and decide how reasoning connects to execution. The recommendation is about having a place to enforce those decisions: a sandbox alone cannot choose appropriate permissions or prevent sensitive values from entering logs.

08

证明推理可信，再直面工具调用问题

Confidential compute moves privacy protection down to the hardware level. A trusted execution environment protects the inference process. In Venice’s described flow, a request produces a response and an attestation, which the user can check with an attestation verifier. The attestation supplies something inspectable about the protected reasoning environment, rather than requiring the user to rely only on a service’s privacy claim.

That protection has a defined scope: inference at the reasoning layer. Confidential tool calls remain an open engineering problem in the talk. Mo describes TEEs as useful for tool calls and says Venice also offers end-to-end encryption, then identifies the unresolved API challenge: returning entirely encrypted tool calls while preserving an ergonomic experience for developers. Protecting model execution does not automatically solve how external actions and their data move through the rest of an agent.

One proposed direction is for providers to own the compute layer where tool calls run. That would extend their role from inference into tool execution. Mo leaves the proposal undeveloped and closes with confidential tool calls still unfinished. The ending preserves the distinction the architecture requires: verifiable private reasoning is one achievement; carrying that protection through useful external actions requires further design.

要点总结

  • 减少保留的敏感数据，就减少了一次泄露可能暴露的东西；即使模型服务商不保留任何对话，应用日志也可能重新造成暴露。
  • 把凭据保管库与执行连接起来，让模型可以请求一个动作，而不必拿到执行它所需的密钥。
  • 收窄工具范围与筛查提示词注入针对的是不同的风险。可以联网的沙箱仍需要权限监控。
  • 经过证明的机密推理保护了推理环境；符合人体工学的、全程加密的工具调用在这里展示的设计中仍未解决。

可靠企业智能体的三种原料

当企业智能体能可预测地完成有价值的工作、让错误可以挽回，并让人参与到关键决策中时，它们才变得有用。

熟悉 LLM 工具调用、检索增强生成（RAG）以及 Git 分支和 pull request，有助于理解示例。

01

每个任务一个智能体——外加一个监督的人

设想一家企业里满是各司其职的智能体，人以经理和主管的身份协调它们的工作，要做到这一步需要什么条件？在公司内部开发智能体的开发者要面对这个问题，向企业销售智能体的厂商同样要面对。把工作交给智能体，这个愿景再诱人，最终也得变成组织愿意真正采用的东西。

为什么有的智能体能在企业里落地，有的却不行？Harrison Chase 说，他的很多想法来自和 Assaf 的一次交流。他介绍 Assaf 是 Monday 的 AI 负责人，也是 GPT Researcher 的作者。Chase 的出发点不是先选架构，而是先算清楚用一个智能体的经济账。

02

生产门槛

智能体成功时的价值越高，就越有吸引力。成功概率越高，也越有吸引力。第三个因素方向相反：失败时的代价越高，企业越不愿意采用。这三者是彼此独立的杠杆。任务价值高、犯错又便宜，表现不完美也说得过去；一旦犯错代价高昂，能力再强的智能体也很难获批。

Chase 把三者的关系写成一个期望值门槛。设 p 为成功概率，V 为成功结果的价值，L 为失败造成的损失，C 为运行智能体的成本：

``math \begin{aligned} \text{Expected net value} &= pV - (1-p)L - C \\ \text{Production threshold:}\quad pV - (1-p)L &> C \end{aligned} ``

这套推理不只适用于企业。实际要回答的问题是：靠产品设计和工程手段，能把这几项推动多少，直到部署变得划算。

03

提升工作的价值

最直接的杠杆是选对任务。Chase 举的例子有法律领域的 Harvey，以及金融领域的研究、投资研究和摘要。人们本来就愿意花大价钱请律师、买专业研究。有了现成的付费意愿，成功的结果值多少钱就更容易看清。

不过，提高价值不一定要换行业，也可以让智能体每次交互多干一些活。Chase 说，早期的 RAG 和问答界面追求五秒内给出答案；深度研究（deep research）则会花很长时间钻研一个问题。在编程领域，Cursor 的行内自动补全和聊天属于短交互，后台编程智能体则承接更大块的委托工作。Chase 粗略数了数，前三周里就冒出了七个这样的例子，智能体一次能连续跑上好几个小时。

讲编程的那张幻灯片用两个标签把对比摆得很直白：“Cursor：30 秒”和“Claude Code：2 小时”。两者体现的是工作时长的量级差别，并不是控制变量后的速度对比。产品上的机会在于让智能体在后台自主完成更有分量的工作。要做到这一点，得改 UI 和交互模式，光把快速响应聊天框背后的模型换掉是不够的。

04

把必需的行为放进控制流

要提高成功概率，先得正视原型和生产系统之间的差距。跑通一次就能做出漂亮的演示，但证明不了可靠性。有些应用能容忍探索式的行为，哪怕每一步都难以预测。企业往往需要更严格的控制：某一步必须跟在另一步之后，不管模型自己会怎么选。

Chase 举了个示意性的例子：用提示词要求智能体在 B 之后执行 A，它大约 90% 的时候会照这个顺序来。把顺序写进确定性的控制流，顺序就成了程序本身的属性。这不能保证哪一步的结果是对的，只是把一项决定从模型手里拿走。凡是要求可预测的地方，都可以让智能体多一些确定性的部分。

Anthropic 的 Building effective agents 把工作流和智能体区分开来。Chase 更喜欢的说法是工作流与智能体并存：工具调用循环可以和固定流程同时存在。如果智能体 A 总是把结果交给智能体 B，那么即便两者内部各自做决定，外层结构依然是工作流。用 TypeScript 写，这条边界可以小到这样：

```typescript type Agent<Input, Output> = (input: Input) => Promise<Output>;

async function runInOrder<Input, Intermediate, Output>( input: Input, agentA: Agent<Input, Intermediate>, agentB: Agent<Intermediate, Output>, ): Promise<Output> { const resultA = await agentA(input); return agentB(resultA); } ```

这里 agentB 拿到的是 agentA 跑完的结果；A 一旦抛出异常，B 就不会被调用。两个智能体内部可以保持灵活，交接环节则始终明确。

Chase 举的框架例子是 LangGraph，它正是围绕这条光谱设计的。真正该问的是：应用在哪些地方需要确定性的结构，又在哪些地方适合交给模型来主导执行。不同应用在这条光谱上的位置各不相同。

05

让表现对审查者清晰可读

智能体要获批，实际可靠性只是一方面。相关方可能还对它的行为心里没底。把智能体做得更好，和让别人放心，相关但不是一回事。可观测性和评测两头都能帮上忙：既支撑工程工作，也让决定能否部署的人看懂它的表现。

Chase 介绍说，LangSmith 最初是为了让开发者检查自己的智能体而做的，后来也成了和外部相关方沟通的工具。逐步的 trace 能看出一次运行在哪里成功、在哪里失败，哪些模式反复出现。评审者能看到多次 LLM 调用和串起它们的各个步骤，不必把智能体想象成一个不透明、一次出答案的黑箱。评测和基准测试则进一步提供系统表现的证据。

Chase 讲了一位客户的经历：对方先用 LangSmith 搭建智能体，后来把同样的视图带进了上线评审会。评审组看到了系统内部到底发生了什么，觉得风险没那么大了，会议提前结束。这个故事说明，开发者工具还有第二类受众：负责批准它上线的人。

06

降低出错的代价

评审者还担心后果：智能体可能损害品牌，或者把东西白白送出去。Chase 认为，这类担忧往往左右着是否采用的决定。有两种产品机制分别应对风险的不同部分：让改动可以撤销，以及在关键操作前设一道人工审批关口。

代码天然适合说明可撤销性。Chase 在讲生成的 diff 和 pull request 时展示了一张 Replit Agent 的截图，然后解释：回到之前的 commit 就能撤销代码改动。按他的回忆，Replit 早期会把每次文件改动都存成一个新 commit。如今，Replit 的 checkpoint 文档 写的是在里程碑和其他关键节点创建 checkpoint，而不是每次编辑都存。不变的机制是总有一个能恢复的早期状态；但这不代表所有外部影响都能回滚。

审批和撤销是两道不同的保护。 开 pull request 而不是直接合并进 main，人就能在改动进入主分支前先审一遍。撤销提供事后的恢复手段，审批提供事前叫停的机会。两者结合，改变了智能体出错的后果，也改变了企业评估这些后果的方式。

07

先澄清意图，再产出可审查的东西

深度研究说明，人的参与不只能控制风险，还能提升价值。开始调研之前，系统会先追问几个问题，弄清用户真正想要什么。这一来一回，让最终报告更有可能切中正题。在另一端，产出是一份供用户阅读、再决定怎么做的报告，而不是自动发布的博客文章或发给客户的邮件。研究交给了智能体，发不发布仍由人另行决定。

Chase 说 Claude Code 也是类似的模式：先通过澄清式提问确定意图，再用单独的分支加 pull request 保留审查关口。这套流程不要求每改一个文件就 commit 一次，要求的是：在有人决定接受之前，提议的工作一直和主分支隔开。

08

把有用的工作扩展到聊天框之外

一旦智能体的期望值为正，下一个机会就是把这份有用的工作成规模地重复下去。环境式智能体（ambient agent）在后台运行，由事件触发，不需要人每次手动发起。Chase 拿两种情形作对比：一边是管理一两个聊天框，一边是可能上百个智能体在后台同时干活。交互从一对一变成了一对多。他说的“无限并发”指的是这种交互模式，不是实测的基础设施容量。

对延迟的预期也变了。聊天时，有人在等回复。事件触发的后台工作就没那么急着立刻给答案。这为更长的推理和工具调用序列留出了空间：改一行代码，可以变成改整个文件，甚至新建一个代码仓库。多出来的时间有用，是因为能干更多的活，而不只是答得更慢。

09

后台执行仍然需要监督

环境式不等于完全自主。 智能体在后台运行，人依然需要一个界面来监督它的工作。不然，同样的担忧又会回来：智能体自行其是，却没人理解或掌控后果。

Chase 介绍了几种干预模式：

- 批准或拒绝： 指定的工具必须先获得明确许可才能运行。 - 编辑工具调用： 在 UI 里直接修正智能体打算执行的操作，不必把整次运行推倒重来。 - 回答问题： 智能体卡住时，让它请求澄清或补充缺失的信息。 - 回到之前的步骤： 运行结束后，退回到先前某个节点，换一种指导继续往下跑。Chase 称之为“时间旅行”，也叫 human on the loop；他举的例子是：一百步里发现第十步出了错，就回到第十步重来。

这些控制手段把人的判断放在特定关口上，不需要人去指挥每一个内部操作。

在聊天和环境式智能体之间，还有一个中间阶段。按 Chase 更严格的定义，深度研究和 Claude Code 都不算环境式，因为它们仍然要由人发起。对于由人发起请求、随后在后台持续运行的工作，他喜欢用 Factory 的叫法：异步编程智能体（async coding agent）。开头的交互用来校准任务，之后异步执行，过程中随时可以求助。

于是，Chase 在“聊天 vs. 环境式”的二分法中间，加了一个概念上的过渡栏：

| 交互方式 | 由什么启动 | 工作模式 | |---|---|---| | 聊天 | 人发来的消息 | 即时往来 | | 同步转异步 | 人的请求与校准 | 后台执行 | | 环境式 | 外部事件 | 后台执行，有选择地监督 |

关键区别在于：工作由谁、或由什么启动。光是异步执行，并不能让智能体变成环境式的。

10

一个存放待处理智能体动作的收件箱

Agent Inbox 给这种监督模式提供了一个具体的界面。它把需要人处理的操作集中展示出来，让用户批准、拒绝或留下反馈。这几个说法描述的是交互；看实际代码，它的响应类型叫 accept、edit、response 和 ignore。待处理的操作是智能体想做的事，并不表示它已经做了。

邮件是很自然的应用场景。一封新邮件就是一个事件，用户不用打开聊天就能触发工作。大量来信可以生成许多并发任务；而发出去的邮件或日历邀请，可以按用户的放心程度决定要不要先审批。事件驱动的接收和受控的对外操作，完全可以同时存在。

Chase 自己做了一个邮件智能体，在内部用它检验这些模式。演讲最后，他在屏幕上放出一个二维码，分享这个智能体的开源实现。这个例子把整套架构串了起来：事件启动工作，智能体准备操作，收件箱则是人做决定的地方。

11

编程智能体之外也适用的经验

问答环节，一位听众问：编程智能体之所以容易拿到融资，是不是因为它的工作可衡量、可撤销？Chase 回答时把代码的两个优势拆开来讲，但没有去坐实问题里隐含的前提，即只有编程智能体才拿得到融资。

第一个优势是可验证性。代码可以运行，可以检查能否编译，当然，能编译不等于正确。数学同样能给出可检验的结果。文章质量就模糊得多：判断一篇文章“对不对”，本身就不是一个界定清晰的任务。Chase 把这种差异和训练联系起来：输出可验证，就更容易自举生成训练数据，编程模型因此更强，编程智能体也跟着更强。

第二个优势是一种更容易迁移到其他领域的产品模式：初稿。代码天然支持 commit、草稿和预览，法律文书和文章也有大家熟悉的“起草—审阅”流程。智能体可以先完成一大块工作，再把成品交给人判断。

如果每一个细小步骤都要人插手，委托的价值就被消磨殆尽。设计上的难题在于：既让智能体完成大量工作，又让人在关键节点参与进来。初稿恰好提供了这样一个边界：已完成的工作足够有用，接受或使用之前又有一个明确的决定点。在法律、写作和代码领域，这种模式比可验证性更容易推广，尽管后者能帮助训练编程模型。

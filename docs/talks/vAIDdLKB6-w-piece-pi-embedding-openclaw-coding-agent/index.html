一块 PI：把 OpenClaw 编程智能体嵌入你的产品

Pi 的智能体循环、执行运行时、扩展和会话，为那些用户可能永远看不到编程智能体界面的产品提供了基础构件。

熟悉 TypeScript、命令行工具和 LLM 工具调用，有助于理解示例。

01

小工具如何变成产品能力

OpenClaw 看起来像是学会了一项新本事，这时它内部到底发生了什么？Matthias Luebken 正是带着这个问题找到了 Pi。一次 OpenClaw 线下聚会后，他想弄清这种行为背后的机制，而不是去追那些更炫的玩法。他在 TAVON.ai 为企业构建智能体，想要的是自己看得懂、能复用的组件。他提供的配套示例也带着这种实验精神：Pi 的底座足够精简，可以把智能体拆开来看。至于怎样用好它，他的理解也还在变。

第一个有用的参照是 Unix 的工具组合。Luebken 先放出一张幻灯片，引出“程序只做好一件事”的原则，并注明出自 Ken Thompson。随后他转向 Claude 桌面端的 Cowork。Cowork 把编程智能体包装起来，去做那些看上去不像软件开发的工作。比如在财务流程里，用户要处理 Excel 表格。按 Luebken 的描述，Cowork 的表格技能用的是 pandas、openpyxl 和 LibreOffice 这些工具，并不直接操作 Excel。产品能力来自把一批小工具组合起来，再放到面向任务的界面后面。

Luebken 说 Cowork 反响不错，但这里更值得关注的是架构上的机会：让系统便于智能体使用。他和 Ivan 聊过一次，这个正在成形的模式因此更清晰了：智能体本来就擅长处理哪些形式，就用这些形式开放能力。多余的复杂度只会添乱。这套思路还没有现成的打法。要找到有用的产品模式，就得先做出好上手的工具，再拿它们的组合去做实验。

02

从核心智能体循环开始

做这类探索，Pi 是一个开源、精简的起点。Luebken 提到 Pi 的作者 Mario Zechner 加入了 Earendil，接着给出一个实用的上手办法：打开 Pi，让它把你想要的功能做出来。扩展可以下载，也可以自己写，还可以让编程智能体帮你写。这里的目标不是改进在编程助手里写代码的日常体验，而是看看这套机制还能驱动些什么。

先从编程智能体往下一层看。核心智能体拿到一个目标和一些上下文（通常是 AGENTS.md 里的指令），然后在循环里调用工具：

1. 把目标和相关上下文交给模型。 2. 让模型请求一次工具调用。 3. 执行工具，把结果返回给模型。 4. 带着新信息继续，直到智能体能给出回复。

一个应用独有的行为，来自挂在这个循环上的上下文、工具和控制逻辑。

Pi 用一个 TypeScript 智能体类开放这套循环。这个类接收提示词，并提供事件系统。Luebken 的第一个演示是终端里的 CRM 线索评估工具，据他介绍，整个应用只有三个 TypeScript 文件。请求很简单：列出所有线索并打分。从 trace 里能看到助手调用工具、拿到结果，最后返回输出。系统提示词写明了有哪些工具、什么时候该用。这是一个学习用的小原型，很快就搭好了，目的就是让循环看得见。

03

在工具执行之前控制边界

应用也可以在工具边界上插手。更新联系人的工具运行之前，hook 可以先检查这次操作该不该放行。Luebken 认为，这个拦截点可以用来做鉴权和基于角色的访问控制。关键是分清两件事：智能体请求修改数据，和应用允许修改数据。智能体提出要更新联系人，不等于这次更新一定会执行。

在应用层写一个 TypeScript 包装函数，就能把这个先后顺序写明白。联系人更新会一直挂起，等确认回调放行之后，写入函数才能运行：

```typescript type ContactUpdate = { contactId: string; email: string; };

type UpdateResult = | { status: "blocked" } | { status: "updated" };

async function updateContactWithConfirmation( proposed: Readonly<ContactUpdate>, confirm: (update: Readonly<ContactUpdate>) => Promise<boolean>, write: (update: Readonly<ContactUpdate>) => Promise<void>, ): Promise<UpdateResult> { const pending = Object.freeze({ ...proposed });

if (!(await confirm(pending))) { return { status: "blocked" }; }

await write(pending); return { status: "updated" }; } ```

工具调用前的闸门，强制执行的就是这个顺序。确认只是应用的一种控制手段。要做完整的鉴权，还得决定谁有权执行这项操作。

执行的另一面交给事件：告诉界面发生了什么。终端输出流订阅了智能体的活动，出现一个勾，就表示一次工具调用已经完成并返回了结果。hook 决定执行能否继续，事件订阅则让执行的进度和结果看得见。

04

加上 shell 和运行时

编程智能体保留了同样的工具循环，但多了运行时和 shell，通常是 Bash。这样它在解决任务的过程中就能运行程序。目标、上下文、工具请求和返回结果都还在，只是执行环境变大了，这些请求能做的事也多了。

Luebken 讲了 Peter 分享过的一个小故事来说明区别：OpenClaw 收到了一条语音消息。按 Peter 的说法，OpenClaw 起初并不会处理语音消息。它用手头现有的工具拼出了一套处理办法，其中就有本机上的 FFmpeg。到这次演讲时，是否已经有了专门的语音插件，Luebken 没有说清。他强调的机制是工具组合：从外面看像是“学会了”，其实可能只是在循环里多执行了一个工具。

05

把 CRM 变成一个交互式扩展

下一个 CRM 示例离开核心智能体类，转到 Pi 编程智能体的扩展 API。这个演示最依赖两项能力：会话事件和 UI 交互。一个 TypeScript 扩展注册了 /pipeline 命令，加载 CRM 上下文，再通过扩展的 UI 上下文给出选项。这样，工作流可以直接让用户做选择，不必全靠自由发挥的提示词和后端工具调用。

演示是在下载下来的 Pi 编程智能体里跑的。调用新命令后，界面上会弹出下拉菜单等选择控件。扩展能表达的东西也就变了：它可以把智能体会话和用户的明确决定结合起来。Luebken 再次建议让编程智能体来生成扩展，但也指出，Pi 的扩展框架主要面向编程智能体的场景。想把它改造成适用于其他应用的框架，还得多下功夫。

下一个实验是 Web 界面。Luebken 展示了他让 Pi 做的一个 Web UI 概念，借助扩展机制沿用了同样的命令和选择交互。他也提到，现有的支持还有局限，团队正在重构，好让集成更干净。这应该看作一次把交互搬出终端的探索，并不是说演示里的 Web 界面已经是 Pi 正式发布、人人可用的功能。

06

把执行引擎与编排分开

OpenClaw 把场景从“一个会话里的一个编程智能体”扩展到多个渠道、多个线程和多个智能体。在 Luebken 描述的架构里，OpenClaw 使用 Pi 的核心包，调用一个嵌入函数来创建智能体会话，并以流的形式把信息传回。所以会话支持在终端之外也派得上用场：外层应用掌控交互，同时复用这套执行机制。

这些包把职责分成了几层，每层都能单独复用：

| 组件 | 职责 | |---|---| | 编程智能体 | 面向编程的智能体功能 | | 智能体核心 | 底层的智能体循环 | | pi-ai | 统一的 LLM 抽象层 | | 终端 UI | 终端交互组件 |

OpenClaw 还加了自己的插件机制，因为它的需求不止于一个编程会话：多渠道路由、模型提供商编排、子智能体和网关支持。录像里展示的是 Pi 集成早期的样子。当前的 OpenClaw 运行时文档描述的则是 OpenClaw 自己的运行时和 @openclaw/agent-core。不要把这些现行的内部实现套进本文的讲解。

07

围绕销售流程构建

这个客户应用从销售流程切入：客户发邮件，请公司为所售的系统或零部件出报价方案。团队没有开放编程智能体的界面，而是从收到的邮件入手。系统监控一个收件箱，把邮件送进网关，网关再把邮件路由给负责该客户的智能体。

客户智能体把不同层级的指令组合在一起：

- 通用框架： AGENTS.md 这类指令文件规定智能体的角色、系统怎么用，以及怎么处理输入和输出。 - 客户上下文： 每个客户有一份 Markdown 文档，写明这个客户专属的权限、优惠和折扣。 - 工单会话： 每个工单新建或复用一个会话，邮件来回往复时，之前聊过的内容都会保留下来。

客户决定用哪份上下文，工单决定接着哪段对话。这样应用既能保持连续性，用户也不用自己管理智能体会话。

08

在执行边界内暴露业务工具

邮件到了对应的客户智能体和工单会话之后，智能体靠工具接入 CRM 和 ERP。这两个系统提供它需要的业务信息，包括联系方式。团队把这些能力做成了 CLI，因为 Luebken 发现智能体用 CLI 很顺手。这正是开头那条设计原则的直接应用：用智能体本来就会用的接口，开放相关的业务操作。

Luebken 说团队用的是自己的沙箱，生成草稿前会先把数据保护好，不过他也承认沙箱这块还在完善。前面的确认 hook 和这里的执行边界作用不同。闸门能拦下某一次工具操作，但它本身管不住文件系统、进程、网络或凭据的访问。Pi 当前的文档明确说，这些限制不归智能体管，需要在外部做隔离。

团队也在研究 NVIDIA OpenShell 和它的策略机制，看能否用来保护智能体的执行。这只是一个备选方案，Luebken 并没有说已经把它部署到客户系统里。

09

让用户留在邮件里

最后一个演示从收件箱出发，由内向外展示整个应用。仪表盘上列出收到的邮件。LLM 判断每封邮件是否相关，忽略掉大部分，挑出示例里这封来处理。这封邮件归到一个工单下，工单背后是一个智能体会话。系统接着把生成回复草稿要做的事都做完。用户始终待在熟悉的“收件箱加草稿”工作流里就行。

仪表盘主要是给管理员看的。草稿背后，会话 trace 记录了助手处理请求的过程。在这个德语示例里，助手查找商品或条目，调用工具，拿到结果，然后继续循环。到了用户那里，这一切归结成一件简单得多的事：收到的邮件归入某个工单，一份可以编辑的草稿已经备好。这套流程不会自动发送邮件。

这就是 Luebken 押注的产品形态：把编程智能体当作可复用的软件积木，嵌在适合具体工作的界面后面。他最后邀请大家去试试 Pi，因为它足够精简，零件很容易拆开再重新拼装。销售助手正好走完了这条路：从终端里看得见的工具循环出发，最终变成一个用户只管处理邮件、智能体机制在底下默默运转的应用。

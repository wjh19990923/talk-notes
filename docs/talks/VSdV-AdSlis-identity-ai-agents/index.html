选择令牌交换流程

幻灯片原文
For long-lived access, the slide pairs refresh-token exchange with a JWE. For SPAs and API servers exchanging short-lived tokens, it pairs access-token exchange with a signed JWT.

[12:32](https://www.youtube.com/watch?v=VSdV-AdSlis&t=752s) [Slide comparing refresh-token and access-token exchange flows, with architecture diagrams.](https://assets.ai.engineer/sites/aiecode2025/sha256/2574649f20f5b0abc0a4868a3362c654d376aaa193d402bfd247e43af9536452.webp)

Picking the right exchange right flow.

subject_token_type: urn:ietf:params:oauth:token-type:refresh_token
- Often ideal for regular web applications, native apps, and embedded agents which require long-lived access.
- A JWE is used as the subject_token when requesting the third-party AT.

subject_token_type: urn:ietf:params:oauth:token-type:access_token
- Often ideal for SPAs with backend APIs, MCP API servers, and other OAuth 2.0 resource servers (RS) which need to exchange tokens to access external APIs.
- A signed JWT is used as the subject_token when requesting the third-party AT.
- Custom API Clients, which are linked to an API (RS), can exchange a SPA’s access token or an API’s access token for a third-party access token.
- Ideal for short-lived access & one time transactions

Key Security Concepts
• Leveraging Short-lived tokens - create short-lived, fine-grained access tokens ensuring a minimal blast radius if a token is ever compromised.
• Federated Login with OIDC - Enable users to login to one application using credentials from a different, external identity provider using OpenID Connect.

• Client Initiated Backchannel Authentication - Allow clients to initiate authentication requests on behalf of users, and receive tokens asynchronously once the user approves on a separate device.

Updating our solution for Asynchronous Authorization

1. Let's first add additional helper function (getTokenByBackchannelAuth) to lib/auth0.ts for asynchronously receiving the authorization token using our existing Agent client. Append this function to the existing file:

Ts
import { AuthorizationDetails } from "@auth0/nextjs-auth0/types";

export async function getTokenByBackchannelAuth({
  bindingMessage,
  authorizationDetails,
}: {
  bindingMessage: string;
  authorizationDetails?: AuthorizationDetails[];
}) {
  const session = await auth0.getSession();
  if (!session) {
    return undefined;
  }

try {
    const token = await auth0.getTokenByBackchannelAuth({
      bindingMessage,
      authorizationDetails,
      loginHint: {
        sub: session.user.sub,
      },
    });
    if (!token.tokenSet) {
      throw new Error("The user didn't authorize the request");
    }
    return token.tokenSet.accessToken;
  } catch (error) {
    console.error("Failed to get token by backchannel auth:", error);
    throw error;
  }
}

01

是什么授权一个智能体去行动？

How do you authorize an AI agent—and the MCP servers it calls—to act for a user? A login is only the beginning. The workshop introduces two mechanisms for the next steps: Token Vault for delegated upstream API access, and Async Auth for requesting human approval. Patrick describes several capabilities as newly generally available during the workshop week. The material, adapted from work prepared by architect Abhishek, also places fine-grained authorization in the broader architecture, while leaving the open-source FGA project and its deeper access-control model for another talk.

02

身份必须在聊天会话之外延续

Okta and Auth0’s ambition to let people safely use technology predates agents, but the threats change with the technology. Carlos uses the OWASP LLM Top 10 as the threat context, then broadens the application model: interactive chatbots and code editors are followed by task runners, autonomous agents, and eventually agents communicating with other agents. Once work continues without a person watching the chat window, identity and permission cannot depend on a fresh conversational instruction at every step.

Four requirements follow:

- Know the user. Establish whose identity and permissions apply to the operation. - Call APIs on the user’s behalf. Give the agent a controlled way to consume external services. - Request confirmation. Let the agent reach the person when an operation needs supervision. - Constrain resource access. Limit access to the intended resources, collections, or documents.

An employee also represents an organization, so company policy must govern the delegation alongside the employee’s choices. An audience question makes the identity boundary explicit: in this scenario, the subject is a human—perhaps an employee, owner, or administrator. The workshop covers both who may use an agent and what that agent may access. Those are separate authorization decisions.

03

两种机制：请求批准与获取上游凭据

Async Auth starts with the agent. A long-running process reaches a purchase or another operation that the application considers risky, then initiates an authorization request. Its foundation is Client-Initiated Backchannel Authentication, or CIBA, an OpenID Connect specification that separates the initiating client from the user’s authentication interaction. In the workshop’s transaction-approval flow, the SDK sends structured details to the user; approval returns an access token carrying the approved details. CIBA provides the backchannel, while Auth0’s combination with rich authorization details supplies the transaction-specific information.

Token Vault addresses a different problem: an agent needs credentials for an upstream service, such as Slack or Facebook, without managing that service’s token lifecycle itself. Auth0 persists upstream refresh tokens and granted scopes, manages token lifetimes, and exchanges an appropriate user token for an upstream access token. The right exchange depends on where the agent runs.

| Application shape | Exchange approach described | | --- | --- | | SPA or agent behind an external API | Short-lived access token | | Embedded Next.js agent or suitable native app | Refresh-token flow | | MCP server or asynchronous component | Custom API client for upstream access |

07

上游服务定义了一个 scope 的含义

The MCP server is modeled as an API with permissions for reading trades and portfolios, and those scopes appear in tool metadata. An audience member asks what makes a portfolio permission mean a stock portfolio rather than a project-management portfolio. The answer is the upstream service’s contract. A service requires particular scopes and rejects requests that lack them, whether the caller is an agent or a conventional REST client. The agent implementer must know both the request shape and the authorization requirements.

The connection configuration requests the upstream scopes. Those permissions appear in the user’s consent prompt, and Token Vault handles the exchange between the local and upstream contexts. The demonstration uses matching names for simplicity, but local and upstream scope names need not match. Nothing in this process requires the model to infer permission semantics from the word portfolio.

Scopes describe API access. Roles and personas describe another dimension of policy; Patrick points to role-based controls and FGA for restrictions around tools or pages. The connection mechanism itself already existed in Auth0—the new piece here is using a connection for Token Vault.

An audience question about discovering scopes leads into the MCP implementation. The server exposes a well-known protected-resource metadata endpoint that advertises supported scopes and authorization information. Middleware verifies token signatures and claims, then checks the permissions required by the protected handlers. This is signature verification and claim validation, rather than encryption of the JWT payload. Patrick describes the dynamic client registration feature as entering early access that week.

For calls onward to the trading API, the MCP server receives a linked custom API client, constructed with its own client ID and secret. The implementation reuses the stock and portfolio tools, registers them on the MCP server, and invokes the authorization middleware when constructing the transport endpoint.

The workshop implements both ends to make the entire path visible. An application could instead consume an existing upstream MCP server and implement only its client-side authorization.

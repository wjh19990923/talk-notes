用知识图谱为企业生成式 AI 锚定方向

一个生物制药搜索应用把文档检索、组织激励和图关系，与把生成式 AI 推向生产的实际工作联系起来。

对语言模型和文档搜索有基本了解会有帮助；文中会介绍检索增强生成和基于图的上下文。

01

当一位高管想让生成式 AI 上生产

高管看到生成式 AI 轻松搞定一件私事，就以为企业级应用也能照样顺手做出来——这时会发生什么？Stephen Chin 开场就谈热情和交付之间的落差。他引用了 Gartner 的预测：到 2025 年底，至少 30% 的生成式 AI 项目会在概念验证之后被放弃。这是预测，不是实测结果。他在现场做了一次非正式调查，让交付难题变得具体可感：有些听众承认手上的项目失败了，更多人的项目还没进入生产环境。

难点在于把这股热情变成技术上做得到的目标，还要让组织能理解、愿意支持。Chin 夸张地描绘了这样一位高管：孩子在学校用 GenAI 写作业，于是他指望两个月内就有业务方案上线。配图的漫画也是同样的跳跃，从一首写狗的诗一步跨到业务转型。Jonathan Lowe 则从落地实施的角度补充：在生命科学领域做应用，领导层、组织壁垒和技术限制都得同时应付。

02

从实验台上的知识到工厂的生产

Lowe 自称是那个持怀疑态度的实施者。等他讲清楚在企业里上线 AI 意味着什么，同事可能就把他当成专门泼冷水的人。他的具体用例是生物制药里的技术转移：把药物研发从实验台上的烧杯推进到工业化生产。他描绘的终点是日产百万剂的工厂。这条路可能要走好几年，因为设计工厂和设备的人得翻遍几十万份科学文献、笔记和测试结果。要把生产所需的知识转移过去，搜索是其中一环。

文档只是知识库的一部分。资深员工身上还有隐性知识，他们一退休，这些知识就可能随之流失。Lowe 引用了一项未具名的研究：2019 年制造业工人的平均任职年限约为二十年，到他讲这段经历时只剩三年。一份与之吻合的 PMMI 报道把三年这个数字标为 2023 年；统计的是哪类人群、怎么算出来的，这里无从确认。真正的运营隐患是经验流失：新员工既要能查到前人写下来的东西，也要能拿到资深员工心里有数、却从没记录下来的东西。

03

用图来了解一个检索单元应该是什么

Lowe 介绍了一个用图来表示的语料库，规模达数百万份文档。他随即强调了一个关键区别：团队并不一定把整份文档原样放进图里，放进去的是分块（chunk），同时保留了结构——文档、块、段落、行。幻灯片上的层级里还有“页”，旁边是药品和病症节点。这样一来，检索到的片段仍然和它所属的完整文档结构连在一起。

这种结构撑起了一个改进闭环。团队先做相似度搜索，看哪些分块返回的正是用户真正想要的内容，再据此改进分块的存储和管理方式。这些观察又反过来决定后续文档怎么分块。分块方式要从检索表现中学出来，而不是导入数据时一次定死的配置。 有了图，团队就能在不同层级的文档结构上做这种探究。

04

一个有用的应用仍然必须赢得采用

这就给项目找到了业务目标：让技术转移所需的知识更容易找回来，有望让救命的药更早送到患者手中。Chin 说，在他引用的 Gartner 研究里，最大的失败原因是缺少一个真实、能变现的用例。这个排序是他自己的说法；那份预测列出了好几个导致项目被放弃的因素，业务价值不清只是其中之一。至于更快送药，这是推动这个应用的理由，不是实测的临床结果。

用例再好，内部决策也不会就此拍板。团队可能更看好另一篇论文、另一个平台或框架，而不是这里提出的 GraphRAG 方案。他们也可能质疑经济账。GenAI 可能比传统计算更贵，架构没设计好时尤其如此；替换现有系统还要调研、投入、重新开发。一个系统即便不太好用，只要替换成本更高，就很难换掉。Chin 围绕这个问题引出 Lowe 在 Pfizer 的经历：怎么说服组织，这次改进值得花这笔钱？

Lowe 把自己当成大公司里的创业者来应对这个问题。他说现在所在的组织有十万多人，此前还在 IBM 和 Deloitte 干过。在他幻灯片的层级图里，提出想法的人是个拿着灯泡的小红人，身边是数据科学家、开发者和 SRE 组成的团队。Chin 建议直接去找 CEO。Lowe 的直觉却是先从会用这个应用的人入手。

用户会用很实际的标准来检验：

- 少干苦活： 把他们不想干的无聊活拿掉。 - 结果准确： 省了力气，答案却是错的，也没用。 - 响应迅速： 按下按钮后，不该等上一杯咖啡的工夫才出结果。

Lowe 认为，这些要求越来越容易满足。更难的是让组织里的其他人支持这个工具。

05

把工具翻译成受众的目标

在大公司里隔着好几级的人，很难约到 CEO——就算偶然碰上，也未必有用。Lowe 想起电影 Dirty Dancing（《辣身舞》）里的一幕：Baby 初见 Johnny 时手足无措，脱口而出“我搬了个西瓜”。他自己在总部电梯里也上演过类似的一幕。CEO 主动打破沉默，说刚度假回来，又问 Lowe 在忙什么。电梯门开了，CEO 往外走，Lowe 只来得及挤出一句：“我在做 LLM 相关的工作。”一个技术名词，几乎说明不了这位高管想达成什么。

高管的优先事项往往始于一套宏观叙事：行业领先、竞争地位，其中一部分出自咨询顾问之手。Lowe 举了一个使命蓝图的例子：每年改变十亿人的生活。这是愿景，不是成果。好的提案应该把搜索应用和这个使命挂上钩，而不是只宣布“我们在用 LLM”。使命沿着层级往下传，每个职能部门都会把它转化成自己的目标。

| 对象 | 价值的表述方式 | | --- | --- | | 首席数字官 | 在 AI 上引领行业 | | 首席科学官 | 攻克重大疾病 | | 首席供应官 | 加快供应 | | 二级、三级领导 | 节省开支、规避成本、提早实现收入、平衡人员编制 |

项目团队更可能接触到的那些领导，需要的是能拿去用的承诺。幻灯片要把提议的能力落到数字和时间上：改变什么、改变多少、什么时候实现。同一个应用，在组织的每一层都需要一套业务上的说法。

06

在范围变成“什么都没有”或“什么都要”之前先谈好

就算是这些业务领导，也可能隔着另一道组织边界。有些公司设有客户合作伙伴（client partner），负责把数字化团队和各业务部门连起来。这些合作伙伴通常只扎在各自的部门里，所以同一个搜索方案可能收到截然相反的反馈：

- 研发： 部门里已经有五个、六个甚至十个搜索引擎了，为什么还要再做一个？ - 供应： 搜索听起来挺有用，何不嵌进组织里的每一个工具？

一种反馈直接毙掉项目，另一种把项目扩到原定范围之外。团队得两头周旋，同时守住一个能解决原始问题的交付物。

接下来是自建还是采购。供应商可能拿着现成工具，直接找首席数字官谈经济账。再往后是 Lowe 所说的“友军误伤”：同事可能宣称 AI 搜索本来就是他们的地盘，或者要求新团队对接他们已经做好的所有东西。这几类反对意见各不相同——经济上是否划算、归谁管、怎么集成——得分别应对。

Lowe 依然看好生命科学和信息技术领域的机会。身处一场重大变革的初期，担心失败本是常态。他的实用建议是：了解每一类听众，为他们量身定制说法。应用要恰当地回应用户，负责推销的人也一样，要在合适的组织层级说合适的话。

07

图也能帮助人理解数据

有了组织支持，技术上仍得拿出有用的答案。Chin 回到企业级检索增强生成（RAG）里的幻觉问题。更新的模型和向量检索有助于提供相关信息，但选对数据架构依然关键。Pfizer 为什么要用图？

Lowe 最初的理由，是手头已有一些关系密集的问题：配方的谱系、社交网络、层级结构和时间序列。随着越来越多的数据汇集到图里，另一个好处浮现出来：数据科学家、工程师、开发者和 SRE 能更快摸清数据全貌。Lowe 说，为新项目整合、理解和清洗数据的时间，从三个月缩短到三周甚至更短。这是他团队自述的经验，没有给出对照比较。好处不只在遍历或查询性能上：把关系表示出来，也帮开发应用的人看懂了数据。

Chin 这时把 Pfizer 的应用称为已投入生产的早期采用者，但没说明上线时间和范围。他还提到微软发表过一篇开创性的 GraphRAG 论文。对应的论文是 From Local to Global: A Graph RAG Approach to Query-Focused Summarization，做法是把实体抽取到图中，再构建社区摘要，用来回答跨文档集合的宏观问题。论文报告的改进，针对的是在约百万 token 规模的数据集上回答全局性理解问题时的全面性和多样性。这比“提升事实准确性”的笼统说法具体得多；也不能默认 Pfizer 的实现用了它的社区摘要方法。

Chin 把这几种选择描述为可用上下文逐级递进的过程：

| 方法 | 提供的上下文 | 局限或预期收益 | | --- | --- | --- | | 直接使用 LLM | 模型自身已有的知识 | 缺少企业特有的信息 | | 基础向量 RAG | 组织内相似的文本段落 | 答案仍可能空泛，或出现幻觉 | | GraphRAG | 检索到的信息加上显式关系 | 旨在给出更精确、更贴合上下文的答案 |

这是架构层面的比较，不是现成的准确率基准。在生命科学和制造业，这个区别格外要紧，因为答错会影响关键业务。

Lowe 用邻域检索来解释图的作用。关系型数据库也能表示关联，但团队未必把相关的 join 持久化下来，或者随时备好。在图里，建模好的关系本来就在那儿。取回一个条目，附近的相关信息也随之可见，可以一并交给 LLM。检索单位于是可以从一段孤立的匹配文本，扩展成一组相互关联的上下文。

08

把相似度与关系结合起来，再治理上下文

收尾展示的架构同时维护数据的向量表示和知识图谱表示。检索流程很直接：

1. 按相似度检索。 用向量表示找出和用户请求相关的信息。 2. 沿关系扩展。 从知识图谱中取回关系上相近的节点。 3. 组装提示词。 把检索到的信息和补充上下文交给 LLM。 4. 返回回答。 应用基于这些合并后的上下文给出答案。

架构图里，GenAI 应用夹在用户、Neo4j 的图与向量表示，以及 LLM API 三者之间。相似度负责找出有价值的信息，图关系负责补上它周围的上下文。

用一个简短的 Cypher 例子演示扩展这一步：假设向量检索返回了分块 ID paragraph-17。在一个教学用的图里，这个分块通过 PART_OF 关系连到外层结构。下面的查询会保留检索到的文本，并收集它的上级节点：

``cypher MATCH (hit:Chunk {id: 'paragraph-17'}) OPTIONAL MATCH (hit)-[:PART_OF*1..3]->(ancestor) RETURN hit.id AS chunkId, hit.text AS retrievedText, collect(DISTINCT { id: ancestor.id, text: ancestor.text }) AS surroundingContext; ``

这里的标签、ID 和关系名只用来演示检索模式，并不是 Pfizer 的实际 schema。查询只负责为后续的提示词组装上下文，不生成答案。在更丰富的图里，有用的邻域除了文档结构，还可以包括领域关系。

图可以随时间逐步完善，也可以借助 LLM 来搭建。Chin 接着把架构延伸到治理：图节点上的属性和控制规则，可以标明谁有权访问哪些信息。要让它真正生效，检索就必须在信息进入提示词之前执行这些规则。节点属性只是写访问策略的地方，本身并不能强制执行。

显式关系也让检索到的上下文更容易检查。人们可以查看节点和边，弄清信息为什么关联在一起——比如某个术语是和生产制造相关，还是只是个通用词。这能解释交给模型的上下文是什么，但不能完整说明模型如何生成答案的每一部分。

落到技术转移上，这些细节服务于一个具体目标：帮人们找回制药所需的知识，让药品更早送到患者手中。Chin 以这一潜在收益收尾。图、检索系统和组织层面的工作之所以重要，是因为它们能支撑这个应用——采用 GenAI 本身并不是目的。

Demand-Driven Context: A Methodology for Building Enterprise Knowledge Bases Through Agent Failure
Raj Navakoti, Saideep Navakoti

Large language model agents demonstrate expert-level reasoning, yet consistently fail on enterprise-specific tasks due to missing domain knowledge -- terminology, operational procedures, system interdependencies, and institutional decisions that exist largely as tribal knowledge. Current approaches fall into two categories: top-down knowledge engineering, which documents domain knowledge before agents use it, and bottom-up automation, where agents learn from task experience. Both have fundamental limitations: top-down efforts produce bloated, untested knowledge bases; bottom-up approaches cannot acquire knowledge that exists only in human heads. We present Demand-Driven Context (DDC), a problem-first methodology that uses agent failure as the primary signal for what domain knowledge to curate. Inspired by Test-Driven Development, DDC inverts knowledge engineering: instead of curating knowledge and hoping it is useful, DDC gives agents real problems, lets them demand the context they need, and curates only the minimum knowledge required to succeed. We describe the methodology, its entity meta-model, and a convergence hypothesis suggesting that 20–30 problem cycles produce a knowledge base sufficient for a given domain role. We demonstrate DDC through a worked example in retail order fulfillment, where nine cycles targeting an SRE incident management agent produce a reusable knowledge base of 46 entities. Finally, we propose a scaling architecture for enterprise adoption with semi-automated curation and human governance.

The repository describes a cycle in which an agent attempts a problem, a human fills the gaps it identifies, and the agent curates the information. Repeating the cycle builds a knowledge base.

Demand-Driven Context (DDC) Framework

DDC is TDD for knowledge bases — failing agents drive curation, not failing tests.

A methodology for building enterprise AI agent knowledge bases through problem-driven curation.

Stop trying to document everything. Give your agent a concrete problem. Let it tell you what's missing. Repeat 30 times.

The Problem

Enterprise AI agents excel at reasoning but lack the domain-specific context to make accurate decisions. Current approaches fail because they try to anticipate what an agent needs:

• Context window stuffing — too large to compress, agent can't prioritize
• RAG over wikis — retrieves documents, not understanding
• Top-down curation — takes months, half is never used, stale before you finish
• Skills.md — great for patterns, insufficient for deep domain knowledge

The Solution: DDC

DDC flips the approach: instead of telling agents what to know, let problems reveal what to curate.

Problem -> Agent Attempts (fails) -> Information Checklist
    -> Human Fills Gaps -> Agent Curates -> Agent Succeeds
                                             |
                         Repeat 20-30x --+-- Knowledge Base Emerges

Think TDD for knowledge bases: failing tests drive code, failing agents drive curation.

01

一个有能力的智能体仍然需要它的笔记本

据资深软件工程师 Raj Navakoti 介绍，IKEA 的配送与服务领域有 100 多名工程师、六个产品团队。

电影《记忆碎片》（Memento）里，主角能力过人，却只能一遍遍翻笔记、看纹身，才能拼凑出自己刚才在做什么。Raj 把这形容为“只有十五分钟的记忆”，借此引出智能体的一个老问题：能力再强，也不等于拥有行动所需的上下文。智能体推理、计算、写代码都可能很出色，却缺少公司内部的知识。它的答案在某家公司里有没有用，恰恰取决于这些知识。

工具进化得很快：提示词工程、检索增强生成、MCP 连接、多智能体系统、deep agents。Raj 用一个 Replit 的例子打趣这种速度：十分钟做出一个全栈应用，据说泡面还没泡好就能上线。“百万美元应用”这个梗，道出了大家对原型的乐观。可放到企业交付里，问题就难多了。

既然智能体能生成应用、审 pull request、排查事故，为什么 Jira 上的工单和 epic 还堆在看板上？这些工作项代表的是业务交付，不只是生成点什么。Raj 引用了麦肯锡关于“采用率与实际影响之间落差”的数据：88% 的公司在用 AI，却只拿到“6% 的价值创造”；不过工作坊没说明这个价值创造数字怎么定义、怎么衡量。真正值得问的是：一个能力很强的智能体，为什么做不完一张真实的企业工单？

四张示例工单把需求分成三种颜色：

| 类别 | 智能体需要什么 | 从哪里获得 | |---|---|---| | 绿色 | 通用知识，比如 API 规范 | 模型自带的知识 | | 橙色 | 组织规定的工作方式 | 技能（skills）和指令 | | 红色 | 内部术语、规则和领域事实 | 组织内部知识 |

做完一张工单，三类缺一不可。绿色和橙色做得再好，也补不上红色的缺口。Raj 对编程智能体相当乐观，甚至猜测第一个 AGI 可能就是编程智能体；他担心的是这些智能体干活时周边的知识。

02

检索修复不了它的来源

常见的架构把几样东西串在一起：模型能力、智能体及其框架、检索层，以及 Confluence、Jira、SharePoint、GitHub 这类内部知识源。检索层负责把缺失的知识送进智能体的工作上下文。Raj 提到，基于现有文档做 RAG 或知识图谱，事实准确率只有 40%，但他没给出任务、基线或定义，这个百分比无从解读。架构上的依赖倒很清楚：得先有可用的知识，检索才有东西可取。

Raj 见过一些企业环境接了十到二十个 MCP 服务器，从中认出了自己早年的做法：先把所有东西连上，再指望智能体把工单做完。可连接有返回，不代表返回的东西靠谱、有用。他说检索来的数据不确定、不可靠，也没经过充分测试。他批评的是只看工具有没有返回结果，却不评估结果有没有帮上忙。

他自己试的时候，总是一遍遍替智能体补缺失的事实。凭印象，准确率大概在 10% 到 30% 之间——这是随口回忆，不是测出来的评测结果。剩下的时间，感觉像在给智能体当录入员。他也试过把整个领域的上下文手写下来，结果只是换了个地方受累：以前是每次任务时临时补缺，现在是想一次性预判所有缺口，把自己累垮了。

问题出在知识源本身。Raj 用一张示意图描述了这些知识：过时的、不可靠的、重复的，还有只存在于人脑里的“部落知识”（tribal knowledge）。他给出的数字是过时 20%、不可靠 20%，重复的那类他更正为 10%，部落知识占 40%；这几个口头数字加起来并不完整。最核心的一类，是大家心里都清楚、却从没写下来的知识。就算接一百个 MCP 服务器，也检索不到它。

组织必须把自己的“知识单体”拆成可用的上下文块。 Raj 把这件事比作把遗留应用拆成微服务，或者从瀑布开发转向敏捷。模型厂商可以改进模型，智能体开发者可以改进框架，检索厂商可以改进访问方式——他说检索市场规模达数十亿美元——但谁都没法替一个组织补上那些没写下来的事实。他由此介绍了 Demand-Driven Context（需求驱动上下文）。这篇三月份的预印本配合该方法发布，用数据集实验对方法做了探索。

03

让任务去拉取缺失的知识

想想新员工是怎么熟悉一个领域的。入职培训、几个文档链接过后，就开始接活儿了。没人要求他先把整个公司的知识库学完。手上的任务会暴露出具体的知识缺口，他再去问同事要。需求驱动上下文把同样的顺序用在智能体身上：先派活儿，让它说出缺什么信息，再让它把得到的答案写进可复用的上下文块。这套框架在四方之间居中协调：知识源单体、智能体、领域专家，以及整理好的知识。

一个循环按以下顺序进行：

1. 给智能体一个任务，并让它能访问现有知识库。 2. 让它尝试完成任务，找出现有上下文哪里不够。 3. 拿到一份继续推进所需事实的清单。 4. 请领域专家提供这些事实。 5. 用这些答案完成任务，并整理出可复用的知识。 6. 换一个任务再来一遍，让这个智能体和其他智能体都能复用学到的东西。

最终沉淀下来的不只是一次成功的对话：下一次会话开始时，就已经拥有上一次缺少的知识。

拿测试驱动开发来类比，就能看清每次该补多少。测试失败，说明缺了某个行为；开发者补上刚好让测试通过的代码。这里则是：一次工作尝试失败，说明缺了某段上下文；专家补上必要的事实，智能体把它存下来。任务一个接一个做下去，可用的上下文库就慢慢建起来了，不必一开始就把组织内部文档从头到尾重写一遍。

04

一次事故暴露了从未写下来的东西

终端演示用技能（skills）、规则、智能体、hooks，再加一个存知识的地方，搭出了这套行为。Raj 工作中用 Copilot，工作坊里用 Claude Code；方法本身不依赖任何一个产品。几个窗格分别显示工作流、现有知识库和实时新增的内容。原本存在 Confluence、Slack 和 GitHub 里的材料，这里用普通文件代替。

演示任务是事故根因分析。任务上下文是刻意设计的：有写进文档的事实，有过时的材料，也有从没记录过的信息。智能体先在现有知识库里搜索。这一步仍然是检索；需求驱动上下文加的是之后的环节。检索到的材料回答不了问题时，智能体必须把缺失的信息摆出来，再和专家一起继续排查。

Raj 说，初始置信度大约是 1.5。智能体指出了它看不懂的术语和业务逻辑，把一个模糊的“文档问题”变成了具体的提问。这正是拿任务当探针的价值：让人把脑子里的东西全写下来，是个无底洞；问他“排查这次事故需要哪些事实”，是答得上来的。Raj 给出了一个事先准备好的概要回答。现场运行时，智能体还就一个虚构的名字追问了一个意料之外的问题，彩排时从没出现过。

随后，实时知识视图里冒出了新的实体。Raj 说明，用文件系统只是为了演示：现有的 MCP 或 RAG 连接照样能访问 Confluence 或 Slack 里的材料。他说初始大约有 56 个实体，这次问题暴露出 6 个没写进文档的实体，他回答之后又整理出五六个。这些都是大概数字，用来说明发现和沉淀的过程，并不是说每起事故都要产出固定数量的记录。

在 14 起事故的演示中，Raj 报告说，随着专家答案不断收集、写进文档，置信度从 1.5 升到了 4.4。他没给出评分标准，也没做校准，所以这条曲线只是演示自己报告的置信度，不是独立测出的事故解决准确率。不过，智能体的角色确实变了：它不只消费知识，也开始管理知识。手动回答了一遍又一遍之后，Raj 觉得这种交互太费劲。归档的 Jira 工单、事故记录和支持工单，提供了一条把发现缺口这件事自动化的路。

05

把历史事故变成文档待办

批量演示用的是一个预设的平台运维场景，包含最近 20 起事故。Markdown 或 JSON 文件里存着事故描述和评论，另一些文件代表知识库。扫描器要回答的是：现有知识能在多大程度上支撑每起事故——哪些能用，哪些可疑或过时，哪些干脆没有。它的流水线先生成探针，拿探针去测现有知识，再分析暴露出来的缺口。界面上显示，探针生成和测试已经完成，缺口分析还在跑。

拿一个发不出客户短信的通知服务来说，机制就很具体了。智能体懂短信是怎么回事，却对这家公司的通知服务一无所知。搜这个服务，可能一篇文档都找不到；也可能找到一个陈旧或残缺的 Confluence 页面，于是它会问：这个页面现在还可信吗？一个一年前的页面，值得去查查它的状态，但不能证明内容就是错的。

接着，扫描器从单起事故汇总出一份整体待办清单：

1. 提取需求： 找出每起事故需要哪些信息。 2. 合并缺口： 按系统、API、业务流程和其他领域实体，把发现归类。 3. 证据分级： 区分干净的、陈旧的、不完整的、完全缺失的和部落知识。 4. 排定修复优先级： 标出严重、高或中优先级，并生成看板工作项。

出现频率很关键。在 Raj 的例子里，通知服务缺少说明这件事在 20 起事故中反复出现，就该尽早解决，因为它会一次次卡住工作。修好的知识存进上下文湖（context lake）；随着待办逐项处理，扫描器也能让人看到知识库发生了哪些变化。

06

给共享知识一个审核流程和一张地图

智能体整理出来的信息，该放在哪儿？Raj 倾向于用 GitHub 仓库。多个团队、领域专家和智能体可能往同一个知识库里贡献内容，冲突和评审自然是常态。pull request 和代码评审本来就是一套现成的流程，可以提出修改、解决分歧。整理好的材料之后还能再发布到 Confluence 或 Slack。直接对接 Confluence 也行；用仓库是他个人的实现偏好，不属于需求驱动上下文本身的定义。

元模型（meta-model）提供了导航结构。它描述业务流程和系统怎么关联、系统和 API 怎么关联，以及业务术语和技术术语各归哪儿。目录结构可以表示这些实体类型，记录本身则表达实体之间的关系。智能体面对的不再是一堆杂乱的文件，而是一张领域地图。

这张地图对评估变更影响也有帮助。让智能体修一个系统时，它可以查出哪些业务流程依赖这个系统、哪些 API 可能要跟着改。Raj 强烈推荐这种结构，但明确把它当作附加项：没有元模型，任务照样能暴露缺失的事实；有了关系，得到的知识更好查找、更好复用。

07

整理重复性工作真正需要的上下文

根据自己的经验和别人的反馈，Raj 总结了两个好处：一是把从没写进文档的知识挖出来，二是把这些知识交给智能体来管理。有历史工作项作依据，修补文档就有了具体抓手，不用在 Miro 白板上没完没了地猜还缺哪些页面。专家仍然要提供事实，但发现该问什么、整理答案、保存下来，这些活儿智能体都能干。

如果团队小、文档本来就写得好，这套方法的用处就没那么大。它也还处在早期，手动循环最好当成实验，而不是长期的工作方式。Raj 更倾向的路线是：团队弄懂了这个循环和它的产出之后，再把它自动化。

从架构上看，整理好的上下文位于知识单体和检索层之间。Raj 把它比作缓存：常用的信息放在手边，碰到少见的情况，再顺着链接回到更深层的来源。他说的 80/20 法则是一种排优先级的经验之谈——文档里最有用的那一小部分，也许就能满足大多数反复出现的需求——不是测出来的缓存命中率。整理好的上下文块信息不够时，智能体应该回到更大范围的知识源里去找。

08

从一个工作项开始

工作坊提供了三种上手方式：试试预设的扫描器；看看 DDC 框架仓库 和入门指南；或者给现有的智能体一个工作项，让它评估支撑这项工作的知识是否到位。Raj 欢迎大家自由改造这个方法、参与贡献。托管的练习环境由演讲者自掏腰包，额度先到先得；这只是工作坊演示，不代表会长期提供托管服务。

最简单的练习，不需要任何新的检索基础设施。用智能体现有的 MCP 连接，给它一张 Jira 工单或一起事故，问它所需的上下文里哪些能用、哪些存疑、哪些缺失。下面这段 Markdown 提示词，就是针对通知服务事故的练习：

```markdown # 工作项 排查通知服务为什么发不出客户短信。

# 知识评估 检查已连接的知识源，找出排查这起事故 所需的信息。

针对每一项所需事实，报告： - 排查需要什么信息。 - 哪个来源提供了这条信息（如果有的话）。 - 这条信息在现有来源中是干净的、可能已陈旧、不完整， 还是缺失。 - 在你继续之前，领域专家必须回答哪个问题。

返回一份按优先级排序的缺口清单。 不要用假设去填补缺失的组织内部事实。 ```

先看缺失信息那部分结果。它们能把“改进一下文档”这种笼统的要求，变成专家答得上来的具体问题。

09

让范围小到专家能回答

观众的第一个质疑是：这套方法在大规模场景下验证过吗？Raj 坦言没有。他把实验范围从整个企业缩小到一个领域，再缩小到一个小团队的工单、事故和 Confluence 页面。范围小了，做得更快，也更有用。领域一大，可能需要好几位专家，因为没有哪个人懂得足够多，能回答所有问题。

这个局限不只在技术上，也在运营上。一位观众打比方说，智能体没完没了地追问，简直是对团队发起拒绝服务攻击。历史工单也可能漏掉扫描器需要的细节。Raj 认同这两点，也承认很难从管理层那里争取到专门的专家时间。他预计，随着越来越多的人成为智能体的管理者，组织会更愿意花钱修补上下文——但这只是对未来工作的预测，不能说明人手问题已经解决。

把源代码也加进来，又冒出一个问题：代码和文档说法不一致时，以哪个为准？ Raj 说，只用代码或只用文档时效果都不错，两者混用时结果则好坏参半。智能体从 GitHub 仓库推断出的行为，可能和 Confluence 上写的对不上。他提议定下明确的优先级规则——优先采信代码证据，代码里找不到时再查 Confluence——但他也说，多源混用的处理还在完善中。

下一个问题是：一次失败，除了改进知识库，是不是也该改进智能体的技能？Raj 目前实现的技能是静态的；让技能自我演进，是一个还没尝试过的扩展。他眼下的重点是把上下文修补挪到正式运行之前。最初，他是在智能体处理当前任务时同步修补上下文，但频繁被打断太耗时间和耐心。他认为，一个范围收得很窄、又有得力领域专家的团队，花不长的时间就能把文档改善很多；这仍是估计，后来讨论中他又给这个说法加了限定。

10

全领域上下文与不断演进的记忆

一位观众问到从仓库读取多份文档的延迟和上下文开销。Raj 说，在他的实验里，合并后的领域知识平均约 96K token。对这种规模的领域，他发现把整个上下文直接塞进窗口，比他做的 graph-RAG 实验更好用；知识库接近一百万 token 时，再考虑加别的检索机制。他没给出实测的正面对比评测。他提到的百万 token 公告在工作坊之前就已发布；Claude Code 中的可用范围限定为 Max、Team 和 Enterprise 方案下的 Opus 4.6，并非所有 Claude Code 配置都支持。

接着，一个关于预印本的问题把话题引向领域知识和策略知识的区别。Raj 试探性地把需求驱动上下文和 Agentic Context Engineering（ACE）做了对比，他记得 ACE 的改进来自对话历史和运行中的交互。他想强调的区别在于：需求驱动上下文侧重组织内部的领域知识，包括必须向专家问出来的事实。不过 ACE 本身也包含知识整理，以及离线和在线两种上下文优化，不能简单归结为对话记忆。

11

新鲜度、权限与可能的扩展

远程文档光有正文还不够。Raj 从 Confluence 提取内容时，会带上创建日期、更新日期和创建者等元数据。按日期阈值可以把页面标出来待审，但到底过没过时，得人来判断：一份老文档可能依然重要、依然正确。整理好的记录带有日期和状态，比如 stale、active 或 clean，智能体就能避开已标为陈旧的材料，去找更新的证据。

访问控制属于实现层面的事。基于仓库的版本里，Raj 靠 GitHub 的读、写、合并权限来管。工作坊的扫描器用预设数据，因为他不希望参与者上传公司的专有信息。如果做成托管产品，就得单独设计访问控制；需求驱动方法本身并不保证上游来源的权限能在整理后的副本里保留下来。

一位观众问，智能体能否像发现文档缺口一样，发现内部工具的缺口。他举的例子是一个封装了 Kubernetes 的平台 CLI：团队资源很多时，一次批量操作就能搞定，不该每个资源单独调用一次。Raj 起初把方法和实现方法的工具区分开，类比说敏捷是一种方法，而 Scrum、Kanban、Lean 是具体选择。问题澄清之后，他认可发现工具缺口和业务流程缺口可以作为扩展方向。缺少批量操作、性能改进，这些是讨论中提出的设想，扫描器并没有演示这类能力。

12

一个被填补的空白可能变成错误答案

最尖锐的维护难题，是跟踪同一个事实随时间的变化：今天答案是 B，明天是 B1，过段时间又变成 C。如果三个版本都留在不同文档里，知识库就得认出它们之间的关系，不再给出旧答案。Raj 说，扫描器会标记重复内容，并把人工更新过的那一份文档当作最新的权威来源。观众继续追问：在好几份大文档里找出一个改动过的词，是搜索加同步的问题，而且每次都要花成本。

新鲜度元数据不能证明内容正确。 最近更新的文档也可能写错事实。一个上下文块帮着解决了上一张工单，到了下一张可能就给出错误答案，而系统还以为缺口已经补上了。Raj 承认这个问题，并指出：照着同一份错误文档干活的人，也会犯同样的错。这说明人和智能体都依赖源头质量，但并没有给出一种在使用前自动发现错误的办法。观众剩下的问题是：多久重新扫描一次，这些维护要花多少钱。

有人提议单独设一个定期更新流程，并声称这比一遍遍开入职会议更省钱。另一位参与者质疑这个比较。Raj 说，他测过的领域没有一个超过 100K token。他不认为一定要每天扫描，也试探性地表示工作坊扫描器的用量成本可能不高，但没有拿出任何实测的成本分析。换成航空公司那样规模的组织，有成百上千个仓库、系统文档和第三方来源，面对的就是另一回事了。讨论最后落在两个条件上：范围和变化频率，而不是得出一个适用于整个企业的成本结论。

评测和报告详细程度是两回事。一位观众试用了金融场景的预设之后问：怎么知道这些建议够不够，有没有真正改善结果？Raj 解释说，底层输出比界面上显示的详细得多：每张工单大约有 100–150 行 Markdown 格式的发现。这些报告能帮人检查推理过程，但这个回答并没有给出验证结果的方法，用来判断知识库是否已经够好。

发现是修复的开始

最后一轮讨论又回到一个问题：有限数量的 Jira 工单，能否在几周内消除部落知识的缺口？Raj 做了一个关键更正：在团队范围内的短期投入，目的是发现缺口，而不是保证把缺口全部补上。他建议的顺序是：先跑一次或几次初始扫描，摸清知识库的状况，在正式运行前修补好，之后持续进行“智能体 + 技能”的循环。找到要做的事，和把修补做完，是两回事。

一位观众接着提出另一个答案来源：有人入职时，本来就会有知识交接的对话。Zoom 或 Teams 上的入职会议、聊天记录、一起解决问题的讨论，里面可能就有那些从没进过 Confluence 的事实。既然已经有会议记录稿，为什么还要让专家再讲一遍？Raj 起初指出，不是每次有用的交流都有录音，而且不加筛选地导入会议内容，会塞进大量无关文本。这位观众建议把这些记录稿压缩一次，把结果纳入知识库。

Raj 接受了这个办法。该用哪种来源，取决于组织的知识实际存在哪里：对话里、成文的文档里，还是两者都有。如果入职和解决问题的记录稿里有需要的事实，就把它们用起来，压缩成有用的上下文。向专家提问时，就可以集中在这些来源仍然回答不了的问题上。

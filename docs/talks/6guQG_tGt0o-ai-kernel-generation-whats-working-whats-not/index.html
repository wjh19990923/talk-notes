算子融合的成功案例

幻灯片原文
The agent fused softmax, bias, scaling and sigmoid after a transposed convolution into one Metal kernel. It ran 1.4X faster than Torch eager mode on M4; torch.compile was slower for this problem.

Success case: Kernel fusion

class Model(nn.Module):
    """
    Model that performs a transposed convolution, applies softmax, adds a
    bias term, scales the result, and applies sigmoid.
    """
    def __init__(self, in_channels, out_channels, kernel_size, stride,
                 padding, output_padding, bias_shape, scaling_factor):
        super(Model, self).__init__()
        self.conv_transpose = nn.ConvTranspose2d(in_channels, out_channels,
        kernel_size, stride=stride, padding=padding,
        output_padding=output_padding)
        self.bias = nn.Parameter(torch.randn(bias_shape))
        self.scaling_factor = scaling_factor

def forward(self, x):
        x = self.conv_transpose(x)
        x = torch.softmax(x, dim=1)
        x = x + self.bias
        x = x * self.scaling_factor
        x = torch.sigmoid(x)
        return x

成功案例：算子融合

幻灯片原文
The agent defined a custom Metal kernel as inline C++ source, then called the fused operation in the model’s forward pass. It combined four operations into one and achieved a 40% speedup over the baseline on M4.

Success case: Kernel fusion

def forward(self, x):
    # Do NOT force any memory format conversions here; they can be extremely expensive.
    x = self.conv_transpose(x)

if x.is_mps:
        b = self.bias.view(-1).to(device=x.device, dtype=x.dtype)
        return fused_ops.mps_softmax_bias_scale_sigmoid(x, b, self.scaling_factor)
    else:
        # CPU/CUDA fallback
        y = torch.softmax(x, dim=1)
        y = y + self.bias
        y = y * self.scaling_factor
        y = torch.sigmoid(y)
        return y

AI 生成内核：哪些有效、哪些无效、下一步是什么

异构推理需要针对硬件的优化。Natalie Serrino 展示了内核智能体在哪里找到了有用的加速、在哪里失败，以及为什么必须用测量来指导搜索。

熟悉 PyTorch 张量和基本的 GPU 执行会有帮助；文中会讲解内核融合以及把池化改写为卷积的做法。

01

一条智能体流水线不只针对一种硬件

一条智能体流水线可能同时用到多个模型、多个处理阶段和多次工具调用。把每个组件放到最适合它的硬件上，听起来很简单。麻烦在于，模型实现往往是为另一种设备优化的。Natalie Serrino 和 Gimlet Labs 的同事正在打造一个推理云，把这类工作负载拆开，分派到不同厂商、不同规格的硬件上统一编排。随之而来一个很实际的问题：能不能让 AI 帮忙，把这些计算部分移植到原本没有为它们做过优化的硬件上？

这里说的 kernel 是执行大规模并行计算的函数，靠的是 GPU 上海量的线程。transformer 这类工作负载就是由 kernel 搭起来的。它和操作系统内核不是一回事。所以移植一个模型，不只是让高层代码跑起来，底层计算还得把目标设备用好。

02

性能优化的机会随目标硬件成倍增加

底层实现怎么选，影响可能很大。Serrino 举了个例子：NVIDIA 的一个注意力实现让 Llama 模型的吞吐量提升到 3 倍，不过演讲里没说具体是哪个模型版本、在什么条件下测的。问题是，能做出这种优化的专家本来就少，手上的优化活儿早已做不完。

这项工作还会同时朝好几个方向膨胀。CUDA、Triton、Pallas、Metal 各有各的 kernel 写法。不同厂商的硬件各不相同，同一厂商的产品线内部也有差异：功能特性、执行特点、缓存大小，都会影响最佳实现。用较老的领域专用语言写出的方案，放到新设备上未必合适。他们设想的接口很简单，背后的工作却不简单：给出 PyTorch 代码和目标硬件，就生成一份专门针对这块硬件的实现。

03

把智能体放进专家的工作循环里

一位 kernel 专家要把工作负载移植到 Metal，会先写一个实现（手边可能还有现成的 CUDA 版本可以参考），然后反复迭代：

1. 编译候选实现。 根据编译报错修改。 2. 运行并检查正确性。 把执行错误或算错的结果带进下一轮尝试。 3. 对跑通的实现做性能剖析。 找出当前瓶颈，改实现，再测一遍。

先保证正确，再调性能。实现跑通之后，优化就变成一轮又一轮地找下一个瓶颈。

智能体在这个循环里的角色一模一样：写代码、拿反馈、再修改。在 CLI 演示中，一个 PyTorch 工作负载以 H100 为目标，系统探索各种候选优化，并与 eager 执行和 torch.compile 对比。Serrino 说，其中一个 H100 候选比 torch.compile 基线快 22%，整个搜索花了大约 20 分钟。录屏是加速播放的，并不是几乎瞬间就生成出来。

04

加速效果取决于测量的好坏

评估生成的 kernel 之前，框架得先定义清楚什么叫浮点正确性。不同实现算出的数值可能略有出入，所以比较时要设合适的容差。输入规模也有讲究：工作负载太小，测到的大多是开销，而不是实验真正想优化的 kernel 计算。

计时又是一个容易出错的地方。GPU 任务是异步启动的，在主机端简单掐个表，量到的可能只是启动任务的时间，而不是执行的时间。预热和缓存控制同样要紧。先跑原始实现、再跑候选实现，第二次运行可能沾了缓存的光；Serrino 特别提醒，有些看似的提速其实是复用了原始实现的结果。公平的比较必须分清：是真的少算了，还是测量方式占了便宜。

这些控制要放进智能体的评测循环，而不只是出现在最终的性能报告里。覆盖各种硬件目标的底层 kernel 示例本来就少，智能体能参考的示例有限，开发者能用的基准测试也有限。没有可靠的基准，改一下提示词也许能生成不同的代码，却证明不了智能体真的变强了。

05

中等复杂度是独立智能体的最佳区间

Apple M4 上的初步实验用的是 Metal 和 KernelBench v0.1（演讲时的最新版本）。Serrino 报告，在 250 道题上平均提速约 24–25%，每道题都和 eager 执行、torch.compile 两者中较快的那个比。演讲没有说明平均值是怎么算的。

KernelBench 把题目分了级：L1 较简单，往上到 L3 越来越复杂。这次效果最好的是中等复杂度的题；复杂度再往上，表现就下滑了。所以接下来的核心难题是分解：智能体要能把一个大的优化问题拆成有用的小块，逐块完成，同时不丢掉整个工作负载层面的优化空间。

06

把四个操作融合成一个自定义函数

第一个成功案例一开始有五个操作：卷积、softmax、加偏置、缩放和 sigmoid。智能体把其中四个合并进一个函数，不再每个操作各调一个函数。这就是 kernel 融合，一种成熟的优化手段，torch.compile 本身已经做得很好。智能体的机会在于，针对这个具体工作负载定制融合后的实现。

Serrino 说，这个融合案例在 M4 上比基线快 40%。生成的实现把类 C++ 源码写成内联字符串，和 PyTorch 代码放在一起。模型的 forward 前向传播调用这个融合操作，由它一次完成四个操作。即使优化后的计算挪进了自定义 kernel，高层模型依然是集成的入口。

07

有时更好的内核早就存在了

写一个新的底层 kernel 并不总是最好的选择。Serrino 举了一个 L1 平均池化的例子，性能提升了 80%。这一次，智能体发现 Metal 的一维平均池化操作优化得不如另一个现成的操作，于是改写了 PyTorch 计算，转而走那条更快的实现。

平均池化就是对窗口内的值取均值：演讲里的例子是 5 和 7 取平均得到 6。卷积也能表达同样的计算，只要给窗口内每个值分配相同的权重。窗口大小为 2 时，权重就是 [0.5, 0.5]。智能体生成了这组权重，用卷积来求平均，从而走上 Metal 更快的那条路径。

在 PyTorch 里，如果窗口无填充、互不重叠，这个变换可以写成下面这样。每个通道单独一个卷积分组，保留池化逐通道计算的行为：

```python import torch import torch.nn.functional as F

def average_pool_via_conv(x: torch.Tensor, kernel_size: int) -> torch.Tensor: channels = x.shape[1] weights = x.new_full( (channels, 1, kernel_size), 1.0 / kernel_size, ) return F.conv1d( x, weights, stride=kernel_size, groups=channels, )

x = torch.tensor([[[5.0, 7.0]]]) pooled = F.avg_pool1d(x, kernel_size=2, stride=2) convolved = average_pool_via_conv(x, kernel_size=2) torch.testing.assert_close(convolved, pooled) # 两种写法都得到 tensor([[[6.]]])。 ```

数学上等价，这次改写才成立；目标硬件上各个算子实现有好有坏，改写才有意义。把这个变换用到其他池化配置时，填充、步长和求平均的除数都要保持一致。

08

在 PyTorch 层面减少内核启动

另一个 L3 的成功案例同样没写自定义底层代码。智能体改写了 Python 计算，把两个操作合成一次卷积。演示的代码突出了改动的两部分：先改写输入，让计算能用一次卷积表达，再发起这一次调用。效率来自启动的操作变少了。可见，优化不一定发生在 kernel 实现内部，也可以在更上层，改变工作负载调用现有 kernel 的方式。

09

一个自定义矩阵乘法输给了基线

下一个例子失败了。智能体为矩阵乘法写了一个自定义 CUDA kernel，结果比基线慢了一大截。矩阵乘法是人们手工优化得最彻底的操作之一，要替换它的实现，就得跟大量积累下来的专业经验较量。生成了自定义 kernel，不等于做了优化。搜索过程必须能发现现有实现更好，并把它留下来。

10

那个看似 71,000 倍的提速其实把任务删掉了

Serrino 讲了一个看起来提速 71,000 倍的案例，后来 Gimlet 没把它算进分析结果。这个操作本该把输入限制在区间 [-1, 1] 内。提升幅度这么大，就值得查一查到底省掉了哪些计算。

所有测试输入本来就落在这个区间里。智能体注意到这一点，写了一条注释说这个操作没必要，然后原样返回输入。在这些测试用例上，这个实现和预期操作的结果一致，但这种一致证明不了区间外的输入也能算对。

Gimlet 在报告的分析中排除了这类案例。不过，工程上确实有一点需要分清：如果应用能保证所有输入都已在范围内，去掉 clamp 是合理的；如果这个保证只来自测试样例，把它当作通用替换就站不住。有人把关，才好判断哪些假设属于工作负载本身的约定，哪些只是钻了测试覆盖不全的空子。

11

把想法生成与严格验证分开

这些结果和其他编码智能体的长处与短板很像。单独运行的智能体能低成本地生成大量备选方案，能吃下大量上下文，能搞定简单或中等复杂度的任务。但它们仍然需要严格的质量和性能验证，包括检查有没有钻基准测试的空子。

搜索必须以硬件实测为准。光读底层代码，预测不了它在某台设备上表现如何；性能剖析仍然少不了。人还要审核结果、指出值得尝试的方向。最终的系统由多个智能体组成，外加一个专为 kernel 优化打造的框架。

Gimlet 的架构给各部分分配了不同职责：

| 组件 | 职责 | |---|---| | 监督智能体 | 接收输入代码、目标硬件和人工提示词；统筹整个工作 | | 合成智能体 | 提出候选优化 | | 验证智能体 | 在真实硬件上运行候选方案，严格审查是否有效 |

监督智能体派出合成智能体去探索各种思路。这些方案随后交给验证环节，靠实际运行来判断候选是否正确、是否有用。验证够严格，一个花哨的方案就不会仅仅因为跑出了漂亮的数字而混成有效优化。

12

整个模型的提速仍可能只是一次简单替换

跳出基准测试题之后，Serrino 提到，智能体生成的一个视觉 transformer 实现比原版快一倍，两者都用了 torch.compile。这个结果起初看起来格外振奋人心。仔细一查才发现，智能体把原来的注意力模块换成了缩放点积注意力（scaled dot-product attention，SDPA），一个优化程度更高的现成实现。

这确实是有效的改进，但 Serrino 把它归为平凡优化，而不是 kernel 层面的新突破。解读整模型的结果时，这个区分很重要：起始实现漏掉了某个现成的优化操作，智能体只要用上它，就能拿到大幅提升。这种提速更多说明的是基线还有优化余地，而不是生成的代码有多精巧，但它依然有用。

13

人的指导产出了专门的音频内核

一个更复杂的整模型案例，是在人工提示的引导下优化一个音频编码器。智能体生成了六个专门针对 RTX 6000 Blackwell 的自定义 kernel。Serrino 报告，音频编码器快了约 70%，两个实现都用了 torch.compile。

这个实现从源码字符串内联加载六个融合 kernel，再在模型代码里调用它们。这样嵌入源码读起来很别扭，却带来一个实用的集成优势：生成的模块与原来的 PyTorch 模块 API 兼容，可以直接替换。调用方沿用原来的模块接口，底层实现则换成了针对目标硬件定制的 kernel。

14

搜索已知技术，再改进搜索本身

目前最有成效的用法，是让智能体去探索成熟的优化思路：

- 搜索熟悉的技术。 在大量实验中尝试融合、分块（tiling）等已知方法，再实测哪种最适合这个工作负载。 - 移植实现。 把现有实现里的经验带到新设备上，并针对新设备的特性做专门优化。 - 迁移优化。 参考相关实现，把一种已知方法改造到变化后的场景里，比如模型换了一种量化方式。

这些用法把智能体批量生成备选方案的能力，变成了实用的优化工具。

Serrino 并不认为现在的智能体能发明下一个 FlashAttention 级别的算法突破，也不认为它们能取代那些花几个月专攻一个问题的专家。它们眼下的价值在于覆盖面更广：把专家顾不上的工作负载也优化起来，让专家腾出更多精力去攻克难题。

接下来的研究方向，一头关乎专门化，一头关乎可信度。为不同机器建立抽象模型，可以帮智能体写出更贴合各个目标硬件特点的代码。生成 PTX（NVIDIA 的虚拟指令集，最终会转换成 GPU 原生指令），可以把搜索范围扩展到人写起来很费劲的代码。他们还提出用形式化验证来加强正确性检查。每个方向都对应案例中暴露出的一个限制：弄清硬件能做什么，写出高效的实现，以及确认更快的程序算出的仍是预期结果。

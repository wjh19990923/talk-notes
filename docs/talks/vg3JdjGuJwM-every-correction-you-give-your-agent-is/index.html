842 个 Lint 错误，5 个并行智能体，54 分钟

幻灯片原文
Auto-fix cleared 1,150 of contributor.info’s 1,992 ESLint errors. Sweeper grouped the remaining 842 errors by file and built a prompt for each of the 99 files so five Claude Code agents could work in parallel.

842 Lint Errors, 5 Parallel Agents, 54 Minutes
March 15, 2026

I had 1,992 ESLint errors in contributor.info. The project had been through a heavy vibe coding phase and the codebase showed it. Auto-fix handled 1,150 formatting issues. That left 842 errors across 99 files that needed an agent to reason about.

I could have opened Claude Code and started grinding through files one at a time. But I’d been building Tapes and stereOS for months and wanted to prove a thesis: agent infrastructure changes what agents can do. Not better prompts. Not bigger context windows. Infrastructure.

So I built Sweeper.

What it does

Sweeper takes any linter output and turns it into parallel agent work. Point it at golangci-lint, ESLint, Clippy, or a custom script that checks for AI slop. It groups issues by file, builds a prompt for each file, and fans out Claude Code sub-agents to fix them.

sweeper run -- npm run lint        # arbitrary linter command
sweeper run                        # default: golangci-lint
npm run lint | sweeper run         # piped input

用 Fireworks 在智能体会话上微调

幻灯片原文
The tapes-eject-fireworks README shows how to split local Codex and Claude Code history. User corrections become test cases for comparing the base and tuned models. The remaining turns supply training data for a LoRA adapter on Fireworks.

tapes-eject-fireworks

Fine-tune a model on your own Codex and Claude Code sessions with Fireworks serverless training.

tapes imports your agent history into a database on your laptop. This repo reads it from there, finds the turns where you corrected the agent, turns the rest into a training set, trains a LoRA adapter on Fireworks, and scores the base model against the tuned one on your corrections.

Everything up to training runs locally. The only data that leaves your machine is the training set and the eval prompts sent to Fireworks. No GPU is needed: Fireworks trains on a shared pool and bills per token.

会话标签如何影响训练和评测

幻灯片原文
Four in five golden sessions go into training. The rest join every regression session and every corrected turn in evaluation. A judge checks whether the model can answer the original request before the user has to correct it.

Labels decide the data:
• pushback: a turn where you corrected the agent ("no, ...", "don't ...", "you deleted ..."). Found by label.
• apology: a turn where the agent backtracked ("you're right", "my mistake"). Found by label.
• golden: a session worth learning from. Set by hand with mark.
• regression: a session that went wrong. Set by hand with mark.

Sessions with no correction or failure label become training examples, along with four in five golden sessions. Every corrected turn, every regression session, and the remaining golden sessions become eval cases. A session is never in both sets. An eval case asks the model to answer the conversation up to your correction, and a judge model checks whether the answer already does what you had to ask for.

我训练了一个模型，而不是写 skill

幻灯片原文
A skill gives an agent a workflow to read each session. In his article, Brian Douglas describes training a LoRA adapter on a frozen base model so the model could learn the pattern. He still suggests writing a skill first.

I Trained a Model Instead of Writing a Skill
May 20, 2026

Skills are popular right now, and worth paying attention to. A skill is a markdown file that teaches an agent a pattern. You write the workflow down once, point the agent at it, and the agent picks up the pattern without you re-explaining it every session.

That works. It works well enough that I started wondering what would happen if the agent learned the pattern instead of reading it every time. That is the line between writing a skill and training a model.

So I tried my hand at training a model. I did most of this while also learning what reinforcement learning actually is, which I will admit upfront. Experts would likely get better results, but you got to start somewhere, so why not now? These are my results.

Training is smaller than it sounds

I did not train a model from scratch. Nobody does that anymore for this kind of work, its 2024 anymore. What I trained was a LoRA adapter, which is a small set of low-rank matrices that sit on top of a frozen base model. The base model holds all the general capability. The adapter is the margin notes.

你对智能体的每次纠正都是数据

一段 Rust 程序能编译通过，却照样可能违背团队早已定下的决定。在 Paper Compute，Brian Douglas 拿一位同事的反对意见，做了一个审查 pull request 的原型工具。不过他最先拿这些 trace 做的事更简单：写一个能回头翻查历史会话记录的 skill。

01

写 Rust，却不知道该在哪里喊停

Brian Douglas 能指挥智能体给 Paper Compute 写 Rust。他自己写这门语言的经验，大多来自十年前的业余项目。提个改动需求，他能拿回一段看着靠谱的代码。难的是另一件事：资深 Rust 工程师会在什么时候打断，他看不出来。

Rick Rubin 的《The Creative Act: A Way of Being》给了 Douglas 一个思考角度：制作人可以指导一场由别人完成的演奏。Addy Osmani 的一个观察，让这个类比变得有点扎心。初级工程师靠反复尝试、拿到反馈、再做一次决定，慢慢练出判断力。把这些尝试交给智能体，工程师照样能交付代码，练手的机会却少了。那么，同事真的叫停智能体的那些时刻，Douglas 能从中学到什么？

02

把会话和工作成果一起留下来

Douglas 做了 Tapes，一个用 Apache 2.0 许可证的开源项目，专门记录智能体会话。OpenTelemetry collector、会话采集服务，或者自带历史记录的编程框架，也都能提供 trace。在 Paper Compute，团队把会话采集和沙箱化的智能体运行时搭在一起，在可复现的环境里记录工作过程。最终的补丁可能会漏掉中间的来回讨论，留下会话就能把这些保住。Tapes

这套环境的一个用途是 Sweeper Agent。写文档、写测试、清理代码，这些活边界清楚，适合交给并行的智能体，其中也包括整理 Douglas 过去 18 个月生成的软件。他说 Sweeper Agent 扩到了 10 个智能体；另一项工作里，他同时跑了大约 200 个 Daytona 沙箱。清理代码的产能上去了，可哪段 Rust 有问题，他还是得靠同事来认。

03

顺着 `pushback` 标签找到背后的决定

一个自己没经验去质疑的决定，Douglas 要怎么找到？Paper Console 把他和一位同事的会话汇进同一个存储。他打开了一个讨论 Paper Cloud 导出内存上限的会话，因为它带着 pushback 标签。这个标签说明有工程师反驳过智能体，原因就藏在前后的对话里。

Douglas 重点找的是 Matt 的反对意见。Matt 是团队里写 Rust 和 Go 的同事。下面两类反对，能看出 Matt 识别得出什么。

- API 结构。 Rust 代码能编译通过，API 的组织方式却可能正是团队早就否掉的那种。Matt 清楚这段代码该怎么和代码库其他部分配合。有之前的决定在，他就有理由去挑战一个看似合理的实现。 - 服务复用。 智能体缺了部分仓库上下文，可能会提议新建一个服务，而现有服务早就在干这件事。要发现重复，得先知道仓库里已经有什么。

换成 Douglas 自己操作，反对意见往往来得更晚。他通常接受生成的 Rust，直接开 pull request。自动审查打了五分满分，他就满意了，可审 PR 的工程师照样提出了反对。Matt 早先的对话提供了一条路：把这种审视提前。

04

让 Twin Review 审 PR 381

Console 记录下每个会话，Douglas 也能在命令行里查看细节。他把带标签的 trace 收成一个数据集。为了做 Twin Review，他挑出 Matt 反驳 Go 或 Rust 代码的例子，拿来做后训练。每段交流都把智能体的一个选择和它引来的反对意见对应起来。

到了真正审查改动时，Twin Review 需要什么？Douglas 在命令行工具里传入 PR 381，让它写出 Matt 会在 GitHub pull request 上留的那种评论。PR 提供要检查的代码；Matt 早先的反对意见则在训练阶段塑造了这个审查工具。至于换一批独立的 PR，它的判断有多大比例和 Matt 一致，这次演示没有回答。

GitHub 的审查讨论串本来也可以当样本来源。但 Douglas 团队里多数人已经改在命令行里做审查：工程师让智能体审一个改动，质疑它的回答，在框架里把问题解决掉。最后进共享仓库的代码，可能几乎没留下关于这个决定的说明。所以 Twin Review 的训练样本全部来自会话 trace。Douglas 用 Fireworks 做后训练；原型里有敏感数据，他没有公开。

05

Go 里的反复性失败长什么样

pushback 只是回看 trace 的理由之一。智能体一道歉，Douglas 就能顺着找到引发道歉的那段交流。黄金会话是有人特意标出来、值得研究的会话。回归问题则给了他一批智能体反复栽跟头的例子。

有一种失败反复出现：智能体自己重写一个现成的 Go 库。团队在测试用的 mock 库上就碰到过。如果你熟悉这个库，一看出智能体在造什么就能叫停。如果你从没用过，这个新实现看起来就像正常推进。这样的打断，正好给审查者一个具体的学习点。Douglas 还认为，这类例子不用训练模型，也能放进本地的审查框架里用。

06

把一次纠正变成可测试的 skill

Douglas 的第一个实验，是把 Paper 的 trace 变成 skill，其中一个能让智能体查阅历史会话记录。他本地装的 Tapes 把会话存在 PostgreSQL 里，所以在 Paper Console 还处于候补名单阶段时，他也能直接用自己的历史数据。整个团队有将近 80,000 个会话，可以拿来提炼 skill。

拿 Matt 对重复服务的反对来说。一个 skill 可以要求智能体：提议新服务之前，先找找有没有现成的。再配一个评测：给审查工具一个重复造服务的改动，看它能不能指出来。“遵守团队的 Rust 规范”这种宽泛目标，就这样变得具体到可以测试。以后团队也能拿同一个问题去考后训练过的模型。

07

调整模型的硬件成本

讲到规模较小的微调实验时，Douglas 把 adapter 比作书页边上的批注。书是预训练模型；adapter 加上一些学到的权重，让模型的行为更专门化。他用量化把训练塞进一块较小的 GPU，在一个 40 亿参数的模型上拿到了让他满意的结果。

直接偏好优化（DPO）用候选回答之间的偏好来引导模型，他在这上面的实验要多耗不少算力。Douglas 说，DPO 实验需要 700 亿参数以上的模型。他本地没有这样的硬件；当时能让他用上所需的大型 NVIDIA GPU 的，只有 Brev 一家。他提醒想走这条路的人：拿到算力可能要先预付一大笔钱。

Douglas 最后推荐的，是他一开始做的那个更便宜的实验：用你已经能采集到的会话历史，找一条能说明团队决定的反对意见，写一个可以测试的 skill。下次智能体又开始造 mock 库时，这个 skill 能不能像那位同事一样发现问题？

要点总结

  • 把专家纠正前后的交流留下来。pushback 标签帮你以后再找到它；trace 则把智能体提议的实现，和它违背的团队决定连在一起。
  • 去工程师真正审代码的地方找样本。在 Douglas 的团队里，反对意见留在命令行会话里，很少出现在 GitHub 讨论中。
  • 团队还没花算力做后训练，一个反复出现的错误就能先变成评测。给审查工具一个重造现有测试库的改动，看它能不能认出重复。

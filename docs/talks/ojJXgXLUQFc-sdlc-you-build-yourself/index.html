你自己构建的软件开发生命周期

Andy Wong、Andrei Bocan 和 Shane Wolf 讲解了 Atlassian 如何把 Jira 中的工作、组织上下文、仓库规范和自主开发连接起来——并在需求、证据和审查能力起关键作用的节点保留人的判断。

01

从代码两侧的工作入手

A coding agent can produce a change while leaving the surrounding work untouched: deciding what to build, finding the relevant decisions, reviewing the result and operating it afterward. Andy Wong opens this Atlassian workshop with the judgment that gains from additional coding tools are tapering, making the work “left and right of code” an attractive place to improve the software development life cycle. Joined by Andrei Bocan and Shane Wolf, he introduces a set of agents connected through organizational context.

The Jira coding agent makes a work item the starting point. Its proposed advantage is access to the material surrounding that item: Jira tickets, Confluence documents, email and Slack messages. That material supplies requirements and background for planning and implementation, while the cloud experience lets a developer interact with the resulting pull request inside Jira.

Agent choice and triggering are separate decisions. A team can assign a Jira item to its preferred agent, with Claude, Cursor and Codex named as options, or use Jira automation to start code generation when a condition is met. The workflow therefore begins before an editor session: a work-management event can initiate implementation.

02

审查需要需求、标准以及更少的低价值评论

AI Reviewer is introduced with three jobs: catch bugs, enforce standards and verify requirements. Reviewing against requirements requires knowing what the change was meant to accomplish, so the intended review reaches beyond the diff into Jira, Confluence, source control and Slack. Centralized standards add another input: a team defines its rules once and applies them across relevant repositories, with GitHub, GitLab and Bitbucket Cloud named as supported platforms.

More comments can make that review less useful. Atlassian describes training models to filter low-value or overly nitpicky comments before they reach a pull request. What does the presented comparison say about whether the remaining comments get resolved? Wong reports a resolution rate of around 40%, against a human baseline of 45%. The recording does not define the evaluation population or resolution metric precisely, so this is a reported comparison about review comments, rather than a general measure of bug-detection accuracy.

The opening overview extends the same context-driven approach to two other kinds of work:

- AutoDev: examine a Jira backlog, identify work suitable for autonomous execution, apply relevant standards and produce pull requests for review. Repository scope, credit limits and per-user work limits control how much it takes on; dashboards distinguish runs waiting for requirements from those waiting for review. - AI SRE: bring previous incidents, Jira and Confluence into incident diagnosis. The described Slack experience summarizes impact, proposes root-cause theories and suggests mitigation steps, including during the familiar 2:00 or 3:00 AM incident.

The shared dependency is the AI context engine: a way to retrieve relevant material scattered across repositories and documentation and make it available to agents. Semantic code search is part of that plan. Browser, IDE and CLI access are described as ways to bring these capabilities into existing work habits.

03

关联上下文而不必把一切都搬进单体仓库

The intended hands-on session runs into persistent Wi-Fi trouble, turning much of the workshop into questions about the machinery underneath the products. The first substantial question is what the context engine actually connects.

Graph databases connect information from Jira, Confluence and Bitbucket, along with third-party sources such as Notion and Slack. Some relationships are inferred from product use; others are explicit. A Jira ticket based on a Confluence specification is the concrete example: the ticket and its specification become connected pieces of context rather than independent search results.

Agentic search operates over those connections to bring relevant information into a coding session. A change in one part of an organization may depend on another team’s platform documentation or an initiative elsewhere. Retrieval needs to discover those dependencies even when the developer’s immediate task does not name them.

Code search also offers an alternative to consolidating repositories just to give agents more context. A monorepo can make related code available together, but it brings tooling costs and potential slowdowns. The proposed code context engine lets separate product repositories “feel like monorepos” by retrieving code across them when needed. Direct access to implementation also helps distinguish current behavior from documentation that captured an earlier state.

Freshness and correctness remain separate problems. In response to a question about saving context, the explanation favors retrieving information on the fly over keeping a task-level snapshot that can become stale. 06

AutoDev 必须匹配团队的审查能力

Bocan describes AutoDev’s initial release as a way to reclaim engineering capacity from suitable backlog work. It selects items the agents are confident they can handle and puts up pull requests for people to review. The human review checks both whether the work was worth doing and whether the implementation follows the team’s standards. AutoDev is presented here as an initial-release plan and product direction, rather than a full live demonstration.

Standards create two different workloads. Review can check incoming code against a new rule. Bringing existing code into compliance requires finding old violations and changing them progressively. A single pull request that rewrites half the codebase is difficult to approve; fifty small pull requests a day can overwhelm the team just as effectively. Bocan gives three or five assigned pull requests per person per week as examples of a manageable configuration, rather than a universal target.

The longer-term example is an organization upgrading Rails across a hypothetical ten thousand similar services. Much of the implementation work repeats, so a coordinating team could direct agents to produce changes across services and retain lessons from earlier migrations. Humans would coordinate the initiative while agents perform more of the repeated implementation. This is the stated vision for organizational steering, including memory across runs, rather than a demonstrated migration result.

Keeping autonomous work visible in Jira lets people intervene when AutoDev chooses the wrong item or assigns the wrong reviewer. Two independent limits then constrain the stream: work-in-progress limits protect the team from excessive review demand, while spending limits constrain cost per ticket or per week. Limiting token expenditure alone would still allow the system to create more review work than the team can absorb.

Underspecified tickets require a different intervention. A backlog item that says only “Do the thing” may represent valuable work, but it does not tell the agent what success means. AutoDev should ask a person whether the work is wanted and help obtain a usable specification before proceeding. After implementation, the next human decision is review: accept the change, request more work or discard it. Slack is the planned initial channel for reaching reviewers, because unattended review queues are where autonomous work can stall.

AI Planner addresses an earlier uncertainty: whether an idea is feasible in the current repository and what implementing it would require. The proposed input is an idea for a feature or a spike. Wolf makes the retrieval problem concrete with Atlassian’s roughly 15,000 repositories. Questions such as “Where do I implement this change?” and “What services are using this other service?” first require finding the relevant part of the organization’s code. The context engine narrows the search space to likely locations, digs into that code and adds information from the Teamwork Graph.

Current code and historical documentation answer different questions:

- Current code: what exists and how it behaves today. - Historical decisions: why an earlier implementation took its particular shape, including constraints and mistakes worth remembering.

An old document can be inaccurate as a description of today’s system while still explaining a decision that matters to the next change. Combining these sources gives planning more than a location to edit: it supplies reasons to preserve or revisit the existing design.

The integration is uneven at the time of the workshop. AI Planner and AutoDev use the context engine, while AI Reviewer uses it relatively little and is experimenting with deeper integration. Rovo Chat provides another entry point.

超越 API：AI 网页智能体如何自动化知识工作的“长尾”

一个浏览器智能体可以结合页面交互、结构化抽取和 API 调用，把零散的标签页变成表格数据、研究素材和行动。

01

当浏览器成为瓶颈

在网站上找到需要的信息之后，还剩多少活要干？总得有人把它复制进 Google Sheets 或 CRM，再和 API 拿到的数据核对一遍，然后到下一页再来一次。rtrvr.ai（读作 Retriever）在 Chrome 侧边栏里放了一个用自然语言驱动的智能体，把浏览器操作、结构化提取和 API 调用结合在一起。Arjun Chintapalli 和 Bhavani Kalisetty 演示了这几项能力怎么配合使用。

瓶颈不只是手工录入。抓取外包出去，会带来成本和可靠性问题。传统 RPA 机器人碰上网站改版，就可能失灵。另外，有些信息只能从网站上拿到，有些能通过 API 拿到，两边一直是割裂的。让智能体跟着日常浏览一起工作，就能把这些来源连起来，再把结果导进手头正在用的表格。

02

先检查页面状态，再行动

第一个任务很小，但带条件：在 LinkedIn 上找到 Latent Space 播客的主页并关注。如果账号已经关注了，就不用动。提交指令后，智能体填好搜索框，查看页面。它发现账号已经关注了这个主页，所以不用再点关注。指令描述的是想要达到的状态，也包括什么情况下页面保持原样。

下一个例子从交互转向结构化输出。请求里写明了要从页面上每篇文章提取哪些数据，导出操作再把结果写进 Google Sheets。这些能力可以组合：先在页面上完成任务，再提取操作后得到的数据。Chintapalli 估计，这次页面提取大概花了不到一美分。不过演示里没有实测成本，也没有给出通用的单页价格。

03

把工作分散到多个标签页

表格也可以当输入。给智能体一列 Google Sheet 里的 URL，它就能逐个打开页面、在上面操作并提取内容。在 arXiv 的例子里，请求要求从一次搜索结果的前五篇 PDF 中提取指定字段。智能体把工作拆成子任务，打开新标签页，各自独立、同时处理，最后把结果写进 Sheets。演讲者还提到，同样的“开标签页、做操作”模式也能用来投递 LinkedIn 职位。

做商品对比时，用户换了个方式：直接选中三个 Amazon 商品标签页。提示词留空，智能体会自己推断该比哪些字段，并汇总到表格里。如果想要的输出超出了这些推断出来的字段，明确写出指令仍然有用。演示中还额外提取了商品原图的 URL，这样图片也能和其他数据放在一起比较。

04

在抽取之前改变审阅顺序

Amazon 评论的例子把“先操作、再提取”的依赖关系讲得很具体。页面一开始显示的是热门评论，请求要的却是最新评论。如果直接提取当前内容，回答的就是另一个问题。流程如下：

1. 选中要处理的商品标签页。 2. 在每个标签页里，把评论下拉菜单从“热门评论”切换到“最新”。 3. 从更新后的页面中提取最新一条评论的详细信息。

智能体在后台对选中的各个标签页执行这些操作。Chintapalli 指给大家看页面上的下拉菜单正在切换，随后智能体报告最新评论已经提取完毕。页面状态本身就是提取任务的一部分，而不只是读一遍就完事的数据源。

05

把选定的文档作为研究上下文

下一个工作流从浏览器里已经打开的几份设计文档开始。为了给同事准备一份简要总结，用户选中这些文档，让智能体给出要点和摘要。选中哪些文档，智能体就读哪些；输入可以混合 Google Docs、PDF 和 Google Sheets。返回结果把各份文档分开讲，其中一份讲的是带记忆的 LLM。这是对一组选定资料做综合，而不是让它漫无目的地上网搜索。

06

让缺失的字段引导导航

公司调研把任务延伸到了最初选中的页面之外。Kalisetty 要求对比 Retriever、Bardeen 和 Browse AI 三家的战略、功能和定价。智能体先根据请求生成一份提取 schema，再从各公司首页出发，跳到定价页，补齐首页上没有的信息。可见，请求里列的字段既决定了输出长什么样，也决定了要去浏览哪些页面才能把它填满。

Kalisetty 把这定位为一种早期的深度调研能力，对标 OpenAI 的 Operator。演示中真正实用的一点，是用户能控制调研的输入：既可以选中自己有权限的文档，也可以指定智能体能访问哪些 URL 或网站。收集到的公司信息最后写进 Google Sheets。

07

从一个不合适的起始 URL 中恢复

股票调研的例子从 Google Sheet 里的几行数据开始。请求要求从 Yahoo Finance 获取市盈率（P/E）和过去两年的营收，再新增一个字段，用这些数值算出营收增长率。这里组合了三种操作：读取已有的股票记录，抓取更多财务数据，再用抓到的数字算出新值。

其中一个给定的 URL 指向公司官网，而不是 Yahoo Finance。智能体发现起始页面和要求的数据源对不上，就自己跳到 Yahoo Finance，继续提取并写入 Sheets。这次纠偏说明，任务描述可以纠正不合适的起始 URL。但它证明不了这些财务数据是否准确，也没有演示任何投资决策。

08

把电子表格的行变成 WhatsApp 消息

浏览器交互不一定以导出收尾，也可以接着驱动 API 操作。Retriever 的动态函数调用让用户自己提供工具信息，不必完全依赖厂商预先做好的那套固定连接器。宏观上的目标是对接任意第三方 API；这里的具体例子用的是一个配置好的 WhatsApp 消息工具。

选中的表格里有两位客户的电话号码。Kalisetty 让智能体给这两个号码发消息。智能体逐个识别号码，调用 WhatsApp 工具，然后报告消息已全部发出。Kalisetty 打开 WhatsApp 核对，指出收到了一条测试消息，时间戳是 2:32，和演示现场的当地时间一致。这条看得见的收件记录，能证明消息确实送到了屏幕上那个测试号码；这和智能体笼统报告“全部成功”是两回事。

09

生成数据的一种表示

从发消息的例子可以设想更多跨 Instagram、Facebook 和 WhatsApp 的社交沟通工作流，不过这些平台上的发送并没有演示。接下来演示的工具换了个方向：一个图表机器人。演讲者称它是 Retriever Agent Studio 里的迷你智能体，能拿现有数据按需生成分析图表。这样一来，同一个工作流既能收集结构化信息，也能产出给人看的图表。

10

在用户的会话中读取网页文本

谈到架构时，演讲者把两件事分开讲：智能体怎么观察页面，以及它的浏览器跑在哪里。Kalisetty 把 Retriever 基于文本的做法，和 Operator、Claude computer use 发布时基于截图的交互方式做了对比，还把 Google Mariner 归为两者混合。基于截图的方式，会在智能体操作或滚动时把页面当图像捕捉下来；Retriever 则直接把网页文本交给模型。演讲者认为这样幻觉更少、成本更低，但没有拿出对照实验来证明。

第二个区别在于浏览器会话本身：

| 部署方式 | 相关上下文 | 演讲中提到的基础设施问题 | |---|---|---| | 云端浏览器 | 独立会话看到的内容可能不一样 | 代理路由和 IP 基础设施 | | 本地扩展 | 用户现有的浏览器会话 | 直接用用户电脑上已有的浏览器 |

Kalisetty 谈到云端托管浏览器时提到了 Browserbase，认为维护所需的网络路由会增加开销。真正有参考价值的区分是会话上下文和部署开销；演讲并没有实际测算两种方式的成本差距。

扩展可以处理当前标签页和后台标签页，用的都是用户本来就能访问的内容。演讲者表示，Retriever 不要求用户交出密码，也不存储密码。需要登录或订阅才能看的内容，可以借助现有的已登录会话访问；但这不等于演示了能绕过所有付费墙或 Cloudflare 防护。反过来，云端智能体也不一定非得把密码暴露给模型：Operator 的文档就写明，登录时可以由用户手动接管，接管期间输入的信息不会被收集，也不会被截图。

11

用文本跨后台标签页工作

Chintapalli 把基于文本的观察方式和前面的多标签页演示联系起来。页面文本直接放进上下文，模型就能用这些内容，不需要给每个后台标签页截图。按他描述的实现，这些标签页不用在屏幕上渲染出来，智能体照样能在上面操作。这样既能并行处理互不相干的工作，也能综合多个标签页的上下文来决定下一步。

这是在单个本地浏览器里操作后台标签页的一个具体优势，并不意味着基于视觉的智能体就一律做不了并行。Operator 发布时的文档也提到，可以在不同对话里同时跑多个任务。架构上真正要问的是：系统怎么获取观察结果，怎么隔离并发任务。光靠视觉，并不会让并发变得不可能。

12

把重复性工作分解成更小的任务

产品主攻重复性的知识工作，而不是订机票、订餐厅这类消费级任务。演讲者把客户端的 Chrome 扩展当作一种手段：既能减少托管开销，又能借用户的浏览器访问本地网站或需要登录的网站。这是录像里展示的架构；如今的 Retriever 还提供云端执行和其他接入方式。

对应的可靠性策略是任务拆分。Retriever 不让一长串操作都挤在同一个标签页里跑，而是把子任务分派到新标签页。Chintapalli 认为这样能减少失败，避免错误层层累积，不过并没有基准测试证明失败率真的更低。在集成上，与之配套的扩展思路是让用户自己定义、配置和分享函数调用，以此扩充可用工具，不用厂商亲自开发每一个连接器。

13

在志愿者的浏览器中构建数据集

结尾的设想把数据提取扩展到个人工作流之外：搭建一个 AI 驱动的交换平台，让大家用各自的笔记本电脑在本地协作构建数据集。比如要汇总整个旧金山湾区各地方政府的活动信息，可能得访问成百上千个网站，集中采集的成本很高。Chintapalli 提议让志愿者通过各自的扩展贡献提取工作，一起分担这类难以汇总的数据集的构建工作。这个交换平台还只是长期目标，演讲中并没有演示已经上线的功能。

录像最后邀请观众到 rtrvr.ai 下载扩展，或扫描屏幕上的二维码。眼下的切入点，是一个在浏览器里陪用户干活的智能体；设想中的终点，是许许多多这样的浏览器一起协作采集数据。

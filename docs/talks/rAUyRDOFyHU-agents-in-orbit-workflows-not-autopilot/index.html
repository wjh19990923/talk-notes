轨道上的智能体：要工作流，不要自动驾驶

Eduardo Simon 和 Javier Casal 讲解了 Flywire 如何把模型判断放进经过审核的确定性工作流中——以及为什么执行限制、可复用的技能和人工审批与模型本身同样重要。

01

一个智能体平台必须适配这家支付公司

Flywire’s engineers were already building skills, MCP servers and an early code-review bot before a dedicated AI Platform Experience team existed. The demand was there; the missing piece was shared infrastructure that could turn those experiments into routine engineering work. In this recording, Eduardo Simon and Javier Casal explain how that infrastructure became Orbit.

The setting matters. Flywire processes high-value international payments and operates under PCI DSS and SOC 2 requirements. Sensitive customer and payment context cannot simply be handed to another service without governance. Around 400 engineers work across Java, Ruby, Go, Python, .NET and PHP, so an automation platform also has to accommodate several toolchains rather than assume one kind of repository.

Most applications already run on Victoria, Flywire’s internal platform as a service built on GitLab and AWS. Victoria supplies standardized builds and deployment practices. Reusing it made an internal platform attractive: execution could stay within existing controls, deployment followed a familiar path, and the team could avoid another vendor’s security-review process. The speakers also credit frontier models with reducing the effort of building the custom platform.

Orbit’s answer to a fast-changing tool ecosystem is to keep repetitive procedure in code and insert small LLM steps where judgment is needed. The team calls it a “toil killer.” Rather than ask an agent to discover the entire procedure on every run, a workflow supplies the procedure and reserves model calls for the parts that need interpretation.

02

代码审查给模型一份狭窄的工作

Every Orbit agent is defined in a single YAML file stored in a repository. Changes to that definition go through merge-request review like other code. That makes the workflow’s behavior something engineers can inspect before it runs, using a format and approval process they already know.

The code-review example shows where the model begins and ends. An engineer mentions the review bot on a merge request, triggering a webhook. Deterministic activities fetch the request’s metadata, classify its risk tier, load prior findings and clone the repository. Only after that preparation does the model read the code and return findings in a strict output schema. It cannot modify the files. A final deterministic activity posts the findings back to the merge request. The useful distinction to inspect in the workflow is which activities prepare or publish information and which activity receives permission to reason over it.

The YAML excerpt places one llm_session between deterministic repository preparation and finding storage/posting, and declares its output schema and read-only tools.

``yaml id: code-review-agent triggers: - source: gitlab_webhook # @bot_reviewer activities: - kind: gitlab_mr_info - kind: gitlab_classify_risk_tier - kind: code_review_load_prior_findings - kind: gitlab_clone - kind: llm_session # the only LLM step output_schema: ReviewOutput allowed_tools: [Read, Grep, Glob, Agent] - kind: store_findings - kind: gitlab_post_findings ``

This division removes several procedural choices from the model’s job. It does not have to decide how to retrieve the repository or how to publish a review; the workflow already does those things. Its contribution is the review itself, within a read-only step. “Workflows, not autopilot” describes that allocation of responsibility.

YAML also lets coding agents read, write and review workflow definitions. For corporate users who do not normally work in repositories, the team is considering a different authoring interface: dragging predefined activities into a workflow in Orbit’s UI. That interface is a proposal, while repository-based YAML is the established starting point.

03

不同的入口，同一个人工审查点

Orbit supports three ways to start work, each suited to a different relationship with the task:

- Direct invocation: Engineers and systems call an internal API, either directly or through the internal CLI. - Event-driven invocation: Webhooks from GitLab, Jira, Sentry and AWS start work when something happens, such as a new merge request or production error. - Scheduled invocation: Recurring jobs handle tasks such as daily translation syncs, feature-flag cleanup and knowledge-base refreshes.

An Orbit MCP server is being built to expose workflow invocation to other AI tools. The intended experience is to request an Orbit workflow from a Claude conversation in Slack. This would add another way to start an existing workflow; the reviewed workflow would still determine how the task runs.

The examples make the inputs and outputs concrete:

- Translations: Fetch new strings, translate them, update the files and notify teams with the updated documents. The automation covers the surrounding file and notification work as well as translation. - Production investigation: A Sentry webhook starts an investigator, which assesses the issue, posts its assessment in Slack and shares a merge request containing a fix in the same place. - Support routing: Ticket triage classifies new tickets and routes them to the appropriate engineering area. - Repository improvement: AI-readiness scorecards identify how prepared a repository is for AI-assisted development, and a fixer acts on the findings. - Ticket implementation: The Jira implementer takes a ticket and produces a merge request.

The largest benefit the team identifies is applying changes across many repositories: migrations, library updates and deprecations become bulk operations. That scale does not remove the approval step. The merge request remains the unit of work, and people still review and approve the proposed changes.

04

分离执行，再限制能运行多少

Orbit began with orchestration, the agent harness and the runtime environment in one AWS ECS Fargate container. As requirements grew, the team separated orchestration, agent execution and session state into distinct components. That separation lets the pieces scale independently and receive different resources. It also reduces failure coupling: an error in the orchestration side need not terminate the execution environment.

Fargate supplies elastic task execution, while Victoria makes deployment familiar. But a platform that can launch many agents also needs controls against accidental multiplication of work:

- Timeouts bound duration. Every agent stops after a configurable amount of time. - Rate limits bound incoming demand. Aggressive defaults protect against a broken API integration spawning thousands of agents and inflating the bill. - Locks suppress duplicate work. If a code review is already running for a task, the control plane drops a duplicate request rather than launching another review.

The original runtime has a practical limitation. Its lightweight, restricted container includes common language runtimes but deliberately omits package managers such as Bundler, Maven and Composer. A code-writing agent can therefore reach a point where it cannot easily build the project or run its unit tests. The Jira implementer exposes this gap: producing a change and verifying it require different capabilities.

The team now also uses managed microVM environments with a runtime chosen by project type, supplying each stack with its own toolchain. They describe those environments as able to pause and resume execution. Full sandboxing remains unfinished, however. Docker-in-Docker or multiple microVMs are possible directions for supporting more complex local environments, builds and verification across repositories.

05

逐步审查权限，跨环境复用技能

Orbit reuses the Claude Agent SDK for the harness inside LLM steps. Tool use, subagents and skills come from that existing implementation, leaving the platform team to concentrate on workflow behavior and access controls.

Each step’s YAML declares four kinds of access:

- Network: Which destinations the agent can reach. - Tools: Which operations it can call. - Skills: Which reusable instructions it can load. - MCP: Which servers it can use, including the specific tools allowed from each server.

The restrictions follow the task. Code review permits reading and searching, while excluding file edits and pushes. The Sentry investigator can query traces through an MCP server using a short list of read-only tools. Access is therefore part of the reviewed definition of an LLM step, rather than an implicit consequence of everything available in its environment.

Skills come from a central repository published internally as a Claude Code plugin marketplace. Orbit connects to that marketplace at build time. The same skill can run in an engineer’s local Claude Code session and inside an automated Orbit workflow, so a team can develop useful task knowledge before committing to background automation.

That leads to the adoption advice: “Start with the skill.” It is inexpensive to write and easy to revise while the team learns whether the task recurs often enough to automate. Once it does, the predictable parts move into code and the model handles the remaining judgment. Background execution then removes the need to keep a session open and guide it through every procedural step.

06

校验响应形状，再评估其质量

Strict JSON schemas connect model output to deterministic control flow. Subsequent branches, error handling and state transitions consume a defined response structure rather than depend on ad hoc string parsing. If a response fails schema validation, Orbit takes a targeted retry or fallback path before proceeding.

What happens when the model produces an unusable response? The branching relationship below separates the normal continuation from the validation-failure path. A valid structure makes the response usable by the workflow; it does not establish that the model’s judgment is correct. That second question requires evaluation.

The evaluation harness isolates individual LLM steps. Instead of repeatedly executing a whole synthetic workflow, it injects historical state and context into a particular node and evaluates that node’s output. Holding the input context fixed makes prompt changes and model changes easier to compare, while avoiding the expense and variability of rerunning every surrounding activity.

The production-entry standard is still modest. A new agent usually starts with what the team calls a “vibe check”: a few real cases that appear to behave as expected. Once deployed, every execution is traced end to end with OpenTelemetry, including activities, model calls and tool calls. Traces from real runs then become examples in a golden dataset versioned beside the code.

Those datasets run on demand. Teams adjust a prompt or change a model, rerun the dataset and compare results. Online evaluations are still being built. The intended destination is an evaluation workflow accessible through Orbit’s UI or MCP server, where teams can monitor production behavior and improve an agent without redeploying it. The distinction matters: tracing and replay datasets exist today; the integrated online evaluation experience is roadmap work.

Validation failure selects a targeted retry or fallback; it does not continue as an ordinary response. - LLM response — The model returns output for a workflow step. - Validate JSON schema — Check the response against the expected structure. - Deterministic continuation — Use structured output for subsequent branches and state transitions. - Retry or fallback — Take a targeted recovery path before proceeding. - LLM response → Validate JSON schema (Response to check) - Validate JSON schema → Deterministic continuation (Schema valid) - Validate JSON schema → Retry or fallback (Schema invalid)

07

大量运行衡量的是采用率，而不是答案的正确性

For the preceding 30 days, the team reports more than 9,700 code-review runs averaging under three minutes per merge request. Other results use different units: the audit fixer opened 159 merge requests for vulnerable dependencies, the AI-readiness fixer improved around 80 repositories, the Victoria linter fixer fixed 413 projects, and the merge-conflict resolver ran 921 times. Across the workflows, the reported total exceeds 11,000 executions with a 99% success rate. These figures describe activity, outputs and execution success; the talk does not define success precisely enough to treat 99% as a measure of answer correctness. The useful comparison is between the labeled measures, rather than treating every count as an equivalent completed fix.

Self-service expands who can build this automation. Standardized guardrails allow teams in SRE, security, IT and support to create custom workflow steps. The platform supplies common controls while task owners contribute the procedure and judgment their work requires.

Cost control also happens at the step level. Each LLM step declares its own model, so planning and implementation can use different models instead of assigning the most capable model to everything. A cost-aware router is planned to automate more of that selection. Meanwhile, separating engineering SDLC data, corporate operational data and sensitive payment-production data remains an ongoing responsibility, as does choosing high-impact work from the demand for new automation.

08

执行能力更强，但不交出控制权

The remaining platform work addresses several separate constraints:

- Complete sandboxing: Support complex builds, local environments and test suites across project types. - Resumable sessions: Carry complex, multistep tasks across interruptions or pauses. - Integrated evaluation: Let teams measure workflow quality within Orbit itself. - Model flexibility: Refactor orchestration to support different vendors and eventually route tasks to a cost-effective model automatically. - Harness flexibility: Avoid tying the platform permanently to one agent harness.

The closing advice keeps adoption concrete: pick a repetitive, well-defined task and prove it works before scaling it. Keep predictable operations in code, use the model where judgment adds value, and retain owners, limits and human merge-request review. Orbit’s expansion depends on those controls accompanying each new capability.

  • Orbit 让准备和发布变得确定，同时给代码审查模型一个只读、受 schema 约束的判断步骤。
  • 超时、速率限制和防重复任务锁分别应对不同的运营故障：运行时间失控、需求过多和重复工作。
  • 一个共享技能可以先在本地证明有用，再让它的周期性流程变成一个经过访问控制审查的后台工作流。
  • schema 校验支撑可靠的控制流；基于历史上下文的评估关注输出质量。仅凭执行成功并不能证明正确。

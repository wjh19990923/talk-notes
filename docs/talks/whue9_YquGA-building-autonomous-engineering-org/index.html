打造一个自主的工程组织

Block 的工程师早就在用 AI 了，但功能交付到客户手中的速度并没有变快。改变这一点，需要准备代码仓库、原生的委派方式、审查自动化，以及跨服务的共享上下文。

熟悉 Git 仓库、pull request、问题跟踪系统和编程智能体，有助于理解这些工作流上的变化。

01

采用率很高，交付却没有变快

一个工程组织大量使用 AI，交付速度却丝毫没有变快，这是怎么回事？在 Block，Angie Jones 要在 3,500 名工程师的规模上解决这个问题。Block 很早就开始做 goose。Jones 说，那时 LLM 还不支持工具调用。Block 还和 Anthropic 合作推出了第一版 Model Context Protocol，她把 goose 称作 MCP 的参考客户端实现。据 Jones 介绍，几个月后，约 90% 的工程师经常用 goose、Claude Code 这类工具生成代码。

可 CEO 认定工程部门根本没在用 AI，理由是交付没有变快。用量指标和 token 账单都显示工程师在用，可功能送到客户手里的时间一点没缩短。工具用起来了，交付却没有因此变快。

Jones 把 AI 赋能分成三个阶段：试验、采用、见效。大多数工程师还停留在 IDE 里用 AI 问问题、写样板代码。要再往前走，就得把智能体接进构建和发布流程，而不只是让写代码这一步更顺手。

02

从辅助到指挥工作

2025 年上半年，Jones 负责 Block 全公司 12,000 名员工的 AI 赋能，市场、设计、财务、法务都包括在内。她接到的下一个任务范围更窄，要求却更高：打造一个智能体化的工程组织。按她的定义，在这样的组织里，工程师主要靠智能体产出工程成果。工程师负责拆解问题、分派任务、审查结果、验证成果。指挥智能体会成为他们默认的工作方式。

为了把差距说清楚，Jones 设计了一个成熟度模型，衡量工程师和智能体之间的关系：怎么思考、怎么委派、怎么编排。2025 年第三季度她已经有了早期版本，后来参考 Steve Yegge 的 Welcome to Gas Town 重新梳理。下面六个阶段就出自 Jones 的模型。

| 阶段 | 关系 | 工程行为 | |---|---|---| | 0 | 未参与 | 工作流程中不用 AI | | 1 | 辅助 | 用自动补全，不用智能体模式 | | 2 | 对话 | 和智能体聊天，但不产出 PR | | 3 | 指挥 | 委派任务并审查产出 | | 4 | 并行 | 同时运行多个智能体 | | 5 | 自主 | 委派完整任务，无需人工引导就能拿到可发布的结果 |

一级级往上走，变的是由谁来推进任务：起初工程师只是接受辅助，接着委派边界清楚的工作，最终指挥智能体完成整项任务。

到 2025 年上半年结束时，大多数工程师处在第 1 到第 2 阶段之间。终点是第 5 阶段，但眼下的难题是让工程师信得过智能体，敢把可能变成 pull request 的活交给它。

03

给一个小组时间来建立共同的实践

指望每个工程师各自摸索出好用的智能体工作流，多半行不通。下一个模型或工具一发布，这些做法可能就过时了。工程师已经有了 AI 疲劳，管理层再一施压，有些人反而更抵触。Jones 想到了 1-9-90 参与法则：极少数人创造内容，另一小群人偶尔贡献，绝大多数人只消费前两类人的产出。她把这条法则当作推动采用的经验法则，并不是说 Block 员工实测就是这样分布。

放到工程团队里，创造者负责发现智能体模式和实用技巧；偶尔贡献的人也许会改改 AGENTS.md 文件；大多数工程师直接用现成的能力，不必额外花时间去开发。这就指向了另一种规模化思路：让少数专家的工作改善所有人的默认环境。

Jones 没有开放志愿报名，而是从关键团队里亲自挑了约 50 名 AI 先锋。候选人至少要拿出 30% 的时间做赋能，还得扛得住各种说不准的失败，比如工具拿来根本跑不起来。她花了一周和技术负责人、经理逐一沟通，找出能代表最重要代码仓库的工程师。

04

让仓库为委派做好准备

先锋们的第一个目标是第 3 阶段。2025 年 6 月前后，模型已经能写出一个功能，但写出来的代码常常不符合团队的约定和规范。质量时好时坏，工程师就不愿委派。先锋们开始往代码仓库里补充上下文和规则，让智能体看懂代码库、找得到路，并按规矩贡献代码。仓库本身就是分发渠道：指引写进仓库，每个贡献者都能受益，而不只是写下它的那位先锋。

这个计划覆盖 Square、Cash App、Afterpay 和 TIDAL，参与的工程师来自前端、后端、移动端、数据和基础设施。他们在大型遗留 monorepo、小型服务和移动应用上检验各种模式。针对 monorepo，JVM 开发者用上了熟悉的继承模式：共享的上下文和规则放在根目录，更具体的指引放在各个服务目录下。

这种安排可以用一个简单的仓库结构来表示：

``text repo/ ├── AGENTS.md └── services/ ├── payments/ │ └── AGENTS.md └── notifications/ └── AGENTS.md ``

根目录的文件放共享指引，各服务的文件补充本地约定。服务名只是示意，Jones 讲的模式是“根目录 + 服务层”这种分层结构。

先锋们还发现，Web 端的模式不一定搬得到移动端，Android 和 iOS 有时也得分开处理。每位先锋都为自己的仓库挑选行得通的方案。随后，仓库相似的团队逐渐收敛到一批好用的工具和模式。这样既沉淀出了通用组件，又不要求大家实现得一模一样。

仓库工具包包括：

- 上下文： 用 AGENTS.md 或 CLAUDE.md 介绍仓库、指导贡献。 - 规则： 给智能体的行为设护栏。 - 可复用工作流： 先是斜杠命令，后来是智能体 skills。 - AI 审查： 一个代码审查器，附带说明哪些事重要、该检查什么。 - 归属标注： 在 PR 上标明 AI 参与了哪些工作。

智能体已经开始写 PR，但会委派的基本还是先锋们。仓库准备好了，智能体能干的活变多了，可各团队还没把委派当成日常。

05

在工作原本到达的地方进行委派

就连先锋们也还得时刻盯着智能体。为了让委派更省心，也让计划之外的工程师用得上，团队把智能体接到了需求本来就会出现的地方：Jira 或 Linear、GitHub issues，以及 Slack 上的随口讨论。这三类入口，先锋们都做了接入。

从一次 Slack 上的 bug 讨论，可以看出工作流变成了什么样：

1. 一位工程师报告了一个产品 bug，问有没有人也遇到过。 2. 另一位工程师回复后，第三位工程师 @ 了 goose，让它去查。 3. goose 拉取仓库文件，确认了 bug，并在讨论串里给出三个方案，都附上了代码片段。 4. 工程师们一致选了方案一，让 goose 去实现。 5. goose 改完代码，回了一个 PR 链接。

据 Jones 介绍，这一轮从讨论、诊断、建 issue、达成一致，到修复以 PR 的形式交回来，前后大约五分钟。拍板的依然是人：goose 先给出几个备选方案，再由工程师决定实现哪一个。

06

把智能体带进冲刺

工程师还可以把 Linear 工单、Jira 工单和 GitHub issues 直接指派给智能体去实现。智能体成了冲刺执行的一部分。Jones 讲到，第一个试点团队两次把计划内的活提前干完，只好再拉新工单进来。经理和产品团队很喜欢这套流程；工程师也不必先学会先锋们摸索出的全部技巧，就能委派任务。准备好的仓库打下了基础，熟悉的工作平台则成了入口。

先锋计划启动三个月后，Jones 报告了以下变化：

| 指标 | 报告的变化 | |---|---| | AI 编写的代码 | 增长 69% | | 自报节省的时间 | 增长 37% | | 自动化 PR | 增至 21 倍 |

演讲没有给出基线定义、绝对数量或统计方法。这些都是计划自己报告的结果，其中节省时间一项还是工程师自报的；它们也没有直接衡量最初那个问题：功能从开发到交付客户要多久。

07

并行的智能体暴露出审查瓶颈

工程师能稳定地委派之后，迈向第 4 阶段，也就是让多个智能体并行工作，就相对容易了。可产出一多，压力就转到了下游。Jones 说，工程师的 PR 产出翻了三四倍，改动却都在排队等审查。其实早在智能体把量推上去之前，人工审查就已经忙不过来了。

计划早期，AI 审查效果差，工程师用得很恼火，所以只是可选项。后来仓库准备到位、模型更强、工具更好，AI 审查才真正派上用场。Block 在所有仓库启用了 Codex，还加了一个自动修复循环：

1. Codex 审查 PR，找出问题。 2. 另一个智能体修复这些问题。 3. 这个智能体把修改提交到 PR。 4. 人工审查者拿到一份更干净的改动来检查。

负责修复的那个智能体是 Block 自己搭的流程，光接入 Codex 的审查集成并不会自带这个能力。有了这个循环，大家对机器人 PR 质量粗糙的抱怨少了。不过 Jones 也说，审查跟不上的问题仍未彻底解决。

08

给每个智能体一个隔离的工作区

并行执行还带来了本地基础设施的问题。智能体干活时互相干扰，工程师的笔记本内存和 CPU 也吃紧。Block 把这些工作搬到了专用的云端工作空间，每个智能体都跑在独立隔离的环境里。这样并发任务互不干扰，工程师在哪儿都能运行智能体，不用让一台笔记本扛下全部算力。

Jones 说，工程师一次会跑四五个智能体，并发数还在往上涨。一个小团队（其中有不少先锋）开始打造 Builder Bot，这是一个内部编排器，专门协调这些工作。隔离执行让并发变得可行；编排要解决的，是怎么指挥越来越多的智能体。

09

用公司的世界模型跨仓库做规划

如果智能体不知道服务在哪里、谁依赖谁，编排器就没法协调完整的工程任务。Jones 说，Block 从 25,000 个仓库组成的代码库里构建出一个公司世界模型：它以机器可读的形式描述各项服务及其相互关系。先锋们写进单个仓库的只是本地指引，世界模型则把上下文扩展到了整个公司。

有了世界模型，编排器和它委派出去的智能体都能按需检索上下文。多个智能体可以同时探索系统的不同部分，摸清各自负责的区域，再把发现汇报回来。编排器把这些发现整合成一份横跨多个代码库的计划。跨产品线的业务尤其需要这一点：这类功能牵涉多个仓库，单看一个仓库里的改动是理解不了的。

Jones 认为，这就到了第 5 阶段：工程师可以委派完整任务，不用一步步引导智能体，就能拿到可发布的结果。这个入口还把工作流开放给了工程部门以外的人。公司里任何人都能在 Slack 里 @ Builder Bot，请它修 bug 或做新功能，不需要会用 GitHub。这里说的成果是可发布的工作，并不是一套自动部署到生产环境的成熟流程。然而，看似非凡的成功之后，一个难得多的问题随之而来。

10

组织正在变成什么？

演讲结尾转到了裁员。Jones 说，这一轮裁员感觉不一样，她问自己是否要负责任：她帮员工做出了非凡的成绩，这最终是否促成了他们被裁？她把这当作一个令人痛苦的问题提出来，并没有证明先锋计划和裁员之间有因果关系。

就在前一天，她还为员工的成就感到骄傲，为自己打造出一个自主的工程组织而自豪。如今，这份自豪旁边多了一层迷茫：这一切到底为了什么？演讲没有再给出新的成熟度阶段，而是用几个问题收尾：“我们在做什么？我们要去往哪里？”最后一句是：“我们确定那就是我们想去的地方吗？”

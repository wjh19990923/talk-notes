超越原型：用 AI 编写高质量代码

交付智能体生成的代码，需要关于其行为的证据。Sculptor 探索了即时检查、明确的规格说明和更安全的测试，让这些证据成为开发过程的一部分。

熟悉代码 diff、自动化测试和编程智能体会有帮助；Python 示例使用了集合和 dataclass。

01

生成的代码只是开始

你给编码智能体布置一个任务，它写出一大堆代码，原型看上去已经完工。可这些代码要并入一个更大、更成熟的代码库，还差什么？Imbue 的 CTO Josh Albrecht 正是从这个落差出发，推出了实验性的编码智能体环境 Sculptor。本次录像展示的是研究预览版，功能仍可能调整。

智能体可以改进的地方很多：更大的上下文窗口、更低的成本、更快的响应、更可靠的输出解析。Albrecht 的建议是，别把力气花在这些地方，而是集中解决开发者所在领域特有的问题。他预计，大约三到二十四个月内，上游模型和智能体的进步会解决许多通用限制。这是对工程投入方向的判断，就像你会直接选用现成的数据库，而不是自己造一个。真正有长期价值的，是那些对你的产品和组织特别重要的部分。

02

这个 diff 有什么问题？

智能体报告说它加了 59 行代码。这能告诉你改了多少，却几乎说明不了改得好不好。你可以自己逐行检查，也可以直接合并，然后祈祷别出事。Sculptor 探索的是第三条路：让另一个 AI 系统检查这次改动，找出具体问题，比如竞态条件或泄露的 API key。生成代码和建立对代码的信任，是两件不同的事。 图中那个 Slack 数据提取的改动正好说明缺了什么证据：diff 摘要不等于质量评估。

这里对质量的定义围绕缺陷展开：有多少问题，修复要花多久，某种技术能抓到多少。这样一来，反馈的时机就很关键。Sculptor 的定位在编辑循环内部，而不是 PR 审查工具。智能体一生成代码，或者开发者一改动某行，环境就应该立刻指出问题，趁相关上下文还在。反馈越及时，开发者和智能体纠正起来都越容易。

这个循环的预防环节从四项实践开始：先弄清已经有什么，先规划再实现，写规格说明，执行严格的风格指南。每一项都让智能体在动手改代码之前，拿到一个定义更清楚的问题。

03

先调研，再把规划与实现分开

让智能体实现某个功能之前，先问问：哪些现有技术已经解决了这个问题？其他开发者是怎么处理类似工作的？Sculptor 把提问和调研当作开发的一部分，这样在白白重复造轮子之前，就能先发现现成的方案。

接下来的 Scrabble 求解器演示，把“决定做什么”和“写代码”拆成了两步：

1. 把求解器任务交给智能体，系统提示词要求它先出计划，禁止生成代码。 2. 让它产出计划。 3. 修改系统提示词，允许它动手实现。 4. 扩展工作流，在代码生成之后加一个检查阶段。

关键的控制手段，是能在不同阶段之间修改智能体的运行指令。Albrecht 认为，直接改系统提示词，比在对话里追加一句要求的引导力度更强。定制智能体可以让这套流程反复复用：先规划，再实现，然后跑检查。

04

让项目意图明确化

规格说明和文档成本很高，因为总得有人不断让它们和实现保持同步。但智能体需要这些文档提供的上下文。决策可能是在某封邮件或某段 Slack 对话里做出的，智能体未必看得到；就算看得到，也未必能推断出这个决策对代码意味着什么。把意图写下来，它就成了开发的一项输入。

Sculptor 想办法减轻维护负担：它能检测代码、文档和 docstring 之间的偏差，并帮忙修复不一致的地方。它还能标出相互冲突的需求。这是两种不同的检查：一种看实现是否符合描述；另一种在动手实现之前，看描述本身是否自洽。

严格的风格指南提供的是另一种上下文：团队希望软件怎么构建。演示中，Sculptor 建议把一个类改成不可变的。这体现了 Imbue 偏爱函数式、不可变代码，好避开共享可变状态引发的一整类错误。这些规范对人类队友和智能体同样适用。另一份专门针对 AI 智能体常见错误的风格指南，当时还在编写中。

05

在一个不完美的仓库中发现新问题

预防不可能消灭所有错误。下一层结合了三种检测手段：自动化分析、测试和 LLM 检查。演讲提到的 Python 工具有 Ruff、mypy、Pylint 和 Pyre。它们统称 linter 和静态类型检查器，各管一摊、互为补充。零碎的诊断提示会给开发者添不少琐碎活，但也给了智能体具体的修复目标。Sculptor 把检测和自动修复串起来，开发者不必亲手处理每一处小违规。

成熟的仓库里可能早就积累了大量诊断问题。如果要求智能体把整个仓库清理干净，就会把手头的任务和无关的清理工作搅在一起。Sculptor 的做法是：记下智能体开始前已有哪些问题，再和结束后的问题对比。眼下的要求是不引入新错误。 已有的技术债不必挡住这一步改进。

比如，可以在 Python 里用归一化后的诊断标识来表达这种对比：

```python from dataclasses import dataclass

@dataclass(frozen=True) class Diagnostic: path: str symbol: str rule: str

before = { Diagnostic("legacy.py", "load_config", "unused-import"), } after = { Diagnostic("legacy.py", "load_config", "unused-import"), Diagnostic("solver.py", "solve", "undefined-name"), }

introduced = after - before resolved = before - after

assert introduced == { Diagnostic("solver.py", "solve", "undefined-name"), } assert resolved == set() ```

旧的 legacy.py 问题保持原样，新出现的 solver.py 问题则成为修复目标。真正接入时，诊断匹配要经得起日常编辑：不能仅仅因为行号挪了位置，就把旧问题当成新问题。

06

用生成的测试保护行为

测试生成改变了保住已有行为的成本账。过去，实现跑通之后，还得花大力气编写和维护测试。智能体把初次编写的成本降了下来。对于已经认定正确的代码，Albrecht 建议先生成测试，丢掉失败的，留下通过的。这样能把已被接受的行为固定下来，但并不能独立证明实现是正确的。

智能体能快速做大范围修改，保留这些测试的理由就更充分了。回归测试集表达的是：哪些行为你不希望智能体在不知不觉中改掉。Albrecht 借 Google 的一句测试口号来说明：重要的行为就该有测试，因为你对今天这份实现再有信心，也挡不住明天的修改。

07

在搜索失败之前先隔离副作用

好测试的前提，是代码执行起来既方便又安全。把大部分逻辑写成没有副作用的函数式变换，把会碰外部系统的操作隔离出来。Albrecht 举了个反面例子：一个能访问真实 Gmail 账户的测试，只要出一次错，就可能删掉真实邮件。把决策逻辑和外部动作分开，智能体就能放手探索逻辑，不必每做一次试验都把真实账户搭进去。

不同的测试各有用途：

| 测试类型 | 目的 | 建议侧重 | | --- | --- | --- | | 正常路径 | 展示预期的运行方式 | 少量有代表性的用例 | | 异常路径 | 发现 bug 和反常行为 | 广泛探索各种输入 |

对函数式代码，Albrecht 建议生成成百上千个候选输入，逐个运行，再让 LLM 判断哪些输出看着不对劲。不对劲的结果只是一条值得追查的线索，本身不算证据。一旦确认是 bug，这个输入就成了一个具体、可复现的测试用例。

08

保留那些行为重要的测试

生成测试变便宜了，哪些单元测试值得长期维护也要重新掂量。生成的测试集可能固化了一些团队根本不在乎的附带行为。Albrecht 建议想一想：这些测试是直接丢掉、以后再重新生成，还是合并成一套更好维护的测试集。如果测试死守过时的行为，智能体在奉命修改这些行为时就可能被搞糊涂。这里要分清长期的回归保护和一次性的探索：你在乎的契约要保住，其余的要有意识地筛选整理。

09

测试用户能做什么

集成测试把关注点从单个函数转到用户看得见的行为上。比如购物车的测试计划可以写明：点击添加某件商品后，它会出现在购物车里。与之配套的另一条计划是：移除这件商品后，它会从购物车消失。先写好这些计划，智能体就有了明确的行为目标，可以据此写出测试。开发者只需围绕产品交互来思考，不必把测试的每个实现细节都交代清楚。

测试通过只是证据的一部分。Claude Code 写完一处改动，你还得问：这处改动有多大比例被测到了？在 Albrecht 设想的合并决策里，100% 测试覆盖率、测试全部通过，再加上审查认为测试写得合理，比单看行数摘要更让人放心。这不是 Sculptor 的实测结果，也不能保证正确：覆盖率只记录代码有没有被执行，断言有没有用、有没有漏掉边界情况，仍需仔细把关。

最后，尽量让测试能在沙箱里运行，并且不依赖密钥。隔离能降低测试意外波及外部的风险，也能避开那些让测试时好时坏的依赖。智能体驱动的修复需要反复跑测试，隔离也让这件事更可行。

10

检查意图、架构和缺失的需求

第三种检测手段，是向 LLM 提一些常规诊断覆盖不到的问题：

- 改动审查： 当前未提交的改动里，或者分支的其他地方，有没有问题？ - 意图： 要做的这个任务合理吗？ - 设计约束： 实现有没有违反风格指南或架构文档？ - 规格完整性： 有没有漏掉必要细节、没实现的需求，或者测试不充分的行为？

这些检查拿代码去对照项目想表达的意图，而不只是语言本身的规则。Sculptor 在扩展性上的目标，是让团队加入自己的检查，持续审视代码库特有的做法。

11

先把失败说清楚，再安全地尝试修复

问题一旦被精确定位，修起来就容易多了。Albrecht 在这一阶段着墨不多，因为据他的经验，编码智能体只要弄明白哪里出了错，往往就能修好。一个具体的缺陷给了它们明确的靶子，而不是一句“把代码改好点”这种漫无边际的指令。

反复尝试是一种修复策略；Albrecht 甚至建议换个智能体试上一百次。他没有给出这个建议的实测成功率。支撑这种做法的机制是沙箱：智能体彼此安全隔离，就能在成本允许的范围内并行尝试修复，只要有一个成功，就能拿来当解决方案。这样一来，清晰的失败检测就有了双重价值：先用来发现问题，再用来判断某次修复到底有没有解决问题。

12

把循环扩展到代码生成之外

同样的思路可以延伸到实现和部署之后。调试、日志、tracing 和性能剖析，都是专用工具能派上用场的地方。自动化 QA 智能体可以浏览网站，检查用户能否完成预期任务。还有工具能根据视觉设计稿生成代码，更好的上下文搜索则能同时服务开发者和他们的智能体。

更强的基础模型是这幅图景的一部分，专用开发者工具之间的集成也是。Albrecht 在结尾邀请做这些相邻能力的团队与 Sculptor 集成，并预计接下来一两年里，会有更多这类能力变得可用。他设想的开发环境把这些能力串进整个工作流：发现该做什么、检查改了什么、修复失败，以及观察软件部署后的实际表现。

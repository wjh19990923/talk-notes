你的旧提示词正在让 Claude 变差

在一个约 50 张工单的客服基准上，Anthropic 的 Lance Martin 展示了如何通过联合调整模型、effort（推理力度）和提示词，在提升得分的同时把成本降低 90%。他还展示了 Claude 如何改进一个最初只得 66% 分的 API 技能，以及长时间运行的智能体如何从沙箱故障中恢复。

01

应用可能处在成本–质量前沿之内

在为更强的模型付费、或为了省钱而接受更低的分数之前，Lance Martin 会先问：这个应用在它自己的评测上处于什么位置？设想横轴是成本、纵轴是质量。对于给定任务，最优的可选方案会连成一条帕累托前沿。在前沿上的任意一点，想改善一项指标就必须在另一项上有所让步。Martin 勾勒了一组选择：Fable 位于昂贵、高性能的一端，其后依次是 Opus、Sonnet 和 Haiku。

单看模型名称，工程师几乎无法判断一个应用是否已经到达这条曲线。智能体可能在反复花钱处理完全相同的指令；它的提示词也可能让 Claude 把 token 花在一套对得出正确答案毫无帮助的验证流程上。存在这两类问题之一的应用，都有在图上向左移动的空间；而指令含混的应用，或许还能同时向上移动。Martin 是 Anthropic 的技术团队成员，他见过不少客户仅靠小小的配置调整就同时拿到这两种收益。他的第一个例子，涉及一段常常在多次模型升级后仍原封不动保留下来的配置。

02

审查那些为旧模型写的指令

提示词会像代码一样积累技术债。几代模型之前，工程师习惯让模型“一步一步思考”，给它一块草稿区，并规定如何用这块空间推理。他们会加上“仔细检查你的答案”之类的验证指令让模型复查，或者加上“尽可能做到详尽”这样的通用增强语。每一项干预都针对某种可识别的行为；但叠加起来，它们就可能变成强加在每个请求上的固定流程，不管这个请求难不难。

按 Martin 的经验，前沿 Claude 模型已经能自己决定何时推理，也会自然地检查自己的工作。因此，一条继承下来的“务必详尽”的要求，可能会在模型第一次回答本已足够好的情况下，仍然改变它所做的工作量。相互矛盾的规则则有另一种影响：指令遵循能力较弱的模型可能会悄悄忽略其中一条，给出的答案让提示词看起来还能用；而指令遵循能力更强的模型会努力同时满足两条。升级只是暴露了一个早就存在的矛盾。

Martin 介绍了在 Claude Code 中进行提示词审查的两条路径：针对 Claude Code 自身的配置（包括其提示词和技能），使用 checkup 技能的提示词审查；针对调用 Anthropic API 的应用代码，使用内置 Claude API 技能的提示词审查。两者最终执行的是同一套审查，区别只在于工程师在哪里工作。审查可以从工作目录出发，检查技能、工具和提示词中是否存在这些模式并将其删除。如果应用提示词看起来很干净、但某个工具的说明又把同样的验证仪式带了回来，这个检查范围就很重要。

03

把模型升级带来的收益与提示词修改带来的收益分开

Martin 构建了一个约 50 张工单的合成客服评测，并模拟了从 Opus 4.8 迁移到 Opus 5.5 的过程。他逐一引入各种提示词反模式并测量结果，对比中的中间点是这些实验的平均值。这样就能针对同一批工单提出两个问题：在保留继承下来的旧习惯时，新模型表现如何？审查把它们删掉之后，又有什么变化？

仅仅迁移，就让这个点向左并略微向上移动：即便带着那些多余的指令，Opus 5.5 也更便宜、得分略高。迁移后再运行提示词审查，成本进一步下降，得分再次提高。Martin 把 token 的节省归因于删除了那些诱使 Opus 5.5 做过多工作的增强语和验证仪式；而理顺那些会让更强模型困惑的指令，也让它更有机会答对。

对于想复现这个对比的工程师来说，中间那次测量值得保留。如果一次前后对比同时换了模型又清理了提示词，就只能用一个结果去回答两个决策。保持工单集不变，先在新模型上测量继承来的提示词，就能看出应用在升级之后还留下了多少收益没拿到。Martin 在这里报告的是两项收益的方向，他后面给出的百分比节省来自另外的实验。

04

按各部分保持不变的时长来排列智能体的上下文

设想智能体会话中相邻的两次请求。在这两次请求之间，Claude 可能只调用了一次工具。新增的信息很少，但下一次请求携带的上下文与上一次大部分相同。命中提示词缓存，就能让应用以更低的成本、更短的延迟复用这部分工作。Martin 说缓存读取的价格大约是基础 token 价格的十分之一，但也提醒价格因模型而异。在多轮对话中，重复输入里真正命中缓存的比例，关系到整个会话的经济性。

缓存要求严格的前缀匹配。提示词靠前的位置只要有一个字节变了，匹配就在那里断开；变化之后哪怕还有成千上万个相同的 token，也无法延长匹配的前缀。因此，工程师可能发出两个信息几乎完全相同的请求，却几乎得不到复用。检查哪些内容在重复只完成了一半诊断；这些内容在拼装好的请求中所处的位置，决定了缓存能识别多少。

Martin 把输入分为四层：跨会话共享的系统指令和工具定义放在最前面；接着是项目资料，例如 CLAUDE.md 和项目记忆；然后是会话状态；消息则随着每一轮对话在末尾不断累积。切换项目时，共享的指令和工具仍然可以命中；在同一项目内，新会话还能复用项目资料；而追加下一条消息，则让现有对话有机会一直匹配到上一轮为止。

Claude Console 会展示应用的提示词缓存命中率。Claude Code 团队密切关注这个数字，Martin 也建议用 API 构建应用的人去看看它。Claude Code 中的一个诊断工具可以检查 API 项目，找出其提示词构造在哪里破坏了复用，并给出更好的排列顺序；它还会检查提示词和 effort 设置。对缓存排查来说，最重要的产出是一个具体的改进机会——把会变化的内容移到可复用前缀之后——以及随后能证明改动是否奏效的命中率。

05

默认的基准测试框架白白浪费了高达 72% 的缓存节省

Martin 和 Anthropic 应用 AI 团队的同事用这个诊断工具检查了几个内部基准，使用的是发出模型请求的默认测试框架。其中一些框架对提示词缓存的利用很差。团队发现了最多可降低 72% 成本的机会，而测得的性能没有实质变化。这个结果的上限属于那几个特定框架；对于已经能获得很长前缀匹配的应用，起点就不同了。

这个实验分离出的是与客服工单提示词审查不同的一项开销。删除一条验证指令，会改变 Claude 决定去做的工作，也可能影响它的答案；而更好地利用缓存，针对的是处理那些智能体本来就会再次收到的内容所付出的代价。这就解释了为什么基准得分能保持不变，而成本却大幅变化。这也说明，在有人把一次昂贵的基准运行解读为“模型本身太贵”之前，默认测试框架值得先检查一遍。

06

先确认更高的评测分数是可以达到的

Martin 的下一步依赖于 Claude 的自我纠错能力。有了评测，Claude 就能检查失败案例、修改应用的某个部分，然后再试一次。Martin 把这个循环称为爬山优化（hill climbing）。在让它为一次次尝试花费 token 之前，他会先确认这个评测是否真的给了它一座有意义的“山”可爬。他的诊断图把每次尝试的 token 数（衡量模型思考了多少）与最终得分对应起来，不同曲线分别代表前沿、中型和小型模型——在他的例子里大致对应 Opus、Sonnet 和 Haiku。

他关注四个特性。第一，换成能力更强的模型，得分通常应该提高。第二，在同一模型内允许更多思考，表现通常应该更好。第三，最强的模型仍应有一些可解决的失败案例，为更好的配置留出提升空间。第四，在相同条件下重复运行，得分应该相近。如果同一配置本来就经常出现那么大的波动，那么两次相邻运行之间的大差距就说明不了什么。

检查提升空间需要阅读真实案例。一个得分 80% 的评测看起来还有 20 个百分点可拿；但如果剩下的题目本身含义模糊，模型可以一直给出合理的答案却拿不到分。即使是被广泛使用的评测，也可能包含足够多这样的题目，以至于实际上已经饱和。一个自主运行的优化器可能会烧掉大量预算，去寻找一个能夺回这些分数的提示词，而评测根本没有给它任何可靠的得分途径。

Claude API 技能中的 build-eval 工作流，从一个问题、工程师想要测量的目标以及原始数据（例如团队现有追踪系统中的 trace）出发。该技能会分析数据、构建评测，并与工程师一起审阅用例和评分标准。在问答环节，Martin 介绍了他提议的一项改动：在 Claude 把它标记出来的原始 trace 变成评测用例之前，先让工程师检查一遍。

07

让测试用例远离 Claude 的修改循环

一旦评测在不同模型、不同思考预算和重复运行下都表现合理，Claude 就可以开始自主提出修改。风险在于，它可能学会的是在这一组特定样例上拿分的技巧。假设某个基准任务需要光学字符识别（OCR）：被允许修改测试框架的优化器可能会加一个 OCR 工具，从而解出这道题。如果生产环境的用户从不提交这类问题，那么这个新工具只是提高了基准分数，对用户毫无帮助。提示词也可以更隐蔽地获得同样的虚假收益——比如学会样例中特有的措辞。

Claude API 技能的 hill-climb 工作流会把评测拆分为训练集和测试集。Claude 检查训练集上的失败案例，并据此决定改什么；运行器每一轮都会在两个集合上测量表现，而测试样例始终不进入 Claude 的思考过程。这种分离让工程师可以针对同一次修改观察两个分数：如果训练集表现持续上升而测试集分数原地不动，系统就得到了一个早期信号——Claude 可能在拟合训练用例特有的细节。

这种拆分只能回答一个有限的问题：它能显示某个修改是否能迁移到从同一评测中抽取的其他样例上。至于它能否预测生产环境中的表现，仍然取决于原始样例是如何挑选的。一个满是罕见请求的基准，拆出来的训练集和测试集会带着同样的偏差。因此 Martin 会让工程师持续参与，审查爬山优化器改了什么。对于那个新加的 OCR 工具，该问的问题是：哪些真实用户需要它？即便基准会奖励这项添加。

08

给 Claude 一个它可以修改的 API 技能，以及它必须对齐的文档

Martin 在 Claude API 技能本身上测试了这个方法。这个技能为 Claude Code 提供关于 Anthropic SDK 和 API 的指导，因此它的回答必须以 Anthropic 的文档为依据。他根据这些文档编写评测题目，对现有技能进行测试，结果得分 66%。这既给了他一个需要调查的具体失败，也给了他一个范围明确的修改对象：被评测的模型读取的正是优化器被允许修改其文本的那个技能。

随后，他让 Claude Code 可以访问技能文本和底层文档。每一轮中，Claude 都可以检查一个失败案例、查阅原始资料、找出技能在哪里错误描述了文档中的行为，并在重试之前修改其指导内容。文档充当了一个独立于技能当前措辞的参照。因此，每次修改都可以从两方面评估：检查它是否忠实于原始资料，以及测量使用修改后技能的模型是否更好地回答了问题。

Martin 报告说，得分从 66% 有了大幅提升，但没有给出最终分数。他特别强调了任务与可编辑材料之间的契合：评测问的是 API 行为，文档提供了这些行为，而技能正是负责把这些行为传达给 Claude 的那段文本。从一次修改到一个可观察的答案，路径如此之短，使得反复进行自主实验变得可行。他发现提示词和技能尤其适合这种处理方式。

09

在质量底线之下，联合搜索模型、effort 和提示词

同一个运行器也可以针对不同的目标进行优化。告诉爬山优化器去降低成本，它就会寻找一个成本更低、同时表现至少不低于基线的配置。它可以调整三样东西：选择模型，决定由哪个 Claude 来干活；调整 effort，决定模型投入多少推理；修改提示词，改变它解题时所遵循的指令。评测分数为搜索提供了质量底线，而测得的成本则用来区分那些达到底线的配置。

在合成客服基准上，Martin 的起点是高 effort 的 Opus 4.8 加上基线提示词。爬山优化器先换成了低 effort 的 Opus 5：表现大幅跃升，成本略有下降。接着它又试了另一个低 effort 的模型：这一轮带来了大得多的成本降幅，但也让上一轮的部分性能收益回吐。随后 Claude 修改了提示词，把表现拉了回来。最终配置的成本比初始配置低 90%，得分也更高。

这些中间结果解释了为什么 Martin 允许三个控制项都进入搜索。如果在第一次换模型时就停下，只能拿到质量提升和很小的节省；如果仅凭下一个候选相对上一轮高分的回落来评判它，就会错过一个成本低得多、而提示词仍有改进余地的配置。成本目标的参照点是最初的质量底线，运行器可以拿每一个后续选择的效果与它对比。

成本优化还能让一个已饱和的评测继续发挥作用。即便质量已无法进一步提升，这组用例仍可以检验更便宜的配置能否保住分数。Martin 多次看到，低 effort 的强模型解决一个问题所用的 token，比高 effort 的弱模型还少。这样一来，更高的单 token 价格反而可能换来更低的单任务价格。爬山优化器会尝试这种可能性，并在实际工作负载上测量它。90% 这个数字描述的是整个客服基准运行的结果，包括后来那次提示词修改。

10

通宵运行的智能体需要一份能挺过沙箱故障的历史记录

Martin 的话题从单次尝试的经济性，转向智能体能承担的工作时长。他介绍了 METR 的图表：横轴是时间，纵轴是同一任务人类需要花费的时间。他把 Claude Opus 3 放在大约相当于人类四分钟工作量的位置，那是他与自动补全和聊天联系在一起的能力范围。他说，到 2025 年，随着 Claude Code 流行起来，模型已能处理一两个小时量级的任务。他认为智能体正在走向相当于人类一两天工作量的任务，同时也提醒这可能已超出这些图表能测量的范围。

这种前景改变了一个好用的框架必须扛住什么。设想你晚上启动一个智能体，结果它的沙箱在半夜挂掉了。如果它的会话日志只存在沙箱里，那么打断执行的同一次故障，也会带走恢复所需的历史。Claude Managed Agents 把指挥工作的框架（Martin 称之为“大脑”）与它写代码、执行操作的沙箱（“双手”）分离开来；第三个组件——会话日志——拥有独立于两者的生命周期。

这份日志是只追加、可恢复的对象。沙箱挂了，系统可以启动一个替代品；框架挂了，编排器可以拉起另一个框架。无论哪种情况，会话历史都会保留下来，为恢复提供依据。Martin 的例子讲的就是如何依靠这份记录恢复。这种设计把“发生了什么”的证据，放在了最直接参与执行工作的两个组件之外。

凭据有它自己的边界。Managed Agents 把密钥保存在与工具关联的保险库（vault）中。Claude 可以引用某个 API 密钥或其他密钥，而它的值始终留在保险库里，不进入模型视野。这样，智能体在漫长的运行中都能使用需要凭据的工具。在 Martin 看来，既然智能体可能连续数天自主运行，凭据放在哪里和会话日志放在哪里一样，都是框架设计的问题。

11

一个定时 Slack 更新把各托管组件串联起来

Martin 和同事 CJ 做了一个定期汇总上下文更新的示例。工程师指定智能体要查阅的信息源；一个定时部署在 Anthropic 的基础设施上运行，智能体从这些信息源读取内容，并可以把更新写到 Slack。这个示例把定时调度、安全存储的密钥和记忆组合成了一个可定制的自动化。要启动它，Martin 建议工程师使用 Claude Code 中 Claude API 技能里的 Managed Agents 入门工作流；把配套教程交给这个工作流，Claude 就会把示例搭起来供他们探索。

Martin 把这一点与他在同事中看到的一种工作模式联系起来：工程师可以白天定义评测上的“成功”是什么样子，晚上让 Claude 对照它去改进一个技能。在反复的多轮对话中缓存很重要；评测决定哪些改动算作进步；而在负责人离开时，框架必须保证任务可以恢复。随着 Claude 承担越来越多的迭代工作，关于用例、评分器和允许修改范围的决策，在工程师的工作中占比越来越大。

12

先让 Claude 标出可疑的追踪记录，再由人挑选评测用例

一位听众问：评测设计中有多少可以自动化？Martin 回忆起 Hamel 对 build-eval 技能的反馈。在一个客服示例中，起始材料是一批 trace，第一个决策是哪些对话包含值得纳入评测的失败。Claude 很擅长扫描离线日志并指出潜在错误，就像在线评估器标记有问题的交互那样。这能帮人在大量记录中找到值得细读的案例。

Hamel 希望这个技能先带用户把底层数据过一遍。Martin 表示认同，并区分了提议中的工作流和当时已有的行为：当时，技能会直接开始分析数据、构建评测并呈现结果。Martin 已经提交了一个 pull request，增加一个中间查看器：Claude 先标注候选失败或提示该看什么，然后在样例被纳入之前，把原始 trace 展示给人看。这个顺序之所以重要，是因为决定哪些用例进入评测集的人，可以亲自检查引出这条标注的那次交互。

接下来的问题是关于结合人工反馈的爬山优化。Martin 的要求是：每个样例都要有一个 Claude 可以用来区分好坏的信号。人类判断一旦被纳入评测，就可以提供这种信号。这在另一个位置划分了分工：人来确定哪些结果是理想的，Claude 在迭代时使用由此得到的判断。

13

选一个评测能看到其效果的可编辑文件

被问到该从哪里开始爬山优化时，Martin 又回到了“修改”与“答案”之间的关系。对于提示词或技能，Claude 可以改动被评测模型直接读取的一小段文本；而对于智能体框架，一轮就可能产生大得多的代码 diff，其中有些改动可能影响到评测从未覆盖的行为。他说，确实有人成功地对框架做了爬山优化，但当一次修改可能通过系统的多个不同部分起作用时，解读分数变化需要更多功夫。

修改文本容易，也有他在自己实验中观察到的副作用：Claude 很擅长把提示词微调成在所选样例上表现异常好的样子。即使做了训练/测试拆分，提示词仍有可能拟合整个集合共有的某种怪癖。小而清晰的 diff 让人更容易检查 Claude 做了什么；但工程师仍需判断，新措辞所表达的要求是否会在生产中反复出现。

另一个问题是：提示词或标准操作流程（SOP）什么时候应该变成技能？Martin 常常先和 Claude 一起完成一个工作流，然后让它把这套重复流程变成技能。做优化运行时，他通常会从更进一步的地方开始：一个现成的技能，或一段 Claude 可以修改的粗糙样板。他的 API 技能本质上是文档的提炼，指引 Claude 针对特定问题去看特定页面。它包含的那些小坑足以导致较低的初始分数，但也为评测提供了基线，为优化器提供了一个具体可改进的文件。

14

对于开放式答案，先检验评分者之间是否一致

一个关于开放式工作的问题，触及了爬山优化器应该相信什么样的分数。Martin 倾向于：只要任务允许，就用确定性检查。对于难以这样检查的写作类产出，他会先写一份自己也能拿来打分的评分标准。实用的检验方法是：把一份示例答案和标准放在一起读，看自己能否真的给它打分。丢给 Claude 一个随意的 0 到 5 分量表，各分数之间的区别仍然悬而未决；让它从 1 到 10 给文本打分，带来的噪声判断机会就更多了。

对于单一标准，Martin 偏好清晰的二元判断。如果有多个品质都重要，就用多个二元分类器，让每个评分者都只回答一个具体问题。然后检验评分标准本身：让 Sonnet、Opus 和 Fable 按同一标准给同一份工作打分，普遍的分歧就是警告——标准留给解读的空间太大。另外，重复运行，看多次尝试的分数聚得有多紧。前一项检查考察评分者之间的一致性；后一项检查评分者能否足够稳定地复现自己的判断，以指导下一次修改。

15

在两个页面之间二选一，可能更容易评分

一位听众提出了两两比较。Martin 举了两个网页的例子：评审者可能一眼就知道自己更喜欢哪个页面，却很难给任何一个页面打出 0 到 5 分。成对比较提供了数值量表所缺少的参照点。Martin 发现，当单个产出的质量难以打分时，人和模型评判者做比较都更容易。

还有一个独立的问题：该把哪些产出交给评判者。Martin 所说的评测“分布”，是指为评测抽取的用例集合，以及这些用例在多大程度上代表了人们在生产中真正关心的工作。工程师可能有一套出色的方法来评判每个用例，却依然挑出一组对应用描绘失真的用例。一种特别诱人的做法，就是全部用某一个模型的失败案例来构建这组用例。

假设 Sonnet 5 在一组样例上失败了。根据这些运行结果，它们看起来都很难。把它们纳入评测、换成 Opus 5，新模型也许每一道都能解出来。Martin 把模型能力描述为“参差不齐”的：Sonnet 吃力的那个角落，对 Opus 来说可能相当容易。用这种方式（他称之为对抗性抽样）挑出的评测，会带上某一个模型弱点的形状。升级后分数大涨，可能并不能告诉负责人多少关于其余工作负载的信息。

Martin 仍然会把暴露出重要问题的生产故障纳入评测。挑选时要问的是：是什么让这个用例值得跨模型版本保留？产品负责人可能凭经验认出这是个难请求，可能在生产数据中看到它很重要，也可能从第一性原理出发有理由期望应用能处理它。即使某天换了一个模型能答对，这个理由依然成立。

16

评分量表必须对使用它的人和模型都行得通

一位听众追问 Martin 为何明显偏好二元评分：评测能不能把输出分进几个档？可以。二元判断只是简化困难判断的一条捷径。他反对的是那种常见的 0 到 10 分量表：作者能说清两端是什么，却几乎没给评分者区分中间各值的依据。给一个输出打 7 分看起来很精确；但如果评分规则同样支持打 6 分，这种精确对一个正在测量下一次改动的优化器就没什么用。

Martin 给出了他愿意接受多档评分的三个条件：人类评审者能根据规则区分两个档次；重复评分的方差要低；这些区分在不同模型之间可复现。这几项检查合在一起，确立了这些类别对人有意义，而且施行它们的机制能稳定地还原这种意义。一个经过深思熟虑的多类别分类，和二元分类一样能化解他的顾虑。

成本之所以重要，是因为每当一个候选配置产出答案，评判者都可能要运行一次。Martin 常常希望由一个小而便宜的模型来做这项工作。视成本约束而定，用 Fable 做常规评分，可能是在用昂贵的方式执行一份不清晰的评分标准。值得问一问：更便宜的评判者能否做出评测设计者要求的那些区分？

17

个人自动化产出的工作，同样值得做评测

Martin 根据任务的后果来决定是否要构建评测。设想一位财务人员把自己的部分工作流程自动化了：这个工具只有一个制作者，可能也只有一个用户，但它的产出可能会发给组织外部的人。如果这份交付物的质量很重要，Martin 就会构建评测。同样的道理也适用于被委以敏感工作的个人智能体。至于某人为管理自己会议而做的日历助手，他觉得做不做都行。他自己的个人自动化就很少做评测。

在工具上的投入可以跟随任务的规模。被问到平台时，Martin 提到他在加入 Anthropic 之前曾在 LangChain 工作，并且不愿为某个特定供应商背书。在小规模下，他乐意为手头的数据自己做一个查看器。定制化的问题可能需要非常特定的记录视图，而他发现 Claude 能又快又便宜地构建这样的界面。他还提到正在为这个技能做一个简单的数据查看器。眼下的需求很朴素：让做质量决策的人有办法查看底层样例。

18

爬山优化停滞时，检查剩下的失败案例有什么共同点

爬山优化意味着：做一处修改，运行评测，检查结果，并用这些证据选择下一处修改。Martin 多次看到这个过程卡住。一个常见的起因是：有人在一个现成的用例集上直接调用了爬山优化器，事先既没有运行构建评测的命令，也没有仔细检查用例。分数会一直上升，直到容易理解的样例都通过；剩下的失败在纸面上仍然许诺着收益，于是优化器继续在它们身上打转。

设想用例集的最后 20% 包含含义模糊的指令或有缺陷的评分样例。一次运行失败，可能是因为作者没有明确预期答案，也可能是因为评分器惩罚了一个站得住脚的答案。无论哪种情况，反复修改应用提示词都不是找出原因的好办法。爬山优化技能为连续几轮没有进展的情况准备了后备方案：把剩余的失败案例分组，寻找它们反复失败的共同原因，包括评测本身的问题。

Martin 在自己的一次运行的第二阶段看到了这个后备方案起作用。进展停滞后，技能对用例做了聚类，调查答案为何被判错，找到了几个含义模糊的用例并改写了它们。在解读下一次分数时，这个顺序很重要：修改技能，可以让应用把已有的问题答得更好；改写问题，则是在澄清后续答案要接受评判的任务本身。两者都能推进工作，但它们对应用所说明的东西不同。

被问到这种方法与 DSPy 的关系时，Martin 介绍说，爬山优化器是 Claude Code 自带的一个开源技能，其核心是一套搭建优化循环的指令，开发者可以把这些指令移植到其他环境中。Martin 认为这套指导或许可以改编到 DSPy 上，并向 Omar 和 DSPy 团队致谢。他本人没有用过 DSPy，只是把这种联系作为一种可能的实现方式提出来，并不声称自己测试过。

19

以当前分数为底线，联合搜索模型与 effort

选择 effort 设置是如此反直觉，以至于 Martin 承认他自己也觉得困惑。有了评测，他就能把这个选择变成一次搜索：确定应用的基线表现，让爬山优化器用低 effort 尝试不同的模型，同时比较它们的得分和成本；逐个尝试候选配置，直到表现跌破基线。最后那次测量即便对应的配置永远不会上线，也很有信息量——它找到了节省开始以不可接受的质量代价为前提的那个点。

Martin 展示的对比里缺了这样一项观察：低 effort 的 Haiku 4.5 出现了明显的退步。他把这个结果与 Haiku 5.5 区分开来，并称后者是更好的模型；观察到的退步属于他实际试过的 4.5 配置。这也解释了为什么“从低 effort 开始”的建议仍然需要做性能检查：一个强模型能经济地解决某个任务，并不能说明另一个模型在同样设置下会表现如何。

如果没有评测，Martin 的起步建议是用 Opus 5.5 这样的强模型配合低 effort。被问到为什么是低而不是中时，他指出工程师随时可以往上调。从最高 effort 起步，会在还没有证据表明任务能从中受益之前，就承担最大的推理开销；从低处起步，则让工程师有机会先看看模型本来就能做到什么。Martin 把这作为一种有用的实验顺序提出，同时承认：在应用缺乏质量衡量手段时，最终该怎么选就没那么确定了。

这种经济直觉取决于每个任务消耗的 token 数。effort 告诉 Claude 要多努力地思考。单 token 基础价格较低的模型，在高 effort 下可能花掉大量 token 推理；更强的模型在低 effort 下，可能用更少的思考 token 就得到同样好的答案。token 的减少可能大到足以抵消更高的单 token 价格。Martin 一开始把更强的配置称为“更有效”，随后又纠正了自己：他所说的优势是 token 效率；它是否同时带来更好的答案，是另一个需要单独测量的结果。

20

为搜索设定预算，并由人来定义什么是严重的失败

爬山优化技能会在设置阶段询问预算，并在运行过程中追踪花费。这个预算覆盖的是实验本身；搜索最终选出的配置的单任务成本，是另一项指标。如果用例集的最后 20% 根本无法解决，优化器可能会花大钱去追这些分数。检查这些顽固的用例，能帮负责人判断是否值得再花钱跑一轮。

关于 Claude 与人之间的分工，Martin 借鉴了 Hamel 公开使用 build-eval 技能的经验。以客服应用为例：在 Claude 读取 trace 之前，需要由懂产品的人决定一次客服交互中什么重要、为什么重要。客户满意度就是一个可能的关注点。把它说清楚，Claude 才有理由标记特定的对话；如果只是丢过去一堆 trace，产品层面的决策就隐含在了模型碰巧觉得有趣的东西里。

负责人明确目标后，Claude 就可以读取原始 trace，找出应用似乎表现不佳的交互。Martin 把这比作带在线评估器的追踪系统：对话一进来，就为客户满意度打分。两种情况下，最初的产出都是一批待检查的候选。负责人阅读这些对话、弄清发生了什么，并找出值得做成评测的用例。只有这样，构建评测集的请求才同时具备了样例，以及它们为何应该入选的说明。

Martin 说，在 Anthropic，评测的责任通常跟着产品的归属走，许多不同角色的人都会构建评测。Claude 可以承担诸如编写评测运行器之类的工作，从而降低负责人所需的专业实现经验。留给负责人的部分，是定义什么样的结果算令人满意，以及识别出那些要紧的失误。对于客服产品，一个能说清一次糟糕对话会造成什么后果的人，就能提供这种指导——即便按传统做法，运行器会由别人来写。

21

把对生成 UI 的反复偏好判断，变成一次配置对比

被问到“模型当评委”的具体用法时，Martin 回忆起一次对生成式 UI 的评测：A、B 两套配置各自生成候选界面，评判者同时看到两者并选出更好的那个。在大量试验中重复这种判断，就能得到关于两套配置的证据，而不只是某一个页面的成败。Martin 记得结果被汇总成了类似 Elo 分数的东西；他对两两评判的流程比对具体的汇总方法更有把握。

这让开头那个网页例子有了实际用途：单次判断，对一个能分辨偏好却难以给出绝对分数的评审者来说是做得到的；而累积起来的判断，则回答了工程师“该用哪套配置”的问题。Martin 还见过语言模型评判检索和写作任务，以及把 trace 分为好坏两类。这些应用都需要判断，只是判断的形式可能不同：在两个界面中二选一，和判断单条 trace 是否值得关注，是给评分者的两种不同指令。

22

划分好的评测集和可度量的 loss 可以驱动同一个实验循环

Martin 把爬山优化的部分动机追溯到 autoresearch（自动化研究），以及模型纠正自身工作的能力不断提升。前提条件是它们能理解的反馈：模型运行一个实验，测量一个目标，检查结果，再调整下一个实验。在一长串尝试中，这种测量可以引导原本需要人一次一处地去驾驭的工作。

讨论中有两种问题表述。Claude Code 的命令是为带拆分的评测集设计的：对应用的修改要用一组用例来评估。而在 Martin 对 autoresearch 的描述中，系统构建或修改某个产物（例如一个网络），然后测量某个量，比如 loss。他记不清 Karpathy 例子中的具体问题，只是用 loss 来说明可用的反馈类型。在前一种表述中，优化器可以检查它没做对的用例；在后一种中，它可以检查针对该产物的实验结果。两者都有可观察的结果，可以作为下一次尝试的依据。

一位听众问：是否该先从爬山优化做起，再扩展到 autoresearch？Martin 把这看作问题表述的选择。在 nanoGPT 这样的仓库里工作的人，可以试着把这个技能交给 Claude，让它把循环改造成适合那里的实验。他把这作为值得一试的事情提出。通用流程本身已经很精简：做一处修改，测量结果，用结果决定下一步改什么。改造的工作在于明确 Claude 能改什么、应该测量什么结果。

23

成本、质量与速度让“选出胜出改动”变得复杂

爬山优化器可以同时测量不止一个目标。Martin 自己的例子把成本与性能配对：可以把两者都告诉 Claude，让它在比较候选修改时同时考虑这两项测量。速度是他会考虑的第三个维度。一个答得又对又便宜的配置，返回答案可能仍然更慢——只比较成本和质量会忽略这一点。

Martin 主要实践的是成本与性能这一对。随着目标增多，选择下一处修改会变得更难，因为不同的测量可能偏向不同的候选。他建议串行地做修改、一次只改一样，以简化实验。他没有为这三个维度给出综合分数或加权方案。在 effort 搜索中，现有基线已经为比较提供了具体含义：一个跌破质量底线的便宜配置，就是没满足负责人设定的条件之一。

24

在迁移时审查继承来的提示词，并检查难题上的 effort

回到提示词审查，Martin 称它是最容易尝试的干预。prompt-audit 技能会寻找目标模型不再需要的继承模式。对于迁移到 5.5 系列前沿模型时删除已知多余的指导，他很有把握；但要给出一个历史分界点，他就没那么有把握了。他的测试表明，一些较老的提示习惯可能大约从 Opus 4.5 开始就逐渐失去作用，但他不会把这个观察当作精确的版本界线。

这个技能包含针对特定模型的注意事项。例如，把应用迁移到 Haiku 时，就有理由问一问：相比上一个实验所用的模型，它是否更需要明确的指导？Martin 把这作为一种可能性提出，承认自己并不确定，并把答案拉回到实际的迁移目标上。审查的任务是找出对于接收提示词的那个模型来说已知多余的指导；从最新 Opus 版本推断出的规则，未必能解决另一个模型家族的所有情况。

一个关于 effort 的追问澄清了这个控制项的作用。Martin 把它描述为：指导 Claude 应该为问题投入多少思考。它并不设定硬性的 token 上限。即使在很高的 effort 下，一个简单问题也可能得到简短的回答，因为 Claude 仍会判断这个任务需要多少验证。他手头没有评测来量化这种行为，这是他对该设置的工作性解释。

对于困难的编程问题，Martin 会特别关注测量结果。在超高或最高 effort 下，Claude 用于检查结果的 token 可能比中、低 effort 时多得多，而最终结果可能差不多。这种模式解释了为什么：在简单输入上观察到的成本差异很小，并不足以作为把整个应用设为最高 effort 的证据。昂贵的差异，恰恰可能出现在那些会引发又一轮验证的困难输入上。

25

即使模型行为符合预期，提示词优化也可能过拟合

Martin 同意，爬山优化在一个重要方面与训练相似：给模型一个奖励或目标，以及修改某个系统的能力，它就会去搜索能提高目标的修改。训练/测试拆分在两种场景下都有用。这里的模型已经部署，可编辑的组件是提示词或技能之类的运行时输入。应用负责人可以在自己的领域里，把训练的实验纪律用在这些组件上。

Claude 会不会知道自己正在被评测？Martin 承认，“评测意识”是 Anthropic 在训练背景下讨论过的一个担忧。而在这些应用实验中，他观察到的更直接的问题是过拟合：给 Claude 一个可编辑的提示词，以及一个能为它打分的分布，它就能找到让分数显著提高的措辞——而这些措辞可能只对用例集中出现的问题有效。这个结果无需任何“Claude 识破了测试”的特殊解释，它直接来自优化器可用的目标和样例。

训练/测试拆分为这种行为设了一道检查：优化器用训练用例来选择修改，而留出用例上的表现则单独说明这些修改能否推广到那些样例之外。听众问到最小可用的数据集规模和合适的拆分比例。Martin 没有系统研究过不同规模，既没有给出最少数量，也没有给出固定比例。技能里有一些经验规则，他建议与 Claude 一起，根据负责人想测量的信号来确定合适的规模。

样例很少时，有三个问题会变得格外突出：样本可能遗漏重要的生产工作；提示词很容易被量身定制到那寥寥几个样例上；分数也可能噪声很大，结果的变化更难归因于修改。留出一部分样例能解决一种过拟合来源，但两部分仍然继承了负责人当初挑选原始样本时所做的选择。

26

长达数小时的任务改变了每次迭代的成本

Martin 通常选择提示词这类可编辑组件，因为它改起来快。一位听众问到耗时很长的任务。在这种情况下，准备下一个候选可能只是实验中最短的一环：负责人仍得等智能体执行完任务，才能拿到质量信号。一次失败的运行既耗算力也耗时间，而每多一轮，这种延迟就要再承受一次。

对于持续数小时甚至数天的实验，框架本身必须在整个期间保持可靠。Martin 提到了 Anthropic 内部对 Managed Agents 的使用。长时间的爬山优化是可行的，但它把基础设施故障和反馈等待时间带进了实验设计。如果循环的下一步决策取决于一整天工作的结果，那么只改进提示词编辑器，对加速这个循环帮助不大。

智能体通常也需要多轮评测。Martin 建议让 build-eval 命令访问真实的 trace，明确说明评测应为多轮，并解释负责人想检查什么。Claude 可以检查这些 trace，帮助挑选值得纳入的交互。之后，评分器可以检查整条轨迹（包括智能体采取的动作序列），也可以只检查最终结果。前者回答的是智能体如何工作，后者回答的是它最终完成了什么。

27

上下文压缩之后，会话日志仍要可查询

被问到哪种上下文工程技巧对可靠性帮助最大时，Martin 提到了一个他与递归语言模型（RLM）联系在一起的思路：让上下文对象独立于模型及其框架。在他介绍的 Managed Agents 设计中，框架可以用工具去查询一份单独存放的会话日志。因此，Claude 当前工作上下文中的消息，只是智能体可用历史的一种视图。

上下文压缩（compaction）说明了这样做的好处。在一项长任务进行到一半时，智能体会总结自己的消息历史以便继续工作。这时它必须决定哪些细节重要到值得保留，尽管它还不知道之后会遇到什么问题。如果这份总结是唯一留存的记录，被省略的细节就彻底丢了。有了独立的日志，框架可以在某个细节变得相关时回到早先的交互中把它找回来。可恢复性来自两点：保留记录，以及给框架一个查询记录的接口。

可靠的历史仍然留下一个问题：如何评判其中记录的工作。智能体的结果具有不确定性，而许多有用的任务涉及开放式写作或判断，没有容易验证的答案。Martin 又回到了清晰的评分规则、低方差，以及检查多个模型能否复现同一判断。如果问题本身无解，或评分器对几种合理解读的处理前后不一，那么优化器在一份精心保存的 trace 上干上几个小时，也可能毫无进展。花在验证器设计上的时间，决定了这样一次长时间运行能让负责人学到什么。

28

用值得保留的生产案例来更新已饱和的评测

Martin 预计，随着模型进步，结构良好的现有评测上的分数总体应该会上升；如果没有这种趋势，他会重新审视这组评测到底在测什么。另一个极端是，强模型可能很快就让评测集饱和。设计真正能难住 Fable 或 Opus 5.5 这类模型的更难用例，是一项需要反复进行的工作。旧的评测集即使失去了区分进一步提升的能力，仍然可以用来检查团队已经实现的行为。

Martin 最后介绍了一个他在追踪服务商那里看到的工作流：已部署的智能体产生 trace；在线评估器为其打分，得分低的交互成为离线评测集的候选；团队针对挑选出的生产故障做爬山优化；一旦应用能成功处理它们，这些用例就变成回归测试。与此同时，已部署的智能体不断产生新的 trace，负责人可以继续寻找下一个严重故障，并观察生产中故障率是否在下降。

LangChain、Arize 和 Braintrust 是 Martin 认为提供了这类外层循环工具的服务商，但他没有密切关注它们最新的产品变化。他留给产品负责人的难点，位于任何平台选择的上游：在线评估器在生产中把什么认定为好的工作？哪些被标记的交互值得纳入？这些决策决定了下一轮优化改进的，是否是用户真正能感受到的东西。

要点总结

  • 模型迁移时，先在新模型上给继承来的提示词打分，再做审查。这次中间测量能把升级本身的效果，与删除过时指令带来的成本和质量变化区分开。
  • 检查智能体相邻两次请求的前缀从哪个字节开始出现分歧。把共享的工具和指令放在最前，接着是项目上下文，然后是会话状态和不断增长的消息历史。用缓存命中率来验证结果。
  • 把训练集上的失败案例交给爬山优化器，让测试样例远离它的修改循环，并在每一轮同时测量两个数据划分。做成本优化时，先设定基线质量底线，再联合搜索模型、effort 和提示词。
  • 在信任一个开放式评分器之前，先亲自按它的评分标准打分，比较不同模型给出的分数，并重复运行评分。在二元判断或两两选择更容易保持一致的地方，就改用它们。
  • 对于开放式产出，试试两两对比评判。只有当人能说清相邻等级的区别、且廉价的模型评判者也能复现这种区别时，才使用多级绝对评分。
  • 给爬山优化器设定预算，并保留留出集。进展停滞时，把未通过的案例归类，先检查题目和评分器，再决定是否花钱跑更多轮。
  • 在同一工作负载上把模型和 effort 作为一个组合来比较。先用能力强的模型配合低 effort，再对照现有质量底线衡量每个任务的成本。
  • 对于长时间运行的智能体，要保留可查询的会话历史。决定评测应该给执行轨迹打分还是给最终结果打分，然后把严重的生产故障提升为回归测试。

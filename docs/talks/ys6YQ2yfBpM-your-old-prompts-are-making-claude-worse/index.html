你的旧提示词正在让 Claude 变差

Anthropic 的 Lance Martin 拿一套约 50 张工单的客服评测做演示：只调整模型、思考强度和提示词，成本就降了 90%，分数反而更高。他还展示了 Claude 如何把一个只拿 66 分的 API 技能自己改好，以及长时间运行的智能体在沙箱崩溃后如何恢复。

01

你的应用可能还没碰到成本—质量前沿

是花钱换更强的模型，还是为了省钱接受更低的分数？Lance Martin 认为，做选择之前先要搞清楚一件事：你的应用在自己的评测上处在什么位置。设想一张图，横轴是成本，纵轴是质量。对某个具体任务，所有最优方案会连成一条帕累托前沿；站在这条线上，想提升一项就得牺牲另一项。Martin 画了一组选项：最贵、最强的一端是 Fable，往下依次是 Opus、Sonnet 和 Haiku。

光看用的是哪个模型，工程师几乎判断不出应用有没有碰到这条线。智能体可能一遍又一遍地为同样的指令付费；提示词也可能让 Claude 把 token 花在一套验证流程上，而这套流程对答对题毫无帮助。有其中任何一个问题，应用在图上就还有往左挪的空间；如果指令本身写得含糊，说不定还能同时往上挪。Martin 是 Anthropic 的技术团队成员，他见过不少客户只改了几处配置，成本和质量就同时有了改善。他举的第一个例子，是一段经常跨越好几次模型升级、却始终没人动过的配置。

02

清理旧模型才需要的指令

提示词和代码一样，也会欠技术债。往前数几代模型，工程师习惯让模型“一步一步思考”，给它一块草稿区，还规定这块地方该怎么用来推理。为了让它回头检查答案，会加一句“仔细检查你的结果”；或者干脆加一句通用的“尽可能详尽”。每一条当初都是为了纠正某种具体的毛病，可是叠在一起，就成了每个请求都要走一遍的固定流程，不管题目难不难。

按 Martin 的经验，前沿的 Claude 模型已经会自己判断什么时候该推理，也会主动检查自己的结果。所以，就算模型第一次就答得够好了，提示词里那句沿用下来的“务必详尽”还是会逼它多干一些活。互相矛盾的规则则是另一回事。指令遵循能力弱一些的模型，可能会悄悄忽略其中一条，给出的答案让人觉得提示词还挺管用；能力更强的模型却会努力两条都满足。升级并没有制造矛盾，只是把一直存在的矛盾暴露了出来。

在 Claude Code 里做提示词审查，Martin 介绍了两条路：如果要查的是 Claude Code 自己的配置，包括它的提示词和技能，就用 checkup 技能里的提示词审查；如果要查的是调用 Anthropic API 的应用代码，就用内置 Claude API 技能里的提示词审查。两条路背后是同一套审查，区别只在于工程师在哪儿干活。审查会从当前工作目录出发，把技能、工具和提示词里的这类写法都找出来删掉。查的范围之所以要这么广，是因为有时候应用提示词本身已经很干净，那套验证流程却又从某个工具的说明里混了回来。

03

把升级模型的收益和改提示词的收益分开算

Martin 搭了一套约 50 张工单的合成客服评测，模拟从 Opus 4.8 迁移到 Opus 5.5。他把几种提示词反模式一个个加进去，分别测量结果，对比图里的中间那个点是这几组实验的平均值。这样，对同一批工单就能分开问两个问题：沿用旧习惯的提示词，在新模型上表现如何？审查把这些习惯删掉之后，又会发生什么变化？

光是迁移模型，这个点就往左移了，还稍微往上抬了一点：即便带着那些多余的指令，Opus 5.5 也更便宜，分数还略高。迁移之后再做一次提示词审查，成本继续下降，分数也再提高。Martin 认为，省下来的 token 主要来自删掉了那些“增强语”和验证流程，它们原本会让 Opus 5.5 做很多不必要的工作。把会让强模型困惑的指令理顺，它答对的机会也更大。

想复现这组对比的工程师，最好把中间这一步也测出来。如果一次就既换模型又清理提示词，前后对比只能得到一个结果，却要拿它回答两个决策。固定同一批工单，先用旧提示词在新模型上跑一遍，就能看出升级之后应用还有多少收益没拿到。Martin 在这里只说明了两项收益各自的方向；后面提到的具体节省比例，来自其他几组实验。

04

按“多久不变”给智能体的上下文排序

看智能体会话里前后两次请求。两次之间，Claude 可能只调用了一次工具，新增的信息很少，但下一次请求带上的上下文大部分和上一次一样。如果命中提示词缓存，应用就能以更低的成本、更短的延迟复用之前的计算。Martin 说缓存读取的价格大约是基础 token 价格的十分之一，不过各个模型的定价不一样。轮次一多，重复输入里究竟有多大比例命中了缓存，就直接决定了整个会话的成本。

缓存要求前缀严格一致。提示词靠前的位置只要变了一个字节，匹配就在那里断掉；后面就算有几千个一模一样的 token，也接不上了。所以两次请求的内容几乎完全相同，复用率却可能很低。排查时光看哪些内容在重复只做了一半，还得看它们在拼好的请求里排在什么位置，这决定了缓存能认出多少。

Martin 把输入分成四层：最前面是跨会话共用的系统指令和工具定义；其次是 CLAUDE.md、项目记忆这类项目资料；再往后是会话状态；最后是随轮次不断增长的消息。这样排，切换项目时，共用的指令和工具依然能命中缓存；同一个项目里开新会话，项目资料也能复用；在末尾追加新消息，已有的对话就有机会一直匹配到上一轮。

Claude Console 里可以看到应用的提示词缓存命中率。Claude Code 团队一直紧盯这个数字，Martin 也建议用 API 构建应用的人去看一看。Claude Code 里有一个诊断工具，能检查 API 项目，找出提示词拼装在哪里破坏了复用，并给出更好的排序，同时还会看提示词和思考强度的设置。就缓存问题而言，最有用的产出是一个具体的改法：把会变的内容挪到可复用的前缀后面。改完之后，再看命中率有没有上去。

05

默认评测框架白白浪费了高达 72% 的缓存收益

Martin 和 Anthropic 应用 AI 团队的同事，用这个诊断工具检查了几套内部基准测试，这些测试用的都是负责发请求的默认框架。结果发现，有些框架几乎没用好提示词缓存。团队找到的优化空间能把成本最多降低 72%，测得的表现却没有明显变化。72% 是这几套框架的上限；本来就有很长前缀命中的应用，起点不一样。

这组实验省下的钱，和前面客服工单的提示词审查不是一回事。删掉验证指令，改变的是 Claude 决定做多少工作，也可能影响它的答案；用好缓存，省的是重复处理那些智能体反正还要再收到一遍的内容。这就解释了为什么基准分数可以纹丝不动，成本却大幅下降；也说明了在认定“模型本身太贵”之前，应该先检查一下默认框架。

06

先确认评测分数还有提升空间

Martin 的下一步，靠的是 Claude 自我纠错的能力。给它一套评测，它就能分析失败的题目，修改应用的某个部分，然后再试一次。Martin 把这个循环叫作“爬山”。不过，在让它一轮轮花 token 之前，他会先确认这套评测确实有山可爬。他用一张诊断图来判断：横轴是每次尝试消耗的 token 数，代表模型想了多少；纵轴是得到的分数。图上几条曲线分别代表前沿、中等和小型模型，在他的例子里大致对应 Opus、Sonnet 和 Haiku。

他要看四个特征。第一，换成更强的模型，分数总体上应该更高。第二，同一个模型，允许它多想一些，表现总体上也应该更好。第三，最强的模型仍然要有一些能被解决的失败题，这样更好的配置才有提升空间。第四，同样条件下重复跑几次，分数应该差不多。如果同一套配置本来就经常波动这么大，前后两次之间的差距也就说明不了什么。

判断还有没有提升空间，必须去读具体的题目。一套评测拿了 80 分，看上去还有 20 分可以争取。但如果剩下的题本身就有歧义，模型给出的答案再合理也拿不到分。即便是用得很广的评测，也可能包含不少这样的题，实际上已经饱和了。让一个自主优化器去寻找能把这些分数拿回来的提示词，它可能会烧掉一大笔预算，而这些分本来就没有靠谱的拿法。

Claude API 技能里的 build-eval 流程，从三样东西开始：要解决的问题、工程师想衡量什么，以及原始数据，比如团队现有追踪系统里的 trace。技能会分析这些数据、搭出一套评测，再和工程师一起检查题目和评分标准。问答环节里，Martin 还提到他提议的一个改动：Claude 标记出可疑的 trace 之后，先让工程师看一看原始记录，再决定是否把它们做成评测题。

07

别让测试集进入 Claude 的修改循环

评测在不同模型、不同思考预算和多次重复运行下都表现正常之后，就可以放手让 Claude 自己提出改动了。风险在于，它可能学会的只是在这一批题上怎么拿分。假设基准里有一道题需要 OCR（光学字符识别），一个可以改框架的优化器也许会加一个 OCR 工具，把这道题做对。可如果真实用户根本不会提这类问题，这个新工具只提高了基准分，对用户毫无用处。提示词也能更隐蔽地制造这种虚假的提升，比如学会了样例里特有的措辞。

Claude API 技能的 hill-climb 流程会把评测拆成训练集和测试集。Claude 只看训练集里的失败题，并据此决定改什么。每一轮，运行器都会在两个集合上分别测一次，但测试题从不出现在 Claude 的思考过程里。这样，同一个改动就能看到两个分数。如果训练集分数一路上涨、测试集分数却原地不动，就说明 Claude 可能在迎合训练题的某些特殊细节，这是个早期预警。

这种拆分能回答的问题是有限的。它能告诉你，一个改动能不能推广到同一套评测里的其他题目；但它能不能预测线上表现，还要看最初的题目是怎么挑出来的。如果基准里尽是些不常见的请求，拆出来的训练集和测试集也会带着同样的偏差。所以 Martin 始终让工程师参与审查优化器改了什么。面对那个新加的 OCR 工具，该问的是：哪些真实用户需要它？哪怕基准确实会为它加分。

08

给 Claude 一个能改的 API 技能，和一份必须对得上的文档

Martin 拿 Claude API 技能本身来试这个方法。这个技能给 Claude Code 提供 Anthropic SDK 和 API 的使用指南，所以它给出的答案必须以 Anthropic 的官方文档为准。他根据文档出了一批评测题，测试现有的技能，结果只拿了 66 分。这样一来，他既有了具体的失败可以排查，也有了明确的修改对象：被评测的模型读的是这份技能，优化器能改的也正是这份技能。

接着，他让 Claude Code 同时能看到技能文本和背后的文档。每一轮，Claude 都可以先看一道失败题，去查原始文档，找出技能里哪些地方和文档描述的行为对不上，修改说明之后再试一次。文档是独立于技能当前写法的参照物，所以每个改动都能从两方面检验：它是否忠于文档，以及用了新技能的模型是否答得更好。

Martin 说分数比 66 分有了大幅提升，但没有给出最终分数。他特别强调，这个任务和可修改的材料之间配合得很好：评测问的是 API 的行为，文档写清了这些行为，而技能就是把这些行为传达给 Claude 的那段文字。从改动到可观察的答案，路径很短，所以反复做自主实验才行得通。他发现，提示词和技能尤其适合用这种方法来优化。

09

在质量底线之上，同时搜索模型、思考强度和提示词

同一个运行器也可以换一个优化目标。告诉爬山优化器去降成本，它就会去找一个更便宜、且表现至少不低于基线的配置。它能调的有三样：选哪个模型，决定由哪个 Claude 来干活；思考强度，决定模型投入多少推理；改提示词，决定它在什么样的指令下解题。评测分数给搜索定了一条质量底线，实测的成本则用来比较那些过了线的配置。

在那套合成客服基准上，Martin 的起点是 Opus 4.8、高思考强度，加一份基线提示词。优化器先换成了低思考强度的 Opus 5：表现大幅提升，成本略降。接着它又试了另一个低思考强度的模型：这一轮成本降得多得多，但上一轮涨上去的表现回落了一部分。然后 Claude 修改了提示词，表现又补了回来。最终的配置比起点便宜 90%，分数还更高。

中间这几步说明了 Martin 为什么要把三样都放进搜索。如果在第一次换模型之后就停下，能拿到质量提升，但只省了一点钱；如果只看下一个方案比上一轮的高分掉了多少就否定它，就会错过一个便宜得多、只是提示词还有改进空间的配置。成本优化的参照点，始终是最初那条质量底线；运行器的每一步选择，都拿它来衡量。

对一套已经饱和的评测，降成本也让它还有用武之地：即便质量已经提不上去了，它仍然可以检验一个更便宜的配置能不能保住分数。Martin 多次看到，低思考强度的强模型，用的 token 比高思考强度的弱模型还少，问题也解决了。这样一来，每个 token 的单价虽然更高，完成整个任务的总价反而更低。爬山优化器会去试这种可能，并在真实负载上测出来。90% 这个数字，指的是客服基准的整轮运行，包括后面那次提示词修改。

10

跑一整夜的智能体，需要一份沙箱崩了也不会丢的历史记录

Martin 从单次尝试的经济账，转到智能体能承担多长的工作。他提到 METR 的图表：横轴是时间，纵轴是同样的任务人类需要做多久。他说 Claude Opus 3 大约能完成相当于人类 4 分钟的工作，对应的是自动补全和聊天那个阶段。到了 2025 年，随着 Claude Code 流行起来，模型能做的任务已经达到一两个小时的量级。他认为智能体正在走向相当于人类一两天工作量的任务，不过他也补充说，这可能已经超出了这些图表能衡量的范围。

有了这样的前景，一个好用的框架必须扛得住什么，也就变了。设想你晚上启动一个智能体，半夜它的沙箱崩了。如果会话日志只存在沙箱里，那么同一次故障不仅打断了执行，还把恢复所需的历史记录一起带走了。Claude Managed Agents 把指挥工作的框架（Martin 叫它“大脑”）和写代码、执行操作的沙箱（“双手”）分开。第三个组件是会话日志，它的生命周期独立于前两者。

日志是一个只能追加、可以恢复的对象。沙箱挂了，系统可以启动一个新的；框架挂了，编排器可以再拉起一个。无论哪种情况，会话历史都还在，可以拿来恢复。Martin 的例子讲的正是如何依靠这份记录恢复工作。这种设计把“发生过什么”的证据，放在了直接干活的这两个组件之外。

凭证也有自己的边界。Managed Agents 把密钥存在与工具关联的保险库里。Claude 可以引用某个 API key 或其他密钥，但密钥的值始终留在保险库里，模型看不到。这样，智能体在长时间运行中可以一直使用那些需要凭证的工具。在 Martin 看来，既然智能体要自主运行好几天，凭证放在哪里，和会话日志放在哪里一样，都是框架设计要考虑的问题。

11

一个定时发 Slack 更新的例子，把这些托管组件串了起来

Martin 和同事 CJ 做了一个定期收集上下文更新的例子。工程师先指定智能体要看哪些信息源；一个定时部署在 Anthropic 的基础设施上运行，智能体从这些来源读取信息，再把更新发到 Slack。这个例子把定时调度、安全存储的密钥和记忆组合成了一个可以自定义的自动化流程。想上手的话，Martin 建议在 Claude Code 里打开 Claude API 技能中的 Managed Agents 入门流程，把配套教程交给它，Claude 就会把这个例子搭起来，让你自己摸索。

Martin 把这一点和他在同事身上看到的一种工作方式联系起来：白天花时间定义评测上怎样才算成功，晚上把时间交给 Claude，让它对照评测去改进某个技能。在这一轮轮重复里，缓存决定成本，评测决定哪些改动算进步，而框架要保证主人不在的时候任务依然可以恢复。Claude 承担的迭代工作越多，工程师的精力就越多地花在这些决定上：选哪些题、怎么评分、允许改什么。

12

先让 Claude 标出可疑的 trace，再由人来挑评测题

有观众问，评测设计有多少可以自动化。Martin 想起 Hamel 对 build-eval 技能的反馈。在一个客服的例子里，起点是一堆 trace，第一个决定是：哪些对话里有值得拿来做评测的失败。Claude 很擅长扫一遍离线日志、指出可能出错的地方，就像在线评估器会标出有问题的交互一样。这能帮人在一大堆记录里找到值得细看的案例。

Hamel 希望技能先带着用户把底层数据过一遍。Martin 表示同意，并说明了提议中的流程和当时的实际行为有什么不同：当时的技能会直接分析数据、搭好评测，然后把结果拿给用户看。Martin 已经提了一个 Pull Request，要在中间加一个查看器：Claude 先标注可能的失败、或者建议该看哪里，然后把原始 trace 给人看，之后才把它们做成评测题。顺序之所以重要，是因为决定哪些题放进评测集的人，可以亲眼看到 Claude 标注所依据的那次交互。

有人接着问，能不能结合人工反馈来爬山。Martin 的要求是：每道题都要有一个信号，让 Claude 能分辨好坏。只要把人的判断纳入评测，它就能提供这样的信号。这其实是换了个地方分工：由人来确定什么样的结果是好的，再由 Claude 在迭代时用上这些判断。

13

选一个改动效果能被评测看到的文件来改

有人问爬山该从哪里开始，Martin 又回到了改动和答案之间的关系。改提示词或技能，Claude 改的是被评测模型会直接读到的一小段文字；改智能体框架，一轮下来可能就是一大段代码 diff，其中有些改动影响的行为，评测根本覆盖不到。他说确实有人成功地对框架做过爬山优化，但如果一个改动可能通过系统里好几个不同的地方起作用，解读分数变化就要费劲得多。

文字好改，也有坏处，这是他在自己的实验里看到的。Claude 很擅长把提示词一点点推成一种在所选题目上效果出奇好的样子。即使拆分了训练集和测试集，提示词仍然可能去迎合整个题集共有的某种怪癖。改动小而且读得懂，就更容易看出 Claude 到底做了什么；但工程师仍然要判断，新的措辞表达的是不是一个在生产中会反复出现的真实需求。

还有人问，提示词或标准作业流程什么时候该变成技能。Martin 常常先和 Claude 一起把一个流程走完，再让它把其中反复出现的步骤整理成技能。做优化时，他通常会再往前走一步，从一个现成的技能，或者一段粗糙的样板文字开始，让 Claude 去改。他的 API 技能基本上就是文档的浓缩版，告诉 Claude 遇到什么问题去看哪一页。里面的小坑多到足以拉低初始分数，但它给评测提供了一个基线，也给优化器提供了一个具体可改的文件。

14

开放式回答，先看评分者之间是否一致

有人问到开放式任务，这其实是在问：爬山优化器该把什么当作可信的分数。Martin 的原则是，只要任务允许，就优先用确定性的检查。对于一篇没法这样检查的文章，他会先写一份自己就能用的评分标准。实用的检验办法是：拿一个样例答案对照标准读一遍，看自己到底能不能打出分来。随手给 Claude 一个 0 到 5 分的量表，各个分数之间的差别其实没有讲清楚；让它给文字打 1 到 10 分，评分的随意性就更大了。

对单个标准，Martin 更喜欢干脆的二元判断。如果有好几项品质都很重要，就用好几个二元分类器，让每个评分者只回答一个具体问题。然后还要检验评分标准本身：让 Sonnet、Opus 和 Fable 按同一套标准给同一份作品打分。如果它们普遍意见不一，就说明标准留给主观解读的空间太大了。另外，还要重复打几次分，看结果有多集中。前一项检查的是评分者之间是否一致；后一项检查的是同一个评分者能否稳定地复现自己的判断，稳定到足以指导下一次修改。

15

在两个页面里二选一，往往比单独打分容易

有观众提议用两两比较。Martin 举了两个网页的例子：评审的人可能一眼就知道更喜欢哪一个，却很难给任何一个打出 0 到 5 的分数。放在一起比，就有了数字量表给不了的参照。Martin 发现，当单件作品的质量难以打分时，无论是人还是模型评审，做这种比较都会容易得多。

另一个问题是，该把哪些作品交给评审。Martin 说的评测“分布”，指的是抽进评测的那批题目，以及它们在多大程度上代表了大家在生产中真正关心的工作。一个工程师可以把每道题都评得很准，却挑了一批会让人误判整个应用的题目。一个特别诱人的坑，就是整套题全用某一个模型的失败案例来凑。

假设 Sonnet 5 在一批题上都失败了，单看这些运行记录，它们都显得很难。把它们放进评测，换成 Opus 5，新模型却可能一道不落地全做对。Martin 形容模型的能力是“参差不齐”的：Sonnet 卡住的那一块，对 Opus 来说可能很容易。用这种方式挑出来的评测，他称之为“对抗式采样”，最后会长成某一个模型弱点的形状。一升级，分数大涨，但这对其余的工作负载几乎说明不了什么。

不过，如果某个线上失败暴露了重要的问题，Martin 仍然会把它放进评测。关键在于，什么理由能让这道题在模型换代之后仍然值得保留。产品负责人可能凭经验知道这是一个难请求，可能从生产数据里看出它很重要，也可能从第一性原理出发，认为应用理应处理好它。有了这样的理由，哪天换了一个模型把它做对了，这道题依然站得住。

16

评分量表要让用它的人和模型都用得明白

有观众追问，为什么 Martin 好像偏爱二元评分？评测能不能把输出分成好几档？当然可以。二元判断只是把一个困难判断简化的捷径。他反对的，是常见的 0 到 10 分量表：出题的人能说清两端是什么意思，评分的人却没有依据去区分中间的分数。打个 7 分看起来很精确，可如果按评分规则打 6 分也同样说得通，这种精确对一个要衡量下一次改动的优化器来说就没什么用。

Martin 给出了三个条件，满足了他才放心用多档评分：人工评审能依据规则区分相邻两档；重复打分的波动小；不同模型也能复现同样的区分。这三项检查合起来，才能说明这些档位对人来说有意义，而执行评分的机器也能稳定地把握这层意思。只要多档分类设计得足够周全，和二元评分一样能打消他的顾虑。

成本也要考虑，因为每个候选配置每给出一个答案，评审可能都要跑一次。Martin 往往希望用一个便宜的小模型来干这个活。视成本限制而定，拿 Fable 来做日常评分，可能就是花大价钱去执行一份含糊的标准。值得问一问：便宜的评审，能不能做出评测设计者要求的那些区分？

17

个人自动化也可能产出值得做评测的东西

要不要做评测，Martin 看的是这个任务的后果。比如一个做财务的人，把自己的部分工作流程自动化了。工具只有一个作者，可能也只有一个用户，但它的产出也许会发给公司外面的人。如果这份交付物的质量很重要，Martin 就会做评测。被托付了敏感工作的个人智能体也是同理。至于某人给自己做的管理会议的日历小助手，做不做都行。他自己的个人自动化，很少专门做评测。

在工具上投入多少，可以随工作的规模来定。被问到用什么平台时，Martin 提到自己在加入 Anthropic 之前在 LangChain 工作过，并表示不为任何一家服务商背书。规模小的时候，他会直接为手头的数据做一个查看器。特殊的问题可能需要一种很特别的方式来看记录，而他发现 Claude 能又快又便宜地把这种界面做出来。他还提到正在为这个技能做一个简单的数据查看器。眼下的需求并不复杂：让做质量判断的人能看到底层的样例。

18

爬山卡住时，看看剩下的失败题有什么共同点

爬山的意思是：做一个改动，跑一遍评测，看结果，再根据这些证据决定下一个改动。Martin 见过很多次这个过程卡住。常见的起因是，有人直接对一套现成的题集启动了爬山优化器，事先既没有跑 build-eval 命令，也没有仔细看过题目。分数会一直涨，直到容易理解的那些题都通过了。剩下的失败题看上去还有分可拿，优化器就继续在它们身上使劲。

假设题集最后那 20% 里，有的指令本身有歧义，有的评分样例是错的。一次运行之所以失败，可能是出题人没把预期答案说清楚，也可能是评分者把一个说得通的答案判错了。无论哪种情况，一遍遍去改应用的提示词，都很难找到真正的原因。爬山技能为此设了一个兜底：连续几轮没有进展时，它会把剩下的失败题分组，找出它们反复失败的共同原因，其中也包括评测本身的问题。

Martin 在自己的一次运行中，就在第二阶段看到了这个兜底机制起作用：进展停滞之后，技能把题目分了组，调查答案为什么被判错，找出了几道有歧义的题并重写了它们。解读下一个分数时，这个过程很重要。改技能，可以让应用把已有的题答得更好；改题目，则是把后续答案要对照的任务讲清楚。两者都能推动工作，但它们证明的是关于应用的不同事情。

被问到这个方法和 DSPy 有什么关系时，Martin 介绍说，爬山优化器是 Claude Code 自带的一个开源技能，核心是一组搭建优化循环的指令。开发者可以把这些指令搬到别的环境里用。Martin 认为这套指南或许可以改造成 DSPy 的形式，并向 Omar 和 DSPy 团队致谢。他自己没有用过 DSPy，所以只是把这当作一种可能的实现方式，并没有说自己验证过。

19

以当前分数为底线，同时搜索模型和思考强度

思考强度该怎么设，确实不太符合直觉，Martin 坦言他自己也觉得困惑。有了评测，他就能把这个选择变成一次搜索：先确定应用的基线表现，让爬山优化器在低思考强度下试不同的模型，同时比较分数和成本。一个个试下去，直到表现跌破基线为止。最后那次测量就算对应的配置永远不会上线，也很有参考价值：它标出了省钱开始以不可接受的质量为代价的那个点。

Martin 展示的对比图里就少了这样一个数据点：低思考强度的 Haiku 4.5 出现了明显退步。他特意把这个结果和 Haiku 5.5 区分开来，说后者是更好的模型；退步只属于他实际试过的 4.5 配置。这也说明，就算建议从低思考强度起步，仍然需要检查表现。一个强模型能便宜地解决某个任务，并不代表另一个模型在同样设置下也能做到。

如果没有评测，Martin 的起步建议是用 Opus 5.5 这样的强模型，配低思考强度。有人问为什么不选中等，他的回答是：工程师随时可以往上调。一开始就用最高强度，在还没有证据表明任务需要那么多推理之前，就先花掉了最多的钱。从低处起步，工程师可以先看看模型本来就能做到什么。Martin 把这当作一个合理的实验顺序；至于在没有质量衡量手段的应用里最终该怎么选，他就没那么确定了。

这里的经济账，取决于每个任务消耗多少 token。思考强度告诉 Claude 要想得多用力。一个单价更低的模型，在高思考强度下可能花大量 token 去推理；更强的模型在低思考强度下，用更少的思考 token 就可能得到同样好的答案。省下的 token 多到一定程度，就能抵消更高的单价。Martin 本来想说强模型的配置“更有效”，随即改了口：他说的优势是 token 效率，答案是否也更好，是另一个需要测量的结果。

20

给搜索设预算，让人来定义什么样的失败才要紧

爬山技能在设置阶段会要一个预算，并在每一轮中跟踪花了多少。这个预算覆盖的是实验本身；搜索最终选定的配置在每个任务上花多少钱，是另一回事。如果题集最后那 20% 根本做不出来，优化器可能会为了这几分花掉一大笔钱。仔细看看那些顽固的题目，能帮负责人判断还值不值得再买一轮。

关于 Claude 和人怎么分工，Martin 参考了 Hamel 公开使用 build-eval 技能的经验。以一个客服应用为例：在 Claude 读 trace 之前，得有一个懂产品的人先想清楚，一次客服交互里什么重要、为什么重要。客户满意度就是一个可能的关注点。把它讲明白，Claude 才有理由去标出特定的对话。如果只是把一堆 trace 丢过去，那么本该由产品做出的决定，就变成了模型碰巧觉得哪里有意思。

负责人把目标讲清楚之后，Claude 就可以读原始 trace，把应用看起来没做好的交互挑出来。Martin 把这比作一个带在线评估器的追踪系统，对话一进来就给客户满意度打分。两种情况下，第一步的产出都是一批待查看的候选。负责人读这些对话、弄清楚发生了什么，再挑出值得做成评测的案例。到这时再要求搭建题集，才既有了样例，也说得清它们为什么该放进去。

Martin 说，在 Anthropic，谁负责产品，通常就由谁负责评测，各种岗位的人都在做。像搭建评测运行器这样的工作，Claude 可以接手，负责人就不需要那么多专门的实现经验。留给负责人的，是判断什么样的结果算令人满意，以及认出哪些失误真正要紧。对于客服产品，一个能说清楚一次糟糕对话会带来什么后果的人，就能提供这样的指导，哪怕运行器传统上应该由别人来写。

21

把对生成式 UI 的反复偏好比较，变成配置之间的对比

被问到“模型当评审”的具体用法，Martin 想起一次对生成式 UI 的评测：两个配置 A 和 B 各自生成候选界面，评审看过这一对之后选出更好的那个。在大量试验中重复这个判断，得到的就不只是某一个页面的成败，而是关于两个配置本身的证据。Martin 记得结果被汇总成了类似 Elo 分数的东西。他对两两评审的流程比较有把握，对具体的汇总方法就没那么确定了。

这让开头那个网页的例子有了实际用途：单次判断，评审只要能认出自己更喜欢哪个就行，不必给出绝对分数；大量判断累积起来，回答的则是工程师的问题——到底该用哪个配置。Martin 也见过用语言模型评判检索和写作任务，以及把 trace 分成好和坏两类。这些用法都需要判断，只是判断的形式各不相同：从两个界面里选一个，和判断某一条 trace 是否值得关注，是给评分者的两种不同指令。

22

拆分好的评测集和可测量的损失，可以驱动同一种实验循环

Martin 认为，爬山的部分动机来自 autoresearch（自动研究），以及模型纠正自己工作的能力越来越强。前提是它们能拿到看得懂的反馈：模型跑一个实验，测量一个目标，查看结果，再调整下一个实验。在一长串尝试中，这种测量可以引导原本需要人一步步把关的工作。

讨论中出现了两种形式。Claude Code 的命令是为拆分好的评测集设计的，应用的改动要拿一批题目来检验。而在 Martin 描述的 autoresearch 里，系统会构建或修改某个产物，比如一个神经网络，然后测量损失之类的量。他不记得 Karpathy 那个例子具体是什么问题，只是用损失来说明可以拿到哪种反馈。前一种形式里，优化器能查看自己做错的题；后一种形式里，它能查看对产物做实验的结果。两者都有一个可观察的结果，可以据此决定下一次尝试。

有观众问，是不是应该先从爬山做起，再扩展到 autoresearch。Martin 认为这取决于你怎么定义问题。在 nanoGPT 这样的仓库里工作的人，可以试着把这个技能交给 Claude，让它把循环改造成适合那里的实验。他把这当作一个值得一试的方向。通用的流程其实很简单：做一个改动，测量结果，用结果决定下一步改什么。真正的适配工作在于，规定 Claude 能改什么、应该测量什么结果。

23

成本、质量和速度，让“哪个改动最好”变得更难判断

爬山优化器可以同时衡量不止一个目标。Martin 自己的例子是把成本和表现放在一起：可以把这两项都告诉 Claude，让它在比较候选改动时同时考虑。他还会考虑第三个维度：速度。一个配置可能答得又对又便宜，返回答案却更慢，光比较成本和质量是看不出这一点的。

Martin 主要试过的是成本加表现这一对。目标越多，下一个改动就越难选，因为不同的指标可能偏向不同的候选。他建议一次只改一样东西，让实验更简单。他没有给出把三个维度合成一个分数或者加权的方案。在思考强度的搜索里，现有的基线已经让比较有了具体含义：一个便宜但跌破质量底线的配置，就是没满足负责人的条件之一。

24

迁移时审查旧提示词，难题上要检查思考强度

回到提示词审查，Martin 说这是最简单、最值得先试的干预。提示词审查技能会找出目标模型已经用不上的那些旧写法。迁移到 5.5 系列的前沿模型时，删掉已知多余的指导，他很有把握；但要说从哪个版本开始这些写法过时了，他就没那么确定了。他的测试显示，一些老的提示习惯大概从 Opus 4.5 前后开始失去作用，但他不会把这个观察当成一条精确的版本分界线。

技能里也写了针对具体模型的注意事项。比如把应用迁到 Haiku 时，就有理由问一句：它是不是比前一次实验用的模型更需要明确的指导？Martin 把这当作一种可能性提出来，承认自己并不确定，并把答案拉回到实际要迁移的那个模型上。审查要做的，是找出对接收提示词的那个模型来说已知多余的指导；从最新版 Opus 身上总结出的规则，不一定适用于其他模型家族。

有人追问思考强度，这才讲清楚了这个设置到底管什么。Martin 说，它是在指导 Claude 应该为这个问题投入多少思考，并不是一个硬性的 token 上限。即使思考强度设得很高，一个简单问题也可能得到很短的回答，因为 Claude 仍会自己判断这个任务值得做多少验证。他手头没有评测能量化这种行为，所以只把这当作他对这个设置的理解。

Martin 会特别留意测量的，是困难的编程题。在超高或最高思考强度下，Claude 可能会比中低强度多花大量 token 去检查结果，最终结果却差不多。这说明，在简单输入上看到成本差别不大，并不足以证明整个应用都该开到最高强度。昂贵的差距，恰恰可能出现在那些会引发又一轮验证的难题上。

25

即使模型完全按预期工作，提示词优化也可能过拟合

Martin 同意，爬山在一个重要方面很像训练：给模型一个奖励或目标，再给它修改系统的能力，它就会去寻找能提升目标的修改。拆分训练集和测试集在两种情境下都有用。区别在于，这里的模型已经部署好了，能改的是提示词、技能这类运行时输入。应用负责人可以把训练中的实验规范，用到自己领域的这些组件上。

Claude 会不会知道自己正在被评测？Martin 承认，Anthropic 在训练的语境下讨论过“评测意识”这个问题。但在这些应用实验里，他实际看到的更直接的问题是过拟合。给 Claude 一份可以改的提示词和一个打分用的题目分布，它就能找到一种措辞，让分数大幅上涨，而这种措辞可能只对题集里的那些问题有效。这个结果根本不需要“Claude 发现了自己在被测试”这种特殊解释，它直接来自优化器手里的目标和样例。

拆分训练集和测试集，能给这种行为加一道检查：优化器用训练题来选改动，留出的测试题则单独看这些改动能不能推广到别的题目上。有观众问，数据集至少要多大、该怎么拆分。Martin 没有系统研究过不同的规模，所以既没给最小数量，也没给固定比例。技能里有一些经验规则，他建议和 Claude 一起，根据负责人想测量的信号来定一个合适的规模。

样例太少时，有三个问题会特别突出：样本可能漏掉重要的生产场景；很容易针对这几道题把提示词调到刚好合适；分数噪声大，结果变了也很难说是改动带来的。留出一部分测试题能解决一种过拟合，但训练集和测试集都来自负责人最初挑的那批样本，同样继承了当初挑选时的偏差。

26

一个任务要跑几个小时，每一轮迭代的成本都变了

Martin 通常会选提示词这类改起来很快的组件。有观众问到非常耗时的任务。在这种情况下，准备下一个候选方案可能是整个实验里最快的一步，负责人仍然得等智能体把任务跑完，才能拿到质量信号。一次失败的运行不仅花算力，还要花时间，而每多一轮，又要再等一次。

如果实验要跑好几个小时甚至好几天，框架本身就必须在这段时间里一直可靠。Martin 提到了 Anthropic 内部使用 Managed Agents 的情况。长时间的爬山优化是可行的，但基础设施故障和拿到反馈要多久，都会成为实验设计要考虑的因素。如果下一个决定要等一整天的工作结果，光把提示词改得更快，对加速整个循环帮助不大。

智能体通常也需要多轮评测。Martin 建议，把真实的 trace 交给 build-eval 命令，说明评测要是多轮的，并讲清楚负责人想检查什么。Claude 可以查看这些 trace，帮忙挑出要放进评测的交互。之后，评分者可以检查整条轨迹，包括智能体采取的一连串动作，也可以只看最终结果。前者回答的是“智能体是怎么做的”，后者回答的是“它最终完成了什么”。

27

上下文压缩之后，会话日志依然要能查

被问到哪种上下文工程技巧对提升可靠性最有帮助，Martin 提到了一个他和递归语言模型（RLM）联系在一起的思路：让上下文对象独立于模型和框架。在他描述的 Managed Agents 设计里，框架可以用工具去查询一份单独存放的会话日志。所以，Claude 当前工作上下文里的那些消息，只是智能体可用历史的一个视图。

上下文压缩最能说明这样做的好处。长任务做到一半，智能体会把消息历史总结一下，才能继续干活。这时它必须决定哪些细节重要、值得带下去，可它还不知道后面会遇到什么问题。如果这份总结是唯一留下的记录，被漏掉的细节就再也找不回来了。有了独立的日志，等某个细节变得要紧时，框架还能回到之前的交互，把它找回来。可恢复性来自两点：保留完整的记录，以及给框架一个能查询它的接口。

历史记录可靠了，还剩一个问题：怎么评判记录下来的工作。智能体的结果是不确定的，很多有用的任务涉及开放式写作或判断，没有容易验证的标准答案。Martin 又回到了那几条：清晰的评分规则、低波动，以及检查多个模型能否复现同一个判断。如果问题本身无解，或者评分者对几种合理的解读前后标准不一，优化器就算对着一条保存完好的 trace 干上几个小时，也可能毫无进展。在验证器设计上花的时间，决定了这样一次长时间运行能告诉负责人什么。

28

用值得保留的生产案例，给饱和的评测换血

随着模型进步，Martin 预计一套结构合理的现有评测，分数总体上会往上走。如果没有这个趋势，他会回头重新审视这套题集到底在测什么。另一个极端是，强模型可能很快就把一套题集做饱和了。持续设计能真正难住 Fable、Opus 5.5 这类模型的新题，是一项要反复做的工作。旧题集仍然可以检查团队已经做到的行为，只是越来越难分辨出新的进步。

Martin 最后介绍了他在追踪服务商那里见到的一套工作流程：线上的智能体产生 trace；在线评估器给它们打分，得分低的交互成为离线评测集的候选；团队针对挑出来的线上失败做爬山优化；等应用能处理好它们之后，这些案例就变成回归测试。同时，线上的智能体还在不断产生新的 trace，负责人可以去找下一个要紧的失败，也能看看线上观察到的失败率有没有下降。

Martin 提到，LangChain、Arize 和 Braintrust 等服务商都在做支撑这个外循环的工具，不过他没有密切关注它们最新的产品变化。他留给产品负责人的难题，在选平台之前就已存在：在线评估器把什么认作线上的好结果？哪些被标出的交互值得放进评测？这些决定，决定了下一轮优化改进的是不是用户真正能感受到的东西。

要点总结

  • 迁移模型时，先用新模型跑一遍旧提示词，再做审查。中间这一步能把“升级带来的变化”和“删掉过时指令对成本、质量的影响”分开。
  • 对比智能体前后两次请求，找到前缀开始不一致的第一个字节。共用的工具和指令放最前面，其次是项目上下文，最后是会话状态和不断增长的消息历史。用缓存命中率来验证效果。
  • 只把训练集里的失败交给爬山优化器，测试题不进入它的修改循环，每一轮都在两个集合上分别测量。做降本优化时，先定好质量底线，再同时搜索模型、思考强度和提示词。
  • 在信任一个开放式评分者之前，先自己用一遍它的评分标准，比较不同模型的打分，再重复评几次。如果二元判断或两两比较更容易做到一致，就把评分拆成几个二元判断，或改用二选一。
  • 评判开放式作品，可以试试两两比较。只有当人能说清相邻两档的区别、而且便宜的模型评审也能复现这种区别时，才用多档绝对评分。
  • 给爬山优化器设好预算，并留出测试题。进展停滞时，先把做错的题分组，检查题目和评分者本身，再决定要不要花钱跑更多轮。
  • 在同一批任务上，把模型和思考强度放在一起比较。从强模型加低思考强度起步，对照现有的质量底线测量每个任务的成本。
  • 长时间运行的智能体，要保留一份可以查询的会话历史。想清楚评测是评整条轨迹还是只评最终结果，再把要紧的线上失败转成回归测试。

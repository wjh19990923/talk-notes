函数调用与工具笔记本

幻灯片原文
The notebook defines a bill tool for a stationery-shop chatbot, with item name and quantity as inputs. The sample calculation uses the stapler price and a 10% discount.

Function Calling and Tools

Generally when users query an LLM, it returns responses based on it's existing knowledge, but sometimes users need context specific information or access to external APIs that the LLM does not have by itself. In this case function calling using tools allows LLMs to interface with user defined functions, APIs and external systems to generate these responses. First users define a set of functions or tools along with descriptions and usage instructions and then they send a prompt. Based on the user prompt LLMs can intelligently select and invoke the appropriate functions to accomplish these tasks.

Let's try to understand this using an example: Here we have the use case of a shop that sells several stationary items. The store sometimes has ongoing discounts and varying prices set by the owner. The store owner uses a chatbot for the user to inquire about the total price they have to pay if they want to buy certain items. In general an LLM by itself would not have the knowledge of the context specific store prices and discounts, and this is where we can make use of an external function. The LLM will recognize the need to use this external function will return the total price while adhering to the system message instructions we set.

借助 Azure AI 模型目录，从模型选择走向生产

跟随模型发现、部署、有据可依的聊天、函数调用和流程评测，看看一个共享的推理接口如何支持针对应用的模型选择。

熟悉 API 端点、聊天消息，以及“检索文档来辅助 LLM 回答”的基本思路，有助于理解演示。

01

AI 能解决这个用例吗——能规模化吗？

这个用例 AI 能不能做？哪个模型最合适？应用怎样扩展到生产环境？模型目录越来越大，做实验更方便了。但光看模型名气，这三个问题反而更难回答。应用需要一套流程：先确认可行，再把效果做好，最后稳定运行。

第一步是原型验证：多试几个模型，对比基准测试结果，筛出能完成任务的候选。接着针对应用的成本、延迟和区域要求做优化，视情况用提示词工程、检索增强生成（RAG）或微调。最后把应用投入运营，容量规划、成本管理、监控、扩展性、隐私和内容过滤都要到位。这三个阶段是一个循环：原型再有希望，也得针对具体应用做优化，才能成为生产负载。

这套流程不一定要用一个模型包打天下。Sharmila 问，客户是在同一个用例里用多个模型，还是在不同用例里用不同模型。Shubhi 说，模型目录让人能把模型直接接进应用，快速对比，换掉一个模型也不用重写周边代码。多试一个模型的成本足够低，模型选择才真正有用。

02

选择能力，而不只是模型大小

录制中展示的模型目录包括 GPT-4o、Mistral、Llama 和 Cohere 的模型，还有 Phi-3 和 Mistral 开源模型这类小模型。选型也不止文本生成，还涵盖多模态任务、图像生成和嵌入。模型大小只是一个因素。模型支持哪些操作、要处理什么数据，同样决定它适不适合。

- 工具与结构化输出： GPT-4o 支持函数调用和 JSON，适合智能体工作流，这类工作流需要把生成结果对接到应用操作上。 - 语言覆盖： Shubhi 特别提到 Mistral 擅长欧洲语言，Cohere 的多语言嵌入适合多语言检索。Jais 则提供了阿拉伯语选项。 - 开源与闭源： 数百个 Hugging Face 模型扩大了选择范围。Meta、Databricks、Snowflake 和 NVIDIA 都是把模型引入平台的合作伙伴。

03

检查一个模型、部署它并比较基准

演示从 Azure AI Studio 的模型目录开始。据 Shubhi 介绍，录制时目录里已有 1,600 多个模型。可以按部署类型、推理任务或模型系列筛选，这样找模型就能从应用需求出发，不必对着一长串名字挑。

按 Cohere 筛选，找到 Cohere Command R。它的模型卡介绍了定制、工具调用和 RAG 能力，还给出了 LangChain、LiteLLM 等集成的推理示例。模型卡既是能力说明，也是写应用代码的起点。标准化 API 的用意，是让这些集成能用在目录里所有受支持的模型上。

接下来是部署，从选定模型一路走到可计费的端点：

1. 查看定价，点击 Deploy。 2. 订阅该模型在 Azure Marketplace 上的产品，token 用量按这份订阅计费。 3. 如果已经订阅过，直接沿用现有订阅。 4. 填写部署名称，决定是否启用内容过滤，然后提交部署。

Shubhi 说，拿到端点 URL 和密钥一般不到一分钟。

部署进行时，演示打开了模型基准测试页面。准确性、连贯性和有据性（groundedness）是缩小候选范围的常用维度。回到部署页面，Shubhi 说这次部署几秒钟就完成了，目标 URL 和密钥可以直接写进应用代码。前面说的耗时，依据的就是这次实际观察，并非服务等级保证。

04

给同一个问题一个更好的来源

进 IDE 之前，可以先在 Chat Playground 里交互式地测试已部署的模型。Shubhi 选了一个现成的 Mistral Large 部署，问微软如何推广捐赠文化。没接自定义数据时，回答只讲了些笼统的举措，比如员工配捐计划和公开资料里的信息。

接着用 Add your data 把对话连到一个现有索引，名叫 Microsoft Give。再问一遍同样的问题，这次期待索引里的文档补上公司内部特有的上下文。这样对比才有意义：问题和模型都不变，只改变回答能用到的信息。

等待回答时，Sharmila 问微软或模型提供方会不会拿客户数据训练模型。Shubhi 保证，推理时的提示词和补全结果不会共享给模型提供方，也不会用来训练模型。这说的是推理数据怎么处理；为微调任务主动上传数据是另一回事。

返回的答案里有个具体细节：捐赠计划给新员工发放 50 美元额度。之前的回答里没有这一条。演示的改进不只是答案变长了，而是答案里出现了来自所连索引的信息。50 美元是 Playground 的输出结果，并没有另行核实过，不能当作现行的员工福利。

05

把基础设施选择与推理接口分开

刚才演示的部署用的是无服务器 API。模型目录还提供托管计算，两者的计费单位不同，由谁准备算力也不同。

| 部署方式 | 容量由谁负责 | 计费方式 | 录制时可选模型 | | --- | --- | --- | --- | | 托管计算 | 用户自行获取 GPU 容量并管理配额 | 按虚拟机使用小时计费 | 数百个开源模型 | | 无服务器 API | 现成的托管端点，开箱即用 | 按消耗的输入和输出 token 计费 | 据 Shubhi 介绍，有 30 多个旗舰或高级模型 |

无服务器路线通过 Azure OpenAI Service 和 Models as a Service 提供。选托管计算，GPU 配额和容量就成了应用必须自己操心的事；选无服务器 API，应用拿到端点就能开工，按用量付费。

在这些部署方式之上，还有一套共用的推理约定。Azure 与模型提供方合作，统一了 REST 接口格式和 SDK 结构，支持 LangChain 和各家提供方自己的 SDK 等集成。设想中的工作流是：换个端点，跑一遍评测，对比应用行为有什么变化。

统一接口格式带来的是接口可移植，不是模型能力一致。 后来发布的 Azure AI Model Inference REST API 参考文档把这条边界写得很清楚：模型可以拒绝自己不支持的参数。所以能不能直接换端点，要看能力是否兼容，包括应用需要的工具调用和输出格式。录制中用的是旧版 Azure AI Studio 界面，后来那份参考文档里的 API 示例，不能当成这里演示的确切版本。

06

用一个函数算出店铺的实际账单

文具店聊天机器人暴露出另一种“缺乏依据”的问题：模型也许知道订书机是什么，却不会自动知道这家店的价格和当前折扣。Shubhi 借助 Mistral Large 的函数调用能力，把对话接到一个 Get Bill Amount 函数上。模型负责判断该调用哪个操作、传什么参数，具体的业务结果则由应用里的函数给出。

工具定义向模型说明有哪些操作可以调用。系统消息则另有要求：帮用户算清要付多少钱，并就这些文具的使用给出环保建议。两项职责各管各的：账单金额来自外部函数，附带的说明由系统指令决定。

用户问 10 个订书机要多少钱，模型选中计费函数，给出商品和数量。在 Python 里，应用这一侧接手时可以把这条边界写得很明确：先校验请求的操作，再调用店铺的定价函数，最后把结果包装成工具消息，交给模型的下一轮。

```python import json from collections.abc import Callable

def run_bill_tool( tool_call: dict, get_bill_amount: Callable[..., dict], ) -> dict: function = tool_call["function"] if function["name"] != "get_bill_amount": raise ValueError("Unknown tool")

arguments = json.loads(function["arguments"]) item = arguments["item"] quantity = arguments["quantity"] if not isinstance(item, str) or not item.strip(): raise ValueError("Item must be a nonempty string") if type(quantity) is not int or quantity <= 0: raise ValueError("Quantity must be a positive integer")

bill = get_bill_amount(item=item, quantity=quantity) return { "role": "tool", "tool_call_id": tool_call["id"], "content": json.dumps(bill), } ```

这里的 get_bill_amount 属于店铺自己的应用。模型提出的参数本身定不了价格，执行这个函数才能定。

演示的最终回答是：10 个订书机共 45 美元，已含当前折扣。Notebook 里还显示了环保和安全提醒，这是系统消息起的作用。回答内容因此有两个来源：应付金额来自工具结果，怎么介绍这笔购买则来自指令。

Notebook 随后回到更通用的换端点工作流，同时在需要时保留各提供方特有的能力。其中 safe_prompt 设成了 true。这是 Mistral 专有的选项，并非公共接口背后所有模型通用的安全开关。

07

把检索构建成一个流，再更换模型

下一个演示从 notebook 代码转到 prompt flow，用检索流水线搭一个购物助手。基础版本很简单：接收用户问题，到索引里查相关信息，再把这些上下文交给 LLM 生成回答。Shubhi 在检索前加了一步查询改写：

1. 改写：把用户简短的问题扩写成更明确的搜索请求。 2. 检索：在索引中查找相关上下文。 3. 生成：用检索到的信息生成回答。

Shubhi 说，按他们的经验，把简短问题扩写之后，RAG 效果更好；不过没有给出量化对比。

计算会话启动后，示例从一个问题开始：“你们有新款徒步鞋吗？”改写步骤把它扩展成询问徒步鞋的库存、材质和功能。检索步骤随后输出从索引中取回的上下文，再交给生成步骤。看这些中间输出，就能分清问题出在检索还是出在生成。

旁白接着指出，生成的结果是一条女式夹克推荐。这和前面问的徒步鞋对不上。所以这段演示只展示了流程的各个阶段，并没有证明这个问题答对了。改写后的查询、检索到的上下文和最终回答，要放在一起评估。

为了不重搭流程就能对比模型，生成节点支持变体（variants）。它最初连接的是 Cohere Command R；再加一个变体，就能让同一个节点指向另一个模型连接。嵌入模型也可以换：演示用的是 Ada 嵌入模型，并提议让 Command R 搭配 Cohere 的嵌入模型。Shubhi 称后者为“Command Embed”，公开的产品名其实是 Cohere Embed，提议使用的具体部署标识在这里无法确认。

之前跑过的评测对比了 Cohere Command R、Llama 3 和 Mistral Large，目的是在同一个应用流程下，按各项评测参数比较输出。演示没有给出具体分数，也没说哪个模型胜出。真正值得借鉴的是这套评测方法：流程不动，换一个模型连接，看应用输出怎么变。

08

控制数据处理、模型完整性和访问权限

谈到企业场景，平台的管控分为三块：数据隐私、安全与合规、负责任 AI 与内容安全。Shubhi 回到前面关于推理数据的保证，明确说托管计算和无服务器 API 都适用：提示词和补全结果不会共享给模型提供方，也不会用来训练模型。

模型完整性又是一层防护。据介绍，HiddenLayer 扫描会检查模型里有没有嵌入恶意软件和后门、有没有常见漏洞和暴露（CVE），以及各层是否遭到篡改或损坏。Shubhi 说，这些检查必须覆盖标为 curated by Azure AI 的模型。要注意适用范围：精选模型要过扫描，不等于目录里每个模型都没有漏洞。

- 网络隔离： 借助专用网络，入站和出站流量都可以走虚拟网络；访问非 Azure 资源的出站流量，要通过完全限定域名（FQDN）规则放行。 - 模型访问： 与 Azure Policy 集成，可以给模型集合设允许列表和拒绝列表。 - 环境隔离： 开发、测试和生产环境可以分别套用不同的策略。

这几项管控守的是不同的边界：流量能走到哪里，应用能用哪些模型，每个部署阶段适用什么规则。

09

从内部辅助到客服自动化

客户案例又回到跨应用选模型的话题。EY 起初用的是 Azure OpenAI Service 里的模型，后来开始探索用 Llama 处理更具体的文档和摘要任务。它的 EY.ai 平台服务于专业工作，效率和准确性都很要紧。据 Sharmila 介绍，EYQ chat 已有 27.5 万名内部员工采用。录制中没有说明“采用”指开通权限、完成注册还是实际在用。

EY 在运营上的体会是：部署 AI 不是选一次模型就完事。性能要持续评测，生产使用也要始终符合负责任 AI 的要求。Sharmila 提到，EY 选这个平台，看中的是模型目录和 Studio 的评测能力：第一个应用上线后，模型选择还得继续。

CMA CGM 的业务横跨海运、陆运、空运和物流，是另一类例子。它在传统机器人流程自动化（RPA）的基础上，用目录里的一个 Mistral 模型做了聊天机器人，辅助客服人员。Sharmila 说，这个用例的响应延迟降了，客户满意度上去了，但没有给出具体数字。后续计划扩展到开票、客户文档分析、解读客户自由填写的文本，以及撰写邮件。

10

预测扩展了聊天之外的目录

Bridgestone 的例子跳出了对话应用，做的是月度需求预测，覆盖大量产品。它用的是 Nixtla 的 TimeGEN 时间序列模型。据 Sharmila 介绍，这个模型在录制前一个月的 Build 大会上登陆 Azure。目标是简化预测流水线、提高准确率、降低运营复杂度。

据 Sharmila 介绍，Bridgestone 用 TimeGEN 把预测误差平均降低了近 30%。录制中没说用的是哪种误差指标、跟什么基线比、怎么评估的。所以这个数字只是该客户报告的结果，不能指望其他预测任务也有同样的提升。

结尾把这些客户案例和开头讲的生命周期串了起来。Sharmila 认为，有了模型目录和 Studio 的集成工具，从开始用模型到产生业务价值，路径大大缩短，但她没有给出具体用时。两者的联系很实际：发现和原型验证确认可行，优化让模型适配任务，运营管控支撑生产使用。把这几件事连起来做，应用就能随着数据、需求和模型选择的变化不断演进。

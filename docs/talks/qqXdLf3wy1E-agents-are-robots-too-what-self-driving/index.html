智能体也是机器人：自动驾驶教会我的构建智能体之道

一个编程智能体需要的不只是强大的模型：它还需要一个可观测的环境、来自其行动的反馈，以及一个能从失败中学习的开发循环。

熟悉调用工具的智能体、shell 命令和基本的模型训练会有帮助；机器人学概念会在出现时介绍。

01

模型周围是什么？

要把一个能力强的模型变成能在真实世界里干活的智能体，需要什么？Jesse Hu 从自己在机器学习和机器人领域的经历出发，回答这个问题。他在 YouTube 和 Google 做过双塔 embedding、早期的 BERT 和混合专家模型；在 Waymo 负责数据、奖励建模和评测；现在在 Abundant 为基础模型实验室构建数据集，供它们训练编程智能体。这里谈的是机器人领域的通用做法，不涉及 Waymo 的内部系统。

Hu 把工程负担概括为“1% 是模型，99% 是其他一切”。这只是示意性的比例，不是实测出来的分配。在机器人领域，“其他一切”包括硬件、传感器、执行器、系统集成、部署、仿真和训练。模型再强，系统的大部分也还得自己搭。

数字智能体同样有身体。API 和 MCP 工具让它能采取行动；终端、浏览器和虚拟机给它提供更丰富的环境；操作系统和持久化文件系统又让这具身体进一步扩展。真正该比较的，不只是语言模型和机器人的大脑，而是两个完整的系统：它们都能感知周围环境，也都能改变环境。

两类系统还都需要一套离线技术栈：仿真与训练、持续重训、监控，以及人类反馈闭环。Hu 提到自动驾驶圈里反复出现的一个说法：最强的团队能胜出，离线工具的功劳可能不亚于模型或运行时。开发基础设施越好，工程师就越能把行为查清楚、迭代得更快、交付得更稳。

02

命令不等于它的结果

把方向盘往左打。车实际转了多少？光看指令回答不了：执行机构并不完美，控制器必须测量结果再做调整。这次测量把预期运动和实际运动连成了闭环。闭环控制用一个动作的后果来指导下一个动作。

放到编程智能体上，对应的就是一条长时间运行的 Bash 命令。如果智能体在进程运行时看不到输出，判断不了它有没有结束，也没法提前终止，它就丢掉了关键的反馈和控制。启动进程只是第一步，接口还得支持观察和干预进程的执行。

03

对话话轮决定了智能体何时能做出反应

机器人领域会把输入设计摆到明面上。系统可以通过视觉、激光雷达、毫米波雷达或它们的组合来观察。它还得决定什么时候观察：定期观察、事件到达时观察，或者按更快的固定节奏观察。Hu 举了 50 Hz 的例子，也就是每秒观察 50 次，定期采样世界状态。反复观察让控制器能随着世界变化更新状态估计、重新规划。

智能体往往沿用了对话的节奏：走一轮，调一次工具，等完整响应回来，再走下一轮。就算没人刻意这么选，这也是一种设计选择。

| 交互模式 | 让什么更容易 | 限制了什么 | | --- | --- | --- | | 完整的对话轮次 | 逐一推理每次输入和输出 | 工具还在运行时难以及时反应 | | 反复观察世界 | 随条件变化更新计划 | 需要处理持续发生的变化 |

轮次带来清晰的边界，但边界也可能变成延迟。智能体在等工具返回时，可能没法立刻应对弹窗，也没法干预长时间运行的进程。关键问题是：环境什么时候能告诉智能体，它的计划得改了。

04

选择一个动作意味着什么

手写的工具，以及来自工具或用户的数据流，只是可选接口中的几种。Terminal-Bench 的 Terminus 用的是一个交互式 tmux 会话。Hu 特别强调字符级交互，包括 Control-C 和窗口命令：智能体可以直接操纵终端会话，不必把每条命令都当成不可拆分的一问一答。这些能力由接口提供；观察频率如何，仍取决于智能体怎么用它。

举个例子，Bash 控制器可以在一个分离的终端里启动进程，查看输出，之后再发送中断：

```bash # 启动一个示例用的长时间运行进程。 tmux new-session -d -s agent-job \ 'bash -c "while true; do date; sleep 1; done"'

# 观察终端当前的内容。 tmux capture-pane -p -t agent-job:0.0

# 当某次观察或用户请求要求停止时： tmux send-keys -t agent-job:0.0 C-c ```

关键在于把启动、观察和中断拆开。在这几步之间，控制器可以自己决定接下来做什么，不必干等原进程返回。

机器人领域在不同层级上也有同样的自由度。一个动作可以是“向上移一格、横移两格”，也可以是指定连续空间里的一个点。它可以在二维或三维空间中进行，控制的可以是位置、速度或加速度。每种表示方式都让一些行为容易表达，另一些行为则很别扭。对智能体来说，类似的选择有结构化的 MCP 调用、终端字符，或者更底层的鼠标键盘操作。

Hu 提到一个 Dreamer 的例子：以每秒 20 帧的频率进行鼠标和键盘交互。演讲没说具体是哪篇论文；相关的 Dreamer 4 论文 确实用了这个频率，但场景是 Minecraft，不是通用的桌面自动化演示。这个设计问题依然值得一问：一个动作接口开放了哪些能力，又让智能体无法表达哪些？

05

会话结束时，世界并不会重置

赛车游戏可以在一局开始时生成一辆车，结束时直接丢掉。真实的车在任务开始前、结束后都实实在在占着空间。它怎么开过来的、会停在哪、车速多少、周围车辆怎么动，全都有影响。任务发生在一个持续运转的世界里。

编程智能体正在经历类似的转变。一次性会话可以产出一个成果，然后消失。持久化 VM 则会保留正在运行的进程和文件。智能体加入一个团队，也就进入了正在进行的工作，比如已有的 Slack 对话。它要考虑自己接手的整个环境，而不只是启动会话的那条指令。这既改变了运行时的行为，也改变了评测和仿真要想有意义所需的初始条件。

06

小错误会改变下一个输入

模仿学习用示范数据训练，就像监督微调用人类示例训练编程模型。强化学习是另一条路，仿真可以作为它的训练环境之一。Hu 介绍了 DAgger，作为理解模仿学习中分布问题的背景知识；它属于模仿学习，不是 RL 的别称。

难点在于，智能体未来的输入有一部分是它自己造成的。一旦行为偏离示范路径，它就可能遇到训练样本里没见过的状态。浏览器弹窗就是个具体例子：人自然而然就处理了，没学过这种情况的智能体却可能懵掉。它的下一个错误又可能把它带得离熟悉的状态更远，最后引发一连串失误，而不只是一次孤立的预测错误。

07

模拟后果，而不只是预测

一个动作，会改变智能体接下来要解决的问题。 分类器只给出一个预测；智能体则要预测、行动、承受后果，再回头审视先前的决定。这些后果在一个混乱的世界里展开，最初的计划可能很快就和现实对不上了。

仿真提供了一种办法：先在初始状态里把这种混乱表示出来，再探索接下来会发生什么。仿真器不只评测已经观察到的那条路径，还能在智能体行为变化时推演其他路径。这就是反事实推演：从同一情境出发的不同可能走向。在 Hu 的测试金字塔里，仿真位于测试场测试和线上生产之下，是探索“会带来后果的行为”的基础设施之一。

马尔可夫决策过程（MDP）为这个循环提供了一套术语：智能体接收状态和奖励信息，选择一个动作，作用于环境，环境再产生下一个情境。这套形式化的价值在于方便沟通。团队在决定智能体能观察什么、能控制什么、行为怎么评测时，有了可以精确讨论的对象。

08

理解场景并不等于完成任务

Hu 认为，2017 到 2020 年的自动驾驶工作高度聚焦于感知：识别物体，给它们画框，然后假定绕着这些框开车会相对简单。这个假设掩盖了选择和执行动作的复杂性。看懂场景，不等于能开过去。

语言智能体面临类似的鸿沟。模型也许能读懂一段详细描述，生成一长串精巧的推理 trace，可一旦计划落成一连串真实的工具调用，就可能失败：某次调用报错，进度卡住，或者智能体改不了自己的错。在 Hu 看来，剩下的工程工作大多集中在这个“执行—恢复”循环里。

尽管如此，汽车和代码的起点格外有利。Hu 对比说，自动驾驶已经在有限场景中投入生产使用，而其他很多机器人技术还停留在演示阶段。汽车本身就有成熟的人类操控装置、电子化的执行机构和内置的遥测系统。它既提供了执行动作的接口，也提供了收集“到底发生了什么”的证据的接口。

编程也有类似优势：动作是预先定义好的，结果看得见，软件因此既方便操作，也方便从中学习。需要用到整个桌面的知识工作，往往更难规范化。选新领域时，可以问两个相互关联的问题：现成的人类界面能不能让动作容易执行？它暴露的信息够不够观察这些动作的后果？

09

用部署中的失败指导下一个实验

改进智能体是一个爬山式的过程。在传统应用里，实现一个功能，通常就相当直接地交付了这个功能。而对智能体来说，一次工程改动往往只是一个“能提升某项指标”的假设。跑一遍实验，分数可能涨，也可能跌。进步来自反复实验，而不是默认每次实现都会增加能力。

自动驾驶的开发循环把这些实验和真实世界连了起来：

1. 学习： 利用已有证据改进模型或系统。 2. 仿真： 部署前检查行为，仿真既支撑学习，也给部署提供信心。 3. 部署： 让系统面对真实条件。 4. 收集日志： 记录在这些条件下发生了什么。 5. 反哺仿真： 用这些日志让下一轮仿真场景和实验贴近真实。

回流这一环很关键。没有真实世界的证据回灌，仿真就可能慢慢偏离已部署智能体实际遇到的情境。

Hu 用一个假设的 70% 基准分数，说明汇总数字的局限。分数能给出大致信号，但要按类别、城市和失败模式拆开看，才知道行为在哪里出问题。逐个检查失败案例，团队就能知道该改什么、在哪儿再做一次实验最可能见效。Hu 说，这套分诊流程是 Abundant 工具链的核心，也是他们帮客户改进系统的核心。

10

从令人惊艳的演示到完成的工作

Hu 的最后一张幻灯片显示，真实工作的自动化率只有 2.5%，标注为 RLI。它引用的是 Remote Labor Index，并把智能体的现状比作 2015 年的自动驾驶。这个数字应该理解为端到端完成工作的一次基准快照，而不是对当下整体经济自动化程度的估计。预测能力很强的模型、令人惊艳的演示，离可靠地把活干完仍有不小的差距：动作会带来后果，真实环境会冒出各种复杂情况，计划得扛得住才行。

要补上这段差距，需要把反馈、观察时机、动作接口、持久化状态、仿真，以及改进系统用的基础设施串在一起。Hu 提议用 agentics 来命名建立在这些概念之上的实践：它应该是一个有可复用抽象和科学方法的领域，而不是一个接一个临时拼凑的智能体实现。

推荐的阅读路径，正好对应智能体开发者已经会碰到的问题：想理解反馈，看开环控制和闭环控制；想描述世界，看 MDP 以及完全可观察与部分可观察环境；想解决模仿学习的分布偏移，看 DAgger；想从经验中学习，看离线 RL、强化学习入门和近期的机器人学文献。把这些概念和卡住的进程、意外的弹窗、持久化环境对上号，就更容易理解。智能体在世界中行动，会犯错，也得能恢复。构建这种恢复能力，本身就是构建智能体的一部分。

延伸阅读

  • Terminus: the original agent design — Explains the tmux-based terminal interface, keystroke actions, external execution process and sandbox assumptions.
  • DAgger: imitation learning under induced state distributions — The original paper on collecting expert labels for states encountered by a learned policy and aggregating them across training iterations.
  • Remote Labor Index: original results — The October 2025 launch report evaluates complete freelance deliverables across 240 projects and explains common failure categories.
  • Dreamer 4: Training Agents Inside of Scalable World Models — Studies offline Minecraft learning from pixels and mouse/keyboard actions, with reinforcement learning performed inside a learned world model.
  • Dreamer 4 demonstrations — Shows Minecraft agent evaluations, imagined training trajectories and human interaction with the learned world model.

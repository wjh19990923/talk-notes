打造 Floyd：一个会打电话的 AI 助手

一个语音请求通过响应式数据库查询、个人上下文和流式语音流水线变成了一通电话——而现场通话暴露出了它的局限。

熟悉 React hooks、TypeScript 以及 HTTP 或 WebSocket 连接，有助于跟上代码讲解。

01

一个私人助理实际上会做什么？

日历事件、提醒和计时器，只占私人助理工作的一小部分。除了跑腿，大量工作要靠电话和邮件完成。AI 助手能不能足够了解用户，替用户和另一个人把这些对话办妥，又不让对方觉得别扭？Convex 开发者体验负责人 Tom Redman 从这个问题出发：把实时语音识别、个人上下文和近乎实时的语音合成组合起来，做一个能打电话办事的助手。

这个原型叫 Floyd，因为 Redman 把《明星伙伴》（Entourage）里私人助理 Lloyd 的名字记错了。运行它需要四样东西：开通了语音转文字的 Google Cloud、一个 Convex 账号、一个 OpenAI key 和一个 Twilio 账号，每一项都要在环境变量里配好。项目配有 Floyd workshop 仓库。workshop 期间，Redman 说明仓库还没上 GitHub，并承诺会后通过 Slack 分享。

02

数据库就是交接点

以预约牙医这样的请求为例。手机或网页客户端把用户的语音流式发给 Google Cloud，拿回转写文本，再把请求文本和发起请求的用户存进 Convex。客户端就靠这次写入把任务交给后端。

服务器订阅了一个监听新请求的响应式查询（reactive query）。它不轮询，客户端也不用另外通知它有活来了。查询结果一变，服务器就接手请求，并写入进度状态。客户端有自己的订阅，这个状态会通过同一套数据库机制出现在界面上。派发请求和汇报进度，共用同一条持久化记录。

03

准备上下文，再开始对话

一句简短的请求，背后要用到很多用户不会再说一遍的信息。给孩子的学校打电话，得知道是哪所学校；预约汽车保养，可能要知道车型和常去的修理工。按设想，Floyd 的记忆来自三个地方：历次请求、用户主动提供的信息，以及邮箱这类可能接入的数据源。用户想提供多少都行，缺了什么，助手会主动问。每个任务开始时，服务器都会在请求上保存一份当下的上下文快照，和请求人、请求文本放在一起。

通话开始前，GPT-4o 会拿到请求和对应的上下文。服务器先让模型做好准备：接下来和它对话的，是接电话的人。目标号码通常来自已有的用户上下文。根据用户位置查找商家是设想中的扩展，这里没有实现。如果真搜不到，Floyd 可以发短信问用户有没有常去的商家。

接通后，对话按下面这条流水线循环：

1. 模型生成对话回复。 2. OpenAI 文本转语音把回复变成音频。 3. Twilio 把音频传给电话那头的人。 4. 对方的回答流式发给 Google Cloud 转写。 5. 转写结果回到模型，开始下一轮。

这个循环一直跑到对话结束。有观众建议用多模态的 Gemini 直接接收音频，省掉单独的转写步骤。Redman 还没试过。他把各个服务的边界设计成可替换的，正是为了方便做这类实验。

通话过程中，服务器把转写条目追加到 Convex 里的请求上。用了 useQuery 的 React 客户端会自动收到更新后的结果。换成本地 useState，就得手动更新；订阅查询则让数据库写入直接驱动界面上的转写内容。用户不用接入媒体连接，也能看着对话一步步展开。

04

给学校打电话

现场演示时，所有目标号码都改成了 Redman 自己的手机号。他扮演接电话的商家或学校，原型并没有联系真实商家。他让 Floyd 给学校打电话，说 Mara 生病了，今天在家休息。他一停下来，客户端就自动提交请求，并显示请求 ID。接着，他的手机响了。

Redman 以 Mara 学校的身份接起电话。Floyd 自我介绍说是代表 Tom Redman 打来的，告知 Mara Redman 生病在家。对方接着追问：她没事吧？什么时候能回来？Floyd 说她希望本周结束前能回来。口头请求里并没有提到返校日期，演示也没交代 Floyd 这个答案从哪来。

对话礼貌地收了尾，但每轮之间的停顿很明显。Redman 认为延迟是关键，打算接下来试试生产环境配置和其他模型。他还提到用 Opus 实现高效的电话音质流式传输；后面讲解媒体处理时会说明，这里说的编解码器和发给 Twilio 的音频格式是两回事。

通话背后有一份行动计划，在 Floyd 对商家开口之前就已生成。提示词让 OpenAI 扮演队友：这是请求，这是我们对用户的了解，这是要完成的任务。以给学校打电话为例，计划会提取出 Mara 的全名、学校、缺勤原因、当天日期，以及完成请求需要的步骤。服务器把这份计划作为额外的对话上下文喂回模型，但不会念出来。

应付自动语音菜单是另一项工作。Redman 既没试过，也没做专门支持，不过他认为这个问题能解决。他的第一个实验瞄准更没把握的部分：和真人把对话进行下去。请求详情页也会实时显示陆续到来的转写。

05

订花——以及知道何时停下

下一个请求是给 Krista 订花。Redman 扮演 Sweet Violet’s Flowers 花店接电话，界面上同时出现了行动计划。Floyd 要求当天送达。被问到要什么花时，它说 Krista 喜欢店里常卖的那些，请对方推荐一款受欢迎的。

花店推荐芍药和玫瑰，价格 560 美元。Floyd 先说了句“听起来不错”，又问当天能不能送到安大略省 Guelph 的一个地址。花店问 Tom 的信息是不是已经存档，Floyd 反问需不需要再提供一遍，随后突然说得回头再打过来。演示里没有完成购买。

这样退出是有意设计的：助手有一条“撤退”指令，缺少对方需要的信息时就挂断。Redman 说，下一步是给用户发短信，说明没有预算、花又很贵。这条短信只是设想中的后续动作，演示里没看到它发出。实际演示的能力更有限：Floyd 能中止通话，但在那之前，它已经口头接受了报价。

接着，Redman 在 Convex 控制台打开存好的订花请求，补上“没有预算”，然后保存。客户端立刻显示了修改后的请求。追加的转写条目能出现在界面上，靠的也是这套机制：数据库 mutation 改变了被订阅的查询结果。控制台里也存着用户上下文。Redman 明确说这只是概念验证，离生产环境的最佳实践还很远。这次编辑演示的是数据同步，订单既没有恢复，也没有完成。

06

把电话连接与界面分开

最初的目标包括把通话转写实时推回给用户，最终还要让用户能实时收听通话。Redman 一开始想把所有功能都放进一个部署在 Vercel 上的 Next.js 应用里。Socket.IO 帮他搞定了最初的部分转写功能，但在这种 serverless 托管环境下，Twilio 有状态的 WebSocket 音频连接很难处理。这是 2024 年实现时的限制；2026 年 6 月，Vercel 宣布 Fluid compute 上的 Functions 支持 WebSocket，但仍受函数本身的限制。

改版后的设计把需要长连接的媒体处理交给一台 Express 服务器。它负责打电话，并把更新写入 Convex；前端只订阅自己需要的数据，既不用持有通话的 socket，也不用轮询进度。界面和数据库视图并排摆着，拆分的效果一目了然：Floyd 里显示通话转写，Convex 的 sessionUsers 记录里存着个人上下文。

代码库仍然可以共用。Convex 的 schema、后端函数和 API 可以和前端代码放在一起，但它们部署到 Convex 服务器上，不会打包进浏览器。如果托管平台支持所需的持久 WebSocket，媒体服务器的部署形态也可以换。代码放在哪里，和代码在哪里运行，是两个独立的决定。

07

一个查询把 React 看板与服务器状态连接起来

讲到前端时，一个订阅查询就拿到了整个请求数组。前端面板把这个数组渲染成列表，再用选中请求的数据填充详情面板。匹配的请求一有变化，查询结果就跟着更新，React 随即渲染新状态。

前面的架构草图和实际查询有个重要区别：原型里的 get 函数不区分用户，应用也没有身份认证。所以在这个实现里，设想中的按用户订阅并不能起到访问控制的作用。

自动生成的标识符 api.requests.get 把 React 订阅和导出的 Convex 查询连了起来。下面这个最小组件展示了数据流，没有在本地 state 里再存一份查询结果：

```tsx import { useQuery } from "convex/react"; import { api } from "../convex/_generated/api";

export function RequestInspector() { const requests = useQuery(api.requests.get);

if (requests === undefined) { return <p>Loading requests…</p>; }

return <pre>{JSON.stringify(requests, null, 2)}</pre>; } ```

Convex 根据后端函数生成带类型的 API，文件一改就自动更新。查询的实现留在服务端；导入它的 API 引用，不会把数据库函数打进浏览器包。

Redman 介绍说，Convex 的 V8 执行环境紧挨着数据库，并强调了它的速度，以及应用不必再自己管缓存。更准确地说，TypeScript 先编译成 JavaScript，再在 V8 里执行；这并不意味着每个函数和数据库操作都跑在同一台物理机上。对 Floyd 来说，架构上的好处是客户端直接用订阅结果，不用自己搭一套失效和刷新机制。

08

后端函数、HTTP 操作与调试

为什么选 Convex，而不是 MongoDB、DynamoDB 或 Postgres？Redman 的回答围绕开发体验：schema 驱动的类型安全一路贯通到前端，编辑器能自动补全，要维护的基础设施代码也更少。他更进一步的说法是，这能减少对专职后端或基础设施人员的需求。Floyd 的请求后端只有几个操作：获取所有请求、按 ID 获取单个请求、获取待处理请求、提交请求。

HTTP action 提供了另一个入口。它可以定义 GET 或 POST 端点，返回任意响应，访不访问数据库都行。演示中，一个 POST 路由运行 action，更新存储的请求数据。单独的 Express 进程仍然保留，因为 Twilio 的音频流要靠它处理。

讨论到的几种调试工具各有分工：

| 工具 | Redman 用它做什么 | |---|---| | 控制台日志 | 查看请求和运行时输出 | | 控制台函数运行器 | 调用函数、查看返回结果 | | 本地编译输出 | 开发时发现错误 | | 服务端断点 | 是否支持，workshop 上没有给出答案 |

控制台既能看日志，也能看函数定义。被专门问到 Convex 服务端代码能不能打断点时，Redman 说他不清楚，答应会后跟进。他自己调试靠的是日志和本地编译报错。

09

从待处理请求到接通的电话

Express 服务器里有自己的 Convex 客户端，订阅的是待处理（pending）的请求——客户端新建请求时，默认就是这个状态。worker 随后按下面的顺序干活：

1. 确认请求存在。 2. 把状态从 pending 改成 in-flight。 3. 取出完整请求和会话名。 4. 收集该用户存储的上下文。 5. 从中筛出和本次任务相关的信息，存到请求上。 6. 发起通话。

前面说的响应式交接，具体就是这样实现的。Redman 也指出这个设计还要打磨。状态切换是演示过的流程，并不是生产环境任务协调的完整方案。

调用 Twilio 会开启一段异步交互。通话配置告诉 Twilio 把状态回调和流数据发到哪里。开发阶段用 ngrok 把 Express 服务器暴露出去，Twilio 才能访问到它。服务器负责处理通话生命周期通知，以及从 WebSocket 连接传来的媒体数据。

要把这些事件和用户的任务重新对上号，关键在于请求 ID。Redman 通过通话配置把它带进回调地址。Twilio 回连时，媒体流处理器取出这个 ID，查到对应的请求。这样，通话就能找回自己的指令和上下文，不必指望最初那次函数调用还在运行。

10

音频块变成对话话轮

传入的媒体交给一个反复触发的消息处理函数。Redman 的说法是，应用在对方说完一句话后收到音频；他还讨论了用固定分块、停顿或标点来切分。别把这种说法和传输协议混为一谈：Twilio Media Streams 传的是带序号和时间戳的原始音频块，不是按标点切好的语音。应用自己的轮次处理逻辑建立在这些媒体消息之上。

传入的音频先转换成适合 Google Cloud 识别的格式。返回的转写进入对话，生成的回复再交给语音合成函数。发出去的音频要转成 μ-law，再做 Base64 编码，然后发给 Twilio。Twilio 文档规定的传输格式是单声道 8 kHz μ-law；Base64 只是载荷编码，不是另一种音频编解码器。这和前面把 Opus 当作流式传输优化的讨论是两回事。

最后的序列化步骤可以直接用 TypeScript 写出来：

```typescript import { Buffer } from "node:buffer";

export function encodeTwilioMedia( streamSid: string, mulawAudio: Uint8Array, ): string { return JSON.stringify({ event: "media", streamSid, media: { payload: Buffer.from(mulawAudio).toString("base64"), }, }); } ```

这里的 mulawAudio 必须已经是格式正确的音频字节。Base64 编码不会重采样，也不会转码。

处理媒体的同时，一个客户端 mutation 会把 Google Cloud 返回的每条新转写追加到 Convex。前端的查询订阅再把这些变化推到转写视图上。音频传输和转写展示共用同一个请求 ID，但不必走同一条连接。

11

接通时争取时间，再建立信任

第一轮对话有个特殊的延迟问题：对方接起电话后，识别、对话、合成这条流水线才开始运转。Redman 加了一段预先生成的开场白，让 Floyd 能立刻开口，不用等整条链路跑完。他怀疑现场演示时这段开场白没生效。

录好的开场白播放时，第一轮对话循环同时在跑。开场白说明 Floyd 是代表客户打来的，为后面针对具体任务的内容争取时间，比如在 Brock Road Garage 预约换机油。这个做法是让有用的话和启动工作同时进行，并没有让底层服务本身变快。Redman 说，能让接电话的人体验更好的小改动有好几处，这是其中之一。

按设计，开场白还会表明来电的是 AI。Redman 不希望 Floyd 隐瞒自己的身份。它的定位是购买服务，或者处理取消预约这类日常变更，绝不推销。他的假设是：商家会接受正当的购买来电，也可能慢慢学会和助手高效打交道。

有观众提出，商家也可以有自己的智能体。这又暴露出一处短板：如果通话另一方让它忘掉指令，原型毫无防备。Redman 明确说，这种提示词注入风险正是不能上线的原因之一。他还说，如果双方最后都派智能体去商定预约，这种交流就开始像 API 之间在对话了。

12

测量让人等待的各个阶段

有观众问，开头的延迟是不是 serverless 冷启动造成的。Redman 说 Convex 没有预热延迟，它的部署始终在运行，而且围绕 WebSocket 构建。他还顺带对可扩展性做了一个笼统的判断，但他对延迟的诊断来自语音流水线上的埋点：转写耗时、拿到对话回复的耗时、合成回复的耗时。他没有展示分阶段的基准测试表。

延迟越拖越长，一个已观察到的原因是对话历史。每次请求模型都要带上之前的对话，通话越久，提示词越长。Redman 说，对话越长，延迟往往越严重。他打算缩减提示词，并试试 OpenAI Threads API——做这个功能时他还没用过。这些都只是计划中的实验，workshop 并没有演示 Threads 能降低延迟。

Redman 说，在这个原型里，用 OpenAI 文本转语音合成三句话可能要 2 到 5 秒。这个观察没说明用的是哪个模型、测了多少次、从哪里开始计时，所以只能用来描述演示系统的延迟，不能当作服务的基准数据。他的实现里能调的东西不多，他会考虑花钱换更低的延迟，或者换一家语音合成服务商。

整条链路上，处处都有优化空间：

- 对话生成：减少每轮发送的历史。 - 语音合成：找延迟更低的服务或配置。 - 端到端编排：降低每个服务的延迟，因为每一环的等待会累加成来电者听到的停顿。

Redman 说，还有好几项重要的优化没试过。他预计，靠服务商自身的进步，系统六个月内不改应用代码也能快一倍——他明确说这是押注，不是实测结果。模块化架构留出了余地，等服务变好后，可以验证这个判断。

13

原型背后的基础设施押注

最后一个技术问题关于 Convex 的内部实现：查询怎么分布，底层跑的是什么数据库基础设施。Redman 介绍说，这是一个用 Rust 从零写的数据库，代码已经开源。他说领导团队里的 Jamie 和 James 是他加入 Convex 的原因之一。James Cowling 在 MIT 读博时研究的是大规模分布式事务处理和共识协议——Redman 讲这套系统的由来时，看重的正是这份数据库功底。

按 Redman 的说法，Convex 的数据库和应用都跑在一个 AWS 集群上，WebSocket 连接和订阅也在其中。物理上怎么分布超出了他的专业范围，他没有细答，表示会后跟进。他说已经有大客户在用，到目前为止没遇到根本性的扩展问题，但没给出量化数据。想了解实现细节，他推荐看 Convex 后端仓库，以及首席科学家 Sujay Jayakar 写的 How Convex Works。

放着 Postgres 这类熟悉的选项不用，自研数据库是一场押注。Redman 的理由是开发体验和产品迭代速度：让基础设施工程师把时间花在客户真正需要的东西上，而不是去维护数据库备份。Floyd 让这个取舍变得看得见、摸得着。请求状态和实时更新有了共同的落脚点，剩下的工程精力就能集中到让电话助手真正好用的地方：把事办成，处理好缺失的信息，让接电话的人觉得这通电话聊得顺。

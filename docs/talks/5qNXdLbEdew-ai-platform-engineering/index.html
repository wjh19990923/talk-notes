AI 平台工程：从试点团队到生产环境

在整个组织中规模化应用生成式 AI，需要共享的基础设施、务实的赋能，以及帮助应用团队构建和运营有用产品的治理。

熟悉应用开发、API 和基本的部署实践会有帮助；不需要模型训练背景。

01

第一个 AI 试点之后会发生什么？

你的团队正在试验 GenAI。要让组织里的其他人也用起来，需要什么？Patrick Debois 借一次更早的变革来回答这个问题。2009 年，他组织了第一届 DevOpsDays，当时约有 60 人参加；此后，他亲眼看着 DevOps 在企业里铺开。这段经历提供了一个有用的视角，但他也明确提醒：拿旧范式套新技术，可能看出规律，也可能完全看错。

他对 GenAI 的兴趣始于自动化智能（automation intelligence）。他在 DevOps 领域做的很多事，都是把流水线自动化、做稳，并确保它们真正产生价值。AI 延续了这项工作，也带来了一个老问题：一项看起来很有前景的能力，怎样才能变成组织可以稳定依赖的东西？

技术推广从一个试点团队开始。接着又有两三个团队试用，从他们的经验里提炼出可复用的模式，再靠这些模式推动更大范围的采用。云基础设施就是这么走过来的。共享的抽象层最终让应用团队可以在各自领域里跑得更快，不必弄懂底层基础设施的每个细节。

这个实践至今没有定名，但名字本身也有用处。Debois 回忆起当年围绕 DevOps 这个名字的争论，更早的敏捷和 ITIL 运动也吵过类似的架。像 AI engineer（AI 工程师）这样的标签，能帮人们找到新出现的案例和招聘信息，也能帮他们找到彼此。太早把它定义死，反而会限制这个实践的发展方向。

02

生产工作改变了团队

Debois 做了两年 GenAI 应用。据他观察，组织里的第一道摩擦出现在活儿落到数据科学家手里的时候：他们不习惯运维生产服务。于是工程师开始加入数据科学团队。集成工作占比越来越大，工程这一侧的分量也跟着上升。之后，这些能力扩散到其他团队，最终沉淀进平台。

这次转移也让原本孤立在数据湖里的数据，重新和需要它的应用连了起来。Debois 称之为“右移”（shift right），与安全领域的“左移”相对：团队弄清摩擦真正出在哪里，职责就跟着移到哪里。

把开发和运维拉进同一个房间只是开始；长期、高强度的协作没法在整个组织里规模化。Kubernetes 流水线、基础设施和安全工具逐渐变成了共享能力。Team Topologies 脱胎于 DevOps Topologies，它为这种安排提供了一套说法：功能团队在平台之上构建并运行自己的应用。

平台团队可以用三种方式和这些团队互动：

| 互动方式 | 平台团队做什么 | |---|---| | 服务消费 | 提供团队可以直接调用的 API 或服务 | | 协作 | 和团队一起打磨它需要的能力 | | 赋能 | 帮团队解决问题、学习新东西 |

平台是一款产品，应用团队就是它的客户。 平台要做的，是让传统应用开发者在数据科学专长的支持下，在自己团队里交付 AI 功能。

03

模型访问与可复用的数据基础设施

平台的第一项能力是模型访问。与其让每个团队各自调研供应商、申请权限，不如由平台团队判断哪些适合公司。这个选择常常受现有云服务合作关系影响，所以 CloudOps 自然成了协作方。Debois 在这部分提到的厂商只是举例，他并未声称和它们有关联。

检索增强生成（RAG）带来了第二层：向量存储与检索。专门的向量数据库很早就出现了，传统数据库厂商也越来越多地加入向量能力。这类基础设施因此不再那么新奇，但团队仍要理解向量和嵌入（embedding），才能用好它。幻灯片上把 Chroma、Vespa、Milvus 等产品和 PostgreSQL、Redis、SingleStore 并列。

光有向量数据库，并不能把应用接到公司的知识上。平台还需要数据连接器，把内部数据源开放给多个团队。连接器只建一次，就省得每个功能团队重新摸索怎么对接同一批系统。持续负责接入和运维检索基础设施的这份工作，有时被称为 RAGOps。

模型版本控制补齐了这套初始底座。有了中央模型仓库或注册表，各个版本一目了然、可以复用，就像共享代码库让已有成果容易被找到一样。团队不该各自发明一套存放和查找模型的做法。

04

控制访问并观察质量

较大的企业往往不想被某一家模型供应商绑定。共享代理可以居中转发模型请求，同时管控谁能用哪些服务。Debois 略带保留地把 OpenAI API 可能扮演的角色，类比为 S3 在存储领域的角色：各家供应商可能逐渐向它靠拢的通用接口。这是演讲中对历史走向的预测，并不是说已经有了正式标准，或者兼容性已经得到验证。

应用一旦上线，普通的请求监控就不够用了。平台需要记录提示词，并追踪它们之间的关系。Debois 举的例子是：一条初始提示词会引出五六轮迭代或追问，所以值得观察的单位往往是一整串调用，而不是单次 API 调用。由平台集中提供这种追踪，每个团队就不必各自拼装一套。

API 可用，结果照样可能很差。 所以生产监控还得检查数据和输出质量，把 MLOps 里熟悉的做法往前延伸。持续运行的评测相当于另一种健康检查：它能帮忙发现模型的变化或用户的异常行为，这些都是可用性检查发现不了的。

缓存和反馈收集也属于共享服务。反馈不该只有点赞、点踩和重试：用户直接在结果上修改，就能看出他会怎么纠正。把这些能力做好、管好代价不小，每个团队重复建一套纯属浪费。这个生态越来越庞大，广度上很像 Kubernetes；AI 平台早已不只是云访问加几个 API key。

05

帮助团队做实验——并找到用例

提供了基础设施，不等于大家就能用起来。和任何产品团队一样，平台团队必须引导客户，并从他们的使用体验中学习。赋能既是教学，也是反馈渠道：它能看出哪些能力真正有帮助，哪些反而碍事。

以下几类支持能让试验更容易：

- 原型工具：把产品负责人也拉进来，他们和工程师一样需要探索潜在用例。再把这些工具安全地接入公司数据。 - 框架：给开发者一条探索可能性的途径，并配上适合他们现有技术栈的培训和文档。 - 本地开发：让开发者在熟悉的环境里试验，出差路上也行。笔记本上能跑的模型越来越强，可以缩短迭代周期，不过本地技术栈也有它的取舍。

这些都是帮团队学习的手段，而不只是服务目录里多出来的几项。

下一个障碍是挑出值得做的事。强行要求产品每个角落都用上 GenAI，可能还没找到真实用例，就先动手实现了；Debois 把其中一些动作比作花营销预算。他还提醒，过度专注于模型训练和微调，可能导致迟迟拿不出能上线的东西。

过早做成本优化同样让人分心。业务价值还没确立，就坚持要用本地模型或更便宜的模型，可能白白耗掉工程精力。Debois 的顺序是：先确认回报，再降低交付成本。

用户给了反馈，还得有人来解读。习惯看错误堆栈的工程师，未必知道一条定性修正对产品意味着什么。产品负责人往往掌握所需的领域知识，能分辨哪些回答可以接受，哪些会误导人。只收集反馈、不让这些专长参与进来，改进闭环就没有闭合。

06

模型的变化让评测必不可少

开发者体验里有几个格外难做的选择：从哪个模型起步，怎么拿到有代表性的测试数据，又该多大程度上依赖一个变化很快的框架。Debois 描述了这样的过程：开发者先借框架入门，等框架出了破坏性变更就弃用，转而基于更底层的 API 重写。单次调用提示词也许很简单，但 trace、监控和周边集成仍得协同运转。他希望出现一套靠得住的工具生态，而不是每个团队都把这套机制重造一遍。

Debois 回忆，两年里为了追求更好的质量，他前后用过大约八个 LLM。每换一次，应用里的提示词就得重写、返工，而且全靠手工。从工程管理的角度看，这样做成本可观，却很难确保新模型表现正确。先建好评测，再为新模型重构提示词。

评测如果从工程师已经熟悉的检查入手，讨论起来就容易得多。字符数要求、正则表达式，结果都是明确的。比如演讲里提到一条二十个字符的约束，用 TypeScript 可以直接写出这项检查：

```typescript function hasTwentyCharacters(output: string): boolean { return Array.from(output).length === 20; }

const outputs = ["Your order is ready.", "Ready."]; const results = outputs.map(output => ({ output, passes: hasTwentyCharacters(output), }));

console.log(results); ```

这只检查格式要求，说明不了回答是否有用、是否正确。

再往上走，评测的阶梯就超出了确定性规则：

| 方法 | 检查什么 | |---|---| | 情感分析辅助模型 | 回答的情感倾向 | | 语义比较 | 相关性，比如回答是否切题 | | LLM 评审 | 由另一个语言模型评估的质量 | | 人工反馈 | 人对结果的评估 |

用一个 LLM 去评判另一个 LLM，并不能消除可靠性问题，反而引出了新的可靠性问题。Debois 认为这个问题仍未解决，但也承认用模型做评判是个实用的工具。工程上的做法是把这些方法组合起来，而不是只凭一个模糊的印象。

07

更快的生成把工作推向了审查

赋能还有情绪的一面。有些工程师起初害怕 AI；给他们配一个编程 copilot，他们就能亲身体会到它的用处。构建 GenAI 能力的团队因此多了第二个角色：帮同事在自己的工作中放心地使用 AI。

Debois 观察到，用了 copilot 之后，代码变多了，AI 生成的 pull request 变大了，评审时间也变长了。他并没有说评审开销完全抵消了生成带来的收益。重点在于：一个环节提速，可能在下一个环节造成摩擦，所以只看代码生成，对生产力的描述并不完整。

他把这种张力和 Ironies of Automation 联系起来，还提到一篇从生成式 AI 角度重新审视同一问题的新论文 Ironies of Generative AI。使用自动化的人，从产出工作转向管理和审核工作。生成变快了，评估却占去了人更多的时间。

审核者一旦不再足够了解手头的工作，没法评估它，这种角色转变就变得危险。对领域缺乏整体认识，又没亲手干过，直接接受输出可能比认真评估更省事。Debois 讲了一则周末 Copilot 接受率的轶事来说明这一点；他开玩笑说，那是因为开发者周末根本没那么上心——这并不是确证的原因。更深层的担忧是情境感知（situational awareness）在下降：亲手做得越少，人们识别和处理故障时可能就越没准备。

08

自动化带来了为失败做准备的责任

DevOps 早期的承诺，听上去可能就是用一段 shell 脚本替掉一个人的工作。可围绕这些自动化成长起来的，是一门大得多的学问：为故障做准备。Debois 把两者的比例描述为 20% 自动化、80% 故障准备。这是帮助理解的比喻，不是实测的行业比例。

这条演进路径很关键：

1. CI/CD 和测试：给自动化交付加上检查。 2. 生产监控：看清运行中的系统是否健康。 3. 面向故障设计：从“东西一定会坏”这个前提出发。 4. 可观测性：给运维人员足够的情境感知，弄清正在发生什么。 5. 混沌工程：主动注入故障，让团队持续演练应对。

自动化省掉了一部分工作，这些实践则让人在自动化失灵时仍有能力应对。

这些实践还有一个目的：在事故发生时降低认知负荷。那正是人最没有余力去重新摸清一个陌生系统的时候。不是每个组织都要采纳全部实践，该投入多少，取决于自身的风险偏好。但赋能不只是让工程师更快，还要让他们觉得自己有准备。

09

治理必须经得起日常使用

治理从个人意识开始。一款录屏工具可能承诺提升生产力，同时也会把屏幕上的所有内容都暴露出去。团队需要清楚自己在复制或发送什么，以及服务会怎么处理这些输入。拒绝数据用于训练的选项尤其要留意，因为在哪里、什么时候设置它，往往并不明显。

把可用模型限定在一小批获批模型内，许可证审查就更好管。名字里带“开放”，并不代表你就有权使用某个模型，它的许可证和来源仍要仔细审查。Debois 还提到，要对欧洲的工作流风险评估有基本了解：团队应该问一问，某种拟议用途是否被允许、是否恰当，但不必指望每个工程师都变成律师。

运营层面的管控同样马虎不得。Debois 认为提示词注入仍是没有解决的问题，防护必不可少。他把护栏比作入侵检测和 Web 应用防火墙：规则和日志越堆越多，最后可能让人养成无视告警的习惯。装上一套管控措施能带来安心感，却不能保证有人真的用得好。

跨越服务边界的不受控文本越来越多，对个人身份信息（PII）的审查也更加必要，需要围绕传输内容设置有用的指标和告警。这些职责让平台的职能范围清晰起来：运营共享基础设施，帮团队用好它，并为这些使用制定公司规则。

10

把平台与产品体验连接起来

平台聚焦内部，还剩下另一个协调问题：AI 在整个产品中怎样呈现给客户。Debois 介绍了 unFIX Experience Crew。它来自 Team Topologies 之外的另一套方法，可以作为补充的组织思路。放到 AI 上，这个 crew 横跨各功能团队，了解他们在做什么，并让最终的用户体验保持一致。

这样一来，CloudOps、SecOps、开发者体验、数据平台和 AI 基础设施之上，又多了一层体验层。Debois 不建议 10 人规模的公司采用这种结构，而是建议扩展到 10 个或更多团队时再考虑。这是对协调需求的判断，并不是要求在工作量还撑不起来时就先设部门。

好处来自不同专业之间的协作。SecOps 带来访问控制和治理方面的专长，CloudOps 熟悉资源开通和云厂商。把这些能力放进一个共享区域，团队就更有机会一起把整个问题解决掉。

11

护栏归谁负责？

问答环节里，Debois 先答应会分享幻灯片。随后有人提了一个实质性的问题：护栏该怎么交付？是挡在每个对外提供的模型前面，并写进它的模型卡；还是由产品团队负责正确调用一个独立的护栏服务？

Debois 的回答是分层负责。中央治理提供通用规则，各团队再补充适合自己用例的规则。共享组件避免了通用策略的重复建设，自助模式则让团队能处理自己产品特有的需求。他划清了这些职责，但没有规定具体的执行拓扑。平台提供一条共同的基线，产品团队在此之上搭建各自的防护。

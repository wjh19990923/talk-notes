超越转写：打造真正理解对话的语音 AI

光看文字会漏掉打断、附和和说话人切换。Hervé Bredin 展示了说话人分离的原理、如何评估它，以及为什么把它的输出与转写文本对齐仍然困难。

01

缺失的说话人标签

转写系统能把对话里说的每个词都输出来，却不告诉你哪句话是谁说的。Hervé Bredin 在学术界研究这个问题多年，后来联合创办了 pyannoteAI，出任首席科学官。他的开源工具包 pyannote.audio 专做说话人日志（speaker diarization）：追踪录音里每一刻是谁在说话。OpenAI 发布 Whisper 后，用户发现两者天然互补：Whisper 负责转写，pyannote 补上缺失的说话人标签。Bredin 认为，工具包的使用量正是从 Whisper 发布那时起迎来了拐点。

讲到用户增长，他顺带提了个生日请求：再过一周就是他的生日，项目也快到 10,000 个 GitHub star 了，他请台下观众点个 star 当生日礼物。

背后的区别很简单。语音转文字（STT）把录好的或实时流入的音频变成一串词，回答的是“说了什么”。但一场对话压成一条文本流后，可能很难读懂：光看文字，你分不清一个人的话在哪里结束、另一个人的话从哪里开始。

02

从说了什么到谁说的

带说话人归属的转写会给词打上说话人标签，问题就从“说了什么”变成了“谁说了什么”。对会议助手来说，有了这层结构，可能就足以总结讨论内容；再把标签对应到具体参会者，就能把待办事项分给真正认领它的人。一句话转写得再准，安到了别人头上，会议记录照样是错的。

不少应用都有同样的需求：

- 视频翻译与配音：翻译后的语音要给每位参与者配一个固定的声音。在不相干的说话人之间来回换声音，对应关系就乱了。 - 会议纪要：承诺和发言要始终挂在对的人名下。 - 播客分析：要在不同剧集、甚至不同播客里找出同一位嘉宾，就得把语音和反复出现的同一个人对应起来。

这些应用都需要说话人信息，但需要的程度不同。在一段录音里保持标签前后一致，比跨录音认出同一个人要简单得多。

03

时机和语气会改变解读

即便说话人归属完全正确，还是会漏掉信息。在 Bredin 举的例子里，从时间上能看出黑色说话人打断了绿色说话人。如果只有一串标好说话人的句子、没有精确时间，就看不出这次打断。同样会被掩盖的还有附和语（backchannel）：别人还在说话时插进来的简短回应。这类回应可能表示赞同，却不会抢过话轮。漏掉它，就丢了一次虽小却要紧的表态。

停顿也一样重要。两轮发言之间的空隙不贡献任何文字，却会影响别人怎么理解接下来的回应。再往下一层是表达方式，也就是话是怎么说出来的。Bredin 举了笑声和咳嗽的例子：这些声音可能表达什么，要看语境。笑可能是因为听到笑话，也可能是因为场面尴尬；咳嗽可能伴随着不自在。这些只是可能的解读，不能当作判断一个人心理状态的可靠标签。

韵律（prosody，即重音、节奏和语调的模式）和不流利现象还能提供更多信息。Bredin 的例子是“The dog ate the cake”（狗吃了蛋糕）：孩子说同样几个词，重音放的位置不同，言外之意也就不同。保留这些信息，下游的语言模型或其他分析工具能用的就不止一串词。

04

在对谁说话，又是在哪里？

再往大了看，还要问：谁在对谁说话？面向全场发言，和在问答环节回答某个人的提问，是两回事。声学环境又多一层：同样一段对话，发生在安静的房间里和发生在街上，带来的语境信息不同。这些都属于 Bredin 想攻克的对话理解问题，但他把技术讨论收窄到了说话人日志。光是检测出“谁在什么时候说话”，并不能顺带解决听话人识别、韵律或意图理解。

为了说明这个更窄的任务需求有多大，Bredin 展示了一份按下载量排序的 Hugging Face 音频模型榜单。在当时的快照里，前七名中有三个模型和说话人身份或说话人日志有关，其余都是语音转文字模型。这份历史截图说明，开发者在拿到文字的同时，经常也需要说话人信息。

05

从语音活动到一致的说话人标签

Bredin 把说话人日志拆成三个逐步细化的任务：

1. 语音活动检测：找出有人在说话的区段。 2. 切分：在这些区段里定位说话人切换的位置，找出重叠的话轮，包括打断和附和。 3. 说话人分配：给整段录音里的话轮打上前后一致的说话人标签。

切分的细节很要紧。一句极短的肯定回应，可能就带着某位参与者反应的关键信息。只检测出一长段语音、却丢了这个小话轮，是不够的。反过来，找出话轮也还不算完整的说话人日志：系统还得判断哪些话轮属于同一个人。

说话人数量一般事先不知道。会议的参会名单可以作参考，但它并不精确对应录音里的声音：两个人可能共用一路音频，也可能有不在邀请名单上的人中途加入。这和在固定的已知类别里做分类不同，系统必须自己推断出有几个不同的说话人。

这些类别还是匿名的。说话人日志通常返回“说话人一、说话人二、说话人三”这样的标签，而不是 John、Hervé 和 Jack。只要分配前后一致，标签之间可以互换。在双人示意图里，把所有绿色标签换成黑色、黑色换成绿色，得到的说话人日志完全等价。关键在于按说话人给语音分组，标签叫什么、用什么颜色都无所谓。

说话人数量未知、标签可以互换，只是难点的一部分。说话人会重叠，有些话轮极短，各人的发言时长也可能相差悬殊。只说了一句简短附和的人，留给系统的语音素材远少于主导讨论的人。噪声和其他声学条件，又带来了语音处理领域常见的那些难题。

06

在 notebook 中检查说话人分离的错误

第一个 Python notebook 演示把这些错误直观地摆了出来。输入是一段大约 30 秒的双人电话录音。两人先有些迟疑地互相打招呼，接着各自报出所在地——新泽西和得克萨斯——然后发现两人老家都在芝加哥。Bredin 先展示这段样本的人工标注参考答案，再用开源的 Community-1 说话人日志模型跑了一遍。

本地流程是：从 Hugging Face 下载模型，在他的 Mac 上启用 PyTorch 的 MPS 后端，把 pipeline 跑在音频文件上。Bredin 从一个已经跑完的 notebook 标签页切到现场运行，然后把预测结果和参考标注做对比。两条时间线对齐后，就能看出输出在哪些地方和预期的说话人活动对不上。

对比结果把错误分成三类：

| 错误 | 问题出在哪 | | --- | --- | | 说话人混淆 | 语音归到了错误的说话人名下。 | | 误报 | 参考标注里没有语音，系统却检测出了语音。 | | 漏检 | 参考标注里有语音，系统没检测到。在重叠段，两人同时说话却只检测出一人，也算漏检。 |

最后这种情况很容易忽略。系统可能正确检测到有人在说话，却因为另一个人同时在说，仍然漏掉了一部分对话。

Bredin 用 pyannote.metrics 把这三类错误合成说话人日志错误率（DER）。这里的量都是时长，不是词数：

``math \mathrm{DER} = \frac{T_{\mathrm{confusion}} + T_{\mathrm{false\ alarm}} + T_{\mathrm{missed\ speech}}}{T_{\mathrm{reference\ speech}}} ``

据 Bredin 介绍，Community-1 在这段电话样本上的 DER 约为 5%。

> 编者注：这项指标的计分约定按说话人时长计算，而不是按文件实际经过的时长：计入重叠时，参考标注里有两人同时说话的一秒，算作两个“说话人秒”。不同结果能否直接比较，还要看是否计入重叠，以及边界容差（collar，即参考边界前后允许的误差范围）怎么设。

接着，他把同一段样本提交到 Precision-2 的云端 API。从展示的结果看，它纠正了一处说话人混淆，误报和漏检也都减少了。Bredin 说，Precision-2 在同一样本上的 DER 约为 3%。这些只是这段简短演示录音上的结果，不是整套数据集上的基准分数。

07

准确率取决于录音

离开这通简短的电话，说话人日志效果如何？Bredin 的回答是：看使用场景。他给出的数据是，在双人电话对话上，最好的系统 DER 约为 8%；几个朋友在嘈杂餐厅里聊天时，即便是最好的系统，DER 也高达约 41%。这些是按场景分别做的对比，不是 notebook 里那两个模型的额外得分。参与人数和声学环境会大幅改变任务难度；嘈杂环境下的多人对话，离解决还差得远。

08

为什么排行榜分数可能不适用于一场会议

有了转写和说话人日志，要生成带说话人归属的文本，看上去只需给每个词分配一个说话人。第一个障碍是，识别本身可能就已经错了。Bredin 认为，大多数 STT 模型用单人语音数据训练，遇到带重叠和说话人切换的多人录音，泛化能力很差。他拿 NVIDIA Parakeet 和 Open ASR 排行榜举例（ASR 即自动语音识别）。

针对 Parakeet 在 AMI 会议数据集上的表现，他把排行榜上的词错误率（WER）和自己团队测出的结果做了对比：

| Bredin 提到的评测 | 录音条件 | 报告的 WER | | --- | --- | --- | | 展示的 Open ASR 排行榜 | 每人戴一个头戴式麦克风，录到的是单人语音 | 11.4% | | 他团队的 AMI 评测 | 会议桌中央放一个远场麦克风，同时录到多人语音 | 26% |

数据集名字一样，输入条件却不一样。Bredin 解释说，头戴式麦克风录音和桌上共用麦克风，对识别来说是实质不同的两类问题。这组对比同时改变了麦克风位置和对话条件，没法单独看出重叠本身的影响。

难点包括远场语音、说话人切换、串音和打断。Bredin 还提到了语码转换（code switching），也就是一句话里换着说不同语言。对会议类应用来说，实用的评测原则是：拿产品真正会收到的那类录音来测。在单人头戴麦克风语音上拿到的分数，说明不了在会议室共用麦克风上的表现。

09

说话人归属不是简单的时间戳关联

第二个障碍是调和（reconciliation）：让转写和说话人日志在“哪些词属于哪个说话人”上达成一致。两者的时间戳可能对不上，覆盖范围也可能对不上：说话人日志检测到的语音，STT 可能根本没转写出来；STT 输出了词的地方，说话人日志可能认为没人说话。在重叠段，两人同时说话，可能只对应一条识别出来的词流。识别阶段压根没产出的词，靠时间戳匹配也分配不了。

在第二个演示里，Bredin 用 Parakeet 处理同一段电话样本。它返回一串词，每个词都带起止时间，正好提供了做说话人归属所需的词级时间区间。

> 编者注：公开的演示代码注明所用版本是 nvidia/parakeet-tdt-0.6b-v3，并通过 timestamps=True 请求时间戳。

他把这些词和 Precision-2 给出的说话人话轮并排放在一起，逐个检查分配结果：

| 展示的情况 | 归属为什么容易或困难 | | --- | --- | | 某个词的时间区间略微左移 | 虽然时间有偏差，看起来仍然明显该归给黄色说话人。 | | 第三个词 oh 落在两个话轮之间 | 这个词找不到明确可挂靠的话轮。Bredin 一边考虑怎么分配，一边把这段重放了一遍。 | | 词 okay 出现时有两人同时在说话 | 说话人日志给出两个候选，转写却只给了一个词。 |

这是几种不同的失败模式：边界不精确、词落在话轮间的空隙里、重叠时两个说话人相互竞争。把它们一律当成同一个区间匹配问题，就掩盖了调和环节必须解决的不确定性。

10

保留重叠的对话

随后，Bredin 向 pyannoteAI 的云服务提交了一个任务，把 Precision-2 说话人日志、Parakeet 转写和调和串在一起。返回的结果里，每个词都已经分好了说话人，应用不用自己逐个处理冲突的区间。

最能说明问题的是两人自我介绍交接的那一段。一人话尾的 um 和另一人开口的头几个词叠在了一起。Bredin 播放这段音频并指出，输出把两人的词交错排列，在另一人开口时仍保留了那个填充词。他说，系统把这段重叠处理对了。这次成功有明确的范围：在这段交接里，系统保住了两个人的话，没有把其中一方吞进另一人的话轮。演示并没有揭示完整的调和算法。

11

演示背后的工具

演示最后，Bredin 指向了 pyannoteAI/tutorials 里的演讲教程。教程里各组件分工明确：pyannote.audio 提供开源说话人日志，pyannote.metrics 评估预测结果，iPyannote 提供交互式可视化组件。他解释说，开头的 i 代表 interactive（交互式）。SDK 则用来调用付费的高级模型，和前面展示的本地开源流程互为补充。

12

互斥式说话人分离与独立的语音识别模型

有观众问：冲突在哪一层解决？是模型训练时学出来的，还是靠模型外围的启发式规则？Bredin 说，完整的调和技术是专有的，但他点出了已经公开、Community-1 里就有的一部分：独占式说话人日志（exclusive diarization）。

Bredin 解释，在语音重叠时，独占式说话人日志会挑出最可能被 STT 模型转写出来的那位说话人。这样，这份视图里就去掉了相互竞争的说话人分配，调和也更简单。这是整套方法中的重要一环，但并不能完整解释前面的演示如何还原重叠的词并把它们交错排列。

> 编者注：Community-1 模型卡片分别列出了 output.speaker_diarization 和 output.exclusive_speaker_diarization 两种结果。独占输出是专为调和准备的简化视图，不代表原始录音里没有重叠。

被追问是否需要改动模型训练时，Bredin 强调了设计上的边界：编排层应当在不修改 STT 模型本身的前提下工作。他把支持不同的转写系统（包括私下微调的模型）列为一项设计目标。这样，团队可以保留针对自己场景调好的识别器，再在外围加上说话人日志和调和。

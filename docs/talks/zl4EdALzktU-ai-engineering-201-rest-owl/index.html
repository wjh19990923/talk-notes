AI 工程 201：把猫头鹰画完

推理为 AI 应用提供了骨架。语言接口、检索、结构化输出、智能体记忆和生产反馈，把这副骨架变成一个有用的产品。

熟悉语言模型提示词、API 请求和基本的数据库查询会有帮助；文中会在出现时讲解检索、受约束的生成和智能体记忆。

01

推理只是开始

从一个能跑推理的模型，到一个真正创造价值的产品，中间还差多少？Charles Frye 开场先讲了“画猫头鹰”的梗：先画两个简单的圆，勾出基本形状，可怎么把整只猫头鹰画出来，几乎一笔都没交代。推理就是那两个圆。包在外面的应用，以及持续改进它的流程，才是剩下的整只猫头鹰。

语言用户界面（language user interface，简称 LUI）为这层应用提供了一个好用的组织思路。用终端时，用户得先学会计算机的专用语言。图形界面借助人的空间直觉和视觉，让专业圈子以外的人也能上手用电脑。语言模型又带来一次转变：用户只要说出自己想要什么，系统就把这个意图翻译成机器能执行的操作。

Frye 引用了 Sam Altman 对语言界面的热情，但这个愿景比基础模型早得多。1960 年代的 ELIZA 就以对话形式扮演心理治疗师。SHRDLU 在一个图形化的积木世界里，能听懂“拿起一个大的红色积木”这样的指令。Ask Jeeves 想做互联网的语言入口，Alexa 则把语音请求带进了日常设备。基础模型带来的机会，是让这种交互在众多领域里都能成立，不必再为每个狭窄的场景单独做一套工程。

02

从查询助手到各种不同的产品

红杉的 Generative AI’s Act Two 描述了基础模型如何成为完整解决方案里的组件。Honeycomb 的查询助手就是个具体例子。用户不用在陌生的界面里一点点拼查询，直接问慢请求、错误，或者按状态码看延迟分布就行。SQL 当年也寄托过让普通业务人员自己写查询的愿望；而“能给我看看慢请求吗？”这样的问法，更接近人们真正想要的交互。

给现有功能加上语言接口，是眼下就能抓住的机会。把时间拉长到整个产品周期，界面可能反过来改变它背后的机器，就像终端、桌面和移动界面各自撑起了不同的计算形态。Google 的 SayCan 展示了这个方向：想要一瓶水，开口说就行，不用打开 App 再翻好几层下拉菜单。Frye 也提醒，那段机器人演示是 4 倍速播放的，别以为它已经很成熟。想要的交互很简单，真要做出来，仍然需要大量工程。

03

RAG 提供通用模型所缺的上下文

检索增强生成（RAG）聊天机器人，已经成了语言界面里的“待办清单应用”——几乎人人入门都做一个。但它背后的需求不会过时。一个通晓常识的模型，并不会自动了解用户、了解所在组织，也不知道哪些文档跟当前问题有关。检索的作用，就是在生成之前把缺失的上下文补上。

常见的实现就这么几步：

1. 收集并存储相关资料。 2. 建立索引，通常用 embedding。 3. 根据用户的提问检索相关资料。 4. 把这些资料插进模型的提示词。

Frye 给 Full Stack Deep Learning 做的 Discord 机器人，用的是课程讲座、精选论文和课程网站。它要做的是依据这些资料、站在作者的视角回答问题，而不是再给一个泛泛而谈的语言模型答案。

向量搜索之所以成了默认选项，部分原因是方便：已经在用 OpenAI 的开发者，用同一个库就能拿到 embedding。做 transformer 的人对点积和 softmax 也很熟。这就解释了“和你的文档聊天”类示例为什么遍地都是。但长期需求不只是向量存储，而是找到有用的信息，并放到模型用得上的地方。

| 检索方式 | 示例 | 作用 | |---|---|---| | 向量搜索 | Pinecone、Chroma | 按 embedding 相似度检索 | | 关键词搜索 | Elasticsearch 一类的系统 | 按文本匹配检索 | | 混合搜索 | Vespa | 结合向量和关键词两种信号 | | 现有数据库 | Redis、Postgres 生态 | 在常规检索之上加入向量能力 |

Frye 说 Redis 的向量搜索用起来别扭，但能用。更重要的是：从海量数据里快速检索，本来就是数据库问题；用了 RAG，不代表就得单独上一个向量数据库。

用户的自由提问五花八门，单靠一种检索方法很难都照顾到。一个实用的组合是：关键词搜索加向量搜索，再让语言模型抽取元数据，直接拿来做过滤。Frye 推荐了 The Data Quarry 从数据库角度写的文章。回答听众追问时，他又回到那条不变的原则：在从外部世界存下来的信息里搜索，再把结果放进提示词。常规数据库技术也好，专用向量库也好，都只是这个模式的不同实现。

04

上下文、对话历史与学到的知识

检索和跟 GPT-4 对话时的历史记录，区别在哪？在 API 这一层，消息历史是应用自己拼出来的。之前的用户消息和助手消息都只是传进去的输入，不一定是不可更改的事件记录。Frye 指出，伪造的助手历史还可能被拿来越狱，同时也提醒大家别违反服务条款。

在他介绍的实现里，检索到的信息通常放进系统提示词，可以只放一次，也可以每轮用户发言都刷新。模型之所以会重视这条消息，他认为是训练使然。应用也可以把检索到的事实伪装成用户之前说过的话，但他觉得很少有人这么做。真正的区别在于内容归谁：检索是程序员给模型补充它该知道的信息；对话历史记的是用户和助手说过的话。

另一位听众质疑了那条常见的经验法则——检索管知识，微调管风格：如果训练集里有 100 GB 研究论文呢？Frye 认为，这条法则成不成立，要看适配的规模和方法。聊到托管平台上的小规模微调时，有听众说上限是 10,000 行，Frye 不太确定地表示认同；这段对话不能当成现行的 API 限制。

LoRA 通过对模型各层做低秩更新来适配模型。Frye 的直觉是：小规模适配改变的，往往是模型已有的哪些计算更重要。一个能力强的模型本来就知道 Homer Simpson 或 Rick Sanchez 平时怎么说话；角色聊天机器人要做的，是让这种说话方式在下一个 token 的概率里从可有可无变成主导。这只是对小规模适配的一种解释性直觉，并不能证明低秩更新教不会模型新的事实。

拿一大批教科书来训练，就是另一回事了。Frye 把这种情况和“风格 vs 知识”法则所针对的小规模微调区分开，并举了面向编程的 Llama 衍生模型为例：它们的变化不止于风格，还包括编程能力和对各种库的了解。真正该问的是模型吃进了多少数据、做了哪种更新，而不只是这件事叫不叫微调。

05

围绕实际约束选择检索方式

一个关于 Neo4j 的问题，把话题引到了图数据库。Frye 自称不是数据库专家，转述了专家们的看法：他们更倾向于用 Postgres 来表示图。扩展时的具体难点在分区：任意一张图都没有明显的切法，新加的边还可能改变最优的分区方式。所以重新平衡更像是一次迁移，而不是把彼此独立的记录简单挪一挪。

如果只是把图当作模型的外部记忆，这个难点未必是主要矛盾。Frye 设想了几种负载：数据量在 MB 或 GB 级，每秒几万到几十万次请求，借此追问：分布到很多台机器上，到底是不是该操心的事？这些只是举例，并非实测容量。知识图谱和语言模型的记忆天然契合，但他还没见过哪个应用能让这个选择一锤定音。

元数据过滤暴露出一个更现实的检索问题。假设用户想找旧金山的螃蟹餐厅。布尔标记、类别或地点约束，和模糊的相似度分数，含义完全不同。

| 策略 | 执行顺序 | 后果 | |---|---|---| | 后过滤 | 先检索和螃蟹相关的候选，再检查地点 | 其他城市的候选可能占满检索名额 | | 预过滤 | 先限定在旧金山，再搜索和螃蟹相关的结果 | 相似度搜索只在相关范围内进行 |

后过滤做起来简单，但回答的问题可能和用户问的有微妙的出入。

要高效地做预过滤，建索引时就得考虑进去：搜索系统既要支持地点这类限制，又要能快速找到相似条目。不同数据库支持的限制类型各不相同。Frye 提到 Vespa 和 Weaviate 在这方面口碑不错，但他没做过全面比较。过滤是检索设计的一部分，不只是相似度搜索之后的收尾清理。

06

让生成的文本能被其他系统使用

语言模型产出的是文本，但应用通常需要能直接拿来执行的东西。把生成的文本接到另一个系统的输入上，模型就成了那个系统的语言界面。结构化输出限定或引导模型能返回什么，让这条连接更牢靠。

几种方法分别在生成过程的不同环节起作用：

- 提示词： 用 ReAct 风格的示例，引导模型发起对外部 API 的请求。请求一出现，应用就把它截下来，调用真正的 API，再把结果交回去，而不是让模型自己编一个响应。Frye 还讲了 Riley Goodside 那个夸张的提示词：如果不输出合法的 JSON，就会有个孤儿死掉。这是个让人过目不忘的“说服”案例，效果如何只有坊间说法。 - 微调： Gorilla、Toolformer、GPT-J 以及经过适配的 Llama 模型，都是为工具调用或结构化生成而训练的例子。托管的 OpenAI 微调对生成任意结构能帮上多少忙，Frye 持怀疑态度；OpenAI 当时的微调公告 确实把“改善格式”列为一个用例，但这和保证符合 schema 是两回事。 - 重试： 校验输出，说明哪里不对，再让模型重来一次。Frye 特别提到 Guardrails 基于 XML 的接口，并推测它可能很适合 Claude。

这三种方法，分别作用于请求本身、模型学到的行为，以及校验失败后的应对。

语法约束采样在无效 token 输出之前就介入。在 llama.cpp 里，可以用语法排除违反目标格式的续写。被禁止的 token 概率为零，相当于把它们的对数概率设为负无穷：

``math \begin{aligned} \ell'_t & = \begin{cases} \ell_t, & t \text{ is allowed by the grammar},\\ -\infty, & \text{otherwise}, \end{cases}\\ p(t) & = \frac{\exp(\ell'_t)}{\sum_u \exp(\ell'_u)}. \end{aligned} ``

上下文无关语法可以约束 JSON、代码，以及其他常规系统能解析的格式。哪怕另一个模型的通用能力更强，只要能严格控制解码，某个模型在特定集成场景里反而可能更好用。

听众提到了 TypeChat（Frye 没用过），接着问能不能把 GPT 的回答交给 Gorilla 来整理格式。他认为转换结构比生成原始答案容易，交给小一点的模型来做说得通。他举的例子是：GPT-4 负责主要生成，GPT-3.5 负责处理错误。Guardrails 式的修复和 LangChain 式的链式调用，都能把这两类职责拆开。

07

为什么解码控制应该靠近推理

一位听众纠正了一处说法，也让两个概念的区别更清楚：查看对数概率，和用 logit bias 改变 token 概率，是两种不同的能力。Frye 同意 API 可能仍然支持 token 偏置，接着指出了实际操作上的麻烦：生成过程中，语法允许的下一个 token 一直在变。客户端要是靠连续请求来跟上这些变化，每个 token 都得走一趟网络往返，没法一次请求拿回整段续写。

随后他把眼光放到单个 token 的决策之外。更强的解码器可以探索几条符合语法的续写，再从中挑选，比如借助蒙特卡洛树搜索之类的方法。Frye 把这当作一个前瞻方向，认为它多半会先在开源模型上出现，因为开发者能掌控推理循环。这里讨论的 API 状况，早于 OpenAI 后来推出的 Structured Outputs；这项功能在 2024 年 8 月上线，在服务端实现了受 schema 约束的解码。它改变了实现上的选择，但生成的值对不对，仍然是另一个问题。

08

一次函数调用可以只是一个结构化的回答

针对特定工具做训练，会碰上泛化问题。Gorilla 针对的是 Torch Hub、TensorFlow Hub 和 Hugging Face 上的 API；懂这些工具，不代表懂所有工具。有了共享接口，问题就变了。OpenAI 的函数调用接口用 JSON Schema 描述参数，模型只要学会这种通用格式，应用写一层小小的适配代码，就能接上大量工具。语法约束还能进一步保证格式正确。集成工作开始变得像普通的 Web 开发：把一个 JSON 对象交给知道怎么处理它的代码。

函数不一定真要执行。假设应用要判断一条消息是不是垃圾信息，好渲染对应的界面。只要描述一个虚构的函数，让它的参数就是这个分类结果，模型就会以机器可读的形式给出判断。应用直接拿这些参数来用就行。

下面用 JavaScript 表示这条边界。schema 描述需要的结果；调用方校验并使用返回的参数，并不真的调用什么分类函数：

```javascript const classificationFunction = { name: "report_spam_classification", description: "Report whether the input message is spam.", parameters: { type: "object", properties: { label: { type: "string", enum: ["spam", "not_spam"] } }, required: ["label"], additionalProperties: false } };

function readClassification(argumentsJson) { const result = JSON.parse(argumentsJson); if ( result === null || typeof result !== "object" || Array.isArray(result) || Object.keys(result).length !== 1 || !["spam", "not_spam"].includes(result.label) ) { throw new Error("Invalid spam classification"); } return result.label; } ```

Jason Liu 的 Instructor 把这种抽取结构化结果的通用模式做成了现成的库。真正有用的是参数对象本身，下游有没有函数可调，都无所谓。

请求仍然得符合函数调用接口，以及模型学到的那套惯例。Frye 用函数式编程来解释这种灵活性：连常量都能表示成函数，可选结果也能用 maybe 这类结构来表示。他还介绍了一个“DAG 构造器” schema，它产出的不是单次调用，而是一张由拟调用函数组成的图。生成这张图只是完成了规划；真正去执行，仍然是应用的事。

结构化结果让流式输出变得麻烦。Frye 认为，函数调用这种模式更适合后台数据处理，不太适合需要即时展示给用户的文本。流水线可以在上游相关信息一到位就启动下游工作，但得有一条可靠的边界，来判断什么才算完整。Unix 管道有按换行分隔的记录；函数调用的半截参数，并没有天然的对应物。想找回有用的增量处理，得在流水线设计上下功夫，光打开 token 流解决不了。

09

智能体保留记忆并积累技能

检索和结构化抽取，都是一眼就能认出来的自然语言处理任务。智能体则更接近大众心目中的人工智能：行为会随时间演化。Generative Agents 在模拟环境里把记忆流和推理流程结合起来，角色的性格和彼此的互动都在不断演变。

Voyager 把这种积累体现得尤其具体。它的 Minecraft 智能体调用环境 API 编写 JavaScript，为砍树、打僵尸等活动写出例程，再把这些例程存成可复用的技能。它还会自己安排学习课程。Frye 特别提到它在挖钻石上的进展，这曾是强化学习领域的一大难题。这里的记忆包括可执行的程序，不只是过往观察的流水账。

信息、技能和工具攒得再多，也绕不开核心障碍：可靠性。结构化输出能让单次交互不那么脆弱。Frye 是结合演讲当时的研究现状提出这个建议的：那时已发表的智能体研究里，用上他所说的新版函数调用能力的还很少。

10

给智能体行为一个明确的架构

Cognitive Architectures for Language Agents（简称 CoALA）提供了一套词汇，可以拿来比较 Voyager、ReAct 和 Generative Agents 里各自零散的设计选择。这项工作出自普林斯顿 Tom Griffiths 的团队，重新审视了早期 AI 研究中的产生式系统和认知架构，包括程序性记忆、语义记忆和情景记忆。

那些老系统有清晰的组织结构，却缺少通用知识和常识。语言模型补上了大部分知识，却没有持久记忆，也没有明确的认知组织方式。两者一结合，就可以由架构来规定智能体怎样观察、记忆、推理、选择行动，以及怎样与世界交互。

内部行动是一个特别有用的区分。智能体可以花时间推理、更新长期记忆或修改自己的决策流程，而不是马上对外部环境采取行动。把这些选择摆到明面上，就能把记忆设计、与外部世界的对接（grounding）和行动选择分开来看。CoALA 还提出了一份研究议程，内容来自语言模型技术与认知架构思想的各种组合。架构部分的最后，Frye 推荐了 Eugene Yan 写模式与反模式的文章。

11

生产中的观察变成工程输入

架构讲的是系统怎么搭。工程上还需要一套改进系统的流程。Frye 说，现在主流的做法是“上线了才能学到东西”，也就是 Full Stack Deep Learning 和 Andrej Karpathy 一直强调的数据引擎或数据飞轮：收集真实数据，找出失败案例，改进系统，再循环往复。

Charity Majors 拿传统软件测试做对比，后果一下就清楚了。软件团队把测试看作上生产环境前的关卡；ML 团队却往往要先看到生产环境里的情况，才知道测试该测什么。Frye 开玩笑说，最后就成了“哎呀，全是回归测试”。所以监控从一开始就得做，覆盖用户行为、性能、成本和 bug。

Discord 机器人就是个具体的小例子。用户会问：点表情回应算不算反馈？它的数据集里有没有它自己的源代码？它是干什么的？甚至问谁是好机器人。开发时，这些“元问题”看起来都无关紧要。在真实对话里看到之后，Frye 才在提示词里加上了对这类输入的处理。他把交互记录到 Gantry，看了点赞和点踩的例子，还把所有记录从头读了一遍——反正总共才两百来行。

12

监控体验，而不只是平均请求

延迟分位数之所以重要，是因为用户经历的是一连串请求。一个系统对大多数单次请求都很快，活跃用户却仍可能一次次撞上它那条慢尾巴。Frye 强调要盯住 p99 这样的极端分位数，别看到 p90 达标就收手。吞吐量是另一个信号：系统总共完成多少工作，和单个请求要等多久，是两回事。

| 部署方式 | 运维信号 | |---|---| | 托管推理 API | 请求速率、API 错误、延迟、成本 | | 自建推理服务 | 上述应用信号，外加算力利用率和推理吞吐量 |

随机抽样的 profile 和 trace，能帮你解释汇总数字，并找到吞吐量问题出在哪。自己部署推理时，维持吞吐量就成了你的直接责任，需要针对具体模型和硬件做更多排查。

工具生态横跨几个已经成型的类别：

- 通用可观测性： Datadog、Sentry、New Relic、Honeycomb，或者兼容 OpenTelemetry 的自定义埋点。 - ML 工具： Weights & Biases（Frye 曾在这里工作），以及 Fiddler、Arize 和 Gantry。它们各有侧重，有的偏训练管理，有的偏生产监控。 - LLM 应用工具： LangChain 的 LangSmith，以及 Langfuse。

Frye 没说哪家已经胜出。他偏爱那些能方便地对非结构化数据做各种刁钻查询的工具，举了 Weights & Biases 和 Gantry 的例子，同时提到通用工具可能得自己写分析代码，或者开 notebook 来查。

Langfuse 的文档聊天机器人提供了一种很吸引人的产品体验方式：先用聊天机器人，再到监控界面里看它刚生成的记录。Frye 推荐这种现场演示的做法，但因为时间不够，跳过了原本准备的演示。收集这些记录也只是开始；接下来要问的是，靠这些记录，能不能解释并改进应用的行为。

13

可观测性取决于能否识别出失败

可观测性问的是：从外部观察，能不能看清系统内部发生了什么。换成软件的说法：不进实时调试器，光看日志能不能调试？当系统复杂到你没法预判它会怎么出错时，这就成了刚需。对语言模型应用来说，在 GPT-3 或 GPT-4 内部深处打个断点，并不是诊断坏答案的可行办法。应用必须留下足够的证据，才能定位并修复问题。

更难的一关，是认出一个答案是错的。连对错都说不清，诊断失败和验证修复也就都无从谈起。Frye 提到了 Anthropic，以及《AI Snake Oil》作者 Arvind Narayanan 和 Sayash Kapoor 对评测提出的担忧，还认为 OpenAI 开源自家评测框架，同样说明这个问题有多难。The False Promise of Imitating Proprietary LLMs 给出了一个具体警示：回答风格让人信服，就容易让人高估模型能力，而针对性的评测并不支持这种印象。这一发现针对的是论文研究的那几种模仿方法，并不覆盖所有形式的蒸馏。

14

使用最有力的可用评估证据

评测从持续关注数据开始。Frye 引用了 Stella Biderman 和 Jason Wei 的观点：逐条看样例、弄懂评测本身、为此搭内部工具，都很值得。如果输入和输出都没什么结构，开放式生成就特别难评。Josh Tobin 在 Full Stack LLM Bootcamp 里给出的流程图，能帮你避免把每个任务都当成这种最难的情况。

| 已有证据 | 评测方法 | |---|---| | 已知正确答案 | 对照标准答案，用常规 ML 指标 | | 参考答案 | 与可接受的回答做较宽松的匹配 | | 系统之前的回答 | 由人或模型比较新旧回答 | | 人工反馈 | 检查修改后的版本是否吸收了反馈 | | 以上都没有 | 直接评测开放式生成 |

选择题的答案可以有明确的正确标签。简短的书面回答，可能就要靠和参考答案比对。即使两者都没有，之前的输出也能回答一个范围更窄的问题：新答案是不是更好；明确的反馈则可以用来检查要求的修改有没有落实。这些证据全都用不上时，剩下的才是完全无结构的评测。

Elicit 从科学论文中抽取信息的工作，展示了迭代分解的做法：

1. 先做出一个端到端能跑通的任务。 2. 找一个失败案例来看。 3. 拆分任务，让这个失败落进一个更简单的子任务里。 4. 针对这个子任务做优化和评测。

这样能把一个看不透的生成问题，变成几个答案更明确的小问题。代价也实实在在：链式调用会增加延迟，而且对话式的回答不一定拆得出有用的结构。

15

从失败中扩充测试，从使用中收集反馈

如果实在绕不开自然语言评测，先准备几个靠得住的用例，是个合理的起点。这些用例都通过了，也不能告诉你下一个例子失败时该怎么办，但用例集可以不断扩充：把生产环境里的失败加进来，留作回归用例，再放进 GitHub Action 里跑。一次小小的人工检查，就是这样一步步长成前面说的数据引擎的。

用户反馈能自然地融进产品时，用处才更大。Frye 以 Midjourney 为例，说明可以从显示性偏好中学习：用户实际选择怎么做，往往比强制填写的反馈表信息量更大。Honeycomb 更进一步，把查询助手和下游业务目标挂上了钩。衡量链条从功能出发，经过用户行为，一直延伸到组织目标。

付费标注团队是另一种反馈来源。普通用户未必会停下来认真审查，标注团队却可以专门做这件事。不过标注本身也是一项任务，成本和质量同样要盯着。

16

剩下的工程工作

OpenAI 花钱买人工反馈的做法可以作为参照，但语言模型也能帮忙标注和改进数据。按 Frye 的说法，在文本标注任务上，GPT-3.5 Turbo 大致相当于中等水平的众包标注员，GPT-4 大致能排进前 10%，而且同等表现下成本更低。他没给出这些对比的基准条件，所以这些说法只能当作一个理由，促使你在自己的实际任务上试试模型辅助标注，不能拿来估算要配多少人手。一种混合方案是：由一个规模较小的人工团队，来监督一批语言模型标注员。

演讲结束时，这个产品难题依然没有答案。合适的界面和用户体验还没定型，让这些系统稳定给出正确结果的方法也还没找到。要把猫头鹰画完整，就得在真实应用里摸索出那些缺失的步骤：试一种做法，看看效果，加以改进，再把管用的经验分享出去，让下一个开发者起步时，手里不只有两个圆。

The Twelve-Factor App

Introduction

In the modern era, software is commonly delivered as a service: called web apps, or software-as-a-service. The twelve-factor app is a methodology for building software-as-a-service apps that:

• Use declarative formats for setup automation, to minimize time and cost for new developers joining the project;
• Have a clean contract with the underlying operating system, offering maximum portability between execution environments;
• Are suitable for deployment on modern cloud platforms, obviating the need for servers and systems administration;
• Minimize divergence between development and production, enabling continuous deployment for maximum agility;
• And can scale up without significant changes to tooling, architecture, or development practices.

The twelve-factor methodology can be applied to apps written in any programming language, and which use any combination of backing services (database, queue, memory cache, etc).

Background

The contributors to this document have been directly involved in the development and deployment of hundreds of apps, and

The Twelve Factors

I. Codebase
One codebase tracked in revision control, many deploys

II. Dependencies
Explicitly declare and isolate dependencies

III. Config
Store config in the environment

IV. Backing services
Treat backing services as attached resources

V. Build, release, run
Strictly separate build and run stages

VI. Processes
Execute the app as one or more stateless processes

VII. Port binding
Export services via port binding

VIII. Concurrency
Scale out via the process model

IX. Disposability
Maximize robustness with fast startup and graceful shutdown

X. Dev/prod parity
Keep development, staging, and production as similar as possible

XI. Logs
Treat logs as event streams

XII. Admin processes
Run admin/management tasks as one-off processes

12 要素智能体：可靠 LLM 应用的模式

Dex Horthy 把智能体还原为结构化的模型输出、确定性的执行、显式的状态和受控的循环——然后展示了在哪些地方，小剂量的模型判断胜过一个放任自流的智能体。

01

原型能用——直到可靠性变得重要

用智能体框架，项目很快就能做到 70–80% 的质量，看起来相当振奋人心。麻烦出在剩下那些失败开始影响客户的时候。Horthy 说，他曾经顺着调用栈翻了七层，才搞清楚一个提示词是怎么拼出来的、工具又是怎么传给模型的。到了这一步，当初帮你快速做出原型的抽象，反而会妨碍你把它做稳定。

他早期做的一个 DevOps 智能体，给出了最清楚的警示。他给了智能体一个 Makefile，允许它执行 Make 命令，结果它把构建步骤的顺序搞错了。他花了两个小时改提示词，最后把确切的执行顺序一步步写了进去。智能体终于能照着流程走了，可同样的流程写成 Bash 脚本，大概只要 90 秒。一项任务一旦不再需要判断，用确定性代码实现通常更简单。

Horthy 和 100 多位创始人、开发者、工程师聊过之后，对生产环境里的智能体有了一个没那么戏剧化的看法：它们大多就是普通软件，只在需要理解语言或灵活判断、而且值得付出这份成本的地方，插入 LLM 的决策。团队不一定在用新的智能体技术栈替换原有应用，而是在现有代码里加进一些小模式。

由此整理出的 12-Factor Agents 指南 既不是要大家推倒重写，也不是在攻击框架。在 Horthy 看来，它是一份写给工具的愿望清单：既要保住开发速度，也要把提示词、状态、上下文和控制流交到开发者手里，让他们能去提升可靠性。

02

工具调用就是一段 JSON 加上普通代码

第一个有用的基本单元，是把自然语言转成结构化数据。模型收到一句话，输出一段 JSON，描述想要执行的动作。转换和执行是两回事：怎么校验、怎么分发、怎么运行这个操作，仍然由应用决定。

Horthy 故意抛出一个挑衅的说法：“工具调用”这个抽象可能有害。他的用意就在这里。他并不反对智能体操作外部系统，他反对的是把机制说得神乎其神。模型输出 JSON；确定性代码用循环、switch 语句、API 客户端或其他熟悉的写法来解释它；应用再视情况把结果交回给模型。

最朴素的智能体循环很简短：接收事件，问模型下一步做什么，执行，把结果追加到上下文，如此反复，直到模型说任务完成。一次运行走下来，这串步骤会形成一张实际的图，但这张图并不是开发者事先定义的。

工作流一长，这种简单的代价就暴露出来了。每个结果都会让上下文变长，而模型塞得下很长的提示词，并不代表它就能做出精准可靠的决策。Horthy 在这里的说法来自实践经验，而不是基准测试：限制并控制发给模型的 token，通常比不加筛选地堆积历史效果更好。

由此可以得出一个实用的定义。智能体由四个自己掌控的部分组成：

- 提示词： 指导模型选择下一步。 - 分发器： 一段确定性代码，负责解释模型的结构化输出。 - 上下文构建器： 决定挑出哪些已发生的事、以什么形式呈现。 - 循环控制器： 规定何时继续、分支、总结、切换策略或停止。

把这几部分握在自己手里，应用就能显式加入中断、分支、总结和基于模型的检查，而不必接受一个不透明的循环。

去掉神秘感的智能体循环 模型提出结构化的下一步动作。应用代码负责执行，整理由此产生的上下文，并决定要不要再跑一轮。 - 事件或当前状态 — 用户消息、故障或上一次工具调用的结果，提供当前的任务状态。 - 模型选择下一步 — 提示词要求模型输出一个结构化动作，或表明任务已完成。 - 确定性分发器 — 用 switch 语句或类似代码解释 JSON。 - 整理后的上下文 — 应用记下有用的结果，并决定下一次模型调用能看到什么。 - 事件或当前状态 → 模型选择下一步（构建提示词） - 模型选择下一步 → 确定性分发器（结构化输出） - 确定性分发器 → 整理后的上下文（执行结果） - 整理后的上下文 → 模型选择下一步（如有需要则继续）

03

持久化状态，让长时间运行的工作可以消失再回来

循环一旦显式化，执行状态和业务状态就可以一起放进应用自己的存储里。执行状态包括当前步骤、下一步和重试次数。业务状态包括消息、用户能看到的数据，以及工作流正在等待的审批。两者都在手边，就能用和产品体验相同的口径查看智能体的进度。

有了这些状态，就能做常规的启动、暂停和恢复 API。把智能体放在 REST API 或 MCP 服务器后面。智能体发起一个耗时较长的操作时，中断循环，把上下文序列化存进数据库。外部操作完成后，带着状态 ID 和结果发起回调。应用重新加载存好的状态，追加结果，再次调用模型。

模型不需要一直在线，也不需要记得发生过异步任务。在它看来，下一次调用无非是带着之前的状态，外加一个新结果。持久性归应用管，不靠模型进程。

暂停与恢复长时间运行的智能体操作 状态由应用掌控，模型循环就能在外部任务运行期间停下，之后靠回调恢复，不依赖模型的记忆。 - 收到请求 — 一个 REST 或 MCP 请求启动工作流。 - 智能体请求长时间任务 — 模型选择一个会异步完成的操作。 - 持久化上下文和状态 ID — 应用把自己掌控的工作流状态序列化，存入数据库。 - 接收结果回调 — 操作完成后，带着对应的状态 ID 返回结果。 - 恢复并继续 — 应用重新加载状态，追加结果，再次调用模型。 - 收到请求 → 智能体请求长时间任务（加载上下文） - 智能体请求长时间任务 → 持久化上下文和状态 ID（中断循环） - 持久化上下文和状态 ID → 接收结果回调（在模型进程之外等待） - 接收结果回调 → 恢复并继续（按状态 ID 查找）

04

可靠性在很大程度上是一个上下文构建问题

自动生成提示词的抽象是个很好的起点。但 Horthy 认为，团队想突破最初的质量门槛，就得直接查看和修改提示词。他讲的是做实验时的掌控力：既然模型输出取决于输入的 token，开发者就得能改动这些 token、比较不同方案，评测哪种写法效果最好。

上下文也应该自己掌控。标准的 messages 数组只是一种表示方式，不是铁律。应用可以按自己的需要组织事件、对话历史、检索到的材料、记忆和业务状态，再把相关信息序列化成一条或多条模型消息。目标是把到目前为止发生了什么，讲得既紧凑又清楚。

这样一来，几个通常分开处理的机制，就归成了同一个工程问题：

- 提示词指令 规定模型要做什么决策。 - 历史 记录相关的过往动作和结果。 - 记忆 在多次交互之间保留挑选出来的信息。 - 检索 补充当前决策所需的外部材料。

这四样东西最终都会变成当前模型输入里的 token。架构上可以为了存储和维护把它们分开，但模型收到的始终是一份构建好的上下文。

看看错误处理，就知道不加筛选地保留历史有多危险。把失败的工具调用和报错交回给模型，能帮它修正无效的 API 请求，或应对暂时的服务中断。可如果不停地追加失败记录，循环就可能困在过时的错误上下文里。Horthy 建议：一旦出现有效动作，就清掉待处理的错误；有用时把之前的失败总结一下；除非细节真能帮模型选出下一步，否则别把完整的堆栈跟踪塞进去。

05

把人放进控制流，然后让自主范围保持小巧

联系人类应该是一等动作，而不是例外情况下的逃生通道。Horthy 建议给模型几种不同的意图，比如完成、澄清、上报。用自然语言表达这些意图，还能把一个重要的选择提到生成的最开头：模型先决定需要哪种交互，再生成动作的其余部分。

交互应该发生在人们本来就在用的地方。审批和纠正可以走邮件、Slack、Discord 和短信，不必逼每个用户再多开一个 ChatGPT 式的标签页。这不等于多渠道投递就很简单，但它把人的参与当作工作流的一部分，而不是把任务交接到工作流之外。

与之配套的架构是小而专注的智能体：一个大约三到十步的循环，嵌在一张以确定性为主的有向图里。可预测的流水线交给常规代码；模型只负责一块有边界的区域，在那里，理解自然语言、调整优先级或从错误中恢复才真正有用。

HumanLayer 的部署机器人就是这种模式的例子。确定性的 CI/CD 代码先等 GitHub 上的 pull request 合并、开发环境测试通过。接着，一个专管部署的智能体提出下一步动作。如果它提议先部署前端，人可以回复说应该先部署后端。模型把这条纠正转成结构化的工作流状态，提议部署后端，等待审批，执行，然后再回到前端。

部署成功后，确定性代码接手，对生产环境跑端到端测试。如果部署失败，另一个回滚智能体可以接管，负责它自己那块有边界的任务。Horthy 认为，即使整个产品有很多工具和步骤，这样的系统也依然可控，因为每个智能体拿到的上下文有限，职责也很明确。

能力更强的模型，可能会逐步接管这些流水线里更大的部分。Horthy 预计这条边界会移动：先从确定性软件起步，插入 LLM 决策，随着可靠性提升再扩大它们的范围。真正长期有用的本事，是学会在模型能稳定做到的边界附近工作，再借助提示词、上下文、状态、控制流和人的判断，把这种难以驾驭的能力变得可靠。

嵌在确定性 CI/CD 中的专注型部署智能体 模型负责一个有边界的排序决策，并接受人的纠正；周围的流水线和生产环境测试归常规代码管。 - PR 已合并、开发环境测试通过 — 确定性 CI/CD 走到部署决策点。 - 智能体提议部署前端 — 模型把部署目标转成下一步结构化动作。 - 人要求先部署后端 — 有人用自然语言改了提议的顺序。 - 审批并部署后端 — 智能体提出修正后的下一步，工作流执行。 - 部署前端 — 智能体回到剩下的部署任务。 - 跑生产环境端到端测试 — 部署成功后，控制权交回确定性代码。 - PR 已合并、开发环境测试通过 → 智能体提议部署前端（进入专注型智能体循环） - 智能体提议部署前端 → 人要求先部署后端（请求人工审核） - 人要求先部署后端 → 审批并部署后端（自然语言转结构化动作） - 审批并部署后端 → 部署前端（继续剩余工作） - 部署前端 → 跑生产环境端到端测试（退出智能体循环）

06

让模型保持无状态，让脚手架归你所有

Horthy 的最后一条要素，把智能体描述为实质上无状态：每一步所需的状态都由应用掌控并提供。他也承认，用 reducer 这个词形容多步流程不太贴切，但不管叫法怎么争，落到实现上的经验站得住：持久记忆、工作流进度和业务记录，都不该依赖内存里的模型会话。

这种偏好也决定了他想要什么样的工具。他不要一层包着隐藏行为的封装，而是要一套生成出来的脚手架，开发者能查看、能修改、能一直留着用。团队当时正按这个思路开发 Create Twelve-Factor Agent：先生成一个看得懂的初始结构，再让开发者把生成的代码接过去，归自己所有。

结尾把分工讲得更清楚了。配套工具应该替开发者拿掉外围的运维杂活，把时间留给 AI 特有的难题：怎么构建提示词、选哪些上下文、怎么设计控制流、如何与人协作。一个把这些决策藏起来的框架，拿走的可能恰恰是跨越生产可靠性鸿沟所需的控制手段。

Horthy 还提到了 A2H Protocol 方面的工作，目的是统一智能体联系人类的方式。录音里对这个提案只是一笔带过。能确定的设计原则范围更窄：只要澄清、审批和干预都能通过显式动作和熟悉的沟通渠道完成，人就能帮智能体变得更好。

落到实践上，结论刻意显得很平常。在把语言转成结构化决策能创造价值的地方用模型。把状态和执行放在自己掌控的软件里。先搭一个最小的可用循环，让人参与进来；只有当周围的系统能守住可靠性时，才扩大智能体的自主权。

要点总结

  • 只在模型驱动的判断能增加价值的地方使用智能体。如果正确流程本来就是一个确切的序列，确定性代码可能更快写好，也更容易信任。
  • 把工具使用看作结构化的模型输出加上由应用控制的执行。分发器、循环、分支和终止规则都要掌握在自己手里。
  • 把执行状态和业务状态持久化在模型之外，让长时间运行的工作流可以暂停、接收回调，并通过普通 API 恢复。
  • 上下文工程意味着选择和表示提示词、历史、记忆、检索、结果和错误——而不是把最大的上下文窗口塞满。
  • 在确定性工作流中嵌入聚焦的三到十步智能体循环，并设置明确的人工澄清、纠正和审批路径。
  • 优先选择能生成可检查、归你所有的脚手架的工具，它们去掉外围工作，却不隐藏提示词、上下文、状态或控制流。

AgentCraft：把“兽人”放进智能体编排

AgentCraft 把编程会话变成即时战略游戏式的单位，然后从可视化和快速干预出发，逐步走向自主的“战役”、基于证据的审查和共享的工作空间。

01

生成智能体是容易的部分

一个编码智能体有用，那为什么不同时开 10 个、20 个，甚至 100 个？满屏的智能体看着很唬人，可谁来确保它们一直朝对的方向推进？人成了编排的瓶颈。 平时写代码的工程师，突然得管几十个行为难以预料的“工人”。这和他们的本职工作完全是两码事。

需要的管理技能，可能早就在一个意想不到的地方练过了：游戏。即时战略游戏的玩家常常要同时操控几十个单位，在多处之间分配注意力，随局势变化随时应对。Ido Salomon 做了 AgentCraft，把这些交互模式搬进与智能体协作的实际工作中。他想抬高人与智能体协作的上限，第一步是改变人们查看和指挥运行中会话的方式。

02

一个游戏单位就是一个实时编程会话

AgentCraft 地图上的每个智能体，都对应一个真实运行中的编码会话。Salomon 举的例子有 Cursor、Claude Code、Codex 和 OpenClaw。AgentCraft 能检测设备上已经在跑的会话并把它们可视化，也能直接从界面里启动新会话。演示中，智能体还会像游戏单位一样回一句“At your command.”（遵命）。

会话建好后，用户可以像在 CLI 里那样给它发提示词，语音、文字、图片都行。演示中，Salomon 让一个智能体开发某个功能，只听见一句“Prompt prompt”，智能体就开始干活了。游戏化的界面换了进入会话的方式，但熟悉的“发提示词、让它干活”的交互一点没少。

地图周围的建筑提供各种辅助功能。有一座专门管理技能和插件；内置的终端和 Git 工具让整个开发流程都留在同一个环境里。界面上那个终端入口就是个具体例子：这张地图是通往开发工具的入口，不只是一群动画小人的展示板。

03

看到工作正在哪里发生

智能体跑起来之后，下一个问题是怎么快速看懂它们在干什么。侧边栏给出任务的整体状态和摘要。地图则提供另一种视角：它是文件系统的投影，目录铺在地图上，文件就是一个个房间。看智能体站在哪儿，就知道它在改哪个文件。

这个空间视图还连着一份变更列表。用户可以查看某个文件里发生了什么，编排器则记下每处改动是哪个智能体、在什么时候做的。几种视图各自回答不同的问题：

| 视图 | 回答的问题 | |---|---| | 任务面板 | 智能体想做什么？ | | 文件系统地图 | 它在哪儿干活？ | | 变更列表与溯源 | 改了什么、谁改的、什么时候改的？ |

每项活动既有位置，又能对上具体的智能体，Salomon 便提出用热力图暴露冲突，甚至提前避免冲突。演示没说具体怎么预防；真正落地的基础，是能看清哪些工作撞在了一起，以及各自的来龙去脉。

04

更快的反应仍然消耗注意力

光看得见还不够，用户还得能及时响应。AgentCraft 又借鉴了即时战略游戏的一种操作：靠肌肉记忆在需要关注的单位之间快速切换。在这里，打断用户的是两类请求：批准计划，或者回答问题。用户不用一遍遍去找下一个卡住的会话，只要依次处理需要帮忙的智能体就行。

Salomon 说，这让他能并行使用更多智能体，但只撑了一小会儿。切换再快，脑子里同时装着好几件事的负担也没减轻，人最后还是会累。降低每次介入的成本，不等于减少介入的次数。 所以下一层要同时解决两件事：活从哪儿来，以及谁来持续盯着。

05

委派任务发现和监督

在找活这件事上，Salomon 让智能体自己去发掘任务。这些任务以 quest 的形式出现，用户点一下按钮就能启动，其中包括重构和测试类的工作。这样用户不必亲自想出每一项新任务，但另一项成本还在：总得有人不停地在智能体之间切换、盯着它们。

战役（campaign） 把更多职责交给了智能体系统：

1. 用户给出一个宽泛的目标。 2. AgentCraft 启动一个容器，让智能体在里面干活。 3. 智能体拆解任务、制定计划，再交给用户过目。 4. 战役编排器接手，持续监督拆解后的各项工作。

Salomon 给出的理由是，有容器隔离，战役内部就可以容许更多探索性操作；但这并不是经过验证的保证，不代表任何操作都安全。真正的变化在于分工：人的精力集中到规划和审查上，不必再时时刻刻在旁边看着。

06

从提供想法到审查实现

智能体能管好一场战役之后，连最初的点子也不一定非得由用户来出。Salomon 提议每天跑一个 cron 任务，去 Twitter 上搜罗有意思的点子，把它们实现出来，再由他决定要哪些结果。他说，靠这个办法，他很快就把频道功能做出来了。紧接着又冒出一个新队列：一大堆等着审查的 pull request。

审查包（review bundle）让这个队列更好评估。它把改动、改动原因和相关任务汇总到一起，还附上截图和视频。审查者既能看到智能体改了什么，又能直接看到结果长什么样，不必翻着活动记录把每场战役从头拼凑一遍。

这改变了规划和挑选之间的比重。Salomon 问：如果智能体能直接做出十种实现，让用户挑最合适的那个，那一份详细的计划还值得花多少力气？“十种”是他提出的探索策略，不是实测出来的生产力数据。它的前提也很明确：只有备选方案审查起来足够省事，把精力从规划上挪开才行得通。这也是为什么演示里，审查证据紧跟在战役自主性之后登场。

07

与人以及他们的智能体共享工作区

智能体能自主，不代表就不需要别人了。智能体仍有局限，所以 AgentCraft 把工作区扩展到了人类队友。在 Salomon 的例子里，一位产品设计师和自己电脑上的智能体一起工作。每个参与者都能看到对方的智能体，也明白它们在做什么。

设计师开始做一个新页面。工程师可以等这项工作做完，也可以立刻把它交给工程这边的智能体，从那里接着往下做。Salomon 说着说着，把“我的智能体”改口成了“我们的智能体”：在这个工作区里，智能体是大家共同出力的一部分，而不是藏在每位队友电脑里、各管各的助手。

于是，协作有了两种形式：

- 直接下提示词： 参与者既可以给自己的智能体下指令，也可以给队友的智能体下指令。 - 共享对话： 人和智能体在同一个聊天里交流，进行中的工作一目了然，又不用把每条消息都变成命令。

比如，一个智能体宣布自己要开工了，一个人回复：“我也在弄这个。”智能体下一步行动时，就能把这块重叠的工作考虑进去。知道别人正在改哪些文件，能支撑这种更柔性的协调；但它本身不会加排他锁，也不能保证杜绝冲突。

08

指挥工作的技能

演示还有不少功能没来得及展开，最后落在了产品背后人的转变上。从自己写代码到指挥别人写代码，可能感觉像闯进了一份陌生的工作。Salomon 的回答是：所需的一些技能，其实在职场之外早就有了。游戏就是这样一个地方，人们在里面练过操控单位、分配注意力和协调行动。

AgentCraft 的方向，是靠更好的可见性、更强的智能体自主性，以及人与智能体之间的协作，把这些技能用起来。Salomon 把它作为免费软件提供下载，录像结尾展示了网站和二维码。他也坦言产品还很新，带有实验性质，仍有不少地方要改，并邀请用户加入 Discord 社区反馈意见。他的邀请很简单：试试这种编排方式能不能让真实的工作变得更好；如果不能，就一起把它改好。

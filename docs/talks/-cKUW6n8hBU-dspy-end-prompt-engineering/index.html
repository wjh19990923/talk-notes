核心概念

幻灯片原文
Signatures declare inputs and outputs; modules organize them, and adapters turn them into prompts. Tools connect the program to the outside world, while optimizers improve it against metrics.

[7:06](https://www.youtube.com/watch?v=-cKUW6n8hBU&t=426s) [Six cards summarize signatures, modules, tools, adapters, optimizers, and metrics.](https://assets.ai.engineer/sites/aiecode2025/sha256/fc77a02541f883b768792853ad1c8647f4a1199d90df9cc4a86fae6753068ed0.webp)

Core Concepts

Signatures
Specify what you want, not how; let the LLM figure it out

Modules
Structure your program logically

Tools
Interact with the outside world - or the rest of the program

Adapters
Customizable prompt formatters: think JSON, BAML, XML, etc.

Optimizers
Optimize your DSPy program, ML-style

(let the LLM figure it out!)

Metrics
Define what to optimize against (can be multiple things)

选择 DSPy 模块

幻灯片原文
DSPy modules match different tasks: Predict makes a basic model call, ReAct exposes tools, and ProgramOfThought uses generated code for calculations. Other modules compare outputs, refine results, or process items in parallel.

[15:37](https://www.youtube.com/watch?v=-cKUW6n8hBU&t=937s) [Table matching tasks such as inference, reasoning, tool use, comparison, refinement and parallel processing to DSPy modules.](https://assets.ai.engineer/sites/aiecode2025/sha256/453b83e86d113612df403e15dbcceae83f1e0528cc82dbb214aeb79e2189dcdb.webp)

Modules

Do you need... | Module
To perform a basic inference? | dspy.Predict
Step-by-step reasoning? | dspy.ChainOfThought
To interact with tools (like search/APIs) or execute code for external data/actions? | dspy.ReAct (for tools) or dspy.CodeAct (for code)
Deterministic, high-precision, or complex calculations performed by generated code? | dspy.ProgramOfThought
To compare multiple outputs? | dspy.MultiChainComparison or dspy.BestOfN
Iterative improvement? | dspy.Refine
To process multiple items? | dspy.Parallel

# Define your tools as functions
def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    # In a real implementation, this would call a weather API
    return f"The weather in {city} is sunny and 75°F"

def search_web(query: str) -> str:
    """Search the web for information."""
    # In a real implementation, this would call a search API
    return f"Search results for '{query}': [relevant information...]"

# Create a ReAct agent
react_agent = dspy.ReAct(
    signature="question -> answer",
    tools=[get_weather, search_web],
    max_iters=5
)

# Use the agent
result = react_agent(question="What's the weather like in Tokyo?")
print(result.answer)
print("Tool calls made:", result.trajectory)

def forward(self, image):

DSPy：提示词工程的终结

从检索合同到检查优化后的模块，Kevin Madura 展示了带类型的签名、普通的 Python 控制流和可衡量的反馈如何在 DSPy 中结合在一起。

具备基础的 Python、类型注解知识，并了解如何调用语言模型，有助于理解示例。

01

检索合同从一个程序开始

How do you search ten thousand contracts for a particular clause or paragraph? In Kevin Madura’s consulting work, that problem sits alongside law-firm investigations, process improvement, and internal AI deployment. DSPy gives his team a way to express these tasks as modular Python programs whose functions can call language models. The work becomes defining the processing steps and their inputs and outputs, rather than repeatedly adjusting strings by hand.

The workshop repository collects small examples: sentiment classification, PDF analysis, multimodal questions, web research, document-boundary detection, recursive summarization, and GEPA optimization. These are demonstration utilities assembled over several days, not a finished production application. Their value is in showing how the same primitives combine across quite different tasks.

Keep the program’s intent and control flow stable while changing the model underneath. A DSPy call looks like a function with declared inputs and outputs. That removes routine work such as navigating .choices[0].message.content, parsing strings, and moving JSON between stages. Madura connects this to Omar Khattab’s systems-minded description of DSPy: the system’s design should remain useful even as model capabilities change. Generated prompts remain inspectable when the abstraction needs investigation.

Pydantic AI, LangChain, and Agno are also ways to build applications around models. Madura’s preference comes from how DSPy fits his team’s work, and he acknowledges that its declarative style initially took some effort to understand. The examples are an invitation to test that fit against a concrete workload.

02

通过签名声明任务

DSPy separates six responsibilities that otherwise tend to accumulate inside one prompt-building function:

| Primitive | Responsibility | |---|---| | Signature | Declare inputs, outputs, types, and task instructions | | Module | Compose model calls with ordinary program logic | | Tool | Expose a Python function to the model | | Adapter | Format the signature and values as model messages | | Optimizer | Improve a program against an evaluation criterion | | Metric | Define what successful behavior means |

Modules follow a PyTorch-inspired organization. Adapters bridge the declarative interface and the strings ultimately sent to a model. Optimization is optional: the programming abstractions are useful before any search for better prompts begins.

A signature can be a short string or a class backed by Pydantic. In the class form, field names do more than label Python attributes: they become part of the instructions the model sees. A name such as sentiment communicates an intended task; a description explains its scale or constraints. The adapter carries those names, descriptions, and types into the generated message. Choose names for both the Python reader and the model.

An existing, carefully developed prompt can go in the signature’s docstring. DSPy also permits additional instructions and lower-level changes to the final message. Adopting signatures does not require throwing away useful wording; it gives that wording a place inside a composable program.

For a sentiment prototype, the shorthand declares a text input and an integer output. Instructions then establish the direction of the scale:

```python import dspy

sentiment_signature = dspy.Signature( "text: str -> sentiment: int", instructions=( "Classify the sentiment of the text. " "Lower numbers mean more negative sentiment; " "higher numbers mean more positive sentiment." ), )

classify_sentiment = dspy.Predict(sentiment_signature) ```

This creates a predictor to use with a configured language model. The type alone cannot define the meaning of an integer, so the instructions remain part of the contract. Start with that small declaration, inspect its behavior, and add constraints or a surrounding module as the task becomes clearer.

03

把模型调用与普通 Python 混在一起

A module packages a reusable piece of behavior. DSPy includes modules for several familiar techniques, and a custom module can make an existing approach available to the rest of a program.

| Module | Role | |---|---| | dspy.Predict | Make a direct prediction from a signature | | dspy.ChainOfThought | Add an explicit reasoning step to the response | | dspy.ReAct | Let the model use supplied tools | | dspy.CodeAct | Support an agent approach built around code | | dspy.ProgramOfThought | Generate code and return its execution result |

Madura questions how much explicit chain-of-thought prompting adds for newer models, but uses it to illustrate how a prompting technique can live inside a replaceable module. ProgramOfThought provides a Python interpreter and can use a custom execution harness. Other modules support output comparison, refinement, and parallel processing.

The time-entry corrector shows why the surrounding Python matters. A client needed hundreds of thousands of entries to follow consistent conventions, including tense, capitalization, and periods at the end of sentences. Initialization creates a predictor for changing tense and supplies the relevant instructions. The module’s forward method then calls that predictor and applies hard-coded business rules. Linguistic judgment and deterministic formatting can occupy separate steps while remaining one callable component.

Tools are ordinary Python functions exposed through DSPy’s tool interface; LiteLLM underlies the model interface. The introductory agent supplies get_weather and search_web to ReAct, uses the signature question -> answer, and caps the loop at five rounds. Asking about the weather in Tokyo then gives the model a question, a bounded opportunity to use the tools, and an answer field to populate. The functions implement the capabilities; the agent chooses when to invoke them.

04

改变表示方式，保持任务不变

An adapter turns a signature, its inputs, and associated instructions into model messages. In the clinical-note example, a string input and a nested patient-details output become a prompt containing the fields and their schema. A default adapter handles the ordinary case; replacing it changes how the model sees the task without requiring a rewrite of the program.

Madura reports a use-case-dependent 5–10% performance improvement from JSON-versus-BAML adapter testing, without specifying the task or metric. He attributes the testing to Prashanth and suggests that the more readable format might also use fewer tokens. The historical BAMLAdapter discussion describes simplified schema notation derived from BAML, rather than the full BAML language. That workshop-era formatting example should not be read as a version-independent API contract or a general performance guarantee.

Multimodal inputs use the same signature-based approach, provided the selected model supports the modality. The Attachments library prepares files as model-ready content and integrates with DSPy. In the first document example, it fetches an NVIDIA SEC Form 4, prepares the document, and passes it with a question asking how many shares were sold. Answering requires combining two transactions; the displayed answer is 497,797 shares.

An audience question establishes the actual data path: there is no vector store, embedding step, or retrieval search in this example. The model receives the document images and extracted text directly. Madura initially speculates about OCR, but the mechanism needed here is simply document preparation followed by a model call over that content.

05

在优化之前先定义成功

Once a program has measurable inputs and outputs, an optimizer can search for instructions that improve its behavior. Madura recommends trying this before committing to fine-tuning infrastructure. One motivation is model transfer: preserve the application’s structure while finding a prompt that makes a less expensive model adequate for the task.

Madura illustrates model transfer with a hypothetical million-call-per-day classifier moving from GPT-4.1 to GPT-4.1 nano, whose score rises from 70% to 87% after optimization. Those are teaching values, not results from a run. His accompanying suggestion of multiple orders of magnitude in savings is too broad for the named models’ like-for-like token rates: their launch pricing differs by a factor of twenty. Total workload savings also depend on token usage and the cost of optimization.

The optimizer works on prompts inside the composed program, measuring the resulting input-to-output behavior. That is why decomposition matters: a system with several modules exposes several places where instructions can improve. Madura returns to Khattab’s distinction here—DSPy supplies programming abstractions that happen to be optimizable. Its usefulness does not depend on running an optimizer first.

A discussion between Karpathy and Dwarkesh provides Madura with an intuition about this search. Models can discover weaknesses in an LLM judge; he wonders whether prompt optimization can exploit a related sensitivity in a useful direction, finding instructions that elicit better behavior. This is his analogy for the search process, rather than its formal definition. The practical procedure is simpler:

1. Decompose the task into modules. 2. Define metrics that express the behavior you need. 3. Optimize the program against those metrics.

Madura then cites Chris Potts’s discussion of GEPA matching or exceeding GRPO in studied settings. That comparison belongs to specific research experiments, not every model or fine-tuning workload.

The metric determines what the optimizer learns to improve. Each proposed change produces outputs that the metric scores. For time-entry correction, some requirements admit exact checks; others can use an LLM judge to assess whether the generated text meets qualitative criteria. These choices define the feedback available to the optimizer, so a vague or misaligned metric leaves the search pursuing the wrong behavior even when its score improves.

带类型的答案、缓存的调用与用量

07

让模型选择字段——或者事先规定好

The live Form 4 example makes document preparation visible. Attachments uses pdfplumber, produces Markdown, and prepares images before the question about total shares sold is passed to the model. Madura then changes the output contract: instead of answering one question, a ChainOfThought document analyzer returns a dictionary of information it considers important. The model chooses the keys and values within that broad structure.

For a specific business workflow, the schema can instead prescribe the required fields. Madura defines Pydantic classes for filing information and transactions, then makes that schema the analyzer’s output type. The document input still contains prepared text and images; the response now contains filing date, form date, form type, transactions, and the answer in a predictable structure.

| Output contract | Useful when | |---|---| | Model-selected dictionary | Exploring what a document contains | | Prescribed Pydantic schema | Feeding known fields into downstream code |

The structured result supports dot notation, so downstream logic can use the returned object directly.

08

检查模型实际收到了什么

inspect_history exposes the messages beneath the abstraction. For the document analyzer, Madura shows the generated system message, input and output fields, extracted document content and metadata, and the formatted model response. DSPy parses that response into the object available as response.document_schema. The short signature is therefore an interface to a longer message-building and parsing process, not the literal prompt by itself.

The clinical example makes the adapter boundary easier to see. A patient-details model contains a nested patient-address object, and a signature extracts that structure from a clinical note. Python’s with context lets a call override the globally configured language model or adapter. In the live sequence, Madura switches from his Smart LLM configuration, which he identifies tentatively as GPT-4.1, to Anthropic while also using the BAML adapter. After a connection interruption, both calls show the same extracted output.

Inspecting the last two calls reveals the representation change:

```python import dspy

dspy.inspect_history(n=2) ```

One message contains the expanded JSON schema; the other uses the more compact BAML-derived notation. Since the live comparison changes both the model and the adapter, it demonstrates inspectability and interchangeable configuration, not an isolated measurement of adapter quality.

09

一个停车问题变成了一个有状态的组件

A photograph of street signs becomes another typed task: given the image and the current time, can the driver park now, and when should they leave? The signature asks for a Boolean and a departure-time string. The displayed prediction contains can_park_now=True and a departure time of 15:30, alongside a reasoning field. The optimizer returns another callable module. It can be serialized, saved, loaded, and used wherever the original module was used. For GEPA, a language model proposes new prompts, the program runs with those prompts, and evaluation feeds the next iteration. The resulting instruction string is accessible separately, but the module also retains the program interface and signature state. That explains why the artifact is more useful than an isolated prompt pasted into a document: the optimized behavior remains attached to a callable component with defined inputs and outputs. The last question concerns expense and large contexts in optimization datasets. DSPy makes model calls convenient, but their number still matters: Madura uses a million asynchronous calls as an example of how a program can create substantial spend. A short signature also expands into a longer prompt containing instructions and schema information, so the visible declaration is not an estimate of input tokens.

A custom adapter can compress the message representation. Program logic or modules can track context state and decide what to retain, summarize, or pass onward. Madura does not offer a concrete recipe for shrinking large-context optimization datasets; his expectation that larger windows or more abstracted context management may help is an intuition. The operational responsibility stays with the program: choose the calls, inspect the messages, measure the behavior, and manage the context that each stage actually needs.

规模化的智能体：深入 MiniMax 的模型及其背后的基础设施

MiniMax 的 Olive Song 和 Together AI 的 Dan Fu 把多模态训练、有用的内核基准、长时间运行的智能体评测，以及承载它们所需的基础设施联系在一起。

熟悉语言模型推理、强化学习和 GPU 内核会有帮助；不需要了解 MiniMax 的架构。

01

从训练模型到提供服务之间发生了什么？

新模型发布了。开发者要想稳定地用上它，之前得先做好哪些事？发布之后，又有哪些事还在持续变化？Dan Fu 和 Olive Song 恰好站在这次交接的两端。Dan 是 Together AI 的 Kernels 副总裁，负责推理和 GPU 优化。Olive 是 MiniMax 的强化学习研究负责人，负责最后阶段的训练和发布，也就是紧挨在推理前面的那段工作。

主持人介绍说，MiniMax-M3 是 MiniMax 迄今最强的模型，并问公司为什么要开放权重。Olive 的回答把“开放”和“改进”连在一起。开发者可以用这个模型，反馈意见，提交 pull request，帮着把它做得更好。推理专家可以针对同一份权重做优化，让它跑得更快。开放权重让训练到服务的交接环节成了其他团队也能出力的地方，改进不必全靠模型的创造者一家来做。

02

从一次非正式介绍到架构工作

主持人说，当天上午 M3 的 token 用量大头都来自这次分发合作，但没给出具体占比，也没说分母是什么。Dan 把 Together 的目标说得更宽：放出更多 token，让更多人用它们做有用的事。双方的合作起初很随意。前一年在拉斯维加斯的一场汽车活动上，一位 MiniMax 的代表劝 Together 来服务他们的下一个模型。

此后，Together 先后上线了 MiniMax-M2.5 和 MiniMax-M2.7。临近 M3 发布时，团队已经看到了足够多的用量和开发者活跃度，对下一个版本充满期待。合作随后落到具体的工程上：研究模型架构，做优化，摸索最好的推理服务方式。这段关系不只是一份分发协议，它让服务团队能深入到模型的技术决策里。

03

能力取决于任务如何被定义

和 M2 系列相比，M3 最大的变化是多模态。它除了理解文本、写代码，还能看懂图像和视频。Olive 重点提了两个应用：

- Computer use：操作电脑，用电脑上的工具做出东西来。 - 游戏开发：MiniMax 专门下过功夫的能力，Olive 认为这是这个模型被低估的一种用法。

这些例子让任务不再只是输出一段文字答案。模型得借助工具干活；做视觉类应用时，还得看懂工具产出的结果。

主持人接着提到 SVG-Bench、KernelBench 和 OSWorld，问针对特定领域做后训练需要什么。Olive 先讲的是数据和问题定义，而不是某一套训练配方。以 kernel 优化为例，环境必须让模型能动手改 kernel，并一轮轮提升性能。设计环境本身就是在定义学习问题：它决定了模型能采取哪些动作，也决定了强化学习能发现哪些改进。

04

一个解法可以变成基础设施的基准

Dan 说，开源和闭源模型写 kernel 的能力都在变强，Together 开发 kernel 和优化框架时已经在用模型了。ParallelKernelBench 又往前走了一步：里面收录了一些 Dan 口中“尚未解决”的问题。团队梳理了模型推理的各种服务方式，发现有些地方明明有加速空间，却还没有好用的 kernel。这些空白就成了基准测试的目标。

这样一来，刷基准的动机就变了。通常，过拟合让人担心分数涨了，却没做出测试之外真正有用的东西。在这里，Dan 反而欢迎专门针对基准的解法，因为 Together 可以直接拿走这些 kernel，用来加速推理和开发。如果解出基准里的任务就能得到可用的工程成果，这个基准就有价值。 主持人顺着这个思路往下说：如果基准覆盖了足够多实际有用的问题，把这些问题纳入模型的训练分布，本身就是好事。

05

发布首日开启了一份优化待办清单

服务工作在发布前就开始了：合作方会提前分享架构细节。M3 的细节里就有 MiniMax Sparse Attention。注意力机制只是差异之一，开源模型在混合专家（MoE）的设计和量化方案上也各不相同。推理引擎不能想当然地认为，每个新模型都只是上一个模型换了套权重。

Dan 介绍了一套实际流程：

1. 检查架构。找出模型需要哪些算子。 2. 给现有 kernel 跑基准测试。判断哪些现成实现能直接用，哪些要改，哪些得从零写。 3. 守住发布质量。确认上线的模型能达到预期的质量和用户体验。 4. 逐项清理待办。发布后继续改进 KV cache、注意力 kernel 和量化。

Dan 提到，发布后的头几周里性能一步步在提升，但没给出具体的加速数字。发布只是一个能用的起点，性能工程远没有结束。

主持人讲了一段和 Ingrid 的对话，说明节奏有多快。他问 M3 的性能有没有提升，本意是和上个月比，她却理解成和前一天晚上比。这个小插曲说明，模型一旦开始承接真实流量，优化周期能短到什么程度。

06

智能体改变了推理引擎需要优化的东西

模型在变，负载也在变。过去是人偶尔发几轮对话；现在，一个框架能在持续进行的任务里发起几百次工具调用。Dan 说，这会影响 KV cache 的设计、提示方式，以及优先优化技术栈的哪些部分。他做了个对比：一边是不算长的系统提示词加对话历史，另一边是把整个代码库都塞进来的编程工作流。

| 负载类型 | 上下文形态 | 服务关注点 | |---|---|---| | 聊天 | 系统提示词和对话历史 | 处理一轮接一轮的对话 | | 编程智能体 | 代码库和反复的工具交互 | KV cache、路由和 kernel 表现 |

关键区别在于工作的形态，而不只是提示词变长了。引擎要围绕大段上下文，一轮又一轮地处理交互。Together 会跟踪这些负载变化，决定推理栈往哪个方向演进。

07

训练模型看见自己的代码产出了什么

主持人举了一个具体的多模态智能体循环：让编程智能体改进一个 Web 应用，它先自己用一遍，再把观察到的东西带进下一轮迭代。只读源代码的模型会漏掉一部分线索。要改进渲染出来的界面，最好能直接看到并理解界面本身。

Olive 解释说，M3 从第一步起就同时用文本和图像训练。她说 MiniMax 克服了其他实验室也碰到过的那类训练崩溃，但没讲具体怎么解决的。她指出，能直接观察到的现象在注意力图里：文本 token 会关注视觉 token，两种信息由此产生交互。

网站开发正好用得上这种交互。模型可以看网站长什么样，再据此改进它，强化学习过程中也一样。在主持人描述的循环里，渲染出来的应用成了下一步编码决策的依据。文本和视觉一起训练，让模型能把代码实现和它呈现出的效果对上号。

08

架构会变，工程经验可以迁移

主持人提到，M3 同时带来了一百万 token 的上下文窗口、多模态和稀疏注意力。几样叠在一起，能优化的地方就非常多。被问到一千种可能里该先做哪个，Dan 开玩笑说要做一千零一个。他的意思是把能找到的改进都找出来，并没有给瓶颈排优先级，也没说哪一项优化最关键。

铺得这么开，并不等于每个模型都要从头来过。Dan 说，MiniMax Sparse Attention 和 DeepSeek、GLM 里的变体不一样，但优化那些变体积累的经验仍然用得上。哪怕具体算子变了，优化流程和写 kernel 的经验也能沿用下去。

Dan 说，这些经验可以一直追溯到他读博时的研究。看到这些想法被大规模训练、用进已部署的模型，本身就是一种验证。主持人把这放进更大的图景：开源模型实验室可以互相借鉴成功的做法，让好的架构和工程思路传播开来。

09

长期研究任务需要中间证据

主持人引用了 MiniMax 发布时的说法：模型用 12 个小时复现了一篇 ICLR 论文。讨论中没说是哪篇论文，也没说按什么标准算复现成功，所以这只是一个对外介绍的案例，不能当成复现成功率。它引出了一个比短编程任务更难的训练问题：复现论文、优化 kernel 框架，可能需要一长串决策，需要 GPU，还要在有限的硬件资源下完成。

训练上的答案又回到了和 kernel 后训练一样的基础：定义问题，选数据，设计奖励，搭环境。长任务还促使团队改进 RL 算法，让训练更高效。讨论讲到了能力如何在一轮轮 RL 迭代中涌现，但没给出完整的算法配方。

评测不必等整个运行结束。模型可以多次提交，每次提交都能单独评测。划分验证集和测试集，有助于分清真正的进步和钻评测空子的尝试。中间提交能证明有进展；留出集检查则看这种进展离开模型一直在优化的目标后是否还站得住。

一个简单的 Python 评测器，就能在结果记录里守住这种区分：

```python from collections.abc import Callable, Iterable from typing import TypeVar

Candidate = TypeVar("Candidate")

def evaluate_submissions( submissions: Iterable[Candidate], validation_score: Callable[[Candidate], float], test_score: Callable[[Candidate], float], ) -> list[dict[str, int | float]]: records = [] for submission_id, candidate in enumerate(submissions): records.append({ "submission_id": submission_id, "validation_score": validation_score(candidate), "test_score": test_score(candidate), }) return records ```

这段代码只负责评测记账，不是训练算法。针对具体任务的打分函数，以及哪些结果会作为反馈交给模型，仍由框架决定。而且只有测试集始终独立于优化过程，单独保留测试分数才有意义。

讨论接着把评测和 M2.7 的自我进化工作 联系起来。用模型加速内部研发，又多了一个任务来源：研究员自己的工作。这些任务可以变成内部评测，让模型评估和团队真正想提升的研发工作紧紧挂钩。

10

KV 缓存变成了一个分布式存储问题

长时间运行的智能体，又把话题拉回了服务基础设施。并发请求一多、上下文一长，KV cache 就会不断膨胀。Dan 把管理 KV cache 比作搭一个分布式文件系统，或者一个超大型数据库。问题不再只是 kernel 跑得多快，还包括系统怎么存储、查找和搬运推理所需的状态。

Dan 把它归结为几个熟悉的存储问题：

- 放置：缓存该放在哪？ - 识别：系统以前见过这段内容吗？ - 检索：怎么取回需要的缓存？ - 迁移：怎么在不同位置之间传输缓存？

他开玩笑说，整个行业正在重新发现本科系统课上讲过的东西。概念也许不新，实现上仍得小心：好的缓存设计，必须把这些存储决策和真正读取缓存状态的推理工作衔接起来。

11

更好地利用硬件，更快地开发模型

主持人提到 Dan 在 Stanford 的一次讲座，问他三年后回头看，今天的做法会是什么样。Dan 头一个说的是 GPU 利用率不足。他随口引了一个数字：据说 SpaceX 的 FLOP 利用率只有 10% 左右，但没说是什么负载、怎么测的。他更大的期待是，训练和推理都应该把现有硬件用得充分得多；进步不必全指望拿到新 GPU。

Dan 还希望，开源模型能不能追上闭源前沿这场反复出现的争论能就此尘埃落定。他举了 M3、GLM 和 Kimi，认为它们让人有理由乐观地看待开源模型和 Anthropic、OpenAI 的竞争。这是他对发展方向的判断，讨论中并没有拿出基准对比。

主持人把同样的展望问题抛给后训练这边，把自我进化描述为：模型搭一个框架，在框架里训练，再产出下一个 checkpoint。这种简化说法更适合理解为模型辅助研发，并不能证明已经有了完全自主的训练流水线。Olive 回忆说，三年前她还在上学，还没入行；那时很难想象今天的节奏会这么快。

她现在已经看得到的，是模型在加速研发，她说这个过程一年多以前就开始了。这些工具越来越好，开发下一代模型的速度也会跟着加快。Olive 把这种加速和开放权重模型追上前沿实验室联系在一起，也回到了 MiniMax 开放权重的初衷：让这些能力人人都能用上。

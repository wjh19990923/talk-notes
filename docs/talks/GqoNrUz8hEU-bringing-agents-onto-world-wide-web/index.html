把智能体带上万维网

可靠的浏览器智能体需要的不只是强大的模型：还需要精选的上下文、可复用的网站知识、一致的浏览器环境，以及代表用户安全行事的方式。

熟悉 LLM 工具调用和基本的浏览器自动化会有帮助；TypeScript 示例使用 Playwright。

01

为什么浏览器自动化仍然会出问题

智能体已经会用电脑了，为什么还是很难在网上把日常工作做完？用过 Operator 的人都能看到其中的潜力。难的是把这种潜力变成一个能持续运转的系统。Browserbase 创始人 Paul Klein IV 把这种情况称为能力过剩（capabilities overhang）：模型能做的事，超出了周边系统能稳定支撑的范围。

网页是为人设计的。页面会变，页面内容会吃掉大量上下文，浏览器会启动失败，各种拦截会打断原本很简单的任务。Klein 职业生涯早期就碰上过这些问题。那时做网页自动化，意味着每天都要维护脚本。现在智能体能帮他写出更耐用的自动化脚本。但耐用的脚本离能自主处理陌生工作的智能体，还有一段距离。要解决的正是这段差距。

02

模型需要一个能工作的环境

一年前，Klein 认为模型是长程任务的一大瓶颈。后来模型操作界面的能力提升了，他的看法也随之改变。他把部分进步归功于强化学习环境：在接近真实网页的环境里，用人类操作轨迹训练模型，模型就能提前练习日后真正会遇到的工作。Klein 说，过去六个月里，计算机操作（computer use）RL 环境获得的投入，相当于编程环境此前一年的投入。这是他对行业势头的判断，不是这里给出的投资实测对比。

模型变强了，部署问题依然存在。Klein 引用了 Dwarkesh 的观点：模型只要足够强，自然会被广泛用起来。接着他指出了缺失的那块工程：智能体框架（agent harness），也就是让模型与外部世界交互的脚手架、工具和系统。在这套外围系统上投入，能释放出裸模型接口发挥不出来的能力。

Karpathy 在 2023 年 11 月画过一张图：LLM 居中，四周环绕着各种工具。这张图可以当作架构参考。代码解释器让模型能计算、执行程序；音视频输入（包括截图）让它能观察；浏览器让它能访问网站；其他 LLM 可以充当子智能体。框架把这些能力连成一套为任务服务的操作系统，而不是让模型只管输出文字。

03

对照基线衡量框架

编程智能体已有先例。Klein 举了 Factory 和 Claude Code 的对比：两者底层用同一个模型，只是外围系统不同，任务表现就可能拉开差距。他认为 Cursor 很早就在做框架工程，也把 Browserbase 在浏览器上的工作看作同类尝试，目的都是让模型适配某个特定领域。这里比较的是共用同一模型的完整系统，并不是说框架能让分数超出模型本身的水平。

领域框架是工程团队自己就能做的事，不必先变成模型实验室。 公司了解自己的任务、界面和失败模式，可以用这些知识改进智能体手里的工具和上下文。定制框架最终能否胜过越来越强的 RL 训练系统，演讲没有给出定论。眼下的要求更实际：加上框架，再拿它和基线模型配置比一比表现。

04

把浏览器交互与代码结合起来

机会远不止编程。Klein 提到 Greg Brockman 的一个习惯：遇到一件事，就问自己为什么没用 Codex 来做，借此找出还没用上的能力。Klein 说，从定性观察看，编程任务的完成率高于计算机操作任务，原因在于编程的工具更好，框架也更成熟。一张 Andreessen 的幻灯片给出了下一步的动力：大量非编程工作流都能从计算机操作中受益。要拿下这些场景，他认为需要三样东西：多模态操作、框架工程和可靠的基础设施。

这里的多模态操作，既包括选模型，也包括选方法。复杂页面也许值得用更强的模型，简单页面未必需要。智能体还可以把编程和计算机操作结合起来，不必把每个操作都当成在截图上点一下。一种做法是先查看网络请求，再让编程智能体写个脚本，重放相关请求。

| 任务情况 | 合适的执行方式 | | --- | --- | | 复杂界面 | 用更强的模型来理解 | | 简单界面 | 用更简单的模型完成交互 | | 可重复的请求序列 | 写代码重放相关请求 |

Klein 说，可靠的生产级浏览器智能体，往往一边用浏览器，一边写代码。他对比了两种做法：让 Claude Code 生成脚本，或让 Claude in Chrome 直接完成交互。对于重复性工作，用脚本描述任务，比反复查看页面占用的上下文少。浏览器负责摸清和走通工作流，重复的部分交给代码。

05

别再一遍遍重新摸索同一个网站

工作流一旦开始重复，记忆和技能就成了执行策略的一部分。Klein 介绍了 Browse.sh，这是演讲前几周上线的网站技能目录。有了这些技能，智能体在访问网站之前，就能先看看自己能做什么。WebMCP 则提供了另一种途径，让智能体知道网站上有哪些可用操作。两者针对的是同一种浪费：熟悉的操作，智能体不该每次都从头摸索。

智能体通过 CLI（比如 Playwright 的 CLI）控制网站时，道理也一样：给工具的同时，把相关技能和上下文一并给上。把整个页面一股脑塞给模型，每次交互都很贵，有用的信息也可能被淹没。框架既要选工具，也要选用好这些工具所需的信息。 上下文里应该留下决定下一步动作的内容，去掉那些无助于得出可重复结果的页面内容。

06

保持浏览器环境的一致性

框架底下的基础设施也必须靠得住。Klein 拿大家抢购 Mac mini 来跑 OpenClaw 举例，很能说明问题：家里的一台机器能提供 macOS、SSH 远程访问，还有住宅网络环境，而网络环境会影响遇到 CAPTCHA 的情况。个人这么用没问题，但光靠它，解决不了几千个客户智能体的运行问题。他开玩笑说，还没见过通过 SOC 2 合规的 Mac mini 大规模部署。这句玩笑点出的，正是一台能用的个人机器和一套受管控的生产环境之间的距离。

还没到规模化，一致性就已经很重要。多次运行应该遇到同类的输入和输出，页面尺寸和布局也要稳定。如果这次拿到移动端布局，下次拿到桌面端布局，同一个任务就可能出现不同的控件和导航。框架和模型只好去消化自家基础设施带来的波动。

对基于 Playwright 的框架来说，固定浏览器上下文，就能把视口要求明确写死。下面这个 TypeScript 辅助函数打开的每个页面都使用同一个桌面尺寸，调用方传入浏览器和目标地址：

```typescript import type { Browser, BrowserContext, Page } from "playwright";

export async function openAgentPage( browser: Browser, url: string, ): Promise<{ context: BrowserContext; page: Page }> { const context = await browser.newContext({ viewport: { width: 1280, height: 720 }, isMobile: false, hasTouch: false, });

try { const page = await context.newPage(); await page.goto(url, { waitUntil: "domcontentloaded" }); return { context, page }; } catch (error) { await context.close(); throw error; } } ```

任务结束后，调用方负责关闭 context。固定视口能消除一个布局变化的来源，但挡不住网站本身发生变化。

07

让网站上的操作可被发现

改进智能体只是问题的一面。要改进网页，就得说服网站运营方：他们其实希望智能体来访问，替用户办事。无障碍功能已经打下了基础。智能体不必只读原始 HTML 和 DOM，还可以借助无障碍树和 ARIA 标签识别组件，弄清该点哪个控件。带标签的组件，比一团不分彼此的页面标记好用得多。

WebMCP 把这个思路往前推了一步：从识别控件，走到暴露结构化操作。Klein 把它描述为在页面里发布 MCP 服务器；更准确地说，Chrome 的 WebMCP 是通过 HTML 和 JavaScript API 暴露页面工具。它最初以早期预览版推出，后来更新的 Chrome 文档 写的是源试用（origin trial），还没有全面开放。实际的例子是通过网站提供的工具提交注册表单：智能体拿到的是网站有意暴露、节省上下文的操作，不用另外安装服务器集成。

llms.txt、skills.md、AGENTS.md 这类文件，则是另一个渠道，可以随网站一起发布有用的说明。无障碍控件、结构化操作和可发现的说明合在一起，能减少智能体单凭视觉界面去推断的工作量。

08

给智能体安全的委托访问权限

找到了正确的页面，下一个问题还没解决：智能体怎么代表用户登录？Klein 列出了两种常见做法，各有各的运维成本。

- 共享密码： 智能体可以用用户的账号登录，但要安全地保管这些凭据很难。 - 服务账号： 智能体拿到的是受限权限，但遇到新工作，可能要反复申请授权。

某些操作可能还需要人工批准。在企业场景里做计算机操作，就算模型和框架能完成任务，能否访问所需系统也会成为部署的关卡。

Klein 提到了 WorkOS 的 auth.md，智能体可以通过它了解如何注册。这个协议描述的是代表用户注册，以及与用户绑定、限定权限范围的凭据，不一定要给智能体创建一个独立身份。所以产品设计上的问题很具体：注册和登录由智能体来完成时，应该是什么样子？把这条路径明确下来，软件才有机会安全地支持智能体使用，而不是逼它硬走一套为人设计、临时拼凑的流程。

09

区分经授权的智能体与恶意爬虫

登录认证解决不了更大的信任问题。网站原本为拦截恶意爬虫而设防，现在也会碰上替人办正事的智能体。Klein 认为，CAPTCHA 拦智能体的效果，没有大家以为的那么好。更值得问的是：网站能不能识别出智能体，并把它和授权它干活的人对应起来？

Klein 在这里提到了 WebAuthn。不过 Browserbase 公开发布的智能体身份相关工作用的是 Web Bot Auth。这是两种不同的技术，名字不能混用。他更大的设想是为智能体设立类似 Verisign 的角色：一个可信的签发方，为智能体或其厂商作担保。他把这层信任和安全认证一起，看作尚待解决的机会，而不是行业里已经建成的体系。

10

选择支持持续改进的基础设施

把这些问题全部解决，可能就是一份全职的工程工作。如果现成平台能把这些活接过去，同时保留应用需要的选择空间，它就有价值。Klein 的要求很务实：

- 规模： 支持从一个智能体扩展到几千个。 - 模型选择： 模型能力提升时，应用可以更换提供商。 - 身份与访问： 平台出面和反爬虫服务商协调可信智能体的访问，免得每个应用各自去谈。

平台的价值在于这些能力的组合，而不只是一个远程托管的浏览器。

再往上一层是可观测性。录屏记录智能体看到了什么，日志展示它走了哪些步骤，网络活动揭示浏览器和网站交换了什么。这些记录可以喂给智能体的下一轮迭代，让失败和多余的操作都能拿出来复盘。Klein 介绍了当年早些时候发布的 Autobrowse，作为通过多轮循环改进智能体的例子。目标是用执行证据改进之后的行为。每次运行都有进步只是一种期望，收集了 trace 并不会自动带来这个结果。

11

工作早就藏在网页表单后面了

浏览器智能体和网页数据抽取，服务的不只是大型 AI 原生公司。Klein 说，能从浏览器自动化中受益的小企业五花八门，让他很意外。他举的例子都在科技行业之外：新加坡的一家物流公司、南非的一家银行、墨西哥的一家木材厂。

这些企业可能靠 PHP 网站、表单，再加上每天点按钮的员工来运转。它们的工作流已经有界面，只是这些界面默认由人来操作。Klein 认为，计算机操作的经济价值，就在于能把 AI 带进这些现成的软件里。机会在于用可靠的浏览器基础设施打底，解决公司真实的工作流。

12

把浏览器打包成一个专门的智能体

Klein 介绍了前一天刚发布的 Browserbase Agents，它把智能体和框架打包在一起。他说，Browserbase 平台每月跑数百万个浏览器会话，这些经验帮它处理好各种边界情况。这个数字是平台的会话量，不代表成功完成了这么多自主任务。

演示中，提示词是进入执行系统的入口。平台提供框架、运行时、沙箱、代码执行、抓取和搜索工具，以及模型。Klein 介绍，智能体在运行过程中会检查并记住自己的步骤，以便复用学到的东西。

设想中的集成方式是：一个浏览器专家作为子智能体，嵌在更大的智能体系统里。这样应用开发者可以专注于客户的问题，不必自己拼装每一项浏览器能力。演示结束时的画面上，护理执照查询页面旁边是运行时间线、操作列表，以及文本和结构化结果：任务产出和执行证据同屏可见。

接下来，优化环节会回看这次执行，琢磨怎样把任务做得更好。前面提到的反馈回路就此闭合：观察一次运行，复盘行为，再用学到的东西改进下一次尝试。完成的结果是这次运行的证据；回顾式优化则是另一个独立的过程，用来改进以后的运行。

13

重新拾起计算机操作的理由

最后，Klein 坦言了现场听众稀少背后的挫败感：浏览器智能体折腾了一年，还是很难投入生产，一些开发者已经暂时抽身。他用自己的一线经历来回应这种情绪：确实有客户把这些系统用起来了。他预测，随着模型、技术和工具不断进步，一年后这个会场会座无虚席。他留给开发者的任务，是把这些进步变成更好的系统，让它稳定完成人们本来就在网上做的那些工作。

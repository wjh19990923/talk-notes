视野太小了

幻灯片原文
Baraiya expands the familiar chatbot flow to agents that run in the background, react to events, coordinate over time, or work together. Most run without a human watching.

[1:06](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=66s) [A chatbot flow contrasted with six kinds of agents, including background workers and multi-agent systems.](https://assets.ai.engineer/sites/aiecode2025/sha256/f1debae63d8aa4185b89e31d20abe5313ad824701942ada187e36ed602807976.webp)

THE FRAME
The picture is too small

What everyone pictures when you say “agent”
User → Bot → Tool → Response
Useful — but a special case.

Background workers
run with no UI at all

Scheduled agents
wake on a cron, act, sleep

Event-driven
react to a message, then halt

Monitors & reviewers
watch, judge, escalate

Long-running coordinators
drive work across hours or days

Multi-agent systems
many agents, one outcome

Most real agents are nothing like the chatbot. No human is watching most of them run.

智能体是组件，不是应用

幻灯片原文
Like microservices, agents work as a system: an orchestration layer coordinates them through routing, state, policy and failure handling.

[2:55](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=175s) [Five agents connect to an orchestration layer responsible for routing, state, policy and failure handling.](https://assets.ai.engineer/sites/aiecode2025/sha256/dcec6524ffd1f33dc2edca651e73983d0acb6faa97b9d347a85b085d5c0aeec2.webp)

COMPONENT, NOT APPLICATION

An agent is a component, not an application

You never ship one microservice.

You ship a system of them — and you don’t hand-wire their coordination per app. You stand up an orchestration layer.

Agents are arriving at the same place, for the same reason.

routing · state · policy · failure handling

框架运行的不只是一个智能体循环

幻灯片原文
The harness combines agent reasoning and planning with deterministic workflows for payments, approvals and other operations. Humans also participate in the loop.

[4:59](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=299s) [Non-deterministic agent tasks such as planning are compared with deterministic work such as payments and approvals.](https://assets.ai.engineer/sites/aiecode2025/sha256/f33af8ead02b9c3775a39589affc3114918bec0c9952c6f2c569c3f0e37cb12a.webp)

TWO KINDS OF WORK

A harness runs more than an agent loop

Non-deterministic
the agent’s job
• Plan
• Reason
• Classify
• Summarize
• Choose the next step
• Replan

Deterministic
must never be improvised
• Payments
• Provisioning
• Approvals
• Compliance checks
• Rollbacks
• SLA timers

Plus humans in the loop. The agent has no business owning the deterministic half.

循环横跨智能体与框架

幻灯片原文
The agent plans toward a goal, while the harness executes and records what happened. The agent then replans from that feedback, returning to the planning step.

[7:13](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=433s) [A loop connects the goal, agent planning, harness execution and recording, and agent replanning.](https://assets.ai.engineer/sites/aiecode2025/sha256/092f1a3e60fd03e7866454fe1218f4e0b526e0c521eb85e3a3db52b281010a12.webp)

THE LOOP

The loop spans the agent and the harness

Goal → Agent plans → Harness executes → Harness records → Agent replans

observe → replan

the plan adapts to what actually happened

The useful loop isn’t inside the agent. The edge that matters is observe → replan — where the world becomes the feedback signal.

重新规划改变的是未来，而不是过去

幻灯片原文
The harness preserves completed work, side effects, approvals and failures. Replanning adds steps from the current state, such as checking downstream health and verifying recovery.

[7:24](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=444s) [Two panels contrast preserved work and side effects with new steps added from the current state.](https://assets.ai.engineer/sites/aiecode2025/sha256/7c51d6e2149f9c2a913d6c159a5b1829424e0fe071b1b9760dd73139971ac0e9.webp)

THE INVARIANT

Replanning changes the future, not the past

Preserved
locked the moment it happened

Completed work
Recorded side effects
Attached approvals
Visible failures

Added from current state
the new plan, from here forward

Check downstream health
Trip a circuit breaker
Notify the owning team
Verify recovery

New steps are added from the current state — the past is never rewritten.

智能体负责规划，框架负责执行

幻灯片原文
When an agent proposes restarting an unhealthy cluster, the harness decides how to execute the restart and whether it needs approval. It also governs retries and compensation.

[8:06](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=486s) [Two panels list planning decisions made by the agent and execution decisions made by the harness.](https://assets.ai.engineer/sites/aiecode2025/sha256/d2e4d88e556b426bd937a7cb95969963210d1ecec2d9b965518cf41494242f71.webp)

SEPARATION OF RESPONSIBILITIES

The agent plans. The harness executes.

The agent decides
• What to do
• Why
• How the plan adapts as the world changes

The harness decides
• What’s allowed
• What already happened
• What can be retried
• What needs approval
• What must be idempotent
• What gets compensated
• What runs next

The agent proposes. The harness operationalizes.

显而易见的反对意见

幻灯片原文
The slide proposes a bounded vocabulary for runtime plans, addressing how the harness can handle idempotency, compensation, and recovery for code it has never seen.

[10:03](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=603s) [The slide asks how a harness can guarantee properties of runtime plans and answers that the available operations are bounded.](https://assets.ai.engineer/sites/aiecode2025/sha256/bad2fc418aaf026bd9f99b42fbf28f649f9a562efa0af3a1ce22b5c928e727e5.webp)

THE OBVIOUS OBJECTION

If the agent writes the plan at runtime, how can the harness guarantee anything about a program it has never seen?

Idempotency. Compensation. Recovery — on code that didn’t exist at deploy time.

The answer is a constraint. Planning is free — the alphabet is bounded.

延迟绑定的 saga

幻灯片原文
The agent assembles a runtime plan from registered operations. The diagram traces trip_circuit_breaker back to its registered compensation, reset_breaker.

[10:19](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=619s) [A deployment-time operation registry with compensations is connected to a runtime workflow composed from those operations.](https://assets.ai.engineer/sites/aiecode2025/sha256/cf9cfad18edef60b236bcf1caf7460919c5301411663522b76d42eee36b69627.webp)

THE MECHANISM

Late-bound sagas

REGISTRY · DEPLOY TIME (early binding)

rollback_deploy
↩ compensate: redeploy

trip_circuit_breaker
↩ compensate: reset_breaker

notify_team
↩ compensate: —

provision_capacity
↩ compensate: deprovision

+ 9 more operations

PLAN · RUN TIME (late binding)

investigate_errors
check_downstream
trip_circuit_breaker
notify_team
↩ reset_breaker
verify_recovery

traces to its registered op

Bound late, over operations whose guarantees were bound early. The agent owns the plan — within a vocabulary the harness defines.

这不就是一个带分支的工作流吗？

幻灯片原文
A branching workflow chooses among paths drawn at deploy time. A late-bound saga composes a sequence at runtime from a registered vocabulary, preserving compensation for its operations.

[11:19](https://www.youtube.com/watch?v=NaOkR3VSfR4&t=679s) [A predefined branching tree is contrasted with a runtime sequence composed from a registered vocabulary.](https://assets.ai.engineer/sites/aiecode2025/sha256/6d08647f745c6c204b931bf0a3cb719ef16b214f97bd215cdd9d1124c0f782f7.webp)

THE SHARP QUESTION
“Isn’t this just a branching workflow?”

CLOSED WORLD
branching workflow
start
branch → path, path
branch → path, path
every path drawn at deploy time — the planner only picks

OPEN WORLD
late-bound composition
vocabulary: a, b, c, d, e → composed at run time
c → a → e
the shape wasn’t known until the agent emitted it

A branching workflow enumerates the futures. A late-bound saga composes one — and compensation still holds, because the vocabulary was registered early.

大脑与双手：如何在生产环境中安全运行 AI 智能体

Viren Baraiya 讲解了 LLM 如何在运行时拼装计划，同时由一个确定性的框架控制执行、审批和副作用。一个双循环的 SRE 示例说明了为什么下一份计划必须考虑已经发生的事情。

01

生产级智能体需要的不只是一个工具调用循环

The hello-world agent makes a tool call, uses some context or memory, and plans its next move. That example leaves out much of the work involved in running an agent in production. Viren Baraiya opens with the larger picture: agents may work without a chat session, wake up on a schedule, respond to infrastructure events or coordinate other agents over a long period.

These operating modes create different responsibilities for the software around the model:

- Scheduled work. An agent might run every hour to check a calendar and identify something new that needs attention. Its trigger comes from time rather than a user message. - Event-driven work. A production agent might listen for alerts and incoming logs, then investigate what is happening in the system. - Long-running coordination. One agent might monitor another, decide whether it needs a nudge and suggest a different action. - Multi-agent work. Specialized agents communicate with one another instead of assigning every responsibility to one agent. Baraiya connects that narrower scope to reducing the risk of hallucinations.

Once these responsibilities accumulate, the agent starts to look like an application. The question becomes how to coordinate reasoning, tools, events and ongoing work so that the whole system achieves a goal.

02

框架就是应用

Microservices offer a useful precedent. A production application typically combines several services, each with a focused responsibility, and connects them through choreography or orchestration. An SRE harness has a similar shape: it can coordinate agents that examine logs, interact with a Kubernetes cluster, query metrics or inspect customer-service dashboards. The business goal belongs to the assembled system.

“Your harness is the application” is Baraiya’s framing for this assembly. The harness controls agent execution while connecting databases, internal systems, humans and tools exposed through APIs or MCP. Its job extends beyond repeatedly calling a model: it must make all those participants work together.

That application combines two kinds of behavior. LLM reasoning supplies a non-deterministic way to interpret a situation and decide what should happen. Operations such as payments or restarting a production cluster need a defined execution procedure. For a cluster restart, the harness should know the sequence of steps and run that procedure consistently whenever the operation is selected.

The useful design decision is where to put flexibility. Interpreting an unhealthy deployment can benefit from model reasoning. The procedure that carries out a restart should live in code whose behavior the application controls. Deterministic execution makes the procedure predictable; it does not make the model’s diagnosis correct.

03

等待和恢复也是工作的一部分

A harness can run for a few seconds, days or months. Much of that lifetime may involve waiting: an order-management process waits for a third-party shipment, an approval step waits for a human, and an event-driven agent waits for its next trigger. The application must continue to make sense across those pauses.

Long lifetimes make infrastructure failures unavoidable design inputs. The machine or sandbox running the harness can disappear; networks can fail or partition. Durability means the harness can recover its work when those failures occur. Baraiya calls it the “cost of admission”: a production harness needs recovery before its more interesting agent behavior can be useful.

Recovery also needs a meaningful record of the world. The harness tracks completed work, successes, failures and side effects. A cluster restart or a sent email must become part of that record. The next model call then reasons from the current state and the goal, including what execution has already changed.

This gives state two jobs. It lets the application retain knowledge of completed work, and it gives the planner the context needed to choose the next action. The second job matters even when nothing crashes: a remediation loop that forgets its previous actions can propose work that has already been done.

04

大脑提议，双手执行流程

The central split is between deciding what should happen next and executing that decision. The LLM writes a plan. The harness performs the work. If the planner concludes that an unhealthy cluster should restart, the harness supplies the restart procedure, including the steps required to carry it out.

Three execution responsibilities make that separation consequential:

- A defined procedure. The harness controls how a restart happens, so the operation follows the same prescribed process each time. - Required approval. A production restart might require sending someone a Slack message and waiting for approval. If that gate is required, the workflow must enforce it. The model should not be able to omit it because it decides approval is unnecessary. - Side-effect handling. Ideally, an operation is idempotent: repeating it does not introduce an additional effect. Where it is not, the harness records what happened so the application can handle those effects separately.

Recording a non-idempotent action does not itself make repeating the action safe. It preserves information needed to deal with the consequences. That is why execution policy and execution history both belong in the harness: the policy controls required steps, while the history tells later work what has already occurred.

“Harness is the hands. The brain is the LLM.” The metaphor names a concrete division of labor. The model can adapt the plan to a changing situation, while application code retains responsibility for the procedures and gates attached to the chosen actions.

05

在运行时拼装已知的任务

Baraiya calls this arrangement a “late bound saga.” The comparison starts with workflows whose steps developers define ahead of time. An agentic harness still has a finite set of tools and deterministic tasks, but the agent proposes how to put those tasks together at runtime.

The late binding happens in the composition. A tool’s prescribed behavior remains defined; its place in the plan can change with the situation. The resulting workflow gives the application visibility into what is happening and a way to control execution. The planner can propose one step or several steps before the harness runs them and obtains fresh information.

This addresses the difficulty of authoring every possible branch in advance. A hand-written workflow would need to anticipate many combinations of tools and circumstances. Runtime planning chooses a relevant combination from the available tasks. The tradeoff is that the application now needs a way to turn the proposed composition into executable work while preserving the procedures that make those tasks predictable.

06

两个 SRE 循环，一次回滚

The SRE example makes the composition visible through a completed remediation run with two iterations. Baraiya explicitly describes it as a pre-planned, canned demo. It illustrates the planning and execution structure rather than establishing how reliably the system diagnoses unfamiliar production incidents.

The first LLM call proposes a sequence: gather evidence, analyze logs, roll back a deployment if the evidence calls for it, and verify recovery. A specialized tool named Plan and Compile receives that plan and compiles it into a runnable workflow for Conductor, the workflow execution engine used in the example.

The first workflow analyzes logs, queries metrics, performs a rollback and verifies recovery. Those results then become the starting point for another planning loop. The second iteration recognizes that the earlier work has happened, checks downstream systems and calls for recovery verification if needed before completing the task.

What changes between the two plans, and where does that change enter the system? The diagram follows the rollback through execution and back into planning. The second plan omits another rollback because the first iteration already performed it; the loop continues with checks appropriate to the updated state.

The observable change is in the work selected for the second iteration. The system goes from diagnosing and rolling back to checking what remains downstream. Its causal sequence is straightforward: execute the first plan, observe the output, reason from the resulting state, then compile and execute the next plan. Completion history changes the plan rather than merely documenting it afterward.

Each iteration can plan several steps at once, execute them and verify the result before the next iteration. The same arrangement can respond to events, run on a schedule or continue over a longer period. The two-loop demonstration is a short instance of that operating model.

The ending identifies Conductor as an open-source workflow orchestration platform that supports agentic loops and systems, with an Enterprise Edition provided by Orkes. Baraiya also describes support for running LangChain and OpenAI agents. In this architecture, the workflow engine supplies the execution layer around agent reasoning: the agent framework can produce plans, while the harness manages the work those plans select.

Omit another rollback. - Execute and complete — Run the next iteration's work and finish the task. - First LLM plan → Plan and Compile (Proposed sequence) - Plan and Compile → Execute first workflow (Runnable workflow) - Execute first workflow → Updated state (Completed work and observed results) - Updated state → Second LLM plan (Plan from what has already happened) - Second LLM plan → Execute and complete (Run the remaining checks)

要点总结

  • 把框架看作围绕一个目标协调智能体、系统、人和工具的应用。
  • 让 LLM 选择接下来该发生什么；把执行流程、必需的审批和副作用处理放在框架里。
  • 一个延迟绑定的 saga 在运行时组装一组有限的、预先定义好的任务，让计划可以变化，而任务行为仍然受控。
  • 执行历史必须为下一份计划提供输入。在 SRE 演示中，第二轮迭代跳过了第一轮已经执行过的回滚，转而进行下游检查。

Connecting to Neo4j AuraDB

For this workshop, you will need a Neo4j AuraDB instance.

Primary Method: Neo4j AuraDB ProTrial
1. Go to console.neo4j.io.
2. Sign up or log in to your Neo4j Aura account.
3. Create a new Free Tier or ProTrial instance. A ProTrial instance is recommended if available, as it provides more resources. Ensure GDS (Graph Data Science) is enabled or can be enabled on your instance.
4. Once your instance is running, note down your connection URI, username, and password. You will need these for your .env file.

Alternative: Using the Provided Database Dump (Optional)

If you prefer to run a local Neo4j instance or need to restore the database to a specific state, a dump file is available. This can also be loaded into an AuraDB instance if needed.

1. Download the .dump file from the link above.
2. Stop your local Neo4j instance.
3. Run the load command (replace your-database-name and path to your dump file):
   neo4j-admin load --from=/path/to/your/downloaded.dump --database=your-database-name --force
4. Start your Neo4j instance.

图智能：用图分析增强推理与检索

图可以把检索到的文本块与它们的来源、对话和相邻节点连接起来，为工程师提供诊断冗余、丰富上下文多样性和追踪应用放大了什么的实用方法。

熟悉检索增强生成、文本嵌入和基础 Python 会有帮助；图的概念和 Cypher 模式会在使用时介绍。

01

你的检索器缺少什么信息？

Are you retrieving the right data, chunking it appropriately and preserving the relationships that make an answer useful? Those questions open the workshop’s technical discussion. The audience adds two immediate difficulties—establishing relationships and managing volume—then raises temporal relationships. Graph analytics offers ways to investigate these problems together. As Cossette explained before these audience questions, the accompanying Jupyter notebooks support that investigation, but the underlying responsibility extends beyond the pipeline: AI engineers must care about both the pipes and the quality of the water flowing through them.

A vector store is a useful starting point. Alison Cossette compares its chunks to index cards handed to someone on their first day at work: each card contains a relevant fact, but the newcomer still needs to know how those facts fit together. Semantic similarity can find a promising card without explaining what it connects to. A knowledge graph brings structured and unstructured information together to supply those connections. Some relationships come from explicit material, such as a table extracted from a document; others require an LLM to identify entities and infer relationships from prose. The workshop starts with an already-built database combining several sources.

Consider two people and a car. One person owns the car; another drives it. The people also know each other. These are nodes and relationships, with properties supplying the details: a person’s attributes, the car’s brand and model, or the date when someone began driving it. The analogy to relational tables, foreign keys and columns is approximate, but useful for orientation. Properties can belong to relationships as well as nodes.

The car also has a description and a description embedding. To answer a question about people who own cars described a certain way, retrieval first uses vector similarity to find matching car nodes. It then traverses ownership relationships to reach the people. Semantic search supplies the entry point; graph traversal supplies connected context. Because the relationships already exist, the retriever does not need a new table or view for each such question.

02

把应用活动放进图里

Start with a document connected to its chunks, then connect the application to those chunks. Prompts, assistant responses and retrieved context record what the system actually does. This application graph, also described as a memory graph, lets you investigate which documents get used and which may influence outcomes. Chunks can also connect to products, people and other domain entities drawn from structured sources or extracted from documents. The workshop concentrates on the smaller slice containing prompts, responses and their context documents.

These are neighborhoods within one system, not separate databases. In the explanatory diagram, yellow nodes identify application data and blue nodes identify information from unstructured sources. The colors distinguish origins and roles; the relationships make it possible to query across them. Starting with one connected system does not require designing an entire organization’s ontology before doing useful work. Begin small and keep the application’s latency requirements in view.

Schema complexity and data volume are different dimensions of graph size. Many labels and relationship types can make a graph difficult to work with even before its node count becomes large. The practical sequence is:

1. Start with generic labels and relationship types. 2. Load a representative subset of the data. 3. Evaluate whether it supports the questions you need to answer. 4. Specialize the schema where the results or volume justify finer distinctions. 5. Bring in the remaining data after refining that model.

Here, starting small means iterating on the ontology as well as limiting initial ingestion.

The same evaluation discipline applies to the audience’s comparison with RAPTOR, which organizes content into a hierarchy with summaries at higher levels. A tree of summaries, summaries over graph communities and an entity-and-relationship representation expose different routes through the material. The questions users ask should determine which representation earns its place. The workshop offers no performance winner between RAPTOR and knowledge graphs.

03

探索更多关系，再加载工作坊环境

The workshop distributes its repository and an OpenAI key through the conference workspace. For readers following the recorded setup, the clarified Slack channel is workshop-neo4j, not workshop-neo4j2025; Graph Analytics Workshop is the repository name discussed during that exchange.

Why add relationships to an existing corpus? A chunk can answer questions about its own contents. A pair of chunks can also support questions about their similarities, differences or connections. Communities add another level: questions about connected groups. The co-presenter illustrates this with a deliberately simple counting model—one question per chunk, then a Cartesian product of pairs, then possible subsets:

``math \begin{aligned} \text{individual chunks} &: N \\ \text{ordered pairs, including self-pairs} &: N^2 \\ \text{all possible subsets} &: 2^N \end{aligned} ``

His ten-chunk illustration has 100 ordered pairs. These are candidate combinations, not measured answerability gains: a useful question does not automatically exist for every pair, and the connected communities do not realize every possible subset. The useful intuition is that relationships expose questions unavailable when chunks are considered only in isolation.

The recorded exercise uses a hosted AuraDB Professional trial. The repository refresh adds the slides and setup links, and participants are told to ignore its Docker instructions for this session. Aura Free is presented as a smaller option for later experimentation, while the Professional trial supplies the workshop environment. Cossette initially estimates a longer trial, then corrects herself to the seven days displayed in the interface; those are historical setup details, not a current offer. No cloud-provider preference is required. Participants pass through onboarding, retain the default four-gigabyte instance and can enable graph analytics and vector optimization before starting it.

The console brings together instances, graph analytics and a query IDE. Its first Cypher pattern is deliberately small:

``cypher MATCH (n) RETURN n LIMIT 10; ``

Parentheses identify a node pattern; n names the matched node for the return clause. The notebooks contain the workshop queries. That is part of the recorded setup exchange, rather than a prerequisite for understanding the graph.

04

跟随 Agent Neo 的对话进入它们的上下文

The dataset comes from Agent Neo, an application built around graph data science knowledge. Query results can appear as a graph, a table or raw values. Its application model records a session, conversations, user messages and assistant responses, with responses connected to the context chunks retrieved through cosine similarity. The grounding material comes from documentation, developer blogs and support content. Early ingestion used LangChain’s recursive splitter with a stated chunk size of 512.

The example conversations begin with requests to build graphs and questions about what GDS means. A follow-up asks how to learn more about GDS. Repeated opening questions draw on shared context documents; later turns move toward other information areas. That movement becomes visible because the conversation and its evidence are represented together. You can distinguish chunks used in both answers from chunks exclusive to one response, then investigate which parts of the corpus people repeatedly reach.

In the conversation visualization, pink nodes represent chunks, orange nodes represent user prompts and tan nodes represent application responses. This turns an otherwise isolated retrieval result into a usage trail: a prompt leads to an answer, and that answer identifies the material supplied as context.

05

存储可搜索的表示并限定检索范围

Agent Neo stores both chunk text and its embedding as node properties, with a vector index over the embeddings. That removes the need for a separate vector database in this design. In response to a storage question, the co-presenter distinguishes ordinary kilobyte-scale chunks from megabyte-scale payloads, which warrant more concern. A subsequent question about growing legal-document collections receives only informal scale guidance: the discussion mentions tens of millions as seeming manageable and hundreds of millions as requiring further scaling work, without specifying the counted unit, workload, hardware or latency target. It does not establish a deployment capacity.

A vector query searches the contents of its chosen index. Multiple indexes can therefore separate use cases or available datasets; the workshop gives a governance example involving broadly available and restricted information. Large media use a different storage split: keep images in external storage such as S3, and put their URLs and embeddings on graph nodes. Relationships can then preserve the association between a document’s text and its images without placing the image binaries in the database.

Retrieval also depends on the graph pattern followed after finding an entry point. Cossette’s GPS analogy is to start somewhere and then follow a specified route. She points to the Python GraphRAG package and the GraphRAG pattern catalog while discussing pre-filtering, post-filtering and index scoping. Source structure can help: SEC filings contain predictable sections, so chunks can retain their place in a document hierarchy. Multiple labels provide another useful distinction. A node labeled both Message and Assistant can participate in a query over all messages or a narrower query over assistant responses. This is a retrieval-design explanation; the audience’s question about the vector index’s internal multilayer architecture is not resolved in detail.

Versioned documentation supplies a concrete scoping example. Separate indexes for versions such as 1.9 and 2.6 let a chatbot route a customer’s question to documentation matching the installed version. Cossette presents this as her practical preference. The subsequent clarification distinguishes that choice from filtering retrieved nodes: a vector index produces candidates, then property predicates can remove candidates that do not meet the application’s requirements.

The filtering exchange describes the workshop-era API. The current vector-index documentation records additional indexed filtering properties and SEARCH WHERE introduced in Neo4j 2026.01. When reproducing the exercise, keep its index-scoping and post-filtering explanation distinct from those later capabilities.

07

连接、聚类、整理

The second notebook introduces a three-stage corpus-management process:

1. Connect: run nearest-neighbor similarity over document embeddings. The workshop uses K = 25 to build connections among similar chunks. 2. Cluster: run community detection over those connections, grouping related chunks for collective inspection. 3. Curate: use the groups to find problems and improve the grounding dataset.

The similarity graph also retains links to source URLs. Overlap is unsurprising when many chunks come from related source material, but turning that overlap into explicit relationships makes it available for analysis.

Small friendship diagrams make communities look obvious: one tightly connected clique here, another there. Real graphs look more like tangled spaghetti. In the workshop illustrations, node size represents PageRank and edges carry weights. Community detection supplies a computational way to identify groups within that tangle instead of relying on a visually tidy layout.

Louvain uses modularity optimization. Its intuition is that a community has more internal connectivity than an expected-edge baseline would suggest. Starting with individual node assignments, it tests whether moving a node into a neighboring community improves modularity. It then aggregates the resulting groups and repeats at the coarser level. In the illustrated aggregation, pink and yellow have three edges between them, while pink has 14 internal connections, yellow two, green four and blue 14. The aggregate graph exposes both the strength within groups and the links between them.

The alternatives differ in how they form communities:

| Algorithm | Mechanism to keep in mind | | --- | --- | | Louvain | Improve modularity through local moves and aggregation | | Leiden | Refine communities to address connectivity problems in Louvain’s output | | Label propagation | Update labels from neighboring labels over repeated iterations |

Cossette introduces Leiden through connected-versus-unconnected graphs; more precisely, its connectivity guarantee concerns the resulting communities, rather than simply whether the input graph is disconnected. Label propagation is presented as a fast option for large graphs, while other methods may justify more computation when the grouping needs greater nuance. Modularity is the objective used by Louvain here, not a definition of every clustering algorithm.

08

只投影算法需要的数据

Before running KNN, the notebook creates a graph projection: the working graph on which an algorithm operates. An attendee encounters a missing gds.graph.project procedure, but the recorded exchange does not establish its cause. The explanation focuses on the intended projection, named docs, containing document nodes and their embedding property. Excluding unrelated nodes and unnecessary properties keeps the working dataset focused.

At this point in the model, documents connect to assistant responses but do not yet have the document-to-document similarity relationships that KNN will build. The notebook therefore includes an empty relationship setup. Projection output supplies the graph name and node count so the caller can inspect what was created. That separation matters: preparing the working graph is a distinct operation from calculating similarity and storing its results.

The subsequent Explore walkthrough uses similarity relationships that have already been computed and colors nodes by community. Network problems interrupt the live display, but the intended view is clear: clusters of similar documents, with some documents connecting otherwise distinct regions. The visualization is a way to inspect the algorithm’s output, not the mechanism that determines community membership.

09

一个紧密的聚类可能暴露出一个糟糕的语料库

Some documents act as bridges between regions, motivating the later discussion of betweenness centrality. A two-dimensional embedding view makes the groups easier to survey, though Cossette initially likens it to a bowl of Froot Loops. Zooming in reveals a dense single-community cluster beside a more dispersed area. Which is better? A tight cluster may be desirable in customer segmentation, but in a document corpus it can mean that many chunks say almost the same thing.

The grounding-quality discussion asks whether the material is relevant, adds useful information, is reliable, covers needed knowledge and uses retrieval capacity efficiently. Dispersed retrieval can prompt an investigation into coverage gaps; excessive density can prompt an investigation into redundancy. Once each chunk has a community assignment, summary statistics let you inspect these patterns by group instead of reviewing the entire corpus one document at a time.

One malformed community has a reported median average word length of 512 characters and a median word count of one, in a dataset whose affected chunks are 512 characters long. Built-in GDS algorithms follow a consistent invocation pattern: call the algorithm, identify the projection and choose an output mode. The betweenness-centrality discussion points toward the third notebook. The modes make experimentation and persistence separate decisions:

| Mode | Destination | | --- | --- | | stream | Return calculated values for inspection | | mutate | Store results in the in-memory projection | | write | Persist results back to the database |

For example, with a prepared projection named docs, inspecting betweenness scores takes this form:

``cypher CALL gds.betweenness.stream('docs') YIELD nodeId, score RETURN nodeId, score ORDER BY score DESC; ``

A useful projection for this calculation needs relationships whose paths have the intended meaning. Streaming lets you examine the result before deciding to retain it.

The third notebook introduces a relationship derived from application behavior: co-occurrence. Find the context documents attached to one assistant message, pair distinct documents and MERGE a co-occurs-with relationship. MERGE creates the relationship if it does not already exist. Weighting it by repeated co-retrieval records how often the documents appear together. This can reveal complementary concepts after duplicate content has been reduced; the chunks need not be near-identical to be useful together.

A small Cypher example expresses the pairing operation using an illustrative HAS_CONTEXT relationship from an assistant message to its documents:

``cypher MATCH (m:Assistant)-[:HAS_CONTEXT]->(d:Document) WITH m, collect(DISTINCT d) AS docs UNWIND docs AS leftDoc UNWIND docs AS rightDoc WITH m, leftDoc, rightDoc WHERE elementId(leftDoc) < elementId(rightDoc) WITH leftDoc, rightDoc, count(DISTINCT m) AS sharedMessages MERGE (leftDoc)-[r:CO_OCCURS_WITH]->(rightDoc) SET r.weight = sharedMessages; ``

The ordering condition excludes self-pairs and gives each pair one orientation; that orientation is an implementation convention, not a temporal claim. Recomputing the weight from distinct messages avoids incrementing it merely because the query is rerun. A different derived relationship could represent sequence: these chunks appeared first, then those chunks appeared in a later turn. Such follow-on edges motivate questions about likely next topics or the direction a conversation will take.

For a response with ten retrieved context chunks, all ten participate in that response’s co-occurrence group. They are ten pieces of context, not ten generated answers. Co-occurrence records being supplied together; follow-on relationships record appearing in succession. Keeping those meanings distinct makes their downstream analysis interpretable.

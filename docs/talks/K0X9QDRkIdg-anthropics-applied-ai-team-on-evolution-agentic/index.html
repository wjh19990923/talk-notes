Anthropic 应用 AI 团队谈智能体界面的演进

随着智能体从回答问题走向对结果负责，它们的基础设施必须把推理、执行和持久的历史分开，同时不把对模型能力的假设固化下来。

熟悉模型 API、工具调用、容器和上下文窗口会有帮助；这里的 MCP 是把智能体连接到外部工具和数据的协议。

01

当智能体要对一个结果负责时，什么会改变？

What must change in the software around a model when the request grows from answering a question to completing a task—or owning an entire outcome? Gagan Bhat and Isabella Kai He approach that question from Anthropic’s Applied AI team, which sits between product, research, and go-to-market. Their work combines building internal agents, evaluating Claude, and helping enterprise customers turn model capabilities into working products.

The progression begins with model capability. Gagan traces it through the transformer architecture, scaling-law research associated with Anthropic’s founders, and successive model releases. As capabilities expand, developers delegate more complex work: first questions, then tasks, then outcomes. The interface for building agents has to absorb the operational demands that come with that progression. A request-and-response API is only the beginning.

02

从 token 到一个嵌入式框架

The first surface in this progression is the Messages API: information and tokens go in; generated text comes out. Gagan introduces it through the Claude 3 era, although the Messages API beta announcement preceded that generation and included Claude 2.1 examples. As tasks became longer, applications needed the model to fetch information, use tools, and manage its accumulating context.

Developers supplied those capabilities by building an agentic loop beneath their product. The loop called Claude, executed requested tools, returned their results, and managed context before calling the model again. Maintaining that loop was substantial work, but it was only one layer: a production application also needed session management, observability, credentials, hosting, and sandboxing.

The Claude Agent SDK packaged the Claude Code harness into an embeddable component. It supplied the loop, filesystem access, tools, a sandboxing system, and primitives for sessions and observability. The product could embed that harness instead of rebuilding it. Developers still had to decide how to host it, supply credentials, and scale it for customers.

That remaining work becomes clearer as a set of concrete design questions:

- Hosting and scaling: Where does the process run, how long does it live, and what happens under load? - Session management: Where do history and progress persist, and how do concurrent agents operate? - Filesystem and isolation: Where can Claude create or edit files, and where does generated code execute securely? - Credentials: How does the agent reach sensitive systems without seeing their security tokens? - Observability: How can a developer reconstruct what happened across the orchestration?

These concerns consume time that could otherwise go into the application’s task and context.

03

托管基础设施的边界

Claude Managed Agents moves that infrastructure boundary. The developer owns the product, task, context, and domain knowledge. Anthropic operates the machinery beneath it: a brain containing Claude, the agentic loop, and evolving harness components; and hands, a sandbox created when needed for filesystem access and code execution. Credentials, sessions, observability, and hosting are also managed services.

| Surface | What it supplies | What the developer builds around it | | --- | --- | --- | | Messages API | Model input and output | Agent loop and production infrastructure | | Claude Agent SDK | Embedded agent harness | Hosting, scaling, and remaining infrastructure | | Claude Managed Agents | Harness and managed infrastructure | Product, task, context, and domain expertise |

Each surface absorbs another layer of work between the application and the model. The architectural challenge is to keep that absorbed layer adaptable as the model changes.

04

当一次有用的框架修复变成了负担

Harnesses encode assumptions about what the model cannot do on its own. Context resets and compaction policies are examples: they compensate for limitations in the model’s ability to sustain useful work. Isabella’s design principle is to revisit those assumptions frequently, because a new model can make a previously necessary intervention obsolete.

With Sonnet 4.5, the team observed what it called context anxiety. As the agent approached its context-window limit, it sometimes wrapped up or terminated work early, despite still having space available. Context resets in the harness helped it continue. When the team tested Opus 4.5, Isabella reports that this behavior disappeared. The resets remained, however, adding latency and sometimes incorrectly discarding cached context. The same intervention had changed from a remedy into overhead.

This is a maintenance problem as much as a model-selection problem. A rigid harness built around an older model can take weeks or months to migrate while model release cycles keep shortening. Managed Agents therefore uses a small set of independent, replaceable components: the architecture can remain stable while individual mechanisms change to capture new capabilities.

05

把推理、执行和持久状态分开

Products such as Claude Code and Claude Tag, alongside enterprise agents, point toward increasingly asynchronous work. These agents accumulate context, take actions in secure environments, run for hours or days, and divide complex problems into parallel workflows. Supporting that work requires more than a loop that succeeds while its original process stays alive.

The initial Managed Agents design put the agent loop and tool execution in the same container. This made tool calls and result access straightforward, but it also coupled their lifecycles. Model reasoning could not begin until the container finished setting up. A failure in one part could bring down the whole agent. Separating the brain from the hands removed that shared dependency and allowed the brain to request a sandbox only when needed.

The separation creates two recovery paths:

- Sandbox failure: The surviving brain can create a replacement sandbox, retry, and continue. - Brain failure: A replacement brain can read the durable session log, reconstruct its context, and resume the work.

The session log matters because neither the reasoning process nor the execution container has to be the sole owner of the agent’s history.

The public resource model follows that architecture:

| Primitive | Definition | | --- | --- | | Agent | Model, prompts, tools, and skills for a use case | | Environment | Execution configuration used to provision containers | | Session | Durable cloud record of interactions for an agent and environment |

Multiple sessions can use the same environment definition while receiving isolated container instances. Combining an agent and environment creates a session whose persisted interactions support observability, long-running work, and recovery.

The production requirement is different from serving one person on a laptop. At large user counts, long-running work must survive tool failures without losing its identity or progress. Managed Agents exposes four session states:

| State | Meaning | | --- | --- | | idle | Waiting for user input | | running | Executing work | | rescheduling | Retrying after an error | | terminated | Unrecoverable failure |

Recoverable failures can lead back into execution through the existing session; an unrecoverable session terminates.

06

上下文窗口是历史的一个视图

Context engineering becomes difficult when a harness treats the session and the model’s current context window as the same thing. Discarding material to make room can then mean losing the ability to recover it during that run. A durable session log changes the relationship: the harness can load selected slices into the current window, edit or discard them, and later reread the original material from persisted history. Reducing the active context need not erase the session’s memory of what happened.

Managing the loop, memory, and observability does not eliminate application-specific design. Developers still choose how to manage context and express domain expertise. Claude Code uses tools such as Bash and Grep much as a developer uses a terminal. A legal or go-to-market agent needs different tools and instructions. System prompts, skills, and tool design remain the means of turning a general harness into an agent suited to particular users.

This demonstration follows one session. An application can create sessions dynamically for different users, while the Claude console provides a place to inspect them. 09

凭据隔离与更快的启动

The first deployment lesson begins with a common customer concern: an agent that can inspect files might read an environment file containing security tokens. Separating the loop from execution provides part of the boundary. Managed Agents adds vaults that store credentials and decrypt them only when needed at tool-execution runtime. In the design Gagan describes, the model can use an authenticated tool without seeing its security token.

The second lesson concerns latency. With the coupled design, container provisioning sat directly on the path to model reasoning and the first response token. With the decoupled design, reasoning can start immediately while container setup runs in parallel. If a task never needs sandbox execution, setup can be skipped entirely.

Isabella reports roughly 60% lower P50 time to first token and over 90% lower P95 time to first token after decoupling container startup from reasoning. Anthropic’s engineering account identifies this as latency from session acceptance to the first response token, rather than total task duration. The workload, absolute timings, sample size, and model configuration are not specified. The mechanism is clear even without those details: container provisioning no longer has to finish before inference begins.

10

复用 trace，控制工具在哪里执行

The third field lesson joins two questions: how can developers see what an agent is doing, and how can they improve its future behavior? The session log records user messages, model responses, tool executions, and results in order. Displaying it in a UI provides observability. Retaining it also gives the agent a history of past executions that can complement user-specific memory. Gagan introduces dreaming as a way to use that history to update memory between runs.

The fourth lesson is control over tool execution. Security-conscious teams wanted execution inside their own virtual private cloud. Because the hands are independent of the brain, self-hosted sandboxes can place tool execution in customer-controlled infrastructure while the agent loop remains on Anthropic infrastructure. Customers control the sandbox control plane and the policies under which tools run.

MCP tunnels address the related problem of reaching private MCP servers without publishing them on the internet. A gateway inside the private network establishes an outbound connection, allowing the managed agent to use those servers without requiring a public MCP endpoint or inbound firewall access. Execution placement and private tool connectivity become separate choices from where orchestration runs.

11

在运行之间打磨记忆

These foundations also support capabilities beyond the basic agent loop. Gagan names scheduled deployments, self-hosted sandboxes, multi-agent orchestration, dreaming, outcomes, and memory as areas of ongoing development and experimentation. Dreaming and outcomes receive the detailed treatment: one changes what future sessions remember; the other changes how a current task is judged complete. Dreaming was introduced as a research preview, while outcomes, multi-agent orchestration, and memory were described as public beta.

Dreaming takes two inputs: transcripts from the agent’s sessions and its current memory state. A periodic batch process reviews them, extracts insights, organizes information, and edits memory for subsequent sessions. The feedback loop operates through remembered information; it does not describe retraining model weights. Gagan frames this as a path toward agents that improve through repeated work, with the next day’s sessions benefiting from what earlier sessions revealed.

The direction extends beyond remembering details about one user. Organizational memory could hold a team’s runbooks and shared operational knowledge, with dreaming maintaining and enriching those structures over time. The unified-memory diagram connects ongoing sessions, shared team files, and periodic review. This is an emerging architecture for accumulated organizational knowledge, rather than a fully specified memory system.

12

让“完成”成为一个显式的判断

Outcomes starts with a developer-defined rubric: what counts as successful completion, and which failure cases should prevent acceptance? A separate grader agent evaluates the working agent against that rubric. After the agent attempts the task, the grader checks the result. If it falls short, the agent receives another opportunity to work toward the criteria.

Isabella describes this as continuing until the success criteria are reached. The current Outcomes documentation makes the stopping condition more precise: success or exhaustion of the iteration budget. That distinction matters when designing a workflow around grading. A rubric provides a mechanism for evaluating and revising work; it does not guarantee that every task can be completed. The intended benefit is more reliable completion of increasingly complex tasks as model capabilities improve.

The closing architectural concern is the gap between what a model can do and what a product allows it to do. A static harness can preserve old limitations long after the model has moved past them. Managed Agents addresses that gap with independent execution and reasoning, durable sessions, and replaceable harness mechanisms, then builds memory refinement and explicit outcome evaluation on that foundation. The goal is a production system whose surrounding software can advance alongside the intelligence it exposes.

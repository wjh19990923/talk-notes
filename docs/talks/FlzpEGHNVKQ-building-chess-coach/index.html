打造一个能讲清每步棋的国际象棋教练

Take Take Take 结合国际象棋引擎、战术检测器和语言模型来讲解对局，再利用棋手的反馈驱动一个由智能体辅助的改进循环。

了解基本的国际象棋走法和语言模型提示会有帮助；引擎、检测器和智能体机制会在出现时讲解。

01

那步马为什么是妙着？

白方的马从 f3 跳到 e5，吃掉一个兵，局面由此导向将杀。复盘系统把这步棋标为“妙着”。但真正有用的指导在棋盘下方：这步棋为什么成立？它威胁什么？是哪些战术或局面特征让它与众不同？

这是 Anant Dole 和 Asbjørn Steinskog 开场展示的例子。两人在 Take Take Take 做了一个已上线的国际象棋教练，这家公司由 Magnus Carlsen 创办。公司的 iOS 和 Android 应用可以让人和朋友对弈，还能发布自己的对局。下完一盘棋，复盘会把自动生成的着法标注和生成的解说结合起来：检测器找出相关的棋局特征，语言模型再把这些发现写成对这步棋的讲解。

教练的指导不止于单步棋。各阶段的准确率、当前等级分、对某个开局的熟悉程度，这些洞察构成另一层分析。教练据此找出值得学习的地方，把这盘棋里发生的事，和玩家接下来能改进什么联系起来。

02

从搜索着法到挑选变化

国际象棋很早就暴露出两件事的区别：一是探索各种可能，二是决定哪些可能值得关注。历史起点是 Claude Shannon 的 Programming a Computer for Playing Chess，这篇论文 1949 年收稿，1950 年 3 月发表。Steinskog 介绍 Shannon 时称他为“元祖 Claude”，并借他提出的 A 型和 B 型策略来界定问题。

| 策略 | 计算资源怎么花 | | --- | --- | | A 型 | 广泛搜索各种可能着法，但只搜到有限深度 | | B 型 | 挑出有希望的着法和变化，做进一步分析 |

按 Steinskog 的说法，早期计算能力有限，选择性搜索看起来必不可少：机器不可能把整棵博弈树都搜一遍。

计算机越来越快，搜索能力也越来越强，象棋引擎远远突破了早期的局限。里程碑是 1997 年 Deep Blue 在对抗赛中战胜 Kasparov：对手是当时的卫冕世界冠军，比赛采用标准赛制用时。Deep Blue 第一次赢下单盘对局，则是在 1996 年。

Steinskog 接着讲到 AlphaGo：围棋的搜索空间大得多，神经网络帮它挑选变化。随后是 AlphaZero，把这套方法推广到围棋、国际象棋和将棋。A 型/B 型的划分是一个好用的历史视角，而不是对现代引擎的严格分类。语言模型登场时，能力特点截然不同：它们能走出像模像样的开局，可下着下着就搞不清局面，开始产生幻觉。

03

下棋水平与讲解能力是两回事

一段视频把这个局限讲得很具体：Magnus Carlsen 在公司的奥斯陆办公室解说一盘棋。Grok 在一个毒兵变例里过早把后走到 b6，随后输得很惨。Carlsen 在解说中认为，问题不只出在开局选择上，更在于它整体上就下不稳棋。

这盘棋来自 Kaggle Game Arena，这个平台通过对弈来评测模型。它后来加入了狼人杀，带来另一种挑战：模型得应对社交推理和欺骗。国际象棋则让持续计算上的失误格外显眼。

推理模型能在一定程度上推演着法，但 Steinskog 发现，它们算着算着还是会出错。这并不说明 Transformer 架构天生不适合下棋。他提到 DeepMind 的一个 Transformer：用数百万个局面及对应的 Stockfish 评估来训练，学的是评估局面，而不是普通的下一个 token 预测。据他介绍，这个模型达到了特级大师的棋力。

关键区别在训练目标。一个学会评估局面的模型，不会因此就能用自然语言讲解局面；一个能聊国际象棋的语言模型，也不会因此就成为可靠的象棋引擎。教练既需要强大的分析，也需要清楚的讲解，两者之间还要划出明确的界线。

04

把棋局事实交给语言模型

复盘流水线的第一步，是用 Stockfish 分析整盘棋，为每个局面给出最佳着法作参照。但光有最佳着法，还撑不起一堂课：玩家还得理解威胁、计划、战术机会，以及自己实际那步棋之外还有哪些选择。

下一步是提取这些特征。战术检测器寻找捉双、牵制和串击；局面检测器捕捉结构性主题，包括叠兵这类潜在弱点。这样，生成模型拿到的是现成的象棋概念，只管讲解，不必自己从棋盘上去发现。

多伦多大学研究出的 Maia 提供了另一种信号：人类大概会怎么走。给定一个等级分，比如线上 1500 分，它会预测当前局面下各个着法的概率分布。

| 来源 | 回答什么问题 | | --- | --- | | Stockfish | 按引擎分析，哪步棋最好？ | | 战术与局面检测器 | 哪些威胁、模式和结构特征值得关注？ | | Maia | 这个等级分的玩家可能会走哪步？ |

把这些信号结合起来，团队就能把“着法好不好”和“对人来说难不难”分开看。一步棋可能是 Stockfish 眼中的最佳着法，Maia 却预测这个水平的玩家很少会走。教练就可以把它当作这位玩家不容易找到的一步来讲。

所有这些信息都作为上下文交给语言模型。团队刻意把它的任务限定得很窄：把给定的信息翻译成英文。团队不希望它自己编造战术解释，也不希望它额外去算变化。幻觉仍然会出现，但这种架构让每条讲解应该出自哪里一目了然：先分析，后生成语言。

05

一步坏棋仍可能包含威胁

在 Steinskog 下的一盘棋里，对手把兵挺到 f5。Stockfish 判定这是一步坏棋。这个结论用来给对局打分很有用，可玩家马上会冒出一个实际问题：对手到底想干什么？

检测器识别出一个困后的威胁，其中包括象走到 g5。它们也找到了应对办法：吃掉中心兵，就能守住后逃跑要用的格子。这样生成的讲解既能承认威胁存在，又能说明它为什么不成立。

用一段精简的 JSON 表示这些输入的事实，分工就一目了然：

``json { "playedMove": "f5", "engineVerdict": "bad move", "threat": { "goal": "trap the queen", "continuation": "bishop to g5" }, "response": { "action": "capture the central pawn", "effect": "defend an escape square for the queen" } } ``

这里的字段名示意了一份上下文契约。真正重要的是其中的因果关系：吃兵保住了后的逃跑路线。正是这层关系，把引擎贴的“坏棋”标签变成了指导。

06

从一个踩到一次经过审核的修改

改进循环从玩家给解说点踩开始。反馈会发到 Slack，同时通过 Claude Code channel 送进一个正在运行的 Claude Code 会话。按这里的介绍，channel 是一种处于研究预览阶段的机制：一个 MCP 服务器把外部事件注入正在进行的会话。这个机制负责把反馈送到编程智能体手里；智能体拿到后该做什么，由团队自定义的分诊 skill 决定。

排查遵循一套可重复的流程：

1. 查看反馈。 解说分诊 skill 引导智能体检查局面和生成的讲解。 2. 修改相关成因。 智能体可以调整提示词、修改检测器，或新建检测器。 3. 重新生成解说。 借助脚本，它可以带着拟议的改动重新生成解说，并检查结果。 4. 请求指导。 问题会通过 Slack 发回来，Steinskog 即使不在电脑前，也能帮忙做象棋上的判断。 5. 提交人工审查。 结果看起来没问题时，他让智能体提一个 pull request，在 GitHub 上审查后合并。

智能体自主完成的是排查和提出候选改动。按这套流程，改动合并之前仍然要经过人的指导和批准。

现场演示从一条故意不靠谱的反馈开始：演讲者在手机上打开应用，没先确认解说有没有错，就直接点了差评。Slack 收到了棋盘局面和生成的文字。同一事件也送到了 Claude Code，它调用分诊 skill，开始排查。

智能体开着高 effort 运行，两位演讲者就趁它干活时先讲别的。到这一步，能看到的只是反馈顺利交接进了排查流程，问题还没有修好。

07

逐步复盘需要短暂的等待

赛后复盘和后台排查对延迟的要求不一样。玩家想一步步回看着法，弄清发生了什么。如果屏幕上一直挂着“教练思考中”，交互就被打断了，哪怕最后的答案很好。

团队的目标是 3 秒内生成教练反馈。Dole 介绍，在他们的应用里，Gemini 3 Flash 通常约 1 秒返回首个 token，端到端平均延迟约 3 秒。所以 Gemini 3 Flash 已经接近他们想要的交互速度。这些都是应用内的实测数据，请求规模、路由和推理设置都没有说明。

其他推理模型也能给出有用的分析，但完成时间难以预测，放在即时复盘里就不太合适。计划中的“和教练聊天”功能则是另一回事：用户主动提问时，本来就能接受比回看对局更长的等待。界面的节奏，决定了在哪些地方多花时间推理是划算的。

08

用棋局场景检验讲解

Dole 和 Steinskog 把自己的棋力当作最后一道质量关：看一个局面，推演自己会怎么下，再拿这份理解去对照生成的回答。自动化评测让这类检查更容易重复。

团队用 16 个场景覆盖战术模式、大漏着和幻觉边界，场景都取自真实对局。比如一个马捉双的用例，检查的是模型拿到上下文引擎的信息后，能不能识别并提到这个战术。LLM 评审协助评估回答。这样评的是讲解有没有用上给定的象棋事实，而不只是读起来顺不顺。

有了 OpenRouter，新模型一发布就能方便地换上来试，包括各版 Gemini、GPT-5 和 Claude 系列模型。团队先比较输出质量，再凭自己的象棋功底判断结果是不是真的好。

Dole 给出了团队场景测试集上的结果：

| 模型 | 场景测试结果 | 延迟情况 | | --- | --- | --- | | Gemini Flash | 通过率约 75% | 复盘场景的基线 | | Claude（开更多思考） | 通过率略低于 60% | 延迟长得多 | | GPT-5 Mini | 准确率较低 | 没有给出明确对比 |

据介绍，GPT-5 Mini 准确率较低，但演讲里对它延迟的比较没说清楚。具体模型版本、Claude 的思考配置、评审设置和多次运行的细节都没有给出，所以这张表反映的是这个团队自己的评测，不是通用的模型排名。剩下那些没通过的用例，正是模型更新后还要继续测的理由。

09

难点在于塑造上下文

把数据流水线和语言生成拆开，团队不用让生成模型包揽一切，也能提升对棋的理解。再用智能体把反馈循环闭合起来，不管问题出在提示词还是检测器，排查和迭代都更容易。

上下文本身需要持续打磨。Dole 讲到，他们一开始用的是一个很大的 JSON 文件，然后一步步删减，边删边看输出质量怎么变。把分析流水线能产出的东西全塞进去，并不会自然得到清晰的上下文模型；它是在一次次判断“什么对讲解有帮助”的过程中慢慢成形的。

在这个过程中，自动化评测能提供反馈，但领域专家仍然不可或缺。在这个团队里，做系统的人本身就是棋力很强的棋手。换到别的领域，有资格评判讲解好坏的人，可能得找合作伙伴，而不是搭系统的工程师自己。

10

这份报告并不需要修复

回到智能体之前，两位演讲者邀请观众下午 3:45 左右到三楼入口下棋，可以扫码报名，也可以直接过来。他们介绍了一场车轮战：一位演讲者同时对阵四位对手、下四盘棋，并多给一些时间在棋盘之间走动。赢家能拿到木质棋盘；如果没人赢，下得最好的两位也能拿到棋具。他们开玩笑说，要是所有人都赢了，就只好再去买棋盘了。

回到现场会话，智能体还在思考，但已经发了一条进展，说正在排查这个局面。接着它问：“具体是解说的哪里让你觉得不对？”

演讲者承认其实没什么问题，并表示会关掉这次排查。演示里没有出现完成的修复，也没有 pull request。有价值的恰恰是这次追问本身：一个踩引发了排查，但并不能证明真有缺陷。这个循环给智能体留出了空间，让它在改动系统之前先质疑反馈本身。

延伸阅读

  • Programming a Computer for Playing Chess — Shannon's March 1950 paper on evaluating positions and selecting moves in computer chess.
  • AlphaZero: Chess, shogi, and Go — DeepMind explains AlphaZero's self-play training and evaluation across three board games.
  • Amortized Planning with Large-Scale Transformers — Research on learning chess action values from Stockfish annotations, including a search-free policy evaluated against humans on Lichess.
  • Maia-2 implementation — Code and inference examples for predicting human chess moves conditioned on player skill.
  • Stockfish — The open-source UCI chess engine used for position analysis and move evaluation.
  • Claude Code Channels reference — Current documentation for delivering external events into Claude Code through MCP servers and supporting replies.
  • Game Arena adds Werewolf and poker — Google's announcement of social-deduction and imperfect-information games for evaluating AI models.

改造公共 MCP 服务器而不把它弄坏

一个基于浏览器的规格审查器展示了工具过滤、更好的描述、路径检查、证据采集和确定性的登录流程如何改变智能体的行为。

熟悉 Python 异步函数、调用工具的智能体和 MCP 客户端，有助于理解封装和执行流程。

01

为什么加工具反而会让智能体变差？

第三方工具本该让智能体更能干。可如果它反而让应用变得不可靠，该怎么办？Nimrod Hauser 开场放了一个看起来着了火的 MCP 服务器。这个“修理”的比喻贯穿全场：要接好一个集成，光把工具列表原样接进来远远不够。他在 Baz 开发 AI 代码审查，以及面向开发者和产品经理的其他智能体功能。他自我介绍说，2023 年起就是 Baz 的创始工程师，此前在后端和数据领域干了大约二十年，待过 Salesforce，也待过创业公司。这场演讲要回答一个实际问题：怎样把别人写的工具改造成适合自己应用的样子。

智能体工具（agentic tool）就是一个可调用函数加一段描述。函数负责执行操作；描述告诉智能体什么时候请求调用它，以及怎么调用。不管集成来自 MCP 服务器、某个库，还是直接拷过来的代码，这个区分都成立。演示用的例子是 Playwright MCP：一套浏览器集成代码，它的描述得照顾到形形色色的应用。

通用工具可能做出意料之外的操作，返回错误结果，或者执行起来绕远路。它们还可能带来安全问题。在多租户应用里，智能体未必知道哪些文件夹、数据库或 schema 属于哪个客户。如果给它一个能力很宽的集成，却不强制这些边界，一个客户的数据就可能流到另一个客户那里。应用特有的约束必须在工具调用中守住，哪怕工具作者对这个应用的架构一无所知。

02

从一张工单和设计稿到浏览器中的证据

Baz 的 Spec Reviewer 负责比对需求和实现。工作流第一步是从 Jira、Linear 这类系统读取工单，并查看 Figma 里的视觉设计稿。接着它启动 Playwright MCP，打开待审分支对应的应用，检查实现是否满足需求。最终输出一份结论，附截图作为证据。这些重复的验证工作原本要由产品经理来做，现在自动化了。这里“打开分支对应的应用”只是浏览器检查这一步；演示没有展示怎样为这个应用搭建环境。

这个 Python 玩具项目把工作流压缩到最小。它定义了截图输出目录，配置了一个 Playwright MCP 服务器，并初始化 MCP 客户端。基类暴露 get_tools 方法，后续每一版实现都会提供定制程度更高的工具集。main 加载完工具后先调用 login_to_baz，然后才创建 LLM 和智能体，传入系统消息和用户消息，启动审查。为什么把登录放在智能体之外，后面会讲。

系统消息给智能体设定了一个一丝不苟的 QA 角色，并规定了具体步骤：

1. 阅读并理解工单。 2. 在应用中导航，检查实现。 3. 给出通过或不通过的结论，附上具体观察。 4. 引用截图作为证据。

用户消息提供了工单截图和配套的设计稿。用工单截图只是这个玩具项目的捷径，真实产品并不是这样读取工单的。任务是在 Baz 的 Agents 标签页里找到 Spec Reviewer 的配置抽屉，检查它和给定的设计稿是否相符。

03

基线把导航失败误判为需求未满足

v0 版通过 LangChain 的 MCP 适配器 加载服务器的工具，直接用 load_mcp_tools，不做任何改动。在基线断点处，演示共暴露了 21 个工具，覆盖关闭页面、调整页面大小、处理对话框、上传文件、填写表单、按键等浏览器操作。它们的描述也同样宽泛：browser_resize 写的是“Resize the browser window”（调整浏览器窗口大小），browser_close 写的是“Close the page”（关闭页面）。Playwright 不可能知道这个审查器具体要完成什么工作流。

浏览器启动，确定性的登录流程跑完，智能体从 Baz 的 Changes 首页接手。它要找到 Agents 标签页，结果这次运行却以“不通过”告终：结论称需求没有实现，理由是智能体打不开 Baz.co/spec-reviewer——这个地址看起来是它自己编出来的。它的观察说的是一次失败的导航，根本没涉及要找的抽屉。结果里还引用了一张 404 截图，可打开截图文件夹一看，证据并没有正确保存。基线版既没找到功能，也没给结论留下可用的证据。

修复分五步：精选可用工具、包装工具描述、加确定性护栏、组合出任务专用的工具、在智能体循环之外直接调用选定的函数。前几项改动调整的是智能体看到的上下文；后几项让应用代码对执行有更多控制。每一步都复用现有的第三方集成代码。哪些交给描述去引导、哪些用代码强制执行，界线怎么划，要看哪种分法能让应用表现出需要的行为。

04

v1：去掉审查者不需要的选项

v1 版修改了 get_tools：加一个按工具名排除的列表，再用 Python 列表推导式过滤加载进来的工具。针对这个审查器，Hauser 排除了调整浏览器大小、拖拽元素、在页面里自主运行代码等操作。这些能力在别处也许有用，放在这个工作流里只是多余的选项。过滤机制很简单，完全可以明写出来：

```python from langchain_mcp_adapters.tools import load_mcp_tools

async def get_curated_tools(session, excluded_names: set[str]): tools = await load_mcp_tools(session) return [tool for tool in tools if tool.name not in excluded_names] ```

排除哪些工具，由应用根据任务的实际需要来定。

到了精选后的断点处，调试器显示还剩 16 个工具。智能体面前的工具清单变短了，要挑选的操作也少了。但这不代表每次改进都得缩短上下文：下一版会刻意给留下的工具加上更多指导。

05

v2：教智能体先检查再行动

v2 版引入了 ToolWrapper.wrap_playwright_tools。除了工具名，它还维护一个字典，存放增强后的描述。这些描述沉淀了做这个审查器导航任务的经验，包括哪个工具应该先于哪个工具调用。

关键在于区分无障碍快照（accessibility snapshot）和视觉截图：

| 工具输出 | 提供什么 | 在审查中的作用 | | --- | --- | --- | | 无障碍快照 | 描述页面控件的文本，包括按钮和菜单项 | 交互前先理解页面 | | 视觉截图 | 渲染后页面的图像 | 检查外观，保留证据 |

别看名字，browser_snapshot 生成的其实是无障碍表示。Hauser 发现，它能让智能体很好地理解当前页面。新的描述告诉智能体：悬停或点击之前先拍快照；想弄清页面上有哪些控件时，优先用快照，而不是截图。

包装器遍历原始工具，过滤掉不需要的，为剩下的每个工具查出增强描述，再生成一个替代工具。替代工具的可调用函数仍然调用原函数。执行逻辑不变，变的是给模型看的说明。 在断点处能明显看到描述变长了，比如 browser_click 上附加了“先检查页面”的指令。这一版还多过滤掉了一些工具，工具更少、描述更丰富，两者同时起作用。

06

v3：在执行前拒绝无效的截图目标

描述能引导决策，但敏感操作需要强制约束。即使指令就写在上下文里，智能体也可能无视。Hauser 举了大海捞针现象和 Lost in the Middle 这篇论文，说明不能只靠上下文；不过它们并不是前面导航失败的原因。在这个演示里，要强制执行的规则很简单：视觉截图必须保存在配置好的输出目录下。

v3 版保留了过滤和增强描述，又在 create_playwright_tool_wrapper 里加了 PathValidation。转发截图请求之前，包装器先取出请求里的目标路径，检查它是否位于截图根目录之下。演示当时检查的是 path 或 filename；而按照当前 Playwright MCP 的文档，browser_take_screenshot 用的参数是 filename。值得借鉴的是“调用前先检查”这个机制，而不是假定这两个参数名今天的 schema 里都有。

举个具体例子：假设允许的目录是 /work/screenshots，请求的文件名是 ../outside.png。解析后的路径是 /work/outside.png，落在允许的目录之外。包装器应该在调用截图函数之前就拒绝它：

```python from pathlib import Path

def validate_destination(root: Path, filename: str) -> Path: root = root.resolve() candidate = Path(filename) destination = ( candidate if candidate.is_absolute() else root / candidate ).resolve() if not destination.is_relative_to(root): raise PermissionError(f"Save screenshots under {root}") return destination

async def save_screenshot(original_tool, root: Path, filename: str): try: destination = validate_destination(root, filename) except PermissionError as error: return f"Access denied: {error}. Provide a valid filename." return await original_tool.ainvoke({"filename": str(destination)}) ```

无效请求永远到不了原始工具。内部的校验错误会转成一条给智能体看的回复，指明允许保存的位置，并要求它改正参数，整个审查不会因此中断。之后智能体换成 drawer.png 这样的文件名重试，就能通过校验；不过重试得由智能体自己发起，拒绝这一步本身不会触发重试。Hauser 预期这种反馈能帮智能体自行纠正。这只是一道限定保存位置的护栏，并不是完整的文件系统隔离或租户隔离边界。

被拒绝的路径永远到不了截图工具 包装器拦下写入操作，同时让智能体仍能提出改正后的文件名。 构造示例：路径 /work/screenshots、../outside.png、/work/outside.png 以及回复原文，都是和旁边 Python 示例共用的教学用值，并非录像里出现的值。 请求的截图参数——不变：filename = ../outside.png 操作：以 /work/screenshots 为基准解析请求的路径，检查是否在该目录范围内，并在调用前拒绝请求。 - 允许的目录 - 之前：请求待处理：/work/screenshots - 之后：校验拒绝：/work/screenshots - 请求的文件名 - 之前：请求待处理：../outside.png - 之后：校验拒绝：../outside.png - 解析后的路径 - 之前：请求待处理：无 - 之后：校验拒绝：/work/outside.png - 底层截图调用 - 之前：请求待处理：未调用，等待校验 - 之后：校验拒绝：未调用，路径在允许的目录之外 - 给智能体的回复 - 之前：请求待处理：无 - 之后：校验拒绝：Access denied: Save screenshots under /work/screenshots. Provide a valid filename. 包装器拦下写入操作，同时让智能体仍能提出改正后的文件名。

07

v4：给证据采集一个专门的工具

探索应用时拍的截图，和作为最终审查证据保存的截图，用的浏览器功能几乎一样，目的却不同。v4 版给证据截图单独做了一个工具。它有自己的描述，智能体可以在审查收尾时选中它，通用截图功能则留着做别的用途。有了专用包装器，还可以在调用底层截图之前，插入只针对取证的操作。

实现上保留了 ToolWrapper 和 PathValidation，先跑完原有的过滤和包装循环，再注入证据工具。在这个演示里，只有底层截图工具没被过滤掉，才会加入这个新工具。这条依赖规则是专门为这个应用明确定下的。

新描述和提示词里最后的取证步骤一一对应。它规定这个工具只用来取证，并要求智能体找出相关工单，把工单号写进保存图片的文件名。这样智能体既知道什么时候用，也知道怎么命名。同一个底层操作，就此支撑起两种不同的任务约定：

- 通用截图： 探索过程中，审查需要时拍一张图。 - 证据截图： 为最终结论留存依据，并按工单命名，方便和工单对应起来。

这个包装器还可以承载取证专属的其他确定性检查或准备工作。在演示的描述里，具体的区别就在于按工单命名。

08

直接调用必需的设置函数

第五种做法回到 login_to_baz，它从基线版起就一直在。工具的可调用函数，不经过智能体解读描述，照样能直接用。在 main.py 里，应用先拿到 MCP 工具，跑完登录，再创建并调用智能体。这样，必不可少的准备步骤始终处在确定性控制之下。

认证很适合这么处理：每次运行 Spec Reviewer 都要认证，而不同客户系统的登录方式和密钥各不相同。Hauser 说，把这件事交给智能体，效果不理想。所以工作流直接复用 MCP 函数，登录时做哪些操作、按什么顺序，都不交给智能体决定。

玩具实现从环境变量读取 JWT token，挑出需要的浏览器工具，把 token 注入浏览器的 local storage，然后点击 Login。Hauser 特意说明，这只是图省事的做法，和真实产品的认证方式不同。浏览器认证完成后，控制权交给智能体去执行审查。这段准备流程应用早就知道非跑不可，没必要耗费智能体的推理和上下文。

09

重新运行找到了抽屉并保存了证据

工具改造完成后，Hauser 去掉断点，用同样的工单和设计稿把任务重跑一遍。先执行 JWT 登录，浏览器进入 Changes 页面。接下来智能体要导航到 Agents，找到配置抽屉。Hauser 提到浏览器画面有延迟和卡顿，屏幕上看到的导航过程并不能完整反映每一步操作。这次运行结束时给出了“通过”：抽屉存在，而且包含要求的各个部分。

结果附带推理过程，还有一张文件名里带工单编号的截图。打开这张证据后，Hauser 指出给定的设计稿是深色模式，被检查的应用却是浅色模式。玩具审查器找到了抽屉和预期内容，但这不等于像素级吻合。Hauser 说，真实产品支持更细致的视觉校验，能检查内边距、外边距和样式。录像只展示了失败的基线和一次成功的改进版运行，既没有多次试验的可靠性测量，也没有像素级准确率基准。

最终的设计取舍，是在有用的上下文和必要的控制之间找平衡。去掉无关工具，智能体的选择变少；把留下的工具描述写得更详细，它选得更有依据。确定性检查在执行时强制约束，直接调用则把不需要智能体决策的工作拿掉。平衡点落在哪里取决于任务本身，不管集成来自 MCP、某个库还是别的地方。目标是把现成的函数打磨成应用真正需要的接口。

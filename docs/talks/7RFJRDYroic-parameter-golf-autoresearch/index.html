用 AutoResearch 打“参数高尔夫”

Weco AI 把语言模型研究变成对代码的一次可检查的搜索，再把同一套机制用在一个 Flappy Bird 控制器上。真正有价值的工作在于定义评估器、给实验划定边界，以及知道何时介入引导。

01

给智能体代码和一个可重放的测试

A coding agent usually waits for the next instruction. An AutoResearch system keeps proposing and testing changes on its own. In this workshop, Vayum Arora, Zhengyao Jiang, Dixing Xu and Dhruv Srikanth of Weco AI begin with a small specification: give a language model some code and a replayable evaluation script, let it try ideas, keep changes that improve the score and discard the rest. The score might measure accuracy, speed or cost.

Autonomy makes the initial setup matter more. A person steering each coding step can correct a misunderstanding quickly; an unattended search can spend its whole budget pursuing the wrong signal. Zhengyao's phrase is that the right evaluation lets the agent “boil the ocean for you.” The same persistence becomes waste when the evaluator rewards something other than the intended behavior.

The team's earlier system, AIDE, released in April 2024, applied this approach to machine-learning engineering: write code, run experiments, read results and improve. Vayum reports that AIDE achieved about four times the medal rate of the next best agent in OpenAI's MLE-bench evaluation. The workshop moves from that background to a more constrained example, Parameter Golf, before giving participants a smaller version they can watch run.

02

“参数高尔夫”让质量与规模和训练时间同场竞争

Parameter Golf asks participants to train the best language model they can while satisfying two hard constraints: the submitted artifacts, including model weights and training code, must fit within 16 megabytes, and training must finish within ten minutes. Within those limits, the objective is to minimize bits per byte, or BPB, on the FineWeb validation set. Lower BPB means better prediction of the validation text. A larger model or a longer training run cannot simply buy a better result if it breaks the rules.

OpenAI supplied a baseline, data and evaluation scripts, and participants submitted improvements through GitHub. Dex describes a 44-day competition with 1,016 researchers and 2,048 pull requests; 47 PRs from 31 contributors were merged as records. That open submission process also made other participants' implementations available as research inputs.

Aiden, Weco's multi-agent system built around the Claude and GPT model families, searched against that single metric. Its inputs included arXiv papers, GitHub implementations and its own experiment logs. It proposed and tested ideas, checked whether they complied with the competition rules, retained useful work and submitted a PR after results passed its quality gates. The legality checks matter: an improvement only counts if the resulting program still satisfies the challenge.

Dex reports seven merged leaderboard records and 435 downstream PRs that cited and built on Aiden's work. The team also reports using 4% of the community's GPU compute to produce 15% of the merged records, which it describes as 3.7 times the field's average cost effectiveness. Here, cost effectiveness means merged records per share of GPU compute; it does not establish an equivalent advantage in total research cost.

03

把实验缩小到能看得见多次尝试

Mini Parameter Golf, shortened to MiniPG, preserves the task's essential structure while reducing its scale. Each candidate still trains a real language model and receives a validation score, val_bpb, from a fixed evaluator. A tiny dataset replaces FineWeb, and training plus evaluation takes a few minutes. The point is to make several actual experiments visible during a workshop rather than spend the session waiting for one large run.

The setup divides the work between Weco, which runs the research search, and Modal, which supplies compute for training and evaluation. Participants are asked to clone the workshop repository and tell their coding agent to follow its README and start a run. Internet problems interrupt this plan, so the workshop turns first to the configuration that makes the search possible.

The first configuration choice is what the agent may edit. In MiniPG, that is solution.py, which defines the model configuration and training dynamics. This file defines the search space: the agent can change how the candidate model is built and trained, while a separate evaluation procedure measures the result.

04

评估器决定了你负担得起多少有用的搜索

Dhruv puts evaluation at the center of the system. Every generated solution needs a simple evaluation procedure that returns a scalar score. Three properties serve different purposes:

- Fast: shorter experiments allow more attempts within a time limit. - Cheap: lower experiment cost allows more attempts within a spending limit. - Low noise: a score change is easier to trust when repeated measurements do not vary widely on their own.

The first two increase search capacity. The third helps the agent and the person decide whether a candidate deserves further work.

A reliable number can still reward the wrong thing. Agents can find holes in a benchmark or evaluation protocol and exploit them. That makes reward hacking a design problem before the search begins: the evaluator must reward the intended behavior, and the allowed edits must not let the agent redefine success. MiniPG's stated goal is explicit—minimize validation BPB to improve prediction on unseen text.

The workshop chooses 20 search steps to give participants room to see different ideas succeed or fail. That is a practical starting budget, not a claimed optimum. There is no known step count that guarantees a breakthrough; cheaper and faster evaluations simply create room to test more possibilities under the same constraints.

Each evaluation also needs a timeout. Generated code can hang, loops can stall and hardware can fail. MiniPG sets a 210-second limit, budgeted as 60 seconds for training, 60 seconds for testing on unseen text and 90 seconds for GPU startup and other overhead. The overhead allowance keeps normal infrastructure delays from consuming the whole useful experiment window; the outer limit prevents a broken candidate from blocking the search indefinitely.

Initial guidance supplies knowledge the search would otherwise have to rediscover. Weco can read a Markdown file containing constraints, promising ideas and approaches that have already failed. For MiniPG, suggested directions include compression, quantization and weight sharing across model blocks. These are starting hypotheses, not demonstrated improvements in this walkthrough: the evaluator still decides whether a particular implementation helps.

05

让代码改动始终与分数挂钩

Weco organizes the search as an experiment tree. The root contains the baseline program and its measured score. Each later node contains a modified version of the code and the score obtained by evaluating it. Promising branches receive further refinement; unsuccessful directions are pruned. This preserves the lineage of an idea, so a useful change can become the starting point for another experiment.

What changed when the score moved? That is the question the tree and diff view are meant to answer together. Hovering over a node gives a summary; opening it exposes the code change. The tree locates the candidate within the search, while the diff shows the intervention associated with its result. Keeping both matters when a run lasts hours and accumulates hundreds of experiments.

Steering adds a way to act on that inspection. A person can submit an idea in plain English, open a new branch and assign budget to nodes so compute goes toward the desired direction. This lets domain knowledge enter during the run, after the experiment history has exposed a dead end or a promising opportunity. The human contribution can change what the system tries next without discarding the work already accumulated.

06

当一个外部想法遇上积累的工作，平台期就被打破了

The Parameter Golf example gives steering a concrete purpose. From April 15 through April 19, Aiden kept trying changes involving attention, compression and a richer stack, but its score essentially plateaued. A community participant then published a new tokenizer. Within eight hours of that change appearing, Weco reports that Aiden incorporated it, combined it with the pieces it had already developed and produced its biggest improvement in weeks.

What does the chart make easier to compare? Vayum identifies the agent's work as the pink line and the community tokenizer as the blue line. The useful relationship is the stalled search followed by improvement after the outside contribution was incorporated. The recording does not explain the tokenizer's implementation or isolate its contribution from the accompanying changes, so the example supports the value of combining research streams rather than a specific tokenizer recipe.

The chart links Aiden’s pink run to the blue community tokenizer and the later lower-BPB results, making the plateau and subsequent improvement comparable across dates.

07

打印出的分数驱动搜索，约束定义可接受的取舍

The guided setup resumes over a mobile hotspot. A coding agent receives the repository instructions and starts the default Weco run. The important distinction in the configuration is between the editable training program and the evaluation command. The command runs the evaluation and prints a score to the terminal; the agent parses that output. That parsed number becomes the signal for choosing which changes to pursue.

While the run starts, an audience question asks whether AutoResearch can apply to reinforcement learning. Zhengyao's answer is yes: the editable object can be an RL training script. The same outer search proposes changes to that script and evaluates their consequences. This places AutoResearch around the training procedure; it does not require every code proposal to be a reinforcement-learning update.

Multiple objectives require a decision about tradeoffs before a single-score search can compare candidates. The answer offers two approaches:

- Weighted combination: combine the objectives into one score with different weights. - Constraints plus an objective: require some metrics to satisfy limits, then optimize another.

Parameter Golf uses the second approach: artifact size and training time restrict eligible solutions, while validation BPB determines which eligible model is better. This preserves the hard limits instead of allowing a sufficiently good prediction score to compensate for breaking them.

08

检查一项改进，再要求一种不同类型的实验

The live dashboard reaches a concrete result: node zero is the baseline, with validation BPB of 3.93, and the agent has generated a candidate node. The presenters describe an apparent improvement and point to the option to open its code. What score belongs to the baseline, and what changed in the candidate? Those are the useful details to inspect together; the walkthrough does not state the candidate's new score or explain its diff.

The proposed steering instruction is more specific than “make it better”: explore quantization, rather than only changing the model configuration. That asks the search to try a different class of intervention instead of continuing with hyperparameter tuning. It is a useful example of how human guidance can change the kinds of hypotheses being tested.

The live steering attempt runs into a connection problem. The presenters say they do not think the session is connected and suggest that Claude Code did not follow the setup instruction. They then explain Weco's bridged session, which puts Claude Code alongside the experiment tree and metric so a person can direct the search through the coding agent. The intended quantization branch is therefore an instruction example here, not a demonstrated successful run.

09

Flappy Weco 检验控制器能否在不同的世界里存活

The final exercise removes the Modal dependency after participants encounter connectivity and payment problems. Flappy Weco turns Flappy Bird into a code-optimization task: a controller named should_flap decides every frame whether the bird should flap. The objective switches direction from MiniPG—maximize average game score, which depends on how far the bird flies.

The evaluator tests four worlds:

- Normal: the classic game. - Moving gap: the opening between pipes drifts up and down. - Wind: wind pushes the bird around. - Variable: conditions are mixed.

The final score averages performance across all four. A policy that excels in the normal world but fails in wind loses ground in that average. The aggregation rewards performance across conditions, although an average does not itself require a minimum score in every world.

The leaderboard uses a hidden validation set, so the local score is not expected to match the submitted score. This withholds the final test cases from the search and reduces the opportunity to tailor a controller to the public game alone. The editable program is also tightly restricted: participants may change only ai_controller.py, must preserve the should_flap signature and may not modify the game or evaluator. Imports, external libraries and file I/O are prohibited.

The competition also prohibits parallel compute and assigns everyone the same model through Weco. These rules address a different source of advantage from the hidden test: they constrain the research resources available to participants. Evaluation design has several jobs here—measure play across conditions, keep the final cases hidden, protect the game and evaluator from edits, and limit differences in search resources.

The suggested starting point is the working baseline controller. Improve it with small, focused edits: adjust safety margins, change the bottom buffer or adapt behavior to a particular world. Then inspect successful nodes and build on them, while trying other directions when useful. This gives each experiment a narrower question and keeps a functioning controller available as the search proceeds.

The original 30-minute exercise budget, estimated at about 50 steps, is extended; the closing deadline becomes midnight. A Nintendo Switch is offered as the prize. As scores begin arriving, an entry with only one node prompts the organizers to say they will inspect runs for cheating. A thin experiment history is not proof of misconduct, but it gives them a reason to look beyond the final number. The workshop ends with the same requirement it began with: a useful score needs an evaluation process—and an inspectable path to the result.

要点总结

  • 一个有用的 AutoResearch 配置需要规定可编辑的代码、可重放的评估、指标的优化方向、搜索预算、超时和初始指导。
  • 快速又便宜的评估增加了负担得起的实验次数；低噪声让分数比较更可信。但这些特性本身都无法防止奖励投机。
  • 一棵实验树把候选方案的谱系、分数和代码修改关联在一起，让人可以检查结果并引导新的分支。
  • 所报告的分词器突破，是在停滞五天后，一项外部贡献与智能体累积的工作结合的结果；持续的自主搜索只是整个过程的一部分。
  • Flappy Weco 结合了多个环境、隐藏的验证用例和受限的控制器修改，让分数更贴近预期的游戏行为。
  • Beating RL With Reflection: GEPA and Optimize Anything —— 讲解执行轨迹如何指导候选修改，以及保留备选方案如何帮助搜索走出停滞的改进路线。

The Sweet Side of the Bitter Lesson

Thariq Shihipar expected coding models to push developers toward a narrow set of tools. His fighting game shows what growing model flexibility lets him do. An agent can work on the engine while he reads the rules, edits them, and tries them in play.

01

Early bets on Bash, React, and AI art

When coding agents got good at Bash and Claude Code was built around the Bash tool, turning every tool into a command-line interface seemed like a plausible bet. Thariq Shihipar took it seriously. He had expected models to edit and generate video, use HTML to make sense of their work, and help people plan when they were unsure where to start. The Bash bet took a strength that agents showed at the time and turned it into a forecast about how everyone would work.

- Tool interfaces. Shihipar came to prefer the Model Context Protocol (MCP) to the CLI. He also points to code mode, skills, and progressive disclosure, where an agent gets more detailed instructions as a task calls for them. In hindsight, he suspects the early reliance on Bash reflected how the models were initially trained.

- Interface code. Models wrote React well enough that React Native and the web seemed like natural defaults for AI-assisted development. Shihipar found that models could produce roughly similar-looking interfaces in HTML, React, Swift, or Figma’s proprietary JSON format. Each leaves the developer with a different artifact to work on.

- Art production. Shihipar worried that diffusion models might make beautiful images while leaving artists little control over how they were made. Language models opened another route. They could write code or operate tools such as Blender, Photoshop, and Figma, giving artists a choice about where and how to shape the result.

These bets grew out of a fear Shihipar associated with the Bitter Lesson. As models grew more capable, people might have to adapt to methods that felt foreign to them. His experience pointed toward more ways to make something and more say in which one to use.

Shihipar checks off his predictions about models generating and editing video and using HTML to understand work. He gives the most space to a third idea about how models can help you figure out what you don’t know as you plan and learn.

02

Software factories and a software renaissance

What would it look like to take advances in AI seriously and still design work around people? Software engineering is an early test. Shihipar expects the ways engineers learn to work with AI to influence how other kinds of knowledge work adopt it.

“Software factories” capture the industrial side of the change. More reliable execution makes it easier to turn an idea into working software. Shihipar sees a renaissance happening alongside it. As implementation becomes less of a bottleneck, there is value in the extra work that makes a piece of software more useful, distinctive, or enjoyable.

03

The smooth interior of the jagged frontier

One way to picture model progress is by the size of the request. Ask for a function, then a feature, then a simple to-do app, then a Slack clone. Eventually the requests get extravagant. Build Mario Kart from scratch. Port it to the Wii while you’re at it. Ambitious demos and benchmarks probe the “jagged frontier,” the uneven edge of what a model can do.

What can you count on well inside that edge? Shihipar illustrates the “smooth interior” as a circle inside the jagged outline. The outline marks where capability gets uneven. The circle represents the range of tasks the model already does well. Writing React, producing Figma JSON, and using Bash can all sit inside it. As that range grows, several approaches can become practical for the same job.

A mockup makes the choice concrete. Ask for HTML if you want a page you can open in a browser, React if you want to keep working on components, or a Figma file if you want to keep editing in Figma. To explore motion, you could have the model operate After Effects or ask it to make a video. What you want to do with the mockup next helps determine which artifact to ask for.

Greater reliability could also change the developer’s role. Shihipar imagines a perfect model that can reliably turn agreed goals into code. In that hypothetical, developers spend less time checking implementation details, including looking for security flaws. The goals and spec still determine what counts as a correct implementation.

Shihipar’s rising zigzag traces roughly two years of increasingly ambitious AI coding prompts, from writing one function to building whole apps. At the top is the biggest ask: build Mario Kart from scratch.

04

Drawing the Earth one classification at a time

Give a model a latitude and longitude and ask whether the point is on land or water. Repeat for many coordinates and plot each answer at its location. A single response gives you one binary classification. The map lets you see how much geographic structure emerges across all those small decisions.

How much of the Earth can you recognize from those answers? Shihipar describes the earlier model’s map as blurry and the later model’s as much sharper. The comparison is qualitative. The shapes show how well the individual answers fit together geographically, with classification accuracy left unquantified. Watch the map comparison from 9:34.

For Shihipar, that breadth opens up a practical question about the work itself. If a model can work with many formats and tools, can it help build the one you’d actually like to use? His fighting game gave him a reason to try.

05

What happens when you ask for a rock throw

Shihipar is making a 2D isometric fighting game inspired by Avatar and Smash Brothers. He asked a coding agent to give a character a rock throw. The same character can summon a wall, so even that small request leaves a collision rule open. Does the rock go through the wall? The agent also has to make choices about speed, size, and charge. A playable move arrives with answers to design questions Shihipar has barely had time to ask.

Playtesting turned into a way of discovering the agent’s choices. Shihipar would send a prompt, switch to something else, then come back to a character whose behavior he struggled to explain. He lost focus and felt he made less progress. Designing a move involves trying rules before you know which ones feel right, then choosing which to keep or drop. To make those choices, he needed to know which rules were already in play.

The model makes choices for Shihipar’s game. When he tries the result, he’s unsure what the characters do. He switches tasks after sending a prompt, loses focus, and says he makes less progress this way.

06

The engine and the rules you want to read

The game now has two parts. The engine contains implementation details such as camera code that Shihipar delegates to the agent. A separate folder contains the characters and their abilities. That code is linted, and Claude gets rules for writing it in a style close to English. Shihipar can open a character’s file to see what it does and edit its rules in place.

What can you learn by opening the rock move? Comments explain what you can tune, and units such as meters give the numbers meaning. The code also exposes choices about where a rock comes from. Shihipar counts three ways to throw one and mentions the ground and a wall as possible sources. Where the character gets a rock is a separate design choice from how it collides with a wall. The abstractions let Shihipar read gameplay decisions at that level while the engine handles their implementation. He has effectively given the game its own scripting language.

07

Tuning the rock and sketching a wall rule in Cursor

How does the rock behave as you charge it? In the IDE, Shihipar gives 1.5 as an example size value for a bigger rock, then switches to the game. He charges the rock, it grows large, and he throws it. The demo shows how charging changes the rock before release. Whether that run used the example size value is unclear.

A rule change calls for a different kind of edit. Shihipar sketches a rule that queues a wall summon as an action and describes using Cursor’s Tab completion to fill it in. He calls this a form of spec-driven development. The script is where he expresses a change and where he can read it back later to understand the character. Follow the wall-rule example from 15:49.

The design is still an experiment. If a complicated move needs an operation the script lacks, Shihipar asks Claude to build that primitive so the script can use it. For changes the script can already express, he can work directly in the code. He can also review changes while the agent is working, so he stays involved in the decisions that determine how the move plays.

08

Designing the software and the work around it

The scripting layer let Shihipar start with what would help him make a better game. He sees room for a software renaissance if developers use that same freedom to choose languages, tools, and workflows around the quality of the software they want to make.

- Languages. Shihipar cites Rust for efficiency and names readability, modularity, and hot reloading as design goals worth exploring. A language can help people understand the code they’re changing and see the effect of an edit while the program runs.

- System primitives. New kinds of databases, servers, and operating-system interactions could give developers different building blocks. Shihipar has been experimenting at a personal scale, using coding agents to make software that changes how he works with his own operating system.

- Interaction and aesthetics. When it becomes easier to prototype a different way of using software, older human-computer interaction research is worth another look. The same opportunity extends to how software looks and feels.

For the fighting game, the experience Shihipar wants is a short path from reading a move’s rules to changing them and trying the move in play. The agent can help build that working experience as well as the game. The choice of what that experience should feel like belongs to the people doing the work.

要点总结

  • When several output formats work, choose for the next edit. A mockup can leave you editing React components, working in Figma, or refining motion.
  • Keep frequently revisited design decisions in code you can read and edit. Ask the agent to build an underlying primitive when the script needs a new operation.

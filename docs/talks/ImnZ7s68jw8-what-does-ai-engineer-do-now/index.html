AI 工程师现在都做些什么？

Aparna Dhinakaran 讲解了 Arize Signal 背后的工程：调查遥测数据的智能体、在一次性运行之间保留状态、提出修复方案，以及依赖经过人工判断校准的评估器。

AI 工程循环把构建、评测、发布、监控和改进连接在一起。

01

从编写功能到构建改进功能的系统

Using an LLM occasionally and operating thousands of agents are very different engineering practices. Aparna Dhinakaran of Arize AI opens with that gap, drawing on a funnel she attributes to Andrej Karpathy. It places roughly six billion people in a group who have barely touched an LLM, one to two billion among casual free-tier users, about 20 million among math and coding professionals using agents to compress weeks of work, and roughly 5,000 among users with frontier access running thousands of agents. Dhinakaran presents these figures as estimates. The question is how the rest of the field moves toward operating those systems.

The progression raises the level at which engineers work: from writing code in higher-level languages, through copying generated code and using local agents, to delegating work to cloud agents and eventually teams or “factories” of agents. Dhinakaran presents this as both a roadmap and a direction Arize has already begun pursuing internally. As more execution moves into agents, the engineer has to design how that execution gets checked and improved.

That changes several responsibilities together:

- Feature development: Build the loop that produces and improves a feature, extending the job beyond implementing its first version. - Review: Set up systems and agents to review work, with evaluations that can assess tasks whose outputs vary between runs. - Observability: Give agents access to telemetry so they can inspect behavior and find recurring patterns.

The familiar sequence—build, evaluate, ship, monitor, improve—remains. The new engineering work is making the system carry out those activities.

02

Signal 读取 trace，并让一次调查跨越多次运行

Arize’s concrete implementation is Signal, an always-on agent that reads traces, identifies patterns in telemetry and can propose a fix or open a pull request when it has repository access. Its starting task is deliberately small: read a configurable volume of traces collected over a configurable interval and look for problems. The trace data supplies the behavior to investigate; repository access gives the investigation a possible route to a code change.

What must persist when the next batch of traces arrives? Signal needs to remember previously identified issues, rather than treating every batch as unrelated evidence. Dhinakaran gives a useful progression: something initially looks suspicious without becoming a captured issue; later traces make the same concern look more critical. Keeping that history lets a later run reconsider an earlier observation as evidence accumulates. It also gives the agent context about problems already found.

This makes agents primary consumers of observability data. Telemetry becomes input to an ongoing investigation, with memory connecting one run to the next. Designing that consumption path is a different task from putting metrics on a dashboard for a person to inspect: the agent must receive enough recorded behavior and prior issue history to decide what deserves attention.

03

触发器启动一个全新的沙箱，并附上调查所需的上下文

An always-on service still needs a rule for when work begins. Signal supports several alternatives:

- Scheduled sweeps: Wake every three or six hours, for example, and pull the configured amount of recent trace data. - Events: Start an investigation from a Slack message or a user complaint. - Metrics: Start when a configured metric condition triggers the agent.

These are alternative ways to initiate a run. A scheduled sweep does not need to wait for a complaint, and an event need not wait for the next scheduled interval.

Once triggered, the run receives the material it needs to investigate: trace context, additional third-party telemetry such as APM logs and metrics, repository access, and any necessary keys. Signal starts a sandbox for that run and places the required context and access inside it. The sandbox is the working environment for the investigation.

How does information cross that environment’s boundary? In Dhinakaran’s architecture, a single proxy is the only route in or out of the sandbox. Everything happening inside is traced, and generated outputs—including identified issues—are saved to memory. This arrangement makes the investigator observable too: its actions produce records that can be inspected, while its findings survive beyond the process doing the work.

04

保留发现和恢复状态，拆掉运行时

A sweep can finish with an issue or without one. At completion, Signal separates what future work needs from what belonged only to this execution. The useful distinction is between retained knowledge and temporary access:

- Retained: Issue outputs and history, traces of the agent’s calls and PR activity, and any learned skills saved to the repository. - Removed: The sandbox, credentials and repository access associated with the finished run.

A later run can therefore begin with the investigation’s history while receiving a newly created working environment.

The same separation supports recovery during a run. If the sandbox or agent harness fails, Signal is designed to resume from the failed step rather than repeat the investigation from the beginning. Here, the harness is the software running the agent’s work. State lives outside the sandbox, so a replacement sandbox and harness can recover it. The disposable environment can fail without taking all progress with it.

The recovery diagram shows what happens when step 3 fails. Steps 1 and 2 have already been saved, along with the conversation, memory and which step comes next. A new sandbox loads that state and restarts at step 3. Issue history serves a different purpose in a later sweep, helping Signal recognize a problem it has seen before. The talk leaves unspecified what happens if the interrupted step already produced an external effect.

05

让模型和框架的选择可测试

Signal’s architecture also aims to avoid dependence on one model or harness. Dhinakaran says it began with Claude Code and, at recording time, also supported Cursor and Codex. Supporting other major harnesses, including open-source ones, is a goal. She describes broader multiple-model support as forthcoming while also describing model selection within the Anthropic family when using Claude Code.

That flexibility creates an evaluation question with a practical cost attached: can a cheaper configuration preserve the quality of detected issues and proposed PRs? More powerful models may produce better work, but their value needs to be assessed through the agent’s results. Dhinakaran presents cost and quality comparison as a reason for the design; she does not give a measured configuration comparison here.

Producing a PR then creates another piece of work to evaluate. Signal runs evaluations over the agent’s proposed change. Finding a plausible problem and writing a patch do not by themselves establish that the change solves the problem or preserves existing behavior. The evaluation stage supplies the check between a proposed improvement and confidence in its outcome.

06

定义好的行为，再检验评判者能否认出它

An evaluation can begin with a dataset, a prompt and outputs checked for regressions as part of development. The harder responsibility is deciding what those checks should reward or reject. Dhinakaran recommends spending time with traces and agents, identifying common errors and translating human judgment into evaluations. This is where the engineer defines what good behavior means for the particular product.

Skills can assist with writing those evaluations. Dhinakaran mentions Arize’s Evaluator skill as help for both creating evals and aligning them with human judgment. Assistance with authoring still leaves a separate question: does the resulting evaluator actually make the judgments the team intends? A judge that misses the errors people care about cannot reliably check an automated repair.

Arize addresses that question by evaluating its evaluators. The team builds ground-truth datasets, runs the candidate evaluations and compares their decisions with human outputs. It then works on alignment before releasing a new evaluator. The human judgments provide reference decisions; agreement with them is something to check, rather than assume because an evaluator returns a confident verdict. The talk gives the procedure without specifying an agreement threshold.

Once aligned, evaluations can serve two settings:

- Offline testing: Check a proposed change during development, including whether it introduces regressions on the chosen examples. - Online evaluation: Judge recorded production behavior as the application runs.

The same effort to define useful judgments can therefore support both release testing and continued observation after release.

07

追踪编程智能体，也追踪产品

After pre-release evaluations and deployment, the instruction is to “trace everything.” That includes the product’s agents and the coding agents that built them. Claude Code, Cursor and Codex runs are themselves observable work. Recording their behavior helps explain what happened inside the factory producing the application, extending investigation beyond the application’s final responses.

Production traces then receive online evaluations. Those results become additional data for agents investigating the system: the investigator reads telemetry together with evaluation results to find problems within traces. The causal connection matters. Instrumentation records execution; evaluations attach judgments to that behavior; agents consume both to locate gaps and propose improvements. An evaluation result becomes an input to subsequent engineering work.

This returns to the opening gap between frontier labs and ordinary businesses. Dhinakaran suggests that part of the difficulty is business data: it is messier than the constrained, testable work available in a lab. AI engineers have to make testing and improvement work with that operational reality. Her closing direction is concrete: trace the agents, learn to evaluate the products, and build systems that use collected telemetry to improve them. The engineering responsibility extends through the behavior of the system after it ships.

要点总结

  • Signal 以可配置的批次调查 trace，并记住之前的问题，让后来的证据可以改变早先某个观察的重要性。
  • 一次性沙箱和持久的外部状态服务于不同的目的：临时访问随一次运行结束，而发现和恢复状态支撑未来的工作。
  • 评估器本身也需要验证：在依赖它们评估智能体工作之前，先在有标准答案的数据集上把它们的判断与人工判断进行比较。
  • 既追踪生产智能体，也追踪背后的编程智能体。基于这些 trace 的在线评估，可以为下一次调查提供行为证据和判断。

智能体构建智能体：评测、实验与生产反馈

当一个编程智能体能检查失败、检验具体假设，并只保留通过评测的修改时，它就能改进另一个智能体。

熟悉 LLM 工具调用、自动化测试和 Git 分支会有帮助；TypeScript 示例只需要基本的异步编程知识。

01

如何改进一个行为不确定的软件？

智能体的答案会波动，会产生幻觉，还可能花掉不少钱。这样的智能体，要怎样才能可靠到能用于工作流自动化或搜索？Alfonso Graziano 在 Nearform 做智能体项目，他就是从实际工作出发来回答这个问题的。他自我介绍是一名技术负责人，帮助团队转向 AI 原生工程，也是《Learning AI-Native Software Engineering》一书的作者。大家对智能体的需求显而易见；怎样用工程方法持续改进它们，同样需要投入精力。

智能体也是软件，所以编程助手可以帮忙构建和改进它们。难点在于给这些助手一套可重复的方法，让它们能判断有没有进步。Graziano 的流程不能完全解决非确定性、延迟、成本和幻觉这些问题。但有了它，改进就成了团队能调查、能验证的事，而不是靠猜。

02

在优化之前先定义行为

说到底，智能体就是在循环里运行的 LLM：它接入工具，也能检索上下文。评测和可观测性围绕着这个循环。评测告诉你智能体有没有完成该做的事，可观测性帮你弄清到底发生了什么。于是，排查故障有两个地方：评测集和线上实际使用。真实用户带来的输入和期望，往往比评测里已有的用例更宽泛、更杂乱。

评测要从 Golden dataset 做起。它是和领域专家一起打磨出来的一个或一组文件，把输入和期望行为一一对应起来。在简单的数据集里，期望输出可能是一个数字、一段文字，或者一个 IMPOSSIBLE 标签。有了这些具体例子，动手优化之前，大家就先明确了系统应该返回什么。

如果智能体要通过工具来做事，期望输出描述的可以是执行过程，而不只是一个答案。

| 期望 | 评估器检查什么 | |---|---| | 答案 | 必须出现的文本或数值 | | 工具选择 | 调用了指定的工具 | | 工具参数 | 调用时用了预期的参数 | | 工具顺序 | 按规定顺序调用 |

比如，某个任务要求先检索、再更新。最后一句话说得再像样，也证明不了智能体真按这个顺序执行了。所以，这个数据集就像一套专为非确定性系统写的测试，再配上一个或多个评分器（scorer），把观察到的行为转换成度量。有了这些度量，就能建立基线，智能体一改动，回归也会暴露出来。

03

一个极简的智能体暴露出缺失的能力

演示从一个最简的 Mastra 智能体开始。它叫 math agent，不过它的 Golden dataset 里有好几类问题。这个智能体只有名字、几条指令和一个模型，没有任何工具。评估器同样简单：检查模型回复里有没有包含预期的标准答案。核心检查逻辑用 TypeScript 可以直接写出来：

```typescript type AnswerCase = { input: string; expected: string; };

type AnswerResult = AnswerCase & { actual: string; passed: boolean; };

async function evaluateAnswers( cases: readonly AnswerCase[], answer: (input: string) => Promise<string>, ): Promise<AnswerResult[]> { const results: AnswerResult[] = [];

for (const testCase of cases) { const actual = await answer(testCase.input); results.push({ ...testCase, actual, passed: actual.includes(testCase.expected), }); }

return results; } ```

这段代码保留了演示里刻意设计得很朴素的评分规则。它只检查子串有没有出现，既证明不了解释是对的，也证明不了智能体按要求的顺序调用了工具。

Graziano 介绍，在这套示例用例上用子串评估器打分，不带工具的智能体通过率是 18%。他认为，通过的用例（比如简单的加法和乘法）靠的是模型权重里已有的知识。这能解释一个接触不到外部资源的智能体为什么还能答对一些题；但光看分数，看不出它的权重究竟能答到什么程度。

这些失败指向三个值得排查的地方，按顺序依次是：

- 缺工具。 如果任务需要浏览或抓取网页，没有这些能力的智能体就走不完预期的工作流。 - 系统指令不完整。 系统提示词定义了期望的行为、禁止的行为和领域相关的指令。改一改提示词，也许不用新增组件就能解决问题。 - 缺上下文检索。 智能体可能不知道去哪里找需要的信息。检索通常以工具的形式提供，比如 RAG 搜索或网页抓取，这些工具必须安全地开放访问。

这些都是编程智能体可以动手改、再拿去评测的具体改动。

04

把评估变成一个实验循环

先例来自 Andrej Karpathy 的 autoresearch：编程智能体修改 Python 训练代码和超参数，跑实验，再根据结果决定下一步试什么。Graziano 讲到的那张图里，每个点代表一次实验。他把进展描述为准确率上升、loss 下降；按项目文档，确切的目标是在固定 5 分钟的训练预算内，降低验证集上的每字节比特数（bits per byte），越低越好。真正能迁移过来的，是“反复实验、次次度量”这套机制。同样的机制，能不能用来改进智能体？

AutoAgent 把这个循环用在了智能体的实现上。它先跑评测，然后修改代码或系统提示词，必要时创建工具，再跑一遍评测，看改动有没有用。

Graziano 介绍，那个最简示例大约迭代十轮，评测准确率就从 18% 提升到了 83%。起点很关键：一个没有任何工具的智能体，本来就有不少明摆着该补的能力；而且这个例子用的还是前面那个简单的评估器。

他还单独提到，一个已经经过人工优化的生产环境智能体，在一些内部基准上提升了 +10%。演讲没有说明这是相对百分比还是百分点。有价值的发现在于：编程智能体找到了人工优化时漏掉的改进点。

05

给编程智能体反馈和边界

演示用的编程智能体是 Claude Code，换成其他编程智能体也可以。它负责写目标智能体的代码，再从目标智能体的评测里拿到反馈：哪些用例现在通过了，哪些出现了回归。它还能查看完整的执行 trace，包括能拿到的思考过程 trace，去深挖某个失败，而不是只盯着一个汇总分数。

不能让优化器为了通过测试，擅自改写“成功”的定义。 人负责提供智能体的初始结构、相关文件和领域上下文，并划定允许改动的范围。尤其要禁止它只为让评测通过就去改 Golden dataset 或评分器。否则分数涨了，可能只是测试变弱了，智能体并没有变好。

优化任务本身就是一份 Markdown 文档。文档写明目标、目标仓库、指标，以及编程智能体在这些边界内干活所需的其他上下文。这正是规格说明在实践中的作用：告诉优化器要改进什么、允许在哪里动手。

06

保留成功的代码，记住失败的实验

先跑一遍评测建立基线，再启动一个有轮数上限的优化循环。每轮迭代针对某一类失败提出一个假设，修改智能体，然后评估结果。出现回归就回滚；有了提升，就拿它当下一轮实验的起点。图示的过程里有一次回归、一次提升、一次持平，接着又提出了新假设。过往的假设都会保留，跑多少轮由操作者决定。

基线报告不只是一个分数。它记录了每个用例，总结了哪些行得通、哪些失败了，给编程智能体一个具体的调查起点。没有这些细节，智能体只知道效果差，却几乎找不到原因的线索。

之后的每次实验都遵循一套可审查的流程：

1. 新建分支，提出假设。 2. 修改目标智能体，实现这个假设。 3. 运行评测集，把结果写成报告。 4. 更新实验的共享记忆。 5. 指标提升，就从这个候选分支继续；否则退回上一个成功的分支。

Graziano 把每次实验产出的文件叫作 report.md。仓库里现在的文件名区分大小写，分别是 REPORT.md、MEMORY.md 和 JOB.md，机制是一样的。记忆文件和之前的报告会为下一轮调查提供依据。

比如，第一个假设成功了，第二个失败了。第三次实验会从第一个假设成功后的代码拉分支，而不是接着被否掉的第二次改动往下做。但第二次实验的记录依然有用。回滚撤掉的是代码改动，抹不掉优化器学到的东西。

多轮迭代下来，就攒出了一份变更日志，记录各个假设、提升、回归和报告。人可以翻看失败的实验，分辨是思路本身不行，还是思路不错、只是实现错了。之后再补一条指令，就能引导编程智能体换个更好的实现，而不是盲目重复这个假设，或者把它彻底丢掉。

07

改进现有智能体的细节

在后面一个例子里，Graziano 介绍，一个如今已在生产环境运行的智能体，大约迭代十轮，评测准确率从 67% 提升到 86%。他把提升归功于找出边界情况、打磨系统提示词、改进工具描述和修复工具逻辑，而不是改动评测标准。演讲没有给出这个结果对应的任务定义、评测集划分和评分器。

08

用实时反馈发现缺失的失败案例

智能体在现有评测上有了提升，真实用户照样可能失望。第二套工作流从用户、beta 测试者和领域专家的数据入手。一个简单的“有帮助吗”的问题，一个是或否的回答，再加一条备注，就能给团队带来原始数据集可能从没料到的反馈。

这条流水线把反馈和执行证据对应起来：

1. 用户使用服务，系统收集 trace。 2. 用户提交反馈；或者专家查看输入、输出、工具调用和行为之后，给 trace 加标注。 3. 分析工作流检查正面和负面反馈，重点看负面案例。 4. 把反复出现的问题归成失败聚类。 5. 领域专家验证这些聚类之后，编程智能体再生成修复方案并实现。 6. 团队用收集到的 trace 测试修复，然后上线，再观察真实数据上的表现有没有改善。

聚类把一堆抱怨收拢成少数几种候选解释。Graziano 举了几个失败模式为例，每个背后都有一组 trace 支撑：要问的是哪个共同原因导致了这种行为，而不只是有多少用户不喜欢某个回答。

09

把一条投诉与它的 trace 和源代码联系起来

具体的用户例子是问怎么优化一个 React 组件。除了回复本身，系统还会记录这次交互、工具使用情况、响应时间和 token 消耗。随后，用户可以写下哪里做得好、哪里不行、自己原本期望什么。演示中的反馈表单和 trace 里是同一条评论，嫌回答太长。抱怨和记录下来的执行过程之间有什么关联，一眼就能看出来。

如果用户没留反馈，领域专家可以查看 trace，代为标注。演示把 114 条带反馈的 trace 导出到本地做聚类分析。一个编程智能体 skill 让智能体检查这些 JSON、给失败做聚类，再对分析结果做一轮对抗性审查。

编程智能体既能看到目标智能体的源码，又能拿到详细的 trace，就能追查可能的根因。提出改动之前，它可以顺着生成某个答案的执行过程往下看，把这种行为和具体实现对上。最后产出一份 Markdown 报告，内容包括执行摘要、正面和负面反馈、负面反馈率、失败聚类，以及可能的改进方向。

其中一个聚类和 Markdown 格式有关：URL 没做成超链接，格式也前后不一。报告把这个聚类和 trace ID、用户反馈关联起来，再列出可能的原因和修复建议。有了这些关联，诊断过程就能核查；但报告终究只是一组待审的候选项。报告生成出来，不等于已经定好要改什么。

10

把经过验证的失败变成回归测试覆盖

领域专家给报告做分诊，决定哪些马上修、哪些以后修、哪些不动。确定要修的问题，编程智能体会拿到失败模式、相关上下文和支撑它的 trace。聚类也可以直接丢弃：它可能是误报，也可能描述的是刻意设计的行为，只是恰好有用户不喜欢。系统该采纳哪些期望，要靠人来判断。

确认采纳的失败模式会加入 Golden dataset，评测和评分器也随之更新，一旦问题复发就能抓住。这是团队在调查和验证之后，有意扩大期望行为的范围。它和前面那条限制正好互补：不许优化器只为提分而削弱测试。这样一来，过去只出现在线上反馈里的失败，下一次代码改动就能拿来对照检验了。

11

选择分析节奏和修复路径

Graziano 的团队发现，每个 sprint 分析一次比较合适，节奏再根据反馈量调整。他给的数量只是操作上的参考：大约 100 条 trace 可能就值得出一份报告；如果有 10,000 条带反馈的 trace，最好拆成几份报告。目标是让每次分析都有足够的有效证据，又不让积压的问题多到难以处理。

Graziano 提到，有些情况下，只要给足上下文和回归测试，编程智能体一条提示词就修掉了一整批问题。有了测试，智能体能自己检查改动，而不是改完代码就收工。遇到更复杂的情况，他的团队会让 AutoAgent 针对失败聚类去处理，产出 pull request 草稿交给人审查。

12

构建让改进成为可能的环境

两套工作流都离不开框架工程（harness engineering）：围绕编程智能体搭建环境，让它能改代码、验证自己的改动，并修正没成功的方案。框架提供任务、约束、反馈循环和治理机制。少了这些，编程智能体能生成改动，却没有可靠的流程判断这些改动到底有没有用。

这个环境把四种互补的控制手段结合在一起：

- 规格驱动开发。 把每个确认的失败模式写成期望行为的规格说明，再去实现。 - 质量关卡。 用 lint、单元测试、评测和 LLM 代码审查，从不同角度检查改动。 - 上下文工程。 给编程智能体提供理解任务和约束所需的相关信息。 - 可观测性。 让生产环境的行为看得见，上线后出了问题也能追查。

持续观察生产环境，这个流程就不会走到头：每次上线的改动都会产生新证据，这些证据又可能暴露下一个 bug，或者一条遗漏的期望。编程智能体能把系统改进到什么程度，取决于团队能不能让这些行为看得见、测得了。

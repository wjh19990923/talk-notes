在 VS Code 中构建交互式 MCP 应用

跟随一个纯文本的图表请求，走向一个交互式的聊天界面，然后追踪一个 Go 性能剖析应用如何经过它的 MCP 工具、HTML 资源、React 前端和沙箱化的宿主。

对聊天助手、服务端工具和前端开发有基本了解会有帮助；文中会介绍 MCP 的核心角色。

01

要把一个界面放进聊天里需要什么？

聊天回复怎样才能变成真正能用的界面？Marlene Mhangami 和 Liam Hampton 借 MCP Apps 回答这个问题：从协议的基本角色讲起，一直讲到在 VS Code 里跑起来的性能分析器。Mhangami 是 Microsoft 和 GitHub 的高级开发者布道师；Hampton 负责 VS Code 和 GitHub Copilot 的开发者工具布道。

Model Context Protocol（MCP） 是 Anthropic 创建的开放协议，统一了应用向语言模型提供上下文的方式。它提供的能力包括工具（tools）、提示词（prompts）和资源（resources）。在架构上，用户使用的应用是一层，提供这些能力的连接和程序是另一层，两者分开。

| 角色 | 职责 | 演讲中的例子 | | --- | --- | --- | | Host（宿主） | 想要使用服务器能力的应用 | VS Code | | Client（客户端） | 与一个服务器保持一对一连接 | 按两位讲者的说法，是 GitHub Copilot | | Server（服务器） | 通过 MCP 暴露能力的轻量程序 | 自建或现成的 MCP 服务器 |

服务器可以自己写，也可以用现成的。在 VS Code 的扩展视图里搜索 @mcp，就能列出可用的服务器。Mhangami 建议先从 VS Code 或 GitHub 的列表里挑。从网上随便下载的服务器可能藏有恶意代码。服务器是可执行软件，选哪个服务器，其实就是决定信任谁。

02

从图表文本到一个可编辑的图表

假设你让模型画一张图来解释 MCP。按 Mhangami 的描述，早期得到的回复往往是文字：ASCII 字符画、图表源码，或者一份用 emoji 点缀的 README。问题出在交互体验上，并不是说 MCP 当时只能传文本——2024-11-05 版工具规范就已经支持图片和嵌入资源。可不管文字怎么表达，用户手里都没有一张能直接操作的图。

有了 MCP Apps，服务器工具可以提供丰富的交互组件，直接在聊天里渲染。 Mhangami 用 Excalidraw MCP App 服务器重新提了一遍画图请求。这次用户不只是读回复，还能直接上手改图。她的幻灯片只是截图，但她讲到了实际应用的效果：不用离开对话，就能拖动图里的元素、修改上面的文字。

03

宿主把一个资源变成一个界面

Mhangami 用一个简单的数据分析请求，梳理了整个交互流程：

1. 用户问：“给我看看分析数据。” 2. 智能体从某个 MCP 服务器暴露的工具里挑出合适的一个。 3. 服务器返回结果，结果关联着一个 UI 资源引用，指向一段 HTML。 4. 宿主（这里是 VS Code）拉取这段 HTML，在沙箱化的 iframe 里渲染出来。 5. 用户与应用交互，应用可以向服务器请求更多数据，并更新显示内容。

界面由宿主渲染，工具由模型挑选。 分清这一点，就明白为什么在她的讲解里，去拉取 HTML 的是 VS Code，而不是 Copilot 客户端。

演讲里说，UI 引用是随结果一起返回的。按当前的 MCP Apps 架构，工具定义里会声明 _meta.ui.resourceUri，宿主在工具执行完之前就能发现 UI，甚至提前加载。之后应用和工具之间的通信，也都经过宿主中转。核心分工没有变：工具产出数据，资源提供界面，宿主把两者连起来。

04

点击胜过再写一个提示词的地方

拿数据探索来说，第一个问题可能让柱状图显出某种趋势。下一步往往更具体：看看某几个数值，或者换一种图表。如果每一步都得用文字描述，用户就要把视觉上的意图再翻译回语言。有了按钮之类的控件，用户可以直接动手做下一步。

电商是另一个相关的例子，不过它更适合通用聊天产品，而不是 VS Code。购物助手可以返回一个链接，把买家送到浏览器里；Mhangami 设想的体验，则是挑商品和结账都在聊天里完成。UI 推着交易往下走，对话不再只是一份跳转地址清单。

这些例子涵盖了几类不同的界面：

- Shopify： Mhangami 提到，渲染出来的组件保留了商家网站的品牌风格，在聊天里就能走完整个结账流程。她强调的是这种体验，没有演示具体的结账 API。 - Excalidraw： 架构图变成可交互的可视化图表。她还提到一个她称为 Quip Code 的例子。 - Figma： 她说可以即时生成组件，但没有展示实际渲染出来的 Figma 应用。

这些设计的共同目标，是把完成任务真正用得上的交互界面，直接放在对话旁边。

05

构建一个工具、一个资源以及两者之间的连接

Hampton 的实现从 Model Context Protocol MCP Apps 仓库里的一个 skill 起步。他改了改这个 skill，再交给 GitHub Copilot CLI 运行，生成了好几个应用。他的演示仓库里有接下来要演示的 FlameGraph 示例，还有 Markdown 查看器、航班状态应用和取色器。目的都一样：让交互留在同一个工作环境里，也就是 VS Code。

实现上有三个关键部分：

| 部分 | 提供什么 | | --- | --- | | 工具 | 模型可以选用的服务器操作 | | 资源 | 打包好的 HTML 界面 | | 关联 | 工具与其 UI 资源的对应关系 |

工具和挑选它的 LLM 是两回事。同样，资源和工具返回的数据也是两回事：宿主要靠两者之间的关联，才知道该用哪个界面展示这些数据。前端可以用 React、Vue、原生 JavaScript 或 Svelte 来写。

这个 skill 给编码助手准备了搭建和运行说明、代码示例、处理函数（handler），以及设置工具可见性的指引。可见性决定了谁能调用某个工具：

- 仅模型： 模型可以在对话中选用它。 - 模型和应用： 模型和嵌入的界面都能调用它。 - 仅应用： 界面可以调用它，但模型看不到、也选不了它。

这个选择应该在设计应用时就定下来，因为交互控件和智能体需要的操作不一定相同。

06

把一个 Go 工作负载变成性能分析数据

Flamegraph Profiler 应用分析的是一个 Go 程序，里面有冒泡排序和斐波那契计算两类负载。这样性能分析器就有了容易辨认的函数，可以逐个查看执行开销。这两个负载函数的精简版如下：

```go package workload

func BubbleSort(values []int) { for end := len(values) - 1; end > 0; end-- { for i := 0; i < end; i++ { if values[i] > values[i+1] { values[i], values[i+1] = values[i+1], values[i] } } } }

func Fibonacci(n uint) uint64 { if n < 2 { return uint64(n) } return Fibonacci(n-1) + Fibonacci(n-2) } ```

冒泡排序反复比较相邻的两个值，必要时交换位置。递归版斐波那契函数则一遍遍对更小的输入重新求值。两者合起来，代表了这个演示要分析的那类应用负载。

Hampton 用 Go 的 pprof 设了一个 5 秒的采样窗口。MCP 服务器跑在 localhost 上，由一个本地入口调用 TypeScript 写的服务器实现。最关键的服务器操作会准备 Go 程序、运行它、做性能分析，再把结果数据返回。注意，5 秒是数据采集的时长，不是测出来的提速。

与工具关联的前端是一个 React 应用，Hampton 叫它 Flame App。它用 hooks 接收工具的输入和结果，再把分析数据画成火焰图，并展示程序把时间花在了哪里。工具与资源分离的实际价值就在这里：性能分析仍然交给服务器，前端负责让结果更容易看懂。

07

在 Copilot 聊天里检查结果

装好 MCP 服务器并启动后，Hampton 打开 GitHub Copilot。服务器只暴露了一个工具，他称之为“Profile the App”。他让 Copilot 分析这个应用；Copilot 认出已安装的 Flame Graph Profiler，选中这个工具，开始加载 MCP App。界面随后出现在聊天窗口的一个 iframe 里。

界面里列出了最耗时的函数和一份性能分析摘要。尺寸和展示方式都可以调，以适应聊天窗口；台上演示的版本开得相当大。用户不必一遍遍问模型：这份分析结果是好是坏？时间都花在哪儿了？直接看函数信息就行。Hampton 想说的是，这能省掉不少来回问答：相关数据已经摆在应用里了。

08

让界面保持有用且受约束

完整的演示走的是和前面数据分析例子相同的路径。分析应用的请求到达模型，模型选中工具，MCP 服务器返回 JSON 数据。宿主识别出关联的 UI 资源，在聊天里渲染出界面。模型不必先把分析结果的每个细节都写成文字，用户就能自己动手探索。

Hampton 用仓鼠打了个比方来解释 iframe：把仓鼠放在房间里随便跑，它可能到处乱啃；给它一个笼子，它就只能在笼子里活动。同样的道理，嵌入的应用不能随意访问 VS Code 设置或外部系统。iframe 是这道边界的一部分，但并不等于一刀切地禁止所有外部访问：能访问哪些资源，由宿主权限和内容安全策略（CSP）决定，工具调用也要经过宿主中转。界面照样可以交互，却拿不到编辑器的全部权限。

演讲最后，两位讲者邀请大家去 GitHub 展位交流，也欢迎大家参加 Microsoft Build 上偏重代码的分场和工作坊，继续学习。技术演示到本地服务器和嵌入的性能分析界面就结束了：一个有用的应用完全可以待在对话里，渲染和隔离则仍由宿主负责。

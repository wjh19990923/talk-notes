Workflow: Prompt chaining

Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks (see “gate” in the diagram below) on any intermediate steps to ensure that the process is still on track.

In → LLM Call 1 → Output 1 → Gate
Pass → LLM Call 2 → Output 2 → LLM Call 3 → Out
Fail → Exit

工作流：编排者—工作者

幻灯片原文
An orchestrator breaks a task into input-specific subtasks, delegates them to worker LLMs, and synthesizes their results. This flexibility suits complex tasks whose subtasks cannot be predicted in advance.

Workflow: Orchestrator-workers

In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.

In → Orchestrator → LLM Call 1, LLM Call 2, LLM Call 3 → Synthesizer → Out

The orchestrator-workers workflow

When to use this workflow: This workflow is well-suited for complex tasks where you can’t predict the subtasks needed (in coding, for example, the number of files that need to be changed and the nature of the change in each file likely depend on the task). Whereas it’s topographically similar, the key difference from parallelization is its flexibility—subtasks aren't pre-defined, but determined by the orchestrator based on the specific input.

对反工作流言论的反应

Declarative vs non-declarative graphs

Some frameworks are declarative, requiring developers to explicitly define every branch, loop, and conditional in the workflow upfront through graphs consisting of nodes (agents) and edges (deterministic or dynamic handoffs). While beneficial for visual clarity, this approach can quickly become cumbersome and challenging as workflows grow more dynamic and complex, often necessitating the learning of specialized domain-specific languages.

In contrast, the Agents SDK adopts a more flexible, code-first approach. Developers can directly express workflow logic using familiar programming constructs without needing to pre-define the entire graph upfront, enabling more dynamic and adaptable agent orchestration.

智能体还是工作流：为什么不能两者兼得？

智能体决定下一步做什么；工作流让依赖关系变得明确。把两者结合起来，系统就能在保持灵活性的同时，在需要可靠性的地方加上控制。

熟悉 LLM 工具调用和基础的异步 TypeScript，有助于理解示例。

01

智能体会让工作流过时吗？

Should you build an agent or a workflow—and why should you have to choose? Sam Bhagwat, a Gatsby co-founder and author of Principles of Building AI Agents, opens with the dispute behind that question. His talk puts the hot takes first and the practical design patterns afterward.

The starting point is Anthropic’s December article, Building effective agents, with its diagrams of agents, workflow routing, and orchestration. Then came an OpenAI guide that Bhagwat places in April, followed by criticism about both its novelty and its treatment of workflows. He characterizes its language as an “anti-workflow blast.” The matching discussion in A practical guide to building agents specifically criticizes declarative graph frameworks, a narrower target than workflows generally. Bhagwat recalls swyx responding with an emergency Latent Space post. The practical question underneath the controversy is whether model-directed execution should displace explicit orchestration.

02

当服务商的建议变成了正统

Bhagwat’s first objection concerns who gets to define the right way to build. He directs it at OpenAI, then reaches back to a hallway conversation with Laurie Voss about the previous decade of web development: a developer in a prominent, public-facing role can turn a personal architectural preference into an ecosystem-wide prescription.

His example is the pressure certain Googlers put on web developers to “use the platform”—with an explicit qualification that he does not mean all Googlers. Bhagwat remembers that rhetoric functioning as an argument against React and in favor of technologies he found harder to use. Model providers now occupy a similarly influential position: their recommendations carry more weight than an ordinary developer’s preferences. That makes careful distinctions between useful patterns and supposedly mandatory approaches especially consequential.

03

让执行顺序可读

His second objection is more concrete: workflow frameworks should not make developers assemble nodes and edges just to express a process. Naming LangChain, Bhagwat calls that API style harmful—and draws on his own experience with Gatsby to explain why. Gatsby made GraphQL its default data-fetching pattern in 2017. Some users loved it; others wanted a React metaframework without having to adopt that additional way of working, and chose alternatives. GraphQL could be a good technology while still being the wrong requirement to impose on every user.

Graph-oriented workflow APIs give him the same concern. His objection is the learning burden placed on the whole team, not just the person who initially wires up the application. In the alternatives he shows, Mastra uses fluent workflow syntax and Inngest expresses a sequence whose control flow is visible as you read downward. The code’s reading order should help reveal its execution order. Separately declaring nodes and connecting edges can obscure that relationship.

04

从架构模式到话轮和依赖关系

A readable API is only part of the problem. Developers also need a shared vocabulary for the arrangements they build. Bhagwat introduces that need through Christopher Alexander, the Berkeley architect associated with A Pattern Language. Published in 1977, the book catalogs 253 patterns spanning towns, buildings, and construction. Bhagwat contrasts what he describes as architects’ cooler reception with software engineers’ enthusiasm, placing the latter roughly in the late 1980s and early 1990s. His concern for agent engineering is that a similarly accepted glossary of patterns has not yet emerged.

He credits Nick and Zach’s previous-day Mastra workshop for the definition slides, then supplies two everyday mental models. An agent resembles a turn-based game: the user takes a turn, the agent responds, and the agent may take additional turns or make tool calls. A workflow resembles the rules behind a Civilization technology tree. In his examples, bronze working precedes iron working, and metallurgy precedes gunpowder. The essential property is a dependency: step B cannot happen until step A has happened. A data pipeline extends that relationship through A → B → C → D → E.

The two starting points lead to different capabilities:

| Starting point | Capabilities that follow | |---|---| | Messages and turns | Conversation threads and memory | | Steps and dependencies | Branches, parallelism, conditions, and loops | | Managed workflow execution | Suspension, resumption, and replay |

These are complementary ways to organize an application. Messages preserve an interaction’s context; workflow dependencies express when work may proceed and how execution can continue.

05

在行为变得不可靠的地方加上控制

Ordinary code can already execute A, then B, then C, then D. Why introduce a workflow framework? In AI applications, nondeterminism makes it especially useful to trace what happened and inspect how execution reached a result. Bhagwat emphasizes this by calling tracing “10X as important”; the phrase expresses urgency rather than a measured comparison. Instrumentation and replayability help make a variable process inspectable.

Choose flexibility and control separately for each part of the application. You can begin by giving an agent freedom to decide, then add structure where its behavior goes off the rails. This turns the agents-versus-workflows question into a local architectural decision: which operation benefits from discretion, and which needs a more constrained process?

Bhagwat describes a whiteboarding problem involving a large PDF of medical documentation. The application is trying to work through symptoms but is not extracting the right information. He proposes splitting one LLM call into multiple focused calls; he reports no measured accuracy improvement. The proposed change separates the work so that each call can concentrate on a particular symptom.

In TypeScript, that decomposition can be expressed by passing the same document through a focused extraction operation for each symptom:

```typescript type SymptomEvidence = { symptom: string; passages: string[]; };

type ExtractSymptom = (input: { documentText: string; symptom: string; }) => Promise<string[]>;

async function extractSymptoms( documentText: string, symptoms: readonly string[], extractSymptom: ExtractSymptom, ): Promise<SymptomEvidence[]> { const results: SymptomEvidence[] = [];

for (const symptom of symptoms) { const passages = await extractSymptom({ documentText, symptom }); results.push({ symptom, passages }); }

return results; } ```

This procedure makes one focused call per symptom entry and retains the symptom associated with each result. The architectural question comes first: identify the unreliable operation, then decide what structure could improve it. Bhagwat recommends explaining the architecture to a colleague and drawing it on a whiteboard; making the dependencies visible can expose a better way to combine the primitives.

06

让智能体和工作流相互嵌套使用

The composition rules are small. Agents call tools; workflows execute steps. Either primitive can occupy either role:

| Composition | What it enables | |---|---| | Agent as a workflow step | Model-directed work inside a structured process | | Workflow as an agent tool | A structured operation the agent can choose to invoke | | Agent as an agent tool | Delegation to a specialist | | Workflow as a workflow step | A larger process assembled from smaller processes |

The useful design space comes from combining these arrangements, rather than choosing one primitive for the entire application.

The agent supervisor pattern uses the third arrangement. An orchestrator agent calls specialist agents as tools; Bhagwat’s example includes a research agent and a summary agent. The supervisor provides the point of coordination, while specialist agents perform the delegated work. His Mastra examples are intentionally small enough to fit in a slide panel: the point is that simple primitives can yield understandable combinations. These are historical API illustrations; the TypeScript example above expresses the decomposition directly without reconstructing the slide’s framework calls.

07

结构化的工具、变化的工具集和嵌套的流程

For workflows as tools, Bhagwat switches to trip planning: plan a location, check the weather, then plan the trip. Those operations may each contain a more complex workflow. Exposing them as tools lets an agent iterate and decide while the invoked workflows retain their internal structure. He also names workflows that perform agent handoffs, extending the idea of structured execution coordinating agents.

Dynamic tool injection changes which tools an agent receives at a particular moment. Bhagwat warns that agents can begin failing when given double-digit numbers of tools, and recommends selecting tools for the current task and stage of execution. The mechanism is to make the available set relevant to what the agent is doing now, rather than expose every capability throughout the interaction.

Nested workflows apply the same composition principle to processes: a workflow becomes a step inside another workflow. Bhagwat closes the presentation by emphasizing that the value comes from combining these patterns appropriately. Production applications accumulate details, so their agentic workflows will too. The architecture must accommodate those details through combinations of tools, steps, agents, and workflows.

08

保留那个满足需求的系统

The audience immediately tests that advice against a working system. A questioner first asks whether a deep-research agent should be combined with a workflow rather than replace it. They then explain that their workflow already works very well with 20 tools, despite arguments that orchestration is unnecessary. Bhagwat restates it as an agent working well with 20 tools. Neither account supplies an evaluation metric, but the example makes clear why the earlier tool-count warning cannot be treated as a fixed limit.

His response is to keep using the system if it meets its requirements. Agent engineering is a “community of practice” more than a “community of theory.” If a working implementation contradicts a theoretical prescription, that can reveal a weakness in the theory. In a young field, practice is evolving faster than the explanations that attempt to organize it.

Workflow: Prompt chaining

Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks (see “gate” in the diagram below) on any intermediate steps to ensure that the process is still on track.

In → LLM Call 1 → Output 1 → Gate

工作流：编排者—工作者

幻灯片原文
An orchestrator breaks a task into input-specific subtasks, delegates them to worker LLMs, and synthesizes their results. This flexibility suits complex tasks whose subtasks cannot be predicted in advance.

Workflow: Orchestrator-workers

In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.

In → Orchestrator → LLM Call 1, LLM Call 2, LLM Call 3 → Synthesizer → Out

The orchestrator-workers workflow

When to use this workflow: This workflow is well-suited for complex tasks where you can’t predict the subtasks needed (in coding, for example, the number of files that need to be changed and the nature of the change in each file likely depend on the task). Whereas it’s topographically similar, the key difference from parallelization is its flexibility—subtasks aren't pre-defined, but determined by the orchestrator based on the specific input.

Declarative vs non-declarative graphs

Some frameworks are declarative, requiring developers to explicitly define every branch, loop, and conditional in the workflow upfront through graphs consisting of nodes (agents) and edges (deterministic or dynamic handoffs). While beneficial for visual clarity, this approach can quickly become cumbersome and challenging as workflows grow more dynamic and complex, often necessitating the learning of specialized domain-specific languages.

In contrast, the Agents SDK adopts a more flexible, code-first approach. Developers can directly express workflow logic using familiar programming constructs without needing to pre-define the entire graph upfront, enabling more dynamic and adaptable agent orchestration.

智能体还是工作流：为什么不能两者兼得？

智能体决定下一步做什么；工作流让依赖关系变得明确。把两者结合起来，系统就能在保持灵活性的同时，在需要可靠性的地方加上控制。

熟悉 LLM 工具调用和基础的异步 TypeScript，有助于理解示例。

01

智能体会让工作流过时吗？

该做智能体还是工作流？为什么非得二选一？Sam Bhagwat 是 Gatsby 联合创始人，著有 Principles of Building AI Agents。他从这个问题背后的争论讲起：先抛出几个犀利观点，再讲实用的设计模式。

争论的起点是 Anthropic 12 月发表的文章 Building effective agents，文中配有智能体、工作流路由和编排的示意图。随后 OpenAI 发布了一份指南，Bhagwat 记得是在 4 月。这份指南招来不少批评：有人说它没什么新意，也有人不满它对待工作流的态度。他形容指南的措辞是“对工作流的一通猛轰”。不过 A practical guide to building agents 里相关的段落，批评的其实是声明式图框架，范围比工作流整体要窄。Bhagwat 记得 swyx 为此在 Latent Space 紧急发文回应。争议背后真正的实际问题是：该不该让模型主导执行，取代显式编排？

02

当服务商的建议变成了正统

Bhagwat 的第一个反对意见是：谁有资格规定“正确的构建方式”？矛头指向 OpenAI。他还回忆起和 Laurie Voss 在走廊里聊过的上一个十年的 Web 开发：一位身处显眼位置、直接面向公众的开发者，能把自己的架构偏好变成整个生态都得遵守的规矩。

他举的例子是，某些 Google 员工曾向 Web 开发者施压，要大家“use the platform”（用好平台原生能力）。他特意说明，不是指所有 Google 员工。Bhagwat 记得，这套说辞实际上成了反对 React 的论据，推的却是一些他觉得更难用的技术。如今模型厂商处在类似的位置，他们的建议比普通开发者的偏好分量重得多。所以，哪些只是好用的模式、哪些号称非用不可，这条线划得清不清楚，影响格外大。

03

让执行顺序可读

第二个反对意见更具体：工作流框架不该逼开发者拼装节点和边，只为表达一个流程。Bhagwat 点名 LangChain，说这种 API 风格有害，并用自己在 Gatsby 的经历解释原因。2017 年，Gatsby 把 GraphQL 定为默认的数据获取方式。有些用户很喜欢；另一些用户只想要一个 React 元框架，不想再多学一套工作方式，于是转投别家。GraphQL 可以是好技术，但强加给每个用户就错了。

面向图的工作流 API 让他有同样的担忧。他在意的是整个团队都要背上的学习负担，而不只是最初搭起应用的那个人。在他展示的替代方案里，Mastra 用的是链式（fluent）工作流语法，Inngest 写出来是一串顺序步骤，从上往下读就能看清控制流。代码的阅读顺序应该帮人看懂它的执行顺序。 把节点和边分开声明，反而会让这层关系变模糊。

04

从架构模式到话轮和依赖关系

API 好读只解决了一部分问题。开发者还需要一套共同的词汇，来描述自己搭出的各种结构。Bhagwat 借 Christopher Alexander 引出这一点。Alexander 是伯克利的建筑师，代表作是 A Pattern Language。这本书 1977 年出版，收录了 253 个模式，从城镇、建筑一直讲到具体建造。Bhagwat 说，建筑师对它反应平平，软件工程师却热情高涨，时间大约在 1980 年代末到 1990 年代初。他担心的是，智能体工程至今还没有一套同样公认的模式词汇表。

定义部分的幻灯片，他归功于 Nick 和 Zach 前一天主持的 Mastra 工作坊，随后给出两个日常的思维模型。智能体像回合制游戏：用户走一步，智能体回应，智能体还可以再多走几步或调用工具。工作流像《文明》里科技树背后的规则：在他的例子里，青铜器要先于铁器，冶金要先于火药。关键在于依赖关系：A 步没完成，B 步就不能开始。数据管道把这种关系延伸成 A → B → C → D → E。

两个出发点通向不同的能力：

| 出发点 | 随之而来的能力 | |---|---| | 消息与轮次 | 对话线程与记忆 | | 步骤与依赖 | 分支、并行、条件与循环 | | 托管的工作流执行 | 挂起、恢复与重放 |

这是组织应用的两种互补方式。消息保留交互的上下文；工作流依赖则规定工作何时可以推进、执行怎样继续下去。

05

在行为变得不可靠的地方加上控制

普通代码本来就能先执行 A，再执行 B、C、D。为什么还要引入工作流框架？AI 应用有不确定性，追踪发生了什么、查看执行是怎么走到某个结果的，就显得格外有用。Bhagwat 说 tracing “重要 10 倍”，这是在强调紧迫，不是实测对比。有了埋点和重放，一个多变的过程就变得可以检查。

为应用的每个部分分别决定要多少灵活性、多少控制。 可以先放手让智能体自己决定，哪里跑偏了，再在哪里加结构。这样，“智能体还是工作流”就变成了局部的架构决策：哪个操作适合交给模型自行判断，哪个需要更受约束的流程？

Bhagwat 讲了一个在白板上讨论过的问题：有一份很大的医疗文档 PDF，应用要逐一梳理其中的症状，却提取不到正确的信息。他建议把一次 LLM 调用拆成多次聚焦的调用，但没有给出准确率提升的实测数据。拆开之后，每次调用都能专注于一个特定症状。

用 TypeScript 可以这样表达这种拆分：同一份文档，针对每个症状各跑一次聚焦的提取操作：

```typescript type SymptomEvidence = { symptom: string; passages: string[]; };

type ExtractSymptom = (input: { documentText: string; symptom: string; }) => Promise<string[]>;

async function extractSymptoms( documentText: string, symptoms: readonly string[], extractSymptom: ExtractSymptom, ): Promise<SymptomEvidence[]> { const results: SymptomEvidence[] = [];

for (const symptom of symptoms) { const passages = await extractSymptom({ documentText, symptom }); results.push({ symptom, passages }); }

return results; } ```

这段程序对每个症状条目各做一次聚焦调用，并在每个结果里记下对应的症状。先想清楚架构问题：找出不可靠的那个操作，再决定用什么结构改善它。Bhagwat 建议把架构讲给同事听，在白板上画出来；依赖关系一旦摆在眼前，往往就能发现更好的原语组合方式。

06

让智能体和工作流相互嵌套使用

组合规则不多。智能体调用工具，工作流执行步骤。两种原语都可以充当这两种角色：

| 组合方式 | 能做到什么 | |---|---| | 智能体作为工作流步骤 | 在结构化流程里由模型主导干活 | | 工作流作为智能体工具 | 智能体可以自行选择调用的结构化操作 | | 智能体作为智能体工具 | 把任务委派给专职智能体 | | 工作流作为工作流步骤 | 用小流程拼出大流程 |

真正有用的设计空间来自组合这几种方式，而不是整个应用只认一种原语。

智能体主管（agent supervisor）模式用的是第三种组合。一个编排智能体把专职智能体当作工具调用；Bhagwat 的例子里有一个研究智能体和一个总结智能体。主管负责协调，专职智能体完成分派下来的工作。他的 Mastra 示例刻意写得很短，一页幻灯片的小面板就装得下：重点在于，简单的原语能组合出好懂的结构。这些只是当时 API 的示意；上面的 TypeScript 示例直接表达了拆分思路，没有照搬幻灯片里的框架调用。

07

结构化的工具、变化的工具集和嵌套的流程

讲到工作流作为工具，Bhagwat 换成了旅行规划的例子：先定地点，再查天气，最后规划行程。每个操作内部都可能是一个更复杂的工作流。把它们暴露成工具，智能体就能反复尝试、自行决定，被调用的工作流仍保留各自的内部结构。他还提到会做智能体交接（handoff）的工作流，把“用结构化执行协调智能体”的思路又往前推了一步。

动态工具注入决定智能体在某一时刻拿到哪些工具。Bhagwat 提醒，工具数量一到两位数，智能体就可能开始出错；他建议按当前任务和执行阶段挑选工具。做法是让可用的工具只跟智能体眼下在做的事相关，而不是在整个交互过程中把所有能力都摆出来。

嵌套工作流把同样的组合原则用在流程上：一个工作流成为另一个工作流里的一步。Bhagwat 在结尾强调，价值来自把这些模式恰当地组合起来。生产环境的应用细节会越积越多，里面的智能体工作流也一样。架构必须容得下这些细节，靠的就是工具、步骤、智能体和工作流的各种组合。

08

保留那个满足需求的系统

观众马上拿一个跑得好好的系统来检验这条建议。一位提问者先问：深度研究智能体是不是应该和工作流结合使用，而不是取代工作流？接着他说，尽管有人认为编排没必要，他们的工作流配了 20 个工具，效果已经非常好。Bhagwat 把这句话复述成“一个配了 20 个工具、效果很好的智能体”。双方都没给出评测指标，但这个例子说明，前面关于工具数量的提醒不能当成硬性上限。

他的回答是：系统能满足需求，就接着用。智能体工程更像一个“实践共同体”，而不是“理论共同体”。一个能跑的实现如果跟某条理论规定相矛盾，暴露的可能正是理论的漏洞。在一个年轻的领域里，实践演进得比试图梳理它的理论更快。

ASK FOR PATTERNS ACROSS EVERYTHING
It samples when you need all of it.

112 bulletins & recalls in — ~7 patterns out, with its own gaps flagged.

ASK HOW THE RECORDS RELATE
It guesses the connections.
On a big, look-alike schema, Text2SQL picks the wrong table, loops, and runs up cost — or gives up.
Hundreds of near-identical tables, no map of how they join.

Each gap is a missing shape.
Not a model problem. Not a vendor problem.

AI on Your Lakehouse — workshop environment

Companion environment for the GraphAcademy workshop AI on Your Lakehouse: Context Comes in Shapes, Not Queries.

You build a service-advisor skill for AutoFix Group: a playbook + scripts that let your coding agent answer questions about the technical library and the repair history — grounded in a graph that spans the lakehouse's documents and warehouse tables.

The data comes in two halves that share keys (part numbers, trouble codes):
- Documents — repair manuals, service bulletins, and recall notices (PDFs), parsed into a Neo4j document graph (a navigable tree plus Leiden themes).
- Warehouse — vehicles, work orders, and parts in BigQuery. The rows stay in BigQuery; neocarta reads only their metadata (the foreign-key join paths) into a Neo4j connections graph, and the agent federates across the two.

neo4j-cypher-skill

Generates, optimizes, and validates Cypher 25 queries for Neo4j 2025.x and 2026.x.

Topics covered

Query writing — reads, writes, subqueries, batch operations, LOAD CSV, schema inspection, EXPLAIN/PROFILE validation
Patterns — MATCH, OPTIONAL MATCH, WITH, UNION, MERGE (constrained-key rules), FOREACH, UNWIND, CALL IN TRANSACTIONS
Subqueries — EXISTS {}, COUNT {}, COLLECT {}, CALL (x) { }, OPTIONAL CALL
Path expressions — Quantified Path Expressions (QPEs), match modes (DIFFERENT RELATIONSHIPS, REPEATABLE ELEMENTS), path selectors (SHORTEST 1, ALL SHORTEST)
Search — vector search (SEARCH clause 2026.01+, procedure fallback for 2025.x), fulltext (db.index.fulltext)
Schema — db.schema.visualization, SHOW INDEXES/CONSTRAINTS/PROCEDURES, apoc.meta.schema() (preferred when APOC available)

Cypher 技能使用指南

幻灯片原文
The Cypher skill covers query writing and optimization; it directs search combining vector with fulltext or other ranked sources to a separate skill. The speaker recommends the Neo4j CLI for loading current skills.

name: neo4j-cypher-skill

description: Generates, optimizes, and validates Cypher 25 queries for Neo4j 2025.x and 2026.x. Use when writing new Cypher queries, optimizing slow queries, graph pattern matching, vector or fulltext search, subqueries, or batch writes. Covers MATCH, MERGE, CREATE, WITH, RETURN, CALL, UNWIND, FOREACH, LOAD CSV, SEARCH, expressions, functions, indexes, and subqueries. Does NOT handle driver migration or API changes — use neo4j-migration-skill. Does NOT cover DB administration or server ops — use neo4j-cli-tools-skill.

compatibility: Neo4j >= 2025.01 (safe baseline); Cypher 25
version: 1.0.1

When to Use
• Writing, optimizing, or debugging Cypher queries
• Graph pattern matching, QPEs, variable-length paths
• Vector/fulltext search, subqueries, batch writes, LOAD CSV

When NOT to Use
• Driver migration/API changes → neo4j-migration-skill
• DB admin (users, config, backups) → neo4j-cli-tools-skill
• Hybrid search that combines vector with fulltext or other ranked sources → neo4j-vector-index-skill

GQL conformance note: LET, FINISH, FILTER, and INSERT are valid Cypher 25 clauses (introduced via GQL conformance, mostly in Neo4j 2025.06). On older versions, fall back to WITH / (omit RETURN) / WHERE / CREATE. INSERT requires &-separated multi-labels and does not support dynamic labels/types.

The Outline Shape

AutoFix has a library of documents - service manuals, technical bulletins, and recall notices - and your agent needs to find its way around them.

The reflex move is to chunk every document, embed the chunks, and search by similarity. That hands the agent a slice that reads like the query. URI 承载层级结构

幻灯片原文
Each node’s URI follows the containment tree from library to folder, file and section. A subtree can be selected by its string prefix, while child URI pointers let the agent retrieve only the sections it needs.

URIs carry the hierarchy

Every node has a uri - a hierarchical slug that encodes its place in the tree:

technical-library
technical-library/bulletins
technical-library/bulletins/tsb-20-501.pdf
technical-library/bulletins/tsb-20-501.pdf#condition
technical-library/manuals/man-falcon-engine.pdf#misfire-diagnosis

Because URIs sort hierarchically, any subtree is a string prefix - scoping anything to the bulletins is STARTS WITH 'technical-library/bulletins'. Section fragments carry the full heading path, so a URI is always copy-pasteable back into any tool.

One more rule: a section’s content holds only its own body text, followed by uri: pointer lines for its children. Wherever the agent sees a uri: line, deeper content exists - one more lookup away, never duplicated upward. The outline shows the shape; the agent pulls the text only for the sections it actually needs.

湖仓上的 AI：上下文是以形状出现的，而不是查询

一个维修副驾驶需要的不只是匹配的段落和合法的 SQL。数据仓库连接、可导航的文档和链接社区，为它提供了拼装问题所需上下文的不同方式。

具备基础 SQL、Python 和命令行知识有助于完成练习；文中会在出现时介绍图的概念。

01

维修历史和手册只是开始

一个汽修 copilot 能检索到正确的记录，却照样给出错误答案。它的数据仓库里存着结构化的维修历史，文档库里则是维修手册、安全通告和召回通知。Text-to-SQL 和向量搜索让智能体能访问这些数据源，但能访问不等于能看清它需要的关联。

以 Autofix 为例。这是一家虚构的全国连锁维修企业，贯穿整场工作坊。一位技师的工位上停着一辆车，他需要知道怎么修。管理层希望用 copilot 辅助这项工作，AI 工程师就得把技术资料库和已完成的维修历史连起来。演示用的是云端存储的文档和 BigQuery，这套模式也计划推广到 Databricks 和 Snowflake。相似的表和文档越来越多时，即使每次检索调用都没出错，相关上下文也可能被漏掉。

更难的问题关乎整个业务：哪些进厂车辆缺少文档？哪些文档从来没人用？哪些维修反复失败？哪些召回会反复聚成一类？相似度搜索返回的是和查询相像的东西；要找出缺失的关联，得检查覆盖范围和彼此的关系。哪怕一个看似普通的数仓问题，也可能取决于能否在众多长得差不多的表之间选对 join。

智能体拿到的上下文，应该和它要回答的问题对得上。 工作坊介绍了三种形态（shape）：

| 形态 | 提供的上下文 | 适合回答的问题 | |---|---|---| | Table of Contents（目录） | 层级结构和文档交叉链接 | 接下来该读什么？ | | Themes（主题） | 从相互链接中推断出的分组 | 整个资料库里有哪些规律？ | | Connections（关联） | 数仓元数据和 join 路径 | 这些记录之间是什么关系？ |

实现从 Connections 开始，然后搭建文档导航和 Themes。

02

一个图谱、一个智能体和一个可运行的工作区

底层模型是属性图（property graph）。节点代表人、车之类的实体；关系代表实体之间的关联，比如某人拥有或驾驶某辆车。节点和关系都可以带属性，包括字符串、数字、日期和向量。Blumenfeld 把这种相连的结构比作预先 join 好的表：关系一旦建立，查询就可以顺着关系走，不必每次从头重建关联。

GraphAcademy 工作坊把练习分成十七节课。跟着做的步骤如下：

1. 登录，报名课程，打开其中的 Environment 一课。 2. 在自己的账号里启动预先配置好的 GitHub Codespace。也可以用仓库里的 Bash 安装脚本克隆到本地，但要先装好本地依赖，包括 Claude Code。 3. 等初始化完成，然后在环境变量文件里填入 Anthropic 访问凭证、BigQuery 凭证，以及分配给你个人的 Neo4j sandbox 凭证。 4. 启动 Claude Code。演示中，Claude Code 有时不认 API key，反而要求订阅，新开一个终端就能解决。接受已配置好的 MCP server，然后让智能体检查一下 Neo4j 连接。

Blumenfeld 的图里已经有上一次运行留下的数据；新参与者的 sandbox 一开始是空的。

编码流程用 Neo4j CLI 执行数据库查询，用一个 Cypher skill 指导查询编写，后面的算法则用 Graph Data Science skill。参与者不用手写每条查询，而是把想要的输出写成规格说明交给智能体。

仓库把这些职责分开：.claude 里放 skill；outline、search 和 themes 脚本里留着待实现的占位代码；一个小小的 Python SQL runner 负责调用 BigQuery；Markdown 规格说明描述要求的输出。生成的查询跑不通时，可以用参考答案脚本兜底。仓库里还有数据加载材料、用来对比 Genie 和 AI Search 的 Databricks 指引、源 PDF，以及一份可读的 Markdown 语料。本地也可以改用 Cursor，不过 Blumenfeld 没用它测过这个工作坊。

03

Connections：用图谱选择 SQL

数仓 schema 以工单为中心，车辆、故障诊断码（DTC）、维修流程、工单配件和配件通过主键、外键相连。第一项任务是让智能体看懂这些关系。NeoCarta 是 Neo4j Labs 的项目，它把数仓元数据表示成图。它也能表示业务术语和流程，不过工作坊没用到这些扩展。

Blumenfeld 区分了两个概念：本体（ontology）帮助解读数据、对数据做推理；语义层（semantic layer）提供一套约定好的术语，让人能准确地查询数据。另有一种虚拟图方案，可以通过联邦式 Cypher 接口暴露 SQL 数据；这个练习则用一个 MCP 导入操作来构建元数据图。按工作坊的说法，这次加载会生成六张表和五条参考 join 路径。层级从数据库到 schema、到表、再到列，还可以附带代表性取值。

第一个问题很具体：零件 IC2042 装到了哪辆车上？智能体通过 MCP 读取 NeoCarta 元数据，找出相关的 join 路径，再用 Python runner 查询 BigQuery。图负责指引数仓查询，并不把整个数仓复制一遍。 元数据旁边可以附带代表性取值，但维修记录仍留在 BigQuery，答案由 SQL 取回。

回顾环境搭建时，有个细节对跟着做的人很重要：如果没有 .env，或者工作区里只有 .env.example，可能说明初始化还没跑完。安装脚本是异步生成这些文件的。每位参与者都要用自己的 sandbox 凭证，再加上共享的服务凭证。查询完成后，筛选和 join 都由智能体发起的 Python SQL 调用完成，展示出的答案按品牌分组并列出车辆数。演示里的 join 路径来自 BigQuery 的主键/外键元数据；NeoCarta 也可以用查询日志，或者手动提供的 join、术语和指标。

04

什么时候元数据就够了——什么时候要导入记录

图既能改进执行，也能改进智能体对 schema 的理解。供应链里的最短路径和变长遍历属于前一种用法。从数百张候选表里挑出一条短的 join 路径属于后一种：最终的 SQL 也许很简单，难的是找到正确的关系。NeoCarta 解决的正是这个发现问题，同时保留现有的数仓访问方式。Neo4j Virtual Graph 在录像中提到时还是预览功能，它通过 Cypher 下推把图接口下沉到查询执行层。演讲还提到了相关的上下文图（context graph）工作，但不在这次实现之内。

为什么不把交易数据直接复制到 Neo4j？要看复制能换来什么：

- 记录留在数仓： 持续更新的数据集需要同步，选择性复制可能要写定制 ETL，安全策略也可能不允许把敏感记录搬到另一个系统。 - 把记录导入图来跑图计算： 大规模递归 join、图算法、图嵌入和聚类，都可能值得用原生图存储。非结构化文档也能受益，前提是导入过程给了它们有用的结构。

元数据图本身会持久保存。启动 NeoCarta 不会重建它：build-connections 脚本显式调用导入，之后的查询复用已存好的元数据。Blumenfeld 认为加载是幂等的，但没有重跑一遍来演示。

Cypher skill 由内部维护，和智能体记忆、云基础设施、语言驱动等 skill 一起发布。它的作用是提供最新的查询指导，免得智能体照搬网上的旧示例。Blumenfeld 没讲 SKILL.md 具体是怎么写出来的；dev container 的安装文件里可以看到 CLI 和 skill 装在哪里。

有人问到 bronze、silver、gold 数据分层，得到的是路线图层面的回答，没有额外演示。NeoCarta 由客户需求驱动；工作坊举办时，Databricks 连接器正在开发，正在讨论的扩展方向包括 metric view 和文档支持。

05

目录：保留文档已有的结构

文档这边是模拟的维修手册、技术通告和召回通知，有 PDF 和 Markdown 两种格式。比如一份 ABS 手册会引用资料库里别处的平台代码和故障诊断排查材料。这些引用本身就带着有用的结构。练习中，加载器读取本地文件，代替云端存储的文档集。

Table of Contents 形态让智能体能在这种结构里导航。Blumenfeld 拿 PageIndex 作类比，说明怎么阅读文档层级；工作坊并不依赖它。大纲从资料库开始，往下依次是文件夹、文档和章节，并包含指向其他文档的交叉链接。每个位置都有一个层级化 URI。智能体可以用 URI 取文本、查看某棵子树，或顺着引用跳到资料库的其他部分。和 Connections 不同，这种形态会把文档内容导入图中。

常见的 GraphRAG 导入流水线会抽取实体（比如车辆或零件），再把它们连到来源文本块上。这里的第一张图更轻量：一个确定性的解析器保留包含关系、章节顺序和已有的命名链接，类似 Obsidian 笔记库里的引用。超链接也能提供同类的跨文档关系。

文档结构统一、相互链接又多时，这种做法可以省掉一轮 LLM 抽取。加载器按幂等设计，层级会写进每个节点的 URI，从资料库、文件夹、文件一直到章节。查看加载好的图，可以看到工具要用的三种关系：用 HAS 表示包含，章节顺序，以及用 LINKS_TO 表示跨文档引用。

06

构建一个能在合适深度停下的大纲

outline 工具起初只是 Autofix skill 脚本里的一个查询占位符。一份 Markdown 规格说明描述了人类可读的输出形态和可选参数，智能体借助 Cypher skill 把它实现出来。核心操作是沿 HAS 做变长遍历；演示中的上限是 *0..25，遍历深度由脚本控制。另一条查询负责取回交叉链接。

包含关系的操作可以直接用 Cypher 写。给定一个根 URI，下面的查询会在演示的上限内返回根节点及其后代，以及各自的深度：

``cypher MATCH (root {uri: $rootUri}) MATCH path = (root)-[:HAS*0..25]->(node) RETURN node.uri AS uri, length(path) AS depth ORDER BY depth, uri; ``

长度为零的路径包含根节点本身。这是遍历的核心；完整的大纲还会排版层级，并附上单独取回的引用。

如果不给根 URI、也不限深度，脚本会返回整张图。工作坊的语料小，Blumenfeld 可以这么做，但对更大的文档集不建议这样。把深度设为 1 能得到浅层视图；传入 URI 则会换一个根。现场示例从 Falcon 2.0 文档开始，然后从一条链接里拿到线圈识别的 URI，再用它请求另一份大纲。上一步导航的输出，成了下一步的输入。

要确认智能体真的用了这些工具，就看它的工具调用历史，包括 NeoCarta 的 MCP 调用。让智能体描述自己的步骤适合教学，但生产环境的验证应该看执行日志。导入代码同样可以检查：对这些结构统一的文档，语料解析器用的是正则。更杂乱的数据源可能需要额外处理，比如用 GLiNER 抽取实体，或者用 LLM；但这两者都算不上完整的文档结构解析器。NeoCarta 的 MCP 端点、它的 CLI 以及 skill 这套做法，本身都不绑定特定模型。

07

让词汇对写查询的人保持有用

所有包含层级都用同一种 HAS 关系，变长查询就很简单。如果拆成 HAS_FOLDER、HAS_DOCUMENT、HAS_SECTION 等不同类型，就要处理更多情况。LINKS_TO 保持通用也是同样的道理。关系越具体，能表达的区分越丰富，但类型多到几百种时，人和智能体都更难管。在数仓那边，语义元数据起着类似的作用：把业务术语和物理 schema 对齐。

导航和搜索是互补的。全文或向量查询可以找到起点；大纲则能展示它的邻居和周围更大的结构。排查某样东西的缺失或覆盖缺口时，反复做相似度搜索可能漏掉关键文档。显式遍历提供了另一种查看文档集的方式，不要求每一步都和最初的问题相似。

工作坊也让有些实体保持隐式。智能体不必为每次提到的零件都建一个专门的零件节点，而是可以从文档里读出零件，再拿它去查数仓。Blumenfeld 认为，智能体能力变强后，这种做法在一些场景下变得可行。生命科学之类的领域可能仍然需要显式的分子和药物本体，因为关系必须精确，推断才站得住。怎么取舍，取决于领域需要什么样的语义；并没有一条普适的规定，要求导入时必须把所有东西都抽出来，或者什么都不抽。

08

搜索文本，再限定到一个子树

下一个占位符用 Neo4j 的 Lucene 全文索引实现搜索，不用向量搜索。索引覆盖带文本的文档节点和章节节点，不包括文件夹，返回带分数的匹配结果。每个匹配都带着层级化 URI，所以查询可以在全文检索之后再按子树过滤：只保留 URI 以指定前缀开头的节点。

语义扩展不需要 embedding 流水线，也能带来一定的词汇灵活性。如果用户说发动机在抖，智能体可以把这个描述扩展成 misfire（缺火）、rough idle（怠速不稳）之类的词，再用 Lucene 的 OR 组合起来。演示还只在召回通知里搜索线圈。URI 里编码的包含信息足以限定结果范围，不需要额外的图遍历。

完整的可调用过程是 db.index.fulltext.queryNodes()。下面的 Cypher 展示了先搜索、再过滤的顺序，配置好的索引名、Lucene 表达式、URI 范围和结果数量上限都以参数传入：

``cypher CALL db.index.fulltext.queryNodes($indexName, $lucene) YIELD node, score WHERE node.uri STARTS WITH $scopeUri RETURN node.uri AS uri, score ORDER BY score DESC LIMIT $limit; ``

在症状那个例子里，$lucene 可以是 misfire OR "rough idle"。只在召回通知里搜线圈时，它装的是线圈查询，$scopeUri 则指向召回通知所在的子树。前缀条件只过滤返回的节点，并不会把全文索引变成那个文件夹专用的索引。

09

名称、新鲜度和引用都是检索质量的一部分

智能体可以帮忙建缺失的全文索引，但索引怎么建，仍然要有合理的约定。Neo4j 支持对多个标签和属性建索引，这种灵活性也带来了一些智能体可能理解错的选择。Blumenfeld 觉得工作坊的索引可能是他用智能体生成的，但记不清这一步了。

文档名很重要，因为大纲先展示名字，再展示内容。标题起得差，智能体判断往哪里导航的依据就少；搜索可以深入文档内部来弥补。内容过时或走样是另一个问题。Blumenfeld 提议可以加上最后更新时间或权威性之类的元数据，并强调链接别名要有描述性：别名说明了一份文档为什么指向别处。缺少这类描述信息时，导入阶段用 LLM 补充会有帮助。

来源不变时，确定性加载能重建出同一张文档图。增量更新也做得到，但文档不是孤立的：给它改名会改变它的 URI，而其他文档可能正引用这个 URI。所以部分同步不能只替换一个节点，而要更新或清理受影响的子树，并处理指向它的链接。

观众问到能否有选择地应用 PageIndex，由此引出一个关于顺序的有用澄清：并没有必须先看大纲的规定。智能体可以先看大纲，再在有希望的区域里搜索；也可以先搜索，再顺着匹配文档的链接往下走。可选的练习材料会进一步讲 Cypher 细节，不过现场工作坊直接进入了 Themes。

10

主题：通过文档链接发现分组

只看 LINKS_TO 关系，又能看出另一种形态。维修手册、召回通知和技术通告彼此引用；一份指南可能是许多维修流程共同指向的目标。把视角拉远，就能看到一组组高度互连的文档。这些分组可能揭示资料库里从来没人显式标注过的主题。

工作坊用 Leiden 社区发现 给文档分组。目标类似 Microsoft GraphRAG 里全局与局部的区分，但这里的输入是已有的文档结构，而不是 LLM 抽取出来的实体图。Blumenfeld 把 Leiden 描述为 Louvain 的后继算法，运行更高效。Neo4j Graph Data Science 在相关子图的内存投影上运行它。他谈到的数百万乃至数十亿节点，指的是图分析的目标规模，并非工作坊实测；投影仍然需要足够的内存。

智能体拿到的不是图的可视化，而是每个分组的精简视图：

| 字段 | 含义 | |---|---| | Theme ID | 社区归属 | | 互连描述 | 按传导率（conductance）衡量和其他分组分得多开 | | 头部共同目标 | 组内共同引用的对象 | | 被链接最多的文档 | 下一步值得查看的核心文档 |

传导率把跨社区边界的连接和图内的连通性联系起来，可以支撑“紧密互连”“松散互连”这类描述。链接标签和文档标题让分组变得好理解：示例中出现了一个 BCM/总线簇，还有一个包含刹车盘、刹车片和液压管路的制动簇，都没有生成新的主题名。

实现同样从一份规格说明和一个占位符开始，这次在 themes.py 里。智能体用 Cypher 和 GDS skill 构建投影，脚本则通过 GDS 库调用 Leiden。投影之前，它利用 URI 结构把章节之间的引用折叠到各自所属的文档上。这样得到的是文档级的关系，生成的社区反映的是文档怎样聚在一起，不会把视图打散到一个个章节上。

Blumenfeld 报告，在模拟的工作坊语料上，默认 gamma=1 时得到 13 个分组，gamma=2 时得到 14 个主题。gamma 控制分辨率，可以把视图切得更细；合适的取值取决于语料。输出仍然沿用来源中的链接标签和文档名。返回的 URI 让智能体能从某个主题跳到大纲或限定范围的搜索，用来回答这类问题：哪些问题集中出现，哪里的文档太单薄，新材料该放在哪里。

11

社区描述、变化的数据与信任

Leiden 给出分组 ID；怎么描述这些分组是另一回事。工作坊展示的是来源元数据，不用生成标签，但依赖好的文档标题和链接名。也可以走 Microsoft GraphRAG 那种处理方式，加上实体抽取和分层的 LLM 摘要，代价是更多成本和延迟，生成的文本也可能每次不同。直接取自来源的描述没有生成带来的波动，但文档不变并不能保证 Leiden 每次分组都一样：可复现性还取决于随机性控制和执行设置。

数据会变的话，就重跑投影，并保留社区及其描述的快照。有了快照，应用就能观察分组随时间怎样演变。Blumenfeld 举了退单欺诈（chargeback fraud）和反洗钱分析的例子，它们是时序社区分析的成熟用法，反复聚类有助于发现不断变化的模式。

主题视图很大时，可以按社区规模或传导率过滤，但小社区也可能很重要。过滤视图也不等于验证了来源。确定性解析器信任已有的引用：错的链接还是错的，格式有问题的章节也可能原样进入图中。智能体遍历可以帮忙审查这类问题，但工作坊没有演示完整的清洗方案。

12

从一个诊断码到一条维修建议

预定义的形态不必覆盖所有可能的问题。Neo4j CLI 能获取 schema、执行自定义 Cypher，编码智能体需要以意料之外的方式关联信息时，可以自己写查询。Blumenfeld 说，配合 CLI 和持续维护的 skill，text-to-Cypher 的体验更好，但没有给出量化对比。现场的 CLI 练习做了删减，不过 schema 检查展示了智能体能拿到哪些信息。

第一个综合演示回到技师的问题：给定 VIN 和诊断码，类似的车之前是怎么修好的？业务目标是降低返修率（comeback ratio），也就是客户因为上次没修好又回来的比例。数仓里的历史记录了这些结果，维修手册、召回通知和技术通告则说明零件和维修流程。一个预先写好的领域 skill 暴露了 outline、search 和 themes 脚本，以及 SQL runner 和 NeoCarta MCP 访问。

答案靠几步操作拼起来：

1. 搜索诊断码和相关症状，包括 misfire 或 rough idle。 2. 找到相关的发动机手册，查看它链接的维修流程。 3. 取回数仓 join 路径。 4. 查询这辆车，以及涉及该诊断码和零件的同类工单。 5. 把维修历史和文档结合起来，建议把旧点火线圈换成改进版零件。

图提供从文档到维修流程的路径；数仓提供以往维修的实际结果。

Blumenfeld 拿向量检索作比较，着眼点在于穿过证据的路径。基于搜索的系统也能回答这个问题，但每个相关流程都要反复搜索，就多了几次机会检索到一段讲缺火、却针对另一个零件的内容。顺着手册里的显式链接走，智能体在回到数仓之前，走的路线更受约束。

13

找到资料库与现场之间的不匹配

主管的问题更宽：文档里的维修流程和现场问题一致吗？缺了哪些文档？哪些文档没人用？这需要把技术资料库和工单历史对照起来。单凭一条搜索结果，无法确定相关文档不存在；分析得先弄清两边各有什么。智能体在文档信息、诊断码和数仓查询之间来回，排查这些缺口。

在这个练习里，Blumenfeld 特意禁用了 Neo4j CLI，好让预定义的形态保持可见。如果不限制 CLI，智能体可能更倾向于写自定义 Cypher。预期的排查方式是拿现场故障码、维修选择和返修历史去对照资料库：反复修不好，可能说明没用上正确的流程；有文档却没有对应的现场记录，则是另一类覆盖问题。

现场的智能体没有按要求的路线走。它没用大纲，而是做了大量带语义扩展的全文搜索。Blumenfeld 报告发现了维修流程不匹配的情况，还有两个现场 DTC 码没有任何码级别的文档。层级化 URI 仍然帮它在搜索结果间导航，但演示没能展示预期的大纲遍历。Blumenfeld 认为多出来的耗时来自这些地毯式搜索，并说顺着显式链接走本可以少做些工作。工具摆在那儿，不代表智能体会选它。

14

主题覆盖，以及智能体仍需执行的关联

最后一个演示要找出技术通告和召回通知中的共同模式，以及每种模式影响多少辆车。智能体调用 Themes 找出分组，从数仓历史里取回修复记录，再把工单关联到相应的主题上。这样，资料库的主题结构就和实际业务活动连了起来。

有人问这些形态是什么时候定义的，由此引出设计顺序：先明确智能体应该拿到什么，再推导出生成它所需的查询，然后用这些查询指导数据建模。底层的文档图依旧是 HAS 包含树加交叉链接。最终答案用了 Themes 和 Connections，没有用搜索，按主题类型把车辆和工单归组，并给出百分比。

有人问知识库变大后准确率能否保持，Blumenfeld 说他没对这套实现做过基准测试。客户会在自己的数据集上，拿自己的本体和查询模式去和普通向量搜索等方案做评测。这些练习的作用是把机制搭起来，并展示现场运行时智能体做了哪些工具选择；评测准确率、改进 skill 里的路由指引，仍然要结合具体应用来做。

最后一个架构问题拿财务报表和 CEO 评论举例，作为结构化与非结构化数据源并存的另一个场景。在这个工作坊里，数仓元数据图和文档图之间没有显式的边相连。智能体从一个来源里抽出零件或诊断码，再拿去另一个来源查信息，跨来源的匹配在查询时完成。把链接存下来能让这种映射更确定。Blumenfeld 没这么做，是为了让最初的实现容易搭建，并且不绑定模型。

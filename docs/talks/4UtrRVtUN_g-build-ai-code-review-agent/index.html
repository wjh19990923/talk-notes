如何构建 AI 代码审查智能体

Daksh Gupta 讲解了“一个会在 PR 下发评论的沙箱”与“一个有用的审查者”之间的差距：有针对性的 bug 检测、基于历史数据的评测、写代码和审代码用不同的模型、代码库上下文、自主测试，以及有选择地投入推理成本。

代码库上下文、运行中的代码和按任务选择模型，共同支撑对 pull request 的审查与测试。

01

一个 webhook 能给你评论，验证则需要更多

When engineers—and increasingly their colleagues outside engineering—can generate code quickly, review becomes the bottleneck. Daksh Gupta, co-founder of Greptile, builds agents that review and test pull requests with codebase context. His starting point is practical: some companies have requirements specialized enough to justify building their own reviewer, and the first working version is surprisingly small.

Put a coding agent in a sandbox. Connect GitHub or GitLab so that opening a pull request sends its contents to the agent through a webhook. Give the agent a prompt asking for a review, then post its feedback through the review API. Codex or Claude Code can supply the agent; Gupta recommends a model-independent harness, a choice that becomes important when the reviewer needs to use a different model from the code’s author. In his sketch, the PR receives feedback about five minutes later.

That proves the plumbing works. It also exposes several different failures:

- Missed bugs: The agent produces comments without necessarily finding the defects most likely to cause an outage or incident. - Missing context: A change can depend on library behavior, architectural direction, or interactions across thousands of repositories. The PR contents alone do not explain those relationships. - High inference costs: Gupta reports seeing internal implementations spend between $3 and $25 per pull request. Repeated exploration and file reading can quietly accumulate substantial token bills. - Nitpicky comments: Technically correct but overly pedantic findings consume attention that should go to consequential problems. - An unstable stream of findings: Running the reviewer again on the same PR can reveal another batch of issues, making the review feel as though it will never finish.

Nitpicks have a second cost beyond annoying humans. Review comments often become instructions for another coding agent, which attempts to resolve all of them without deciding whether each requested change is worthwhile. A pedantic suggestion can therefore turn into another layer of defensive code. The causal chain matters: noisy review does not merely hide useful feedback; it can actively steer implementation toward unnecessary complexity.

02

告诉审查者哪些 bug 要紧——以及哪些别管

The cheapest improvement is to replace the generic review prompt with a more selective one. A request such as “Review this PR” and return comments in GitHub’s API format specifies the output shape, but says little about what deserves a comment. Gupta separates that missing guidance into two parallel instructions:

- Search for specific failure types. Examine previous outages and incidents, identify the kinds of mistakes the company repeatedly makes, and build a catalog. Ask the reviewer to look for those bug types rather than conducting an unrestricted search for anything questionable. - Define and exclude nitpicks. Explain which technically defensible objections are not useful review findings. Gupta’s examples include demanding three levels of defensive checks or objecting to slightly untidy error handling without establishing a consequential failure.

The difficulty is knowing whether a quieter prompt is better. A small wording change can produce a large change in comment volume. Fewer comments might mean the agent stopped being pedantic, or it might mean the agent stopped catching real bugs. A reviewer can demonstrate the presence of a defect; a clean review cannot establish the absence of defects. Because catastrophic failures are rare, an apparently successful prompt change can remain in production for a long time before a serious miss becomes visible.

03

重放那些引发事故的 pull request

Historical incident PRs give prompt tuning a more useful test than comment counts. Start with the company’s incident records, collect the pull requests responsible for those failures, and run each candidate version of the reviewer against them. The question becomes concrete: how often does this version catch the bugs already known to have caused trouble? That comparison lets a team reduce noise while checking whether it has also lost detection ability.

The dataset needs to keep changing. Gupta estimates that about 80–90% of bugs repeat prior mistakes, which makes historical cases valuable, but coding agents also develop new failure modes. An evaluation set that covers yesterday’s mistakes can miss tomorrow’s. Broad coverage is difficult for an individual company because rare bug types require a very large number of PRs to encounter.

This is one of the advantages Gupta attributes to Greptile’s cross-company corpus: it can test changes against a much wider range of pull requests than most internal tools can. Internal incident data still gets a company meaningfully far, particularly on its own recurring problems. The limitation is coverage, not the usefulness of replaying known failures.

04

用另一个模型来审查代码

Model independence now earns its place in the architecture. Gupta’s research found different error patterns in Claude and GPT models, including a greater tendency toward authentication bypasses in the GPT models he studied. His proposed explanation is that a model can carry similar blind spots into generation and review: the reasoning that failed to notice a problem while writing code may fail again while checking it.

The correction is model inversion. If Claude Code wrote the change, route the review to a GPT model; use the opposite direction for GPT-written code. Gupta reports a 10% higher bug catch rate when flipping models. The talk does not specify the experimental conditions or whether that means a relative increase or percentage-point gain, so the result supports trying and evaluating cross-model review—not calculating a corresponding reduction in production incidents.

The routing problem is identifying what wrote the PR. Gupta describes fingerprints such as a codex/ branch-name prefix or a Claude co-author attribution in PR or commit metadata. He estimates these clues cover about 80% of cases. Manually named branches and other exceptions make the rest harder. An internal catalog of coding-agent usage or telemetry from development machines can supply additional evidence, but the model’s identity is not always recoverable from the code submission alone.

05

认证类 bug 需要一张代码库地图

A reviewer can use a different model and still misunderstand the system it is reviewing. Greptile began as a codebase-context company, working on retrieval over large repositories. Gupta rejects the idea that grep alone solves that problem: imprecise search encourages the agent to read large quantities of files, then load their contents into model context. The expensive pattern is repeated search, file read, and cache write.

Greptile instead builds an internal knowledge base that catalogs the system’s parts. An authentication entry, for example, describes how authentication works, the flows involved, and the files that implement them. The entry helps the reviewer find the relevant code without reconstructing the entire subsystem through broad searches on every PR.

Authentication bypasses make the need for this context concrete. To decide whether a missing check is a bug, the reviewer needs to know whether execution has already entered an authenticated environment at that point in the codebase. A local code fragment does not necessarily answer that question. The flow and its surrounding files supply the relationship needed to distinguish a real bypass from a check that belongs elsewhere.

06

一个活的 wiki 把实现、行为和意图联系起来

Code can run correctly and still implement the wrong thing. Gupta uses the image of Slack becoming an IDE: someone sends a sentence or two asking an agent to fix something, but those sentences leave much of the intended behavior unstated. The agent may misinterpret the request or make an arbitrary choice where a human colleague would draw on shared knowledge.

Tickets and documentation supply some of that missing knowledge. Jira or Linear can carry the work’s intent; Confluence or Notion can explain the product and its conventions; the codebase index explains the implementation. Engineers often underestimate how much accumulated organizational knowledge helps them fill gaps in a short request. Giving the agent access to these sources makes more of that background available during review.

How do those sources help both review quality and search cost? Greptile places a living wiki between the context sources and the agent. The wiki combines knowledge of the codebase, application behavior from production telemetry and logs, and roadmap information from documentation and tickets. It supplies background for reasoning about a change and helps direct code searches toward relevant files.

The two outputs matter separately. Organizational context helps the reviewer assess whether the change fulfills its intended purpose. More precise retrieval reduces the amount of code it needs to read to make that assessment. Gupta describes the goal emphatically as never reading an unnecessary file; the supported mechanism is the wiki’s guidance about where to look, rather than a demonstrated guarantee of perfect retrieval.

07

渲染改动并测试用户流程

Reading React changes can leave the reviewer satisfied while the rendered interface is unusable on a phone. Gupta’s example is a button that technically appears in the application but is hidden on an iPhone or falls outside the initial visible area. Static review examines the implementation; running the application exposes the result the user actually encounters.

Greptile runs the customer’s stack in dependency-rich, configurable virtual machines and uses a computer-use agent to test it end to end. Two prerequisites make that possible:

- Documented application flows: The agent needs a map of behaviors to exercise, such as authentication and sign-up. - A reproducible development environment: A sufficiently simple build script must start the stack with its required dependencies. Gupta describes helping customers prepare this environment as one of the trickier implementation tasks.

How do the environment and flow map fit together? The setup Gupta describes has a dev box running the PR branch with its dependencies, plus a flow map that tells the agent what paths to test. The running app supplies something the agent can operate; the map supplies the behaviors it should exercise. Vision models can then assess the rendered result, including the phone-layout problem that reading the changed files did not reveal.

The useful change is from a judgment about source code to an observation about behavior: a button can exist in the implementation yet remain inaccessible in the rendered interface. Gupta is optimistic enough to call end-to-end QA nearly solved by improved computer use, but that is his assessment, not a coverage result established here. Even in this approach, documented flows and a working environment remain necessary inputs.

08

把前沿推理花在需要它的决策上

A context-aware agent that also runs the application can still be expensive. After describing autonomous testing, Gupta again puts a review in the range of several dollars to roughly $20. The next optimization is to stop assigning every subtask to a frontier model. He reports that frontier models account for about 20% of Greptile’s mix at the time of the talk, reserved for the most critical work, while smaller models handle much of the exploratory activity and file reading.

Where can a cheaper model take over without replacing the most consequential reasoning? Gupta’s illustrative split separates the jobs:

- Finding context: A small model locates useful information. - Testing user flows: A lightweight computer-use model operates the application. - Analyzing and submitting the review: A frontier model handles bug analysis, the review process, and submission.

The distinction is task-specific: finding a file and deciding whether a change contains a serious bug do not automatically need the same model or inference budget.

Greptile’s actual implementation divides the work into 20 subtasks, each with a specific set of models, and a small research team continually revisits those assignments. An internal implementation need not begin with that degree of specialization. Gupta suggests getting much of the benefit by replacing simple tasks with simple models first.

This brings the historical PR dataset back into the design. A smaller model can make a subtask faster and cheaper while quietly reducing the final reviewer’s ability to catch bugs. Without known failure cases to replay, the cost improvement is immediately visible and the quality regression may remain hidden until an outage. Model routing therefore needs evaluation of the resulting review quality, not just a lower token bill.

The final optimization targets what enters the frontier model’s context at all. A cheap model can inspect candidate context pieces and choose which ones to include. Gupta also proposes using a decision model to rerank those pieces before loading them into the frontier model’s cache. This is a proposed allocation mechanism: spend inexpensive inference selecting information so that the more expensive model reads less irrelevant material. In his framing, frontier-model cache is one of the system’s most expensive and scarce resources.

That leaves a concrete build-or-buy decision. A company with unusually specialized needs can build around its own incident history, application flows, and organizational context, but it also takes on environment setup, dataset maintenance, and model-selection work. Gupta closes by offering help to teams that choose to build. The small webhook prototype remains a useful beginning; the ongoing work is making its findings worth acting on at a cost the company can sustain.

要点总结

  • 定义值得抓的 bug 类型和值得压制的吹毛求疵。低价值的评论会浪费人的注意力，还会让编程智能体加入不必要的防御性代码。
  • 对照历史上的事故 PR 评估审查器的修改，并不断补充新的失败模式。评论更少或推理更便宜，并不能证明审查器仍能抓住重要的 bug。
  • 当你能识别出某次修改是由哪个模型写的时，试着用另一个模型家族来审查它。Greptile 报告这种做法让 bug 捕获率提高了约 10%。演讲没有说明测试样本和基线捕获率。
  • 代码库流程有助于发现认证绕过这类依赖上下文的 bug；文档、工单、日志和遥测有助于把实现与预期行为和观测到的行为联系起来。
  • 自主 UI 测试既需要一个运行中的 PR 环境，也需要有文档记录的流程。更小的模型可以负责上下文选择和操作应用，前沿模型则专注于有后果的审查决策。
  • The Death of the Code Review: What the Data Actually Says — Laurie Voss, Arize AI —— 在审查瓶颈的讨论上更进一步，涉及误报过滤、多轮审查、组织层面的质量标准，以及对审查者本身的评估。
  • Why AI Didn't Actually Make You Ship Faster — Gabriel Spencer-Harper, Meticulous —— 提供了运行时验证的互补方法：重放浏览器工作流并比较视觉变化，并有明确的可重复性和测试选择机制。
  • Evals for High-Stakes AI Agents — Doneyli De Jesus & Annabell Schäfer, Langfuse —— 展开讲解安全修改提示词和模型背后的评估工作，包括有代表性的数据集、专家标注、实验和质量关卡。

五种多智能体策略

幻灯片原文
Direct communication connects agents peer-to-peer without a coordinator, risking fragmented state. Broadcast sends shared updates from one agent to many to maintain coherence.

AGENT TEAMS
Five multi-agent strategies

Delegation
One agent spawns another for a subtask. The simplest multi-agent pattern.

Creator-Verifier
One agent builds, a different agent checks. Separation of concerns removes sunk-cost bias.

Direct Communication
Agents talking peer-to-peer without a coordinator. Hard to get right: state fragments.

Negotiation
Two agents coordinate over shared resources. Best when there's a possible win-win.

Broadcast
One agent sends status updates and shared context to many. Critical for coherence.

真正能交付的多智能体架构

Luke Alvoeiro 讲解了 Factory 的 Missions 如何结合事先约定的验证契约、专门的智能体角色、结构化的交接和严格限制的并行度，在数小时乃至数天内执行软件项目。

真正能交付的多智能体架构

01

真正的瓶颈是人的注意力

Luke Alvoeiro 认为，现代软件开发的瓶颈在于人的注意力，而不只是模型够不够聪明。工程师手上可能有几十个想做的功能，真正能推进的却只有寥寥几个。写实现、盯进度、审代码，样样都在抢他们的时间。架构上要回答的问题是：能不能让人只说清楚要做什么，由智能体系统长时间自主决定怎么做。0:15 1:17

多智能体系统的做法五花八门，Alvoeiro 把它们归纳成五种交互模式。委派：一个智能体把活儿分给另一个；创建者-验证者：实现和独立审查分开；直接通信：智能体之间不经中央协调者直接交流；协商：协调共享资源的使用；广播：把信息或约束同步给整个群体。每种模式解决的是不同的协调问题。1:17 2:22 3:23

这些模式各有取舍。直接通信缺少协调者来维护唯一可信的状态，状态容易四分五裂；协商则能让各方互利协作，而不是彼此对抗。Factory 的 Missions 把委派、创建者-验证者、协商和广播组合成一套工作流：人先讨论范围、批准计划，再交给系统长时间执行。2:22 3:23

- 人的注意力限制了软件交付：盯实现、审提交，各项任务都在抢同一份精力。 - 五种协调模式各管一类需求：委派、创建者-验证者、直接通信、协商和广播。 - 直接通信容易让共享状态四分五裂；广播则把更新和约束同步给所有智能体。 - 人先划定范围、批准计划，Missions 再组合委派、创建者-验证者、协商和广播来执行。

02

三种角色把一项任务变成一次受管理的行动

一次 mission 并不是一段从头到尾不中断的智能体对话，而是一个智能体生态。各个智能体靠共享状态和结构化交接连在一起，分成三种角色：编排者、工作者和验证者。编排者负责澄清需求、提出关键问题，然后产出一份计划，里面包括功能、里程碑和验证契约。这份契约在动手实现之前就规定好什么才算完成。4:27

工作者每次带着干净的上下文实现单个功能。它不必背着一场漫长会话攒下的历史，注意力也不会因此涣散。每个工作者读取自己的规格说明，完成改动，再通过 Git 提交。下一个工作者从一份能跑的代码库接手，不用继承上一个智能体的全部对话包袱。4:27

验证者始终和写代码的智能体分开。除了常规的 lint、类型检查、测试和代码审查，它们还要确认软件端到端是否真的能用。这样分工，一是避免负责实现的智能体给自己的决策打分时带着偏见，二是防止长时间运行的 mission 慢慢偏离预期行为。2:22 5:34

- 编码开始前，编排者先澄清需求，定好功能、里程碑和验证契约。 - 工作者带着干净的上下文实现分到的规格，通过 Git 提交，留给后续工作者接手。 - 独立的验证者既做常规检查，也验证端到端的实际行为。 - 实现和验证分开，能减少沉没成本偏差，保证审查的独立性。

三角色执行 mission 先在规划阶段定义正确性，再实现，再独立验证。 - 编排者 — 澄清需求，制定 mission 计划。 - 验证契约 — 编码开始前定义何为完成。 - 工作者 — 以干净的上下文实现功能，并通过 Git 提交。 - 验证者 — 检查代码质量和端到端行为。 - 编排者 → 验证契约（制定） - 验证契约 → 工作者（先于实现） - 工作者 → 验证者（先实现，后验证）

03

在写代码之前先定义正确性

最核心的保障是验证契约。它在规划阶段就写好，那时还没有任何实现。Alvoeiro 认为，代码写完再补测试，测试往往只会照着实现里已有的选择去写，没法独立检验代码本该达成的目的。先把“什么算正确”定下来，后面的验证者手里就有了一把尺子，而这把尺子不是从被检查的代码里来的。5:34

复杂项目可能需要几百条断言：每个功能分到一条或多条，所有功能合起来覆盖整份契约。每到一个里程碑，审查验证者会跑测试套件、类型检查和 lint，并调用专门的代码审查智能体检查已完成的功能。另一个用户测试验证者则启动应用，实际走一遍流程：填表单、看页面渲染、点按钮，检验应用的各种行为。6:42

行为验证代价不小：和运行中的应用交互，比常规审查慢得多。Alvoeiro 提到，一次 mission 的实际耗时里，很大一部分花在等待真实环境执行上，而不是生成 token。换来的好处是独立、带对抗性的验证：做验证的智能体之前没见过这份实现，也没有替它辩护的动机。7:38

工作没通过验证时，系统靠的是结构化交接，而不是智能体的记忆。工作者会记下：做完了什么、还剩什么、执行过哪些命令和对应的退出码、发现了哪些问题，以及是否遵守了编排者规定的流程。这样一来，每个里程碑节点都成了纠错的机会：找出错误，划定修复用的功能，把执行拉回原计划。7:38 8:43

- 验证契约在实现之前定义正确性，并把断言分配到所有计划中的功能上。 - 审查验证者跑测试、类型检查、lint 和专门的代码审查；用户测试验证者在运行中的应用上实际走流程。 - 实时行为验证比常规审查慢，可能占掉 mission 的大部分实际耗时。 - 结构化交接记录已完成的工作、遗留问题、执行的命令、退出码和流程遵守情况，为修复工作提供依据。

里程碑验证与纠错循环 独立的里程碑检查暴露问题、划定修复工作，让执行回到 mission 的正轨。 - 功能实现 — 工作朝着里程碑断言推进。 - 结构化交接 — 记录结果、命令、退出码和问题。 - 里程碑验证 — 审查加实时用户测试，检查已完成的工作。 - 修复工作 — 发现的问题变成范围明确的后续工作。 - 功能实现 → 结构化交接（工作者记录结果） - 结构化交接 → 里程碑验证（在里程碑处复查记录的问题） - 里程碑验证 → 修复工作（为发现的错误划定范围） - 修复工作 → 功能实现（修复后恢复推进）

04

串行化代码修改，并行化安全的调研

Alvoeiro 质疑一个常见假设：同时跑的智能体越多，软件交付就越快。Factory 发现，多个智能体并发写代码时，会互相覆盖或冲突彼此的改动，重复干活，还会做出互不兼容的架构决策。这种情况下，协调开销吃掉了预期的提速，token 花费也跟着涨。8:43

所以 Missions 串行执行功能，同一时刻只有一个工作者或验证者在干活。并行只留给功能或验证步骤内部的只读操作，比如搜索代码库、调研 API、做独立的代码审查。按简化的吞吐量公式算，这样看起来更慢；但 Alvoeiro 认为，在持续好多天的任务里，少犯错的优势会不断累积。9:50

长时间的自主执行，光看普通的聊天记录很难看明白。于是 Factory 专门做了一个运行视图 Mission Control。它展示项目进度、预算消耗、当前在干活的工作者，以及交接摘要，摘要里写着有哪些新发现、做过哪些纠偏。人既可以实时盯着，也可以异步监督，不必守着每一步实现。9:50 10:45

这套架构已经证明能跑很久，但它的边界也说得很清楚。Alvoeiro 说，Factory 跑得最久的一次 mission 持续了 16 天，他相信将来能做到 30 天——后者只是预期，不是实测结果。他还坦言，怎样进一步并行化工作负载、怎样在多个 mission 之间做编排，都还没有答案。8:43 16:49

- 多个智能体并发写代码，会互相冲突、重复干活，做出不一致的架构决策。 - Missions 同一时刻只运行一个工作者或验证者，只把代码搜索、API 调研和代码审查这类只读操作并行化。 - Mission Control 展示项目进度、预算消耗、当前工作和交接摘要，方便异步监督。 - 目前最长的一次 mission 跑了 16 天；30 天仍只是预期，更大范围的并行化也还没解决。

05

让模型匹配角色，并保持编排的可调整性

三种角色对底层模型的要求各不相同：规划要推理缜密，实现要写代码快、有创造力，验证要精准遵循指令。在这些能力之间挑选模型，正在成为一门新的实操技能，Alvoeiro 称之为 Droid whispering（“驯 Droid”）：摸清不同模型的脾性，知道它们会在哪里翻车，以及这些失误在持续多天的工作流里会怎样相互叠加。10:45 11:42

与模型无关的架构让不同角色可以用不同的模型或提供商。比如验证环节换一家提供商，降低模型之间偏见雷同的风险。反过来，验证契约和里程碑检查点也能弥补单个模型能力的不足。Alvoeiro 说，正因如此，就算用开放权重模型，mission 也能跑成功。他的意思并不是哪个模型都一样好用，而是系统结构加上有意识的角色分配，能让整体更可靠。11:42 12:45

Alvoeiro 举了一个仿制 Slack 的例子：实现阶段占了 60% 的时间和 60% 的 token，第一次验证没通过，还得追加功能来修补。最终的代码库里，大约 50% 的代码行是测试，这些测试覆盖了 90% 的代码；为了压低长时间运行的成本，他们用上了 prompt caching。这些数字只代表这一个示例，不保证每次 mission 都能做到。12:45

为了不让模型一升级架构就过时，Factory 把大部分编排逻辑放进提示词和技能（skills），而不是写死成一个僵硬的状态机。Alvoeiro 介绍，大约 700 行文本规定了怎样拆分功能、怎样处理失败；另有针对具体 mission 的工作者技能；再加上一层很薄的确定性逻辑，负责记账、验证，并在交接问题没解决时卡住进度。分工很简单：系统负责执行上的纪律，模型负责灵活的智能。14:34 15:04 回到开头说的注意力瓶颈，Alvoeiro 认为，有了 Missions，团队可以专心做架构和产品决策，执行交给系统。他还说，一路积累下来的端到端测试、单元测试、技能和项目结构，会让代码库比开始时更整洁，之后无论人还是智能体，干活都更高效。15:51 16:17

- 按角色选模型：规划看重缜密推理，实现看重编码熟练度和创造力，验证看重精准遵循指令。 - 与模型无关的编排允许验证环节换用其他提供商；契约和检查点能让开放权重模型也跑出好结果。 - 在仿制 Slack 的例子里，实现阶段消耗了 60% 的时间和 token；测试占代码的 50%，覆盖了 90% 的代码库。 - 提示词和针对具体 mission 的技能负责编排，一层很薄的确定性逻辑负责记账、验证，并拦住交接中未解决的问题。

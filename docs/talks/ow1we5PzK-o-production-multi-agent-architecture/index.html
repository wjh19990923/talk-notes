Five multi-agent strategies

幻灯片原文
Direct communication connects agents peer-to-peer without a coordinator, risking fragmented state. Broadcast sends shared updates from one agent to many to maintain coherence.

[1:48](https://www.youtube.com/watch?v=ow1we5PzK-o&t=108s) [Five cards describe delegation, creator-verifier, direct communication, negotiation, and broadcast.](https://assets.ai.engineer/sites/aiecode2025/sha256/1248fbd14784a10e7fd2f4aa4a574f7d5daad344527da26e91140110c6c66c65.webp)

AGENT TEAMS
Five multi-agent strategies

Delegation
One agent spawns another for a subtask. The simplest multi-agent pattern.

Creator-Verifier
One agent builds, a different agent checks. Separation of concerns removes sunk-cost bias.

Direct Communication
Agents talking peer-to-peer without a coordinator. Hard to get right: state fragments.

Negotiation
Two agents coordinate over shared resources. Best when there's a possible win-win.

Broadcast
One agent sends status updates and shared context to many. Critical for coherence.

The validation loop

幻灯片原文
Before coding, the orchestrator defines correctness in a validation contract. After each milestone, one validator checks code and tests while another exercises the live app; neither has seen the code before.

[6:56](https://www.youtube.com/watch?v=ow1we5PzK-o&t=416s) [A planning-stage validation contract is followed by scrutiny and user-testing validators after each milestone.](https://assets.ai.engineer/sites/aiecode2025/sha256/8589eeb5a54e832a811606fb762e6dd239232f61a21dbd20536914695c9efefc.webp)

HOW THEY WORK
The validation loop
Tests written after implementation don't catch bugs. They confirm decisions.

PLANNING PHASE
Validation Contract
Written by orchestrator during planning, before any code. Hundreds of assertions define correctness independently of implementation.

After each milestone...

</>
Scrutiny Validator
Runs tests, typechecking, linting. Spawns code review agents for each completed feature.

</>
User-Testing Validator
Acts like a QA engineer. Launches the app, navigates via computer-use & verifies flows end-to-end.

Neither validator has ever seen the code. Validation is adversarial by design.

The right model in each role

幻灯片原文
Missions can use different models for planning, implementation, and validation. A separate validation provider may reduce shared training-data bias, while model-agnostic design lets each role use a specialized model.

[12:24](https://www.youtube.com/watch?v=ow1we5PzK-o&t=744s) [Three panels describe model roles, followed by a conclusion about model-agnostic architecture.](https://assets.ai.engineer/sites/aiecode2025/sha256/f1200cff5a721699c9c8c7b67e929d892c0633f59b8e62c73cf67b8fe86289df.webp)

USING MISSIONS

The right model in each role

No single model is best at planning, implementation, and validation.

PLANNING
Slow, careful reasoning.
Strategic questions, constraint analysis.

IMPLEMENTATION
Code fluency and creativity.
Fast generation, tool use.

VALIDATION
Strict instruction following.
Different provider avoids training-data bias.

Model-agnostic architecture = compounding advantage as models specialize

You're only as strong as your weakest link. If locked into one model family, you're constrained by that family's weakest capability.

真正能交付的多智能体架构

Luke Alvoeiro 讲解了 Factory 的 Missions 如何结合事先约定的验证契约、专门的智能体角色、结构化的交接和严格限制的并行度，在数小时乃至数天内执行软件项目。

真正能交付的多智能体架构

01

真正的瓶颈是人的注意力

Luke Alvoeiro frames modern software development as a problem of human attention, not simply model intelligence. Engineers may face dozens of potential features but can advance only a handful because implementation, supervision, and review all compete for their time. The architectural question is whether a person can specify what should be built while an agent system determines how to execute it over extended periods. 0:15 1:17

To organize the fragmented landscape of multi-agent systems, Alvoeiro identifies five interaction patterns. Delegation lets one agent assign work to another; creator-verifier separates implementation from independent review; direct communication enables agent-to-agent exchanges without a central coordinator; negotiation coordinates access to shared resources; and broadcast distributes information or constraints across a group. Each pattern addresses a different coordination problem. 1:17 2:22 3:23

These patterns carry different tradeoffs. Direct communication can fragment state when no coordinator maintains a single source of truth, while negotiation can produce mutually beneficial coordination rather than adversarial competition. Factory’s Missions combines delegation, creator-verifier, negotiation, and broadcast into a workflow in which a person discusses scope, approves a plan, and then allows the system to handle extended execution. 2:22 3:23

- Human attention limits software delivery because implementation supervision and commit review compete across tasks. - Five coordination patterns address distinct needs: delegation, creator-verifier, direct communication, negotiation, and broadcast. - Direct communication can fragment shared state, while broadcast distributes updates and constraints across agents. - Missions combines delegation, creator-verifier, negotiation, and broadcast after a human scopes and approves the plan.

02

三种角色把一项任务变成一次受管理的行动

A mission is not one uninterrupted agent conversation. It is an ecosystem of agents linked by shared state and structured handoffs, with three distinct roles: orchestrator, worker, and validator. The orchestrator clarifies requirements, asks strategic questions, and produces a plan containing features, milestones, and a validation contract that establishes what completion means before implementation begins. 4:27

Workers implement individual features with clean context rather than carrying the accumulated history and degraded attention of a single prolonged session. Each worker reads its specification, makes the required changes, and commits through Git, allowing the next worker to begin from a working codebase without inheriting the previous agent’s full conversational baggage. 4:27

Validators remain separate from the agents that created the implementation. Beyond conventional linting, type checking, testing, and code review, they examine whether the software actually works end to end. This separation is designed to reduce the bias of an implementation agent evaluating its own decisions and to prevent a long-running mission from drifting away from its intended behavior. 2:22 5:34

- Orchestrators clarify requirements and define features, milestones, and a validation contract before coding begins. - Workers implement assigned specifications with clean context and commit through Git for subsequent workers. - Independent validators combine conventional checks with end-to-end behavioral verification. - Separating implementation from verification reduces sunk-cost bias and preserves independent review.

Three-role mission execution Planning establishes correctness before implementation and independent verification. - Orchestrator — Clarifies requirements and creates the mission plan. - Validation contract — Defines completion before coding begins. - Worker — Implements features with clean context and Git commits. - Validator — Checks code quality and end-to-end behavior. - Orchestrator → Validation contract (defines) - Validation contract → Worker (precedes implementation) - Worker → Validator (implementation then verification)

03

在写代码之前先定义正确性

The central safeguard is the validation contract, written during planning before any implementation exists. Alvoeiro argues that tests written after code can mirror the choices already embedded in that implementation instead of independently checking its intended purpose. By specifying correctness first, the mission gives later validators a standard that does not originate from the code they are evaluating. 5:34

A complex project may require hundreds of assertions, with every feature assigned one or more assertions and the complete feature set collectively covering the contract. At each milestone, a scrutiny validator runs the test suite, type checks, linting, and dedicated code-review agents for completed features. A separate user testing validator launches the application and exercises practical flows by interacting with forms, rendered pages, buttons, and other application behavior. 6:42

Behavioral validation has a significant cost: interacting with a live application takes longer than conventional scrutiny, and Alvoeiro reports that much of a mission’s wall-clock time can be spent waiting for real-world execution rather than generating tokens. The benefit is independent, adversarial verification by agents that have not previously seen the implementation and are not invested in defending it. 7:38

When work fails validation, the system relies on structured handoffs rather than agent memory. Workers record completed and unfinished work, executed commands and their exit codes, discovered issues, and compliance with orchestrator-defined procedures. Milestone boundaries then become opportunities to identify errors, scope corrective features, and return execution to the original plan. 7:38 8:43

- Validation contracts define correctness before implementation and assign assertions across all planned features. - Scrutiny validators run tests, type checks, lint, and dedicated code reviews; user testing validators exercise live application flows. - Live behavioral validation is slower than scrutiny and can dominate mission wall-clock time. - Structured handoffs record completed work, outstanding issues, commands, exit codes, and procedural compliance to support corrective work.

Milestone validation and correction loop Independent milestone checks expose issues, scope corrective work, and restore alignment with the mission. - Feature implementation — Work progresses toward milestone assertions. - Structured handoff — Records outcomes, commands, exit codes, and issues. - Milestone validation — Scrutiny and live user testing inspect completed work. - Corrective work — Detected issues become scoped follow-up work. - Feature implementation → Structured handoff (worker records results) - Structured handoff → Milestone validation (documented issues reviewed at milestones) - Milestone validation → Corrective work (caught errors are scoped) - Corrective work → Feature implementation (corrective work restores progress)

04

串行化代码修改，并行化安全的调研

Alvoeiro challenges the assumption that adding more simultaneously active agents automatically increases software-delivery throughput. Factory found that concurrent implementation agents could overwrite or conflict with one another’s changes, duplicate work, and make incompatible architectural decisions. In that setting, coordination overhead consumed the expected speed gains while also increasing token expenditure. 8:43

Missions therefore executes features serially, with only one worker or validator active at a time. Parallelism is reserved for read-only operations inside a feature or validation step, such as searching a codebase, researching APIs, or conducting independent code reviews. Although this can appear slower in a simplified throughput calculation, Alvoeiro argues that fewer errors compound into an advantage across tasks lasting many days. 9:50

Because extended autonomous execution cannot be understood effectively through a conventional chat transcript alone, Factory built Mission Control as a dedicated operational view. It exposes project progress, budget consumption, the currently active worker, and handoff summaries describing discoveries and course corrections. The interface supports both active oversight and asynchronous supervision without requiring a human to monitor every implementation step. 9:50 10:45

The architecture has demonstrated extended duration, but its boundaries remain explicit. Alvoeiro says Factory’s longest mission ran for 16 days and expresses a belief that missions could reach 30 days; the latter is presented as an expectation, not an observed result. He also identifies greater workload parallelization and orchestration across multiple missions as unresolved questions. 8:43 16:49

- Concurrent implementation agents can conflict, duplicate work, and make inconsistent architectural decisions. - Missions runs one worker or validator at a time while parallelizing read-only code search, API research, and code review. - Mission Control tracks project progress, budget consumption, active work, and handoff summaries for asynchronous oversight. - The longest reported mission ran 16 days; 30-day missions remain an expectation, and broader parallelization remains unresolved.

05

让模型匹配角色，并保持编排的可调整性

The three roles impose different demands on underlying models. Planning benefits from careful reasoning, implementation from fast coding fluency and creativity, and validation from precise instruction following. Alvoeiro describes the emerging operational skill of choosing among these capabilities as Droid whispering: understanding how different models behave, where they fail, and how those failures interact across a multi-day workflow. 10:45 11:42

A model-agnostic architecture allows different models or providers to occupy different roles, including using a separate provider for validation to reduce the risk of shared biases. Conversely, validation contracts and milestone checkpoints can compensate for less capable individual models, which Alvoeiro says allows missions to run successfully even with open weight models. His argument is not that any model works equally well, but that system structure and deliberate role assignment can improve reliability. 11:42 12:45

In an example involving a Slack clone, Alvoeiro reports that implementation accounted for 60% of time and 60% of tokens, validation did not succeed on the first attempt, and follow-up features were needed. He also describes a final codebase in which approximately 50% of lines were tests and 90% of code was covered by those tests, with prompt caching used to mitigate the cost of long-running execution. These figures describe the presented example rather than a guaranteed outcome for every mission. 12:45

To avoid making the architecture obsolete when models improve, Factory places most orchestration behavior in prompts and skills rather than a rigid hard-coded state machine. Alvoeiro describes roughly 700 lines of text governing feature decomposition and failure handling, mission-specific worker skills, and a thin deterministic layer responsible for bookkeeping, validation, and blocking progress when handoff issues remain unresolved. The intended division is straightforward: the system supplies operational discipline while models supply adaptable intelligence. 14:34 15:04 Returning to the opening human-attention bottleneck, Alvoeiro argues that Missions lets teams focus on architecture and product decisions while the system manages execution. He also says the accumulated end-to-end tests, unit tests, skills, and structure leave the codebase cleaner than it began, making both humans and agents more productive in subsequent work. 15:51 16:17

- Assign models by role: careful reasoning for planning, coding fluency and creativity for implementation, and precise instruction following for validation. - Model-agnostic orchestration supports different validation providers, while contracts and checkpoints can improve outcomes with open weight models. - In the Slack-clone example, implementation consumed 60% of time and tokens; tests represented 50% of code and covered 90% of the codebase. - Prompts and mission-specific skills govern orchestration, while a thin deterministic layer handles bookkeeping, validation, and unresolved handoff blockers.

要点总结

  • Treat human attention as the limiting resource: let people set goals and approve scope while a structured agent system manages extended execution. 0:15 1:17 3:23
  • Separate orchestration, implementation, and validation so planning, coding, and independent review do not share the same responsibilities or implementation bias. 4:27 5:34
  • Write a validation contract before coding, then combine conventional scrutiny with live end-to-end user testing at milestone boundaries. 5:34 6:42 7:38
  • Use structured handoffs to preserve completed work, unfinished tasks, command results, discovered issues, and procedural compliance across agents. 7:38 8:43
  • Keep code-changing execution serial, reserving parallelism for read-only research and review to reduce conflicts and coordination overhead. 8:43 9:50
  • Assign models according to role-specific strengths and keep orchestration in adaptable prompts and skills, with deterministic code enforcing essential operational safeguards. 10:45 11:42 14:00 15:04

export class CodingAgent {
  private anthropic = new Anthropic();
  private messages: Anthropic.MessageParam[] = [];
  private abort: AbortController | null = null;

constructor(private cwd: string) {}

async prompt(userText: string): Promise<StopReason> {
    this.abort = new AbortController();
    this.messages.push({ role: "user", content: userText });

try {
      return await this.agentLoop();
    } catch (err) {
      if (this.abort.signal.aborted) return "cancelled";
      throw err;
    } finally {
      this.abort = null;
    }
  }

现场构建一个兼容 ACP 的智能体

一个极简的 TypeScript 智能体，借助 Agent Client Protocol 获得了会话、流式文本、可见的工具调用、感知编辑器的文件访问和终端工具。

熟悉 TypeScript、异步事件和基本的模型工具调用，有助于理解实现。

01

把你的智能体带进编辑器

编辑器怎样才能让用户自带喜欢的编码智能体，同时又提供一致的界面？Bennet Fenner 在 Zed 正是从这个问题出发的。Zed 是一款用 Rust 写的 AI 代码编辑器。Claude Code、Codex 和 Gemini CLI 让终端成了编码智能体的常见落脚点。如果给每个智能体单独做一套编辑器集成，就得一遍遍解决同一个通信问题。

Agent Client Protocol（简称 ACP）在智能体和客户端之间提供了一套共享接口。它是开源协议，基于 JSON-RPC，作用类似 MCP 和 LSP，都是把原本互不相通的系统连起来。有了它，编辑器不必了解某个智能体的原生接口，也能展示它的工作。

智能体接入 ACP 有两种方式：通过适配器把原生接口转成 ACP，或者直接实现 ACP。Fenner 举了 OpenCode 和 Cursor 的例子，两者都内置了 ACP 模式。据 Fenner 估计，演讲时已有多达四十个客户端支持 ACP。他说 OpenClaw 既是客户端也是智能体，支持 ACP 的客户端里还有 JetBrains 和 Obsidian。现场编码演示站在智能体这一侧：从一个普通的编码智能体出发，让 Zed 能看到它在做什么。

02

从模型循环开始

起始代码是 TypeScript，不过 Fenner 自我介绍说他是 Rust 开发者，没怎么写过 TypeScript。这份代码已经实现了一个最小的编码智能体：只有两个工具，不支持 ACP。读取工具接收文件路径，返回文件内容。编辑工具接收路径、要查找的旧文本和要替换成的新文本，修改已有文件。有了这两个工具，还没接入任何编辑器，智能体就能查看和修改代码。

智能体调用的是 Anthropic 的 API。模型请求是无状态的，所以智能体自己维护对话，每次请求都把累积的历史一并发过去。它的循环很简单：

1. 把用户的提示词追加到对话里，调用模型。 2. 接收模型响应。停止原因是 end_turn，就说明这一轮结束了。 3. 如果模型要求调用工具，就在本地执行读取或编辑，收集结果。 4. 把结果加进对话，再次调用模型。

工具处理函数一开始直接读文件系统。ACP 不必替换这套“推理加工具调用”的循环，只需要把它接到客户端上。

03

给智能体一个 ACP 会话

Fenner 给自己定的目标是十分钟内完成改造，用的是 ACP TypeScript SDK 提供的样板代码。录像里用的是基于接口的智能体实现。现在的 SDK 文档改为推荐 fluent 风格的 agent() 和 client() API，旧的连接类已经弃用；本文沿用录像里基于接口的结构。

第一个方法是 initialize。演示代码返回自己支持的最新协议版本，能力声明尽量精简。更准确地说，初始化阶段会协商版本：智能体如果支持客户端请求的版本，就返回该版本；否则返回自己支持的最新版本。双方都可以声明各自的能力。演示用的 Anthropic API key 从环境变量读取，所以不需要交互式认证流程。

会话（session）对应编辑器里的一个线程。创建会话时，适配器生成一个随机 ID，用客户端提供的工作目录实例化编码智能体，把实例存进内部映射表，再返回这个 ID。之后的提示词都靠这个 ID 找到同一个智能体和它的对话历史。

提示词请求里带着会话 ID 和一组内容块。ACP 可以传文本、图片等内容，但这个智能体只支持文本。适配器找到会话对应的智能体，过滤掉非文本块，把剩下的文本交给现有的 prompt 函数，前面说的“模型加工具”循环就跑起来了。

Fenner 顺手把取消操作也接到了会话的智能体上。到这里，适配器已经打通了基本路径：初始化、创建会话、发送提示词、取消。屏幕上的完整代码先处理提示词，接着是取消方法：取出智能体，调用它的 cancel 方法。

04

一个完成了却看不到答案的提示

Zed 不需要为这个智能体写专门的代码。配置里只要声明一个兼容 ACP 的智能体，指定用 Node 启动，再给出编译后的 JavaScript 文件路径。Fenner 构建项目，启动一个新实例，输入提示词。Zed 显示了等待标志，随后就结束了，却没有显示任何回答。

ACP 调试视图点出了缺的那一环。Zed 发送 session/new，拿到会话 ID，发送提示词，收到停止原因。视图里还出现了红色的适配器报错。Anthropic 在后台确实在输出，只是智能体没把这些输出转发给 Zed。处理了提示词请求，不等于发布了响应内容。 这一轮运行期间，适配器需要持续发送通知。

05

把模型文本作为会话更新转发出去

为了让输出可见，Fenner 把 ACP 连接和会话 ID 传进编码智能体。Anthropic SDK 通过 stream.on 暴露文本事件。每个事件都转成一条 会话更新（session update）：它是挂在对话上的通知，而不是对原始提示词请求的最终响应。

模型文本对应的更新类型是 agent_message_chunk。它的 content 里放新文本，外层消息标明所属会话。TypeScript 代码大致如下，其中 stream、connection 和 sessionId 来自智能体的提示词处理函数：

``typescript stream.on("text", (text: string) => { void connection.sessionUpdate({ sessionId, update: { sessionUpdate: "agent_message_chunk", content: { type: "text", text, }, }, }); }); ``

通知一到，客户端就能做出反应，不必等提示词返回停止原因再显示回答。

重新构建、重启智能体后，Fenner 打了个招呼。这次 Opus 的回复出现在了 Zed 里，一块块流式输出到对话中。模型循环本来就在产出文本，新加的通知通道才让编辑器有东西可渲染。

06

先引入工具调用，再更新它

光有文本输出，还看不出编码智能体在做什么。Fenner 让智能体读取 helpers.ts。现有工具跑了起来，模型也描述了文件内容，但 Zed 没有显示读取这个操作本身。下一步，是把工具活动也通过会话更新发布出去。

智能体先发出一条 tool_call 更新，里面包含 ID、标题、描述操作的元数据、in_progress 状态和文件位置。有了这些字段，Zed 就能把操作展示得更有用，比如配上合适的图标，关联到受影响的文件。截图里正是往处理函数里加这条初始读取通知的那一步。

客户端知道这次调用之后，智能体再针对同一个 ID 发送 tool_call_update 消息。后续更新可以修改状态，附上结果内容。

| 更新 | 作用 | 常见内容 | |---|---|---| | tool_call | 引入一个操作 | ID、标题、类型、状态、位置 | | tool_call_update | 更新这个操作 | 同一 ID、新状态、结果内容 |

顺序很重要：第一条通知建立客户端要展示的对象，后续通知只修改这个对象，不会再冒出不相干的操作。

07

读取编辑器中的文件版本

读取处理函数仍然调用 fs.readFile，读的是磁盘上的文件。ACP 提供了另一条路：客户端如果声明了相应的文件系统能力，智能体就可以请客户端代为读取。这是显式的客户端代理文件访问，不会自动拦截文件系统调用。

之所以这样设计，是因为编辑器里有一种再常见不过的状态：未保存的修改。缓冲区里可能有还没写入磁盘的代码。通过 ACP 调用 readTextFile，编辑器就能返回当前内容，智能体处理的正是用户眼前的那个版本。前提是客户端提供读取能力；读和写是两项独立的能力。

``typescript const { content } = await connection.readTextFile({ sessionId, path: absolutePath, }); ``

智能体的读取工具照样把文本返回给模型，变的只是这段文本由谁提供。

Fenner 运行 npm run build，重启演示智能体，让它再读一次文件。这回读取工具的调用出现在了 Zed 里。测试也暴露出输出重复的问题，演示往下走时这个问题一直存在。

08

把一次编辑显示为 diff

现在，客户端里的读取结果会显示文件的实际内容。Fenner 给编辑处理函数也加上类似的工具通知，重新编译，重启智能体，让它在 src/agent.ts 顶部加一行 Hello World 注释。

智能体通过 ACP 发送了 diff 内容，所以这次编辑在 Zed 里显示成一个 diff。集成已经从显示模型文本，推进到显示具体的代码改动。开头的几个 token 仍然重复；Fenner 怀疑连接有问题，但没在现场排查原因。

09

用智能体来添加它的下一个工具

读和改都能用之后，智能体就可以修改自己的实现了。Fenner 给它一段事先准备好的提示词，让它给自己加一个终端工具。提示词里附带了相关 ACP API 的信息，智能体可以用现有的文件工具实现这项新能力。

终端支持和文件访问遵循同样的能力边界。客户端可以声明自己能替智能体创建和管理终端。智能体也可以自己管理终端，但交给客户端的话，编辑器就能以交互方式展示正在运行的操作。演示中，智能体先加了一段新的工具描述，接着实现了终端工具。

生成的实现顺利构建通过。Fenner 重启智能体，让它等五秒再列出目录。Zed 先显示一个正在运行的终端，随后显示输出。整个过程形成了一条很有意思的递进：最初的读、改两个工具就足以造出另一个工具，而 ACP 让客户端有办法把这个新操作展示出来。

10

演示的交接环节

Fenner 说，这次 ACP 改造大约花了十五分钟。他建议观众去看协议网站，但明确提醒：别把这份由智能体生成的演示代码用到生产环境。录制时配套仓库还是空的，他说下一步就上传代码。结尾那页仓库幻灯片只是给出地址，不代表代码已经能拿到。

11

客户端计算了什么，以及它如何连接

观众的第一个问题是：diff 由谁计算？ACP 支持一种结构化的 diff 内容类型：智能体发送文件路径和新旧两版文本，Zed 负责算出差异并显示。所以智能体不必生成编辑器里的可视化 diff，也不用发送预先算好的补丁。它只管提供两个版本，怎么呈现交给客户端。

最后一个问题是：连接是不是在本地？Fenner 明确说，演示实现用的传输方式是 标准 I/O。他提到远程传输正在开发，不太确定地说是 JetBrains 的贡献者在做，并预计很快会推出。这只是预期，并不是这次演示过的能力。本场实际跑通的连接，是编辑器启动智能体进程，通过标准输入输出和它通信。

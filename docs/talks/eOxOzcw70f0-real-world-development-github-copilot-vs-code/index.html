用 GitHub Copilot 和 VS Code 做真实世界的开发

一场 VS Code 现场工作坊，跟随一个一次性的前端原型，走向可复用的指令、自定义的 TDD 模式、MCP 工具，以及一个把规格说明、规划和实现分开的工作流。

熟悉 VS Code、基本的 Git 工作流和一个 JavaScript 前端项目，有助于理解示例；MCP 和 Copilot 定制会在出现时讲解。

01

当一个能用的应用已经不够时

You build an app in a day, put it online and make money. Then it leaks data, and the experiment stops being fun. That is the opening problem behind Harald Kirschner’s progression from outcome-first coding to development with guardrails: as agents work longer and generate more code, what lets an engineer trust the result? He points to an Anthropic conference chart as motivation, but the practical question is how to add safeguards without losing the speed of experimentation.

| Approach | Primary purpose | Added discipline | |---|---|---| | YOLO vibes | Creativity, speed and learning | Judge the visible result | | Structured vibes | Sustainable development | Readability, handover and quality control | | Spec-driven vibes | Scale and reliability | Explicit requirements and repeatable process |

These stages describe different needs. A throwaway experiment can prioritize immediate feedback; a product that someone else must maintain needs more structure around how the agent works.

The first stage stays almost entirely in natural language: request something, accept changes, inspect the output and ask for another attempt when it goes wrong. That makes sense for proofs of concept and UX mockups that help nontechnical colleagues communicate an idea in a meeting. It also creates a useful learning route. During a live game-building exercise at Build, Kirschner returned to Three.js after years away; once the generated application worked, he could inspect its structure and learn how it produced shapes. A water tracker or a weekend project with children can serve the same purpose: create something tangible, then explore it.

02

从一个空的工作区开始

The prototype begins in a new VS Code window, opened with Command+Shift+N, with no folder selected and Copilot alongside the Explorer. Kirschner uses Claude Sonnet 4, his preferred model for frontend work. The recording mixes Stable and daily Insiders builds, and several controls differ across attendees’ installations; the steps here follow the demonstrated interface.

Switch Copilot to Agent mode before looking for the tools picker. Several attendees begin in Ask mode and cannot find it. Kirschner initially wants to disable Scaffold New Workspace so the model can produce a simple HTML experiment without a full project setup. When that control proves difficult to locate across versions, he changes course and keeps the scaffolding tool enabled. That choice determines the shape of the next demonstration.

03

给饮水记录应用一套技术栈和设计方向

The request supplies a familiar stack—React and Vite—and a loose product description: a water-consumption tracker with a large, accessible interface. Kirschner adds Apple-inspired design guidance and Material UI. He deliberately leaves button counts, mobile behavior and CSS choices unspecified. Popular frameworks reduce the amount of unfamiliar territory the model must navigate, while the broad design request exposes the assumptions it makes.

The New Workspace flow turns that request into a project:

1. Submit the app request from the empty window. 2. Continue when Copilot asks for an empty folder. 3. Create and open vibing-at-ai-engineering. 4. Let the agent continue scaffolding inside that folder.

The new-project command handles the initial stack and setup decisions that otherwise interrupt a greenfield experiment.

Next comes a consequential setting: search Settings for approve, select Workspace rather than User scope, and enable automatic approval. Kirschner explicitly cautions that this removes the Continue confirmations for tool actions. Workspace scope limits where the setting applies; it does not make every command safe. The agent’s visible plan includes installing Material UI, building the tracker and applying the requested design direction.

The live setup exposes two sources of confusion. Attendees reach different settings screens through different entry points, and the existing conversation continues asking for confirmation. Kirschner attributes the latter to enabling auto-approval after the chat began. He also distinguishes the more granular MCP permissions already available—such as approval for a session or workspace—from the broader automatic-approval setting.

04

再做一次设计实验

While the first app runs, Kirschner opens another window, checks automatic approval before starting and requests a Fluent design variant in a second folder. This is where cheap generation becomes useful for design exploration: ask for several ways to solve the same problem, such as three signup flows, and compare what appears. The second session runs without repeated confirmations, although managing two windows makes it harder to remember which process belongs to which app. The agent also selects an incorrect Fluent dependency and attempts to repair it.

For attendees still searching, Command+, opens Settings, where they can search for Auto-approve. But finding the switch is only the usability problem. An audience member wants a middle ground between approving every command and approving everything. Kirschner explains why terminal permissions are difficult: a command can chain other commands, so allowing a familiar command name does not necessarily constrain everything the shell will execute. The transport distinction is precise even though the live explanation uses loose wording. stdio connects a client to a subprocess through standard input and output; a remote HTTP configuration connects to an endpoint. 17

先写规格，再写计划，然后实现

The operational foundation extends beyond prompts. An agent can consult an existing implementation through cross-repository search; Kirschner uses the Model Context Protocol TypeScript SDK as a reference when building MCP servers. Starter templates should also configure tasks, linting and Problems integration so the agent can receive concrete feedback. During work, pause and steer the conversation, review changes and grant trust selectively to read-only tools. Refine instructions after mistakes and commit each working state so the next experiment has a reliable recovery point.

Spec-driven work adds an explicit specification and implementation plan to that foundation. MCP tools can supply database access, logs and project-tracking information; testing and debugging depend on the corresponding VS Code setup being in place. Kirschner mentions o3 for deeper reasoning, then suggests creating a specification from the project’s existing conversations. A meeting transcript is useful input only if the final decisions are clearly identified, so the generated document does not mistake every explored option for an agreed requirement.

An attendee proposes generating a spec, asking the model to critique it and arguing through omissions until it improves. Kirschner’s own Critique Idea prompt asks three questions about an idea. That moves the model’s role beyond producing code: use it to question assumptions, expose gaps and act as a design partner before implementation makes those decisions expensive to change.

The closing discussion compares this approach with planning in Cline and customizable modes in Roo. VS Code has no built-in Plan mode in the recording, but a custom mode can provide the behavior. Kirschner separates the work into three stages:

1. Specification: decide what the product should do. 2. Implementation plan: decide how to build it. 3. Implementation: execute the agreed plan.

Spending more time on the first two stages gives the agent clearer work to perform in the third.

18

让流程——以及代码库——更容易理解

The appropriate amount of structure depends on the task. Experiment to find where a direct request works and where writing a spec first pays off. When an answer is poor, give feedback and iterate; when a process works for the team, encode it in modes, prompts and instructions. An audience comparison with Emacs major and minor modes captures the growing overlap among those customization mechanisms, which Kirschner acknowledges still needs cleanup.

The final requirement is a codebase the agent can understand. Keep code well structured and self-explaining, plan with codebase context, and give the AI concrete examples in its guidance. Maintain the instructions and prompts as the project changes. Those practices let the workflow grow beyond a disposable hydration tracker without depending on the agent to infer every convention anew.

@contextmanager
def identity(token: str | None) -> Iterator[None]:

async def mint(resource: str, scope: str | None = None) -> str:
    subject_token = _user_token.get()
    async with _oauth_client as client:
        if subject_token is None:
            response = await client.client_credentials_grant(resource=resource, scope=scope)
        else:
            response = await client.exchange_token(
                subject_token=subject_token,
                subject_token_type=TokenType.ACCESS_TOKEN,
                resource=resource,
                scope=scope,
            )
    return response.access_token

Step 8: Keep secrets out of history
Temporal keeps a Workflow's Event History while it runs and for the namespace's retention period after it closes, and anyone who can read the Workflow can see what's in it. So anything sensitive should stay out of it.

The Client tab printed a command to check your Workflow's history. Click on the Client tab and type it, using your Workflow ID:

别再给你的 AI 智能体 API 密钥了：Expense Desk 的身份与持久化执行

Kim Maida 用限定范围的 token 展示了是谁提交了一笔 30 美元的报销，以及智能体为什么可以批准它。随后 Mason Egger 在一次账本扣款后杀掉了一个工作进程，展示 Temporal 如何在不重复扣款、也不把访问 token 存进工作流历史的情况下完成结算。

01

一项报销服务需要知道是谁行使了它的权限

Kim Maida of Keycard and Mason Egger, a solutions architect at Temporal, introduce two responsibilities of an agent runtime. Maida works on the identity and access an agent needs while it runs. Egger works on durable execution for applications, including agents. Maida takes the first part of the workshop, which starts with a functioning expense application and changes how it gets permission to do its work. Participants can use the supplied sandbox and join Keycard during the exercise. Registration for a personal account afterward is separate.

Consider what an expense service learns when an agent presents an API key. It can grant the operations attached to the key, but possession alone identifies neither the particular agent making the request nor the person who asked it to act. The agent can exercise every permission the key carries, even if the current request needs only one. Requiring a person to click Approve leaves the attribution problem intact if the agent still submits the approval with that key. People can also make mistakes, and some agents need to work autonomously. Expense Desk will need a way to represent both delegated human authority and the agent’s own authority.

02

用户登录确立了可以委托谁的访问权限

Maida introduces Token Exchange, an open standard dating to 2020 that extends OAuth 2. To follow a human identity through an execution, start at sign-in. An authorization server verifies the user’s identity and issues tokens. Google, Okta and Auth0 are examples of identity providers that offer authorization servers. Logging in establishes who is present. The subsequent consent step establishes which portion of that person’s access the agent may exercise.

The user consents to delegate a subset of their permissions, expressed as scopes. This is the first opportunity to narrow access, before the agent has even received a prompt. The authorization server issues a token identifying the user and their level of access. Later, when the application presents that token in an exchange, it serves as the subject token. The subject is the person on whose behalf the application wants to act. The application will supply a separate means of identifying itself, so a downstream authorization decision can account for both parties.

03

跟随一个提示词从 LangChain 循环走到报销账本

Expense Desk is the runtime, the process that runs the agent loop and executes calls. Inside the custom application, a LangChain agent calls an LLM. An expense Model Context Protocol (MCP) server exposes a defined set of tools and connects them to a ledger API. The ledger API in turn connects to the database that stores expenses. Within this arrangement the MCP client has a specific job: take the tool calls the model proposes and dispatch them to the MCP server.

A user submits a prompt to Expense Desk. The runtime calls the model, which proposes a tool call. The MCP client dispatches it, the MCP server executes the tool, and the tool calls the ledger API. The result travels back through the server and client to the runtime. Expense Desk calls the model again with the result. The model can propose another call, sending the application around the loop again, or return an answer to the user. This order matters for authorization. By the time a proposal reaches the client, the application knows which operation it needs permission to perform.

Implementing the exchange requires an OAuth client capable of executing code. Maida describes three places it could live. A gateway could perform the exchange between an MCP client and a third-party MCP server. A custom agent application could perform it inside its own runtime. A CLI wrapper could add the exchange around an off-the-shelf coding agent. Expense Desk takes the second approach for access to the expense MCP server. That server also supports exchange, giving it a way to ask for access at the next boundary, the ledger API.

04

为 MCP 调用签发一个凭据，为账本签发另一个

In the delegated path, the prompt and subject token arrive at Expense Desk together. Once the model proposes a tool call, the application authenticates to Keycard’s security token service, a specialized authorization server. It can establish its own identity with client credentials or a workload identity. It also presents the user’s subject token and asks for access to the expense MCP server for the particular tool call the model proposed.

Keycard can now evaluate the requesting agent, the user it represents and the extent of the user’s delegation alongside the target resource and requested access. A user’s permission to use Expense Desk therefore does not by itself settle whether to issue this next credential. The delegation chain and the operation requested at this resource must fit policy. If they do, Keycard issues an access token addressed to the expense MCP server. Maida says it typically expires within minutes and instructs participants to keep it out of storage.

The Expense Desk MCP client presents the issued token as a bearer credential with the tool call. The MCP server validates it and uses it to authorize the operation. Executing the tool now requires the server to call a different resource. For this second hop, the MCP server becomes the requester. It asks Keycard to exchange the token it received from Expense Desk for a token that grants the access this operation needs at the ledger API.

Keycard evaluates the second request against policy, then issues the ledger credential if permitted. The MCP server calls the API, the API validates the token, and the server discards it when the call finishes. The API result flows back to the model through the normal agent loop. If the model proposes another tool call, the runtime requests access for that call. This places credential issuance at the point of use on each hop, even when a single user prompt produces several operations.

运行 API 密钥版本并检查一笔 75 美元的报销

Start the workshop sandbox and allow a minute or two for setup. Participants work in one pre-provisioned Keycard organization, so they can see one another’s work. Each runs a separate Expense Desk agent against the same MCP server. The initial application requires no login. Each agent uses an API key, and the desk cannot reliably tell whether participants use a common key or different ones. Later configuration requires Keycard administrator access, which the workshop team grants as participants appear in the organization’s user list.

The desk supports a familiar sequence. Someone files an expense, a reviewer approves or rejects it, and an approved expense can proceed to payout. The workshop makes no actual payments. Every interaction with the desk goes through the agent. Maida asks hers to submit $75 for workshop snacks. The expense appears as pending. Its activity entry says that an API key granted access to create it. There is no user identity attached to the filing, and the agent has yet to acquire an identity of its own.

Maida refreshes the desk, picks another participant’s expense and clicks Approve. The button sends an approval prompt to her agent, which successfully approves the expense. Looking at the entry afterward, she can see that a key authorized creation. This gives the group a baseline they can reproduce before changing any credentials.

把 Expense Desk 同时注册为令牌请求方和接收方

The first implementation goal is to let the agent act on its own behalf. Follow the invitation in the workshop instructions and log in with GitHub to join Keycard. This login gets Maida into the console where she configures the agent. A user signing into Expense Desk itself will be a separate event.

In Applications, create an application registration for the agent. An application is a registration for something that can request tokens. Maida names hers as an agent app and incorporates her GitHub handle so she can find it among the other participants’ registrations. Give it a unique identifier, select implicit consent and obtain the redirect URL by running the supplied instruction in the sandbox terminal. Copy that instance-specific URL into the registration. It tells the sign-in flow where to return the user after login. Then choose Create application.

Expense Desk will also receive a user’s sign-in token. In Keycard, a resource is a registered target to which a token can be addressed. The same running component can hold both roles. Open Resources, add an agent resource, and give it a recognizable name and identifier using the same personal naming convention. Set its credential provider to the zone provider. This makes Keycard responsible for handling token exchange and issuing tokens for this resource.

In the resource configuration, select the agent application just created as the application that provides the resource, then save. This association has an operational consequence. It tells Keycard that this particular application can exchange sign-in tokens addressed to this particular resource. Similar names in the two registration lists do not establish that relationship. If the provider association is omitted, Keycard rejects the exchange requests.

连接四个依赖并配置沙箱的客户端凭据

把 MCP 工具集接到令牌签发，以智能体身份运行

It uses a client credentials grant, authenticating with the application’s configured client ID and secret. The resulting authority belongs to the agent itself. This is the path the group can test immediately, before adding human sign-in to the desk.

In the Terminal tab, activate checkpoint two and restart the services so Expense Desk loads the updated code. Back in the application, choose Continue as the agent. 跟随智能体的凭据从 MCP 服务器走到账本

To carry out that call, the server needs access to a second resource, the ledger API. At that point the server becomes the requesting application. Its actor registration lets it exchange the incoming token for a credential to call the ledger.

Maida switches to the preregistered expense MCP actor and filters its activity by calls to the ledger API. 让人登录，同时保留智能体自己的权限

追踪 Kim 的委托权限穿过两次令牌交换

15

把智能体循环放进工作流，把外部调用放进活动

Mason Egger of Temporal takes over with Ziggy, the plush tardigrade he carries with him, and a question about deploying the expense agent. A service can identify every participant correctly and still lose its place halfway through a task. An agent loop calls tools and external services in succession. Once a process fails, the application needs some way to determine which calls completed, what they returned and which operation should run next.

Egger introduces Temporal as a durable execution framework. His mental model for its Python interface is a parent function and its child calls. The parent is a workflow, which describes the sequence or loop. Each run is a separate workflow execution. An external operation such as a tool call is an activity. Activities give the workflow places to apply retry behavior when a dependency fails and results from which it can reconstruct progress after an interruption. An activity implementation looks like ordinary Python. Egger points to an asynchronous function, async def assess, as an example.

The concrete workflow he will interrupt is settlement. It specifies a retry policy, executes a debit against the ledger, waits on a timer, then executes a second activity to mark the expense settled. The timer stands in for time a human might take to review something. It also creates a useful interval for the experiment. Once the debit has completed and before settlement finishes, there is already a ledger operation whose result a replacement worker needs to respect.

16

在工作进程执行活动时给它一个凭据

Egger draws attention to the first decorator above an activity, which declares the resource for which it needs a grant. Keycard implemented the corresponding behavior using a Temporal interceptor. Egger describes an interceptor as a hook at a particular point in execution. When the worker executes the activity, that hook obtains identity and permission from Keycard so the activity can authenticate to its resource.

This gives the deployment a choice about the identity used for work. Individual workers can have distinct identities, or a fleet can use an identity assigned to the fleet. The choice determines what the operator can identify and scope when those workers request access. For the workshop, the worker identity, Temporal application and environment configuration are already set up. Egger proceeds directly to starting a worker.

Temporal separates the service that maintains execution state from the processes that perform the work. Egger suggests thinking of a fleet of workers as pods or processes within a pod. He starts one worker, and the worker tab reports PID 572. That process is now available to execute work. The separate Temporal service will still have the execution record if PID 572 disappears.

17

扣款后杀掉 PID 572，看看什么留了下来

From the client tab, Egger invokes a settlement and gets a workflow ID. He switches back to the worker tab to see the application’s execution log, including credential minting for the call, then refreshes the Temporal web UI to find the running workflow. These views serve different purposes. The client identifies the execution he requested, the worker shows what its process is doing, and the service holds the history he will inspect after that process dies.

With the debit complete, Egger kills the worker cold. Back in the Temporal UI, he can still inspect the retry policy, the completed activity task and the debit’s stored output. He reads the debited value as 4,200 without specifying a unit. While the worker is down, a workflow task times out. That timeout and the completed debit are both visible. The service has evidence of the successful ledger operation even though there is currently no worker to advance settlement.

Egger restarts the worker. Temporal reconstructs the workflow’s state by replaying its progress using the recorded responses. When the workflow reaches the completed debit, it already has the result. The worker can proceed to mark the expense settled without sending a second debit. The timing is important to this demonstration. The service had recorded completion before Egger stopped the process. That recorded result is what replay can reuse.

18

恢复一次长时间的智能体运行而不必重新花钱买答案

Egger asks the audience to consider losing a worker twelve steps into an agent loop. Starting over can mean paying again for model responses the application already obtained. Recording progress in an application database is one possible design, but the developer then owns the logic to reconstruct the loop and determine what to retry. In Temporal, a completed model activity’s recorded response can serve the same purpose as the debit result in the settlement example.

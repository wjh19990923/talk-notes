别再上线只在纸面上胜出的 LLM 配置

DigitalOcean 做了一个调参智能体。它在推理硬件上实测 vLLM 配置，看服务器在延迟目标内能交付多少 token。两次跑完的实验展示了胜出配置改了什么，也说明了为什么要看这个指标。

01

每次实测都在决定下一套配置

下载一个模型，工程师会拿到一份起步用的部署配置。可要在某台机器上找到真正好用的设置，往往得试上好几个小时。Rohan Pandey 演示了 DigitalOcean 的做法：把这件事挪到后台去做。工程师只提供初始配置，剩下改参数、测效果的活都交给智能体。

智能体用 Optuna 跑贝叶斯优化。每次试验都是一组配置加一个实测分数。Optuna 根据这些结果挑下一组要试的参数。这样智能体不用穷举所有组合，试验预算能花在更有希望的配置上。预算用完后，得分最高的那组配置就是赢家。

按 DigitalOcean 的介绍，在生产环境里，智能体会把方案推到 AMD MI355 推理服务器上。它先上线一套候选的 vLLM 和 Kubernetes 配置，对照延迟目标测吞吐，然后留下更好的那套，或者回滚到原来的配置。Pandey 把评分指标叫作 goodput（有效吞吐）。有的设置能拉高每秒总 token 数，但如果更多请求超出延迟目标，goodput 几乎不涨。

02

用四种负载定义测试

演示从一台 Droplet 开始，上面已经加载了 GPT-OSS 模型。拿什么流量来压它？初始配置定义了四种负载：短对话、长对话、检索增强生成（RAG）和批量分类。每种负载都有输入序列长度（ISL）和输出序列长度（OSL），单位都是 token。两个数放在一起看，就知道每个请求要处理多少文本、要生成多少回复。

这两个长度可以调。短提示词配长回复，和长输入配短分类结果，给服务器的工作负担完全不同。所以初始 YAML 为实验定下了两件事：一是调参器的起始部署配置，二是评判每次改动时用的流量。

03

按试验预算启动一次实验

智能体要把这份 YAML 跑起来，还需要什么？权重已经放在 Droplet 上。启动命令指向权重所在位置，激活虚拟环境，然后运行 tuner.py。脚本接收四个参数：实验名、初始 YAML 文件、运行的硬件，以及试验次数。示例里设的是 24 次。最后这个参数决定搜索什么时候停。

这些实验跑得很久，Pandey 直接切到已经跑完的结果来讲。据他回忆，GPT-OSS 大约跑了四五个小时，另一个模型跑了两个小时左右。每份报告都来自一次单独设定预算的实验。

04

GPT-OSS 比初始配置提升 17.5%

GPT-OSS 这次实验跑了 50 次试验。HTML 报告标出了其中最好的一次。配套的 YAML 记下了选中配置的各项部署参数。工程师可以直接拿来用，不用再翻试验记录去拼。

Pandey 指出了其中一个选中的值 256，但没说它对应 YAML 里哪个键。对比看的是整套配置。按计入 goodput 的生成 token 来算，胜出配置比第一组配置高出 17.5%。

05

DeepSeek 第九次试验：吞吐和出词速度都变好了

第二份报告测的是 DeepSeek R1 Distill 模型。九次试验里，第九次得分最高。对服务器和看流式回复的用户来说，分别变了什么？

- token 吞吐翻倍。 在报告的对比里，服务器单位时间生成的 token 数翻了一倍。 - token 间延迟降了将近一半。 开始生成之后，相邻两个 token 之间的等待时间缩短到原来的一半左右。

两次实验结束时，HTML 报告都展示了每次试验的表现，YAML 则给出可以直接复跑的设置。结果接近时，这一点很关键。DigitalOcean 在录像介绍里举了个例子：四次实验中，有一次看似提升了 4%，后来发现只是两次运行之间的随机波动。介绍里也提到团队正在做的事：把智能体扩展到分离式推理（disaggregated serving），也就是让 prefill（处理提示词）和 decode（逐个生成 token）跑在不同的服务资源上。

要点总结

  • 看胜出配置时，要连同选出它的负载一起看。输入和输出的 token 长度决定每个请求的工作量构成，goodput 只算满足延迟目标的那部分吞吐。
  • 说提升时要带上指标。GPT-OSS 在 50 次试验里，goodput 比第一组配置高 17.5%。DeepSeek 最好的一次试验把 token 吞吐翻了一倍，相邻 token 之间的延迟降了将近一半。

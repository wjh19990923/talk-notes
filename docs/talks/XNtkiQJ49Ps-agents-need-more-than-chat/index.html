智能体需要的不只是聊天

当智能体能低成本地产出复杂工作时，难点就变成了引导和审查。持久的文档和表格把人的判断放在了工作发生的地方。

01

修好了第三条，第四条怎么了？

让智能体调研一件事、起草一份合同，还要求“别出错”。它开始读资料、启动子智能体、搜索网页、写文件。接着又启动更多子智能体，读更多材料，写更多文件。在 Jacob Lauritzen 开场举的例子里，合同三十分钟后才交上来，可第三条看起来不对。你让它再对照另一份文档，把这一条改掉。

智能体回答：“您说得完全正确。”接着就开始压缩上下文（compaction）。Lauritzen 说，用户正是在这一刻开始怀疑智能体还能不能记住它需要的上下文。又一轮工作之后，新合同出来了，可问题已经不只是第三条对不对，而是别的地方有没有也跟着变了。幻灯片上追问了一句第四条，把这种担心说得很具体。本来只想改一处，结果又得把整份文档重新审一遍。

Lauritzen 自我介绍是 Legora 的 CTO。Legora 是一个面向律所的 AI 协作工作空间。据 Lauritzen 介绍，Legora 的客户机构超过一千家，覆盖五十多个市场。他提到公司融资规模可观、增长迅速；至于“可能是史上最快”，他说是别人这么告诉他的。他还欢迎工程师加入伦敦团队。增长背后的产品目标，和其他垂直领域 AI 公司一样：让智能体端到端地完成越来越复杂的工作。

02

廉价的执行转移了瓶颈

Lauritzen 谈到过去六到十二个月里的一个变化：干活本身已经足够便宜，规划和审查越来越成为主要工作量。总得有人说清楚想要什么结果、定下非功能性需求，再检查交回来的东西。一个大型 GitHub pull request 就能说明问题：生成一大段改动，可能比弄清楚它对不对还容易。让智能体审查自己的工作也许有帮助，但 Lauritzen 没有断言这样做有多可靠。

演讲里提到 Jason Wei 提出的验证者法则，可以用来思考这个瓶颈。Lauritzen 把它概括为：只要一个任务可解、又容易验证，AI 就会把它解决。对基础模型来说，有了有效的验证，才能搭建强化学习环境、做后训练。他把这个思路延伸到智能体上：跑一遍任务，找出哪里错了，给出纠正反馈，再来一遍。他预期智能体最终能做到；但这条法则本身并不保证这样的循环多久能解出来，也不保证一定收敛。

03

一个垂直领域包含多种验证

验证难度不只在行业之间不同，同一个行业内部也不同。法律工作把这种差别体现得尤其明显。检查合同里的定义，做起来简单，查起来也简单。让智能体写合同条款同样不难，但要判断这些条款能否达到预期的法律效果，就难得多。Lauritzen 说得很直白：真正的检验，要等合同打到法庭上、看法官怎么解释。

在他看来，诉讼策略更难。问五个律师某个案子该怎么打、怎么守，可能得到五种不同的答案；也许根本没有一个客观答案能拿来给智能体打分。编程也一样：边界清晰的实现任务很容易检查，而做出一款成功的消费级应用，取决于一个很难事先验证的结果。

| 任务 | 验证难点 | | --- | --- | | 检查合同定义 | 核对定义过的术语和实际用到的术语是否一致 | | 起草合同 | 判断条款能否达到预期效果 | | 制定诉讼策略 | 没有公认答案，只能评判几种不同方案 | | 做出成功的消费级应用 | 证明产品成功，而不只是实现正确 |

实际分析时，要看的是具体任务，而不是“法律”或“编程”这样的标签。

04

控制决定引导，信任决定审查

目标是让人在需要判断力的地方参与，把可以放心交出去的工作交给智能体。这种协作该怎么运作，取决于两个维度：

- 控制： 一个人能多有效地把自己的知识注入智能体的工作，引导它做决策？ - 信任： 这个人需要审查多少工作？信任低时，可能每条 trace 都要看；信任高时，可能几乎不看，甚至完全不看。

这是两个不同的问题。用户可能需要牢牢把控某个战略选择，同时又放心让智能体去做随之而来的机械性工作。该从哪方面下手，取决于任务在“可解性—可验证性”光谱上的位置。

05

给智能体一个可以检查的东西

提高信任的一种办法，是让任务更容易验证。做功能实现时，有了浏览器访问和测试驱动开发，智能体就能检查程序行为，测试自己的工作是否满足需求。Lauritzen 提到金融领域也有类似的机会，然后又回到合同。没法直接验证时，以前成功的合同可以当参考样例：拿新草稿和这些“黄金合同”对比。相似度只是一种验证代理，不能证明新条款在法律上没问题。

拆分任务还能带来更多机会。不要把“写一份合同”当成一个笼统的任务整个交出去，而是把需要判断力的决策，和能检查得更清楚的操作分开：

- 人来判断： 选定风险偏好、参照的先例文件和谈判立场。 - 智能体执行： 按现有合同的格式排版，检查定义。

检查定义本质上就是 lint。定义过的术语都用到了吗？用到的术语都有定义吗？比起问“整份合同好不好”，这类问题的反馈回路要紧凑得多。

举个实现示意：把定义的术语和用到的术语提取出来之后，这两项检查就是简单的集合差：

```typescript function lintDefinitions( definedTerms: readonly string[], usedTerms: readonly string[], ) { const defined = new Set(definedTerms); const used = new Set(usedTerms);

return { unusedDefinitions: [...defined].filter(term => !used.has(term)), undefinedTerms: [...used].filter(term => !defined.has(term)), }; }

const findings = lintDefinitions( ["Agreement", "Effective Date", "Services"], ["Agreement", "Services", "Business Day"], ); // unusedDefinitions: ["Effective Date"] // undefinedTerms: ["Business Day"] ```

这样就把一个可检查的子任务单独拎了出来；至于怎么提取和理解这些术语，是另一回事。智能体拿到具体的问题清单去修，人则继续掌握合同的战略选择。

06

信任也可以来自限定范围

护栏的作用是缩小智能体能做的动作范围，从而提高信任。Lauritzen 举的例子很具体：只能编辑指定的三个文件，只能读取某个目录里指定的内容，或者只能搜索批准过的网站。智能体的活动范围小了，用户要担心的事也就少了。

Claude Code 正好展示了两个极端。一端是智能体每个动作都要请求许可，想推进点有用的工作都很麻烦。另一端是用户跳过权限检查、放手让它跑——幻灯片上展示的是 --dangerously-skip-permissions，Lauritzen 还顺带提醒了删掉生产数据库的风险。工程上的关键区别在于：是请智能体遵守限制，还是强制执行限制。按 Claude Code 目前的文档，权限属于框架层面的控制，不是提示词能改的。这份文档讲的是现在的产品，不是幻灯片上的旧版本。

07

规划只能覆盖它能预见到的工作

要理解控制，可以把一个复杂的智能体任务看成一棵工作树，更一般地说，是一个有向无环图。Lauritzen 举的例子是一份劳动合同报告。智能体先调研这家机构，再逐份审查每份合同的几个方面，最后起草报告。如果人只能在根节点介入，就只能提个需求，然后等下游所有工作做完，才能再给出判断。开头那个合同问题，就这样被放大重演了一遍。

规划能改善这种安排：执行前先就做法达成一致。人可以批准步骤、指出要检查哪些条款、定下审查标准。比起笼统地要一份成品报告，这样能给智能体更明确的方向。

但要了解得足够多、写出一份完整的计划，可能得先把任务做掉一大半。规划阶段来回问很多问题，也未必能确保必要信息都收集齐了。某份劳动合同里有个不寻常的条款，智能体可能要读到那份合同才会发现；没发现之前，双方都没法提前定下怎么处理。

这种协作就像一个同事，和你商量好做法就消失了，直到最终文档写完才露面。事先对齐有帮助，但中途有了新发现，你没有机会回应。所以 Lauritzen 预测，规划不会一直是主要的协作方式。它的局限在于：人给出判断的时刻，和真正需要判断的时刻，隔得太远。

08

在发现问题的那一刻做判断

Skills 把可复用的人类判断放到工作图的单个节点上。人不必提前把整份报告描述清楚，只需规定保密条款该怎么审。终止条款审查的 skill 里，还可以写上针对某个欧盟法律特殊情形的指导。执行中一旦遇到这种情况，相关指令早已就位。

Lauritzen 特别提到了渐进式发现：智能体随着工作推进，按需取用相关指导。这样能应对初始计划里没列出的情况，但前提是有合适的指导可用。不可能每件事都有对应的 skill。

没覆盖到的情况，就要靠下一个机制：引导提问（elicitation），也就是针对任务中遇到的具体疑点去问人。提问时手里有一个具体问题，不必要求用户在开工前就把所有可能的问题都想到。

Lauritzen 建议把引导提问和决策日志结合起来，避免不必要的阻塞：

1. 拿不准时，先做一个临时决定。 2. 把这个决定记进日志，继续干活。 3. 事后让人审查日志，必要时推翻决定。

工作已经基于这个决定往下推进了，但这不等于人已经认可了它。让决定保持可见、可撤销，后面才有机会介入。

09

在产物内部审查决策

现在设想工作图变大十倍、一百倍。一个聊天窗口塞进五十个问题，不一定能换来五十个有用的回答。每个问题都得结合它涉及的合同、条款或决策才看得懂。线性对话把这种分支结构压平成一条信息流，用户只能自己去还原。

人和智能体应该在持久化的工件里协作，让工作和上下文一起摆在眼前。 用什么工件，取决于行业和任务。起草法律文件时，文档就是天然的工作空间。在 Lauritzen 的例子里，用户高亮第三条，智能体就只改这一条。交互范围直接挂在文档的对应位置上。开头那次修改之所以让人抓狂，就是因为范围不明确，这样做正好解决了这个问题。

文档还支持评论、给智能体和同事打标签，以及把特定段落交给专门的智能体处理。这些交互都保留了指令作用的位置，用户不必在聊天里一遍遍描述是哪里。

对于劳动合同报告，Legora 的替代方案是表格式审查，这是它的用户早已熟悉的基本形式。智能体搭好审查表、检查合同，再标出需要人拿主意的条目。用户能很快定位问题，就地给出判断，还能看到智能体已经做了哪些工作。审完这些条目，用户再让智能体继续剩下的工作。有了表格，人既能控制具体决策，又能检查整体结果。

10

把聊天当作输入，而不是整个工作区

Lauritzen 举了 PostHog 和 Linear 的例子，说明各家界面都在向聊天靠拢。他说这些都是最近上线的，所谓“两周内”只是大致说法。聊天框依然有用，因为它能接受各种灵活的指令。问题在于，把同一种输入方式当成贯穿整个复杂任务的主要协作方式。

语言是一种用途很广的界面，有了语音，下指令还能更轻松。但你用什么形式跟智能体说话，它不必只用同样的形式回答。

演讲前不久，Lauritzen 正在给一位候选人介绍 Legora 的组织架构。那次谈话里，他只能靠嘴把结构讲清楚。他真正想要的，是一张候选人能看到、能交互、能拿来用的组织架构图。智能体完全可以在交互中直接生成这样的图。文档、表格或交互式图表能让用户更直接地理解和塑造工作，既然如此，就没有理由让智能体困在口头对话的局限里。

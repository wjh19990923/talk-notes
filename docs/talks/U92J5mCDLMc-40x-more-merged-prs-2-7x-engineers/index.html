工程师只多了 2.7 倍，合并的 PR 多了 40 倍

Cognition 重建了自己的开发流程。现在客户在 Slack 里发来一段 bug 视频，Devin 就能一路做到测试过的修复。Walden Yan 还介绍了两个交给智能体长期运行的任务：一个在新 GPU 上调推理吞吐，一个让 Android 应用持续跟上 iOS 版本。

01

Cognition 涨了 40 倍的是什么

大约一年里，Cognition 合并的 pull request 涨了 40 倍。开场图表里，蓝色曲线是合并量；底部那条贴着横轴的黑线是工程师人数，同期只涨了 2.7 倍。Walden Yan 是 Cognition 联合创始人兼首席产品官。他用这个差距引出两类变化：代码库怎么改，团队怎么干活。

摊到每个工程师头上是多少？两个增幅一除，全团队人均合并的 PR 大约多了 15 倍。Yan 认为这些 PR 的质量至少不比以前差。不过图表只统计合并数量，没有衡量改动的规模和质量。

02

自动驾驶式 PR 和更小的小组

在 Cognition，一个“自动驾驶”的改动可以从 bug 报告开始，一路走完实现、合并、监控和维护。默认由 Devin 把活干完，它是 Cognition 自己的编程智能体。遇到需要人来判断的决定，再升级给人。

到 3 月前后，这种默认做法让人重新思考工程师的角色。如果工程师一整天只是从 Linear 里拿需求写得清清楚楚的工单、转手交给智能体，那他只是在给 Devin 传话，而这些活 Devin 本来就能自己接。于是 Cognition 把大团队拆成两三个工程师的小组，给每组配一批智能体，同时扩大每个小组负责的范围。

现在，同一个小组听取客户的 bug 反馈、决定做什么，也负责 QA。每个工程师管理自己的 Linear 看板，把实现工作派给智能体。这样一来，判断客户需要什么的人，也负责检查改动有没有真正解决问题。

03

Slack 里收到 bug 视频，回一段修复视频

一位客户在 Slack 里给 Yan 发来一段 bug 视频。他把视频转到内部频道，@ Devin，让它修。Devin 交回一个 pull request，附上代码改动，还有一段演示修复效果的视频。

两段视频各有用处。客户的录屏告诉 Devin 要排查哪个行为。Devin 回传的录屏展示改动后的行为，Yan 直接看一眼就能转给客户，很多时候连 IDE 和 GitHub 都不用打开。要录出第二段视频，Devin 得把改过的应用跑起来，把相关流程实际操作一遍。Watch the transition to the test setup at 4:28

在这个 Slack 例子里，Cognition 把客户的 bug 报告转到内部频道并 @ Devin。Devin 回复一个 pull request 和修复证明，Cognition 再把证明发回给客户。

04

一台 VM 装下完整测试环境

Cognition 过去在云端部署上做测试。工程师连上 staging 数据库和线上服务器，在应用里一路点下来，端到端验证流程。后来团队把每个服务都迁到 Docker Compose 上本地运行，第三方服务则做成本地 mock。这里的“本地”指智能体所在的云端 VM。Devin 可以在里面启动应用、测试改动，完全不碰线上服务。测试覆盖的第三方行为，就是 mock 模拟出来的那部分。

Cognition 每小时拉一次最新代码，从头重建 VM 环境。代码库变得快，构建难免会挂，所以快照失败时，第一个出手修的是 Devin。快照修好了，下一个从 Slack 启动的智能体拿到的就是一台新机器：代码是新的，测试环境也能用。

VM 让 Devin 有地方做测试。测试 skill 则给它一套可复用的说明，告诉它怎么测这个特定的代码库。这些说明由 Devin 自己写，应用和测试流程变了，它也会跟着更新。

因为测试都能在 VM 里跑，Cognition 有几位工程师已经改用 iPad 写代码。Yan 还看到一个安全上的好处：开发集中在受控的云端 VM 里，工程师就没什么理由把密钥之类的机密存在个人设备上。

要测试 Devin 用语音加入 Zoom 会议的能力，得有多个参会者。Devin 建了几个账号，让它们在同一台 VM 里加入同一个会议，互相发语音消息。通过这样的往来，它能确认参会者之间真的能互传音频。

Cognition 把测试从线上服务搬进一台 VM，用 Docker Compose 加上 mock 掉的集成服务。每小时的重建失败了，由 Devin 修复；测试 skill 跑不通，也由 Devin 修。

05

让智能体找开发流程里的浪费

云端环境会记录智能体写的代码、生成的 PR 和做出的决定。Cognition 可以把这些记录交给智能体，让它找出哪些时间或 token 花在了重复劳动上。分析结果可能建议给某个反复出现的操作写个脚本，或者加一个测试，专门拦住某类反复出现的问题。Devin 每天都会往一个频道里发改进建议。

Yan 举了这个频道里的两个提议。

- CI 更快。 改一下 Node 的配置，CI 可能缩短大约一分钟。 - 更早发现 bug。 改一下 lint 脚本，这类 bug 在进入 AI 代码审查之前，可能多拦下约 20%。

06

给智能体一个要改进的指标

bug 报告给 Devin 的是一个具体要修的行为。长期任务则可以从一个目标出发，比如降低后端 P99 延迟，也就是观测到的响应时间里第 99 百分位的那个值。目标本身不规定改什么。只要智能体能测到响应时间分布里最慢的那一端，它就能判断某个改动有没有让指标变好。

在 Yan 的例子里，智能体先加上遥测，摸清当前的 P99，再把改进目标拆成一个个可以尝试的改动。Datadog 告警会标出需要关注的改动。智能体干活期间，工程师有两个渠道跟进：每周的 Slack 报告和每天的手机推送，都能看到当前延迟和已经降了多少。

智能体测什么，取决于团队想改进什么。

- 点击响应。 测用户在应用里点击后感受到的延迟。 - 布局稳定。 跟踪界面元素的边界框，看它们移动了多少，专门消除不该有的跳动。 - 新用户引导。 以留存率作为结果指标。

Yan 的建议是：团队一旦有了智能体能观测的指标，就把目标交给它，让它持续去优化。

07

在新 GPU 上调推理

Cognition 拿到 Nvidia Vera Rubin 硬件时，缺少需要的 GPU kernel，只能为新硬件搭一套推理栈。团队给一个智能体分配了一组专用 GPU，并定了一个具体目标：每分钟多少 token。GPU 让它有地方跑实验，吞吐指标让它能比较实验结果。Watch the throughput goal at 10:15

大约一周里，智能体找出并测试了各种策略。Yan 估计这样发现的想法有八九个。智能体把最有希望的几个交给一位人类工程师做最终审批。

新硬件起步时不如 Cognition 用来对照的 GB300 GPU。Yan 说，调优之后，新硬件的推理吞吐明显领先。他只给了相对结果，没有说明具体负载和吞吐的绝对数值。

08

照着不断变化的 iOS 版做 Android 应用

Cognition 有一个团队在做 iOS 应用，却抽不出多少人手做 Android 版。团队里的工程师 Sam 提议：拿 iOS 应用当蓝图，给 Devin 一个长期任务，让它做出 Android 版，并在 iOS 更新时保持功能一致。Watch how the Android job started at 11:08

Sam 让 Devin 在代码库里设好常驻 hook，用来监控 iOS 应用，并留意 Slack 里的用户反馈。iOS 的改动告诉 Devin 要同步什么，用户反馈给它提供要排查的问题。运行中的 iOS 应用还有第二个用处：在实时 QA 中，Devin 拿它当参照，逐像素检查 Android 应用。

44 天后，Cognition 有了一个能用的 Android 应用，准备发布。延时回放能让人感受到，两次提示之间能完成多少工作。大多数日子里，没有人给智能体发过一条消息；其中有几天，Devin 合并了大约 40 到 50 个 PR。

工程师一般通过 Devin 发到 Slack 的录屏来跟进进度。最重要的决定 Devin 会升级给人，需要时工程师可以出面拍板。Watch the review workflow at 12:52

Yan 最后呼吁各个团队在选题上更有野心。Android 本来是 Cognition 抽不出人手的项目。有了一个持续更新的参照应用、一套对照它测试的方法，再加上重要决定能交给人的通道，团队靠现有人手就把它做了出来。Watch the closing remarks at 13:33

iOS 怎样同时指导 Android 的改动和 QA？ iOS 代码库提供要跟进的改动，运行中的 iOS 应用提供可以对照的行为。Slack 反馈是 Devin 的另一路输入。工程师接收录屏，处理升级上来的决定。 - iOS 应用与代码库 — Android 版不断演进的蓝图，也是 QA 的实时参照。 - Slack 里的用户反馈 — Devin 留意关于应用的问题报告。 - Devin — 更新 Android 版保持同步，并处理反馈。 - 实时一致性 QA — 逐像素对照 iOS 应用检查 Android 实现。 - 工程师 — 在 Slack 里查看录屏，处理升级上来的决定。 - iOS 应用与代码库 → Devin（通过代码库 hook 观察到的改动） - Slack 里的用户反馈 → Devin（待排查的用户反馈） - iOS 应用与代码库 → 实时一致性 QA（参照行为与外观） - Devin → 实时一致性 QA（待测试的新版 Android 应用） - Devin → 工程师（Slack 录屏和升级的决定）

要点总结

  • Devin 能把改过的应用跑起来，所以一条 Slack 里的 bug 报告，最后能换回一段修复视频。撑起这套流程的是 Docker Compose、本地 mock、每小时重建的 VM，以及针对这个代码库的测试 skill。
  • 长期任务需要让智能体有办法评判自己的工作。推理调优用的是专用 GPU 上的每分钟 token 数。Android 维护拿不断变化的 iOS 应用当参照，既决定要实现什么，也决定要检查什么。
  • 人工审核可以放在某个具体决定上。GPU 智能体把最好的几个策略交给人类工程师做最终审批。Android 智能体把录屏发到 Slack 给工程师看，最重要的决定则升级给人。

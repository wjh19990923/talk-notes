Frameworks

• What we recommend for enterprise:
  ○ go native or build with langgraph, why?

  ○ CrewAI/autogen

    ▪ Easy to leverage pre-built agents and orchestrate multi-agents

Simple Agent

• Always start simple: a single LLM with a handful of tools
• The tools should contain:
  ▪ clear descriptions with examples
  ▪ have simple input types e.g. str, list or float instead of complex nested dictionaries
• Provided instruction list should be short to avoid conflicting instructions the model may receive in the user turns
• Long chat history chains can induce hallucinations so caching and retrieving relevant information is often needed

评估智能体

幻灯片原文
Developers can trace agent performance by measuring each stage of a tool call: deciding whether to call, selecting and executing the function, supplying inputs, using results, and correcting errors.

Evaluating Agents

What makes a successful agent? A lot goes into even a simple, single-step tool call

1. Relevance: Model must correctly decide if a function is needed or not
2. Routing: Model must select the correct function
3. Execution: Model needs the correct auths / permissions
4. Inputs: Model must use the correct parameter values and types
5. Reasoning: Model must use the function’s response to generate a response for the user
6. Course correction: If an exception occurs at any point, can the model fix its mistakes?

For the final product, what matters most is the final output, but for developers, you must measure all of these aspects to trace the root cause of performance

构建真正可用的企业级 LLM 智能体

可靠的企业智能体需要清晰的工具契约、受约束的编排、明确的人工审核，以及能暴露工具型工作流在哪里失败的评测。

熟悉 LLM 工具调用和检索增强生成会有帮助；不要求特定的智能体框架。

01

这些零件如何组成一个可靠的智能体？

手里有一个模型、一组工具和一个编排框架，怎样把它们组装成能在企业规模下安全运行的智能体？客服助手、个人助理、检索增强生成（RAG）智能体、金融分析智能体，都会碰到这个集成难题。每个组件单独拿出来也许都能用，可整条工作流要扩展、要保证安全、要平稳运行，仍然很难。

难点首先在于选项太多：框架、工具、模型、编排策略和评测标准，都得在同一条流水线里配合起来。Shaan Desai 在 Cohere 积累的经验给出了一个实用的决策顺序：先选一个你能调试的框架，再判断任务需要多少智能体协作，最后定下怎样评测智能体的行为。

02

选一个你能调试的框架

AutoGen、CrewAI、LangChain 这些框架各有取舍。用三条标准衡量，取舍就具体了：

| 标准 | 实际要问的问题 | |---|---| | 可观测性 | 出了故障，能不能查看、调试并修好？ | | 搭建成本 | 多快能把智能体搭起来并开始迭代？ | | 支持度 | 文档、模型、工具和所需功能是否齐全？ |

这三条要放在一起看：初始搭建再快，如果解决第一个棘手故障就要花大代价，快也没多大意义。

如果是对可观测性要求很高的大型企业级智能体，Desai 推荐自己原生实现，或者用 LangGraph。如果只是快速测试和做概念验证，他推荐 CrewAI 和 AutoGen：搭建工作量小，预置的智能体和工具也容易拼起来用。这些是演讲当时的建议，不是永久排名；AutoGen 的代码仓库现在已经挂出了维护模式的通知。

Cohere 的做法是随着各框架能力的演进，持续改进与它们的集成。最终的好处是有一系列选项，分别适合不同的应用，而不是某一个框架通吃所有场景。选定框架之后，下一步要决定怎样组织智能体本身。

03

从一个智能体和一份清晰的工具契约开始

单智能体执行、多智能体协作、引入人工反馈，都是需要明确做出的设计选择。先从一个 LLM 加少量工具开始。 在增加智能体之前，先让这个模型更容易用好手上的工具。Desai 认为，把工具规格写仔细，本身就能带来相当大的提升。

Cohere 有一位客户，手上有一长串 API，每个 API 的规格最多要接收 10–15 个参数。客户的需求是让模型能成功调用这些 API。Cohere 的办法是简化呈现给模型的接口：把描述写清楚，给出有效调用的精确示例，并在合适的地方把复杂的嵌套字典换成 list、str、float 这样更简单的输入。这个参数数量说的是那位客户的具体情况，并不是可靠调用工具的通用上限。

写指令也要守同样的规矩。指令列得简短直接，模型更容易看出该怎么做。Desai 发现，指令一长，反而可能把模型搞糊涂，诱发幻觉。指令加得越多，规格并不会自动变得越好。

04

检索要紧的那部分历史

对话历史也会带来类似的问题。Desai 在多个模型和框架上都观察到，对话一长就会出现幻觉。他举的例子是超过 20 轮的对话，但这不是通用的分界线。他的建议是把历史缓存起来，新查询需要时再检索相关部分。这样历史仍然可用，但模型不必在每次请求里都带上之前的全部往来。这样做对某个具体的智能体有没有帮助，要靠后面讲的评测流程来判断。

05

在扩大自主性之前先约束路由

当应用确实需要多个智能体时，架构就变成一组较简单的智能体，由一个路由器来协调。Desai 提到的编排框架之一是 AutoGen。系统是否稳健，取决于三点同时到位：路由模型能力强，推理能力好，子智能体的职责范围受限。智能体加多了，并不意味着可以不去规定它们的行为。

路由器需要清晰的工具描述和明确的路由指令，边界情况也要写进去。要写清楚：工作从路由器交给子智能体、再转给另一个智能体时，分别该发生什么。有了这些交接指令，模型能选出下一步该走哪个环节，而不是反复尝试那些推进不了任务的动作。

每个子智能体应当负责一项具体、独立的任务，手上只配一小组完成任务所需的工具。这样一来，大系统内部依然保留了单智能体设计的简单性：协作变多了，但每个参与者的职责仍然很窄。

06

让人工审核成为一条执行规则

智能体能自主行动，就需要划一条安全边界。以 Gmail 智能体为例：发邮件之前，它应该先请用户批准拟好的邮件。这时邮件还处于待发状态；智能体提议发送，不等于获得了发送的许可。HR 支持和金融分析场景里，也有类似的审核要求。

人工审核可以由写成代码的规则触发。 与其让人工介入全凭运气，不如事先定义好：满足哪些条件时，工作流必须停下来交给人。

这些规则可以设在工具调用的前后两侧：

- 执行前： 对拟执行的动作（比如发邮件）请求许可。 - 执行后： 先审核工具返回的信息，再允许智能体继续处理。

第二个检查点的作用不同：它管的是结果怎么用，而不是批准一个已经发生的动作。

07

评估通往答案的路径

一个合格的智能体，要在合适的时机选对工具，传入准确的参数，根据执行结果推理，出了问题还能自己恢复。用户主要关心最终答案。开发者还得看到得出答案的那些中间决策，因为答案看起来说得通，并不能说明这些决策都是对的。

拿查天气的例子来说，这几个阶段就很具体了。用户问纽约市 2 月 5 日的天气，预期的工作流是：

1. 选择合适的天气工具。 2. 传入地点和日期这两个必填参数。 3. 拿到工具的执行结果。 4. 解读结果，生成最终回复。

示例回复说纽约市大部分时间晴朗；这只是用来演示工作流，不是经过核实的天气预报。每个阶段都给了开发者一个单独的位置去排查故障。

Cohere 会构建黄金评测集，把整条路径上每一步的预期都记录下来：

| 评测项 | 用来确定什么 | |---|---| | 用户查询 | 交给智能体的任务 | | 预期函数调用 | 应该选哪个工具 | | 预期参数 | 工具应该收到什么输入 | | 预期工具输出 | 智能体应该基于什么结果推理 | | 预期最终回复 | 用户应该收到什么 |

把这套语料放进智能体框架里跑一遍，就能定位行为是在哪个阶段偏离预期的。工具选错了，和参数传错了、或者工具结果没错但最终答案解读错了，排查方向各不相同。正因如此，可观测性在选框架时就该考虑进去，而不是等到事后调试时才补上。

08

让缓解措施与观察到的失败相匹配

自主智能体确实会出错，所以评测之后必须有修复策略。如果故障严重程度低或出现频率低，Desai 建议先从提示词工程入手：改进工具 API 的规格，把输入说清楚。这些改动可以弥补剩下的性能差距，不必马上动模型。

如果是特定任务上的工具调用故障或幻觉，比例在 10–20% 之间，Desai 建议构建一个有针对性的标注数据集。这是 Cohere 根据经验得出的实用判断，不是通用的决策分界线。演讲没有讲这个数据集后续怎么用，所以不要把这一步直接等同于微调。

如果故障率很高，Cohere 会用合成数据构建更大的语料，然后微调模型。Desai 特别提到，这种做法适合那些很难调用的 API，或者名字相近、需要模型区分清楚的 API。整个升级路径是：先把现有的接口约定讲清楚；如果根本难点还在，再补充更多针对任务的训练材料。

09

提升模型的工具调用能力

框架设计、编排和故障缓解之外，还有另一条工作线：提升基础模型本身调用工具的能力。Desai 提到 BFCL V3 是衡量工具调用的一个基准，并称 Cohere 在上面表现不错。这里的说法只是定性的，并没有给出具体分数或排名。

Desai 特别介绍了一个 70 亿参数的模型，用来回应市场对轻量级工具调用模型的需求。他在口头讲解中没有说出模型名字。不过它在架构中的作用很清楚：模型层面的工具调用能力更强，可以和围绕模型搭建的约束与评测相互补充。

10

North 把工作流整合进一个产品

North 把前面在框架、智能体设计和企业部署上的经验打包到了一起。按 Desai 的介绍，演讲中展示的版本是单容器部署，带 RAG，能访问向量数据库和搜索，并能连接 Gmail、Outlook、Drive、Slack 等应用。这个产品既能用来使用智能体应用，也能用来构建智能体应用。

收尾的演示把 North 连上了 Gmail、Slack、Salesforce 和 Google Drive。用户问了一个关于 Salesforce 商机的问题，系统随即去检索相关文档。界面上会展示 Desai 所说的推理链，以及调用了哪些工具、各自输出了什么。这些活动细节显示在表格结果上方，回答背后做了哪些工作，都能查看。

接下来查的是最近的对话。Desai 介绍说，Salesforce 的调用用的是类似 SQL 的查询，然后演示了用户怎样纠正工具选择。纠正之后，系统调整了做法，改用 Gmail 检索相关信息。演示真正的落点就是这个修复闭环：查看智能体的活动，发现工具选得不合适，再把它引向任务真正需要的数据源。

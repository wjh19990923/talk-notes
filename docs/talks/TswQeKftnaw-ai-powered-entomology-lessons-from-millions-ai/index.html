AI 驱动的“昆虫学”：数百万次 AI 代码审查的经验

Diamond 的开发历程说明，找到 bug 只是开始：AI 审查者必须挑选出有用的评论，然后衡量开发者是否会据此行动。

熟悉 pull request 和代码审查就足够了；不需要机器学习背景。

01

AI 能找出 AI 帮着制造的 bug 吗？

AI 写的代码越来越多，它能不能顺便把随之而来的 bug 也找出来？带着这个问题，Graphite 联合创始人 Tomas Reimers 和团队做了 Diamond，一个接入 GitHub 的 AI 代码审查工具。项目在这次演讲前大约一年启动。当时团队发现，AI 生成的代码在增加，bug 也在增加。Reimers 把这项工作称为“AI 驱动的昆虫学”（entomology），也就是研究 bug 的学问。

最初的实验很简单：把一个 pull request 交给 Claude，让它找 bug。结果里有一个 Graphite 自家代码库中的真实故障：某些代码路径直接返回了数据库 ORM 类，却没有实例化它。Reimers 说，这会让服务器崩溃。另一个例子发在 Twitter 上，涉及 border-radius 的计算。按他的描述，代码除以了一个负数，导致前端崩溃。这个例子能说明审查工具会标出哪类问题。但单凭这句口头描述，解释不了崩溃的原因，因为除以负数本身并不会出错。

02

一条正确的评论仍可能不受欢迎

能找到真 bug，不代表审查工具一直有用。它确实抓到过问题，但也会建议把代码改成它本来就在做的事，会把合法的 CSS 行为说成不合法，还会仅仅因为代码以前那样写，就要求恢复旧行为。有用的评论攒下了信任，这些评论又把信任一点点耗掉了。

第一个解释是能力边界：有些问题 LLM 能发现，有些发现不了。如果问模型“别人会在这个 PR 上留什么审查意见”，等于鼓励它模仿代码审查的全部活动。这里面既有它能力范围内的评论，也有超出能力的评论。把这些能力分门别类后，情况有所好转，但还剩另一类让人烦的输出：要求给某个类写文档、把逻辑抽成函数、补测试。这些建议在技术上站得住脚，却未必值得打断开发者。

后来，开发者和设计师一起翻看人类和机器人留下的历史评论，区别才清晰起来。哪些评论可以接受来自 LLM，开发者的看法大体一致。设计师却对其中一些判断感到困惑：表面上差不多的评论，得到的反应却不一样。原因在于，开发者评判的不只是对错。同一条建议，同事提出来可能很受欢迎，换成自动审查工具提出来，就显得吹毛求疵、惹人烦。模型能力和开发者的接受度是两个独立的维度。有用的审查工具必须两头都满足。

03

从真实的审查中构建分类体系

Graphite 反复让多个 LLM 给 10,000 条评论分类，评论来自自家代码库和开源代码库，再把分类结果汇总起来。这样就有了一套词汇，用来讨论审查者实际在说什么，而不是把每条评论都当成 bug 报告。

| 评论类别 | 指出的问题 | |---|---| | Bug | 导致意外行为的逻辑矛盾 | | 误提交的代码 | 无意中混进来的代码 | | 性能隐患 | 潜在的性能问题 | | 安全隐患 | 潜在的安全问题 | | 文档不一致 | 代码和描述对不上 | | 风格调整 | 注释或写法不符合本地约定 |

不同类别需要不同的判断。比如文档不一致，只能说明两者有出入，错的是实现还是文字说明，还说不准。风格建议则可能要先知道这个仓库遵循哪种写法。

有些评论很受欢迎，需要的信息模型却拿不到。资深开发者可能会解释：团队以前用过某种做法，后来因为某个原因放弃了。如果这段历史只存在于开发者的脑子里，审查工具就没法从代码里还原出来。这类团队内部的隐性知识（tribal knowledge），属于分类图中“想要但很难做到”的那一侧。

04

最佳实践建议需要一个出现的理由

反过来的问题是：有些建议模型张口就来，开发者却未必想要，比如给这个函数写注释、补测试、抽出一个类型、把这段逻辑挪进函数里。人类审查者会结合具体情况判断：这段逻辑在这个代码库里是不是格外难懂？会不会有人看错？抽出来真的有帮助吗？缺了这层判断，机器人几乎在任何地方都能提出站得住脚的整洁性建议。一条评论该不该出现在审查里，光看技术上对不对是不够的。

上下文多了，边界也会跟着变。仓库代码、过往历史、风格指南和明确的规则，都能帮审查工具判断哪些建议适合这个项目。Reimers 认为，上下文越多，“模型提得出、开发者也乐意接受”的评论范围就越大。眼下实际能瞄准的，是现有上下文所能支撑的那块交集。

05

随着审查器的变化不断检查边界

离线做出的分类法能指明最初的方向，却没法保证一个不断变化的审查工具始终有用。Graphite 更新了提示词，只让模型提出能力范围之内、开发者也愿意收到的评论。Reimers 说，从零散的反馈来看，大家对评论的接受度提高了。接下来的问题是：系统不断演进，怎样让这种表现保持下去。

换成 Claude 4，或者用 Opus 替代 Sonnet，同样的问题又会冒出来：审查工具还落在图中有用的那块区域里吗？加入更多上下文，也带来一个相关的机会：以前够不着的一些有价值的评论类别，现在也许能做了。Graphite 先从审查工具实际产出的评论类型分布入手。Reimers 强调，这个分布只反映 Graphite 自己的观察。它描述的是审查工具输出了什么，本身并不能衡量这些输出成不成功。

06

用表情反馈检测越界

Graphite 给审查评论加上了表情点赞和点踩，专门用来收集能力不足方面的反馈。点踩数突然飙升，可能说明模型出现了幻觉，或者审查工具被推到了它无法可靠判断的地方。应对办法是再次收窄它的行为范围。这样，表情反应能用来发现问题，但第二个维度，也就是开发者想不想要这些评论，仍然很难衡量。

Reimers 说，演讲时点踩率低于 4%。他没说明分母是什么，所以不能把这个数字当成误报率或幻觉率。更根本的是，没人点踩，不代表评论真的帮人改进了代码。要回答这一点，得看评论之后发生了什么。

07

衡量被要求的修改是否真的发生

审查评论通常是在请人改代码。于是 Graphite 开始统计：评论之后真的出现了对应改动的，占多大比例。统计范围包括开源仓库，以及通过自家代码审查产品能接触到的仓库。这样，“有没有用”就变成了一个能观察到的结果：要求的改动到底有没有发生？

Reimers 说，人类审查评论中约有 50% 会在同一个 PR 里促成改动。这给机器人定了一个实际的目标：达到人类反馈的采纳水平。观察窗口的选法很关键。开发者可能同意某条评论，但把修复留到后续 PR；有的建议针对的是以后的工作，而不是当前的改动；有些个人偏好不去落实，也完全合理。健康的审查文化本来就容许分歧，所以没被采纳的评论，不一定就是失败的审查。

Reimers 说，截至 3 月，Diamond 在 PR 内的采纳率达到了 52%。他认为能追平人类基准，靠的是给审查工具写对了提示词。这些数字是报告出来的采纳率，不是 bug 检测准确率。演讲也没给出样本量和足够的对比细节，没法证明它在统计上胜过人类审查者。这个结果能支持的结论更窄，但依然有用：把审查工具限定在合适的评论范围内，开发者按它的要求去改代码的比例，大致能达到观察到的人类水平。

Diamond 是 Reimers 介绍的生产级产品，这些发现就落地在它身上。背后的思路是把范围和反馈连起来：挑出模型能处理、开发者也欢迎的评论类别，再衡量这些评论有没有带来改动。正是这套做法，把“偶尔能抓到个 bug”的能力，变成了大家真正用得上的代码审查产品。

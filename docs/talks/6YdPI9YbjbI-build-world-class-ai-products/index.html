如何打造世界级的 AI 产品

Notion 的评测工作流和一场 Braintrust 更新日志工作坊，展示了如何把产品预期、生产 trace 和人工反馈变成可重复的测试。

对 LLM 提示词、检索增强生成和 TypeScript 有基本了解，有助于理解工作坊示例。

01

当一次成功的演示还不够

Your prompt finally works on the train to work, or produces a convincing answer in a demo for a VP. What tells you it will work consistently for the people using the product? Evaluation and observability turn that isolated success into an engineering process. Sarah Sachs estimates that Notion’s team spends 10% of its time prompting and 90% evaluating, improving evaluations, and inspecting usage in Braintrust. The work extends beyond engineers running experiments: technical leads, leadership, data labelers, and specialists all inspect the same system.

Notion’s connected workspace combines documents, project management, and asynchronous work with tools such as Slack, Jira, and Google Drive. Sachs reports more than 100 million Notion users overall—not 100 million active AI users. Trials for almost all its AI products mean a feature’s potential audience extends well beyond paying AI customers. That creates a difficult combination: broad availability, the polish expected of a design-driven product, and rapid adoption of new foundation models alongside Notion’s own fine-tuned models. Sachs says new models usually reach production users in less than a day. Evaluations provide the evidence needed to move at that pace.

The AI product suite shown next makes the scope concrete. Meeting notes combine speech-to-text transcription with generated summaries; task-database integration and workspace-aware action items are described as forthcoming. Enterprise search helps recover context from a long Slack thread without reading every message. Deep research goes further, executing parallel searches and using reasoning to choose tools and spend more time on a task. That is a transition from a fixed sequence of steps toward an agent deciding which steps to take.

02

更强大的产品带来更难的评测数据

Sachs traces Notion AI’s beginnings to before ChatGPT, starting with an inline AI Writer that generated text on a page. Database Autofill expanded the unit of work: AI could act across database properties, run frequently, and translate content into different languages across columns. That produced usage the team had not anticipated and coincided with building a dedicated AI team. Retrieval-augmented Q&A then brought the data platform into the work. Offering it to free users meant maintaining embeddings broadly and handling multilingual workspaces. Cross-app search and attachment search followed, before the newest suite. Each layer used what the models could reliably do at the time.

Because Notion employees use Notion to build Notion, internal usage supplies abundant training and evaluation examples. The bottleneck became understanding them. Human specialists were looking through prompt dumps in Google Sheets, writing formulas to recover what the user had actually asked, and trying to inspect few-shot examples inside that representation. More rows did not solve that problem. The team needed a way to extract high-quality labels and insights, manage large datasets, and retain development feedback such as thumbs-down responses.

03

把一个 Jira 连接器变成一个有针对性的测试

Suppose universal search is gaining a Jira connector. The evaluation problem starts with product semantics: can the AI recognize a task, understand a sprint, and construct a useful query against the workspace? Notion’s data specialists build handcrafted examples from logs and prototypes. Their role combines product management, analysis, and annotation; on a smaller team, the people closest to the data may be a PM or an engineer.

The iteration procedure is deliberately small at first:

1. Curate ten examples. Check that their structure contains the information the task and evaluators will need before generating more. 2. Inspect the data before choosing scores. Define product-specific success criteria instead of selecting a generic scorer first. 3. Use deterministic checks where possible. For the targeted Jira cases, inspect whether the tool query actually specifies Jira. 4. Run the evaluations, inspect failures, and revise. The dataset, scorer, and application all remain open to improvement.

This avoids a costly failure mode Sachs has encountered: creating a large amount of dummy data in the wrong format.

Multilingual behavior needs its own targeted examples. A Toyota workspace may contain Japanese and English, and a Japanese request does not by itself settle which language the requested paragraph should use. The product team must decide the intended behavior, encode it in a curated dataset, and check that a change preserves language switching. Notion runs these evaluations before shipping relevant changes as a form of ad hoc CI. At the time of the talk, it does not run them on every CI submission: evaluation duration and the volume of code changes make that too expensive for its existing pipeline.

Inspection also changes the product specification. Internal thumbs-down logs for research mode showed that people often wanted to draft reports, rather than conduct research alone. PMs and designers could see that behavior directly in Braintrust. The same trace that helps an engineer find a failure can serve as user research into what someone expected the feature to accomplish.

04

把预期写成规则，而不是冻结的答案

An LLM judge can apply one criterion—such as concision or faithfulness—to every row in a dataset. Notion also uses a more laborious approach: write a particular evaluation prompt for an individual example. A rubric might require Japanese, a specific bullet format, coverage of specified topics, and a reference to page A. Those requirements express acceptable behavior more directly than character-level similarity to a golden answer. Levenshtein distance cannot tell whether a differently worded response satisfies the user’s needs, while one exact reference answer can reject useful variation.

Rules also help when the underlying content changes. For an offsite search, the expectation can be that the first result is the most recent document about the Q1 offsite. A new document may appear after the example was created. A fixed document ID would then encode stale expectations, whereas the recency rule can remain useful. The evaluator still needs enough context to assess the rule, but the dataset no longer depends on one historical answer remaining correct forever.

This evaluation structure supports selective model replacement. Notion has different prompts for different tasks and different models behind those prompts. When Nano becomes available, Sachs describes gathering high-frequency tasks that need speed and low cost more than advanced reasoning, running their evaluations, and switching only the prompts where the candidate performs well. The evaluation assets and model-selection logic are part of the product’s intellectual property, alongside prompts and application code.

The stakes are particularly clear for language coverage. Sachs reports that 60% of Notion Enterprise users are non-English-speaking, while all Notion AI engineers speak English. Rigorous multilingual evaluation lets the team inspect experiences its own everyday usage would otherwise underrepresent.

05

评判者需要一个范围——以及有人去检查它的失败

The Q&A clarifies that a unique judge for one thumbs-down example can coexist with judges that cover an entire dataset. Notion has built layers over the Braintrust SDK to help specialists author these prompts. A dataset row also need not represent a complete interaction: the team can extract one call from a sequence of five LLM calls and evaluate that stage alone. Automated prompt optimization has been tried, but Sachs has not found that it solves most of Notion’s problems, even though she has heard other teams report success.

Historical feedback and current evaluation scores answer different questions. Some alpha users authorize evaluation access through submitting feedback. A thumbs-up is not a consistent quality label, although internal positive examples sometimes seed fine-tuning data. A thumbs-down from September 2023 identifies a request the system handled poorly then; it does not prescribe the score a new implementation should receive today. The durable asset is the request and available workspace context. The application, prompt, model, and resulting answer can all change when that case is rerun.

Sachs believes Notion’s judge scores use a scale that is not particularly well calibrated. In practice, the team collects cases below a threshold and treats them as failures for human inspection. With thousands of samples, another LLM summarizes failure themes and differences between experiments into a report for the engineer. More elaborate calibration has not been a priority for this workflow. Pairwise comparisons are useful when choosing between methods or protecting a production control; they are less common during exploratory development or alpha testing, where the desired experience is still being discovered.

A passing score only covers the criteria the judge was asked to check. Notion initially used graders to catch regressions in its special Markdown format, bullet usage, and topic coverage. Those graders could approve an answer that had switched to the wrong language. As thousands of criteria accumulate, they can acquire authority without anyone examining what they miss. Sachs recommends either separating tasks such as formatting and language following, or keeping a small set of judges whose failures the team commits to reviewing.

06

控制检索输入，规划模型降级方案

A question such as “When is our next offsite?” exposes a second source of evaluation instability: the search index changes. Index freshness and the date of evaluation can alter the answer before generation begins. Freezing an entire index is expensive, especially when the relevant documents are not known in advance. Notion instead separates retrieval evaluation from downstream generation evaluation.

| Evaluation target | What is controlled | What is examined | |---|---|---| | Retrieval | Search setup and available index | Whether the right material was retrieved | | Downstream generation | A fixed set of retrieved results | What the remaining pipeline does with that material |

Retrieval has its own evaluation framework around vector databases and Elasticsearch. For generation, the task assumes the captured results were retrieved and executes the remaining steps. If a sample cannot be evaluated because the answer was absent from the index, the team drops it. Reconstructing historical indexes also raises privacy problems: an object’s permissions may have changed. Heavy internal usage helps supply fresh, natural cases without repeatedly reconstructing old workspace states.

Managing prompts becomes an operational problem during provider outages. Notion has hundreds of prompts, including model-specific variants. Moving all GPT-4o mini traffic to Claude Sonnet 3.7 is not a uniform fallback strategy: an expensive replacement might be acceptable for one feature and untenable for frequent database operations. For database Autofill, Sachs describes a fallback that could cost 12 times more and create millions of dollars in additional expense during an outage. That is her workload-specific example; the traffic, duration, and pricing assumptions are not specified.

The practical solution is ownership. Each product or prompt owner preselects an acceptable fallback in code or configuration so the on-call engineer can switch traffic without rediscovering the trade-offs during an incident. Retrofitting that configuration required gathering everyone who had written a prompt. Sachs wishes the team had established it from the beginning.

07

用任务、数据集和打分器构建一个评测

Carlos Esteban and Doug Guthrie turn the case study into a workshop: first the playground, then the TypeScript SDK, production logging, human feedback, and finally remote evaluations. The questions remain product questions: did a change cause a regression, is a cheaper model sufficient, does the output match the brand, and can failures be diagnosed? Prompt versioning, automated evaluations, and production observability give technical and nontechnical collaborators a common place to answer them.

An evaluation is a structured test with three components:

- Task: the prompt or code being tested, from a single model call to a complete agent workflow. - Dataset: the examples supplied to the task. - Scorer: the logic that assesses each output against a chosen criterion.

The workshop uses normalized scores from 0 to 1, displayed as percentages. Offline evaluations run predefined examples during development. Online evaluations score live application outputs, helping identify failures and capture cases for the next offline dataset.

Before optimizing the application, compare the score with your own inspection:

| Human inspection | Evaluation score | Where to investigate | |---|---|---| | Good output | High | Preserve the behavior | | Bad output | Low | Improve the application | | Good output | Low | Investigate the scorer | | Bad output | High | Investigate the scorer’s blind spot |

Agreement makes a score useful. Disagreement is evidence that the measurement itself needs attention, rather than an instruction to optimize blindly toward it.

In the playground, a task can combine a system prompt with Mustache-templated user input. Extra messages package a conversation—including assistant responses and tool calls—into one evaluation context. Tools pushed to the Braintrust library become available to playground users and experiments. The agent feature shown in the recording chains prompts so one output becomes the next input; it is described as beta, with branching still forthcoming.

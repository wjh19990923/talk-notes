MCP 的未来是一套面向生产级智能体的完整连接技术栈

David Soria Parra 解释了为什么生产级智能体需要互补的连接方式、渐进式的工具发现、程序化的组合、更丰富的 MCP 应用，以及一个可扩展性更强的协议。

MCP 的未来是一套面向生产级智能体的完整连接技术栈

01

从工具协议到共享的应用基础设施

MCP 应用让服务器在提供工具的同时，一并交付一个界面。这个界面不写死在某个产品里，不在客户端临时生成，也不靠插件或 SDK 分发。服务器提供的是一种兼容客户端都能理解、都能渲染的东西。David Soria Parra 举了几个能运行这类服务器的环境：Claude、ChatGPT、VS Code 和 Cursor。 0:15

架构上的关键是共享语义：客户端和服务器都要知道界面存在、该怎么呈现、交互该怎么进行。应用和工具结合起来，还带来两种互补的使用方式：人直接操作界面，模型则通过配套的工具来操作。 0:15

Soria Parra 回顾了 MCP 的演进。它最初只是一个仅限本地的规范，配几个 SDK 和基础工具；如今已经发展成一个完整的协议，支持远程运行、集中授权、elicitation、任务以及实验性的应用。他提到，MCP 每月下载量约 1.1 亿次。这个量级不只来自直接使用，也来自 OpenAI agents SDK、Google ADK、LangChain 等框架对它的依赖。公开的例子有 WhatsApp、Blender、Linear、Slack 和 Notion 的集成；不过他说，大多数服务器其实是在企业内部，默默把私有系统接给智能体。 1:34 2:46

- MCP 应用让服务器直接交付界面，不同产品里的兼容客户端都能渲染。 - 协议层的共享语义负责协调界面呈现：人用应用，模型用工具。 - MCP 从本地工具扩展到远程运行、集中授权、elicitation、任务和实验性应用。 - 月下载量约 1.1 亿次，说明各类智能体框架和集成都在用它，其中包括企业私有系统。

02

生产智能体需要多种连接能力

编程智能体的工作条件格外优越：它们通常在本地运行，能用编译器验证结果，出了问题身边还有开发者随时介入。Soria Parra 认为，面向更广泛知识工作的智能体，碰到的是另一类问题。财务分析师或市场人员需要的智能体，可能要同时连通好几个 SaaS 应用和一个共享网盘。这时，连接能力就是产品的核心，而不是附带功能。 3:59

他提出的连接技术栈分三大类：Skills 负责可复用的领域知识；MCP 负责协议层的互操作和更丰富的语义；CLI 或 Computer Use 则用在适合它们的环境里。没有哪种方法是万能的，选哪种要看智能体本身、可用的执行环境和具体任务。 5:06 17:03

CLI 对本地智能体特别好用：在 bash 里天然就能组合，模型能自己摸清它有哪些能力，用法也和 GitHub、Git 这些熟悉的工具一脉相承。但这些优势有前提，比如要有沙箱、能执行代码，而这些前提并不总成立。如果应用需要平台无关、需要长时间任务的接口，或者需要资源、授权、治理、策略，又或者要用 MCP 应用、Skills over MCP 这类更丰富的功能，MCP 就更有优势。 6:02

- 编程智能体能在本地验证结果；知识工作智能体不同，需要连通各种 SaaS 应用和共享网盘。 - Skills 提供可复用的领域知识；MCP、CLI 和 Computer Use 各自满足不同的连接需求。 - 智能体有沙箱、有代码执行环境时，CLI 能在 bash 里自然组合。 - MCP 支持更丰富的语义、平台无关、授权、治理、资源，以及长时间任务的接口。

03

让客户端负责渐进式发现

Soria Parra 认为，上下文占用过多，不该想当然地算到 MCP 头上。协议只负责在系统之间传递信息；决定这些信息怎么进入模型上下文的，是客户端或智能体框架。早期实现常常一启动就加载所有可用工具，集成一多，上下文窗口就无谓地膨胀起来。 7:12 8:20

他给出的替代方案是渐进式发现（Progressive Discovery）。客户端不在启动时把所有工具定义都塞进上下文，而是给模型一个类似 Tool Search 的机制，等某个工具用得上时再单独加载。这相当于把一份常驻的工具目录，换成按模型当下需要随时查找。 8:20

Soria Parra 说，Anthropic 的产品和 API 已经支持这种模式，竞品的 API 上也能用，应用开发者也可以自己实现。他展示了一个例子：引入这种模式后，工具占用的上下文大幅减少；不过文字记录里没有给出具体数字。更深一层的启示是：连接能力要想扩展，靠的是用心设计客户端，而不是一味多接几个服务器。 7:12 8:20

- 决定哪些可用工具进入模型上下文的，是智能体框架，而不是协议。 - 渐进式发现借助 Tool Search，把工具定义推迟到模型真正需要时再加载。 - 按需加载工具，可以在现有产品、API 或自建的智能体应用里实现。

渐进式发现 模型确认需要某个工具后，客户端才加载它的定义。 - 模型需要工具 — 任务产生了对某种能力的需求。 - Tool Search — 模型查找相关工具。 - 按需加载 — 客户端加载选中的工具。 - 模型需要工具 → Tool Search（触发查找） - Tool Search → 按需加载（需要时加载）

04

通过代码组合工具，并为智能体设计服务器

客户端的第二种模式是程序化工具调用（Programmatic tool calling），也叫 Code Mode。如果模型调一个工具、读返回结果、再调下一个，如此循环，每一步编排都得走一次推理。Soria Parra 认为这会拖慢速度，效果也可能不如让模型直接写一段脚本，把所需操作一次编排好。 9:36

一种实现方式是提供执行环境，比如 V8 Isolate、Monty 或 Lua 解释器。生成的代码在里面组合工具、过滤结果、继续处理，不必把每个中间决策都绕回模型。MCP 的 Structured Output 能描述返回值、提供类型信息，让组合更容易。拿不到这些信息时，Soria Parra 建议用一个更便宜的模型，把输出提取成预期的结构。 10:33

这些思路也改变了服务器的做法。Soria Parra 不赞成把 REST 端点机械地一对一转成 MCP 工具；服务器作者应该琢磨智能体或人实际怎么完成任务，再围绕这一点设计能力。程序化执行可以放在客户端，也可以放在服务器端。他举了 Cloudflare MCP 服务器的例子：它提供的是一个执行环境，而不只是一个个孤立的工具。在他看来，这种做法能省 token、降延迟、让组合能力更强。他也鼓励服务器作者在确实有帮助的地方，用上应用、Skills、Task 和 Elicitations 这些语义。 11:45 12:40

- 程序化工具调用让生成的脚本直接组合工具操作，不再每一步都绕回模型编排。 - V8 Isolate、Monty、Lua 等执行环境可以运行生成的代码，并过滤中间结果。 - MCP Structured Output 提供返回值的类型信息；没有这些信息时，可以用更便宜的模型提取结构化结果。 - 围绕智能体的实际任务设计 MCP 服务器，不要把 REST 端点直接映射成工具。

程序化工具组合 生成的代码借助结构化的返回信息，执行并组合工具。 - 生成代码 — 模型编写编排逻辑。 - 执行代码 — V8 Isolate、Monty 或 Lua 运行脚本。 - 组合工具 — 脚本协调各项工具操作。 - Structured Output — 返回值类型指导组合。 - 过滤结果 — 先精简中间 JSON，再继续处理。 - 生成代码 → 执行代码（运行生成的脚本） - 执行代码 → 组合工具（执行编排） - Structured Output → 组合工具（提供类型信息） - 组合工具 → 过滤结果（过滤中间输出）

加强传输、身份、发现和扩展机制

Soria Parra 列出了协议层面几处仍待解决的局限。他说，目前的 HTTP 流式传输方案，大型云厂商很难扩展。Google 支持的一项提案——无状态传输协议（Stateless Transport Protocol）——想让 MCP 服务器更像大家熟悉的无状态 REST 服务，能直接部署在 Cloud Run 或 Kubernetes 上。他还把异步任务看作智能体间通信的实验性基础，但目前支持这项能力的客户端很少，还需要更多客户端跟进。 13:49

SDK 和企业功能的路线图里，有 TypeScript SDK 第 2 版和 Python SDK 第 2 版，吸收了过去一年的经验教训。Soria Parra 特别提到，FastMCP 的 Python SDK 比他们团队自己发布的那版好用。他还介绍了 Cross App Access：用户通过公司的身份提供商（如 Google 或 Okta）登录一次，之后访问 MCP 服务器就不用反复登录。 14:52

另一项提案是服务器发现（Server Discovery）：规定智能体、浏览器和爬虫如何通过 well-known URL 找到 MCP 服务器，而不只靠解析普通网页。扩展机制带来了明确的兼容性取舍：不是每个客户端都支持每项能力，比如在网页里渲染的 MCP 应用，就很难放进 CLI 界面。还有一项计划中的扩展叫 Skills over MCP，服务器作者可以借它分发并持续更新领域知识，帮智能体用好复杂的服务器。Soria Parra 指出，共享的协议语义虽然还没定稿，现在已经可以用一个加载 Skills 的工具，粗略实现类似效果。 14:52 16:05 17:03

所以，整体方向不是用 MCP 取代 CLI、Computer Use 或 Skills，而是让这些方法在一个更强的智能体技术栈里协同工作。Soria Parra 把协议的演进看作开放社区的共同事业，离不开持续的反馈。他也承认，眼下的智能体、框架、客户端支持和协议细节，都还有很大的改进空间。 7:12 17:03

- 无状态传输协议的目标是像 REST 服务一样可扩展地部署；异步任务要撑起智能体间通信，还需要更多客户端支持。 - TypeScript SDK 第 2 版和 Python SDK 第 2 版吸收了早期 SDK 的经验。 - Cross App Access 复用公司身份提供商的认证；Server Discovery 通过 well-known URL 定位 MCP 服务器。 - Skills over MCP 让服务器作者分发持续更新的领域知识；扩展能不能用，取决于客户端的能力。

不破不立：为 AI 智能体构建自我改进的技术栈

智能体评测从单次工具调用开始，扩展到轨迹和完整对话，最后通过检验评估器本身是否正确来闭合循环。

你需要了解 LLM 智能体如何调用工具，以及如何利用对话上下文决定下一步。

01

当一张电子表格说不清什么变好了

团队在 Excel 表格里换提示词，对比几条模型输出，觉得哪个版本好就上线哪个。可模型和工具定义本身也可能在同步变化。到底是哪处改动起了作用，又在哪些样例上起了作用？没有系统化的对比，结果再好看，也很难沉淀成一套可重复的开发流程。

问题还在于谁能参与进来。产品经理和领域专家也需要一种方式，把自己的判断放进同一套评测流程。Arize 联合创始人 Aparna Dhinakaran 认为，智能体开发的关键就是把这些判断系统化。智能体上线生产后，问题会变得更具体：哪个子智能体或哪次工具调用总在给出糟糕的回答？那里需要改什么？

评测范围要跟着被测行为的范围走。 工具调用要检查选得对不对、输入对不对；轨迹要检查整串调用；对话要跨轮检查，看前面的上下文有没有用到后面的回答里。想改进智能体，也得同步改进那些负责找出失败的评测。

02

把工具选择与参数正确性分开

一个带多个工具的智能体，首先要判断眼下该采取哪个动作。这个判断取决于用户的请求、之前的对话上下文，以及已经执行过的动作。选定工具后，它还要从上下文里提取参数。这两步各有各的出错方式。

| 检查项 | 问题 | |---|---| | 工具选择 | 下一步动作用这个工具合适吗？ | | 参数正确性 | 输入与请求、上下文和必填参数相符吗？ |

工具名选对了，不代表这次调用就是对的。把两个判断分开，结果才能直接指导下一步：路由出错和输入提取出错，修法完全不同。

03

从需要关注的路径开始

演示接着转到 Arize 自家的 copilot。这个智能体帮用户排查应用性能、定位问题、寻找可能的改进点。Arize 会记录用户提问的 trace，再用自家工具评测这些交互。有了 trace，回答背后的每一步都能拿出来检查。

打开单条 trace 之前，Dhinakaran 先通盘看了智能体可能走的各条路径。这个 copilot 采用编排者-工作者模式：顶层规划器决定把请求发往哪里，工具负责执行接下来的动作。工具的输出还可能交给另一个路由器或编排器，再由它挑选下一个工具。所以最终的回答可能取决于好几层决策。

在规划器这一层，值得问的是：这些路径的质量从哪里开始拉开差距？Dhinakaran 说，屏幕上的 copilot 搜索问答结果大约一半对、一半错。录像没有给出这个粗略结果的样本量、采集时段、模型或评测器配置。但它指明了排查方向：评测结果更健康的路径可以先放一放，搜索更值得优先关注。

04

顺着一个失败的答案追到它的参数

聚合视图负责缩小范围，trace 负责给出诊断。Dhinakaran 按一套具体的下钻步骤来排查：

1. 选中搜索问答正确性评测。 2. 筛出标记为错误的样例。 3. 打开一条失败的 trace，查看整条 trace 的评测结果。 4. 逐个检查工具调用，把函数选择和参数正确性分开看。

同一条 trace 里，整体回答可能失败了，某个局部决策却是对的。正因为能分清这一点，下一步检查才有意义。

在选中的样例里，函数调用评测判定为正确，参数评测却判定为错误。评测器给出的解释是：参数与必填参数不符。Dhinakaran 判断，问题很可能出在工具选对了，却没按这段对话的上下文给对参数。演示停在了诊断这一步，没有展示实际的修复。

下面这段简短的 Python 测试样例，说明了为什么要把两个结果分开。用户想搜索如何复制仪表盘，智能体选了 search，传入的查询却是关于监控告警的。在这个样例里，精确比较就够用了；真正要诊断的是，参数有没有表达出用户的本意。

```python request = "Find documentation on duplicating a dashboard." expected = { "name": "search", "arguments": {"query": "duplicate a dashboard"}, } actual = { "name": "search", "arguments": {"query": "configure monitor alerts"}, }

checks = { "tool_selection_correct": actual["name"] == expected["name"], "arguments_correct": actual["arguments"] == expected["arguments"], }

assert checks == { "tool_selection_correct": True, "arguments_correct": False, } ```

只打一个“失败”标签，就会掩盖“工具选对了”这个有用的事实。把结果分开记录，既保住了这条信息，又把排查方向引向参数构造。

05

正确的调用仍可能组成一条糟糕的轨迹

copilot 的搜索路径会调用多个子工具。所以逐个评测完每次调用后，还剩一个问题没回答：智能体调用它们的顺序对不对？轨迹评测考察整条 trace 上的调用序列，而不是把每个动作当成孤立的决策。

同一类任务跑多次时，Dhinakaran 关心的是：智能体能否稳定地完成必要的动作，并收敛到合适的步数。某次运行一旦偏到别的顺序上，处理同样的请求就可能多花 token；动作不再构成有效序列时，还可能输出错误结果。这里既看完成质量，也看为此付出的工作量。

屏幕上的工具调用顺序评测结果为错误。这在前面的参数问题之外，又多出一类失败：单个动作可能要改，动作的编排也可能要改。演讲没有给出目标步数，也没有给出实测节省了多少 token。而 trace 级别的判断仍然只覆盖一次交互，于是引出下一个评测范围：对话。

06

在整段对话中传递上下文

一个人与智能体来回三轮的例子，展示了单条 trace 无法完整描述的行为。智能体的语气前后一致吗？明明已经拿到答案，它还在反复问同一个问题吗？就算每条回答单独看都合理，重复提问也会暴露出它没用上之前的交互。

核心要求是：回答第 N 轮时，要用上前 N−1 轮的上下文。所以会话评测比逐条检查回答覆盖得更广：

- 语气一致性： 智能体在各轮之间是否保持了恰当的语气？ - 上下文保持： 它是否用上了之前提供的信息，而不是再问一遍？ - 全程正确性： 它在整个交互过程中是否都答对了问题？

随后，Dhinakaran 打开另一个项目里的一段对话，既看回答对不对，也看有没有漏掉之前的上下文。会话评测检验的是哪些信息能在交互之间延续下来，正好补上工具和 trace 层面检查的空白。

07

在改进智能体的同时改进评估器

工具评测、轨迹评测和会话评测，最终都汇入应用改进的循环：评测智能体，找出它在哪里失败，标注或修正输出，再用这些样例改进它的提示词。评测决定了哪些案例会进入这个流程，所以评测的质量直接影响团队选择去修什么。

出错的也可能是评测器。 用 LLM 当评判者时，应用一直在演进，评判提示词就不能一成不变。要回头检查评测结果本身：一条判为错误的应用回答，也许其实可以接受，是评判者分错了类。如果把每个负面评测都当成应用缺陷，改进流程就会追错目标。

评测器也需要自己的迭代流程：找出误判，改进评测提示词，构建一个黄金数据集并持续完善。两个循环协同运作：

| 循环 | 要检查的证据 | 改动对象 | |---|---|---| | 应用 | 失败的输出和修正后的样例 | 应用提示词 | | 评测器 | 误判和参考标签 | 评测提示词和黄金数据集 |

这里介绍的自我改进技术栈，是一套反复评测、反复打磨的工作流，并不是一个已经演示过的自主优化器。它能否奏效，既要看智能体的行为维护得好不好，也要看用来改进智能体的那些判断是否始终可靠。

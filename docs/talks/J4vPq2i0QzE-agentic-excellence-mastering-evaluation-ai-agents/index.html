卓越的智能体：用 Azure AI Evaluation SDK 掌握 AI 智能体评测

从检查单个模型回复，到测试一个浏览器智能体，再借助数据集、Python 评估器和针对应用的验收阈值来扩大评测规模。

熟悉 Python、模型提示词和调用工具的智能体，有助于理解示例。

01

凭什么证明这个智能体可以交付？

怎么判断一个智能体已经好到可以发布？常规的数据集评测和红队测试一起回答这个问题。红队测试故意给出一些输入，诱导智能体生成有害内容或做出有害行为；常规评测则用一组预期任务来检验智能体。微软首席 AI 布道师 Cedric Vidal 在这场演讲里讲的是后一种流程。

模型和 SDK 一升级，智能体的能力几乎一夜之间就能上一个台阶。Vidal 在准备这次演示时就碰上了。可智能体越自主，出错的代价也越大。试几个提示词，觉得回答不错，就把智能体推上生产环境，这样没检查到的地方太多了。抽查通过只是评测的起点，不能当作发布标准。

所以，评测应该从项目第一天就开始，而且不能只盯着基础模型。Vidal 把整个系统分成四层：

| 层级 | 在演示中的职责 | | --- | --- | | 模型 | 平台层面的模型行为 | | 安全系统 | 平台层面的防护 | | 系统消息与 grounding | 应用的指令和辅助信息 | | 用户体验 | 应用的交互与缓解措施 |

Vidal 说，前两层由 Azure 内置提供，后两层要看应用怎么设计。一个具体的智能体要做到既安全又好用，靠的是指令、grounding 和交互设计，平台防护给不了这些。

02

在平均许多答案之前先检查一个答案

第一步是手动评测模型，因为汇总分数会掩盖单条样例的表现。平均分再高，也说不清某条提示词上到底发生了什么。跑大数据集之前，先挑几个样例仔细看，弄清楚好答案长什么样。

演示用的是 AI Toolkit for VS Code，直接在开发环境里做对比，不用在几个网站之间来回切换，也不用另外打开 GitHub Models。录像里还是 AI Toolkit 当时的名字和界面，现在的文档已经改叫 Foundry Toolkit。Vidal 先提了一个具体请求：一份加咸焦糖黄油的意式奶冻（panna cotta）食谱。

先由 GPT-4.1 给出食谱。接着 Vidal 把同一个请求发给 GPT-4o，左边显示 GPT-4.1，右边显示 GPT-4o。在这条食谱提示词上，Vidal 发现 GPT-4.1 输出更快。他会前看过两边的回答，也更喜欢 GPT-4.1 的版本。不过演讲没有给出计时数据，也没有在受控条件下做基准测试。这一步比的仍是未经定制的基础模型，还没有智能体指令或工具可评。

03

把一个模型变成一个事件抽取智能体

选定模型后，评测范围就扩大到整个系统。Vidal 的应用是一个辅助他做布道工作的助手，能从网站上抓取活动信息，包括议程、演讲、讲者和参会情况。借助 AI Toolkit，他很快就能从这个需求做出一个能用的浏览器智能体。

搭建分两步走，先跑内置示例，再定制自己的智能体：

1. 选择 web-scraper 示例。它会生成一段系统提示词，把智能体设定为网页探索助手，并配置好一个 MCP server。 2. 运行示例。它会启动 Playwright MCP，去探索一个示例域名。 3. 把示例改成抽取活动信息。Vidal 选用 GPT-4.1，要求按指定格式输出活动名称、日期、地点和参会人数。 4. 给智能体一个 Luma 活动页面并运行。Playwright 在页面上导航，智能体返回抽取到的信息。

05

选择指标，再在整个数据集上运行

光靠肉眼检查撑不起规模，要扩大范围，就得在更多样的输入上做可重复的检查。Azure AI Foundry 提供了几类评估器：

| 类别 | 示例 | 用途 | | --- | --- | --- | | AI 辅助的质量评估 | 有据性、流畅性、连贯性 | 评估回答质量 | | 传统 NLP 指标 | F1、BLEU、ROUGE | 与参考答案对比 | | AI 辅助的风险与安全评估 | 内容风险检查 | 评估有害内容 | | 自定义 | 由应用定义的评估器 | 衡量特定任务的要求 |

这些检查既可以在 Foundry 门户里跑，也可以用代码跑。选哪些指标要看应用的用途，不要把所有现成的分数都当成同样有用。

接着 Vidal 打开一个连接 Azure AI Foundry 项目的 Python notebook。完整跑一遍太花时间，他没有现场执行，而是带大家看已有的代码和结果，并答应之后分享链接。核心操作是 evaluate()：传入一个数据集，再配上相关性、连贯性、有据性、流畅性和相似度五个评估器。

Azure AI Evaluation SDK 把两件事分开：给已存的回答打分，和运行应用收集新回答。evaluate() 可以直接从数据集读取回答；传了可选的 target 参数，它就会先调用应用。下面这段 Python 用前面提到的五个质量评估器给已存的回答打分。JSONL 的每一行都要包含评估器需要的输入，包括 query、response、context 和 ground_truth。

```python import os

from azure.ai.evaluation import ( CoherenceEvaluator, FluencyEvaluator, GroundednessEvaluator, RelevanceEvaluator, SimilarityEvaluator, evaluate, )

model_config = { "azure_endpoint": os.environ["AZURE_OPENAI_ENDPOINT"], "azure_deployment": os.environ["AZURE_OPENAI_DEPLOYMENT"], "api_key": os.environ["AZURE_OPENAI_API_KEY"], }

evaluators = { "relevance": RelevanceEvaluator(model_config=model_config), "coherence": CoherenceEvaluator(model_config=model_config), "groundedness": GroundednessEvaluator(model_config=model_config), "fluency": FluencyEvaluator(model_config=model_config), "similarity": SimilarityEvaluator(model_config=model_config), }

results = evaluate( data="responses.jsonl", evaluators=evaluators, ) print(results["metrics"]) ```

这样一来，生成回答的应用和评判输出的模型就分开了。跑评估器时，不必为每一行重新开一次浏览器会话。

notebook 里的样例包括法国首都、最防风雨的帐篷和一张露营桌。Vidal 介绍说，界面上的质量分数在 1 到 5 之间，阈值可以配置，并展示了一个通过的例子。有了逐题结果，就能具体去看哪里没通过，不必只盯着汇总分数。讲到阈值，他把话题转向产品预期：一款允许暴力内容的游戏和一款儿童应用，对“能不能接受”的判断会完全不同。

06

把安全严重程度与验收策略分开

最后一个技术示例把评测扩展到文本加图像。Vidal 也提到支持多轮对话，但没有演示对话的例子。这是两项不同的能力：按当前经典版 SDK 的文档，文本对话可以评测，多模态评测却只支持一条用户消息加一条助手消息。

为了演示图像评测，Vidal 需要一张暴力程度足够触发测试、又能在公开会议上展示的图。评估器给出的解释是：图中角色的头上扎满了大头针或钉子。图像安全结果给暴力项打了 4 分，对照阈值 3 判为不通过。同一份输出里，色情内容和自残两项都通过了。

Vidal 说这个暴力分数低于满分 5 分。但当前的风险与安全评估器文档规定的严重程度量表是 0–7，其中 4–5 属于中等严重。演示里到底用的是哪个历史版本的评估器，已经无从确认。按文档的规则，分数小于或等于设定的阈值才算通过。

放到暴力电子游戏的场景里，Vidal 提议接受 4 分。按上面的规则，把阈值调到 4，结果就会从不通过变成通过，而图像本身和它被评定的严重程度都没有变。他把这个选择和“游戏里允许出现这类画面”联系起来，但调评测阈值改变的只是验收判断，改变不了图像生成器的安全策略或能力。真正有用的设计决策，是把应用能容忍到什么程度明确写下来，再始终按这个标准去测。

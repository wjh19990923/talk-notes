幻灯片原文
A query constructor separates a question into a search for “foo” and an author filter. A translator then formats the query and filter for the vector store.

Self-querying

A self-querying retriever is one that, as the name suggests, has the ability to query itself. Specifically, given any natural language query, the retriever uses a query-constructing LLM chain to write a structured query and then applies that structured query to its underlying VectorStore. This allows the retriever to not only use the user-input query for semantic similarity comparison with the contents of stored documents but to also extract filters from the user query on the metadata of stored documents and to execute those filters.

Self-querying
“What did bar say about foo” → Query constructor → Query: ”foo”
Filter: eq(“author”, “bar”) → Query translator → Query: ”foo”
Filter: {“author”: “bar”} → Vector store

AI 工程 101：用五种 AI 能力构建一个 Telegram 机器人

从一个能跑的 Telegram 机器人出发，逐步加上对话记忆、文档检索、代码生成、图像和语音转写，同时梳理每项能力背后的工程选择。

具备基础 Python、终端命令和 API 概念会有帮助；跟着做机器人练习还需要 Telegram 和相应的 API 凭据。

01

一位新晋 AI 工程师应该会构建什么？

走进一场 AI 工程大会时，每个分会场似乎都默认你读过所有论文、试过所有 API。在此之前，你该先知道些什么？开场要解决的是共同基础的问题：学会已经行之有效的技术，搞懂怎样把一个 AI 想法变成软件，遇到陌生的实现时知道去哪里查。这场由 Noah Hein 主讲的 Latent Space University 工作坊 更像一份“试吃拼盘”，并不承诺一天就让你成为专家。它后面还有 Gradient 的午餐分享会、Anthropic 的提示词工作坊，以及 Charles Frye 的 AI Engineering 201。想跟着动手，需要准备好 Python 和 Telegram Messenger。

整个项目依次覆盖五项能力：调用聊天模型、理解 token 与 embedding、生成代码、生成图像、转写语音。贯穿其中的主线是程序化调用：拿到模型的响应，在应用里用它做点有用的事。在这场演讲里，DALL-E 3 还处于抢先体验阶段。Hein 认为这类工作是一种机会，和构建底层模型基础设施是两回事。他那张搜索趋势幻灯片拿“AI”这个词当代理指标，还把截至 2023 年的数据往后外推。它只是在说明为什么值得学这些技能，算不上对工程岗位的实测预测。

02

从一个只会回应 /start 的机器人开始

所有能力都会放进同一个 Telegram 机器人。工作坊的广播频道负责分发仓库链接和资料；检查点分支让参与者可以从某个能跑通的阶段接着做，不必实时跟着重做每一处修改。机器人本身通过 BotFather 创建：

1. 给 BotFather 发送 /newbot。 2. 起一个显示名称和一个唯一的机器人用户名，比如用你的 GitHub 用户名来起。 3. 保存 HTTP API token，打开机器人的分享聊天链接。 4. 从工作坊仓库的 main 分支开始，按照 README 安装 Python 依赖、准备好环境。

录像里提到的仓库是 inheingit/ai101，2026 年 8 月 28 日查看时已无法访问。它的检查点分支是原工作坊流程的一部分。

应用需要两个凭据：TG_BOT_TOKEN 标识 Telegram 机器人，OPENAI_API_KEY 授权模型调用。配置时把 .env.example 改成 .env，再把这两个值填进去。Hein 演示了怎样申请 OpenAI key，还分享了一个临时的工作坊 key，免得大家卡在这一步。这条捷径不改变架构：Python 进程分别独立连接 Telegram 和 OpenAI。

src/main.py 里先是 import 和加载环境变量，接着是一个 messages 数组和日志配置。Telegram 回调会收到两个参数：update 装着收到的消息和所在聊天的信息，context 用来访问机器人。最初的 start 回调调用 context.bot.send_message，传入 update.effective_chat.id 和一句问候。CommandHandler 把 /start 映射到这个函数；把它注册到配置好 token 的应用上，这个行为就生效了。之后靠轮询拉取新的 update。在仓库根目录运行 python src/main.py，然后在 Telegram 里打开机器人的聊天窗口，点 Start。界面虽然在 Telegram 上，应用其实跑在你自己的电脑上。

大家配置时提的问题，暴露出三种不同的故障。文件或行号对不上，可能是仓库状态不对；导入报错，可能是根本没装 Python 依赖；普通消息没反应，可能只是还没写对应的处理器。装了 Telegram Messenger 不等于装了它的 Python 客户端库，只复制 main.py 也装不上依赖。BotFather 是 Telegram 官方的凭据服务，但 token 只负责把应用连上，不提供应用的行为。到这个检查点为止，反复发 /start 都能用，发“hello”则毫无反应。

03

对话记忆就是一个你反复发送的数组

第一个检查点加入了聊天回调。导入 openai，加载 API key，把收到的 Telegram 文本以 user 角色追加到 messages。这个数组以一条 system 消息开头，说明助手的职责。之后每轮对话在 user 和 assistant 之间交替。openai.ChatCompletion.create 把整个数组交给 GPT-3.5 Turbo，参数是 model="gpt-3.5-turbo"。这里的代码片段保留了录像中旧版 OpenAI SDK 的接口；后来的 Python SDK v1 重写 引入了显式的 client，调用方式也跟着变了。

API 返回的对象里既有答案，也有元数据。取出 choices[0].message.content，把这段回答作为 assistant 消息追加进历史，再把文本发回原来的 Telegram 聊天。模型只能看到你放进请求里的对话。 双方的发言都留着，才能接着追问。

```python import os import openai

openai.api_key = os.environ["OPENAI_API_KEY"] messages = [ {"role": "system", "content": "You are a helpful assistant that answers questions."} ]

async def chat(update, context): messages.append({"role": "user", "content": update.message.text}) completion = openai.ChatCompletion.create( model="gpt-3.5-turbo", messages=messages, ) answer = completion["choices"][0]["message"]["content"] messages.append({"role": "assistant", "content": answer}) await context.bot.send_message( chat_id=update.effective_chat.id, text=answer, ) ```

这里复现的是工作坊把历史存在进程内的做法。如果机器人要给互不相干的用户共用，还得把每个人的历史分开；一个全局列表做不到这种隔离。

用 MessageHandler(filters.TEXT & ~filters.COMMAND, chat) 注册这个回调。小写的 filters 模块筛选文本消息，~filters.COMMAND 排除斜杠命令，这样普通聊天就不会吞掉 /start 或后面各功能的命令。定义函数、构造处理器、把处理器加到应用上，这个模式会在整场工作坊里反复出现。第一个检查点里还有一个 question 处理器，不过它属于下面要讲的检索功能。

现场测试把记忆机制演示得很直观。Hein 问“Simon Cowell 是谁？”，得到一段介绍。接着他问“他的身家有多少？”第二次请求带上了第一轮的问答，模型因此知道“他”指谁。重启 Python 进程会重建初始的 messages 数组，这层指代关系也就没了。要让聊天记忆持久，得把历史存下来再恢复，光让 Telegram 对话一直开着并不够。

系统提示词也能改变行为：Hein 举了两个机器人分别扮成海盗和贵族互相对话的例子，还有一个游戏，用一层比一层强的指令防止秘密泄露。但不停追加对话会碰上另一种限制：请求迟早会超出模型的上下文容量。Hein 估计，这个简单实现到时会记一条错误日志，用户则收不到任何回答，因为代码里没写失败时的兜底回复。检索提供了另一条路：挑出相关的早先内容，而不是把无限增长的历史整个重发。

04

token 衡量输入，嵌入支撑搜索

token 是语言模型处理和生成的单位。token 数量既影响计费，也影响上下文容量。Hein 用一个假想模型说明这条边界：假如它只接受 100 个 token，一个 101 token 的问题就已经超了。他粗略估算一个 token 约等于四个英文字符。这个数字便于建立直觉，但实际数量取决于分词器、语言和文本本身。他对比了西班牙语和英语的分词成本，还提到 Replit 专为代码设计的分词器。

token 的切分方式有时也出人意料。Hein 举了 rawdownloadcloneembedreportprint 这个例子：LessWrong 上讨论过，它反常地成了单个 token。他建议去 OpenAI 的分词器 playground 亲手试试，看文本是怎么切开的。更普遍的道理是：分词器和用它的 token ID 训练出来的模型是绑定的。系统提示词照样用普通文本写，但你不能随手把模型的分词器换成一个不相干的。

embedding 是一个浮点数向量，用来表示某个输入，供语义比较之类的操作使用。幻灯片上把狗放在猫旁边、草莓放在蓝莓旁边，表示它们含义相近。这给处理大型语料提供了另一种思路：要回答一个关于 Taylor Swift 的问题，不必把整个 Wikipedia 塞进提示词，先找出相关段落就行。原文仍然少不了，向量只是帮你找到它。

预处理任务写在 embedding/embed.py 里，从仓库根目录用 python3 embedding/embed.py 运行。它用 Pandas 处理表格数据，用 tiktoken 数 token，用 LangChain 的 RecursiveCharacterTextSplitter 切分文本。Hein 提醒，它可能一跑就是好几分钟，终端里也看不到什么有用的输出。一位参与者给了个直观的解释，说明为什么要切分：用一个定长 embedding 代表整本书，就像求一部电影的平均颜色；细到场景级别，才说得清某个具体时刻。这个比喻讲的是细节损失，并不是说 embedding 模型能吃下任意长的书。

LangChain 提供了好用的组件，但底层操作并不依赖这个框架。眼下实际的麻烦是大家共用一个 API key：同时跑 embedding 任务可能触发限流。Hein 建议先重试，不行再换自己的 key。他估计整场工作坊的 API 费用大约 0.05 美元。卡在 embedding 任务上的参与者，可以直接用提供的 embedding.csv，里面是预先算好的结果。语料是原样抓取的 MDN 文档，这样每个人都能接着做检索，不必各自重新生成同一批向量。

05

清洗、分块并嵌入 MDN 语料

数据导入从普通的数据准备开始。脚本把换行替换成空格，再从文件名还原出源路径，因为文件名里的斜杠都编码成了下划线。还原出的 URL 和页面文本放在一起，留下足够的出处信息，之后回答时就能引用来源。贡献者文件和没用的抓取结果（比如登录页、需要 JavaScript 才能显示的页面）会剔除掉。剩下的文件名/文本对组成一个 Pandas dataframe，并存成一份抓取结果 CSV。

接下来，tiktoken 加载 cl100k_base，给每行文本数 token。另一个切分步骤把过大的页面拆成更小的输入，跳过空行，收集缩短后的文本，再数一遍 token。注意别把单位搞混：递归字符切分 在 length_function=len 时，量的是字符。所以演示里设的 1000 并不代表每块 1,000 个 token。口头举例虽然这么说，一个 3,000 token 的页面也未必正好切成三块。token 计数和切分器的长度函数是两个不同的控制项。

切出来的每个文本块都通过 openai.Embedding.create 送进 text-embedding-ada-002。脚本取出 data[0].embedding，作为新的一列加进 dataframe，再写出处理后的 CSV。按官方公布的规格，这个模型输出 1,536 维向量，输入上下文上限为 8,192 个 token。这些是模型本身的上限；把块切得更小，既是为了输入不超限，也是为了检索效果。

一个文本块放得进 API，不代表它是好的检索单元。在“小红帽跑向了……”后面一刀切下去，后半句的意思就没了。检索回来的片段于是缺了回答问题所需的信息。库可以自动切分，但数据边界仍然要由应用来决定：选哪个 embedding 模型、块切多大、能不能保住完整的意思，都会影响生成模型最后拿到什么。

06

在要答案之前先检索文本

流水线的在线部分在 src/questions.py 里。它加载保存好的 dataframe，把存下来的 embedding 转成 NumPy 数组，方便做数值运算。一个有 1,536 个元素的数组，仍然是 1,536 维 embedding 空间里的一个向量；NumPy 并没有把这个空间压成一维。工作坊用 openai.embeddings_utils.distances_from_embeddings 比较问题向量和文档向量。

create_context 接收一个问题、dataframe 和最大上下文长度。它把整个问题（比如“JavaScript 里的 event 是什么？”）做成 embedding，再逐一算出它和每个文本块的余弦距离。距离越小，排名越靠前。Hein 先用相近的浆果和不相干的物件来说明，再把同样的思路套到相关的 JavaScript 资料和不太相关的 CSS 资料上。应用加一列距离、排好序，然后为提示词收集对应的文本，而不是向量。

工作坊给检索上下文设了 1,800 token 的预算。它按排名依次取文本块，直到用完预算，为 answer_question 拼出一段有长度上限的文本。下面这个精简实现演示了“先排序、再装填”的过程，两步的分工一目了然：

```python import numpy as np

def select_context(question_embedding, rows, max_tokens=1800): query = np.asarray(question_embedding, dtype=float) vectors = np.asarray([row["embedding"] for row in rows], dtype=float) similarities = (vectors @ query) / ( np.linalg.norm(vectors, axis=1) * np.linalg.norm(query) ) order = np.argsort(1.0 - similarities)

selected = [] used_tokens = 0 for index in order: row = rows[int(index)] cost = row["n_tokens"] + 4 if used_tokens + cost > max_tokens: break selected.append(row["text"]) used_tokens += cost return "\n\n###\n\n".join(selected) ```

这里每一行存着一个文本块的文本、token 数和 embedding，另外给分隔符留了一点余量。检索上下文的预算只是最终请求的一部分：指令、问题和生成的回答也都要占位置。

embedding 模型和回答模型各管一摊。Ada 负责生成检索用的表示；GPT-3.5 Turbo 拿到选出的文本，写出回答。提示词要求它依据提供的上下文作答，上下文不够就回答“I don’t know”。导入时保留了源 URL，所以提示词还可以要求附上来源链接。在生成开始之前，应用已经把庞大的语料筛过一遍了。

回答调用引入了 temperature、max_tokens、top_p、频率惩罚、存在惩罚和停止条件。这些参数控制的是生成过程，不会让检索到的文档变好。Hein 起初拿回答的多样性和精选搜索结果来类比采样。后面的讨论澄清了一个关键区别：采样作用于候选的下一个 token，而不是一份排好序的完整答案列表。回答再流畅，也可能编造事实，比如说海王星比地球离太阳更近。

07

只在有帮助的地方使用语义搜索

听众问到该选哪个模型，引出了一条关键边界。生成模型不必和 embedding 系统同属一个模型家族，因为它拿到的是检索出来的文本。但查询和文档的 embedding 必须处在兼容的向量空间里；不同模型产出的向量，不会因为都是数字就能随便互换。一位参与者建议试试开源替代品，并点名阿里巴巴的 GTE，说它是当时领先的选择之一。它公开的模型卡足以支撑拿它和 ada-002 做比较，但证明不了工作坊当天排行榜上的确切名次。换 embedding 模型，意味着语料和查询的编码都要重新考虑。

成本讨论同样要放在当时的背景下看。一位参与者回忆起 OpenAI 的一个说法：给整个互联网做 embedding 可能要花 5,000 万美元。Hein 估计，他抓取的数据大约覆盖 MDN 的 80%，做一遍 embedding 约花 0.04 美元。这些都是转述的估算，没有账单记录、语料规模或完整算式，不能拿来当今天做预算的价格。

随后听众把三个采样概念区分开来：

| 参数 | 改变的是什么 | |---|---| | top_k | 保留多少个候选的下一个 token | | top_p | 保留下来的候选累计占多少概率质量 | | temperature | token 概率分布是集中还是分散 |

所以 top_p=0.1 并不是“最好的那 10% 的回答”。调低 temperature 会减少随机性，但不保证某个百分比的可复现性。API 参数定义 正式写明了这种基于概率的解释。

结构化元数据带来的是另一种检索问题。假设每条记录有一段描述，外加布尔型的通过/失败值、ID 或类别。一位听众建议先按精确属性过滤，再对剩下的文本做语义搜索。embedding 是有损的；精确的约束就该精确处理。 如果失败信息埋在自然语言描述里，把关键词检索和 embedding 检索结合起来，也许能捞回单靠任何一种方法都会漏掉的有用信号。讨论中展示的自查询（self-querying）示意图把这种分工画了出来：查询构造器和转换器为向量库生成一条搜索查询和一个元数据过滤条件。

什么时候拒答、块切多大，也都取决于语料。Hein 说，一个关于 event emitter 的问题得到了“I don’t know”，他怀疑是抓取时漏了相关内容。他还提到，超出语料范围的问题经常被拒答，但没有测过可靠率。至于块的大小，信息密集的参考文档需要的上下文可能比叙事文本少：从《魔戒》中间抽出一页，可能不够总结一整章。讨论中提到了 LangChain 的多种切分策略和它的 text-splitter playground，但最终怎么定，还得拿有代表性的问题对着实际切出的块去试。

08

让 /question 成为一条独立的应用路径

回到 main.py，导入 answer_question，启动时加载 embedding CSV 并转换其中的向量。这样重启会慢一点，但示例更容易看明白。新的 question 回调把 dataframe 和 update.message.text 传给回答函数，再把结果发到 Telegram。注册 CommandHandler("question", question) 之后，这条路由就打通了。Hein 建议一直用本地 NumPy 方案，等存储或搜索性能真成了瓶颈再说；pgvector 和 Pinecone 是以后可以走的下一步，不是理解检索的前提。

现在演示里有了两种不同的行为：

| 输入路径 | 提供的上下文 | 历史记录行为 | |---|---|---| | 普通文本 | 系统提示词和聊天历史 | 追加到对话中 | | /question | 检索到的 MDN 文本块和回答指令 | 不追加到普通聊天历史 |

/question What is CSS? 给出了一段对 Cascading Style Sheets（层叠样式表）的解释。event emitter 的问题返回“I don’t know”，Hein 又一次把原因初步归到抓取不完整上。一个关于 Taylor Swift 的普通问题则走了通用聊天那条路。检索没有改变模型本身的知识，改变的是应用拼装出来的请求。同一套流水线也可以用来搜索产品自己的文档。

两条路分开，也就解释了为什么同一个问题在普通聊天里能得到有用的回答，在 /question 下却被拒答：后者被要求只依据提供的证据作答。这也暴露出一条安全边界：有位参会者说，只要让机器人忽略之前的指令、改用通用知识，就能绕过“只用上下文”的限制。Hein 初步建议把系统提示词写得更强硬，同时承认自己在提示词注入防御上经验有限。“只用上下文”的提示词并不是一道能强制执行的安全边界，检索做得再好，也挡不住生成模型产生幻觉。

采样参数要跟着任务走。写诗需要变化，解释 CSS 通常更需要稳定。Hein 说这个例子用的 temperature 是 0.5。他的做法是一次只改 temperature 或 top_p 中的一个，多试几条提示词，再看输出。讨论最后更正了 temperature 的取值范围：所讨论的这个 API 是 0–2，默认值为 1。这些设置管的是采样行为，不是事实上的确定性。

09

在边界处、跨问题地保留含义

手写流水线会把一些控制项摆到台面上，换成更高层的库调用，它们可能就藏起来了。text splitter 的预览能显示切分边界，但边界切得好不好，还是得把文本块做成 embedding、再看下游的回答才知道。重叠（overlap）会在边界附近重复一部分文本，让至少一个相邻的块更有可能装下一个完整的意思。回到小红帽的例子，目的就是避免只检索到半句话，而意思却落在下一块里。

Hein 没比较过不同的距离度量；他在试验流水线其他部分时，始终固定用余弦距离。复合问题带来的限制更明显。在一次请求里同时问位运算、CSS 和事件，会把好几层意思塞进同一个查询 embedding，各自检索到的证据还要争抢同一份上下文预算。一位参与者提议把问题拆开，分别为每个部分检索上下文，最后再合并结果。Hein 觉得这是个合理的扩展，但自己没试过。

应用工程正是在这里比单纯的聊天界面多出价值：几步精心编排的检索和提示，比一条笼统的请求更能做好特定任务。不过基线依然简单：一个完整的用户问题生成一个 embedding，拿去和文档块比较。最后一位听众问到 token 和 embedding 容易混淆，这时会场正好进入休息。好在关键区别前面已经讲清：分词产出的是模型的输入单位，embedding 产出的是表示某个输入的向量。

10

用示例来规定生成的代码

休息之后，工作坊把代码当作另一种生成文本，并换用 GPT-4。Hein 拿一张 AP 考试成绩对比图说明，换模型是看中它的推理能力。接着他解释，重复出现的代码结构对预测下一个 token 很有帮助：一个开头的 div 标签，强烈暗示后面会有对应的闭合标签。熟悉的框架也自带成熟的约定。他举的例子是 Rails 和它的认证包 Devise：提一个配置需求，模型就能借助常见的文件布局和生成模板来完成。

他把这看作手写软件和习得行为的结合：Software 1.0 直接写出指令，Software 2.0 靠训练数据改变行为，他所说的 Software 3.0 则把两者合在一起。眼下的具体做法是少样本提示（few-shot prompting）：给模型几组示例输入和你想要的输出，再让它按同样的约定接着写。运行或渲染生成的代码是另一个可选步骤。

第二个检查点加入了一段代码提示词，里面有两个示例：一个带红色描边、装着三个黄色圆圈的蓝色方框，以及一个写着“Click Me”的红色按钮。两者都用 JSX 加内联样式。这段提示词作为一条额外的 system 消息，再由一个 /code 处理器把用户的请求发给 GPT-4。现场的请求是：一个红色方框，里面放一个蓝色的“yes”按钮。返回的代码沿用了既定的 JSX 和内联样式格式，用户不用再把这些要求说一遍。想改用 Vue 或 Nuxt，把指令和示例换成相应的约定就行。

有人提议做个扩展：把生成的 HTML 转成 SVG 字符串，再把 SVG 转成 PNG 字节，把图片发回 Telegram。每多一个环节，就多一处可能出错的地方。就连更简单的 div 居中演示也值得细看：返回的代码把 flex 对齐和绝对定位加偏移混在了一起。Hein 承认它满足了要求，但也说代码并不完美。他接着讲到，自己在没有 Ruby 经验的情况下做了一个 Rails RAG 应用，每次只要求做增量修改，最后还得到了一位经验丰富的前上司的好评。实用的工作流是：提一个范围明确的需求，检查结果，再在此基础上往下走。

11

委派计算并改进提示词

附加的渲染示例把迭代过程摆在了眼前。要一组 yes/no 按钮，第一次得到的是白屏；改了一次还是不行。把“绿色的 yes 按钮、红色的 no 按钮”这个意图再说一遍，最后才渲染出能用的结果。配套的算术示例先生成表达式，再交给一个名为 math.evaluate 的 Python 求值函数计算。Hein 明确警告，不要在生产应用里放不受限制的 eval。值得记住的原则是：算术交给计算工具，别指望纯语言模型来算，同时让执行始终处在应用的控制之下。

有人问到 Vertex AI，引出了可移植性的问题：不同厂商可能用不同的 API 名称提供类似的 chat 或 completion 能力。续写模型能把“yellow brick”补全成“road”；聊天接口则把带角色标签的消息打包在一起。这两种叫法本身都不带来记忆。前面的机器人已经说明，要追问 Mark Cuban 的身家，必须以某种方式把相关的前文交给模型。请求怎么组织、历史怎么处理，比端点是不是叫 chat_completion 重要得多。

想把提示词写好，Hein 建议在回答没对上预期时，直接问模型还需要哪些信息。它的回答可能会暴露出缺失的约束，下次补上即可。他举了 Kent C. Dodds 设定偏好的提示词为例：回答要简洁，不要反复提醒自己是 AI，不要多余的客套和表情符号。目标不是攒一套一成不变的“咒语”，而是随着模型和 API 不断演进，摸清哪些指令和示例能让输出往有用的方向变。

12

一把牛油果扶手椅很容易提出来——却很难保证效果

图像生成从令人难忘的 DALL-E 牛油果扶手椅讲起：一句普通的话，就能换来一个大多数人想象得出、却画不出来的物件。失败的例子同样有启发。“Salmon in the river”（河里的三文鱼）生成的画面字面上没错，却不是想要的场景。手常常画得畸形，用户只好写“把手背在身后”之类的指令来绕开。数数和写字又是另外的难题。

对“森林里有四个人”这条提示词，Hein 说展示的四张结果里只有一张人数对了，在这个小样本里命中率是 25%。他还说，自己花了大约 30 分钟，才得到满意的“fox”字样。这些演示说明，“看着像回事”的图像和真正符合具体要求的图像是两回事。DeepFloyd IF 是文字渲染更强的例子。它同样基于扩散，具体是像素空间的级联扩散，配合 T5 文本编码器，并不代表扩散之外的另一条路线。

个性化是和产品接上的那一环。Hein 举了 Lensa 的头像生意和 Pieter Levels 的图像应用，作为赚到钱的成功案例，然后介绍了 RoomGPT：上传一张客厅照片，要求换一种风格，比如中古现代风。Midjourney 则是另一条生成图像的途径。这些产品让不懂技术的用户也能把脑子里的画面变成看得见的东西，而不只是拿到一些靠搜索也能找到的信息。

13

返回图像字节，再考虑基于推断的路由

第三个检查点加入了 requests 和一个 image 回调。openai.Image.create 接收提示词、图片数量 n 和尺寸。响应里是一个 URL；用 HTTP GET 取回图片字节，再通过 context.bot.send_photo 发到原来的聊天里。一个 /image 命令处理器把这个回调接入应用。传输上最关键的变化，是从发文本变成了发媒体内容。

函数调用（function calling）只是提议一个操作，真正执行的是应用代码。 描述一个 add 函数，模型就能返回函数名和 2、4 这样的参数，但它自己并没有调用你的 Python 函数。要不要调用、怎么调用，由应用决定。同样的机制可以取代显式的斜杠命令：一句“生成一张机器人拥抱考拉的写实照片”，就能变成一次带相应提示词的图像生成调用。Hein 管这叫一种聪明的 if/else，并把它作为现有处理器的扩展提出来；基础版机器人里还没有实现。

现场的图像请求是“The Iron Giant sitting in the forest, 4K”（坐在森林里的钢铁巨人，4K）。这里的 4K 只是提示词的一部分，不能说明返回图像的分辨率。Hein 澄清，工作坊用的接口是 DALL-E 2，DALL-E 3 正在陆续上线。他建议多试试其他选择，包括能在本地运行的 Stable Diffusion，还拿生成结果和那张广为流传的教皇时装照做了对比。换一个更简单的请求“A koala sitting in a tree”（坐在树上的考拉），结果让他满意得多。

在图像上，提示词写得具不具体格外要紧，因为很多用户没法自己修图。Hein 让大家三到五人一组，花十分钟做实验，建议用逗号分隔不同的想法，除了主体也要描述场景。这个练习把一个能跑通的 API 连接，变成了对照意图和产出的工具。

14

从生成的角色到代码库示意图

休息时的交流把工作坊延伸到了参与者自己的工作流里。有一次视觉识别似乎认出了代码里的处理器，只是有几个认错了；有人提议补一句“这段代码属于一个 Telegram 机器人”，作为有用的上下文。一位参与者讲到，他根据团队成员的选择（比如英雄还是反派、奇幻还是科幻）给每人生成一个角色。其中一位 CTO 的魔法大象角色，又成了 Runway ML 的输入，做成了动画。Hein 觉得展示的效果比他自己用 Mage 做的实验更流畅。这些都是参与者把多个工具的输出串起来用的例子。

图表是一种更偏技术的组合方式。Hein 讲到，他让模型根据自己的函数调用代码输出 Mermaid 语法：文本模型生成结构化表示，再由另一个工具渲染成图。一位参与者介绍了他在 Cursor 里的工作流：从一个 URL 索引文档，把它和代码库一起引用，生成 Mermaid 或 UML 架构图。他用这套方法帮新人上手，也用它先吃透陌生的智能体代码仓库，再讲给团队听。他还提到，Cursor 的环境和 VS Code 差不多，能导入扩展，回答里也会引用所用的文档。

高强度的实验会同时改变注意力和花销。一位参与者提醒，摆弄这个助手可能会挤掉原本计划好的工作。一位参与者说自己的 API 账单到了 140 美元；另一位说超过了 100 美元，而平时每月只有 5–10 美元。他们讨论认为，比起用自己的 key 的花费，每月 20 美元的 Cursor 订阅很划算；不过这些只是个人当时的开销，并不是同等用量下的对比。还有一位参与者讲到为不同的输出选用不同的模型，包括用 GPT-3.5 做函数调用和微调。

Hein 拿一次加密货币转账来对比：他转 10 美元，手续费就要 6 美元，工作坊里的实验比这便宜多了。他打赌大家在工作坊里实验很难花超过一美元，参与者马上补充：用 GPT-4 就不好说了，尤其是它的大上下文版本。一位参与者会有选择地用 GPT-4 32K 处理较大的文件、搜索代码库。小组练习结束时，Hein 请大家把最喜欢的图像提示词和结果发给他，好在广播频道里分享。

15

上下文混淆和投递失败是应用层的问题

后来一个关于代码生成的问题，给前面的乐观打了折扣。一位参会者碰到过架构层面的上下文限制，也搞不清长对话里模型指的是哪段代码。Hein 自己没遇到过同样的限制，但建议换到另一条代码路径时就新开一个对话。把处理字节的工作和另一个编码问题混在一起，可能会把不相干的旧假设带进回答。另一个办法是通过 GPT-4 的 Code Interpreter 上传文件，他觉得挺有用，只是有时也让人抓狂；大家还推测了 Replit 可能会做哪些改进。

这位参会者讲了他在企业里使用和微调 StarCoder 的经历，包括它允许开发者选择退出（opt-out）的条款。Hein 建议看看 Llama 和 Llama 2，同时承认自己没用它们做过代码生成。有人问怎样在 embedding 里同时兼顾结构化和非结构化信息，这个问题暂时搁置了。这几段交流说明，选模型还是得看实际环境和任务，没有放之四海皆准的推荐。

图像功能也碰上了一个具体的集成故障。一位参会者说，往 Telegram 发图片时超时了，改发图片 URL 似乎就没问题。Hein 记下了这个反馈，但没有诊断或修复。另一位参会者问，有没有检测器或后处理工具，能找出渲染得不自然的图像，再把它修得正常些。Hein 不知道有这样的工具，只是试探性地类比了某些系统的做法：生成后做安全过滤，不合格就重新生成。这段讨论并不能说明存在自动修复图像质量的环节。

16

把语音变成现有技术栈的输入

自动语音识别（ASR）把音频转成文本，也就是机器人已经会处理的那种输入。Alexa、Siri 和 Google 的语音界面都是大家熟悉的例子。Hein 介绍了 Whisper 和它的 transformer 架构，并和早期基于循环神经网络的方法做了对比。训练语音系统还需要带有可用标注的音频，这和收集普通文本是两种不同的数据采集难题。

工作坊用的是已经配好的托管 API，不过也可以走本地或浏览器的路子：

- 浏览器体验： Hugging Face Space 可以提供一个上手门槛很低的语音识别演示。 - 本地推理： 开源的 Whisper 能在本地硬件上运行；whisper.cpp 是它的 C/C++ 实现，Hein 推荐用它试试在 CPU 上跑。 - 说话人分离： WhisperX 把转写、对齐和可选的说话人分离（diarization）结合在一起。 - 反方向： 从文本生成语音，可以用提到的 Tortoise TTS。

说话人分离要回答的是：一段音频里，谁在什么时候说话。在 Hein 举的 Noah 和 Justin 播客的例子里，系统可以给每段发言分配说话人 ID；但要把 ID 对上真实姓名，还需要额外的信息。多人同时说话时，说话人的归属仍可能出错。

17

转写一段语音备忘，并展示进行中的工作

Telegram 语音消息是最后一种输入类型。流程很直接：录一段语音，取回音频文件，发给 Whisper，再返回转写结果。这是第四个检查点。现场演示时，Hein 把 git branch 改成了 git checkout，编辑器这才真正切到实现代码。

回调读取 update.message.voice.file_id，用 context.bot.get_file 获取文件，再用 download_to_drive 存到本地。文件名带上语音 ID 以免重名，后缀是 .ogg。在演示的实现里，这些录音会一直留在应用服务器上，所以文件留存是实打实的运维问题，不是一个看不见的 API 细节。

转写完成之前，机器人会先告诉用户正在处理。Hein 用反面情形说明为什么流式输出或进度反馈很重要：默默等上半天，然后突然甩出一大段文字。这里没有实现流式输出，所以先回一句确认，是最起码的有用反馈。旧版的转写调用是 openai.Audio.transcribe("whisper-1", audio_file)，之后回复转写文本。下面这个精简的回调做的是同一套流程：

```python from pathlib import Path

async def transcribe_message(update, context): voice_id = update.message.voice.file_id voice_file = await context.bot.get_file(voice_id) path = Path(f"voice_note_{voice_id}.ogg") await voice_file.download_to_drive(custom_path=path)

await update.message.reply_text("Downloaded. Transcribing your voice note…") with path.open("rb") as audio_file: transcript = openai.Audio.transcribe("whisper-1", audio_file) await update.message.reply_text( "Transcript finished:\n" + transcript["text"] ) ```

和 /question、/image 不同，语音转写用的是 MessageHandler(filters.VOICE, transcribe_message)。收到音频附件本身就决定了走哪条逻辑，所以不需要 /voice 或 /transcribe 这样的文本命令。

最后测试时，Hein 用手机录了一段话，向在场的人介绍自己，还说了句绕口令“rubber baby buggy bumpers”。Telegram 把录音送到正在运行的机器人，机器人依次报告已下载、正在转写、转写完成。返回的文本大体准确，但把他的姓拼成了 Hine，而不是 Hein。结果能用，但并非毫无差错，专有名词尤其容易出错。

结尾回到这些 API 合在一起的价值：语音一旦变成文本，就能进入已经搭好的检索、对话或生成流程。手机上的这次演示，打通了一个跨模态的可用界面；Hein 也展望了更个性化、更具交互性的应用。接下来要做的产品决策是：这些串起来的能力，应该帮人完成什么事。

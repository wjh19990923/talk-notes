When does the agent work?
Runs continuously and involves you when a decision is required

On schedule
Cron and interval.
Calendar-aligned work like a morning status report or an on-call handoff at shift change. Intervals for periodic maintenance.

Event streams
Keyword-matched ingestion.
Deploy events with "deploy," "release," or "rollback" auto-trigger the deploy monitor. No human needed.

Message-based
Direct human contact.
A Slack DM or channel message wakes the agent immediately. The message is the signal, no polling delay.

The agent tracks why it woke up each time, and acts accordingly.

常驻智能体运行生产环境，免去值班之苦

更快的代码交付带来了更多的生产运维工作。后台智能体结合触发器、持久执行和生产上下文，监控变更并让团队随时掌握情况。

熟悉 CI/CD、生产监控和值班轮换，有助于理解示例。

01

我们现在能交付的这么多代码，由谁来运行？

What happens to production when writing code becomes much faster? Justin Smith approaches that question from the operational side: he introduces himself as a founding product engineer at Resolve AI, with more than fifteen years in monitoring and observability, including work as an architect on Splunk’s Observability Suite and a tenure at VMware. His interest in product design and front-end architecture also shapes the question of where engineers should interact with operational agents.

AI-assisted development produces larger pull requests and more frequent releases. It also lets people ship code without necessarily understanding its operating principles. That increases development output, but it leaves the downstream work intact. Smith cites an unnamed survey putting 70% of engineering time outside writing code, which he describes as running shipped software. The survey’s population and methodology are not supplied.

That work includes maintaining platforms, scaling infrastructure, debugging incidents, serving on call and shipping hotfixes. It also includes handling alerts, updating runbooks, restoring services, managing escalations and answering other teams’ questions. Faster code generation does not remove these responsibilities; it can increase the number of changes engineers must understand.

Smith also describes tightening token allowances, rising prices and stricter company controls on AI use. These are his observations, rather than a comparison of named providers or plans. Together, they motivate a broader requirement: production AI needs domain context around the model, so that model capability translates into useful work inside a particular environment.

02

从响应告警到记住环境

Production systems were already complex before AI accelerated development. Multiple teams operate interdependent systems, pursuing local goals that must stay aligned with organizational goals. Resolve’s founding hypothesis is that increased coding velocity will create more production issues, making AI assistance valuable on the operational side as well. Smith says work with engineering customers operating at large scale informs that hypothesis; it is not a demonstration that on-call work has disappeared.

Resolve’s agents began with on-call work: triaging incoming alerts and investigating root causes. An engineer returning to an on-call rotation after several weeks may not know the latest changes or every system involved. An agent can help assemble that missing context. When a single page expands into a cross-team incident, the coordination problem grows too: responders need a shared account of where the incident is happening and what it affects.

Background agents address what remains when there is no active fire: context handoffs, one-off issues and the nagging question of whether a subsystem is healthy. Smith describes an architecture combining models, context, reasoning and actions. Its difficult requirement is an evolving knowledge system. More capable models do not automatically know how a company’s services interact, where its hotspots are or which causal chains matter. That understanding must be captured and kept current as the environment changes.

An enterprise layer sits beneath that architecture, though Smith does not detail it here. The rest of the talk narrows to background agents rather than immediate incident response.

03

那些没有告警的工作

Asked about agents outside coding, audience members suggest meeting reviews, market research and therapy. Smith connects meeting reviews to Granola, which had appeared during the presentation. These are audience examples of non-coding workflows, not demonstrated Resolve capabilities. They lead into a less conspicuous category of engineering work: responsibilities that lack the clear starting signal of a page or incident bridge.

Someone still has to watch a deployment finish, prepare a morning incident digest and investigate recurring P99 latency drift that has not crossed an alert threshold. Someone must produce a capacity report against a quarterly goal and check system health before a customer complains. These tasks consume attention even when nothing explicitly announces that they are due.

Smith defines a task as execution plus the context needed to execute it well. Tool access can get an agent to a dashboard. Production context lets it recognize that a metric looks wrong and decide to investigate another layer.

| Capability | What it contributes | | --- | --- | | Execution | Open the dashboard and retrieve observations | | Production context | Judge whether an observation matters |

The distinction is between obtaining a value and understanding its significance. A useful background agent needs both.

04

触发器、持久执行与共享学习

Three questions define the background-agent machinery: when does it work, how does it run and how does it know what to do? The activation mechanisms are simple enough to compose into many workflows.

| Trigger | Example | | --- | --- | | Schedule | Morning report or weekly on-call handover | | Event stream | Deployment event or relevant Slack message | | Direct request | A message asking the agent to do work |

Smith’s team hands over on-call duties on Thursdays. A scheduled agent can prepare the preceding week’s important trends for the next engineer. Event-driven work instead begins when a connected system emits something worth acting on, such as a CI/CD deployment or a Slack message.

Execution lives in the cloud, so closing a laptop does not stop the agent. Smith describes a sandbox with a filesystem that lets the agent organize its work. Beneath individual runs, a memory and learning system supports reflection: what a task discovers can improve its next run, and shared knowledge can carry lessons into other tasks.

A task system supplies the work definition, imports existing skills and connects the necessary integrations. These primitives are intended to support more than a fixed catalog. The four workloads that follow are examples Smith says have worked inside Resolve and with customers.

05

可以移交的四类工作负载

Deployment monitoring starts with the observation that every change creates an opportunity for something to go wrong. Existing CI/CD checks provide useful baselines, but they are not exhaustive: different releases need different signals. Feature flags and infrastructure changes may also happen outside the monitored pipeline, leaving the on-caller to reconstruct who changed what only after an alert fires. A background agent can watch those change events and assess system stability.

Scheduled health and anomaly checks inspect systems without waiting for an alert. A morning dashboard review might look for unusual behavior overnight. A task can also be temporary: after changing an integration, ask an agent to watch the third-party service for a week, then stop. Operational reports and handoffs turn those observations and other operational activity into information teammates can use.

First response to engineering questions targets interruptions. Smith describes watching Slack channels while trying to build software: the questions may be easy to answer, but responding breaks concentration, while not responding leaves colleagues waiting. Internally, Resolve’s agent already has access to much of the information people ask about. It watches critical channels and decides whether it has enough confidence to answer. If uncertain, it can DM an engineer for confirmation before posting a response.

06

这次发布的监控计划

The deployment demonstration takes place in an explicitly fake application environment and a demo Slack workspace. Posting a GitHub tag gives the agent a potential release event. It first identifies that event as a release, then inspects the changes to choose telemetry that could reveal whether the system has entered an abnormal state. The result is a monitoring plan specific to that release.

The agent complements the CI/CD pipeline. It adds the change-specific attention that would otherwise require an engineer to watch each release closely. In the example involving checkout and the currency service, Smith points to checkout latency, error rates and the Kafka pipeline as signals to inspect along the relevant causal chain. The useful mechanism is the connection from the change to its possible effects, rather than a fixed list of checks applied to every release.

Monitoring can continue beyond one pass.

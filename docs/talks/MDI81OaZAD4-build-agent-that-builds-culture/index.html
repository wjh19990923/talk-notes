How to build an agent that builds the culture

Ramp built Inspect so teammates could work in the same remote coding session. A telemetry bug and a homegrown code review agent show what happened once engineers could see, question, and build on each other’s work.

01

Put the coding session where teammates can join

When Ramp decided to build its own coding agent, it made every session remote and multiplayer. Teammates could work with Inspect together in Inspect itself or through integrations such as Slack and Linear. For Ramp engineer Zach Bruggeman, that early design decision shaped who could take part in the work.

Inspect grew to include built-in design tools, review agents, and verification flows, so a builder could go from a prompt to shipping in the same system. Companywide integrations connected builders to the tools and data they needed, including telemetry databases. At the time of the talk, Bruggeman put the share of Ramp’s code that Inspect wrote and shipped at around 75%, using a counting method he left unspecified.

When Ramp first shared Inspect publicly, people wanted to know how it started sandboxes in under five seconds, wired in company context, and let agents work together. As those capabilities spread, the question shifted from how to run a remote coding agent to what happens when a whole company works with one.

When Ramp shared Inspect publicly in January, people asked how it worked. Inspect spun up sandboxes in under 5 seconds, wired up internal context, and let agents work together. As those ideas spread, the tech became less of a barrier.

02

Make a good setup available companywide

Fifteen minutes to set up a coding agent sounds cheap. Across hundreds or thousands of people, it adds up to days of work. Then a better way to configure the agent comes along and the work starts again. The people who hear about the change and apply it get better tools sooner, while the rest of the company has to discover the same improvement for itself.

Ramp kept one Inspect for the whole company. When someone found a tool or a way of working that could help other teams, Ramp could roll the improvement out through the shared setup. Most changes reached people in the course of work they were already doing. Engineers could still tune their own setups, and Inspect gave them a good enough baseline that Ramp never needed to mandate its use.

03

Learn from the sessions teammates already run

Inspect sessions are visible within Ramp by default. You can watch someone work with the agent in a channel you already follow, or ask Inspect to look through a teammate’s recent sessions and explain how they structure prompts or break down a gnarly problem. Those everyday examples gave Ramp a way to teach people how to use Inspect without scheduling formal training.

The same sessions give the Inspect team clues about what to build. An unexpected use can reveal a recurring task that deserves a built-in feature. The work also exposes where people need a tool or data source the agent lacks. The team can make those decisions by watching what people actually try to accomplish.

04

Give reviewers the session behind the diff

Better models made it easier to get good code out of an agent. Engineers still had to judge whether an individual change held up. Inspect makes the session that produced a change easy to share, so reviewers can learn from the way their colleagues actually work, including people who would never give a talk about it.

Take a pull request with a 400-line diff. The diff shows what changed in the code. The session lets the reviewer ask how the builder and agent arrived at the change, and what behavior the verification agent actually checked.

- Conversation and tool use. Read what the builder asked for and see which tools Inspect used to get there. - Screenshots and browser recordings. Compare the app’s visible state before and after the change, or watch the route the verification agent took through the app and see how it behaved along that route.

05

Debug the instrumentation that made the bug visible

In February, a Ramp engineer named Andrew reported a bug in Inspect, so Bruggeman asked Inspect to investigate itself. The agent had access to Datadog, and Ramp had only just instrumented Inspect. Tracing was new territory for a team made up mostly of frontend product engineers. Inspect’s first diagnosis was a surprise. The instrumentation that let them investigate the error was causing it.

Bruggeman and Dylan doubted the diagnosis, and Andrew was ready to switch to another coding agent. The investigation was happening in a shared thread, so Dylan could ask Inspect a sharper question. What if the error had been happening all along and the new instrumentation had only made it visible? He asked Inspect to read the telemetry library’s source.

Inspect came back with a specific operation to check. The telemetry exporter called fetch and left the response body unread and uncancelled. That hit a Cloudflare platform limitation at the time, even though the library was written for Cloudflare Workers. Diagnosis at 8:35

What had to change after fetch returned? At the team’s request, Inspect patched the exporter to explicitly cancel the response body. That let the exporter discard the body without reading it. After deployment, the team reported seeing no further instances of the error over an unspecified observation window. Deployment result at 9:01

Before Inspect, a report like Andrew’s might have become a ticket that someone debugged in private. Andrew might have heard back when the fix shipped. In the shared thread, he could follow the diagnosis, bring his own experience into the discussion, and suggest other work Inspect could help with. Bruggeman put the exchange at about an hour. Andrew started it with a broken experience and ended it looking for something the group could build together.

Inspect flags a possible bug in the OTLP exporter. It calls fetch without reading or canceling the response body, which fits Cloudflare’s deadlock warning. Bruggeman says Inspect patched the exporter to cancel the body.

06

Let other people shape what the agent is for

Bruggeman worries about the appeal of the “lone wolf operator.” An agent makes it easier to build something entirely around your own use. When people can follow work in progress, they can bring their own problems and experience into it. Bruggeman had seen the exchange with Andrew play out many times at Ramp.

Inspect became familiar enough that people at Ramp knew its face, dressed it up for holidays, and added Easter eggs. Some iterations went better than others. One that changed how the team thought about Inspect started with a recurring problem in code review.

07

Build Review Buddy on the pull request trigger

Ramp had been rotating through off-the-shelf code review products looking for a good fit. Two engineers realized they already had a way to start an in-house review agent. Inspect could trigger automations from several sources, including the event fired when someone opened a pull request. They could use that event to start a review as soon as a change was up for review. Existing trigger at 11:54

The engineers started on their own, reused the trigger, and used Inspect itself to speed up development. They quickly built Review Buddy, a review agent that worked better for Ramp in Bruggeman’s judgment. Seeing what others had built with Inspect’s automation pushed the Inspect team to think beyond code generation. Bruggeman thought it would have taken the team much longer to see that possibility on its own.

08

Ask what the team has been waiting to build

As models improve, Bruggeman’s challenge is to ask the people you work with, “What have we been waiting to do that we haven’t done yet?” Pick something from those conversations and try building it together. Inspect began with that kind of motivation. Bruggeman and Jason wanted to give a team they cared about a more enjoyable way to work.

Bruggeman closed by announcing that Inspect was opening to teams outside Ramp and offering priority on the waitlist through the event’s signup page.

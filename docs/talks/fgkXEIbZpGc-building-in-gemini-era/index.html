在 Gemini 时代构建

Kat Kampf 和 Ammaar Reshi 制作了基于搜索结果的贴纸、分支剧情漫画和一款多人赛车游戏，展示了 AI Studio 如何把模型能力连接到可用的应用上。

对 Web 应用和 API 有基本了解会有帮助；演示不需要 Gemini 或 AI Studio 的使用经验。

01

一个编程模型应该擅长什么？

你想要的是一句提示词就生成一个精致的网站，还是一个能在大型代码库里干活的智能体？这两类任务需要的能力并不一样。Kat Kampf 负责 vibe coding 和 AI Studio，Ammaar Reshi 带领 AI Studio 的产品与设计团队。两人把这两种能力放在同一套构建体验里介绍。开场回顾了从 Transformer 到 AlphaGo 的发展脉络；连他们那条时间线的终点 Gemini 2.5，到发布周就已经过时了。

Gemini 3 Pro 在那一周早些时候刚刚发布，演讲从两个方面展示它：

- 设计理解：一次生成风格统一、界面可用的网站。 - 智能体式工具调用：借助工具和连续操作，在大型代码库里完成更复杂的工作。

Kat 介绍，在一项基于基础智能体框架的 SWE-bench 实验里，Gemini 3 的成绩超过了对比模型。演讲没有给出足够的评测细节，这张图表没法当作可复现的对比来看。它在这里的实际作用，是在现场演示应用之前，先引出模型借助工具干活的能力。

02

运用知识、文本和参考资料的图像

Nano Banana Pro 据介绍前一天刚发布，后面几个应用里的图像能力都靠它。Ammaar 先问了一个泡茶的问题。Google Search 提供信息，模型把这些信息做成一份图解食谱：选出的那页幻灯片上有小豆蔻奶茶的配料、制作步骤和小贴士。Search grounding 负责提供信息，图像生成再把信息排成一张文字清晰可读的图示。

文字渲染不只是在平面上加标签。Ammaar 先展示了环绕在罐身上的文字，又展示了一版韩语本地化，构图和参考图保持一致。接着他提到一张 14 人合影，说这是团队目前测到的一致性基准，而不是硬性上限。这个口头举例和官方发布的规格对不上：规格里分开写了两件事，一是最多输入 14 张图片，二是最多保持 5 个人的相貌一致。

下一组对比是局部编辑：画面里的女人和花都还在，只是焦点换了。指令很简单：“把焦点换到花上。”好用的地方在于“保持不变”：只改用户要求的那一处，不必重新构图。支持多种宽高比之后，同一套图像流程还能用来做壁纸、横幅和广告牌。

03

从一块 AI 芯片到一个生成的应用

Google AI Studio 可以和模型对话、获取 API key，不过 Kat 直接进入了它的 Build 体验。示例库给用户提供起点，输入框则让用户直接描述想要的应用。输入框下方的 AI chips 提供模型选择之外的能力，包括 Google Search grounding 和 Google Maps grounding。有了它们，这些能力直接写进应用需求里，不用再单独做一遍集成。

Live API 带来了持续交互。Kat 介绍了一个应用：它通过摄像头看她挥拍打网球，并指出动作哪里要改。另一个例子是姿势反馈，有人身体太往前倾，它就会提醒。这类应用的输入随时间不断变化，反馈必须在动作进行时就给出来。

按台上的说法，用提示词生成应用是免费的，大多数模型不需要 API key，访问共享应用的人用的是他们自己的 AI Studio 免费额度。Kat 说，这样某个共享应用火了，也不会给创作者带来一笔意外账单。这是当时的计费方式：现在的 Build 文档规定，共享应用的用量记在创作者名下，用到付费模型时还会按规则收费。

接着 Kat 开始做一个笔记本贴纸应用，灵感来自最近流行的个性化贴纸插画。她在需求里同时选了 Google Search grounding 和 Pro 图像模型这两个 chip。两者分工明确：Gemini 3 负责构建应用，图像模型负责生成应用里的图片。

1. Kat 选中 Pro 模型能力，提交贴纸应用的需求。 2. Gemini 3 拆解任务，生成一个端到端的完整应用。 3. 生成过程中，加载界面用 Gemini 给出扩展这个应用的建议。

Ammaar 转去讲别的例子时，应用还在生成。就连等待界面，也成了帮用户理清需求的机会。

04

一部进行中的漫画，中间夹着一个网站

文字渲染和角色一致性都提升了，自然就有了一个玩法：把自己画进漫画书。Ammaar 生成的应用可以上传人脸照片，还能选题材和语言。他选了 Kat 和自己，再写下故事设定：两人正在纽约的 AI Engineer 大会上介绍 AI Studio，一边 vibe coding，一边即兴应付这场演讲。提交之后，漫画开始生成。

漫画渲染期间，他切到一个网站示例。他对以前生成的网站有个很具体的不满：紫色渐变太多。这个网站则用了着色器动画、跨页面过渡和各种视觉特效，字体也由模型来挑。最初的需求是做一个炫酷的动画网站，同时明确要求不要赛博朋克风。这个例子把 Gemini 3 的设计能力和一个实用的提示词技巧联系起来：说清楚想要什么效果，同时排除你不想要的风格。Ammaar 认为，用不惯 Figma 这类设计工具的人，可以靠这个办法拿到一个能用的视觉起点。

回到漫画，生成的页面里既有故事文字，也有两位演讲者赶往会场的画面，背景里还出现了 AI Engineer 的横幅。Gemini 3 负责叙事，Nano Banana Pro 负责画面和文字渲染。两者一配合，应用讲出的故事里，环境、角色和文字都在为场景服务。

读者还能在故事中途选择剧情走向。两个角色是该找个安静角落检查一下 API key，还是顺其自然、即兴发挥？Ammaar 选了即兴。故事随之转向，剩下的页面按这个选择开始生成。其中一句写到一只“好用得可疑的机器狗”，正是他喜欢的那种不经意的幽默。这不只是让模型再画一张图：用户做的决定，成了多模态故事下一段的上下文。

05

搜索变成一页个性化贴纸

回到 Kat 的应用，第一步是添加 API key。这款新发布的图像模型当时在 AI Studio 里要付费，是前面“大多数模型不需要 key”的例外。生成的界面提供两种输入方式：输入贴纸主题的关键词，或者用 Google Search。Kat 选了 Search，输入 Ammaar 的名字，分辨率选 1K。预想的流程是：先检索最新资料，整理出关于他的背景信息，再把这些信息变成像模像样的笔记本贴纸。

生成的图片里有一款 Weekend Builder 贴纸，还提到了 Ammaar 写的儿童绘本 Alice and Sparkle。这些细节让 grounding 的效果一目了然：输出用上了和被搜索者本人相关的信息，而不只是通用的贴纸图案。Kat 接着把同样的机制延伸到新闻：检索当天的信息，就能补上模型训练截止日期之后的背景。

06

用 AI Studio 给 AI Studio 做原型

下一个应用源于产品团队的一个现实约束：Kat 和 Ammaar 的点子比工程时间多。所以他们先用 AI Studio 试交互，再决定要不要真正实现。其中一个点子是打通到 Antigravity 的路径，Antigravity 是 Google 新发布的智能体 IDE。在浏览器里构建也许足够起步，但有些功能或移动端开发，还是得转到 IDE 里做。

Kat 给了一张 AI Studio 的截图，让模型尽量还原这个界面，再加一个导出到 Antigravity 的流程。生成的原型复刻了浅色模式的界面，并加上了 Antigravity 按钮、导出交互，以及在 IDE 中打开项目的入口。这只是一个正在探索的产品概念，不是已经正式上线的导出功能。

备选方案也有价值。Kat 让模型大胆发挥，不必拘泥于 AI Studio 现有的设计模式。几轮迭代下来，它有时会用命令行风格来显示导出状态。截图限定了周边界面，提示词则给新交互留出发挥空间。这样做出来的原型，很适合用来比较不同的产品方向。

07

一个赛车游戏延伸到了前端之外

接下来 Ammaar 打开一个用 Three.js 生成的 3D 赛车游戏。几句简单的提示词，就做出了赛道场景、一个机器人对手和开始界面。他又加了个加速功能，好让自己甩开机器人。这和前面的网站考的是两回事：输出的是一个能跑起来的场景，有玩家操作和游戏逻辑，而不只是视觉布局。

Ammaar 说，到目前为止，这些应用都是纯前端的 React 应用。他接着预告了后端支持和全栈运行时，录制时还处于“即将推出”阶段。例子包括：用提示词安装 shadcn；把“做一个多人应用”的需求变成 Express 后端，并把该接的线都接好。设想中，用户只需说清楚想要的行为，构建工具自己推断需要哪些依赖包和服务端工作。

08

大厅能用，比赛却开始不了

两位演讲者只用了几句提示词，就把赛车游戏改成了多人模式。他们放出一个二维码邀请观众加入，还说之前从没在这么多人的情况下试过。赛车陆续加载进游戏，Ammaar 请大家都点“准备”。

人一多，两条游戏规则就显现出来了。一条是车辆之间开启了碰撞，车子互相弹开，挤在起跑线上。Ammaar 报出大厅里的人数：19、20，然后是 23。这些只是现场看到的大厅人数，不代表一场比赛能顺利跑完的人数上限。

另一条规则是准备屏障：所有玩家都准备好，比赛才能开始。用 JavaScript 把这条规则写出来，卡住的条件就一目了然：

```javascript const players = [ { id: "kat", ready: true }, { id: "ammaar", ready: true }, { id: "guest", ready: false } ];

function canStartRace(players) { return players.length > 0 && players.every(player => player.ready); }

const before = canStartRace(players); // false

const updatedPlayers = players.map(player => player.id === "guest" ? { ...player, ready: true } : player );

const after = canStartRace(updatedPlayers); // true ```

在这个三人示例里，最后一位访客点了准备，屏障就解除了。可现场演示中，屏障一直没解除，两位演讲者没法开始比赛。人一多，暴露的不只是碰撞问题，还有协调问题。

不过 Ammaar 说，运行时没有崩溃。这样就能把三种很容易混为一谈的结果分开来看：

| 演示环节 | 实际结果 | | --- | --- | | 加入多人大厅 | 观众的赛车都加载进来了 | | 开始比赛 | 卡在“全员准备”这一条件上 | | 运行时稳定性 | Ammaar 表示没有崩溃 |

现场的结果是：多人应用里挤满了玩家，游戏流程却卡住了。它证明连接链路是通的，也暴露出有些规则得改，才能撑起观众规模的对局。

09

让应用需求隐含基础设施

运行时的用途不止于游戏。Kat 介绍，接下来几个月，团队会让 Google 自家的 API 和热门第三方 API 更容易集成。有了后端，这些服务就有了接入的地方，没法完全放在前端预览里的能力也有了依托。

之所以把这套基础设施直接做进构建体验，是因为能做软件的人正在变。Kat 回忆，那天早上她遇到一位做技术支持的人，对方看了一个 YouTube 视频，就开始在 AI Studio 里做应用。对这样的用户来说，入口不一定是传统 IDE。工具要做的，是足够理解用户想要什么样的应用，帮他把它做出来。

用户的意图，本身就应该说明需要哪些能力。 Kat 最后举了存储和支付两个例子：需要持久化的应用，应该自动配好存储，创作者不必专门提出要数据库；电商应用则应该有一条接入支付方案的路径。这些是演讲中提出的产品愿景，还没有完整演示出来。它们给构建工具定了一个比“生成一个好看的首屏”更高的目标：先推断应用要做什么，再提供实现这些功能所需的软件能力。

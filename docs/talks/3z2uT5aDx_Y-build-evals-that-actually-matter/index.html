评测为什么会失败？

幻灯片原文
Eval scores need to gate decisions, judges need to be trusted, and someone must own regressions. Make results trustworthy and consequential before automating.

Why do Eval Fail?

1
Numbers don't gate anything
If moving a score costs nothing, no one defends it.

2
Judges are too noisy to trust
People quietly stop believing the metric.

3
No owner of the consequence
When something regresses, nobody is on the hook.

What to do?: Make eval results both trustworthy and consequential. Automation is the last step, not the first.

Offline Eval

A real synthetic-data methodology

“Don’t simply prompt LLM to generate 50 test queries.”

1. Seed from production
Start generation from real logs / traces, not blank prompts.

2. Inject a perturbation
Add a new constraint or modified variable for realistic edge cases.

3. Enforce an output schema
Constraint structure so samples are parseable and gradable.

4. Over-generate, then filter
Keep only the hardest, highest-quality examples.

未经验证的评判者——像验证分类器一样验证它们

幻灯片原文
Hand-label about 100 pass/fail examples and compare the judge with human labels on a held-out slice. Precision measures how often its passes are correct; recall measures how many true passes it catches.

LLM Judge
Unverified judges - validate like a classifier

1. Treat the judge as a classifier
Its output is binary: pass or fail. Hold it to the bar you'd set for any classifier.

2. Hand-label ~100 examples
Annotate pass / fail yourself, then split into train and validation slices.

3. Score precision & recall
Measure against the held-out validation slice not a gut feeling.

JUDGE vs. HUMAN GROUND TRUTH
Human: PASS | Human: FAIL
Judge: PASS | TP — True Positive | FP — False Positive
Judge: FAIL | FN — False Negative | TN — True Negative

Precision TP / (TP+FP)
Of traces the judge passes, how many truly pass.

Recall TP / (TP+FN)
Of truly passing traces, how many the judge catches.

标准漂移与验证验证者

幻灯片原文
Grading model outputs reveals and changes human criteria for quality. The rubric and judge must evolve with the model, while the gap between the judge and human judgment remains.

LLM Judge
Criteria drift & validating the validators

Evaluation can't be decoupled from model observation
• Grading outputs is how people discover what their criteria actually are.
• Criteria evolve as new LLM outputs are seen, they aren't fixed up front.
• The rubric and the judge co-develop with the model under test.

Who validates the validators?

There is always a gap between an LLM judge and a human's evolving sense of quality. We should not assume the criteria themselves are stable.

构建真正有用的评测

Lyft 的客服智能体需要这样的评测：经得起逼真的用户考验，产出可据以行动的失败案例，并直接与上线决策和工程改动挂钩。

熟悉 LLM 工具调用、多轮智能体和基本的分类器指标，有助于理解评测工作流。

01

怎么知道一个客服智能体已经准备好面对用户？

一个客服智能体，提示词写得用心，工具也好用，检索管线也搭好了，却仍可能应付不了真实对话。怎样才能在客户沦为它的测试数据之前，确认它真能帮上忙？Nick Ung 和 Akshay Sharma 结合自己在 Lyft 多智能体客服系统上的工作回答这个问题。他们把离线评测、线上监控，以及让评测可重复的框架串到了一起。

开发从上下文管理、检索增强生成（RAG）、工具定义、智能体图和系统提示词入手。部署前，这些部件要在完整的交互中配合起来。对多轮客服智能体来说，这意味着要有一套有代表性的场景数据集，再加一个用户 LLM，把每段对话一路推进到结束。评分器给生成的轨迹打分，明确的性能标准决定智能体能否通过上线关卡。目的是赶在真实用户碰上之前，先把问题找出来。

上线之后，评测并不停止。生产环境的 trace 记录智能体的每次执行，以及它作答时依据的上下文。线上评分器给这些交互打分，人则负责检查错误、归纳失败模式，再把发现反馈给开发。离线评测和线上评测是同一个闭环的两段：先确认能上线，再从真实发生的情况里学习。

02

让分数产生后果

评测分数得能改变某个决策。 有三种情况会让它做不到：

- 没有关卡： 评审模型给出了数字，但这些数字既不影响开发，也不影响部署。 - 没人信： 分数嘈杂又笼统，几乎给不出可操作的信息。Lyft 早期的评审模型就碰到过这个问题：大家既不相信这些分数，也不知道怎么用。 - 没人管： 线上出现退化时，既没有明确的检测机制，也没有人负责修。

一个有用的评测系统，三条连接缺一不可：分数要服务于某个决策，评分器要让人信得过，结果要有人负责落实。

03

模拟完整的客服交互

Lyft 借鉴了 Sierra AI 的 τ-bench：让智能体和模拟用户在某个领域的策略约束下交互，产出一条多轮 trace。客服策略规定了每类问题该怎么处理；模拟则检验智能体在对话推进过程中怎样执行这些策略。

在 Lyft 的模拟器里，一个 LangGraph 智能体和用户 LLM 对话。用户 LLM 的指令分别定义了场景的几个部分：

- 意图： 用户想办成什么事，这个客服问题本质上是什么。 - 世界状态： 相关的用户数据，比如一位跑豪华车型的资深司机。 - 行为与人设： 用户以什么姿态参与对话，比如一位对 Lyft 收入体系不满的忠实老用户。

这些字段既决定智能体要解决什么问题，也决定它解决问题时能从对方那里得到多少配合。

生成的轨迹交给几类互补的评估器。LLM 评审负责需要解读的行为；确定性断言负责检查能直接写明的结果。比如某个场景要求智能体给出补偿，评估器就拿智能体的工具调用和这个预期动作对比。这样能在工具调用层面检验指令遵循，而不是只看最终回复听起来有没有帮助。

04

一个乐于助人的助手会模拟出一个不切实际地配合的用户

模拟质量从数据集开始。让 LLM 生成 50 条测试查询是条省事的捷径，但没法证明这些场景贴近生产环境。Lyft 用历史客服交互的样本补充离线数据集，再变换场景条件，把预期路径和边界情况都覆盖到。配套的幻灯片在这个流程上又加了两步：定义输出 schema，以及“先多生成、再筛选”。

场景再合理，模拟用户要是不像真实客户，测试也会变得太容易。前沿模型的训练目标是做一个乐于助人的助手。让它们扮演 Lyft 用户时，它们会耐心地用完整、礼貌的消息把问题讲清楚。Nick 提到，Lyft 第一次离线评测用的就是这种过分配合的用户模拟器，通过率（或准确率）超过 90%。演讲没有给出数据集规模，也没有给出更精确的指标定义。

生产环境里的交互完全是另一番样子。用户本来就窝着火，没耐心，也不太愿意把问题讲清楚。Lyft 用真实 Lyft 用户的语言微调了用户 LLM，让模拟对话更接近这些交互。改完之后，评测分数下降了；Nick 没有给出微调后的具体数字。更难的模拟给智能体留出了改进空间，让它学着应付棘手的对话，而不是靠一群格外配合的用户刷出好成绩。

人设又增加了一层真实感。“绕行者”（bypasser）不给 AI 任何机会，只想立刻转人工；其他人设还有想要退款的用户和不信任 AI 的用户。这些指令让用户模型的行为落到一个个可辨认的类型上。Nick 还提到，Microsoft 关于用户 LLM 的研究给了他们启发：那项研究也发现，微调后的用户模型让对话更真实，评测分数随之下降。

05

用任务结果取代泛泛的质量分数

不同应用的侧重点不同：安全、泄露、成本、延迟，或者回复质量。有些检查能用代码实现，有些得靠 LLM 来判断。问题不在于维度多，而在于定义出来的维度没法告诉任何人该修什么。

Lyft 起初用的是 DeepEval 的预置指标，包括工具使用是否恰当、回复是否有帮助、对话是否自然、内容是否完整。Akshay 提了个很实际的问题：有帮助程度得了 0.5 分，工程师该拿它怎么办？毒性、偏见、公平性、简洁度这些分数，一旦脱离具体需求，也是同样的问题。预置指标可以当基线，但核心评测应该和产品结果挂钩。这番批评针对的是 Lyft 当初对通用指标的用法；现在的 DeepEval 也支持自定义标准、评分细则和二元打分。

更好的做法是和领域专家、数据科学家一起定义任务成功还是失败。二元结果让评审模型更容易校准，也让错误分析有了明确的靶子。Lyft 针对“讲解”的评分细则能说明两者的差别：

| 智能体行为 | 细则判定 | |---|---| | 该升级时还在继续讲解 | 不通过 | | 还没做应有的讲解就升级 | 不通过 | | 按预期处理讲解与升级 | 通过 |

过度坚持和过早升级，都可能判为不通过。笼统的有帮助程度得分会掩盖这种区别；评分细则则能指出具体该改哪种行为。

06

把评判者当作分类器

评审模型本身也是模型，它的判断同样需要评测。Akshay 建议先针对相关任务或指标，人工标注 100 条左右的通过/不通过样本。把这些样本分成训练集、开发集和留出验证集，再以人工标注为准，衡量评审模型的精确率和召回率。一个没验证过的评审模型说智能体没问题，并不能证明智能体真的没问题。

这里的“训练”指的是打磨评审模型的提示词，而不是更新权重。每份数据各有分工：

1. 从训练样本里挑出放进提示词的 few-shot 示例。 2. 在开发集上迭代提示词或框架。 3. 在留出的测试集上评估，看这些改动有没有对开发集过拟合。

幻灯片给出的训练/开发/测试比例大约是 20%/40%/40%。这样分配，是因为目的在于打磨提示词：训练部分只用来提供示例，占比更大的开发集和测试集才用来检验评审模型的表现。

验证还得考虑标准漂移。看的输出越多，团队对“好”的理解就会跟着变：一次原本模棱两可的交互，暴露出少了一条规则；或者一种新的失败，说明现有规则不完整。所以评测标准应该随着对智能体的观察一起演进。标准变了，就要相应改进评审模型，再按新的预期重新评测它。

07

为重要的数字加上不确定性范围

只报一个一致率，会把不确定性藏起来。置信区间、校准和合理的抽样能让报出来的分数更有用，尤其是这些分数要决定是否发布，或者要写进给管理层的汇报时。Akshay 建议把代价高的统计工作集中用在这些分量重的决策点上。

Akshay 举了个假设的例子：两个评估器在 50 条 trace 上分别得到 84% 和 88%，光凭这 4 个百分点的差距，并不能说明真有提升。幻灯片画出了相互重叠的置信区间，让这种不确定性一目了然。要判断差距有没有意义，光看这两个总比率不够，还需要更多信息，包括对比是怎么设计的。效应越大，或者采用配对设计，所需样本就可能越少；演讲没有给出配对结果，也没有算出确切的样本量。

08

让错误分析成为一个反复进行的工程循环

一切的基础是亲眼看数据。不看样例，团队就定不出有意义的标准和标签。没有标签，就没法验证评审模型。评审模型没验证过，就没法放心解读智能体的分数。LLM 可以帮忙，但省不掉“看看到底发生了什么”这一步。

把错误分析当成例行流程来做：

1. 查看智能体交互的原始 trace。 2. 找出具体的失败模式。 3. 只保留和业务或功能需求挂钩、真能改变决策的指标，砍掉噪声。 4. 对需要改进的地方提出新的假设，重新评测，然后重复。

Akshay 建议每周或每两周做一次。关键在于这是持续的工作，不是一次性审计。

这套流程离不开有用的 trace。借助 LangSmith 和 Langfuse 这类工具，团队可以记录并检查图的执行：跑了哪些节点、模型看到了什么、调用了哪些工具，以及每次调用的 token 用量和延迟。还可以附加元数据，让记录更完整。有了这些细节，就能从一个失败的结果顺藤摸瓜，找到导致它的那次执行。

标注队列让领域专家也能用上这些记录。审阅者在专门的界面里给样例打标签、写反馈，不用在原始的 trace JSON 里翻找。审阅过的 trace 有两个用处：可以变成离线评测用例，人工标签也可以用来衡量评审模型的精确率和召回率。生产环境里的证据，就成了下一轮测试的素材。

09

把发现变成改动——再重新运行评测

评测发现的问题真正让智能体变好了，闭环才算闭合。Nick 区分了三个可以下手改进的地方：

| 学习路径 | 改什么 | |---|---| | 模型 | 通过后训练或定制模型改变权重 | | 上下文 | 文档、存储的用户记忆、工具输出 | | 框架 | 系统提示词、工具 schema、路由、重试、控制流 |

Lyft 的错误分析已经推动了智能体提示词、知识库更新和上下文管理策略的改进。找准失败模式，才知道该动系统的哪一部分。

做这场演讲时，离线模拟器还依赖散落在各个 notebook 和分析仓库里的脚本；Nick 说它可重复性不够。团队正在建设一个系统化的评测框架，提供预定义的基础组件，大家通过写配置来贡献内容。团队也在考虑，怎样用积累下来的真实用户信号做针对具体任务的模型微调，以及强化学习的奖励建模。这些是更往后的方向，和前面讲的用户模拟器微调是两回事。

这个框架的设计让各个智能体和子智能体的评测有了统一标准。YAML 配置可以直接编辑，分析师和数据科学家也能和工程师一起贡献。Nick 说评测样例有数千条，将来可能到数万条，所以需要并行和高吞吐。可复用的基础组件有任务、数据集、人设、LLM 适配器和评估器。

下面这个示意配置把这些组件组合起来，用在补偿场景上。数据集记录提供世界状态和预期动作；人设控制用户行为；两个独立的评估器分别检查工具调用结果和讲解细则。

``yaml task: customer_support_concession datasets: - concession_cases personas: - loyal_customer_frustrated_with_earnings llm_adapter: support_user_simulator evaluators: - name: expected_concession_tool_call type: deterministic - name: education_rubric type: llm_judge outcomes: [pass, fail] ``

这正是这套设计想要的配置形态：场景和评估器的定义都能复用，贡献者自己拼装就行，不必重写模拟运行器。

定义好之后，同一份配置可以在开发的不同关口反复运行。改完提示词，在本地跑一遍，就能和智能体的上一版对比。提交前检查可以在改动推送到智能体服务之前发现退化。Nick 还提到，团队正在探索把它接入 CI/CD 的回归测试和验收测试套件。最终目标是一套可重复的工程流程：评测紧跟每次改动，紧到足以决定改动能不能往下走。

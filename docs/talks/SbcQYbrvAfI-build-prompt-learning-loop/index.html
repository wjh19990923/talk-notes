构建一个提示词学习循环

SallyAnn DeLucia 和 Fuad Ali 把智能体的失败和评测解释转化为修改后的提示词，然后构建了一个 JSON 网页实验，保留每一个候选版本及其结果。

01

找到缺失的指导

智能体接到一个任务，却没有任何关于如何规划的指导。给它一份死板的计划，又会冒出另一个问题：下一步可能要依赖还没拿到的信息。就算智能体手里有合适的工具，如果指令从没说明每个工具该在什么时候用，它照样可能选错。这些都是模型外围应用的毛病，光换一个更强的模型未必修得好。

DeLucia 把这些缺口归为三类：适应、规划和上下文。指令应当吸收智能体在实际运行环境中积累的经验教训。规划既要有足够的结构来指导执行，又要足够灵活，能根据中间结果调整。上下文必须提供做决策所需的相关数据、可用工具和指导。否则，应用就是在要求模型根据它从没拿到的信息行事。

这项工作还跨越了组织边界。工程师和数据科学家负责代码、自动化、流水线、性能和成本。领域专家和产品经理清楚一次成功的交互应该达成什么。他们能看出某个回答虽然在技术上完成了请求，却违背了一条重要的产品预期。提示词学习循环需要这两类专长：一边是记录行为的基础设施，一边是解释行为为什么该改的反馈。

02

给优化器的不只是一个分数

工作坊用学生考试来解释这套学习机制。学生作答，老师打分，分数影响下一次作答。在这个类比的强化学习版本里，分数是一个标量奖励，用来更新模型权重。这要动的是系统的另一部分，应用开发者写提示词时通常不会碰它。

元提示（meta-prompting）把改动挪到了文本层面。LLM 拿到某个提示词的表现信息，然后提出一版修改后的提示词。在工作坊简化后的对比里，这相当于老师根据评测结果直接改学生的指令。但只给一个分数，老师还得自己做很多功课：分数只说明这次答得怎么样，不一定指出错在哪里。

Arize Prompt Learning 在修改过程中加入了解释性反馈。哪些答案错了？为什么错？学生该补哪些内容？专家标注或 LLM 评测可以指出漏掉了哪条指令，并说明期望的行为。负责修改的 LLM 拿到这些信息，写出更好的指令，有时还附带示例。学习的对象是提示词本身，整个过程不需要改模型权重。

举个例子，专家可能会指出某个回答忽略了必需的上下文，而不只是标一个“错误”。评判模型（judge）同样可以在给出标签的同时返回理由。有了这些解释，优化器就知道该在系统提示词里具体改什么。标签仍然适合用来统计结果，但保留输入、输出和失败原因，修改才有方向。这正是 DeLucia 强调的实际区别：充分利用评测过程中本来就有的丰富文本，而不是把它们全压缩成一个数字。

03

把编程失败变成可复用的规则

Cline 编码智能体案例研究把这种变化讲得很具体。展示出来的基线提示词交代了智能体要做编码工作，却没有规则部分。角色描述告诉模型它是哪类助手，但不一定规定了遇到棘手的工程决策时它该怎么做。

修改后的版本加入了好工程师一看就认同的要求：

- 处理错误和异常时，找出根本原因。 - 改动要与系统设计保持一致，并检查有没有引入技术债。 - 改动要配上合适的测试。

这些是关于“怎么干活”的通用指令，而不是针对具体问题的解法。

DeLucia 介绍，加入这些规则后，Cline 在 SWE-bench Lite 上的成绩提高了。SWE-bench Lite 是一个由代码仓库 issue 修复任务组成的基准。这次干预只改了系统提示词，没有微调模型，没有换工具，也没有改智能体架构。这个例子把提示词修改变成了一个具体的实验变量：先确认更好的指令能不能改善行为，再考虑是否真的要重建外围系统。

Arize 公布的结果给出了改进幅度。实验在 ACT Mode 下运行 Cline，模型用 GPT-4.1，把 SWE-bench Lite 分成 150 个训练样例和 150 个测试样例；补丁通过单元测试即算成功。训练准确率从 18.67% 升到 34.00%，提高了 15.33 个百分点。报告中最高的测试准确率出现在第 2 轮优化循环，从 17.33% 的基线升到 31.33%，提高了 14.00 个百分点。之后几轮的测试准确率是 28.00% 和 30.00%，可见最后一轮并不是最好的。

靠失败案例来修改，会引出一个明显的担忧：优化器会不会只是学会了迁就已经见过的样例？给出的应对办法是：要求优化器总结高层次的编码规范，而不是针对单个失败打补丁，然后在另一批样例上评测。这些规则必须在写规则所用的失败案例之外也管用。编码实验的数据划分，和工作坊后面用到的网页 notebook 是两回事。

DeLucia 还拿招工程师打了个比方。你希望这个人熟悉你代码库的约定和怪癖，而不是一直泛泛而谈，忽视代码库的具体要求。针对应用定制的指令也能提供类似的专长。专门化并不能免去检查泛化能力的必要，但它说明了本地知识为什么有价值。新问题出现时，就把它们收集起来、解释清楚，再改一次指令。规则就这样成了需要在应用整个生命周期里持续维护的东西。

04

反思仍然需要一个可靠的评估器

GEPA 同样通过反思评测反馈来修改提示词。它的搜索过程会评测候选提示词，让一个反思模型检查结果，再提出变异。基于帕累托的选择会保留各有所长、有潜力的候选，而不是立刻只留一个赢家、其余全部丢掉。搜索继续进行时，合并（merge）提供了另一种组合候选的方式。

DeLucia 介绍，在她展示的对比中，Prompt Learning 用更少的优化轮次取得了比 GEPA 更好的效果。接着她指出这些实验共同依赖的一点：评测器的质量。优化器只能利用它收到的信号。如果信号奖励的是不该有的行为，修改反而会强化错误的教训。工作坊在 Arize 的优化器对比中，把 GEPA 和 MIPRO 系列放在一起讨论。

所以，评测器工程本身就是改进过程的一部分。评测器的提示词需要清晰的指令，它的判断也需要检查。只改进智能体、却放着有缺陷的评测器不管，等于在追一个误导人的目标。接下来要问的不只是怎么更快地修改智能体，而是两个提示词都在演进时，怎么让反馈始终有用。

05

评估没有明显标准答案的任务

有位观众对编码示例提出质疑：如果工作的成败不那么容易量化，该怎么评测？DeLucia 的回答是从懂这个应用的利益相关方入手。把领域专家、产品经理、安全团队和管理层召集起来，一起定义什么叫成功。现成的问答评测器起步时可能有帮助，但最终的检查项应当由应用自身的需求决定。

以 Arize 自己的助手为例，这些需求涉及几项不同的决策：

- 它找到对的数据了吗？ - 它在语义搜索和结构化过滤之间选对了吗？ - 它检索信息的顺序对吗？ - 它的计划适合这个任务吗？ - 安全团队需要了解哪些越狱尝试？

先定义期望的行为，再把每项关切转化成一项评测。只对最终回答做一次判断，可能会掩盖流程中真正需要关注的环节。

Ali 补充了一个来自 Booking.com 的主观性例子：判断一个房源页面或一张照片好不好。不同的人看了，对它有没有吸引力可能意见不一。可以先从粗略的好/坏判断开始，再细化到更具体的因素，比如光线昏暗、房间布局等。这些因素把判断背后的原因讲了出来，而且能直接指导修改。

有人接着问：比起二元标签，这些额外因素是否给改进指了更好的方向。它们让反馈包含更多信息，但并不需要一个字面意义上的连续梯度。审阅者发现有用的区分点后，可以据此细化评测器，并把其中一些区分直接写进生成用的提示词。

06

在两个独立的循环中分别修改智能体和评判者

另一个问题是：不断演进的规则部分，怎么避免冗余和互相矛盾的指令？初始提示词可以手写，但之后的修改应当基于积累下来的样例。LLM 在吸收反馈的同时，可以把指令合并精简。设想中的工作流会持续收集失败案例，产出新的提示词版本，之后再交给应用采用。

这并不意味着把每个失败样例都抄进一个越来越长的规则部分。样例是输入，用来生成一套新的指令。修改后的提示词是这个过程的产物，和促成它的数据集是分开的。

DeLucia 接着区分了两个共同演进的循环。智能体循环收集失败的回答，说明智能体应该怎样换一种做法。评测器循环收集值得推敲的判断，说明评测器该怎么改。两个循环都可以修改提示词，但研究的失败不同，要修的提示词也不同。

人工审阅、评判模型之间的分歧，以及与置信度相关的信号，都能帮忙找出值得检查的评测器决策。这些只是审阅线索，不能证明某个判定就是错的。有用的标注要指出真正的错误：评测器误解了什么，用错了哪条标准，下次它的指令该怎么区分这种情况。

来看两个基于网页评测器内部链接规则的教学案例：内部路径必须以 / 开头。

| 生成的链接 | 评判模型的决定 | 审阅与修复 | | --- | --- | --- | | reset-password | 因缺少开头的斜杠而判为不通过。 | 判定恰当。在智能体提示词里把内部路径的要求写得更清楚。 | | /reset-password | 判为不通过，理由是要求使用绝对 HTTPS URL。 | 评判模型给内部路径强加了错误的要求。修复评测器，有效的回答保持不变。 |

这两个示例说明，错误的判定不应该自动变成智能体的训练反馈。智能体改进循环能否奏效，取决于评测器能否分清这两种情况。

最后有观众问清范围：这是否需要一个模拟整个产品的模拟器？在这里，工作对象只是智能体提示词和评测器提示词。搭建端到端模拟器是另一项工作，不是本次工作坊演示的前提。

07

从一个原型和一个有边界的任务开始

工作坊从幻灯片转到 Prompt Learning 代码仓库，参与者把它克隆到本地动手操作。趁着配置环境，又有人提了一个实际问题：新智能体应该先从评测做起，还是先做原型，靠原型的失败暴露出需要评测什么？

DeLucia 的建议是，别让一套完整的评测体系成为拦路虎。先做一个小到能逐条检查的东西。现成的评测器可以帮你筛选输出、减轻人工审阅的负担，但它只是起点。随着功能逐步成型、失败模式越来越清楚，再同步完善评测器。这样既守住了前面说的“反馈要可靠”，又不必在第一次实验前就写好完整的规格。

还有人问，提示词学习怎么用在子智能体和多智能体系统上。演示的做法把每个提示词当作可以独立优化的任务。每个专职智能体都能学到更有用的指令，包括与交接相关的指令。Ali 认为，这类局部改进能让更大的系统受益；不过工作坊只做单个提示词的实验，不涉及所有智能体的联合优化或整体模拟。

08

设定 notebook 实验的规模

JSON 网页生成 notebook 给这个循环配了一个具体的小任务：根据请求生成网页 JSON，评测结果，再改进提示词。演示用的是 OpenAI，生成和评测组件也可以改成适配其他提供商或应用。

现场配置时，先调整了一个依赖的版本，又加上了异步执行，然后才开始配置实验。核心输入是一个带有用反馈的数据集：人工标注、评测器结果，或两者兼有。优化器根据这些信息提出指令；评测结果再帮助判断是否继续，以及哪个候选可能在应用中派上用场。

配置项控制着几个不同的维度：

- 样本量： 演示从 100 行开始。样本小，探索性运行更快；样本大，能覆盖更多情况。 - 训练划分： 把用来生成修改反馈的样例，和用来评估候选的样例分开。 - 规则配置： 指定评测实验所对应的规则。 - 优化预算： 限制“生成、评测、修改”的轮数。

这些设置决定了实验的范围。增加数据量和允许更多优化轮次，是两种不同的干预。

接着有位参与者指出单轮样例的问题：对话可能在中途出错。只重放开头的请求，可能永远复现不了出错的那个决策。DeLucia 建议把相关的交互拆成独立样例，让它们各自接受评测和人工反馈。如果只采样对话开头，就会反复检查同一类行为，而漏掉后面出现的失败。

另一个问题涉及指令和上下文的区分。优化器应该修改指令，而不是篡改记录下来的事实，好让答案看起来更好。数据集里可以加几列，存放模型当时能看到的上下文。实验重新生成答案时，需要具备在同样条件下作答所需的信息。

notebook 用了两个 LLM 评判模型；如果代码检查能测出所需的属性，也可以用它代替评判模型：

- 整体评测器对照输入查询和评测规则来评估生成的网页，返回 correct 或 incorrect，并附上详细解释。 - 规则检查器逐条检查合规情况，找出更具体的违规之处。

为每个候选提示词重新生成输出

生成函数就是被测的应用。在这个 notebook 里，生成模型是 GPT-4.1，配置为返回 JSON、温度设为 0。它接收数据集和系统提示词，为各行生成输出，再交给评测。每个新的候选提示词都要走一遍生成函数，实验才能评估这套指令带来的行为。

JSON 响应格式有助于约束输出形式，但不能保证网页满足请求、遵守每条规则；那仍是评测器的工作。函数接收数据集、当前提示词、输出模型和并发设置，然后返回生成结果。把这些职责分开，就能替换应用逻辑，而不用重写整个学习循环。

有观众问，温度设为 0 会不会牺牲有用的创造力。DeLucia 认为这取决于任务。结构化的网页生成更看重一致性，换一个智能体则可能需要不同的采样方式。这里的 temperature=0 是针对该任务选的实验设置，不是通用建议，也不保证每次运行结果完全相同。

数值汇总有助于跟踪运行情况，但代替不了解释性反馈。对于一组非空的已评测输出，二元正确性标签可以直接算出一个评判通过率：

``math \text{评判通过率} = \frac{\text{标为正确的输出数}}{\text{已评测的输出数}}. ``

这个比率概括的是评测器的判定，不是经过独立确认的正确性。讲解中还提到了准确率、精确率、召回率和 F1。要把它们当作分类指标来解读，需要有明确的参照标准来比对；仅仅把评判模型的标签转成数字，并不能提供这个参照。

运行循环，并保留每个候选方案的证据

优化单元格分三个阶段把各组件串起来：

1. 在对比数据集上用当前提示词生成输出，并评测其正确性。 2. 如果结果不理想，就生成训练输出并评测，再根据反馈修改提示词。 3. 重复上述步骤，直到达到目标分数或用完迭代预算。

讲解一开始允许 5 轮优化。设置停止阈值可以让实验提前结束。

notebook 把反复参照的对比划分叫作测试集。由于这里的分数会影响优化何时停止，这个划分实际上起的是验证或选择数据的作用。从未动用过的最终测试集用途不同：在提示词选定并固定之后，估计它的表现。这遵循调参与最终测试的标准区分。演示的循环里并没有单独留一份不动的最终测试集。

循环会跟踪各轮迭代的结果，返回各个提示词版本、原始输出，以及两个划分上的分数。参数包括停止目标、优化预算和规则配置。目标不必绑定某个特定指标，但它的含义必须和评测器实际测量的东西一致。

开始时，先做一次初始评测，建立基线，并检查它是否已经达到阈值。如果应用已有生产环境的输出和反馈，可以直接用这些证据，不必从头生成全部内容。notebook 从一次全新评测开始，是为了把过程展示清楚，并不要求每次部署都照这个流程起步。

在一轮修改中，先生成训练输出，再由评测附上正确性、解释和违反的规则。提示词学习优化器接收提示词和这批带反馈的训练数据，产出修改后的指令。可以用上下文长度上限来控制有多少材料进入优化请求。可见，解释是修改时实际用到的输入，而不只是留着写报告的字段。

返回的提示词仍然只是候选。实验会用它生成输出，在训练划分和对比划分上评测，记录分数，并检查停止条件。如果既没达到目标、也没到最大循环次数，就继续跑下去。写出一版看似合理的修改只是其中一步，修改带来的实际行为仍然需要评估。

提取选中的提示词，并保留它的结果

notebook 的最后一步根据保存的对比结果提取提示词。它声明的目标是选出测试准确率最高的那个，并同时展示原始指令和优化后的指令。最后一个候选不一定最强：选哪个取决于记录下来的表现。假设有一个 Python 列表，存放已评测的候选记录，每条记录含 prompt 和 selection_score 字段，这条选择规则可以写成：

``python def select_prompt(records): if not records: raise ValueError("No evaluated prompt candidates") best = max(records, key=lambda row: row["selection_score"]) return best["prompt"] ``

选出的指令随后可以放进应用代码。生成并选出一个提示词，不等于应用已经自动采用了它。

DeLucia 接着介绍了托管方案，用它就不必自己维护 notebook 循环。在演示的 Arize 工作流中，提示词存放在 prompt hub 里，数据集则带有人工标注或评测结果。这些数据集可以来自收集到的 trace，也可以单独导入。notebook 里那些在函数之间传来传去的产物，平台都提供了统一管理的地方。

一个提示词优化任务需要指定名称、训练数据集、输出位置和反馈列，再由参数控制实验。启动任务后，hub 中会出现一个优化后的提示词，这套指令可以作为新版本，连同结果一起保存下来。

演讲提到，把评测进一步整合进这些任务的工作还在进行中。托管方案的实际作用，是为不想自己维护这些循环的团队提供任务基础设施和版本存储。最终产出是一个应用可以直接使用的提示词版本，附带能说明它为何被选中的实验结果。

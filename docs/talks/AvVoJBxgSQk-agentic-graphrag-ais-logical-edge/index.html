OpenAI o3 Reasoning Response
(40 seconds):

2. Applying the Failure Rate

The teacher fails 75% of the students.
Out of 36 students:

36×0.75=27 students fail

If we assume the failure rate applies uniformly (or proportionally) to both girls and boys, then the number of failing girls is:

9×0.75=6.75

Since we can't have a fraction of a student, we interpret this as 7 girls failing (and 2 girls passing) so that the total failures come out right when paired with the boys. (Indeed, 27 boys × 0.75 = 20.25, which we can assume rounds to 20, giving 7 + 20 = 27 failures.)

3. Elective Options and Assignments

The school's elective choices are:
• Computer Science (the original course),
• Sports, and
Home Economics.

The problem context implies that when students fail the computer science class, they “move” to one of the other electives. Traditionally in these puzzles (and as in similar versions you may have seen) the idea is that girls are not inclined toward sports and so all failing girls go to home economics.

Thus, the failed girls (7 in number) join the home economics course.

智能体化 GraphRAG：AI 的逻辑优势

Stephen Chin 讲解了智能体如何结合向量检索、图遍历和 MCP 工具来获取相互关联的证据——以及哪些实现选择仍然很关键。

熟悉嵌入向量和检索增强生成会有帮助；图遍历和 MCP 会在出现时讲解。

01

当一个课堂问题出了错

一间按网格排座的教室，最多能坐多少个女生？在 Stephen Chin 举的例子里，OpenAI o3 抓住一篇讲“互不攻击的国王”问题的文章不放，默认网格是正方形。这个假设影响很大：幻灯片上列出的其他方案里有长方形布局，只算正方形，就漏掉了一部分答案。Chin 用这个例子引出一个更大的担忧：智能体系统常常达不到预期用途。他还提到了 Gartner 的警告，但没说是哪一项预测。

完整的幻灯片列出了四种布局：6×6 时 G=9，3×12 时 G=12，4×9 时 G=10，2×18 时 G=9。看了这几种长方形方案，就知道“网格是正方形”这个假设毫无依据。

Chin 说，o3 在这道题上推理了大约 40 秒。接着他追问：这些女生和男生会去上家政课还是体育课？同时给出一个有误导性的男女比例。模型算出的答案是：所有女生都去上烹饪课。这下错误叠了两层：先从无关信息里做推断，再套上性别刻板印象。

放在教室谜题里，这些错误一眼就能看出来。换到药物研发或供应链规划，一个没有依据的假设可能还没人察觉，就已经传进了业务决策。Chin 批评的是：语言流畅、推理繁复，容易让用户以为系统具备它从未展示过的能力。他提出用知识图谱来补足：给系统明确的信息和关系作依据，而不是只靠语言生成。

02

把智能体编排与工具分开

一种对策是引入多个协作的智能体。每个智能体都会观察、思考、行动；编排层把这些智能体和生成模型、工具连起来。不同的智能体可以负责工作流的不同环节，互相检查或补充对方的成果。但把这些部件紧紧耦合在一起，会带来维护问题：换工具变得麻烦，安全边界也更难管。

Model Context Protocol（MCP） 在智能体和它们用到的工具、数据源之间划出一道客户端/服务器边界。数据源可以是文件、数据库记录，也可以是充当记录系统（system of record）的图数据库。这样，各项集成就有了可拆分的接口；但光有这一层，并不能说明整个系统就是安全的。

演讲中展示的 Neo4j MCP 工具 分管三项不同的职责：

| 工具 | 职责 | |---|---| | mcp-neo4j-cypher | 用 Cypher 查询图 | | mcp-neo4j-memory | 为智能体提供知识图谱记忆 | | mcp-neo4j-cloud-aura-api | 云端管理，包括创建数据库 |

Cypher 是一种图查询语言。Chin 介绍了一个由提示词驱动的流程，能把问题转成 Cypher 查询。不过按目前代码仓库的文档，服务器提供的是读取 schema 和执行查询的功能。所以“从自然语言生成查询”这一步，应该看作整个智能体/工具流程的一部分，不要默认它全在服务器里完成。记忆和云端操作仍是各自独立的能力，智能体架构可以按需组合。

03

工作流图、记忆图与检索

图可以用来描述智能体的工作流，比如 Chin 展示的 LangGraph 示意图；另一张图则存放智能体记住的信息。两者用途不同：一张组织活动，一张让信息在整个活动中随取随用。Chin 提到 Zep、Cognee 和 Mem0 都用 Neo4j 做图记忆，也指出其中有些允许自选图数据库。这是他对当时生态的描述，并不是说每个部署都必须用 Neo4j。

他展示的视频搜索与摘要架构把这几块串到了一起：短期记忆、查找信息、一条 GraphRAG 管道和一条向量管道。图检索和向量检索并存，是因为两者拼装上下文的方式不同。Chin 认为 GraphRAG 这条路得到的结果更丰富，幻觉通常也更少；但他把这当作定性的好处来讲，并没有给出这个系统的基准测试数据。

04

找到话题，再检索它的关联

医疗的例子让两种检索的区别一目了然。直接问 LLM，得到的回答很泛。基础的检索增强生成能补充更多信息，但答案仍可能不完整：向量相似度找回的是语义相近的文本，不一定能找全和问题相关的每一种关系。相似不等于相关。

以一个关于肺气肿的问题为例，建议的检索步骤是：

1. 执行向量搜索。 把问题和嵌入向量做匹配，可以用独立的向量数据库，也可以用 Neo4j 自带的向量搜索功能。 2. 把匹配结果映射到图中。 嵌入向量和图节点之间事先建好了关联，借此定位到“肺气肿”节点。 3. 沿关系向外扩展。 取回相连的节点，包括相关的诊断和病症。

语义匹配先找到主题，图遍历再补上相连的信息，而这些信息单靠相似度搜索可能会漏掉。源材料里结构化关系和非结构化文本混在一起时，这种做法尤其有用。

整体架构的流程是：接收问题，通过向量或知识图谱检索，再用图分析整理结果。社区算法和分组是另一种汇集上下文的办法；Chin 在这里提到了 Microsoft 的 GraphRAG 研究。检索到的信息随后作为上下文交给 LLM，由它生成答案。图提供证据和关系，回答的文字仍由模型来写。

05

选择一种检索模式并为上下文排序

Text-to-Cypher 能从问题直通图检索，但好不好用，要看生成的查询质量如何。Chin 提醒，LLM 生成的 Cypher 可能达不到应用的要求。他建议先从向量搜索加图上下文入手：用语义匹配找到切入点，再取回相关节点。

过滤是另一道关卡，决定哪些内容能送到模型面前。预过滤缩小候选范围，后过滤精修检索结果。Chin 还强调，要把最相关的信息放在上下文靠前的位置。他说模型基本会忽略长上下文窗口里的其余内容，这个说法超出了他给出的证据；但实际的顾虑很明确：上下文窗口再大，也不能保证放进去的每条事实都会影响答案。选哪些上下文、按什么顺序排，仍是检索设计要考虑的事。

06

企业应用与进入图开发的途径

Chin 举的企业案例是 Klarna 的知识助手，它整合了企业 wiki、HR 系统和内部文档。他说这个项目取代了 Klarna 所有的 SaaS 系统；而客户案例能证实的是大规模整合，并没有到“全部取代”的程度。据 Chin 介绍，第一年员工提了约 25 万个问题，每天有 2000 次查询，员工使用率达 85%。这些是他引用的使用数据，不代表回答准确率；每日查询量反映的是统计时的情况，不是全年平均值。

想学习底层的图技术，Chin 推荐 Neo4j 认证项目：通过后能拿到一枚 LinkedIn 徽章，还会收到寄来的 T 恤。他还推荐了 GraphAcademy 上关于聊天机器人和 LLM 应用的课程。至于再推出 GraphRAG 认证，只是他提到的未来可能，并没有宣布已经上线。

Chin 介绍说，NODES 是一年一度的免费大会，横跨三个时区，连开 24 小时。通过大会上的分享和示例，也可以入门图开发。

07

嵌入向量如何与图节点关联

观众的第一个问题把整个检索流程核对了一遍：提交问题，做嵌入，执行语义搜索，找到对应的图节点，再取回相关节点。Chin 确认就是这样。好处在于，一个绕来绕去的自然语言问题，不必先变成精确的 Cypher 查询，语义匹配就能提供切入点。

这个切入点依赖事先建好的关联。在肺气肿的例子里，匹配到的嵌入向量之所以指向“肺气肿”节点，是因为图和嵌入向量早就连起来了。下一步是挑出周边的相关信息，而不是把所有邻居节点一股脑儿返回。Chin 提到，可以用余弦相似度和社区分组算法来筛选，再把得到的上下文往下传。

有人接着问：在简单的架构里，嵌入的文本块和节点代表的是不是同一块内容？这些关联又是谁建的？Chin 介绍的做法是：用 LLM 从非结构化数据中构建节点结构，再把文本嵌入作为属性存到节点上。这只是其中一种数据导入方式，并不要求每个文本块都和每个实体一一对应。

至于怎么建这些关联，他先提到 Neo4j 的 Python 库和插件，然后是与 LangChain、LlamaIndex、Haystack 的集成。框架可以自己挑；真正要做的事不变：建好图结构，再把它和检索时要搜索的嵌入文本连起来。

08

谁负责记忆的更新与删除？

下一个问题区分了两件容易混为一谈的事：提供记忆工具，和决定记忆该怎么变。更新和删除的逻辑归记忆 MCP 服务器自己管，还是由别的框架来编排？Chin 说他不清楚具体实现。他指出这个服务器是开源的，建议去问开发这些 MCP 服务器的 Michael Hunger 团队，或者去听之后 Hunger 和 Jesus 的分享。记忆生命周期该怎么管，这场演讲没有给出答案；光有工具，并不能说明由谁决定一条记忆何时该改、何时该删。

09

选择适合应用的框架

最后一个问题是：LangChain 和 LangGraph 是不是互补的？Chin 没有细致比较，只说 LangGraph 是 LangChain 团队做的智能体工具。他的团队用 LangGraph 做过一些智能体实验和原型，也做了与 LangChain 及多家记忆服务商的集成。他最后的观点是：选适合应用的工具。Neo4j 做这些集成，是为了支持这种选择，而不是非要绑定某一个编排框架。

为 Uber 规模的多模态智能体构建闭环评测

改善美食照片需要的不只是好看的修图：Uber 的智能体系统会评估路由决策、保住菜品的本来面目，并把生产反馈转化为经过基准测试的配置更新。

熟悉 LLM 智能体、结构化 JSON 输出以及分类的精确率与召回率，有助于理解评测设计。

01

如何改善一张美食照片而不改变食物本身？

外卖平台要优化数以百万计的菜品照片，同时还得保证照片和顾客实际收到的东西对得上，该怎么做？规模一大，这就不只是摄影问题，也是工程问题。据 Jai Chopra 介绍，这个平台的年化交易规模约 900 亿美元，同比增长 20%，覆盖 10,000 座城市，每月新增商品数以百万计。这些数字是演讲给出的背景信息，没有注明统计期。年化交易规模也不能理解为 Uber 的营收。Chopra 称，外卖业务的体量和 Uber 的出行业务相当。

照片往往是顾客对商家的第一印象。顾客是继续往下划、点开商品，还是直接加入购物车，可能就取决于这张照片。视频的分量也在上升，平台要处理的视觉内容随之变多。可独立商家的照片常常拍不出菜品本来的水准。他们受限于几件很实际的事：时间、摄影技巧和成本。请专业摄影师很贵，菜单一换还得再拍一轮，花费就更高了。

02

保住真实性和平台的多样性

图片好看有用，前提是顾客信得过。Chopra 指出，消费者不信任 AI 生成的图片，这是产品必须面对的约束：修图必须忠于原本的菜品，保留商家的品牌特色，也不能把每家餐厅都修成一个样子。一条修图提示词就可能抹平整个平台的多样性，哪怕单张输出看上去都很精致。

输入的图片也没法一刀切。平台遍布全球，照片的毛病五花八门：清晰度差、构图偏、颜色寡淡，还有别的质量问题，各种组合都有。用户上传的内容又多了一层变数。所以增强必须有选择：该改的改，已经好的保留。目标也不止于单张图片，还要看整个平台的结果：增长不能只是抢了其他商家的份额，上线要安全，系统要持续学习，运营成本也要控制住。

有两个极端都不好用。确定性的规则系统可控，但面对长尾图片很容易失灵。不受约束的智能体有发挥空间，泛化能力强，却可能突破安全要求，而一次修图能不能被接受，正取决于这些要求。Uber 的做法是划出明确的护栏，让智能体在护栏内自主行动。下面介绍的架构做了简化，但能代表生产系统的真实面貌。

03

路由、编辑、检查——并记录整个执行过程

执行流程从图像理解与路由开始。多模态 LLM 先描述照片内容，生成结构化输出。路由器根据这份评估，决定增强还是跳过。跳过就保留原图。增强则把图片交给修图智能体，QA 智能体给它反馈，它可以循环修改。如果反复尝试仍不合格，系统就不发布修改后的图片。合格的候选图还要经过最后的后处理和 QA，才会上架到菜单。

每个环节都有日志。按 Chopra 的描述，各个智能体的记录放在同一个扁平的 JSON 结构里，工程和产品同事都能看到一个案例的全貌。这些记录也能拿来做汇总分析。下面是跳过路径的一条示例记录，做了什么决策、下游哪些步骤没有执行，一目了然：

``json { "image_understanding": { "assessment": "No enhancement needed" }, "router": { "decision": "skip" }, "image_editing": null, "editing_qa": null, "publish_ready_qa": null, "outcome": "keep_original" } ``

这里的字段名只是为了说明扁平结构，并不是 Uber 真实的 schema。这种结构的好处是：排查案例时，既能看到发生了什么，也能看到哪些环节根本没被调用。

先有日志，再谈优化。 没有执行记录，就几乎没有证据来诊断故障，也搭不起学习闭环。Chopra 提到，Uber 用的可观测性平台是 Arize。这里说的扁平 JSON 结构是 Uber 自己记录执行过程的方式，并不是说 Arize 通用的 trace 模型是扁平的。

04

对照人工判断评估路由器

路由器会把图片、文字描述和元数据放在一起看。模型先用结构化的形式描述它看到的内容，再按一套带通过/不通过标准的评分细则给这份输出打分，得出增强还是跳过的决定。这样一来，视觉评估和路由决策就分开了，团队手里也有了一个可以评测的分类问题。混淆矩阵能显示哪些判断对了、哪些漏了，精确率和召回率则从不同角度衡量结果。

更复杂的路由不只决定改不改，还能选择执行策略。

| 路由问题 | 评测结构 | 要权衡的问题 | | --- | --- | --- | | 增强还是跳过 | 2 × 2 混淆矩阵 | 哪些图片需要干预？ | | 在多个分支中选择 | n × n 混淆矩阵 | 每个输入适合走哪个分支？ |

比如，某个分支可以把图片交给更小、延迟更低的模型，省成本、少等待，代价是质量可能下降。在这个更大的矩阵里，每个格子都能帮团队看出输入有没有进到合适的分支。

第一个版本上线时，Soumya Gupta 把人工标注当作模型要对齐的基准。流程从一份有代表性的数据集开始，覆盖不同地区、菜品类型和图片质量。标注员拿到的是客观的标注规范，用来减少主观偏差和噪声。随后团队运行智能体，把输出和这份黄金数据集对比，反复调优，直到通过发布护栏。路由环节的护栏是召回率：系统不能让差图漏过去。

05

一次路由错误可能变成一次忠实度错误

芝士汉堡的例子说明了多余干预的代价。一张高质量照片被误判为需要增强。Gupta 说，这等于花了算力却没换来任何质量提升，还让一张本来就好的照片有被改坏的风险。正确判断“这张不用动”，本身就是产品质量控制的一部分。

鸡翅的例子暴露了另一种风险：照片里有六只鸡翅，菜品描述写的却是八块。Gupta 把路由器放行这张图算作一次召回失误。下游的隐患在于，修图模型可能为了弥合这个差异，凭空多画出两只鸡翅。这样图片倒是和文字对上了，却不再忠于原照片。这个例子说明了多模态评测为什么要紧：图片和描述可能互相矛盾，而修图不能悄悄编造食物来“化解”矛盾。即便离线模型通过了初始评测，这类长尾失误依然可能发生。

06

把生产环境中的不一致变成经过基准测试的配置

静态模型没法一直跟上不断变化的生产数据分布。Uber 会定期抽样生产数据，交给人工标注，标注规范和离线基准用的是同一套。智能体结果和人工标注对不上的样本，会交给一个统管全局的诊断智能体（diagnoser agent），由它定位问题并触发自动调优。调优后的智能体必须在黄金数据集上达到既定指标才能上线，否则继续循环。这里虽然以路由为例，但 Gupta 表示，每个组件都有这项能力。

诊断智能体可以自己写配置、触发调优流水线，不需要人手动编排这些步骤。但这套自动化仍然离不开进入闭环的人工标注样本。这个区别很关键：目标由人的判断来定，诊断、优化和发布评测则交给配置驱动的机制去执行。

在自动调优内部，提示词优化器把工作拆给 Reflect 和 Synthesize 两部分：

1. 在没见过的人工标注样本上评测目标智能体，找出结果一致和不一致的样本。 2. 由 Reflect 分析不一致的样本，过滤噪声，找出系统性问题。 3. 把这些反馈连同智能体当前的配置交给 Synthesize，生成更新后的配置。 4. 对更新后的智能体跑基准测试。通过后，把新版本注册到智能体配置库。 5. 下一次生产运行时，加载这个已注册的版本。

这样，“提出来的配置”和“有资格上生产的配置”就区分开了：两者之间隔着一道基准测试。

这个自动化闭环的护栏本身也接入了可观测性，还配有快速回滚机制。基准测试管的是能不能上线；监控和回滚处理的是上线后才暴露的问题。

07

生成针对单张图片的编辑，再反馈它的失败

图片进入增强环节后，系统会专门为它生成一条提示词。生成提示词要用到图片描述，以及路由智能体给出的改进指示。这条提示词驱动图像增强，之后还要过一道多维度的 QA 关卡，检查摆盘、忠实度、色彩等方面。

候选图没通过时，QA 反馈会连同原始输入一起回到提示词生成环节。这样，下一次尝试既知道最初的任务，也知道上次错在哪。这个循环有上限：K 轮之内，系统要么得到一张通过修图关卡的候选图，要么接受覆盖率损失，不产出任何被采纳的增强结果。不能因为已经花了算力，就硬把修图结果发布出去。

以红薯薯条为例，第一次修图因为分量不对、摆盘不真实，没通过 QA；第二次拿到这些反馈后通过了。Gupta 把这个指标叫作 pass at K，解释为第 K 轮的通过率，并预期更多反馈能提高通过率。演讲没有说清楚，汇总通过率是前 K 轮的累计结果，还是只统计第 K 轮。所以落地这个指标前，必须先把定义讲明白。

08

通过比较原图和编辑后的图来定义“更好”

生成结果的评测采用成对比较：把输入图和输出图放在一起，判断输出是不是更好。这要求产品层面先定义清楚什么叫“更好”，而不只看审美偏好。Uber 和产品、设计、政策、法务团队一起对齐评分细则。具体标准不公开，已披露的维度包括忠实度、完整性、自然度和真实感。判断结果可以是“是”“否”或“不确定”。

下面两个例子区分了两类错误：凭空添加内容，和丢掉原有内容。

| 修图结果 | 未通过的标准 | 改动了什么 | | --- | --- | --- | | 加了虾 | 忠实度 | 加进了输入图里没有的食物 | | 去掉了寿司下面的酱汁 | 完整性 | 删掉了原菜品的一部分 |

两张输出图看上去可能都挺像回事。和原图一比，才看得出为什么两张都不算合格的增强。

09

揪出过度修正、不连贯的物体和不确定性

反馈也可能把修图模型带偏。有个例子里，第一次修图很有创意，却被打回；下一次就矫枉过正，换成了一只普通的陶瓷碗。Chopra 把这称为 reward hacking（奖励投机）：智能体为了应付 QA，变得过于保守。像素可以改动很多，却没带来实质改进。如果评测器只奖励“有变化”，就分不清“换了一张图”和“有用的修图”。

另一张输出图里，盘子盖住了酱汁。这是物体连贯性和物理合理性上的失败，说明底层图像编辑模型的局限会一路传导到应用产品上。Uber 有时会把这类失败案例分享给前沿模型团队，和他们一起解决底层问题。所以，应用层的 QA 既能找出调整智能体配置就能解决的错误，也能发现负责修图的模型本身的短板。

拿不准，本身就是停下来的理由。在馄饨的例子里，输入图和输出图都看不清是不是八个。系统没法有把握地核实数量，于是在生产中拒绝了这个结果。unsure 这个结论有实际后果：只要关键信息无法核实，图片看着再像样也不能通过。

10

把“是否发布”变成一个单独的决定

通过修图 QA 还不是最终的发布决定。候选图还要经过后处理和发布前 QA（publish-ready QA），包括额外的政策和质量检查。最后这道关卡看得更全面，能揪出前面环节本该发现却漏掉的问题。

Chopra 用瑞士奶酪模型解释这种冗余：每一层检查都有漏洞，所以系统叠加多层检查，降低故障漏到生产环境的概率。有些检查是故意重复的。最后这道关卡就是为了减少漏网的失败，哪怕上游评测已经放行了这张候选图。

11

把诊断扩展到模型评测循环之外

人工标注闭环负责应对数据漂移、保持和离线基准对齐，但它只是反馈来源之一。上线前的内部测试和线上产品的实际使用，也会产生更多信号。为了接住这些信号，Uber 把诊断智能体放在各个智能体之上：它接收来自不同闭环的反馈，判断哪个组件需要改进，再把配置工作分派给一个或多个智能体。

内部测试会收集点赞、点踩和自由填写的反馈。商家、设计团队和 Uber 其他产品团队也会提意见，这些都会回流到诊断和调优中。推送最新配置之前，系统会重放被标记的样本（好样本和坏样本都有），并对各项指标跑基准测试。一条投诉可以引发排查，但配置能不能上线，仍然要看重放和评测的结果。

12

评估部署之后发生的事情

生产环境的评测还延伸到平台的质量和健康度。Chopra 重点提到转化：顾客有没有把商品加入购物车、有没有转化、有没有完成下单。这些是持续监控的目标；演讲没有给出转化率提升的具体数字。

到了生产规模，数据可以按地区、设备类型和菜品类型切分。切分后能看出哪些地方效果变好了，哪些细分群体可能需要不同的调优。所以，学习过程不止于修图有没有通过 QA，还会跟着上线的系统走进平台，再用细分群体的数据指导后续改动。

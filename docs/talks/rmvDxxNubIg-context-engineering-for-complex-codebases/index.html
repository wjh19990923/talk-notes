面向复杂代码库的上下文工程：调研、规划、实现，并让人保持思考

Dex Horthy 讲解了有意识的上下文压缩、有针对性的调研、明确的实现计划和人工审查，如何帮助编程智能体在现有代码库中更有效地工作，同时不牺牲团队的理解。

面向复杂代码库的上下文工程：调研、规划、实现，并让人保持思考

01

为什么现有代码库会暴露随意 AI 编程的局限

Dex Horthy 认为，核心问题在于“看上去的产出”和“真正持久的工程进展”对不上。他说，AI 辅助的软件开发确实让交付的代码变多了，同时也带来了返工、代码反复改动和技术债。从零开始的简单项目也许很适合编程智能体，但大型的老系统是另一回事：得先弄懂现有架构，绕开历年积累下来的种种限制，做出的改动还不能只是又制造一个要收拾的烂摊子。0:24 1:09

他给出的对策是上下文工程：有意识地管理上下文窗口里放什么信息，从而让现有模型做成更多事。Horthy 说，他们三个人的团队花了艰难的八周，改变了协作和开发的方式，最后的产出大约提高到原来的两到三倍。他把这当作自己团队的经验和尝试这套流程的动机，而不是任何组织都能保证得到的结果。1:09 2:02

目标不只是写出看起来正确的代码。Horthy 同时提了好几项要求：智能体要能应付老代码库和复杂问题，不能产出低质量的东西，要让团队保持认知同步，还要真正把工作分担给 AI。当代码生成的速度超过了人能理解的速度，这几个目标就会互相冲突。所以，协作和审查本身就是技术问题的一部分，而不是事后才考虑的事。2:02 15:03 15:46

- 在老系统里，代码产出变多，可能掩盖了返工、反复改动和不断累积的技术债。 - 上下文工程通过有意识地管理上下文窗口，让现有模型发挥得更好。 - 一个三人团队经过八周艰难的流程调整，产出提高到原来的两到三倍。 - 认知同步让团队即使在实现量大增的情况下，也清楚代码库怎么变、为什么变。

02

把上下文窗口当作有限的工程资源

一种常见的失败模式是：让智能体做一个任务，它出错了就一遍遍纠正，一直纠正到对话长得没法收拾。用一个全新的上下文、更清楚的指引重新开始，会有些帮助，但 Horthy 推荐一种更有意识的做法：主动压缩。让智能体把现有对话里有用的信息浓缩成一份可以审阅的 Markdown 文档，新的智能体或新的上下文窗口就能直接从这些关键发现开始，不用把整个排查过程再走一遍。2:52 3:59

压缩有没有价值，取决于挑出来的信息会不会真正影响下一个决策。找文件、理解控制流、改代码、收集测试或构建的输出，这些都会占用上下文，冗长的工具返回结果也一样。一份好的压缩产物，应该保留任务本身、相关文件和精确的位置，把不必要的噪声去掉。Horthy 的说法是：凡是当前对话里没有的信息，编程模型一概不知道，所以它下一步做得好不好，取决于它手头那些 token 的质量。3:59 4:52

他从四个维度评估上下文：正确性、完整性、大小，以及对话的走向。错误的信息危害最大，其次是缺失的信息，再次是过多的噪声；反复失败的尝试也会让对话陷入一种没用的模式。他非正式地提出了一个“笨区”的说法，指上下文窗口越填越满、效果越来越差的阶段。以 Claude Code 为例，他认为用到 40% 左右可能就开始边际递减了，但也强调这个阈值会随模型和任务的复杂度而变化。4:52 5:42

- 主动压缩：把现有对话浓缩成一份可审阅的 Markdown 文档，交给新的上下文窗口。 - 保留任务、相关文件和精确位置，去掉探索性的搜索、冗长的工具输出等噪声。 - 从正确性、完整性、大小和走向四个维度评估上下文；错误信息的危害最大。 - “笨区”指上下文越满效果越差；40% 左右只是一个会变化的参考线，不是固定阈值。

主动压缩上下文 把干活中的对话浓缩成一份简洁的产物，带着关键发现启动一个新的智能体。 - 现有上下文——排查过程和累积的对话 - 压缩产物——任务、相关文件和行号 - 新的智能体——从压缩后的发现开始 - 现有上下文 → 压缩产物（浓缩成 Markdown） - 压缩产物 → 新的智能体（提供审阅过的发现）

03

用子智能体和“调研-规划-实现”来压缩工作

Horthy 认为，子智能体最有用的地方是控制上下文，而不是模拟公司里的各种角色。与其给智能体安上拟人化的头衔，不如让主智能体把一项范围明确的排查，委派到一个单独的上下文窗口里去做。这个“工人”负责那些费 token 的搜索和阅读，最后只交回一个简短的结论，比如相关的文件是哪个，这样主智能体就不用吸收每一步探索过程，可以直接往下做。6:34

在这个基础上，他提出了频繁的主动压缩，并把它组织成三个实用阶段：调研、规划、实现。调研要弄清现有系统实际上是怎么运作的，找出相关的文件；规划要把这些理解和要做的改动，转成明确的步骤，包括文件名、代码片段，以及每一步改完之后怎么测试；实现则按照审阅过的计划执行，同时让当前上下文保持聚焦。7:28 8:15 13:57

这套流程并不是说这三个阶段放之四海而皆准、永远不变。Horthy 明确说，“调研—规划—实现”未必会一直是标准顺序，真正长久的原则是：压缩、上下文工程，以及别把上下文窗口塞得太满。他也反对“Markdown 文档攒得越多效果越好”的想法：文档只有在准确浓缩了相关事实或意图、并且能让执行更好时，才有意义。17:40 18:36

- 用子智能体把费力的排查隔离到单独的上下文窗口里，而不是去模仿公司里的职位头衔。 - 调研弄清现有系统怎么运作、哪些文件要紧；规划写明改动、代码片段和测试方法。 - 实现按审阅过的计划执行，让当前上下文保持精简。 - “调研—规划—实现”的力度要和任务匹配；上下文工程和有意义的压缩，比死板的阶段或堆文档更重要。

调研—规划—实现工作流 把查清楚的代码库事实变成可执行的计划，再变成实现，上下文始终保持聚焦。 - 调研——找出相关文件，弄清系统行为 - 规划——写明改动、代码片段和测试 - 实现——在较少的上下文中执行计划 - 调研 → 规划（把发现转成明确步骤） - 规划 → 实现（执行准备好的计划）

04

让调研立足于实时代码，在计划变成代码之前审查它

常驻的仓库入门文档能给智能体提供有用的背景，但它有扩展性问题。代码库越来越大，面面俱到的说明要么写得太长，要么漏掉重要细节；智能体还没开始干正事，有效的上下文预算可能就已经被吃掉一大块。渐进式披露可以改善这一点：把指引分散到仓库的各级目录里，智能体只加载根目录的信息，以及和当前工作区域相关的那部分上下文。11:54 12:39 13:26

即使文档整理得再好，也可能和实现脱节。所以 Horthy 更倾向于按需生成的压缩上下文：把智能体引到相关的区域，用有针对性的排查去看系统的一个个纵向切片，再根据当前代码本身整理出一份调研文档。他把这称为“压缩事实”，而不是依赖那些团队未必能跟上线改动及时更新的文档。13:26 13:57

规划于是成了压缩意图。一份有用的计划，要把调研结果和产品需求、bug 报告或其他要做的改动结合起来，把要做什么写得足够具体，让人能判断这条路对不对。Horthy 说，他们团队越来越多地在计划里直接放上拟议的代码片段，因为含糊的计划没法让人对最终的改动有足够的把握。代价是：计划越长，执行越可靠，但也越难读，每个团队都得找到一个合适的平衡点。13:57 15:46

这个审阅环节守护的是认知同步：大家对系统在怎么变、为什么变，有共同的理解。Horthy 说，代码照样要审查，但审查计划能帮技术负责人跟上不断演变的架构，更早发现问题，而不必只靠看一大堆 diff。他还强调，把实现步骤、提示词和构建成功的证据一并展示给审查者很有价值，这样他们看到的不只是最终的代码，还有这个改动是怎么一步步做出来的。15:03 15:46 16:42

- 渐进式披露：只加载根目录的指引，以及和当前任务相关的那部分仓库上下文。 - 常驻文档可能过时；按需调研直接从当前代码中压缩出相关事实。 - 计划把调研和要做的改动压缩成明确步骤和拟议代码；写得越细越可靠，但也越难读。 - 尽早审阅调研和计划，及时发现误解、保持认知同步，避免错误的假设扩散成大量代码改动。

05

认清局限，按问题规模调整流程

Horthy 用一个 30 万行的 Rust 代码库来说明这套方法，那是 Boundary ML 旗下一门编程语言的代码。他说，他们对比了有调研和没有调研时做出的计划，扔掉了质量差的调研结果，最后提出的修复方案得到了正面回应。在另一次针对 BAML 的长时间会话里，他说七个小时交付了 3.5 万行代码，同时也明确指出，其中一部分是生成的代码和更新过的 golden 文件；其中一个 Pull Request 大约一周后被合并。这些只是具体的个人经历，不是对照实验，也不能证明代码行数就等于生产力。8:15 9:02

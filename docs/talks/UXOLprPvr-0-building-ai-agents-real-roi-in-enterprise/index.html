在企业软件开发生命周期中构建有真实投资回报的 AI 智能体

Booking.com 与 Sourcegraph 的合作把 AI 采用与交付指标联系起来，然后借助精心挑选的上下文和明确的规则，攻克了 GraphQL 生成、遗留系统迁移和代码审查。

熟悉 pull request、CI 流水线、功能开关和基础 GraphQL，有助于理解示例。

01

采用 AI 实际上改变了什么？

CEO 说公司必须拥抱 AI。于是有人买了 Copilot。与其说是想清楚了要解决什么问题，不如说是怕落后。六个月后，CFO 问：这笔钱换来了什么回报？工程团队到底变了什么，又该怎么衡量？买下使用权很容易；证明软件交付真的变好了，要难得多。

Sourcegraph 和 Booking.com 的合作，就是围绕这个问题展开的。Beyang Liu 说，Booking 正在把 AI 落地一路推进到看得见的成效。Bruno Passos 更谨慎：在 Booking 自己看来，他们还在起步阶段。真正值得看的是这条路径：从一个充满不确定的起点出发，经过推广、度量和培训，最后做出针对具体维护任务的智能体。

02

实验带来了一个清理问题

Booking 的开发者体验使命源自它的旅行业务：替开发者扫清障碍，让他们专心做那些帮人们体验世界的功能。公司各部门的进展并不一致。Passos 介绍，公司有 3,000 多名开发者。他还提到约 150 万个间夜，但没有说明这个数字对应哪段时间。

Passos 提到，Booking 每年要跑 250 万个 CI 任务。不过维护工作的根源更深，在于 Booking 的实验文化。每次 A/B 测试都会引入实验分支和 feature flag。团队转头去做新功能，flag 和死代码却常常留在原处。这样反复几十年，堆下来的实验在代码库里占了相当大一块，开发者都得去读懂。

Passos 准备幻灯片时，孩子们问他 feature flag 是什么。他解释说，这些东西会一直赖着不走，把代码库搞得乌烟瘴气。孩子们接了一句：“就像代码放屁？”他特意说明这个笑话和“代码坏味道”（code smell）是两回事，然后回到实际后果：代码库越大，周期越长，调试越多。Passos 形容，在这种臃肿的代码库里干活，90% 以上都是苦差事。这是他的个人描述，不是全公司范围的时间分配调研。

每季度的开发者调查也印证了这一点：开发者反映，在这个代码库里干活越来越难。Liu 举了 PwC 的例子：一位很有才华的工程师专门搭了一套复杂系统，用来更新遗留代码。这套系统也许做得很漂亮，但它耗掉的专业能力，本可以用在新功能和用户问题上。光是清理失效 feature flag 的迁移，就可能自成一项好几年的工程。

03

先做搜索，再做一个大家用得上的助手

Sourcegraph 的几款工具，分别对付这些负担的不同部分。Code Search 帮开发者在庞大的代码库里找到代码，理清来龙去脉。重构和迁移工具支持大规模改动。编码助手 Cody 则结合代码库上下文生成代码。Liu 把目标分成两个循环：在开发的内循环里增强人的创造力，在软件生命周期的外循环里把重复劳动自动化。

Booking 先从 Search 入手。代码库再臃肿，散落各处的上下文也更容易找到了。随后 Booking 开始试用 Cody，因为这个助手能直接用上搜索得到的上下文。下一步的打算，是把同一套基础延伸到智能体：自动化流程动手改代码之前，得先能找到相关代码。

据 2025 年 2 月 AI Engineer Summit 上的介绍，推广从 2024 年 1 月开始。Booking 向全体开发者开放了 Cody，但开放不等于大家会一直用下去。有些开发者试了试，觉得没什么用，就放下了。起初公司只提供一种 LLM，还设了 token 上限，大家没法放开手脚去试。

后来，Booking 和 Sourcegraph 放宽了用量限制，并让每位开发者自选模型。理由很实际：擅长挖掘遗留代码库的模型，写新服务时未必最合适。7 月，培训跟了上来。之前弃用助手的开发者渐渐找到了用武之地，成了常客。能用上模型、任务对路、学会怎么用，是推广落地中各自独立的三件事。

04

衡量交付、质量和现代化

Booking 最初的指标是节省的工时。Passos 觉得这个指标根基太弱：只拿几位开发者做的研究，撑不起业内流传的那些惊人总数。“节省了几万小时”这类说法，容易逼着团队去追一个标题数字，却说不清到底改善了什么。于是 Booking 开始找和自家工程流程贴得更紧的指标。

10 月定下新的 KPI 后，Passos 说，到 11 月已有迹象表明：每天使用 Cody 的开发者，速度快了 30% 以上。Booking 对“每天使用”的定义是一个月里至少 12 天在用，周末和不写代码的日子都算进去了。这是观察到的使用群体，不是随机分配的实验组；演讲并没有证明这个差异完全来自 Cody。

双方合作还在 Cody 前面架了一层 API，让它有机会进入 Slack、Jira 等 IDE 之外的工具。这是 Booking 当年做的集成；现行的 Cody 文档没有说明这层 API 的接口约定，也没说它现在是否可用。走出编辑器很重要：许多有用的开发任务，起点是一张工单、一次对话或一个自动化流程。

Booking 给 KPI 计划定了一年的期限。短期、中期、长期指标都得落在这一年里，所谓长期就是指一年。Passos 介绍了四个 KPI，先讲变更前置时间、质量和代码库洞察，再把它们和现代化改造串起来。

交付方面，团队看的是合并请求的评审时间和吞吐量。Passos 说，每天使用 Cody 的开发者，提交的合并请求比不用 Cody 的多 30%。这个吞吐量数据和前面说的提速是两回事。这些用户的合并请求代码量也更少；Passos 当时还没想好该怎么解读。

剩下的工作，是把度量和具体的工程举措挂上钩：

| 领域 | 拟采取的举措 | 目的 | |---|---|---| | 安全漏洞 | 把历史漏洞和代码库上下文结合起来 | 找出残留或可能存在的弱点 | | 测试覆盖率 | 围绕遗留行为补测试 | 检验替换后的实现 | | 代码库洞察 | 找出无用代码、过期 flag 和慢代码 | 确定现代化改造的目标 | | 平台迁移 | 借助这些发现减少迁移工作量 | 从按年计缩短到按月计 |

测试覆盖率这条思路，给出了一座具体的桥：先用测试把遗留行为固定下来，再要求迁到新平台后的实现通过这些测试。把平台迁移从几年缩短到几个月，仍然只是目标，不是已经拿到的结果。

05

定制提示词变成了智能体开发

用助手的工程师，也开始拿底层 API 做实验。定制完提示词，下一个问题自然就来了：能不能把几次调用串起来，做成更长的自动化流程？这些调用链，就是智能体的起点。

早期尝试碰上了预期错位：大家对 LLM 能稳定做好什么，想法并不一致。配套幻灯片还把模型选择、可复现性和可靠性列为几个坑。Booking 和 Sourcegraph 的对策，是在阿姆斯特丹办了一场为期一周的联合黑客松，把两边团队拉到一起，围绕具体任务和提示词逐个攻克。最后做出了三个应用：GraphQL 生成、迁移分析，以及贴合组织自身规范的代码评审。

06

在生成 GraphQL 之前先检索 schema 路径

第一个智能体针对的是 Booking 庞大的 GraphQL API。Liu 说，它的 schema 超过 100 万 token。按他的说法，当时的上下文窗口装不下这么大的 schema；就算装得下，模型也很难连贯地用好它。容量这一点得放回当时的背景看：这场演讲之前，Gemini 1.5 Pro 已经提供了 200 万 token 的窗口。但这既不能说明 Booking 的完整 schema 放得进它获准使用的工具，也不能说明模型能据此稳定地生成查询。真正的工程难题，是挑出可用的 schema 上下文，而不只是提高 token 配额。

这个智能体分几步拼出上下文：

1. 搜索 schema，找出与请求相关的候选节点。 2. 从搜索结果中筛选相关节点。 3. 向上回溯，取回把这些节点连起来所需的父节点。 4. 拼好相关的 schema 结构后，生成回答。

只找到一个孤立的字段还不够，模型还得知道怎么从查询根节点走到它。向上回溯，保住的就是这层结构上下文。演示中，右侧面板先展示智能体挑选节点的过程，然后才出现回答。

举个简单的例子：假设要查酒店名称。匹配到的字段 Hotel.name，还需要经过父路径 Query.hotel，包括它的必填参数。相关的 schema 片段可以是：

```graphql type Query { hotel(id: ID!): Hotel }

type Hotel { id: ID! name: String! } ```

有了这条路径，生成的查询就能同时带上根字段和嵌套的选择：

``graphql query HotelName($id: ID!) { hotel(id: $id) { name } } ``

由此可见，schema 检索必须保留节点之间的关系，不能只返回含有匹配词的片段。Liu 提到，朴素的生成方式虽然界面看着差不多，却会产生幻觉；黑客松期间针对具体任务打磨提示词和检索之后，效果明显上了一个台阶。

07

在尝试重写之前先划定迁移范围

迁移实验从遗留代码入手，其中有的函数超过 1 万行。方法上结合了代码搜索、结构化元提示词和分而治之的拆解。改造一个庞大的函数或服务之前，团队得先弄清它的依赖，把工作拆成能下手的小块。

专家结对，帮开发者学会给出合适的提示词和上下文。Passos 把这和前面的推广难题联系起来：有些开发者看不上这个助手，是因为还不知道怎么在自己的代码上用好它。把专家请进办公室，这些知识就落到了实处，不再停留在纸面上。

Passos 说，此前团队已经调查了好几个月，而黑客松的两天就帮他们找出了调用点，摸清了迁移问题的规模。有了这些认识，团队就有了起点，也看清了哪些容易的部分可以先动手。“几个月缩短到几天”说的是理解代码库、划定范围；迁移本身仍在实验阶段。在智能体动手改之前，先摸清改动的边界，本身就很有价值。

08

让代码审查具体而有选择性

起初，代码评审看起来不太值得再做一个智能体，因为市面上的 AI 评审产品已经很多了。但和 Booking 及其他企业聊过之后，他们发现了一个没被满足的需求：评审要依据大量团队特有的规则、规范和约定，这是一条长长的尾巴。通用的评审工具，恰恰可能漏掉组织最在意的那些约束。

Sourcegraph 当时正在把一套流程做成产品，用来搭建贴合这些需求的评审工具：

1. 用一个简单的平面文件写下团队规则。 2. 找出 pull request 改动了哪些文件。 3. 对这些文件应用相关规则。 4. 有选择地发评论，每条都对应一条适用的规则。

平面文件把评审要求写得明明白白；按相关性筛选，则让无关的规则不会混进某次评审。

明确的目标是精确率优先于召回率。评审工具应该优先给出开发者能据此动手的评论，哪怕因此漏掉一些潜在问题。在这种场景下，评论多不等于有用：噪声一多，智能体就成了本已拥挤的评审流程里又一个添活的来源。

09

声明服务规则并更早执行

合作一年后，Booking 开始把评审的思路延伸到服务本身。既然 CI 能报告某个改动违反了规则，开发者能不能更早拿到这个信息？比如直接在 IDE 里看到，还附带修复建议。更长远的设想，是让服务能自己发现并修好一部分问题。

原料包括代码库上下文，以及开发者已经攒下的提示词库。把这些问题自动化地拿去问服务器，就能挖出关于代码库的知识，找出该做的事。Passos 说，目标是在 2025 年底前实现这个愿景的一部分，但前面还有大量工作；服务自愈只是一个方向，不是已经交付的成果。

Liu 把声明式规则和《人月神话》里讲的架构一致性流失联系了起来。成功的软件会带来用户、收入、功能需求和 bug 报告。竞争压力推着团队欠下技术债。参与的人越多，共同的愿景和统一的标准就越难守住。

按这套设想，资深工程师和架构师负责定义整个代码库都该遵守的约束。不论代码是人写的还是 AI 写的，这些约束都能在评审时和编辑器里生效。企业合规要求就是一个现成的场景：这类义务反复出现，开发者必须满足，却不会直接带来新的用户功能。配套幻灯片还把这个愿景延伸到了在后台自动提交 pull request 的智能体。

10

培训把访问权限变成日常实践

把合规要求写进服务规则，是减少重复性开发工作的一种办法。但 Passos 最后讲的，是他眼中最重要的组织实践：教育。Booking 和一个个业务部门整体合作，通过为期两天的工作坊和黑客松，给开发者手把手的支持，也给他们留出尝试的时间。亲眼看到工具怎么用在自己工作上的人，更可能成为常用用户。

这些培训是为了巩固交付上的改善。Booking 把这些改善和每天使用联系在一起，并没有单独衡量培训本身的效果。实际经验很具体：一个人人都能用的助手，照样可能被冷落；开发者得学会给它有用的上下文，挑合适的任务，看清它在哪里帮得上忙。智能体也正是从同样的做法里长出来的：和真正懂这些代码的人一起，啃真实的问题。

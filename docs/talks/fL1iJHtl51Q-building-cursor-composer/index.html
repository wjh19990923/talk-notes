打造 Cursor Composer：快速的智能体需要真实的环境

Composer 把低延迟生成与学习得到的工具使用能力结合起来，背后是一套与开发者实际工作环境高度一致的强化学习基础设施。

对编程智能体和工具调用有基本了解会有帮助；不需要强化学习背景。

01

一个有用的编程智能体能有多快？

编程智能体能不能既快到可以和开发者并肩干活，又聪明到能胜任真正的软件工程？Cursor 的第一个智能体模型 Composer 瞄准的正是这两者的结合。Lee Robinson 介绍了 Cursor 工程和研究团队的这项工作，内容承接他的同事 Sasha 之前的一场分享。在 Cursor 的内部基准上，Robinson 把 Composer 排在最好的开放模型之上，略低于当时的前沿水平，也就是 Sonnet 4.5 和 GPT-5.1 Codex。

Robinson 称，Composer 的 token 生成速度大约是同等智能水平模型的四倍。这里比的是生成速度，并不是说每个编程任务都能快四倍完成。Cursor 公开的基准方法用的是自家内部框架，按分词器归一化后计算每秒 token 数；文中的模型对比反映的是发布时的格局。

先例是 Cursor 的自动补全模型 Tab：建议下一处编辑时，低延迟就已经很关键，团队想把这种响应速度带到智能体上。早期原型以 cheetah 的名字发布，用户对速度的反馈很积极。但他们觉得它能力不够，没法当日常主力编程模型。

于是 Cursor 围绕自己的代码仓库和开发工作，搭了一套内部基准。实际的验收标准是：Cursor 自己的开发者每天都愿意选这个 checkpoint 来开发产品。有两项改进帮他们达标：并行调用工具，以及用好语义搜索。光生成得快不够，还得能判断好下一步该做什么。

02

让调查过程保持在前台

演示用的是 Cursor 2.0、它新的智能体视图，以及标为 Composer One 的模型。智能体排查一个开源仓库里的问题时，会并行调用 grep、读文件、运行 shell 命令、编辑文件，还维护一份待办清单。最特别的是这些动作一个接一个地呈现在眼前：开发者看着，排查就一直在往前推。

这和“启动智能体、过很久再回来看”是两种不同的交互。Robinson 以大约二十分钟的等待为例：任务一长，人就忍不住切去干别的。响应快的智能体则能让开发者一直盯着问题，跟着它的进度走。接下来他转向支撑这种编程方式的训练和基础设施，并说明自己是从工程师而不是 ML 研究员的角度来讲。

03

在完整的工具使用尝试上训练

用户的查询到达 Cursor 后端，智能体决定调用哪些工具。Robinson 说可用工具大约有十个，重点介绍了五类：读文件、编辑文件、搜索代码库、检查 lint、运行终端命令。智能体还要决定这些调用串行还是并行。强化学习环境的目标，就是尽可能还原生产环境里的这些选择。

经验的基本单位是 rollout：通过一连串动作回应一次查询的一次尝试。训练时可以从同一个初始状态出发，探索不同的尝试：

1. 从相同的查询和环境出发。 2. 让模型选择并执行一连串工具调用。 3. 回到同一起点重来，允许走出不同的序列。 4. 给输出打分，比较几次尝试。 5. 用得到的反馈更新模型参数。

图示里有两次尝试：一次是读文件再编辑；另一次先搜索代码库，再读文件、编辑。完整的幻灯片上，第一次标了叉，第二次打了勾。训练信号由此变得具体：在工具之间走不同的路径，结果可能完全不同。

04

简单的循环变成了基础设施问题

把这个循环规模做大，会遇到三个约束：

- 训练与采样对齐。 Composer 是一个大型混合专家（MoE）模型，分布在数千块 GPU 上。训练必须快，同时又要和生成 rollout 的模型保持高度一致。 - rollout 时长不均。 Robinson 提到，一次尝试会消耗几十万到上百万个 token，调用几百次工具。不同路径耗时不同，完成时间参差不齐。 - 工具要和生产环境一致。 训练需要和产品完全相同的工具格式和返回结果，但训练的请求是成批集中涌来的，和平常的生产流量很不一样。

这些约束起初是为了让模型学到有用的行为，但要真正满足它们，得靠模型周边的系统。

整个架构把服务器分成三种角色：

| 服务器 | 职责 | 所用技术 | |---|---|---| | 训练 | 更新模型参数 | PyTorch | | 推理 | 生成并协调 rollout | Ray | | 环境 | 在类似 Cursor 的工作区里执行工具 | 编程环境 |

推理端把 rollout 的 advantage（优势） 回传给训练端：这些信号会推动学习去强化或抑制某次尝试里的行为。训练端据此生成更新后的参数。把环境执行单独拆出来，系统既能还原编程工作区，又不必把它塞进训练服务器里。

为了给这个大模型提速，Cursor 开发了用于极低精度训练的自定义 kernel。Robinson 说好处有两个：训练更快，交接给推理也更顺。他称在 NVIDIA Blackwell 芯片上，混合专家层大约提速 3.5 倍。对应的 kernel 报告 把这个单层结果和端到端数据分开列出：在 Blackwell 上，相比 BF16，端到端训练吞吐量提升约 1.5 倍。单层的提升不能直接套到整个训练过程上。

05

在真实的编程环境中让 rollout 保持忙碌

一次训练更新后，新权重回到推理服务器，继续跑 rollout。这些 rollout 不会同时结束：有的要执行一长串工具调用，或者装一个包，有的很快就跑完了。调度方式太简单的话，算力就会在这些空档里闲置。Cursor 在线程和进程之间做负载均衡，减少长短不一的尝试造成的浪费。整个 rollout 过程中，推理端不断向环境服务器发送工具请求，再接收结果。

Cursor 既做编程产品又做模型，这带来了一个难得的机会：搭建 Composer 强化学习系统的同时，他们也在做 Cloud Agents。Cloud Agent 可以脱离本地 IDE 运行，从手机、网页或 Slack 上启动。它的云端虚拟机会加载用户的代码，为修改文件和执行工具提供安全沙箱。

同一套基础设施正好能提供逼真的 RL 环境。训练系统不必另造一个与产品无关的仿制工作区，直接用给用户跑智能体的那套基础设施就行。剩下的难题在运维上：训练需求的峰谷比 Cloud Agents 的流量剧烈得多。Robinson 介绍了跨多个集群的编排，以及规模达数十万台虚拟机的机群，还展示了团队用 Composer 搭的内部机群看板。

06

成为语义搜索的熟练用户

为什么要还原真实环境，而不是 mock 工具？语义搜索能说明多出来的这份真实度换来了什么。Cursor 自己训练 embedding 模型，给代码仓库建索引，让智能体能用自然语言查询找到相关文件。这样模型就能按代码的含义去找，而不必完全依赖精确的文本匹配。

在语义搜索研究中，Cursor 在 Cursor Context Bench 上对比了有无语义搜索的智能体，这个基准考的是代码库相关的问题。Robinson 称，在 Cursor 的框架里，几乎每个模型都能从中受益，Composer 受益尤其明显。展示的对比显示，在这项代码库问答评测上，加上语义搜索后 Composer 相对提升了 23.5%。它衡量的是检索辅助下的问答能力，不代表编程任务的成功率整体提高。

原因和训练直接相关：Composer 训练时用的，就是推理时会用到的那个搜索工具。它能学会这个工具什么时候有用，以及怎样把搜索结果融进排查过程。所以环境的真实度不只关系到调用能不能正确解析；它让模型真正练过那些让产品与众不同的能力。

07

学会更早完成、更谨慎地编辑

随着训练推进，更多 rollout 和算力继续带来提升。Robinson 描述了一条进步曲线：从大致相当于最好的开放模型，逐步逼近前沿编程智能体。他认为这说明强化学习值得用在困难的专门任务上：编程已经验证过，其他领域也可能适用。

端到端的响应速度不只取决于 token 速度，也取决于动作序列。 Robinson 举的例子是并行读取十个文件，而不是一个个读。一旦路径已知、读取互不依赖，同样的调度原则可以用 Python 这样写：

```python from concurrent.futures import ThreadPoolExecutor from pathlib import Path

def read_files(paths: list[Path]) -> dict[Path, str]: def read(path: Path) -> str: return path.read_text(encoding="utf-8")

with ThreadPoolExecutor(max_workers=10) as pool: contents = list(pool.map(read, paths))

return dict(zip(paths, contents)) ```

这段代码的结果仍然把每个路径和它的内容对应起来，互不依赖的读取则可以同时进行。智能体要决定的是什么时候适合这样批量处理：找出路径的那次搜索，仍然得在读取之前完成。Composer 经过训练，养成了并行调用工具的习惯，前面演示里的体验也因此更好。

Robinson 还提到模型变得更克制了。早期的 checkpoint 改得太多，有些改动根本没必要。训练得越多，Composer 越倾向于先搜索、读文件再动手，找到相关代码后才尝试修复。后面还有不少提速工作要做，但行为上的改进已经不只是把同样的动作做得更快：模型在学一种更高效的操作顺序。

08

走出尴尬的中间地带

Composer 随 Cursor 2.0 于 2025 年 10 月 29 日发布，就在这次大会的前一个月。Robinson 问台下谁用过，举手的人比他预想的多。讲到使用体验，他先拿飞机上的 Wi-Fi 打比方：能用，但慢得让人抓狂。

编程智能体也可能卡在类似的尴尬中间地带，他称之为“半异步死亡谷”。一个要跑十分钟、二十分钟的任务，想持续交互嫌太慢，却又占着不少注意力，让开发者没法彻底撒手。真正好用的选择在两头：

| 模式 | 开发者的角色 | 工作方式 | |---|---|---| | 快速的前台智能体 | 全程参与 | 跟着进度走，随时回应 | | 强大的后台智能体 | 把活交出去 | 让它长时间运行 |

Robinson 把这个让人沮丧的中间地带，和可能跑三十分钟、几小时甚至几天的后台任务做了对比。这些时长说的是交互模式，不是实测的 Composer 完成时间。在他看来，Composer 让写代码重新有了同步的感觉，找回了几分亲手写代码的乐趣。

他自己的工作流在模型层面兼取两者之长：先用 GPT-5.1 Codex 制定计划，再让 Composer 去实现。计划给更快的实现模型备好了上下文——这正是 Dex 在本次大会早些时候讲的上下文工程的一个实际应用。

09

模型与其部署环境共同发展

第一条研究心得关于专精。有了高质量数据和充足算力，强化学习在 Cursor 的具体目标上效果很好：打造优秀的编程模型。Robinson 明确把这个目标和追求通用智能区分开来。贴近生产的任务、环境和工具集，让训练有了具体的靶子。

第二条心得关于构建系统的过程。Robinson 说，Cursor 团队写代码、调试，全程都在用 AI 辅助。这方面的进步会在整个工程工作中产生复利：团队能尝试更多想法，发布更多产品改动，做更多研究。用 Composer 搭的那个机群看板，就是产品反过来帮忙搭建自身配套基础设施的一个实例。

最后一条心得回到 ML 和系统工程的关系。训练 Composer 遇到的很多障碍，最后都成了基础设施问题：提供逼真的执行环境，协调长短不一的任务，在训练和推理之间高效切换。Robinson 联系起自己在 Vercel 的经历：一个 JavaScript 或 Python 框架用起来顺不顺手，部分取决于运行它的基础设施。智能体好不好用，既取决于模型，也取决于它运行的环境。

最后他发出邀请，欢迎大家一起打造这些编程模型：Cursor 当时正在多个岗位招人，还开了纽约办公室。

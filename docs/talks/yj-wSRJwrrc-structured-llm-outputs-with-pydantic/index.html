Pydantic 示例

幻灯片原文
Pydantic parses a timestamp string into a datetime and a list of numeric strings into an integer tuple. The typed fields also give IDEs autocomplete and spell checking.

Pydantic Example

from datetime import datetime
from typing import Tuple

from pydantic import BaseModel

class Delivery(BaseModel):
    timestamp: datetime
    dimensions: Tuple[int, int]

m = Delivery(timestamp='2020-01-02T03:04:05Z', dimensions=['10', '20'])
print(repr(m.timestamp))
#> datetime.datetime(2020, 1, 2, 3, 4, 5, tzinfo=TzInfo(UTC))
print(m.dimensions)
#> (10, 20)

用 Pydantic 获得结构化的 LLM 输出：从脆弱的 JSON 到可编程的系统

Jason Liu 讲解了 Pydantic 模型、OpenAI 函数调用、Instructor 和显式的校验，如何把语言模型的输出变成现有软件能够检查、执行和维护的带类型对象。

用 Pydantic 获得结构化的 LLM 输出：从脆弱的 JSON 到可编程的系统

01

真正的集成问题不是聊天——而是结构化数据

Jason Liu 认为，生产环境的核心问题是：怎样把语言模型接到现有软件上。这些软件早就对 schema、API 和数据结构有明确要求。很多开发者最初是在聊天界面里接触这些模型的。但他们实际要搭的系统往往需要处理输入、产出结构化结果，还得兼容那些改不了的接口。这种场景下，让模型输出 JSON，再祈祷结果能被解析，算不上可靠的编程方式。 0:14 1:14

就算回答看起来是合法的 JSON，也可能藏着细微的契约问题，直到下游代码出错才暴露出来。比如这次回复用 user 字段，下次换成 username；或者模型在数据前后加上几句闲聊。Liu 认为，这类错误应该靠显式契约暴露，而不是靠日志、正则表达式和逐个盯着字符串检查。 2:07

OpenAI function calling 让情况好了一些：开发者可以指定输出的 JSON schema，在更固定的位置拿到结构化参数。不过 Liu 强调，JSON 解析成字典之后，应用照样会碰上缺键、类型错误、拼写不一致，还得手写一堆检查。更好的接口应该先校验数据，再交给应用代码一个能直接用的对象。 2:07 3:04

- 生产环境的集成必须满足现有的 API、schema 和软件接口，光能聊天远远不够。 - 输出看起来像 JSON，也可能违反契约：字段名不一致、夹带对话文字、缺值或类型错误。 - OpenAI function calling 让按 schema 抽取更可靠，但字典交给应用使用前，仍要显式校验。

02

让 Pydantic 模型成为应用契约

Liu 把 Pydantic 看作语言模型输出和传统 Python 系统之间缺失的那一层。它用类型提示定义数据模型，用字段校验和模型校验保证数据符合预期，还能生成 JSON schema，直接传给 OpenAI function calling。在他举的配送例子里，时间戳以字符串给出，尺寸以字符串列表给出，都能解析成声明好的 datetime 和整数元组。 3:04 3:58

好处不止是解析成功。timestamp 和 dimensions 一旦声明为字段，IDE 就能显示类型、提供自动补全，还能抓出命名错误。提示词也更好审查了：期望的结构不再埋在一长段文字指令里，也不用靠手动维护的 JSON 示例，而是写成代码里的输出契约，开发者可以检查，也可以持续迭代。 3:58 4:59

Liu 介绍了自己开发的 Instructor 库，用来把这套契约接到 OpenAI function calling 上。按他演示的流程，开发者先给 completion API 打补丁，再把一个 Pydantic 对象声明为 response model，拿回来的就是这个模型的实例，不用再手动从无类型的字典里取值。他也承认，给 completion API 打补丁这个设计有争议，而且这个实现只支持 OpenAI function calling。想接入更多语言模型、用上更多功能，可以选另一个框架 Marvin。 4:59 5:57

- Pydantic 把类型提示、字段校验、自动解析和 JSON schema 生成结合起来，构成应用层的数据契约。 - 声明好的模型字段带来 IDE 自动补全和类型提示，结构化提示词也更便于审查。 - Instructor 接收 Pydantic response model，通过 OpenAI function calling 返回带类型的对象。 - Marvin 是另一个可选框架，支持更多语言模型和功能。

03

在模型内统一提示、校验和恢复

Pydantic 模型能表达的不只是扁平的回复。它可以包含嵌套引用、关联对象列表、可复用的类，以及定义行为的方法。Liu 用用户信息、地址、最好的朋友和朋友列表来演示。类的 docstring 和字段描述会写进发给模型的 JSON schema，所以文档既影响模型怎么理解任务，也影响开发者怎么理解生成的对象。 5:57 6:50

这样一来，提示词质量、数据质量和代码质量可以放在同一处审查。好的变量名、清晰的字段描述、准确的文档，都直接参与模型交互，不再是各管各、慢慢脱节的独立产物。Liu 想说的不只是结构化生成能产出更干净的 JSON，而是数据模型应该把提示词、数据和行为一并收拢。 5:57 6:50

校验给模型输出划出了一道明确的边界。常规校验器可以规范化或拒绝取值，并返回应用代码能捕获的错误；LLM 驱动的校验器则能判断定性条件，比如一句话是否令人反感。Instructor 还能设定重试上限，把校验失败的信息发回给语言模型，要它给出修正后的回答。 6:50 7:51

Liu 特意把这个重试循环和更宽泛的提示词框架区分开：这套机制由校验、错误处理和重新提问组成，每一块都是独立、可管理的软件。规则可以是字符数上限，也可以是去数据库里查某个名字是否存在。代价是开发者得显式定义相关约束和恢复逻辑，不能指望一开始的提示词就落实所有业务规则。 7:51

- 嵌套模型、可复用类、方法、docstring 和字段描述，把提示词、数据和行为合进一个便于审查的结构。 - 常规校验器负责规范化或拒绝取值，LLM 驱动的校验器可以判断定性条件。 - Instructor 把校验错误反馈给模型，并在设定的上限内重试生成。 - 字符数限制、基于数据库的名字检查，都可以作为显式的应用约束来执行。

校验与修正循环 校验失败会变成修正反馈，驱动下一次有次数上限的生成。 - 模型响应 — 生成一个候选的结构化对象。 - 校验 — 应用模型和字段约束。 - 收集错误 — 记录失败的校验和错误信息。 - 重新提问 — 在最大重试次数内把错误发回给模型。 - 模型响应 → 校验（检查输出） - 校验 → 收集错误（失败时） - 收集错误 → 重新提问（发送反馈） - 重新提问 → 模型响应（再试一次）

04

显式地对不确定性和可复用结构建模

结构化输出可以表达不确定性，不必指望模型一字不差地复述某句约定好的标记短语。Liu 提出用一个包装对象，里面放一个可选的用户抽取结果、一个 error 标志和一条错误信息；单个字段（比如角色）也可以设为可选。有了这个逃生出口，“没有结果”就成了应用里的一等状态，下游代码可以据此分支处理。否则就只能拿字符串去比对一句表示“模型不知道”的话，这种做法很脆弱。 8:47

可复用组件也让提示词的行为更模块化。Liu 用同一个时间区间结构来定义工作时间和休闲时间，两者共用 start 和 end 字段。如果抽取不稳定，他建议在这个组件里加一个思维链（chain-of-thought）字段，对比加与不加两种配置，弄清测试和生产环境下延迟与性能的取舍。 9:49

做开放式抽取时，可以用键值属性列表表示任意属性，同时不丢掉结构。属性键要保持一致，可以靠指令引导、校验器检查、重试修复；再加一个显式索引，还能把列表控制在期望的属性数量内。同理，每个用户带一个 ID，再配一份朋友 ID 列表，就能表示一张关系网络，普通的图处理代码直接就能遍历。 9:49 10:50

- 可选结果、可选字段和显式错误信息可以表示抽取失败，不必依赖脆弱的标记字符串检查。 - 可复用的时间区间组件可以带一个可选的思维链字段，用来对比测试与生产环境的延迟或性能。 - 键值属性列表支持开放式抽取，再用校验器、重试和显式索引约束一致性与数量。 - 用户 ID 加朋友 ID 列表，把关系网络编码成结构化数据。

05

把检索、规划和引用变成可执行的数据

Liu 把同样的建模思路用在了检索增强生成（RAG）上。他不假设每个问题都对应一次向量搜索，而是设计了结构化的搜索请求，包含搜索类型、标题、查询语句和日期过滤条件。一个方法就能把视频搜索和邮件搜索分派到不同的后端；模型生成的一组搜索请求，也可以交给常规应用代码异步处理。 11:41 12:37

规划也可以表示成图。Liu 描述了一种查询计划，每个节点包含 ID、问题和依赖关系。相互独立的查询可以并行执行，后面的节点再合并结果。他拿这种“模型一次生成完整计划”的做法，和反复问智能体“下一步做什么”做对比：计划生成之后，执行就变成了普通的依赖管理和检索问题。 12:37 13:40

做知识图谱抽取时，Liu 建议让生成的结构尽量贴合图可视化 API。模型输出和下游使用方对齐了，创建和渲染图的代码就简单得多。他以一段量子力学的描述作为输入示例，只用很短的代码就把它转成了可视化图。 13:40 14:36

要求最严格的例子是有出处的问答。Liu 把答案建模成一组事实，每条事实关联一段或多段从原文摘出的子串。如果摘录在原始文本块里找不到，校验器就丢掉这条事实；第二层校验只保留至少有一段摘录通过验证的事实。这能证明引用的文字确实出现在提供的材料里。但这套机制只检查子串是否存在，本身并不能保证每一处解读或转述都正确。 14:36 15:28

- 带类型的搜索请求写明了后端、查询语句、标题和日期过滤条件，可以按后端分派、异步执行。 - 模型一次生成查询计划 DAG，标出依赖关系；相互独立的检索先并行执行，再合并结果。 - 让抽取出的图结构贴合可视化 API，能减少创建和渲染图的代码。 - 引用校验器只保留至少有一段摘录能在原文中找到的事实；子串存在不代表解读正确。

按依赖关系执行检索 模型生成一份查询计划，先并行查询，再按依赖关系合并。 - 查询计划 — 生成包含 ID、问题和依赖关系的节点。 - 第一次查询 — 执行一次独立检索。 - 第二次查询 — 并行执行另一次独立检索。 - 依赖节点 — 等待所需的前置结果。 - 最终合并 — 合并已有的依赖结果。 - 查询计划 → 第一次查询（独立） - 查询计划 → 第二次查询（独立） - 第一次查询 → 依赖节点（所需结果） - 依赖节点 → 最终合并（依赖已满足） - 第二次查询 → 最终合并（合并结果）

06

把未来的能力当作领域建模的机会

Liu 更大的论点是：结构化提示词把工作重心从临场琢磨更好的指令，转向了领域建模。对象可以自带专属指令、嵌套或递归结构，还可以带上行为，让生成的数据融入现有软件。模型一旦产出图、工作流或计划，普通代码就能遍历它，或者把它分派给 Airflow 这类系统，不必依赖不受约束的循环。 10:50 11:41 15:28

他还提到，结构化评测仍在持续实验中：一个接口可以判断回答是否刻薄，另一个接口可以考察数值属性的分布，并对照明确的预期打分。演讲把这部分定位为仍在推进的工作，而不是已经完成、或已普遍解决的评测体系。 16:35

技能问题：我们如何用 AI 让智能体真正擅长使用 Supabase

一份部门报表可能数字全对，却暴露了不该暴露的数据。这场工作坊跟随一个 Supabase 安全技能，从指令和安装一直走到一次很能说明问题的不完美评测。

具备基础 SQL 并熟悉编程智能体会有帮助；文中会在出现时介绍技能打包、MCP 和行级安全。

01

如何让智能体擅长使用你的产品？

How do you give an agent the product knowledge it needs, and then check that the knowledge changes its behavior? Pedro Rodrigues’s workshop approaches that question through the work of writing Supabase skills. Onstage, he renames the session Level Up Your Skills, reserving Skill Issue and the production lessons for the following day.

The presentation itself is a small demonstration: a localhost application built with Claude, complete with a dark-mode toggle. Rodrigues introduces himself as a Supabase AI tooling engineer working on agent experience, or AX—the counterpart to developer experience. The workshop follows a practical sequence: write a skill, test it manually, and automate the test with evaluations.

02

在指令变得相关时再加载它们

A skill is a folder, not merely a long prompt. Its required entry point, SKILL.md, contains Markdown instructions and frontmatter with a name and description. Optional files can supply reference material or executable workflows in Bash, Python, or another language.

The central mechanism is progressive disclosure. Initially, the agent receives the skill’s metadata rather than its entire body. The description acts like an envelope: it tells the agent enough to decide whether to open the instructions. Once loaded, those instructions can point to additional files that the agent reads only as needed. The Agent Skills specification describes this separation between discovery metadata, instructions, and supporting resources.

Rodrigues compares SKILL.md to a book’s index with extra instructions. Reference files are ordinary Markdown chapters, often kept in a reference directory. They can link to one another, so a skill can form a graph of information; that possibility does not require building a deeply nested reference hierarchy. The useful design property is that a task can reach the relevant detail without loading every chapter first.

03

把技能和 MCP 结合使用

Skills and MCP address different parts of an agent workflow. A skill supplies context and instructions, including workflows too extensive for a tool description. MCP supplies an integration through which the agent can act. An agent without Bash access can still use a service through an MCP tool.

| Component | Main responsibility | Execution dependency | |---|---|---| | Skill instructions | Explain what to do and when | Agent reads the files | | Bundled script | Perform a scripted operation | Compatible local runtime | | Remote MCP tool | Expose a service operation | Server runs the operation |

A remote MCP tool does not require the agent’s machine to provide the tool’s execution environment. A bundled script does: its commands and dependencies must work on the local operating system. That distinction matters more than treating skills and MCP as competing packages.

04

在编写技能之前先定义成功

Testing Markdown means testing what the agent does after reading it. The scope can be narrow, like checking a tool call, or broad, like checking a complete workflow. Because an LLM produces variable outputs, exact text matching often captures less useful behavior than inspecting the steps taken, tools called, and resulting state. An evaluation still starts with an input and an expected outcome.

The cycle Rodrigues adopts comes from OpenAI’s Testing Agent Skills Systematically with Evals:

1. Define success. Decide whether the skill should route the agent to documentation, enforce a workflow, or produce a particular result. 2. Write the skill. Create SKILL.md, adding references and scripts where they help. 3. Run scenarios. Exercise the skill manually or through an evaluation runner. 4. Grade behavior. Compare outputs and actions with the intended criteria. 5. Iterate. Change the skill and repeat the checks.

Braintrust is introduced as a way to observe agent behavior inside controlled evaluation scenarios. Even when the overall workflow is nondeterministic, individual checks can remain deterministic: a tool either was called or was not, and a database object either has a required property or does not.

05

不用技能，构建一份部门报表

The testbed is a deliberately vulnerable performance-review application with four switchable accounts: an employee, two managers, and an HR representative. The plan is to expose a database mistake manually, add a skill that guides the agent away from it, and reuse the scenario in an automated evaluation. Supabase provides the backend: Postgres, authentication, storage, and edge functions, which Rodrigues compares to AWS Lambda functions. He introduces the service as an open-source alternative to Firebase.

The workshop repository contains the employee-directory exercise. In the recording, Rodrigues works in a workspace with two Next.js apps, including the presentation; the application he opens is under demo. The current public checkout has a different root layout, so use its README for setup rather than assuming those recorded paths still apply. He credits skills with improving the presentation’s visual quality before turning to the application itself.

The application lets HR inspect employee information and lets the presenter switch users to test access boundaries. The planned Reports page initially includes salary and average performance ratings by department. The actual task sent to Claude is narrower: create department_stats, a SQL view showing headcount and average salary by department. A prepared reporting interface will display the database result.

06

一次成功的查询只是第一道检查

The local setup follows a short sequence: clone the repository, install dependencies, start Supabase through npx, reset the database to its migrations and seed data, then run npm run dev. The dashboard is served at localhost:3000/dashboard. A prepared .mcp.json points Claude Code at the local Supabase MCP server, which requires no authentication in this setup.

Rodrigues inspects a policy involving reviewer_id and current_setting, then turns to the permission context of the newly created view.

By default, underlying access through a Postgres view uses the view owner’s permissions and applicable RLS policies. In this setup, that allows the view to bypass the restrictions intended for the caller. The security_invoker option changes those checks to use the invoking user. It does not copy policies onto the view, and a default view does not universally bypass RLS; the owner and permission context matter. The PostgreSQL 15 view documentation explains this distinction.

Changing one checklist item should not silently break another workflow, and the checks need to travel across agent environments.

The hardest evaluation work is defining representative scenarios and their expected behavior. Prompts and expectations can live in CSV or JSON; Braintrust and Langfuse can add observability. For this workshop, Rodrigues uses an eval.json containing an array of scenarios, following the Agent Skills guidance he cites. The format is the workshop’s test organization, rather than a requirement imposed by the skill file format.

Two grading approaches serve different needs:

- Deterministic assertions: Check observable facts, such as whether a tool was called or a view has the required setting. - LLM-as-a-judge: Give another model the output and explicit success criteria, then ask it to grade the result.

The workshop reuses the department-report prompt and expects security_invoker=true on department_stats. Its prepared runner uses deterministic assertions for that check.

There are two distinct failure modes here. Deterministic grading code can inspect the wrong object or encode the wrong expectation. An LLM judge can additionally produce an unreliable judgment. The live discrepancy belongs to the first category; Rodrigues raises judge hallucination as a separate risk when discussing how evaluation becomes harder with model-generated behavior.

14

让生产技能保持精简、及时更新且可测试

The first evaluation pipeline can remain simple: compare with-skill and without-skill conditions on the harness that will actually use the skill. A Docker container or sandbox gives each run a fresh environment containing only the skill under test. That removes unrelated installed skills and leftover state from the comparison. The workshop stops at this testing structure; Supabase’s product-skill maintenance and production evaluation are reserved for the next day’s talk.

The final audience question asks whether progressive disclosure means one can keep installing skills indefinitely. Rodrigues offers no numerical limit. For local experimentation, he tolerates a messy inventory: unused descriptions still consume context, but their small size makes aggressive pruning less urgent in his personal workflow. For production and CI, his advice is stricter: include only the skills needed for the specific task.

A production skill is maintained documentation with behavioral consequences. Publish it alongside the repository, update it when features or workflows change, and put that maintenance requirement in CLAUDE.md or AGENTS.md. Periodic jobs can check whether its workflow remains valid. Where skill-loading telemetry is available, long periods of nonuse can prompt a review of whether the skill still belongs in the inventory. The work continues after the Markdown is written: the instructions must remain relevant to the product and useful to the agents that read them.

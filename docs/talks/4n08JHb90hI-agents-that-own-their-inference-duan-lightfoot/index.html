掌握自己的推理意味着什么

幻灯片原文
Running your own model server on owned or rented GPUs lets you choose its configuration and keep requests inside your infrastructure. The speaker includes a private VPC as one option.

[2:36](https://www.youtube.com/watch?v=4n08JHb90hI&t=156s) [Slide describes running a model server on your own GPU, choosing its configuration, and keeping requests within your infrastructure.](https://assets.ai.engineer/sites/aiecode2025/sha256/607e333053f987ef7acec4747e1176ad2a6c901d9708f29af8f3432d8fef15e5.webp)

What owning your inference means

You run the model server yourself, on your own GPU, instead of calling a hosted API.

You choose the model, the precision, the context length, and the batching.

The requests never leave your server, cluster, datacenter or traverse the public internet.

何时自建，何时不自建

幻灯片原文
Own inference when steady usage keeps GPUs working and data or model control matters. Rent for bursty traffic, access to larger models, or when your team doesn't want to run servers.

[3:28](https://www.youtube.com/watch?v=4n08JHb90hI&t=208s) [Two columns compare reasons to own inference, such as steady usage and data control, with reasons to rent, such as bursty traffic and access to larger models.](https://assets.ai.engineer/sites/aiecode2025/sha256/e587f0827c4cbae82d942ae2271a1f8df2e67df298d89eb2bf42fa079e1ed6bf.webp)

When to own, and when not to

Own when
• Usage is high and steady
• Data must stay in your datacenter
• Your only limit is your own hardware
• You control which model runs and how

Rent when
• Traffic is low or comes in bursts
• You need the best models, including ones too big to host yourself
• You don't want to run the servers

vLLM 是什么

幻灯片原文
An app sends chat and tool calls through a vLLM server to Qwen3-4B on a GPU. Continuous batching and prefix caching help the server handle requests through one OpenAI-compatible endpoint.

[9:04](https://www.youtube.com/watch?v=4n08JHb90hI&t=544s) [vLLM features and a diagram connecting an app through a vLLM server to a model on a GPU.](https://assets.ai.engineer/sites/aiecode2025/sha256/177f09e7ffdd963ca8ac9053236f4b83f304e07b6e443484a3c6a6fb8eaba44e.webp)

What is vLLM

An inference server that puts one model on a GPU behind an OpenAI-compatible API.

What it gives you
• OpenAI-compatible endpoint: point your agent at it
• Continuous batching and PagedAttention for throughput
• Serves many requests at once on one GPU
• Automatic prefix caching reuses repeated prompt prefixes
• Quantization (FP8, INT4) to fit and speed up models

连续批处理

幻灯片原文
Static batching leaves slots idle when requests finish early. Continuous batching fills those slots with new requests, keeping the GPU working while longer requests continue.

[9:53](https://www.youtube.com/watch?v=4n08JHb90hI&t=593s) [Colored batch-slot diagrams compare idle slots in static batching with continuously filled slots.](https://assets.ai.engineer/sites/aiecode2025/sha256/92e5ac8529306d321a29b66a95b59fa35f75158db55a59378d4d73a4f7f88fd9.webp)

What makes vLLM fast - Continuous batching

Static batching

Requests that finish early leave their slot idle until the whole batch completes.

The GPU does no work in those gaps, so throughput falls as request lengths vary.

Result: wasted GPU time and lower tokens per second.

Each row is a batch slot, each column a step. When a request finishes, the next one starts in that slot the same step.

The batch never drains, so the GPU keeps working. Static batching would hold every slot until the slowest request finished.

PagedAttention

幻灯片原文
PagedAttention allocates fixed-size KV cache blocks as sequences grow, instead of reserving unused space for each request. The shared pool reduces waste and lets more sequences fit at once.

[10:30](https://www.youtube.com/watch?v=4n08JHb90hI&t=630s) [Block diagrams compare reserved KV cache space with fixed-size blocks allocated as sequences grow.](https://assets.ai.engineer/sites/aiecode2025/sha256/9e62a39c0dadf873ce9217205c2545e6020fa88f26f6aa0d66023f7fb410ab2a.webp)

What makes vLLM fast - PagedAttention

KV Cache with no paging

Req A
Req B
Req C
Free

Legend: used; reserved, unused; free

Most outputs are short, so most of each reserved block sits empty, locked to that one request.

That over-reservation and fragmentation cap how many sequences fit at once.

Result: wasted VRAM and lower concurrency.

PagedAttention

KV cache pool, fixed-size blocks

Legend: Seq A; Seq B; Seq C; Free

The KV cache is split into fixed-size blocks, allocated on demand as a sequence grows.

Nothing is reserved for the longest possible output, so waste is near zero and far more sequences fit at once.

Together: paging frees the memory, and batching keeps every slot working.

7. Switch the manifest to FP8

Open the repo-root file manifests/vllm.yaml in the JupyterLab editor. Walk through the fields before changing anything: the Deployment, the Service, the vLLM image, --model, parser flags, the /models cache volume, GPU request/limit, and the baseline tuning flags that later modules change.

Change only this argument:

- "--model=Qwen/Qwen3-4B"

to:

- "--model=RedHatAI/Qwen3-4B-FP8-dynamic"

Then preview, apply, and wait for rollout.

On a platform-generated namespace you may also see harmless metadata label normalization. rollout status should finish successfully, and /v1/models should report RedHatAI/Qwen3-4B-FP8-dynamic. Loading can take a few minutes if the pod has to warm the model.

2. The quantization map

Pick precision by workload and serving stack, not by a leaderboard. The lower the precision, the more you need evidence that your application still behaves.

Method | What changes | Upside | Main risk | Good fit
BF16 / FP16 | Baseline half-precision weights | Broad support, low surprise | Larger weight reads | Baseline and fallback
FP8 weights | 8-bit floating-point weights | Smaller reads and more cache room | Hardware and engine support | This live workshop path
INT8 weights | 8-bit integer weights | Conservative compression | Less gain than lower-bit paths | Mature stacks with good support
INT4 / W4A16 | 4-bit weights, higher-precision activations | Large memory drop | More quality risk | Memory-constrained serving after evals pass
AWQ / GPTQ | Calibrated post-training quantization | Better low-bit quality | Calibration set can miss failures | Known workload with representative prompts
KV-cache quantization | Lower-precision attention cache | More concurrent context | Long-context drift | Long-context or high-concurrency serving
NVFP4 | NVIDIA/Blackwell-specialized low precision | Strong when the hardware path fits | Stack-specific | Conceptual here, not the live path
GGUF | Local/offline quantized format | Great for llama.cpp and edge workflows | Different serving stack | Local and offline inference

The live exercise uses the pre-cached FP8 model RedHatAI/Qwen3-4B-FP8-dynamic. NVFP4 and GGUF matter, but they are not this Kubernetes/vLLM path.

自己掌控推理的智能体

Du'an Lightfoot 和 Khaja Omer 用 vLLM 实际操作了专用 GPU 推理：上下文如何消耗显存，为什么 FP8 对他们的工作负载有帮助，推测解码为何反而让它变慢，以及在负载下设置序列上限会带来什么变化。

01

智能体循环把推理变成一项反复发生的开支

Du'an Lightfoot’s first agent, built in January 2023, parsed a model response, called a tool through Python, and returned the result to the model. Repeating that loop became expensive. Moving to local models introduced another problem: a smaller model could be less capable, while the GPU still had to hold the growing conversation. Lightfoot and Akamai colleague Khaja Omer begin with that practical tension—how to control cost and latency without losing the ability to finish the task.

The recurring unit of work is larger than one answer. A model chooses an action, a tool executes it, and the result returns to the model. The model then revises its plan, calls another tool, or finishes. Each pass generates tokens and carries context forward. A model that responds quickly to one prompt can still produce a slow agent if the task requires many passes.

To “own your inference” here means operating the model on a GPU you own or rent. The distinction is operational control: choosing the hardware, serving configuration, and location of the data. A cluster, data center, laptop, or private cloud network can contain the inference path when the surrounding system is configured that way.

The initial decision has several independent dimensions:

- Utilization. A steady workload can keep a dedicated GPU busy. Low or bursty traffic can leave paid capacity idle. - Data requirements. Intellectual property, governance, or compliance requirements may favor keeping requests within infrastructure you control. - Capability and operations. Hosted providers can supply models whose hardware requirements exceed your budget. They also absorb serving work that your team may lack the expertise to perform.

02

一个命名空间、一个 notebook 和一个推理端点

The workshop gives each participant one GPU and a Kubernetes namespace within a cluster described as having more than 200 GPU nodes. Each namespace contains a Jupyter notebook and a vLLM inference endpoint; a separate agent pod is also part of the planned environment. Participants change the serving deployment and rerun requests against it, so optimization becomes a deployment exercise rather than just a client-side prompt change.

vLLM supplies an OpenAI-compatible API and two useful serving mechanisms:

- Continuous batching. Finished requests can leave while new requests enter, instead of waiting for an entire fixed batch to finish. Lightfoot’s school-bus analogy is a bus that can pick up a new child as another gets off. - Paged attention. KV-cache memory is managed without giving every short request a large contiguous allocation sized for a longer one. This helps the server accommodate requests of different lengths while its scheduler manages the active work.

The endpoint is only one part of a production service. In the setup described, each serving endpoint hosts one model. Multiple models therefore need additional endpoints and routing. Authentication alone also does not supply authorization or rate limiting. The presenters discuss gateways and tools such as KServe and llm-d for the surrounding routing, scaling, and access-management work.

The first connection uses Qwen3-4B through the compatible API. An early correction matters: the model has four billion parameters and starts in BF16, rather than FP8. At two bytes per parameter, its weights occupy roughly 8 GB. Precision changes the bytes used to represent the weights; it does not double the parameter count. Requests from the notebook then travel to the endpoint inside the cluster.

03

衡量首 token、后续 token 和整个智能体

What does a streaming response reveal that a completed answer hides? The notebook records arriving chunks and separates time to first token from subsequent token generation. One run reports a first token after 37 milliseconds and generation around 40 tokens per second. That second number describes one request. Aggregate throughput can rise when multiple requests run together, even if each individual stream stays near that rate or slows down.

The CPU comparison is simulated because the notebook container has only 1 GB of memory; it is not a measured CPU inference run. A subsequent GPU run reports 45 tokens per second. Whether that is sufficient depends on the application: a chatbot needs a responsive first token, while a background job may tolerate slower generation if it completes the work well.

The first “agent” is deliberately modest: a system prompt assigns the role of an Akamai solutions architect, followed by a single request. It has no tools yet. Adding tool calls changes both the latency calculation and the context budget, because the system prompt, prior responses, and tool results become part of later model inputs.

Server metrics and agent traces answer different questions. The workshop’s foundation.py helper reads vLLM metrics through Prometheus; Grafana can display how the server behaves under load. Lightfoot also recommends tracing agent steps with a tool such as Langfuse, which can run beside the agent in the cluster. Those traces reveal token counts and latency for individual tool calls. If a smaller model repeatedly calls tools and takes longer to finish, the useful correction may be a clearer prompt, fewer tools, or a narrower role.

Increasing prompt length makes the first token take longer in the notebook exercise. Lightfoot directs attention to the slow requests rather than relying only on the median. That matters for agents whose later turns accumulate substantially more context than their opening request: a quick first exchange can conceal the expensive part of the task.

The cost exercise compares an illustrative workload of 200,000 tokens per day: about $1,500 per month through a hosted service versus about $1,000 for a rented GPU under the notebook’s assumptions. These are scenario figures, not a general break-even price; the provider rate, GPU size, model capability, and actual workload determine the comparison. Runtime choice also follows workload: the presenters point to SGLang for shared long prefixes and multi-turn requests, TensorRT for NVIDIA throughput, and llama.cpp for heavily quantized edge deployments.

04

为权重和不断增长的对话做预算

GPU memory must accommodate both the model and the requests it serves. The workshop starts with roughly 8 GB of BF16 weights for the four-billion-parameter model, then considers the remaining room for KV cache. The prompt establishes an initial cached context; generated tokens extend it. System instructions, tool calls, and tool results all contribute to the context the application needs to support.

Model files explain what the server is loading. The tensor files contain weights, while config.json describes the architecture the runtime must interpret, including layers, attention heads, and vocabulary. These architecture fields should not be treated like serving knobs: changing them without matching weights can prevent loading. Fine-tuning or LoRA adapts behavior through a different mechanism.

The useful weight calculation is simple: parameter count multiplied by bytes per weight. BF16 uses two bytes; FP8 uses one. A uniformly represented four-billion-parameter model therefore has about 8 GB or 4 GB of weights respectively, before considering other memory needs. The workshop uses that arithmetic alongside memory bandwidth to estimate a generation ceiling, then asks whether the intended concurrency and context lengths fit.

How does that become a user-capacity estimate? In the notebook’s example, the available KV pool holds about 37,000 tokens after accounting for the weights. Four simultaneous users with 8,000 tokens each consume 32,000 tokens of that pool. Each user’s allowance must cover the relevant input, output, and tool context together. The pool is shared across active requests; it is not a separate 37,000-token allowance for everyone.

Lightfoot connects this to a previous workshop: could roughly three or four 20 GB GPUs serve 80 students? Counting students alone could not answer it. The required context per student, simultaneous arrivals, batching behavior, and slowdown under load all had to be evaluated. The memory estimate narrows the possible deployment; a realistic workload test checks how it behaves.

05

预填充处理提示词，解码负责续写

Prefill and decode put different work on the GPU. Prefill processes the supplied prompt and contributes to the delay before the first streamed token. Decode generates the following tokens. Measuring them separately makes a long-prompt problem distinguishable from slow ongoing generation. In one notebook run, the first-token measurement is 57 milliseconds and the reported decode interval is 25 milliseconds.

The KV-cache exercise compares repeated attention work with retaining information from the context for reuse. The practical point is reuse during generation, rather than learning new model weights from a prompt. The notebook works through attention calculations, then grows a request while observing peak KV utilization and utilization after completion. This connects the abstract context budget to memory occupied during an actual request.

What changes when a request can reuse an already processed prefix? The cold-versus-warm exercise reports a drop from 220 milliseconds to 41 milliseconds. Prefix caching retains reusable KV work for the shared beginning of requests. Lightfoot distinguishes this serving mechanism from hosted providers’ prompt-cache billing discounts: both can reward repeated context, but one measurement concerns local serving latency and the other concerns the provider’s pricing policy.

06

模型总规模与每个 token 的计算量是两种不同的预算

A dense model uses its full set of layers to produce each token. A mixture-of-experts model activates selected experts, so its total parameter count can be much larger than the portion used for an individual token. The workshop’s illustrative 30-billion-parameter configuration has 128 experts with eight active per token. That distinction can reduce work and weight movement during generation, even though the complete model still presents a larger storage requirement.

The bandwidth calculation gives the four-billion-parameter baseline an estimated ceiling around 45 tokens per second, close to the observed rate around 40. That ceiling belongs to the model representation and hardware assumptions being calculated. It does not mean every serving configuration must produce the same result: the later quantization exercise changes how many bytes the GPU must move, while batching changes aggregate work across requests.

Thinking introduces another budget: how many tokens the model generates before finishing. The demonstrated response uses 35 tokens with thinking disabled and about 600 with thinking enabled. Extra reasoning may help the model interpret tool results or troubleshoot, but it consumes generation time and context. The presenters confirm that thinking budgets can be adjusted, making the useful question how much reasoning a task needs rather than whether more tokens are always better.

This foundation ends by separating the resource pressures: prefill is presented as compute-heavy, while decode is often constrained by memory bandwidth. The workshop discusses separating prefill and decode pools conceptually, but does not deploy that arrangement. Its hands-on optimization continues on the single-GPU serving endpoint.

07

FP8 释放了缓存空间并减少了权重搬运

Omer begins optimization with quantization. In the 20 GB memory budget used for this exercise, smaller weights help in two ways: they leave more space for KV cache, allowing more requests to remain active, and they reduce weight movement during decode. Those are separate benefits—capacity for parallel requests and speed within generation.

The baseline load test uses approximately 256 input tokens and 128 output tokens per request across concurrency levels. With BF16, one request generates 37.5 tokens per second, with a 61-millisecond time to first token. At concurrency 32, aggregate throughput reaches 714 tokens per second. Moving from concurrency 32 to 64 raises first-token latency from 277 to 1,300 milliseconds. Higher throughput has already begun to carry a substantial waiting-time cost.

Quality checks have to accompany that performance baseline. Omer expects BF16-to-FP8 conversion to preserve useful quality for many tasks, but treats that as something to test on the actual workload. A concrete failure case is malformed JSON: text can look plausible while a function call fails because its structured arguments are invalid. Hallucinations, broken reasoning, and repeated loops are other regressions an application-specific evaluation should catch.

The deployment change happens in vllm.yaml. A persistent volume holds downloaded models, and the deployment arguments select which model vLLM loads. Omer switches from the BF16 model to a pre-quantized FP8 version from Red Hat, checks the diff, and applies the deployment. The first rollout is delayed; an audience member spots duplicate model flags, which Omer corrects before rerunning it. A valid manifest and a successful rollout are necessary before attributing a result to quantization.

打造 Uber 的智能体化软件工厂

Uber 的软件工厂把受管控的模型访问、共享工具、开箱即用的环境和运维知识，连接到一个在 CI 之前就验证改动的功能开发工作流上。

熟悉 pull request、CI、模型上下文窗口，以及 MCP（一种向智能体开放工具的方式）会有帮助。

01

当智能体生成了大部分 pull request，什么会改变？

Uber 有几千名工程师，分布在全球十二个技术站点，已经开始面对智能体大规模使用带来的后果。Uday Kiran Medisetty 介绍，现在超过 70% 的 PR 有本地或云端智能体参与，人均代码行数同比翻了一番。Uber 还完成了 250 多次自动化迁移，累计覆盖九百万行代码。这些数字反映的是采用程度、产出和重复劳动的减少，单凭它们证明不了软件质量。

基础设施比智能体来得早。Uber 在 monorepo 和 Bazel 上投入了六年，打下了一个统一的底座，工程工作的自动化就建在这上面。Medisetty 先介绍了六个构建模块，随后 Adam Huda 把它们串成一个端到端的功能开发示例。这些组件的成熟度和推广进度各不相同：演示讲的是一座仍在建设中的软件工厂，不是一套已经全面铺开的系统。

02

模型请求的共享边界

Model Gateway 从三条要求出发：默认不让 PII 越过 Uber 的边界流向供应商；严格限制护栏带来的额外延迟；每个请求都能追溯到具体的用户、项目和团队。内部应用、编码框架和外部用例都走同一个兼容 OpenAI/Anthropic 的端点，网关自然成了统一落实这些要求的地方。

请求先经过基于 SPIRE 的身份与认证中间件，再经过数据匿名化模块和 AI 防护层。SPIRE 提供的是工作负载身份，不要把它和智能体完整的身份及委托链混为一谈。Medisetty 介绍，网关能脱敏二十多种 PII，配有五个专门的安全与策略模型，上述中间件整体执行时间不到 100 毫秒。演讲没有说明这是哪个延迟分位数。

缓存和 token 优化也放在这一层。每个请求都对应 Uber 项目目录里的一个项目，调用方、用户和团队的归属信息既能实时查看，也会写入数据湖。有了这本账，就能在整个项目组合范围内设定支出档位和护栏。审计日志和会话 trace 还会用于基准测试和自我改进，所以网关既是管控点，也是评测数据的来源。

对工程师来说，理想的用法是拿一个普通客户端，配上项目 ID 就行，外围的管控交给平台。Medisetty 介绍，目前有 800 多个内部项目接入网关，每天经过网关的模型请求超过 1 亿次。网关可以路由到前沿模型和开源模型，这些模型有的部署在 Uber 内部，有的由供应商托管。

03

让工具可访问，而不塞满上下文

能调用模型，不等于智能体就能用上 Uber 的系统。起初，数千个内部 API 没有智能体能访问的接口，各个 SaaS 工具又各有一套认证和配置。要暴露足够多的 MCP 工具，还得额外付出一笔 token 开销。MCP Gateway 把这些入口统一起来：自动爬虫只需改一下配置，就能把内部 API 映射成 MCP；网关还托管 Google、Slack、Jira 等服务的 SaaS MCP，并负责 token 交换。工程师只要一个入口、一种安装方式。

随后，Uber 分几步改变了智能体使用这些工具的方式：

| 调用方式 | 变化 | | --- | --- | | 直接调用 MCP | 智能体直接访问各个 MCP。 | | OmniMCP | 只装一个 MCP，由它在网关中发现并调用其他 MCP。 | | CLI 映射 | 工具返回的结果不必全部进入模型上下文。 | | 代码模式技能 | 生成 Python 脚本，优化开销大的工具调用流程。 |

有了发现机制，就不必一开始把所有工具都暴露出来。CLI 和代码模式则处理返回结果这一侧：中间数据可以放在模型上下文之外处理，只把有用的结果交回去。

下面这个小小的 Python 过滤器演示了最后这一步。它从标准输入读取一个 JSON 数组，里面是工具返回的记录；脚本只保留 id 和名称，再把结果交给智能体：

```python import json import sys

records = json.load(sys.stdin) selected = [ {"id": record["id"], "name": record["name"]} for record in records ] json.dump(selected, sys.stdout, ensure_ascii=False) sys.stdout.write("\n") ```

关键在于在哪一侧做裁剪：Python 看到的是完整载荷，模型拿到的只是挑出来的字段。Uber 的代码模式技能专门为 token 消耗最高的那些工具用例生成脚本。

Medisetty 介绍，目前有 1,000 多个 MCP 工具，这些优化在全公司范围内节省了 40% 以上。他没有说明这个比例的分母、基线和统计时间窗口，所以不能把它当作通用的 token 或成本削减基准。

04

给智能体一个已经准备好的环境

智能体有了模型和工具，还需要一个干活的地方。Uber 原本就有 DevPods——为包含数百万行代码的 monorepo 打造的远程开发环境。要让它适配智能体，还得满足几项新要求：能长时间运行、相互隔离、快速启动、支持大量环境并发，并且在全球各站点都能用。

Uber 预先准备好一批 Kubernetes balloon pod，随时可以分配。仓库快照和搜索索引都已就位，智能体不用从零开始准备工作区。Medisetty 说，智能体几秒钟内就能开工。

工作区的边界也在变。早期的 DevPod 按语言区分，比如 Go、Java 和 Android。智能体和工程师越来越需要跨越这些边界，于是有了 mega DevPod：把所有仓库放进同一个环境，供自主编码使用。启动流程简化之后，非工程岗位的员工也能直接用上智能体框架，不必自己搭开发环境。

05

把技能当作一个生命周期来管理

工程师开始在各个仓库里编写技能后，冒出了三个问题：重复劳动、难以发现和配置、质量参差不齐。Uber 的对策是建一个托管技能市场，里面既有核心技能，也有领域专用技能。技能交给智能体使用之前，要先过 lint 检查和自动审查，守住一条基本质量线。

一条命令就能发现并安装插件。基于角色画像的默认配置更进一步：自动装好相关技能，智能体可以直接选用，不需要每个工程师先自己配置。再往上一层是反馈：trace、评论和持续评测会把证据交回技能作者，帮他们改进技能的行为。Medisetty 说这块正在重点投入，目前有 2,500 个技能，全公司每天执行技能超过 20,000 次。

06

把智能体反复重新发现的上下文连接起来

执行 trace 暴露出另一种浪费：智能体花了大量时间找基本的上下文。改一个服务之前，它得先知道服务在哪、依赖什么、归谁负责、实现上有什么约定。这些信息散落在二三十个系统里，每个系统都要单独的技能或 MCP。反复查找既耗 token，又拖慢速度，结果也更难预测。

Uber 用一张上下文图谱把这些关系汇总起来。Medisetty 介绍，图谱有 150 种不同的节点和边类型，共四千万个条目，把移动应用、后端系统、数据湖、设计文档、Jira 和事故记录连在一起。值班根因分析、规划、数据分析、安全扫描等技能，正在陆续接入这个共享的上下文来源。

举个例子：印度的出行订单里，有多少是现金支付？要回答这个问题，光生成一段看起来像样的 SQL 不够。智能体得先弄清相关的业务概念，找到对应的表，再决定要构造哪些公共表表达式（CTE）。在早期的内部对比中（有图谱和没图谱），Medisetty 说 token 用量、轮次和延迟都有改善，但没有给出具体数字。图谱的作用，是让智能体在写查询之前更容易理清这些依赖。

07

在 Slack、CLI 和网页中开放相同的能力

Cortana 是 Uber 的内部 AI 助手，它把技能、MCP 和图谱上下文打包进 Slack、CLI 和网页界面。员工提一个问题，助手就能检索上下文、调用技能、跨代码库查看代码。入口换了，底层能力还是同一套。

员工可以用自定义提示词和技能把 Cortana 个性化，再把定制好的角色接入团队的 Slack 频道。多人可以在频道里一起协作，比如一起研究前面那个印度现金订单的问题。Medisetty 介绍，过去一个月新建了 300 个不同的角色，每天的会话超过 20,000 次。

08

从一个体育场接人的想法到一份设计

Huda 演示的功能从一个场景开始：一位乘客正要离开人山人海的世界杯球场。App 能不能推荐一个避开人群、更合适的上车点？团队在 Slack 里讨论这个想法，并 @ 了 Cortana。借助上下文图谱，助手帮忙分析这个商业机会，然后把工作转到网页界面继续推进。调研内容包括以往的大型场馆活动和候选球场。

接下来，示例依次走过需求和设计阶段：

1. 为球场功能提出北美推广方案。 2. 用 Figma 做出初版设计稿，包含两个变体，区别在于按钮文案。 3. 规划一个 A/B 实验来比较这两个变体。 4. 找出可以复用的现有 App 界面和后端能力，并列出需要改动的代码。

这只是一个设想中的功能开发流程，既不代表功能已经上线，也不代表有了实验结果。Huda 拿它和过去可能耗时数周的对齐过程对比，强调能很快做出原型，但没有给出实测的新耗时。

09

把实现交出去，但在 CI 之前停下

Cortana 把设计交给 Uber 的云端编码智能体 Minion。Minion 既能交互式运行，也能自主运行。它所在的 DevPod 提供完整的构建环境，并能访问各个仓库，所以球场功能的前端和后端改动可以放在一起开发。

演示的流程停在一个草稿 PR，没有马上送进 CI。这条边界是有意设的。很多繁琐任务直接生成改动就够了；但端到端的功能在占用共享的 CI 资源之前，得先验证行为。提早验证本身就是容量管理的一部分，还能在离生成更近的地方抓到错误。

10

在智能体的工作循环内验证功能

Uber 把智能体的内循环和平时跑 CI 的外循环分开，再把更多检查挪进内循环。验证流程不止静态分析：

1. 发现并修复静态分析问题。 2. 用一个技能在模拟器里启动 App 并截图。 3. 把截图和 Figma 设计规范做对比。 4. 在 staging 环境启动后端服务，验证前后端集成。

拿球场功能来说，流程在进入 CI 之前，就能同时检查用户看到的界面，以及界面和后端服务的连接。staging 验证和生产部署仍然是两回事。

11

用 CI 和审查补充证据

内循环验证并不能消灭 CI 失败。改动进入外循环后，Uber 的自愈 CI 能修复在那里碰到的很多问题。代码审查也分到两个循环里：更小、更快的模型先做早期审查；更强的模型借助推理和审查技能，在外循环做更深入的审查。

面对 Minion 自主生成的 diff，人工审查者需要知道第一次生成之后又发生了什么。PR 里附了一张表，列出做过的各项检查，还带有截图。有了这些证据，审查者就能看清智能体做了哪些验证和改进；但这不能保证代码正确，也替代不了人的判断。

12

在共享容量内安排维护工作

生成的代码越多，维护就越重要。功能和服务可以登记使用维护类技能。回到球场的例子：一旦变体 B 不再需要，功能开关清理技能就能删掉这个过时的变体和相关的分支逻辑。这个例子的前提是已经决定要清理，并不说明哪个变体在实验中胜出。

这些任务统一放在一个托管循环里运行，而不是交给成千上万个各自为政、毫无约束的定时任务。通过共享的配置界面，可以把任务安排在 CI 容量更宽裕的周日，并限制周一工程师要处理多少个由此产生的 diff。安排执行时间和控制审查量是两件事：算力有富余，不代表审查者的精力也用不完。

维护循环还会产生学习信号。审查评论，以及生成的 diff 最后有没有合入，都会变成带标签的数据，用来改进当初提出这个 diff 的技能。Uber 大约每月翻一遍事故复盘，从中提炼经验，做成新的维护技能，再推广到各个服务。这样一来，维护工作既推动具体的代码改动，也在喂养下一版自动化。

13

下一个限制在于实验和决策

整个流程不止上面展示的这些阶段——Huda 还提到了监控——但实现吞吐量上去之后，新的约束也跟着来了。代码越多，基础设施压力越大，CI 容量和底层投入也就越关键。

实验容量同样有限：能生成的功能，组织不可能每个都拿去测试。决策成了另一个瓶颈。做出一个功能一旦变得相对容易，“能不能实现”就回答不了产品问题了。这座工厂仍然需要人来决定：这个功能该不该做。

用 AI 智能体做性能优化：交付更快，花钱更少

生产环境的性能剖析可以把编程智能体引向代价高昂的代码模式，而共享的目录、测试和金丝雀发布能把一次次的修复变成可重复的性能优化流程。

熟悉调用栈、CPU 性能剖析、Git 版本和自动化测试会有帮助；代码示例使用 Java 和 Guava 的 ImmutableMap。

01

为什么更快的编码会制造性能瓶颈

当生成代码比算清它的运行成本还容易时，会发生什么？Rajat Shah 在 Netflix 的 AI 平台部门工作，负责机器学习模型托管背后的大规模分布式系统。他关心的问题是性能工程的吞吐量：编码智能体帮工程师交付越来越多的代码，基础设施怎样才能保持高效？

Shah 这样描述两者的错位：写代码快了 10 倍。他还故意夸张地说，CPU 账单也在以同样的速度上涨。背后的担忧很实在：智能体追求的是尽快写出能跑的代码，而能跑的代码未必是最快的实现。

更强的模型有帮助，但模型不会自动了解一家公司的内部平台、框架和既有代码模式。智能体可能把别的代码库的惯例搬过来，也可能用一种框架设计者从没想到的方式调用内部框架。性能不只看通用编码能力，也看对本地代码的了解。

02

手动性能剖析循环

性能工程师通常要反复走这样一套流程：

1. 在服务集群中挑一台生产实例，触发性能剖析。 2. 下载剖析结果，里面可能有 JSON 格式的结构化调用栈和 CPU 数据。 3. 打开可视化工具，查找开销大的路径。 4. 在源码仓库里找到对应的包和方法。 5. 诊断问题、写好修复，提交代码评审并合并。 6. 寻找下一个优化机会，把排查过程再走一遍。

可视化工具让数据变得可读，但读懂数据仍是一门靠经验积累的手艺。找到热点路径只是开始，工程师还得把它对应到真正能改进的代码上。

正因为要反复做，主动剖析很难在大量服务上长期坚持下去。剖析很容易沦为凌晨 2 点 CPU 告警时才想起来的工具。据 Shah 估计，工程师找出热点路径大约要 20 分钟。这次实验并没有一上来就追求自主优化，问题要窄得多：LLM 能不能读懂剖析结果，缩短这段搜索时间？团队在线上服务上验证了这个想法。

03

性能剖析工具和编程智能体已经提供了什么

第一个假设是：不同运行时的剖析器给出的信息大体相当。Java、Python 或 Go 的剖析器都能对生产实例高频采样，记录调用栈，其中包括 self CPU（方法自身消耗的 CPU）和 inclusive CPU（还算上调用路径中下层方法的开销）。文件格式不必完全一样，智能体照样能基于这种共同结构做推理。

第二个假设是：编码智能体在训练中已经认识常见的性能模式：

- 平方级开销： 总工作量按 O(N²) 增长的循环。 - 循环不变量： 结果只需算一次，却在循环里反复计算。 - 重复分配： 在高频执行的路径上反复创建对象，其实完全可以挪到别处构造。 - 争用与批处理： 协调开销，或大量重复的小操作，重新组织后能降低开销。

Shah 也指出，这种能力取决于训练数据里代码的质量。真正有用的起点是模式识别：把运行时的高开销路径和熟悉的实现“坏味道”对上，就能找到值得深挖的地方。

04

从调用栈到部署的源代码

第一个很有代表性的发现，来自把剖析结果里的两行联系起来。第一行和第三行属于同一条调用路径：ImmutableMap.copyOf 出现在一个张量合并方法里，幻灯片上显示为 TensorSet.merge。智能体知道这个拷贝操作在做什么，于是怀疑这里有重复拷贝和平方级累积。据 Shah 介绍，智能体还没看源码，单凭剖析结果里的调用栈就做出了这个初步推断。这给排查指明了目标；接下来查看源码，才弄清这个目标具体是怎么实现的。

要把这个怀疑变成修复方案，智能体得把运行时证据和正确版本的代码对应起来：

1. 搜索这个方法，确定它属于哪个仓库。 2. 把生产构建对应到确切的 Git commit，并检出这个版本。 3. 找到相关实现，别绕进无关的内部库细节里。 4. 对照源码，追踪完整的方法调用路径。

生产环境的 commit 本身就是证据的一部分。 看错了版本，解释的可能是根本没产生这份剖析结果的代码。打通这一环后，团队在几个服务上做实验，检验智能体能否不止于发现问题，而是真正写出可以交给工程师审批的修复。

05

一项发现，然后在各服务间搜索

在张量合并的例子里，据 Shah 介绍，这个平方级模式在剖析期间占了 8.8% 的 CPU 时间。这是记在该模式头上的开销，不等于消除它之后能省下的量。只要有合适的 skill 或提示词指令，再配上能力足够的编码智能体，这套流程就能一路走完：检出仓库、找到实现、提出代码修改。

Shah 表示，在大型代码库的实验中，从开始到提交代码评审不到五分钟。他还说，优化上线后，生产环境的 CPU 和延迟都观察到了下降。从实际运维看，真正有用的是：智能体能把排查一路推进到可评审的代码修改，而不只是点出某个方法开销大。

下一个机会是复用已有的发现。一份剖析结果显示，在一条热点路径上，每次迭代都会新建一个 Spectator 指标计数器对象。智能体认出这个模式后，就能去其他仓库搜索同样的写法。Shah 说，他们在七个服务里找到了这种创建计数器的写法；如果在这些仓库里全部修掉，有望节省 0.5%–4.6% 的 CPU 周期。这些节省目前还只是预估；更值得关注的是背后的机制：一次生产环境的发现，可以变成搜索模式，套用到更多服务上。

06

把共享目录当作持久的记忆

智能体能找问题、提修复之后，下一个问题是怎样把这些发现带进开发流程。单次调用并不具备性能工程师积累下来的全部上下文。模型的记忆容量有限，记不住组织里的各种模式、过往的排查记录和特定框架的经验教训。

Shah 的方案是有状态的模式库，搭配无状态的 LLM。把模式和反模式集中存放，不同团队、不同产品的智能体都能复用。有些条目只适用于某个内部框架；另一些，比如平方级累积，可以推广到各种语言。久而久之，模式库就成了一份长期有效的记录，写明组织在高效代码上学到了什么。

最初的实现可以只是集中式 Git 仓库里的一些 Markdown 文件，起步阶段用不着向量数据库。生产排查中发现了新模式，智能体就往库里添条目；之后排查另一个服务时，可以直接查阅这些条目，不必把同样的解释重新摸索一遍。一个服务的剖析成果，就这样变成了整个集群可复用的知识。

07

目录条目里应该有什么

模式库从空开始也完全可以，但现成的资料能帮它起步。Shah 推荐了 Jeff Dean 关于 C++ 优化的文章、TorchFix 和内部的性能手册。更准确地说，TorchFix 是一个针对 PyTorch 代码的 Python 静态分析 linter，会尽量提供自动修复；它的仓库已于 2026 年 1 月归档。不过它文档里列出的检查项，依然很好地展示了模式库可以收录哪类可复用的模式。内部手册则补上组织特有的知识，这恰恰是通用编码智能体缺少的。

一个有用的条目应该包含：查询提示、相关符号、已确认存在该模式的服务，以及一个随证据积累而更新的置信度。置信度用来帮助判断要不要请人评审，而不是授权直接推到生产环境：一次优化可能改变业务行为，智能体未必理解这些行为，测试也未必覆盖得到。

把反模式和推荐的实现写在一起。拿 ImmutableMap 累积的例子来说，区别在于：是反复拷贝一个不断变大的 map，还是先累积所有条目、最后只做一次不可变拷贝。下面的 Java 示例把这个差别写得很清楚：

```java import com.google.common.collect.ImmutableMap; import java.util.LinkedHashMap; import java.util.List; import java.util.Map;

final class MapAccumulation { static <K, V> ImmutableMap<K, V> copyEachStep( List<Map.Entry<K, V>> entries) { ImmutableMap<K, V> result = ImmutableMap.of(); for (Map.Entry<K, V> entry : entries) { Map<K, V> next = new LinkedHashMap<>(result); next.put(entry.getKey(), entry.getValue()); result = ImmutableMap.copyOf(next); } return result; }

static <K, V> ImmutableMap<K, V> copyOnce( List<Map.Entry<K, V>> entries) { Map<K, V> result = new LinkedHashMap<>(); for (Map.Entry<K, V> entry : entries) { result.put(entry.getKey(), entry.getValue()); } return ImmutableMap.copyOf(result); } } ```

假设键互不相同，键和值也都不为 null：第一个方法会反复拷贝一个越来越大的 map；第二个方法先累积到一个可变 map 里，最后再生成不可变结果。遇到重复的键，两者都保留最后一个值。把实现和模式一起记下来，模式库就能直接拿来用；当然，实际应用的语义仍然需要核对。

08

在人工审查之前先跑测试和金丝雀发布

如果系统不停地生成试探性的优化评审，瓶颈只会转移到评审者身上。在请人看之前，智能体应该先跑单元测试、集成测试和基本的功能测试。这些检查能确认：提议的改动有没有保住测试套件里体现的业务行为。

测试覆盖总有缺口，所以第二道关卡很有价值：自动化的金丝雀对比。Shah 举的例子用了两台机器，一台跑旧代码，一台跑提议的优化。给两台机器发送同样的流量，持续一段时间，比如十分钟，然后比较它们的表现。只要自动化做到位，这次对比可以在需要人工评审之前就完成。

对比报告给了智能体依据，判断要不要发起评审：

| 信号 | 问题 | |---|---| | CPU 使用率 | 改动有没有降低计算资源消耗？ | | 延迟 | 请求处理有没有变快？ | | 错误率 | 优化有没有破坏原有行为？ |

只要错误率上升，就该停下，哪怕 CPU 使用率降了。可观测性、金丝雀发布和验证都是标准的工程基础设施，智能体必须会用。最终拍板的仍然是工程师。Shah 的分工说得很直接：剖析器估算优化空间，金丝雀确认实际效果，工程师决定是否接受改动。

09

把目录移进审查和编写环节

从生产环境剖析入手是个好起点，但要改的是生产环境里已经正常运行的代码，必须格外小心。随着模式库不断扩充，它的发现可以前移到开发的更早阶段。评审智能体可以检查提议的改动，查找相关模式，再根据过往的剖析证据留下行内建议。同一个模式库，既能用于事后诊断，也能用于事前评审。

下一步是把模式库直接交给写代码的智能体。智能体在写出已知的低效模式之前，可以先查到推荐做法，一开始就照着写。查阅模式库可能拖慢代码生成，还会多消耗 token，所以模式库需要有结构、有索引。分层导航应该能把智能体引到相关条目，而不必把整个库都塞进上下文。在编写阶段就拦住低效模式，既省掉了之后评审时的返工，也避免了把已知的低效代码部署上线。

10

打好集成的基础

把智能体放进更多开发环节，前提是底层的检查靠得住。业务逻辑需要扎实的测试覆盖。金丝雀自动化必须可靠，智能体也要有清晰的办法触发它、拿到数值报告。Git 里的模式库是另一块共享基础：人和智能体都能读，也都能写。开发框架的工程师可以趁设计思路还清楚，把框架的正确用法和错误用法记下来。

整条集成链路要能支撑这样的工作流：在 CPU 集群的某个实例上触发剖析，下载数据，交给模型分析，取回相关源码，再借助影子流量或真实流量，在生产环境用金丝雀验证提议的修复。环节之间衔接不牢，就会产生摩擦，甚至引入生产 bug。先从事后排查做起，把基础打牢，再逐步把积累的知识推到开发的更早阶段。

11

从辅助诊断到定时编排

第一次有用的落地，不必做到完全自动化。在 Shah 描述的手工基线下，工程师可能要花好几个小时找问题。到了第一级，触发剖析器、传输剖析结果、运行金丝雀这些事可能仍然由人来做，LLM 负责找出可能的修复。光是这样，就已经省下了原本盯着火焰图的时间。

第二级把各种工具、集成、框架和 hook 串成一套预先定义好的工作流。步骤是固定的：触发剖析、下载剖析结果、分析、用金丝雀验证候选改动，再给出修复建议供评审。模型不需要自己规划整体流程。这套流程跑稳之后，就可以定时执行，比如每周在每个服务上跑一次，趁代码刚写完不久就发现新引入的问题。

12

更高自主性的边界

第三级允许智能体跳出固定工作流，自己规划、推理和行动。灵活性也带来了更多责任：更严格的评测、沙箱隔离，以及安全护栏，用来防范提示词注入等针对智能体基础设施的攻击。Shah 建议先从辅助做起，再推进到编排——他认为编排的实际收益最大。更高的自主性需要进一步投入，等工作流真正需要时再上。

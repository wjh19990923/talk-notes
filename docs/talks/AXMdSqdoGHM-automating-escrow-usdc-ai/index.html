用 USDC 和 AI 实现托管交易自动化

跟随一个托管交易工作流，从协议信息抽取到注资智能合约再到图片审核，然后看看哪些环节仍然需要人工审批。

对 API、区块链钱包和智能合约有基本了解会有帮助；文中会讲解托管工作流用到的 USDC 操作。

01

在资金流动之前必须发生什么？

托管协议要同时解决两个问题：判断一方是否履行了义务，以及在履行之后放款。AI 可以帮忙核查证据，智能合约可以强制规定资金能怎么流动。把两者结合起来，就是 Corey Cooper 这次演讲的出发点。他自我介绍是 Circle 的 DevRel 负责人。

Cooper 认为，做托管时 USDC 比传统支付通道好上一个数量级，但他没有给出任何基准数据。他实际的出发点是：先由 AI 核实工作流里的条件，再由可编程美元结算相应的付款。按他的说法，这种结算是即时的，在全球范围内都比 T+2 快。演讲先讲 Circle 的基础设施，再讲 USDC 合约接口，最后介绍一个最近开源的托管应用，大家可以在本地跑起来试试。

02

发行方、流动性服务和开发者工具

应用底层的美元基础设施由 Circle 提供。据 Cooper 介绍，Circle 是一家 2013 年成立的金融科技公司，投资方包括 BlackRock 和 Fidelity。公司发行代币化的美元和欧元，以储备金 1:1 支撑。他说这些储备是法币和短期国债。在他看来，稳定币监管能让企业和个人更方便地用上这项技术。

Cooper 提到，截至演讲时，链上累计交易量超过 26 万亿美元，支持约 20 条区块链。这些数字反映的是整个支付网络，并不是托管业务的交易量，也不是应用的吞吐量。产品线也不止 USDC 和 EURC：Circle 收购 Hashnote 之后，推出了一只代币化货币市场基金，Cooper 还提到将来可以随时把它换成 USDC。机构流动性服务负责铸币和赎回，资金进出企业的金库钱包，用于支付、获取美元和资本市场业务。

面向开发者的服务把集成工作拆成几块，各管一摊：

| 服务 | 职责 | |---|---| | Circle Wallets | 以编程方式嵌入和创建钱包 | | Circle Contracts | 部署合约，读写合约状态 | | Circle Paymaster | 用 USDC 余额支付 gas | | Cross-Chain Transfer Protocol（CCTP） | 在不同区块链网络之间转移 USDC |

有了 Paymaster，用户不必为了交易专门持有某条链的原生代币。CCTP 解决的是另一个问题：用户的 USDC 可能在别的网络上，不在应用所用的那条链上。Cooper 说，在支持的网络之间转账无需许可。他还预告了打通各链余额的后续工作，但没讲具体怎么实现。这里介绍的都是录像里展示的服务，没有换成后来推出的产品或 API。

03

银行美元如何变成可编程美元

USDC 的账本记在区块链网络上，智能合约对外提供一组操作，供应用调用。Cooper 说 USDC 几秒钟就能完成全球转账，还拿电子邮件和短信打比方：开发者可以在公共网络上搭建跨境收发和存储的体验。不过，任何人都能加入这个网络，而企业要直接通过 Circle 铸币则需要审批，这是两回事。

发行流程把这些公共网络和存在银行的储备金连了起来：

1. 企业获得 Circle 审批后，开通 Circle Mint 账户。 2. 企业绑定银行账户，把法币电汇到 Circle 的储备金银行账户。 3. 美元到账结算后，Circle 铸造等额 USDC，存入该企业的 Circle Mint 账户。 4. 企业要退出时，按相反流程赎回，1 USDC 兑 1 美元。

Cooper 提到，可以通过 Circle 的透明度页面和每月鉴证报告核查储备金，此外还有独立机构监督。这一点对托管应用很重要：链上转账，和依托银行资金的发行、赎回，是两套各自独立的操作。

04

支出权限、共同审批和离线准备

Circle 把 USDC 部署到一条新的区块链之前，会先确认它能提供标准化的行为和保护性控制。Cooper 先讲了允许名单和封禁名单：发行方可以禁止受制裁或恶意的地址交易，包括与其他用户交易。所以，网络对公众开放，发行方对代币的控制也同时存在。

委托支出让一方可以在授权额度内，花另一个钱包里的钱。Cooper 举的例子是：公司用一个 USDC 钱包给员工的虚拟借记卡供款，再由工作流设定支出门槛或每日上限。代币的支出授权只是一块积木，围绕它定什么规则，由业务工作流决定。Cooper 说这种委托可以扩展到数万张卡或数万名用户，但没有给出压测结果。

另外几项控制，管的是谁能创造货币、谁能授权资金流动：

- 铸币方配置：代币合约可以授权更多实体铸币。Cooper 设想将来可以给金融机构分配铸币额度，但也说明 Circle 目前还没这样做。 - 多签审批：支付工作流可以要求多方共同审批超过门槛的交易，比如 CEO、CFO 和 COO 一起签。这样能降低某一个人独自握有掏空钱包权限的风险。

离线准备把签名和广播分开。以定期发薪为例，公司可以提前准备一笔金额确定的交易，离线完成审批和签名，到发薪日再广播。现场观众追问：这能不能同时证明到时候钱一定够？Cooper 的回答是不能：签好一笔交易，本身既不会冻结资金，也不能保证之后付款不失败。要证明资金充足，还需要另外设计。

05

应用调用的合约接口

接着 Cooper 讲了合约的暂停和升级，并以 USDC v2.2 为例，说明如何提升 gas 效率。这个版本于 2023 年 11 月发布，在支持的各条 EVM 链上陆续上线。它的改动不能理解成每条区块链上的实现都做了一模一样的升级。

几个核心函数组成一个小接口，用来查余额，以及授权或转移代币：

| 函数 | 用途 | |---|---| | balanceOf | 读取某个地址的代币余额 | | totalSupply | 读取代币总供应量 | | allowance | 读取所有者给某个支出方的授权额度 | | transfer | 从调用者账户发送代币 | | transferFrom | 凭支出授权转移代币 | | approve | 设置支出方的授权额度 |

用 Solidity 可以直接写出这个接口：

```solidity pragma solidity ^0.8.20;

interface IUSDCToken { function balanceOf(address account) external view returns (uint256); function totalSupply() external view returns (uint256); function allowance(address owner, address spender) external view returns (uint256); function transfer(address to, uint256 amount) external returns (bool); function transferFrom(address from, address to, uint256 amount) external returns (bool); function approve(address spender, uint256 amount) external returns (bool); } ```

Cooper 重点讲了 transferFrom：它的参数指定来源地址、目标地址和金额。应用提交一笔调用这个操作的交易，区块链随后完成代币转移。来源地址只是一个参数，不能代替支出授权。后面的托管流程，就是围绕这个可编程接口搭起来的。

06

从智能体支付到一个托管交易应用

有了智能体，结算和验证就得放在一起考虑。Cooper 认为，近乎即时的支付确认很适合软件之间互相交易；而在可撤销的支付通道上，自动化转账越来越快，拒付也就越来越难管。公共区块链基础设施还能在银行下班后照常交易，签名和公开可查的交易记录提供了密码学层面的验证。

条件支付逻辑应该写进智能体能交互的合约里。智能体在请求转账前，可能需要先确认某个前提条件已经满足。可组合的智能合约负责定下这笔转账的规则，智能体负责按这些规则去交互。托管场景把这种分工体现得很具体：必须先有工作完成的证据，才能放款。

示例应用由三块积木组成。Circle Wallets 为智能体和托管双方创建钱包。一个 Solidity 托管模板通过 Circle Contracts 反复部署，每份协议对应一个实例。在这些合约里流转的货币是 USDC：注资前先用法币入金，事后受益方也可以出金换回法币。应用复用的是现成的合约设计，并不让模型为每份协议重新发明一套金融程序。

07

把一份协议变成一个已部署的托管合约

企业和自由职业者先在平台上注册账户。每次注册，后台都会调用一次 API 创建钱包。接着企业上传一份 PDF 协议，协议内容是双方在应用之外谈好的。OpenAI 的多模态模型从中提取付款金额，以及自由职业者要完成的任务。

提取出来的只是一份待发布的需求草稿，并不是立即生效的付款指令。企业发布前要先核对金额、任务清单和协议摘要。批准后，这些值会填入一个预先写好的合约模板。模板配置里指定了币种 USDC、存款方钱包、受益方钱包，以及一个智能体钱包；按演讲的说法，智能体钱包只有放款权限。模型提供协议数据，模板提供可执行的规则。

部署也是一步单独的显式操作。平台调用 Circle 的 API，合约部署完成后报告成功。开发者可以在 Circle 控制台查看这些活动，也可以用 webhook 监听已索引的链上事件，在上面做通知或其他工作流。这样，“发起请求”和“确认完成”之间就有了明确的分界——现场演示时，这个区别就暴露出来了。

08

为合约注资并评估工作成果

部署完成后，企业通过入金通道获得 USDC，或者直接从已有的外部钱包注资。Cooper 介绍的存款流程是：先授权一笔指定金额，再把它从存款方钱包转进托管合约。资金到账后，受益方会收到可以开工的通知。自由职业者可以在区块浏览器里查看合约已注资的状态，不必只凭企业一句“会付钱”。

这个应用里的交付物是一张营销图片，要满足企业品牌方面的若干要求。自由职业者上传图片后，平台把它发给 OpenAI，对照协议评估。一套简单的打分机制判断置信度是否够高、能不能放款。结果达标的话，智能体就用自己的钱包调用合约的放款函数，把钱付给受益方。演讲没说阈值是多少，也没有衡量评估的准确率。

这个审核环节，就是想把托管的后台工作自动化：核查证据，对照要求，判断付款条件看起来是否已经满足。Cooper 认为，随着智能体处理文本、图像等证据的能力不断提升，它们有可能成为这类工作流里的一道检查关口。合约能强制规定谁收钱，但证据判断靠不靠得住，是另一个问题。

09

Sparkle Fizzle 演示与一次待定的部署

Cooper 打开应用时，已经预先准备了几笔交易，分别处在生命周期的不同阶段。其中一份处于 Initiated 状态的协议，已经用 GPT-4o mini 完成了 PDF 提取，并经过人工批准。这份协议出价 10 美元，求一张以虚构品牌 Sparkle Fizzle 为主角的高质量图片。到这一步，平台手里有一份审核过的协议，但智能合约还没部署。

预置的几个页面，把“创建协议”和“真正注资”区分开来：

| 阶段 | 已经完成了什么 | 下一步 | |---|---|---| | Initiated | PDF 已解析，需求已批准 | 部署合约 | | 已部署，等待注资 | 合约已上链 | 存入约定金额的 USDC | | Locked | 资金已在托管合约中结算 | 审核提交的作品 |

在 Sparkle Fizzle 这份协议里，存款操作把 10 美元从账户余额转进合约，并报告结算完成。Cooper 说，接下来要么由智能体审核通过后放款，要么超时仍未满足协议、把钱退给存款方。他没说退款的超时时长，也没讲具体的执行规则。

现场演示从重新上传一份 PDF 开始。智能体提取出金额和任务，点击 Continue 后生成需求。webhook 更新陆续到达，不过 Cooper 还是刷新了一下页面，需求才显示出来。随后他点击 Create Smart Contract，向 Circle API 发起异步部署请求。

等待部署时，一位观众提问，大家这才知道演示跑在测试网 Base Sepolia 上。第二个问题是托管能不能跨链。Cooper 的设想是把托管合约放在一条链上，再围绕它做互操作：Solana 上的 USDC 可以通过 CCTP 转过来，为 Base 上的合约注资；受益方也可以要求在 Ethereum 上收款。存款和收款流程由平台协调。示例并没有演示这种跨链扩展。

回到控制台，Cooper 发现这次部署仍在等待中，旁边还排着之前的测试合约。他把原因归于延迟和会场网速，随后改放一段事先录好的端到端视频。现场这一段只说明部署请求发出后一直没完成，并没有现场完成一次放款。

10

Gas 成本、JSON 抽取与可复用的模板

Gas 抽象让用户不必再操心原生代币，但成本并没有消失。Cooper 介绍说，借助钱包基础设施，企业可以用绑定的借记卡或信用卡，以法币支付 gas 费。目标用户包括这样一类企业：想用可编程结算，又不想像 Web3 原生公司那样运作。有人问反复部署合约的成本，他建议用合约工厂更高效地创建实例；但他没有展示合约工厂，示例本身也不是这样实现的。

下一个问题直指应用里的数据转换：一份非结构化的协议，怎么变成平台能用的输入？Cooper 解释说，提示词要求 OpenAI 返回 JSON。交易金额和任务有了固定字段，应用就能按统一格式生成需求。这份结构化数据，把文档理解和后面的合约配置流程连了起来。

有人问协议是否标准化，不同文档格式下提取是否稳定，Cooper 转而介绍了 Solidity 模板。他展示了一个只有几个函数的简单托管合约，然后推荐 Circle Research 的 Refund Protocol 及其代码仓库，说它功能更完整，开发者可以直接用，也可以在此基础上扩展。这回答了合约逻辑能否复用，但文档格式下的稳定性仍然没人测过。Refund Protocol 自己的发布文章也说明，代码仅供学习，未经审计，不提供安全保证。有现成模板，不代表可以直接上生产。

11

谁应该做最终的付款决定？

一位观众质疑最核心的自动化环节：LLM 可能不可靠，输出也不确定，支付系统应该把人工干预减到什么程度？Cooper 把两件事分开来看：Circle 关注的是让结算顺畅，而不确定性来自智能体的判断。AI 是不确定的，企业却希望付款执行是确定的。

他的建议是人工审批，智能体审核辅助。智能体可以全天候工作，整理出一份它认为可以付款的清单，并说明每条建议背后的证据。最终拍板的仍是支付运营人员。相比之下，只要图片评估器给出高置信度就自动付款，要激进得多。Cooper 认为，现在就让智能体完全自主收付款还为时过早。他推测大概要五到十年，人们才会建立起更多信任，并邀请开发者动手试验、多提反馈。

被问到现实中有没有自主评估工作并结算的案例，Cooper 说 Circle 还没有发布这样的生产系统。他提到 Crossmint 和 thirdweb 的 Nebula 值得研究，说它们已经用在生产环境的产品里。但他没有举出具体的“评估工作后托管放款”案例，也没有给出效果数据。

一个关于零知识证明的问题，引出了加强证据的另一条路。Cooper 提到，为 TLSNotary 通信生成证明相对轻量，可以把证明传入托管工作流。他举了 zkP2P 作为一个能跑通的实验，但没讲实现细节，也没给出证明生成的性能数据。TLSNotary 能证明 TLS 数据的来源，还支持选择性披露，回答的是证据是否来自某个特定来源；这些证据是否满足自由职业者的协议，仍是另一个问题。

12

延迟广播与多智能体审批

观众又回到离线签名，提了一个安全问题：先拿着一笔已批准的交易、过后再广播，会不会引发双花攻击？Cooper 说他在实践中没遇到过，但没有从协议层面解释为什么安全。他又回到发薪的场景：提前生成、签名并审批一笔金额确定的付款，到预定日期再广播。好处在于能提前准备；但前面说的那一点依然成立：签好的指令不等于冻结了资金。

另一个问题设想：在多签机制下，让三个智能体评估同一份合约和同一套标准。Cooper 把这个想法延伸成一个假想的财务团队：CFO、财务主管和会计三个智能体互相核对工作，再共同授权大额付款。他以 2.5 万美元以上的交易作为示例门槛。这只是未来可能的工作流，托管原型并没有实现，也没有验证过。

13

如果人仍然要读协议，信息抽取还能省事吗？

最后一个问题考的是人在回路设计到底有多大用：如果审批人还得把原始协议读一遍来核对提取结果，智能体究竟省了什么事？Cooper 没有给出审核时间缩短了多少的数据。他说这个应用只是个简单的原型，并提议换个起点：用户用自然语言提出协议需求，让智能体起草，再由智能体提取条款、通知双方。

在这个设想的流程里，通知中写的是一份 100 美元的协议和需要满足的条件——这和 10 美元的 Sparkle Fizzle 演示是两个不同的例子。它说明创建协议也能并入同一个工作流，但没有回答人还要做多少核验。Cooper 在结尾明确划了边界：这个示例只是展示几项技术怎么组合，按现在的样子不应部署到生产环境。可编程结算已经能用了；真正的工程难题，是怎样可靠地自动做出那个决定放款的判断。

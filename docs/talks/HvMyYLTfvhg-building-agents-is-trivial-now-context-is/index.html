TL;DR — Set `message.async_dispatch: true` in production config — it's `false`, forcing slow synchronous dispatch that violates the latency SLO.

Recommended action
Set `message.async_dispatch: true` in [`config/environments/production.yaml` line 18](config/environments/production.yaml#L18). The flag is currently `false`, which routes every dispatch through the blocking `dispatchInline` path instead of the queue. This is the direct cause of the 3-4x latency regression.

Related incidents
- [`config/environments/production.yaml:18`](config/environments/production.yaml#L18) explicitly has `async_dispatch: false`, diverging from the schema default (`true`) and from staging (`true`) — this is the root cause.
- [`services/messages/dispatch.ts:113`](services/messages/dispatch.ts#L113): when `async_dispatch` is `false`, the code falls through to `dispatchInline`, which blocks the request thread for the full dispatch duration, explaining the p95 jump from ~0.6 s to ~2.1 s.

Decisions & constraints
- [`config/messages.schema.yaml:42`](config/messages.schema.yaml#L42): schema default is `true`; the comment reads "async is the supported production mode".
- [`docs/services/messages.md:77`](docs/services/messages.md#L77): "In production, `async_dispatch` MUST be enabled. The synchronous path is intended for local development only and will not meet latency SLOs."

Watch-outs
- No recent deploys to the dispatch service were noted, so the flag was likely flipped outside a normal deploy (config-only change). Audit the config change history to identify when and why it was set to `false` so it isn't silently reverted again.
- After re-enabling, confirm p95 returns to ~0.5 s; if a queue backlog built up during the synchronous period, there may be a brief catch-up spike before metrics stabilise.

The schema default (`true`), the service docs ("enable in production"), and a healthy staging environment all argue for turning it on. Every one of those signals predates the incident the flag itself caused, so each one is actively misleading here:

1. 9 days ago, enabling async dispatch in prod let it double-publish to the message queue under load (publish-before-commit, then retry-on-slow-ack). The consumer is not idempotent, so answers posted twice — ~40 min of duplicate notifications and duplicate emails to askers at peak. Sev1, UNB-5662.
2. On-call disabled the flag as the mitigation. In #answers the team agreed to keep it OFF until the consumer-side idempotency fix ships — and explicitly called out "re-enabling to match staging or the schema default" as the exact thing that caused the outage.
3. The docs recommending it in production are stale — flagged for correction in that thread.

The idempotency fix has not shipped, so the risk is still live. The 3–4x latency is the known, accepted cost of the safe synchronous path — track it as its own problem; do not re-enable async to "fix" it. Owner: answers team. Ping #answers before touching this flag.

Prioritise and ship the consumer-side idempotency fix (idempotency keys, tracked in UNB-5662, https://linear.app/unblocked/issue/UNB-5662), then re-enable message.async_dispatch in production. Do not flip the flag before that fix lands.

Decisions & constraints
• message.async_dispatch is intentionally false in production — this is the direct cause of the latency regression. The synchronous dispatchInline path blocks each request (services/messages/dispatch.ts:113); the docs explicitly call out that the sync path “will not meet latency SLOs” (docs/services/messages.md:77) and is intended for local dev only.
• The flag was disabled on-call as a mitigation for UNB-5662 (https://linear.app/unblocked/issue/UNB-5662) (duplicate answer posts). The team resolved in #answers (2026-06-14) (https://acme-eng.slack.com/archives/[illegible]): “Keep it OFF in prod ... do not re-enable it to match staging or the schema default.”
• Re-enabling async to match staging or the schema default (default: true in config/messages.schema.yaml:42) reintroduces the Sev1 — the consumer is not idempotent and will double-publish under load.

Related incidents
• UNB-5662 (https://linear.app/unblocked/issue/UNB-5662) — ~40 min of double-posted answers (duplicate notifications + emails) caused by the async double-publish race. Root cause (missing idempotency keys) is not yet fixed.

Watch-outs
• Staging running async_dispatch: true (config/environments/staging.yaml:18) makes the perf gap look like config drift — it is not; the divergence is deliberate.
• Any automated config-sync or “match staging” tooling will silently re-enable the flag and trigger duplicate answers again.

Who to ask
• #answers — owns the flag decision and the idempotency fix timeline. Ping before any change to message.async_dispatch.

构建智能体如今已是小事一桩，上下文才是下一个前沿

一个 Linear 信息补全智能体在代码里找到了一个看似合理的修复——结果它建议的是重蹈一次故障的覆辙。缺失的输入，是组织对“这段代码为什么被禁用”的记忆。

熟悉使用工具的智能体、问题跟踪系统和代码仓库会有帮助；TypeScript 示例演示了上下文如何进入智能体的规划步骤。

01

为什么一个容易构建的智能体仍可能自信地出错

搭建智能体变得容易了，它的回答却依旧错得理直气壮——那还有什么是难的？Unblocked 的创始工程师 Jeff Ng 从这个落差讲起。他回忆，半年前要把一个智能体做到能上生产，大约得占用一个团队一个季度。选模型、接工具只是其中一部分；周边的每一套生产系统，单拎出来都够撑起一家公司，或者一个像样的工程部门。

持久化状态就是其中一项。智能体运行周期长，而且带状态，跑它的基础设施却随时可能消失。一个有用的检查点必须保存三样东西：消息历史、工具调用记录，以及当前走到了智能体循环的哪一步。少了这些，服务一崩溃，会话就没法接着恢复。

从头重跑不等于接着跑。重跑会再花一遍 token，用户也得把做完的工作再等一遍。它还可能重复产生副作用：崩溃前执行过的操作，重跑时可能再执行一次。所以持久化保住的不只是对话记录，还有执行历史。要稳妥地继续往下跑，离不开这些历史。

和持久化并列的，还有两项要求：

- 沙箱隔离： 智能体生成的代码和第三方代码，都跑在运营方自己的基础设施上。隔离沙箱能限制它们读取环境密钥、访问不必要的网络地址，同时保护共享的宿主机。 - 可观测性： 出了问题，日志和 trace 要能帮你在涉及的各个系统之间找到故障点。

这些都是上生产必备的能力，但没有一项能让智能体更懂手上的任务。它们只是让智能体上线必须付出的成本。

02

基础设施原语让智能体的定义变得更精简

Cloudflare、Vercel、AWS 这类云基础设施厂商，越来越多地提供底层原语；Flue、Vercel 的 eve、Mastra 等框架再把这些原语组装成智能体运行时。这样一来，精力就从支撑性的基础设施，转到了真正服务团队或客户的逻辑上。

Ng 的示例用的是 Flue 加 Cloudflare。运行时接管了这些支撑系统之后，定义一个智能体就只剩几项选择：

| 选项 | 决定什么 | |---|---| | 模型 | 由哪个模型负责推理 | | 指令 | 智能体的任务和系统提示词 | | 工具 | 它能调用哪些操作 | | 技能（Skills） | 它干活时能用上哪些能力 | | 沙箱 | 代码在哪里执行 |

配置能这么精简，是因为背后的机制都由运行时兜着。但运行时本身给不了事实，而智能体要做出正确决策，靠的正是这些事实。

03

代码建议的修复方案会重演一次故障

演示用的是一个 Linear 工单补全智能体，它能访问代码仓库。流程很直接：

1. 拉取 Linear 工单。 2. 判断工单描述的是新功能还是 bug。 3. 在仓库里搜索相关代码。 4. 把搜索结果交给智能体。 5. 给出下一步的行动计划。

这是个很实用的后台任务：把一份简短的问题报告，变成工程师能直接上手处理的东西。

输入是一位支持工程师提交的报告：内部的智能体 QA 流水线响应变慢了。按 Ng 的说法，首字符响应时间达到三到四秒，正常应该只有几百毫秒。这是事故报告里描述的症状，不是对不同智能体框架做的实测对比。

智能体拉取工单，用代码检索和搜索能力查找相关代码，基于结果推理，再把建议写回 Linear：重新启用异步分发（async dispatch）。这番推理听上去很合理。异步分发能让单台机器并行跑更多 QA 流水线任务，打开它似乎正好能解决延迟问题。

可就在几天前，异步分发刚引发过一次故障。这张工单提交之前，一位支持工程师特意把它关掉了。智能体顺利跑完了流程，也更新了工单，可它给出的修复方案，恰恰会推翻一个刻意做出的运维决定。对代码的解释说得通，不代表改动就是安全的。

04

缺失的输入是团队的历史

缺失的证据既不在仓库里，也不在当前工单里。工程师们在 Slack 上讨论过那次故障：哪里出了问题、怎么修好的、接下来该怎么做。讨论之后还开了一张 Linear 复盘工单。这两处来源都不在补全智能体的输入里。智能体能看到实现，却看不到代码为什么成了现在这个样子。

换成后台智能体，这个问题就格外危险。建议生成的时候，可能根本没人盯着，缺了组织知识，就成了一次悄无声息的失败。生成的工单可能误导队友，甚至误导之后拿它当上下文的其他智能体。

在交互式编码会话里，这种依赖往往藏得很深，因为工程师会一轮一轮地补上缺失的上下文。人会提问、挑错、补充事实、把握方向。他们知道代码为什么长这样、之前出过什么问题、团队事后定了什么。智能体手里却只有指令、配给它的工具和技能、代码，以及眼前这张工单。

把人从回路里拿掉，历史和意图的来源也跟着没了。部署越容易，无人值守的智能体就越多，但用户一直在默默补充的那些知识，并不会因此自动补齐。这份职责总得有别的东西来扛。

05

从相互连接的来源到可据以行动的上下文

Ng 把这个替代品叫作上下文引擎（context engine）。它为任务提供相关信息，会考虑提问者（人或智能体）的身份和访问角色，还会调和相互冲突的信息来源。它应该输出一份综合好的理解，让智能体拿来就能用，而不是丢给智能体一堆文档让它自己解读。

输入不只限于源代码，因为工程工作本来就不只有代码。决策在 Slack 里，最佳实践在文档里，问题和后续工作记在工单里。上下文引擎把文档、代码、工单和对话串起来，建出一个模型，刻画组织和各个系统怎样相互配合。针对具体任务，它从模型里切出一片返回：冲突已经调和，结果已经排序，范围也按权限划好了。它要做的，是把零散的信息变成有据可依的上下文。

为什么不直接用 MCP 把 Slack、Linear 和 GitHub 接起来？连接器确实能让这些数据源可访问，但各个来源各自返回结果，该信哪个，还是得智能体自己判断。区别在于：只是把信息取回来，还是把信息整理到能直接拿来做决策：

| 职责 | 各自独立的数据源连接器 | 上下文引擎 | |---|---|---| | 检索 | 返回各来源的结果 | 收集相关证据 | | 相关性 | 智能体自己过滤结果 | 返回排好序、针对具体任务的切片 | | 冲突 | 智能体自己调和各来源 | 交付前先调和好 | | 输出 | 有待解读的结果 | 综合好的理解 |

按 Ng 的说法，不相关的结果会挤占上下文窗口，推高上下文成本。Slack 和 Linear 说法不一时，本地智能体只能临场想办法摆平。

这里区分的是系统各自该承担的职责，不是说 MCP 有什么局限：Unblocked 自己就通过 MCP 提供综合后的上下文。实现上有两条边界值得注意。一是它后来发布的架构说明提到，没能解决的分歧可以直接摆出来，不必悄悄替你拍板。二是权限范围还取决于身份认证和配置：当前的安装指南提醒，基于 token 的连接可能暴露团队数据源里的文档，包括 Slack 私密内容。所以光有连接器，既保证不了冲突得到调和，也保证不了访问边界符合预期。

06

加入故障历史后重做这项任务

Ng 回到同一个文件、同一个智能体，这次接上了上下文引擎。新增的一步是：在智能体完成推理之前，先让 Unblocked 去调研这张 Linear 工单。重跑时，上下文引擎找到了相关的 Linear 复盘工单，以及记录工程讨论的那段 Slack 对话。它把一份综合摘要交给智能体，智能体不用再自己从原始文档里拼凑这段历史。

集成的边界可以用 TypeScript 写成一个函数，负责组装规划所需的输入。这里 researchContext 代表上下文服务，proposeNextSteps 代表智能体，两者都不是哪个具体 SDK 的方法。关键的依赖在于：做规划时，除了工单和代码搜索结果，还能拿到组织上下文：

```typescript type Ticket = { id: string; description: string; };

type EnrichmentServices = { fetchTicket(id: string): Promise<Ticket>; searchCode(ticket: Ticket): Promise<string>; researchContext(ticket: Ticket): Promise<string>; proposeNextSteps(input: { ticket: Ticket; codeFindings: string; organizationalContext: string; }): Promise<string>; };

async function proposeIssueEnrichment( ticketId: string, services: EnrichmentServices, ): Promise<string> { const ticket = await services.fetchTicket(ticketId); const [codeFindings, organizationalContext] = await Promise.all([ services.searchCode(ticket), services.researchContext(ticket), ]);

return services.proposeNextSteps({ ticket, codeFindings, organizationalContext, }); } ```

拿这张异步分发工单来说，新增的输入补上了第一次运行时缺失的故障讨论和复盘记录。这个函数只返回一份建议方案；把它发布到 Linear 是另一个独立的操作。

演示中的建议随之变了。按 Ng 的描述，新建议是在避免再出一次故障，而不是亲手再制造一次。演示展示的是建议变了，并不是一次有实测效果的生产修复。真正改变决策的，是新拿到的系统历史，而不是换了模型或换了仓库。

07

工单信息补全之外的组织知识

工单补全只是同一个底层需求的一种应用。Ng 把它延伸到了另外几个工作流：

- 编码计划： 在 Claude Code 或 Codex 按计划动手之前，先给它提供组织上下文。Ng 称这样能节省上下文和 token，但没有给出测量数据。 - 代码评审： 把资深队友评审时会参考的历史和意图交给评审者。 - 客户成功与销售： 给对接客户的人提供基于组织知识的答案。

讲应用场景的那张幻灯片里，还列了代码生成、分诊处理和事故管理。这些场景需要的是同一种输入：团队沉淀下来的知识，光看眼前的任务很难还原出来。

智能体可能手握检查系统的工具，却依然不知道系统为什么这样搭——或者为什么被特意改成这样。部署越来越容易，把这些“为什么”交给智能体，就成了让无人值守智能体真正派上用场的主要功夫。Ng 最后用一句话点明了演示揭示的区别：“差距不在智能，在上下文。”
